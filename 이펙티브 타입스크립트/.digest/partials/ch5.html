ITEM 38

any 타입은 가능한 한 좁은 범위에서만 사용하기

any 를 쓸 수밖에 없다면, 퍼지는 반경을 최소로 만든다.

핵심 const x: any 는 변수가 사는 내내 any 이고, x as any 는 그 줄에서만 any 다. 후자를 쓴다.

변수를 any 로 만들지 말고, 표현식을 단언한다

scope.ts 원래 오류 
interface Foo { foo: string; }
interface Bar { bar: string; }

declare function expressionReturningFoo(): Foo;
declare function processBar(b: Bar): void;

function f() {
  const x = expressionReturningFoo();
  processBar(x);
  //         ~ 'Foo' 형식의 인수는 'Bar' 형식의 매개 변수에
  //           할당될 수 없습니다.
}
해법 1 범위가 넓다 
function f1() {
  const x: any = expressionReturningFoo();
  processBar(x);
  return x;  // 이 함수를 쓰는 모든 곳이
             // any 로 오염된다
}

const value = f1(); // any
해법 2 한 줄에 갇힌다 
function f2() {
  const x = expressionReturningFoo(); // Foo
  processBar(x as any);
  return x;  // 여전히 Foo
}

const value = f2(); // Foo
i

반환 타입을 적으면 방어벽이 하나 더 생긴다

함수 반환 타입을 명시하면(아이템 19) 내부에서 any 를 쓰더라도 바깥으로 새어 나가지 않는다. 함수가 any 의 격리 경계가 되는 셈이다.

객체는 통째로 단언하지 말고 문제되는 속성만

    key: value,

좋음 key 만 꺼진다

  b: 2,

@ts-expect-error 가 더 낫다 TS 3.9+

@ts-ignore 는 오류가 사라져도 조용하다. 코드를 고쳐 오류가 없어져도 주석이 그대로 남아, 나중에 진짜 오류가 생기면 그것까지 삼킨다.

@ts-expect-error 는 오류가 없으면 그 자체가 오류다. "여기 오류가 있을 것"이라고 선언하는 것이므로, 문제가 해결되면 컴파일러가 "이제 이 주석을 지우라"고 알려 준다.

// ~~~~~~~~~~~~~~~~~ 처리되지 않은 '@ts-expect-error' 지시어입니다.

둘 다 이유를 주석으로 남기는 것이 전제다. 이유 없는 억제는 언젠가 반드시 문제가 된다.

정리

  • 의도치 않은 타입 안전성 손실을 피하기 위해 any 의 사용 범위를 최소한으로 좁힌다.
  • 함수의 반환 타입이 any 인 경우 타입 안전성이 전염된다. 반환 타입을 명시해 막는다.
  • 강제로 타입 오류를 제거해야 한다면 @ts-expect-error 를 이유와 함께 쓴다.
ITEM 39

any를 구체적으로 변형해서 사용하기

any 를 써야 한다면 더 구체적인 any 가 없는지 본다. 조금만 좁혀도 얻는 게 많다.

핵심 any 대신 any[], Record<string, any>, (...args: any[]) => any 처럼 형태만이라도 알려 준다.

배열이라는 것만 알려도

any 아무 검사도 없다 
function getLengthBad(arr: any) {
  return arr.length; // any
}

getLengthBad(/123/); // 통과. 결과는 undefined
any[] 셋을 얻는다 
function getLengthGood(arr: any[]) {
  return arr.length; // number
}

getLengthGood(/123/);
//            ~~~~~ 'RegExp' 형식의 인수는
//            'any[]' 형식의 매개 변수에
//            할당될 수 없습니다.
  1. 함수 안에서 arr.length 가 실제로 검사된다.
  2. 반환 타입이 any 가 아니라 number 로 추론된다.
  3. 호출할 때 배열인지 확인한다.

객체일 때 — 세 단계의 선택지

      return true;
    }

function hasTwelveLetterKey2(o: object) {

    if (key.length === 12) {

      //                      사용할 수 없으므로 요소에 암시적으로

object 는 키는 열거할 수 있지만 값에는 접근할 수 없다. 값이 필요 없다면 object 가 {[key: string]: any} 보다 안전하다.

함수 타입도 세 단계로 구체화한다

type Fn1 = (arg: any) => any;      // 매개변수 1개
type FnN = (...args: any[]) => any; // 매개변수 개수 무관 (= Function)

const numArgsBad = (...args: any) => args.length;    // any 를 반환

!

Function 타입은 피한다 보강

Function 은 어떤 함수든 받고, 호출하면 any 를 반환하며, 매개변수 검사도 하지 않는다. typescript-eslint 의 no-unsafe-function-type 규칙이 이걸 경고한다. (...args: any[]) => any 로 쓰거나, 가능하면 실제 시그니처를 적는다.

정리

  • any 를 쓸 때는 정말로 모든 값이 허용되어야 하는지 다시 생각한다.
  • any[], {[id: string]: any}, () => any 처럼 더 구체적인 형태를 쓴다.
  • 키만 필요하면 object, 아무것도 모르면 unknown 을 고려한다.
ITEM 40

함수 안으로 타입 단언문 감추기

단언을 아예 안 쓸 수는 없다. 대신 정확한 시그니처를 가진 함수 안에 가둔다.

핵심 함수 바깥으로 드러나는 타입은 정확하게, 내부 구현은 필요하면 단언을 쓴다. 단언이 코드 여기저기 흩어지는 것보다 훨씬 낫다.

예 1 — 마지막 호출을 캐싱하는 래퍼

cache.ts 타입 체커가 T 와 연결짓지 못한다 
declare function shallowEqual(a: any, b: any): boolean;

function cacheLast<T extends Function>(fn: T): T {
  let lastArgs: any[] | null = null;
  let lastResult: any;

  return function (...args: any[]) {
  //     ~~~~~~~~~~~~~~~~~~~~~~~~ '(...args: any[]) => any' 형식은
  //                              'T' 형식에 할당할 수 없습니다.
    if (!lastArgs || !shallowEqual(lastArgs, args)) {
      lastResult = fn(...args);
      lastArgs = args;
    }
    return lastResult;
  };
}

사람이 보기에는 명백하다. 반환하는 함수는 fn 과 같은 매개변수로 호출되고 같은 값을 돌려준다. 타입 체커는 그걸 증명할 수 없을 뿐이다.

cache.ts 단언은 안에, 시그니처는 정확하게 
function cacheLast<T extends Function>(fn: T): T {
  let lastArgs: any[] | null = null;
  let lastResult: any;

  return function (...args: any[]) {
    if (!lastArgs || !shallowEqual(lastArgs, args)) {
      lastResult = fn(...args);
      lastArgs = args;
    }
    return lastResult;
  } as unknown as T;
}

단언은 함수 안에 한 번 있고, cacheLast 를 쓰는 쪽에서는 T 를 그대로 받는다. 호출자는 단언의 존재조차 모른다.

예 2 — 얕은 객체 비교

equal.ts 인덱스 접근이 막힌다 
function shallowObjectEqual<T extends object>(a: T, b: T): boolean {
  for (const [k, aVal] of Object.entries(a)) {
    if (!(k in b) || aVal !== b[k]) {
      //                      ~~~~ 'string' 형식의 식을 '{}' 인덱스
      //                           형식에 사용할 수 없으므로 ...
      return false;
    }
  }
  return Object.keys(a).length === Object.keys(b).length;
}
equal.ts 검증한 뒤의 단언 
function shallowObjectEqual<T extends object>(a: T, b: T): boolean {
  for (const [k, aVal] of Object.entries(a)) {
    if (!(k in b) || aVal !== (b as any)[k]) {
      return false;
    }
  }
  return Object.keys(a).length === Object.keys(b).length;
}
✓

이 단언이 안전한 이유

k in b 를 바로 앞에서 확인했다. 단축 평가 덕분에 (b as any)[k] 는 k 가 b 에 있을 때만 실행된다. 타입스크립트가 in 검사 결과를 인덱스 접근까지 이어 주지 못할 뿐, 논리적으로는 증명되어 있다.

단언을 쓸 때 스스로에게 물어야 할 질문이 바로 이것이다. "내가 타입 체커보다 더 아는 근거가 코드에 있는가?"

정리

  • 타입 선언문은 일반적으로 타입을 위험하게 만들지만, 상황에 따라 필요하고 현실적이다.
  • 불가피하게 사용해야 한다면 정확한 정의를 가지는 함수 안으로 숨긴다.
  • 단언 옆에는 왜 안전한지에 대한 근거가 있어야 한다.
ITEM 41

any의 진화를 이해하기

일반적으로 변수의 타입은 선언할 때 결정된다. 암시적 any 만은 예외다.

핵심 const x = [] 처럼 암시적으로 any 가 된 변수는 값을 할당할 때마다 타입이 진화한다. : any 를 명시하면 진화하지 않는다.

진화 1 — 분기마다 다른 타입

evolve.ts 
let val;              // any

if (Math.random() < 0.5) {
  val = /hello/;
  val;                // RegExp
} else {
  val = 12;
  val;                // number
}

val;                  // RegExp | number

진화 2 — 배열

evolve.ts 
const result = [];    // any[]
result.push(1);
result;               // number[]
result.push("hello");
result;               // (string | number)[]
i

이건 유니온이 아니라 진화다

일반적인 타입 좁히기와 다르다. 좁히기는 선언된 타입 안에서 범위를 줄이는 것이고, 진화는 타입 자체가 넓어지는 것이다. 진화하는 any 는 오직 noImplicitAny 가 켜진 상태에서 암시적 any 로 시작한 변수에만 일어난다.

진화하지 않는 경우

no-evolve.ts 함수 호출을 거치면 멈춘다 
function range(start: number, limit: number) {
  const out = [];
  for (let i = start; i < limit; i++) {
    out.push(i);
  }
  return out;         // number[] — 정상적으로 진화했다
}

function makeSquares(start: number, limit: number) {
  const out = [];
  //    ~~~ 'out' 변수는 형식을 확인할 수 없는 경우
  //        암시적으로 'any[]' 형식입니다.
  range(start, limit).forEach((i) => {
    out.push(i * i);  // 콜백 안에서의 push 는 진화를 일으키지 못한다
  });
  return out;
  //     ~~~ 'out' 변수에는 암시적으로 'any[]' 형식이 포함됩니다.
}
×

왜 콜백 안에서는 안 되나

진화는 같은 스코프의 제어 흐름을 따라 일어난다. 콜백은 언제 실행될지 알 수 없으므로 타입스크립트가 순서를 보장할 수 없다. 그래서 진화를 포기한다.

또 하나 — 진화하는 any 는 값을 할당할 때만 진화한다. 할당 전에 읽으면 그대로 오류다.

explicit.ts 그냥 타입을 적는다 
function makeSquares(start: number, limit: number): number[] {
  const out: number[] = [];
  range(start, limit).forEach((i) => {
    out.push(i * i);
  });
  return out;
}

// 더 나은 방법 — 애초에 만들지 않는다 (아이템 27)
function makeSquares2(start: number, limit: number): number[] {
  return range(start, limit).map((i) => i * i);
}

정리

  • 일반적인 타입은 정제되기만 하지만, 암시적 any 와 any[] 는 진화한다.
  • 이 동작을 알아 두되 의존하지는 않는다. 오류 없이 진화하는 코드는 읽는 사람에게 혼란스럽다.
  • 진화를 기대하기보다 명시적 타입 구문을 쓰는 것이 안전하고 명확하다.
ITEM 42

모르는 타입의 값에는 any 대신 unknown 사용하기

unknown 은 "아직 모른다"를 정직하게 표현하는 타입이다. any 는 "신경 쓰지 마"라고 말한다.

핵심 unknown 은 어떤 값이든 받지만, 확인하기 전에는 아무것도 못 하게 만든다. 이 비대칭이 핵심이다.

세 타입의 위치

딱 한 칸이 다르다 — unknown 은 나가는 방향을 막았고, any 는 양방향으로 열려 있다. 그 한 칸이 타입 안전성의 전부다. (never 는 정반대로, 어떤 값도 들어갈 수 없지만 어디로든 나갈 수 있다.)

YAML 파서 — any 버전의 문제

yaml.ts 조용히 통과한다 
function parseYAML(yaml: string): any { /* ... */ }

interface Book { title: string; author: string; }

const book: Book = parseYAML(`
  name: Wuthering Heights
  author: Emily Brontë
`);
// title 이 아니라 name 을 넣었는데도 오류가 없다
console.log(book.title.toUpperCase()); // 런타임: undefined 접근
yaml.ts unknown 이면 확인을 강제한다 
function parseYAML(yaml: string): unknown { /* ... */ }

const book1 = parseYAML("...");
console.log(book1.title);
//          ~~~~~ 'book1'은(는) 'unknown' 형식입니다.

// 방법 1 — 단언 (책임은 개발자에게)
const book2 = parseYAML("...") as Book;
console.log(book2.title); // 정상

방법 2 — 타입 가드로 좁히기

yaml.ts 런타임 검증까지 함께 
function isBook(obj: unknown): obj is Book {
  return (
    typeof obj === "object" &&
    obj !== null &&
    "title" in obj &&
    "author" in obj
  );
}

const book = parseYAML("...");
if (isBook(book)) {
  console.log(book.title);  // Book 으로 좁혀졌다
  console.log(book.author);
}
!

원문 교정 원문 교정

원문 노트의 isBook 은 "name" in obj 를 검사하고 있었다. Book 인터페이스에는 name 이 없으므로 항상 false 가 되어 타입 가드가 무의미해진다. "title" in obj 가 맞다.

덧붙이면, obj !== null 검사가 반드시 앞에 와야 한다. typeof null === "object" 이기 때문이다(아이템 22).

방법 3 — 제네릭 (권장하지 않음)

yaml.ts 단언을 예쁘게 포장한 것뿐 
function parseYAML<T>(yaml: string): T {
  return {} as T;   // 결국 안에서 단언한다
}

const book = parseYAML<Book>("...");
!

기능은 같지만 정직하지 않다

제네릭 버전은 안전해 보이지만 실제로는 단언과 똑같다. 런타임 검증은 어디에도 없다. 차라리 unknown 을 반환하고 호출자가 명시적으로 단언하거나 검증하게 하는 편이 위험이 눈에 보인다.

비슷하지만 다른 타입들

타입포함하는 값비고
unknown모든 값가장 넓다. 기본 선택지
{}null, undefined 를 제외한 모든 값unknown 보다 아주 조금 좁다
object모든 비기본형 — 객체와 배열true, 12, "foo" 는 제외

catch 절의 e TS 4.4+

useUnknownInCatchVariables(strict 에 포함)가 켜지면 catch (e) 의 e 가 any 가 아니라 unknown 이 된다. 자바스크립트는 무엇이든 던질 수 있으므로 이게 정직한 타입이다.

catch.ts 
try {
  // ...
} catch (e) {
  e.message;
  // ~ 'e'은(는) 'unknown' 형식입니다.

  if (e instanceof Error) {
    console.error(e.message); // 정상
  } else {
    console.error(String(e));
  }
}

정리

  • unknown 은 any 대신 쓸 수 있는 안전한 타입이다. 어떤 값이 있지만 그 타입을 모를 때 쓴다.
  • 사용자가 타입 단언문이나 타입 검사를 하도록 강제하려면 unknown 을 쓴다.
  • {}, object, unknown 의 차이를 알아 둔다.
ITEM 43

몽키 패치보다는 안전한 타입을 사용하기

자바스크립트는 아무 객체에나 속성을 붙일 수 있다. 붙일 수 있다고 붙여도 되는 건 아니다.

핵심 전역 객체를 확장해야 한다면 declare global 로 선언하거나, 확장한 타입으로 단언한다. as any 는 마지막 선택지다.

왜 몽키 패치가 문제인가

  • 타입스크립트가 추가된 속성을 알지 못한다.
  • 전역으로 동작하므로 모듈 사이에 숨은 의존성이 생긴다. 실행 순서에 따라 있을 수도 없을 수도 있다.
  • 부수 효과의 범위를 추적하기 어렵다.
monkey.ts 오류가 두 번 난다 
document.monkey = "Tamarin";
//       ~~~~~~ 'Document' 형식에 'monkey' 속성이 없습니다.

(document as any).monkey = "Tamarin"; // 통과하지만
console.log(document.monkey);
//                   ~~~~~~ 'Document' 형식에 'monkey' 속성이 없습니다.
//                          단언이 저장되지 않는다

해법 1 — 타입 보강 (declaration merging)

global.d.ts 타입이 프로젝트 전체에 반영된다 
export {}; // 이 파일을 모듈로 만든다

declare global {
  interface Document {
    /** 몽키 패치 속. 원숭이 이름 */
    monkey: string;
  }
}

document.monkey = "Tamarin"; // 정상, 자동완성도 된다
장점단점
any 보다 안전하다모듈 전 영역에 적용된다
자동완성과 문서(TSDoc)가 붙는다코드 실행 시점의 시간 순서는 표현하지 못한다
몽키 패치가 어디에 쓰였는지 추적된다페이지 로드 중에는 undefined 인데 타입은 string 이다
i

시간 문제를 타입으로 표현하려면

monkey: string | undefined 로 선언하면 정직해지지만, 쓸 때마다 검사해야 해서 번거로워진다. 이 트레이드오프 자체가 몽키 패치가 나쁜 설계라는 증거다.

해법 2 — 구체적인 타입 단언

monkey.ts 영향 범위가 좁다 
interface MonkeyDocument extends Document {
  /** 몽키 패치 속. 원숭이 이름 */
  monkey: string;
}

(document as MonkeyDocument).monkey = "Macaque";

Document 자체를 건드리지 않으므로 모듈 영역 문제가 없다. 몽키 패치가 일어나는 곳에서만 MonkeyDocument 를 임포트하면 되고, 단언이 as any 보다 훨씬 구체적이다.

i

Window 를 확장하는 실전 예 보강

분석 스크립트나 개발용 디버깅 훅처럼 window 에 무언가를 붙여야 할 때가 실제로 있다.

window.d.ts 
export {};

declare global {
  interface Window {
    dataLayer?: unknown[];
    __APP_DEBUG__?: { store: unknown; version: string };
  }
}

선택적 속성(?)으로 선언하는 것이 요령이다. 존재 여부가 실행 시점에 달려 있다는 사실을 타입이 정직하게 말해 준다.

정리

  • 전역 변수나 DOM 에 데이터를 저장하지 말고 데이터를 분리해서 사용하는 것이 가장 좋다.
  • 내장 타입에 데이터를 저장해야 한다면 안전한 타입 접근법(보강 또는 사용자 정의 인터페이스 단언)을 쓴다.
  • 보강의 모듈 영역 문제를 이해해야 한다.
ITEM 44

타입 커버리지를 추적하여 타입 안전성 유지하기

noImplicitAny 를 켜도 any 는 남는다. 얼마나 남았는지 측정하지 않으면 관리할 수 없다.

핵심 any 는 수치로 추적할 수 있다. type-coverage 로 측정하고, 임계값을 CI 에 걸어 되돌아가지 않게 만든다.

noImplicitAny 를 켜도 남는 두 종류

종류예대응
명시적 anyany[], {[k: string]: any}, as any내 코드다. 하나씩 줄인다 (아이템 39)
서드파티 타입 선언@types 가 반환하는 any추적이 어렵다. 감싸거나 PR 을 보낸다

두 번째가 특히 성가시다. @types 에서 흘러나온 any 는 noImplicitAny 오류를 내지 않으면서 내 코드로 조용히 퍼진다.

측정하기

terminal 
$ npx type-coverage
(1 / 5) 20.00%
type-coverage success.

$ npx type-coverage --detail
src/app.ts:1:14: a
src/app.ts:1:22: b
src/app.ts:2:10: a
src/app.ts:2:14: b
(1 / 5) 20.00%

--detail 이 어떤 식별자가 any 인지 위치까지 알려 준다. 이 목록이 곧 개선 작업 목록이 된다.

i

CI 에 걸어 두기 보강

package.json 
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "type-coverage": "type-coverage --at-least 95 --strict --ignore-catch"
  }
}
  • --at-least 95 — 커버리지가 95% 미만이면 0 이 아닌 종료 코드로 실패한다
  • --strict — any[] 같은 것도 엄격하게 센다
  • --detail — 실패한 위치를 출력

핵심은 수치를 100% 로 만드는 것이 아니라 후퇴를 막는 것이다. 임계값을 현재 수치보다 조금 낮게 잡고, 개선될 때마다 올린다. 아이템 62의 점진적 마이그레이션과 같은 전략이다.

!

any 를 찾아서 무엇을 할 것인가

발견한 any 마다 이유가 다르다.

  • 마이그레이션 잔재 → 이제 타입을 붙일 수 있다
  • @types 가 부실함 → 미러 타입으로 감싸거나(아이템 51) DefinitelyTyped 에 PR 을 보낸다
  • 당시엔 표현할 수 없었던 타입 → 타입스크립트가 그동안 발전했다. 지금은 될 수 있다

정리

  • noImplicitAny 가 설정되어 있어도 명시적 any 와 서드파티 선언의 any 는 여전히 존재한다.
  • 작성한 프로그램의 타입이 얼마나 잘 선언되었는지 추적해야 한다.
  • 추적함으로써 any 의 사용을 줄여 가고, 타입 안전성을 점진적으로 높일 수 있다.
