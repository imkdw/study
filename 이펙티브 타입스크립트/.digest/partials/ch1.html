ITEM 1

타입스크립트와 자바스크립트의 관계 이해하기

타입스크립트는 자바스크립트의 상위집합이다. 다만 "상위집합"이라는 말은 문법에 대한 이야기이고, 타입 체커를 통과하는 것은 또 다른 문제다.

핵심 모든 자바스크립트는 타입스크립트지만, 모든 타입스크립트가 자바스크립트인 것은 아니다. 그리고 둘 중 어느 쪽도 타입 체크를 통과한다는 보장은 아니다.

상위집합이라는 말의 뜻

  • 타입스크립트는 작성된 코드를 파싱해 자바스크립트로 변환할 수 있다.
  • 자바스크립트는 .js / .jsx, 타입스크립트는 .ts / .tsx 확장자를 쓴다.
  • 확장자만 .ts로 바꿔도 기존 .js 파일은 그대로 유효하다. 마이그레이션이 점진적으로 가능한 이유가 여기에 있다.
  • 반대로 타입스크립트에는 자바스크립트에 없는 고유 문법이 있어서, .ts 파일을 그대로 자바스크립트 엔진에 넘길 수는 없다.
두 원은 다른 질문에 답한다 — 왼쪽은 "자바스크립트로도 유효한가", 오른쪽은 "타입 오류가 없는가". 겹치는 영역이 타입 구문 없이도 타입 체크를 통과하는 코드다.

예시 1 — 타입 구문을 쓰는 순간 자바스크립트가 아니게 된다

app.ts 
function greeting(who: string) {
  console.log("Hello", who);
}

문법상 유효한 타입스크립트다. 하지만 이 파일을 자바스크립트 엔진에 그대로 넘기면 실패한다.

×

node app.ts

SyntaxError: Unexpected token :

: string 은 자바스크립트에 없는 문법이다. 이 한 글자를 적는 순간 코드는 타입스크립트의 영역으로 넘어간다.

↑

지금은 node app.ts 가 동작한다 최신 반영

Node.js 는 22.6 에서 --experimental-strip-types 를 도입했고, 22.18 과 23.6 부터는 플래그 없이 기본 활성화되어 node app.ts 가 그냥 실행된다.

다만 이건 타입 주석을 공백으로 지우는 것뿐이다. 타입 체크는 전혀 하지 않고, tsconfig.json 도 읽지 않으며, enum·네임스페이스처럼 코드 생성이 필요한 문법은 별도 플래그(--experimental-transform-types)를 요구한다. 오히려 아이템 3이 말하는 "코드 생성과 타입 체크는 별개"를 런타임이 직접 증명해 준 셈이다.

예시 2 — 타입 구문이 없어도 타입 체커는 일한다

app.js 런타임에 터짐 
let city = "new york city";
console.log(city.toUppercase());
app.ts 미리 잡힘 
let city = "new york city";
console.log(city.toUppercase());
//                ~~~~~~~~~~~
// 'toUppercase' 속성이 'string' 형식에 없습니다.
// 'toUpperCase'을(를) 사용하시겠습니까?

두 파일의 내용은 완전히 같다. 그런데도 왼쪽은 실행해야 TypeError: city.toUppercase is not a function 을 만나고, 오른쪽은 편집기에서 즉시 잡힌다. : string 같은 타입 명세가 하나도 없는데 가능한 이유는 타입스크립트가 초기값으로부터 타입을 추론하기 때문이다.

✓

타입 시스템의 목표

런타임에 발생할 오류를 미리 찾아내는 것. 정확히 이 한 가지다.

예시 3 — 그렇다고 모든 오류를 잡아주지는 않는다

실행은 잘 되지만 의도와 다르게 동작하는 코드가 있다.

app.js 
const states = [
  { name: "Alabama", capital: "Montgomery" },
  { name: "Alaska",  capital: "Juneau" },
  { name: "Arizona", capital: "Phoenix" },
];

for (const state of states) {
  console.log(state.capitol);
}
// undefined
// undefined
// undefined

capitol(국회의사당)과 capital(수도)의 혼동이다. 에러 없이 undefined 세 줄만 남는다. 타입스크립트는 추가 타입 구문 없이도 이걸 잡아낸다.

app.ts 
for (const state of states) {
  console.log(state.capitol);
  //                ~~~~~~~
  // 'capitol' 속성이 형식에 없습니다. 'capital'을(를) 사용하시겠습니까?
}

그런데 오타가 배열 쪽에 있었다면? 이번엔 타입스크립트가 반대로 지적한다.

app.ts 어느 쪽이 오타인지 알 수 없다 
const states = [
  { name: "Alabama", capitol: "Montgomery" },
  { name: "Alaska",  capitol: "Juneau" },
  { name: "Arizona", capitol: "Phoenix" },
];

for (const state of states) {
  console.log(state.capital);
  //                ~~~~~~~
  // 'capital' 속성이 형식에 없습니다. 'capitol'을(를) 사용하시겠습니까?
}

타입스크립트 입장에서는 둘 다 "선언된 적 없는 속성"일 뿐, 어느 쪽이 오타인지 판단할 근거가 없다. 의도를 명시적으로 알려주면 해결된다.

app.ts 의도를 타입으로 고정 
interface State {
  name: string;
  capital: string;
}

const states: State[] = [
  { name: "Alabama", capital: "Montgomery" },
  { name: "Alaska",  capitol: "Juneau" },
  //                 ~~~~~~~~~~~~~~~~~
  // 개체 리터럴은 알려진 속성만 지정할 수 있지만 'State' 형식에 'capitol'이(가) 없습니다.
  // 'capital'을(를) 쓰려고 했습니까?
  { name: "Arizona", capital: "Phoenix" },
];
i

함께 알아두기 보강

마지막 오류 메시지가 앞의 두 개와 다르다는 점에 주목할 만하다. 이건 잉여 속성 체크라는 별개의 규칙이 작동한 결과다. 객체 리터럴을 타입이 명시된 자리에 직접 대입할 때만 켜진다. 자세한 동작과 그 한계는 아이템 11에서 다룬다.

타입 시스템은 자바스크립트의 런타임 동작을 모델링한다

app.ts 오류 없음 
const x = 2 + "3";  // "23", 타입은 string
const y = "2" + 3;  // "23", 타입은 string

다른 언어라면 컴파일 에러가 났을 코드지만 타입스크립트는 통과시킨다. 자바스크립트 런타임이 실제로 그렇게 동작하기 때문이다. 타입 시스템은 자바스크립트의 실제 동작을 흉내 내도록 설계되어 있다.

반대로, 정상 동작하는 코드에 오류를 표시하기도 한다.

app.ts JS 에선 되지만 TS 는 막는다 
const a = null + 7;
//        ~~~~ '+' 연산자를 'null' 형식에 적용할 수 없습니다.
const b = [] + 12;
//        ~~~~~~~ '+' 연산자를 '[]'와 'number' 형식에 적용할 수 없습니다.
alert("Hello", "TypeScript");
//             ~~~~~~~~~~~~ 1개의 인수가 필요한데 2개를 가져왔습니다.
!

모델링은 근사치다

자바스크립트에서 위 세 줄은 각각 7, "12" 를 만들고 alert 는 두 번째 인수를 조용히 무시한다. 즉 실행은 된다. 그럼에도 타입스크립트가 막는 이유는 이런 코드가 거의 언제나 실수이기 때문이다. 타입 시스템의 규칙은 "런타임 동작"과 "작성자의 의도" 사이 어딘가에서 균형을 잡고 있다.

원문 노트는 [] + 12 의 결과를 12 로 적었는데, 실제로는 문자열 "12" 다. [] 가 빈 문자열로 변환된 뒤 문자열 연결이 일어난다. 원문 교정

타입 체커를 통과해도 런타임 오류는 난다

app.ts 타입 오류 0개, 런타임 오류 1개 
const names = ["Alice", "Bob"];
console.log(names[2].toUpperCase());
// TypeError: Cannot read properties of undefined (reading 'toUpperCase')

타입스크립트는 names[2] 를 string 으로 본다. 배열 인덱스 접근이 범위를 벗어날 가능성을 기본적으로 고려하지 않기 때문이다.

↑

noUncheckedIndexedAccess 최신 반영

TypeScript 4.1 에 추가된 이 옵션을 켜면 인덱스 접근 결과에 undefined 가 자동으로 붙는다. 위 코드는 그제서야 'names[2]'은(는) 'undefined'일 수 있습니다 로 잡힌다. strict 에 포함되지 않는 별도 옵션이라 직접 켜야 한다.

정리

  • 타입스크립트는 자바스크립트의 상위집합이다. 모든 자바스크립트 프로그램은 이미 타입스크립트 프로그램이다.
  • 반대는 성립하지 않는다. 타입스크립트에는 고유 문법이 있어 자바스크립트 엔진이 바로 실행할 수 없다.
  • 타입 시스템은 자바스크립트의 런타임 동작을 모델링한다. 그래서 2 + "3" 은 통과한다.
  • 그러면서도 자바스크립트에서 허용되는 것 일부는 막는다. 인수 개수 불일치가 대표적이다.
  • 타입 체커를 통과한 코드도 런타임에 오류가 날 수 있다. 타입 체크는 안전망이지 보증서가 아니다.
ITEM 2

타입스크립트 설정 이해하기

"이 코드에 타입 오류가 있나요?"라는 질문은 설정을 모르면 대답할 수 없다. 타입스크립트의 성격은 100개 가까운 설정이 결정한다.

핵심 설정은 커맨드라인이 아니라 tsconfig.json 에 둔다. 그리고 새 프로젝트라면 strict: true 부터 켠다.

설정하는 두 가지 방법

terminal 공유되지 않음 
tsc --noImplicitAny app.ts
tsconfig.json 권장 
{
  "compilerOptions": {
    "noImplicitAny": true
  }
}

가능하면 설정 파일을 쓴다. 팀 단위로 일하면 모두가 같은 규칙 아래에서 컴파일해야 하고, 편집기와 빌드 도구도 이 파일을 읽어 동작을 맞추기 때문이다.

!

원문 교정 원문 교정

노트에 tsx --init 으로 적혀 있는데, 설정 파일을 생성하는 명령은 tsc --init 이다. (tsx 는 TypeScript 를 즉시 실행해 주는 별개의 서드파티 도구다.)

가장 중요한 두 옵션

noImplicitAny — 변수가 미리 정의된 타입을 가져야 하는가
noImplicitAny: false 통과하지만 위험 
function add(a, b) {
  return a + b;
}
// 실제로는 이렇게 해석된다
// function add(a: any, b: any): any

매개변수가 암시적으로 any 가 되면 타입 체커는 그 자리에서 무력해진다. add(1, "hello") 도, add(null, undefined) 도 전부 통과한다.

noImplicitAny: true 권장 
function add(a: number, b: number) {
  return a + b;
}

이 설정을 끄는 게 정당한 상황은 사실상 하나뿐이다. 자바스크립트 프로젝트를 타입스크립트로 옮기는 도중일 때다(아이템 62).

strictNullChecks — null 과 undefined 가 모든 타입에 허용되는가
app.ts 
// strictNullChecks: false → 통과한다
const x: number = null;

// strictNullChecks: true → 오류
const y: number = null;
//    ~ 'null' 형식은 'number' 형식에 할당할 수 없습니다.

// null 을 허용하려면 타입에 명시해야 한다
const z: number | null = null;

실제로 이 옵션이 힘을 발휘하는 곳은 DOM 이나 API 응답처럼 없을 수도 있는 값을 다룰 때다.

app.ts 
const el = document.getElementById("status");
el.textContent = "ready";
// ~~ 개체가 'null'인 것 같습니다.

// 방법 1 — null 체크 (권장)
if (el) {
  el.textContent = "ready";
}

// 방법 2 — non-null 단언. 정말 null 이 아님을 아는 경우에만
el!.textContent = "ready";
!

언제 켜야 하나

strictNullChecks 는 null/undefined 관련 런타임 오류를 잡는 데 대단히 효과적이지만, 코드 작성 난이도를 확실히 올린다. 프로젝트 초기에 켜고 컨벤션을 잡는 편이 압도적으로 싸다. 코드가 쌓인 뒤에 켜면 수백 개의 오류를 한 번에 마주하게 된다.

strict 아래에 무엇이 들어 있나

i

함께 알아두기 보강

위 두 옵션은 사실 strict 라는 우산 아래 있는 아홉 개 중 둘이다. 하나씩 켜는 대신 "strict": true 한 줄이면 전부 켜진다.

옵션막아 주는 것
noImplicitAny타입을 안 적어서 몰래 any 가 되는 것
strictNullChecksnull/undefined 를 아무 타입에나 넣는 것
strictFunctionTypes함수 매개변수의 안전하지 않은 공변 할당
strictBindCallApplybind/call/apply 의 잘못된 인수
strictPropertyInitialization생성자에서 초기화되지 않은 클래스 필드
noImplicitThis타입을 알 수 없는 this (아이템 49)
useUnknownInCatchVariablescatch (e) 의 e 를 any 로 두는 것
alwaysStrict출력 파일에 "use strict" 누락
strictBuiltinIteratorReturn내장 이터레이터 return 타입의 부정확한 처리 TS 5.6+
i

추가로 켜 볼 만한 것 보강

strict 에 포함되지 않지만 값어치가 큰 옵션들이 있다. noUncheckedIndexedAccess(인덱스 접근에 undefined 추가), noImplicitOverride, exactOptionalPropertyTypes, 그리고 번들러/Node 네이티브 실행을 쓴다면 verbatimModuleSyntax 와 erasableSyntaxOnly(TS 5.8) 다.

정리

  • 타입스크립트 컴파일러는 언어의 핵심 동작을 바꾸는 설정을 다수 포함한다.
  • 설정은 커맨드라인이 아니라 tsconfig.json 에 둔다. tsc --init 으로 만든다.
  • 자바스크립트를 옮기는 중이 아니라면 noImplicitAny 를 켠다.
  • undefined는 객체가 아닙니다 류의 런타임 오류를 막으려면 strictNullChecks 를 켠다.
  • 가장 엄격한 설정은 strict: true 다. 새 프로젝트라면 여기서 시작한다.
ITEM 3

코드 생성과 타입이 관계없음을 이해하기

타입스크립트 컴파일러는 두 가지 일을 한다. 그리고 그 둘은 서로 완전히 독립적이다.

핵심 타입 오류가 있어도 .js 는 나온다. 그리고 그 .js 안에 타입은 한 글자도 남지 않는다. 
flowchart LR
  SRC["소스 .ts / .js"] --> TC["타입 체크
오류를 보고할 뿐"]
  SRC --> TR["트랜스파일
구버전 JS 로 변환"]
  TC -. "결과를 넘기지 않음" .-> TR
  TR --> OUT["출력 .js
타입 정보 없음"]
두 화살표는 만나지 않는다 — 타입 체크 결과는 출력물에 영향을 주지 않고, 출력물은 타입 정보를 갖고 있지 않다.

1. 타입 오류가 있는 코드도 컴파일된다

  • 타입스크립트의 오류는 편집기가 보여 주는 경고(warning) 에 가깝다. 빌드를 세우지 않는다.
  • 오류가 있어도 tsc 는 .js 를 만들어 낸다. 덕분에 문제 있는 부분만 남겨 두고 나머지를 실행해 볼 수 있다.
  • 오류가 있을 때 출력을 막고 싶다면 noEmitOnError: true 를 켠다.

2. 런타임에는 타입 체크가 불가능하다

area.ts 동작하지 않음 
interface Square {
  width: number;
}
interface Rectangle extends Square {
  height: number;
}
type Shape = Square | Rectangle;

function calculateArea(shape: Shape) {
  if (shape instanceof Rectangle) {
    //                  ~~~~~~~~~
    // 'Rectangle'은(는) 형식만 참조하지만, 여기서는 값으로 사용되고 있습니다.
    return shape.width * shape.height;
    //                         ~~~~~~ 'Shape' 형식에 'height' 속성이 없습니다.
  } else {
    return shape.width * shape.width;
  }
}

instanceof 는 런타임 연산자인데 Rectangle 은 타입이다. 컴파일 시점에 지워지므로 런타임에는 그런 이름의 값이 존재하지 않는다. 해결법은 셋 중 하나다.

방법 1 — 속성으로 분기 (in 연산자)
area.ts 가장 가벼운 해법 
function calculateArea(shape: Shape) {
  if ("height" in shape) {
    return shape.width * shape.height; // shape: Rectangle
  } else {
    return shape.width * shape.width;  // shape: Square
  }
}

속성 존재 여부는 런타임에 확인 가능한 값에 대한 질문이다. 타입 체커도 이 분기를 이해해서 각 갈래에서 타입을 좁혀 준다(아이템 22).

방법 2 — 태그 붙이기 (태그된 유니온)
area.ts 가장 널리 쓰이는 해법 
interface Square {
  kind: "square";
  width: number;
}
interface Rectangle {
  kind: "rectangle";
  width: number;
  height: number;
}
type Shape = Square | Rectangle;

function calculateArea(shape: Shape) {
  if (shape.kind === "rectangle") {
    return shape.width * shape.height;
  } else {
    return shape.width * shape.width;
  }
}

런타임에 접근 가능한 타입 정보를 값으로 명시해 저장하는 기법이다. 타입스크립트에서 워낙 흔해서 태그된 유니온(tagged union) 또는 구별된 유니온(discriminated union) 이라는 이름이 붙어 있다(아이템 28, 아이템 32).

방법 3 — 클래스로 만들기 (타입이자 값)
area.ts 
class Square {
  constructor(public width: number) {}
}
class Rectangle extends Square {
  constructor(public width: number, public height: number) {
    super(width);
  }
}
type Shape = Square | Rectangle;

function calculateArea(shape: Shape) {
  if (shape instanceof Rectangle) {
    return shape.width * shape.height;
  } else {
    return shape.width * shape.width;
  }
}

interface 는 타입으로만 쓸 수 있지만 클래스는 타입이면서 동시에 값이다. 그래서 같은 Rectangle 이라는 이름이 두 자리에서 다르게 읽힌다.

코드어떤 공간의 Rectangle 인가
type Shape = Square | Rectangle;타입 공간 — 인스턴스의 형태
shape instanceof Rectangle값 공간 — 런타임의 생성자 함수

이 이중성은 아이템 8에서 본격적으로 다룬다.

↑

erasableSyntaxOnly 를 쓴다면 최신 반영

위 클래스 예제의 constructor(public width: number) 는 매개변수 속성이라 불리는 타입스크립트 고유 문법으로, 지워지는 게 아니라 코드를 생성한다. Node.js 네이티브 실행처럼 타입만 지우는 환경에서는 쓸 수 없다. TypeScript 5.8 의 erasableSyntaxOnly 를 켜면 이런 문법(매개변수 속성, enum, 런타임 코드가 있는 namespace, 레거시 데코레이터)을 컴파일러가 미리 잡아 준다. 아이템 53과 같은 결론이다.

3. 타입 연산은 런타임에 영향을 주지 않는다

app.ts 타입 체커는 통과 
function asNumber(
  value: string | number
): number {
  return value as number;
}
app.js (컴파일 결과) 아무 일도 안 함 
function asNumber(value) {
  return value;
}

as number 는 타입 공간의 연산이라 정제 과정이 통째로 사라진다. 값을 실제로 바꾸려면 런타임에 존재하는 자바스크립트 연산을 써야 한다.

app.ts 런타임에 실제로 변환된다 
function asNumber(value: string | number): number {
  return typeof value === "string" ? Number(value) : value;
}

4. 타입은 런타임 성능에 영향을 주지 않는다

  • 타입은 전부 지워지므로 런타임 오버헤드는 0 이다. 대신 빌드 타임 오버헤드가 생긴다.
  • 컴파일러는 빠른 편이고, 증분 빌드(incremental)를 켜면 체감이 더 좋아진다.
  • 타입 체크 부담이 크다면 타입 체크와 트랜스파일을 분리할 수 있다. 이 챕터의 주제가 그대로 실무 전략이 되는 지점이다.
!

원문 교정 원문 교정

노트에 transfile only 로 적힌 부분은 도구마다 이름이 다르다. ts-node --transpileOnly, ts-loader 의 transpileOnly: true, 또는 esbuild·SWC·Babel 처럼 아예 타입 체크를 하지 않는 트랜스파일러를 쓰고 tsc --noEmit 를 CI 에서 따로 돌리는 구성이 일반적이다. 이때 파일 하나만 보고 변환할 수 있어야 하므로 isolatedModules 를 함께 켜 두는 편이 안전하다.

정리

  • 코드 생성은 타입 시스템과 무관하다. 타입 오류가 있어도 코드는 생성된다.
  • 타입 오류가 있을 때 컴파일을 막으려면 noEmitOnError 를 켠다.
  • 런타임에는 타입이 존재하지 않는다. 런타임에 타입을 알아야 한다면 값으로 만들어 두어야 한다 — in 체크, 태그된 유니온, 클래스.
  • 타입 단언(as)은 값을 바꾸지 않는다. 값을 바꾸려면 자바스크립트 연산이 필요하다.
  • 런타임 오버헤드는 없지만 빌드 타임 오버헤드는 있다. 필요하면 타입 체크와 트랜스파일을 분리한다.
ITEM 4

구조적 타이핑에 익숙해지기

타입스크립트는 "이 값이 어떤 타입으로 선언됐는가"가 아니라 "이 값이 어떤 모양인가"를 본다.

핵심 타입스크립트의 타입은 봉인되어 있지 않다. 어떤 타입에 맞는 값은 언제나 그보다 더 많은 속성을 갖고 있을 수 있다.

덕 타이핑을 그대로 모델링한 결과

  • 자바스크립트는 본질적으로 덕 타이핑(duck typing) 기반이다. 필요한 값만 제대로 주어지면 그 값이 어떻게 만들어졌는지는 신경 쓰지 않는다.
  • 타입스크립트는 이 동작을 그대로 모델링한다. 매개변수의 요구사항을 만족하면 선언된 타입 이름이 무엇이든 통과시킨다.
  • 이것을 구조적 타이핑(structural typing) 이라고 한다. Java·C# 의 명목적 타이핑(nominal typing) 과 대비되는 개념이다.
질문 자체가 다르다 — 구조적 타이핑은 값의 출신을 묻지 않는다. 이 성질이 아래 세 가지 놀라움의 원인이자, 테스트를 쉽게 만드는 이유이기도 하다.

놀라움 1 — 이름이 달라도 통과한다

vector.ts 
interface Vector2D {
  x: number;
  y: number;
}

function calculateLength(vector: Vector2D) {
  return Math.sqrt(vector.x * vector.x + vector.y * vector.y);
}

interface NamedVector {
  name: string;
  x: number;
  y: number;
}

const v: NamedVector = { name: "John", x: 3, y: 4 };
console.log(calculateLength(v)); // 5 — 오류 없음

NamedVector 는 Vector2D 와 아무런 선언상 관계가 없다. 그럼에도 x, y 를 갖고 있다는 사실만으로 통과한다. 여기까지는 편리하다.

놀라움 2 — 3차원 벡터가 2차원 함수를 조용히 통과한다

vector.ts 타입 오류 없이 틀린 답 
interface Vector3D {
  x: number;
  y: number;
  z: number;
}

function normalize(vector: Vector3D) {
  const length = calculateLength(vector); // Vector2D 를 받는 함수!
  return {
    x: vector.x / length,
    y: vector.y / length,
    z: vector.z / length,
  };
}

console.log(normalize({ x: 3, y: 4, z: 5 }));
// 기댓값: { x: 0.4242..., y: 0.5656..., z: 0.7071... }  (길이 √50 으로 나눔)
// 실제값: { x: 0.6, y: 0.8, z: 1 }                      (길이 5 로 나눔)
×

무엇이 잘못됐나

calculateLength 는 z 를 모르므로 2차원 길이 5 를 돌려준다. 정작 나눗셈은 세 축 모두에 적용된다. 결과 벡터의 길이는 1 이 아니라 √1.4 ≈ 1.183 이다. 정규화 함수가 정규화를 못 한 셈인데, 타입 체커는 아무 말도 하지 않는다.

!

원문 교정 원문 교정

노트에는 기댓값이 { x: 1, y: 1.333, z: 1.666 } 로 적혀 있는데, 이는 z(=5)로 나눈 값이다. 정규화의 정의는 벡터의 크기로 나누는 것이므로 기댓값은 √(9+16+25) = √50 ≈ 7.071 로 나눈 { x: 0.424, y: 0.566, z: 0.707 } 이다. 결론(z 가 무시되어 잘못된 결과가 나온다)은 그대로 유효하다.

함수를 작성할 때 우리는 매개변수가 선언된 속성만 갖고 있을 것이라고 무심코 가정한다. 그런 타입을 봉인된(sealed) 또는 정확한(precise) 타입이라고 부르는데, 타입스크립트의 타입 시스템에는 이런 개념이 없다. 타입은 언제나 열려 있다.

놀라움 3 — 그래서 for-in 순회가 막힌다

vector.ts 오류가 나는데, 사실 옳은 오류다 
function calculateLengthL1(vector: Vector3D) {
  let length = 0;
  for (const axis of Object.keys(vector)) {
    const coord = vector[axis];
    //            ~~~~~~~~~~~~
    // 'string' 형식의 식을 'Vector3D' 인덱스 형식에 사용할 수 없으므로
    // 요소에 암시적으로 'any' 형식이 있습니다.
    length += Math.abs(coord);
  }
  return length;
}

const vec3D = { x: 1, y: 2, z: 3, address: "seoul" };
console.log(calculateLengthL1(vec3D)); // 타입은 통과, 결과는 NaN

얼핏 보면 지나친 오류 같다. vector 는 Vector3D 이고 키는 x, y, z 뿐인데 왜? 하지만 구조적 타이핑 때문에 vector 안에 다른 속성이 더 있을 수 있고, 그 값이 number 라는 보장이 없다. Math.abs("seoul") 는 NaN 이다. 타입스크립트의 경고가 정확했던 것이다.

vector.ts 속성을 명시적으로 쓴다 
function calculateLengthL1(vector: Vector3D) {
  return Math.abs(vector.x) + Math.abs(vector.y) + Math.abs(vector.z);
}

루프를 도는 대신 세 축을 그냥 적었다. 코드는 길어졌지만 타입은 정확해졌다. 객체 순회의 다른 방법들은 아이템 54에서 다룬다.

놀라움 4 — 클래스도 예외가 아니다

structural-class.ts 
class C {
  foo: string;
  constructor(foo: string) {
    this.foo = foo;
  }
}

const c = new C("instance of C");
const d: C = { foo: "object literal" }; // 오류 없음!

console.log(c); // C { foo: 'instance of C' }
console.log(d); // { foo: 'object literal' }

d 가 C 타입에 할당되는 이유는 단순하다. string 타입의 foo 속성을 갖고 있고, 구조적으로 C 와 구별할 방법이 없기 때문이다.

!

생성자에 로직이 있다면

C 의 생성자가 값 검증이나 계산을 한다면 d 는 그 과정을 전부 건너뛴 객체가 된다. 타입은 맞지만 불변식은 깨져 있다. 이런 구별이 꼭 필요하면 아이템 37의 상표 기법(branded type) 이나 private/# 필드를 쓴다. private 필드가 있으면 구조적 호환이 깨지므로 외부 객체 리터럴로는 만들 수 없다.

반전 — 테스트에서는 이게 축복이다

authors.ts 테스트하려면 DB 전체를 모킹해야 한다 
interface Author {
  first: string;
  last: string;
}

function getAuthors(database: PostgresDB): Author[] {
  const authorRows = database.runQuery("SELECT first, last FROM authors");
  return authorRows.map((row) => ({ first: row.first, last: row.last }));
}

이 함수가 실제로 필요로 하는 건 PostgresDB 전체가 아니라 runQuery 하나뿐이다. 필요한 만큼만 인터페이스로 잘라 내면 된다.

authors.ts 필요한 모양만 요구한다 
interface DB {
  runQuery(sql: string): any[];
}

function getAuthors(database: DB): Author[] {
  const authorRows = database.runQuery("SELECT first, last FROM authors");
  return authorRows.map((row) => ({ first: row.first, last: row.last }));
}

const pg = new PostgresDB();
const authors = getAuthors(pg); // 실제 환경에서도 그대로 동작

PostgresDB 를 고치지도, implements DB 를 붙이지도 않았는데 그대로 통과한다. 그리고 테스트에서는 이렇게 쓴다.

authors.test.ts 모킹 라이브러리가 필요 없다 
test("getAuthors", () => {
  const authors = getAuthors({
    runQuery(sql: string) {
      return [{ first: "John", last: "Doe" }];
    },
  });

  expect(authors).toEqual([{ first: "John", last: "Doe" }]);
});
✓

부수 효과 하나 더

테스트 코드가 PostgresDB 에 대한 의존성을 전혀 갖지 않게 됐다. 라이브러리 타입을 직접 참조하지 않고 필요한 모양만 선언하는 이 기법은 아이템 51의 미러 타입으로 이어진다.

정리

  • 자바스크립트가 덕 타이핑이므로 타입스크립트는 구조적 타이핑으로 이를 모델링한다.
  • 어떤 인터페이스에 할당 가능한 값이라면 선언에 명시되지 않은 속성도 가질 수 있다. 타입은 봉인되어 있지 않다.
  • 클래스도 구조적으로 판정된다. instanceof 로 만들어졌다고 보장할 수 없다.
  • 이 성질 덕분에 테스트에서 목(mock)을 아주 가볍게 만들 수 있고, 라이브러리 의존성을 끊을 수 있다.
ITEM 5

any 타입 지양하기

타입 시스템은 점진적이고 선택적이다. any 는 그 선택지의 가장 극단이고, 대가는 생각보다 크다.

핵심 any 는 타입 체커를 끄는 게 아니라 타입스크립트를 쓰는 이유 전체를 끄는 것이다. 자동완성, 리팩터링, 문서화, 신뢰도가 한꺼번에 사라진다.
타입 시스템의 성격의미
점진적 (gradual)코드에 타입을 조금씩 추가할 수 있다
선택적 (optional)언제든지 타입 체커를 비활성화할 수 있다

이 두 성격을 가능하게 하는 게 any 다. 마이그레이션에는 필수적이지만(아이템 62), 남용하면 아래 여섯 가지를 잃는다.

1. any 에는 타입 안전성이 없다

app.ts 런타임에 조용히 틀린다 
let age: number = 0;

age = "12";
//~~ 'string' 형식은 'number' 형식에 할당할 수 없습니다.

age = "12" as any; // 통과
age += 1;          // 통과

console.log(age);  // "121"  — number 라고 선언했는데 문자열이 나온다

as any 하나로 number 라는 선언이 거짓말이 됐다. 그리고 아무도 그 사실을 모른다.

2. any 는 함수 시그니처를 무시한다

age.ts 약속이 깨진다 
function calculateAge(birthDate: Date): number {
  return new Date().getFullYear() - birthDate.getFullYear();
}

let birthDate: any = "1999-09-21";
calculateAge(birthDate); // 타입 오류 없음
// TypeError: birthDate.getFullYear is not a function

함수 시그니처는 호출하는 쪽과 구현하는 쪽 사이의 약속이다. any 는 그 약속을 일방적으로 무효화한다.

3. any 에는 편집기 지원이 사라진다

타입스크립트를 쓰는 실질적인 이유 중 큰 몫이 편집기 경험이다. any 는 그것부터 가져간다.

자동완성
const person = { firstName: 'Kim', lastName: 'Dongwoo' };
console.log(person.firstName);   // { firstName: string; lastName: string; }
◇ firstName
타입이 있으므로 실제 존재하는 두 속성만 제안된다. 오타는 애초에 후보에 없다.
타입이 추론된 객체 — 속성 이름을 외울 필요가 없다.
const person: any = { firstName: 'Kim', lastName: 'Dongwoo' };
console.log(person.firstName);   // 식별자만 나열됨

타입스크립트의 모토

"확장 가능한 자바스크립트(JavaScript that scales)". 여기서 확장성의 상당 부분은 도구가 코드를 이해한다는 사실에서 나온다. any 는 그 이해를 끊는다.

4. any 는 리팩터링 때 버그를 감춘다

selector.ts 리팩터링 전 
interface ComponentProps {
  onSelectItem: (item: any) => void;
}

let selectedId = 0;

function handleSelectItem(item: any) {
  selectedId = item.id;
}

renderSelector({ onSelectItem: handleSelectItem });

콜백이 객체 전체를 받을 필요가 없다는 걸 깨닫고 시그니처를 좁힌다.

selector.ts 리팩터링 후 — 타입 오류 0개 
interface ComponentProps {
  onSelectItem: (id: number) => void;
}
// handleSelectItem 은 그대로 두었다. 컴파일은 통과한다.
// 런타임: selectedId = (3).id → undefined
×

타입 체커가 잡아 줬어야 할 순간

item: any 가 아니라 item: Item 이었다면 (id: number) => void 로 바꾸는 순간 바로 오류가 났을 자리다. 리팩터링에서 타입 체커가 가장 큰 값을 내는 지점이 정확히 여기인데, any 가 그걸 없앴다.

5. any 는 타입 설계를 감춘다

  • 앱 상태 같은 객체의 타입을 제대로 정의하는 일은 번거롭다. any 로 넘기고 싶어지는 순간이 온다.
  • 하지만 타입은 설계를 읽을 수 있게 만드는 문서이기도 하다. any 는 그 문서를 지운다.
  • 동료가 코드를 이해하려면 이제 구현을 전부 읽어야 한다. 아이템 28의 "유효한 상태만 표현하기"도 애초에 시도할 수 없게 된다.

6. any 는 타입 시스템의 신뢰도를 떨어뜨린다

  • 사람은 실수하고, 타입 체커는 그 실수를 잡아 준다. 잡히는 경험이 쌓이면 코드에 대한 신뢰가 생긴다.
  • 그런데 타입 체크를 통과한 코드가 런타임에 계속 터지면, 신뢰는 빠르게 무너진다.
  • 타입 체커를 믿지 못하게 되면 매번 직접 확인하게 되고, 결국 타입스크립트를 쓰면서 자바스크립트의 비용을 그대로 치르게 된다.
i

그럼 어떻게 하나 보강

any 를 완전히 없애기는 어렵다. 대신 피해 반경을 좁히는 방법들이 5장에 모여 있다. 값의 타입을 정말 모를 때는 any 대신 unknown 을 쓰고(아이템 42), 꼭 필요하면 가능한 한 좁은 범위에서만 쓰며(아이템 38), any[]·Record<string, any> 처럼 조금이라도 구체적으로 만든다(아이템 39).

정리

  • any 는 타입 안전성을 없애고, 함수 시그니처의 약속을 무시하며, 편집기 지원을 지운다.
  • 리팩터링 시 버그를 감추고, 타입 설계를 숨기며, 타입 시스템 전체의 신뢰도를 떨어뜨린다.
  • 타입스크립트를 쓰는 이유를 한 번에 무력화하는 타입이다. 가능한 한 쓰지 않는다.
  • 불가피하다면 unknown 을 먼저 검토하고, 범위를 최대한 좁힌다.
