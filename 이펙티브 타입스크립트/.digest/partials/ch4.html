ITEM 28

유효한 상태만 표현하는 타입을 지향하기

이 책에서 가장 값어치가 큰 한 문장. 표현할 수 없으면 발생할 수도 없다.

핵심 유효한 상태와 무효한 상태를 둘 다 표현하는 타입은, 혼란스럽고 오류를 유발하는 코드를 낳는다. 유효한 상태만 표현하는 타입을 만든다.

문제 — 무효한 상태가 표현되는 타입

state.ts 네 가지 조합 중 두 개가 무효 
interface State {
  pageText: string;
  isLoading: boolean;
  error?: string;
}

function renderPage(state: State) {
  if (state.error) {
    return `Error! Unable to load: ${state.error}`;
  } else if (state.isLoading) {
    return `Loading...`;
  }
  return `<h1>${state.pageText}</h1>`;
}
두 불리언이 만드는 네 칸 중 하나가 정의되지 않았다 — 타입이 무효한 상태를 허용하면, 코드는 그 상태를 만났을 때 무엇을 해야 할지 알 수 없다.

같은 타입으로 전환 함수를 쓰면 상황이 더 나빠진다

state.ts 세 가지 버그가 숨어 있다 
async function changePage(state: State, newPage: string) {
  state.isLoading = true;
  try {
    const response = await fetch(getUrlForPage(newPage));
    if (!response.ok) {
      throw new Error(`Unable to load ${newPage}: ${response.statusText}`);
    }
    const text = await response.text();
    state.isLoading = false;
    state.pageText = text;
  } catch (e) {
    state.error = "" + e;
  }
}
×

숨은 버그 셋

  1. 오류가 발생했을 때 state.isLoading = false 로 되돌리는 코드가 없다. 영원히 로딩 중이 된다.
  2. state.error 를 초기화하지 않는다. 다음 페이지 전환에서 로딩 대신 과거 오류가 보인다.
  3. 로딩 중에 사용자가 다른 페이지로 이동하면 어떻게 될지 알 수 없다. 응답 도착 순서에 따라 화면이 뒤죽박죽이 된다.

세 버그 모두 원인은 같다. 상태 값의 두 가지 속성이 동시에 정보가 부족하거나(로딩 중인지 오류인지 알 수 없음) 충돌한다(로딩이면서 동시에 오류).

해법 — 상태를 태그된 유니온으로 다시 설계한다

state.ts 무효한 상태가 아예 표현되지 않는다 
interface RequestPending {
  state: "pending";
}
interface RequestError {
  state: "error";
  error: string;
}
interface RequestSuccess {
  state: "ok";
  pageText: string;
}
type RequestState = RequestPending | RequestError | RequestSuccess;

interface State {
  currentPage: string;
  requests: { [page: string]: RequestState };
}

타입이 길어졌지만 얻는 것이 훨씬 크다. 요청 상태를 페이지마다 따로 추적하므로 세 번째 버그(응답 순서 문제)까지 구조적으로 사라진다.

state.ts 분기마다 필요한 값만 정확히 있다 
function renderPage(state: State) {
  const { currentPage } = state;
  const requestState = state.requests[currentPage];

  switch (requestState.state) {
    case "pending":
      return `Loading ${currentPage}...`;
    case "error":
      return `Error! Unable to load ${currentPage}: ${requestState.error}`;
    case "ok":
      return `<h1>${currentPage}</h1>\n${requestState.pageText}`;
  }
}

async function changePage(state: State, newPage: string) {
  state.requests[newPage] = { state: "pending" };
  state.currentPage = newPage;

  try {
    const response = await fetch(getUrlForPage(newPage));
    if (!response.ok) {
      throw new Error(`Unable to load ${newPage}: ${response.statusText}`);
    }
    const pageText = await response.text();
    state.requests[newPage] = { state: "ok", pageText };
  } catch (e) {
    state.requests[newPage] = { state: "error", error: "" + e };
  }
}
i

주변에서 실제로 쓰이는 예 보강

  • TanStack Query 의 status: "pending" | "error" | "success" 와 data/error 의 조합
  • Redux Toolkit 의 createAsyncThunk 가 만드는 pending/fulfilled/rejected 액션
  • Rust 의 Result<T, E>, Kotlin 의 sealed class

이름은 달라도 전부 같은 아이디어다. 있을 수 없는 조합을 타입으로 막는다.

정리

  • 유효한 상태와 무효한 상태를 모두 표현하는 타입은 혼란과 오류를 부른다.
  • 유효한 상태만 표현하는 타입은 코드가 길어지고 표현하기 어려워질 수 있지만, 결국 시간을 아껴 주고 고통을 줄여 준다.
  • 불리언 플래그가 여러 개 모여 있다면 태그된 유니온으로 바꿀 수 있는지 먼저 검토한다.
ITEM 29

사용할 때는 너그럽게, 생성할 때는 엄격하게

"당신이 하는 일은 엄격하게, 남의 것을 받을 때는 너그럽게." 포스텔의 법칙을 타입 설계에 적용한다.

핵심 매개변수 타입은 넓게, 반환 타입은 좁게. 반환 타입이 느슨하면 그 부담이 전부 호출하는 쪽으로 넘어간다.

문제 — 반환 타입이 너무 넓다

camera.ts 전부 선택적이고 유니온이다 
interface CameraOptions {
  center?: LngLat;
  zoom?: number;
  bearing?: number;
  pitch?: number;
}

type LngLat =
  | { lng: number; lat: number }
  | { lon: number; lat: number }
  | [number, number];

declare function setCamera(options: CameraOptions): void;

type LngLatBounds =
  | { northeast: LngLat; southwest: LngLat }
  | [LngLat, LngLat]
  | [number, number, number, number];

declare function viewportForBounds(bounds: LngLatBounds): CameraOptions;

매개변수가 너그러운 건 좋다. 일부 값만 바꾸고 싶을 수 있으니 전부 선택적이고, 좌표를 세 가지 형태로 받는다. 문제는 viewportForBounds 의 반환 타입도 CameraOptions 라는 점이다.

camera.ts 쓰기가 괴롭다 
function focusOnFeature(f: Feature) {
  const bounds = calculateBoundingBox(f);
  const camera = viewportForBounds(bounds);
  setCamera(camera);

  const {
    center: { lat, lng },
    //        ~~~  ~~~ 'LngLat | undefined' 형식에 'lat' 속성이 없습니다.
    zoom,   // number | undefined
  } = camera;

  window.location.search = `?v=@${lat},${lng}z${zoom}`;
  //                              undefined,undefined zundefined 가 될 수 있다
}
×

두 가지 문제가 겹쳤다

  1. center 가 선택적이라 undefined 일 수 있다.
  2. center 가 세 가지 형태의 유니온이라, 값이 있어도 lat/lng 로 바로 못 꺼낸다. 형태별로 분기해야 한다.

즉 편의를 위해 넓힌 타입이 반환값에도 그대로 쓰이면서, 호출하는 쪽이 그 대가를 치른다.

해법 — 기본 형태와 느슨한 형태를 분리한다

camera.ts 두 개의 타입 
// 엄격한 기본 형태 — 반환 타입에 쓴다
interface LngLat { lng: number; lat: number; }
interface Camera {
  center: LngLat;
  zoom: number;
  bearing: number;
  pitch: number;
}

// 느슨한 형태 — 매개변수에 쓴다
type LngLatLike = LngLat | { lon: number; lat: number } | [number, number];
interface CameraOptions extends Omit<Partial<Camera>, "center"> {
  center?: LngLatLike;
}

declare function setCamera(options: CameraOptions): void;
declare function viewportForBounds(bounds: LngLatBounds): Camera;
//                                                        ^^^^^^ 엄격해졌다
camera.ts 호출하는 쪽이 편해졌다 
function focusOnFeature(f: Feature) {
  const bounds = calculateBoundingBox(f);
  const camera = viewportForBounds(bounds); // Camera
  setCamera(camera);                        // Camera 는 CameraOptions 에 할당 가능

  const { center: { lat, lng }, zoom } = camera; // 전부 확정된 값
  window.location.search = `?v=@${lat},${lng}z${zoom}`;
}
i

이 패턴의 이름들

Camera/CameraOptions, LngLat/LngLatLike 처럼 같은 개념의 엄격한 버전과 느슨한 버전을 짝지어 두는 것이 이 아이템의 실천법이다. 라이브러리에서 XxxLike, XxxInit, XxxOptions, PartialXxx 같은 이름이 보이면 대체로 이 패턴이다.

Omit<Partial<Camera>, "center"> 처럼 계산해서 만들면 Camera 가 바뀔 때 자동으로 따라온다(아이템 14).

정리

  • 보통 매개변수 타입은 반환 타입에 비해 범위가 넓은 경향이 있다. 선택적 속성과 유니온이 매개변수에 더 흔하다.
  • 매개변수와 반환 타입의 재사용을 위해서는 기본 형태(반환)와 느슨한 형태(매개변수) 를 도입하는 것이 좋다.
  • 사용하기 편한 API 일수록 반환 타입이 엄격하다.
ITEM 30

문서에 타입 정보를 쓰지 않기

주석은 갱신되지 않으면 쓰레기가 된다. 타입은 컴파일러가 강제로 갱신시킨다.

핵심 타입 정보를 주석에 중복해서 쓰지 않는다. 코드와 주석이 어긋나면 둘 다 틀린 것이 된다.

나쁜 예 1 — 시그니처를 산문으로 옮겨 적기

color.ts 세 군데가 틀렸다 
/**
 * 전경색(foreground) 문자열을 반환한다.
 * 0개 또는 1개의 매개변수를 받는다.
 * 매개변수가 없을 때는 표준 전경색을 반환한다.
 * 매개변수가 있을 때는 특정 페이지의 전경색을 반환한다.
 */
function getForegroundColor(page?: string) {
  return page === "login" ? { r: 127, g: 127, b: 127 } : { r: 0, g: 0, b: 0 };
}
주석의 주장실제
문자열을 반환객체 {r, g, b} 를 반환한다
0개 또는 1개의 매개변수시그니처에 이미 page?: string 로 적혀 있다
4줄에 걸친 설명불필요하게 장황하다
color.ts 한 줄이면 충분하다 
/** 애플리케이션 또는 특정 페이지의 전경색을 가져온다. */
function getForegroundColor(page?: string): Color {
  // ...
}
✓

주석이 답해야 할 질문

주석은 "무엇을 하는가"가 아니라 "왜 이렇게 하는가"에 답할 때 값이 있다. 타입이 이미 대답하는 질문을 주석이 또 대답하면, 나중에 둘 중 하나만 갱신되어 서로를 배신한다.

나쁜 예 2 — 규칙을 주석으로 부탁하기

부탁 강제력이 없다 
// nums 를 변경하지 마세요
function sort(nums: number[]) {
  // ...
}
강제 컴파일러가 지켜 준다 
function sort(nums: readonly number[]) {
  // ...
}

아이템 17의 readonly 가 여기서 그대로 쓰인다. 규칙을 문서에 적는 대신 타입으로 만든다.

나쁜 예 3 — 변수 이름에 타입 넣기

naming.ts 
const ageNum = 10;  // ✗ 타입이 이미 number 라고 말하고 있다
const age = 10;     // ✓
i

단위는 예외다

값의 단위가 이름에 있는 건 오히려 좋다. timeMs, temperatureC, sizeKb 처럼. 이건 타입 정보가 아니라 타입이 표현하지 못하는 도메인 정보이기 때문이다. 단위를 타입으로 강제하고 싶다면 아이템 37의 상표 기법을 쓴다.

정리

  • 주석과 변수명에 타입 정보를 적지 않는다. 최선의 경우 중복이고, 최악의 경우 서로 모순된다.
  • 타입이 명확하지 않은 경우라면, 그건 주석이 아니라 변수명을 고쳐야 하는 신호다.
  • 값을 변경하지 않는다는 등의 규칙은 주석 대신 readonly 로 선언한다.
  • 단위가 있는 값은 이름에 단위를 포함시키는 것을 고려한다.
ITEM 31

타입 주변에 null 값 배치하기

값이 전부 null 이거나 전부 null 이 아닌 상태가, 뒤섞인 상태보다 훨씬 다루기 쉽다.

핵심 null 을 작은 값 하나하나에 흩뿌리지 말고, 더 큰 객체 하나에 몰아넣는다. 검사 한 번으로 전부 해결된다.

예 1 — 최솟값과 최댓값 구하기

extent.ts null 이 두 곳에 흩어져 있다 
function extent(nums: number[]) {
  let min, max;
  for (const num of nums) {
    if (!min) {
      min = num;
      max = num;
    } else {
      min = Math.min(min, num);
      max = Math.max(max, num);
      //             ~~~ 'number | undefined' 형식의 인수는
      //                 'number' 형식의 매개 변수에 할당될 수 없습니다.
    }
  }
  return [min, max];
}

const [min, max] = extent([0, 1, 2]);
const span = max - min;
//           ~~~ 'max'은(는) 'undefined'일 수 있습니다.
×

세 가지가 동시에 잘못됐다

  1. !min 조건 때문에 최솟값이 0 이면 무시된다. extent([0, 1, 2]) 는 [1, 2] 를 돌려준다.
  2. 빈 배열을 넣으면 [undefined, undefined] 가 나온다.
  3. 반환 타입이 (number | undefined)[] 라, 호출하는 모든 곳에서 오류가 난다.

근본 원인은 min 과 max 라는 두 값이 각각 undefined 가 될 수 있도록 설계한 것이다.

extent.ts null 을 하나로 모은다 
function extent(nums: number[]) {
  let result: [number, number] | null = null;

  for (const num of nums) {
    if (!result) {
      result = [num, num];
    } else {
      result = [Math.min(result[0], num), Math.max(result[1], num)];
    }
  }
  return result;   // [number, number] | null
}

const range = extent([0, 1, 2]);
if (range) {
  const [min, max] = range;  // 둘 다 number 로 확정
  const span = max - min;
}

이제 null 검사는 한 번이고, 통과하면 두 값 모두 확정이다. 반환 타입 [number, number] | null 이 호출자에게 "빈 배열이면 결과가 없다"는 사실까지 알려 준다.

예 2 — 클래스에서 null 을 없애기

user-posts.ts 네 가지 상태가 가능하다 
class UserPosts {
  user: UserInfo | null;
  posts: Post[] | null;

  constructor() {
    this.user = null;
    this.posts = null;
  }

  async init(userId: string) {
    return Promise.all([
      async () => { this.user = await fetchUser(userId); },
      async () => { this.posts = await fetchPosts(userId); },
    ]);
  }

  getUserName() {
    // this.user 가 null 일 수 있다 — 모든 메서드에서 검사해야 한다
  }
}

네트워크 요청이 진행되는 동안 두 속성은 둘 다 null / 하나만 null / 둘 다 아님 세 가지 상태를 오간다. 이 불확실성이 모든 메서드에 전염된다.

user-posts.ts 데이터가 준비된 뒤에 생성한다 
class UserPosts {
  user: UserInfo;
  posts: Post[];

  constructor(user: UserInfo, posts: Post[]) {
    this.user = user;
    this.posts = posts;
  }

  static async init(userId: string): Promise<UserPosts> {
    const [user, posts] = await Promise.all([
      fetchUser(userId),
      fetchPosts(userId),
    ]);
    return new UserPosts(user, posts);
  }

  getUserName() {
    return this.user.name; // 검사가 필요 없다
  }
}
✓

이 리팩터링이 하는 일

객체가 존재한다 = 데이터가 준비되었다 라는 불변식을 만들었다. 정적 팩토리 init 이 그 불변식을 보장하는 유일한 통로다. 아이템 28의 "유효한 상태만 표현하기"를 클래스에 적용한 형태다.

로딩 중 상태를 화면에 표시해야 한다면, 그건 UserPosts | null 처럼 클래스 바깥에서 다룬다.

!

원문 참고 원문 교정

원문 노트의 init 은 Promise.all 에 함수 자체를 넘기고 있어(async () => ...) 실제로는 아무것도 기다리지 않는다. 함수를 호출한 결과(프로미스)를 넘겨야 한다. 개선된 코드는 그 점도 함께 고쳤다.

정리

  • 한 값의 null 여부가 다른 값의 null 여부에 암시적으로 관련되도록 설계하지 않는다.
  • API 를 만들 때는 반환 타입 전체를 null 이거나 아니게 만들어, 사용하는 쪽을 명확하게 한다.
  • 클래스는 필요한 값이 모두 준비된 뒤에 생성하여 null 이 존재하지 않게 만든다.
  • strictNullChecks 를 켜야 이 모든 논의가 의미를 갖는다(아이템 2).
ITEM 32

유니온의 인터페이스보다 인터페이스의 유니온 사용하기

유니온 타입 속성을 여러 개 가진 인터페이스를 보면, 순서를 뒤집을 수 있는지 먼저 생각해 본다.

핵심 interface { a: A1|A2; b: B1|B2 } 보다 {a:A1,b:B1} | {a:A2,b:B2} 가 낫다. 어긋난 조합을 애초에 만들 수 없기 때문이다.

예 1 — 지도 레이어

layer.ts 9가지 조합 중 6가지가 무효 
interface Layer {
  layout: FillLayout | LineLayout | PointLayout;
  paint: FillPaint | LinePaint | PointPaint;
}

layout 이 FillLayout 인데 paint 가 LinePaint 인 조합은 성립하지 않는다. 그런 조합을 타입이 허용한다면 언젠가 만들어진다.

layer.ts 인터페이스의 유니온 
interface FillLayer {
  type: "fill";
  layout: FillLayout;
  paint: FillPaint;
}
interface LineLayer {
  type: "line";
  layout: LineLayout;
  paint: LinePaint;
}
interface PointLayer {
  type: "point";
  layout: PointLayout;
  paint: PointPaint;
}
type Layer = FillLayer | LineLayer | PointLayer;

function drawLayer(layer: Layer) {
  if (layer.type === "fill") {
    const { layout, paint } = layer; // FillLayout, FillPaint
  } else if (layer.type === "line") {
    const { layout, paint } = layer; // LineLayout, LinePaint
  } else {
    const { layout, paint } = layer; // PointLayout, PointPaint
  }
}
i

type 태그를 넣는 이유

세 인터페이스는 태그 없이도 구조가 다르지만, 명시적 태그가 있으면 좁히기가 확실하고 빠르다(아이템 22). 태그된 유니온은 타입스크립트에서 가장 흔한 패턴이라, 익숙해지면 설계할 때 자연스럽게 손이 간다.

예 2 — 함께 있거나 함께 없는 속성

person.ts 주석으로 규칙을 부탁하고 있다 
interface Person {
  name: string;
  // 다음 두 속성은 동시에 있거나 동시에 없다
  placeOfBirth?: string;
  dateOfBirth?: Date;
}

아이템 30이 말한 대로, 타입 안에 주석으로 적힌 규칙은 문제의 신호다. 두 속성을 하나로 묶으면 타입이 규칙을 스스로 표현한다.

person.ts 중첩 객체로 묶는다 
interface Person {
  name: string;
  birth?: {
    place: string;
    date: Date;
  };
}

const alan: Person = {
  name: "Alan Turing",
  birth: {
    date: new Date("1912-06-23"),
    // ~~~~ 'place' 속성이 '{ date: Date; }' 형식에 없지만
    //      '{ place: string; date: Date; }' 형식에서 필수입니다.
  },
};

function eulogize(p: Person) {
  console.log(p.name);
  const { birth } = p;
  if (birth) {
    console.log(`was born on ${birth.date} in ${birth.place}.`);
  }
}

검사가 한 번으로 줄어든 것도 이득이다(아이템 31).

타입 구조를 바꿀 수 없다면

person.ts 인터페이스의 유니온으로 
interface Name {
  name: string;
}

interface PersonWithBirth extends Name {
  placeOfBirth: string;
  dateOfBirth: Date;
}

type Person = Name | PersonWithBirth;

function eulogize(p: Person) {
  console.log(p.name);
  if ("placeOfBirth" in p) {
    p.placeOfBirth; // string
    p.dateOfBirth;  // Date
  }
}

API 응답 형태처럼 내가 바꿀 수 없는 타입이라면 이 방식이 유용하다. in 연산자 하나로 두 속성이 동시에 좁혀진다.

정리

  • 유니온 타입의 속성을 여러 개 가진 인터페이스는 속성 간 관계가 분명하지 않다. 실수를 유발한다.
  • 유니온의 인터페이스보다 인터페이스의 유니온이 정확하고 이해하기 쉽다.
  • 타입스크립트가 제어 흐름을 분석할 수 있도록 태그된 유니온을 사용한다.
  • 여러 선택적 속성이 동시에 존재하거나 부재해야 한다면 하나로 묶는다.

string 타입보다 더 구체적인 타입 사용하기

핵심 string 을 쓰려는 순간, 더 좁은 타입이 적절하지 않은지 항상 먼저 생각한다. string 이 난무하는 코드를 stringly typed 라고 부른다.

enum 은 쓰지 않는다

"두 값만 허용"이라고 하면 enum 이 떠오르지만, 타입스크립트의 enum 은 여러 이유로 권장되지 않는다(아이템 53). 문자열 리터럴 유니온이 더 안전하고, 코드 생성도 하지 않는다.

좁은 타입이 주는 세 가지 이득

1. 값이 어디로 전달되어도 타입 정보가 유지된다
album.ts 
function getAlbumsOfType1(recordingType: string): Album[] { /* ... */ }

//               ~~~~~~~~ '"Studio"' 형식의 인수는 'RecordingType' 형식의

2. 타입에 주석을 달 수 있고, 그 주석이 편집기에 나타난다
/** 이 녹음은 어떤 환경에서 이루어졌는지 의미한다. */
type RecordingType = "live" | "studio";

function getAlbumsOfType(recordingType: RecordingType): Album[] {
  // ...
}
type RecordingType = "live" | "studio"
이 녹음은 어떤 환경에서 이루어졌는지 의미한다.
TSDoc 주석은 타입 위에 붙이면 그 타입을 쓰는 모든 자리에서 툴팁으로 보인다. // 가 아니라 /** */ 형식이어야 한다(아이템 48).
3. keyof 로 속성 접근을 정밀하게 만들 수 있다
pluck.ts 1단계 — any 
function pluck(records: any[], key: string): any[] {
  return records.map((r) => r[key]);
}
// 반환 타입이 any[] 라 아무 도움이 안 된다
pluck.ts 3단계 — keyof T 로 제한 
function pluck<T, K extends keyof T>(records: T[], key: K): T[K][] {
  return records.map((r) => r[key]);
}

const albums: Album[] = [/* ... */];

pluck(albums, "releaseDate"); // Date[]
pluck(albums, "artist");      // string[]
pluck(albums, "recordingType"); // RecordingType[]
pluck(albums, "recordingDate");
//            ~~~~~~~~~~~~~~~ '"recordingDate"' 형식의 인수는
//                            'keyof Album' 형식의 매개 변수에 ...
✓

여기서도 자동완성이 따라온다

pluck(albums, " 까지 입력하면 편집기가 artist, title, releaseDate, recordingType 네 개를 제안한다. key: string 이었다면 아무것도 제안하지 못했을 것이다.

정리

  • 문자열을 남발한 코드를 피한다. 모든 문자열을 할당할 수 있는 string 타입보다 더 구체적인 타입이 낫다.
  • 변수의 범위를 정확히 표현하려면 string 대신 문자열 리터럴 타입의 유니온을 쓴다.
  • 객체의 속성 이름을 함수 매개변수로 받을 때는 string 보다 keyof T 를 쓴다.
ITEM 34

부정확한 타입보다는 미완성 타입을 사용하기

정밀도를 올리려다 틀린 타입을 만들면, 없느니만 못하다.

핵심 타입은 구체적일수록 좋지만, 정확도가 함께 오르지 않으면 손해다. 틀린 타입은 잘못된 확신을 준다.

정제가 이득인 경우 — GeoJSON 좌표

전 너무 추상적 
interface Point {
  type: "Point";
  coordinates: number[];
}
interface LineString {
  type: "LineString";
  coordinates: number[][];
}
interface Polygon {
  type: "Polygon";
  coordinates: number[][][];
}
type Geometry = Point | LineString | Polygon;
후 튜플로 정밀도 상승 
type GeoPosition = [number, number];

interface Point {
  type: "Point";
  coordinates: GeoPosition;
}
// LineString, Polygon 도 동일하게
!

이 정제조차 대가가 있다

GeoJSON 명세는 고도(elevation)를 담은 세 번째 요소를 허용한다. [number, number] 로 좁히면 유효한 데이터를 거부하게 되고, 사용자는 결국 as any 로 우회한다. 더 좁은 게 항상 더 옳은 것은 아니다.

정제가 손해가 되는 경우 — Lisp 풍 수식

true
["+", 1, 2]                        // 3
["/", 20, 2]                       // 10

Mapbox 같은 라이브러리가 지도 스타일을 이런 형식으로 표현한다. 다섯 단계로 정밀도를 올려 보자.

단계타입결과
1모두 허용아무것도 잡지 못한다
2문자열, 숫자, 배열 허용true 를 잡는다
3알려진 함수 이름으로 시작하는 배열["**"] 를 잡는다
4매개변수 개수까지 확인오류 메시지가 무너진다
5매개변수 타입까지 확인사실상 불가능
3단계 여기까지가 실용적이다 
type FnName = "+" | "-" | "*" | "/" | ">" | "<" | "case" | "rgb";
type CallExpression = [FnName, ...any[]];
type Exp3 = number | string | CallExpression;

const tests: Exp3[] = [
  12,
  "red",
  true,
  // ~~~ 'boolean' 형식은 'Exp3' 형식에 할당할 수 없습니다.
  ["+", 1, 2],
  ["case", [">", 20, 10], "red", "blue"],
  ["**", 2, 31],
  // ~~~~ '"**"' 형식은 'FnName' 형식에 할당할 수 없습니다.
  ["rgb", 255, 0, 127],
];
4단계 여기서부터 손해 
interface MathCall {
  0: "+" | "-" | "*" | "/" | ">" | "<";
  1: Exp4;
  2: Exp4;
  length: 3;
}
interface CaseCall {
  0: "case";
  1: Exp4;
  2: Exp4;
  3: Exp4;
  length: 4 | 6 | 8 | 10 | 12 | 14 | 16; // 이게 정말 최선인가?
}
interface RgbCall {
  0: "rgb";
  1: number;
  2: number;
  3: number;
  length: 4;
}
type CallExpression = MathCall | CaseCall | RgbCall;
type Exp4 = number | string | CallExpression;

무엇이 무너졌나

  • 오류 메시지가 쓸모없어진다. ["**", 2, 31] 은 이제 '"**"' 형식은 'FnName' 형식에 할당할 수 없습니다 대신 '[string, number, number]' 형식은 'Exp4' 형식에 할당할 수 없습니다 로 보고된다. 무엇이 잘못됐는지 알 수 없다.
  • 자동완성이 죽는다. 유니온이 커질수록 편집기가 도움을 주지 못한다.
  • length: 4 | 6 | 8 | ... 같은 표현은 명세를 정확히 옮긴 것도 아니다. 홀수 개 인수를 여전히 부정확하게 다룬다.
✓

판단 기준

정밀도를 한 단계 올릴 때마다 물어본다. "이 변화로 잡을 수 있게 된 오류"와 "이 변화로 나빠진 오류 메시지·자동완성·거짓 양성"을 저울에 올리면 어느 쪽이 무거운가? 후자가 무거우면 되돌린다.

정리

  • 타입 안전성에서 불쾌한 골짜기는 피한다. 잘못된 타입은 없는 것보다 나쁘다.
  • 정확하게 모델링할 수 없다면 부정확하게 모델링하지 말라. any 나 unknown 을 적절히 쓴다.
  • 타입 정보를 구체적으로 만들수록 오류 메시지와 자동완성 품질에 주의해야 한다. 이것도 타입 설계의 일부다.

GraphQL 이 특히 잘 맞는 이유

GraphQL 스키마는 그 자체로 타입 시스템이고, nullable 여부까지 명세에 들어 있다. 그래서 생성된 타입스크립트 타입이 string | null 처럼 정확하게 나온다. 쿼리마다 필요한 필드만 뽑아 쓰므로 쿼리에 딱 맞는 타입이 만들어진다는 것도 큰 장점이다.

!

생성된 타입도 런타임 보증은 아니다

타입 생성은 컴파일 타임 문제만 해결한다. 서버가 명세를 어기면 런타임에서 터진다. 경계에서 zod 같은 스키마 검증을 함께 두면 두 층이 모두 막힌다(아이템 15).

정리

  • 코드의 구석구석까지 타입 안전성을 얻기 위해 명세로부터 타입을 생성하는 것이 좋다.
  • 예시 데이터가 아닌 명세를 참고해 타입을 만든다. 예시는 내가 본 것만 알려 준다.
  • 이미 공개된 @types 가 있다면 직접 만들지 말고 그것을 쓴다.
ITEM 36

해당 분야의 용어로 타입 이름 짓기

"컴퓨터 과학에서 어려운 두 가지는 캐시 무효화와 이름 짓기다."

핵심 새 용어를 만들지 말고 이미 그 분야에 있는 용어를 정확히 가져다 쓴다. 도메인 전문가와 같은 언어를 쓰게 된다.

나쁜 예

animal.ts 세 속성 모두 모호하다 
interface Animal {
  name: string;
  endangered: boolean;
  habitat: string;
}

const leopard: Animal = {
  name: "Snow Leopard",
  endangered: false,
  habitat: "tundra",
};
속성무엇이 문제인가
name학명인가 일반명인가? 영어인가 한국어인가? 너무 일반적이다
endangered불리언이다. 이미 멸종한 동물은 true 인가 false 인가?
habitatstring 이라 범위가 지나치게 넓다. "tundra" 는 어떤 분류 체계의 값인가?
객체 이름 leopard변수명은 leopard 인데 name 은 "Snow Leopard" 다. 의도적인가?

좋은 예 — 분야의 표준 체계를 쓴다

animal.ts 모든 필드가 자기 자신을 설명한다 
/** IUCN 적색 목록 등급 */
type ConservationStatus =
  | "EX"  // Extinct
  | "EW"  // Extinct in the Wild
  | "CR"  // Critically Endangered
  | "EN"  // Endangered
  | "VU"  // Vulnerable
  | "NT"  // Near Threatened
  | "LC"; // Least Concern

/** 쾨펜의 기후 구분 */
type KoppenClimate =
  | "Af" | "Am" | "As" | "Aw"
  | "BSh" | "BSk" | "BWh" | "BWk"
  | "Cfa" | "Cfb" | "Cfc"
  | "Dfa" | "Dfb" | "Dfc" | "Dfd"
  | "EF" | "ET";

interface Animal {
  commonName: string;
  genus: string;
  species: string;
  status: ConservationStatus;
  climates: KoppenClimate[];
}

const snowLeopard: Animal = {
  commonName: "Snow Leopard",
  genus: "Panthera",
  species: "uncia",
  status: "VU",              // 취약
  climates: ["ET", "EF", "Dfd"], // 고산대, 아고산대
};
  • name → commonName, genus, species 로 나눴다. 무엇을 담는지 이름이 말해 준다.
  • endangered → IUCN 표준 분류 체계인 ConservationStatus 로 바꿨다. 불리언이 표현할 수 없던 상태들이 표현된다.
  • habitat → 쾨펜 기후 구분인 KoppenClimate 를 썼다. 배열이므로 여러 기후에 서식할 수 있다.
✓

모르는 값이 나오면 검색하면 된다

"ET" 가 무엇인지 모르는 사람은 "쾨펜 기후 ET" 를 검색하면 정답이 나온다. 반면 habitat: "tundra" 는 검색해도 이 코드가 무슨 뜻으로 썼는지 알 수 없다. 표준 용어를 쓰는 것 자체가 문서화다.

이름 지을 때 지킬 세 가지

  1. 같은 의미에는 같은 용어를 쓴다

    글이나 말에서는 같은 단어 반복을 피하려고 동의어를 쓰지만, 코드에서는 정반대다. 용어가 다르면 읽는 사람은 "뭔가 다른 것"이라고 생각한다. 정말 의미가 구분될 때만 다른 용어를 쓴다.

  2. 모호하고 의미 없는 이름을 피한다

    data, info, thing, item, object, entity. 다만 entity 처럼 해당 분야에서 특별한 의미를 갖는 경우는 예외다. 귀찮아서 붙이는 것과 정확해서 붙이는 것은 다르다.

  3. 데이터 자체가 무엇인지로 이름 짓는다

    포함된 내용이나 계산 방식이 아니라 개념으로 짓는다. INodeList 보다 Directory 가 낫다. 전자는 구현을, 후자는 개념을 말한다.

i

DDD 의 보편 언어와 같은 이야기 보강

도메인 주도 설계의 보편 언어(ubiquitous language) 가 정확히 이 아이템의 확장판이다. 도메인 전문가가 쓰는 단어를 코드가 그대로 쓰면, 회의에서 오간 말이 타입 이름으로 바로 이어진다. 번역이 필요 없는 상태가 목표다.

정리

  • 가독성을 높이고 추상화 수준을 올리기 위해 해당 분야의 용어를 사용한다.
  • 같은 의미에 다른 용어를 쓰지 않는다. 특히 전문 용어를 정확한 의미로만 쓴다.
  • data, info 같은 모호한 이름을 피한다.
  • 이름은 구현이 아니라 개념을 가리켜야 한다.
ITEM 37

공식 명칭에는 상표를 붙이기

구조적 타이핑을 의도적으로 끄는 기법. 타입 시스템에서 명목적 타이핑을 흉내 낸다.

핵심 구조가 같아도 다른 것으로 취급해야 하는 타입이 있다. 상표(brand)를 붙여 구분한다.

문제 — 구조적 타이핑이 지나치게 관대할 때

vector.ts 3D 벡터가 2D 함수를 통과한다 
interface Vector2D { x: number; y: number; }

function calculateNorm(p: Vector2D) {
  return Math.sqrt(p.x ** 2 + p.y ** 2);
}

calculateNorm({ x: 3, y: 4 });          // 5, 정상
calculateNorm({ x: 3, y: 4, z: 5 });    // 5, 오류 없음 — 하지만 틀렸다

아이템 4에서 본 그 문제다. 이번엔 해결한다.

해법 1 — 인터페이스에 상표 속성 붙이기

vector.ts _brand 한 줄로 봉인 
interface Vector2D {
  _brand: "2d";
  x: number;
  y: number;
}

function vec2D(x: number, y: number): Vector2D {
  return { x, y, _brand: "2d" };
}

function calculateNorm(v: Vector2D) {
  return Math.sqrt(v.x ** 2 + v.y ** 2);
}

calculateNorm(vec2D(3, 4));            // 5, 정상
calculateNorm({ x: 3, y: 4, z: 5 });
//            ~~~~~~~~~~~~~~~~~~~~ '_brand' 속성이 '{ x: number; y: number;
//                                 z: number; }' 형식에 없지만 'Vector2D'
//                                 형식에서 필수입니다.

{ x, y, z, _brand: "2d" } 를 만들어 우회할 수는 있지만, 그러려면 의도적으로 그렇게 써야 한다. 실수로 통과하는 일은 없어진다.

해법 2 — 기본형에 상표 붙이기

객체가 아니라 string 이나 number 를 구분해야 할 때는 인터섹션을 쓴다.

path.ts 
type AbsolutePath = string & { _brand: "abs" };

function listAbsolutePath(path: AbsolutePath) {
  // 절대 경로임이 타입으로 보장된다
}

function isAbsolutePath(path: string): path is AbsolutePath {
  return path.startsWith("/");
}

function f(path: string) {
  if (isAbsolutePath(path)) {
    listAbsolutePath(path); // 정상 — path 는 AbsolutePath
  }
  listAbsolutePath(path);
  //               ~~~~ 'string' 형식의 인수는 'AbsolutePath' 형식의
  //                    매개 변수에 할당될 수 없습니다.
}
i

런타임에는 아무것도 없다

AbsolutePath 는 실행 시점에는 그냥 문자열이다. _brand 속성은 만들어지지도 않는다. 순수하게 타입 체커를 위한 표식이며, 런타임 비용이 0 이라는 뜻이기도 하다. 진짜 검증은 isAbsolutePath 같은 타입 가드가 담당한다.

해법 3 — 검증된 상태를 타입에 담기

binary-search.ts 
type SortedList<T> = T[] & { _brand: "sorted" };

function isSorted<T>(xs: T[]): xs is SortedList<T> {
  for (let i = 1; i < xs.length; i++) {
    if (xs[i] < xs[i - 1]) return false;
  }
  return true;
}

function binarySearch<T>(xs: SortedList<T>, x: T): boolean {
  // 정렬되어 있음이 타입으로 보장되므로 안심하고 이분 탐색한다
  let low = 0, high = xs.length - 1;
  while (low <= high) {
    const mid = low + Math.floor((high - low) / 2);
    if (xs[mid] === x) return true;
    if (xs[mid] < x) low = mid + 1;
    else high = mid - 1;
  }
  return false;
}
✓

이 패턴의 진짜 이름

"검증했다"는 사실을 타입에 기록하는 것이다. isSorted 를 한 번 통과하면 그 정보가 타입에 남아, 이후 어디로 전달되든 다시 검증할 필요가 없다. ValidatedEmail, SanitizedHtml, UserId vs PostId 같은 곳에 그대로 응용된다.

↑

요즘 쓰는 상표 관용구 최신 반영

_brand 를 문자열로 쓰면 다른 사람이 우연히 같은 문자열을 써서 충돌할 수 있다. unique symbol 을 쓰면 선언한 파일 밖에서는 만들 수 없는 상표가 된다.

brand.ts 
declare const brand: unique symbol;

type Brand<T, B> = T & { readonly [brand]: B };

type UserId = Brand<string, "UserId">;
type PostId = Brand<string, "PostId">;

declare function getUser(id: UserId): User;

declare const postId: PostId;
getUser(postId);
//      ~~~~~~ 'PostId' 형식의 인수는 'UserId' 형식의
//             매개 변수에 할당될 수 없습니다.

둘 다 런타임에는 그냥 문자열이지만, 서로 절대 섞이지 않는다. 식별자를 다루는 코드에서 특히 값어치가 크다.

정리

  • 타입스크립트는 구조적 타이핑이라 값을 잘못 구분해도 문제가 드러나지 않을 때가 있다.
  • 구조적으로 같지만 개념적으로 달라야 하는 타입은 상표를 붙여 구분한다.
  • 상표는 런타임에 존재하지 않는다. 타입 시스템 안에서만 작동한다.
  • "검증을 통과했다"는 사실을 타입에 담는 용도로도 쓸 수 있다.
