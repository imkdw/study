세 번째 상자만 문제다 — 타입스크립트가 자바스크립트에 모듈 시스템도 클래스도 없던 시절에 직접 만든 기능들이다. 지금은 표준이 그 자리를 차지했다.

1. 열거형(enum)

enum.ts 
enum Flavor {
  VANILLA = 0,
  CHOCOLATE = 1,
  STRAWBERRY = 2,
}

let flavor = Flavor.CHOCOLATE; // Flavor.CHOCOLATE
Flavor[0];                     // "VANILLA"
문제 1 — 숫자 열거형은 역매핑을 만든다
enum.ts 범위 밖도 조용히 통과 
console.log(Flavor[0]); // "VANILLA"
console.log(Flavor[3]); // undefined — 오류 없음

이 역매핑은 원래 비트 플래그 구조를 위해 설계된 것이다. 일반적인 상수 집합에는 필요 없고, 위험만 남긴다.

문제 2 — const enum 은 런타임에서 완전히 사라진다
입력 
const enum Flavor {
  VANILLA = 0,
  CHOCOLATE = 1,
}
console.log(Flavor.CHOCOLATE);
출력 숫자로 인라인된다 
"use strict";
console.log(1 /* Flavor.CHOCOLATE */);

Flavor 라는 객체는 어디에도 존재하지 않는다. preserveConstEnums 를 켜면 객체는 남지만, 참조는 여전히 숫자로 인라인된다. 같은 문법이 설정에 따라 다르게 동작하는 것 자체가 문제다.

문제 3 — 문자열 열거형은 명목적 타이핑을 쓴다
enum.ts 타입스크립트 안에서만 통하는 규칙 
enum Flavor {
  VANILLA = "vanilla",
  CHOCOLATE = "chocolate",
}

let flavor = Flavor.VANILLA;
flavor = "chocolate";
//       ~~~~~~~~~~~ '"chocolate"' 형식은 'Flavor' 형식에
//                   할당할 수 없습니다.

값이 같은데도 할당이 막힌다. 타입스크립트의 다른 모든 곳은 구조적 타이핑인데(아이템 4) 여기만 예외다. 그리고 이 라이브러리를 자바스크립트에서 쓰면 "vanilla" 를 그냥 넘기게 되므로 두 언어에서 동작이 다르다.

flavor.ts 리터럴 유니온을 쓴다 
type Flavor = "vanilla" | "chocolate" | "strawberry";

let flavor: Flavor = "vanilla";
flavor = "chocolate";  // 정상
flavor = "mint";
//       ~~~~~~ '"mint"' 형식은 'Flavor' 형식에 할당할 수 없습니다.

열거형만큼 안전하고, 자바스크립트와 호환되며, 자동완성도 그대로 동작한다. 코드도 생성하지 않는다.

↑

enum 을 둘러싼 최근 변화 최신 반영

  • TS 5.0 — 모든 열거형이 유니온 열거형으로 통일되어 동작이 조금 일관되어졌다. 그래도 위 문제들은 남는다.
  • isolatedModules — const enum 은 파일 하나만 보고 변환할 수 없어 금지된다. esbuild·SWC·Babel 을 쓰면 자동으로 걸린다.
  • erasableSyntaxOnly(TS 5.8) — enum 을 아예 오류로 잡는다. Node.js 네이티브 실행에서는 쓸 수 없다.

즉 생태계가 enum 을 점점 더 밀어내고 있다. 꼭 상수 객체가 필요하다면 as const 객체가 대안이다.

alternative.ts 
const Flavor = {
  VANILLA: "vanilla",
  CHOCOLATE: "chocolate",
} as const;

type Flavor = (typeof Flavor)[keyof typeof Flavor];
// "vanilla" | "chocolate"

ITEM 54

객체를 순회하는 노하우

for-in 의 키가 string 인 것은 버그가 아니라 정확한 추론이다.

핵심 키와 값이 모두 필요하면 Object.entries, 키의 타입이 중요하면 let k: keyof T 를 선언한다.

왜 오류가 나는가

iterate.ts 키 타입이 어긋난다 
const obj = { one: 1, two: 2, three: 3 };

for (const k in obj) {
  // k: string
  console.log(obj[k]);
  //          ~~~~~~ 'string' 형식의 식을 '{ one: number; two: number;
  //                 three: number; }' 인덱스 형식에 사용할 수 없으므로
  //                 요소에 암시적으로 'any' 형식이 있습니다.
}
!

타입스크립트가 옳다

keyof obj 는 "one" | "two" | "three" 인데 for-in 이 주는 k 는 string 이다. 구조적 타이핑 때문에(아이템 4) obj 에는 선언되지 않은 속성이 더 있을 수 있고, 그 값이 number 라는 보장이 없다. for-in 은 상속된 열거 가능 속성까지 돌기도 한다.

해법 1 — 키의 타입을 선언한다

iterate.ts 
const obj = { one: 1, two: 2, three: 3 };

let k: keyof typeof obj;
for (k in obj) {
  const v = obj[k]; // number
  console.log(k, v);
}

다만 이건 런타임을 보장하지 않는 약속이다. 실제로 다른 키가 들어오면 타입은 거짓말이 된다. 아이템 18의 shouldUpdate 처럼 대상이 확실할 때 쓴다.

해법 2 — Object.entries

iterate.ts 가장 무난하다 
const obj = { one: 1, two: 2, three: 3 };

for (const [k, v] of Object.entries(obj)) {
  k; // string
  v; // number
  console.log(k, v);
}
// one 1
// two 2
// three 3

k 가 string 인 것은 여전하지만, 이번엔 값 v 의 타입이 정확하다. 대부분의 경우 이걸로 충분하다.

i

순회 방법 정리 보강

필요한 것방법키 타입
키와 값Object.entries(obj)string
값만Object.values(obj)—
키만, 타입 정확히let k: keyof typeof obj + for-inkeyof T
키만, 안전하게Object.keys(obj) as (keyof T)[]단언이 필요하다

Object.keys 가 string[] 을 반환하는 것도 같은 이유다. 타입스크립트 팀은 이를 의도적인 설계로 유지하고 있다. 정말 키의 집합이 고정되어야 한다면 객체 대신 Map 을 쓰는 것도 방법이다(아이템 58).

정리

  • 객체를 순회할 때, 키가 어떤 타입인지 정확히 파악하고 있다면 let k: keyof T 와 for-in 을 쓴다.
  • 객체를 순회하며 키와 값을 얻는 가장 일반적인 방법은 Object.entries 다.
  • for-in 의 키가 string 인 것은 구조적 타이핑의 결과이지 실수가 아니다.

ITEM 56

정보를 감추는 목적으로 private 사용하지 않기

private 는 컴파일하면 사라지는 약속이다. 진짜로 감추려면 다른 수단이 필요하다.

핵심 private 는 타입 시스템의 규칙일 뿐이다. 실제로 감추려면 # 비공개 필드(표준)나 클로저를 쓴다.

private 가 감추지 못하는 것

private.ts 단언 한 번이면 뚫린다 
class Diary {
  private secret = "cheated on my English test";
}

const diary = new Diary();
diary.secret;
//    ~~~~~~ 'secret' 속성은 private이며 'Diary' 클래스 내에서만
//           액세스할 수 있습니다.

(diary as any).secret;  // 통과
console.log(JSON.stringify(diary)); // {"secret":"cheated on my English test"}

컴파일된 자바스크립트에는 private 라는 흔적조차 없다. 언더스코어(_secret) 관례와 강제력 면에서는 똑같다.

방법 1 — 클로저

closure.ts 진짜로 접근할 수 없다 
declare function hash(text: string): string;

class PasswordChecker {
  checkPassword: (password: string) => boolean;

  constructor(passwordHash: string) {
    this.checkPassword = (password: string) => {
      return hash(password) === passwordHash;
    };
  }
}

const checker = new PasswordChecker(hash("s3cret"));
checker.checkPassword("s3cret"); // true
// passwordHash 에 접근할 방법이 없다
!

대가가 두 가지 있다

  1. passwordHash 가 생성자 스코프에 있으므로, 그것에 접근하는 모든 메서드를 생성자 안에 정의해야 한다.
  2. 메서드가 프로토타입이 아니라 인스턴스에 붙으므로 인스턴스마다 함수 복사본이 생긴다. 인스턴스가 많으면 메모리 낭비다.

방법 2 — # 비공개 필드 (권장)

private-field.ts 표준이고, 프로토타입 메서드를 쓸 수 있다 
class PasswordChecker {
  #passwordHash: string;

  constructor(passwordHash: string) {
    this.#passwordHash = passwordHash;
  }

  checkPassword(password: string): boolean {
    return hash(password) === this.#passwordHash;
  }
}

const checker = new PasswordChecker(hash("s3cret"));
checker.checkPassword("s3cret");  // true
checker.checkPassword("wrong");   // false

checker.#passwordHash;
//      ~~~~~~~~~~~~~ 'PasswordChecker' 클래스 외부에서는 프라이빗
//                    식별자이므로 '#passwordHash'에 액세스할 수 없습니다.

그럼 private 은 쓸모없나

아니다. "이 속성은 외부에서 쓰지 말라"는 설계 의도를 표현하는 데는 여전히 유효하다. 자동완성에서 가려지고, 실수로 건드리면 컴파일 오류가 난다. 이 아이템의 요지는 보안 수단으로 착각하지 말라는 것이다.

정리

  • public, protected, private 접근 제어자는 타입 시스템에서만 강제된다. 런타임에는 소용이 없고 단언으로 뚫린다.
  • 확실하게 데이터를 감추고 싶다면 클로저나 # 비공개 필드를 쓴다.
  • # 필드는 ES2022 표준이며, 프로토타입 메서드와 함께 쓸 수 있어 클로저보다 실용적이다.
ITEM 57

소스맵을 사용하여 타입스크립트 디버깅하기

실행되는 것은 컴파일된 자바스크립트다. 디버깅은 원본 타입스크립트로 하고 싶다면 소스맵이 필요하다.

핵심 sourceMap: true 한 줄로 원본 코드에 중단점을 찍을 수 있다. 다만 프로덕션에 노출되지 않게 관리해야 한다. 
flowchart LR
  TS["app.ts
내가 쓴 코드"] --> C["tsc"]
  C --> JS["app.js
실제 실행되는 코드"]
  C --> MAP["app.js.map
위치 대응표"]
  JS -.->|"//# sourceMappingURL"| MAP
  MAP -.->|"디버거가 되돌린다"| TS
소스맵은 위치 대응표다 — "출력의 12번째 줄 5번째 열은 원본의 8번째 줄 3번째 열"이라는 정보를 담는다. 디버거가 이를 읽어 원본을 보여 준다.

켜는 법

tsconfig.json 
{
  "compilerOptions": {
    "sourceMap": true
  }
}

컴파일하면 outDir 아래에 *.js 와 함께 *.js.map 이 생기고, .js 파일 끝에 //# sourceMappingURL=app.js.map 주석이 붙는다. 브라우저 개발자 도구나 Node 디버거가 이 주석을 보고 맵을 불러온다.

주의할 점

×

소스맵이 일반 사용자에게 로딩되지 않게 한다

  • 개발자 도구를 열지 않으면 로드되지 않으므로 성능 저하는 없다.
  • 하지만 소스맵에는 원본 소스 전체가 들어 있을 수 있다. 내부 주석, 미공개 로직, 심지어 지워야 했던 키가 그대로 노출된다.
  • 공개 서버에 .map 파일을 올리지 않거나, Sentry 같은 오류 추적 도구에만 비공개로 업로드한다.
i

소스맵 관련 옵션들 보강

옵션효과
sourceMap별도 .js.map 파일 생성
inlineSourceMap맵을 .js 안에 base64 로 삽입 (파일 수는 줄지만 크기가 커진다)
inlineSources원본 소스까지 맵 안에 포함 (편하지만 노출 위험이 커진다)
declarationMap.d.ts 의 소스맵. "정의로 이동"이 원본 .ts 로 간다 — 모노레포에서 특히 유용

번들러(webpack, Vite, esbuild)를 쓴다면 타입스크립트가 만든 맵과 번들러가 만든 맵이 이어져야 한다. 대부분 자동으로 처리하지만, 중단점이 엉뚱한 줄에 걸린다면 이 연결이 끊어진 것을 의심한다.

정리

  • 원본 코드가 아닌 변환된 자바스크립트 코드를 디버깅하지 않는다. 소스맵으로 원본을 본다.
  • 소스맵이 최종적으로 변환된 코드에 완전히 매핑되었는지 확인한다. 번들러를 거치면 맵이 끊길 수 있다.
  • 소스맵에 원본 코드가 그대로 포함되도록 설정되어 있을 수 있다. 공개되지 않도록 관리한다.
