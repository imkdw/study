ITEM 45

devDependencies에 typescript와 @types 추가하기

타입은 런타임에 존재하지 않는다. 그러니 런타임 의존성이 아니다.

핵심 typescript 와 @types/* 는 언제나 devDependencies 에 넣는다. 그리고 타입스크립트는 전역이 아니라 프로젝트 단위로 설치한다.

package.json 의 세 가지 의존성

필드언제 필요한가예
dependencies프로젝트를 실행하는 데 필수lodash, react
devDependencies개발과 테스트에만 필요. 런타임에는 불필요jest, typescript, @types/*
peerDependencies런타임에 필요하지만 버전 선택을 사용자에게 맡김플러그인이 요구하는 호스트 라이브러리
i

peerDependencies 가 쓰이는 곳

jQuery 플러그인이나 React 컴포넌트 라이브러리가 대표적이다. 플러그인이 자기 버전의 React 를 함께 설치해 버리면 React 인스턴스가 두 개가 되어 훅이 깨진다. 그래서 "당신 프로젝트의 React 를 쓰겠다"고 선언하는 것이다. 애플리케이션을 만들 때는 거의 쓸 일이 없다.

1. 타입스크립트 자체를 프로젝트 의존성으로

terminal 권장 
npm install --save-dev typescript
npx tsc --version
  • 팀원들이 모두 같은 버전을 쓴다는 보장이 생긴다. 버전이 다르면 오류 여부가 사람마다 달라진다.
  • 프로젝트 셋업이 npm install 한 줄로 끝난다.
  • CI 와 로컬이 같은 버전으로 돌아간다.
!

편집기도 같은 버전을 쓰게 한다 보강

VS Code 는 기본적으로 자체 내장 타입스크립트로 파일을 검사한다. 프로젝트 버전과 다르면 편집기와 tsc 의 결과가 어긋난다. Cmd+Shift+P → "TypeScript: Select TypeScript Version" → Use Workspace Version 으로 맞춰 둔다. 팀 전체에 적용하려면 .vscode/settings.json 에 "typescript.tsdk": "node_modules/typescript/lib" 를 넣는다.

2. 타입 의존성(@types)

정리

  • 타입스크립트를 시스템 레벨로 설치하지 않는다. 프로젝트의 devDependencies 에 넣어 팀 전체가 같은 버전을 쓰게 한다.
  • @types 의존성은 dependencies 가 아니라 devDependencies 에 포함한다.
  • 편집기가 쓰는 타입스크립트 버전도 프로젝트 버전에 맞춘다.
ITEM 46

타입 선언과 관련된 세 가지 버전 이해하기

타입스크립트에서는 의존성 하나에 세 개의 버전이 딸려 온다. 하나만 어긋나도 이상한 오류가 난다.

핵심 라이브러리 버전 / 타입 선언(@types) 버전 / 타입스크립트 버전 세 가지를 함께 본다.
버전이 세 개다 — 자바스크립트라면 왼쪽 하나만 신경 쓰면 됐다. 이 복잡성이 타입스크립트를 쓰는 비용의 일부다.
terminal 
npm install jest
npm install --save-dev @types/jest
package.json 버전이 정확히 일치하지 않는다 
{
  "dependencies": { "jest": "^29.7.0" },
  "devDependencies": { "@types/jest": "^29.5.12" }
}

@types 는 메이저·마이너까지만 라이브러리를 따라가고 패치 번호는 독립적이다. 시맨틱 버저닝을 잘 지키면 대체로 괜찮지만, 보장은 없다.

어긋나는 네 가지 상황과 대응

상황증상대응
라이브러리만 최신 신기능을 쓸 때마다 "속성이 없습니다" 오류 타입 보강으로 임시 대응(아이템 43) → 커뮤니티에 PR
타입만 최신 없는 API 를 있다고 믿는다. 런타임에 터진다 버전을 맞춘다 (올리거나 내린다)
타입 선언이 요구하는 TS 가 더 최신 타입 선언 파일 자체가 컴파일되지 않는다 TS 를 올리거나, @types/lodash@ts3.1 처럼 버전 태그를 쓴다
@types 의존성 중복 "식별자가 중복되었습니다" 오류 양쪽 @types 를 호환되는 버전으로 맞춘다
node_modules 구조 전역 네임스페이스에서는 이게 안 통한다

    bar/

          foo/index.d.ts  # @2.3.4  ← 중첩 설치로 격리

npm 은 버전이 충돌하면 중첩 폴더로 격리한다. 하지만 전역 네임스페이스를 쓰는 타입 선언(declare global, 전역 interface)은 격리할 수 없어서 중복 선언 오류가 난다.

타입을 라이브러리에 번들할 때의 네 가지 문제

  1. TS 버전을 고를 수 없다

    @types 라면 라이브러리 버전에 맞춰 타입만 따로 고를 수 있다. 번들된 타입은 그럴 수 없어서, 타입 선언 하나 때문에 TS 업그레이드가 막힐 수 있다.

  2. 내 타입이 외부 라이브러리에 의존할 때

    타입 선언이 @types/xxx 를 참조하는데 그게 devDependencies 에 있다면, 사용자에게는 설치되지 않는다. 자바스크립트 사용자에게는 아예 필요 없는 것을 dependencies 에 넣게 되는 딜레마가 생긴다.

  3. 과거 버전에 패치를 낼 수 없다

    구버전의 타입만 고치려면 그 버전으로 돌아가 릴리스해야 한다. DefinitelyTyped 는 버전별 폴더를 두어 이 문제를 해결한다.

  4. 패치 업데이트가 느려진다

    DefinitelyTyped 는 커뮤니티가 관리해 반응이 빠르다. 개인 관리 저장소가 같은 속도를 내기는 어렵다.

✓

공식 권장

  • 라이브러리가 타입스크립트로 작성되었다면 타입 선언을 내부에 포함한다. 컴파일러가 자동으로 뽑아 주므로 유지보수가 쉽다.
  • 라이브러리가 자바스크립트로 작성되었다면 타입 선언을 DefinitelyTyped 에 공개해 커뮤니티가 관리하게 한다.
i

요즘 도구들 보강

Are the types wrong?(attw) 는 패키지의 타입 선언이 ESM/CJS 양쪽에서 제대로 해석되는지 검사한다. 라이브러리를 배포한다면 CI 에 넣어 둘 만하다. 또 package.json 의 exports 필드로 조건별 타입 진입점을 지정하는 것이 types 필드 하나보다 정확하다.

정리

  • @types 의존성과 관련된 세 가지 버전이 있다. 라이브러리, @types, 타입스크립트.
  • 라이브러리를 업데이트하면 @types 도 함께 업데이트한다.
  • 타입스크립트로 작성된 라이브러리는 타입 선언을 자체 포함하고, 자바스크립트 라이브러리는 DefinitelyTyped 에 공개한다.
ITEM 47

공개 API에 등장하는 모든 타입을 익스포트하기

숨겨 봐야 소용없다. 어차피 뽑아낼 수 있으니 처음부터 내보내는 게 낫다.

핵심 공개 함수의 시그니처에 등장하는 타입은 이미 공개된 것이다. 사용자가 억지로 추출하게 만들지 말자.
santa.ts 타입을 숨겼다고 생각하지만 
interface SecretName {
  first: string;
  last: string;
}

interface SecretSanta {
  name: SecretName;
  gift: string;
}

export function getGift(name: SecretName, gift: string): SecretSanta {
  // ...
}

두 인터페이스는 export 되지 않았다. 하지만 getGift 는 공개되어 있고, 그 시그니처에 두 타입이 등장한다.

user.ts 사용자 쪽에서 얼마든지 꺼낸다 
import { getGift } from "./santa";

type MySanta = ReturnType<typeof getGift>;       // SecretSanta
type MyName = Parameters<typeof getGift>[0];     // SecretName
✓

그러니 그냥 내보낸다

타입을 숨기는 것은 보안이 아니라 불편일 뿐이다. 사용자는 ReturnType/Parameters 로 추출하거나, 최악의 경우 손으로 다시 정의한다. 그리고 그 손으로 정의한 타입은 내 라이브러리가 바뀌어도 따라오지 않는다.

i

실천 보강

  • 공개 API 를 index.ts 하나로 모으고, 거기서 함수와 타입을 함께 내보낸다.
  • export type { Foo } 문법을 쓰면 타입만 내보낸다는 의도가 분명해지고, isolatedModules/verbatimModuleSyntax 환경에서도 안전하다.
  • 내부 구현 타입까지 전부 내보낼 필요는 없다. 기준은 "공개 시그니처에 등장하는가" 하나다.
index.ts 
export { getGift } from "./santa";
export type { SecretName, SecretSanta } from "./santa";

정리

  • 공개 메서드에 등장한 어떤 형태의 타입이든 익스포트한다. 어차피 사용자가 추출할 수 있으니 편의를 제공하는 편이 낫다.
  • Parameters, ReturnType 같은 유틸리티 타입을 알아 두면 남의 라이브러리를 쓸 때도 도움이 된다.

ITEM 49

콜백에서 this에 대한 타입 제공하기

this 는 정의된 방식이 아니라 호출된 방식에 따라 결정된다. 콜백 API 를 만든다면 그 사실을 타입으로 알려야 한다.

핵심 콜백 타입의 첫 번째 매개변수로 this 를 선언하면, 타입스크립트가 this 의 타입을 검사하고 추론해 준다.

먼저 — this 는 왜 헷갈리는가

this-basics.ts 
class C {
  values = [1, 2, 3];

  logSquares() {
    this.values.forEach(function (val) {
      console.log(val * val);
    });
  }
}

const c1 = new C();
c1.logSquares(); // 1, 4, 9

const c2 = new C();
const method = c2.logSquares;
method();
// TypeError: Cannot read properties of undefined (reading 'values')

c1.logSquares() 는 두 가지 일을 한다. C.prototype.logSquares 를 호출하고, this 를 c1 로 바인딩한다. 참조만 꺼내 호출하면 두 번째가 빠진다.

this-basics.ts call 로 명시적으로 바인딩 
const c3 = new C();
const method3 = c3.logSquares;
method3.call(c3); // 1, 4, 9

클래스에서의 두 가지 선언 방식

button.ts 
class ResetButton {
  // 메서드 — 호출 시점에 this 가 결정된다
  onClick1() {
    console.log("Reset:", this);
  }

  // 화살표 필드 — 선언 시점(인스턴스 생성 시)에 this 가 고정된다
  onClick2 = () => {
    console.log("Reset:", this);
  };
}

const btn = new ResetButton();

const m1 = btn.onClick1;
m1(); // Reset: undefined

const m2 = btn.onClick2;
m2(); // Reset: ResetButton {}
메서드 onClick1()화살표 필드 onClick2 = () => {}
this 결정 시점호출 시점인스턴스 생성 시점

메모리효율적인스턴스 수만큼 함수 생성

i

원문 노트는 this 바인딩의 기초까지만 기록되어 있었습니다. 아래는 "콜백에서 this 에 대한 타입을 제공"하는 방법입니다.

listener.ts this 의 타입을 알 수 없다 
function addKeyListener(
  el: HTMLElement,
  fn: (e: KeyboardEvent) => void
) {
  el.addEventListener("keydown", (e) => {
    fn.call(el, e); // 호출할 때 el 을 this 로 넘기고 있지만
  });               // 타입에는 그 정보가 없다
}

addKeyListener(el, function (e) {
  this.innerHTML = "";
  // ~~~~ 'this'에 암시적으로 'any' 형식이 있습니다.
});
listener.ts this 를 첫 매개변수로 선언 
function addKeyListener(
  el: HTMLElement,
  fn: (this: HTMLElement, e: KeyboardEvent) => void
) {
  el.addEventListener("keydown", (e) => {
    fn.call(el, e);
  });
}

addKeyListener(el, function (e) {
  this.innerHTML = ""; // this 가 HTMLElement 로 추론된다
});
✓

얻는 것이 두 가지다

  1. 콜백 안에서 this 가 정확한 타입으로 추론된다.
  2. 구현부에서 fn(e) 로 잘못 호출하면 컴파일 오류가 난다. this 를 넘기는 것을 잊을 수 없다.

this 매개변수는 가짜 매개변수다. 컴파일하면 사라지고, 호출할 때 인수로 세지 않는다.

!

화살표 함수로는 받을 수 없다

콜백을 화살표 함수로 넘기면 this 가 바깥 스코프의 것으로 고정되므로 위 타입이 무의미해진다. this 를 쓰는 콜백은 function 키워드로 쓴다. 반대로, this 를 쓰지 않을 거라면 화살표 함수가 언제나 더 안전하다.

정리

  • this 바인딩이 동작하는 원리를 이해해야 한다. 호출된 방식이 결정한다.
  • 콜백 함수에서 this 를 쓴다면, 타입 정보를 명시하기 위해 this 를 콜백 타입의 첫 매개변수로 선언한다.
  • 클래스 메서드를 콜백으로 넘길 때는 화살표 필드로 선언하거나 bind 한다.
ITEM 50

오버로딩 타입보다는 조건부 타입을 사용하기

유니온 매개변수 때문에 오버로딩을 쓰고 있다면, 조건부 타입으로 바꿔 본다.

핵심 오버로딩은 각 선언을 독립적으로 처리하지만, 조건부 타입은 유니온에 분배되어 더 정확한 결과를 낸다.

문제 — 오버로딩으로는 관계를 표현할 수 없다

double.ts 반환 타입이 뭉개진다 
function double(x: number | string): number | string;
function double(x: any) {
  return x + x;
}

const num = double(100);     // number | string
const str = double("hello"); // number | string

double(100) 이 string 을 반환할 리 없는데 타입은 그렇게 말한다. 오버로딩 선언을 나눠 봐도 문제가 남는다.

double.ts 유니온을 넘길 수 없게 된다 
function double(x: number): number;
function double(x: string): string;
function double(x: any) { return x + x; }

const num = double(100);     // number ✓
const str = double("hello"); // string ✓

function f(x: number | string) {
  return double(x);
  //            ~ 'string | number' 형식의 인수는
  //              'number' 형식의 매개 변수에 할당될 수 없습니다.
}
×

왜 막히나

타입스크립트는 오버로딩 목록을 위에서부터 하나씩 시도한다. string | number 는 number 에도 string 에도 통째로는 맞지 않으므로 어느 선언도 매칭되지 않는다. 세 번째 오버로딩을 추가할 수는 있지만, 그러면 다시 반환 타입이 유니온으로 뭉개진다.

해법 — 조건부 타입

double.ts 모든 경우가 정확하다 
function double<T extends number | string>(
  x: T
): T extends string ? string : number;
function double(x: any) {
  return x + x;
}

const num = double(100);     // number
const str = double("hello"); // string

function f(x: number | string) {
  return double(x); // string | number ✓
}
i

분배 법칙이 핵심이다

조건부 타입은 유니온을 만나면 각 갈래에 따로 적용된 뒤 다시 합쳐진다.

distribute.ts 
// T = string | number 일 때
(string | number) extends string ? string : number
// ↓ 분배된다
(string extends string ? string : number) |
(number extends string ? string : number)
// ↓
string | number

이 성질 덕분에 오버로딩을 세 개 쓰던 것을 하나로 줄일 수 있다.

!

구현부 시그니처는 여전히 any 다

function double(x: any) 라는 구현 시그니처는 외부에 노출되지 않는다. 호출자는 조건부 타입 시그니처만 본다. 즉 아이템 40과 같은 구조다 — 단언과 any 를 함수 안에 가둔다.

정리

  • 오버로딩 타입보다 조건부 타입을 쓰는 것이 좋다. 유니온에 분배되어 더 정확하다.
  • 조건부 타입은 추가적인 오버로딩 없이 유니온 타입을 지원할 수 있다.
ITEM 51

의존성 분리를 위해 미러 타입 사용하기

필요한 모양만 선언하면, 남의 타입 패키지에 의존하지 않아도 된다.

핵심 구조적 타이핑(아이템 4) 덕분에, 필요한 메서드만 가진 인터페이스를 선언해도 실제 객체가 그대로 들어맞는다.

ITEM 52

테스팅 타입의 함정에 주의하기

타입도 테스트해야 한다. 그런데 순진하게 테스트하면 통과하는 오답이 잔뜩 생긴다.

핵심 변수 할당으로 타입을 테스트하면 "같은가"가 아니라 "할당 가능한가"를 테스트하게 된다. 전용 도구를 쓴다.

출발점 — 호출만 하는 테스트

map.test.ts 반환 타입을 전혀 확인하지 않는다 
declare function map<U, V>(array: U[], fn: (u: U) => V): V[];

map(["1", "2", "3"], (v) => +v); // 실행만 된다

1단계 — 변수에 할당해 본다

map.test.ts 
const lengths: number[] = map(["a", "aa"], (s) => s.length); // 통과

const wrong: string[] = map(["a", "aa"], (s) => s.length);
//    ~~~~~ 'number[]' 형식은 'string[]' 형식에 할당할 수 없습니다.

동작하지만 쓰지 않는 변수가 생긴다. 린터가 경고하고, 억제 주석이 늘어난다. 헬퍼 함수로 바꾼다.

map.test.ts 
function assertType<T>(x: T) {}

assertType<number[]>(map(["a", "aa"], (s) => s.length)); // 통과

함정 1 — 할당 가능성만 검사한다

trap.ts 타입이 달라도 통과한다 
const n = 12;              // 타입은 12
assertType<number>(n);     // 통과 — 12 는 number 의 서브타입이니까

assertType<{ name: string }[]>(
  map(["a", "b"], (v) => ({ name: v, hello: "world" }))
); // 통과 — hello 속성은 검사되지 않는다

우리가 알고 싶은 것은 "타입이 정확히 {name: string}[] 인가"인데, 실제로 검사된 것은 "할당 가능한가"다. 잉여 속성 체크(아이템 11)도 여기서는 작동하지 않는다.

함정 2 — 매개변수가 적은 함수는 언제나 할당 가능하다

trap.ts 둘 다 통과한다 
const add = (a: number, b: number) => a + b;
assertType<(a: number, b: number) => number>(add);    // 통과 (기대대로)

const double = (x: number) => x * 2;
assertType<(a: number, b: number) => number>(double); // 통과 (?!)
✓

이건 버그가 아니라 필수 기능이다

why.ts 
[1, 2, 3].map((item) => item * 2);
// map 의 콜백 타입은 (value, index, array) => U 인데
// 우리는 매개변수 하나만 쓴다

매개변수가 적은 함수를 할당할 수 없다면 거의 모든 콜백 코드가 컴파일되지 않는다. 그래서 타입스크립트는 이걸 허용한다. 타입 테스트에서만 문제가 되는 것이다.

매개변수와 반환 타입을 분리해서 검사하기

trap.ts 이제 잡힌다 
const double = (x: number) => x * 2;

let p: Parameters<typeof double> = null!;
assertType<[number, number]>(p);
//                           ~ '[x: number]' 형식의 인수는
//                             '[number, number]' 형식의 매개 변수에 ...

let r: ReturnType<typeof double> = null!;
assertType<number>(r); // 통과

함정 3 — this 가 있는 콜백

this-test.ts 
declare function map<U, V>(
  array: U[],
  fn: (this: U[], u: U, i: number, array: U[]) => V
): V[];

const names = ["john", "jane", "joe"];
assertType<number[]>(
  map(names, function (name, i, array) {
    assertType<string>(name);
    assertType<number>(i);
    assertType<string[]>(array);
    assertType<string[]>(this);   // this 타입도 검사한다
    return name.length;
  })
);

콜백의 this 까지 테스트하려면 map 의 시그니처가 this 매개변수를 선언해야 한다(아이템 49).

절대 하면 안 되는 것 — 모듈 선언

danger.d.ts 모든 테스트가 통과한다. 아무것도 검사하지 않으니까 
declare module "overbar";

이 한 줄은 해당 모듈 전체를 any 로 만든다. 테스트는 전부 초록불이 되지만 아무 의미가 없다. 타입 시스템 내부에서 암시적 any 를 발견하는 것은 매우 어렵다는 것이 이 아이템의 마지막 교훈이다.

결론 — 전용 도구를 쓴다

dtslint 스타일 
const names = ["john", "jane", "joe"];
map(
  names,
  function (
    name,  // $ExpectType string
    index, // $ExpectType number
    array  // $ExpectType string[]
  ) {
    this;  // $ExpectType string[]
    return name.length;
  }
); // $ExpectType number[]

dtslint 는 타입 체커와 독립적으로 동작한다. 편집기가 표시하는 타입 문자열을 그대로 비교하므로 할당 가능성 문제를 피한다. 다만 문자열 비교라서 string|number 와 number|string 을 다르게 볼 수 있다.

정리

  • 타입을 테스트할 때는 함수 타입의 동일성(identity)과 할당 가능성(assignability)의 차이를 알아야 한다.
  • 콜백이 있는 함수를 테스트할 때는 콜백 매개변수의 추론된 타입을 확인한다. this 도 잊지 않는다.
  • 테스트 자체에 any 를 쓰지 않도록 조심한다. declare module 이 대표적인 함정이다.
  • expect-type, tsd, dtslint 같은 전용 도구를 사용하는 것이 좋다.
