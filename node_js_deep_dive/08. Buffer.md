## 버퍼란

- 버퍼는 컴퓨터의 메모리 내부에 2진 데이터 보관 공간임
- 프로그래밍 언어에서 버퍼를 생성하는 순간 OS는 전체 메모리 공간 중 일부 영역을 확보해줌
- 프로그램이 실행되는 동안 차지한 공간을 다른 프로그램에게 내어주지 않는 작업을 Allocate(할당)이라고 부름
- 이 때 할당받는 보관함의 크기는 1Byte(8Bits) 크기다

<br>

## 버퍼와 배열의 차이

- 버퍼의 생김새는 배열과 매우 유사하게 연속적인 데이터(엘리먼트)로 되어있음
- 각 요소들에는 동일하게 인덱스가 부여되며 마찬가지로 0부터 시작함
- 버퍼의 경우 배열과 초기화시에 모든 값이 전부 0으로 들어가있음
- 하지만 버퍼의 크기의 경우 한번 할당하면 절대 변하지 않음. 초과된건 버려(Discard)짐

<br>

## 버퍼 사용 예시

```js
import { Buffer } from "node:buffer";

// 4바이트(32비트)의 메모리를 할당
const memContainer = Buffer.alloc(4);

memContainer[0] = 0x5a;
memContainer[1] = 0xc2;
memContainer[2] = 0x8f;
memContainer[3] = 0x03;

console.log(memContainer);
console.log(memContainer[0]); // 90
```

<br>

## 버퍼에서 음수 다루기

- 버퍼 내부 첫번째 요소에 직접 -42 라는 음수를 지정하고 이후 출력시 214가 나옴
- 이는 컴퓨터 내부에서 11010110 이라는 2진수 값으로 저장함
- 음수값을 저장하므로 11010110을 저장하게됨
- 하지만 그냥 출력하면 부호없는 양수로 출력해서 214가 나오게됨
- 그래서 실제로 숫자 데이터를 제대로 활용하려면 버퍼 객체에 내장된 전용 메서드를 써야함

```js
import { Buffer } from "node:buffer";

const memContainer = Buffer.alloc(4);

memContainer[0] = -42;

console.log(memContainer[0]); // 214
```

<br>

### 버퍼 내장 메서드를 통한 숫자 데이터 다루기

```js
import { Buffer } from "node:buffer";

const memContainer = Buffer.alloc(4);

memContainer.writeInt8(-42, 0);

console.log(memContainer[0]); // 214

/**
 * 0이라는 값은 offset 이라는 값을 의미함
 * 이는 버퍼의 시작 시준점으로 얼만큼 떨어졌나를 의미함
 * 즉 0인 경우 시작점에서 0byte 만큼 떨어진 지점, 0번째 인덱스를 뜻함
 */
console.log(memContainer.readInt8(0)); // -42
```

<br>

### 4바이트 버퍼 하나에 사용자 나이랑 점수를 나눠서 담기

## 극한의 속도 allocUnsafe

### 일반 buffer

- 버퍼를 생성하면 기본값은 항상 0으로 채워짐
- 메모리는 누구나 번갈아가며 사용하는 화이트보드와 같으므로 메모리를 공유하게됨
- OS로 부터 새로운 새로운 메모리를 할당받을때 빈 공간이 모두 0으로 채워지는데 이는 성능 관점에서 본다면 CPU에게는 무거운 작업임

```js
import { Buffer } from "node:buffer";

/**
 * 2KB의 공간을 할당함
 */
const buffer = Buffer.alloc(2048);
```

<br>

### allocUnsafe

- OS에서 메모리를 할당받자마자 빈 공간을 0이 아닌 원래 존재하던 값을 그대로 이어받음
- 해당 메모리 공간은 방금까지 컴퓨터의 다른 프로그램이 사용하던 정보가 그대로 남아있음
- 단순한 찌꺼기라면 다행이지만 상주하던 정보가 남아있다면 큰 문제가 될 수 있음
- 성능은 alloc 보다 좋은데 이는 0으로 fill 하는 과정이 없기 떄문임
- 이러한 메모리에 남아있던 정보를 가져오는 취약점을 Memory Disclosure 라고 부름

```js
const BUFFER_SIZE = 10240;
const unsafeBuffer = Buffer.allocUnsafe(BUFFER_SIZE);

let foundCount = 0;
for (let i = 0; i < BUFFER_SIZE; i++) {
  if (unsafeBuffer[i] !== 0) {
    const byte = unsafeBuffer[i];
    const binary = byte.toString(2).padStart(8, "0");
    const hex = byte.toString(16).toUpperCase().padStart(2, "0");
    const char = byte >= 32 && byte <= 126 ? String.fromCharCode(byte) : "?";

    // [Index 16] Hex: 0x58 | Bin: 01011000
    // [Index 17] Hex: 0xA0 | Bin: 10100000
    // [Index 18] Hex: 0x15 | Bin: 00010101
    // [Index 19] Hex: 0xB7 | Bin: 10110111
    // [Index 20] Hex: 0x09 | Bin: 00001001
    console.log(`[Index ${i.toString().padStart(5, "")}] Hex: 0x${hex} | Bin: ${binary}`);

    foundCount++;
  }
}
```

<br>

### unsafe를 사용하는 케이스

- 네트워크 소켓에서 쏟아지는 방대한 스트리밍 데이터 청크를 처리하는 경우 사용함
  - FS I/O -> Read Data -> Buffer 100% 채움
  - 위 과정처럼 I/O를 통해서 가져온 데이터를 버퍼에 100% 꽉 채우는 경우 전략적으로 사용
- 청크란 큰 데이터를 작게 나눈 단위인데 이렇게 쉴 새 없이 밀려오는 청크를 담아내는 공간이 버퍼임
- 쉴 새 없이 밀려오는 청크 데이터를 바로 전부 덮어씌울꺼라면 unsafe를 사용해도 안전함
- 단 빈 공간이 있는 상태로 유저에게 네트워크 응답으로 반환하는것 절대 금물임. 무조건 100% 써야함

<br>

### allocUnsafe가 진짜 빠른 이유

- 단순이 0으로 안채운다고 빠르다고 생각하면 안됨
- 실제로는 Node.js 내부 은밀한 캐싱 시스템인 Buffer Pool 덕분에 훨씬 빠름
- 노드 앱을 실행하는 그 순간 OS로 부터 약 8kb의 메모리 통을 할당받아서 가지고있음
- 그래서 매번 자원을 생성하지 않고 필요한 만큼 떼어다가 사용하게됨
- 여기서 알아야하는건 이렇게 버퍼 풀을 사용하기 위해서는 요구하는 크기가 풀 전체의 절반보다 작야야함
- 즉 4096보다 작으면 버퍼 품에서 뗴어오고, 그 이상은 OS에게 할당받음

```js
// 8192
console.log(Buffer.poolSize);

// 4096
// 비트 시프트 연산자로 이진수 데이터 전체를 오른쪽으로 한칸 밀어냄
// 가장 오른쪽을 허공에 그냥 버림, 즉 111100 -> 011110 이런식으로 바뀜
// 숫자를 2로 나누고 나머지를 버리는 연산과 동일함. 추가로 사칙연산보다 비트 연산이 훨씬 빠름
console.log(Buffer.poolSize >>> 1);
```

<br>

### allocUnsafeSlow

- allocUnsafeSlow 메서드도 존재하는데 이는 버퍼 풀을 사용하지 않고 바로 OS에서 할당받는 방식임
- 크기는 아주 작은데 장기간 보관되는 데이터를 버퍼 풀을 통해서 하게되면 불필요한 메모리 단편화가 생김
- 정말 필요할떄 써야하는데 버퍼 풀에서 땡겨오는 조건이 점점 작아지니 정말 필요할 때 사용할 수 없게됨

<br>

## Buffer를 별도의 C++로 만든 이유

- V8의 경우 내부에서 숫자는 무조건 64bit 부동소수점으로만 저장됨
- 1바이트짜리 0, 1을 다루기 위해 8바이트 크기의 거대한 자바스크립트 숫자를 쓰면 메모리 낭비가 발생함

<br>

### Stop the world

- GC가 돌아가는 동안 자바스크립트 프로그램이 완전히 멈춰버리는 치명적인 현상
- V8 힙 공간에 흩어진 자바스크립트 배열은 CPU 입장에서는 파편화된 쓰래기장임
- CPU가 데이터를 읽으려고할때 메모리 주소가 띄엄띄엄 떨어져있으면 캐시 미스가 발생해서 엄청 버벅거림
- 또한 V8의 GC가 이 조각들을 청소하는 경우 Stop the world 현상이 발생해서 프로그램이 멈춤
- 그래서 Node.js는 OS의 RAM에 바로 꽂히는 C++ 레벨의 연속된 메모리 공간인 Buffer를 만듦
- 이 영역은 GC가 간섭하지 못하고 CPU가 한번에 싹쓸이해서 읽어올 수 있는 궁극의 성능 구역임

<br>

## 엔디언

- buf.readInt32BE(), buf.writeInt32LE() 처럼 기괴한 메서드가 존재함
- 엔디언이란 컴퓨터가 메모리에 데이터를 어느 쪽 끝부터 채울 것인가를 의미함
- Big-Endian의 경우 큰 끝 번지 / 큼 놈부터를 의미하는데 12 34 56 78 형태로 저장함
- Little-Endian의 경우 작은 끝 번지 / 작은 놈부터를 의미하는데 78 56 34 12 형태로 저장함
- 인텔/AMD CPU의 경우 더하기/빼기 연산시 항상 1의 자리부터 시작해서 올림수를 계산하는데 CPU 하드웨어 회로 입장에서는 작은놈부터 저장된 게 압도적으로 계산하기 빠르고 효율적임

```js
// 파일명: buffer-methods.js
import { Buffer } from "node:buffer";

const buf = Buffer.allocUnsafe(4);

// 1. 네트워크 통신용 (Big-Endian)
// 가장 큰 자리수(0x12)가 0번 인덱스(낮은 주소)에 들어감
buf.writeUInt32BE(0x12345678, 0);

// Big-Endian (네트워크용): <Buffer 12 34 56 78>
console.log("Big-Endian (네트워크용):", buf); //

// 2. 인텔 CPU 연산용 (Little-Endian)
// 가장 작은 자리수(0x78)가 0번 인덱스(낮은 주소)에 들어감
buf.writeUInt32LE(0x12345678, 0);

// Little-Endian (인텔 CPU용): <Buffer 78 56 34 12>
console.log("Little-Endian (인텔 CPU용):", buf);
```

## 버퍼 크기 동적 할당

- 버퍼를 직접 할당하는 경우 가장 먼저 해야할 일은 공간이 얼마나 필요한지 구해야함
- 계산을 잘못 하는경우 Truncation 현상이 발생하여 데이터가 소실됨
- 이 때 버퍼에 넣는 데이터는 단순한 길이 기반이 아닌 바이트 크기를 재야함
- byteLength 메서드는 실제 버퍼를 파지 않고 C++ 스캐너가 문자열을 스캔하고 이후에 정확하게 필요한 용량을 계산해줌

```js
const myText = "Welcome to Node.js Deep Dive";

const badBuffer = Buffer.alloc(myText.length);

const actualSize = Buffer.byteLength(myText, "utf-8");
const goodBuffer = Buffer.alloc(actualSize);

// 글자 수: 28
console.log(`글자 수: ${myText.length}`);

// 실제 물리적 바이트 수: 28
console.log(`실제 물리적 바이트 수: ${actualSize}`);
```

## 메모리를 아끼는 buf.subarray

- 거대한 버퍼에서 특정 부분만을 잘라내서 읽고 싶을 때 공식 문서는 slice 대신 subarray를 권장함
- 제로 카피 방식으로 복사 자체를 안하고 완전히 새롭게 만듦
- subarray를 사용하면 C++ 엔진은 데이터를 복사하는 대신 수학 계산을 진행함
- 새로운 뷰의 시작 물리적 메모리 주소는 원본 시작주소 + 1byte(offset).
- 즉 새로운 뷰의 길이는 3 - 1 = 2byte
- 실제 물리적 이동은 1개도 없이 메모리를 바라보는 뷰만 만들어서 JS로 던져줌. 매우빠름
- 복제 방식은 아래처럼 존재함
  - Deep Copy : 새로운 영역을 할당하고 원본의 바이트를 전부 그쪽으로 복사함
  - Shallow Copy : 데이터를 복제하지 않고 원본 메모리를 가르키는 새 참조를 만듦. 단 원시값은 복사함
  - Zero Copy : 복사 과정 자체를 없애고 뷰를 만듦

```js
const giantBuffer = Buffer.from([1, 2, 3, 4, 5]);

// 인덱스 1부터 3직전(인덱스 2)까지 잘라냄
const tinyView = giantBuffer.subarray(1, 3);
console.log("잘라낸 뷰:", tinyView); // <Buffer 02 03>

// tinyView의 첫 번째 요소를 99로 수정해버리면?
tinyView[0] = 99;

// 원본 giantBuffer도 함께 오염됨
// 오염된 원본 버퍼: <Buffer 01 63 03 04 05>
console.log("오염된 원본 버퍼:", giantBuffer);
```

<br>

## 안전한 이식, 영혼의 복제 buf.copy

- 위 처럼 subarray의 얕은 복사 원본 오염을 막을려면 진짜 물리적인 빈 공간을 새로 만들어야함
- 만약 다른 비동기 흐름으로 데이터를 넘겨주는 경우는 만드시 물리적 copy를 거쳐서 메모리를 분리해야함
- 물리적 빈 메모리 공간 확보 -> memcpy를 OS 커널에 직접 명령(성능 최고)

```js
const source = Buffer.from([10, 20, 30]);
const target = Buffer.allocUnsafe(3); // 복사본 그릇

// source의 내용물을 target 안으로 물리적으로 완벽히 복사함
source.copy(target);

target[0] = 99;

// 안전하게 보존된 원본: <Buffer 0a 14 1e>
// 수정된 타겟 복사본: <Buffer 63 14 1e>
console.log("안전하게 보존된 원본:", source);
console.log("수정된 타겟 복사본:", target);
```

## 버퍼 스캐닝

- 배열에 존재하는 indexOf 메서드도 버퍼에 존재함. 순수한 16진수 또는 이진수를 C++ 속도로 찾아냄
- SIMD는 단일 명령 다중 데이터 처리로 CPU 레지스터로 데이터를 찍고 거기서 값을 찾아내는 병렬처리 마법임
- 매직넘버는 파일의 맨 앞부분의 숨겨진 고유한 16진수 암호로 PNG의 경우 89 50 4E 47로 시작함
- 명령이 하달되면 for문처럼 비교하지 않고 256bit 같은 넓은 공간에 32byte를 한 묶으로 올림
- 이후에 CPU의 SIMD 명령어를 통해서 하나의 지시로 수십개의 데이터를 한번에 비교해버림

```js
const fileData = Buffer.from("Hello\nWorld\nNodeJS");

// 1. 특정 바이트 찾기: 줄바꿈 문자('\\\\n', 16진수 0x0a) 스캔
const lineBreakPos = fileData.indexOf(0x0a); // 아스키코드 10번 (개행)
// 첫 줄바꿈은 인덱스 5번에 있습니다.
console.log(`첫 줄바꿈은 인덱스 ${lineBreakPos}번에 있습니다.`);

// 2. 버퍼 위변조 검증 : 무결성 검사로 로그인, 보안에 필수
const originalHash = Buffer.from([0xaa, 0xbb]);
const userLoginHash = Buffer.from([0xaa, 0xbb]);
// 버퍼가 똑같나요?: true
console.log("버퍼가 똑같나요?:", originalHash.equals(userLoginHash));

// 3. 버퍼 사전순 정렬
const buf1 = Buffer.from("ABC");
const buf2 = Buffer.from("BCD");
// 사전순 비교결과: -1
console.log("사전순 비교결과:", buf1.compare(buf2));
```

## 흩어진 조각 모으기

- 스트림을 통해서 대용량 크기의 비디오 파일이 들어온다면 64kb짜리 청크로 쪼개져서 밀려옴
- 이렇게 들어온 조각들을 하나로 합칠때 Buffer.concat을 사용함
- 사용 빈도가 매우 높지만 가상 무서운 함정이기도함
  - 메모리 스파이크 현상은 여러 청크를 하나로 합쳐서 커다란 공간을 할당할 때 공간이 부족해서 OOM이 발생할 수 있음
  - O(n)의 시간복잡도를 가지는데 데이터ㅗ가 늘어날수록 컴퓨터가 일해야 하는 시간과 메모리도 정비례해서 늘어남
- 클라이언트가 보낸 작은 용량의 json, text 등을 묶을때는 사용해도 괜찮음
- 하지만 수십메가바이트 이상의 이미지나 영상을 처리하는 경우 청크 그대로 외부 저장소나 DB로 흘려보내는 스트리밍 아키텍처를 필수로 구축해야함
- 내부에서는 byteLength로 길이를 계산하고 allocUnsafe를 통해서 OS로부터 공간을 새로 할당받음
- 이후에 copy(memcpy)를 통해서 물리적 데이터를 하나씩 이어붙임

```js
const chunk1 = Buffer.from("Node.js는 ");
const chunk2 = Buffer.from("정말 ");
const chunk3 = Buffer.from("강력합니다!");

const finalBuffer = Buffer.concat([chunk1, chunk2, chunk3]);

// 병합 결과: Node.js는 정말 강력합니다!
console.log("병합 결과:", finalBuffer.toString("utf-8"));
```
