## Readable Stream

- Writeable Stream이 데이터를 쓰기위한 스트림이라면 이건 데이터를 읽기위한 스트림임
- 이 때 차이점이 한가지 더 있는데 Writeable의 경우 내부 버퍼가 16kb인데 이건 64kb임
- 차이점이 존재하는 이유는 디스크나 스토리지 등이 데이터를 읽고 쓰는 하드웨어적 방식에 숨어있음

<br>

### 스토리지의 설계

- 스토리지는 데이터를 1 바이트씩 쪼개지 않고 일정한 덩어리를 나타내는 블록 단위로 묶어서 처리하도록 설계됨
- 데이터를 긁어오는 I/O 작업은 컴퓨터 입장에서는 아주 무거운 작업임
- CPU가 램에서 연산하는 속도는 매우 빠르지만 디스크에서 무언가 가져올려면 시스템 콜을 거쳐야함
- 또한 구형 하드의 경우 데이터를 찾기 위해서 디스크 헤드를 직접 움직여야하며 SSD의 경우도 내부 플래시 메모리 칩에 전기를 보내서 읽어야함
- 이 처럼 디스크 I/O 작업은 매우 무거우므로 스토리지 블록 단위의 64KB 단위로 가져와서 최적화함

```ts
import fs from "node:fs/promises";

(async () => {
  const fileHandleRead = await fs.open("./server_logs.txt", "r");

  /**
   * 처음 생성된 직후에는 가만히 멈춰있으므로 이벤트 리스너를 통해서 처리해야함
   */
  const streamRead = fileHandleRead.createReadStream();

  streamRead.on("data", (chunk) => {
    // ==================================================
    // <Buffer 0a 32 30 32 36 2d 30 31 2d 30 31 54 30 39 3a 35 32 3a 32 31 2e 33 33 36 5a 20 44 45 42 55 47 20 5b 6f 72 64 65 72 2d 73 76 63 40 65 64 67 65 2d 6b 72 ... 65486 more bytes>
    // 65536
    // ==================================================
    console.log("=".repeat(50));
    console.log(chunk);
    console.log(chunk.length);
    console.log("=".repeat(50));
  });
})();
```

## 스트림을 통해서 대용량 파일 읽고 다시 쓰기

### 백프레셔 제어가 없는 안티패턴

```ts
import fs from "node:fs/promises";

(async () => {
  /**
   * 큰 파일을 가져오기
   */
  const fileHandleRead = await fs.open("./server_logs.txt", "r");

  /**
   * 데이터를 저장할 새로운 목적지
   */
  const fileHandleWrite = await fs.open("dest.txt", "w");

  /**
   * 읽기 스트림 생성
   */
  const streamRead = fileHandleRead.createReadStream({
    highWaterMark: 64 * 1024, // 65536 바이트로 읽기 스트림 내부 버퍼의 기본값
  });

  const streamWrite = fileHandleWrite.createWriteStream();

  /**
   * 파이프가 꽉 차서 write 메서드가 false를 반환하는데도 계속 데이터를 들이부음
   * 이러한 현상은 안티패턴임
   */
  streamRead.on("data", (chunk) => {
    streamWrite.write(chunk);
  });
})();
```

### 백프레셔 제어를 통한 안전한 처리

```ts
import fs from "node:fs/promises";

(async () => {
  console.time("복사_작업시간");

  /**
   * 큰 파일을 가져오기
   */
  const fileHandleRead = await fs.open("./server_logs.txt", "r");

  /**
   * 데이터를 저장할 새로운 목적지
   */
  const fileHandleWrite = await fs.open("dest.txt", "w");

  /**
   * 읽기 스트림 생성
   */
  const streamRead = fileHandleRead.createReadStream({
    highWaterMark: 64 * 1024, // 65536 바이트로 읽기 스트림 내부 버퍼의 기본값
  });

  /**
   * 쓰기 스트림 생성
   * 쓰기의 경우 내부 버퍼가 16kb임
   */
  const streamWrite = fileHandleWrite.createWriteStream();

  /**
   * 파이프가 꽉 차서 write 메서드가 false를 반환하는데도 계속 데이터를 들이부음
   * 이러한 현상은 안티패턴임
   */
  streamRead.on("data", (chunk) => {
    if (!streamWrite.write(chunk)) {
      /**
       * 만약 쓰기 버퍼가 꽉 차버린 상태라면 잠깐 읽기 스트림을 중지시킴
       * 해당 명령은 OS에게 더 이상 디스크에서 데이터를 읽어오지 말라고 시스템 콜을 보내게됨
       */
      streamRead.pause();
    }
  });

  streamWrite.on("drain", () => {
    /**
     * 쓰기 스트림 내부 버퍼가 비워졌다면 다시 디스크에서 데이터를 읽어오기 위해 명령을 내림
     */
    streamRead.resume();
  });

  streamRead.on("end", () => {
    console.log("모든 데이터 처리 완료");
    streamWrite.end();
    console.timeEnd("복사_작업시간");

    // 모든 데이터 처리 완료
    // 복사_작업시간: 188.583ms
  });
})();
```

## 대규모 데이터 처리해보기

### 문자열의 인코딩 방식과 시스템에서의 이진데이터 처리에 대한 충돌

- 주석을 보면 마지막 블록이 그냥 짤린걸 볼 수 있음
- 문자열은 1, 3, 4 바이트 등 다양한 단위로 저장되지만 시스템의 경우 이런걸 신경쓰지 않고 칼같이 자름
- 스트림을 다루는 경우 한정된 버퍼안에서 데이터를 처리하기 때문에 데이터 조각 절단 현상이 빈번하게 발생하며 이를 방지해야함
- createReadableStream 옵션으로 `encoding` 옵션을 지정하면 불완전한 다중바이트 문자를 잠깐 보관해줘서 깨짐 현상은 완화되지만 64KB 단위로 칼같이 짜르는 상황에서 의미있는 문장이나 단어가 짤리는건 막아주지못함

```ts
import fs from "node:fs/promises";

(async () => {
  console.log("시작");

  const fileHandleRead = await fs.open("massive_logs.txt", "r");

  const streamRead = fileHandleRead.createReadStream({
    highWaterMark: 64 * 1024,
  });

  streamRead.on("data", (chunk) => {
    /**
     * 이진 데이터 -> UTF-8 문자열 변환
     * 이후 로그가 저장된 형식인 이중 공백을 기반으로 텍스트를 분리함
     */
    const logs = chunk.toString("utf-8").split("  ");

    // -- 64KB의 새로운 데이터 조각 도착 --
    // 처음 조각: [INFO] 시스템 식별자 0 - 데이터 처리 완료
    // 마지막 조각: [INFO] 시스템 식별자 1092 -
    console.log("-- 64KB의 새로운 데이터 조각 도착 --");
    console.log(`처음 조각: ${logs[0]}`);
    console.log(`마지막 조각: ${logs[logs.length - 1]}`);

    streamRead.pause();
  });
})();
```

### 잘리는 데이터를 이어붙이는 알고리즘

- 꼬리 데이터를 임시 변수에 붙여두고 다음에 이를 붙이면서 절단 현상을 완화함
- 하지만 아래 코드의 경우는 문제점이 존재하는데 64KB 한계에서 완벽하게 짤린 데이터의 경우도 불필요하게 자르고 이어붙임

```ts
import fs from "node:fs/promises";

console.time("time");

const fileHandleRead = await fs.open("massive_logs.txt", "r");
const fileHandleWrite = await fs.open("filtered_erros.txt", "w");

const streamRead = fileHandleRead.createReadStream({
  highWaterMark: 64 * 1024,
  encoding: "utf-8",
});

const streamWrite = fileHandleWrite.createWriteStream();

let leftover = "";

streamRead.on("data", (chunk) => {
  const logs = chunk.toString("utf-8").split("  ");

  /**
   * 마지막 요소의 경우 구분자로 끝나지 않았을 수 있음
   * 이는 64KB 버퍼에 딱 맞게 자르는 상황에서 잘린 조각이 발생할 수 있는데 이를 다음 청크로 넘겨서 이어붙이기 위한 작업임
   */
  leftover = logs.pop() || "";

  /**
   * 이전 청크에서 넘어온 조각을 이번 청크의 첫 로그 앞에 이어붙임
   * 전에 짤렸던 청크라도 이번 루프에서 다시 복원됨
   */
  if (leftover !== "") {
    logs[0] = leftover + logs[0];
  }

  logs.forEach((log) => {
    if (log.includes("[ERROR]")) {
      if (!streamWrite.write(log + "  ")) {
        streamRead.pause();
      }
    }
  });
});

streamWrite.on("drain", () => {
  streamRead.resume();
});

streamRead.on("end", async () => {
  /**
   * 파일의 끝인 경우 뒤에 붙일 청크가 없을 수 있음
   * 만약 마지막에 청크가 남아있다면 읽기 스트림이 종료되는 시점에 마지막으로 저장함
   */
  if (leftover.includes("[ERROR]")) {
    streamWrite.write(leftover + "  ");
  }

  // 더 이상 쓸 데이터가 없음을 알리고(버퍼에 남은 건 flush 된다) 핸들을 정리한다
  streamWrite.end();

  await fileHandleRead.close();
  await fileHandleWrite.close();

  console.timeEnd("time");
});
```

## StringDecoder

### OS에서의 한글

- 일반적으로 사용하는 UTF-8 환경에서 한글이나 이모지는 한 글자당 3바이트를 차지함
  - ex) 식 이라는 한글은 EC + 8B + 9D 형태로 저장됨
- 이 때 깨진 한글을 toString()으로 복원하면 글자가 깨져버림
  - Readable Stream에서 내부 버퍼는 64KB인데 데이터 처리 도중에 64KB에 걸려서 한글이 깨진다고 가정함
  - 식 이라는 글자를 제대로 처리하기 위해서는 EC, 8B, 9D를 모두 저장해야하는데 짤려서 EC만 저장되면 해당 한글은 깨져버림
  - 단순한 toString() 메서드는 이를 처리하는 경우 깨졋다고 판단하여 `?` 같은 깨진 문구를 반환함
  - 이후 청크에서 8B, 9D가 넘어온다고해도 이미 회손된 글자이므로 다시 복원할 수 없게됨
- 이를 위해서 Node.js에서는 바이트 경계 상태 보호기인 StringDecoder가 존재함

<br>

### StringDecoder 동작원리

- StringDecoder의 경우 불완전한 바이트를 감지하며 만약 잘못된 버퍼가 들어오면 toString() 처럼 즉시 변환하지 않으
- 내부에 버퍼가 존재하며 불완전환 바이트를 저장해두었다가 다음번 데이터 청크가 들어오면 앞에 저장한 데이터를 다시 복원하는 역할을 해줌
- `식` 예시에서 디코더에 EC만 들어온 경우 깨졌다고 판단하여 EC를 내부 버퍼에 저장, 이후에 8B, 9D가 다음 청크로 넘어오면 다시 조립하고 복원함
- StringDecoder 내부 버퍼는 Readable Stream의 64KB 처럼 큰 공간이 아닌 3~4KB 사이의 작은 공간이므로 메모리 사용량은 걱정하지 않아도 괜찮음

<br>

### 로그를 저장하는 경우 수학적 논리로 깨졌는지 증명하기

- 앞서 저장한 시스템 로그의 경우 1, 2, ... N 처럼 모든 로그가 1씩 증가하는 방식으로 저장됨
- 만약 버퍼 크기의 한계로 인해서 로그의 원문이 잘못 짤린경우 시스템 로그의 숫자를 통해서 확인이 가능함
