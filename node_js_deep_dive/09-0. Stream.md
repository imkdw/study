## OS 입장에서 파일?

- 파일이라는 개념은 매우 포괄적이지만 CS 지식에서 파일은 사용자에 의해 생성된 0, 1의 집합임
- 이 때 같은 0, 1 시퀀스라도 어떻게 해석하는지에 따라서 완전히 달라짐
  - 예를 들어서 같은 0, 1 덩어리를 이미지라고 해석하거나, 텍스트라고 해석하거나에 따라 완전 다름
- 디스크 입장에서는 실행프로그램, 이미지, 코드 등 모든게 다 파일로 이루어지며 이를 관리하기 위한 메타데이터가 함께 저장되어야함
- OS는 이러한 파일을 직접 열 수 없으며 응용프로그램을 통해서 해당 값을 해석하게됨

<br>

## Node.js에서 파일을 해석하는 방식

- 노드는 물리적인 하드웨어에 직접 접근할 수 없고 방법도 모름
- 그저 OS 위에서 돌아가는 파일중 하나이며 무언가 요청이 발생하면 OS에 요청하는데 이 과정에서 소통하는 방식을 System Call 이라고 부름
- 예를 들어서 파일을 읽을려면 open() 콜, 이름 변경하면 rename() 콜 이런식으로 동작함
- 노드는 시스템 콜을 OS에 전달하기 위해서 내부적으론 libuv 라는 비동기 입출력 라이브러리를 사용함
  - JS Code -> libuv -> OS System Call 형태임

<br>

## Node.js의 fs 모듈에서 제공하는 API

- Promise, Callback, Sync 등 다양한 방식을 제공함
- 기능적인 측면에서만 본다면 이들은 전혀 다르지 않으며 뭘 써도 동일하게 동작함
- 이 때 가능하면 모든 단계에서 Promise API를 적용하는걸 강력하게 권장하며 fs외에도 모두 동일함

<br>

### 뭘 써야할지

- 이 떄 Callback API의 경우 정말 극도로 예외정인 상황(CPU 연산력 한계까지 올리기)에서 사용함
  - 공식문서 기준으로 Promise API보다 아주 미세하게 Callback이 더 빠르다고 명시되어있음
- Sync(동기적) API의 경우는 90% 환경에서 무조건 피해야함
  - 대표적으로는 서버가 실행되기 이전에 환경변수를 읽어오는 등 과정에서만 사용해야함
  - 런타임에는 절대적으로 지양해야하는 API임
  - 동기적 호출의 경우 CPU를 블록킹하기에 싱글스레드 환경에서는 매우 위험함

```js
import promiseFs from "node:fs/promises";
import fs from "node:fs";

/**
 * Promise API
 */
try {
  await promiseFs.copyFile("./src.txt", "./copied-src.txt");
  console.log("Promise API : Complete!");
} catch (error) {
  console.log("error: ", error);
}

/**
 * Callback API
 */
fs.copyFile("./src.txt", "./copied-src.txt", (error) => {
  if (error) {
    console.log("error: ", error);
    return;
  }

  console.log("Callback API : Complete!");
});

/**
 * Sync API
 */
fs.copyFileSync("./src.txt", "./copied-src.txt");
console.log("Sync API : Complete!");
```

## 파일 변경사항 감지 커맨드 센터 만들기

```js
import { access, open, watch, writeFile, unlink, rename, appendFile, open } from "node:fs/promises";

const COMMAND_FILE = "./file-commands";

/**
 * 파일 존재 여부를 확인함
 * 과거에 사용하던 fs.existsSync()와 동일한 기능을 제공함
 */
async function fileExists(path) {
  try {
    await access(path);
    return true;
  } catch {
    return false;
  }
}

/**
 * 명령어 해석기
 */
async function executeCommand(commandString) {
  if (typeof commandString !== "string") {
    return;
  }

  /**
   * trim의 경우 선택이 아닌 생존 스킬로 문자열을 다루는 순간 필수
   * \n, \r 등 이러한 OS에서 숨어드는 문자를 제거함
   * 제거하지 않고 그대로 문자열 일치여부 비교를 하게되면 이러한 숨어드는 문자로 인해서 예상치 못한 결과를 얻게됨
   */
  const command = commandString.trim();
  if (!command) {
    return;
  }

  if (command.startsWith("create a file ")) {
    const filePath = command.replace("create a file ", "").trim();
    await createFile(filePath);
  }
}

async function createFile(path) {
  if (typeof path !== "string") {
    return;
  }

  /**
   * writeFile 메서드는 지정된 경로에 파일을 생성하지만 이미 있다면 그걸 덮어씌움
   */
  if (await fileExists(path)) {
    return console.log(`${path} 파일이 이미 존재합니다.`);
  }

  try {
    await writeFile(path, "");
    console.log(`${path} 파일이 생성되었습니다.`);
  } catch (error) {
    console.error(`${path} 파일 생성 실패: ${error}`);
  }
}

async function deleteFile(path) {
  try {
    /**
     * 직관적으로 delete, remove 등 을 호출하지 않고 unlink를 사용함
     * inode : index node의 줄임말로 실제 파일이 하드에 몇번 주소에 있는지 등 메타데이터를 담은 주소록
     * link : inode 주소록과 파일을 연결해주는 행위
     * 즉 하나의 물리적 데이터인 inode에 여러개의 이름표르 붙여서 관리하는 방식
     *
     * unlink : 파일을 지운다는건 실제 하드에 저장된 데이터를 0으로 바꾸는게 아닌 이름표와 inode의 연결을 끊어버림
     * 연결이 끊어진건 OS에 의해서 빈 공간으로 취급되며 나중에 다른 데이터로 덮어쓸 수 있음
     */
    await unlink(path);
  } catch (e) {
    /**
     * 삭제할 파일이 이미 삭제되었거나 없다면 OS는 노드에게 ENOENT 에러를 반환함
     * 이는 Error NO ENTry라는 뜻으로 해당 항목이 없다는 뜻임
     * OS가 주소록을 뒤져봤지만 삭제할려는 파일이 없다는 뜻인데 이는 시스템 오류보단 논리적 에러에 가까움
     */
    if (e.code === "ENOENT") {
      console.log(`${path} 파일이 존재하지 않습니다.`);
    } else {
      console.error(`${path} 파일 삭제 실패: ${e.message}`);
    }
  }
}

async function renameFile(oldPath, newPath) {
  try {
    /**
     * 이름을 바꾸는거 외 newPath에 다른 경로를 지정하면 다른 폴더로 파일을 옮김
     */
    await rename(oldPath, newPath);
  } catch (e) {
    if (e.code === "ENOENT") {
      console.log(`${oldPath} 파일이 존재하지 않습니다.`);
    } else {
      console.error(`${oldPath} 파일 이름 변경 실패: ${e.message}`);
    }
  }
}

let prevContent = "";

async function appendFile(path, content) {
  /**
   * 파일을 수정한다면 임시파일, 덮어쓰기, 메타데이터 갱신 등 다양한 작업이 백그라운드에서 연쇄적으로 발생
   * 그래서 이러한 이벤트가 발생하면 노드에게 change 이벤트를 여러번 날리는 현상이 자주 발생함
   * 그래서 아래 if를 통해서 직전에 추가한 내용이랑 완전히 일치하면 중복된 값으로 인식해서 함수를 종료시킴
   */
  if (prevContent === content) {
    return;
  }

  try {
    /**
     * appendFile 메서드는 파일에 내용을 추가하는 메서드임
     * 이는 파일을 전부 메모리에 읽어들여서 마지막에 콘텐츠를 추가하고 저장하는 방식으로 동작하지 않음
     * OS 커널 레벨에서 파일의 맨 끝 포인터 위치를 찾고 해당 위치에 데이터를 쏙 추가함
     * 단 사용자가 만약 똑같은 텍스트를 여러번 입력하는 경우 막히는 문제점이 존재함
     */
    await appendFile(path, content);
    prevContent = content;
  } catch (e) {
    console.log(`${path} 파일 쓰기 실패: ${e.message}`);
  }
}

 * 명령어 해석기 뼈대 & 생성/삭제 파싱
 */

  if (typeof commandString !== "string") {
    return;
  }

  const command = commandString.trim();
  if (!command) {
    return;
  }

  // 파일 생성
  if (command.startsWith("creeate a file")) {
    await createFile(command.replace("create a file", "").trim());
  }
  // 파일 삭제
  else if (command.startsWith("delete the file ")) {
    await deleteFile(command.replace("delete the file ", "").trim());
  }
  // 파일 이름 변경 (정규식 활용)
  else if (command.startsWith("rename the file ")) {
    /**
     * ^은 문장의 시작, $는 문자의 종료를 뜻함. 이는 정확한 패턴 매칭으로 엄격한 기준임
     * .은 띄어쓰기를 포함한 어떤 문자든 1개를 의미함
     * +는 그 문자가 1개 이상 연속됨을 의미함
     * 즉 (.+)는 해당 정규식 위치에 존재하는 문자열을 저장하는 역할을 수행함
     */
    const match = command.match(/^rename the file (.+) to (.+)$/);
    if (match) {
      /**
       * match는 RegExpMatchArray 타입을 가진다
       * 0번째 인덱스에는 전체 문장을 저장함
       * 그 이후 1, 2번째에는 (.+)식으로 캡처한 데이터를 보관함
       */
      await renameFile(match[1].trim(), match[2].trim());
    } else {
      console.log("잘못된 파일 이름 변경 명령어 형식");
    }
  }
  // 파일 내용 추가
  else if (command.startsWith("add to the file ")) {
    /**
     * /s 기호는 엔진의 동작방식을 지시하는 플래그임
     * 기본적으로 정규표현식의 . 표현은 개행 인식을 못하고 즉시 탐색이 중단됨
     * 이러면 문장의 첫 줄만 캡처하고 나머진 잘려나가는 문제가 발생하는데 /s를 사용하면 여러줄의 데이터 캡쳐가 가능함

    } else {
      console.log("잘못된 내용 추가 명령어 형식");
    }
```

## 스트림을 언제? 왜? 쓰는지

- 대용량 동영상을 다운로드, 대용량 CSV 파일을 다운로드 등 할때 스트림을 사용함
- 실시간 채팅이나 화상회의에도 쓰이는데 한정된 서버 메모리로 대용량 데이터를 처리할 때 유일한 방법임
- 스트림은 Writeable, Readable Stream 2개로 구분됨
- 이후에 Duplex Stream, Transform Stream 등 다양한 기술이 존재함임

## 100만개의 로그 저장하기

- 아래 코드의 경우 100만번의 쓰기 작업이 하나씩 완료될 때 까지 매번 기다려야함
- 이 경우 CPU가 비동기 작업을 하나하나 조율하느라 전체 작업 완료를 위해 유휴시간이 길어질 수 밖에 없음
- 하나의 코어가 100만번의 작업을 완료시킬때 까지 메모리는 적은 용량으로 아주 안정적인 상태를 유지함
- 이는 메모리를 한번에 올려두지 않고 처리하고 지우고를 반복함
- 하지만 이렇게 오래걸리면 실무에선 좋지 않음

```js
import fs from "node:fs/promises";

async function writeManyPromises() {
  console.time("작업시간");

  const fileHandle = await fs.open("server_logs.txt", "w");

  for (let i = 0; i < 1_000_000; i++) {
    await fileHandle.write(`[Log] ${i}님의 데이터 처리 완료`);
  }

  await fileHandle.close();

  // 작업시간: 13.239s
  console.timeEnd("작업시간");
}

writeManyPromises();
```

## 100만번의 로그 저장을 한번에 비동기 콜백 방식으로 던지기

- 작업시간 자체는 1초 미만으로 아주 빠르게 동작함
- 하지만 한번에 대량의 데이터를 메모리에 올리므로 클라우드 서버 등에서는 OOM이 발생할 수 있음
- 게다가 OS 레벨에서 쓰기 순서 보장이 불가능하므로 경쟁 상태가 발생하며 데이터 무결성이 훼손됨

```js
import fs from "node:fs";

console.time("작업시간");

fs.open("server_logs.txt", "w", (err, fd) => {
  if (err) {
    throw err;
  }

  for (let i = 0; i < 1_000_000; i++) {
    fs.write(fd, `[Log] ${i}님의 데이터 처리 완료`, (err) => {
      if (err) {
        throw err;
      }
    });
  }
});

// 작업시간: 0.114ms
console.timeEnd("작업시간");
```

## 100만번의 로그 저장을 동기 방식으로 처리하기

- 비동기 방식의 open과 동일하지만 메인스레드를 차단하는 방식으로 동작함
- 작업 속도도 매우 빠르지만 치명적인 문제가 존재함
- 해당 코드는 메인스레드를 차단하므로 다른 작업을 처리할 수 없이 완전히 차단됨
- 즉 거대한 로그를 처리하는 동안 다른 작업을 아무것도 못하고 대기하게됨

```js
import fs, { fdatasync } from "node:fs";

console.time("작업시간");

const fd = fs.openSync("server_logs.txt", "w");

for (let i = 0; i < 1_000_000; i++) {
  fs.writeSync(fd, `[Log] ${i}님의 데이터 처리 완료`);
}

fs.closeSync(fd);

// 작업시간: 2.220s
console.timeEnd("작업시간");
```

## 스트림을 통해 로그 저장해보기

- 좋은 코드같지만 현업에선 사용하면 안되는 코드임
- 비동기 방식은 메모리가 터지고, 동기식 처리는 메인스레드가 블록킹되고, 스트림은 속도는 빠르지만 메모리 폭발 가능성이 있음
- 이러한 문제를 해결하기 위한 완벽한 해결책은 스트림의 백프레셔를 올바르게 제어하는 것에 있음

```js
import fs from "node:fs/promises";

(async () => {
  console.time("작업시간");

  const fileHandle = await fs.open("server_logs.txt", "w");

  /**
   * 스트림 파이프라인 시작점을 생성함
   * 내부적으론 16KB의 내부 버퍼 크기를 가지게됨
   */
  const stream = fileHandle.createWriteStream();

  for (let i = 0; i < 1_000_000; i++) {
    /**
     * 데이터를 스트림의 내부 버퍼 메모리에 저장하는 역할
     *
     */
    stream.write(`[Log] ${i}님의 데이터 처리가 완료됨`);
  }

  /**
   * 작업시간: 323.941ms
   *
   * 해당 시간은 실제로 데이터를 모두 디스크에 저장하기까지 걸린 시간이 아님
   * 단지 메모리 버퍼에 100만개의 데이터를 순식간에 쏟아붓는데 걸린 시간임
   * 타이머가 종료된 이후에도 파일 시스템은 백그라운드에서 버퍼의 데이터를 디스크로 옮기고있음
   * 결과적으로 누락 없이 완벽한 순서로 데이터를 모두 기록할 수 있음
   * 겉으로는 문제가 없어보이지만 그 짧은 찰나에 메모리 사용량이 치솟는 폭주 현상이 일어나며 OOM 발생 가능성이 존재
   */
  console.timeEnd("작업시간");
})();
```

## 스트림의 백프레셔 제어를 통해서 대용량 데이터 안전하게 처리하기

```js
import { createWriteStream } from "node:fs";
import { finished } from "node:stream/promises";

async function writeManyStreams() {
  console.time("최종_작업시간");

  /**
   * File Handler를 거치지 않고 직접 파일 경로를 지정해서 쓰기 스트림 생성
   * 기본적으로 16KB의 내부 버퍼를 가짐
   */
  const stream = createWriteStream("server_logs.txt");

  for (let i = 0; i < 1_000_000; i++) {
    const data = `[Log] ${i}님의 데이터 처리 완료`;

    /**
     * 스트림 내부 임시 저장소인 버퍼가 꽉 차면 write 메서드가 더 이상 저장할 수 없다고 false를 반환함
     * Stream.Writable.write(chunk: any, callback?: ((error: Error | null | undefined) => void) | undefined): boolean
     *
     * false가 반환되면 해당 순간이 Backpressure가 발생한 순간임
     * 이 때 무작정 데이터를 더 넣는게 아닌 버퍼가 비워질 때 까지 await를 사용해서 잠깐 대기해야함
     * 이는 drain 이벤트로 해당 이벤트가 발생하면 버퍼가 다 비워졌다는 뜻으로 다시 로그 데이터를 붓기 시작함
     *
     * 그래서 메모리가 폭발하지 않고 비동기 방식으로 인해서 메인 스레도 차단되지 않음
     */
    if (!stream.write(data)) {
      /**
       * stream.once는 특정 이벤트 발생시 딱 한번만 실행될 콜백 함수를 등록하는 EventEmitter의 기능
       * 해당 코드에서는 버퍼가 비어졌음을 알리는 drain 이벤트를 감지해서 Promise를 resolve 하는데 사용
       */
      await new Promise<void>((resolve) => stream.once("drain", resolve));
    }
  }

  /**
   * 스트림에 더이상 쓸 데이터가 없으면 해당 메서드를 호출해서 내부적으로 파일 닫기 절차가 시작됨
   */
  stream.end();

  /**
   * 스트림이 완전히 비워지고 종료될 때까지 대기하는 Promise를 반환함
   * stream.end를 호출했다고 해서 즉시 디스크 I/O가 완료되는건 아니라 기다려야함
   */
  await finished(stream);

  // 최종_작업시간: 359.301ms
  console.timeEnd("최종_작업시간");
}

await writeManyStreams();
```

## 스트림?

- Node.js 공식문서에선 스트림은 스트리밍 데이터와 같이 작업하기 위한 데이터라고 정의함
- 보통 스트리밍이라고 하면 유투브나 게임방송 등에서 보이는걸 떠올리게됨
- 하지만 컴퓨터공학 지식에서 스트림은 그보다 훨씬 더 거대하고 포괄적인 개념임
- 데이터가 끊임없이 계속해서 흘러가는 상황을 스트림이라고 부름
- 즉 거대한 데이터를 한번에 옮기는게 아닌 잘개 쪼개서 연속적으로 도착하고 도착 지점에서 다시 조립하는 방식임

<br>

### 10GB 짜리 고화질 영화를 USB로 옮기는 상황 가정

- 만약 스트림 개념없이 그냥 복제하게되면 OS는 하드에 있는 파일을 그대로 올려서 메모리에 상주시킴
- 만약 메모리가 16GB라면 복사 작업으로 인해서 10GB가 한번에 점유됨. 메모리가 부족하면 크래시가 발생함
- 이런 문제를 해결하기 위해서 OS도 스트림을 사용하는데, 이러한 파일을 청크 단위로 쪼개버림
- 이후 쪼깨놓은걸 하나씩 메모리에 상주 -> USB로 옮기기 -> 메모리 비우기 방식으로 처리하게됨
- Node.js를 기준으로 스트림은 내부 램 버퍼에 모아놨다가 용량이 꽉 차게되면 시스템 콜을 발생시킴
- 무겁고 느린 디스크 I/O를 극단적으로 줄이고 속도가 빠른 메모리에서 처리해서 작업속도가 매우 단축됨

<br>

### 스트림을 또 사용하는곳

- 스트림은 파일 저장에만 사용하지 않고 다른 경우에도 사용됨
- 대표적으로 네트워크에서도 사용하는데 NIC를 통해서 들어온 데이터 조각들을 스트림을 통해 메모리에 가공하고, 응답시에도 스트림을 통해서 다시 내보내게됨
- 유투브를 생각해보면 대용량 동영상 파일을 업로드하면 모든걸 한번에 메모리에 올리는게 아닌 SSD와 서버 사이에 파이프를 연결하게됨
- 디스크에서 스토리지로, 스토리지에서 압축엔진으로, 이후에 다시 네트워크로 등 과정을 반복함
- 이러한 과정에서 절대 큰 용량의 데이터가 한번에 메모리에 적재되는 일은 존재하지 않음
