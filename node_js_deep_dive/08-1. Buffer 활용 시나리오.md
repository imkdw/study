## Binary Data Handling (Custom Network Packet)

- Node.js에서 버퍼의 첫 번쨰 존재 이뉴는 네트워크 통신에서 발생하는 순수한 이진 데이터를 바이트 단위로 해부하는것임
- 게임 서버나 고성능 IoT 서버를 개발한다면 HTTP의 무거운 헤더를 버리고 바이트 단위로 직접 통신 규약을 만드는데 이런 경우에 버퍼가 없다면 통신 자체가 불가능함
- 사실 JSON으로 보내도 되지만 이 경우 글자로만 벌써 15바이트를 잡아먹음
- 하지만 버퍼 + Endian을 활용하면 1바이트에 구겨 넣을 수 있음
- 초당 100만번의 통신이 일어나는 시스템에서는 이 차이는 클라우드 비용을 수천만 원씩 아껴주는 기적을 만듦

```js
import { Buffer } from "node:buffer";

// 클라이언트에서 날아온 16바이트짜리 압축된 바이너리 패킷이라고 가정
// 구조: [매직넘버: 4바이트] [버전: 1바이트] [명령어: 1바이트] [페이로드 길이: 2바이트] [타임스탬프: 8바이트]
const packet = Buffer.from("4B4F524101FF0400000001878E0F2B00", "hex");

// 앞서 배운 Endianness(BE)를 활용해 0과 1의 덩어리를 완벽하게 해부
const magicNumber = packet.subarray(0, 4).toString("utf8"); // 오프셋 0~4: "KORA"
const version = packet.readUInt8(4); // 오프셋 4: 1
const command = packet.readUInt8(5); // 오프셋 5: 255 (0xFF)
const payloadLength = packet.readUInt16BE(6); // 오프셋 6~8: 1024
const timestamp = packet.readBigUInt64BE(8); // 오프셋 8~16: 1680000000000n

// [수신] 매직: KORA, 버전: v1, 명령: 255, 길이: 1024
console.log(`[수신] 매직: ${magicNumber}, 버전: v${version}, 명령: ${command}, 길이: ${payloadLength}`);
```

## 데이터 포맷 변환 (gzip, base64)

- 자바스크립트의 거대한 문자열 객체를 Buffer.from을 통해서 이진 데이터로 변환함
- zlib.gzipSync는 C++ 압축 엔진을 통해서 패턴을 분석하고 5000byte -> 50byte 수준의 고밀도 버퍼로 눌러버림
- 압축된 버퍼는 사람이 볼 수 있는 문자가 아니므로 toString('base64')를 통해서 안전한 문자로 환전해서 HTTP로 전송함

```js
// 파일명: buffer-preview.js (이어서 작성)
import zlib from "node:zlib"; // 데이터를 압축해주는 Node.js 내장 모듈
import { Buffer } from "node:buffer";

// 1. 엄청나게 거대한 JSON 데이터가 있다고 가정
const hugeData = JSON.stringify({ message: "Hello".repeat(1000) });
const rawBuffer = Buffer.from(hugeData, "utf8");

// 2. 이 거대한 버퍼를 Zlib을 이용해 하드웨어 레벨에서 Gzip 알고리즘으로 압축
const compressedBuffer = zlib.gzipSync(rawBuffer);

// 3. 압축된 이진 데이터를 다른 서버의 API로 쏘기 위해 Base64 텍스트로 변환
const base64Payload = compressedBuffer.toString("base64");

// H4sIAAAAAAAAE+3EIREAIBAAsC4fgwTUQPxh4BBIju6kwG1iJ2bu3XpGiZpjLEmSJEmSJElfi/sAL+1ZmpYTAAA=
console.log(base64Payload);

// 원본 크기: 5014 바이트
// 압축 크기: 65 바이트
console.log(`원본 크기: ${rawBuffer.byteLength} 바이트`);
console.log(`압축 크기: ${compressedBuffer.byteLength} 바이트`); // 용량이 미친듯이 줄어듦
```

## 현대 암호화

- 만약 중간에 데이터를 가로채서 조작한다면 수신측 서버가 저 패킷을 받아 IV, Auth Tag를 잘라내어 검증 로직에 돌리는 순간 CPU 연산 결과가 어긋나고 에러를 뱉고 연결을 차단시킴
- 버퍼를 자유자재로 쪼개고 합칠 수 있어야만 이런 보안 아키텍처 구성이 가능함

```js
import crypto from "node:crypto";

// 1. 해킹이 불가능한 진정한 난수(버퍼)로 32바이트 키와 12바이트 IV를 생성
const key = crypto.randomBytes(32);
const iv = crypto.randomBytes(12);

const cipher = crypto.createCipheriv("aes-256-gcm", key, iv);

// 2. 데이터를 암호화 (결과물은 버퍼)
const encryptedData = Buffer.concat([cipher.update("Top Secret User Data", "utf8"), cipher.final()]);

// 3. GCM 모드의 핵심, 데이터가 조작되지 않았음을 증명하는 16바이트 인증 태그(버퍼)를 뽑아냄
const authTag = cipher.getAuthTag();

// 4. 네트워크로 전송하기 위해 IV + 인증태그 + 암호화데이터를 하나의 거대한 버퍼로 합침(concat)
const finalNetworkPayload = Buffer.concat([iv, authTag, encryptedData]);

// 네트워크로 날아갈 최종 보안 페이로드: 5458eae6a52040e2de3ae26063ddf29f592472c5fee1594f0164758ce394969f30f687144b6761fb93d09df479dbcfc3
console.log("네트워크로 날아갈 최종 보안 페이로드:", finalNetworkPayload.toString("hex"));
```

## 성능 최적화

- 스트림으로 들어온 C++ 버퍼 객체 1개를 재활용해서 CPU의 하드웨어 스캐너인 indexOf를 통해 전기 신호만 읽고 지나감
- 그래서 아무리 큰 파일이여도 메모리 사용량은 영원히 64kb에 고정되며 10GB 파일을 0.1초 단위로 처리할 수 있음

```js
import fs from "node:fs";

// 10GB짜리 거대한 서버 로그 파일이 있다고 가정
const stream = fs.createReadStream("massive_server_log.csv");
let totalLines = 0;

// 파이프(스트림)를 통해 64KB짜리 물통(버퍼 청크)이 들어올 때마다 이벤트가 터짐
stream.on("data", (chunk) => {
  let offset = 0;

  // C++ SIMD 엔진이 내장된 indexOf를 이용해 이진 데이터 상태에서 개행문자(10 = \\\\n)만 찾아냄
  // 문자열로 변환해서 .split('\\\\n') 이런걸 하게되면 OOM으로 즉사함
  while ((offset = chunk.indexOf(10, offset)) !== -1) {
    totalLines++;
    offset++; // 찾은 위치 다음부터 다시 스캔
  }
});

stream.on("end", () => console.log(`엄청난 파일의 줄 수 계산 완료: 총 ${totalLines}줄`));
```

## 상호 운영성

- 다른 언어랑 물리적 메모리를 공유하는 방식임
- WASM은 브라우저나 Node.js 안에서 C++/Rust 같은 빠른 언어를 실행할 수 있게 해주는 엔진임
- 코인 채굴이나 AI 연산 등 JS로 감당이 불가능한 일을 처리함
- JS 객체를 C++로 넘기벼러면 데이터를 모두 분해하고 번역하는 아주 무거운 직렬화 과정이 필요함
- 하지만 버퍼는 사실 그 자체로 C++의 메모리 주소라서 Node.js가 버퍼를 WASM으로 넘기는 행위는 데이터를 복제하는게 아니라 내 메모리 n번지부터 m번지까지 너가 알아서 하라고 주소만 던져주는 Zero-copy 통신임

```js
import { Buffer } from "node:buffer";

// 1. WASM(C++) 엔진이 사용할 하드웨어 메모리 공간 1페이지(64KB)를 개통
const wasmMemory = new WebAssembly.Memory({ initial: 1 });

// 2. 소름돋는 마법: Node.js의 Buffer가 WASM의 메모리 칩을 직접 가리키게 만듦 (Zero-copy)
const sharedBuffer = Buffer.from(wasmMemory.buffer);

// 3. Node.js에서 버퍼에 글씨를 쓰면...
sharedBuffer.write("Hello C++ Engine!", "utf8");

// 4. 데이터를 복사해서 넘겨줄 필요 없이, C++ 엔진은 자기 메모리를 쳐다보면 이미 데이터가 들어와 있음
console.log("WASM 메모리에 다이렉트로 데이터 주입 완료.");
```

## 미디어 동영상 스트리밍

- 넷플릭스, 유투브 처럼 동영상 스트리밍의 핵심인 미디어 구간 스트리밍 방식임
- Range 헤더의 경우 특정 구간을 잘라서 보여줘 등에 사용하고 HTTP 206 Partial Content는 부분만 잘라서 성공적으로 보냈다고 응답하는 서버의 코드임
- 하드디스크의 컨트롤러는 이 명령을 받으면 디스크의 헤드를 정확히 n바이트 위치의 메모리 섹터로 이동시키고 딱 지정된 용량만 버퍼에 담아 NIC로 흘려보냄
- 버퍼의 Offset, Length를 통제하지 못한다면 동영상 스트리밍 서버는 절대 만들 수 없음

```js
import fs from "node:fs";

// 1. 넷플릭스 클라이언트(브라우저)가 영상 중간으로 스킵을 눌러 Range 헤더를 보냈음
const rangeHeader = "bytes=1048576-2097151"; // "1MB 지점부터 2MB 지점까지만 줘!"

// 2. 정규식으로 필요한 바이트의 시작(Start)과 끝(End) 지점을 파싱함
const [start, end] = rangeHeader
  .replace(/bytes=/, "")
  .split("-")
  .map(Number);

// 3. 파일 시스템 스트림에게 지시: "파일 다 읽지 말고, 딱 저 물리적 바이트 위치만 읽어서 버퍼로 퍼올려!"
const videoStream = fs.createReadStream("movie.mp4", { start, end });

console.log(`클라이언트에게 ${start} 바이트부터 ${end} 바이트까지만 잘라서 206 상태코드로 스트리밍함`);
// 실무에서는 이 videoStream을 HTTP Response 객체로 파이프(pipe) 연결하여 쏨
```

## 실전 과제

```js
import { Buffer } from "node:buffer";

const incomingPacket = Buffer.from("4155544f0000018bd5506b006e00aabbccdd", "hex");

// 검증용 정답 매직 넘버
const VALID_MAGIC_NUMBER = Buffer.from("AUTO", "utf8");

console.log("--- 주행 데이터 파이프라인 가동 ---\n");

try {
  // [Task 1] 보안 검증 (Zero-copy 렌즈로 앞 4칸만 보고 비교)
  const magicNumber = incomingPacket.subarray(0, 4);
  if (!magicNumber.equals(VALID_MAGIC_NUMBER)) {
    throw new Error("매직 넘버 불일치! 우리 차량이 보낸 패킷이 아닙니다.");
  }
  console.log("[Task 1] 매직 넘버 검증 통과:", magicNumber.toString("utf8"));

  // [Task 2] 데이터 파싱 (타임스탬프는 BE, 차량 CPU 속도는 LE)
  const timestamp = incomingPacket.readBigUInt64BE(4);
  const speed = incomingPacket.readUInt16LE(12);
  console.log("[Task 2] 타임스탬프:", new Date(Number(timestamp)).toISOString());
  console.log("[Task 2] 주행 속도:", speed, "km/h");

  // [Task 3] Zero-copy 뷰 (GPS 해시 부분 14~17 인덱스)
  const gpsHash = incomingPacket.subarray(14, 18);
  console.log("[Task 3] GPS 해시 (원본 보존):", gpsHash);

  // [Task 4] 안전한 이식과 수정 (Deep Copy 후 속도 -10 수정)
  // 힌트: incomingPacket.length 크기만큼 allocUnsafe -> copy -> writeUInt16LE
  const modifiedPacket = Buffer.allocUnsafe(incomingPacket.length);
  incomingPacket.copy(modifiedPacket);
  modifiedPacket.writeUInt16LE(speed - 10, 12);
  console.log("[Task 4] 수정된 속도:", modifiedPacket.readUInt16LE(12), "km/h");
  console.log("[Task 4] 원본 속도 (불변 확인):", incomingPacket.readUInt16LE(12), "km/h");

  // [Task 5] 최종 병합 (수정한 버퍼 뒤에 <Buffer FF FF> 를 Concat)
  const footer = Buffer.from([0xff, 0xff]);
  const finalPacket = Buffer.concat([modifiedPacket, footer]);
  console.log("[Task 5] 최종 패킷:", finalPacket);
  console.log("[Task 5] 최종 길이:", finalPacket.length, "바이트");
} catch (error) {
  console.error("🚨 보안 관제 시스템 알림:", error.message);
}
```
