## 공식문서에서의 Readable Stream

- Node.js 공식문서는 Readable Stream에 대해서 데이터가 소비되는 출발점, 즉 소스에 대한 추상화라고 뜻함
- 이러한 추상화라는 단어는 하드웨어를 만나면 아주 거대한 의미를 가지게됨
- CS에서 추상화란 디스크의 동작방식, 전기신호 등 복잡한 내용은 숨기고 개발자가 read(), write() 등 단순하고 통일된 인터페이스로만 기계를 다룰 수 있게 만들어주는 설계 기법을 뜻함
- 문서에서는 HTTP 요청/응답, 파일시스템, 암호화 등 다양한 작업이 모두 하나의 Readable Stream Interface로 구현되어있음

<br>

## Readable Stream의 중요한 2가지 읽기 모드

- 아래 2개의 상태중 1개로만 동작하며 Object Mode랑은 별개임

### Flowing

- 효과적으로 데이터가 끊임없이 흐르는 모드를 의미함
- OS로 부터 데이터가 자동으로 읽혀지고 EventEmitter 인터페이스를 통해서 앱으로 가능한 한 빠르게 데이터가 들어옴
- Paused -> Flowing 모드로 전환하는 방법에는 3가지가 존재함
  - on('data') 이벤트를 핸들러를 추가하기
  - 흐름을 다시 재개하는 resume() 메서드 호출
  - read -> write 스트림 연결을 위해서 pipe() 메서드 호출
- 보통 넷플릭스나 유투브 같은 동영상 스트리밍이나 대용량 파일 고속 복사기를 만드는 경우 유용함
  - 목적지가 데이터를 받아들일수 있다면 중간에 CPU가 정밀한 조작 없이 스토리지의 데이터를 NIC로 빠르게 흘려보냄

<br>

### Paused

- 데이터의 흐름이 일시적으로 멈춘 모드를 의미함
- 데이터를 수동으로 퍼올리는 방식임
- 생성된 모든 스트림은 기본적을 Paused 모드로 동작함
- 압축파일 파서나 커스텀 바이너리 프로토콜 통신처럼 데이터 구조가 아주 엄격한 경우 사용함
  - 정확히 하나의 파일 단위를 짤라내서 잠깐 멈추고, 이후에 정해진 형식에 맞게 추출해야 오류없이 데이터 해석이 가능함
- Flowing -> Paused 전환의 경우도 pause() 메서드를 호출하면 즉시 전환됨

<br>

### Readable Stream의 중요한 원칙

- Readable Stream의 경우 데이터를 소비하거나 받아들이는 매커니즘이 제공되기 전까지는 절대 데이터를 생성하지 않음
- 만약 소비자가 있다가 사라지는 경우 스트림은 데이터 생성을 중단하려고 시도함
- 과거 버전과 호환성 문제로 인해서 단순 데이터 핸들러를 제거한다고해서 자동으로 paused 모드로 전환되지는 않음
- 또한 목적지가 파이프로 연결된 상태에서 pause() 메서드 호출 이후에 목적지에서 버퍼가 비워져 데이터를 더 달라고하면 스트림이 멈춰있다고 보장은 불가능함
- 가장 무서운 상황은 스트림이 Flowing으로 전환되었는데 데이터를 처리할 스트림이 없는 상황임. 이 경우 데이터가 전부 유실되어버림
  - 케이스 1 : data 이벤트 리스너 없이 resume() 메서드를 호출하기
  - 케이스 2 : 스트림에서 data 핸들러를 도중에 제거해버리는 상황

<br>

### 실제 내부 상태

- 실제로는 내부에 null, false, true 3개의 슬롯으로 상태를 관리하지만 알기 쉽게 Flowing, Paused 2개로 추상화함
- stream.readableFlowing 속성이 존재하는데 실제 값은 아래와 같음
  - null : 데이터를 처리할 소비자가 없어서 데이터가 생성되지 않음. data 이벤트를 리스닝하거나 resume()을 호출하면 데이터를 방출하기 시작함
  - false : pause(), unpipe(), backpressure를 받게되면 설정됨. 이 때 이벤트 방출만 멈추는거지 데이터 생성이 멈추지는 않음
    - 이 때 계속해서 데이터를 내부 버퍼에 적재하다가 꽉 차는 순간 시스템 콜을 통해서 더이상 물리적인 읽기를 중단하라고 명령함

<br>

### 안티패턴

- 공식문서에서는 하나의 단일 API 선택의 원칙을 제시함
- 데이터를 소비하는 방식이 여러개가 섞여있는데 이 선택지에서 1개만 선택해야하고 하나의 스트림에서 여러개를 선택하면 안됨
- 만약 Flowing 방식과 수동으로 읽는 read 방식을 사용하면 경합조건이 발생해서 순서가 엉키거나 증발할 수 있음
- 또한 스트림 사용이 종료됬다면 스트림이 자동으로 닫히지 않아서 파일 디스크립터 반납이 이루어지지 않을 수 있으니 명시적인 destroy() 메서드 호출이 필요함

```ts
import { open } from "node:fs/promises";

const fileReadHandle = await open("some.txt", "r");
const streamRead = fileReadHandle.createReadStream();

streamRead.on("data", (chunk) => {
  console.log(`자동으로 가져온 데이터: ${chunk}`);
});

streamRead.on("readable", () => {
  const maunalChunk = streamRead.read();
  console.log(`수동으로 가져온 데이터: ${maunalChunk}`);
});
```

## Pipe 메서드

- 이전 예시를 보면 읽기/쓰기 스트림을 직접 제어하며 중간에 백프레셔 등 복잡한 예외를 직접 구축함
- 이러한 단계를 모두 추상화한걸 파이프라고 부르며 한 줄의 코드로 바로 적용이 가능함
- 파이프를 연결하는 순간 2개의 스트림에 파이프가 직결되며 Flowing 모드로 전환됨
- 위 과정에서 알아서 pause(), resume(), drain 이벤트 등 자동으로 처리해줌

```ts
import { open } from "node:fs/promises";

const fileReadHandle = await open("some.txt", "r");
const streamRead = fileReadHandle.createReadStream();

const fileWriteHandle = await open("dest.txt", "w");
const streamWrite = fileWriteHandle.createWriteStream();

streamRead.pipe(streamWrite);
```

<br>

### pipe 사용시 주의점

- 파이프의 경우 pipe() 메서드가 목적지 스트림을 그대로 반환하므로 체이닝이 가능함
- 만약 파이핑 도중 원본 스트림에서 에러가 발생하더라도 목적지 스트림은 자동으로 닫히지 않음
- 위 경우 메모리 누수가 발생할 수 있는데 반드시 error 이벤트 감지를 통해서 파이프를 직접 없애줘야함
- Node.js의 경우 위 pipe의 한계를 극복하기 위해서 에러가 발생하면 파이프 전체를 파괴해주는 pipeline도 제공해줌
- 이러한 파이프는 중간 단게에서 변형(Transform)이 불가능하며 데이터를 복제하는 복사기 역할만 수행함

<br>

## 단순 파일시스템의 한계점

- 아래 코드는 파일 크기만큼 메모리를 그냥 잡아먹게됨
- 수십기가의 파일을 올리면 서버는 OOM으로 종료됨
- Node.js의 경우 한번에 단일 버퍼에서 다룰 수 있는 크기가 2GB로 그 이상을 사용하면 메모리 에러가 발생함

```ts
import fs from "node:fs/promises";

const label = "파일_복사_성능_테스트";

console.time(label);

const sourcePath = "source.txt";
const targetPath = "target.txt";

const targetFileHandle = await fs.open(targetPath, "w");

/**
 * 해당 시점에서 큰 파일을 한번에 메모리에 상주시킴
 */
const fileContent = await fs.readFile(sourcePath);

/**
 * 메모리에 상주시켰던 큰 파일을 통째로 하드에 기록함
 */
await targetFileHandle.write(fileContent);

// 파일_복사_성능_테스트: 65.787ms
console.timeEnd(label);
```

## 스트림 없이 수동 파이프라인 구축

```ts
import fs from "node:fs/promises";

const label = "파일_복사_성능_테스트";

console.time(label);

const inputPath = "source.txt";
const outputPath = "target.txt";

const fileReader = await fs.open(inputPath, "r");
const fileWriter = await fs.open(outputPath, "w");

// 16KB의 버퍼 공간
const CHUNK_SIZE = 16384;

/**
 * 파일을 옮기기 위한 버퍼를 단 하나만 생성해서 무한으로 재사용함
 * 공간복잡도가 O(n)이 아닌 O(1)이 됨
 */
const sharedBuffer = Buffer.alloc(CHUNK_SIZE);

try {
  let readCount = -1;

  while (readCount !== 0) {
    /**
     * 매번 새로운 버퍼를 생성하지 않고 하나의 버퍼를 계속해서 사용함
     */
    const { bytesRead } = await fileReader.read(sharedBuffer, 0, CHUNK_SIZE, null);
    readCount = bytesRead;

    /**
     * EOF(End of File)에 도달했을 경우 반복문을 종료함
     */
    if (readCount === 0) {
      break;
    }

    /**
     * 읽어온 버퍼의 크기만큼 유효한 버퍼를 생성함
     * 16KB라는 고정된 크기에서 마지막에 읽어온 데이터는 16KB보다 작을 수 있음
     * 실제 읽어온 데이터 크기만큼 버퍼를 잘라내고 유효한 값만 하드에 기록함
     */
    const validBuffer = sharedBuffer.subarray(0, readCount);
    await fileWriter.write(validBuffer);
  }
} catch (error) {
  console.error(error);
} finally {
  await fileReader.close();
  await fileWriter.close();
}

console.timeEnd(label);
```

## pipeline

- 복잡하게 버퍼를 다루거나 stream을 직접 다룰필요 없이 pipeline 함수로 처리가 가능함
- pipe의 단점이던 각 스트림간 장애 전파를 내부에서 알아서 처리해줌
- 속도 자체는 최적화를 통한 버퍼를 다루는것보다 느리겠지만 편의성이 압도적임

```ts
import { pipeline } from "node:stream/promises";
import { createReadStream, createWriteStream } from "node:fs";

const inputPath = "source.txt";
const outputPath = "target.txt";

const readStream = createReadStream(inputPath);
const writeStream = createWriteStream(outputPath);

try {
  await pipeline(readStream, writeStream);
  console.log("데이터 파이프라인 처리 완료");
} catch (err) {
  console.error("데이터 파이프라인 처리 중 오류 발생", err);
}
```

## 암호화 파이프라인 만들기

### 더미데이터 생성

```ts
import { createWriteStream } from "node:fs";

const LABEL = "1GB_더미_텍스트_파일_생성";
async function createDummyFile(filePath: string) {
  console.log(`${LABEL} 시작`);
  console.time(LABEL);

  const writeStream = createWriteStream(filePath);

  /**
   * 1MB 크기의 버퍼를 생성하면서 알파벳 A로 가득 채움
   */
  const chunk = Buffer.alloc(1024 * 1024, "A");

  /**
   * 1MB 청크를 1024번 써서 총 1GB
   */
  for (let i = 0; i < 1024; i++) {
    const canWrite = writeStream.write(chunk);
    if (!canWrite) {
      await new Promise<void>((resolve) => writeStream.once("drain", resolve));
    }
  }

  writeStream.end();

  await new Promise<void>((resolve) => writeStream.on("finish", resolve));

  console.timeEnd(LABEL);
  console.log(`${LABEL} 완료`);
}

await createDummyFile("1GB_더미_텍스트_파일.txt");
```

### 데이터 압축이란

- 반복되는 패턴이나 불필요한 정보를 찾아서 데이터가 차지하는 용량을 줄이는 방식
- AAAAA -> 5A 처럼 데이터를 줄이는 방식
- zlib의 경우 gzip, Deflate, Brotil 등 여러 알고리즘을 제공해줌

<br>

### 예제

- 각 압축 알고리즘마다 시간에는 차이점이 존재하는데 brotil의 경우 엄청 오래걸림
- 극한의 압축을 위해서 CPU에 엄청난 부하를 주는데 만약 이러한 로직을 요청마다 굴리면 부하가 심함
- 보통 실시간으로 압축을 하는게 아닌 빌드나 배포 단계에서 미리 압축해두고 요청하면 전달함
- 스트리밍같은 저지연이 필요하다면 Deflate, 고정된 정적파일의 경우는 Brotil 등 유연하게 선택해야함
-

```ts
import { pipeline } from "node:stream/promises";
import { createReadStream, createWriteStream } from "node:fs";
import { stat } from "node:fs/promises";
import type { Transform } from "node:stream";
import { createBrotliCompress, createDeflate, createGzip } from "node:zlib";

async function createDummyFile(filePath: string) {
  const LABEL = "1GB_더미_텍스트_파일_생성";
  console.log(`${LABEL} 시작`);
  console.time(LABEL);

  const writeStream = createWriteStream(filePath);

  const chunk = Buffer.alloc(1024 * 1024, "A");

  for (let i = 0; i < 1024; i++) {
    const canWrite = writeStream.write(chunk);
    if (!canWrite) {
      await new Promise<void>((resolve) => writeStream.once("drain", resolve));
    }
  }

  writeStream.end();

  await new Promise<void>((resolve) => writeStream.on("finish", resolve));

  console.timeEnd(LABEL);
  console.log(`${LABEL} 완료`);
}

async function maesureCompression(algoName: string, transformFilter: Transform, inputFile: string, extension: string) {
  const outputFile = `compressed_${algoName}_${extension}`;
  console.log(`${algoName} 파이프라인 가동중..`);
  console.time(`${algoName} 소요시간`);

  try {
    await pipeline(createReadStream(inputFile), transformFilter, createWriteStream(outputFile));
  } catch (error) {
    console.error(`${algoName} 파이프라인 오류: ${error}`);
    return;
  }

  console.timeEnd(`${algoName} 소요시간`);

  const originalSize = (await stat(inputFile)).size;
  const compressedSize = (await stat(outputFile)).size;

  const originalMB = (originalSize / (1024 * 1024)).toFixed(2);
  const compressedMB = (compressedSize / (1024 * 1024)).toFixed(2);
  const ratio = (((originalSize - compressedSize) / originalSize) * 100).toFixed(4);

  console.log(`${algoName} 압축률: ${ratio}%`);
  console.log(`${algoName} 원본 파일 크기: ${originalMB}MB`);
  console.log(`${algoName} 압축 파일 크기: ${compressedMB}MB`);
  console.log(`${algoName} 압축 파일 크기: ${compressedSize} bytes`);
  console.log(`${algoName} 원본 파일 크기: ${originalSize} bytes`);
  console.log("=".repeat(50));
}

(async () => {
  const TARGET_FILE = "dummy_1gb.txt";

  await createDummyFile(TARGET_FILE);

  console.log(`벤치마크 시작`);

  // gzip 파이프라인 가동중..
  // gzip 소요시간: 1.625s
  // gzip 압축률: 99.9028%
  // gzip 원본 파일 크기: 1024.00MB
  // gzip 압축 파일 크기: 1.00MB
  // gzip 압축 파일 크기: 1043658 bytes
  // gzip 원본 파일 크기: 1073741824 bytes
  // ==================================================
  // deflate 파이프라인 가동중..
  // deflate 소요시간: 1.543s
  // deflate 압축률: 99.9028%
  // deflate 원본 파일 크기: 1024.00MB
  // deflate 압축 파일 크기: 1.00MB
  // deflate 압축 파일 크기: 1043646 bytes
  // deflate 원본 파일 크기: 1073741824 bytes
  // ==================================================
  // brotli 파이프라인 가동중..
  // brotli 소요시간: 10.815s
  // brotli 압축률: 99.9998%
  // brotli 원본 파일 크기: 1024.00MB
  // brotli 압축 파일 크기: 0.00MB
  // brotli 압축 파일 크기: 1681 bytes
  // brotli 원본 파일 크기: 1073741824 bytes
  // ==================================================
  await maesureCompression("gzip", createGzip(), TARGET_FILE, "gz");
  await maesureCompression("deflate", createDeflate(), TARGET_FILE, "deflate");
  await maesureCompression("brotli", createBrotliCompress(), TARGET_FILE, "br");
})();
```
