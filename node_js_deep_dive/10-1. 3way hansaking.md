## 4계층 (전송 계층)

- 불안전한 3계층을 보완하기 위해서 등장한 계층으로 Layer-7 계층에서 4번째 계층에 해당됨
- 전송 계층은 물리적 이동을 담당하지 않으며 핵심 역할은 아래와 같음
- 정확한 포트를 지정하는데 도착한 데이터를 올바른 앱으로 분배하는 역할을 해줌
- 통신의 안전함(TCP)과 빠름(UDP)중 무엇을 택할지 결정해줌

<br>

## TCP(Transmission Control Protocol)

- 전송을 제어하는 통신 규약으로 데이터 전송의 모든 과정을 깐깐하게 제어하여 신뢰성을 보장하는것이 가장 중요한 목적
- 데이터가 유실되면 다시 보내라고 계속 요구하고, 순서가 바뀌면 원래대로 조립해서 변질되지 않았나 철저하게 검사함
- Node.js의 net 모듈이 TCP를 담당함

<br>

## UDP(User Datagram)

- 복잡한 확인 절차를 생략하고 속도에 초점을 맞춰서 독립적인 데이터를 연속으로 보내는 프로토콜
- 유실, 변형 등 전혀 검사하지 않고 데이터를 엄청나게 쏟아부음
- 유투브, 넷플릭스의 실시간 스트리밍이나 디스코드로 음성채팅을 하는 경우 가끔 화면이 깨지거나 목소리가 끊기는게 UDP 데이터가 일부 유실되서그럼
- Node.js는 dgram 모듈이 UDP를 담당함

<br>

## 3-way handshake

### TCP 통신에서 보이는 플래그들

- SYN(Synchronize) : 통신을 시작하기 위해서 서로 상태랑 순서 번호를 동기화 하자는 연결 요청 깃발
- ACK(Acknowledgment) : 요청이나 데이터를 내가 확실하게 잘 받았다고 인정하는 확인의 깃발
- FIN(Finish) : 통신을 마쳤으니 깔끔하게 연결을 종료하겠다는 작별의 깃발
- 즉 TCP 에서는 무작정 데이터를 전송하지 않고 진짜 데이터를 보내기 전 여러 단계에 걸친 치밀한 확인 작업을 거치게됨
- 실제로 연결이 잘 이루어지기 전까지는 데이터를 전송하지 않으므로 불필요한 네트워크 낭비를 막음

<br>

### 클라이언트의 SYN

- 먼저 클라이언트가 서버에게 SYN 요청을 보내는데 이때 시퀀스 0번, 길이 0으로 요청을 보냄
- 맨 처음에는 데이터 없는 가벼운 껍데기를 보내서 서버에게 노크를 하게됨

```
Flag: SYN
LEN: 0Byte
Seq: 0
```

<br>

### 서버의 ACK + SYN

- 서버는 동시에 클라이언트에게 응답과 자신의 요청을 동시에 보내게됨
- 해당 패킷 자체도 실제 데이터는 0Byte임

```
Flag: SYN, ACK
Ack: 1
Seq: 0
Len: 0 Byte
```

<br>

### 클라이언트의 최종 확인

- 클라이언트는 다시 ACK를 보내서 마지막 확답을 진행하게됨

```
Flag: ACK
Seq: 1
Ack: 1
```

<br>

### 실제 데이터 전송

- 클라이언트는 서버에게 PSH, ACK를 보내는데 이 때 실제 데이터가 전송됨

```
Len: 4 Byte
Data: "node"
```

<br>

### 데이터 받았다고 알림

- 서버가 다시 클라이언트에게 ACK를 전달함
- 서버는 데이터를 잘 받았으니 다음엔 어떤 패킷을 보내라고 명령하게됨

```
Fag: ACK
Ack: 5 (이는 이전에 Len: 4 짜리 데이터를 보내서 다음엔 5번째를 보내라는 의미)
```

<br>

### 통신의 끝

- 통신이 완전히 끝날때도 임의로 종료하는게 아닌 서로 FIN, ACK를 주고받으며 종료 과정을 거치게됨
- 이런식으로 맺어진 연결에서 TCP는 데이터의 전송을 확실하게 보장히기 위해서 세그멘트의 여러가지 헤더 정보를 꼼꼼하게 기록하게됨
- 조립 설명서 역할을 하는 Seq 번호랑 ACK 번호 덕분에 중간에 패킷이 유실되는 경우 수신자가 알아채고 재전송 요구가 가능함

<br>

### Window Size 헤더

- 다운로드를 예시로 들면 처음에는 느린 속도로 다운로드 하다가 점점 지속되면 더 큰 크기로 다운로드됨
- 그러다가 한계점에 도달하기 전까지 속도를 늘려서 이후로는 고정된 속도로 다운로드를 진행하게됨
- TCP의 경우 신뢰성을 보정하기 위해서 데이터를 일정한 크기(MTU / Window 규격 증)로 잘라서 보내게됨
- 그래서 클라이언트 입장에서 데이터를 한번만 보내도 서버에서는 데이터를 나눠서 받을 수 있음
- 결국 앱에서 처리해야하는 스트림을 통해 분해되어 들어오는 데이터를 합쳐서 완벽한 하나의 메시지로 재조립하는 파싱 알고리즘이 중요함

<br>

### CHECKSUM 헤더

- 데이터의 합계를 검사해서 오류를 찾아내는 기법
- 송신사자 패킷속의 모든 이진 데이터를 수학적으로 연산한 결과를 체크썸에 전달해주면 수신자도 동일하게 계산해서 두 숫자가 일치하는지 대조함
- 단 하나의 숫자라도 깨진 경우는 파일이 깨지거나 변질되었다고 인식함
- 이처럼 TCP의 경우 수많은 제어 기능을 위해서 헤더 자체가 매우 무거운데 UDP는 그런 과정이 없으므로 매우 가볍게 구성됨

<br>

## 캡슐화

- 데이터는 하위 게층으로 내려가면서 포장되며, 상위 계층으로 올라가면서 해석됨
- 이러한 과정은 캡슐화 / 디캡슐화라고 불리는데 이는 소프트웨어의 개념을 네트워크도 그대로 물려받았음
- Node.js에서 4바이트의 데이터를 보내면 아래와 같은 작업들이 이루어짐

<br>

### 포장하기 (캡슐화)

- Node.js는 L7에 존재하며 L4로 내려가면 이러한 데이터를 첫번째 상자에 담고 겉면에 TCP 헤더(출발지, 도착지 포트 등)를 붙임
- L3에서는 IP 헤더(출발지, 도착지 IP 등)를 붙임
- L2에서는 이더넷 헤더(MAC 주소 등)를 붙임
- L1에서는 랜선을 타고 전기신호로 변해서 상대방 컴퓨터에 도착하게됨

<br>

### 해석하기 (디캡슐화)

- L2에서 MAC 주소를 해석하고 L3로 올려보냄
- L3에서 IP를 확인하고 L4로 올려보냄
- L4에서 포트 번호, 체크썸 등을 검사하고 문제가 없음을 확인함
- 유효한 L7에게 해당 데이터를 전달하게됨
