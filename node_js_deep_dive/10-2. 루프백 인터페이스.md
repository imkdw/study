## 루프백

- OS가 설치될 때 커널 레벨에서 소프트웨어적으로 무조건 생성하는 가상 네트워크 장치로 보통 lo0 이라는 이름으로 관리함
- 127.0.0.1, ::1 주소가 고정적으로 할당되며 매번 외우기 힘드므로 localhost로 부름

<br>

## 물리적 랜카드

- 기기 자체에 내장된 WIFI / 이더넷 같은 물리적 랜카드를 의미함
- OS 내부에선 en0, wlan0 같은 이름으로 명명함

<br>

### 핫스팟을 켜면 일어나는일

- 단순 전화기를 넘어서 하나의 라우터의 역할을 하게됨
- 와이파이를 사용할 수 있는 기기에서는 이러한 라우터로 접근을 요청하는데 이 때 핸드폰은 자신의 네트워크망에 접속한 노트북을 식별 & 통신 가능하게 만들어야함
- 스마트폰은 내부적으로 DHCP를 가동해서 자동으로 노트북에게 IP를 부여해줌

<br>

### Node.js에서 인터페이스 목록 조회

```ts
import os from "node:os";

const netInterfaces = os.networkInterfaces();

// [
//   'lo0',       'utun0',
//   'utun1',     'utun2',
//   'utun3',     'en0',
//   'awdl0',     'llw0',
//   'bridge100', 'bridge101',
//   'bridge102', 'bridge104',
//   'bridge103', 'utun4',
//   'utun5',     'utun6',
//   'utun7'

//   mac: '00:00:00:00:00:00',
//   internal: true,

console.log(netInterfaces["lo0"][0]);
```

### Hostname 관련

```ts
import net from "node:net";

const port = 9472;
const hostname = "0.0.0.0";

const server = net.createServer((socket) => {
  socket.write("Hi there!");
  socket.on("data", (data) => console.log(data.toString()));
});

/**
 * 9472번 포트를 바인딩해서 외부에서 접근이 가능하게 만들어줌
 *
 * OS에게 bind()라는 시스템 콜을 날려서 포트 점유를 요청함
 * 이후 커널에선 IP Table 스캔 이후에 실제 내 컴퓨터가 가진 IP 및 유휴 포트를 확인해서 연결을 대기함
 *
 * 이 때 0.0.0.0 이라는 주소도 존재하는데 이는 어떤 종류든 전부 외부에 공개하겠다는 의미임
 *
 */
server.listen(port, hostname, () => {
  console.log(`Server running at ${hostname}:${port}`);
});
```

## 포트

- 인터넷 포트 번호의 경우 0부터 65535까지 사용이 가능하고 IANA에서는 크게 3개의 부분으로 나눠서 관리함
- WELL KNOWN/SYSTEM : 이미 선점한 포트로 0 ~ 1023은 이미 사용됨. ssh(22), dns(53) 등이 포함됨
- 등록포트 : 1024 ~ 49151은 정식으로 등록된 포트들임. mysql(3306), postgres(5432) 등이 포함됨
- 동적/임시 포트 : 49152 ~ 65535 사이로 미등록 번호임. 클라이언트 -> 서버 접근시 임시로 사용되고 폐기되고 그럼

<br>

### 포트는 한정적인데 수십만개의 클라이언트가 연결 가능한 이유

- 서버의 아이피랑 포트번호만 가지고 서버를 식별하지 않음
- OS는 출발지 IP/포트, 도착지 IP/포트 4개의 조합을 통해서 소켓 세션을 유니크하게 식별함
- 서로 각기 다른 IP 주소랑 임시 포트를 사용하므로 이는 서버 입장에서 중복되지않고 처리가 가능함
- 또한 전송 프로토콜(TCP/UDP)가 다르면 같은 포트를 사용해서 처리가 가능함
  - 이는 서로 다른 프로토콜 라인을 타기때문에 OS 내부적으로 완전히 별개의 소켓 엔트리로 관리됨

<br>

## 연결 해제의 중요성

- 인터넷이 끊어지거나 재연결이 발생하는 등 새로운 요청이 다시 온다면 기존 좀비 세션은 정리해야함
- 기존 소켓을 정리하지않고 계속해서 메모리에 쌓게되면 OOM이 발생할 수 있음

```ts
socket.on("error", (err) => {
  console.log("소켓 에러 발생, 연결을 종료함", err);
  socket.destroy();
});
```

<br>

### 소켓의 end(), destroy()의 차이점

- 위 2개는 OS 레벨에서 완전히 다름
- end()의 경우 마치 Graceful Shutdown 방식으로 동작함
  - 4-way handshake 방식을 위해서 FIN 전송 -> 파이프라인 내부 처리 다 끝냄 -> 종료 방식
  - 정상 비즈니스 로직에서는 end를 사용하게됨
- distroy()의 경우 강제적으로 즉시 파괴하는 방식임
  - 4-way handshake를 바로 무시하고 RST를 전송해서 연결을 즉시 파괴해버림
  - 좀비 소켓이나 크래시의 경우 데이터 완결성 파악이 불가능하므로 즉시 없애버림

<br>

### 탐지 패킷

- 아무런 신호 없이 잠적해버린 클라이언트를 커널 수준에서 감시하고 찾아내기 위해서 마지막 통신이 끝나고 가만히 있는 소켓에세 메시지를 전송함
- Node.js의 경우 setKeepAlive() 메서드를 통해서 편하게 제공함

```ts
// IDLE 상태에서 아래 시간만큼 통신이 없다면 커널 레벨에서 Probe Packet을 날려서 확인함
// 답이 없다면 연결이 끊어진것으로 판단하고 연결을 종료시킴
socket.setKeepAlive(true, 10_000);
```
