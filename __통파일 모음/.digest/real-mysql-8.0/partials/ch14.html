14-1

스토어드 프로그램 장단점

DB 안에서 절차적 처리를 할 수 있다는 것과, 해야 한다는 것은 다른 이야기다.

핵심 스토어드 프로그램의 이득은 보안과 네트워크 왕복 절감이고, 대가는 낮은 처리 성능과 코드의 조각화다.

스토어드 프로그램이란

  • MySQL 내부에서 절차적인 처리를 하기 위해 쓴다.
  • 스토어드 프로시저, 스토어드 함수, 트리거 등을 모두 아우르는 명칭이다.

장점

장점내용
데이터베이스 보안 향상 자체 보안 설정 기능이 있어 프로그램 단위로 실행 권한을 줄 수 있다. 특정 테이블 읽기·쓰기, 특정 컬럼 등 세밀한 제어가 가능하다
기능의 추상화 여러 애플리케이션에서 같은 로직을 각자 구현하지 않고 공통으로 호출할 수 있다
네트워크 소요 시간 절감 애플리케이션과 DB 사이의 왕복이 줄어든다. 데이터가 많고 호출이 잦으면 네트워크가 부하를 받는데, 스토어드는 한 번만 왕복하면 된다
절차적 기능 구현 SQL에는 IF, WHEN 같은 절차적 구성이 없어 보통 애플리케이션에서 처리한다. DB를 관리하는 조직이 분리되어 있다면 스토어드를 호출하는 식으로도 개발할 수 있다

단점

단점내용
낮은 처리 성능 DB의 목적은 절차적 처리가 아니라 프로그래밍 언어보다 성능이 떨어진다. 게다가 MySQL의 스토어드 프로그램은 실행할 때마다 코드가 파싱된다
애플리케이션 코드의 조각화 로직이 분산되면 설치·배포가 복잡해지고 유지보수도 어려워진다
i

"실행할 때마다 파싱된다" 의 무게 보강

다른 DBMS는 스토어드 프로그램을 컴파일해 캐싱하지만 MySQL은 그렇지 않다. 이 한 가지 차이 때문에, 다른 DBMS에서 통하던 "무거운 로직은 DB로 내리자" 라는 전략이 MySQL에서는 잘 통하지 않는다. MySQL의 스토어드는 성능 최적화 수단이 아니라 보안·추상화 수단으로 보는 편이 정확하다.

정리

  • 스토어드 프로그램 = 프로시저 + 함수 + 트리거 + 이벤트.
  • 얻는 것 — 권한 세분화, 추상화, 네트워크 왕복 절감.
  • 치르는 것 — 매 실행마다 파싱, 그리고 로직이 코드베이스 밖으로 흩어지는 것.
14-2

스토어드 프로그램의 문법

프로시저 · 함수 · 트리거 · 이벤트 네 가지의 선언 방법과 호출 방법.

핵심 프로시저는 CALL 로만, 함수는 SQL 안에서만 실행된다. 이 하나가 둘을 가르는 가장 큰 차이다.

공통 구조

  • 헤더(정의부) — 이름과 입출력 값을 명시한다. 보안이나 작동 방식 관련 옵션도 여기에 쓴다.
  • 본문(바디) — 실제 실행할 내용을 작성한다.

스토어드 프로시저

  • 서로 데이터를 주고받아야 하는 여러 쿼리를 하나의 그룹으로 묶어 독립적으로 실행하기 위해 쓴다.
  • 배치 프로그램에서 첫 쿼리의 결과로 두 번째 쿼리를 실행해야 할 때가 대표적이다.
  • 반드시 독립적으로 호출해야 하며 SELECT, UPDATE 같은 SQL 문장에서 참조할 수 없다.
생성 및 삭제
  • 기본적으로 반환값이 없다. 즉 RETURN 절을 쓸 수 없다.
  • 파라미터는 세 가지다.
종류용도
IN입력 전용. 내부에서는 읽기 전용
OUT출력 전용. 실행이 끝나면 외부 호출자로 값을 전달하는 용도로만
INOUT입력과 출력 양쪽으로 사용
  • 본문을 변경하려면 삭제 후 다시 만드는 방법밖에 없다.
  • ALTER PROCEDURE 는 보안 및 작동 방식 관련 특성을 바꿀 때만 쓸 수 있다.
CREATE PROCEDURE sp_sum (IN p1 INTEGER, IN p2 INTEGER, OUT p3 INTEGER)
BEGIN
  SET p3 = p1 + p2;
END;
실행
  • 프로시저와 함수의 가장 큰 차이가 실행 방법이다.
  • 프로시저는 SQL 문 안에서 쓸 수 없고 항상 CALL 로 실행해야 한다.
  • OUT, INOUT 파라미터에는 세션 변수를 써야 한다.
SET @result := 0;
SELECT @result;              -- 0

CALL sp_sum(1, 2, @result);
SELECT @result;              -- 3
커서 반환
  • 커서를 파라미터로 전달받거나 반환할 수는 없다.
  • 다만 프로시저 안에서 커서를 열지 않거나 SELECT 결과를 Fetch 하지 않으면 그 결과가 클라이언트로 바로 전송된다.
  • 이 성질을 디버깅 용도로 자주 쓴다.
결과를 그대로 클라이언트로 
CREATE PROCEDURE sp_selectEmployees (IN in_empno INTEGER)
BEGIN
  SELECT * FROM employees WHERE emp_no = in_empno;
END;

CALL sp_selectEmployees(10001);
디버깅 메시지 출력 
CREATE PROCEDURE sp_sum (IN p1 INTEGER, IN p2 INTEGER, OUT p3 INTEGER)
BEGIN
  SELECT '> Stored procedure started' AS debug_message;
  SELECT CONCAT('> p1 : ', p1) AS debug_message;
  SELECT CONCAT('> p2 : ', p2) AS debug_message;
  SET p3 = p1 + p2;
  SELECT '> Stored procedure complete' AS debug_message;
END;

information_schema.ROUTINES 뷰로 정보 조회만 가능하다.

SELECT routine_schema, routine_name, routine_type
FROM information_schema.ROUTINES
WHERE routine_schema='realmysql';

스토어드 함수

  • 하나의 SQL 문장으로 작성할 수 없는 기능을 SQL의 일부로 구현해야 할 때 쓴다.
  • 8.0 이후로는 레터럴 조인이나 윈도우 함수가 이 역할을 대신할 수 있다.
  • 독립적으로 쓸 수 있는 상황이라면 프로시저 쪽이 낫다. 함수의 장점은 SQL의 일부로 쓸 수 있다는 것뿐이다.
생성 및 삭제
  • CREATE FUNCTION 으로 만든다.
  • 모든 파라미터가 읽기 전용이라 IN/OUT 을 명시할 수 없다.
  • 본문에 반드시 RETURNS 로 반환 타입을 명시해야 한다.
  • 본문에서 커서나 SELECT 를 써도 되지만 화면에 출력할 수는 없다 (프로시저와 다른 점).
  • 프로시저와 마찬가지로 ALTER 로 본문을 바꿀 수 없다. DROP → CREATE 가 필요하다.
  • 쓸 수 없는 것들
    • PREPARE + EXECUTE 를 이용한 프리페어드 스테이트먼트
    • 명시적·묵시적 ROLLBACK / COMMIT 을 유발하는 SQL
CREATE FUNCTION sf_sum(p1 INTEGER, p2 INTEGER)
  RETURNS INTEGER
BEGIN
  DECLARE p3 INTEGER DEFAULT 0;
  SET p3 = p1 + p2;
  RETURN p3;
END;
실행

CALL 로는 실행할 수 없고 SELECT 안에서 호출한다.

SELECT sf_sum(1, 2) AS sum;   -- 3

트리거

  • 테이블의 레코드가 변경되거나 저장될 때 미리 정의해 둔 작업을 자동 실행하는 기능이다.
  • 데이터 변화가 생길 때 다른 작업을 기동시키는 방아쇠 역할이다.
  • INSERT, UPDATE, DELETE 에 적용할 수 있고 유효성 검사, 복사·백업 등에 쓴다.
  • 프로시저나 함수보다 필요성이 떨어지는 편이고, 테이블에 대해서만 만들 수 있다.
복제 포맷에 따른 동작 차이
바이너리 로그 포맷소스 서버레플리카 서버
ROW 트리거가 실행되고, 그로 인한 변경 결과가 바이너리 로그에 기록된다 트리거를 따로 기동하지 않는다 — 이미 결과가 넘어오므로 실행한 것과 같은 효과
STATEMENT 트리거에 의한 데이터 변경은 기록하지 않는다 레플리카가 트리거를 직접 실행한다
생성
  • CREATE TRIGGER 로 만든다.
  • 트리거가 실행될 이벤트(사건) 와 시점(변경 전/후) 을 명시한다.
  • FOR EACH ROW 로 개별 레코드 단위 실행을 지정한다.
  • DROP, TRUNCATE 에서는 이벤트가 발생하지 않는다.
  • OLD, NEW 키워드로 각각 변경 전/후 값을 참조한다.
CREATE TRIGGER on_delete BEFORE DELETE ON employees
  FOR EACH ROW
BEGIN
  DELETE FROM salaries WHERE emp_no = OLD.emp_no;
END;
!

TRUNCATE 는 트리거를 부르지 않는다

위 예시처럼 트리거로 연관 데이터를 정리하고 있다면, 누군가 DELETE 대신 TRUNCATE 를 쓰는 순간 salaries 에 고아 레코드가 남는다. 트리거를 데이터 정합성의 유일한 보증 수단으로 삼기 어려운 이유다.

실행과 딕셔너리
  • 명시적으로 호출할 수 없다. 등록된 테이블의 레코드를 실제로 수정해야 동작한다.
  • 정보는 information_schema.TRIGGERS 뷰로 조회만 할 수 있다.
SELECT trigger_schema, trigger_name, event_manipulation,
       action_timing, action_statement
FROM information_schema.TRIGGERS
WHERE trigger_schema='employees';

이벤트

  • 주어진 시각에 스토어드 프로그램을 실행하는 스케줄러 기능이다.
  • 스케줄링 전담 스레드가 활성화되어 있어야 이벤트가 실행된다.
    • event_scheduler 를 ON 또는 1 로 설정한다.
생성
  • 반복 실행 여부에 따라 일회성과 반복성으로 나뉜다.
  • 일회성은 ON SCHEDULE AT 으로 설정하며, 정확한 시각이나 상대적 시각을 쓸 수 있다.
  • 단일 SQL만 실행한다면 BEGIN ... END 가 필요 없다.
  • ON COMPLETION 으로 완료된 이벤트의 삭제 여부를 지정한다.
    • 기본은 삭제. ON COMPLETION PRESERVE 를 붙이면 남는다.
  • 기본적으로 소스 서버에서는 enable, 레플리카에서는 disable 된다.
    • 레플리카가 소스로 승격될 때는 이벤트를 수동으로 활성화해야 한다.
CREATE EVENT onetime_job
  ON SCHEDULE AT CURRENT_TIMESTAMP + INTERVAL 1 HOUR
DO
  INSERT INTO daily_rank_log VALUES (NOW(), 'Done');
실행 확인과 딕셔너리
  • 테스트를 위해 강제로 실행시킬 수는 없다.
  • 스케줄링 정보와 최근 실행 시각은 information_schema.EVENTS 에서 확인한다.
    • 단, 마지막 실행 정보만 남으므로 전체 로그가 필요하면 별도 테이블을 만들어야 한다.

페일오버 시 잊기 쉬운 것

레플리카에서는 이벤트가 SLAVESIDE_DISABLED 상태로 들어온다. 장애로 레플리카를 소스로 승격시켰다면 배치성 이벤트가 전부 멈춘 상태라는 뜻이다. 승격 절차 체크리스트에 이벤트 활성화를 반드시 넣어 두어야 한다.

정리

  • 프로시저 — CALL 로만 실행, 반환값 없음, IN/OUT/INOUT 파라미터.
  • 함수 — SQL 안에서만 실행, RETURNS 필수, 파라미터는 전부 읽기 전용.
  • 둘 다 본문 변경은 DROP → CREATE 뿐이다.
  • 트리거 — OLD/NEW, FOR EACH ROW. TRUNCATE/DROP 에서는 동작하지 않는다.
  • 이벤트 — event_scheduler 가 켜져 있어야 하고, 레플리카에서는 비활성이다.
