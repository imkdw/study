11-1

쿼리 작성과 연관된 시스템 변수

같은 SQL이 서버마다 다르게 동작하는 이유 — sql_mode 와 운영체제.

핵심 5.x → 8.0 업그레이드에서 가장 자주 터지는 지점이 sql_mode 다. 8.0의 기본값은 훨씬 엄격하다.

SQL 모드

  • sql_mode 에는 여러 값이 들어가며 콤마로 구분된다.
  • 익숙하지 않다면 기본 설정을 그대로 쓰는 것을 권장한다.
  • 5.x → 8.0 업그레이드 시 특히 주의해야 한다.
기본 옵션효과
ONLY_FULL_GROUP_BYGROUP BY 에 없는 컬럼을 SELECT 하면 에러. 5.x에서 되던 쿼리가 깨지는 1순위 원인
STRICT_TRANS_TABLES잘못된 값 입력 시 경고가 아니라 에러
NO_ZERO_IN_DATE'2024-00-15' 같은 날짜를 거부
NO_ZERO_DATE'0000-00-00' 을 거부
ERROR_FOR_DIVISION_BY_ZERO0으로 나누면 에러
NO_ENGINE_SUBSTITUTION없는 스토리지 엔진을 지정하면 조용히 대체하지 않고 에러

영문 대소문자 구분

  • 서버의 운영체제에 따라 다르다.
  • 윈도우는 구분하지 않지만 유닉스 계열은 구분한다.
  • 가능하면 초기에 DB나 테이블을 전부 대문자 또는 전부 소문자로 생성하는 것을 권장한다.
!

개발 환경과 운영 환경이 다를 때

맥/윈도우에서 개발하고 리눅스에 배포하면 테이블명 대소문자 때문에 운영에서만 깨진다. 이 사고는 코드 리뷰에서 절대 잡히지 않는다.

예약어

  • 예약어를 DB·테이블·컬럼 이름으로 쓰려면 백틱(`)으로 감싸야 한다.
  • 하지만 에러 메시지를 명확히 받기 위해서라도 예약어로 객체를 만들지 않는 편이 좋다.

정리

  • 8.0의 sql_mode 기본값은 엄격하다. ONLY_FULL_GROUP_BY 가 업그레이드 시 가장 자주 문제를 만든다.
  • 대소문자 구분은 OS에 달렸다. 명명 규칙을 하나로 통일해 두는 것이 유일한 예방책이다.
  • 예약어는 백틱으로 쓸 수 있지만, 애초에 쓰지 않는 것이 답이다.
11-2

매뉴얼의 SQL 문법 표기를 읽는 법

기호 다섯 개만 알면 공식 매뉴얼의 문법 정의를 그대로 읽을 수 있다.

핵심 [ ] 는 선택, { } 는 필수 택일, | 는 택일, ... 는 반복, 이탤릭 은 내가 채워 넣을 자리.

MySQL 공식 매뉴얼의 INSERT 구문 정의는 다음과 같이 세 가지 형태로 제시된다.

MySQL Manual — INSERT Statement 
INSERT [LOW_PRIORITY | DELAYED | HIGH_PRIORITY] [IGNORE]
    [INTO] tbl_name
    [PARTITION (partition_name [, partition_name] ...)]
    [(col_name [, col_name] ...)]
    { {VALUES | VALUE} (value_list) [, (value_list)] ... }
    [AS row_alias[(col_alias [, col_alias] ...)]]
    [ON DUPLICATE KEY UPDATE assignment_list]

INSERT [LOW_PRIORITY | DELAYED | HIGH_PRIORITY] [IGNORE]
    [INTO] tbl_name
    [PARTITION (partition_name [, partition_name] ...)]
    SET assignment_list
    [AS row_alias[(col_alias [, col_alias] ...)]]
    [ON DUPLICATE KEY UPDATE assignment_list]

INSERT [LOW_PRIORITY | HIGH_PRIORITY] [IGNORE]
    [INTO] tbl_name
    [PARTITION (partition_name [, partition_name] ...)]
    [(col_name [, col_name] ...)]
    { SELECT ...
      | TABLE table_name
      | VALUES row_constructor_list
    }
    [ON DUPLICATE KEY UPDATE assignment_list]

세 형태는 각각 VALUES 방식, SET 방식, SELECT 방식 이다. 세 번째에 DELAYED 가 없다는 것도 이 표기법에서 바로 읽어 낼 수 있다.

표기의미예
이탤릭체 사용자가 직접 채워 넣는 토큰. 대부분 테이블명·컬럼명 tbl_name, col_name
[ ] 대괄호 그 키워드나 표현식이 선택 사항. 없어도 있어도 문법 에러가 아니다 [INTO], [IGNORE]
| 파이프 앞뒤 중 하나만 선택 가능 VALUES | VALUE
{ } 중괄호 괄호 안의 항목 중 반드시 하나는 써야 함 {VALUES | VALUE}
... 앞의 키워드·표현식 조합이 반복될 수 있음 [, (value_list)] ...
i

조합해서 읽어 보기 보강

{ {VALUES | VALUE} (value_list) [, (value_list)] ... } 한 줄을 풀면 — 중괄호라 반드시 있어야 하고, 파이프라 VALUES 나 VALUE 중 하나를 쓰고, 값 목록이 하나는 필수이며, 대괄호 + ... 이므로 , (...) 를 원하는 만큼 덧붙일 수 있다. 즉 멀티 로우 INSERT가 문법적으로 허용된다는 사실이 이 한 줄에 담겨 있다.

정리

  • [ ] 선택 · { } 필수 택일 · | 택일 · ... 반복 · 이탤릭 사용자 입력.
  • 이 다섯 개면 공식 매뉴얼의 어떤 구문 정의도 읽을 수 있다.
11-3

MySQL 연산자와 내장 함수

MySQL에는 ANSI가 아닌 자체 문법이 섞여 있다. 가독성을 위해 ANSI 쪽을 쓰자.

핵심 숫자 컬럼에 문자 상수는 괜찮지만 문자 컬럼에 숫자 상수는 재앙이다. 컬럼 쪽이 통째로 형변환되어 인덱스를 못 쓴다.

리터럴 표기법

문자열
  • 표준은 홑따옴표(') 다.
  • MySQL은 ' 와 " 를 모두 허용한다.
  • 객체 이름(예약어 등)을 감쌀 때는 백틱(`)을 쓴다.
-- ANSI 표준 (홑따옴표 이스케이프는 두 번 반복)
SELECT * FROM departments d WHERE dept_no = 'd''001';
SELECT * FROM departments d WHERE dept_no = 'd"001';

-- MySQL 자체 문법
SELECT * FROM departments d WHERE dept_no = "d'001";
SELECT * FROM departments d WHERE dept_no = "d""001";

-- 예약어를 객체명으로 쓸 때는 백틱
CREATE TABLE `insert` (id INT PRIMARY KEY);
숫자
  • 따옴표로 감싸거나 그대로 쓸 수 있다.
  • 숫자와 문자를 비교하면 자동 형변환이 일어나는데, 어느 쪽이 변환되느냐가 결정적이다.
비교변환 대상인덱스
숫자 컬럼 = 문자 상수 상수가 숫자로 변환 정상 사용
문자 컬럼 = 숫자 상수 컬럼 전체가 숫자로 변환 사용 불가 — 풀 스캔
문제 없음
SELECT * FROM test
WHERE num_col = '10001';
인덱스 사용 불가
SELECT * FROM test
WHERE str_col = 10001;
날짜
  • 정해진 포맷으로 표기하면 자동으로 DATE / DATETIME 으로 변환해 준다.
  • STR_TO_DATE() 같은 함수를 굳이 쓸 필요가 없다.
-- 아래 둘은 같은 의미이고, 둘 다 인덱스를 쓴다
SELECT * FROM dept_emp de WHERE from_date = '2011-01-01';
SELECT * FROM dept_emp de WHERE from_date = STR_TO_DATE('2011-01-01', '%Y-%m-%d');
불린
  • BOOL, BOOLEAN 타입이 있지만 실제로는 TINYINT 다.
  • C/C++ 처럼 TRUE=1, FALSE=0 으로 매핑한다.
  • 따라서 숫자 컬럼을 TRUE/FALSE 로 조회하면 0이나 1 이외의 값은 조회되지 않는다.
  • 꼭 불린 의미를 살리고 싶다면 ENUM 으로 관리하는 편이 명확하고 실수도 줄인다.

MySQL 연산자

동등 비교 (=, <=>)
  • <=> 는 = 와 같지만 NULL 도 하나의 값으로 취급해 비교한다.
SELECT NULL = NULL;      -- NULL
SELECT NULL IS NULL;     -- 1
SELECT NULL <=> NULL;    -- 1
부정 비교 (!=, <>)
  • 둘 중 무엇을 써도 동작은 같다. 가독성을 위해 하나로 통일하는 것을 권장한다.
  • 보통 <> 를 많이 쓴다.
NOT 연산자 (!)
  • TRUE/FALSE 결과를 반대로 만든다.
  • 숫자나 문자처럼 부정의 결과를 정확히 예측할 수 없다면 쓰지 말자.
SELECT NOT 1;        -- 0
SELECT NOT 0;        -- 1
SELECT NOT (1=1);    -- 0
AND(&&), OR(||)
  • MySQL은 &&, || 도 지원한다.
  • 그런데 sql_mode 의 PIPES_AS_CONCAT 때문에 || 가 문자열 연결 연산자가 될 수도 있다.
  • 가독성과 안전을 위해 AND, OR 를 쓰자.
나누기(/, DIV) 와 나머지(%, MOD)
SELECT 29 / 9;        -- 3.2222
SELECT 29 DIV 9;      -- 3      (정수 나눗셈)
SELECT MOD(29, 9);    -- 2
SELECT 29 MOD 9;      -- 2
SELECT 29 % 9;        -- 2
REGEXP 연산자
  • 문자열의 패턴을 검사한다. 좌측에 대상 문자열, 우측에 정규식.
  • POSIX 방식을 표준으로 사용한다.
  • 인덱스 레인지 스캔을 쓸 수 없어 성능상 좋지 않다.
  • 꼭 써야 한다면 WHERE 의 다른 조건으로 탐색 범위를 먼저 좁힌 뒤 쓰는 것을 권장한다.
LIKE 연산자
  • DBMS에서는 REGEXP 보다 LIKE 를 훨씬 많이 쓴다.
  • 와일드카드가 앞쪽에 붙으면 left-most 특성 때문에 인덱스를 쓸 수 없다.
BETWEEN 연산자
  • >= 와 <= 를 하나로 합친 연산자다.
  • IN 과 작동 방식이 다르므로 주의해야 한다.
    • IN 은 동등 비교로 작동한다.
    • BETWEEN 은 선형으로 인덱스를 훑지만, IN 은 동등 비교를 여러 번 수행하므로 IN 이 유리한 경우가 많다.
필요한 값이 듬성듬성하다면 IN 이 이긴다 — BETWEEN 은 그 사이의 쓸모없는 값까지 전부 읽는다.
IN 연산자
  • 여러 값에 대해 동등 비교를 수행한다.
  • NOT IN 은 부정형 비교라 인덱스 풀 스캔을 해야 한다.
튜플 IN — 복합 인덱스를 온전히 사용 
EXPLAIN
SELECT * FROM dept_emp de
WHERE (dept_no, emp_no) IN (('d001', 10017), ('d002', 10144));
-- key_len = dept_no(4*4) + emp_no(4) = 20

key_len 이 20이라는 것은 복합 기본키의 두 컬럼을 모두 작업 범위 결정에 썼다는 뜻이다.

MySQL 내장 함수

  • 기본 제공되는 내장 함수와 직접 만들어 쓰는 사용자 정의 함수로 나뉜다.
  • 사용자 정의 함수는 C/C++ API 로 만드는 것이라, 스토어드 함수·프로시저와는 다르다.

개별 내장 함수 목록은 노트에서 생략되었다.

정리

  • 문자 컬럼 = 숫자 상수 조합은 컬럼 전체를 형변환시켜 인덱스를 무력화한다.
  • 날짜는 문자열 리터럴로 그냥 쓰면 된다. STR_TO_DATE 는 불필요하다.
  • <=> 는 NULL-safe 동등 비교, || 는 sql_mode 에 따라 의미가 바뀐다.
  • 흩어진 값들을 찾을 때는 BETWEEN 보다 IN 이 낫다.
  • REGEXP 는 인덱스를 못 쓴다 — 다른 조건으로 범위를 먼저 좁힐 것.
11-4

SELECT

SELECT의 처리 순서에서 시작해 조인 · 서브쿼리 · CTE · 윈도우 함수 · 잠금 읽기까지.

핵심 LIMIT 은 WHERE 조건이 아니라 맨 마지막 단계다. LIMIT 200000, 10 이 느린 이유가 여기서 전부 설명된다.

SELECT 절의 처리 순서

어느 절이 먼저 실행되는지 모르면 결과를 예측할 수 없다. 대부분의 쿼리는 아래 순서를 따른다 (윈도우 함수와 CTE는 예외).

  1. 드라이빙/드리븐 테이블 조인 및 WHERE 적용
  2. GROUP BY 로 그루핑
  3. DISTINCT 로 중복 제거
  4. HAVING 조건으로 필터링
  5. ORDER BY 로 정렬
  6. LIMIT 으로 건수 제한
ORDER BY 가 조인보다 먼저 실행되는 경우

주로 GROUP BY 없이 ORDER BY 만 쓴 쿼리에서 나타나는 순서다.

  1. 드라이빙 테이블에서 WHERE 필터링
  2. ORDER BY 로 정렬
  3. 드리븐 테이블들과 조인
  4. LIMIT 으로 건수 제한
작업 순서 커스터마이징
  • 위 순서를 벗어나려면 서브쿼리(인라인 뷰) 를 써야 한다.
  • 다만 DERIVED 로 임시 테이블이 생기므로 주의해야 한다.
  • WITH 절(CTE)도 가장 먼저 실행되어 임시 테이블로 저장된다.
SELECT emp_no, cnt
FROM (
  SELECT s.emp_no, COUNT(DISTINCT e.first_name) AS cnt, MAX(s.salary) AS max_salary
  FROM salaries s
    INNER JOIN employees e ON e.emp_no = s.emp_no
  WHERE s.emp_no IN (100001, 100002)
  GROUP BY s.emp_no
  HAVING MAX(s.salary) > 1000
  LIMIT 10
) inline_view
ORDER BY max_salary ASC;

안쪽에서 LIMIT 까지 끝낸 뒤, 바깥에서 ORDER BY 를 적용한다. 원래는 불가능한 순서다.

MySQL 의 LIMIT 동작 방식
  • LIMIT 은 WHERE 조건이 아니라 모든 처리 결과에 대해 건수를 제한하는 형태다.
  • 그래서 항상 마지막에 실행된다.

WHERE · GROUP BY · ORDER BY 의 인덱스 사용

기본 규칙
  • 인덱스된 컬럼의 값을 변형하지 않고 그대로 써야 한다.
  • 컬럼을 가공한 뒤 상수와 비교하면 인덱스를 활용할 수 없다.
  • md5() 나 복잡한 연산이 필요하면 가상 컬럼이나 함수 기반 인덱스를 쓴다. (→ 8-6)
  • WHERE 에서는 상수값과 컬럼의 자료형이 일치해야 한다.
WHERE 의 인덱스 사용

인덱스를 쓰는 방식은 작업 범위 결정 조건과 체크 조건 두 가지다.

  • 작업 범위 결정 조건 — 동등 비교나 IN 으로 구성된 조건이, 인덱스의 컬럼 구성과 왼쪽부터 얼마나 일치하느냐에 따라 결정된다.
  • AND 조건 — 나열 순서와 무관하게 옵티마이저가 최적의 계획을 만들어 준다.
  • OR 조건
    • 조건 중 하나라도 인덱스가 없으면 풀 테이블 스캔이 된다.
    • 모두 인덱스가 있다면 index_merge 로 처리할 수 있다.
    • WHERE 에 OR 가 있다면 항상 주의하는 편이 좋다.
GROUP BY 의 인덱스 사용
  • GROUP BY 컬럼의 순서가 인덱스 구성 순서와 같아야 한다.
  • 인덱스 뒤쪽 컬럼은 생략해도 되지만, 앞쪽 컬럼이 빠지면 사용할 수 없다.
  • GROUP BY 에 명시된 컬럼 중 하나라도 인덱스에 없으면 — WHERE 와 달리 — 인덱스를 아예 쓸 수 없다.
사용 불가
-- INDEX(COL_1, COL_2, COL_3) 기준
... GROUP BY COL_2, COL_1
... GROUP BY COL_1, COL_3
사용 가능
... GROUP BY COL_1, COL_2
... GROUP BY COL_1, COL_2, COL_3
WHERE + GROUP BY 를 함께 쓸 때
... WHERE COL_1='const' ... GROUP BY COL_2, COL_3
... WHERE COL_1='const' ... GROUP BY COL_1, COL_2, COL_3
  • 둘 다 COL_1 이 상수와 비교되므로 인덱스를 쓴다.
  • GROUP BY 절을 고쳐도 결과가 같다면, WHERE 와 GROUP BY 모두 인덱스를 쓴다고 판단한다.
ORDER BY 의 인덱스 사용
  • GROUP BY 조건과 거의 같지만 한 가지가 더 있다.
  • 각 컬럼의 ASC/DESC 가 인덱스와 전부 같거나 전부 정반대여야 한다.
  • MySQL 인덱스는 기본적으로 ASC 로 저장된다.
  • 즉 ORDER BY 의 모든 컬럼이 전부 ASC 이거나 전부 DESC 여야 한다.
사용 불가 
-- INDEX(COL_1, COL_2, COL_3) 기준
... ORDER BY COL_2, COL_3            -- 선행 컬럼 누락
... ORDER BY COL_1, COL_3, COL_2     -- 순서 불일치
... ORDER BY COL_1, COL_2 DESC, COL_3 -- 방향 혼재
WHERE + ORDER BY (또는 GROUP BY) 의 인덱스 사용

아래 세 가지 중 하나의 방법으로만 인덱스를 쓴다.

방법설명적합한 경우
WHERE + ORDER BY 가 같은 인덱스 조건과 정렬 대상이 하나의 인덱스에 연속해서 포함됨 가능하다면 이 방식으로 유도하는 것이 최선
WHERE 만 인덱스 사용 정렬은 소트 버퍼(Filesort)로 처리 WHERE 결과가 많지 않을 때 효율적
ORDER BY 만 인덱스 사용 인덱스 순서대로 읽으며 한 건씩 조건 검사 후 취사선택 정렬할 레코드가 아주 많을 때. 단 랜덤 I/O가 많이 발생
둘 다 인덱스로 처리
SELECT * FROM test
WHERE col_1 > 10
ORDER BY col_1, col_2, col_3;
ORDER BY 는 별도 처리
SELECT * FROM test
WHERE col_1 > 10
ORDER BY col_2, col_3;
GROUP BY + ORDER BY 의 인덱스 사용
  • 하나의 인덱스로 둘 다 처리하려면 양쪽의 컬럼과 순서가 동일해야 한다.
  • 둘 중 하나라도 인덱스를 못 쓰면 둘 다 못 쓴다.
  • 8.0부터는 GROUP BY 가 자동 정렬을 하지 않으므로, 그루핑과 정렬을 다 하려면 양쪽 모두 명시해야 한다.
WHERE + GROUP BY + ORDER BY

WHERE 비교 조건 사용 시 주의사항

NULL 비교
  • MySQL은 NULL 허용 컬럼도 인덱스로 관리한다.
  • NULL 비교에는 IS NULL, ISNULL(), <=> 를 써야 한다.
  • 그 외의 형태는 인덱스를 쓸 수 없으므로 IS NULL 사용을 권장한다.
인덱스 사용 가능
SELECT * FROM titles t
WHERE to_date IS NULL;

SELECT * FROM titles t
WHERE ISNULL(t.to_date);
인덱스 사용 불가
SELECT * FROM titles t
WHERE ISNULL(to_date)=1;

SELECT * FROM titles t
WHERE ISNULL(to_date)=true;

차이는 미묘하다 — ISNULL(col) 자체는 최적화되지만, 그 결과를 다시 비교하는 순간 표현식이 되어 인덱스를 잃는다.

문자열이나 숫자 비교
  • 컬럼 타입에 맞는 상수값을 쓰는 것을 권장한다.
  • 숫자 컬럼에 문자열 상수를 비교하면 상수만 변환되므로 영향이 없다.
  • 문자열 컬럼에 숫자를 비교하면 비교 대상 컬럼을 전부 숫자로 변환하므로 성능에 영향이 있다.
날짜 비교
DATE / DATETIME 과 문자열
  • MySQL이 내부적으로 문자열을 자동으로 DATETIME 으로 변환해서 비교한다.
  • STR_TO_DATE() 도 쓸 수 있고, 두 방식 모두 인덱스를 쓰므로 걱정하지 않아도 된다.
  • 하지만 날짜 타입 컬럼을 문자열로 변환하거나 연산을 하면 인덱스를 쓸 수 없다.
  • 가능하면 컬럼이 아니라 상수 쪽을 변형하는 형태로 조건을 쓰는 것이 좋다.
DATE 와 DATETIME 비교
  • date_col > DATE(NOW()) 형태로 쓰면 된다.
  • 인덱스 사용에는 영향이 없으므로 결과값에만 주의하면 된다.
DATETIME 과 TIMESTAMP 비교
컬럼 타입변환 방법
DATETIMEFROM_UNIXTIME(상수) 로 TIMESTAMP를 DATETIME 으로 바꿔 비교
TIMESTAMPUNIX_TIMESTAMP(상수) 로 DATETIME 을 TIMESTAMP 로 바꿔 비교

핵심은 변환 대상이 항상 상수 쪽이어야 한다는 것이다. NOW() 를 쓰는 방법도 있다.

Short-Circuit Evaluation
  • 여러 표현식이 AND/OR 로 연결된 경우, 선행 조건의 결과에 따라 후행 조건 평가를 건너뛰는 최적화다.
  • MySQL도 이 방식으로 처리할지 판단한다.
  • 단, WHERE 에 인덱스를 쓰는 조건이 있으면 그 조건이 최우선으로 평가된다.
  • 서브쿼리나 복잡한 연산은 WHERE 절의 뒤쪽에 배치하는 것이 성능에 도움이 된다.

DISTINCT

  • 특정 컬럼의 유니크한 값을 조회할 때 붙인다.
  • 남발하면 성능뿐 아니라 결과도 의도와 다르게 나올 수 있다. (→ 9-2 DISTINCT 처리)

LIMIT n

  • 처리된 결과에서 지정된 순서에 위치한 레코드만 가져온다.
  • WHERE 조건이 아니라서 항상 맨 마지막에 실행된다.
  • 모든 레코드의 정렬이 끝나지 않았더라도 상위 N건만 정렬되면 작업을 멈춘다.
  • 중요한 것은 보이는 결과가 아니라 그 결과를 만들기 위해 무슨 일을 했는가 이다.
  • LIMIT (N, M) 의 인자에는 함수나 서브쿼리를 넣을 수 없다.
다른 문법과 함께 쓸 때
쿼리동작LIMIT 의 효과
SELECT * FROM employees LIMIT 0, 10 풀 스캔 시작 → 10건 읽는 순간 종료 매우 큼
... GROUP BY first_name LIMIT 0, 10 그루핑이 전부 끝나야 LIMIT 적용 가능 거의 없음
SELECT DISTINCT first_name ... LIMIT 0, 10 풀 스캔하며 중복 없는 값을 만들다가 10건 되면 종료 중복 분포에 따라 클 수 있음
WHERE ... ORDER BY ... LIMIT 0, 10 WHERE로 읽고 정렬하다 10건 완성되면 중단 레코드 접근 비용이 더 커서 향상은 제한적
성능상의 이슈 — 깊은 페이징
  • LIMIT 200000, 10 은 200,010건을 먼저 읽는다.
  • 그리고 앞의 20만 건을 버리고 맨 뒤 10건만 반환한다.
  • 결국 읽는 양은 똑같으므로 페이지가 깊어질수록 느려진다.

WHERE 로 읽을 범위 자체를 좁힌 다음 필요한 만큼만 반환하는 것이 해법이다.

COUNT()

  • 결과의 레코드 건수를 반환한다.
  • COUNT(*) 의 * 는 모든 컬럼이 아니라 레코드 자체를 의미한다.
  • InnoDB는 데이터나 인덱스를 직접 읽어야 계산할 수 있으므로 대용량 테이블에서는 주의해야 한다.
    • 대용량이라면 SHOW TABLE STATUS + ANALYZE TABLE 로 대략값을 보는 편이 낫다.
많이 저지르는 실수
  • ORDER BY 로 정렬하거나, LEFT JOIN 처럼 건수와 무관한 작업을 함께 하는 것.
  • 레코드 개수를 세는 데 정렬은 아무 상관이 없다.
  • LEFT JOIN 도 건수 변화가 없거나 아우터 테이블에서 별도 검사를 하지 않아도 된다면 제거하자.
  • 8.0부터는 COUNT(*) 에 붙은 ORDER BY 를 무시하도록 개선되었다. 그래도 쿼리 복잡도를 낮추고 가독성을 높이기 위해 필요한 문장만 쓰는 것이 좋다.
COUNT 와 인덱스
  • 인덱스를 제대로 쓰도록 튜닝되지 않은 COUNT 쿼리는 페이징 쿼리보다 더 느릴 수 있다.
  • COUNT(*) 도 상당한 부하를 만든다.
COUNT 와 NULL
  • 인자로 컬럼명이나 표현식을 쓰면 NULL 이 아닌 것만 카운팅된다.
  • NULL 허용 컬럼이라면 결과가 의도와 맞는지 반드시 검사해 봐야 한다.

JOIN 의 순서와 인덱스
  • 인덱스 레인지 스캔은 탐색(Seek) 과 스캔(Scan) 으로 나뉜다.
  • 가져오는 레코드가 적으면 스캔 부하는 작지만, 탐색은 상대적으로 부하가 높다.
  • 드리븐 테이블에서 레코드를 읽는 것이 훨씬 큰 부하이므로, 옵티마이저가 최적의 계획을 세워 준다.
SELECT *
FROM employees e, dept_emp de
WHERE e.emp_no = de.emp_no;
인덱스 상황드라이빙 선택이유
양쪽 다 인덱스 있음 레코드 건수에 따라 둘 다 가능 옵티마이저의 선택이 대개 최적
employees.emp_no 에만 인덱스 dept_emp employees 가 드라이빙이면 레코드마다 dept_emp 를 풀 스캔해야 한다
dept_emp.emp_no 에만 인덱스 employees 위와 반대
양쪽 다 인덱스 없음 레코드가 적은 쪽 어차피 풀 스캔은 발생하므로, 반복 횟수를 줄이는 편이 낫다
JOIN 컬럼의 데이터 타입
  • 인덱스를 쓰려면 비교 양쪽의 데이터 타입을 일치시켜야 한다.
  • 문자 집합과 콜레이션이 다른 경우도 풀 스캔이 될 확률이 높으니 주의해야 한다.
    • 이 경우 서로 통일하는 것이 유일한 해결책이다.
    • 각 컬럼에 맞는 타입을 선정하고, 최종적으로 점검하는 것이 좋다.
OUTER JOIN 의 성능과 주의사항
  • 아우터 조인은 양쪽 데이터가 일관되지 않은 경우에만 필요한 방법이다.
  • 옵티마이저는 아우터로 조인되는 테이블을 절대 드라이빙으로 선택하지 못한다. 그래서 풀 스캔이 필요한 테이블을 드라이빙으로 고르게 된다.
  • 이너 조인으로 충분한데 아우터 조인으로 작성하는 것은 옵티마이저에게서 최적화의 기회를 빼앗는 것이다.
LEFT JOIN — e 를 풀 스캔
EXPLAIN
SELECT * FROM employees e
LEFT JOIN dept_emp de
  ON de.emp_no = e.emp_no
LEFT JOIN departments d
  ON d.dept_no = de.dept_no
 AND d.dept_name = 'Development';
-- e: ALL, rows 300,252
INNER JOIN — d 부터 시작
EXPLAIN
SELECT * FROM employees e
INNER JOIN dept_emp de
  ON de.emp_no = e.emp_no
INNER JOIN departments d
  ON d.dept_no = de.dept_no
 AND d.dept_name = 'Development';
-- d: ref, rows 1

이너 조인으로 바꾸니 dept_name='Development' 인 부서 1건부터 시작한다. 시작점이 30만에서 1로 바뀐 것이다.

OUTER JOIN 에서 자주 하는 실수
  • 아우터로 조인되는 테이블의 조건을 WHERE 절에 쓰는 실수다.
  • 이 경우 옵티마이저는 LEFT JOIN 을 INNER JOIN 으로 변환해 실행한다 — 아우터 조인의 의미가 사라진다.
  • 정상적인 아우터 조인이라면 조건을 ON 절로 옮겨야 한다.
before — 사실상 INNER JOIN
SELECT * FROM employees e
LEFT JOIN dept_manager mgr
  ON mgr.emp_no = e.emp_no
WHERE mgr.dept_no = 'd001';
after — 진짜 OUTER JOIN
SELECT * FROM employees e
LEFT JOIN dept_manager mgr
  ON mgr.emp_no = e.emp_no
 AND mgr.dept_no = 'd001';
JOIN 과 외래키
  • 외래키와 조인은 아무런 연관이 없다. 외래키는 참조 무결성을 위한 수단이다.
  • 데이터 모델링에서는 관계를 그리지만, 실제 테이블 생성 시에는 걸지 않는 경우도 많다. (→ 8-10 외래키)
지연된 조인 (Delayed Join)
  • 조인이 실행되기 전에 GROUP BY, ORDER BY 를 처리하는 방식이다.
  • 인덱스를 쓰지 못하는 쿼리에서 유용하다.
기존 방법 조인 후 그루핑·정렬 
EXPLAIN
SELECT e.*
FROM salaries s, employees e
WHERE e.emp_no = s.emp_no
  AND s.emp_no BETWEEN 10001 AND 13000
GROUP BY s.emp_no
ORDER BY SUM(s.salary) DESC
LIMIT 10;

조인된 결과를 임시 테이블에 저장하고 그루핑·정렬한 뒤 상위 10건을 반환한다.

지연된 조인 그루핑·정렬 후 조인 
EXPLAIN
SELECT *
FROM (
  SELECT s.emp_no
  FROM salaries s
  WHERE s.emp_no BETWEEN 10001 AND 13000
  GROUP BY s.emp_no
  ORDER BY SUM(s.salary)
  LIMIT 10
) x, employees e
WHERE e.emp_no = x.emp_no;

서브쿼리에서 레코드를 10건으로 줄인 다음 조인한다. 조인 대상이 극적으로 줄어드는 것이 핵심이다.

지연된 조인을 쓸 수 있는 조건
  • LEFT (OUTER) JOIN 의 경우 드라이빙-드리븐이 1:1 또는 M:1 관계여야 한다.
  • 드라이빙 테이블의 레코드가 드리븐 테이블에 모두 존재해야 한다.
  • 즉 데이터 정합성이 보장된다는 전제이므로, 반드시 확인 후 적용해야 한다.
레터럴 조인 (Lateral Join)
  • 특정 그룹별로 서브쿼리를 실행해 그 결과와 조인할 수 있는 기능이다.
  • FROM 절 서브쿼리가 외부 컬럼을 참조하려면 LATERAL 키워드가 있어야 한다.
  • 다만 LATERAL 서브쿼리는 조인 순서상 후순위로 밀리고, 외부 결과값마다 임시 테이블이 만들어지므로 꼭 필요할 때만 써야 한다.
그룹별 최신 N건 — 레터럴 조인의 전형 
EXPLAIN
SELECT *
FROM employees e
LEFT JOIN LATERAL (
  SELECT * FROM salaries s
  WHERE s.emp_no = e.emp_no
  ORDER BY s.from_date DESC
  LIMIT 2
) s2 ON s2.emp_no = e.emp_no
WHERE e.first_name = "Matt";
실행 계획으로 인한 정렬 흐트러짐
  • 네스티드 루프에서는 드라이빙 테이블에서 읽은 순서가 조인 후에도 유지된다.
    • 드라이빙 테이블을 스캔한 순서가 그대로 최종 결과에 반영되기 때문이다.
  • 하지만 해시 조인이 쓰이면 결과의 순서가 달라진다.
  • 정렬된 결과가 필요하다면 드라이빙 테이블 순서에 의존하지 말고 ORDER BY 를 명시해야 한다.

ORDER BY

  • 인덱스를 쓸 수 있으면 인덱스로, 아니면 서버가 자체적으로 정렬한다.
  • 어떤 DBMS도 자동 정렬을 보장하지 않는다. 정렬이 필요하면 ORDER BY 를 명시해야 한다.
    • MySQL은 클러스터링 인덱스 특성 때문에 풀 스캔 시 정렬된 것처럼 보일 뿐이다.
사용법 및 주의사항
  • ORDER BY 의 인자는 숫자 또는 컬럼명만 가능하다.
  • 문자열 리터럴이 들어오면 옵티마이저가 ORDER BY 자체를 무시한다.
-- dept_no 로 오름차순 정렬
SELECT * FROM dept_emp de ORDER BY de.dept_no;

-- SELECT 의 첫 번째 컬럼 기준으로 오름차순 정렬
SELECT * FROM dept_emp de ORDER BY 1;

-- ORDER BY 가 없는 것과 동일 (조용히 무시된다)
SELECT * FROM dept_emp de ORDER BY "dept_no";
×

따옴표 하나로 정렬이 사라진다

ORDER BY "dept_no" 는 에러가 아니다. 문자열 상수는 모든 행에서 같은 값이라 정렬 기준이 되지 못하고, 그냥 무시된다. 동적으로 정렬 컬럼을 만들어 넣는 코드에서 특히 위험하다.

여러 방향으로 동시 정렬
  • 컬럼마다 ASC / DESC 를 섞을 수 있다.
  • 인덱스도 그 순서대로 생성되어 있다면 정렬에 인덱스를 쓸 수 있다. (→ 8-3 내림차순 인덱스)
SELECT * FROM dept_emp de ORDER BY de.emp_no ASC, de.dept_no DESC;
함수나 표현식을 이용한 정렬

8.0부터는 가상 컬럼과 함수 기반 인덱스로 표현식 정렬에도 인덱스를 쓸 수 있게 되었다.

서브쿼리

  • 서브쿼리를 쓰면 단위 처리별로 쿼리를 독립적으로 작성할 수 있다.
  • 조인처럼 테이블을 섞지 않아 가독성이 좋고 복잡한 쿼리도 쓰기 쉽다.
  • 보통 SELECT, FROM, WHERE 세 곳에 쓰인다.
SELECT 절의 서브쿼리
  • 반드시 컬럼 1개, 레코드 1건인 결과를 반환해야 한다.
  • 값이 NULL 이든 아니든 레코드가 1건은 있어야 한다. 없으면 그냥 NULL 이 나온다.
-- OK (결과가 없어 NULL 이 나온다)
SELECT emp_no, (SELECT dept_name FROM departments d WHERE dept_name='Sales1')
FROM dept_emp de LIMIT 10;

-- SQL Error [1242] [21000]: Subquery returns more than 1 row
SELECT emp_no, (SELECT dept_name FROM departments d)
FROM dept_emp de LIMIT 10;

-- SQL Error [1242] [21000]: Subquery returns more than 1 row
SELECT emp_no, (SELECT dept_no, dept_name FROM departments d WHERE dept_name='Sales1')
FROM dept_emp de LIMIT 10;
JOIN vs 서브쿼리
  • 서브쿼리보다 조인이 빠른 경우가 많다. 가능하면 조인으로 처리하자.
  • 레코드 건수가 클수록 차이가 벌어진다.

FROM 절의 서브쿼리
  • 이전에는 항상 임시 테이블로 처리했지만, 현재는 외부 쿼리로 병합하는 최적화가 들어갔다.
  • 다만 병합이 불가능한 경우도 있다 — MAX/MIN 등 집합 함수, DISTINCT, GROUP BY/HAVING 등.
  • 이 최적화는 optimizer_switch=derived_merge 로 제어한다. (→ 9-3 파생 테이블 머지)
WHERE 절의 서브쿼리

세 가지 형태가 있다 — 동등/부등 비교, IN, NOT IN.

동등 / 부등 비교
  • 풀 스캔이 아니라 서브쿼리를 먼저 실행해 상수로 변환한다.
  • 그 상수값으로 서브쿼리를 대체해 나머지를 처리한다.
  • 실행 계획에서 ref 가 전부 const 인 것으로 확인할 수 있다.
SELECT * FROM dept_emp de
WHERE de.emp_no = (
  SELECT e.emp_no FROM employees e
  WHERE e.first_name = 'Georgi' AND e.last_name = 'Facello'
  LIMIT 1
);
IN 비교 — 세미 조인
  • 다른 테이블의 레코드와 일치하는지 확인하는 형태를 세미 조인이라 한다.
  • 즉 WHERE 의 IN (subquery) 는 조인의 한 방식이다.
  • 세미 조인 최적화가 많이 개선되어 테이블 풀아웃, 퍼스트 매치 등으로 잘 처리된다.
  • 8.0 이후를 쓴다면 쿼리를 여러 조각으로 쪼개는 습관은 버리고 세미 조인에 익숙해지는 편이 낫다.
NOT IN 비교 — 안티 세미 조인
  • 일반적으로 DBMS에서 Not Equal 연산에는 인덱스를 쓸 수 없다.
  • 안티 세미 조인은 NOT EXISTS 나 구체화 방법으로 최적화된다.
  • 가능하면 다른 조건으로 검색 범위를 최대한 좁히는 것을 권장한다.

CTE (Common Table Expression)

  • 이름을 가진 임시 테이블로, SQL 문장이 끝나면 자동 삭제된다.
  • 재귀 반복 여부에 따라 비재귀(Non-Recursive) 와 재귀(Recursive) 로 나뉜다.
  • ANSI 표준을 준수해 WITH 절로 정의한다.
비재귀적 CTE
서브쿼리와 동일하게 쓰기 (결과·실행 계획 모두 동일) 
WITH cte1 AS (SELECT * FROM departments d)
SELECT * FROM cte1;

SELECT * FROM (SELECT * FROM departments d) cte1;
여러 개의 임시 테이블을 하나의 쿼리에서 
WITH cte1 AS (SELECT * FROM departments d),
     cte2 AS (SELECT * FROM dept_emp de)
SELECT *
FROM cte1
  INNER JOIN cte2 ON cte2.dept_no = cte1.dept_no;

재귀적 CTE
  • 비재귀 파트와 재귀 파트로 구성된다.
  • 두 파트를 UNION 또는 UNION ALL 로 연결해야 한다.
  • 비재귀 파트 — SELECT 1 에 해당하는 부분으로, CTE 테이블의 구조를 결정한다.
  • 재귀 파트
    • 지금까지의 전체 결과가 아니라 직전 단계의 결과만 입력으로 쓴다.
    • 재귀 파트의 결과가 0건이 될 때까지 반복한다.
    • 최대 반복 횟수는 기본 1000, cte_max_recursion_depth 로 조정한다.
WITH RECURSIVE cte (no) AS (
  SELECT 1                                    -- 비재귀 파트
  UNION ALL
  SELECT (no + 1) FROM cte WHERE no < 5       -- 재귀 파트
)
SELECT * FROM cte;
-- 1, 2, 3, 4, 5

재귀적 CTE 의 실전 활용 예제는 노트에서 생략되었다.

윈도우 함수 (Window Function)

  • 현재 레코드를 기준으로 연관된 레코드 집합에 대한 연산을 수행한다.
  • 집계 함수는 그룹별로 하나의 레코드로 묶지만, 윈도우 함수는 레코드 건수를 그대로 유지한다.
  • 즉 GROUP BY 는 결과 집합의 모양을 바꾸지만, 윈도우 함수는 모양을 유지하면서 다른 레코드의 컬럼값을 참조할 수 있게 해 준다.
쿼리 각 절의 실행 순서
  1. FROM · WHERE · GROUP BY · HAVING
  2. 윈도우 함수 처리
  3. SELECT · ORDER BY · LIMIT
SELECT emp_no, from_date, salary,
  AVG(salary) OVER() AS avg_salary
FROM salaries s
WHERE emp_no = 10001
LIMIT 5;

기본 사용법
  • 집계 함수와 달리 OVER() 절로 연산 대상을 파티션할 수 있다.
  • OVER() 로 만들어진 그룹을 파티션 또는 윈도우 라고 부른다.
전체 기준 입사 순서 
SELECT e.*,
  RANK() OVER(ORDER BY e.hire_date) AS hire_date_rank
FROM employees e;

  • 각 파티션 안에서도 레코드별로 연산 대상이 되는 소그룹이 쓰인다.
  • 이를 프레임이라 하며, 명시하지 않아도 알맞은 프레임이 묵시적으로 선택된다.

그 외 프레임 옵션은 노트에서 생략되었다 (원서 P130~P132).

집계 함수와 비집계 함수
  • 윈도우 함수에는 집계 함수와 비집계 함수를 모두 쓸 수 있다.
  • 집계 함수는 OVER() 없이 단독으로도 쓸 수 있지만, 비집계 함수는 불가능하다.
  • 비집계 함수(RANK, ROW_NUMBER, LAG 등)는 오직 윈도우 함수로만 쓸 수 있다.
윈도우 함수의 성능
  • 아직 인덱스를 이용한 최적화가 많이 부족하다.
  • 너무 의존하지 않는 편이 좋다.
  • OLTP 서비스에서 많은 레코드에 윈도우 함수를 적용하는 것은 가능하면 피하자.

잠금을 사용하는 SELECT

  • InnoDB의 SELECT 는 기본적으로 아무런 잠금도 걸지 않는다.
  • 하지만 읽은 값을 애플리케이션에서 처리하는 동안 수정되지 않도록 해야 할 때가 있다.
    • 이때 FOR SHARE 또는 FOR UPDATE 를 쓴다.
  • 두 방법 모두 AUTOCOMMIT=off 이거나 트랜잭션이 시작된 상태에서만 동작한다.
  • 이 절이 없는 단순 SELECT 는 아무 대기 없이 실행된다.
  • 아무리 좋은 서버라도 처리가 전부 순차화되면 남는 자원을 활용할 수 없다.

잠글 테이블 선택 — OF
  • 외부 테이블을 조인하는 쿼리에 FOR UPDATE 를 쓰면 조인된 모든 테이블에 배타 잠금이 걸린다.

  INNER JOIN dept_emp de ON de.emp_no = e.emp_no
FOR UPDATE OF e;
NOWAIT
  • 이미 다른 세션이 잠근 상태라면 기다리지 않고 즉시 에러를 반환한다.
  • 잠금이 없다면 일반 쿼리처럼 실행된다.
SELECT * FROM employees e WHERE emp_no = 10001 FOR UPDATE NOWAIT;
SKIP LOCKED
  • 잠긴 레코드는 건너뛰고 잠기지 않은 레코드만 가져온다. 에러를 내지 않는다.
  • 이 특성 때문에 비확정적(NOT-DETERMINISTIC) 쿼리가 된다.
    • 입력이 같아도 시점에 따라 다른 결과가 나올 수 있다.
    • 문장 기반 복제에서는 소스와 레플리카의 데이터가 달라질 수 있다.
    • 이를 대비해 바이너리 로그 포맷은 STATEMENT 보다 ROW 또는 MIXED 를 권장한다.
  • 결과적으로 잠긴 레코드를 스킵하는 시간만 지나면 각 트랜잭션이 서로를 기다리지 않고 진행할 수 있다.
SELECT * FROM employees e WHERE emp_no = 10001 FOR UPDATE SKIP LOCKED;
사용 예시
  • 주로 큐(Queue) 같은 기능을 구현할 때 유용하다.
  • 간단한 예시로 쿠폰 발급 기능이 있다 — 여러 워커가 동시에 SKIP LOCKED 로 아직 발급되지 않은 쿠폰을 집어 가면, 서로 대기하지 않고 각자 다른 쿠폰을 가져간다.

정리

  • 실행 순서는 조인/WHERE → GROUP BY → DISTINCT → HAVING → ORDER BY → LIMIT. LIMIT 은 언제나 맨 끝.
  • 인덱스는 WHERE·GROUP BY·ORDER BY 중 한 조합에만 쓰인다. 셋을 다 만족시키는 인덱스가 최선.
  • 깊은 페이징은 OFFSET 대신 커서(마지막 값 기준 WHERE) 로 푼다.
  • 아우터 조인 조건은 반드시 ON 절에. WHERE 에 쓰면 이너 조인으로 변환된다.
  • 같은 상관 서브쿼리를 여러 번 쓴다면 레터럴 조인으로, 같은 파생 테이블을 여러 번 쓴다면 CTE 로.
  • 윈도우 함수는 LIMIT 보다 먼저 실행된다 — 결과 해석에 주의.
  • 큐 구현에는 FOR UPDATE SKIP LOCKED. 단 복제 포맷은 ROW/MIXED 로.
11-5

INSERT

INSERT 문 자체에는 튜닝할 것이 거의 없다. 테이블 구조와 기본키가 성능을 결정한다.

핵심 대량 INSERT의 성능은 기본키 순서대로 들어오는가에 달렸다. 순서대로면 페이지 분할이 없고, 랜덤이면 매번 자리를 찾아야 한다.

들어가며

  • INSERT가 동시에 실행될 때는 문장 자체보다 테이블 구조가 성능에 영향을 준다.
  • 대부분의 경우 INSERT와 SELECT 성능을 동시에 빠르게 만들 수 있는 구조는 없다. 인덱스를 늘리면 SELECT는 빨라지고 INSERT는 느려진다.

INSERT IGNORE

다음 두 경우를 에러 대신 경고로 낮추고 다음 레코드를 계속 처리하게 한다.

  • 기본키나 유니크 인덱스 컬럼이 이미 테이블에 존재하는 경우
  • 저장하려는 값이 컬럼 타입과 호환되지 않는 경우
    • NOT NULL 컬럼에 NULL을 넣으면 숫자 컬럼 기준 0 이 들어간다.
  • 여러 레코드를 하나의 INSERT 문으로 처리할 때 특히 유용하다.
  • 중복 무시 목적으로 쓴다면 중복 외의 다른 문제가 함께 삼켜지지 않는지 면밀히 확인해야 한다.
INSERT IGNORE INTO employees
  (emp_no, birth_date, first_name, last_name, gender, hire_date)
VALUES (10001, '1956-06-08', 'Margareta', 'Markovitch', 'M', '1985-01-01'),
       (10002, '1959-10-28', 'Ebru', 'Alpin', 'M', '1985-01-01'),
       (10003, '1953-06-24', 'Shirish', 'Ossenbruggen', 'F', '1985-01-01'),
       (10004, '1956-06-08', 'Krassimir', 'Wegerle', 'F', '1985-01-01');
!

조용히 값이 바뀐다

INSERT IGNORE 는 중복만 무시하는 것이 아니라 타입 불일치도 무시하고 기본값으로 바꿔 넣는다. NULL을 넣었더니 0이 저장되는 식이다. 중복 회피가 목적이라면 ON DUPLICATE KEY UPDATE 쪽이 의도가 명확하다.

INSERT ... ON DUPLICATE KEY UPDATE

  • 기본키나 유니크 인덱스에 중복이 발생하면 UPDATE 처럼 동작한다.
  • REPLACE 도 비슷하지만, 내부적으로 DELETE + INSERT 조합으로 작동한다.
  • 일별 집계값 관리 같은 곳에 매우 편리하다.
upsert.sql 권장 
CREATE TABLE daily_statistic (
  target_date DATE NOT NULL,
  stat_name VARCHAR(10) NOT NULL,
  stat_value BIGINT NOT NULL DEFAULT 0,
  PRIMARY KEY (target_date, stat_name)
);

INSERT INTO daily_statistic (target_date, stat_name, stat_value)
  VALUES (DATE(NOW()), 'VISIT', 1)
  ON DUPLICATE KEY UPDATE stat_value = stat_value + 1;

첫 방문이면 INSERT, 이후에는 UPDATE — 애플리케이션에서 존재 여부를 조회할 필요가 없다.

LOAD DATA 명령 주의 사항

  • 일반적으로 INSERT 보다 빠르지만 단점이 있다.
  • 테이블 간 복사라면 LOAD DATA 보다 INSERT ... SELECT 를 WHERE 로 분할해 실행하는 것을 권장한다.
    • 이렇게 하면 멀티 스레드로 나눠 삽입할 수 있다.
단점내용
단일 스레드 적재할 데이터가 많으면 시간이 매우 길어진다. 인덱스가 많으면 더 심해진다
단일 트랜잭션 문장이 시작한 시점부터 언두 로그가 계속 유지된다. 디스크 기록 부담뿐 아니라, 쌓인 언두 때문에 다른 조회 쿼리들이 원하는 레코드를 찾는 오버헤드도 커진다

가능하면 파일을 여러 개로 나눠 LOAD DATA 를 여러 트랜잭션으로 실행하는 것이 좋다.

성능을 위한 테이블 구조

  • INSERT 문 자체에는 튜닝할 부분이 별로 없다.
  • 실제 튜닝에서도 소량 삽입 문장은 무시하는 경우가 많다.
대량 INSERT 성능
  • 다수 건을 삽입한다면 미리 기본키 순서로 정렬해서 넣는 것이 도움이 된다.
  • 레코드를 삽입할 때마다 InnoDB는 기본키를 찾아 저장될 위치를 결정해야 한다.
  • 이미 정렬되어 있다면 매번 위치를 찾지 않아도 되므로 성능이 향상된다.

세컨더리 인덱스와 대량 INSERT
  • 대량 삽입 성능은 기본키가 크게 좌우하지만 그것이 전부는 아니다.
  • 세컨더리 인덱스도 정렬된 순서로 들어오면 마찬가지로 이점이 있다.
  • 하지만 세컨더리 인덱스의 정렬 순서까지 보장하기는 어려우므로 남발하지 않는 것이 좋다.
  • 세컨더리 인덱스는 결국 SELECT 를 위한 것이니 적절한 trade-off 가 필요하다.
기본키 선정
  • 기본키는 INSERT 성능을 결정하는 가장 중요한 요소다.
  • 대량 삽입 시 어느 정도까지는 B-Tree 전체가 메모리에 올라가지만, 결국 디스크 읽기가 필요해진다.
  • 클러스터링 키 구조이므로 단순히 INSERT 성능만 보고 정해서는 안 된다.
  • 대부분의 OLTP 서비스는 SELECT 비율이 압도적이므로, 가능하면 단조 증가/감소하는 값을 쓰자.
Auto-Increment 컬럼
  • InnoDB 테이블은 자동으로 기본키로 클러스터링된다.
  • 자동 증가 컬럼을 쓰면 클러스터링되지 않은 테이블과 유사한 효과를 얻을 수 있다 — 삽입 위치가 항상 끝이기 때문이다.
  • 자동 증가 컬럼은 가장 빠른 INSERT를 보장하는 방법이다.
  • 마지막으로 증가된 값을 조회할 때는 MAX() 대신 LAST_INSERT_ID() 를 쓰자.
동시성 문제 가능
SELECT MAX(id) FROM test;   -- 10
커넥션별로 정확
SELECT LAST_INSERT_ID();    -- 10

MAX(id) 는 다른 커넥션이 방금 넣은 값을 가져올 수 있다. LAST_INSERT_ID() 는 내 커넥션이 마지막으로 생성한 값만 돌려준다.

정리

  • INSERT IGNORE 는 타입 오류까지 삼킨다. 중복만 다루려면 ON DUPLICATE KEY UPDATE.
  • LOAD DATA 는 단일 스레드·단일 트랜잭션이다. 파일을 나누거나 INSERT ... SELECT 로 분할한다.
  • 대량 INSERT 성능의 핵심은 기본키 순서다. 단조 증가 키가 유리하다.
  • 마지막 자동 증가 값은 반드시 LAST_INSERT_ID() 로.
11-6

UPDATE, DELETE

조인 UPDATE/DELETE 는 강력하지만 데드락의 온상이다.

핵심 조인 UPDATE 는 읽기 참조 테이블에는 읽기 잠금, 변경 테이블에는 쓰기 잠금을 건다. 여러 테이블에 잠금이 퍼지는 순간 데드락 확률이 올라간다.

UPDATE ... ORDER BY ... LIMIT n

  • 특정 컬럼으로 정렬해 상위 몇 건만 변경·삭제하는 기능이다.
  • 한 번에 너무 많은 레코드를 바꾸면 과부하를 유발하거나 다른 커넥션을 방해할 수 있어, 이를 나눠 처리할 때 쓴다.
  • 바이너리 로그 포맷이 ROW 면 문제없지만 STATEMENT 면 문제가 될 수 있다.
    • ORDER BY 로 정렬된 순서가 소스와 레플리카에서 달라질 수 있다.
    • 기본키로 정렬하면 문제는 없지만 여전히 경고는 나온다.
    • 복제가 구축된 서버에서는 조심히 쓰자.
mysql 
SET binlog_format=STATEMENT;

DELETE FROM employees ORDER BY last_name LIMIT 2;

SHOW WARNINGS;
×

경고 메시지

JOIN UPDATE

  • 2개 이상의 테이블을 조인해 그 결과 레코드를 변경·삭제하는 쿼리다.
  • 한 테이블의 컬럼값을 다른 테이블의 컬럼에 반영해야 할 때 주로 쓴다.
  • 양쪽에 공통으로 존재하는 레코드만 골라 변경하는 용도로도 쓸 수 있다.
  • OLTP 서비스에서는 데드락 유발 가능성이 높아 주의해야 한다.
    • 읽기 참조만 되는 테이블에는 읽기 잠금, 컬럼이 변경되는 테이블에는 쓰기 잠금이 걸린다.
  • 조인 순서에 따라 성능이 달라질 수 있으니 실행 계획을 확인하는 것이 좋다.
CREATE TABLE tb_test1 (
  emp_no INT PRIMARY KEY,
  first_name VARCHAR(255)
);

INSERT INTO tb_test1 VALUES (10001, NULL), (10002, NULL), (10003, NULL);

UPDATE tb_test1 t1, employees e
SET t1.first_name = e.first_name
WHERE e.emp_no = t1.emp_no;
GROUP BY, ORDER BY 사용하기
  • JOIN UPDATE 쿼리에서는 기본적으로 쓸 수 없다.
  • 서브쿼리로 파생 테이블을 만들면 같은 효과를 낼 수 있다.
EXPLAIN
UPDATE departments d,
  (
    SELECT de.dept_no, COUNT(*) AS emp_count
    FROM dept_emp de
    GROUP BY de.dept_no
  ) dc
SET d.emp_count = dc.emp_count
WHERE dc.dept_no = d.dept_no;

JOIN_ORDER 옵티마이저 힌트나 STRAIGHT_JOIN 으로 순서를 바꿀 수 있고, 레터럴 조인도 쓸 수 있다.

여러 레코드를 서로 다른 값으로 UPDATE

  • 8.0부터 레코드 생성 문법(VALUES ROW(...)) 을 써서 레코드별로 다른 값을 업데이트할 수 있다.
  • 임시로 만든 new_user_level 을 실제 테이블과 조인해 업데이트하는 형태다.
CREATE TABLE user_level (
  user_id INT PRIMARY KEY,
  user_lv INT NOT NULL,
  created_at DATETIME NOT NULL
);

EXPLAIN
UPDATE user_level ul
  INNER JOIN (VALUES ROW(1, 1), ROW(2, 4)) new_user_level (user_id, user_lv)
    ON new_user_level.user_id = ul.user_id
SET ul.user_lv = ul.user_lv + new_user_level.user_lv;

user 1은 +1, user 2는 +4 — 한 문장으로 서로 다른 값을 적용했다. 예전에는 CASE WHEN 을 길게 늘어놓아야 했던 패턴이다.

JOIN DELETE

JOIN UPDATE 와 마찬가지로 실행 계획을 확인할 수 있고 조인 순서도 바꿀 수 있다.

3개 테이블을 조인해 하나에서만 삭제
  • 일반적으로는 DELETE FROM <table> 이지만, 여기서는 DELETE 와 FROM 사이에 삭제 대상 테이블을 명시한다.
DELETE e
FROM employees e, dept_emp de, departments d
WHERE e.emp_no = de.emp_no
  AND de.dept_no = d.dept_no
  AND d.dept_no = 'd001';
여러 테이블에서 동시에 삭제
DELETE e, de
FROM employees e, dept_emp de, departments d
WHERE e.emp_no = de.emp_no
  AND de.dept_no = d.dept_no
  AND d.dept_no = 'd001';

정리

  • UPDATE/DELETE ... ORDER BY ... LIMIT 은 STATEMENT 복제에서 안전하지 않다.
  • 조인 UPDATE 는 읽기/쓰기 잠금이 여러 테이블로 퍼진다 — OLTP에서 데드락 주의.
  • 조인 UPDATE 에 GROUP BY/ORDER BY 가 필요하면 파생 테이블로 우회한다.
  • 8.0의 VALUES ROW(...) 로 레코드별 다른 값을 한 문장에 적용할 수 있다.
  • 조인 DELETE 는 DELETE <삭제할 테이블들> FROM ... 형태다.
11-7

스키마 조작 (DDL)

온라인 DDL의 정체는 알고리즘 3종 × 잠금 수준 3종 의 조합이다.

핵심 INSTANT 는 메타데이터만, INPLACE 는 리빌드하되 온라인, COPY 는 복사하며 쓰기 차단. 어느 것이 선택되는지가 전부다.

온라인 DDL

  • 5.5 이하에서는 테이블 구조를 바꾸는 동안 다른 커넥션이 DML을 쓸 수 없었다.
  • 그래서 Percona의 pt-online-schema-change 같은 도구를 쓰기도 했다.
  • 현재는 많이 개선되어 더 이상 쓰지 않는다.
  • 대부분의 DDL이 온라인으로 처리 가능해졌지만, 오래 걸리고 부하가 큰 작업이 많으니 여전히 조심해야 한다.
온라인 DDL 알고리즘
  • old_alter_table 로 예전 방식과 최신 방식 중 무엇을 쓸지 정할 수 있다.
  • 알고리즘을 지정하지 않고 ALTER TABLE 을 실행하면 서버가 알아서 적합한 것을 고른다.
알고리즘동작소요 시간다른 커넥션 영향
INSTANT 데이터는 그대로 두고 메타데이터만 변경 레코드 건수와 무관하게 매우 짧다 거의 없음
INPLACE 임시 테이블로 복사하지 않고 스키마 변경. 다만 내부적으로 리빌드가 일어날 수 있다 레코드 수에 비례 시작·종료 지점에서만 잠깐 읽기/쓰기 차단
COPY 변경된 스키마의 임시 테이블을 만들고 레코드를 전부 복사한 뒤 이름 교체 가장 길다 읽기만 가능, 변경은 전면 불가

이 성질을 역이용하기 보강

"명시했는데 불가능하면 에러를 내고 아무것도 하지 않는다"는 성질 덕분에, ALGORITHM=INPLACE, LOCK=NONE 을 안전장치로 붙일 수 있다. 이렇게 쓰면 실수로 COPY 가 선택되어 운영 중 테이블이 잠기는 사고를 원천 차단한다. 운영 DB의 ALTER TABLE 에는 항상 붙이는 습관을 들일 만하다.

INPLACE 알고리즘의 내부 처리

임시 테이블로 복사하지 않더라도 내부적으로 모든 레코드를 리빌드해야 하는 경우가 많다.

  1. INPLACE 지원 여부 확인

    해당 스토리지 엔진이 INPLACE 변경을 지원하는지 확인한다.

  2. INPLACE 스키마 변경 준비

    DDL 작업 동안 변경되는 데이터를 추적할 준비를 한다. 배타 잠금이 필요해 다른 커넥션의 DML이 잠깐 대기한다.

  3. 스키마 변경 및 새로운 DML 로깅

    가장 오래 걸리는 단계. 다른 커넥션의 DML은 대기하지 않고 즉시 처리되며, 별도의 로그에 기록된다.

  4. 기록했던 로그 적용

    3번 동안 수집된 DML 로그를 반영한다. 배타 잠금이 필요하다.

  5. INPLACE 스키마 변경 완료 (COMMIT)
  • DML 로그는 메모리에만 생성되고 기본 크기는 128MB 다.
  • innodb_online_alter_log_max_size 로 조정할 수 있다.
온라인 DDL의 실패 케이스
  • INSTANT 는 메타데이터만 바꾸므로 거의 시작과 동시에 끝난다.
  • 반면 INPLACE 는 리빌드와 로그 적용 과정에서 실패할 수 있다.
  • ALTER TABLE 이 오래 걸려 DML 로그 메모리가 부족한 경우
  • ALTER TABLE 이후에 적합하지 않은 레코드가 삽입·수정되어 마지막 단계에서 실패
  • 변경에 요구되는 것보다 낮은 잠금 수준을 지정한 경우
  • 처음과 끝에 필요한 테이블 락에서 데드락으로 타임아웃이 발생한 경우
온라인 DDL 진행 상황 모니터링

모든 ALTER TABLE 은 performance_schema 로 진행 상황을 볼 수 있다. 전제조건은 Performance 스키마 활성화다.

SET GLOBAL performance_schema=ON;

UPDATE performance_schema.setup_instruments
  SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'stage/innodb/alter%';

UPDATE performance_schema.setup_consumers
  SET ENABLED = 'YES'
WHERE NAME LIKE '%stages';

SELECT event_name, work_completed, work_estimated
FROM performance_schema.events_stages_current;

데이터베이스 변경

  • MySQL에서 스키마와 데이터베이스는 동격이다.
  • 여러 DB를 묶어 조인할 수도 있으므로 논리적인 구분 정도로 생각해도 된다.
  • 주로 객체 권한을 구분하는 용도로 쓰이며, 그래서 관련 DDL도 별로 없다.
-- 생성

CREATE DATABASE db_name CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

DROP DATABASE db_name;

테이블스페이스 변경

  • 전통적으로는 테이블 하나마다 개별 테이블스페이스를 썼다.
  • InnoDB의 시스템 테이블스페이스만 제너럴 테이블스페이스였다.
    • 제너럴 테이블스페이스 = 여러 테이블의 데이터를 한꺼번에 저장하는 테이블스페이스
  • innodb_file_per_table 로 제어하며, 8.0의 기본값은 ON 이라 각 테이블이 개별 테이블스페이스를 쓴다.
제너럴 테이블스페이스의 제약
  • 파티션 테이블은 쓸 수 없다.
  • 소스와 레플리카가 같은 호스트에서 실행되면 ADD DATAFILE 을 쓸 수 없다.
  • 테이블 암호화가 테이블스페이스 단위로 설정된다.
  • 테이블 압축 가능 여부가 테이블스페이스 블록 사이즈와 InnoDB 페이지 사이즈에 의해 결정된다.
  • 특정 테이블을 삭제해도 디스크 공간이 OS로 반납되지 않는다.
8.0에서 개선된 점
  • 파일 핸들러(open file descriptor)를 최소화
  • 테이블스페이스 관리에 필요한 메모리를 최소화

테이블 변경

테이블 생성
  • CREATE [TEMPORARY] TABLE [IF NOT EXISTS] tbl_name 형태다.
  • TEMPORARY — 현재 커넥션에서만 쓸 수 있는 임시 테이블. DERIVED 와는 다르다.
  • ENGINE — 8.0부터 기본값은 InnoDB.
컬럼 형식
  • 컬럼명 + 타입 + [타입 옵션] + [NULL 여부] + [기본값] 형식이다. 예) id INT NOT NULL AUTO_INCREMENT
  • 문자열 타입
    • 저장 가능한 최대 문자 수를 명시해야 한다.
    • CHARACTER SET, COLLATE 로 추가 설정할 수 있다.
  • 숫자 타입
    • 선택적으로 길이를 줄 수 있지만, 이는 저장 크기가 아니라 보여 줄 때의 자릿수다.
    • UNSIGNED 로 양수 전용을 지정할 수 있다. 기본은 SIGNED.
    • ZEROFILL 을 쓰면 자릿수를 0으로 채워 표시한다.

  • ALTER TABLE 로 거의 모든 스키마 변경을 한다.
  • 엔진 옵션 변경뿐 아니라 테이블 데이터를 리빌드하기 위해서도 쓴다.

테이블명 변경
  • RENAME TABLE 로 이름을 바꾸거나 다른 DB로 옮길 수 있다.
  • 같은 DB 안에서 이름만 바꾸는 것은 메타데이터만 수정해서 매우 빠르다.
  • 다른 DB로 옮기는 것은 데이터 파일을 복사한 뒤 원본을 삭제하는 방식이라 느리다.
  • 동시에 여러 테이블의 이름을 바꿀 수 있다.
  • RENAME TABLE 은 대상 테이블 전부에 잠금을 걸고 작업하므로 그동안 DML이 대기한다.

  • 레코드 잠금은 performance_schema.data_locks 에서 확인한다.

정리

  • 알고리즘 INSTANT < INPLACE < COPY 순으로 비싸다. 잠금은 NONE / SHARED / EXCLUSIVE.
  • 운영 DDL에는 ALGORITHM=INPLACE, LOCK=NONE 을 안전장치로 명시한다 — 불가능하면 아무것도 하지 않고 에러를 낸다.
  • 컬럼은 마지막에 추가해야 INSTANT. 삭제·타입 변경·길이 축소는 리빌드나 COPY 를 부른다.
  • 인덱스 삭제 전에는 INVISIBLE 로 먼저 시험해 본다.
  • 여러 변경은 하나의 ALTER TABLE 로 묶어 스캔을 한 번만 한다.
  • 진단은 SHOW PROCESSLIST · innodb_trx · data_locks 세 곳에서.

쿼리 성능 테스트

가장 큰 변수는 버퍼와 캐시다. 이걸 통제하지 않은 측정은 측정이 아니다.

핵심 InnoDB 버퍼 풀은 서버를 재시작하지 않고는 비울 수 없다. 그러니 대개는 워밍업 상태에서 여러 번 측정해 중간값을 쓰는 것이 현실적이다.

성능에 영향을 미치는 요소

가장 큰 변수는 MySQL 서버가 가진 여러 종류의 버퍼와 캐시다.

운영체제의 캐시
  • 대부분의 OS는 한 번 읽은 값을 자체 캐시 영역에 보관한다.
  • 다만 InnoDB는 파일시스템 캐시를 거치지 않는 Direct I/O 를 쓴다 (MyISAM과 다른 점이다).
  • 그래도 정확한 테스트를 위해서는 OS 캐시를 비우고 시작하는 것을 권장한다.
terminal 
# 캐시·버퍼 내용을 디스크와 동기화
$ sync

# OS 페이지 캐시 비우기
$ echo 3 > /proc/sys/vm/drop_caches
MySQL 서버의 버퍼 풀
  • InnoDB의 버퍼 풀은 인덱스 페이지, 데이터 페이지, 쓰기 버퍼링을 전부 겸한다.
  • 서버가 기동된 이상 런타임 중에 버퍼 풀을 초기화할 방법이 없다.
  • 초기화하려면 MySQL 자체를 재시작해야 한다.
  • 게다가 종료 시 덤프한 내용을 시작 시 다시 불러오므로, innodb_buffer_pool_load_at_startup 으로 그 동작도 제어해야 한다. (→ 4-2 버퍼 풀 상태 백업 복구)
독립된 MySQL 서버
  • 같은 서버에서 무거운 작업이 돌면 DB에도 영향을 준다.
  • 테스트 쿼리를 실행하는 클라이언트 프로그램과 네트워크도 변수로 고려해야 한다.
쿼리 테스트 횟수
상태의미언제 쓰나
워밍업 (Warm-up)캐시·버퍼가 준비된 상태대부분의 운영 서버가 이 상태다
콜드 (Cold)캐시·버퍼가 비워진 상태최악의 경우를 측정하고 싶을 때

운영 서버는 대개 워밍업 상태이므로 워밍업 상태에서 6~7회 실행해 중간값으로 비교하는 것이 좋다.

정리

  • 측정 전에 어떤 상태(워밍업/콜드)를 재는지 먼저 정한다.
  • InnoDB는 Direct I/O 라 OS 캐시 영향이 적지만, 버퍼 풀은 재시작 없이 비울 수 없다.
  • 동일 서버의 다른 작업, 클라이언트, 네트워크도 전부 변수다.
  • 워밍업 상태에서 6~7회 측정 후 중간값 을 쓴다.
