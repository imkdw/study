8-1

디스크 읽기 방식

DB 성능은 결국 디스크 I/O를 얼마나 줄이느냐의 문제다. 인덱스 챕터가 여기서 시작하는 이유다.

핵심 같은 양의 데이터라도 몇 번에 나눠 요청하느냐가 비용을 결정한다. 인덱스가 하는 일이 바로 그 횟수를 줄이는 것이다.

디스크는 언제나 병목이다

  • 데이터 저장 매체는 컴퓨터에서 가장 느린 부분이다.
  • 데이터베이스의 성능은 어떻게 디스크 I/O를 줄이느냐가 관건일 때가 많다.
  • DB에서는 거의 항상 디스크 장치가 병목이 된다.

HDD vs SSD

DB의 특성과 OLTP 워크로드를 생각하면 SSD가 훨씬 좋은 선택이다.

구분구조순차 I/O랜덤 I/O
HDD기계식 — 내부 원판을 돌려 작동SSD보다 빠를 수도 있다매우 느리다 (헤드 이동)
SSD플래시 메모리. 전원이 없어도 데이터 유지빠르다HDD보다 훨씬 빠르다

SSD도 메모리보다는 느리다는 점은 잊지 말자 — 버퍼 풀이 여전히 필요한 이유다.

랜덤 I/O vs 순차 I/O

  • 디스크의 읽기/쓰기 시간은 헤더를 읽고 쓸 위치로 옮기는 단계에서 결정된다.
  • 디스크 성능은 헤더 이동 없이 얼마나 많은 데이터를 한 번에 처리하느냐로 결정된다.
  • 따라서 여러 번 나눠 요청하는 랜덤 I/O가 부하가 훨씬 크다.
구분N개의 페이지를 기록할 때
순차 I/O시스템 콜을 1번 요청
랜덤 I/O시스템 콜을 N번 요청
i

이 구도가 반복해서 나온다 보강

InnoDB의 리두 로그(순차)와 데이터 파일(랜덤), MRR 최적화, read ahead 는 전부 "랜덤 I/O를 순차 I/O로 바꾸거나 횟수를 줄인다"는 같은 아이디어의 변주다. 이 절을 이해하면 나머지가 자연스럽게 읽힌다.

정리

  • DB의 병목은 거의 항상 디스크다. 튜닝은 I/O 횟수 줄이기로 수렴한다.
  • OLTP에는 SSD. 다만 SSD도 메모리보다는 느리다.
  • 같은 N개 페이지라도 순차는 시스템 콜 1회, 랜덤은 N회.
8-2

인덱스

인덱스는 쓰기를 팔아 읽기를 사는 거래다.

핵심 인덱스는 컬럼 값을 미리 정렬해 둔 키:값 쌍이다. 정렬을 유지하는 비용이 쓰기 비용이고, 정렬 덕분에 읽기가 빨라진다.

인덱스가 하는 일

  • 테이블의 모든 데이터를 뒤져서 원하는 값을 찾으려면 오래 걸린다.
  • DB는 컬럼의 값과 그 레코드가 저장된 주소를 키:값 쌍으로 저장해 둔다.
  • 인덱스는 컬럼의 값을 주어진 순서대로 미리 정렬해서 저장한다.
  • 즉 저장(INSERT, UPDATE 등)의 성능을 희생하고 검색(SELECT)의 성능을 높이는 기능이다.

인덱스 알고리즘

대표적으로 B-Tree와 Hash 두 가지로 나뉜다.

알고리즘인덱싱 방식동등 비교범위·부분 검색
B-Tree 컬럼 값을 변형하지 않고 원래 값으로 인덱싱 가능 가능 (정렬되어 있으므로)
Hash 컬럼 값의 해시 값으로 인덱싱 매우 빠름 불가 (해시는 순서를 보존하지 않음)

정리

  • 인덱스 = 정렬된 (컬럼 값 → 레코드 주소) 쌍.
  • 읽기를 얻는 대신 쓰기를 지불한다. 공짜 인덱스는 없다.
  • B-Tree는 원본 값을 보존해 범위 검색까지 되고, Hash는 동등 비교만 가능하다.
8-3

B-Tree 인덱스

Binary 가 아니라 Balanced. 전문 검색 같은 특수 요건이 아니라면 사실상 이것 하나면 된다.

핵심 인덱스 키의 크기가 한 페이지에 담기는 자식 노드 수를 정하고, 그것이 트리의 깊이를 정하고, 깊이가 곧 랜덤 디스크 읽기 횟수다.

구조 및 특성

  • B는 Binary가 아니라 Balanced 를 의미한다.
  • 루트 노드 · 브랜치 노드 · 리프 노드로 이루어진 트리 구조다.
  • 맨 끝의 리프 노드는 항상 실제 레코드를 찾아가기 위한 주솟값을 갖는다.
  • 인덱스의 키 값은 항상 정렬을 유지하지만, 실제 레코드는 그렇지 않다.
  • 컬럼의 원래 값을 변형하지 않는다.
엔진리프 노드가 가진 값레코드 접근
MyISAM ROWID — 추가된 순번 또는 데이터 파일 내 위치 ROWID로 데이터 파일에 바로 접근
InnoDB 기본키 값 기본키 인덱스(B-Tree)를 한 번 더 타서 레코드를 읽음

B-Tree 인덱스 키 추가 및 삭제

인덱스 키 추가
  • 새 키가 추가되면 바로 저장될 수도 있지만, 적절한 위치를 찾아 재배치해야 할 수도 있다.
  • 리프 노드가 꽉 차서 저장이 불가능하면 노드를 분리해야 한다. 쓰기 비용이 상대적으로 큰 이유가 이것이다.
  • 간단히 읽기 비용이 1이면 쓰기 비용은 1.5 정도로 생각하면 된다.
  • 이 비용은 CPU나 RAM이 아니라 디스크에서 인덱스를 읽어야 해서 발생한다.
  • 인덱스 키 추가는 체인지 버퍼로 지연 처리할 수 있다. 단 기본키나 유니크 인덱스는 중복 체크가 필요해 즉시 B-Tree에 반영되어야 한다.
인덱스 키 삭제
  • 해당 키가 저장된 노드를 찾아 삭제 마크만 하면 끝난다.
  • 삭제된 자리는 재사용하거나 그대로 방치할 수 있다.
  • InnoDB에서는 이 작업도 체인지 버퍼로 지연 처리할 수 있다.
인덱스 키 변경

먼저 그 키 값을 삭제하고, 다시 새 키 값을 추가하는 방식으로 처리된다. 마찬가지로 지연 처리가 가능하다.

인덱스 키 검색
  • 위와 같은 추가 비용을 감수하면서까지 인덱스를 쓰는 이유는 검색 성능 때문이다.
  • SELECT 외에 UPDATE, DELETE 의 WHERE 조건에서도 쓰인다.
  • B-Tree 인덱스는 100% 일치(=) 또는 값의 앞부분이 일치하는 경우에 사용할 수 있다.
!

인덱스 설계는 곧 잠금 설계다

넥스트 키 락이나 레코드 잠금은 수행한 인덱스를 잠근 뒤 테이블의 레코드를 잠그는 방식으로 동작한다. 인덱스를 잘못 설계하면 테이블의 모든 레코드를 잠글 수 있다. (→ 5-3 인덱스와 잠금)

B-Tree 인덱스 사용에 영향을 미치는 요소

인덱스 키 값의 크기
  • 인덱스도 버퍼 풀처럼 페이지 단위로 관리되며, B-Tree의 자식 노드 개수는 가변적이다.
  • 자식 노드의 개수는 페이지 크기와 키 값의 크기로 결정된다.

페이지 크기가 기본값 16KB이고, 자식 노드 주소가 12바이트를 차지한다고 하자.

자식 노드 개수 계산 
# 인덱스 키가 16 바이트인 경우
16 * 1024 / (16 + 12) = 585 개

# 인덱스 키가 32 바이트인 경우
16 * 1024 / (32 + 12) = 372 개
!

원문 교정 원문 교정

노트에는 두 번째 계산이 "페이지의 크기가 32KB라면 16*1024/(32+12) = 1024 로 자식노드를 372개" 라고 적혀 있다. 세 가지가 어긋나 있다 — ① 분자가 16*1024 그대로이므로 페이지가 아니라 인덱스 키가 32바이트인 경우다. ② 16*1024/44 의 값은 1024가 아니라 372 다. ③ 결론인 372개는 맞다. 즉 "인덱스 키가 32바이트라면 372개" 가 맞는 문장이다. 이 문단의 요지는 키 크기가 커질수록 한 페이지에 담기는 자식 수가 줄고, 그만큼 트리가 깊어져 디스크 접근이 늘어난다는 것이다.

키가 두 배가 되면 팬아웃은 거의 절반이 된다 — 기본키를 짧게 유지해야 하는 가장 근본적인 이유.
B-Tree의 깊이
  • 깊이는 매우 중요하지만 직접 제어할 방법이 없다.
  • 깊이는 곧 값을 찾을 때 몇 번이나 랜덤하게 디스크를 읽어야 하는지와 직결된다.
  • 가능하면 작게 만드는 것이 좋다는 점을 강조하기 위한 이야기이고, 실제로는 대용량 DB라도 보통 5를 넘지 않는다.
선택도(기수성) — Selectivity / Cardinality
  • 모든 인덱스 키 값 중 유니크한 값의 수를 의미한다.
  • 값이 100개인데 유니크한 값이 10개라면 기수성은 10이다.
  • 중복이 많을수록 기수성이 낮아지고 선택도도 떨어진다.
  • 선택도가 높을수록 검색 대상이 줄어들어 빠르게 처리된다.
예시 — 총 10,000건, country 의 유니크 값 수만 다를 때
SELECT * FROM test WHERE country='KOREA' AND city='SEOUL';
CASEcountry 유니크 값인덱스로 읽는 건수버려지는 건수
A10개평균 1,000건999건이 헛수고
B1,000개평균 10건9건만 헛수고
  • CASE A의 country 인덱스는 비효율적이다.
  • 필요한 만큼의 레코드만 읽으면 좋겠지만, 현실적으로 모든 조건을 만족하는 인덱스를 만드는 것은 불가능하다.
읽어야 하는 레코드의 건수
  • 인덱스를 거쳐 레코드를 읽는 것은 테이블을 바로 읽는 것보다 건당 비용이 높다.
    • 옵티마이저는 인덱스를 타서 가져오는 쪽이 약 4~5배 비싸다고 예측한다.
  • 예를 들어 100만 건 중 50만 건을 읽어야 한다면, 전부 읽고 50만 건을 버릴지 인덱스로 50만 건만 읽을지 판단해야 한다.
  • 인덱스로 읽어야 할 데이터가 전체 레코드의 20~25%를 넘어가면, 그냥 전부 읽고 필터링하는 편이 효율적이다.
  • 이런 경우 옵티마이저는 인덱스를 타지 않는다. 결국 그 인덱스는 저장 공간만 낭비하는 셈이 된다.

B-Tree 인덱스를 통한 데이터 읽기

인덱스 사용을 유도할지 말지 판단하려면 어떤 방식으로 인덱스를 경유하는지를 알아야 한다.

인덱스 레인지 스캔
  • 가장 대표적인 접근 방식이다.
  • 검색해야 할 인덱스의 범위가 정해져 있을 때 사용한다.
  • 루트 → 브랜치 → 리프까지 내려가야 레코드 시작 지점을 확인할 수 있다.
  • 문제는 그 시작 지점부터 끝 지점까지 레코드 한 건마다 랜덤 I/O가 발생한다는 점이다.
SELECT * FROM employees WHERE first_name BETWEEN 'Ebbe' AND 'Gad';
  1. 인덱스 탐색 (Index Seek)

    조건을 만족하는 값이 저장된 위치를 찾는다.

  2. 인덱스 스캔 (Index Scan)

    1번에서 찾은 위치부터 필요한 만큼 차례대로 읽는다.

  3. 레코드 읽기 (선택적)

    2번에서 얻은 레코드 주소로 데이터 페이지를 읽어 실제 레코드를 가져온다. 이 단계를 건너뛰는 것이 커버링 인덱스다.

인덱스 풀 스캔
  • 인덱스를 처음부터 끝까지 다 읽는 방식이다.
  • 대표적으로 조인 조건에 사용된 컬럼이 인덱스의 첫 번째 컬럼이 아닐 때 발생한다.
    • 인덱스가 (A, B, C) 순인데 B나 C로 조인하는 경우다.
  • 일반적으로 인덱스는 테이블보다 작으므로, 인덱스만 읽으면 되는 경우에는 효율적이다.
  • 레코드까지 다 읽어야 한다면 절대 이 방식으로 처리하면 안 된다.
  • 레인지 스캔보다는 느리지만 테이블 풀 스캔보다는 낫다.
루스 인덱스 스캔
  • 말 그대로 느슨하게(듬성듬성) 인덱스를 읽는 것이다.
  • 스캔 도중 필요하지 않은 키 값은 건너뛰고(SKIP) 다음으로 넘어간다.
  • 주로 GROUP BY 나 MIN() / MAX() 처리에 쓰인다.
INDEX(dept_no, emp_no) 가정 
SELECT dept_no, MIN(emp_no)
FROM dept_emp
WHERE dept_no BETWEEN 'd002' AND 'd004'
GROUP BY dept_no;

dept_no 가 이미 정렬되어 있으므로, 각 dept_no 그룹의 첫 emp_no 하나만 읽고 다음 그룹으로 점프하면 된다.

인덱스 스킵 스캔
  • 루스 인덱스 스캔과 비슷하지만, WHERE 조건 검색에도 쓸 수 있도록 범위가 넓어진 것이다.
  • 선행 컬럼의 유니크 값이 많으면 오히려 더 느려질 수 있다.
  • 쿼리가 인덱스에 존재하는 컬럼만으로 처리 가능해야 한다 (커버링 인덱스).
  • 결국 선행 컬럼의 유니크 값이 소수일 때만 적용 가능한 최적화다.
skip-scan.sql 
-- gender + birth_date 복합 인덱스 생성
ALTER TABLE employees ADD INDEX ix_gender_birthdate (gender, birth_date);

-- 선행 컬럼 없음 → 스킵 스캔이 없다면 인덱스 사용 불가
SELECT * FROM employees WHERE birth_date >= '1965-02-01';

-- 선행 컬럼 있음 → 정상적인 인덱스 사용
SELECT * FROM employees WHERE gender='M' AND birth_date >= '1965-02-01';

gender 는 값이 두 개(M/F)뿐이므로, 옵티마이저가 내부적으로 gender='M', gender='F' 두 번의 레인지 스캔으로 바꿔 실행할 수 있다. 이것이 스킵 스캔이다.

다중 컬럼(Multi-Column) 인덱스

  • 실제 서비스용 DB에서는 2개 이상의 컬럼을 포함한 인덱스가 더 많이 쓰인다.
  • 인덱스의 두 번째 컬럼은 첫 번째 컬럼에 의존해서 정렬된다.
    • 즉 두 번째 컬럼의 정렬은 첫 번째 컬럼이 같은 레코드들 안에서만 의미가 있다.
  • 따라서 각 컬럼의 순서가 상당히 중요하다.

B-Tree 인덱스의 정렬 및 스캔 방향

인덱스의 정렬
  • 인덱스 키는 항상 오름차순 또는 내림차순으로 정렬되어 저장된다.
  • 어느 방향으로 읽을지는 옵티마이저가 실시간으로 만드는 실행 계획에 따라 달라진다.
인덱스의 스캔 방향
  • 인덱스는 생성 시점에 오름차순/내림차순이 결정된다.
  • 하지만 스캔 방향은 쿼리가 그 인덱스를 읽는 방향에 따라 결정된다.
-- 인덱스가 이미 정렬되어 있으므로 별도의 정렬 작업이 없다
SELECT * FROM employees WHERE first_name >= 'Anneke'
ORDER BY first_name LIMIT 4;

-- 인덱스를 역순으로 스캔하면서 처음 5개만 찾으면 된다
SELECT * FROM employees
ORDER BY first_name DESC LIMIT 5;
내림차순 인덱스

2개 이상의 컬럼으로 구성된 복합 인덱스에서 각 키의 정렬 방향이 섞여 있다면, 내림차순 인덱스로만 해결할 수 있다.

CREATE INDEX ix_a_b ON tbl (a ASC, b DESC);
뭐가 더 빠를까
  • 단순히 역순으로 스캔하는 경우 약 30% 정도 느리다.
  • 이는 인덱스 구조 때문이다.
    • 페이지 잠금이 정순 스캔에 적합한 구조다.
    • 페이지 안의 인덱스 레코드가 단방향으로만 연결되어 있다.
  • 애플리케이션이 어떤 쿼리를 자주 쓰는지에 따라 인덱스의 방향도 정하면 좋다.

B-Tree 인덱스의 가용성과 효율성

비교 조건의 종류와 효율성
  • 다중 컬럼 인덱스에서는 컬럼의 순서와 비교 조건에 따라 활용 형태가 달라진다.
  • 작업 범위 결정 조건은 많을수록 성능이 좋아지지만, 체크 조건은 많다고 성능이 좋아지지 않는다.
SELECT * FROM dept_emp
WHERE dept_no='d002' AND emp_no >= 10114;
CASE인덱스처리 과정5건을 찾을 때
A(dept_no, emp_no) 시작점을 찾은 뒤 dept_no 가 'd002' 가 아닐 때까지 쭉 스캔 비교 작업 5번
B(emp_no, dept_no) emp_no >= 10114 인 모든 레코드에 대해 dept_no 를 하나씩 비교 그보다 훨씬 많은 비용

차이의 원인은 명확하다 — 동등 비교 조건이 선행 컬럼에 와야 인덱스에서 연속된 구간을 잡을 수 있다.

인덱스의 가용성
  • 인덱스 키 값의 정렬 특성이 빠른 검색의 전제 조건이다.
  • 다중 컬럼 인덱스에서 왼쪽 컬럼의 값을 모르면 레인지 스캔이 불가능하다.
  • 이 조건은 WHERE 뿐 아니라 ORDER BY, GROUP BY 에도 똑같이 적용된다.
인덱스 사용 불가
-- 앞쪽에 와일드카드
SELECT * FROM employees
WHERE first_name LIKE '%mer';

-- INDEX(dept_no, emp_no) 인데
-- 선행 컬럼 dept_no 조건이 없다
SELECT * FROM dept_emp
WHERE emp_no >= 10114;
인덱스 사용 가능
-- 뒤쪽 와일드카드는 OK
SELECT * FROM employees
WHERE first_name LIKE 'mer%';

-- 선행 컬럼이 동등 비교로 고정됨
SELECT * FROM dept_emp
WHERE dept_no='d002' AND emp_no >= 10114;
작업 범위 결정 조건으로 쓸 수 없는 조건들

아래는 인덱스의 작업 범위를 좁히는 데 쓸 수 없는 조건들이다. 경우에 따라 체크 조건으로는 쓰일 수 있다.

유형예
NOT-EQUAL 비교 column <> 'N' · column NOT IN ('N1','N2') · column NOT BETWEEN 'N1' AND 'N2' · IS NOT NULL
앞쪽 LIKE column LIKE '%승환' · column LIKE '_승환' · column LIKE '%승%'
컬럼이 함수·연산으로 변형됨 SUBSTRING(column,1,1) = 'X' · DAYOFMONTH(column) = 1
NOT-DETERMINISTIC 스토어드 함수 비교 column = deterministic_function() 형태에서 함수가 비확정적일 때
데이터 타입 불일치 (컬럼 쪽 형변환 발생) char_column = 10
문자열 콜레이션 불일치 utf8_bin_char_column = euckr_char_column
INDEX(col1, col2, col3) 일 때 정리
  • 작업 범위 결정 조건으로 못 쓰는 경우
    • col1 에 대한 조건이 아예 없을 때
    • col1 의 비교 조건이 위 표의 사용 불가 유형 중 하나일 때
  • 작업 범위 결정 조건으로 쓰는 경우
    • col1 ~ col(i-1) 까지 동등 비교(= 또는 IN) 이고,
    • col(i) 가 동등 비교(=, IN) · 부등호(>, <) · 뒷 LIKE(LIKE '승환%') 중 하나일 때

정리

  • B는 Balanced. InnoDB의 리프 노드는 기본키 값을 담고, MyISAM은 ROWID를 담는다.
  • 인덱스 키가 클수록 팬아웃이 줄고 트리가 깊어진다 — 깊이 = 랜덤 디스크 읽기 횟수.
  • 읽을 데이터가 전체의 20~25% 를 넘으면 옵티마이저는 인덱스를 버린다.
  • 접근 방식은 레인지 스캔 · 풀 스캔 · 루스 스캔 · 스킵 스캔 네 가지.
  • 다중 컬럼 인덱스의 생명은 순서다. 동등 비교 컬럼을 앞에 두는 것이 원칙.
  • 컬럼을 변형하거나(SUBSTRING), 타입이 다르거나, 앞쪽 LIKE면 범위를 좁히는 데 못 쓴다.
8-4

R-Tree 인덱스

2차원 공간 데이터를 위한 인덱스. 핵심 개념은 MBR 하나다.

핵심 R-Tree는 도형 자체가 아니라 도형을 감싸는 최소 사각형(MBR) 을 인덱싱한다.

구조 및 특성

  • 공간 인덱스는 R-Tree 알고리즘으로 2차원 데이터를 인덱싱하고 검색한다.
  • POINT, LINESTRING, POLYGON, GEOMETRY 네 가지 유형이 있다.
  • GEOMETRY 는 나머지 셋의 슈퍼 타입이라 어떤 객체든 저장할 수 있다.
  • 단순히 X, Y 좌표만 있는 포인트 데이터도 도형이 될 수 있다.
MBR (Minimum Bounding Rectangle)
  • 도형을 감싸는 최소 크기의 사각형을 뜻한다.
  • R-Tree의 노드에 저장되는 정보가 바로 이 MBR이다.
인덱스는 사각형만 본다 — 그래서 R-Tree 검색은 항상 "후보를 좁히고 정밀 판정"의 2단계다.

R-Tree 인덱스의 용도

  • 좌표 시스템에 기반한 정보에 주로 쓴다.
  • 인덱스를 활용하려면 ST_Contains(), ST_Within() 같은 공간 함수를 써야 한다. 일반 비교 연산자로는 타지 않는다.

정리

  • 공간 인덱스 = R-Tree. 인덱싱 단위는 도형이 아니라 MBR.
  • GEOMETRY 는 POINT / LINESTRING / POLYGON 의 슈퍼 타입.
  • 인덱스를 타려면 ST_Contains(), ST_Within() 등 전용 함수가 필요하다.
8-5

전문 검색 인덱스

어근 분석은 서구권 언어의 것이고, 한글에는 n-gram 이 현실적이다.

핵심 전문 검색 인덱스는 MATCH ... AGAINST ... 문법으로만 탄다. LIKE '%키워드%' 로는 절대 쓰이지 않는다.

왜 B-Tree로는 안 되는가

  • 전문 검색은 문서 전체에 대한 분석과 검색을 위한 인덱싱이다.
  • B-Tree 인덱스는 값의 앞부분만 매칭할 수 있으므로, 문서 중간의 단어를 찾는 데 쓸 수 없다.

인덱스 알고리즘

본문에서 사용자가 검색할 키워드를 분석해, 빠른 검색이 가능한 형태로 인덱스를 만든다. 크게 어근 분석과 n-gram 으로 나뉜다.

어근 분석 알고리즘
불용어 처리
  • 검색에서 가치가 없는 단어를 필터링해 제거한다. (a, the, is 등)
  • DB가 제공하는 불용어 리스트를 쓰거나 직접 정의할 수 있다.
  • 제공되는 목록은 information_schema.innodb_ft_default_stopword 에 있다.
어근 분석
  • 검색어로 선정된 단어의 원형(뿌리) 을 찾는 작업이다.
  • 언어별로 형태소 분석 방법이 완전히 다르며, 한국어는 MeCab 을 쓸 수 있다.
n-gram 알고리즘
  • 형태소 분석은 매우 전문적인 영역이라 만족스러운 결과를 얻기까지 많은 노력과 시간이 든다.
  • n-gram은 단순히 키워드를 검색해 내기 위한 인덱싱 알고리즘이다.
  • 본문을 몇 글자씩 잘라 인덱싱한다. 일반적으로 2글자로 자른다.
"To be or not to be" 의 bi-gram 토큰 
To
be
or
no   ← "not" 에서
ot   ← "not" 에서
to
be
...

단어 경계를 무시하고 기계적으로 잘라 내기 때문에 형태소 분석이 어려운 한글에 특히 유용하다.

불용어 변경 및 삭제

목적방법
불용어 삭제 (전역)ft_stopword_file 에 빈 문자열을 지정. 서버 재시작 필요
InnoDB 테이블 불용어 끄기innodb_ft_enable_stopword = OFF. MyISAM 등에는 여전히 적용됨
사용자 정의 불용어ft_stopword_file='/data/my_stopwords.txt'
사용자 정의 불용어 (InnoDB)테이블을 불용어 목록으로 지정 가능
mysql 순서가 중요하다 
-- 1) 불용어 테이블을 만들고 단어를 먼저 등록한다
mysql> CREATE TABLE my_stopword(value VARCHAR(30)) ENGINE=INNODB;
mysql> INSERT INTO my_stopword(value) VALUES('mysql');

-- 2) 서버에 그 테이블을 알린다
mysql> SET GLOBAL innodb_ft_server_stopword_table='realmysql/my_stopword';

-- 3) 그다음에 인덱스를 생성해야 적용된다
mysql> ALTER TABLE tb_bi_gram
    -> ADD FULLTEXT INDEX fx_title_body(title, body) WITH PARSER ngram;
!

단어 등록 → 인덱스 생성 순서

InnoDB에서 불용어 테이블을 쓸 때는 단어를 먼저 등록하고 그다음에 인덱스를 생성해야 한다. 이미 만들어진 인덱스에는 소급 적용되지 않는다.

전문 검색 인덱스의 가용성

다음 두 조건을 모두 만족해야 전문 검색 인덱스를 탄다.

  • 쿼리가 전문 검색 문법(MATCH ... AGAINST ...)을 사용할 것
  • 테이블이 그 컬럼에 대해 전문 인덱스를 보유할 것
인덱스 미사용
SELECT * FROM tb_test
WHERE doc_body LIKE '%디비%';
인덱스 사용
SELECT * FROM tb_test
WHERE MATCH(doc_body)
  AGAINST('디비' IN BOOLEAN MODE);

정리

  • 전문 검색 인덱스는 어근 분석(서구권 / MeCab) 또는 n-gram(범용, 한글에 적합) 으로 토큰을 만든다.
  • 불용어는 파일 또는 InnoDB 테이블로 정의한다. 단어 등록 → 인덱스 생성 순서를 지킨다.
  • MATCH ... AGAINST 를 써야만 탄다. LIKE 로는 절대 안 된다.
8-6

함수 기반 인덱스

컬럼을 가공한 값에 인덱스를 걸어야 할 때. 가상 컬럼 방식과 함수 방식 두 가지가 있다.

핵심 함수 기반 인덱스는 조건절에 그 표현식이 그대로 등장해야만 탄다. 표현식이 조금이라도 다르면 소용없다.

두 가지 방식

  • 컬럼의 값을 변형해서 만들어진 값에 인덱스를 걸어야 할 때 쓴다.
  • 가상 컬럼 사용 방식과 함수 직접 사용 방식이 있다.
  • 인덱싱할 값을 계산하는 과정만 다를 뿐, 나머지는 B-Tree와 완전히 동일하다.

가상 컬럼을 이용한 인덱스

가상 컬럼은 테이블에 새 컬럼을 추가하는 것과 같은 효과라, 실제 테이블 구조가 변경된다는 단점이 있다.

mysql 
mysql> DESC user;
+------------+-------------+------+-----+---------+-------+
| Field      | Type        | Null | Key | Default | Extra |
+------------+-------------+------+-----+---------+-------+
| user_id    | int         | NO   | PRI | NULL    |       |
| first_name | varchar(10) | YES  |     | NULL    |       |
| last_name  | varchar(10) | YES  |     | NULL    |       |
+------------+-------------+------+-----+---------+-------+

mysql> ALTER TABLE user
    -> ADD full_name VARCHAR(30) AS (CONCAT(first_name, ' ', last_name)) VIRTUAL,
    -> ADD INDEX ix_fullname(full_name);

mysql> DESC user;
+------------+-------------+------+-----+---------+-------------------+
| Field      | Type        | Null | Key | Default | Extra             |
+------------+-------------+------+-----+---------+-------------------+
| user_id    | int         | NO   | PRI | NULL    |                   |
| first_name | varchar(10) | YES  |     | NULL    |                   |
| last_name  | varchar(10) | YES  |     | NULL    |                   |
| full_name  | varchar(30) | YES  | MUL | NULL    | VIRTUAL GENERATED |
+------------+-------------+------+-----+---------+-------------------+

함수를 이용한 인덱스

  • 테이블 구조를 변경하지 않고 계산된 결괏값의 검색을 빠르게 만든다.
  • 단, 조건절에 그 표현식이 그대로 등장해야 인덱스를 탄다.
mysql 
mysql> CREATE TABLE home (
    ->   id INT,
    ->   address VARCHAR(255),
    ->   number VARCHAR(255),
    ->   INDEX ix_home_address_number ((CONCAT(address, ' ', number)))
    -> );
Query OK, 0 rows affected (0.03 sec)
인덱스 사용 key = ix_home_address_number 
mysql> EXPLAIN SELECT * FROM home
    -> WHERE CONCAT(address, ' ', number)='HOME123';
+----+------+------------------------+------------------------+---------+-------+------+-------+
| id | type | possible_keys          | key                    | key_len | ref   | rows | Extra |
+----+------+------------------------+------------------------+---------+-------+------+-------+
|  1 | ref  | ix_home_address_number | ix_home_address_number | 2047    | const |    1 | NULL  |
+----+------+------------------------+------------------------+---------+-------+------+-------+
인덱스 미사용 type = ALL 
mysql> EXPLAIN SELECT * FROM home
    -> WHERE address="asd" AND number="asd";
+----+------+---------------+------+---------+------+------+-------------+
| id | type | possible_keys | key  | key_len | ref  | rows | Extra       |
+----+------+---------------+------+---------+------+------+-------------+
|  1 | ALL  | NULL          | NULL | NULL    | NULL |    1 | Using where |
+----+------+---------------+------+---------+------+------+-------------+

같은 두 컬럼을 참조하지만, 인덱스가 걸린 것은 CONCAT(address, ' ', number) 라는 표현식 이지 두 컬럼 각각이 아니다.

정리

  • 가상 컬럼 방식은 테이블 구조가 바뀌고, 함수 방식은 바뀌지 않는다.
  • 인덱스가 걸리는 대상은 표현식 그 자체다. 조건절에 동일한 표현식이 나와야 탄다.
  • 계산 방식만 다를 뿐 내부적으로는 평범한 B-Tree 인덱스다.
8-7

멀티 밸류 인덱스

레코드 하나가 여러 개의 키 값을 갖는 인덱스. JSON 배열을 위해 도입되었다.

핵심 멀티 밸류 인덱스는 세 개의 함수(MEMBER OF, JSON_CONTAINS, JSON_OVERLAPS)로만 탄다.

왜 필요해졌나

  • 일반적인 RDBMS에서 레코드 하나가 여러 키 값을 갖는 것은 정규화를 위배하는 형태다.
  • 그러나 JSON 타입을 지원하기 시작하면서 이런 요건이 실제로 생겼다.
  • 인덱스를 탈 수 있는 함수는 세 가지뿐이다 — MEMBER OF(), JSON_CONTAINS(), JSON_OVERLAPS().
mysql 
mysql> CREATE TABLE user (
    ->   id INT AUTO_INCREMENT PRIMARY KEY,
    ->   first_name VARCHAR(255),
    ->   last_name VARCHAR(255),
    ->   credit_info JSON,
    ->   INDEX mx_creditscores (
    ->     (CAST(credit_info->'$.credit_scores' AS UNSIGNED ARRAY))
    ->   )
    -> );
Query OK, 0 rows affected (0.01 sec)

mysql> INSERT INTO user VALUES
    -> (1, 'Kim', 'Dongwoo', '{"credit_scores": [360, 123, 123]}');
Query OK, 1 row affected (0.01 sec)
mysql key = mx_creditscores 
mysql> SELECT * FROM user
    -> WHERE 360 MEMBER OF (credit_info->'$.credit_scores');
+----+------------+-----------+------------------------------------+
| id | first_name | last_name | credit_info                        |
+----+------------+-----------+------------------------------------+
|  1 | Kim        | Dongwoo   | {"credit_scores": [360, 123, 123]} |
+----+------------+-----------+------------------------------------+

mysql> EXPLAIN SELECT * FROM user
    -> WHERE 360 MEMBER OF (credit_info->'$.credit_scores');
+----+------+-----------------+-----------------+---------+-------+------+-------------+
| id | type | possible_keys   | key             | key_len | ref   | rows | Extra       |
+----+------+-----------------+-----------------+---------+-------+------+-------------+
|  1 | ref  | mx_creditscores | mx_creditscores | 9       | const |    1 | Using where |
+----+------+-----------------+-----------------+---------+-------+------+-------------+

CAST(... AS UNSIGNED ARRAY) 가 핵심이다. 이 ARRAY 키워드가 "이 인덱스는 레코드 하나당 여러 엔트리를 만든다"는 선언이다.

정리

  • 레코드 1건 → 인덱스 엔트리 N개. JSON 배열 검색을 위한 인덱스다.
  • 선언은 CAST(expr AS <type> ARRAY) 형태.
  • MEMBER OF · JSON_CONTAINS · JSON_OVERLAPS 세 가지에서만 사용된다.
8-8

클러스터링 인덱스

InnoDB에서 기본키는 인덱스가 아니라 테이블 그 자체다.

핵심 모든 세컨더리 인덱스가 기본키 값을 품고 있다. 그래서 기본키 크기가 커지면 모든 인덱스가 같이 커진다.

클러스터링 인덱스란

  • 테이블의 프라이머리 키에 대해서만 적용되는 개념이다.
  • 레코드를 비슷한 값끼리 묶어서 저장하는 형태이며, InnoDB에서만 지원한다.
    • 즉 기본키 값에 의해 저장 위치가 결정된다.
  • 다른 값으로도 클러스터링할 수 있지만, 기본키로 만들어진 것만 클러스터링 인덱스/테이블이라고 부른다.
  • 클러스터링 테이블의 인덱스 리프 노드에는 모든 컬럼이 저장된다. 인덱스 자체가 곧 테이블이다.
기본키가 없을 때는?

InnoDB는 다음 순서로 클러스터링 키를 정한다.

  1. NOT NULL 유니크 인덱스 중 첫 번째

    이것이 있으면 클러스터링 키로 채택한다.

  2. 내부 자동 증가 컬럼 생성

    자동으로 증가하는 유니크한 값을 내부적으로 만들어 클러스터링 키로 쓴다. 이 값은 볼 수도 없고 쿼리 결과에도 영향을 주지 않는다.

그러니 가능하면 기본키를 직접 만들어 클러스터링의 혜택을 누리는 편이 낫다.

세컨더리 인덱스에 미치는 영향

  • InnoDB의 모든 세컨더리 인덱스는 레코드 주소가 아니라 기본키 값을 저장한다.
  • 따라서 세컨더리 인덱스로 검색하면, 먼저 기본키 값을 얻고 → 기본키 인덱스를 다시 검색해 최종 레코드를 가져온다.
flowchart LR
  A["세컨더리 인덱스 (first_name = 'Georgi')"] -->|"emp_no = 10001 획득"| B["기본키 인덱스 (클러스터링 테이블)"]
  B --> C["레코드 전체 반환"]
세컨더리 인덱스 검색은 항상 두 번의 트리 탐색이다 — 다만 필요한 컬럼이 세컨더리 인덱스 안에 다 있으면 두 번째는 생략된다(커버링 인덱스).

장점과 단점

구분내용
장점기본키 및 기본키 범위 검색이 매우 빠르다
장점모든 세컨더리 인덱스가 기본키를 갖고 있어 커버링 인덱스로 처리되는 경우가 많다
단점클러스터링 키가 크면 전체 인덱스 크기가 커진다
단점세컨더리 인덱스 검색 시 기본키를 한 번 더 검색해야 해서 느리다
단점데이터 삽입 시 기본키가 저장 위치를 결정하므로 삽입 성능이 느리다
단점기본키를 변경하면 삭제 후 재삽입이 필요하다 (다만 흔한 일은 아니다)

클러스터링 테이블 사용 시 주의사항

클러스터링 인덱스 키의 크기

세컨더리 인덱스는 항상 기본키 값을 갖는다. 한 테이블에 세컨더리 인덱스가 4~5개 생긴다고 가정해 보자.

기본키 크기레코드당 증가하는 인덱스 크기100만 건 저장 시 증가량
10 바이트10 × 5 = 50 바이트50 × 1,000,000 ≈ 47MB
50 바이트50 × 5 = 250 바이트250 × 1,000,000 ≈ 238MB

기본키를 40바이트 늘렸을 뿐인데 인덱스가 5배 커진다. 이 크기는 그대로 버퍼 풀 점유량이 된다.

기본키는 AUTO_INCREMENT 보다 업무적인 컬럼으로 (가능한 경우)
  • 기본키로 단일 또는 범위 조회를 하면 매우 빠르게 처리된다.
  • 기본키는 그 의미만큼 중요한 역할을 하기 때문에 대부분의 검색에서 자주 쓰인다.
  • 키의 값이 조금 커지더라도, 업무적으로 그 레코드를 대표할 수 있다면 그 컬럼을 기본키로 삼는 편이 좋다.
기본키는 반드시 명시하기
  • 가능하면 AUTO_INCREMENT 라도 명시해서 기본키를 만드는 것을 권장한다.
  • 안 만들면 내부적으로 생성하는 것은 똑같지만 우리가 아무 이득도 볼 수 없다.
  • 또한 ROW 기반 복제와 InnoDB Cluster는 모든 테이블이 기본키를 갖는 것을 사실상 요구한다. 기본키가 없으면 레플리카가 변경할 레코드를 찾기 위해 풀 스캔을 하게 된다.
AUTO_INCREMENT 를 인조 식별자로 쓰는 경우
  • 기본키가 길더라도 세컨더리 인덱스가 필요 없다면 그대로 기본키로 써도 된다.
  • 기본키를 대체하려고 인위적으로 추가한 키를 인조 식별자(surrogate key) 라고 한다.
  • 로그 테이블처럼 삽입만 일어나는 테이블에서는 AUTO_INCREMENT 기본키가 성능에 도움이 된다 — 항상 트리의 오른쪽 끝에만 추가되므로 페이지 분할이 최소화된다.

정리

  • InnoDB에서 기본키 인덱스의 리프 노드 = 레코드 전체. 인덱스가 곧 테이블이다.
  • 세컨더리 인덱스는 기본키 값을 담으므로, 기본키 크기가 모든 인덱스 크기를 좌우한다.
  • 기본키를 안 만들어도 InnoDB가 만든다 — 다만 우리는 쓸 수 없는 키가 된다.
  • 단조 증가하는 인조 식별자는 삽입 성능에, 업무적 기본키는 조회·커버링에 유리하다.
8-9

유니크 인덱스

유니크 인덱스가 일반 인덱스보다 읽기가 빠르다는 것은 오해다. 다만 쓰기는 확실히 느리다.

핵심 유니크 인덱스는 중복 체크 때문에 체인지 버퍼를 쓸 수 없다. 이것이 쓰기가 느린 진짜 이유다.

유니크는 인덱스인가 제약인가

  • 유니크는 사실 인덱스라기보다 제약조건에 가깝다.
  • MySQL에서는 인덱스 없이 유니크 제약조건만 만드는 것이 불가능하다.

유니크 인덱스 vs 일반 세컨더리 인덱스

인덱스 읽기 — 차이가 거의 없다
  • 대부분이 유니크 인덱스가 빠르다고 생각하지만 틀렸다.
    • 유니크는 1건만 읽으면 되고, 일반 인덱스는 한 건 더 읽어야 하므로 느리다고 생각한다.
    • 하지만 그 한 건 더 읽는 비교 작업은 디스크가 아니라 CPU 에서 이루어져 차이가 미미하다.
  • 결국 읽어야 할 레코드 건수가 비슷하다면 성능 차이는 없다.
인덱스 쓰기 — 확실히 느리다
  • 유니크 인덱스는 중복 값이 있는지 확인하는 단계가 하나 더 필요하다.
  • 중복 체크 시 읽기 락, 쓰기 시 쓰기 락을 설정하는데, 이 과정에서 데드락이 빈번하게 발생한다.
  • 원래 인덱스 키 저장은 체인지 버퍼로 백그라운드에서 처리할 수 있지만, 중복 체크가 반드시 필요하므로 버퍼링 자체가 불가능하다.
  • 이런 이유로 유니크 인덱스는 일반 세컨더리 인덱스보다 변경 작업이 느리다.
flowchart TB
  A["INSERT 발생"] --> B{"유니크 인덱스인가?"}
  B -->|"아니오"| C["체인지 버퍼에 기록 후 즉시 응답"]
  C --> D["백그라운드에서 병합"]
  B -->|"예"| E["인덱스 페이지를 디스크에서 읽음"]
  E --> F["중복 여부 확인"]
  F --> G["B-Tree 에 즉시 반영"]
유니크 인덱스는 지연시킬 수 없다 — 중복 여부는 지금 답해야 하는 질문이기 때문이다.

사용 시 주의사항

  • 정말 필요하다면 유니크 인덱스를 만드는 것은 당연하다.
  • 그러나 불필요하게 유니크 인덱스를 만드는 것은 좋지 않다.
  • 유니크 제약을 건 컬럼에는 자동으로 인덱스가 생성되며, 개별로 만든 인덱스와 동일한 역할을 한다. 즉 같은 컬럼에 유니크 인덱스와 일반 인덱스를 둘 다 만들 이유가 없다.
  • 유일성이 보장되어야 하는 컬럼에는 유니크를, 그렇지 않다면 세컨더리 인덱스를 고려하자.

정리

  • 읽기 성능은 일반 인덱스와 사실상 동일하다. 차이는 CPU 비교 몇 번뿐.
  • 쓰기는 중복 체크 때문에 체인지 버퍼를 못 써 확실히 느리고, 데드락 위험도 있다.
  • 유니크 제약은 인덱스를 자동으로 만든다. 같은 컬럼에 인덱스를 또 만들지 말 것.

외래키

외래키의 진짜 비용은 무결성이 아니라 잠금이 다른 테이블로 전파되는 것이다.

핵심 쓰기 잠금이 걸릴 때만 경합이 발생하고, 외래키와 무관한 컬럼의 변경은 경합을 만들지 않는다. 이 두 가지가 외래키 잠금의 전부다.

외래키의 두 가지 특징

  • 외래키 제약이 설정되면 연관 테이블의 컬럼에 인덱스까지 자동 생성된다.
  • 중요한 두 가지 특징
    • 테이블의 변경(쓰기 잠금) 이 발생하는 경우에만 잠금 경합이 발생한다.
    • 외래키와 연관되지 않은 컬럼의 변경은 최대한 잠금 경합을 발생시키지 않는다.
  • 외래키를 물리적으로 생성한다면 잠금 경합까지 고려해 모델링해야 한다.
  • 잠금이 다른 테이블로 확장되면 그만큼 전체적인 동시 처리 성능이 낮아진다.

자식 테이블의 변경이 대기하는 경우

자식 테이블의 외래키 컬럼을 변경하려면 부모 테이블의 해당 레코드를 확인해야 한다. 그 레코드에 쓰기 잠금이 걸려 있으면 끝날 때까지 기다린다.

작업번호커넥션 1커넥션 2
1BEGIN;
2UPDATE tb_parent SET fd='2' WHERE id=2
3BEGIN;
4UPDATE tb_child SET pid=2 WHERE id=100 대기
5ROLLBACK
6QUERY OK

부모 테이블의 변경이 대기하는 경우

반대 방향도 성립한다. 자식 레코드에 쓰기 잠금이 걸린 상태에서 부모를 삭제하려 하면 기다린다. ON DELETE CASCADE 때문에 부모 삭제가 곧 자식 삭제이기 때문이다.

작업번호커넥션 1커넥션 2
1BEGIN;
2UPDATE tb_child SET fd='100' WHERE id=100
3BEGIN;
4DELETE FROM tb_parent WHERE id=1 대기
5ROLLBACK
6QUERY OK

그래서 실무에서는 보강

많은 서비스가 모델링에는 외래키를 그리되 물리적으로는 걸지 않는다. 무결성은 애플리케이션이 보장하고, DB는 잠금 전파를 피하는 선택이다. 다만 데이터 정합성 사고가 났을 때 DB가 잡아 주지 않는다는 대가를 감수하는 결정이라는 점은 분명히 인식하고 있어야 한다. (→ 11-4 JOIN과 외래키)

정리

  • 외래키를 만들면 인덱스가 따라 생긴다.
  • 잠금 경합은 쓰기일 때만, 그리고 외래키 관련 컬럼일 때만 발생한다.
  • 양방향으로 대기가 생긴다 — 자식 변경은 부모 확인을, 부모 삭제는 자식 CASCADE를 기다린다.
  • 물리 외래키는 잠금 전파까지 포함해 결정할 문제다.
