3-1

사용자 식별

MySQL의 계정은 아이디가 아니라 아이디@호스트 쌍이다.

핵심 같은 아이디로 여러 계정이 존재할 수 있고, 인증에는 항상 범위가 더 좁은 쪽이 먼저 선택된다.

MySQL은 사용자를 식별할 때 아이디와 함께 접속 가능한 호스트를 반드시 명시해야 한다.

로컬 호스트에서만 접속 가능한 계정

'user_id'@'127.0.0.1'

모든 호스트에서 접속 가능한 계정

% 는 모든 호스트를 의미한다.

'user_id'@'%'

범위가 겹칠 때 — 좁은 쪽이 이긴다

'user_id'@'192.168.0.1' 과 'user_id'@'%' 두 계정이 동시에 있다고 하자. MySQL은 권한과 사용자 정보에 대해 항상 범위가 더 좁은 것을 먼저 선택한다. 따라서 192.168.0.1 에서 접속하면 'user_id'@'192.168.0.1' 계정으로 인증이 진행된다.

좁은 범위가 우선한다 — % 계정에 권한을 몰아줘도, 더 구체적인 호스트 계정이 있으면 그쪽 권한으로 인증된다.
!

여기서 사고가 난다

"권한을 분명히 줬는데 접근이 안 된다"의 흔한 원인이 이것이다. 'app'@'%' 에 권한을 부여했지만 'app'@'localhost' 라는 빈 껍데기 계정이 남아 있으면, 로컬에서 접속할 때 권한이 없는 쪽으로 인증된다.

정리

  • 계정의 정체성은 아이디 + 호스트 쌍이다. 아이디만으로는 계정을 특정할 수 없다.
  • % 는 모든 호스트, 구체적인 IP는 좁은 범위. 겹치면 좁은 쪽이 선택된다.
3-2

사용자 계정 관리

SYSTEM_USER 권한 하나로 시스템 계정과 일반 계정이 갈린다.

핵심 CREATE USER 의 옵션들은 대부분 비밀번호의 수명 정책에 관한 것이다. 사람에게는 좋지만 애플리케이션 계정에 걸면 장애가 된다.

시스템 계정과 일반 계정

SYSTEM_USER 권한 보유 여부에 따라 나뉜다.

  • 스토어드 프로그램 생성 시 생성자(DEFINER)를 타 사용자로 설정

계정 생성 옵션

8.0에서는 CREATE USER 로 계정을 만들고, 여러 옵션을 함께 지정할 수 있다.

create-user.sql 
CREATE USER 'app'@'10.0.%'
  IDENTIFIED WITH 'caching_sha2_password' BY 'secret'
  REQUIRE NONE
  PASSWORD EXPIRE NEVER
  PASSWORD HISTORY DEFAULT
  ACCOUNT UNLOCK;
IDENTIFIED WITH
  • 인증 방식(플러그인)과 비밀번호를 설정한다. IDENTIFIED WITH 'plugin' BY 'password' 형식.
  • 여러 플러그인이 있고, 8.0의 기본은 Caching SHA-2 Authentication (caching_sha2_password) 이다.
REQUIRE
  • 접속 시 TLS/SSL 채널을 사용할지 여부.
  • 굳이 켜지 않아도 인증 과정 자체는 암호화되어 안전하게 접속된다.
PASSWORD EXPIRE
  • 비밀번호의 유효 기간을 설정한다. NEVER, DEFAULT, INTERVAL n DAY 등.
  • 지정하지 않으면 default_password_lifetime 값이 적용된다.
×

애플리케이션 계정에는 만료를 걸지 말 것

개발자나 관리자 계정에는 만료 정책이 좋지만, 앱이 사용하는 계정에 걸면 어느 날 갑자기 전면 장애가 된다. 만료된 계정은 비밀번호를 바꾸기 전까지 어떤 쿼리도 실행할 수 없다.

PASSWORD HISTORY
  • 과거에 썼던 비밀번호의 재사용 가능 여부를 설정한다.
  • 이력은 mysql.password_history 테이블에 저장된다.
PASSWORD REUSE INTERVAL
  • 썼던 비밀번호의 재사용 금지 기간을 설정한다.
  • 명시하지 않으면 password_reuse_interval 값이 적용된다.
PASSWORD REQUIRE
  • 만료되어 비밀번호를 변경할 때 현재 비밀번호를 요구할지 설정한다.
  • CURRENT / OPTIONAL / DEFAULT. 명시하지 않으면 password_require_current 값이 적용된다.
ACCOUNT LOCK / UNLOCK
  • 계정 정보 변경 시 그 계정을 사용할 수 있는 상태로 둘지 결정한다.

정리

  • SYSTEM_USER 권한이 시스템 계정과 일반 계정을 가르며, 계정 관리는 시스템 계정만 할 수 있다.
  • 기본 인증 플러그인은 caching_sha2_password 다.
  • 비밀번호 만료 / 이력 / 재사용 정책은 사람 계정에만. 앱 계정에는 PASSWORD EXPIRE NEVER.
3-3

비밀번호 관리

8.0은 비밀번호 검증을 플러그인이 아닌 컴포넌트로 제공하고, 계정 하나에 비밀번호 두 개를 허용한다.

핵심 이중 비밀번호는 무중단 비밀번호 교체를 위한 기능이다. 예전엔 비밀번호를 바꾸는 순간 앱이 죽었다.

고수준 비밀번호 — validate_password

글자 조합을 강제하거나 금칙어를 설정하는 기능은 validate_password 컴포넌트가 제공한다.

5.x 와의 차이

5.x는 플러그인, 8.0은 컴포넌트로 제공한다. 제공 기능 자체는 거의 같고, 변수 이름이 validate_password_length(플러그인) 에서 validate_password.length(컴포넌트) 처럼 점 표기로 바뀐 것이 눈에 띄는 차이다.

이중 비밀번호

이전 버전에서는 계정 하나에 비밀번호 하나뿐이었다. 8.0은 Primary / Secondary 두 개를 동시에 유효하게 유지할 수 있다. 공식 문서는 이를 Dual Password(이중 비밀번호) 라고 부른다.

dual-password.sql 
-- 현재 비밀번호는 old_password
mysql> ALTER USER 'root'@'localhost' IDENTIFIED BY 'old_password';

-- 새 비밀번호로 바꾸되, 기존 비밀번호도 남겨둔다
mysql> ALTER USER 'root'@'localhost' IDENTIFIED BY 'new_password'
    -> RETAIN CURRENT PASSWORD;

-- 앱 설정 배포가 끝난 뒤, 세컨더리(옛 비밀번호)를 폐기
mysql> ALTER USER 'root'@'localhost' DISCARD OLD PASSWORD;
flowchart LR
  A["1. RETAIN CURRENT PASSWORD - 새 비밀번호 설정"] --> B["2. 두 비밀번호 모두 유효 - 앱 설정을 순차 배포"]
  B --> C["3. DISCARD OLD PASSWORD - 옛 비밀번호 폐기"]
2단계가 이중 비밀번호의 존재 이유다 — 이 구간이 있어야 서버 재배포를 롤링으로 진행할 수 있다.
  • 이중 비밀번호를 설정하기 전에는 old_password 만 사용 가능하다.
  • RETAIN CURRENT PASSWORD 를 붙이면 new_password 와 함께 둘 다 사용할 수 있다.
  • 앱 설정 변경이 끝났다면 보안을 위해 세컨더리는 삭제하는 것을 권장한다.

정리

  • 비밀번호 정책은 validate_password 컴포넌트가 담당한다 (5.x는 플러그인).
  • 정책은 LOW < MEDIUM < STRONG 순으로 강해지고, STRONG 만 사전 파일을 본다.
  • 이중 비밀번호는 무중단 교체용이다. 교체가 끝나면 DISCARD OLD PASSWORD 로 반드시 정리한다.
3-4

권한

권한은 글로벌/객체, 정적/동적 두 축으로 분류된다. 이 분류가 GRANT ~ ON 뒤에 무엇을 쓸지를 결정한다.

핵심 권한의 종류가 ON 뒤에 올 수 있는 객체의 범위를 정한다. 글로벌 권한은 언제나 *.*, 테이블 권한은 컬럼 단위까지 내려갈 수 있다.

권한의 분류

분류설명GRANT 시 객체 명시
글로벌 권한데이터베이스/테이블 이외의 객체에 적용명시하지 않는다
객체 권한데이터베이스/테이블을 제어하는 데 필요명시해야 한다
정적 권한MySQL 소스코드에 고정적으로 명시된 권한—
동적 권한컴포넌트/플러그인이 설치될 때 등록되는 권한—
예외적인 ALL (ALL PRIVILEGES)
  • 글로벌과 객체 두 가지 용도로 모두 쓰인다.
  • 특정 객체에 부여하면 그 객체에 적용 가능한 모든 객체 권한을 부여한다.
  • 글로벌로 부여하면 글로벌 수준에서 가능한 모든 권한을 부여한다.

GRANT 구문

GRANT <privileges> ON db.table TO 'user'@'host';
  • 8.0부터는 계정이 없으면 에러가 난다. CREATE USER 를 먼저 해야 한다. (5.x는 GRANT가 계정을 만들어 줬다.)
  • 콤마로 여러 권한을 한 번에 부여할 수 있다.

권한마다 달라지는 객체 범위

GRANT ~ ON 뒤에 무엇을 쓸 수 있는지는 권한의 종류가 결정한다.

flowchart TB
  A["*.* (서버 전체)"] --> B["db.* (데이터베이스 단위)"]
  B --> C["db.table (테이블 단위)"]
  C --> D["db.table.column (컬럼 단위)"]
  G["글로벌 권한 (SUPER 등)"] -.->|"여기까지만"| A
  H["DB 권한 (EVENT 등)"] -.->|"여기까지"| B
  I["테이블 권한 (INSERT 등)"] -.->|"여기까지"| D
권한 종류가 도달 가능한 깊이를 정한다 — 글로벌 권한은 *.* 를 벗어날 수 없고, 테이블 권한만 컬럼까지 내려간다.
글로벌 권한

특정 DB나 테이블에 부여될 수 없어서 항상 *.* 를 쓰게 된다. *.* 는 모든 객체, 곧 MySQL 서버 전체를 의미한다.

GRANT SUPER ON *.* TO 'user'@'host';
DB 권한

특정 DB 또는 서버의 모든 DB에 부여할 수 있다. 테이블 단위로는 내려갈 수 없어 *.* 또는 db.* 만 쓴다.

GRANT EVENT ON *.* TO 'user'@'host';
GRANT EVENT ON employee.* TO 'user'@'host';
테이블 권한

*.* 부터 개별 테이블까지, 그리고 특정 컬럼까지 부여할 수 있다.

GRANT INSERT ON *.* TO 'user'@'host';
GRANT INSERT ON employee.* TO 'user'@'host';
GRANT INSERT ON employee.salary TO 'user'@'host';
GRANT INSERT, UPDATE(dept_no) ON employee.* TO 'user'@'host';
  • 컬럼 단위 권한은 DELETE 를 제외한 INSERT / UPDATE / SELECT 에 부여할 수 있다.
  • 다만 실무에서 잘 쓰지 않는다. 컬럼 노출 제어가 필요하면 뷰(VIEW)로 푸는 편이 관리하기 쉽다.

권한 목록 확인

SHOW GRANTS 또는 권한 관련 시스템 테이블(mysql.user, mysql.db, mysql.tables_priv 등)에서 현재 부여된 권한을 확인할 수 있다.

정리

  • 글로벌 권한은 *.*, DB 권한은 db.* 까지, 테이블 권한은 컬럼까지 내려간다.
  • 8.0에서는 계정을 먼저 만들어야 GRANT 가 통과한다.
  • 컬럼 단위 권한보다 뷰가 현실적인 선택지인 경우가 많다.
3-5

역할

8.0의 역할은 새로운 개념이 아니다 — 내부적으로는 그냥 계정이다.

핵심 역할을 부여받아도 로그인 직후에는 활성화되지 않는다. SET ROLE 을 하거나 activate_all_roles_on_login 을 켜야 한다.

8.0부터 권한을 묶어 역할(Role) 로 관리할 수 있게 되었다.

역할 생성 — 그런데 왜 안 될까

껍데기 역할을 만들고, 권한을 붙이고, 사용자에게 부여하는 자연스러운 순서를 따라가 보자. 역할은 분명히 부여됐는데 조회는 실패한다.

mysql 여기서 막힌다 
mysql> CREATE ROLE role_emp_read;
mysql> GRANT SELECT ON employee.* TO role_emp_read;
mysql> CREATE USER reader@'localhost' IDENTIFIED BY '1234';
mysql> GRANT role_emp_read TO reader@'localhost';

mysql> SHOW GRANTS;
+---------------------------------------------------+
| Grants for reader@localhost                       |
+---------------------------------------------------+
| GRANT USAGE ON *.* TO `reader`@`localhost`        |
| GRANT `role_emp_read`@`%` TO `reader`@`localhost` |
+---------------------------------------------------+
2 rows in set (0.00 sec)

mysql> SELECT * FROM realmysql.employee;
ERROR 1142 (42000): SELECT command denied to user 'reader'@'localhost' for table 'employee'
×

ERROR 1142 — 역할이 부여되지 않은 게 아니다

SHOW GRANTS 는 역할이 부여됐다고 말하고 있다. 문제는 활성화되지 않았다는 것이다.

역할은 로그인 시 자동으로 켜지지 않는다

  • MySQL은 최초 로그인 시 아무런 역할도 할당하지 않는다.
  • SET ROLE <ROLE_NAME> 을 입력해야 그 권한이 들어온다. 단, 로그아웃하면 다시 초기화된다.
  • activate_all_roles_on_login 시스템 변수를 켜면 로그인 시 자동으로 활성화된다.
mysql 해결 
mysql> SELECT current_role();
+----------------+
| current_role() |
+----------------+
| NONE           |
+----------------+

mysql> SET ROLE 'role_emp_read';
Query OK, 0 rows affected (0.00 sec)

mysql> SELECT current_role();
+---------------------+
| current_role()      |
+---------------------+
| `role_emp_read`@`%` |
+---------------------+

mysql> SELECT * FROM realmysql.employee;
Empty set (0.00 sec)
mysql 매번 SET ROLE 하기 싫다면 
SET GLOBAL activate_all_roles_on_login = ON;

  로그인 --> 역할활성 : activate_all_roles_on_login = ON
  역할활성 --> [*] : 로그아웃하면 초기화
부여와 활성화는 다른 단계다 — 부여는 영구적이지만 활성화는 세션마다 새로 필요하다.

8.0 역할의 비밀 — 사실은 계정이다

  • 역할은 사용자 계정과 거의 같은 모습을 하고 있다.
  • 서버 내부적으로 역할과 계정은 동일한 객체로 취급된다.
  • 즉 새로운 개념이 생긴 게 아니라, 하나의 계정에 다른 계정의 권한을 병합해서 쓸 수 있게 된 것뿐이다.
  • 생성 시 계정처럼 호스트 부분을 명시할 수 있고, 생략하면 자동으로 % 가 된다.
mysql 
mysql> SELECT user, host, account_locked FROM mysql.user;
+------------------+-----------+----------------+
| user             | host      | account_locked |
+------------------+-----------+----------------+
| role_emp_read    | %         | Y              |
| mysql.infoschema | localhost | Y              |
| mysql.session    | localhost | Y              |
| mysql.sys        | localhost | Y              |
| reader           | localhost | N              |
| root             | localhost | N              |
+------------------+-----------+----------------+
6 rows in set (0.00 sec)

역할 role_emp_read 가 mysql.user 에 계정으로 들어 있다. account_locked = Y 인 것이 유일한 차이인데, 이 잠금이 "이 계정으로는 로그인할 수 없다"는 표식 역할을 한다.

정리

  • 역할은 권한 묶음이지만, 내부적으로는 mysql.user 에 들어 있는 잠긴 계정이다.
  • GRANT role TO user 로 부여해도 세션에서 활성화해야 효력이 생긴다.
  • 매번 SET ROLE 이 번거로우면 activate_all_roles_on_login = ON.
