15-1

문자열 (CHAR vs VARCHAR)

고정 길이냐 가변 길이냐 — 그리고 얼마나 자주 바뀌는가.

핵심 선택 기준은 길이만이 아니다. 값이 자주 바뀌고 길이가 늘어난다면 VARCHAR의 레코드 이동 비용이 CHAR의 공간 낭비보다 크다.

저장 공간

구분저장 방식추가 공간
CHAR 고정 길이 — 지정한 만큼 항상 차지 없음 (유효 길이를 저장할 필요가 없다)
VARCHAR 가변 길이 — 실제 쓴 만큼만 차지 유효 길이 저장에 1~2바이트 필요
  • 문자열 길이가 일정하다면 항상 CHAR 를 쓰는 것이 일반적이다.
  • 길이가 가변적이면 VARCHAR 를 쓴다.
길이 저장 공간의 경계
  • VARCHAR 의 최대 바이트 길이가 255 이하면 1바이트만 쓴다.
  • 256 바이트 이상이면 2바이트 를 쓴다.
  • 2바이트로 표현 가능한 범위를 넘을 수 없으므로 최대 길이는 65,535 바이트 를 넘길 수 없다.

MySQL 레코드의 최대 크기

  • TEXT, BLOB 을 제외한 컬럼의 전체 크기는 64KB를 초과할 수 없다.
  • 이미 40KB를 쓰는 상황에서 25KB짜리 VARCHAR 를 만들면 자동으로 TEXT 로 변경된다.
  • 65,535 바이트는 글자 수가 아니라 바이트 다. 저장하는 문자에 따라 실제 글자 수는 달라진다.

컬럼이 자주 변경되는 경우 어느 타입을?

선택 기준은 값의 길이도 중요하지만 얼마나 자주 변경되는지도 중요하다.

타입값이 바뀔 때적합한 컬럼
CHAR 그냥 제자리에서 값을 바꾼다 주민번호, 부서번호, 상태 코드
VARCHAR 더 긴 값이 오면 레코드 자체를 다른 공간으로 옮긴다 길이가 크게 변하지 않거나 변경이 드문 컬럼

레코드 이동이나 분리는 CHAR 에서 발생할 수 있는 2~3바이트 낭비보다 훨씬 큰 자원 낭비를 만든다.

자료형 뒤의 숫자가 의미하는 것

  • 바이트가 아니라 문자 수다. char(10), varchar(10) 은 10글자를 저장할 수 있는 공간이다.
  • 실제 디스크·메모리 사용량은 문자 집합에 따라 달라진다.
문자 집합문자당 바이트char(10) 의 최대 크기
영어 등 서구권1 바이트최대 10 바이트
한국어·일본어 (레거시 인코딩)최대 2 바이트최대 20 바이트
유니코드 (utf8mb4)최대 4 바이트최대 40 바이트

저장 공간과 스키마 변경 — 63 과 64 의 차이

기존 varchar(60) 컬럼을 63 또는 64로 확장할 때 소요 시간이 극적으로 달라진다.

한 글자 차이로 온라인 DDL 여부가 갈린다 — 255 바이트 경계가 길이 저장 공간을 1바이트에서 2바이트로 밀어 올린다.
  • 63 — 63 × 4 = 252 바이트라 길이 저장에 1바이트만 쓴다.
  • 64 — 64 × 4 = 256 바이트라 2바이트 를 쓰게 된다.
  • 길이 저장 공간의 크기가 바뀌면 LOCK=SHARED 로 변경을 막고 레코드를 복사하는 방식으로 처리된다.
  • 길이가 크게 늘어날 것으로 예상된다면, 길이 저장 공간이 바뀌지 않도록 미리 조금 크게 설계하는 편이 좋다.

문자 집합 (캐릭터 셋)

  • 문자 집합은 CHAR, VARCHAR, TEXT 타입 컬럼에만 쓸 수 있다.
  • 요즘 애플리케이션은 다국어 처리를 위해 대부분 utf8mb4 를 쓴다.
시스템 변수역할기본값
character_set_system서버가 식별자를 저장할 때 쓰는 문자 집합. 바꿀 필요가 없다utf8
character_set_server서버의 기본 문자 집합. DB나 테이블에 명시가 없으면 이 값이 쓰인다utf8mb4
character_set_databaseDB의 기본 문자 집합utf8mb4
character_set_filesystemLOAD DATA INFILE, SELECT ... INTO OUTFILE 의 파일명 해석에 사용. 파일 내용이 아니라 파일을 찾을 때 쓴다—
character_set_client클라이언트가 보낸 SQL의 인코딩. 인트로듀서가 지정되면 무시된다—
character_set_connection서버가 받은 SQL을 처리하기 위해 변환할 문자 집합. 숫자를 문자로 변환할 때도 쓴다utf8mb4
character_set_results서버가 결과를 보낼 때 쓰는 문자 집합utf8mb4
인트로듀서

SQL에서 별도로 문자 집합을 지정하는 지시자를 인트로듀서 라고 한다. 문자열 앞에 _ 를 붙인다.

SELECT emp_no, first_name FROM employees WHERE first_name = _latin1'Matt';
결과 전송 시의 변환
  • 변환 전과 변환할 문자 집합이 같으면 변환 작업이 전부 생략된다.
  • 문자 집합뿐 아니라 콜레이션까지 포함해서 같은지 비교한다.

콜레이션 (Collation)

  • 문자열 값의 비교나 정렬 순서를 위한 규칙이다.
  • 모든 문자열 컬럼은 독립적인 문자 집합과 콜레이션을 갖는다.
  • 개별 지정이 없으면 기본 문자 집합과 콜레이션이 적용된다.
  • 일치 여부에 따라 쿼리 결과가 달라지고 성능도 크게 영향을 받는다.
콜레이션 이해
  • 한 문자 집합에 속한 콜레이션은 다른 문자 집합과 공유할 수 없다.
  • 문자 집합만 지정하고 콜레이션을 생략하면 그 문자 집합의 기본 콜레이션이 쓰인다.
  • 이름은 보통 두세 개의 파트로 구성된다.
    • 3파트 — 문자 집합 이름 + 하위 분류 + 대소문자 구분 여부 (예: utf8mb4_0900_ai_ci)
    • 2파트 — 문자 집합 이름 + bin (실제 바이트 기준 비교)
  • 0900 은 UCA(Unicode Collation Algorithm) 버전을 뜻한다.
  • ai / as 는 액센트 문자를 같은 문자로 볼지 여부다 (accent-insensitive / accent-sensitive).
  • 문자열 컬럼은 콜레이션 없이 문자 집합만 가질 수 없고, 모든 비교는 콜레이션이 판단한다.
    • 즉 타입 이름과 길이가 같다고 같은 타입이 아니다.
utf8mb4 의 콜레이션 선택
  • 다국어 지원을 위해 utf8mb4 를 쓰는 추세다. latin 은 아주 특별한 경우가 아니면 쓰지 않는다.
  • 성능을 기준으로 콜레이션을 정하지 말고 필요에 따라 결정하는 것이 좋다.
  • 새 서비스를 개발한다면 UCA 9.0.0 기반 콜레이션(utf8mb4_0900_*)을 권장한다.

비교 방식 — 뒤 공백의 처리

  • 대부분의 문자 집합·콜레이션은 CHAR/VARCHAR 뒤에 공백을 붙여 길이를 맞춘 뒤 비교한다.
  • 그런데 UCA 9.0.0 계열은 앞뒤 공백이 비교 연산에 그대로 영향을 준다.
같은 값인데 결과가 다르다 
SET NAMES utf8mb4 COLLATE utf8mb4_bin;
SELECT 'a ' = 'a';        -- 1 (true)

SET NAMES utf8mb4 COLLATE utf8mb4_0900_bin;
SELECT 'a ' = 'a';        -- 0 (false)
!

마이그레이션에서 터지는 지점

레거시 콜레이션에서 utf8mb4_0900_* 로 옮기면 뒤 공백이 있는 데이터의 조회 결과가 달라진다. 값 자체는 그대로인데 조회가 안 되는 현상으로 나타나므로 원인을 찾기 어렵다. 콜레이션 변경 전에는 공백이 섞인 데이터가 있는지 먼저 확인하자.

문자열 이스케이프 처리

  • 일반적인 프로그래밍 언어처럼 이스케이프를 지원한다.
  • 홑따옴표·쌍따옴표는 \ 없이 '' 또는 "" 로 두 번 반복해서 처리할 수도 있다.

정리

  • 길이가 일정하면 CHAR, 가변이면 VARCHAR. 단 자주 길어지는 값은 CHAR 가 나을 수 있다.
  • 괄호 안의 숫자는 문자 수. utf8mb4 에서는 문자당 최대 4바이트.
  • 255 바이트 경계가 길이 저장 공간(1↔2바이트)을 바꾸고, 그것이 온라인 DDL 가능 여부를 가른다.
  • 타입이 같아 보여도 콜레이션이 다르면 다른 타입이다 — 조인 시 풀 스캔의 원인이 된다.
  • UCA 9.0.0(_0900_) 계열은 뒤 공백을 무시하지 않는다.
15-2

숫자

참값이냐 근삿값이냐 — 돈을 다룬다면 선택지는 하나뿐이다.

핵심 FLOAT/DOUBLE 은 동등 비교가 성립하지 않는다. 정확해야 하는 값은 DECIMAL 이거나 정수로 환산해 저장한다.

참값과 근삿값

구분의미타입
참값그 값을 정확히 그대로 유지INT 계열, DECIMAL
근삿값흔히 말하는 부동소수점. 비슷한 값으로 관리FLOAT, DOUBLE

십진 표기법과 이진 표기법

표기법저장 방식타입특징
이진 표기법 프로그래밍 언어의 일반적인 정수·실수. 한 바이트로 256까지 표현 INT, BIGINT 등 대부분 메모리·디스크 절약
십진 표기법 각 자릿값을 4비트나 1바이트 로 표현. 진수가 아니라 저장 형식을 말한다 DECIMAL 돈처럼 정확해야 할 때. 65자리 까지 표현 가능
  • DECIMAL 은 이진 표기법 타입보다 저장 공간을 2배 이상 쓴다.
  • 아주 큰 숫자나 고정 소수점이 꼭 필요한 경우가 아니라면 INT, BIGINT 를 쓴다.

정수

  • 여러 타입이 있지만 값의 범위만 다를 뿐 큰 차이는 없다.
  • 필요한 범위 안에서 가장 적은 공간을 쓰는 타입을 고르면 된다.
SIGNED / UNSIGNED
  • UNSIGNED 는 양수만 저장하는 대신 최댓값이 2배가 된다.
  • 인덱스 관점에서의 영향은 딱히 없다.
  • 다만 저장 범위가 다르므로 외래키나 조인 조건에서는 타입을 일치시켜야 한다.

부동 소수점

  • FLOAT, DOUBLE 을 쓴다.
  • 정확한 유효 소수점을 식별하기 어려워 크다·작다 비교도 쉽지 않고, 동등 비교는 지원하지 않는다.
  • FLOAT — 4바이트, 유효 자릿수 8. DOUBLE — 8바이트, 유효 자릿수 16.
  • 바이너리 로그 포맷이 STATEMENT 면 소스와 레플리카 사이에 데이터 불일치가 생길 수 있다.
i

노트가 제안한 우회 보강

소수 저장이 꼭 필요하다면 유효 소수점 자릿수만큼 10을 곱해 정수로 저장하고, 읽을 때 다시 나누는 방법이 있다. 예를 들어 소수점 둘째 자리까지 필요하면 12.34 를 1234 로 저장한다. 정수 연산이라 정확하고 빠르며, 인덱스와 동등 비교도 정상 동작한다.

DECIMAL

  • 소수점 위치가 고정된 고정 소수점 타입이다.
  • 숫자 하나를 저장하는 데 1/2 바이트 가 필요해, 3~4자리를 저장하면 2바이트가 든다.
  • 소수가 아닌 정수를 관리하려고 DECIMAL 을 쓰는 것은 성능·공간 모두 손해다.

정밀도 표기 시 주의점

표기의미
DECIMAL(20, 5)정수부 20 - 5 = 15 자리, 소수부 5자리
DECIMAL(20)소수부 없이 정수부만 20자리
  • FLOAT, DOUBLE 은 저장 공간이 고정이라 정밀도를 바꿔도 크기가 변하지 않는다.
  • DECIMAL 은 저장 공간이 가변이라 정밀도가 저장 가능한 자릿수와 공간을 함께 결정한다.
  • INT(10) 처럼 정수 타입 뒤에 붙는 숫자는 자릿수 제한이 아니라 화면에 표시할 자릿수 일 뿐이다.

AUTO_INCREMENT 옵션

  • 반드시 기본키나 유니크 키의 일부로 설정해야 한다. (InnoDB 한정 제약)
  • 테이블당 하나만 쓸 수 있다.
  • 개발 서버에서 운영 서버로 스키마를 복제한다면 CREATE TABLE 에 마지막 증가값이 기재되므로 초기값에 주의해야 한다.

정리

  • 정확한 값 — INT 계열 / DECIMAL. 근삿값 — FLOAT / DOUBLE.
  • 부동소수점은 동등 비교 불가. 돈이나 정확한 값에는 쓰지 않는다.
  • INT(10) 의 10은 표시 자릿수 일 뿐 저장 범위와 무관하다.
  • AUTO_INCREMENT 는 키의 일부여야 하고 테이블당 하나다.
15-3

날짜와 시간

DATETIME 은 입력받은 그대로, TIMESTAMP 는 UTC로 저장한다. 이 차이가 전부다.

핵심 타임존 설정은 한 번 틀어지면 되돌리기가 매우 어렵다. 가급적 손대지 말고, 저장은 UTC 기준으로 통일하는 편이 안전하다.

저장 공간

데이터 타입사용 바이트
YEAR1
DATE3
TIME3 + 밀리초
DATETIME5 + 밀리초
TIMESTAMP4 + 밀리초
  • 밀리초까지 저장하면 2자리당 1바이트 가 추가로 필요하다.
    • DATETIME(6) 은 5 + 3 = 8 바이트를 쓴다.
  • 위 값들은 5.6.4 이후 버전 기준이다.
  • 밀리초를 저장하려면 DATETIME, TIME, TIMESTAMP 에 괄호로 자릿수를 명시한다.
  • NOW() 에는 밀리초가 없다. 필요하면 NOW(6) 을 쓴다.

타임존과의 관계

타입저장 방식타임존 변경 시
DATE / DATETIME 클라이언트에게 받은 그대로 저장 값이 그대로 유지된다
TIMESTAMP 항상 UTC 기준으로 저장 조회 시 자동으로 변환된다
  • 타임존 관련 설정은 가급적 건드리지 않는 것을 권장한다.
  • 한 번 틀어지면 해결하기가 매우 어렵다.
  • 다국어 서비스 등을 고려하면 UTC로 저장하는 편이 좋아 보인다는 것이 노트의 판단이다.

자동 업데이트

이전에는 TIMESTAMP 만 가능했지만 현재는 다른 날짜 타입도 자동 갱신을 지원한다.

created_at / updated_at 의 정석 
CREATE TABLE tb_autoupdate (
  id INT NOT NULL PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(255),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

정리

  • DATETIME(5B)은 입력 그대로, TIMESTAMP(4B)는 UTC 변환해서 저장한다.
  • 밀리초는 2자리당 1바이트 추가. NOW() 는 밀리초를 주지 않는다.
  • 타임존 설정은 건드리지 말고, 저장 기준을 하나로 통일한다.
  • DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP 는 이제 DATETIME 에서도 쓸 수 있다.
15-4

ENUM, SET

둘 다 문자열을 내부적으로 정수로 매핑해 관리한다. 공간은 아끼지만 가독성을 잃는다.

핵심 ENUM/SET 은 목록의 마지막에 값을 추가하면 즉시(INSTANT), 중간에 끼워 넣으면 테이블 리빌드다. 설계 시 이것부터 결정해야 한다.

공통점

  • 둘 다 문자열 값을 MySQL 내부에서 숫자 값으로 매핑해 관리한다.
  • 실제 DB에는 인코딩된 값만 저장되어 의미를 바로 파악하기 어렵다는 단점이 있다.

ENUM

  • 테이블 구조에 나열된 목록 중 하나의 값만 가질 수 있다.
  • 주로 코드화된 값을 관리할 때 쓴다.
  • 메모리와 디스크에는 문자열이 아니라 매핑된 정수가 저장된다.
  • 최대 65,535개 까지 지정할 수 있고, 항목이 255개 미만이면 1바이트, 그 이상이면 2바이트 를 쓴다.
  • MySQL에서는 별도의 코드 테이블 없이 이것으로 대신하는 경우가 있는데, 그럴 때 유용하다.
  • 중간에 값을 추가하면 리빌드가 필요하지만, 마지막에 추가하면 INSTANT 로 메타데이터만 바꾼다.
CREATE TABLE tb_enum (
  fd_enum ENUM('PROCESS', 'FAILURE', 'SUCCESS')
);

INSERT INTO tb_enum VALUES ('PROCESS'), ('SUCCESS');

SELECT fd_enum * 1 AS fd_enum_real_value, fd_enum FROM tb_enum;
fd_enum_real_valuefd_enum
1PROCESS
3SUCCESS

* 1 을 곱하면 내부에 실제로 저장된 정수가 드러난다. 인덱스는 1부터 시작한다.

ENUM 의 정렬
  • ENUM 컬럼으로 정렬하면 문자열이 아니라 매핑된 정수 기준으로 정렬된다.
  • 문자열 순서로 정렬하려면 CAST() 를 써야 하는데, 그러면 인덱스를 쓸 수 없다.
CREATE TABLE tb_enum (
  fd_enum ENUM('PROCESS', 'FAILURE', 'SUCCESS', 'ACID')
);

SELECT * FROM tb_enum ORDER BY fd_enum;                 -- #1
SELECT * FROM tb_enum ORDER BY CAST(fd_enum AS CHAR);   -- #2
#1 정의 순서(정수) 기준
PROCESS
SUCCESS
ACID
#2 사전 순서(문자열) 기준
ACID

SUCCESS
ENUM 의 장점
  • 규정된 값만 넣을 수 있다는 제약이 첫 번째 장점이다.
  • 또 하나는 디스크 저장 공간 절약 — 실제로는 매핑된 정수가 저장되기 때문이다.
  • 저장 데이터 크기는 곧 버퍼 풀 효율로 이어지므로, 메모리 절약의 이점도 함께 얻는다.

SET

  • ENUM과의 차이는 한 컬럼에 1개 이상의 값을 저장할 수 있다는 점이다.
  • 내부적으로 BIT-OR 연산으로 선택된 값들을 합쳐 저장한다.
  • 멤버가 8개 이하면 1바이트, 9~16개면 2바이트, 최대 8바이트(= 64개 멤버) 까지 쓴다.
CREATE TABLE tb_set (
  id INT PRIMARY KEY AUTO_INCREMENT,
  fd_set SET('tennis', 'soccer', 'baseball', 'golf', 'basketball')
);

INSERT INTO tb_set(fd_set) VALUES ('soccer'), ('golf,tennis');

SELECT * FROM tb_set;
idfd_set
3soccer
4tennis,golf

'golf,tennis' 로 넣었는데 'tennis,golf' 로 나온다 — 비트 순서, 즉 정의 순서대로 재정렬되기 때문이다.

SET 검색하기
  • 동등 비교를 하려면 WHERE fd_set = 'tennis,golf' 처럼 정의된 순서를 그대로 써야 한다.
  • 그 외에는 FIND_IN_SET() 이나 LIKE 를 쓸 수 있지만 인덱스를 쓸 수 없다.
SET 의 단점
  • ENUM처럼 중간에 값을 추가·수정하면 테이블 리빌드가 필요하다. 마지막 추가는 메타데이터만 바뀐다.
  • 또한 멤버 수가 8 → 9, 16 → 17 로 넘어가 필요한 바이트 수가 바뀌면 리빌드가 필요하다.

정리

  • ENUM/SET 은 문자열을 정수로 매핑해 저장한다 — 공간 절약, 가독성 손실.
  • 값 추가는 반드시 목록의 마지막에. 중간 삽입은 리빌드다.
  • ENUM 정렬은 정의 순서 기준. 사전 순 정렬은 CAST 가 필요하고 인덱스를 잃는다.
  • SET 은 최대 64개 멤버, 검색에 인덱스를 쓰기 어렵다.
15-5

TEXT, BLOB

차이는 하나뿐 — 문자 집합과 콜레이션을 갖느냐.

핵심 레코드 전체가 64KB를 넘지 않는다면 굳이 TEXT/BLOB 일 필요가 없다. 큰 값은 외부 페이지로 밀려나 조회 성능에 영향을 준다.

두 타입의 차이

  • 대량의 데이터를 저장할 때 쓰는 타입이다.
  • 차이는 문자 집합과 콜레이션을 가지느냐 뿐이다 — TEXT 는 갖고 BLOB 은 갖지 않는다.
접두어최대 길이
TINY255
(일반)65,535
MEDIUM16,777,215
LONG4,294,967,295

둘 다 남용해서는 안 된다.

사용 시 주의사항

  • 보통 길이를 예측할 수 없이 클 때 쓴다.
  • 하지만 4000바이트를 넘는다고 반드시 써야 하는 것은 아니다.
  • 레코드 전체 크기가 64KB를 넘지 않는다면 VARCHAR / VARBINARY 로도 충분하다.

인덱스 관련

  • ROW_FORMAT 에 따라 다르지만, 8.0의 기본인 DYNAMIC 에서는 인덱스 생성 시 3,072 바이트 제한이 있다.
  • 인덱스를 만들 때 컬럼값의 몇 바이트까지 인덱싱할지 명시해야 할 수도 있다.
  • utf8mb4 기준으로 768 글자 까지만 인덱스로 만들 수 있다.
  • 실제 저장값이 10MB라도 max_sort_length 에 설정된 길이까지만 정렬한다.
    • 기본값은 1,024 바이트. TEXT 컬럼 정렬을 더 빠르게 하려면 이 값을 줄이는 것도 방법이다.

데이터 크기에 따른 에러

  • max_allowed_packet 때문에 값이 큰 TEXT/BLOB이 포함된 SQL은 에러가 날 수 있다.
  • 대용량 컬럼값을 다룬다면 이 값을 늘려야 한다.

대용량 데이터의 저장 위치 — 외부 페이지

  • 가능하면 큰 컬럼도 다른 레코드와 함께 저장하려 하지만, 길이 제한 때문에 불가능할 때가 있다.
  • 5.6의 기본 포맷 COMPACT 기준, 한 레코드의 최대 길이는 16KB 페이지의 절반인 8,126 바이트 다.
  • 레코드 전체 길이가 이를 넘으면 용량이 큰 컬럼부터 외부 페이지로 옮겨 8,126 바이트에 맞춘다.
    • 이 외부 페이지를 Off-Page 또는 External Page 라고 한다.
  • 데이터는 여러 개의 외부 페이지에 나뉘어 저장되고, 각 페이지는 체인으로 연결된다.
TEXT/BLOB 을 WHERE 나 JOIN 에서 참조하면 이 체인을 전부 따라가야 한다 — 그래서 성능이 떨어진다.

기본키 페이지에 저장되는 BLOB / TEXT

ROW_FORMAT기본키 페이지에 남기는 것영향
COMPACT, REDUNDANT 외부 페이지로 옮긴 컬럼의 앞쪽 768 바이트 인덱스 생성에는 도움이 되지만 저장 효율은 떨어진다
DYNAMIC, COMPRESSED 아무것도 남기지 않는다 BLOB/TEXT를 WHERE·JOIN 에서 참조하면 쿼리 성능이 더 떨어진다

정리

  • TEXT 는 문자 집합·콜레이션을 갖고, BLOB 은 갖지 않는다. 나머지는 같다.
  • 레코드 전체가 64KB 이내라면 VARCHAR 로 충분하다.
  • 인덱스는 DYNAMIC 기준 3,072 바이트(utf8mb4 로 768자)까지.
  • 정렬은 max_sort_length(기본 1KB)까지만 한다.
  • 8.0 기본 DYNAMIC 에서는 기본키 페이지에 접두 768바이트를 남기지 않으므로, 이 컬럼을 조건절에 쓰면 비싸다.

15-7

JSON 타입

내부적으로는 BLOB 이지만, 바이너리 포맷 + 부분 업데이트 덕분에 TEXT 보다 낫다.

핵심 JSON 컬럼의 부분 업데이트가 실제로 이득이 되려면 그 테이블에 기본키가 있어야 한다 — 복제에서 레코드를 식별할 수 없으면 결국 전체를 보내야 하기 때문이다.

저장 방식

  • 내부적으로 JSON 값을 BLOB 타입에 저장한다.
  • 텍스트 그대로가 아니라 바이너리 포맷(BSON 형태) 으로 변환해 저장한다.
  • TEXT, BLOB 보다 공간 효율이 높은 편이다.
  • 16KB보다 큰 JSON은 16KB 단위로 쪼개 여러 데이터 페이지에 나눠 저장한다.
  • 8.0부터는 각 BLOB 페이지의 인덱스를 관리하고 실제 데이터 페이지로의 링크를 저장하는 방식으로 개선되었다.

부분 업데이트

  • JSON_SET(), JSON_REPLACE(), JSON_REMOVE() 로 제어할 때만 작동한다.
  • 부분 업데이트가 실제로 적용되었는지 정확히 확인할 방법은 없다.
  • 컬럼은 4GB까지 담을 수 있지만, 1MB만 저장해도 64개의 페이지로 쪼개진다.
  • 부분 업데이트를 쓰지 않으면 그 64개 페이지를 전부 다시 디스크에 기록해야 한다.
  • 변경 사항이 바이너리 로그에 기록될 때 binlog_row_value_options, binlog_row_image 를 조정하면 부분 업데이트 성능을 더 높일 수 있다.
!

가장 중요한 것은 기본키다

기본키가 없으면 레플리카 서버가 업데이트할 레코드를 식별하기 위해 모든 컬럼값을 필요로 한다. 그러면 부분 업데이트의 이점이 사라진다. JSON 컬럼을 쓰는 테이블일수록 기본키를 반드시 명시해야 한다.

콜레이션과 비교

  • 가공되어 나온 결과값은 모두 utf8mb4 + utf8mb4_bin 이다.
  • 바이너리 콜레이션이므로 대소문자와 액센트 문자까지 구분해서 비교한다.

JSON 컬럼을 선택할 때

  • 부분 업데이트 같은 부가 기능이 많으므로, JSON을 저장한다면 TEXT/BLOB 대신 JSON 타입을 권장한다.
  • 다만 정규화를 하면 애초에 JSON 필드가 필요 없어진다. 성능이 중심이라면 정규화를 권장한다.
  • 저장 공간 측면에서도 JSON은 매번 키 이름을 다 저장하므로 정규화보다 공간을 더 쓴다.

정리

  • JSON은 내부적으로 BLOB에 바이너리 포맷으로 저장된다 — TEXT보다 효율적.
  • 부분 업데이트는 JSON_SET/JSON_REPLACE/JSON_REMOVE 에서만 작동한다.
  • 그 이득을 온전히 누리려면 기본키가 반드시 있어야 한다.
  • 비교는 utf8mb4_bin — 대소문자를 구분한다.
  • 성능과 공간이 중요하다면 정규화가 JSON보다 낫다.
15-8

가상 컬럼 (파생 컬럼)

CPU를 더 쓸 것인가, 디스크를 더 쓸 것인가. 그것이 전부다.

핵심 계산이 싸고 데이터가 크면 가상 컬럼, 계산이 비싸고 데이터가 작으면 스토어드 컬럼.

두 가지 종류

  • 크게 가상 컬럼과 스토어드 컬럼으로 나뉜다.
  • 둘 다 AS 절로 계산식을 정의하며, 마지막 키워드가 STORED 면 스토어드 컬럼, 나머지는 가상 컬럼이다.
구분가상 컬럼 (VIRTUAL)스토어드 컬럼 (STORED)
디스크 저장저장되지 않음물리적으로 저장됨
구조 변경 시 리빌드불필요 (단, 인덱스가 걸린 컬럼은 필요)필요
값 계산 시점레코드를 읽기 직전, 또는 BEFORE 트리거 실행 직후INSERT / UPDATE 시점
비용읽을 때마다 CPU저장 공간 = 디스크

함수 기반 인덱스는 내부적으로 가상 컬럼을 기반으로 동작한다.

flowchart TB
  A{"계산 비용이 비싼가?"} -->|"싸다"| B{"결과 데이터가 큰가?"}
  A -->|"비싸다"| C["STORED 컬럼 - 한 번 계산해 저장"]
  B -->|"크다"| D["VIRTUAL 컬럼 - 디스크를 아낀다"]
  B -->|"작다"| E["둘 다 무방"]
결국 CPU와 디스크의 교환이다 — 어느 쪽이 더 부족한 자원인지가 결정한다.

정리

  • VIRTUAL — 저장하지 않고 읽을 때 계산. 구조 변경이 가볍다.
  • STORED — 쓸 때 계산해 저장. 구조 변경 시 리빌드가 필요하다.
  • 계산이 복잡하고 오래 걸리면 STORED, 계산이 싸고 데이터가 크면 VIRTUAL.
  • 함수 기반 인덱스는 가상 컬럼 위에서 동작한다.
