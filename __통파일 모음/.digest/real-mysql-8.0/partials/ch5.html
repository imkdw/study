5-1

트랜잭션

트랜잭션은 부분 성공을 없애는 장치다. 그래서 애플리케이션의 클렌징 코드를 없애 준다.

핵심 트랜잭션의 이득은 코드에서 온다 — 실패 시 되돌리는 코드를 내가 쓰지 않아도 된다는 것. 대신 범위를 최소로 유지해야 그 값을 치를 수 있다.

MyISAM 과 InnoDB 의 차이

구분1, 2 성공 · 3 실패일 때결과
MyISAM1, 2 는 그대로 저장됨부분 업데이트 — 정합성이 깨진다
InnoDB1, 2 도 저장되지 않음전부 롤백 — 원자성 보장
  • MyISAM에서 벌어지는 이 현상을 부분 업데이트(Partial Update) 라고 부르며, 정합성 측면에서 매우 골치 아프다.
  • InnoDB는 실패 시 전부 롤백하므로, 애플리케이션에 클렌징 코드를 따로 넣지 않아도 DB가 정리해 준다.

주의사항 — 트랜잭션의 범위

  • 커넥션과 마찬가지로 꼭 필요한 최소 구간에만 걸어야 한다.
  • 이는 곧 프로그램 코드에서 트랜잭션의 범위를 최소화하라는 뜻이다.
  • FTP 전송, 외부 API 호출 같은 무겁거나 오래 걸리는 작업을 트랜잭션 사이에 넣으면 곧바로 성능 저하로 이어진다.
문제
START TRANSACTION;
  UPDATE stock ...;
  -- 외부 결제 API 호출 (수 초)
  -- 파일 업로드
  INSERT INTO orders ...;
COMMIT;
개선
-- 외부 결제 API 호출 (트랜잭션 밖)
-- 파일 업로드 (트랜잭션 밖)

START TRANSACTION;
  UPDATE stock ...;
  INSERT INTO orders ...;
COMMIT;
i

왜 그렇게까지 보강

트랜잭션이 열려 있는 동안 그 트랜잭션이 잡은 레코드 잠금이 유지되고, 동시에 언두 로그가 삭제되지 못한다. 외부 호출 하나가 수 초 걸리면 그 수 초 동안 다른 커넥션들이 같은 레코드에서 줄을 선다. 트랜잭션 범위 최소화는 스타일 문제가 아니라 언두 로그와 잠금의 문제다.

정리

  • MyISAM은 부분 업데이트를 남기고, InnoDB는 전부 롤백한다.
  • 트랜잭션의 진짜 이득은 애플리케이션에서 복구 코드를 제거하는 것이다.
  • 네트워크·파일 작업은 트랜잭션 바깥으로. 열려 있는 동안 잠금과 언두가 함께 묶인다.
5-2

MySQL 엔진의 잠금

글로벌 · 테이블 · 네임드 · 메타데이터 — 스토리지 엔진 위쪽에도 네 종류의 잠금이 있다.

핵심 MySQL 엔진 레벨의 잠금은 스토리지 엔진과 무관하게 모든 테이블에 걸린다. 그래서 범위가 크고, 그래서 위험하다.

락은 크게 스토리지 엔진 레벨과 MySQL 엔진 레벨로 나뉜다. 이 절은 후자 — 글로벌 락, 테이블 락, 네임드 락, 메타데이터 락이다.

글로벌 락

  • MySQL이 제공하는 잠금 중 가장 범위가 크다. 범위는 MySQL 서버 전체다.
  • SELECT 를 제외한 DDL, DML 쿼리는 글로벌 락이 걸린 동안 전부 대기 상태가 된다.
  • 락을 걸기 전에 실행 중인 모든 쿼리가 완료되어야 한다 — 그래서 긴 쿼리 하나가 있으면 락 획득 자체가 오래 걸린다.
  • 모든 테이블에 영향을 주므로 웹 서비스용 DB에서는 쓰지 않는 것이 좋다.
mysql 운영 중 실행 금지 
mysql> FLUSH TABLES WITH READ LOCK;
Query OK, 0 rows affected (0.02 sec)

백업 락

  • 백업 실패를 막기 위해, DDL 명령이 실행되면 복제를 일시 중지시키는 역할을 한다.
  • 특정 세션이 백업 락을 획득하면 테이블 스키마나 사용자 인증 정보를 변경할 수 없다.
  • 글로벌 락과 달리 일반적인 DML은 계속 처리된다 — 이것이 백업 락의 존재 이유다.
mysql 백업 시 권장 
mysql> LOCK INSTANCE FOR BACKUP;
Query OK, 0 rows affected (0.00 sec)

mysql> UNLOCK INSTANCE;
Query OK, 0 rows affected (0.00 sec)

테이블 락

  • 개별 테이블 단위로 설정되는 잠금이다. 명시적으로도, 묵시적으로도 걸릴 수 있다.
  • 명시적 락은 특별한 상황이 아니면 애플리케이션에서 쓸 일이 거의 없다.
  • 묵시적 락은 쿼리가 실행되는 동안 자동으로 획득했다가 자동으로 해제된다.
    • InnoDB는 레코드 기반 잠금을 제공하므로 단순 데이터 변경으로는 테이블 락이 걸리지 않는다.
    • 대부분의 DML에서는 무시되고, 스키마를 변경하는 DDL 에만 영향을 미친다.
mysql 
mysql> LOCK TABLES test_table READ;
Query OK, 0 rows affected (0.00 sec)

mysql> UNLOCK TABLES;
Query OK, 0 rows affected (0.00 sec)

네임드 락

  • GET_LOCK() 함수로 임의의 문자열에 잠금을 설정한다.
  • 테이블이나 레코드와 아무 관계가 없다. 단순히 사용자가 지정한 문자열을 대상으로 한다.
  • 자주 쓰이진 않고, 많은 레코드에 대해 복잡한 요건을 처리하는 특정 배치 상황에서 쓰인다.
mysql 
mysql> SELECT GET_LOCK('mylock1', 10);   -- 최대 10초 대기
+-------------------------+
| GET_LOCK('mylock1', 10) |
+-------------------------+
|                       1 |
+-------------------------+

mysql> SELECT GET_LOCK('mylock2', 10);
+-------------------------+
| GET_LOCK('mylock2', 10) |
+-------------------------+
|                       1 |
+-------------------------+

mysql> SELECT RELEASE_LOCK('mylock1');
+-------------------------+
| RELEASE_LOCK('mylock1') |
+-------------------------+
|                       1 |
+-------------------------+

mysql> SELECT RELEASE_ALL_LOCKS();
+---------------------+
| RELEASE_ALL_LOCKS() |
+---------------------+
|                   1 |
+---------------------+
i

쓸모 있는 자리 보강

네임드 락은 분산 환경의 배치 중복 실행 방지에 유용하다. 여러 대의 애플리케이션 서버가 같은 배치를 돌릴 때 GET_LOCK('daily_batch', 0) 이 1을 반환한 인스턴스만 실행하면 된다. 다만 커넥션이 끊기면 잠금도 자동 해제되므로, 커넥션 풀 환경에서는 같은 커넥션을 잡고 있어야 한다는 점에 주의한다.

메타데이터 락

  • DB 객체의 이름이나 구조를 변경할 때 획득하는 잠금이다.
  • 명시적으로 획득할 수 없다. 테이블 이름을 바꾸는 등의 상황에서 자동으로 걸린다.
  • 예를 들어 배치 프로그램에서 실시간으로 테이블을 교체해야 하는 요건이 대표적인 경우다.
시간이 오래 걸리는 테이블 구조 변경 쿼리 개선하기

DDL은 단일 스레드로 작동하기 때문에 데이터가 많으면 오래 걸린다. 노트가 정리한 우회 전략은 다음과 같다.

  1. KEY_BLOCK_SIZE 로 테이블을 압축한다

    대상 테이블의 물리적 크기를 먼저 줄여 둔다.

  2. N개의 스레드로 데이터를 나눠 삽입한다

    단일 스레드 DDL이 아니라 병렬 INSERT로 대부분을 옮긴다.

  3. 남은 데이터를 MAX(id) 기준으로 마저 삽입한다

    병렬 작업 중 새로 들어온 레코드를 따라잡는다.

  4. 최종 전환

    이때 최대한 많은 데이터를 사전에 옮겨 두어야 마지막 락 구간이 짧아진다.

정리

  • 글로벌 락(FLUSH TABLES WITH READ LOCK)은 서버 전체를 멈춘다. 운영 DB에서는 금물.
  • 백업에는 글로벌 락 대신 백업 락(LOCK INSTANCE FOR BACKUP)을 쓴다.
  • InnoDB에서 테이블 락은 사실상 DDL 전용이다.
  • 네임드 락은 테이블과 무관한 애플리케이션 수준의 상호배제 도구다.
  • 메타데이터 락은 명시적으로 못 잡는다. DDL이 곧 메타데이터 락이라고 보면 된다.
5-3

InnoDB 스토리지 엔진 잠금

InnoDB는 레코드가 아니라 인덱스를 잠근다. 인덱스 설계가 곧 잠금 설계다.

핵심 변경할 레코드를 찾기 위해 스캔한 인덱스 레코드는 전부 잠긴다. 인덱스가 없으면 테이블의 모든 레코드가 잠긴다.

InnoDB 잠금의 특징

  • 스토리지 엔진 내부에서 레코드 기반 잠금 방식을 갖는다.
    • MyISAM보다 뛰어난 동시성 제어를 제공한다.
    • 잠금 정보가 상당히 작은 공간으로 관리된다.
  • 예전에는 InnoDB 락 정보에 접근하기 어려웠으나, 지금은 performance_schema 를 통한 모니터링이 가능하다.

네 가지 잠금

갭 락은 "값"이 아니라 "빈 자리"를 잠근다 — 그 구간에 새 레코드가 INSERT 되는 것을 막는다.
레코드 락
  • 레코드 자체만을 잠근다.
  • 단, InnoDB는 레코드 자체가 아니라 인덱스의 레코드를 잠근다.
갭 락
  • 레코드가 아니라 레코드와 인접한 레코드 사이의 간격만 잠근다.
  • 그 사이에 새로운 레코드가 INSERT 되는 것을 제어한다.
넥스트 키 락
  • 레코드 락과 갭 락을 합쳐 놓은 형태다.
  • 주 목적은 복제 일관성이다 — 바이너리 로그에 기록된 쿼리가 레플리카에서 실행될 때 소스 서버와 동일한 결과를 만들도록 보장한다.
자동 증가 락
  • AUTO_INCREMENT 컬럼에서 쓰이며, 테이블 수준의 잠금을 사용한다.
  • 새 레코드를 저장하는 쿼리에서만 필요하고 다른 쿼리에는 걸리지 않는다.
  • 명시적으로 획득·해제하는 방법은 없고, 대부분의 경우 성능 문제가 되지 않는다.
  • innodb_autoinc_lock_mode 로 동작 방식을 바꿀 수 있다.
값모드동작값의 연속성
0전통(traditional) 모든 INSERT가 자동 증가 락을 사용 완전 연속
1연속(consecutive) 건수를 예측할 수 있으면 락 대신 래치(뮤텍스). 예측 불가하면 여러 값을 한 번에 미리 할당 한 INSERT 문 내부는 연속. 남은 값은 누락 가능
2인터리브(interleaved) 절대 락을 쓰지 않고 래치만 사용. 여러 커넥션이 동시에 INSERT 가능 연속 보장 없음. 유일성만 보장
!

바이너리 로그 포맷과의 관계

바이너리 로그 포맷이 ROW 가 아니라 STATEMENT 라면 innodb_autoinc_lock_mode 를 1로 낮추는 것을 권장한다. 2(인터리브)에서는 값이 생성되는 순서가 확정적이지 않아 소스와 레플리카의 데이터가 달라질 수 있다.

인덱스와 잠금

  • InnoDB의 잠금은 레코드가 아니라 인덱스를 잠그는 방식으로 처리된다.
  • 변경할 레코드를 찾기 위해 검색한 인덱스의 레코드를 전부 잠근다.
  • 성능 저하를 막으려면 인덱스 설계를 잘해야 한다 — 잠금 범위는 인덱스가 결정한다.
인덱스 잠금 예시

first_name 컬럼에만 인덱스가 있는 상황이다.

mysql 
mysql> SELECT COUNT(*) FROM employees WHERE first_name='Georgi';
+----------+
| count(*) |
+----------+
|      253 |
+----------+

mysql> SELECT COUNT(*) FROM employees
    -> WHERE first_name='Georgi' AND last_name='Klassen';
+----------+
| count(*) |
+----------+
|        1 |
+----------+

mysql> UPDATE employees SET hire_date=NOW()
    -> WHERE first_name='Georgi' AND last_name='Klassen';
Query OK, 1 row affected, 1 warning (0.01 sec)
Rows matched: 1  Changed: 1  Warnings: 1
×

1건을 바꿨는데 253건이 잠긴다

Rows matched: 1 이지만, last_name 에는 인덱스가 없으므로 InnoDB는 first_name='Georgi' 로 찾은 인덱스 레코드 253건 전부를 잠근 뒤 그중 1건을 변경한다. 만약 인덱스가 하나도 없다면 테이블의 모든 레코드가 잠긴다.

레코드 수준의 잠금 확인 및 해제

  • 레코드 수준 잠금은 테이블 수준 잠금보다 확인이 복잡하다.
  • KILL 로 해당 프로세스를 죽이면 강제로 잠금을 해제할 수 있다.
잠금 시나리오
  • 3개의 커넥션이 동시에 같은 레코드를 업데이트한다고 가정한다.
  • 커넥션별로 순차 처리를 위해 각 프로세스가 그 레코드에 락을 건다.
  • SHOW PROCESSLIST 와 performance_schema 테이블(data_locks, data_lock_waits) 조회로 잠금 대기 순서를 확인할 수 있다.

정리

  • InnoDB의 잠금 단위는 인덱스 레코드다. 스캔한 만큼 잠긴다.
  • 레코드 락 + 갭 락 = 넥스트 키 락, 그 목적은 복제 일관성이다.
  • innodb_autoinc_lock_mode 2는 동시성이 좋지만 값의 연속성을 포기한다. STATEMENT 포맷이면 1로.
  • 인덱스 설계가 곧 잠금 설계 — WHERE 절 전체를 커버하는 인덱스가 잠금 범위를 줄인다.
5-4

MySQL의 격리 수준

네 단계의 격리 수준은 결국 "어느 시점의 데이터를 볼 것인가" 에 대한 네 가지 답이다.

핵심 InnoDB의 REPEATABLE READ 는 갭 락과 넥스트 키 락 덕분에 팬텀 리드까지 막는다. 이론상 표와 실제 동작이 다른 지점이다.

여러 트랜잭션이 동시에 처리될 때, 특정 트랜잭션이 다른 트랜잭션이 변경 중이거나 조회 중인 데이터를 볼 수 있게 할지 결정하는 것이 격리 수준이다.

레벨DIRTY READNON-REPEATABLE READPHANTOM READ
READ UNCOMMITTEDOOO
READ COMMITTEDXOO
REPEATABLE READXXO (InnoDB는 없음)
SERIALIZABLEXXX
  • 뒤로 갈수록 격리 수준이 높아지고 동시성은 떨어진다.
  • SERIALIZABLE 수준만 아니라면 격리 수준 자체로 인한 성능 차이는 크지 않다.
  • 일반적인 온라인 서비스는 READ COMMITTED 또는 REPEATABLE READ 를 쓴다.
  • MySQL(InnoDB)의 기본값은 REPEATABLE READ 다.

READ UNCOMMITTED

  • 커밋이나 롤백을 하지 않아도 다른 트랜잭션에서 그 변경을 볼 수 있는 수준이다.
  • 완료되지 않은 작업을 읽어 버리는 현상을 DIRTY READ 라고 한다.
  • 격리 수준이라고 인정하지 않을 정도로 정합성 문제가 많다.
  • MySQL에서는 최소한 READ COMMITTED 이상을 쓰는 것이 좋다.

READ COMMITTED

  • ORACLE의 기본 격리 수준이며, 온라인 서비스에서 가장 많이 선택된다.
  • DIRTY READ는 발생하지 않는다. 커밋이 완료된 데이터만 다른 트랜잭션에서 보인다.
  • 하지만 하나의 트랜잭션 안에서 같은 SELECT를 두 번 실행했을 때 결과가 달라질 수 있다(NON-REPEATABLE READ).
    • 트랜잭션 B가 열려 있는 동안 A가 중간에 커밋하면, B의 두 번째 SELECT 결과가 달라진다.
    • 일반적인 온라인 서비스에서는 문제가 없지만 금융 같은 분야에서는 문제가 된다.

REPEATABLE READ

  • InnoDB의 기본 격리 수준이다.
  • READ COMMITTED 에서 발생하던 NON-REPEATABLE READ 부정합이 발생하지 않는다.
  • MVCC를 위해 언두 영역에 백업된 이전 데이터를 이용해서, 동일 트랜잭션 내에서는 같은 결과를 보장한다.
언두 영역이 어떻길래 보장이 되는가
  • 언두 영역에 백업된 모든 레코드는 변경을 발생시킨 트랜잭션의 ID를 갖는다. 각 트랜잭션도 고유한 ID를 갖는다.
  • 현재 실행 중인 트랜잭션 번호보다 더 큰 번호의 언두 데이터는 삭제할 수 없다.
  • 더 정확히는, 살아 있는 트랜잭션 번호 구간 안에서 백업된 언두 데이터는 보존되어야 한다.
처리 과정
sequenceDiagram
    participant T6 as TRX 6
    participant T10 as TRX 10
    participant T12 as TRX 12
    participant U as 언두 로그
    T6->>T6: INSERT emp_no=500, name=Lara
    T10->>T10: SELECT emp_no=500 → Lara
    T12->>U: UPDATE name=Toto (이전 값 Lara 백업)
    T12->>T12: COMMIT
    T10->>U: SELECT emp_no=500 다시 실행
    U-->>T10: TRX 10 보다 작은 번호의 백업 → Lara
TRX 10 은 끝까지 Lara 를 본다 — 자기보다 나중에 커밋된 변경은 언두 로그를 거쳐 필터링된다.
그래도 부정합이 발생한다 — 팬텀 리드
  • 위 과정에서 TRX 12가 새로운 레코드를 추가한다고 가정하자.
  • 테이블과 레코드에는 락을 걸 수 있지만 언두 로그에는 락을 걸 수 없다.
  • TRX 10이 WHERE emp_no >= 500 FOR UPDATE 를 수행하면 2건이 반환된다.
    • FOR UPDATE, LOCK IN SHARE MODE 쿼리는 언두 영역을 읽지 않고 최신 레코드에 잠금을 건다.
    • 이렇게 트랜잭션의 변경 작업 때문에 데이터가 보였다 안 보였다 하는 것을 PHANTOM READ 라고 한다.

SERIALIZABLE

  • 가장 단순하면서 가장 엄격한 격리 수준이다.
  • 하나의 트랜잭션이 읽고 쓰는 레코드에는 다른 트랜잭션이 전혀 접근할 수 없다.
  • 다만 InnoDB는 갭 락과 넥스트 키 락 덕분에 REPEATABLE READ 에서도 팬텀 리드가 발생하지 않으므로, 굳이 쓸 이유가 크지 않다.

정리

  • 격리 수준은 곧 "MVCC에서 어느 버전을 볼 것인가" 의 정책이다.
  • REPEATABLE READ 의 보증은 언두 로그가 만든다. 트랜잭션 ID 비교로 필터링한다.
  • 단, FOR UPDATE / LOCK IN SHARE MODE 는 언두를 거치지 않아 팬텀 리드가 노출될 수 있다.
  • InnoDB는 갭 락·넥스트 키 락으로 일반 조회의 팬텀 리드를 막으므로 SERIALIZABLE 은 거의 불필요하다.
