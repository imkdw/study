13-1

개요

논리적으로 하나, 물리적으로 여럿. 데이터가 많다고 해서 무조건 이득은 아니다.

핵심 파티션은 워킹셋(활발히 쓰이는 데이터)의 인덱스를 메모리에 담을 수 있게 만드는 기술이다. 그것이 안 되면 파티션은 오버헤드만 남는다.

파티션이란

  • 논리적으로는 하나지만 물리적으로는 여러 개의 테이블로 분리해 관리하는 기능이다.
  • 주로 대용량 테이블을 여러 개의 소규모 테이블로 분산하는 목적으로 쓴다.

파티션을 쓰는 이유

  • 데이터가 많다고 무조건 효율적이지는 않다.
  • 인덱스 크기가 물리 메모리보다 훨씬 크거나, 데이터 특성상 자주 삭제가 필요한 경우에 유용하다.
단일 INSERT 와 단일·범위 SELECT 의 빠른 처리
  • 인덱스는 SELECT 만을 위한 것처럼 보이지만, UPDATE/DELETE 에서 대상 레코드를 찾을 때도 필수다.
  • 인덱스의 워킹셋이 물리 메모리보다 크면 쿼리 처리가 상당히 느려진다.
    • 워킹셋 = 활발하게 사용되는 데이터
  • 즉 파티션하지 않은 하나의 큰 테이블은 인덱스도 커지고, 그만큼 물리 메모리도 많이 필요해진다.
파티션의 이득은 "다뤄야 할 인덱스가 작아진다"에서 나온다 — 모든 파티션을 골고루 쓰는 워크로드에서는 이 이득이 없다.
데이터의 물리적인 저장소 분리
  • 데이터나 인덱스가 커지면 백업과 관리가 어려워진다.
  • 단, MySQL은 파티션 단위로 인덱스를 만들거나 파티션마다 다른 인덱스를 갖는 형태는 지원하지 않는다.
이력 데이터의 효율적인 관리
  • 로그 데이터는 수명이 매우 짧다. 기록되는 동시에, 일정 기간이 지나면 쓸모가 없어진다.
  • 일반 테이블에서 대용량 데이터를 DELETE 하는 것은 상당한 고부하 작업이다.
  • 파티션으로 쪼개 두면 파티션 추가·삭제만으로 간단히 관리할 수 있다.

MySQL 파티션의 내부 처리

CREATE TABLE tb_article (
  id INT NOT NULL,
  reg_date DATETIME NOT NULL,
  PRIMARY KEY(id, reg_date)
) PARTITION BY RANGE (YEAR(reg_date)) (
  PARTITION p2009 VALUES LESS THAN (2010),
  PARTITION p2010 VALUES LESS THAN (2011),
  PARTITION p2011 VALUES LESS THAN (2012),
  PARTITION p2012 VALUES LESS THAN (2013)
);
INSERT
  • 파티션 키인 reg_date 로 파티션 표현식을 평가한다.
  • 그 결과로 저장될 파티션이 결정된다. 2011-03-09 라면 p2011 에 저장된다.
UPDATE
  • WHERE 에 파티션 키가 있으면 대상 레코드를 매우 빠르게 찾는다.
  • 없으면 모든 파티션을 검색해야 한다.
  • 파티션 키가 변경되지 않으면 일반 테이블과 같이 값만 바꾼다.
  • 파티션 키가 변경되면 기존 파티션에서 삭제 → 새 파티션 결정 → 저장 순으로 처리된다.
SELECT
파티션 프루닝인덱스처리 방식평가
가능사용 필요한 파티션의 인덱스만 레인지 스캔 최선
불가사용 모든 파티션에 대해 인덱스 레인지 스캔 후 결과 병합 파티션이 많으면 성능 저하
가능불가 대상 파티션만 풀 스캔 보통
불가불가 풀 테이블 스캔 피해야 한다
파티션 테이블의 인덱스 스캔과 정렬
  • 인덱스는 파티션 단위로 생성되고, 테이블 전체를 아우르는 통합 인덱스는 없다.
  • 여러 파티션에 인덱스 스캔을 할 때는, 각 파티션에서 정렬된 순서로 읽으며 우선순위 큐에 담는다.
  • 그 큐에서 필요한 순서대로 꺼내므로 별도의 정렬 작업은 하지 않는다.
파티션 프루닝
  • 최적화 단계에서 필요한 파티션만 골라내고 나머지를 배제하는 것이다.
  • 실행 계획의 partitions 컬럼에서 접근한 파티션을 확인할 수 있다.

정리

  • 파티션의 이득은 인덱스 워킹셋 축소와 파티션 단위 삭제 두 가지에서 나온다.
  • MySQL은 파티션마다 다른 인덱스를 가질 수 없다.
  • SELECT 성능은 프루닝 가능 여부 × 인덱스 사용 여부 네 조합으로 갈린다.
  • 프루닝 결과는 실행 계획의 partitions 컬럼에서 확인한다.
13-2

주의사항

파티션 도입을 가장 자주 가로막는 제약 — 모든 유니크 인덱스가 파티션 키를 포함해야 한다.

핵심 AUTO_INCREMENT 기본키 하나로 충분하던 테이블도, 파티션을 붙이는 순간 기본키를 복합키로 바꿔야 한다.

파티션 정의 읽기

PARTITION BY RANGE(YEAR(reg_date)) 한 줄이 담고 있는 것.

  • 이 절이 있다면 그 테이블은 레인지 파티션을 쓴다는 뜻이다.
  • 파티션 컬럼은 reg_date 이며, YEAR 내장 함수로 연도만 추출해 그 연도를 기준으로 범위 분할한다.

제약사항

  • 파티션 테이블에서는 외래키를 쓸 수 없고, 임시 테이블도 쓸 수 없는 등 여러 제약이 있다.
  • 가장 큰 영향을 주는 것은 모든 유니크 인덱스에 파티션 키 컬럼이 포함되어야 한다는 제약이다.
    • 일반적으로 AUTO_INCREMENT 키 하나면 충분하지만, 파티션을 쓰려면 파티션 키와의 복합키로 만들어야 한다.
  • 파티션 표현식에는 산술 연산이나 일부 내장 함수를 쓸 수 있다. 프루닝이 실제로 잘 되는지 확인한 뒤 애플리케이션에 적용하는 것이 좋다.

파티션과 유니크 키 (기본키 포함)

종류와 무관하게 유니크 인덱스가 있다면, 파티션 키는 모든 유니크 인덱스의 일부 또는 전체 컬럼에 포함되어야 한다.

유니크 키가 파티션 키 fd1 을 포함한다 허용 
CREATE TABLE tb_partition (
  fd1 INT NOT NULL,
  fd2 INT NOT NULL,
  fd3 INT NOT NULL,
  UNIQUE KEY (fd1, fd2, fd3)
) PARTITION BY HASH(fd1)
PARTITIONS 4;
!

왜 이런 제약이 있을까

유니크 제약을 검사하려면 모든 파티션을 뒤져야 하는데, 파티션은 각자 독립된 인덱스를 갖는다. 파티션 키가 유니크 키에 포함되어 있으면 어느 파티션을 봐야 하는지 즉시 계산되므로, 그 파티션 하나만 검사하면 된다. 제약이 아니라 파티션 구조가 성립하기 위한 조건인 셈이다.

파티션과 open_files_limit

  • MySQL은 테이블을 파일 단위로 관리하므로 동시에 열린 파일 수가 많아질 수 있다.
  • 일반 테이블은 열린 파일이 2~3개지만, 파티션 테이블은 (파티션 개수 × 2~3) 이 된다.
  • 파티션을 많이 쓴다면 open_files_limit 를 적절히 높여야 한다.

정리

  • 모든 유니크 인덱스에 파티션 키를 포함해야 한다 — 기본키 설계를 바꿔야 하는 경우가 대부분이다.
  • 파티션 테이블에는 외래키를 쓸 수 없다.
  • 파티션 수만큼 파일 핸들이 늘어나므로 open_files_limit 를 함께 조정한다.
  • 파티션 표현식은 프루닝이 실제로 되는지 검증하고 적용한다.
13-3

MySQL 파티션의 종류

레인지 · 리스트 · 해시 · 키 네 가지. 그리고 재분배 비용을 줄이는 리니어 변형.

핵심 레인지·리스트 는 사람이 경계를 정하고, 해시·키 는 서버가 정한다. 그래서 앞의 둘만 파티션 단위 삭제가 가능하다.
종류분할 기준MAXVALUE파티션 단위 삭제
레인지연속된 범위가능가능
리스트값의 목록불가가능
해시사용자가 정한 표현식의 MOD불가불가
키서버가 MD5 해시 + MOD불가불가

레인지 파티션

  • 파티션 키의 연속된 범위로 파티션을 정의한다. 가장 일반적으로 쓰인다.
  • MAXVALUE 키워드로 명시되지 않은 범위를 담는 파티션을 정의할 수 있다.
용도
  • 대부분 로그 저장용 테이블에 쓴다.
  • 날짜 기반으로 데이터가 누적되고 년/월/일 단위로 분석하거나 삭제할 때
  • 범위 기반으로 나누거나 파티션 키 위주의 검색이 자주 발생할 때
CREATE TABLE range_partition_table (
  id INT NOT NULL,
  first_name VARCHAR(255),
  last_name VARCHAR(255),
  hired DATE NOT NULL DEFAULT '1970-01-01'
) PARTITION BY RANGE(YEAR(hired)) (
  PARTITION p0 VALUES LESS THAN (1991),
  PARTITION p1 VALUES LESS THAN (1996),
  PARTITION p2 VALUES LESS THAN (2001),
  PARTITION p3 VALUES LESS THAN MAXVALUE
);

MAXVALUE 가 없다면 2011년 레코드를 넣을 때 에러가 발생한다.

파티션 추가
  • MAXVALUE 파티션이 이미 있다면 단순 ADD PARTITION 이 아니라 REORGANIZE PARTITION 이 필요하다.
  • MAXVALUE 에 들어 있던 레코드를 함께 옮겨야 해서, 값이 많으면 오래 걸린다.
  • 그래서 레인지 파티션에서는 미래에 쓸 파티션을 미리 2~3개 만들어 두는 형태를 쓰기도 한다.
ALTER TABLE range_partition_table ADD PARTITION (
  PARTITION p4 VALUES LESS THAN (2011)
);
파티션 삭제
  • DROP PARTITION 을 쓴다.
  • 날짜 단위로 파티션된 테이블에서 오래된 데이터를 삭제하는 용도로 자주 쓰인다.
  • 삭제는 항상 오래된 순서대로만 가능하고, 중간 파티션은 삭제할 수 없다.
ALTER TABLE range_partition_table DROP PARTITION p0;
파티션 분리와 병합

둘 다 REORGANIZE PARTITION 을 쓰며, 재구성이 필요해 읽기 잠금(LOCK=SHARED) 이 걸린다.

분리
ALTER TABLE range_partition_table
  ALGORITHM=INPLACE, LOCK=SHARED,
  REORGANIZE PARTITION p3 INTO (
    PARTITION p3 VALUES LESS THAN (2011),
    PARTITION p4 VALUES LESS THAN MAXVALUE
  );
병합
ALTER TABLE range_partition_table
  ALGORITHM=INPLACE, LOCK=SHARED,
  REORGANIZE PARTITION p2, p3 INTO (
    PARTITION p23 VALUES LESS THAN (2011)
  );

리스트 파티션

  • 파티션 키 값 하나하나를 리스트로 나열하는 방식이다.
  • 레인지와 달리 MAXVALUE 를 쓸 수 없다.
용도
  • 파티션 키가 코드 값이나 카테고리처럼 고정적일 때
  • 키 값이 연속되지 않고 정렬 순서와 무관하게 나눠야 할 때
  • 키 값 기준으로 레코드 건수가 균일하고, 검색 조건에 파티션 키가 자주 쓰일 때
CREATE TABLE list_part_table (
  id INT NOT NULL,
  name VARCHAR(30),
  category_id INT NOT NULL
) PARTITION BY LIST(category_id) (
  PARTITION p_app    VALUES IN (3),
  PARTITION p_pc     VALUES IN (1, 9),
  PARTITION p_sports VALUES IN (2, 6, 7),
  PARTITION p_etc    VALUES IN (4, 5, 8, NULL)
);
  • 파티션 키에 NULL 도 명시할 수 있다.
  • 정수뿐 아니라 문자열도 파티션 키로 쓸 수 있다.
  • 분리·병합은 VALUES LESS THAN 대신 VALUES IN 을 쓰는 것 외에 레인지와 차이가 없다.

해시 파티션

  • MySQL이 정의한 해시 함수로 저장될 파티션을 결정한다.
    • 파티션 표현식의 결과값을 파티션 개수로 나눈 나머지로 결정한다.
  • 항상 정수 타입 컬럼이나 정수를 반환하는 표현식만 쓸 수 있다.
  • 파티션 개수가 알고리즘에 직결되므로, 추가·삭제 시 전체 레코드 재분배가 필요하다.
용도
  • 레인지나 리스트로 데이터를 균등하게 나누기 어려울 때
  • 모든 레코드의 사용 빈도가 비슷한데 테이블이 너무 커서 파티셔닝이 필요할 때
  • 대표적인 예 — 회원 테이블
CREATE TABLE hash_part_table (
  id INT NOT NULL,
  first_name VARCHAR(30),
  last_name VARCHAR(30),
  hired DATE NOT NULL DEFAULT '1970-01-01'
) PARTITION BY HASH(id) PARTITIONS 4;
분리와 병합
  • 분리·병합 시 모든 레코드의 재분배가 필요하다.
  • 파티션 개수가 바뀌는 것은 해시 함수 자체를 바꾸는 것이라 피할 수 없다.
추가 
-- 1개 추가, 이름 직접 지정
ALTER TABLE hash_part_table ALGORITHM=INPLACE, LOCK=SHARED,
  ADD PARTITION (PARTITION p5 ENGINE=InnoDB);

-- 6개를 한 번에 추가, 이름은 자동
ALTER TABLE hash_part_table ALGORITHM=INPLACE, LOCK=SHARED,
  ADD PARTITION PARTITIONS 6;
작업가능 여부
파티션 단위 삭제불가 — 서버가 키를 가공해 분산한 것이라 특정 파티션만 지울 수 없다
특정 파티션 분할불가 — 테이블 전체의 파티션 수를 늘리는 것만 가능
2개 이상을 하나로 병합불가 — 개수를 줄이는 것만 가능 (COALESCE PARTITION)
 
ALTER TABLE hash_part_table ALGORITHM=INPLACE, LOCK=SHARED,
  COALESCE PARTITION 1;

키 파티션

  • 해시 파티션은 해시 값을 계산하는 방법을 사용자가 직접 지정한다.
  • 키 파티션은 그 계산과 MOD 까지 전부 MySQL 서버가 처리한다.
  • 정수뿐 아니라 대부분의 타입을 파티션 키로 쓸 수 있다.
  • 파티션 키 값의 MD5 해시를 계산하고 MOD 해서 분배한다.
CREATE TABLE k1 (
  id INT NOT NULL,
  name VARCHAR(255),
  PRIMARY KEY(id)
) PARTITION BY KEY()
  PARTITIONS 2;

PARTITION BY KEY() 처럼 비워 두면 기본키를 자동으로 쓴다. 직접 지정할 수도 있다.

주의 및 특이사항
  • 유니크 키를 파티션 키로 쓴다면 반드시 NOT NULL 이어야 한다.
  • 해시 파티션보다 레코드를 더 균등하게 분할할 수 있어 효율이 좋다.

리니어 해시 / 리니어 키 파티션

  • 해시·키 파티션 모두 추가·통합 시 전체 재분배가 필요하다는 단점이 있다.
  • 이를 완화하려고 리니어(Linear) 알고리즘이 도입되었다.
  • 2의 승수 알고리즘을 써서 다른 파티션에 미치는 영향을 최소화한다.
flowchart LR
  subgraph N["일반 해시"]
    N1["파티션 4개 → 5개"] --> N2["전체 레코드 재분배"]
  end
  subgraph L["리니어 해시"]
    L1["파티션 3개 → 4개"] --> L2["3번 파티션만 쪼개면 끝"]
  end
리니어의 이득은 재구성 범위에 있다 — 파티션 조정이 잦은 테이블에서만 의미가 있다.
  • 파티션 추가 — 1,2,3 이 있는 상태에서 4를 추가하면 3의 데이터만 재구성되어 3과 4만 영향을 받는다.
  • 파티션 통합 — 1,2,3,4 에서 4를 제거하면 3의 데이터만 재구성하면 된다.
  • 재구성이 빈번하다면 리니어를, 거의 필요 없다면 일반 파티션을 쓰는 것이 좋다.

파티션 테이블의 쿼리 성능

  • 일부 파티션만 읽느냐 전체를 읽느냐에 따라 성능이 크게 차이 난다.
  • 불필요한 파티션을 모두 제외하고 꼭 필요한 것만 골라내야 성능이 좋다.
  • 10개 파티션을 모두 비슷하게 쓴다면 엄청난 오버헤드 만 생긴다.
  • 반드시 파티션이 정말 필요한지 고민한 뒤 적용하는 것을 권장한다.

정리

  • 레인지 — 날짜 기반 로그 테이블의 정석. MAXVALUE 와 DROP PARTITION 이 핵심.
  • 리스트 — 코드·카테고리처럼 값이 고정적일 때. MAXVALUE 없음.
  • 해시 / 키 — 균등 분산이 목적. 파티션 단위 삭제가 불가하고 개수 변경 시 전체 재분배.
  • 재구성이 잦다면 리니어 변형으로 재분배 범위를 줄인다.
  • 결국 프루닝이 되지 않는 파티션은 오버헤드일 뿐이다.
