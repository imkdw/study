9-1

개요

쿼리 실행은 세 단계다 — 파싱 · 최적화 · 데이터 가져오기. 앞의 둘은 MySQL 엔진의 몫이다.

핵심 현대 RDBMS의 옵티마이저는 비용 기반(CBO) 이다. 즉 실행 계획은 통계 정보의 함수이고, 통계가 틀리면 계획도 틀린다.

쿼리 실행 절차

  • SQL 파싱과 실행 계획 수립은 MySQL 엔진에서 처리한다.
  • 마지막 데이터를 가져오는 부분만 MySQL 엔진과 스토리지 엔진이 함께 처리한다.
  1. SQL 파싱

    요청된 SQL 문장을 쪼개서 DB 서버가 이해할 수 있는 수준으로 분리한다. 내장 SQL Parser가 담당한다.

  2. 최적화 및 실행 계획 수립

    파싱 과정에서 만들어진 트리를 기반으로 실행 계획을 만든다. 불필요한 조건 제거, 연산 단순화, 테이블 접근 순서, 인덱스 선택 등을 결정한다. 옵티마이저의 일이다.

  3. 데이터 가져오기

    수립된 계획대로 스토리지 엔진에 레코드 읽기를 요청하고, 가져온 데이터로 조인·정렬 등을 수행한다.

옵티마이저의 종류

옵티마이저는 DB 서버에서 사람의 두뇌에 해당한다. 크게 두 방식으로 나뉜다.

방식판단 근거같은 쿼리의 계획현재
규칙 기반 (RBO) 옵티마이저에 내장된 우선순위 거의 항상 동일 요즘은 거의 쓰지 않음
비용 기반 (CBO) 단위 작업 비용 + 테이블 통계 정보 데이터 분포에 따라 달라짐 대부분의 RDBMS가 채택
  • RBO — 통계 정보 없이 계획을 수립하므로 예측 가능하지만, 데이터 특성을 전혀 반영하지 못한다.
  • CBO — 각 실행 계획별로 비용을 산출하고 비용이 최소인 방식을 채택한다.
i

이 챕터를 읽는 틀 보강

CBO라는 사실 하나가 이 챕터 전체를 설명한다. 실행 계획이 이상하다면 원인은 셋 중 하나다 — ① 통계 정보가 부정확하거나, ② 비용 모델이 현실과 안 맞거나, ③ 애초에 더 나은 계획을 만들 인덱스가 없거나. 힌트는 이 셋 중 어느 것도 고치지 못하고, 그저 결과를 덮어쓸 뿐이다.

정리

  • 파싱과 최적화는 MySQL 엔진, 데이터 읽기만 스토리지 엔진과 협업.
  • MySQL은 비용 기반 옵티마이저 — 통계 정보가 계획을 만든다.
  • 계획이 마음에 안 들면 먼저 통계와 인덱스를 의심하고, 힌트는 마지막 수단이다.
9-2

기본 데이터 처리

풀 스캔 · 정렬 · 그루핑 · DISTINCT · 임시 테이블 — 옵티마이저가 쓰는 기본 도구 다섯 가지.

핵심 ORDER BY 와 GROUP BY 는 스트리밍 처리를 버퍼링 처리로 바꾼다. 인덱스로 처리되면 다시 스트리밍이 되고, 그것이 LIMIT 최적화의 전부다.

풀 테이블 스캔과 풀 인덱스 스캔

풀 테이블 스캔

인덱스를 쓰지 않고 테이블의 데이터를 처음부터 끝까지 읽는 방식이다. 다음 경우에 선택된다.

  • 레코드가 별로 없어서 인덱스보다 풀 스캔이 빠른 경우
  • WHERE, ON 절에 적절한 조건이 없는 경우
  • 레인지 스캔이 가능하지만, 옵티마이저 판단에 조건 일치 레코드가 너무 많은 경우
풀 테이블 스캔은 페이지를 하나씩 읽을까 — read ahead
  • InnoDB는 연속된 데이터 페이지가 읽히면 백그라운드 스레드가 read ahead 작업을 시작한다.
  • read ahead는 앞으로 필요할 영역을 예측해 미리 버퍼 풀에 올려 두는 작업이다.
  • 처음에는 포그라운드 스레드가 읽지만, 이후 4개 → 8개 씩 늘려 가며 읽는다.
  • 최대 64개의 데이터 페이지까지 미리 읽어 버퍼 풀에 올린다.

innodb_read_ahead_threshold 로 임계값을 조정한다. 일반적인 OLTP 서비스는 기본값으로 충분하고, 데이터 웨어하우스라면 더 낮게 잡는 것도 방법이다.

풀 인덱스 스캔
  • 쿼리에 모든 컬럼이 필요하지 않다면 풀 인덱스 스캔이 더 낫다.
  • read ahead는 동일하게 작동한다.
-- 풀 인덱스 스캔 (인덱스만 읽으면 된다)
SELECT COUNT(*) FROM tb_test;

-- 풀 테이블 스캔 (모든 컬럼이 필요하다)
SELECT * FROM tb_test;

병렬 처리

  • WHERE 조건 없이 전체 테이블을 단순 조회하는 경우에 쓸 수 있다.
  • 보유한 CPU보다 많이 설정하면 오히려 성능이 저하된다.
mysql 
mysql> SET SESSION innodb_parallel_read_threads = 1;
mysql> SELECT COUNT(*) FROM employees;   -- 1 row in set (0.08 sec)

mysql> SET SESSION innodb_parallel_read_threads = 2;
mysql> SELECT COUNT(*) FROM employees;   -- 1 row in set (0.04 sec)

mysql> SET SESSION innodb_parallel_read_threads = 4;
mysql> SELECT COUNT(*) FROM employees;   -- 1 row in set (0.05 sec)

2에서 4로 늘려도 더 빨라지지 않았다. 병렬도를 올린다고 계속 좋아지지 않는다는 것을 보여 주는 결과다.

ORDER BY 처리 (Using filesort)

레코드를 1~2건만 가져오는 쿼리가 아니라면 정렬은 거의 필수다. 정렬은 인덱스를 쓰는 방법과 Filesort 두 갈래다.

방식장점단점
인덱스 사용 이미 정렬되어 있어 읽기만 하면 된다 — 매우 빠름 데이터 수정 시 추가 작업, 디스크 공간과 버퍼 풀 메모리 소모
Filesort 인덱스를 만들지 않아도 됨. 레코드가 적으면 메모리에서 정렬되어 빠름 레코드가 많아지면 응답 속도가 급격히 느려짐
소트 버퍼
  • 정렬을 위한 별도의 메모리 공간이며, 정렬이 필요할 때만 할당된다.
  • 레코드 크기에 따라 가변적이고, sort_buffer_size 로 최댓값을 설정한다.
  • 정렬할 레코드가 버퍼보다 크면 여러 조각으로 나누는데, 이때 임시 저장을 위해 디스크 공간이 필요해진다.
Multi Merge
  • 소트 버퍼에서 정렬 → 디스크에 저장 → 반복 → 다시 저장.
  • 각 버퍼만큼 정렬된 조각들을 병합하면서 최종 정렬을 수행하는데, 이를 멀티 머지 라고 한다.
  • 이 작업은 전부 디스크 I/O를 유발한다.
버퍼 크기와 성능
  • 메모리를 아무리 많이 할당해도 성능은 비슷하다.
  • 일반적인 경우 256KB ~ 1MB 미만을 권장한다.
  • 최댓값을 너무 크게 잡아 OOM이 발생하면 OOM-Killer가 프로세스를 강제 종료한다.
    • 우선순위는 메모리를 가장 많이 쓰는 프로세스 — 즉 MySQL 자신이 죽는다.
!

원문 교정 원문 교정

노트에는 권장 크기가 "56KB ~ 1MB 미만"으로 적혀 있는데, sort_buffer_size 의 기본값이 256KB(262144) 이고 책의 권장 범위도 256KB~1MB이다. 5가 빠진 오기로 보인다.

정렬 알고리즘

소트 버퍼에 레코드 전체를 담을지, 정렬 기준 컬럼만 담을지 에 따라 싱글 패스와 투 패스로 나뉜다. 어느 쪽을 쓰는지는 옵티마이저 트레이스로 확인할 수 있다.

sort_mode담는 내용방식
<sort_key, rowid>정렬 키 + 레코드의 rowid투 패스
<sort_key, additional_fields>정렬 키 + 레코드 전체 (고정 사이즈 메모리)싱글 패스
<fixed_sort_key, packed_additional_fields>정렬 키 + 레코드 전체 (가변 사이즈 메모리)싱글 패스

싱글 패스 방식
  • 정렬 기준 컬럼을 포함해 SELECT 대상 컬럼 전부를 소트 버퍼에 담아 정렬한다.
  • 정렬에 필요 없는 컬럼도 전부 담고, 정렬 후 그대로 결과를 반환한다.
  • 일반적으로 쓰이는 방식이며, 레코드의 크기나 건수가 작을 때 빠르다.
투 패스 방식
  • 정렬 대상 컬럼과 기본키만 소트 버퍼에 담아 정렬한다.
  • 정렬된 기본키 순서대로 레코드를 다시 읽어 결과를 반환한다.
  • TEXT/BLOB 같은 큰 데이터가 있거나 레코드 크기가 클 때 사용된다.
  • 정렬 대상의 크기나 건수가 아주 클 때 효율적이다.

MySQL 8.0.20 기준 최신 반영

노트에는 투 패스 전환 기준으로 max_length_for_sort_data 가 언급되는데, 이 변수는 8.0.20에서 deprecated 되었고 더 이상 아무 효과가 없다. 옵티마이저가 짧은 BLOB도 addon field로 정렬할 수 있게 개선되면서 이 변수가 하던 유일한 역할이 사라졌다. 지금은 옵티마이저가 알아서 판단하며, 실제 사용된 방식은 위의 옵티마이저 트레이스 sort_mode 로 확인한다. (근거: MySQL 8.0 Reference Manual — ORDER BY Optimization)

  • ORDER BY 에 명시된 컬럼이 제일 먼저 읽는 테이블에 속해야 한다.
  • ORDER BY 의 순서대로 생성된 인덱스가 있어야 한다.
  • WHERE 에 첫 테이블 컬럼 조건이 있다면, 그 조건이 ORDER BY 와 같은 인덱스를 쓸 수 있어야 한다.
  • 해시 인덱스, 전문 검색 인덱스, R-Tree 에서는 사용할 수 없다.
  • 테이블이 여러 개 조인되는 경우 nested-loop 조인에서만 가능하다.
  • ORDER BY 를 적는다고 없던 작업이 생기지는 않고 실행 계획에 따라 언제든 바뀔 수 있으므로, 필요하면 반드시 명시하는 것이 좋다.
조인의 드라이빙 테이블만 정렬
  • 조인이 수행되면 레코드 수도 크기도 불어난다.
  • 따라서 조인 전에 첫 번째 테이블을 먼저 정렬하면 차선책이 된다.
  • 단, 정렬 기준이 드라이빙 테이블의 컬럼만으로 이루어져야 한다.
SELECT *
FROM employees e, salaries s
WHERE s.emp_no = e.emp_no
  AND e.emp_no BETWEEN 100002 AND 100010
ORDER BY e.last_name;

옵티마이저가 employees 를 드라이빙 테이블로 고르는 이유는 두 가지다.

  • WHERE 조건이 employees 의 기본키로 검색되므로 작업량이 크게 줄어든다.
  • 드리븐 테이블 salaries 의 조인 컬럼 emp_no 에 인덱스가 있다.

임시 테이블을 이용한 정렬

정렬 기준이 드리븐 테이블의 컬럼이라면, 조인을 먼저 해야 하므로 임시 테이블이 필요해진다.

스트리밍 처리 vs 버퍼링 처리
  • 대부분의 웹 서비스 쿼리는 ORDER BY 와 LIMIT 을 함께 쓴다.
  • LIMIT 은 결과의 일부만 가져오므로 작업량을 줄여 준다.
  • 하지만 GROUP BY, ORDER BY 는 조건을 만족하는 만큼만 가져와서는 처리할 수 없다. 전부 읽거나 그루핑을 끝낸 뒤에야 LIMIT 을 적용할 수 있다.

첫 레코드까지의 시간이 결정적으로 다르다 — OLTP에서 체감 성능은 대개 이 지점에서 갈린다.
스트리밍 처리
  • 조건에 일치하는 레코드가 검색될 때마다 즉시 클라이언트로 전송한다.
  • 클라이언트는 쿼리를 보낸 직후 첫 레코드를 받는다.
  • OLTP 환경에서는 첫 응답 시간이 매우 중요한데, 이 방식은 결과 크기와 무관하게 빠른 첫 응답을 보장한다.
  • LIMIT 이 있으면 전체 응답 시간도 줄어든다.
  • 다만 클라이언트 API마다 다르다 — JDBC는 서버 쪽은 스트리밍이지만 클라이언트가 버퍼링해서 결국 전부 기다린다. 설정으로 진짜 스트리밍으로 바꿀 수 있다.
버퍼링 처리

DB에서 일괄 가공해야 하므로 스토리지 엔진에서 모두 가져올 때까지 대기한다.

인덱스를 사용한다면?
  • 인덱스 정렬 방식에서는 LIMIT 으로 제한된 건수만큼만 읽고 바로 반환할 수 있다.
  • 인덱스를 못 쓰면 모든 연산과 정렬을 끝낸 뒤에야 반환할 수 있다.
  • 가능하면 인덱스 정렬로 유도하고, 최소한 드라이빙 테이블만 정렬하도록 만들어도 좋은 튜닝이다.

GROUP BY 처리

  • ORDER BY 와 마찬가지로 스트리밍 처리를 막는 요소다.
  • GROUP BY 절에 사용된 조건은 별도의 인덱스를 태울 수 없으므로, HAVING 조건 자체에 대한 인덱스 고민은 필요 없다.
인덱스 스캔을 사용하는 경우 (타이트 인덱스 스캔)
  • 조인의 드라이빙 테이블에 속한 컬럼만으로 그루핑하고, GROUP BY 컬럼에 이미 인덱스가 있다면, 그 인덱스를 차례대로 읽으며 그루핑한 뒤 조인을 처리한다.
  • 이 경우 실행 계획 Extra 에 아무 메시지도 나오지 않는다.
루스 인덱스 스캔을 사용하는 경우
INDEX(emp_no, from_date) 가정 
SELECT emp_no
FROM salaries s
WHERE from_date = '1985-03-01'
GROUP BY emp_no;

    인덱스를 순서대로 조회해 emp_no 의 첫 유일값 10001을 찾는다.

  2. 그 그룹 안에서 조건 검사

    emp_no = 10001 AND from_date = '1985-03-01' 과 유사한 형태로 검색한다.

  3. 다음 유일값으로 점프

    10001 처리가 끝나면 그다음 유일값 10002로 건너뛰고 반복한다.

DISTINCT 처리

  • 특정 컬럼의 유니크한 값을 조회할 때 쓴다.
  • 집합 함수와 함께 쓰이는 경우와 그렇지 않은 경우로 나뉜다.
  • 인덱스를 쓰지 못하면 임시 테이블이 필요하지만, 실행 계획에는 아무 메시지도 표시되지 않는다. 이것이 DISTINCT의 함정이다.
SELECT DISTINCT

단순히 유니크한 값만 가져오는 경우는 GROUP BY 와 동일하다.

SELECT DISTINCT emp_no FROM tb;
SELECT emp_no FROM tb GROUP BY emp_no;
주의 1 — 컬럼 하나에만 걸리는 게 아니다

아래 쿼리는 col1 만 유니크하게 가져오는 것이 아니라 col1 + col2 조합 전체가 유니크한 결과를 가져온다.

SELECT DISTINCT col1, col2 FROM tb;
주의 2 — DISTINCT 는 함수가 아니다
이렇게 써도
SELECT DISTINCT(col1), col2 FROM tb;
실제로는 이렇게 실행된다
SELECT DISTINCT col1, col2 FROM tb;

괄호는 그냥 제거된다. DISTINCT 는 SELECT 절 전체에 걸리는 키워드이지 함수가 아니다.

집합 함수와 함께 사용된 DISTINCT

이때는 집합 함수의 인자로 전달된 컬럼에 대해서만 유니크를 적용한다.

예제 1 — 임시 테이블 1개
EXPLAIN
SELECT COUNT(DISTINCT s.salary)
FROM employees e, salaries s
WHERE e.emp_no = s.emp_no
  AND e.emp_no BETWEEN 100001 AND 100100;
  • COUNT(DISTINCT ...) 처리를 위해 임시 테이블을 쓰지만 실행 계획에는 표시되지 않는다.
  • 그 임시 테이블의 salary 컬럼에 유니크 인덱스가 만들어지므로, 레코드가 많아지면 상당히 느려진다.
예제 2 — 임시 테이블 2개
EXPLAIN
SELECT COUNT(DISTINCT s.salary), COUNT(DISTINCT e.last_name)
FROM employees e, salaries s
WHERE e.emp_no = s.emp_no
  AND e.emp_no BETWEEN 100001 AND 100100;

DISTINCT 인자가 두 개면 임시 테이블도 두 개 만들어진다. 역시 실행 계획에는 나타나지 않는다.

MySQL 8.0.16 / 8.0.26 기준 최신 반영

노트에는 기록 방식을 internal_tmp_disk_storage_engine 으로 제어한다고 되어 있으나, 이 변수는 8.0.16에서 제거되었다. 8.0.16부터 디스크 내부 임시 테이블은 InnoDB 만 사용한다. 또 temptable_use_mmap 은 8.0.26에서 deprecated 되었고, 지금은 temptable_max_mmap 을 0으로 두는 것이 같은 효과를 낸다. (근거: MySQL 8.0 Reference Manual — Internal Temporary Table Use)

임시 테이블이 필요한 쿼리
  • ORDER BY 와 GROUP BY 에 명시된 컬럼이 서로 다른 쿼리
  • ORDER BY 나 GROUP BY 에 명시된 컬럼이 조인 순서상 첫 번째 테이블이 아닌 쿼리
  • DISTINCT 와 ORDER BY 가 동시에 있거나, DISTINCT 가 인덱스로 처리되지 못하는 쿼리
  • UNION 이나 UNION DISTINCT 가 사용된 쿼리 (select_type 이 UNION RESULT)
  • 실행 계획에서 select_type 이 DERIVED 인 쿼리
임시 테이블이 디스크에 생성되는 경우
  • UNION / UNION ALL 에서 SELECT 되는 컬럼 중 512바이트 이상인 컬럼이 있는 경우
  • GROUP BY 나 DISTINCT 컬럼 중 512바이트 이상인 컬럼이 있는 경우
  • 메모리 임시 테이블 크기가 tmp_table_size / max_heap_table_size(MEMORY 엔진) 또는 temptable_max_ram(TempTable 엔진) 을 초과하는 경우

정리

  • 풀 스캔은 read ahead(최대 64페이지 선반입) 덕분에 생각보다 빠르다.
  • 정렬은 인덱스 > 드라이빙 테이블만 Filesort > 임시 테이블 + Filesort 순으로 비싸다.
  • Sort_merge_passes 가 0이 아니면 소트 버퍼가 부족해 디스크를 썼다는 신호다.
  • DISTINCT 와 COUNT(DISTINCT ...) 의 임시 테이블은 실행 계획에 보이지 않는다. Created_tmp_* 로 확인한다.
  • 8.0.16+ 디스크 내부 임시 테이블은 InnoDB 단일이다.

고급 최적화

optimizer_switch 뒤에 숨은 열댓 가지 최적화 — 대부분은 켜져 있고, 알아야 실행 계획이 읽힌다.

핵심 이 절의 최적화들은 크게 두 부류다 — 불필요한 레코드 접근을 줄이는 것(ICP, MRR, 인덱스 머지)과 서브쿼리를 조인으로 바꾸는 것(세미 조인 5종, derived merge).

옵티마이저 스위치 옵션

  • optimizer_switch 시스템 변수로 제어한다.
  • 설정이 많고 대부분 활성화되어 있으나, BKA만 기본 off 다.
  • default / on / off 세 가지를 지원한다.
  • 서버 전체 · 현재 커넥션 · 현재 쿼리 세 수준에 적용할 수 있다.

MRR (Multi-Range Read) 과 BKA (Batched Key Access)

네스티드 루프 (Nested Loop)
  • 기존부터 지원하던 기본 조인 방식이다.
  • 드라이빙 테이블의 레코드를 한 건 읽고 → 드리븐 테이블에서 일치하는 레코드를 읽어 조인한다.
  • 건별로 요청이 들어오므로 스토리지 엔진 입장에서는 최적화할 여지가 없다.
MRR
  • 조인 버퍼를 활용해 즉시 조인하지 않고 조인 대상을 버퍼링한다.
  • 드라이빙 테이블 레코드를 읽어 조인 버퍼에 쌓고, 가득 차면 그때 한꺼번에 스토리지 엔진에 요청한다.
  • 필요한 레코드들을 데이터 페이지 순서대로 정렬해서 접근하므로 디스크 페이지 읽기가 최소화된다.
  • 버퍼 풀에 이미 있더라도 버퍼 풀 접근 횟수를 줄일 수 있다.
BKA
  • 기본적으로 비활성화되어 있다.
  • MRR을 응용해 실행되는 조인 방식을 BKA라고 부른다.
  • 쿼리 특성에 따라 도움이 되기도 하지만 부가적인 정렬 작업이 필요해 오히려 나빠질 수도 있다. 기본 off인 이유다.

블록 네스티드 루프 조인 (block_nested_loop)

  • 네스티드 루프에서 조인 버퍼 사용 여부와 드라이빙/드리븐 테이블의 조인 방식에 따라 구분된다.
  • 실행 계획 Extra 에 Using join buffer 가 있으면 조인 버퍼를 쓴 것이다.
조인 버퍼는 언제 쓰이나
  • 어떤 방식으로도 풀 테이블 스캔이나 풀 인덱스 스캔을 피할 수 없을 때 쓰인다.
  • 드라이빙 테이블에서 읽은 레코드를 메모리에 캐싱하고, 드리븐 테이블과 그 캐시를 조인하는 형태다.
  • 조인이 끝나면 버퍼는 즉시 해제된다.

정렬 순서가 흐트러진다

실제 드라이빙 테이블의 결과가 조인 버퍼에 저장되고, 드리븐 테이블을 읽으면서 버퍼에서 일치하는 레코드를 찾는 방식이라, 두 테이블의 역할이 사실상 뒤바뀐다. 그래서 조인 버퍼가 쓰이면 결과의 정렬 순서를 신뢰할 수 없다. 순서가 필요하면 ORDER BY 를 명시해야 한다.

Extra 에 hash join 이 왜 나올까
  • 8.0.18 부터 해시 조인 알고리즘이 도입되었다.
  • 8.0.20 부터는 블록 네스티드 루프 대신 해시 조인이 쓰인다. 그래서 Using join buffer (hash join) 로 표시된다.

  • 해당하는 레코드를 전부 MySQL 엔진에 전달해서 조건을 비교한다.
  • 일치하는 컬럼이 1건이라면 나머지는 전부 불필요한 레코드 조회였던 셈이다.

ICP 가 있다면
  • 인덱스 단계에서 최대한 필터링까지 끝내고 필요한 레코드만 읽는다.
  • 쿼리 성능이 몇 배에서 몇십 배까지 좋아질 수 있는 중요한 기능이다.
  • Extra 에 Using index condition 으로 표시된다.

인덱스 확장 (use_index_extensions)

  • 세컨더리 인덱스에 자동으로 붙은 기본키를 활용할지 결정하는 옵션이다.
  • 클러스터링 키 구조라 모든 세컨더리 인덱스는 기본키와 함께 저장된다.
  • 실행 계획의 key_len 으로 인덱스 중 어디까지 사용했는지 확인할 수 있다.

인덱스 머지 (index_merge)

  • 보통 옵티마이저는 테이블당 하나의 인덱스만 쓰는 계획을 세운다.
  • 그런데 각 조건이 서로 다른 인덱스를 쓸 수 있고, 각각의 예상 건수가 많다면 인덱스 머지를 선택한다.

AND 와 OR 의 결정적 차이

AND 는 조건 중 하나만 인덱스를 쓸 수 있어도 레인지 스캔으로 실행된다. 하지만 OR 는 둘 중 하나라도 인덱스를 못 쓰면 풀 테이블 스캔이 되어 버린다. 성능 차이가 매우 심하니 WHERE 의 OR 는 항상 의심할 것.

정렬 후 합집합 — index_merge_sort_union

  • 그래서 중간에 emp_no 기준으로 정렬한 뒤 중복을 제거한다.
  • 이때 Extra 에 Using sort_union 이 표시된다.

스킵 스캔 (skip_scan)

  • 제한적이지만 인덱스의 제약을 뛰어넘는 최적화다.
  • 보통 다중 컬럼 인덱스는 WHERE 에 선행 컬럼이 반드시 있어야 한다.
  • 스킵 스캔은 선행 컬럼 없이 후행 컬럼 조건만으로도 인덱스를 쓸 수 있게 한다.
  • 내부적으로 선행 컬럼 조건이 있는 것처럼 쿼리를 최적화한다.
  • 따라서 선행 컬럼의 유니크 값이 소수일 때만 선택된다.

해시 조인 (hash_join)

많은 사람이 네스티드 루프보다 해시 조인이 빠르다고 생각하지만 틀렸다. 무엇이 빠른가는 무엇을 재느냐에 달렸다.

  • 해시 조인은 조인 컬럼에 인덱스가 없거나, 조인 대상 중 일부의 레코드 건수가 매우 적을 때만 쓰인다.

해시 조인의 두 단계
  • 빌드 단계 (Build Phase) — 조인 대상 중 레코드가 적어 해시 테이블로 만들기 용이한 테이블(빌드 테이블)을 메모리에 올린다.
  • 프로브 단계 (Probe Phase) — 나머지 테이블(프로브 테이블)의 레코드를 읽어 해시 테이블에서 일치하는 것을 찾는다.

  • 빌드 테이블과 프로브 테이블은 동일한 개수의 청크로 쪼개져 디스크에 저장된다.

  • 메모리에서 전부 처리 가능하면 클래식 해시 조인.
  • 해시 테이블이 조인 버퍼보다 크면 그레이스 해시 조인.

  • ix_hiredate 로 BETWEEN 조건을 만족하는 레코드를 찾고, emp_no 로 정렬 (Filesort)
  • 기본키 인덱스로 먼저 읽으며 hire_date 조건을 만족하는 레코드를 고르기 (정렬 불필요)
  • WHERE 조건의 레코드가 많지 않다면 1번이 효율적이지만, 때로는 2번이 선택되기도 한다.
  • ORDER BY 용 인덱스에 너무 큰 가중치를 두지 않게 하는 것이 이 옵션이다.
EXPLAIN
SELECT * FROM employees e
WHERE hire_date BETWEEN '1985-01-01' AND '1985-02-01'
ORDER BY emp_no;

조인 최적화 알고리즘

조인 쿼리의 실행 계획을 만드는 알고리즘이 두 가지 있다.

SELECT * FROM t1, t2, t3, t4 WHERE ...
Exhaustive 검색 알고리즘
  • FROM 절의 모든 테이블 조합에 대해 최적의 하나를 찾는다.
  • 테이블이 20개라면 20!(약 2.4×1018) 가지의 조합이 생긴다.
  • 테이블이 10개만 넘어도 실행 계획을 만드는 데만 몇 분이 걸린다.
Greedy 검색 알고리즘
  • optimizer_search_depth 에 설정된 깊이만큼만 조합을 생성한다.
    • 기본값은 62 다.
    • 0으로 설정하면 옵티마이저가 알아서 최적의 깊이를 계산한다.
  • optimizer_prune_level 은 휴리스틱 알고리즘 사용 여부다.
    • 휴리스틱을 끄면 optimizer_search_depth 는 4~5가 적절하다.
    • 특별한 이유가 없으면 0으로 설정하지 않는 것을 권장한다.
  • 8.0에서는 최적화가 많이 개선되어 조인 관련 시스템 변수를 손댈 일이 사실상 없어 보인다.

정리

  • ICP 는 조건 검사를 스토리지 엔진으로 밀어내 읽는 레코드 수 자체를 줄인다. Using index condition.
  • 인덱스 머지 는 intersect(AND) / union(OR) / sort_union(정렬 필요) 세 갈래.
  • WHERE 의 OR 는 한쪽만 인덱스가 없어도 풀 스캔이 된다.
  • 세미 조인 5종 — Table Pull-out(항상 이득) · FirstMatch · LooseScan · Materialization · Duplicate Weed-out.
  • 해시 조인은 Throughput, 네스티드 루프는 Response Time. OLTP에선 후자가 옳다.
  • 8.0에서 조인 관련 옵티마이저 변수는 건드리지 않는 것이 기본이다.
9-4

쿼리 힌트

힌트는 옵티마이저와의 대화다. 인덱스 힌트보다 옵티마이저 힌트가 우선이다.

핵심 인덱스 힌트는 ANSI-SQL 문법을 깨고, 옵티마이저 힌트는 주석 안에 들어가 호환성을 지킨다. 새로 쓴다면 후자다.

두 종류의 힌트

  • 서비스 개발자나 DBA가 DB보다 나은 실행 계획을 알고 있을 때가 있다.
  • 쿼리 힌트는 옵티마이저에게 그것을 알려 주는 방법이다.
  • 인덱스 힌트와 옵티마이저 힌트 두 가지가 있다.

인덱스 힌트

  • 옵티마이저 힌트가 도입되기 전에 쓰던 기능으로, ANSI-SQL 문법을 준수하지 못한다.
  • SELECT, UPDATE 두 명령에서만 쓸 수 있다.
  • 가능하면 옵티마이저 힌트를 쓰는 것을 권장한다.

STRAIGHT_JOIN

  • 옵티마이저 힌트인 동시에 조인 키워드이기도 하다.
  • SELECT, UPDATE, DELETE 에서 여러 테이블이 조인될 때 조인 순서를 고정한다.
  • 옵티마이저는 보통 통계 정보와 조건을 보고 최적이라 판단한 순서로 조인한다.
    • 인덱스에 문제가 없다면 조건에 일치하는 레코드가 적은 테이블을 드라이빙으로 고른다.
고정하기 전
EXPLAIN
SELECT *
FROM employees e, dept_emp de, departments d
WHERE e.emp_no = de.emp_no AND d.dept_no = de.dept_no;
순서tabletypekeyrows
1dALLNULL9
2derefPRIMARY41,392
3eeq_refPRIMARY1

레코드가 가장 적은 departments(9건)가 드라이빙으로 선택됐다.

고정한 후
EXPLAIN
SELECT /*! STRAIGHT_JOIN */ *
FROM employees e, dept_emp de, departments d
WHERE e.emp_no = de.emp_no AND d.dept_no = de.dept_no;
순서tabletypekeyrowsExtra
1eALLNULL300,030
2derefix_empno_fromdate1
3dALLNULL9Using join buffer (hash join)

FROM 절에 적힌 순서(employees → dept_emp → departments)대로 조인됐다. 이 예시에서는 확실히 나빠졌다 — 힌트가 늘 이득은 아니라는 좋은 예다.

언제 쓰는 게 좋을까
상황권장 드라이빙 테이블
임시 테이블 + 일반 테이블 조인 임시 테이블. 대개 옵티마이저가 알아서 하지만, 못 하면 힌트로 고정
임시 테이블끼리 조인 임시 테이블에는 인덱스가 없으므로 레코드가 적은 쪽
일반 테이블끼리 조인 (양쪽 다 인덱스 있음 / 없음) 레코드가 적은 쪽
일반 테이블끼리 조인 (한쪽만 인덱스 있음) 조인 컬럼에 인덱스가 없는 쪽을 드라이빙으로
STRAIGHT_JOIN 과 비슷한 역할들
  • JOIN_FIXED_ORDER — STRAIGHT_JOIN 과 동일
  • JOIN_ORDER, JOIN_PREFIX, JOIN_SUFFIX — 일부 테이블의 순서만 제안

USE INDEX / FORCE INDEX / IGNORE INDEX

  • 3~4개 이상의 컬럼을 포함한 비슷한 인덱스가 여러 개 있으면 옵티마이저도 가끔 실수한다.
  • 인덱스 힌트는 그 테이블 바로 뒤에 명시한다.
  • 별도로 만들지 않은 기본키 인덱스는 PRIMARY 로 지칭한다.
  • 정확한 판단이 어렵다면 옵티마이저에게 맡기는 편이 낫다.
i

가장 훌륭한 최적화

힌트를 고민하기 전에 생각해 볼 것들 — 쿼리를 아예 없애기, 다루는 데이터를 최소화하기, 데이터 모델을 단순화하기. 힌트는 이 셋이 모두 불가능할 때의 마지막 수단이다.

힌트강도설명
USE INDEX권장 특정 인덱스를 쓰도록 권장. 채택은 하지만 항상 그 인덱스를 쓰는 것은 아니다
FORCE INDEX강함 USE INDEX 보다 영향이 크지만, 사실상 USE INDEX 만으로 충분하다. USE INDEX 로 안 되는 경우는 FORCE INDEX 로도 안 된다
IGNORE INDEX배제 특정 인덱스를 쓰지 못하게 한다. 풀 인덱스 스캔 대신 풀 테이블 스캔을 유도할 때도 쓴다 
SELECT * FROM employees USE INDEX(PRIMARY) WHERE emp_no = 1000;
SELECT * FROM employees FORCE INDEX(ix_name) WHERE emp_no = 1000;
SELECT * FROM employees IGNORE INDEX(ix_name) WHERE emp_no = 1000;

SQL_CALC_FOUND_ROWS

  • 보통 LIMIT 은 그 건수를 채우면 검색을 중단한다.
  • SQL_CALC_FOUND_ROWS 를 쓰면 중단하지 않고 끝까지 수행한다.
  • 결과가 300건이라면 랜덤 I/O가 300번 발생한다.
  • 이는 성능이 아니라 개발자의 편의를 위해 만들어진 힌트다.
  • 다만 SELECT 가 제대로 튜닝되지 않았거나 인덱스 설계가 잘못된 경우에는 오히려 빠를 수도 있다.
mysql 
mysql> SELECT SQL_CALC_FOUND_ROWS * FROM employees s LIMIT 0, 20;
20 rows in set, 1 warning (0.10 sec)

mysql> SELECT FOUND_ROWS() AS total_count;
+-------------+
| total_count |
+-------------+
|      300024 |
+-------------+

옵티마이저 힌트

종류가 매우 다양하고 영향 범위도 제각각이다.

범위설명
인덱스특정 인덱스 이름을 지정할 수 있는 힌트
테이블특정 테이블의 인덱스를 대상으로 하는 힌트
쿼리 블록힌트가 명시된 쿼리 블록에만 영향을 주는 힌트
글로벌쿼리 전체에 영향을 주는 힌트
주의점
  • 위 구분 때문에 힌트의 작성 위치가 달라지지는 않는다. 모두 /*+ ... */ 안에 쓴다.
  • 인덱스 이름 없이 테이블 이름만 쓰면 테이블 수준 힌트가 된다.
  • 모든 인덱스 수준 힌트는 반드시 테이블명이 선행되어야 한다.
  • 특정 쿼리 블록을 외부에서 지정하려면 QB_NAME() 힌트로 이름을 부여해야 한다.

MAX_EXECUTION_TIME

  • 유일하게 실행 계획에 영향을 주지 않는 힌트다. 단순히 쿼리의 최대 실행 시간(밀리초)을 설정한다.
  • 그 시간을 초과하면 쿼리는 실패한다.
mysql 
mysql> SELECT /*+ MAX_EXECUTION_TIME(1) */ *
    -> FROM employees e
    -> ORDER BY last_name DESC, emp_no ASC LIMIT 1;
ERROR 3024 (HY000): Query execution was interrupted,
maximum statement execution time exceeded

SET_VAR

  • 실행 계획을 바꾸는 것뿐 아니라 버퍼 크기를 일시적으로 늘리는 데도 쓸 수 있다.
  • 대용량 쿼리의 성능 향상 용도로 유용하다.
  • 다만 모든 시스템 변수를 조정할 수 있는 것은 아니다.
EXPLAIN
SELECT /*+ SET_VAR(optimizer_switch='index_merge_intersection=off') */ *
FROM employees e
WHERE first_name='Georgi' AND emp_no BETWEEN 10000 AND 20000;

SEMIJOIN & NO_SEMIJOIN

  • 세미 조인 최적화 전략 중 어느 것을 쓰거나 쓰지 않을지 제어한다.
  • Table Pull-out 은 대부분 성능이 좋아서 제어 옵션 자체가 없다.
!

힌트를 어디에 쓰는가

세미 조인 최적화 힌트는 외부 쿼리가 아니라 서브쿼리에 명시한다. 외부에서 지정하려면 QB_NAME() 으로 쿼리 블록에 이름부터 붙여야 한다.

서브쿼리에 직접 명시 
EXPLAIN
SELECT *
FROM departments d
WHERE d.dept_no IN (
  SELECT /*+ SEMIJOIN(MATERIALIZATION) */ de.dept_no
  FROM dept_emp de
);
쿼리 블록 이름으로 외부에서 지정 
EXPLAIN
SELECT /*+ SEMIJOIN(@subq1 MATERIALIZATION) */ *
FROM departments d
WHERE d.dept_no IN (
  SELECT /*+ QB_NAME(subq1) */ de.dept_no
  FROM dept_emp de
);
특정 전략만 배제 
EXPLAIN
SELECT *
FROM departments d
WHERE d.dept_no IN (
  SELECT /*+ NO_SEMIJOIN(MATERIALIZATION) */ de.dept_no
  FROM dept_emp de
);

구체화를 배제하니 옵티마이저는 LooseScan 을 선택했다.

SUBQUERY

  • 세미 조인 최적화를 쓸 수 없을 때 동원되는 최적화 방법을 지정한다.
  • 세미 조인 최적화는 IN (subquery) 형태에만 쓰이고 안티 세미 조인에는 쓸 수 없다.
  • 서브쿼리에 직접 힌트를 쓰거나, 쿼리 블록에 이름을 붙여 외부에서 지정할 수 있다.
  • 웬만해서는 쓰지 않는다.

BNL / NO_BNL / HASHJOIN / NO_HASHJOIN

  • 8.0.20 이후 로는 블록 네스티드 루프 조인이 더 이상 쓰이지 않는다.
  • HASHJOIN, NO_HASHJOIN 은 8.0.18 에서만 유효하다.
  • 그 이후 버전에서는 BNL, NO_BNL 로 해시 조인을 제어한다 — 이름은 BNL이지만 실제로 켜지는 것은 해시 조인이다.
  • 조인 컬럼의 인덱스가 잘 설계되어 있다면 BNL 을 줘도 그대로 인덱스 조인을 할 것이다.
EXPLAIN
SELECT /*+ BNL(e, de) */ *
FROM employees e
INNER JOIN dept_emp de ON de.emp_no = e.emp_no;

JOIN_FIXED_ORDER / JOIN_ORDER / JOIN_PREFIX / JOIN_SUFFIX

  • STRAIGHT_JOIN 은 FROM 절의 순서 자체를 조인 순서에 맞게 고쳐 써야 했다.
  • 또 일부 테이블만 고정하고 나머지는 옵티마이저에게 맡기는 것이 불가능했다.
  • 이 단점을 보완하려고 네 가지 힌트를 제공한다.
힌트효과
JOIN_FIXED_ORDER()STRAIGHT_JOIN 처럼 FROM 절 순서 그대로 조인
JOIN_ORDER(d, de)힌트에 명시된 테이블들의 순서대로 조인
JOIN_PREFIX(e, de)드라이빙(앞쪽) 테이블만 강제
JOIN_SUFFIX(e, de)드리븐(뒤쪽) 테이블만 강제
 
EXPLAIN
SELECT /*+ JOIN_PREFIX(e, de) */ *
FROM employees e
INNER JOIN dept_emp de ON de.emp_no = e.emp_no
INNER JOIN departments d ON d.dept_no = de.dept_no;

MERGE & NO_MERGE

  • 임시 테이블의 비효율을 줄이려고 서브쿼리를 외부 쿼리와 병합하는 최적화(derived_merge)가 도입되었다.
  • 때로는 옵티마이저가 잘못 판단할 수 있는데, MERGE / NO_MERGE 로 제어한다.
MERGE — 파생 테이블 제거
EXPLAIN
SELECT /*+ MERGE(sub) */ *
FROM (
  SELECT * FROM employees e
  WHERE first_name = 'Matt'
) sub LIMIT 10;
-- select_type: SIMPLE
-- table: e
NO_MERGE — 파생 테이블 유지
EXPLAIN
SELECT /*+ NO_MERGE(sub) */ *
FROM (
  SELECT * FROM employees e
  WHERE first_name = 'Matt'
) sub LIMIT 10;
-- select_type: PRIMARY / DERIVED
-- table: <derived2>

INDEX_MERGE & NO_INDEX_MERGE

하나의 테이블에 여러 인덱스를 동시에 쓰는 인덱스 머지의 사용 여부를 제어한다.

EXPLAIN
SELECT /*+ NO_INDEX_MERGE(employees PRIMARY) */ *
FROM employees e
WHERE first_name = 'Georgi'
  AND emp_no BETWEEN 10000 AND 20000;

NO_ICP

  • 대부분의 경우 인덱스 컨디션 푸시다운은 성능에 도움이 된다.
  • 비활성화가 필요할 때만 쓴다.
EXPLAIN
SELECT /*+ NO_ICP(employees ix_lastname_firstname) */ *
FROM employees e
WHERE last_name="Acton" AND first_name LIKE '%sal';

SKIP_SCAN & NO_SKIP_SCAN

  • 스킵 스캔은 선행 컬럼 조건 없이도 인덱스를 쓰게 해 주는 좋은 최적화다.
  • 하지만 선행 컬럼의 유니크 값이 많아지면 오히려 느려진다.
  • 옵티마이저가 비효율적인 상황에서 스킵 스캔을 선택하면 끌 수 있다.
EXPLAIN
SELECT /*+ NO_SKIP_SCAN(employees ix_gender_birthdate) */ *
FROM employees e
WHERE birth_date >= '1965-02-01';

INDEX & NO_INDEX

  • 기존 인덱스 힌트를 대체하는 용도의 옵티마이저 힌트다.
  • 인덱스 힌트와 달리 테이블명과 인덱스명을 함께 지정해야 한다.
EXPLAIN
SELECT /*+ INDEX(employees ix_firstname) */ *
FROM employees e
WHERE first_name = 'Matt';

정리

  • 새 코드에는 옵티마이저 힌트를 쓴다 — 주석 안에 있어 다른 DBMS에서도 무시된다.
  • STRAIGHT_JOIN 은 FROM 순서를 그대로 강제한다. 부분 고정에는 JOIN_ORDER 계열이 낫다.
  • FORCE INDEX 는 사실상 필요 없다 — USE INDEX 로 안 되면 그것도 안 된다.
  • 세미 조인 힌트는 서브쿼리 안에 쓰거나 QB_NAME() 으로 이름을 붙인다.
  • 8.0.20+ 에서 해시 조인 제어는 BNL / NO_BNL 이다.
  • 가장 좋은 최적화는 쿼리를 없애거나, 데이터를 줄이거나, 모델을 단순화하는 것이다.
