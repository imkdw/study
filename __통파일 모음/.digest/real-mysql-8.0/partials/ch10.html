통계 정보

비용 기반 옵티마이저의 입력값. 8.0에서 히스토그램이 추가되면서 인덱스 없는 컬럼도 예측 대상이 되었다.

핵심 히스토그램은 인덱스가 없는 컬럼을 위한 것이다. 인덱스가 있는 컬럼은 인덱스 다이브가 더 정확하므로 히스토그램을 쓰지 않는다.

테이블 및 인덱스 통계 정보

  • 비용 기반 최적화에서 가장 중요한 것이 통계 정보다.
  • MySQL은 다른 DBMS에 비해 통계 정보의 정확도가 높지 않고 휘발성이 강했다.
  • 그래서 실행 계획 수립 시 실제 테이블 데이터를 일부 분석해 통계를 보완한다.
MySQL 서버의 통계 정보
  • InnoDB 테이블의 통계 정보를 영구적으로 관리할 수 있게 개선되었다.
  • mysql.innodb_index_stats, mysql.innodb_table_stats 테이블에 저장된다.
  • 영구 관리가 되면서 서버를 재시작해도 기존 통계가 유지된다.
  • 자동 수집을 끄면, 점검 시간이나 사용량이 적은 시간대에 더 정확한 통계를 직접 수집할 수도 있다.
STATS_PERSISTENT
  • 테이블 단위로 영구 통계 보관 여부를 결정하는 옵션이다.
  • CREATE TABLE, ALTER TABLE 에서 쓸 수 있다.
  • 기본적으로 활성화되어 있으며, 비활성화하면 통계가 메모리에만 남는다.
CREATE TABLE test (
  id INT PRIMARY KEY,
  c1 VARCHAR(255)
) ENGINE = INNODB
  STATS_PERSISTENT = { DEFAULT | 0 | 1 };

ALTER TABLE test STATS_PERSISTENT = { DEFAULT | 0 | 1 };

히스토그램

8.0에서 도입된, 컬럼의 데이터 분포도를 참조할 수 있는 정보다.

수집과 조회
  • 컬럼 단위로 관리되고, 자동으로 수집되지 않는다. 수동으로 수집·관리해야 한다.
  • 시스템 딕셔너리에 저장되고, 서버 시작 시 information_schema.column_statistics 뷰로 로드된다.
mysql 
-- gender, hire_date 컬럼의 히스토그램 수집
ANALYZE TABLE employees UPDATE HISTOGRAM ON gender, hire_date;

-- 수집된 히스토그램 조회
SELECT * FROM information_schema.column_statistics
WHERE schema_name='realmysql' AND table_name='employees';

노트의 주의 사항 보강

노트에 적힌 대로 8.0.19 미만에서는 히스토그램 생성 시 풀 스캔으로 데이터를 읽는다. 위 예시의 sampling-rate 가 1이 아닌 것은 8.0.19 이상에서 샘플링 방식이 도입된 결과다. 운영 중인 대형 테이블에 히스토그램을 걸 계획이라면 서버 버전을 먼저 확인하는 편이 좋다.

히스토그램 삭제
  • 다른 테이블 데이터를 참조하지 않으므로 즉시 삭제된다.
  • 실행 중인 다른 쿼리에 영향을 주지는 않지만, 이후 실행 계획이 달라질 수 있으니 조심해야 한다.
ANALYZE TABLE employees DROP HISTOGRAM ON gender, hire_date;
옵티마이저에서 히스토그램 비활성화

삭제하지 않고도 실행 계획 수립에 쓰지 못하게 할 수 있다.

SET { GLOBAL | SESSION } optimizer_switch='condition_fanout_filter=off';

SELECT /*+ SET_VAR(optimizer_switch='condition_fanout_filter=off') */ ...
FROM ...
히스토그램의 용도
  • 이전에는 레코드 1,000개에 유니크 값 100개면 동등 비교 시 약 10건 일치 라고 단순 계산했다.
  • 실제 데이터는 절대 균등하지 않으므로 이런 예측은 자주 틀렸다.
  • 히스토그램은 각 범위별 레코드 건수와 유니크 값 개수를 갖고 있어 훨씬 정확한 예측이 가능하다.

인덱스 다이브

옵티마이저가 조건절에 일치하는 데이터 건수를 예측하기 위해 B-Tree를 실제로 샘플링해 확인하는 것을 인덱스 다이브라고 한다.

  • 인덱스된 컬럼을 검색 조건으로 쓰면 히스토그램이 아니라 인덱스 다이브로 얻은 정보를 쓴다.
    • 실제 검색 조건에 대해 샘플링하는 것이라 히스토그램보다 정확하기 때문이다.
  • 따라서 히스토그램은 주로 인덱스되지 않은 컬럼의 분포를 참조하는 용도로 쓰인다.

코스트 모델 (Cost Model)

  • 전체 쿼리 비용을 계산하는 데 필요한 단위 작업들의 비용을 코스트 모델이라고 한다.
  • 8.0부터는 이 비용들을 직접 커스터마이징 할 수 있다.
server_cost, engine_cost 테이블
테이블관리하는 비용
server_cost인덱스를 찾고, 레코드를 비교하고, 임시 테이블을 처리하는 비용
engine_cost레코드를 가진 데이터 페이지를 가져오는 비용
  • 공통 컬럼
    • cost_name — 각 단위 작업의 이름
    • default_value — 각 단위 작업의 기본 비용
    • cost_value — 관리자가 설정한 값. NULL 이면 기본값 사용
    • last_updated, comment — 수정 시각과 설명. 실제 동작에는 영향 없음
  • engine_cost 에만 있는 컬럼
    • engine_name — 비용이 적용되는 스토리지 엔진
    • device_type — 디스크 타입. 아직 0만 사용 가능
계산된 비용 확인

직접 계산해 보고 싶을 수 있지만 쉽지 않다 — 계산에 필요한 모든 정보가 사용자에게 노출되지 않기 때문이다. 대신 결과값은 볼 수 있다.

최적의 값?
  • 이 값들을 커스터마이징하려면 전문적인 지식이 필요하다. 없다면 건드리지 않는 것이 낫다.
  • 약 20년 동안 기본값으로도 잘 써 왔다.

정리

  • InnoDB 통계는 mysql.innodb_index_stats / innodb_table_stats 에 영구 보관된다.
  • 히스토그램은 수동 수집(ANALYZE TABLE ... UPDATE HISTOGRAM)이고, 인덱스 없는 컬럼용이다.
  • singleton(값이 적을 때) / equi-height(값이 많을 때) 두 타입, 기본 버킷 100개.
  • 인덱스가 있으면 인덱스 다이브가 우선한다 — 히스토그램은 인덱스의 대체재가 아니다.
  • 코스트 모델은 손대지 않는 것이 기본이다.
10-2

실행 계획 확인

EXPLAIN 은 계획을 보여 주고, EXPLAIN ANALYZE 는 실제로 실행해 본 결과를 보여 준다.

핵심 EXPLAIN ANALYZE 는 쿼리를 진짜로 실행한다. 그래서 계획이 나쁜 쿼리는 EXPLAIN 으로 먼저 손보고 나서 써야 한다.

실행 계획 출력 포맷

MySQL의 실행 계획은 DESC 또는 EXPLAIN 으로 확인한다. FORMAT 옵션으로 세 가지 형태를 제공한다.

EXPLAIN
query...

EXPLAIN FORMAT=JSON
query...

EXPLAIN FORMAT=TREE
query...
포맷특징
테이블 (기본)12개 컬럼의 표. 가장 익숙하고 빠르게 훑기 좋다
JSON비용 정보(cost_info) 등 가장 많은 정보를 담는다
TREE연산의 중첩 구조가 그대로 드러난다. 조인 순서를 읽기 좋다

취향에 맞게 쓰면 되고, 실행 계획의 흐름을 보여 주는 데는 큰 차이가 없다.

쿼리의 실행 시간 확인 — EXPLAIN ANALYZE

  • 8.0.18 부터 실행 계획과 단계별 소요 시간을 함께 볼 수 있는 EXPLAIN ANALYZE 가 추가되었다.
  • 항상 TREE 형식으로 보여 주므로 다른 FORMAT 은 지정할 수 없다.
  • 단순한 계획이 아니라 실제로 쿼리를 실행하고 그 정보를 보여 주는 것이라 느릴 수 있다.
    • 계획이 아주 나쁜 쿼리라면 EXPLAIN 으로 어느 정도 튜닝한 뒤에 실행하는 것이 좋다.
EXPLAIN ANALYZE
SELECT e.emp_no, AVG(s.salary)
FROM employees e
  INNER JOIN salaries s ON s.emp_no = e.emp_no
    AND s.salary > 50000
    AND s.from_date <= '1990-01-01'
    AND s.to_date > '1990-01-01'
WHERE e.first_name = 'Matt'
GROUP BY e.hire_date, e.emp_no;

            -> Filter: ((s.salary > 50000) and (s.from_date <= DATE'1990-01-01') and (s.to_date > DATE'1990-01-01'))  (cost=1.01 rows=0.522) (actual time=0.151..0.154 rows=0.206 loops=233)
                -> Index lookup on s using PRIMARY (emp_no=e.emp_no)  (cost=1.01 rows=9.41) (actual time=0.149..0.153 rows=9.53 loops=233)

이 출력에서 읽어야 할 것 보강

예측 rows=122 대 실제 rows=48 — 예측과 실제의 간격이 곧 통계 정보의 정확도다. 또 안쪽 Index lookup on s 가 loops=233 인 것에서 드라이빙 테이블 233건마다 드리븐을 한 번씩 탔다는 네스티드 루프의 구조가 그대로 보인다. 튜닝 포인트를 찾을 때는 가장 안쪽에서 loops 가 큰 단계부터 본다.

정리

  • EXPLAIN = 예측, EXPLAIN ANALYZE = 실행 후 실측 (8.0.18+, TREE 고정).
  • 포맷은 취향 — JSON 은 비용까지, TREE 는 중첩 구조까지 보여 준다.
  • ANALYZE 는 쿼리를 실제로 돌린다. 나쁜 쿼리는 먼저 EXPLAIN 으로.
  • 진단은 예측 rows 대 실제 rows 의 간격과 loops 값에서 시작한다.
10-3

실행 계획 분석

12개 컬럼 사전. 이 챕터에서 정말 봐야 할 것은 type, key, rows, Extra 네 개다.

핵심 type 은 어떻게 읽었는가, key 는 무엇으로 읽었는가, rows 는 얼마나 읽을 것 같은가, Extra 는 그 밖에 무슨 일이 있었는가 다.

실행 계획 읽는 순서

  • 각 라인은 쿼리에 사용된 테이블 개수만큼 출력된다.
  • 위에 있을수록 쿼리의 바깥 부분이거나 먼저 접근한 테이블이다.
  • 아래에 있을수록 안쪽 부분이거나 나중에 접근한 테이블이다.

id 컬럼

  • 단위 SELECT 쿼리별로 부여되는 식별자다.
  • SELECT가 하나이고 테이블 여러 개가 조인되면 id는 증가하지 않고 같은 값이 부여된다.
  • N개의 단위 SELECT로 구성되면 서로 다른 id를 갖는다.
  • id 는 테이블 접근 순서를 의미하지 않는다. 순서는 EXPLAIN ANALYZE 로 확인한다.

select_type 컬럼

각 단위 SELECT가 어떤 타입의 쿼리인지 표시한다.

SIMPLE
  • UNION 이나 서브쿼리를 쓰지 않은 단순한 쿼리다.
  • 일반적으로 제일 바깥 SELECT에 표시된다.
PRIMARY
  • UNION 이나 서브쿼리를 가진 쿼리에서 제일 바깥쪽 단위 쿼리에 표시된다.
  • 하나의 실행 계획에 PRIMARY는 하나만 존재한다.
UNION
  • UNION 으로 결합되는 단위 SELECT 중 첫 번째를 제외한 두 번째 이후에 표시된다.
  • 첫 번째 단위 SELECT는 DERIVED 로 표시되는데, 이는 UNION 결과를 모아 담는 임시 테이블을 뜻한다.
EXPLAIN
SELECT * FROM (
  (SELECT emp_no FROM employees e1 LIMIT 10) UNION ALL
  (SELECT emp_no FROM employees e2 LIMIT 10) UNION ALL
  (SELECT emp_no FROM employees e3 LIMIT 10)

SUBQUERY
  • FROM 절의 서브쿼리는 DERIVED, 그 외의 서브쿼리는 모두 SUBQUERY 로 표시된다.
  • 서브쿼리는 위치에 따라 이름이 다르다.
    • 중첩 쿼리(Nested Query) — SELECT 절에 쓰인 서브쿼리
    • 서브쿼리(Subquery) — WHERE 에 쓰인 것. 보통 그냥 서브쿼리라고 부른다
    • 파생 테이블(Derived Table) — FROM 절에 쓰인 서브쿼리
DEPENDENT SUBQUERY
  • 서브쿼리가 바깥쪽 SELECT에서 정의된 컬럼을 쓰는 경우 표시된다.
  • 외부 쿼리가 먼저 실행되고 나서야 내부가 실행되므로 일반 서브쿼리보다 느릴 때가 많다.
EXPLAIN

   FROM dept_emp de, dept_manager dm
   WHERE dm.dept_no = de.dept_no AND de.emp_no = e.emp_no) AS cnt
FROM employees e
WHERE e.first_name = 'Matt';

서브쿼리 안의 de.emp_no = e.emp_no 가 외부 employees 를 참조한다. 그래서 DEPENDENT SUBQUERY 다.

DERIVED
  • SELECT 쿼리의 실행 결과로 메모리나 디스크에 임시 테이블을 만드는 것이다.
  • 이때 만들어지는 임시 테이블을 파생 테이블이라고 한다.
  • 가능하면 DERIVED 로 표시되도록 최적화하되, 더 좋은 것은 서브쿼리를 조인으로 바꾸는 것이다.

  • DEPENDENT DERIVED 는 그 테이블이 레터럴 조인으로 쓰였다는 표시다.

type 컬럼

  • type 이후의 컬럼들은 각 테이블의 레코드를 어떤 방식으로 읽었는지를 나타낸다.
  • 실행 계획에서 반드시 체크해야 하는 정보다.
  • ALL 을 제외한 나머지는 전부 인덱스를 통한 접근 방법이다.
flowchart LR
  A["system / const"] --> B["eq_ref / ref"]
  B --> C["fulltext / ref_or_null"]
  C --> D["unique_subquery / index_subquery"]
  D --> E["range"]
  E --> F["index_merge"]
  F --> G["index"]
  G --> H["ALL"]
왼쪽이 빠르고 오른쪽이 느리다 — range 이상이면 대체로 괜찮고, index 와 ALL 은 스캔이다.
system
  • 레코드가 1건만 있거나 아예 없는 테이블을 참조하는 접근 방법이다.
  • InnoDB에는 나타나지 않고 MyISAM, MEMORY 에서만 쓰인다.
const
  • 기본키나 유니크 키로 WHERE 조건을 걸어 반드시 1건만 반환하는 쿼리의 처리 방식이다.
  • 다른 DBMS에서는 유니크 인덱스 스캔이라고도 부른다.

const 의 내부 처리 — 상수화
  • 최적화 단계에서 그 부분을 먼저 실행하고 결과를 통째로 상수화한다.
  • 옵티마이저에 의해 상수로 치환된 뒤 다음 쿼리로 전달되므로 접근 방법이 const 로 보인다.

eq_ref
  • 여러 테이블이 조인되는 실행 계획에서 표시된다.
  • 조인에서 두 번째 이후에 읽는 테이블에 반드시 1건만 존재한다는 보장이 있어야 쓸 수 있다.
ref
  • 인덱스의 종류와 무관하게 동등(Equal) 조건으로 검색할 때 쓰인다.
  • 동등 조건으로만 검색되므로 매우 빠른 방법이다.
fulltext
  • 전문 검색 문법을 쓰면 무조건 전문 검색 인덱스를 사용한다.
  • 전문 검색 인덱스는 통계 정보가 관리되지 않고, 전혀 다른 문법(MATCH ... AGAINST ...)을 요구한다.
  • 실제로는 일반 인덱스의 레인지 스캔이 더 빠른 경우가 많았다.
ref_or_null
  • ref 방식 또는 NULL 비교 접근 방법이다.
  • 많이 쓰이지는 않지만, 쓰인다고 해도 나쁘지 않은 수준이다.
EXPLAIN
SELECT * FROM titles t
WHERE to_date = '1985-03-01' OR to_date IS NULL;
unique_subquery
  • WHERE 절의 IN (subquery) 형태를 위한 접근 방법이다.
  • 서브쿼리가 중복 없는 유니크한 값만 반환할 때 쓰인다.
  • 8.0 이후에는 세미 조인 최적화가 먼저 적용되어 다른 계획이 나오는 경우가 많다.
index_subquery
  • 서브쿼리 결과의 중복을 인덱스로 제거할 수 있을 때의 방법이다.
  • unique_subquery 와 달리 중복이 있지만 인덱스로 제거할 수 있는 경우이니 헷갈리지 말자.
range
  • 인덱스 레인지 스캔을 통한 접근이다.
  • 주로 <, >, IS NULL, BETWEEN, IN, LIKE 등에서 나타난다.
  • 모든 쿼리가 이 방법만 써도 최적의 성능이 보장된다고 생각해도 좋다.
index_merge
  • 2개 이상의 인덱스로 각각 검색하고 결과를 병합하는 방식이다.
  • 이름만큼 효율적이지는 않다.
    • 여러 인덱스를 읽어야 해서 range 보다 효율이 떨어진다.
    • 전문 검색 인덱스에는 쓸 수 없다.
    • 항상 2개 이상의 집합이 생기므로 교집합·합집합·중복 제거 같은 부가 작업이 필요하다.
-- BETWEEN 조건은 기본키를 통한 레인지 접근
-- OR 의 first_name 은 ix_firstname 을 통한 접근
-- 두 결과를 병합하고 중복을 제거한다
EXPLAIN
SELECT * FROM employees e
WHERE emp_no BETWEEN 10001 AND 11000 OR first_name='smith';
-- Extra: Using union(PRIMARY,ix_firstname); Using where

  • 이름은 좋아 보이지만 인덱스 풀 스캔을 의미한다.
  • 주로 아래 상황에서 선택된다.
    • range, const, ref 를 쓸 수 없을 때
    • 인덱스에 포함된 컬럼만으로 처리 가능할 때
    • 인덱스로 정렬이나 그루핑이 가능할 때

Deleting all rows
  • WHERE 조건이 없는 DELETE 에서 자주 표시되던 것이다.
  • 이전에는 레코드를 하나씩 지웠지만, 이 기능은 한 번에 제거했음을 의미한다.
  • 현재는 더 이상 표시되지 않는다.
  • 모든 레코드를 지울 때는 DELETE 대신 TRUNCATE 를 쓰는 것을 권장한다.
Distinct

최종 결과에서 DISTINCT 를 처리하는 데 필요한 것만 조인하고, 필요한 레코드만 읽었다는 뜻이다.

EXPLAIN
SELECT DISTINCT d.dept_no
FROM departments d, dept_emp de
WHERE de.dept_no = d.dept_no;
-- de 라인의 Extra: Using index; Distinct
FirstMatch

세미 조인 최적화 중 FirstMatch 방식이 쓰였을 때 표시된다. 기준 테이블에 대해 상대 테이블에서 첫 번째 일치 1건만 찾고 그만둔다.

Full scan on NULL key
  • col1 IN (SELECT col2 FROM ...) 형태에서 col1 이 NULL 이면 서브쿼리 테이블의 풀 스캔이 필요해진다.
  • 이 메시지는 실행 도중 col1 에 NULL 이 나오면 풀 스캔을 하겠다는 예고다.
  • NULL 규칙을 무시해도 된다면 WHERE col1 IS NOT NULL 을 추가하면 된다.
  • 이 계획이 표시돼도 실제로 NULL 이 없다면 풀 스캔은 일어나지 않으니 안심해도 된다.
Impossible HAVING
  • GROUP BY ... HAVING 조건을 만족하는 레코드가 없을 때 표시된다.
  • 이 메시지가 보이면 쿼리가 잘못된 경우이니 다시 확인하는 것이 좋다.
EXPLAIN
SELECT e.emp_no, COUNT(*) AS cnt
FROM employees e
WHERE e.emp_no = 10001
GROUP BY e.emp_no
HAVING e.emp_no IS NULL;   -- 절대 만족할 수 없다
LooseScan

세미 조인 최적화 중 Loose Scan 방식이 쓰였을 때 표시된다.

No matching min/max row
  • MIN, MAX 같은 집합 함수가 있는 쿼리의 조건에 일치하는 레코드가 한 건도 없을 때 나온다.
  • 결과값으로 NULL 이 반환된다.
no matching row in const table
  • const 방식으로 접근할 때 일치하는 레코드가 없는 경우 표시된다.
  • Impossible WHERE 처럼 실행 계획을 만들 자료 자체가 없다는 의미다.
No matching rows after partition pruning
  • UPDATE, DELETE 에서 나올 수 있다.
  • 해당 파티션에 수정·삭제할 대상 레코드가 없다는 뜻이다.
No tables used

FROM 절이 없거나 DUAL 테이블을 쓰는 경우에 나온다.

Not exists
  • A에는 있지만 B에는 없는 데이터를 찾을 때 보통 NOT IN (subquery) 나 NOT EXISTS 를 쓴다.
  • 가능하면 같은 의미의 LEFT OUTER JOIN + IS NULL 형태로 처리하는 것이 좋다.
  • 이 메시지는 조인 조건에 일치하는 레코드가 여러 건이더라도 딱 1건만 확인하고 끝냈다는 뜻이다.
EXPLAIN
SELECT *
FROM dept_emp de
LEFT JOIN departments d ON de.dept_no = d.dept_no
WHERE d.dept_no IS NULL;
-- d 라인의 Extra: Using where; Not exists; Using join buffer (hash join)
Plan isn't ready yet
  • MySQL은 다른 커넥션에서 실행 중인 쿼리의 실행 계획을 확인할 수 있다 — EXPLAIN FOR CONNECTION <connection_id>.
  • 이 메시지는 그 커넥션이 아직 실행 계획을 수립하지 못한 상태라는 뜻이다.
Range checked for each record (index map: N)
  • 레코드 한 건마다 인덱스 레인지 스캔을 수행할지 판단한다는 뜻이다.
  • index map: N 은 후보 인덱스들을 비트마스크로 표현한 것이다.
    • 비트 순서는 SHOW CREATE TABLE 에 나오는 인덱스 생성 순서다.
  • type 이 ALL 인 이유는 인덱스 사용 여부를 검토해 보고, 도움이 안 되면 풀 스캔을 하겠다는 것이기 때문이다.
EXPLAIN
SELECT * FROM employees e1, employees e2
WHERE e2.emp_no > e1.emp_no;
-- e2 라인의 Extra: Range checked for each record (index map: 0x1)
index map 읽는 법

(index map: 0x19) 인 경우를 예로 들면, 0x19 를 2진수로 바꾸면 11001 이다. 아래 테이블 정의를 기준으로 1로 켜진 자리에 해당하는 인덱스가 후보다.

SHOW CREATE TABLE employees 
CREATE TABLE `employees` (
  `emp_no` int NOT NULL,
  `birth_date` date NOT NULL,
  `first_name` varchar(14) NOT NULL,
  `last_name` varchar(16) NOT NULL,
  `gender` enum('M','F') NOT NULL,
  `hire_date` date NOT NULL,
  PRIMARY KEY (`emp_no`),                                  -- 1번째
  KEY `ix_hiredate` (`hire_date`),                         -- 2번째
  KEY `ix_gender_birthdate` (`gender`,`birth_date`),       -- 3번째
  KEY `ix_firstname` (`first_name`),                       -- 4번째
  KEY `ix_gender_birthdata` (`gender`,`birth_date`),       -- 5번째
  KEY `ix_lastname_firstname` (`last_name`,`first_name`)   -- 6번째
) ENGINE=InnoDB

11001 을 오른쪽(1번째)부터 읽으면 1·4·5번째 자리가 켜져 있다 — 즉 PRIMARY, ix_firstname, ix_gender_birthdata 가 후보 인덱스다.

Recursive
  • CTE(Common Table Expression) 를 이용한 재귀 쿼리에 표시된다.
  • WITH 와 CTE를 썼다고 나오는 것이 아니라 실제로 재귀인 경우만 표시된다.
EXPLAIN
WITH RECURSIVE cte (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM cte WHERE n < 5
)
SELECT * FROM cte;
-- cte 라인의 Extra: Recursive; Using where
Rematerialize
  • 레터럴 조인에서는 선행 테이블의 레코드마다 서브쿼리를 실행해 임시 테이블에 저장한다.
  • 즉 매번 임시 테이블이 새로 만들어지는 경우에 표시된다.
Select tables optimized away
  • MIN, MAX 만 SELECT에 쓰인 경우
  • GROUP BY 로 MIN, MAX 를 조회하는 쿼리가 인덱스를 오름/내림차순으로 1건만 읽는 형태로 최적화된 경우
Start temporary, End temporary
  • 세미 조인 최적화 중 Duplicate Weed-out 전략이 쓰였을 때 표시된다.
  • 중복 제거를 위해 내부 임시 테이블을 쓰는데, 그 구간을 식별할 수 있게 표시해 준다.
unique row not found

두 테이블이 각각 유니크 컬럼(기본키 포함)으로 아우터 조인을 수행하는 쿼리에서, 아우터 테이블에 일치하는 레코드가 없을 때 표시된다.

Using filesort
  • ORDER BY 를 인덱스로 처리할 수 없어 소트 버퍼에서 CPU 연산으로 처리했다는 뜻이다.
  • 가능하면 인덱스로 처리되도록 쿼리 튜닝이나 인덱스 생성을 권장한다.
Using index (커버링 인덱스)
  • 레코드를 전혀 읽지 않고 인덱스만으로 쿼리를 처리한 경우다.
  • 다만 특정 상황에서는 풀 스캔이 더 효율적인 경우도 있다.
  • InnoDB는 클러스터링 인덱스 특성 덕분에 커버링 인덱스로 처리되는 경우가 많다.
  • type 컬럼의 index 와는 완전히 다른 것이니 주의해야 한다.
!

헷갈리기 쉬운 두 가지

type = index 는 인덱스 풀 스캔(느림). Extra = Using index 는 커버링 인덱스(빠름). 이름은 비슷한데 의미는 정반대에 가깝다.

Using index condition
  • 인덱스 컨디션 푸시다운 최적화가 적용된 경우다.
  • 인덱스로 읽을 범위를 먼저 좁히고, 그다음 스토리지 엔진에서 레코드를 읽는다.
Using index for group-by
  • GROUP BY 가 인덱스를 이용해 처리될 때 표시된다 — 즉 루스 인덱스 스캔인 경우다.
  • 타이트 인덱스 스캔인 경우
    • SUM, AVG 처럼 모든 인덱스를 다 읽어야 하는 경우로, 루스 스캔이 아니므로 표시되지 않는다.
  • 루스 인덱스 스캔인 경우
    • 그루핑 컬럼 외에는 아무것도 조회하지 않는 쿼리에서 쓸 수 있다.
    • MIN, MAX 처럼 인덱스의 처음이나 끝만 읽으면 되는 경우에도 가능하다.
    • 단, WHERE 조건에 따라 인덱스 사용 여부가 달라질 수 있다.
Using index for skip scan
  • 인덱스 스킵 스캔 최적화가 쓰인 경우다.
  • 루스 인덱스 스캔을 확장한 기능이며 아직 부족한 부분이 많지만, 알아 두면 좋다.
Using join buffer (<JOIN_ALGORITHM>)

조인 버퍼가 사용된 경우에 표시된다. 8.0.20 이후에는 대개 (hash join) 이 붙는다.

Using MRR

스토리지 엔진 레벨의 최적화인 Multi-Range Read 가 사용된 경우다.

Using sort_union, Using union, Using intersect

인덱스 머지를 쓸 때 두 인덱스의 결과를 어떻게 병합했는지 알려 준다. (→ 9-3 인덱스 머지)

Using temporary
  • 임시 테이블을 사용했다는 뜻이다.
  • 대표적으로 GROUP BY 에서 인덱스를 쓰지 못할 때 표시된다.
Using where
  • MySQL 엔진 레이어에서 별도의 필터링 작업을 처리한 경우다.
  • 작업 범위 결정 조건은 스토리지 엔진에서 처리되지만, 체크 조건은 MySQL 엔진에서 처리된다.
Zero Limit
  • 때로는 실제 레코드가 아니라 결과의 메타데이터만 필요한 경우가 있다 (LIMIT 0).
  • 레코드를 전혀 읽지 않고 메타데이터만 반환할 때 표시된다.

정리

  • 실행 계획은 위에서 아래로 읽되, id 는 접근 순서가 아니다.
  • 가장 먼저 볼 것 — type(접근 방법), key(선택된 인덱스), rows(예상 건수), Extra(그 밖의 사정).
  • type 은 const → eq_ref → ref → range → index → ALL 순으로 나빠진다. range 이상이면 대체로 합격.
  • type=index(인덱스 풀 스캔)와 Extra=Using index(커버링 인덱스)를 혼동하지 말 것.
  • key_len 은 복합 인덱스를 어디까지 썼는지 알려 주는 유일한 단서다.
  • filtered 는 남는 비율이다. 이 예측이 정확할수록 조인 순서가 좋아진다.
