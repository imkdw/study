16-1

개요

복제는 스케일 아웃이자 백업 전략이자 가용성 확보다. 목적에 따라 구성이 달라진다.

핵심 복제의 본질은 하나의 서버에서 다른 서버로 데이터를 동기화하는 것이고, 그 위에 쌓이는 목적이 네 가지다.

왜 복제인가

  • 대용량 트래픽을 안정적으로 처리하려면 DB 서버 확장이 필수다.
  • 언제든 안정적으로 서비스하려면 가용성이 필요한데, 그때 쓰는 기술이 복제(Replication)다.
  • 복제는 한 서버에서 다른 서버로 데이터가 동기화되는 것을 말한다.
  • 소스 서버 — 원본 데이터를 가진 서버. 레플리카 서버 — 소스에서 복제한 데이터를 가진 서버.
  • 보통 소스 1대 + 레플리카 1대 이상으로 구성한다.

복제의 네 가지 목적

목적내용
스케일 아웃 트래픽이 몰릴 때 부하를 분산한다. 스케일 업은 한 서버가 처리할 수 있는 양에 한계가 있다
데이터 백업 백업 프로그램은 같은 서버의 자원을 나눠 쓰므로 쿼리 성능에 영향을 준다. 레플리카에서 백업해 메인 서버의 부하를 최소화한다
데이터 분석 분석 쿼리는 많은 데이터를 읽어 매우 무겁다. 레플리카에서 실행해 서비스에 영향이 없게 한다
지리적 분산 애플리케이션과 DB는 가까울수록 좋다. 메인 서버 이관이 어렵다면 레플리카를 인근에 배치해 해결할 수 있다

정리

  • 복제 = 소스 → 레플리카 데이터 동기화.
  • 목적은 읽기 확장 · 백업 · 분석 · 지리적 분산 네 가지.
  • 어떤 목적이냐에 따라 토폴로지와 동기화 방식의 선택이 달라진다.
16-2

복제 아키텍처

복제는 3개의 스레드가 만든다 — 소스에 1개, 레플리카에 2개.

핵심 I/O 스레드(가져오기) 와 SQL 스레드(적용하기) 는 서로 독립적으로 동작한다. 그래서 "받았는데 아직 적용 안 됨" 상태가 존재한다.

기본 구조

  • MySQL의 복제는 바이너리 로그를 기반으로 한다.
  • 소스에서 바이너리 로그를 만들면 레플리카가 그것을 읽어 동기화한다.
  • 레플리카가 읽어와 로컬 디스크에 저장해 둔 파일을 릴레이 로그 라고 한다.
  • 복제는 총 3개의 스레드가 담당한다 — 소스에 1개, 레플리카에 2개.

릴레이 로그가 두 스레드를 분리한다 — 네트워크가 느려도 SQL 스레드는 계속 일할 수 있고, 반대도 마찬가지다.

복제에서 사용하는 스레드

레플리카의 두 스레드는 서로 독립적으로 동작한다.

바이너리 로그 덤프 스레드 (Binary Log Dump Thread)
  • 소스 서버에서, 레플리카가 연결될 때 내부적으로 생성되어 바이너리 로그를 전송한다.
  • 각 이벤트를 읽을 때 일시적으로 바이너리 로그에 잠금이 필요하고, 끝나면 해제한다.
  • SHOW PROCESSLIST 로 확인할 수 있다.
레플리케이션 I/O 스레드
  • 소스에서 바이너리 로그를 읽어와 릴레이 로그로 저장하는 역할이다.
  • 복제가 시작되면 생성되고, 멈추면 종료된다.
  • SHOW REPLICA STATUS 의 Replica_IO_Running 으로 확인한다.
레플리케이션 SQL 스레드
  • I/O 스레드가 저장한 릴레이 로그를 읽어 이벤트를 실행한다.
  • SHOW REPLICA STATUS 의 Replica_SQL_Running 으로 확인한다.
!

원문 교정 원문 교정

노트에는 SQL 스레드의 상태도 Replica_IO_Running 컬럼으로 확인한다고 적혀 있으나, SQL 스레드는 Replica_SQL_Running 컬럼이다. 두 스레드가 독립적으로 동작하므로 상태 컬럼도 따로 존재한다 — 실제로 I/O는 Yes 인데 SQL만 No 인 장애가 흔하다. (근거: MySQL 8.0 Reference Manual — SHOW REPLICA STATUS)

복제에서 생성되는 데이터

데이터내용저장 위치
릴레이 로그 소스의 바이너리 로그에서 읽어온 이벤트(트랜잭션) 정보. 인덱스 파일 + 실제 로그 파일로 구성 레플리카의 로컬 디스크
커넥션 메타데이터 소스 연결에 쓰인 DB 계정, 바이너리 로그 파일명 등 mysql.slave_master_info
어플라이어 메타데이터 최근 적용된 이벤트와 그 이벤트가 담긴 릴레이 로그 파일명 등. SQL 스레드가 이 정보로 나머지를 이어서 적용한다 mysql.slave_relay_log_info

정리

  • 스레드 3개 — 소스의 덤프, 레플리카의 I/O 와 SQL.
  • 둘 사이에 릴레이 로그가 있어 네트워크 지연과 적용 지연이 분리된다.
  • 상태 확인은 Replica_IO_Running(가져오기)과 Replica_SQL_Running(적용) 둘 다 봐야 한다.
  • 포지션 정보는 mysql.slave_master_info / mysql.slave_relay_log_info 테이블에 남는다.
16-3

복제 타입

파일명+위치 기반이냐 GTID 기반이냐. 장애 복구의 난이도가 여기서 갈린다.

핵심 바이너리 로그 위치는 그 서버에서만 유효한 식별자다. GTID는 복제 그룹 전체에서 유일하다. 토폴로지 변경의 난이도가 여기서 결정된다.

바이너리 로그 파일 위치 기반 복제

  • 복제 기능이 처음 도입될 때부터 제공된 방식이다.
  • 소스의 바이너리 로그 파일명 + 파일 내 위치로 각 이벤트를 식별한다.
  • 복제에 참여하는 모든 서버는 고유한 server_id 를 가져야 한다.
  • 기록된 이벤트의 server_id 가 자신과 같으면 적용하지 않고 무시한다 (무한 루프 방지).

복제 구축 — 바이너리 로그 위치 기반

1. 설정 준비
  • 소스에서 바이너리 로그가 활성화되어 있어야 한다.
  • 각 서버가 고유한 server_id 를 가져야 한다.
  • 생성된 릴레이 로그는 자동 삭제된다. 유지하려면 relay_log_purge 를 수정해야 한다.
    • 자동 삭제를 끄면 저장 공간 모니터링이 필요하다.
my.cnf 
# 소스 서버
[mysqld]
server_id=1

# 레플리카 서버
[mysqld]
server_id=2
2. 복제 계정 준비
  • 레플리카가 소스로 접속하기 위한 계정이다.
  • 계정 정보가 커넥션 메타데이터에 평문으로 저장되므로, 권한을 최소화한 전용 계정을 쓰는 것을 권장한다.
  • 필요한 권한은 REPLICATION SLAVE 하나다.
  • 아래 예시는 % 지만, 실무에서는 특정 IP 대역으로 좁히는 것이 좋다.
소스 서버 
CREATE USER 'repl_user'@'%' IDENTIFIED BY '1234';
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';
3. 데이터 복사
  • 별도의 백업이나 mysqldump 를 쓴다.
  • mysqldump 를 쓸 때는 반드시 두 옵션을 써야 한다.
    • --single-transaction — 하나의 트랜잭션으로 덤프해 테이블·레코드 잠금을 걸지 않게 한다.
    • --master-data — 소스의 바이너리 로그 파일명과 위치를 함께 기록한다.
      • MySQL 8.0 기준 --source-data 로 대체되었고 구 옵션은 deprecated 예정이다.
      • 1 — 덤프 파일에 복제 설정 구문이 실행 가능한 형태로 기록된다.
      • 2 — 그 구문이 주석 처리되어 참조만 할 수 있다.
      • 이 옵션은 바이너리 로그 위치를 순간적으로 고정하기 위해 글로벌 락을 건다.
terminal 
$ mysqldump -u root -p1234 \
    --single-transaction --source-data=2 \
    --opt --routines --triggers --hex-blob \
    --all-databases > source_data.sql
레플리카 서버 
mysql> SOURCE source_data.sql;
4. 복제 시작
  • CHANGE REPLICATION SOURCE TO (구: CHANGE MASTER TO) 로 설정한다.
  • SSL을 쓰지 않는다면 GET_SOURCE_PUBLIC_KEY=1 옵션이 필요하다.
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='172.17.0.3',
  SOURCE_PORT=3306,
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='1234',
  SOURCE_LOG_FILE='binlog.000003',
  SOURCE_LOG_POS=691,
  GET_SOURCE_PUBLIC_KEY=1;
5. 진행 상황 확인
  • START REPLICA 로 복제를 시작한다.
  • SHOW REPLICA STATUS 로 진행 상황을 확인한다.
  • Seconds_Behind_Source 가 0이 되면 동기화가 끝난 것이다.
mysql> SHOW REPLICA STATUS \G
             Replica_IO_State: Waiting for source to send event
                  Source_Host: 172.17.0.3
              Source_Log_File: binlog.000003
          Read_Source_Log_Pos: 691
               Relay_Log_File: 919a2516f4cd-relay-bin.000002
                Relay_Log_Pos: 323
           Replica_IO_Running: Yes
          Replica_SQL_Running: Yes
        Seconds_Behind_Source: 0

트랜잭션 스킵하기 (위치 기반)

  • 레플리카가 소스에게 받은 트랜잭션을 실행하지 못해 복제가 멈추는 일이 있다.
  • 대부분 사용자 실수 때문이고, 대표적인 것이 중복 키 에러 다.
  • sql_slave_skip_counter 로 문제 트랜잭션을 건너뛸 수 있다.
    • DML이 트랜잭션 없이 개별 실행되었다면 1 로 그 쿼리 하나가 무시된다.
    • 하지만 여러 DML이 하나의 트랜잭션에 묶여 있다면 그 전체가 무시된다.
    • 즉 뒤의 숫자는 이벤트(트랜잭션) 개수 라고 생각하고 신중히 써야 한다.
데이터가 사라질 수 있다 
STOP REPLICA SQL_THREAD;
SET GLOBAL sql_slave_skip_counter=1;
START REPLICA SQL_THREAD;

GTID 기반 복제

  • 바이너리 로그 위치 기반의 단점을 해결한 방식이다.
  • 기존 방식의 식별자(파일명 + 위치)는 그 바이너리 로그를 가진 소스 서버에서만 유효하다.
  • 같은 이벤트가 레플리카에서 같은 파일명·같은 위치에 저장된다는 보장이 없어, 동일한 이벤트에 서로 다른 식별자가 붙는다.
  • 서로 호환되지 않는 정보로는 토폴로지 변경이 어렵고, 그것은 곧 장애 복구가 어렵다는 뜻이다.
  • GTID는 각 이벤트에 복제 그룹 전체에서 유일한 식별자를 부여한다.
GTID 가 필요한 이유 — 시나리오

A(소스), B/C(레플리카)가 있는 상황에서, C가 아직 최신 지점까지 동기화되지 않은 상태로 B가 소스로 승격했다고 하자.

방식C 서버의 상황
바이너리 로그 위치 기반 C는 아직 동기화가 안 되어 B의 요청을 수행할 수 없다. 동기화하려 해도 A가 죽어 버려서 불가능하다. B의 릴레이 로그를 읽어 시도할 수는 있지만 자동 삭제되고, 있어도 쉽지 않다
GTID 기반 파일명도 위치도 필요 없다. GTID 정보만 있으면 B의 바이너리 로그에서 특정 GTID 이후부터 동기화하면 된다

장애 복구 외에도 GTID는 데이터 동기화 등 여러 문제를 함께 해결한다.

GTID 란
  • 커밋된 각 트랜잭션과 연결된 고유 식별자 다. 커밋되어 바이너리 로그에 저장된 트랜잭션에만 할당된다.
  • 소스 아이디 + 트랜잭션 아이디 조합으로 생성되며, 소스 아이디로는 server_uuid 를 쓴다.
  • server_uuid 는 직접 지정하는 것이 아니라 서버 시작 시 auto.cnf 파일에 생성된다.
  • mysql.gtid_executed 테이블 등에서 확인할 수 있다.

GTID 기반 복제 구축

  • GTID 활성화와 GTID 기반 복제 사용은 별개다. 활성화는 조건일 뿐이다.
  • 전제 — 소스와 레플리카 모두 GTID가 활성화되어야 한다.
  • enforce_gtid_consistency 를 반드시 켜야 한다.
  • read_only, super_read_only 는 레플리카에서 DDL/DML 실행 시 에러를 내 준다.
    • 레플리카에서 변경이 일어나면 레플리카의 uuid로 새 GTID가 추가되어 소스와 GTID 셋이 달라지고, 역할 전환 시 문제가 된다.
my.cnf 
# 소스 서버
[mysqld]
server_id=1
gtid_mode=ON
enforce_gtid_consistency=ON

# 레플리카 서버
[mysqld]
server_id=2
gtid_mode=ON
enforce_gtid_consistency=ON
super_read_only
데이터 복사
변수의미
gtid_executed바이너리 로그에 기록된 모든 GTID 셋
gtid_purged바이너리 로그에 기록되지 않은 모든 트랜잭션의 GTID 셋
 
$ mysqldump -u root -p1234 -h 172.17.0.3 \
    --single-transaction --source-data=2 --set-gtid-purged=ON \
    --opt --routines --triggers --hex-blob \
    --all-databases > source_data.sql
복제 시작
  • 위치 기반과의 차이는 LOG_FILE, LOG_POS 대신 SOURCE_AUTO_POSITION 을 쓴다는 점이다.
  • 이 값으로 gtid_executed 를 참조해 그 시점부터 알아서 동기화한다.
mysql> SHOW REPLICA STATUS \G
             Replica_IO_State: Waiting for source to send event
                  Source_Host: 172.17.0.3
              Source_Log_File: binlog.000005
           Replica_IO_Running: Yes
          Replica_SQL_Running: Yes
            Executed_Gtid_Set: 21afb5a7-8223-11ef-a35d-0242ac110003:1-2
                Auto_Position: 1

트랜잭션 스킵하기 (GTID 기반)

  • sql_slave_skip_counter 는 GTID 기반에서 쓸 수 없다.
  • 대신 그 GTID로 빈 트랜잭션을 수동 생성해 "이미 실행했다"고 표시하면 건너뛴다.
GTID 스킵 절차 
-- 복제 중단
STOP REPLICA;

-- 에러가 발생한 트랜잭션의 GTID 로 설정
SET gtid_next='21afb5a7-8223-11ef-a35d-0242ac110003:3';

-- 빈 트랜잭션 생성 (그 GTID 를 소비한다)
BEGIN; COMMIT;

-- 변수값을 자동으로 되돌린다
SET gtid_next='automatic';

-- 복제 재개
START REPLICA;

Non-GTID → GTID 기반으로 온라인 전환

8.0부터 서비스 중단 없이 전환할 수 있다. 두 개의 변수를 단계적으로 바꾸면 된다.

enforce_gtid_consistency
  • GTID 복제에서 소스-레플리카 간 일관성을 해칠 수 있는 쿼리의 실행 여부를 제한한다.
  • 트랜잭션 지원/미지원 테이블을 함께 변경하는 쿼리, CREATE TABLE ... SELECT 등이 해당한다.
  • 공통점은 단일 트랜잭션으로 처리되지 않을 수 있다는 것이다. GTID는 트랜잭션 단위로 올바르게 할당되어야 복제가 정상 동작한다.
값설명

ON그런 쿼리를 차단
WARN허용하되 경고 메시지를 남긴다
gtid_mode
  • 바이너리 로그의 트랜잭션이 GTID 기반으로 기록될 수 있는지, 그리고 유형별로 처리 가능한지를 제어한다.
  • 트랜잭션 유형은 두 가지다.
    • 익명 — GTID가 없는 트랜잭션. 파일명과 위치로 식별한다.
    • GTID — GTID가 부여된 트랜잭션.

전환 절차
  1. 모든 서버에서 enforce_gtid_consistency = WARN

    변경 후 일정 시간 모니터링하며 경고 로그가 나오는지 본다. 경고가 있으면 애플리케이션을 수정하고, 더 이상 경고가 없을 때만 다음으로 넘어간다.

  2. 모든 서버에서 enforce_gtid_consistency = ON

    GTID로 안전하게 복제되는 쿼리만 실행되도록 한다. 반드시 켜야 한다.

  3. 모든 서버에서 gtid_mode = OFF_PERMISSIVE

    소스는 여전히 익명으로 기록하지만, 레플리카는 익명과 GTID를 모두 처리할 수 있게 된다. 순서는 상관없지만 다음 단계 전에 모든 서버가 바뀌어야 한다.

  4. 모든 서버에서 gtid_mode = ON_PERMISSIVE

    이제 신규 트랜잭션이 GTID로 기록되기 시작한다. 레플리카는 여전히 둘 다 처리한다.

복제 데이터 포맷

SQL 문장을 보낼 것인가(STATEMENT), 바뀐 값을 보낼 것인가(ROW).

핵심 ROW 는 일관성이 가장 안전하지만 로그가 크다. 그 크기를 binlog_row_image 와 트랜잭션 압축으로 줄인다.

Statement 형식

  • 변경을 일으킨 SQL 문장 자체를 저장한다.
  • 하나의 SQL이 수많은 레코드를 바꿔도 실제로는 SQL 하나만 저장된다.
  • 변경 내역이 대부분 남으므로 감사(audit) 목적으로도 활용할 수 있다.
  • 단점 — 비확정적(non-deterministic) 쿼리에서 일관성이 깨질 수 있다.
    • ORDER BY 없이 LIMIT 을 쓴 DELETE/UPDATE
    • 비확정적 함수를 쓰는 쿼리
  • 또 다른 단점 — ROW 방식보다 데이터에 락을 더 많이 건다.
  • 제한 — 트랜잭션 격리 수준이 REPEATABLE-READ 이상 이어야 한다.

Row 형식

  • 변경된 값 그 자체가 바이너리 로그에 저장된다.
  • 소스와 레플리카 간 데이터 일관성을 지키는 가장 안전한 방식이다.
  • 함수를 쓰더라도 최종 결과값이 기록되므로 문제가 없다.
  • STATEMENT 에 비해 락이 최소화된다 — 쿼리를 실행하는 것이 아니라 값을 바로 적용하기 때문이다.
  • 모든 격리 수준에서 쓸 수 있다.
  • 단, 계정 생성이나 권한 부여·회수 같은 DDL은 여전히 STATEMENT 형태로 저장된다.

Mixed 형식

  • 기본적으로 STATEMENT 를 쓰되, 서버가 판단해 필요할 때만 ROW 로 전환한다.
  • STATEMENT 로는 일관성이 보장되지 않는 쿼리를 자동으로 ROW 로 바꾼다.
  • 만능은 아니므로 쓰는 쿼리 형태에 가장 적합한 포맷을 고르는 것이 좋다.

  • 로그 크기는 binlog_row_image=minimal 과 zstd 트랜잭션 압축(8.0.20+)으로 줄인다.
  • minimal 이 제대로 동작하려면 기본키가 있어야 한다 — PKE 가 기준이기 때문이다.

복제 동기화 방식

비동기와 반동기. 반동기가 보장하는 것은 전달이지 적용이 아니다.

핵심 반동기는 "레플리카의 릴레이 로그에 기록되었다"까지만 보장한다. 그 내용이 실제 데이터에 반영됐는지는 보장하지 않는다 — 그래서 반동기다.

비동기 복제 (Asynchronous Replication)

  • 기본 동작 방식이다. 변경 이벤트가 레플리카에 잘 전달·적용됐는지 확인하지 않는다.
  • 어떤 확인도 하지 않으므로, 소스에 장애가 나면 최근 트랜잭션이 전달되지 않았을 수 있다. 즉 누락 가능성이 있다.
  • 전달받지 못한 트랜잭션이 있다면 직접 확인하고 수동으로 적용해야 한다.
  • 대신 트랜잭션 처리가 빠르고, 레플리카에 문제가 생겨도 소스는 전혀 영향받지 않는다.
  • 레플리카를 늘려 읽기 트래픽을 분산하는 용도에 제격이다.

반동기 복제 (Semi-Synchronous Replication)

  • 비동기보다 향상된 무결성을 보장한다.
  • 변경 이벤트를 레플리카의 릴레이 로그에 기록한 뒤 응답이 오면, 그때 트랜잭션을 커밋하고 클라이언트에 결과를 준다.
  • 적어도 1대 이상의 레플리카에는 전달되었다는 보장을 해 준다.
  • 다만 릴레이 로그에 기록된 내용이 실제 데이터에 반영됐는지는 보장하지 않는다. 그래서 반동기다.
  • rpl_semi_sync_master_wait_point 로 응답을 기다리는 지점을 제어한다.
wait_point대기 시점특징
AFTER_SYNC (기본값) 스토리지 엔진 커밋 전 커밋 전에 기다리므로 팬텀 리드가 발생하지 않는다. 복제가 안 된 상황이어도 소스에 반영되지 않았으므로 롤백할 필요가 없다
AFTER_COMMIT 스토리지 엔진 커밋 후, 클라이언트에 결과 반환 직전 복제가 안 된 상태에서 소스에 장애가 나면 수동으로 롤백해야 한다

  • 반동기 복제는 플러그인으로 구현되어 있어 설치가 필요하다.
  • 설치 후 시스템 변수를 적절히 설정해야 실제로 적용된다.

정리

  • 비동기 — 빠르고 소스가 영향받지 않는다. 읽기 분산에 적합.
  • 반동기 — 1대 이상에 전달되었음을 보장한다. 적용까지는 보장하지 않는다.
  • AFTER_SYNC(기본)는 커밋 전 대기 — 팬텀 리드가 없고 롤백이 필요 없다.
  • 타임아웃이 지나면 조용히 비동기로 전환된다. 상태 변수로 확인할 것.

  • 소스 1대에 레플리카 1대만 연결한 형태다.
  • 가장 기본적이고 가장 많이 쓰이는 형태다.
  • 애플리케이션은 소스에만 접근하고, 레플리카는 장애 대비 예비 서버나 백업 용도로 쓴다.
  • 이 구성에서 애플리케이션이 레플리카에도 접근한다면, 레플리카에 문제가 생겼을 때 위험하므로 예비용으로만 쓰는 편이 좋다.

멀티 레플리카 복제 구성

  • 소스 1대에 2대 이상의 레플리카를 연결한다.
  • 싱글 구성에서 추가 용도(분석·백업 등)로 서버가 더 필요할 때 쓴다.
  • 읽기+쓰기는 소스로, 읽기는 레플리카로 분산할 수 있다.
  • 읽기 분산용으로 쓸 때도 레플리카 1대는 예비용으로 남겨 두는 것이 좋다.

체인 복제 구성

  • 레플리카가 너무 많아 소스 성능에 악영향이 예상되면 1:M:M 체인 구성을 고려할 수 있다.
  • 장비 교체 시에도 자주 쓴다 — 각 그룹을 구/신 버전 장비 그룹으로 묶어 생각하면 편하다.
  • 다만 토폴로지가 복잡한 만큼 장애 처리의 복잡도도 올라간다.

  • 양쪽 모두 읽기·쓰기가 가능한 것이 특징이며, 목적에 따라 active-passive / active-active 로 나뉜다.

주의사항
  • 동시에 유입되면 시점상 나중에 처리된 트랜잭션이 최종 반영된다.
  • ACTIVE-ACTIVE 에서는 동시점에 같은 데이터를 변경하는 트랜잭션이 있어서는 안 된다.
  • AUTO_INCREMENT 사용을 지양하고, 꼭 써야 한다면 auto_increment_increment / auto_increment_offset 을 적절히 설정해야 한다.
  • 사실상 쓰기 확장 효과는 크지 않다. 쓰기 성능 확장이 필요하면 샤딩을 고려하는 편이 낫다.

  • 주요 용도
    • 여러 서버의 서로 다른 데이터를 하나로 통합
    • 여러 서버에 샤딩된 테이블 데이터를 하나의 테이블로 통합
    • 여러 서버의 데이터를 모아 한 곳에서 백업
  • 복제됐을 때 충돌이 발생할 만한 부분이 없는지 사전에 충분히 검토해야 한다.
  • 장애 대비용 레플리카는 멀티 소스가 아니라 각 소스와 1:1로 구성하는 편이 좋다.

동작 방식
  • 레플리카는 연결된 소스들의 변경 이벤트를 동시점에 병렬로 동기화한다.
  • 각 소스에 대한 복제가 독립적으로 이루어지며, 이를 위한 독립 복제 처리 단위를 채널 이라고 한다.
  • 레플리카는 최대 256개의 복제 채널을 가질 수 있다.
  • CHANGE REPLICATION SOURCE TO ... FOR CHANNEL '이름' 으로 특정 채널을 지정할 수 있다.
    • 지정하지 않으면 전체 채널에 명령이 적용된다.
구축 시 고려사항
  • 2개 이상의 소스에서 데이터를 가져올 때는 공통 DB(information_schema 등)와 시스템 테이블스페이스의 충돌·병합을 고려해야 한다.
  • 초기에는 mysqldump 와 XtraBackup 을 적절히 조합하는 것이 가장 쉽다.
  • master_info_repository 와 relay_log_info_repository 두 변수가 모두 TABLE 이어야 한다.

지연된 복제 (Delayed Replication)

  • 복제의 원래 목적은 소스와 레플리카를 같은 상태로 만드는 것이다.
  • 지연 복제를 쓰면 이전 시점의 데이터를 확인해야 할 때나 부하 테스트에 활용할 수 있다.
-- MySQL 8.0.23 미만
CHANGE MASTER TO MASTER_DELAY=86400;

-- MySQL 8.0.23 이상
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=86400;
!

원문 교정 원문 교정

노트에는 위 예시를 "1시간의 딜레이" 라고 설명하지만, 86400 초는 24시간(1일) 이다. 1시간이라면 3600 이다. 또한 8.0.23 이상에서 CHANGE REPLICATION SOURCE TO 와 함께 쓰는 옵션 이름은 MASTER_DELAY 가 아니라 SOURCE_DELAY 다. (근거: MySQL 8.0 Reference Manual — Delayed Replication)

설정된 지연은 SHOW REPLICA STATUS 의 SQL_Delay 와 Seconds_Behind_Source 로 확인한다.

8.0에서 추가된 타임스탬프

8.0부터 바이너리 로그에 두 가지 타임스탬프가 추가되었다.

타임스탬프의미서버 간 값
OCT (original_commit_timestamp) 트랜잭션이 원본 소스에 커밋된 시각 (밀리초 단위 유닉스 타임스탬프). 원본 = 트랜잭션이 최초로 실행된 서버 모든 서버가 동일
ICT (immediate_commit_timestamp) 트랜잭션이 직계 소스(레플리카 기준 바로 위의 소스)에 커밋된 시각 서버마다 다르다
  • 원본 서버에서는 OCT와 ICT의 값이 같다.
  • 이 값은 복제를 구성하는 모든 서버가 8.0.1 이상일 때만 동작한다.

멀티 스레드 복제

  • 기존에는 단일 스레드로 동작해, 대량의 DML이 실행되면 복제 지연이 발생했다.

  • 병렬 처리 방식은 DB 기반과 LOGICAL_CLOCK 기반 두 가지다.

데이터베이스 기반 멀티 스레드 복제

  • 스키마 기반 처리 방식이라고도 하며, 초기에 유일하게 쓸 수 있던 방식이다.
  • 이름 그대로 데이터베이스 단위로 병렬 처리하므로, DB가 하나뿐이면 아무런 이득이 없다.
  • 워커가 작업 중일 때 다른 DB의 트랜잭션이 오면 다른 워커에게 할당한다.
    • 하지만 같은 DB에 또 하나의 트랜잭션이 오면 대기했다가 처리된다.
  • 테이블·레코드 수준의 충돌 여부는 고려하지 않고 DB가 같은지만 비교한다.
  • 소스와 레플리카의 바이너리 로그에 차이가 생겨 일관성 보장이 어렵다.
[mysqld]
slave_parallel_type='DATABASE'
slave_parallel_workers=N   # N > 0

LOGICAL CLOCK 기반 멀티 스레드 복제

  • 멀티 스레드·분산 시스템의 상태 동기화에 널리 쓰이는 방법이다.
  • 소스에서 트랜잭션을 바이너리 로그에 기록할 때 논리적 순번을 부여하고, 레플리카가 그 순번을 기준으로 병렬 처리한다.
  • Commit-Parent · Lock · Writeset 세 가지 방식이 있다.
배경 — 바이너리 로그 그룹 커밋
  • 5.5의 InnoDB는 한 시점에 하나의 트랜잭션만 커밋할 수 있었다.
  • 바이너리 로그 기록과 디스크 동기화도 병렬로 진행할 수 없었다.
  • MySQL의 분산 트랜잭션 개념은 Prepare → Commit 2단계로 처리된다.
    • 스토리지 엔진의 내용과 바이너리 로그 간 일관성 유지를 위한 것이다.

5.6 이상의 바이너리 로그 그룹 커밋

Prepare 이후 세 단계를 거쳐 커밋된다.

  1. Flush 단계

    대기 큐에 등록된 각 트랜잭션을 순서대로 바이너리 로그에 기록한다.

  2. Sync 단계

    기록된 내용을 디스크와 동기화하는 fsync() 를 수행한다. sync_binlog 설정에 따라 매번 할지 정한다. 한 번에 많은 트랜잭션이 동기화될수록 효율적이라, 일부러 지연시킬 수도 있다.

  3. Commit 단계

    대기 큐의 트랜잭션들에 대해 스토리지 엔진 커밋을 진행한다.

Lock 기반 상세
  • sequence_number — 커밋된 트랜잭션의 논리적 순번
  • last_committed — 현 트랜잭션 이전에 커밋된 가장 최신 트랜잭션의 순번
  • 바이너리 로그가 새 파일로 로테이션되면 sequence_number 는 1, last_committed 는 0이 된다.
  • 실행 가능 여부의 판단 기준 — 실행하려는 트랜잭션의 last_committed < 현재 실행 중인 트랜잭션들의 최소 sequence_number
Writeset 기반 상세
  • 같은 세션에서 실행된 트랜잭션의 병렬 처리 여부에 따라 WRITESET 과 WRITESET_SESSION 으로 나뉜다.
    • WRITESET — 같은 데이터를 변경하지 않는 모든 트랜잭션을 병렬 실행
    • WRITESET_SESSION — 위와 같되 같은 세션의 트랜잭션은 순서를 유지
  • 트랜잭션이 변경한 데이터 목록을 관리하며, 그 값은 모두 해시 로 표현된다. 이 해시된 목록이 Writeset 이다.
  • Writeset은 테이블의 유니크 키 개수만큼 만들어진다.
  • 해시 알고리즘은 transaction_write_set_extraction 으로 관리하며 기본은 xxHash64 다.
    • 다른 알고리즘으로 바꾸려면 바이너리 로그 포맷이 ROW 여야 한다.
  • 서버 메모리에서 해시맵 테이블로 히스토리가 관리되며, 최대 아이템 수는 기본 25,000 개다.
    • 최대에 도달하거나 DDL이 실행되면 이 값은 초기화된다.
  • 다른 방식보다 처리량을 크게 높여 주지만 Writeset 관리 오버헤드가 발생한다.
Writeset 기반 설정 
# 소스 서버
[mysqld]
binlog_format=ROW
binlog_transaction_dependency_tracking=WRITESET   # 또는 WRITESET_SESSION
transaction_write_set_extraction=XXHASH64

# 레플리카 서버
[mysqld]
binlog_format=ROW
slave_parallel_type=LOGICAL_CLOCK
slave_parallel_workers=N   # N > 0
멀티 스레드 복제와 복제 포지션
  • 각 워커가 실행한 바이너리 로그 이벤트의 포지션은 slave_worker_info 테이블이나 데이터 디렉터리의 worker-relay-log.info 파일에 기록된다.
  • 워커가 이벤트를 완료할 때마다 갱신된다.

크래시 세이프 복제

  • 서버 장애 이후에도 문제없이 복제가 계속되는 방식이다.
  • 대표적인 장애가 Duplicate Key 에러다.
  • MySQL 서버 장애는 이 방식으로 복구되지만, OS 자체의 장애는 보장되지 않는다.
서버 장애와 복제 실패
  • 복제 스레드는 읽은 포지션, 재실행한 트랜잭션 등을 기록한다.
  • 파일로 관리하면 처리 내용과 포지션 정보를 원자적으로 동기화할 수 없었다.
  • 테이블로 관리하면 SQL 스레드가 트랜잭션 적용과 포지션 갱신을 하나의 트랜잭션으로 처리한다.
  • 그래도 릴레이 로그 파일 기록과 포지션 갱신은 원자적으로 처리할 수 없어 여전히 불일치가 생겼다.
  • relay_log_recovery 옵션으로 완화되었다.
    • I/O 스레드의 포지션을 마지막으로 실행했던 포지션으로 초기화한다.
    • 새 릴레이 로그 파일을 만들고 SQL 스레드가 읽어야 할 포지션을 초기화한다.
relay_log_recovery=ON
relay_log_info_repository=TABLE

  • sync_relay_log — 지정한 개수만큼 이벤트가 기록되면 디스크와 동기화한다. 기본값 10,000이고 0이면 OS에 맡긴다.
  • 이 값을 1이 아닌 값으로 두면 트랜잭션 갭 때문에 릴레이 로그가 유실될 수 있다.
    • 트랜잭션 갭 — 멀티 스레드 복제의 병렬 처리로 트랜잭션이 순서대로 처리되지 않아 일시적으로 생기는 간격
  • 가능하면 멀티 스레드 복제는 LOGICAL_CLOCK + 커밋 순서 보장 조합으로 쓰는 것을 권장한다.

원문 교정 원문 교정

노트의 표에는 커밋 순서 일치와 불일치 양쪽 모두 slave_preserve_commit_order=1 로 적혀 있는데, 이러면 두 행이 구분되지 않는다. 커밋 순서를 보장하는 쪽이 =1, 보장하지 않는 쪽이 =0 이다. 이어지는 본문이 "커밋 순서가 불일치하면 sync_relay_log 를 써야 한다"고 설명하는 것과도 이렇게 읽어야 앞뒤가 맞는다.

GTID 기반 + 멀티 스레드의 알려진 이슈
  • 설정 자체는 싱글 스레드와 동일하다.
  • 복구 작업 시 갭을 메우는 작업이 실패하면서 복제 연결이 실패하는 경우가 있었다.
  • 8.0.18 또는 5.7.28 미만 에서는 STOP SLAVE; RESET SLAVE; START SLAVE; 로 복제를 재개할 수 있다.

필터링된 복제 (Filtered Replication)

  • 소스의 특정 이벤트만 레플리카에 적용되도록 필터링한다.
  • 소스에서는 데이터베이스 단위로만 필터링할 수 있고, 레플리카에서는 더 다양한 형태가 가능하다.
  • 동작 방식은 소스가 걸러 주는 것이 아니라, 레플리카가 일단 전부 가져온 뒤 거기서 필터링하는 형태다.
  • 1차로 DB 수준에서 걸러내고, 2차로 테이블 수준 옵션을 확인해 최종 적용 여부를 결정한다.
my.cnf 
[mysqld]
binlog-do-db=[바이너리 로그에 기록할 DB]
binlog-ignore-db=[바이너리 로그에 기록하지 않을 DB]

레플리카 쪽 필터링 옵션은 CHANGE REPLICATION FILTER 구문으로 지정하며 FOR CHANNEL 로 채널을 명시할 수도 있다.

정리

  • 지연 복제는 8.0.23+ 에서 SOURCE_DELAY (단위: 초).
  • 멀티 스레드 복제 — DB 기반(DB가 하나면 무의미) vs LOGICAL_CLOCK. 후자 중 Writeset 이 병렬도가 가장 높다.
  • Writeset 은 binlog_format=ROW 가 전제이고, 유니크 키 개수만큼 해시를 만든다.
  • 크래시 세이프의 기본은 relay_log_recovery=ON + 포지션 정보를 TABLE 로 관리하는 것.
  • 필터링은 레플리카가 전부 받은 뒤 걸러낸다 — 네트워크 절감 효과는 없다.
  • 8.0.26+ 에서는 replica_* 계열 새 변수명을 쓴다.
