6-1

페이지 압축

Transparent Page Compression — 파일시스템의 펀치 홀에 기대는 압축이라, 실제로는 잘 쓰지 않는다.

핵심 페이지 압축의 결과물은 스파스 파일이다. DB 안에서는 완벽하게 동작하지만, cp 한 번에 원래 크기로 부풀어 오른다.

어떻게 동작하는가

  • 서버가 디스크에 저장하는 시점에 데이터 페이지가 압축된다.
  • 디스크에서 읽어오는 시점에 압축이 해제된다.
  • 버퍼 풀에 한 번 적재되면 InnoDB는 압축이 해제된 상태로만 관리한다.
  • 사용자 입장에서는 완전히 투명(transparent)하게 동작한다.

문제는 16KB 페이지를 압축한 결과가 몇 KB가 될지 예측할 수 없다는 것이다. 적어도 하나의 테이블은 동일한 크기의 페이지로 통일되어야 하므로, 펀치 홀(punch hole) 기능을 쓴다.

펀치 홀 기능

  1. 16KB 페이지를 압축한다

    결과가 7KB가 되었다고 하자.

  2. 디스크에 압축 결과 7KB를 저장하고, 남는 9KB를 기록해 둔다

    페이지 슬롯 자체는 여전히 16KB 자리를 차지한다.

  3. 남은 9KB 영역에 펀치 홀을 뚫는다

    파일시스템에게 "이 구간은 비어 있다"고 알리는 것이다.

  4. 파일시스템이 9KB를 OS에 반납한다

    결과적으로 실제 디스크 사용량은 7KB가 된다.

파일의 논리적 크기는 그대로 16KB다 — 실제 점유량만 7KB로 줄어든다. 이 간극이 뒤에서 문제를 만든다.

문제점

  • 펀치 홀은 운영체제와 하드웨어가 모두 지원해야 쓸 수 있다.
  • DB 파일은 DB 안에만 있는 것이 아니다. 백업 등으로 외부에서 파일을 다루는 순간 문제가 된다.
  • 실제 페이지 크기가 1GB인 파일도 cp 명령이나 복구 툴을 거치면 펀치 홀이 0으로 채워져 10GB가 될 수 있다.
  • 이런 이유로 페이지 압축은 실무에서 잘 쓰이지 않는다.
page-compression.sql 
CREATE TABLE page_compression (
  id INT PRIMARY KEY AUTO_INCREMENT
) COMPRESSION="zlib";

정리

  • 압축·해제 시점은 디스크 I/O 지점. 버퍼 풀에는 항상 해제된 상태로 올라간다.
  • 가변적인 압축 결과를 고정 페이지 크기에 맞추기 위해 펀치 홀을 쓴다.
  • OS/하드웨어 의존성과 백업 시 원래 크기로 부풀어 오르는 문제 때문에 실무 채택률이 낮다.
6-2

테이블 압축

제약이 없어 활용도가 높지만, 버퍼 풀을 두 벌 쓴다는 값을 치른다.

핵심 테이블 압축의 진짜 비용은 디스크가 아니라 버퍼 풀이다. 압축본과 해제본이 동시에 메모리에 올라간다.

페이지 압축과의 차이

  • 페이지 압축과 달리 OS·하드웨어 제약이 없어 일반적으로 활용도가 더 높다.
  • 디스크에 저장되는 데이터 파일 크기를 줄일 수 있지만 단점도 분명하다.
    • 버퍼 풀 공간 활용률이 낮아진다.
    • 쿼리 처리 성능이 낮아진다.
    • 빈번한 데이터 변경 시 압축률이 떨어진다.

압축 테이블 생성

  • 전제조건 — 압축할 테이블이 별도의 테이블스페이스를 사용해야 한다. 즉 innodb_file_per_table 이 켜져 있어야 한다.
  • ROW_FORMAT=COMPRESSED 옵션이 있어야 압축이 적용된다. 생략해도 KEY_BLOCK_SIZE 가 있으면 자동으로 들어간다.
  • KEY_BLOCK_SIZE 로 압축 후 목표 페이지 크기를 명시한다.
    • 2의 승수만 사용 가능하다.
    • 페이지 크기(innodb_page_size)가 16KB면 4KB 또는 8KB 만 설정할 수 있다.
    • 페이지 크기가 32KB나 64KB인 경우에는 테이블 압축을 쓸 수 없다.
table-compression.sql 
SET GLOBAL innodb_file_per_table = ON;

CREATE TABLE compressed_table (
  id INT AUTO_INCREMENT PRIMARY KEY
)
ROW_FORMAT=COMPRESSED
KEY_BLOCK_SIZE=8;

압축 과정

이 과정에서 InnoDB 스토리지 엔진이 하는 일은 없다 — 압축 라이브러리(zlib)에 맡긴다. 페이지 크기 16KB, 블록 크기 8KB인 경우를 보자.

flowchart TB
  A["16KB 데이터 페이지 압축"] --> B{"결과가 8KB 이하?"}
  B -->|"예"| C["그대로 디스크에 저장 - 압축 완료"]
  B -->|"아니오"| D["원본 페이지를 둘로 쪼갬"]
  D --> E["각각 8KB 슬롯에 저장 시도"]
  E --> A
목표 크기에 들어갈 때까지 페이지를 쪼갠다 — 압축률이 나쁜 데이터일수록 페이지 분할이 늘어난다.

KEY_BLOCK_SIZE 설정

  • 테이블 압축에서 가장 중요한 결정이 이 크기다.
  • 4KB 또는 8KB로 만들어 보고 샘플 데이터를 넣어 본 뒤 적절한지 판단한다.
  • information_schema.INNODB_CMP_PER_INDEX 테이블로 압축 성공·실패 횟수를 확인할 수 있다.

압축된 페이지의 버퍼 풀 적재 및 사용

  • 압축 테이블의 페이지를 버퍼 풀에 적재하면 압축 전과 압축 후 두 개의 버전이 관리된다.
    • LRU 리스트 — 디스크에서 읽은 그대로의(압축된) 데이터 페이지 목록
    • Unzip_LRU 리스트 — 압축 해제 버전
  • 두 버전을 동시에 관리하느라 버퍼 풀 공간을 이중으로 쓰게 된다.
  • 또한 압축된 페이지에서 데이터를 읽거나 변경할 때마다 해제가 필요하므로 CPU를 많이 쓴다.
어댑티브 알고리즘

이 단점을 보완하기 위해 InnoDB는 Unzip_LRU를 별도로 두고, 유입되는 요청 패턴에 맞춰 적절히 조절한다.

  • 버퍼 풀 공간이 필요하면 LRU 리스트는 유지하고 Unzip_LRU 를 먼저 제거해 공간을 확보한다.
  • 압축된 페이지가 자주 사용되면 Unzip_LRU에 계속 유지해 CPU 사용률을 최소화한다.
  • 페이지가 미사용으로 LRU 리스트에서 제거되면 Unzip_LRU에서도 함께 제거된다.
  • CPU 사용률이 높은 상태면 압축/해제를 피하려고 Unzip_LRU의 비율을 높인다.
  • Disk I/O 가 높은 서버면 Unzip_LRU의 비율을 낮춰 버퍼 풀 공간을 더 확보한다.

읽는 요령 보강

두 규칙이 반대 방향처럼 보이지만 논리는 하나다 — 지금 병목인 자원을 아끼는 쪽으로 움직인다. CPU가 병목이면 해제본을 남겨 CPU를 아끼고, 디스크가 병목이면 압축본만 남겨 더 많은 페이지를 캐시한다.

테이블 압축 관련 설정

변수역할
innodb_cmp_per_index_enabled 압축 테이블의 인덱스별 압축 성공·실행 횟수를 수집. information_schema.INNODB_CMP_PER_INDEX, INNODB_CMP 에서 확인
innodb_compression_level 압축률 설정. 0~9 중 선택하며 기본값은 6

이 밖에도 innodb_compression_failure_threshold_pct, innodb_compression_pad_pct_max 등 다양한 옵션이 있다.

정리

  • 테이블 압축은 innodb_file_per_table = ON 이 전제이고, KEY_BLOCK_SIZE 로 목표 크기를 정한다.
  • 16KB 페이지에서는 4KB / 8KB만 선택 가능. 32KB·64KB 페이지에서는 아예 못 쓴다.
  • 비용은 버퍼 풀 이중 점유 + CPU. 어댑티브 알고리즘이 그때그때 균형을 잡는다.
  • KEY_BLOCK_SIZE 는 실측으로 정한다 — INNODB_CMP_PER_INDEX 의 실패 횟수를 본다.
