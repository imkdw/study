17-1

InnoDB 클러스터 아키텍처

복제만으로는 HA가 되지 않는다. 세 가지 구성 요소가 합쳐져야 완성된다.

핵심 소스-레플리카 복제는 데이터를 복제할 뿐이다. 누가 새 소스인지 결정하고(그룹 복제), 트래픽을 그쪽으로 보내는(라우터) 두 가지가 더 있어야 자동 페일오버가 된다.

왜 클러스터인가

  • 일반적으로 소스-레플리카 구성만으로는 HA가 보장되지 않는다.
  • InnoDB 클러스터는 HA 보장을 위해 만들어진 여러 구성 요소의 집합체다.
flowchart TB
  A["애플리케이션"] --> R["MySQL Router (프록시)"]
  R --> P["Primary (읽기 + 쓰기)"]
  R --> S1["Secondary (읽기 전용)"]
  R --> S2["Secondary (읽기 전용)"]
  P <-->|"그룹 복제"| S1
  P <-->|"그룹 복제"| S2
  S1 <-->|"그룹 복제"| S2
  SH["MySQL Shell (AdminAPI)"] -.->|"구축 / 관리"| P
애플리케이션은 라우터 주소만 안다 — Primary 가 바뀌어도 애플리케이션 설정은 그대로다.

구성 요소

그룹 복제 (Group Replication)
  • 소스 → 레플리카 복제와 서버들의 자동화된 멤버십 관리를 담당한다.
  • 각 서버는 읽기·쓰기가 모두 가능한 프라이머리 또는 읽기만 가능한 세컨더리 중 하나로 동작한다.
  • 프라이머리는 그룹 내에 1개 이상 존재할 수 있다.
  • 고가용성을 위해 기본적으로 서버가 3대 이상 필요하다.
MySQL Router
  • 애플리케이션과 DB 사이에서 동작하는 미들웨어로, 쿼리를 적절한 서버로 전달하는 프록시 역할이다.
  • 애플리케이션에는 라우터의 커넥션 정보만 설정해 두면 알아서 실제 서버로 프록시해 준다.
MySQL Shell
  • 기존 클라이언트보다 확장된 기능을 가진 클라이언트 프로그램이다. 다양한 API를 제공한다.

정리

  • InnoDB 클러스터 = 그룹 복제 + MySQL Router + MySQL Shell.
  • 역할은 프라이머리(읽기+쓰기)와 세컨더리(읽기 전용).
  • 고가용성을 위해 최소 3대가 필요하다.
17-2

그룹 복제

반동기처럼 보이지만 다르다 — 과반수의 합의(Consensus) 로 커밋을 결정한다.

핵심 그룹 복제는 과반수 이상의 동의가 있어야 트랜잭션이 적용된다. 그래서 서버 수가 n = 2f + 1 공식을 따라야 한다.

기본 특징

  • 내부적으로 ROW 포맷 바이너리 로그 + 릴레이 로그 + GTID 를 사용한다.
  • 모든 서버가 서로 통신하며 양방향 복제도 가능하다.
  • 하나의 복제 그룹 안에 쓰기를 처리하는 서버가 여러 개 있을 수 있다.
  • 서버를 소스·레플리카가 아닌 프라이머리·세컨더리 로 지칭한다.
  • 그룹에 최소 3대 이상이 있어야 한다.
    • n = 2f + 1 — n은 전체 서버 수, f는 허용할 장애 서버 수

반동기와 무엇이 다른가

구분반동기 복제그룹 복제
커밋 조건 레플리카에서 응답을 받으면 커밋 다른 멤버에게 전송 후 과반수 이상의 응답이 있어야 커밋
실패 시 타임아웃 후 비동기로 전환하고 커밋 전체 복제 그룹에서 트랜잭션이 적용되지 않는다 — 롤백
  • 그룹의 다른 멤버들에게 응답을 확인하는 과정을 합의(Consensus) 라고 한다.
  • 멤버들의 응답에 따라 전체 그룹에서 그 트랜잭션의 적용 여부가 결정된다 — 이것이 가장 큰 차이다.
  • 데이터를 변경하는 작업에만 필요하고, 읽기만 하는 작업에는 필요 없다.

그룹 복제 아키텍처

  • 별도의 플러그인으로 구현되어 있어 설치해야 쓸 수 있다.
  • 클러스터에 참여한 서버들이 이 플러그인을 통해 지속적으로 통신하고 동기화한다.
  • group_replication_applier 채널 — 그룹에서 실행된 모든 트랜잭션을 전달받아 적용한다.
  • group_replication_recovery 채널 — 새 서버가 추가되었을 때 분산 복구 작업을 진행한다.
플러그인 계층 구조
  1. 플러그인 API 집합 (최상위)

    DB 서버 → 플러그인으로는 서버 시작·복구, 트랜잭션 커밋 등의 이벤트를 전달하고, 플러그인 → DB 서버로는 커밋·중단·릴레이 로그 기록 요청 등을 전달한다.

  2. 복제 플러그인 계층 (중간)

    그룹 복제 기능이 실제로 구현된 곳이다. 여러 모듈로 나뉘어 있고 트랜잭션 처리·충돌 감지·전파·분산 복구 가 여기서 이루어진다.

  3. 그룹 통신 시스템 API + 엔진 (하위 두 계층)

    eXtended COMmunication, 줄여서 xCom 이라 부른다. 서버 간 통신을 담당하는 핵심이며 별도 포트 33061 로 통신한다. 트랜잭션이 모든 멤버에게 동일한 순서로 전달되도록 보장한다.

합의 알고리즘
알고리즘주로 쓰이는 상황
Paxos분산 시스템에서 데이터 변경이 여러 서버에서 발생할 때
Raft데이터 변경이 한 대에서만 발생할 때

그룹 복제는 멀티 프라이머리까지 지원해야 하므로 Paxos 계열의 Mencius 알고리즘을 기반으로 구현되어 있다.

그룹 복제 모드

  • 프라이머리 서버 수에 따라 싱글 프라이머리 와 멀티 프라이머리 로 나뉜다.
  • group_replication_single_primary_mode 로 제어한다. ON=싱글, OFF=멀티이며 기본값은 ON 이다.
  • 그룹에 참여하는 모든 서버가 같은 값이어야 한다.
  • 8.0.13부터는 UDF로 온라인 변경이 가능하다.
    • group_replication_switch_to_single_primary_mode()
    • group_replication_switch_to_multi_primary_mode()
싱글 프라이머리 모드
  • 그룹 안에서 쓰기를 처리할 수 있는 서버가 한 대뿐이다.
  • 처음 구축할 때는 구축을 진행한 서버가 프라이머리가 된다.
  • 프라이머리가 그룹을 탈퇴하거나 UDF로 멀티 모드로 바꾸면 프라이머리가 변경된다.
프라이머리 선출 기준
  1. MySQL 서버 버전

    가장 우선하는 요소다. 모든 멤버가 8.0.17 이상이면 패치 버전으로, 미만인 서버가 있으면 메이저 버전으로 정렬한다.

  2. 각 멤버의 가중치

    group_replication_member_weight 를 비교한다. 기본값 50, 범위 0~100.

  3. UUID 사전식 순서

    위 둘로도 결정되지 않으면 UUID가 사전 순으로 가장 낮은 멤버가 선정된다.

멀티 프라이머리 모드
  • 모든 멤버가 프라이머리로 동작하고, 클라이언트는 어느 서버로든 읽기·쓰기 요청을 보낼 수 있다.
  • 호환성이 매우 중요하므로 가능하면 모든 서버가 같은 버전을 쓰는 것이 좋다.
  • 새 멤버가 추가될 때 호환 기준에 따라 참여 가능 여부와 읽기 전용 유지 여부가 결정된다.
    • 그룹 내 가장 낮은 버전보다 더 낮으면 참여 불가
    • 그룹 내 가장 낮은 버전보다 더 높으면 읽기 전용 모드 유지

그룹 멤버 관리

  • 어떤 서버가 참여 중인지 멤버 목록과 상태를 내부적으로 관리한다.
    • performance_schema.replication_group_members 테이블
  • 멤버 변동을 자동으로 감지해 상태를 갱신한다.
  • 이 목록과 상태 정보를 뷰(View) 라고도 부르며, 멤버가 바뀔 때마다 새로운 뷰 ID 가 생성된다.
    • 이 값으로 뷰의 변경을 추적하고 변경 시점을 구분할 수 있다.
    • 형식은 View ID = [Prefix]:[Sequence] — 예: 87116:4

그룹 복제에서의 트랜잭션 처리

합의 (Consensus)
  • 그룹 내 일관된 트랜잭션 적용을 위해 멤버들에게 적용을 제안하고 승낙받는 과정이다.
  • xCom을 통해 트랜잭션이 변경한 데이터의 Writeset 과 gtid_executed 스냅샷 등을 전파한다.
  • Paxos 계열 알고리즘으로 최종 합의가 이루어져 과반수 이상 동의하면 트랜잭션을 적용한다.
  • 동의를 얻지 못하면 롤백되고 클라이언트로 에러가 반환된다.
인증 (Certification)
  • xCom으로 전달받은 Writeset과 로컬이 가진 Writeset을 비교해 충돌 여부를 검사한다.
  • 충돌이 발생하면 롤백되므로, 충돌이 잦은 환경에서는 이 과정이 없는 싱글 프라이머리 모드가 권장된다.

트랜잭션 일관성 수준

group_replication_consistency 시스템 변수로 설정한다. 각 수준은 읽기 전용 트랜잭션과 읽기-쓰기 트랜잭션에 다른 영향을 준다.

수준읽기쓰기적합한 경우
EVENTUAL 기본값 구버전 데이터를 읽을 수 있다 제약 없이 즉시 실행 일관성보다 성능이 중요할 때
BEFORE_ON_PRIMARY_FAILOVER 항상 최신 보장 충돌로 인한 롤백 없음 페일오버 직후의 일관성만 보장하고 싶을 때
BEFORE 항상 최신 선행 트랜잭션 완료까지 대기 읽기가 적고 쓰기가 많을 때
AFTER 읽기 전용은 즉시 처리 모든 멤버가 준비될 때까지 대기 쓰기보다 읽기가 많고 분산된 최신 읽기가 필요할 때
BEFORE_AND_AFTER 항상 최신 양쪽 모두 대기 가장 엄격. 대기 시간 초과 위험이 있다
EVENTUAL
  • 기본값이며, 최종적으로는 멤버들이 일관된 데이터를 가지게 됨을 의미한다.
  • 모든 트랜잭션이 제약 없이 즉시 실행되지만, 다른 서버에서 일시적으로 구버전 데이터를 읽을 수 있다.
  • 페일오버 시 새 프라이머리가 이전 프라이머리의 변경을 적용하느라 트랜잭션 충돌로 롤백이 생길 수 있다.
BEFORE_ON_PRIMARY_FAILOVER
  • 싱글 모드에서 프라이머리 페일오버가 발생해 새 프라이머리가 선출됐을 때만 영향을 준다.
  • 이전 프라이머리의 트랜잭션을 반영하는 동안 모든 트랜잭션이 블로킹된다.
  • 영구 대기는 안 되고 wait_timeout 만큼 기다린 뒤 에러를 반환한다.
    • wait_timeout 기본값은 28,800초(8시간) 이므로, 애플리케이션에서 적절한 타임아웃을 두는 것이 좋다.
  • 모든 쿼리가 막히는 것은 아니다 — SHOW, SET, DO 등 모니터링용 일부 쿼리는 바로 실행된다.
  • 읽기는 항상 최신을 보장하고, 쓰기는 충돌이 발생하지 않아 롤백되지 않는다.
BEFORE / AFTER / BEFORE_AND_AFTER
  • BEFORE — 모든 트랜잭션이 선행 트랜잭션이 완료될 때까지 대기한다. 항상 최신을 읽지만 대기가 길어질 수 있다.
  • AFTER — 읽기-쓰기 트랜잭션이 다른 모든 멤버가 커밋할 준비가 될 때까지 대기한 후 처리된다. 읽기 전용은 변경을 만들지 않으므로 즉시 처리된다.
  • BEFORE_AND_AFTER — 양쪽을 모두 적용한다. 읽기 전용 요청도 선행 트랜잭션을 기다린다.

흐름 제어 (Flow Control)

  • 멤버 간 트랜잭션 적용 불균형으로 생기는 문제를 막기 위해 쓰기 처리량을 조절하는 메커니즘이다.
  • 멤버 간 트랜잭션 갭을 작게 유지해 데이터가 최대한 동기화된 상태로 있게 한다.
  • 평소와 다른 워크로드가 유입되어도 빠르게 적응해 각 멤버의 쓰기 처리량을 균등하게 만든다.
  • group_replication_flow_control_mode 로 제어하며 현재 QUOTA 와 DISABLED 두 모드만 있다.
QUOTA 모드
  • 모든 멤버의 쓰기 처리량과 대기 중인 트랜잭션 통계를 수집해 흐름 제어의 필요성을 판단한다.
  • 조절이 필요하면 통계를 바탕으로 멤버가 최대 쓰기량을 넘지 않도록 제한한다.
  • 그룹 전체가 아니라 각 멤버별로 적용되며, 수집된 정보는 다른 멤버와도 공유된다.
    • 인증 큐 크기, 적용 큐 크기, 인증된 트랜잭션 수, 적용된 원격 트랜잭션 수, 로컬 트랜잭션 수
  • 실제 조절은 인증 큐 크기와 적용 큐 크기를 기반으로 한다.
변수역할기본값
group_replication_flow_control_certifier_threshold인증 큐의 대기 트랜잭션 수가 이 값을 넘으면 흐름 제어 작동25,000
group_replication_flow_control_applier_threshold어플라이어 큐의 대기 트랜잭션 수가 이 값을 넘으면 흐름 제어 작동25,000
group_replication_flow_control_min_quota계산 결과와 무관하게 멤버에게 할당되어야 할 최소 쓰기 처리량0
group_replication_flow_control_max_quota계산 결과와 무관하게 멤버에게 할당되어야 할 최대 쓰기 처리량0
group_replication_flow_control_min_recovery_quota그룹에 복구 상태의 멤버가 있을 때 min_quota 대신 적용—

범위는 대체로 0 ~ 약 21억이며, 이 밖에도 여러 변수가 있다.

자동 장애 감지 및 대응

  • 일부 멤버에 장애가 나도 그룹이 정상 동작하도록 장애 감지 메커니즘이 구현되어 있다.
  • 멤버로부터 5초 이내에 응답을 못 받으면 의심을 시작하고, 과반수가 동의하면 추방한다.
    • 추방 전 의심받은 멤버는 대기 시간 동안 UNREACHABLE 상태로 표시된다.
  • 추방된 멤버는 통신이 복구되면 추방 사실을 감지하고, 5분 간격으로 총 3번 재가입을 시도한다.
  • 통신이 계속 불가능하면 group_replication_unreachable_majority_timeout 으로 스스로 탈퇴할 수도 있다.

분산 복구

  • 새 멤버나 추방됐던 멤버는 그룹 가입 시 동기화된 최신 데이터를 받아야 한다.
  • 이 복구 프로세스를 자동으로 수행하는 것을 분산 복구 라고 한다.
  • 복구를 도와줄 기존 멤버를 기증자(Donor) 라고 부르며, 모든 멤버가 기증자가 될 수 있다.
복구 방식
  • 기존에 가입했던 멤버라면 릴레이 로그에서 탈퇴 시점을 찾아 미적용 트랜잭션을 복구한다.
  • 신규 멤버는 처음부터 복구한다.
  • 방식은 바이너리 로그 복제 와 원격 클론 두 가지다.
  • 서버가 알아서 적절한 방식을 고르며, 원격 클론 플러그인이 없으면 바이너리 로그 복제로 진행한다.
방식동작전제조건
바이너리 로그 복제 비동기 복제 기반. 기증자와 별도 채널로 연결해 미적용 트랜잭션을 가져와 적용 —
원격 클론 다른 멤버의 모든 데이터와 메타데이터를 일관된 스냅샷으로 가져와 재구축 기증자와 신규 멤버 모두 클론 플러그인이 설치되어 있어야 한다
복구 프로세스
  1. 로컬 복구

    이전에 가입한 적이 있다면 릴레이 로그에 미적용 트랜잭션이 남아 있을 수 있다. 이를 먼저 적용한다.

  2. 글로벌 복구

    그룹 내에서 기증자를 선택해 데이터를 가져와 적용한다. 이 작업 동안 그룹은 새 트랜잭션을 내부적으로 캐싱해 둔다.

  3. 캐시 트랜잭션 적용

    글로벌 복구 동안 캐싱해 둔 트랜잭션들을 적용하고 그룹에 참여한다.

복구 설정
변수역할기본값
group_replication_recovery_retry_count 바이너리 로그 복제 방식에서 연결 시도 횟수. 원격 클론은 이 값과 무관하게 멤버당 1번만 시도한다 10
group_replication_recovery_reconnect_interval대상 멤버들에게 한 바퀴 시도한 뒤 대기하는 시간60초
group_replication_recovery_complete_at복구 완료 후 어느 시점에 online 으로 표기할지—
복구 오류 처리
  • 복구 도중 오류가 나도 자동으로 재시도하는 장애 감지 메커니즘이 있다.
  • 재시도 횟수를 모두 소진하거나, 바이너리 로그가 없는데 클론 방식도 안 되는 경우 그 멤버는 그룹을 떠난다.

그룹 복제 요구사항

  • InnoDB 스토리지 엔진 사용
  • 기본키 사용
  • 원활한 네트워크 환경
  • 바이너리 로그 활성화 및 ROW 포맷 사용
  • 바이너리 로그 체크섬 설정
  • log_slave_updates 활성화
  • GTID 사용
  • 고유한 server_id
  • 복제 메타데이터 저장소 설정
  • 트랜잭션 Writeset 설정
  • 테이블스페이스 암호화 설정
  • lower_case_table_names 설정
  • 멀티 스레드 복제 설정

그룹 복제 제약사항

  • 갭 락이 적용되지 않는 READ-COMMITTED 격리 수준을 써야 한다
  • 테이블 락과 네임드 락은 고려되지 않는다
  • 바이너리 로그 체크섬은 8.0.21부터 지원
  • 멀티 프라이머리 모드에서는 SERIALIZABLE 격리 수준을 쓸 수 없다
  • 같은 테이블에 대해 서로 다른 멤버에서 DDL과 DML을 함께 실행할 수 없다
  • CASCADE 제약조건을 쓸 수 없다 (동작하지 않는다)
!

도입 전 확인할 두 가지

요구사항 중 모든 테이블에 기본키가 있어야 한다는 것과, 제약사항 중 ON DELETE CASCADE 가 동작하지 않는다는 것이 실제 도입을 가장 자주 막는다. 기존 스키마를 그대로 옮길 수 있다고 가정하지 말고 먼저 점검해야 한다.

정리

  • 그룹 복제는 과반수 합의로 커밋을 결정한다 — 반동기와 결정적으로 다른 점이다.
  • 서버 수는 n = 2f + 1. 통신은 xCom, 포트 33061, 알고리즘은 Paxos 계열 Mencius.
  • 일관성 수준 5단계 — 기본은 EVENTUAL, 페일오버만 챙기려면 BEFORE_ON_PRIMARY_FAILOVER.
  • 흐름 제어는 인증 큐 / 적용 큐 크기 기준으로 쓰기 처리량을 조절한다.
  • 분산 복구는 바이너리 로그 복제 또는 원격 클론. 5초 무응답 → 의심 → 과반수 동의 시 추방.
  • 전제조건 중 기본키와 ROW + GTID, 제약 중 CASCADE 불가 를 먼저 확인한다.
17-3

MySQL 셸

mysql 클라이언트의 확장판. AdminAPI 가 클러스터 구축을 담당한다.

핵심 InnoDB 클러스터 구축은 사실상 MySQL Shell 의 AdminAPI 로 하는 작업이다.
  • MySQL을 위한 고급 클라이언트 툴이다.
  • SQL만 실행할 수 있던 mysql 보다 확장된 기능을 제공한다.
  • 파이썬, 자바스크립트 등 여러 모드를 지원한다.
API역할
X DevAPIX 프로토콜로 RDBMS에서 문서 기반 데이터를 처리할 수 있게 해 준다
AdminAPI레플리카 셋이나 클러스터 등 서버의 설정을 변경한다

정리

  • MySQL Shell = mysql + 스크립팅 모드(JS/Python) + API.
  • 클러스터 구축·관리는 AdminAPI, 문서 지향 접근은 X DevAPI.
17-4

MySQL 라우터

애플리케이션이 서버 목록을 몰라도 되게 만들어 주는 프록시.

핵심 라우터가 있어야 페일오버가 애플리케이션에 투명해진다. 이것이 클러스터에 라우터가 필요한 이유의 전부다.
  • InnoDB 클러스터에서 애플리케이션 서버의 요청을 적절한 서버에 전달하는 프록시 역할을 한다.
  • 내부 서버들에 대한 부하 분산을 수행한다.
  • 여러 서버 중 특정 서버에서 에러가 나면 다른 서버로 넘겨서 처리해 준다.

정리

  • 라우터는 프록시 + 부하 분산 + 자동 페일오버 전달 세 역할을 한다.
  • 애플리케이션은 라우터 주소만 알면 된다.

이 절은 구축 실습까지 진행하지 않았다

노트에는 요구사항 목록과 "시간되면 구성해보기.." 라는 메모까지만 남아 있다. 실제 구축은 MySQL Shell 의 AdminAPI(dba.createCluster(), cluster.addInstance())로 진행하며, 그에 앞서 17-2 그룹 복제 요구사항 의 항목들이 먼저 충족되어야 한다.

  • 모든 서버에서 Performance 스키마가 활성화되어 있어야 한다.
  • 구축 자체는 AdminAPI 로 진행한다.
