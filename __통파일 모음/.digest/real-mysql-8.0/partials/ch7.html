7-1

MySQL 서버의 암호화

암·복호화가 스토리지 엔진의 I/O 레이어에서만 일어난다. 그래서 인덱스가 멀쩡하고, 그래서 Transparent 다.

핵심 TDE는 디스크에 닿는 순간에만 암호화한다. 버퍼 풀 안의 데이터는 평문이므로 옵티마이저도 인덱스도 아무것도 달라지지 않는다.

어디를 암호화하는가

  • 보안 감사에서 필수적으로 언급되는 부분이다.
  • 애플리케이션 암호화는 주민번호 같은 중요 정보를 가진 컬럼 단위로 수행한다.
  • DB 수준에서는 테이블 단위로 암호화를 적용한다.

MySQL 서버의 데이터 암호화 — TDE

  • DB 서버와 디스크 사이의 데이터 I/O 지점에서 암·복호화를 수행한다.
  • 스토리지 엔진의 I/O 레이어에서만 일어나는 일이다.
  • 이런 특성 때문에 TDE(Transparent Data Encryption) 라고 부른다.
flowchart LR
  A["MySQL 엔진 (옵티마이저, 실행 엔진)"] --> B["버퍼 풀 (평문 상태)"]
  B -->|"쓰기: 암호화"| C["디스크 데이터 파일 (암호문)"]
  C -->|"읽기: 복호화"| B
암호화 경계는 버퍼 풀과 디스크 사이 딱 한 곳이다 — 그 위쪽 레이어는 암호화 사실을 전혀 모른다.

2단계 키 관리

  • 암호화 키는 키링 플러그인이 관리하며, 여러 종류의 키링 플러그인이 있다.
  • 커뮤니티 에디션에서는 keyring_file 플러그인만 쓸 수 있다.
  • 기본적으로 2단계(2-Tier) 키 관리 방식을 사용한다 — 마스터 키와 테이블스페이스 키.
마스터 키를 바꿔도 데이터는 다시 암호화되지 않는다 — 테이블스페이스 키만 새 마스터 키로 재암호화하면 끝이다.
마스터 키
  • 외부 키 관리 솔루션이나 디스크의 파일에서 가져온다.
  • 외부에 노출될 위험이 있으니 주기적으로 변경하는 것이 좋다.
  • 마스터 키가 변경되면 기존 키로 테이블스페이스 키를 복호화한 뒤 새 키로 다시 암호화한다.
ALTER INSTANCE ROTATE INNODB MASTER KEY;
테이블스페이스 키
  • 암호화된 테이블이 생성될 때마다 고유한 키가 만들어진다.
  • 테이블스페이스 키는 마스터 키로 암호화되어 저장된다.
  • 생성된 키는 각 테이블 데이터 파일의 헤더에 보관된다.
  • 한 번 생성된 테이블스페이스 키는 테이블이 삭제되지 않는 한 절대 바뀌지 않는다.
암호화 알고리즘
  • TDE가 지원하는 알고리즘은 AES 256비트 뿐이다.
  • 테이블스페이스 키는 AES-256 ECB 로 암호화된다.
  • 실제 데이터 파일은 AES-256 CBC 로 암호화된다.

암호화의 성능

  • 한 번 읽은 페이지는 복호화되어 버퍼 풀에 남으므로, 평문 테이블과 성능이 거의 같다.
  • 암·복호화 시간만큼 쿼리가 지연되긴 하지만, 디스크 동기화는 백그라운드 스레드가 담당하므로 사용자 쿼리가 그만큼 지연되지는 않는다.
  • 읽기·쓰기 자체는 평문 대비 3~6배 느리지만, 밀리초 단위라 체감되지 않는다.
  • performance_schema.file_summary_by_instance 테이블에서 속도를 확인할 수 있다.
데이터 크기
  • 평문이 짧으면 암호문이 더 클 수 있지만, 데이터 페이지 자체가 이미 훨씬 크므로 사실상 동일하다.
  • 암호화를 적용한다고 버퍼 풀의 효율이나 메모리 사용 효율이 떨어지지는 않는다.
압축과 암호화 — 순서가 중요하다
  • MySQL은 압축을 먼저 하고 그다음 암호화한다.
  • 암호화된 결과물은 랜덤 바이트에 가까워서, 순서를 뒤집으면 압축률이 거의 0 이 된다.
  • 또 버퍼 풀에 암호화된 데이터가 올라간다면 접근할 때마다 복호화해야 하므로 성능이 저하된다.

암호화와 복제

  • 소스와 레플리카 사이에 모든 데이터가 복제되지만 키는 복제되지 않는다.
  • 각 인스턴스는 고유한 마스터 키를 갖는다. 원격 키 관리 솔루션을 쓰더라도 서로 다른 마스터 키를 갖도록 설정해야 한다.
  • ALTER INSTANCE ROTATE INNODB MASTER KEY 명령 자체는 레플리카로 복제되지만, 키 값이 복제되는 것은 아니다.
  • 따라서 백업할 때마다 키링 파일의 백업도 함께 고려해야 한다. 키가 없으면 백업은 쓰레기다.

정리

  • TDE의 암호화 경계는 스토리지 엔진의 I/O 레이어 한 곳뿐이다.
  • 마스터 키(외부) → 테이블스페이스 키(파일 헤더) → 데이터 의 2단계 구조. 로테이션은 마스터 키만 갈아 끼운다.
  • 테이블스페이스 키는 AES-256 ECB, 데이터 파일은 AES-256 CBC.
  • 압축 → 암호화 순서를 지켜야 압축이 의미를 갖는다.
  • 키는 복제되지 않는다. 백업에는 반드시 키링도 포함한다.
7-2

keyring_file 플러그인 설치

TDE 플러그인은 다른 어떤 플러그인보다 먼저 초기화되어야 한다.

핵심 plugin-load 가 아니라 early-plugin-load 다. 데이터 딕셔너리를 열기 전에 키가 준비되어 있어야 하기 때문이다.

keyring_file 이 하는 일

  • 마스터 키를 저장하는 파일을 생성한다.
  • 이때 평문으로 저장되므로, 그 파일이 유출되면 암호화 자체가 무의미해진다.
  • HashiCorp Vault를 쓰고 있다면 keyring_vault 플러그인도 함께 검토할 만하다.

초기화

  • TDE 플러그인은 다른 플러그인과 달리 가장 먼저 초기화되어야 한다.
  • my.cnf 에 early-plugin-load 로 등록한다.
  • 키 파일 경로도 지정할 수 있는데, MySQL 서버 1대당 1개의 키를 가져야 한다.
my.cnf 
early-plugin-load = keyring_file.so
keyring-file-data-path = /etc/mysql/keyring.keyring

재부팅 이후

  • SHOW PLUGINS 로 설치된 플러그인을 확인한다.
  • 최초에는 키 값이 비어 있다. ALTER INSTANCE ROTATE INNODB MASTER KEY 를 실행하면 새 키가 생성된다.
↑

MySQL 8.0.34 기준 최신 반영

keyring_file 플러그인은 8.0.34에서 deprecated 되었다. 지금 새로 구성한다면 같은 역할을 하는 컴포넌트인 component_keyring_file 을 쓴다. 컴포넌트는 early-plugin-load 대신 데이터 디렉터리의 mysqld.my 매니페스트 파일과 별도의 컴포넌트 설정 파일로 구성한다. (근거: MySQL 8.0 Reference Manual — Keyring Component Installation)

정리

  • 키링은 early-plugin-load 로 가장 먼저 올린다.
  • keyring_file 은 키를 평문으로 저장한다 — 파일 권한과 백업 격리가 곧 보안이다.
  • 최초 키는 ALTER INSTANCE ROTATE INNODB MASTER KEY 를 한 번 실행해야 생긴다.
  • 8.0.34+ 신규 구성은 component_keyring_file 로.
7-3

테이블 암호화

애플리케이션 암호화는 인덱스를 포기하지만, DB 암호화는 포기하지 않는다.

핵심 DB단 암호화는 인덱스 작업을 모두 마친 뒤 마지막에 페이지를 암호화한다. 그래서 범위 검색도 정렬도 그대로 된다.

테이블 생성

  • 키링 플러그인은 마스터 키 생성·관리만 담당한다. 그 이후 테이블을 만들고 쓰는 방법은 어느 키링을 쓰든 동일하다.
  • 테이블 생성 시 끝에 ENCRYPTION='Y' 를 붙이면 된다.
  • default_table_encryption 을 켜면 모든 테이블이 기본적으로 암호화되어 생성된다.
encrypt.sql 
CREATE TABLE encrypt_test (
  id INT PRIMARY KEY AUTO_INCREMENT
) ENCRYPTION="Y";

SET default_table_encryption = OFF;

애플리케이션 암호화와의 비교

구분암호화 시점인덱스 활용
애플리케이션 암호화 INSERT 전, 애플리케이션에서 범위·정렬·LIKE 불가. 동등 비교만 가능
DB(TDE) 암호화 데이터 페이지를 디스크에 쓸 때 제약 없음 — 인덱스 작업은 평문 상태에서 끝난다

유즈케이스에 따라 다르지만, 큰 제약이 없다면 DB단 암호화를 권장한다.

i

둘은 배타적이지 않다 보강

TDE는 디스크·백업 파일이 유출됐을 때를 막는 방어선이다. DB 접속 권한을 가진 공격자에게는 아무 의미가 없다 — SELECT 하면 평문이 나온다. 주민번호처럼 DBA에게조차 보이면 안 되는 값은 여전히 애플리케이션 암호화가 필요하다.

테이블스페이스 이동

  • 레코드를 덤프했다가 복구하는 것보다 테이블스페이스 파일을 그대로 옮기는 편이 훨씬 빠르다.
  • 암호화되지 않은 테이블은 단순 명령으로 옮길 수 있다.
암호화된 테이블스페이스 이동
  • FLUSH TABLES <source_table> FOR EXPORT 를 실행하면 임시 마스터 키가 발급되어 <source_table>.cfg 파일에 기록된다.
  • 암호화된 테이블은 .ibd 뿐 아니라 임시 마스터 키가 담긴 .cfg 파일도 반드시 함께 복사해야 한다.

정리

  • ENCRYPTION='Y' 하나로 테이블 암호화가 켜진다. 전역 기본값은 default_table_encryption.
  • DB 암호화는 인덱스를 온전히 쓸 수 있다 — 애플리케이션 암호화의 가장 큰 손실을 피한다.
  • 단, TDE는 파일 유출에 대한 방어일 뿐이다. 접속 권한 기반 위협은 막지 못한다.
  • 암호화 테이블 이동에는 .ibd 와 .cfg 둘 다 필요하다.
7-4

언두 로그 및 리두 로그 암호화

테이블을 암호화해도 로그 파일에는 평문이 흐른다. 별도로 켜야 한다.

핵심 로그 암호화는 켠 시점 이후부터만 적용된다. 그래서 예전 키를 며칠, 길게는 몇 달 보관해야 할 수도 있다.

왜 별도 설정이 필요한가

  • 디스크의 데이터 파일이 암호화되어도 리두 로그와 언두 로그는 평문으로 저장된다.
  • 이 로그들은 테이블이 아니라 외부 파일시스템에 저장되므로 그대로 노출된다.
  • innodb_undo_log_encrypt, innodb_redo_log_encrypt 로 각각 암호화 여부를 지정한다.
my.cnf 
innodb_undo_log_encrypt = ON
innodb_redo_log_encrypt = ON

암호화 시점

  • 기존에는 평문으로 저장되다가, 암호화를 켜는 순간부터 암호화되어 저장된다.
  • 비활성화하면 마찬가지로 그 이후부터 평문으로 저장된다.
  • 즉 하나의 로그 파일 집합 안에 평문 구간과 암호문 구간이 섞일 수 있다.
  • 상황에 따라 며칠 또는 몇 달 동안 예전 암호화 키가 필요할 수도 있다.

사용되는 키

  • 각각 별도의 테이블스페이스 키로 암호화된다.
  • 실제 테이블을 암호화하는 키가 아니라 새로운 테이블스페이스 키를 발급받아 쓴다.
  • 발급된 키는 리두·언두 로그 파일의 헤더에 저장된다.

정리

  • 테이블 암호화와 로그 암호화는 별개다. 각각 켜야 한다.
  • 암호화는 설정 시점 이후 기록분에만 적용된다 — 과거 데이터는 소급되지 않는다.
  • 키는 별도 발급되어 각 로그 파일 헤더에 저장된다.
7-5

바이너리 로그 암호화

바이너리 로그는 장기간 보관되기에, 암호화의 필요성이 다른 로그보다 크다.

핵심 바이너리 로그 암호화는 디스크에 저장된 파일만 보호한다. 소스 → 레플리카 네트워크 구간은 별개이며 TLS/SSL이 담당한다.

대상 범위

  • 리두·언두 로그와 달리 바이너리 로그는 특수한 목적(시점 복구, 감사) 때문에 장기간 디스크에 보관될 수 있다.
  • 바이너리 로그 암호화는 실제 디스크에 저장된 파일에 대해서만 적용된다.
    • 소스 ↔ 레플리카 네트워크 구간의 암호화는 제공하지 않는다.
    • 네트워크 구간까지 필요하면 TLS/SSL 통신으로 별도 처리해야 한다.

암호화 키 관리

  • 동일하게 파일 키로 암호화해서 디스크에 저장하고, 파일 키는 각 로그의 헤더에 담는다.
  • ALTER INSTANCE ROTATE INNODB MASTER KEY 로 마스터 키를 변경할 수 있다.
마스터 키 변경 시 벌어지는 일
  1. 새 로그 암호화 키 발급

    시퀀스 번호를 증가시키고, 새 키를 만들어 키링 파일에 저장한다.

  2. 로그 파일 스위칭

    바이너리 로그 파일과 릴레이 로그 파일을 새 파일로 교체한다.

  3. 새 파일에 적용

    새 바이너리 로그 파일 키로 파일 키를 암호화해 각 로그 파일에 저장한다.

  4. 기존 파일 재암호화

    기존 바이너리·릴레이 로그의 파일 키를 읽어 새 키로 다시 암호화해 저장한다.

  5. 옛 키 제거

    기존 바이너리 로그 암호화 키를 키링에서 삭제한다.

mysql 
mysql> SHOW BINARY LOGS;
+---------------+-----------+-----------+
| Log_name      | File_size | Encrypted |
+---------------+-----------+-----------+
| binlog.000001 |       668 | Yes       |
| binlog.000002 |  89088804 | Yes       |
+---------------+-----------+-----------+
2 rows in set (0.00 sec)

mysqlbinlog 로 읽기

  • 한 번 암호화되면 암호화 키 없이는 복호화가 불가능하다.
  • 그런데 그 키는 MySQL 서버가 쥐고 있으므로, 로컬 파일을 직접 열어서는 읽을 수 없다.
  • --read-from-remote-server 옵션을 주면 서버에게 복호화된 내용을 요청하는 방식이라 읽을 수 있다.
terminal 
$ mysqlbinlog --read-from-remote-server \
    --start-position=mysql-bin.000001 \
    --stop-position=mysql-bin.000002 \
    --database=test \
    --user=root --password=password \
    --host=127.0.0.1 --port=3306
!

원문 교정 원문 교정

노트에는 "바이너리 로그 암호화 키는 MySQL 서버가 갖고 있어서 복호화가 불가능하다"고 두 번 연달아 적혀 있는데, 앞뒤가 맞지 않는다. 정확히는 서버 밖에서(로컬 파일 직접 읽기로는) 복호화할 수 없다는 뜻이다. 그래서 --read-from-remote-server 로 서버에 요청하면 읽을 수 있다.

정리

  • 바이너리 로그 암호화는 디스크 파일 전용. 네트워크 구간은 TLS/SSL의 몫이다.
  • 마스터 키 로테이션은 로그 파일 스위칭 + 기존 파일 키 재암호화를 동반한다.
  • 암호화된 바이너리 로그는 mysqlbinlog --read-from-remote-server 로만 읽을 수 있다.
