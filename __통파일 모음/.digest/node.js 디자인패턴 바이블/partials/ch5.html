5-1

Promise

비동기 결과를 "값"으로 만든 순간, 저장하고 합치고 캐싱할 수 있게 되었다.

핵심 콜백은 전달할 수만 있지만 Promise 는 변수에 담을 수 있다. 11-2의 요청 일괄 처리와 캐싱 레시피는 전부 이 한 가지 성질에서 나온다.

Promise

  • 비동기 결과를 전파하기 위한 CPS 방식 콜백을 대신할 강력한 대안이다.
  • ECMAScript 2015의 일부이며 Node v4 이후부터 기본적으로 사용할 수 있었다.

Promise란 무엇일까

비동기 작업의 최종적인 결과 또는 에러를 가지고 있는 객체다.

Promise의 상태
stateDiagram-v2
  [*] --> pending
  pending --> fulfilled : resolve(value)
  pending --> rejected : reject(reason)
  fulfilled --> [*]
  rejected --> [*]
  note right of fulfilled
    settled (결정됨)
  end note
한 번 결정되면 되돌릴 수 없다 — pending 에서 나가는 화살표는 두 개뿐이고, fulfilled / rejected 에서 나가는 화살표는 없다. 이 불변성 덕분에 같은 Promise 에 then 을 몇 개 붙이든, 언제 붙이든 항상 같은 결과를 받는다.
상태의미
대기중(pending)비동기 작업이 아직 완료되지 않은 상태
완료됨(fulfilled)비동기 작업이 성공적으로 끝났을 때
실패함(rejected)비동기 작업이 에러와 함께 종료됐을 때
결정된(settled)이행되거나 거부된 상태 — 위 둘을 묶어 부르는 말
CPS 방식과의 차이점
CPS
asyncOperation(arg, (err, result) => {
  if (err) {
    // 에러 처리
  }

  // 성공 처리
});
Promise
asyncOperationPromise(arg)
  .then((result) => {
    // 성공 처리
  })
  .catch((err) => {
    // 에러 처리
  });

성공 경로와 실패 경로가 코드상에서도 분리된다는 점이 핵심이다. CPS 에서는 두 경로가 같은 함수 안에 뒤섞여 있었다.

Promise 체인
  • 체인 중 어디서 실패하든 catch 구문으로 넘어간다.
  • 각 상위 체인의 성공값을 하위 체인에서 사용할 수 있다.
chain.ts 
asyncOperationPromise(arg)
  .then((result1) => {
    // 성공 처리
  })
  .then((result2) => {
    // 성공 처리
  })
  .then((result3) => {
    // 성공 처리
  })
  .catch((err) => {
    // 체인 전체의 에러 처리를 담당
  });

4-1의 콜백 지옥과 나란히 놓고 보면 차이가 명확하다. 중첩이 평평한 체인으로 펴지고, 에러 처리가 마지막 한 곳으로 모인다.

Promise/A+ 와 thenable
  • 과거에는 여러 Promise 구현이 존재했고 대부분 서로 호환되지 않았다.
  • 이 한계를 극복하기 위해 Promise/A+ 사양이 만들어졌다.
  • Promise API 를 포함한 구현들은 then() 함수가 있는 모든 객체를 thenable 로 간주한다.

노트에 없는 조합자 하나 더 보강

Promise.any(iterable)(ES2021, Node 15+)는 race 와 달리 가장 먼저 성공한 것을 반환하고 실패는 무시한다. 전부 실패해야 비로소 AggregateError 로 reject 된다. "여러 미러 중 아무거나 먼저 응답한 곳"처럼 실패를 관용해야 하는 상황에 쓴다.

Promise 생성

delay.ts 
function delay(ms: number) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      resolve(ms);
    }, ms);
  });
}

console.log("h");
delay(1000).then(() => console.log("after delay"));
i

이미 표준에 있다

delay 는 Node 코어에 이미 있다. import { setTimeout } from "timers/promises" 로 가져오면 await setTimeout(1000) 처럼 바로 쓸 수 있고, AbortSignal 을 받아 취소도 지원한다(11-3).

Promise화(promisification)

  • 콜백 기반 함수의 특성을 알고 있다면(콜백이 마지막 인자, 에러가 첫 인자) Promise 를 반환하는 동일한 함수로 기계적으로 변환할 수 있다.
  • 아래는 원리를 보여주는 예시이며, 실제로는 util 의 promisify 를 쓴다.
promisify.ts 
import { randomBytes } from "crypto";

function promisify(callbackBasedApi: any) {
  return function promisified(...args: any[]) {
    // 새로운 Promise 를 생성하고 반환함
    return new Promise((resolve, reject) => {
      // 콜백 함수는 항상 마지막 인자라는 규칙을 이용해
      // resolve / reject 로 연결한다
      const newArgs = [
        ...args,
        (err: unknown, result: any) => {
          if (err) {
            return reject(err);
          }

          resolve(result);
        },
      ];

      callbackBasedApi(...newArgs);
    });
  };
}

const randomBytesPromisified = promisify(randomBytes);

randomBytesPromisified(10).then((bytes) => {
  console.log(bytes);
});

3-1의 두 가지 규칙("콜백은 맨 마지막, 에러는 맨 처음")이 기계적 변환을 가능하게 만든 전제였다는 것이 여기서 드러난다. 규칙이 규칙이었던 이유다.

i

요즘 쓰는 방법 보강

대부분의 코어 모듈은 이미 Promise 버전을 별도 네임스페이스로 제공한다 — fs/promises, timers/promises, stream/promises, dns/promises. util.promisify 는 이제 서드파티 콜백 API 를 감쌀 때 주로 쓴다.

정리

  • Promise = 비동기 결과를 담은 값. 저장/전달/재사용이 가능해진다
  • 상태는 pending → fulfilled/rejected 로 한 번만 전이하고 되돌릴 수 없다
  • 조합자 4종: all(전부 성공) / allSettled(전부 대기) / race(첫 결정) / any(첫 성공)
  • promisify 가 기계적으로 가능한 이유는 콜백 규칙이 통일되어 있기 때문
  • 실무에서는 fs/promises 같은 코어의 Promise 네임스페이스를 먼저 찾는다
5-2

async / await

동기처럼 보이게 만드는 문법이지만, 동기처럼 동작한다고 착각하는 순간 함정이 시작된다.

핵심 await 는 차단하는 것처럼 보이게 할 뿐이다. 실제로는 함수 실행이 보류되고 제어권이 이벤트 루프로 돌아간다. 이 사실을 잊으면 forEach 함정과 return await 함정에 그대로 빠진다.

async 함수와 await 표현

  • async 함수는 항상 Promise 를 반환한다.
  • await 표현을 만나면 함수의 실행이 보류되고 상태가 저장되며 제어가 이벤트 루프로 반환된다.
delay.ts await 가 없다 
async function delay(ms: number) {
  return setTimeout(() => {
    console.log(`after ${ms}ms`);
  }, ms);
}

console.log("Hello");
delay(1000);
console.log("World");

/**
 * output
 *
 * Hello
 * World
 * after 1000ms
 */
!

이 예제가 보여주는 것 원문 교정

노트의 이 코드는 async 를 붙였지만 await 를 쓰지 않았고, setTimeout 은 Promise 를 반환하지 않는다. 따라서 delay(1000) 은 Timeout 객체로 즉시 이행되는 Promise 를 돌려줄 뿐, "기다리는" 동작을 전혀 보여주지 못한다. 실제로 기다리게 하려면 5-1의 delay 처럼 new Promise 로 감싸고 호출부에서 await 해야 한다.

delay-fixed.ts 실제로 기다린다 
function delay(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function main() {
  console.log("Hello");
  await delay(1000);
  console.log("World");   // 1초 뒤에 출력된다
}

main();

async/await 에서의 예외 처리

  • 기존에는 then().catch() 방식으로 에러를 처리했다.
  • async/await 에서는 try/catch 문으로 처리한다. 동기 코드와 비동기 코드가 같은 에러 처리 문법을 쓰게 된 것이 가장 큰 실용적 이득이다.
try-catch.ts 
async function playingWithErrors(throwSyncError: boolean) {
  try {
    if (throwSyncError) {
      throw new Error("Sync error");
    }
  } catch (err) {
    console.log("Caught an error:", err);
  } finally {
    console.log("done");
  }
}

playingWithErrors(false);

3-1에서 "콜백 안의 예외는 바깥 try/catch 가 못 잡는다"고 했던 문제가 await 로는 해결된다. await 지점에서 함수 실행이 재개되므로 스택이 논리적으로 이어지기 때문이다.

return vs return await 함정
  • async 함수 안에서 return await 를 붙이지 않으면 거부된 Promise 가 로컬 try/catch 를 그냥 지나쳐 호출자에게 전파된다.
  • 해당 함수 안에서 에러를 잡고 싶다면 반드시 return await 를 써야 한다.
catch 를 통과한다
async function f() {
  try {
    return delayError(10);   // await 없음
  } catch (err) {
    return "caught inside";
  }
}
// → 호출자에게 rejected 전파
여기서 잡힌다
async function f() {
  try {
    return await delayError(10);
  } catch (err) {
    return "caught inside";
  }
}
// → "caught inside" 로 이행
terminal 
$ node return-await.mjs
withAwait -> caught inside
withoutAwait rejected -> boom

왜 이런 차이가 나는가

return promise 는 Promise 를 그대로 넘겨주고 함수를 즉시 떠난다. 떠나 버렸으니 try 블록은 이미 끝났고, 나중에 그 Promise 가 거부돼도 잡을 catch 가 없다. return await promise 는 함수 안에서 결과를 기다렸다가 반환하므로, 거부되면 await 지점에서 예외가 던져져 catch 에 걸린다.

바꿔 말하면 try/catch 밖에서라면 return await 는 불필요한 마이크로태스크 한 번일 뿐이다. try 블록 안에서만 의미가 있다. Node v24.17.0 에서 실행해 위 출력을 확인했다.

안티패턴 — 순차 실행을 위한 Array.forEach with async/await

  • 아래 코드에서 getLinkLength 는 이벤트 루프의 동일한 라운드에서 전부 호출된다.
  • 모두 병렬로 시작되고, forEach 는 완료를 기다리지 않고 즉시 다음 줄로 넘어간다.
foreach-antipattern.ts 순차가 아니다 
links.forEach(async (link) => {
  const length = await getLinkLength(link);
  console.log(length);
});

두 가지가 동시에 깨진다

(1) 순서가 보장되지 않는다 — 전부 동시에 출발하므로 먼저 끝난 것부터 로그가 찍힌다.

(2) 에러가 유실된다 — forEach 는 콜백의 반환값(Promise)을 버린다. 따라서 안에서 발생한 거부는 아무도 처리하지 않고 unhandledRejection 이 된다.

순차가 필요하면
for (const link of links) {
  const length = await getLinkLength(link);
  console.log(length);
}
병렬이 목적이면
const lengths = await Promise.all(
  links.map((link) => getLinkLength(link))
);
lengths.forEach((l) => console.log(l));

병렬 실행

  • 가능하면 Promise.all() 로 구현하는 것을 권장한다.
  • 일반적인 반복문에서 await 를 쓰면 하나가 실패해도 바로 멈추지 않는다 (이미 출발한 작업들은 계속 진행된다).
  • Promise.all() 은 하나라도 실패하면 즉시 거부를 반환하므로 빠르게 상태를 알 수 있다.

동시성을 제한하고 싶다면 보강

Promise.all(items.map(fn)) 은 동시성 제한이 없다. 항목이 1만 개면 요청 1만 개가 동시에 나간다 — 4-2에서 경고한 바로 그 상황이다. 표준에는 제한 기능이 없으므로 p-map / p-limit 의 concurrency 옵션을 쓰거나 TaskQueue 를 직접 짠다.

무한 재귀 프로미스 해결

아래 함수는 무한한 프로미스 체인을 만들고 메모리 누수를 일으킨다.

leaking-loop.ts 체인이 끝없이 자란다 
function delay(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

function leakingLoop(): Promise<void> {
  return delay(1).then(() => {
    console.log(`Tick ${Date.now()}`);
    return leakingLoop();      // ← 반환된 프로미스가 다음 프로미스에 의존
  });
}

leakingLoop();
flowchart LR
  P1["promise 1"] -->|"해결은 promise 2 에 달림"| P2["promise 2"]
  P2 -->|"해결은 promise 3 에 달림"| P3["promise 3"]
  P3 -->|"..."| PN["promise N"]
  PN -.->|"끝나지 않으므로 아무도 해제되지 않음"| P1
루프가 아니라 계속 길어지는 사슬이다 — 각 프로미스는 다음 프로미스가 결정돼야 해결되므로, 가장 오래된 프로미스조차 끝까지 살아 있다. 반복 횟수에 비례해 메모리가 단조 증가한다.
프로미스 체인 끊기
  • leakingLoop 가 반환한 프로미스가 다음 leakingLoop 에 의존하지 않게 만들면 된다.
  • 이전 코드에서 return 문을 제거하면, GC 가 동작해 메모리가 오르내리는 톱니 모양이 된다.
  • 다만 근본적인 동작이 바뀐다. 각 프로미스의 연결이 끊어져 재귀 깊은 곳의 에러를 전파하지 못한다.
non-leaking-loop.ts 메모리는 잡히지만 에러 전파를 잃는다 
return delay(1).then(() => {
  console.log(`Tick ${Date.now()}`);
  leakingLoop();     // return 을 뺀다
});

둘 다 얻는 방법 보강

메모리와 에러 전파를 모두 지키려면 재귀 대신 while 루프 + await 를 쓴다. async 함수의 await 는 스택을 쌓지 않고 같은 함수 프레임을 재개하므로 반복 횟수와 무관하게 메모리가 일정하고, 예외는 그대로 바깥으로 던져진다.

권장
async function loop() {
  while (true) {
    await delay(1);
    console.log(`Tick ${Date.now()}`);
  }
}

정리

  • async 함수는 항상 Promise 를 반환하고, await 는 차단이 아니라 보류 후 재개다
  • 에러는 try/catch 로. 단 try 안에서 반환할 땐 return await 여야 잡힌다
  • forEach(async ...) 는 순차도 아니고 에러도 유실한다 → for...of 또는 Promise.all
  • Promise.all 은 빠른 실패를 주지만 동시성 제한은 없다
  • 재귀 프로미스 체인은 메모리를 먹는다 → while + await 가 정답
