11-1

비동기적으로 초기화되는 컴포넌트 다루기

"아직 준비 안 됐어요"를 누가 알고 있어야 하는가 — 사용자인가, 컴포넌트 자신인가.

핵심 세 가지 해법의 차이는 준비 상태를 아는 책임이 어디에 있느냐다. 로컬 확인은 사용자에게, 지연 시작은 진입점에게, 사전 초기화 큐는 컴포넌트 자신에게 지운다.

비동기적으로 초기화되는 컴포넌트의 문제

  • DB 연결처럼 서버와 연결이 완료돼야 쿼리나 명령을 보낼 수 있는 컴포넌트가 있다.
  • 보통의 해결 방법은 로컬 초기화 확인 또는 지연 시작이다.
db.ts 
import EventEmitter from "events";

class Db extends EventEmitter {
  private connected = false;

  connect() {
    setTimeout(() => {
      this.connected = true;
      this.emit("connected");
    }, 1000);
  }

  async query(queryString: string) {
    if (!this.connected) {
      throw new Error("Not connected");
    }

    console.log(`Query: ${queryString}`);
  }
}

export const db = new Db();
로컬 초기화 확인
  • API 를 호출할 때마다 초기화 여부를 확인하고, 안 됐으면 초기화를 기다린다.
  • 이 검사를 호출 지점마다 매번 해야 한다는 것이 부담이다.

설명과 코드가 어긋난다 원문 교정

노트는 "안 됐으면 초기화를 기다린다"고 설명하지만, 코드는 여전히 throw new Error("Not connected") 로 기다리지 않고 던진다. 추가된 것은 isConnected() 게터뿐이다.

이 방식의 실제 모습은 호출부가 확인하고 기다리는 것이다. 아래처럼 매 호출 지점마다 세 줄이 반복되고, 그 반복이 이 방식의 비용이다.

호출부가 책임진다
async function updateLastAccess() {
  if (!db.isConnected()) {
    await once(db, "connected");     // 호출할 때마다 이 검사
  }
  await db.query("UPDATE users SET last_access = NOW()");
}
지연 시작
  • 컴포넌트가 초기화 루틴을 완료할 때까지, 그 컴포넌트에 의존하는 코드의 실행 자체를 미룬다.
  • 단점은 어떤 컴포넌트가 비동기 초기화에 의존하는지 모두 알고 있어야 한다는 것이다.
  • 간단하고 효과적이지만 전체 시작 시간에 큰 영향을 줄 수 있다.
delayed-startup.ts 
import { once } from "events";

async function initialize() {
  db.connect();
  await once(db, "connected");     // 여기서 한 번만 기다린다
}

async function updateLastAccess() {
  await db.query("UPDATE users SET last_access = NOW()");

initialize().then(() => {
  updateLastAccess();
  setTimeout(() => {
    updateLastAccess();
  }, 600);
});

검사 코드가 진입점 한 곳으로 모였다. 대신 초기화가 끝날 때까지 앱 전체가 아무 일도 못 한다. 초기화가 느린 컴포넌트가 여럿이면 시작 시간이 그만큼 길어진다.

사전 초기화 큐

  • 커넥션이 맺어지지 않았다면 호출 건을 커맨드로 만들어 배열에 저장한다.
  • 커넥션이 맺어지면 큐에 쌓인 커맨드들을 실행한다.
  • 사용하는 쪽은 초기화 여부를 전혀 알 필요가 없고, 모든 로직이 컴포넌트 자체에 내장된다.
db-queue.ts 권장 
import EventEmitter from "events";

class Db extends EventEmitter {
  private connected: boolean;
  private commandsQueue: Array<() => void>;

  constructor() {
    super();
    this.connected = false;
    this.commandsQueue = [];
  }

  async query(queryString: string) {
    if (!this.connected) {
      console.log("Request Queued", queryString);

      return new Promise((resolve, reject) => {
        const command = () => {
          this.query(queryString).then(resolve, reject);
        };

        this.commandsQueue.push(command);
      });
    }

    console.log("Query executed", queryString);
  }

  connect() {
    setTimeout(() => {
      this.connected = true;
      this.emit("connected");
      this.commandsQueue.forEach((command) => command());
      this.commandsQueue = [];
    }, 500);
  }
}

export const db = new Db();

!

이 구현의 사각지대

연결에 실패하면 큐에 쌓인 Promise 들이 영원히 pending 으로 남는다. connect() 에 실패 경로를 두고, 실패 시 큐의 모든 명령을 reject 시켜야 완성이다. 큐 길이에 상한을 두지 않은 것도 위험하다 — 연결이 오래 지연되면 메모리가 계속 증가한다.

방식검사 책임장점단점
로컬 초기화 확인호출부 (매번)구현이 단순모든 호출 지점에 반복 코드
지연 시작진입점 (한 번)검사 코드가 한 곳에 모임시작 시간 증가, 의존 목록을 알아야 함
사전 초기화 큐컴포넌트 자신사용자는 아무것도 몰라도 됨구현 복잡, 실패/상한 처리 필요

정리

  • 비동기 초기화 컴포넌트의 문제 = "준비 상태를 누가 아는가"
  • 로컬 확인은 호출부마다, 지연 시작은 진입점 한 곳, 사전 초기화 큐는 컴포넌트 내부
  • 사전 초기화 큐 = 상태 패턴 + 명령 패턴 + Promise 의 조합
  • 큐 방식은 연결 실패 시 reject 와 큐 길이 상한을 반드시 함께 설계해야 한다
11-2

비동기식 요청 일괄 처리 및 캐싱

Promise 를 값으로 다룰 수 있게 된 순간, 중복 요청 제거는 Map 하나로 끝난다.

핵심 일괄 처리는 진행 중인 Promise 를 재사용하고, 캐싱은 완료된 Promise 를 보관한다. 저장하는 것이 결과값이 아니라 Promise 그 자체라는 점이 두 기법을 하나로 만든다.

Promise를 활용한 일괄 처리 및 캐싱

  • Promise 는 일괄 처리와 캐싱을 구현하기 위한 훌륭한 도구다.
    • 여러 개의 then() 리스너를 동일한 Promise에 연결할 수 있다.
    • then() 리스너는 한 번만 호출되는 것이 보장되고, 항상 비동기적으로 호출된다.
  • 덕분에 일괄 처리와 캐싱이 매우 간단하고 간결해진다.

두 번째 성질이 특히 중요하다. 3-1의 Zalgo 문제 — "이미 끝난 작업에 리스너를 붙이면 놓친다" — 가 Promise 에서는 아예 발생하지 않는다. 이미 결정된 Promise 에 then 을 붙여도 다음 마이크로태스크에 반드시 호출된다.

총 판매 웹 서버의 일괄 처리
  • API 호출 시 동일한 요청이 이미 진행 중이라면, 새 요청을 시작하는 대신 그것이 끝나기를 기다린다.
  • 후속 요청은 해당 호출에 대한 Promise 가 이미 있는지 확인한다. 있으면 그대로 반환하고, 없으면 새 요청을 시작한다.
batching.ts 
interface Product {
  id: string;
}

const runningRequest = new Map();

function totalSalesRaw(product: Product) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      resolve(product.id);
    }, 1000);
  });
}

export function totalSales(product: Product) {
  if (runningRequest.has(product.id)) {
    // Batching — 진행 중인 Promise 를 그대로 돌려준다
    return runningRequest.get(product.id);
  }

  const resultPromise = totalSalesRaw(product);
  runningRequest.set(product.id, resultPromise);
  resultPromise.finally(() => {
    runningRequest.delete(product.id);   // 끝나면 지운다
  });

  return resultPromise;
}

진행 중인 창(window) 안에서만 합쳐진다 — 요청이 끝나는 순간 Map 에서 지워지므로, 캐시와 달리 오래된 데이터를 돌려줄 위험이 전혀 없다. 일괄 처리가 캐싱보다 안전한 이유이자, 대부분의 경우 먼저 시도해 볼 만한 이유다.
총 판매 웹 서버의 요청 캐싱
  • 요청 시간이 만료되거나 에러가 발생하면 캐시에서 바로 제거한다.
caching.ts 캐시 미스 처리를 채운 형태 
interface Product {
  id: string;
}

const CACHE_TTL = 1000;
const cache = new Map();

export function totalSales(product: Product) {
  if (cache.has(product.id)) {
    return cache.get(product.id);      // 캐시 히트
  }

  const resultPromise = totalSalesRaw(product);
  cache.set(product.id, resultPromise);

  resultPromise.then(
    () => {
      setTimeout(() => {
        cache.delete(product.id);      // TTL 만료 시 제거
      }, CACHE_TTL);
    },
    (err: unknown) => {
      cache.delete(product.id);        // 실패는 즉시 제거
      throw err;
    }
  );

  return resultPromise;
}

원문 교정 원문 교정

노트의 캐싱 코드는 첫 두 줄이 이렇다.

원문
const resultPromise = cache.get(product.id);
cache.set(product.id, resultPromise);

캐시 미스일 때 totalSalesRaw 를 부르는 부분이 통째로 빠져 있다. 첫 호출에서 cache.get 이 undefined 를 돌려주고, 바로 다음 줄 resultPromise.then(...) 에서 TypeError: Cannot read properties of undefined (reading 'then') 로 죽는다. 일괄 처리 예제의 구조를 그대로 따라 캐시 미스 분기를 복원했다.

i

결과가 아니라 Promise 를 캐싱하는 이유 보강

완료된 값을 캐싱하면, 첫 요청이 진행 중인 동안 도착한 두 번째 요청은 캐시가 비어 있어 같은 조회를 또 시작한다. Promise 를 캐싱하면 그 구간까지 자동으로 합쳐진다. 즉 이 캐시 구현은 일괄 처리를 포함한다 — 그래서 두 절이 한 아이템으로 묶여 있는 것이다.

캐싱 메커니즘 구현에 대한 참고사항

  • 캐시된 값이 많으면 메모리를 많이 쓸 수 있는데, LRU / FIFO 같은 정책으로 일정한 사용량을 유지할 수 있다.
  • 앱이 여러 프로세스나 서버에 분산된 경우 캐시 값의 일관성을 보장하지 못한다. 외부 서비스로 Redis, Memcached 등을 쓸 수 있다.
  • 시간 만료와 달리 수동 캐시 무효화는 관리가 복잡하다.

두 번째 항목은 12-2의 "상태 저장 통신 다루기"와 같은 문제다. 프로세스마다 별개의 Map 을 갖는 순간, 클러스터의 워커 수만큼 캐시가 갈라진다.

정리

  • Promise 를 Map 에 담는 것만으로 일괄 처리가 된다 — 진행 중이면 같은 Promise 반환
  • 일괄 처리는 오래된 데이터를 돌려줄 위험이 없다. 캐싱보다 먼저 고려할 만하다
  • 결과값이 아니라 Promise 를 캐싱해야 진행 중 구간까지 합쳐진다
  • 실패한 Promise 는 즉시 제거, 성공은 TTL 후 제거
  • 분산 환경에서는 프로세스별 캐시가 갈라진다 → Redis 같은 외부 저장소
11-3

비동기 작업 취소

Promise 에는 취소가 없다. 그래서 매 await 지점마다 직접 물어봐야 한다.

핵심 취소는 중단이 아니라 협조다. 실행 중인 작업을 강제로 멈출 방법은 없으므로, 작업 스스로가 중간중간 "취소됐나?"를 확인하고 조기 종료해야 한다.

취소 가능한 함수 레시피

  • 모든 비동기 호출 이후에 취소가 요청됐는지 확인하고, 요청됐다면 작업을 조기에 종료한다.
cancelable.ts 
async function cancelable(cancelObj: any) {
  const resA = await asyncRoutine("A");
  console.log(resA);
  if (cancelObj.cancelRequested) {
    throw new CancelError("Canceled");
  }

  const resB = await asyncRoutine("B");
  console.log(resB);
  if (cancelObj.cancelRequested) {
    throw new CancelError("Canceled");
  }
  // ... 매 await 마다 반복
}
main.ts 
const cancelObj = { cancelRequested: false };
cancelable(cancelObj).catch((err) => {
  if (err instanceof CancelError) {
    console.log("Canceled");
  } else {
    console.error(err);
  }
});

setTimeout(() => {
  cancelObj.cancelRequested = true;
}, 1000);
!

이미 시작된 작업은 계속 돌아간다

cancelRequested = true 로 바꿔도 실행 중인 asyncRoutine 은 멈추지 않는다. 다음 확인 지점에 도달해야 비로소 중단된다. 즉 취소의 응답 시간은 확인 지점의 간격에 달려 있다.

노트의 예제는 CancelError 를 catch 에서 검사하지만 cancelable 안에서는 일반 Error 를 던지고 있어, 그 분기가 실제로는 타지 않는다. 위 코드는 CancelError 로 통일했다.

비동기 호출 래핑

  • 취소 코드가 많아지면 실제 비즈니스 로직을 알아보기 어려워진다.
  • 래핑 함수 안에 취소 로직을 넣어 추가되는 코드를 줄일 수 있다.
createCancelWrapper.ts 확인 로직을 한 곳으로 
class CancelError extends Error {}

function createCancelWrapper() {
  let cancelRequested = false;

  function cancel() {
    cancelRequested = true;
  }

  function cancelWrapper(
    func: (...args: any[]) => Promise<any>,
    ...args: any[]
  ) {
    if (cancelRequested) {
      return Promise.reject(new CancelError("Canceled"));
    }

    return func(...args);
  }

  return { cancel, cancelWrapper };
}
usage.ts 
const { cancel, cancelWrapper } = createCancelWrapper();

async function cancelable() {
  const resA = await cancelWrapper(asyncRoutine, "A");
  console.log(resA);
  const resB = await cancelWrapper(asyncRoutine, "B");   // if 문이 사라졌다
  console.log(resB);
}

if (cancelObj.cancelRequested) throw ... 두 줄이 cancelWrapper( 라는 한 겹의 호출로 줄었다. 8-1 프록시의 발상을 함수 호출에 적용한 것이다.

AbortController / AbortSignal 이 정확히 이 문제를 위한 표준 취소 프로토콜이다. Node v24.17.0 에서 전역으로 사용 가능함을 확인했다. 위의 수제 cancelObj 대신 이것을 쓰면 코어 API 들이 직접 협조한다는 큰 이점이 생긴다 — fetch, fs/promises, timers/promises, stream/promises 의 pipeline 등이 모두 signal 옵션을 받는다.

const ac = new AbortController();
const { signal } = ac;

async function cancelable() {
  await delay(1000, undefined, { signal });   // 취소되면 여기서 던진다
  signal.throwIfAborted();                    // 직접 확인도 가능
  await doSomething();
}

cancelable().catch((err) => {
  if (err.name === "AbortError") console.log("Canceled");
});

setTimeout(() => ac.abort(), 500);

취소 사유(signal.reason)를 전달할 수 있고, AbortSignal.timeout(ms) 로 타임아웃 시그널을 바로 만들 수도 있다.

정리

  • Promise 는 취소를 지원하지 않는다 — 취소는 작업 쪽의 협조로만 가능하다
  • 매 await 뒤에 확인 지점을 두는 것이 기본형. 응답 시간은 확인 간격에 비례
  • 확인 로직을 래퍼 함수로 모으면 비즈니스 로직이 다시 읽힌다
  • 지금은 AbortController / AbortSignal 이 표준이며, 코어 API 들이 직접 지원한다

CPU 바운드 작업 실행

이벤트 루프 모델의 유일하고 결정적인 약점, 그리고 세 가지 대처법.

핵심 1-2에서 본 리액터 패턴의 전제는 "핸들러는 금방 끝난다"였다. 그 전제가 깨지는 순간 서버 전체가 멈춘다. 해결책은 쪼개거나, 다른 곳으로 보내거나 둘 중 하나다.

CPU 바운드 작업 실행

  • 오랜 시간이 걸리고 완료될 때까지 이벤트 루프에 제어권을 돌려주지 않는 동기 작업을 CPU 바운드라고 부른다.
  • 주된 특징은 I/O 가 많지 않고 CPU 사용률이 높다는 것이다.
  • Node.js 는 단일 스레드에서 작동하므로, 오래 걸리는 작업을 동기적으로 실행하면 다른 요청을 아예 받을 수 없다.
subsetSum-blocking.ts 계산 중 서버가 멈춘다 
import EventEmitter from "events";
import { createServer } from "http";

class SubsetSum extends EventEmitter {
  private totalSubsets: number;

  constructor(private sum: number, private set: number[]) {
    super();
    this.totalSubsets = 0;
  }

  _combine(set: number[], subset: number[]) {
    for (let i = 0; i < set.length; i++) {
      const newSubset = subset.concat(set[i]);
      this._combine(set.slice(i + 1), newSubset);
      this._processSubset(newSubset);
    }
  }

  _processSubset(subset: number[]) {
    const res = subset.reduce((prev, item) => prev + item, 0);
    if (res === this.sum) {
      this.emit("match", subset);
    }
  }

  start() {
    this._combine(this.set, []);
    this.emit("end");
  }
}

createServer((req, res) => {
  const url = new URL(req.url!, "http://localhost");

  if (url.pathname !== "/subsetSum") {
    res.writeHead(200);
    return res.end("im alive");
  }

  const data = JSON.parse(url.searchParams.get("data")!);
  const sum = parseInt(url.searchParams.get("sum")!);

  res.writeHead(200);
  const subsetSum = new SubsetSum(sum, data);
  subsetSum.on("match", (match) => {
    res.write(`match: ${match}\n`);
  });

  subsetSum.on("end", () => {
    res.end();
  });

  subsetSum.start();
}).listen(8000, () => console.log("server running on 8000"));

계산이 도는 동안 / 로 보낸 "im alive" 요청조차 응답되지 않는다. 한 사용자의 무거운 요청이 모든 사용자를 멈춰 세운다.

setImmediate를 사용한 인터리빙

  • 가장 간단한 방법은 각 단계가 끝날 때마다(또는 일정 횟수마다) 제어권을 이벤트 루프에 넘겨주는 것이다.
  • 보류 중인 I/O 요청 뒤에 실행되도록 다음 단계를 예약한다.
부분집합 합계 알고리즘의 단계 인터리빙
subsetSum-interleaved.ts 
class SubsetSum extends EventEmitter {
  private runningCombine: number;

  constructor(private sum: number, private set: number[]) {
    super();
    this.runningCombine = 0;
  }

  _combine(set: number[], subset: number[]) {
    for (let i = 0; i < set.length; i++) {
      const newSubset = subset.concat(set[i]);
      /**
       * 각 단계를 setImmediate 로 이벤트 루프에 미뤄
       * 보류 중인 I/O 요청 뒤에 실행되도록 한다
       */
      this._combineInterleaved(set.slice(i + 1), newSubset);
      this._processSubset(newSubset);
    }
  }

  _processSubset(subset: number[]) {
    const res = subset.reduce((prev, item) => prev + item, 0);
    if (res === this.sum) {
      this.emit("match", subset);
    }
  }

  /**
   * 기존 _combine 을 setImmediate 로 연기하고, 진행 중인 개수를 센다
   */
  _combineInterleaved(set: number[], subset: number[]) {
    this.runningCombine++;
    setImmediate(() => {
      this._combine(set, subset);
      if (--this.runningCombine === 0) {
        this.emit("end");        // 전부 끝났을 때만 end
      }
    });
  }

  start() {
    this.runningCombine = 0;
    this._combineInterleaved(this.set, []);
    // 여기서 emit("end") 를 하면 안 된다
  }
}

원문 교정 — start() 의 emit("end") 원문 교정

노트의 인터리빙 버전 start() 는 이렇게 되어 있다.

원문
start() {
  this.runningCombine = 0;
  this._combineInterleaved(this.set, []);
  this.emit("end");     // ← 계산이 시작도 하기 전에 호출된다
}

_combineInterleaved 는 setImmediate 로 실제 계산을 미루고 즉시 반환하므로, 바로 다음 줄의 emit("end") 는 계산이 시작되기도 전에 실행된다. 서버 코드가 end 에서 res.end() 를 호출하므로 응답이 곧바로 닫히고 match 는 하나도 전달되지 않는다.

인터리빙 버전에서 end 는 runningCombine 이 0 이 될 때 _combineInterleaved 안에서만 발행되어야 한다. 블로킹 버전의 start() 에서 그대로 복사하면서 남은 줄로 보인다.

또 그 카운터다 보강

runningCombine 은 4-2의 병렬 실행 카운터, 6-3의 ParallelStream.running 과 정확히 같은 역할이다. 비동기로 흩어 놓은 작업이 언제 다 끝났는지 아는 방법은 결국 세는 것뿐이다.

인터리빙 방식에 대한 고려사항
  • 매우 간단하게 해결되지만 최선의 방법은 아니다.
  • 작업을 연기할 때마다 생기는 작은 오버헤드가, 알고리즘의 모든 단계에 곱해져 전체 실행 시간에 상당한 영향을 준다.
  • 이런 경우 이벤트 루프가 응답성을 잃고 앱 전체가 지연되므로 프로덕션에서는 추천하지 않는다.

외부 프로세스의 사용

  • 이벤트 루프 차단을 막는 또 다른 방법은 자식 프로세스를 쓰는 것이다.
  • 메인 앱에서 비싼 CPU 작업을 하지 말고 별도 프로세스에 위임한다.
  • 코어 모듈 child_process.fork() 로 자식 프로세스를 만든다.
부분집합 합계 작업을 외부 프로세스에 위임

  • CPU 바운드 작업은 리액터 패턴의 전제("핸들러는 금방 끝난다")를 깬다
  • setImmediate 인터리빙은 간단하지만 오버헤드가 단계 수만큼 곱해진다 → 프로덕션 부적합
  • 실전 해법은 별도 프로세스/워커에 위임하고 풀로 관리하는 것
  • 인터리빙 버전에서 end 는 진행 카운터가 0 이 될 때만 발행해야 한다
  • 지금은 worker_threads 가 기본 선택지 — 가볍고 데이터 전송이 싸다
