4-1

비동기 프로그래밍의 어려움

콜백 지옥은 언어의 결함이 아니라 규칙의 부재다.

핵심 문제는 비동기 자체가 아니라 익명 함수를 남용해 코드가 한 덩어리로 뭉치는 것이다. 이름을 붙이고 밖으로 꺼내는 것만으로 대부분 해결된다.
  • 클로저와 익명 함수는 개발자가 코드베이스 이곳저곳을 옮겨 다니지 않고 원활하게 작업하도록 도와준다.
  • 대부분의 경우 익명 함수를 만드는 것이 절대적으로 요구되지는 않는다. 비동기 프로그래밍 자체보다 규칙 문제가 더 중요하다.

콜백 지옥

  • 많은 클로저와 익명 함수 정의가 코드의 가독성을 떨어뜨리고 관리 불가능한 덩어리로 만드는 상황.
  • 바로 보이는 건 가독성 문제다. 중첩이 깊으면 추적이 불가능해진다.
  • 예제처럼 err 같은 변수 이름이 계속 중복되면서 섀도잉이 발생한다.
callback-hell.ts 피라미드 
asyncFoo((err) => {
  asyncBar((err) => {
    asyncFooBar((err) => {
      // ...
    });
  });
});
!

가독성보다 위험한 것

안쪽 err 이 바깥쪽 err 을 가리기 때문에, 바깥 에러를 참조하려는 코드가 조용히 엉뚱한 값을 읽는다. 들여쓰기는 눈에 보이지만 섀도잉은 보이지 않는다. 이쪽이 실제 버그의 원천이다.

정리

  • 콜백 지옥의 원인은 비동기가 아니라 익명 함수 남용
  • 증상 1: 중첩 깊이로 인한 추적 불가
  • 증상 2: 같은 이름의 변수 섀도잉 — 이쪽이 더 위험하다
  • 해법은 4-2의 규칙들 — 빠른 반환, 이름 붙이기, 모듈화
4-2

콜백 모범 사례와 제어 흐름 패턴

순차 · 병렬 · 제한된 병렬. 세 가지 제어 흐름을 손으로 짜 보면 Promise가 무엇을 대신해 주는지 보인다.

핵심 비동기 제어 흐름은 결국 카운터 하나로 요약된다. "몇 개 끝났나"를 세다가 목표치에 도달하면 다음으로 넘어간다 — 순차든 병렬이든 제한된 병렬이든 마찬가지다.

콜백 규칙

  • 콜백을 정의할 때 익명 함수 정의를 남용하지 않는다.
    • 가능하면 빠르게 함수를 종료한다.
    • 콜백을 위한 함수를 따로 만들어 클로저 바깥에 배치하고, 중간 결과를 인자로 전달한다.
    • 재사용 가능한 함수들로 분할하여 모듈화한다.

콜백 규칙 적용

1. else 구문 제거하기 — 빠른 반환 원칙
전
if (err) {
  cb(err);
} else {
  // 에러가 없을 때 실행할 코드
}
후
if (err) {
  return cb(err);
}

// 에러가 없을 때 실행할 코드

return 하나로 들여쓰기 한 단계가 사라진다. 중첩이 3~4단이면 이것만으로 체감이 크게 달라진다.

2. 재사용 가능한 코드의 구분 시도하기
  • 콜백 안에 명령형 코드를 그대로 쓰지 말고 외부로 분리한다.
  • 재사용 가능성과 테스트 가능성이 함께 올라간다.

순차 실행

  • 비동기 작업이 완료될 때 다음 작업을 호출하는 가장 일반적인 방법이다.
  • 작업의 모듈화에 중점을 두면, 비동기 코드를 처리할 때 굳이 클로저가 필요하지 않다는 점을 보여준다.
sequential.ts 
function task1(cb: () => void) {
  asyncOperation(() => {
    task2(cb);
  });
}

function task2(cb: () => void) {
  asyncOperation(() => {
    task3(cb);
  });
}

function task3(cb: () => void) {
  asyncOperation(() => {
    cb();
  });
}

task1(() => {
  console.log("task 1, 2, 3 are done");
});

// output: task 1, 2, 3 are done

중첩이 사라진 것이 아니라 펼쳐졌을 뿐이다. 하지만 각 태스크가 독립적으로 이름을 갖고 따로 테스트할 수 있게 되었다는 점이 다르다.

순차 반복

  • 순차 실행은 작업의 수와 내용을 미리 알고 있을 때 완벽하게 작동한다.
  • 하지만 컬렉션의 각 항목에 대해 비동기 작업을 순서대로 실행해야 한다면 이 방식으로는 불가능하다. 태스크의 개수를 코드 작성 시점에 모르기 때문이다.
!

원본 노트가 여기서 끊겨 있습니다

노트에는 이 자리에 # ............ 만 남아 있어 구현이 비어 있다. 아래는 책의 순차 반복(sequential iteration) 패턴을 표준 형태로 복원한 것으로, Node v24.17.0 에서 동작을 확인했다. 원문의 주장을 새로 만든 것이 아니라 바로 위 두 문장이 예고한 코드를 채운 것이다.

sequential-iteration.ts 재귀로 인덱스를 전진시킨다 
function iterate(collection: string[], index: number, finish: () => void) {
  if (index === collection.length) {
    return finish();          // 끝났다
  }

  asyncOperation(collection[index], () => {
    iterate(collection, index + 1, finish);   // 다음 항목으로
  });
}

iterate(collection, 0, () => {
  console.log("모든 항목 처리 완료");
});
flowchart LR
  I0["iterate(0)"] --> A0["asyncOperation(item 0)"]
  A0 --> I1["iterate(1)"]
  I1 --> A1["asyncOperation(item 1)"]
  A1 --> I2["iterate(2)"]
  I2 --> Q{"index === length?"}
  Q -->|"예"| F["finish()"]
  Q -->|"아니오"| A2["asyncOperation(item 2)"]
루프가 아니라 꼬리 재귀다 — for 문 안에서 비동기 호출을 하면 전부 동시에 출발해 버린다. 순서를 지키려면 "콜백이 다음 반복을 호출"하는 구조여야 한다.

병렬 실행

  • Node는 논 블로킹 성질 덕분에 단 하나의 스레드로 동시성을 달성할 수 있다.
  • 작업들은 논 블로킹 API 위에서 실행되고 이벤트 루프에 의해 인터리빙된다.
패턴
  • 모든 작업을 한꺼번에 시작하고, 완료 카운트가 전체 개수에 도달하면 finish 를 호출한다.
  • 한 번에 모든 태스크를 동시에 실행하면 경쟁 상태(race condition)가 발생할 수 있다.
parallel.ts 
const tasks = [
  /*...*/
];

let completed = 0;

tasks.forEach((task) => {
  task(() => {
    if (++completed === tasks.length) {
      finish();
    }
  });
});

function finish() {
  console.log("all tasks are done");
}
flowchart TB
  S["forEach 로 전부 시작"] --> T1["task 1"]
  S --> T2["task 2"]
  S --> T3["task 3"]
  T1 --> C["completed++"]
  T2 --> C
  T3 --> C
  C --> Q{"completed === tasks.length?"}
  Q -->|"예"| F["finish()"]
  Q -->|"아니오"| W["대기"]
병렬 실행의 전부는 카운터 하나다 — 완료 순서는 보장되지 않지만 "몇 개 끝났는지"만 세면 언제 끝났는지는 알 수 있다. Promise.all() 이 내부에서 하는 일도 정확히 이것이다.
동시 작업과 경쟁 상태 수정
  • Node에서 여러 비동기 작업을 병렬로 실행하는 것은 리소스 측면에서 직관적이고 비용이 적다.
  • 모든 것이 단일 스레드에서 실행되므로 일반적으로 정교한 동기화 메커니즘이 필요하지 않다.
spider.ts Set 하나로 중복 방지 
const spidering = new Set();

function spider(url: string, nesting: number, cb: () => void) {
  if (spidering.has(url)) {
    return process.nextTick(cb);
  }

  spidering.add(url);
  // ... 실제 크롤링
}

각 작업을 Set 에 기록해 동시에 여러 개의 spider() 가 같은 URL 을 처리하는 것을 막는다.

여기서도 Zalgo 를 피한다 보강

이미 처리 중인 URL 일 때 cb() 를 바로 부르지 않고 process.nextTick(cb) 로 감싼 이유가 있다. 그냥 부르면 캐시 히트일 때만 동기가 되어 3-1에서 본 Zalgo 가 그대로 재현된다. 이 한 줄이 그 방지책이다.

제한된 병렬 실행

  • 제어되지 않는 병렬 작업 생성은 과부하를 일으킬 수 있다.
  • 무한한 병렬 작업을 생성하는 서버는 DoS 공격에 취약하다.
전역적 동시성 제한
  • 현재 진행 중인 작업 수가 최대치보다 작고, 아직 시작하지 않은 작업이 남아 있을 때만 새 작업을 시작한다.
  • 일반적으로 이 패턴은 작업 목록이 미리 정해져 있거나, 시간이 지나며 작업 수가 선형적으로 증가할 때 적합하다.
limited-parallel.ts 
const tasks: any[] = [
  // ...
];

const concurrency = 2;
let running = 0;
let completed = 0;
let index = 0;

function next() {
  while (running < concurrency && index < tasks.length) {
    const task = tasks[index++];
    task(() => {
      if (++completed === tasks.length) {
        return finish();
      }

      running--;
      next();          // 슬롯이 비었으니 다음 작업 투입
    });

    running++;
  }
}

next();

function finish() {
  console.log("all tasks are done");
}
슬롯이 비면 채운다 — 병렬 실행의 카운터에 running 이라는 상한 조건 하나가 추가됐을 뿐이다. 이 구조가 그대로 p-limit 같은 라이브러리의 핵심이다.
큐를 사용한 해결
  • 동시성 제한을 넘지 않는 한 큐에서 가능한 한 많은 작업을 시작한다.
  • 새 작업을 동적으로 큐에 추가할 수 있다는 것이 앞의 방식과의 차이다.
TaskQueue.ts 
class TaskQueue {
  private concurrency: number; // 동시성 제한
  private queue: any[];        // 보류 중인 작업 저장
  private running: number;     // 실행 중인 작업 개수
  private completed: number;

  constructor(concurrency: number) {
    this.concurrency = concurrency;
    this.queue = [];
    this.running = 0;
    this.completed = 0;
  }

  pushTask(task: any) {
    this.queue.push(task);

    // process.nextTick 으로 넘기면 this 컨텍스트를 잃으므로 bind 사용
    process.nextTick(this.next.bind(this));
    return this;
  }

  next() {
    while (this.running < this.concurrency && this.queue.length) {
      const task = this.queue.shift();
      task(() => {
        this.running--;
        process.nextTick(this.next.bind(this));
      });
      this.running++;
    }
  }
}
큐 개선하기
  • 이벤트를 발생시키기 위해 EventEmitter 를 상속받는다.
  • 에러 핸들링과 "더 이상 작업이 없다"는 empty 이벤트를 추가한다.
TaskQueue.ts (EventEmitter 버전) 
import EventEmitter from "events";

class TaskQueue extends EventEmitter {
  private concurrency: number;
  private queue: any[];
  private running: number;
  private completed: number;

  constructor(concurrency: number) {
    super();

    this.concurrency = concurrency;
    this.queue = [];
    this.running = 0;
    this.completed = 0;
  }

  pushTask(task: any) {
    this.queue.push(task);
    process.nextTick(this.next.bind(this));
    return this;
  }

  next() {
    if (this.running === 0 && this.queue.length === 0) {
      return this.emit("empty");
    }

    while (this.running < this.concurrency && this.queue.length) {
      const task = this.queue.shift();
      task((err: unknown) => {
        if (err) {
          return this.emit("error", err);
        }

        this.running--;
        process.nextTick(this.next.bind(this));
      });
      this.running++;
    }
  }
}

const queue = new TaskQueue(2);
queue
  .on("empty", () => {
    console.log("all tasks are done");
  })
  .on("error", (err) => {
    console.error(err);
  });

원문 교정 원문 교정

노트의 next() 는 empty 검사를 while 문으로 감싸고 있다 (while (this.running === 0 && this.queue.length === 0)). 조건이 참일 때 return 하므로 결과적으로는 한 번만 돌지만, 루프가 아니라 단순 분기이므로 if 로 쓰는 것이 의도에 맞다. 위 코드는 그렇게 고쳐 두었다.

또한 에러 발생 시 this.running-- 없이 바로 return this.emit("error", err) 하기 때문에, 실패한 작업이 슬롯을 영구히 점유해 결국 큐가 멈춘다. 실무에서는 running-- 을 먼저 하고 에러를 emit 해야 한다.

i

지금 이 코드를 쓸 일이 있을까 보강

실무에서 이 세 패턴을 직접 짤 일은 거의 없다. 순차는 for await, 병렬은 Promise.all(), 제한된 병렬은 p-limit 이나 Promise.all + 세마포어로 대체된다(5-2). 그럼에도 짜 보는 이유는, 이 구조를 알아야 Promise.all 이 왜 하나라도 실패하면 즉시 reject 하는지, 왜 동시성 제한은 표준에 없는지가 이해되기 때문이다.

정리

  • 빠른 반환 + 이름 붙여 밖으로 꺼내기 = 콜백 지옥 해소의 90%
  • 순차 실행은 콜백이 다음 태스크를 호출, 순차 반복은 인덱스를 전진시키는 재귀
  • 병렬 실행은 완료 카운터 하나. Promise.all() 이 하는 일이 이것이다
  • 제한된 병렬은 여기에 running < concurrency 조건을 더한 것
  • 큐로 만들면 작업을 동적으로 추가할 수 있고, EventEmitter 상속으로 완료/에러를 알릴 수 있다

2026년 기준으로는 보강

콜백 기반 async 라이브러리를 새 코드에 도입할 이유는 거의 없다. 같은 역할이 표준과 소형 패키지로 흡수되었다.

  • 순차 → for await (const x of items)
  • 병렬 → Promise.all() / Promise.allSettled()
  • 제한된 병렬 → p-limit, p-map (concurrency 옵션)
  • 큐 → p-queue

레거시 코드에서 async 를 만났을 때 읽을 수 있으면 충분하다.

정리

  • 원본 노트 미완성 — 내용을 채우지 않고 주제만 표시
  • 이 절의 요지는 "손으로 짠 패턴을 라이브러리로 대체하기"
  • 지금은 for await / Promise.all / p-limit 조합이 사실상의 표준
