6-1

스트림의 중요성 발견

메모리와 시간은 부차적이다. 스트림의 진짜 가치는 조립할 수 있다는 것이다.

핵심 버퍼링은 다 모은 다음 한 번에, 스트리밍은 오는 대로 바로. 이 차이가 메모리 상수화, 지연 시간 단축, 그리고 pipe() 로 부품을 갈아 끼우는 조립성을 동시에 만든다.

버퍼링 vs 스트리밍

지금까지 다룬 대부분의 비동기 API 는 버퍼 방식을 사용한다.

구분버퍼링스트리밍
동작완료될 때까지 들어오는 데이터를 버퍼에 저장새 데이터 청크가 수신되는 대로 소비자에게 전달
전달 시점수집 완료 후 Blob 형태로 한 번에즉시, 청크 단위로
메모리입력 크기에 비례일정 (버퍼 크기)
첫 바이트까지의 시간전체 수집 완료 후거의 즉시

단순히 효율성 관점에서만 봐도 공간(메모리)과 시간(계산) 양쪽에서 스트림이 유리할 수 있다. 하지만 Node의 스트림에는 그보다 더 중요한 조립성이 있다.

공간(메모리) 효율성

  • 매우 큰 파일을 읽어 큰 버퍼를 반환하는 것은 좋은 방법이 아니다.
  • 동시에 여러 개의 큰 파일을 읽으면 쉽게 메모리가 부족해진다.
버퍼링 API를 사용한 Gzipping
gzip-buffered.ts 파일 크기만큼 메모리를 쓴다 
import { promises as fs } from "fs";
import { gzip } from "zlib";
import { promisify } from "util";

const gzipPromise = promisify(gzip);

const filename = process.argv[2];

async function main() {
  const data = await fs.readFile(filename);
  const gzippedData = await gzipPromise(data);
  await fs.writeFile(`${filename}.gz`, gzippedData);
  console.log("Compressed Successfully");
}

main();

// command: npx ts-node src/app.ts static/filename

작은 용량이라면 괜찮지만, 큰 파일은 버퍼의 최대 용량을 초과해 에러가 발생한다.

↑

버퍼 상한이 바뀌었다 최신 반영

노트의 "Node v20 기준 최대 버퍼 크기 4GB"는 당시 기준으로 정확했다. 하지만 Node v22.0.0 부터 buffer.constants.MAX_LENGTH 가 4GiB → 8PiB(2^53-1)로 늘어났다. V8 을 12.4.254.14 로 올리면서 생긴 변화다. Node v24.17.0 에서 값이 9007199254740991 임을 확인했다. (근거: nodejs/node#54207)

그렇다고 버퍼링이 안전해진 것은 아니다. 실질적인 벽은 두 개 더 있다. 하나는 문자열 상한(MAX_STRING_LENGTH, 64비트에서 약 512MB — 위 런타임에서 536870888 확인)이고, 다른 하나는 프로세스가 실제로 쓸 수 있는 물리 메모리다. 1GB 파일 열 개를 동시에 버퍼링하면 상수가 8PiB 여도 프로세스는 죽는다.

스트림을 사용한 Gzipping
  • 모두 읽은 뒤 수행하는 것이 아니라 청크 단위로 읽는 대로 바로 수행한다.
  • 모든 크기의 파일에 대해 일정한 메모리를 사용한다.
  • 청크의 순서도 Node 가 알아서 유지시켜 준다.
gzip-stream.ts 메모리 상수 
import { createReadStream, createWriteStream } from "fs";
import { createGzip } from "zlib";

const filename = process.argv[2];

createReadStream(filename)
  .pipe(createGzip())
  .pipe(createWriteStream(`${filename}.gz`))
  .on("finish", () => console.log("Compressed Successfully"));

버퍼링은 단계마다 전체를 들고 있어야 한다 — 스트리밍은 한 번에 청크 하나만 들고 있으면 되므로, 메모리 사용량이 파일 크기와 무관해진다. 파이프라인이 길어져도 마찬가지다.

시간 효율성

  • 서버에서는 데이터를 실시간으로 청크 단위로 받으면서 바로 저장한다.
  • 모든 데이터 다운로드가 끝나기를 기다리지 않아도 되므로 효율적이다.
server.ts 
import { createWriteStream } from "fs";
import { createServer } from "http";
import { basename, join } from "path";
import { createGunzip } from "zlib";

const server = createServer((req, res) => {
  const filename = basename(req.headers["x-filename"] as string);
  const destFilename = join("received_files", filename);
  console.log("File request receive");
  req
    .pipe(createGunzip())
    .pipe(createWriteStream(destFilename))
    .on("finish", () => {
      res.writeHead(201, { "Content-Type": "text/plain" });
      res.end("That's it\n");
      console.log(`File saved: ${destFilename}`);
    });
});

server.listen(3000, () =>
  console.log("Server running on http://localhost:3000")
);
client.ts 
import { createReadStream } from "fs";
import { request } from "http";
import { createGzip } from "zlib";

const filename = process.argv[2];
const serverHost = process.argv[3];

const httpRequestOptions = {
  hostname: serverHost,
  port: 3000,
  path: "/",
  method: "PUT",
  headers: {
    "Content-Type": "application/octet-stream",
    "Content-Encoding": "gzip",
    "X-Filename": filename,
  },
};

const req = request(httpRequestOptions, (res) => {
  console.log(`Server response: ${res.statusCode}`);
});

createReadStream(filename)
  .pipe(createGzip())
  .pipe(req)
  .on("finish", () => {
    console.log("File send complete");
  });

다섯 단계가 동시에 돌아간다 — 버퍼링이라면 읽기가 100% 끝나야 압축이 시작되지만, 스트리밍에서는 첫 청크가 쓰이는 동안 마지막 청크는 아직 읽히고 있다. 이것이 "시간 효율성"의 실체다.

조립성

  • pipe() 함수는 스트림을 구성하는 방법에 대한 명확한 개요를 제공한다.
  • 여러 개의 단일 책임 프로세스를 연결할 수 있다.
  • 전제조건은 이전 스트림이 반환한 데이터 유형이 다음 스트림이 받는 유형과 맞아야 한다는 것이다. 데이터 유형에는 바이너리, 텍스트, 객체 등이 있다.
i

조립성이 왜 가장 중요한가 보강

위 파이프라인에 암호화를 추가하고 싶다면 .pipe(createCipheriv(...)) 한 줄이면 된다. 나머지 코드는 하나도 바뀌지 않는다. 메모리와 시간 이득은 측정해야 보이지만, 조립성은 코드를 고칠 때마다 체감된다. 6-4 파이핑 패턴이 이 성질을 끝까지 밀어붙인다.

정리

  • 버퍼링 = 전부 모은 뒤 한 번에 / 스트리밍 = 오는 대로 청크 단위로
  • 공간: 파일 크기와 무관하게 메모리 상수. 버퍼링은 상한(과 실제 RAM)에 부딪힌다
  • 시간: 파이프라인의 모든 단계가 동시에 진행되어 첫 결과가 훨씬 빨리 나온다
  • 조립성: 단일 책임 스트림을 pipe() 로 갈아 끼운다 — 실무에서 가장 크게 체감되는 이득
6-2

스트림 시작하기

네 개의 추상 클래스와 배압(backpressure) 하나. 스트림의 전부가 여기 있다.

핵심 write() 가 false 를 반환하면 멈추고 drain 을 기다려라. 이 한 줄의 규약을 지키지 않으면 스트림을 써도 메모리가 터진다.

스트림 해부

  • Node의 스트림은 코어 모듈의 네 가지 추상 클래스 중 하나의 구현이다 — Readable, Writable, Duplex, Transform.
  • 스트림은 EventEmitter 의 인스턴스다.
    • end — 읽기 가능한 스트림이 읽기를 마쳤을 때
    • finish — 쓰기 스트림이 완료됐을 때
    • error — 무언가 잘못됐을 때
  • 스트림이 매우 유연한 이유 중 하나는 바이너리뿐 아니라 거의 모든 자바스크립트 값을 처리할 수 있다는 것이다.
    • Binary 모드 — 버퍼 또는 문자열 청크 형태로 스트리밍
    • 객체 모드 — 데이터를 일련의 개별 객체로 스트리밍
flowchart TB
  S["Stream (EventEmitter)"] --> R["Readable — _read()"]
  S --> W["Writable — _write()"]
  R --> D["Duplex — _read() + _write()"]
  W --> D
  D --> T["Transform — _transform() + _flush()"]
  T --> P["PassThrough — 변환 없이 통과"]
Duplex 는 Readable 과 Writable 을 겹친 것, Transform 은 둘을 연결한 Duplex 다 — Duplex 는 읽기와 쓰기가 무관하지만(소켓), Transform 은 쓴 것이 변환되어 읽힌다(gzip).

Readable 스트림

데이터를 받는 방법이 두 가지 있다.

non-flowing 모드
  • Readable 스트림에서 읽기의 기본 패턴이다.
  • readable 이벤트에 리스너를 연결하고, 그 안에서 read() 로 직접 꺼낸다.
  • 네트워크 프로토콜을 구현하거나 특정 데이터 형식을 구문 분석할 때 유용하다.
non-flowing.ts 
process.stdin
  .on("readable", () => {
    let chunk: Buffer;

    console.log("New data is available");

    /**
     * read 는 스트림 내부 버퍼에서 데이터 청크를 가져오는 동기 작업
     * 데이터 형식은 기본적으로 Buffer 타입
     * 더 이상 읽을 값이 없다면 null 을 반환함
     */
    while ((chunk = process.stdin.read()) !== null) {
      console.log(`Chunk read: (${chunk.length}), (${chunk.toString()})`);
    }
  })
  .on("end", () => {
    console.log("End of stream");
  });

/**
 * New data is available
 * Chunk read: (12), (hello asdasd)
 * New data is available
 * End of stream
 */
flowing 모드
  • data 이벤트에 리스너를 연결하면 스트림이 flowing 모드로 전환된다.
  • read() 로 꺼내는 것이 아니라 도착하는 대로 리스너로 바로 전달된다.
  • non-flowing 모드보다 데이터 흐름 제어의 유연성이 떨어진다.
  • 일시 중단하려면 pause() 를 사용해 버퍼에 캐싱할 수 있다.

process.stdin
  .on("data", (chunk) => {

비동기 iterator
  • Readable 스트림은 비동기 이터러블이기도 하다.
  • 전체 Readable 스트림을 소비하고 Promise 를 반환하는 함수가 필요할 때 매우 유용하다.
async-iterator.ts 가장 읽기 쉬운 방법 
async function main() {
  for await (const chunk of process.stdin) {
    console.log(
      `New data is available: (${chunk.length}), (${chunk.toString()})`
    );
  }

  console.log("End of stream");
}

이 방식이 배압도 공짜로 준다

for await 는 루프 본문이 끝나야 다음 청크를 요청하므로, 소비 속도가 느리면 자연스럽게 생산도 느려진다. 아래에서 손으로 다뤄야 하는 배압이 언어 문법으로 흡수된 셈이다. 새 코드에서 Readable 을 소비할 때 첫 번째 선택지로 두면 좋다.

Readable 스트림 구현
  • Readable 클래스는 내부적으로 _read 를 호출하고, 이 함수는 push 로 내부 버퍼를 채운다.
  • read 는 사용자가 호출하는 메서드이고 _read 는 Node 가 호출하는 것이니 혼동하면 안 된다.
  • push(null) 이 스트림의 끝을 알린다.
RandomStream.ts 
import Chance from "chance";
import { Readable } from "stream";

const chance = new Chance();

class RandomStream extends Readable {
  private emittedBytes: number;

  constructor(options: any) {
    super(options);
    this.emittedBytes = 0;
  }

  _read(size: number) {
    const chunk = chance.string({ length: size });
    this.push(chunk, "utf-8");
    this.emittedBytes += chunk.length;
    if (chance.bool({ likelihood: 5 })) {
      this.push(null);            // 5% 확률로 종료
    }
  }
}

const randomStream = new RandomStream({});
randomStream
  .on("data", (chunk) => {
    console.log(chunk.toString());
  })
  .on("end", () => {
    console.log("End of stream");
  });

Writable 스트림

데이터가 흘러 들어갈 목적지를 나타내는 스트림이다.

스트림에 쓰기
  • write() 로 데이터를 쓴다.
  • end() 로 더 이상 기록할 데이터가 없음을 알린다. 최종 데이터 청크를 함께 넘길 수도 있다.
write.ts 배압을 무시한다 
import { Chance } from "chance";
import { createServer } from "http";

const chance = new Chance();

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });

  // 1% 확률로 종료되는 루프
  while (chance.bool({ likelihood: 99 })) {
    res.write(`${chance.string()}\n`);
  }
  res.end("\n\n");
  res.on("finish", () => {
    console.log("All data was sent");
  });
});

server.listen(8080, () => {
  console.log("Server is running on http://localhost:8080");
});
Backpressure(배압)
  • Node의 스트림은 소비할 수 있는 것보다 더 빨리 데이터가 기록되는 병목을 겪을 수 있다.
    • 들어오는 데이터를 버퍼링해 대처할 수 있다.
    • 하지만 스트림이 생산자에게 피드백을 주지 않으면 버퍼가 계속 쌓여 메모리 문제가 발생한다.
  • 배압 메커니즘은 내부 버퍼 크기를 제한하고, 버퍼가 비워지면 다시 쓰기를 시작해도 안전함을 알려 준다.
  • 이는 강제가 아니라 권고 메커니즘이다. write() 가 false 를 반환해도 계속 쓸 수는 있다 — 그저 메모리가 쌓일 뿐이다.
backpressure.ts drain 을 기다린다 
import { Chance } from "chance";
import { createServer } from "http";

const chance = new Chance();

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });

  function generateMore() {
    while (chance.bool({ likelihood: 95 })) {
      const randomChunk = chance.string({
        length: 16 * 1024 - 1,
      });
      const shouldContinue = res.write(randomChunk);
      if (!shouldContinue) {
        console.log("Backpressure");
        return res.once("drain", generateMore);   // 비워지면 재개
      }
    }
  }

  generateMore();
  res.on("finish", () => {
    console.log("All data was sent");
  });
});

server.listen(8080, () => {
  console.log("Server is running on http://localhost:8080");
});

  B-->>P: 'drain' 이벤트
  P->>B: write 재개
write() 의 반환값은 "더 써도 되냐"는 신호다 — false 는 실패가 아니라 "버퍼가 임계치를 넘었으니 drain 까지 쉬어라"는 뜻이다. 이 신호를 무시하면 스트림을 쓰면서도 버퍼링과 같은 메모리 문제를 겪는다.
↑

기본 highWaterMark 가 바뀌었다 최신 반영

위 예제가 청크 크기를 16 * 1024 - 1 로 잡은 것은 기본 highWaterMark 가 16KiB 였기 때문이다. Node 22 부터 기본값이 64KiB(65536)로 올라갔다. Node v24.17.0 에서 new Readable({read(){}}).readableHighWaterMark 와 fs.createReadStream(...).readableHighWaterMark 모두 65536 임을 확인했다.

따라서 위 코드를 최신 Node 에서 그대로 돌리면 배압이 예전만큼 자주 걸리지 않는다. 메모리에 민감한 환경이라면 stream.setDefaultHighWaterMark() 로 전역 기본값을 낮추거나, 스트림 생성 시 { highWaterMark: n } 을 직접 지정한다.

Writable 스트림 구현
  • Writable 을 상속하고 _write() 를 구현하면 된다.
  • 아래 예제는 객체를 받아 path 위치에 content 를 파일로 쓴다.
ToFileStream.ts 
import { Writable } from "stream";
import * as mkdirp from "mkdirp";
import { promises as fs } from "fs";
import { dirname } from "path";

class ToFileStream extends Writable {
  constructor(options: any) {
    super({ ...options, objectMode: true });
  }

  _write(
    chunk: any,
    encoding: BufferEncoding,
    callback: (error?: Error | null) => void
  ): void {
    mkdirp
      .mkdirp(dirname(chunk.path))
      .then(() => fs.writeFile(chunk.path, chunk.content))
      .then(() => callback())
      .catch(callback);
  }
}

const tfs = new ToFileStream({});

tfs.write({
  path: "static/fileA.txt",
  content: "Hello World",
});

tfs.write({
  path: "static/fileB.txt",
  content: "Hello World 2",
});

tfs.end(() => {
  console.log("done");
});

원문 교정 원문 교정

이 코드는 성공 경로에서 callback() 을 호출하지 않는다. _write 의 callback 은 "이 청크 처리를 끝냈다"는 신호라서, 부르지 않으면 스트림이 다음 청크를 처리하지 않고 end() 콜백도 실행되지 않는다. 즉 위 예제에서 "done" 은 영원히 출력되지 않는다.

또 fs.writeFile 앞에 return 이 없어 Promise 체인이 끊겨 있어, 쓰기 실패도 .catch(callback) 에 걸리지 않는다. 바로 위 클래스 버전이 올바른 형태다.

고친 형태
write(chunk, encoding, callback) {
  fs.mkdir(dirname(chunk.name), { recursive: true })
    .then(() => fs.writeFile(chunk.name, chunk.content))
    .then(() => callback())
    .catch(callback);
}

Duplex 스트림

  • 읽기와 쓰기가 동시에 가능한 스트림이다.
  • 네트워크 소켓처럼 데이터 소스이자 목적지인 엔티티를 설명할 때 유용하다.
  • _read() 와 _write() 를 모두 구현해야 한다.
  • 읽는 데이터와 쓰는 데이터 사이에 아무 관계가 없다는 것이 Transform 과의 차이다.

Transform 스트림

  • 데이터 변환을 처리하도록 설계된 특수한 Duplex 스트림이다.
  • _read() / _write() 대신 _transform() 과 _flush() 를 구현한다.
  • _flush() 는 스트림이 종료되기 직전에 호출되어 남은 데이터를 내보낼 마지막 기회를 준다.
Transform 스트림 구현
ReplaceStream.ts 
import { Transform, TransformCallback } from "stream";

class ReplaceStream extends Transform {
  private searchString: string;
  private replaceString: string;
  private tail: string;

  constructor(searchString: string, replaceString: string, options: any) {
    super(options);
    this.searchString = searchString;
    this.replaceString = replaceString;
    this.tail = "";
  }

  _transform(
    chunk: any,
    encoding: BufferEncoding,
    callback: TransformCallback
  ): void {
    const pieces = (this.tail + chunk).split(this.searchString);
    const lastPiece = pieces[pieces.length - 1];
    const tailLen = this.searchString.length - 1;
    this.tail = lastPiece.slice(-tailLen);
    pieces[pieces.length - 1] = lastPiece.slice(0, -tailLen);

    // 내부 읽기 버퍼로 데이터 저장
    this.push(pieces.join(this.replaceString));
    callback();
  }

  /**
   * 스트림이 종료되기 전에 호출되고 남은 데이터를 저장함
   */
  _flush(callback: TransformCallback): void {
    this.push(this.tail);
    callback();
  }
}

const replaceStream = new ReplaceStream("world", "node.js", {});

replaceStream.on("data", (chunk) => {
  console.log(chunk.toString());
});

replaceStream.write("hello world");
replaceStream.write("world");
replaceStream.end();

왜 tail 이 필요한가

청크 경계는 단어 경계와 무관하다. "...wor" 로 청크가 끝나고 다음 청크가 "ld..." 로 시작하면, 각 청크만 보고는 "world" 를 찾을 수 없다. 그래서 검색 문자열 길이 -1 만큼을 잘라 다음 청크 앞에 붙이는 것이다. 스트림에서 상태를 갖는 파서를 만들 때 반복해서 만나게 되는 패턴이다.

단순화된 생성자
simplified-transform.ts 
import { Transform } from "stream";

const searchStr = "World";
const replaceStr = "Node.js";
let tail = "";

const replaceStream = new Transform({
  defaultEncoding: "utf-8",
  transform(chunk, encoding, callback) {
    let pieces = (tail + chunk).split(searchStr);
    const lastPiece = pieces[pieces.length - 1];
    const tailLen = searchStr.length - 1;
    tail = lastPiece.slice(-tailLen);
    pieces[pieces.length - 1] = lastPiece.slice(0, -tailLen);
    this.push(pieces.join(replaceStr));
    callback();
  },
  flush(callback) {
    this.push(tail);
    callback();
  },
});
Transform 스트림을 사용한 데이터 필터링 및 집계
  • Transform 스트림은 데이터 변환 파이프라인을 구현하기 위한 완벽한 블록이다.
  • 아래 예시는 여러 해의 매출을 담은 큰 CSV 파일을 분석한다 — 필터와 집계를 각각 하나의 스트림으로.
filter-aggregate.ts 
import { Parser } from "csv-parse";
import { createReadStream } from "fs";
import { Transform, TransformCallback } from "stream";

/**
 * country 필드를 기준으로 데이터를 필터링하는 Transform 스트림
 */
class FilterByCountry extends Transform {
  private country: string;

  constructor(country: string, options: any) {
    super(options);
    this.country = country;
  }

  _transform(
    chunk: any,
    encoding: BufferEncoding,
    callback: TransformCallback
  ): void {
    if (chunk.country === this.country) {
      this.push(chunk);       // 조건에 맞을 때만 흘려보낸다
    }
    callback();
  }
}

/**
 * 금액의 합계를 처리하는 Transform 스트림
 */
class SumProfit extends Transform {
  private total: number;

  constructor(options: any) {
    super(options);
    this.total = 0;
  }

  _transform(
    chunk: any,
    encoding: BufferEncoding,
    callback: TransformCallback
  ): void {
    this.total += Number.parseFloat(chunk.profit);
    callback();               // 중간에는 아무것도 push 하지 않는다
  }

  _flush(callback: TransformCallback): void {
    this.push(this.total.toString());   // 끝날 때 한 번만
    callback();
  }
}

const csvParser = new Parser({ columns: true });

createReadStream("static/transform.csv")
  .pipe(csvParser)
  .pipe(new FilterByCountry("italy", { objectMode: true }))
  .pipe(new SumProfit({ objectMode: true }))
  .pipe(process.stdout);

필터는 N개를 받아 M개를 내보내고(M ≤ N), 집계는 N개를 받아 1개를 내보낸다. Transform 이 1:1 변환에만 쓰이는 것이 아니라는 점이 여기서 드러난다.

PassThrough 스트림

  • 변환을 적용하지 않고 모든 청크를 그대로 출력하는 특수한 Transform 이다.
  • 관찰이 가능하고, 느린 파이프 연결과 지연 스트림을 구현하는 데 유용하다.
관찰 가능성(Observability)
monitor.ts 
import { PassThrough } from "stream";

let bytesWritten = 0;

const monitor = new PassThrough();
monitor.on("data", (chunk) => {
  bytesWritten += chunk.length;
});

monitor.on("finish", () => {
  console.log(`${bytesWritten} bytes written`);
});

monitor.write("hello");
monitor.write("world");
monitor.end(); // 10 bytes written

createReadStream("static/transform.csv")
  .pipe(createGzip())
  .pipe(monitor)                                     // 계측 지점을 끼워 넣는다
  .pipe(createWriteStream("static/transform.csv.gz")); // 139 bytes written

파이프라인 중간에 계측 지점을 꽂는다는 발상이다. 앞뒤 스트림은 자기가 관찰당하는지 모른다 — 8-1 프록시와 같은 아이디어다.

느린 파이프 연결(Late piping)
  • 스트림을 파라미터로 받아 처리해야 하는 API 가 종종 있다.
  • 그런데 그 API 를 호출하는 시점에는 아직 데이터가 준비되지 않았을 수 있다.
  • PassThrough 를 빈 자리 표시자로 먼저 넘겨 두고, 나중에 파이프를 연결한다.
late-piping.ts 
import { createReadStream } from "fs";
import { basename } from "path";
import { PassThrough } from "stream";
import { createBrotliCompress } from "zlib";

export async function upload(filename: string, contentStream: any) {
  console.log(`Uploading ${filename}...`);

  return {
    data: "",
  };
}

const filepath = process.argv[2];
const filename = basename(filepath);
const contentStream = new PassThrough();

upload(`${filename}.br`, contentStream)      // 먼저 넘기고
  .then((response) => console.log(response))
  .catch((err) => console.log(err));

createReadStream(filepath)                   // 나중에 채운다
  .pipe(createBrotliCompress())
  .pipe(contentStream);

지연(Lazy) 스트림

  • 동시에 다수의 스트림을 생성해야 하는 경우가 있다.
  • 하지만 순간적으로 많은 스트림을 만들면 EMFILE(열린 파일이 너무 많음) 오류가 날 수 있다. fs.createReadStream 같은 함수는 읽기를 시작하기 전에 이미 파일 디스크립터를 열기 때문이다.
  • lazystream 같은 라이브러리를 쓰면 실제로 데이터를 소비할 때까지 비싼 초기화를 미룰 수 있다.

파이프를 사용해서 스트림 연결하기

  • 한 프로그램의 출력이 다음 프로그램의 입력으로 연결된다 — 유닉스 파이프와 같은 발상이다.
  • pipe() 는 Readable 이 방출한 데이터를 제공된 Writable 로 전달한다.
  • 두 스트림을 파이프로 연결하면 흡입이 생성되어 read, write 를 수동으로 호출할 필요가 없어진다. 배압도 자동으로 처리된다.
파이프 및 오류 처리
  • pipe() 를 쓸 때 error 이벤트는 파이프라인을 통해 자동 전파되지 않는다.
  • 매 스트림마다 따로 에러 핸들링을 해줘야 한다.
  • 또 실패한 스트림을 정리(destroy)하지 않으면 메모리 누수로 이어질 수 있다.
pipe-error.ts 끔찍한 모양

pipeline()을 사용한 개선된 오류 처리

  • 코어 stream 패키지가 pipeline() 을 제공한다 — 에러를 한 곳에서 받고, 실패 시 모든 스트림을 정리해 준다.

정리

  • 추상 클래스 4종: Readable / Writable / Duplex(무관한 읽기+쓰기) / Transform(쓴 것이 변환되어 읽힘)
  • Readable 소비법 3종: non-flowing(readable+read) / flowing(data) / for await
  • 구현은 _read / _write / _transform + _flush. callback() 을 빠뜨리면 스트림이 멈춘다
  • 배압: write() 가 false 면 drain 까지 쉰다. 기본 highWaterMark 는 Node 22부터 64KiB
  • pipe() 는 에러를 전파하지 않는다 → 항상 pipeline()(또는 stream/promises 버전)을 쓴다

스트림을 사용한 비동기 제어 흐름 패턴

4장의 순차 · 병렬 · 제한된 병렬이 스트림 위에서 다시 나타난다.

핵심 _transform 의 done() 을 언제 부르느냐가 전부다. 작업이 끝난 뒤 부르면 순차, 시작하자마자 부르면 병렬이 된다.

순차적 실행

  • 기본적으로 스트림은 데이터를 순서대로 처리한다.
  • Transform 의 _transform() 은 콜백으로 완료를 알릴 때까지 다음 청크를 받지 않는다.
  • 청크를 올바른 순서로 처리하는 데 결정적으로 중요한 성질이다.
concatFiles.ts 
import { createReadStream, createWriteStream } from "fs";
import { Readable, Transform } from "stream";

function concatFiles(dest: string, files: string[]) {
  return new Promise((resolve, reject) => {
    const destStream = createWriteStream(dest);
    Readable.from(files)
      .pipe(
        new Transform({
          objectMode: true,
          transform(filename, encoding, done) {
            const src = createReadStream(filename);
            src.pipe(destStream, { end: false }); // 완료돼도 대상을 닫지 않음
            src.on("error", done);
            src.on("end", done);                  // 이 파일이 끝나야 다음 파일
          },
        })
      )
      .on("error", reject)
      .on("finish", () => {
        destStream.end();
        resolve(true);
      });
  });
}

const main = async () => {
  try {
    await concatFiles("destination.txt", [
      "static/file1.txt",
      "static/file2.txt",
    ]);
  } catch (err) {
    console.error(err);
  }
};

main();

두 가지 장치가 순서를 만든다. (1) { end: false } 로 대상 스트림이 중간에 닫히지 않게 하고, (2) src 의 end 에서야 done() 을 불러 다음 파일로 넘어간다.

순서가 없는 병렬 실행

  • 모든 청크에 대해 느린 비동기 작업이 필요하다면, 병렬화해 전체 속도를 높이는 것이 좋다.
  • 각 청크 사이에 관계가 없을 때만 가능하며, 바이너리보다 주로 객체 스트림에서 쓰인다.
순서가 없는 병렬 스트림 구현
ParallelStream.ts 
import { Transform, TransformCallback, TransformOptions } from "stream";

class ParallelStream extends Transform {
  private userTransform: any;
  private running: number;
  private terminateCb: any;

  constructor(userTransform: Transform, options: TransformOptions) {
    super({ ...options, objectMode: true });
    this.userTransform = userTransform;
    this.running = 0;
    this.terminateCb = null;
  }

  _transform(
    chunk: any,
    encoding: BufferEncoding,
    done: (error?: Error | null | undefined) => void
  ) {
    this.running++;
    // 해당 지점에서 완료되기를 기다리지 않음
    this.userTransform(
      chunk,
      encoding,
      this.push.bind(this),
      this._onComplete.bind(this)
    );
    done();      // ← 즉시 호출해야 다음 청크가 들어온다
  }

  _flush(callback: TransformCallback): void {
    if (this.running > 0) {
      this.terminateCb = callback;   // 아직 진행 중이면 종료를 미룬다
    } else {
      callback();
    }
  }

  _onComplete(err: unknown) {
    this.running--;
    if (err) {
      this.emit("error", err);
    }
    if (this.running === 0) {
      this.terminateCb && this.terminateCb();
    }
  }

원문 교정 원문 교정

노트의 _transform 에는 done() 호출이 빠져 있다. 그러면 스트림이 첫 번째 청크에서 그대로 멈춘다 — 두 번째 청크가 아예 들어오지 않으므로 "병렬"이라는 목적 자체가 성립하지 않는다.

이 패턴의 핵심이 정확히 그 한 줄이다. 사용자 변환이 끝나기를 기다리지 않고 done() 을 즉시 불러 다음 청크를 받아들이고, 실제 완료는 별도의 _onComplete 로 세는 것이다. 위 코드에는 done() 을 추가해 두었다.

미완성 노트

원본 노트에는 이 소제목만 있고 내용이 없다. 책에서는 위 ParallelStream 을 이용해 URL 목록을 받아 각각의 생존 여부를 동시에 확인하는 예제를 다룬다. 내용을 지어내지 않고 자리만 표시해 둔다.

순서가 없는 제한된 병렬 실행

  • 한 번에 수천, 수백만 개의 작업을 처리하면 가용성이 손상될 수 있다.
  • 부하와 리소스 사용량을 제어하는 해법은 병렬 작업의 동시성을 제한하는 것이다.

구현은 ParallelStream 에 concurrency 를 추가하고, running 이 상한에 도달하면 done() 을 즉시 부르지 않고 보관했다가 슬롯이 비었을 때 부르는 방식이다. 4-2의 제한된 병렬 실행과 정확히 같은 구조다.

순서가 있는 병렬 실행

  • 때로는 각 청크를 수신한 순서대로 내보내야 한다.
  • 실행 중인 각 작업의 결과를 버퍼에 담아 두었다가 순서에 맞게 재정렬해 내보낸다.
  • 보통 직접 구현하지 않고 parallel-transform 같은 라이브러리를 쓴다.

정리

  • 스트림은 기본이 순차다. _transform 의 done() 이 다음 청크의 신호이기 때문
  • 병렬로 만들려면 done() 을 즉시 부르고, 실제 완료는 별도 카운터로 센다
  • _flush 에서 카운터가 0이 될 때까지 종료를 미뤄야 데이터를 잃지 않는다
  • 동시성 제한은 done() 을 보관했다 슬롯이 빌 때 부르는 것으로 구현
  • 순서까지 지키려면 출력 버퍼 재정렬이 필요하다 → parallel-transform
6-4

파이핑 패턴

결합 · 분기 · 병합 · 다중화. 스트림을 배관처럼 다루는 네 가지 방법.

핵심 파이프라인 전체를 하나의 Duplex 로 감싸면 내부 구현을 숨기고 에러 처리도 한 곳으로 모을 수 있다. 스트림에서의 캡슐화가 곧 결합(combine)이다.

파이핑 패턴

Node의 스트림은 서로 다른 패턴을 조합해 파이프로 연결할 수 있다.

스트림 결합

  • 결합된 스트림은 일반적으로 Duplex 스트림이다. 첫 번째 스트림을 Writable 쪽으로, 마지막 스트림을 Readable 쪽으로 노출한다.
  • 또 다른 중요한 특징은 파이프라인 내부에서 발생하는 모든 에러를 인지하고 전파한다는 것이다.
  • 장점
    • 내부 로직을 숨겨 블랙박스로 재배포할 수 있다.
    • 스트림마다 error 를 붙일 필요 없이, 결합된 스트림 하나에만 붙이면 된다.
  • 매우 일반적인 작업이므로 특별한 이유가 없다면 pumpify 같은 라이브러리를 쓰는 것이 좋다.
pipeline-return.ts 
import assert from "assert";
import { createReadStream, createWriteStream } from "fs";
import { pipeline, Transform } from "stream";

const streamA = createReadStream("package.json");
const streamB = new Transform({
  transform(chunk, encoding, callback) {
    this.push(chunk.toString().toUpperCase());
    callback();                     // 빠뜨리면 파이프라인이 멈춘다
  },
});
const streamC = createWriteStream("package-uppercase.json");

const pipelineReturn = pipeline(streamA, streamB, streamC, (err) => {
  if (err) {
    console.error(err);
  } else {
    console.log("Pipeline succeeded.");
  }
});

assert.strictEqual(streamC, pipelineReturn); // true
const pipeReturn = streamA.pipe(streamB).pipe(streamC);
assert.strictEqual(pipeReturn, streamC);     // true

원문 교정 원문 교정

(1) 노트의 streamB 는 transform 안에서 callback() 을 호출하지 않는다. 그러면 첫 청크 이후 파이프라인이 멈춰 "Pipeline succeeded." 가 출력되지 않는다. 위 코드에 추가해 두었다.

(2) 노트는 pipeline() 의 한계를 "마지막 스트림만 반환함 → Readable 만 반환함"이라고 적었는데, 정확히는 마지막(목적지) 스트림을 반환하는 것이며 그것이 Readable 인지 Writable 인지는 상황에 따라 다르다. 위 예제에서 반환값은 Writable 인 streamC 다(assert 가 이를 증명한다).

진짜 한계는 "쓸 곳과 읽을 곳을 동시에 주지 못한다"는 것이다. 결합된 스트림으로 재배포하려면 streamA 에 쓰고 streamC 에서 읽는 하나의 Duplex 가 필요한데, pipeline() 은 그 중 한쪽만 돌려준다. 그래서 pumpify 가 필요하다.

Writable 쪽 입구와 Readable 쪽 출구만 노출한다 — 사용자는 세 단계가 있다는 것도, 중간에 무엇이 있는지도 알 필요가 없다. 에러 리스너도 이 껍데기 하나에만 붙이면 된다.

미완성 노트

원본 노트에 소제목만 있고 내용이 없다. 요지는 위 도해대로 첫 스트림의 Writable 면과 마지막 스트림의 Readable 면을 하나의 Duplex 로 노출하는 것이며, 실무에서는 pumpify 또는 stream.compose()(Node 16.9+, 실험적)로 해결한다.

스트림 분기

  • 단일 Readable 스트림을 여러 Writable 스트림으로 파이핑해 분기할 수 있다.
  • 동일한 데이터를 서로 다른 목적지로 보낼 때 유용하다.
  • 유닉스의 tee 명령어와 같은 발상이다.
다중 체크섬 생성기 구현
  • 한쪽은 sha1Stream, 다른 쪽은 md5Stream 으로 파이프한다.
  • { end: false } 를 지정하지 않는 한, 두 스트림은 inputStream 이 끝날 때 자동으로 종료된다.
fork.ts 
import { createHash } from "crypto";
import { createReadStream, createWriteStream } from "fs";

const filename = process.argv[2];
const sha1Stream = createHash("sha1").setEncoding("hex");
const md5Stream = createHash("md5").setEncoding("hex");
const inputStream = createReadStream(filename);

inputStream.pipe(sha1Stream).pipe(createWriteStream(`${filename}.sha1`));
inputStream.pipe(md5Stream).pipe(createWriteStream(`${filename}.md5`));

같은 Readable 을 두 곳으로 흘리면, 한쪽이 느릴 때 소스 전체가 그 속도에 맞춰진다. 두 갈래의 처리 속도가 크게 다르다면 느린 쪽 앞에 버퍼를 두거나 아예 분리해야 한다.

스트림 병합

  • 분기와 반대로 여러 스트림을 하나로 병합하는 작업이며 일반적으로 간단하다.
  • 다만 { end: false } 를 주지 않으면 소스 하나가 끝나자마자 목적지가 닫혀 버리므로 조심해야 한다.
텍스트 파일 병합
merge.ts 
import { createReadStream, createWriteStream } from "fs";
import split from "split";

const dest = process.argv[2];
const sources = process.argv.slice(3);

const destStream = createWriteStream(dest);

let endCount = 0;
for (const source of sources) {
  const sourceStream = createReadStream(source, { highWaterMark: 16 });
  sourceStream.on("end", () => {
    if (++endCount === sources.length) {   // 전부 끝나야 닫는다
      destStream.end();
      console.log(`${dest} 파일 병합 완료`);
    }
  });
  sourceStream
    .pipe(split((line: any) => line + "\n"))
    .pipe(destStream, { end: false });
}

병합 결과의 순서는 섞인다

위 코드는 모든 소스를 동시에 읽어 하나의 목적지에 흘리므로, 출력 파일에서 각 소스의 줄이 뒤섞인다. 순서대로 이어붙이려면 6-3의 concatFiles 처럼 순차 처리해야 한다. highWaterMark: 16 을 준 것도 섞이는 모습을 잘 보이게 하려는 의도다.

멀티플렉싱 & 디멀티플렉싱

  • 병합의 특별한 변형으로, 스트림들을 합치는 것이 아니라 공유 채널로 실어 나른 뒤 원래대로 되돌린다.
  • 멀티플렉싱 — 여러 스트림을 하나의 채널로 결합하는 작업
  • 디멀티플렉싱 — 수신된 데이터를 원래의 스트림들로 재구성하는 작업
  • 이 작업을 수행하는 장치를 멀티플렉서 / 디멀티플렉서라고 부른다.
원격 로거 만들기
  • 자식 프로세스를 시작하고 표준 출력과 표준 에러를 원격 서버로 리다이렉션하는 프로그램이다.
  • 원격 서버는 두 스트림을 두 개의 개별 파일에 저장한다.
  • 공유 매체는 TCP 연결이고, 다중화할 두 채널은 자식 프로세스의 stdout, stderr 이다.
길이를 먼저 보내는 것이 핵심이다 — TCP 는 바이트 스트림일 뿐 메시지 경계를 보존하지 않으므로, 직접 경계를 만들어 넣어야 한다. 그래서 수신 측이 non-flowing 모드로 read(1), read(4), read(N) 을 정확히 호출할 수 있다.
클라이언트 — 멀티플렉싱
client.ts 
import { fork } from "child_process";
import { connect } from "net";
import { Readable, Writable } from "stream";

/**
 * 채널 다중화 처리
 * 1. readable 이벤트에 리스너를 등록, non-flowing 모드 사용
 * 2. 청크를 읽어 채널ID, 패킷의 크기, 실제 데이터 순서로 패킷을 만듦
 * 3. 패킷이 준비되면 목적지 스트림에 기록
 * 4. 모든 소스가 종료되면 목적지를 닫도록 end 리스너 등록
 */
const multiplexChannels = (sources: Readable[], destination: Writable) => {
  let openChannels = sources.length;

  for (let i = 0; i < sources.length; i++) {
    sources[i]
      .on("readable", function () {
        let chunk: Buffer;

        while ((chunk = sources[i].read()) !== null) {
          const outBuff = Buffer.alloc(1 + 4 + chunk.length);
          outBuff.writeUint8(i, 0);
          outBuff.writeUInt32BE(chunk.length, 1);
          chunk.copy(outBuff, 5);
          console.log(`Send packet ${i} with ${chunk.length} bytes`);
          destination.write(outBuff);
        }
      })
      .on("end", () => {
        if (--openChannels === 0) {
          destination.end();
        }
      });
  }
};

/**
 * 1. localhost:3000 서버에 TCP 연결 생성
 * 2. 인자로 받은 자식 프로세스를 실행, silent: true 로 부모 스트림 상속 방지
 * 3. 자식의 stdout, stderr 을 소켓으로 멀티플렉싱
 */
const socket = connect(3000, "localhost", () => {
  const child = fork(process.argv[2], process.argv.slice(3), { silent: true });
  multiplexChannels([child.stdout!, child.stderr!], socket);
});

노트 주석에 "silent: false를 통해서 부모 프로세스 상속 방지"라고 적혀 있으나 코드는 { silent: true } 이고, 상속을 막는 것도 true 쪽이다. silent: true 면 자식의 stdio 가 부모에게 상속되지 않고 파이프로 연결되어 child.stdout / child.stderr 을 코드에서 잡을 수 있다. 주석이 값과 어긋난 오기다.

서버 — 디멀티플렉싱
server.ts 
import { createWriteStream } from "fs";
import { createServer } from "net";
import { Readable, Writable } from "stream";

const demultiplexChannel = (source: Readable, destinations: Writable[]) => {
  let currentChannel: any = null;
  let currentLength: any = null;

  source
    .on("readable", () => {
      let chunk: Buffer;

      if (currentChannel === null) {
        chunk = source.read(1);                    // 채널 ID 1바이트
        currentChannel = chunk && chunk.readUint8(0);
      }

      if (currentLength === null) {
        chunk = source.read(4);                    // 길이 4바이트
        currentLength = chunk && chunk.readUInt32BE(0);
        if (currentLength === null) {
          return null;                             // 아직 안 왔으면 다음 readable 을 기다린다
        }
      }

      chunk = source.read(currentLength);          // 데이터 N바이트
      if (chunk === null) {
        return null;
      }

      console.log(
        `Received packet from child ${currentChannel}: ${chunk.toString()}`
      );
      destinations[currentChannel].write(chunk);

      currentChannel = null;
      currentLength = null;
    })
    .on("end", () => {
      destinations.forEach((destination) => destination.end());
      console.log("end");
    });
};

const server = createServer((socket) => {
  const stdoutStream = createWriteStream("stdout.log");
  const stderrStream = createWriteStream("stderr.log");
  demultiplexChannel(socket, [stdoutStream, stderrStream]);
});

server.listen(3000, () => {
  console.log("Server is running on port 3000");
});

원문 교정 원문 교정

노트의 서버 코드는 createServer 를 http 에서 import 하고 있지만, 클라이언트는 net.connect(3000) 로 순수 TCP 연결을 만든다. HTTP 서버의 createServer 콜백은 (req, res) 를 받으므로 socket 을 쓸 수 없다. 이 예제에서 필요한 것은 net.createServer 이며, 그래야 콜백 인자가 소켓이 된다. 위 코드는 import { createServer } from "net" 으로 고쳐 두었다.

또한 demultiplexChannel 은 readable 콜백이 한 번 호출될 때 패킷을 하나만 처리한다. 여러 패킷이 한꺼번에 도착하면 나머지는 다음 readable 이벤트를 기다려야 하므로, 6-2의 non-flowing 예제처럼 while 로 감싸는 편이 안전하다.

flowchart LR

  E["child.stderr"] --> M2["멀티플렉서 (채널 1)"]
  M --> S["TCP 소켓 (공유 채널)"]

연결 하나로 두 개의 논리 채널을 실어 나른다 — 1-2에서 이벤트 디멀티플렉서가 여러 리소스를 하나의 이벤트 흐름으로 모았던 것과 같은 발상이, 이번에는 애플리케이션 레벨에서 반복된다.

정리

  • 결합: 파이프라인을 하나의 Duplex 로 감싸 내부를 숨기고 에러를 한 곳으로 모은다 → pumpify

  • 병합: 여러 소스를 하나로. { end: false } + 완료 카운터가 필수, 순서는 섞인다
  • 다중화: [채널ID][길이][데이터] 패킷으로 감싸 하나의 채널로 보내고, 수신 측에서 정확히 잘라 복원
  • pipeline() 은 마지막 스트림만 반환하므로 결합된 스트림을 만들지는 못한다
