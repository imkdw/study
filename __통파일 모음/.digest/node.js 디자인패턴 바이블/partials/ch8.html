8-1

프록시

대상 객체인 척하면서 그 앞에 서서, 오가는 호출을 가로챈다.

핵심 구현 기법은 네 가지(컴포지션 / 팩토리 / 객체 확장 / Proxy)지만 선택 기준은 두 개뿐이다. 원본을 건드려도 되는가, 그리고 가로챌 대상이 정해져 있는가.

프록시

  • 다른 객체에 대한 접근을 제어하는 객체다. 다른 이름으로 서로게이트(surrogate)라고도 한다.
  • 실행되는 작업의 전부 또는 일부를 가로채 해당 동작을 증강하거나 보완한다.
유용한 상황
용도프록시가 하는 일
데이터 검증입력을 전달하기 전에 유효성을 검증
보안작업 수행 권한이 있는지 확인한 뒤 전달
캐싱내부에 캐시를 유지하고, 캐시에 없을 때만 실제 작업을 실행

프록시 구현 기술

모든 함수를 가로챌 수도 있고, 일부만 가로채고 나머지는 원본이 직접 처리하도록 위임할 수도 있다.

StackCalculator.ts 
class StackCalculator {
  private stack: number[];

  constructor() {
    this.stack = [];
  }

  putValue(value: number) {
    this.stack.push(value);
  }

  getValue() {
    return this.stack.pop();
  }

  peekValue() {
    return this.stack[this.stack.length - 1];
  }

  clear() {
    this.stack = [];
  }

  divide() {
    const a = this.getValue();
    const b = this.getValue();

    if (a === undefined || b === undefined) {
      throw new Error("Stack is empty");
    }
    const result = a / b;
    this.putValue(result);
    return result;
  }

  multiply() {
    const a = this.getValue();
    const b = this.getValue();

    if (a === undefined || b === undefined) {
      throw new Error("Stack is empty");
    }
    const result = a * b;
    this.putValue(result);
    return result;
  }
}

const calculator = new StackCalculator();
calculator.putValue(3);
calculator.putValue(2);
console.log(calculator.multiply());
calculator.putValue(2);
console.log(calculator.multiply());

목표는 divide() 가 0으로 나누려 할 때 막는 안전한 계산기를 만드는 것이다. 아래 네 가지 방법 모두 StackCalculator 를 한 줄도 고치지 않는다.

객체 컴포지션
  • 기능을 확장하기 위해 객체를 다른 객체와 결합하는 기술이다.
  • safeCalculator 는 원래 Calculator 인스턴스의 프록시다.
  • 주의할 점은 상태는 여전히 원본 인스턴스가 유지한다는 것이다. 프록시는 상태를 복제하지 않는다.
SafeCalculator.ts 
class SafeCalculator {
  calculator: StackCalculator;

  constructor(calculator: StackCalculator) {
    this.calculator = calculator;
  }

  // 가로챈 함수
  divide() {
    const divisor = this.calculator.peekValue();
    if (divisor === 0) {
      throw new Error("Cannot divide by zero");
    }
    return this.calculator.divide();
  }

  // 위임된 함수
  putValue(value: number) {
    return this.calculator.putValue(value);
  }

  multiply() {
    return this.calculator.multiply();
  }
}
!

원문 교정 원문 교정

노트의 컴포지션 예제는 메서드 이름이 device() 이고(오타), 본문에서 getValue() 를 두 번 호출해 원본의 divide 로직을 다시 구현하고 있다. 게다가 0 나누기 검사를 아예 하지 않는다 — 안전 계산기를 만든다는 목적이 사라진 셈이다.

컴포지션 프록시의 요점은 원본 로직을 복제하지 않고 검사만 추가한 뒤 위임하는 것이므로, 위처럼 peekValue() 로 확인하고 this.calculator.divide() 를 호출하는 형태가 맞다. 메서드 이름도 divide 로 통일했다.

객체 컴포지션 — 팩토리 함수
  • 클래스 기반보다 간단하지만, 역시 모든 함수를 명시적으로 위임해야 한다.
  • 위임할 함수가 많은 프록시를 만들 때는 delegates 같은 라이브러리를 쓸 수 있다.
createSafeCalculator.ts 
function createSafeCalculator(calculator: StackCalculator) {
  return {
    divide() {
      const divisor = calculator.peekValue();
      if (divisor === 0) {
        throw new Error("Cannot divide by zero");
      }
      return calculator.divide();
    },
    putValue(value: number) {
      return calculator.putValue(value);
    },
    multiply() {
      return calculator.multiply();
    },
  };
}
객체 확장(Object Augmentation)
  • 객체가 가진 몇몇 함수만 프록시하는 가장 간단하고 일반적인 방법이다.
  • 하지만 대상 객체를 직접 변경하기 때문에 위험할 수 있다.
patchToSafeCalculator.ts 원본을 바꾼다 
function patchToSafeCalculator(calculator: StackCalculator) {
  const divideOrigin = calculator.divide;    // 원본을 먼저 붙잡는다

  calculator.divide = () => {
    const divisor = calculator.peekValue();
    if (divisor === 0) {
      throw new Error("Cannot divide by zero");
    }

    return divideOrigin.apply(calculator);
  };

  return calculator;
}
const calculator = new StackCalculator();
const safeCalculator = patchToSafeCalculator(calculator);
×

원본을 붙잡는 첫 줄이 없으면 무한 재귀다

const divideOrigin = calculator.divide 를 생략하고 새 함수 안에서 calculator.divide() 를 부르면 자기 자신을 부르게 되어 스택 오버플로가 난다. 객체 확장의 유일하지만 치명적인 함정이다 — 8-2 데코레이터의 노트 코드가 정확히 이 실수를 범하고 있다.

또 하나. 이 함수는 calculator 를 전역적으로 오염시킨다. 같은 인스턴스를 참조하는 다른 코드도 전부 안전 버전을 보게 되며, 그것을 알 방법이 없다. 2-5의 몽키패치와 같은 위험이다.

내장 Proxy
  • ES2015에 추가된 스펙으로, Proxy 생성자는 대상(target)과 핸들러(handler)를 받는다.
  • target 은 프록시가 적용될 객체, handler 는 프록시의 동작을 정의하는 객체다. 핸들러에는 특정 연산이 수행될 때 자동 호출되는 트랩 함수(get, set, has 등)가 들어간다.
  • 변경하려는 부분만 가로채고, 원본 코드는 전혀 건드리지 않는다.
proxy-calculator.ts 원본 무수정 
const safeCalculatorHandler = {
  get: (target: StackCalculator, property: keyof StackCalculator) => {
    if (property === "divide") {
      return function () {
        const divisor = target.peekValue();
        if (divisor === 0) {
          throw new Error("Cannot divide by zero");
        }

        return target.divide();
      };
    }

    return target[property];
  },
};

const calculator = new StackCalculator();
const safeCalculator = new Proxy(calculator, safeCalculatorHandler);
console.log(safeCalculator.divide());
i

return target[property] 의 미묘함 보강

이 한 줄은 바인딩되지 않은 함수를 돌려준다. safeCalculator.putValue(3) 처럼 프록시를 통해 호출하면 this 가 프록시가 되고, 그 안의 this.stack 접근이 다시 get 트랩을 거쳐 target.stack 으로 이어지므로 결과적으로는 동작한다.

하지만 const put = safeCalculator.putValue; put(3) 처럼 떼어내면 this 를 잃는다. 안전하게 하려면 함수일 때 .bind(target) 해서 반환하는 편이 낫다.

Proxy 객체의 추가 기능과 제약사항
  • 자바스크립트에 깊이 통합된 기능으로, 객체에 대한 많은 연산을 가로채고 재정의할 수 있다.
  • 단점은 완전한 트랜스파일이나 폴리필이 불가능하다는 것이다. 일부 동작은 런타임 차원에서만 구현 가능하기 때문이다.
virtual-array.ts 
const evenNumbers = new Proxy([], {
  get: (target, index: any) => index * 2,
  has: (target, number: any) => number % 2 === 0,
});

console.log(2 in evenNumbers);  // true  ← has 트랩
console.log(evenNumbers[2]);    // 4     ← get 트랩

실제로는 빈 배열이다. 존재하지 않는 값을 요청 시점에 계산해 돌려주는 가상 객체를 만들 수 있다는 것이 Proxy 만의 능력이다. 컴포지션이나 객체 확장으로는 흉내 낼 수 없다.

미완성 노트

원본 노트에 소제목과 ... 만 있다. 내용을 지어내지 않고 자리만 표시해 둔다.

책의 예제는 Writable 스트림을 Proxy 로 감싸 write 호출만 가로채 로그를 남기고 원본에 위임하는 것이다. 6-2의 PassThrough 관찰과 목적은 같고 계층이 다르다 — PassThrough 는 데이터 흐름에, 프록시는 메서드 호출에 끼어든다.

프록시를 사용한 변경 옵저버

옵저버 패턴은 객체가 변경되면 그 사실을 옵저버에게 알려, 변경 즉시 반응할 수 있게 하는 패턴이다.

observer-proxy.ts 
function createObserver(target: any, observer: any) {
  const observable = new Proxy(target, {
    set(obj, prop, value) {
      if (value !== obj[prop]) {      // 값이 실제로 바뀔 때만 알린다
        const prev = obj[prop];
        obj[prop] = value;
        observer({ prop, prev, curr: value });
      }

      return true;
    },
  });

  return observable;
}

function calculateTotal(invoice: {
  subtotal: number;
  discount: number;
  tax: number;
}) {
  return invoice.subtotal - invoice.discount + invoice.tax;
}

const invoice = {
  subtotal: 100,
  discount: 10,
  tax: 10,
};

let total = calculateTotal(invoice);
console.log("Start Counting");

const obsInvoice = createObserver(invoice, ({ prop, prev, curr }: any) => {
  total = calculateTotal(obsInvoice);
  console.log(`${prop}: ${prev} -> ${curr}`);
});

obsInvoice.subtotal = 200;   // 옵저버 수신   (100 → 200)
obsInvoice.discount = 20;    // 옵저버 수신   (10 → 20)
obsInvoice.discount = 20;    // 옵저버 수신 X (값이 같음)
obsInvoice.tax = 20;         // 옵저버 수신   (10 → 20)

console.log(`Final Total: ${total}`);

원문 교정 원문 교정

(1) 노트는 마지막 obsInvoice.tax = 20 에 "옵저버 수신 X"라고 적었지만, tax 의 초기값은 10 이므로 값이 바뀌고 옵저버가 호출된다. Node v24.17.0 에서 직접 실행해 위 출력을 확인했다. 수신되지 않는 것은 같은 값을 다시 넣은 두 번째 discount = 20 뿐이다.

(2) 노트의 calculateTotla 는 오타이고, 더 중요하게는 매개변수를 구조 분해해 놓고 본문에서는 모듈 스코프의 invoice 를 읽는다. invoice 가 마침 프록시의 target 이라 결과는 맞지만, 순전히 우연이다. 다른 객체를 넘기면 엉뚱한 값이 나온다. 위 코드는 인자를 실제로 사용하도록 고쳤다.

이것이 반응형 프레임워크의 원리다 보강

Vue 3 의 reactive() 와 MobX 의 관찰 가능 객체가 정확히 이 set 트랩 위에 서 있다. 3-2의 EventEmitter 가 명시적으로 emit 해야 하는 반면, 프록시 옵저버는 평범한 대입문이 곧 알림이 된다는 점이 결정적 차이다.

정리

  • 프록시 = 접근을 제어하는 대리자. 검증 / 보안 / 캐싱이 대표 용도
  • 컴포지션은 안전하지만 위임 코드가 많고, 객체 확장은 간단하지만 원본을 오염시킨다
  • 객체 확장에서는 원본 함수를 먼저 변수에 붙잡아야 한다 — 아니면 무한 재귀
  • Proxy 는 위임 없이 포괄적으로 가로채고, 존재하지 않는 속성까지 만들어낼 수 있다
  • set 트랩으로 만든 옵저버가 현대 반응형 프레임워크의 기반이다
8-2

데코레이터

구현은 프록시와 똑같다. 다른 것은 "막으려는가, 더하려는가"라는 의도뿐이다.

핵심 데코레이터는 모든 인스턴스가 아니라 명시적으로 감싼 인스턴스에만 기능을 더한다. 상속이 클래스 전체를 바꾸는 것과 대비되는 지점이다.

데코레이터

  • 기존 객체의 동작을 동적으로 증대시키는 디자인 패턴이다.
  • 모든 객체가 아니라 명시적으로 데코레이팅된 인스턴스에만 추가된다.

데코레이터 구현 기법

프록시와 데코레이터는 개념적으로 서로 다른 의도를 가진 두 개의 패턴이지만, 실제로는 동일한 구현 전략을 공유한다.

컴포지션

데코레이트되는 컴포넌트를 새로운 객체로 감싼다. 감싼 객체는 세 종류의 메서드를 갖게 된다.

EnhancedCalculator.ts 
class Calculator {
  minus(a: number, b: number) {
    return a - b;
  }

  multiple(a: number, b: number) {
    return a * b;
  }
}

class EnhancedCalculator {
  constructor(private calculator: Calculator) {}

  // 신규 메서드 — 원본에 없던 기능
  add(a: number, b: number) {
    return a + b;
  }

  // 수정된 메서드 — 검증을 더한 뒤 위임
  minus(a: number, b: number) {
    if (a < b) {
      throw new Error("a는 b보다 크거나 같아야 합니다.");
    }

    return this.calculator.minus(a, b);
  }

  // 위임된 메서드 — 그대로 통과
  multiple(a: number, b: number) {
    return this.calculator.multiple(a, b);
  }
}
데코레이터가 하는 일은 이 세 칸으로 전부 설명된다 — 프록시와 다른 점은 첫 번째 칸(신규 메서드)의 존재다. 프록시는 원본에 없는 기능을 만들지 않는다.
객체 확장

객체에 직접 새 함수를 정의해 데코레이트한다.

patchCalculator.ts 원본을 붙잡아 둔다 
function patchCalculator(calculator: Calculator) {
  const minusOrigin = calculator.minus.bind(calculator);   // 필수

  calculator.minus = function (a: number, b: number) {
    if (a < b) {
      throw new Error("a는 b보다 크거나 같아야 합니다.");
    }

    return minusOrigin(a, b);
  };

  // 신규 메서드도 붙일 수 있다
  (calculator as any).add = function (a: number, b: number) {
    return a + b;
  };

  return calculator;
}
×

원문 교정 — 무한 재귀 원문 교정

노트의 patchCalculator 는 원본 함수를 붙잡아 두지 않고, 새로 대입한 함수 안에서 return this.minus(a, b) 를 호출한다. this.minus 는 방금 대입한 그 함수 자신이므로 무한 재귀에 빠져 RangeError: Maximum call stack size exceeded 로 죽는다.

8-1의 patchToSafeCalculator 는 divideOrigin 을 먼저 저장해 이 함정을 피했는데, 여기서는 그 한 줄이 빠졌다. 위 코드에 minusOrigin 을 추가했다.

Proxy를 사용한 데코레이팅
proxy-decorator.ts 
const enhancedCalculatorHandler = {
  get(target: any, property: any) {
    if (property === "add") {
      return function add(a: number, b: number) {
        return a + b;            // 원본에 없는 메서드를 만들어낸다
      };
    } else if (property === "minus") {
      return function minus(a: number, b: number) {
        if (a < b) {
          throw new Error("a는 b보다 크거나 같아야 합니다.");
        }
        return target.minus(a, b);
      };
    }

    return target[property];
  },
};

const calculator = new Proxy(new Calculator(), enhancedCalculatorHandler);

Proxy 로 데코레이트할 때의 이점은 위임 메서드를 하나도 쓰지 않아도 된다는 것이다. get 트랩의 마지막 return target[property] 한 줄이 나머지 전부를 통과시킨다.

TypeScript 의 @decorator 와는 다른 이야기 보강

여기서 말하는 데코레이터는 디자인 패턴이고, @Injectable() 같은 문법(TC39 Decorators, TypeScript experimentalDecorators)은 언어 기능이다. 후자는 클래스/메서드 정의 시점에 한 번 적용되므로 "인스턴스별로 선택적 적용"이라는 이 패턴의 성질과는 오히려 반대에 가깝다. 이름만 같다.

정리

  • 데코레이터 = 인스턴스 단위로 기능을 더하는 패턴. 상속과 달리 선택적이다
  • 감싼 객체의 메서드는 신규 / 수정 / 위임 세 종류로 나뉜다
  • 객체 확장 방식은 반드시 원본 함수를 먼저 변수에 저장해야 한다 — 아니면 무한 재귀
  • Proxy 를 쓰면 위임 코드가 return target[property] 한 줄로 끝난다
8-3

프록시와 데코레이터 사이의 경계

코드로는 구분되지 않는다. 구분되는 것은 의도다.

핵심 프록시는 원래 있던 것을 막거나 대신하고, 데코레이터는 없던 것을 더한다. 같은 Proxy 코드라도 무엇을 위해 썼는지에 따라 이름이 갈린다.
  • 두 패턴은 매우 유사하며 때때로 서로 바꿔 쓸 수도 있다.
구분프록시데코레이터
의도고정적이거나 가상인 객체에 대한 접근 제어기존 객체에 새로운 동작 추가
인터페이스원본과 동일하게 유지원본보다 넓어질 수 있다
대상보통 특정 객체 하나다양한 유형의 객체를 감쌀 수 있다
원본 객체건드리지 않는다건드리지 않는다
전형적 예검증, 권한 검사, 캐싱, 지연 로딩로깅 추가, 메서드 추가, 기능 확장
인터페이스가 넓어지는지가 가장 실용적인 판별 기준이다 — 감싼 결과가 원본과 정확히 같은 메서드 집합을 가지면 프록시, 새 메서드가 생겼다면 데코레이터로 보면 대체로 맞다.

어댑터까지 나란히 놓으면 보강

세 패턴은 모두 "감싸기"이며 인터페이스의 변화 방식으로 갈린다.

  • 프록시 — 인터페이스가 같다. 접근을 통제한다
  • 데코레이터 — 인터페이스가 넓어진다. 기능을 더한다
  • 어댑터 — 인터페이스가 달라진다. 맞지 않는 것을 맞춘다 (8-4)

정리

  • 구현이 같아도 의도가 다르면 다른 패턴이다
  • 프록시: 접근 제어, 인터페이스 유지 / 데코레이터: 기능 추가, 인터페이스 확장
  • 판별 기준 = 감싼 뒤 메서드 집합이 같은가, 넓어졌는가, 달라졌는가
