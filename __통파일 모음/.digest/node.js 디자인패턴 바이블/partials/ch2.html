2-1

모듈의 필요성

모듈은 파일 분할 도구가 아니라 "무엇을 감출지"를 정하는 도구다.

핵심 모듈이 주는 네 가지 중 정보 은닉이 가장 중요하다. 나머지 셋(분할/재사용/종속성 관리)은 은닉이 되어야 비로소 안전해진다.
  • 코드를 여러 파일로 분할하는 방법을 제시해 준다.
  • 코드를 재사용할 수 있다.
  • 가능하면 명료한 책임을 가진 인터페이스만 외부에 공개한다(정보 은닉).
  • 종속성을 관리해 준다.

정리

  • 분할 / 재사용 / 은닉 / 종속성 관리 — 모듈이 해결하는 네 가지
  • 이 중 은닉이 나머지의 전제 조건이다. 다 공개된 모듈은 분할해도 결합도가 그대로다
2-2

자바스크립트와 노드에서의 모듈 시스템

표준은 ESM 하나지만, 현실은 아직 두 개다.

구분CJS (CommonJS)ESM (ES Module)
키워드require / module.exportsimport / export
표준 여부Node 고유 규약ECMAScript 표준
위상이전에 유행했고, 대부분의 레거시가 여전히 여기 의존현재 표준이자 기본값

모든 프로젝트가 ESM으로 넘어간 것은 아니다. 그래서 두 시스템의 차이와 상호 운용을 아는 것이 실무에서는 문법 자체보다 중요하다(2-7).

정리

  • CJS = Node 고유 규약, ESM = 언어 표준
  • 새 코드는 ESM, 그러나 CJS 를 만나는 일은 계속된다 → 상호 운용 지식이 필수
2-3

모듈 시스템과 패턴

모듈 시스템이 없던 시절, 함수 스코프 하나로 은닉을 흉내 낸 것이 노출식 모듈 패턴이다.

핵심 즉시 실행 함수로 감싸고 공개할 것만 return 한다. 이 한 줄짜리 아이디어가 CJS 모듈 시스템의 구현 원리 그 자체다.

노출식 모듈 패턴

  • 자바스크립트의 주요 문제점은 네임스페이스가 없어 모든 스크립트가 전역으로 실행된다는 것이다.
  • 이는 내부 앱이나 종속성 라이브러리가 기능을 노출하는 동시에 스코프를 오염시킬 수 있다는 뜻이다.
  • 전역 범위에 의존하는 것은 매우 위험하다. 앱이 확장됨에 따라 개별 기능 구현에 의존해야 하는 상황이 발생한다.
  • 이 문제를 해결하는 기법을 노출식 모듈 패턴(revealing module pattern)이라 부른다.

예제 코드

  • 즉시 실행 함수 표현(IIFE) 패턴을 사용한다.
  • 함수 내부의 변수는 외부에서 접근할 수 없다.
  • 선택적으로 노출시키고 싶은 것만 return 하여 접근하게 한다.
  • 이 아이디어를 기반으로 하는 것이 CJS 모듈 시스템이다.
revealing-module.ts 
const myModule = (() => {
  const privateFoo = () => {};
  const privateBar = [];

  const exported = {
    publicFoo: () => {},
    publicBar: () => {},
  };

  return exported;
})();

console.log(myModule); // { publicFoo: [Function: publicFoo], publicBar: [Function: publicBar] }
console.log(myModule.privateFoo);
×

타입 에러

Property 'privateFoo' does not exist on type '{ publicFoo: () => void; publicBar: () => void; }'

클로저 안에 갇힌 변수는 타입 수준에서도, 런타임에서도 밖에서 닿을 수 없다. 은닉이 규약이 아니라 언어 차원에서 강제된다는 점이 이 패턴의 가치다.

정리

  • 전역 스코프 오염 문제 → IIFE 로 함수 스코프를 만들어 해결
  • 공개할 것만 return, 나머지는 클로저에 갇혀 접근 불가
  • CJS 의 모듈 래퍼가 하는 일이 정확히 이것이다 → 2-4
2-4

CJS 모듈

직접 구현해 보면 모듈 시스템은 마법이 아니라 "함수로 감싸고 캐싱하는 것"임을 알게 된다.

핵심 CJS의 성질은 전부 "require 는 동기이고, 실행하면서 그래프를 그린다"에서 파생된다. 캐시도, 순환 종속성의 불완전한 객체도, 조건부 require 가 가능한 것도 전부 여기서 나온다.

CJS 모듈

  • Node의 첫 번째 내장 모듈 시스템이다.
  • require — 로컬 파일 시스템으로부터 모듈을 가져온다.
  • exports, module.exports — 현재 모듈에서 공개하고 싶은 기능을 내보낸다.

직접 만드는 모듈 로더

  • 모듈은 기본적으로 함수로 래핑된다.
  • exports 에 해당하는 파라미터는 module.exports 로 초기화된다.
  • 파일 시스템을 다룰 때 동기식 버전이 일반적으로 좋진 않지만, 여기서는 의도적인 동기 방식이라 괜찮다.
  • 이런 방식에서는 여러 모듈을 불러올 때 순서를 지키는 것이 중요하다.
loadModule.ts 
import fs from "fs";

function loadModule(filename: string, module: any, require: any) {
  const wrappedSrc = `(function(module, exports, require) {
    ${fs.readFileSync(filename, "utf-8")}
  })(module, module.exports, require)`;
  eval(wrappedSrc);
}

2-3의 노출식 모듈 패턴과 나란히 놓고 보면 같은 그림이다. IIFE 로 감싸 스코프를 만들고, 밖으로 낼 것만 module.exports 에 담는다.

require 함수 구현하기

  1. 모듈의 전체 경로(id)를 알아낸다

    require.resolve 알고리즘에 위임한다.

  2. 이미 로딩된 경우 캐싱된 모듈을 반환한다

    같은 파일은 두 번 평가되지 않는다.

  3. 아직 로딩되지 않았다면 빈 모듈 메타데이터를 생성한다

    { exports: {}, id } 형태.

  4. 최초 로딩 전에 캐시에 먼저 등록한다

    순환 종속성에서 무한 루프를 막는 것이 바로 이 순서다.

  5. 모듈의 코드를 loadModule 로 가져와 실행하고 module.exports 를 반환한다

require1.ts 
import fs from "fs";

function loadModule(filename: string, module: any, require: any) {
  const wrappedSrc = `(function(module, exports, require) {
    ${fs.readFileSync(filename, "utf-8")}
  })(module, module.exports, require)`;
  eval(wrappedSrc);
}

function require1(moduleName: string) {
  console.log(`Require Invoked for module: ${moduleName}`);
  const id = require1.resolve(moduleName);
  if (require1.cache[id]) {
    return require1.cache[id].exports;
  }

  // 모듈 메타데이터
  const module = {
    exports: {},
    id,
  };

  // 캐시 업데이트 (실행 전에 먼저 넣는 것이 핵심)
  require1.cache[id] = module;

  // 모듈 로딩
  loadModule(id, module, require1);

  // 변수 반환
  return module.exports;
}

require1.cache = {} as any;
require1.resolve = (moduleName: string) => {
  // 모듈의 전체 경로를 찾아냄
  return moduleName;
};

이처럼 모듈 시스템은 마법이 아니다. 실제 구현체가 존재하고, 이를 편하게 쓰기 위해 래핑된 것뿐이다.

모듈 정의

  • module.exports 에 할당되지 않으면 모든 것이 비공개다.
  • require 는 최초에만 실행하고 이후에는 캐싱된 것을 반환한다.
module-def.ts 
const dependency = require1("./anotherModule");
function log() {}
module.exports.run = () => {
  log();
};

module.exports vs exports

  • exports 는 module.exports 를 가리키는 참조값일 뿐이다.
  • 따라서 exports = {} 로 재할당해도 실제 module.exports 는 변하지 않는다. 속성을 추가하는 것만 유효하다.
아무것도 내보내지지 않음
exports = { run: () => {} };
// 지역 변수만 갈아끼운 꼴
둘 다 동작
exports.run = () => {};
// 또는
module.exports = { run: () => {} };

require 함수는 동기적이다

  • require 를 동기적으로 제한한 결정은 코드베이스 전체에 영향을 미친다.
  • 이것이 Node 코어 라이브러리가 동기/비동기 두 벌의 API를 제공하는 큰 이유 중 하나다.
  • 비동기로 동작하면 내보내는 시점에 모두 로딩되지 않았을 수 있어 위험하다.
  • 초기에는 비동기로 제공했으나 복잡성 때문에 동기식으로 변경되었다.

해결(resolve) 알고리즘

  • 종속성 지옥이란 프로그램의 종속성들이 공통 라이브러리에 의존하지만 서로 호환되지 않는 버전을 필요로 하는 상황이다.
  • Node는 모듈이 로딩되는 위치에 따라 다른 버전의 모듈이 로딩될 수 있도록 한다.
  • resolve 는 모듈 이름을 받아 모듈의 전체 경로를 반환한다. 이 경로가 로드 이후 모듈을 고유하게 식별하는 키가 된다.
유형조건해석 방법
파일 모듈 (절대)/ 로 시작절대 경로로 간주하고 그대로 반환
파일 모듈 (상대)./ 로 시작요청한 모듈의 위치를 기준으로 계산 후 반환
코어 모듈/, ./ 로 시작하지 않음코어 Node 모듈에서 먼저 검색
패키지 모듈일치하는 코어 모듈이 없음요청 모듈 경로부터 node_modules 를 찾고, 없으면 상위로 올라가며 루트까지 반복

탐색이 "위로 올라가는" 구조라서 버전 공존이 가능하다 — 깊은 곳의 모듈은 자기 옆의 node_modules 를 먼저 만나므로, 상위와 다른 버전을 갖고 있어도 서로를 보지 못한다. 이것이 종속성 지옥을 막는 실제 메커니즘이다.

모듈 캐시

  • require 의 후속 호출은 캐시된 버전을 반환한다.
  • 각 모듈은 처음 로드될 때만 로드되고 평가된다.
  • require.cache 를 삭제해 테스트할 수 있지만, 일반적인 상황에서는 위험하다.

순환 종속성

a 가 b 를, b 가 a 를 의존하고, main 이 둘을 순서대로 불러오는 상황이다.

i

실무에서의 회피법 보강

순환 종속성 자체를 제거하는 것이 정답이지만, 당장 어렵다면 두 가지 완화책이 있다. (1) module.exports 를 통째로 재할당하지 말고 exports.x = ... 로 속성을 채운다 — 참조가 유지되므로 나중에 채운 값도 보인다. (2) 최상단이 아니라 실제로 쓰는 함수 안에서 require 한다 — 그 시점에는 상대 모듈이 이미 완성되어 있다.

정리

  • 모듈은 함수로 래핑되고, exports 는 module.exports 의 참조일 뿐이다
  • require 는 동기다 → 코어가 동기/비동기 두 벌의 API 를 제공하는 배경
  • resolve 는 node_modules 를 위로 거슬러 올라가며 찾는다 → 버전 공존의 실제 메커니즘
  • 모듈은 전체 경로를 키로 캐싱되고, 실행 전에 캐시에 등록된다
  • 순환 종속성에서는 나중에 요청된 쪽이 미완성 스냅샷을 잡는다 — CJS 의 구조적 한계
2-5

모듈 정의 패턴

무엇을 내보내느냐가 곧 모듈의 확장성과 결합도를 결정한다.

핵심 명명된 exports → 함수 → 클래스 → 인스턴스 순으로 갈수록 편의는 늘고 은닉은 줄어든다. "얼마나 감출 것인가"와 "얼마나 확장하게 할 것인가"의 맞교환이다.

exports 지정하기 — named exports

  • 퍼블릭 API를 공개하는 가장 기본적인 방법은 exports 에 속성을 할당하는 것이다.
  • CJS 명세는 퍼블릭 멤버를 공개하는 데 exports 변수만 사용하도록 하고 있다.
  • 따라서 exports 로 지정하는 것이 CJS 명세와 호환되는 유일한 방법이다.
logger.ts / main.ts 
// logger.ts
exports.info = (message: string) => {
  // ...
};

exports.verbose = (message: string) => {
  // ...
};

// main.ts
const logger = require("./logger");
logger.info("asd");
logger.verbose("ads");

함수 내보내기

  • 가장 일반적인 패턴 중 하나는 module.exports 변수 전체를 함수로 재할당하는 것이다(서브스택 패턴).
  • Node의 모듈성은 SRP(단일 책임 원칙)를 지킬 것을 강력히 권장한다.
  • 단일 기능에 집중하게 만드는 완벽한 방법이며, 명백한 단일 진입점을 제공한다.
logger.ts / main.ts 
// logger.ts
module.exports = (message: string) => {
  // ...
};

module.exports.verbose = (message: string) => {
  // ...
};

// main.ts
const logger = require("./logger");
logger("asd");
logger.verbose("asd");

주 진입점은 함수 하나로 두고, 부가 기능은 그 함수의 속성으로 매단다. 1-1의 "작은 외부 인터페이스"가 코드로 나타난 형태다.

클래스 내보내기

  • 단일 진입점을 제공하지만, 서브스택 패턴에 비해 내부를 더 많이 노출한다.
  • 반대로 기능 확장에서는 훨씬 강력할 수 있다(상속, 오버라이드).
logger.ts / main.ts 
// logger.ts
class Logger {
  name: string;

  constructor(name: string) {
    this.name = name;
  }

  log(message: string) {
    // ...
  }
}

module.exports = Logger;

// main.ts
const Logger = require("./logger");

몽키패치가 위험한 이유

패치의 효과가 import 순서에 의존하고, 코드를 읽어도 어디서 바뀌었는지 추적할 수 없다. 다만 8-1 프록시의 "객체 확장" 기법이 사실상 같은 도구이므로, 테스트 목적의 국소적 사용까지 금지할 필요는 없다.

패턴진입점내부 노출확장성
named exports여러 개낮음낮음
함수 내보내기하나낮음낮음
클래스 내보내기하나높음높음
인스턴스 내보내기하나높음중간 (상태 공유)
몽키패치없음전역위험

정리

  • named exports 는 CJS 명세와 호환되는 유일한 방식
  • 함수 내보내기(서브스택 패턴)는 단일 진입점 + 최소 노출로 Node 철학에 가장 가깝다
  • 클래스는 확장성을 주고 은닉을 뺏는다
  • 인스턴스 내보내기는 모듈 캐시를 이용한 싱글톤 흉내 — 경로가 다르면 깨진다
  • 몽키패치는 가능하지만 순서 의존적이고 추적 불가능하다

ESM 모듈

import 를 정적으로 제한한 대가로, 실행 전에 종속성 그래프 전체를 알 수 있게 되었다.

핵심 ESM 은 파싱 → 인스턴스화 → 평가 세 단계로 나뉜다. 코드를 실행하기 전에 그래프가 완성되기 때문에 트리 셰이킹과 라이브 바인딩이 가능해진다.

ESM 모듈

  • 문법이 매우 간단하고, 순환 종속성 지원과 비동기 모듈 로딩을 제공한다.
  • import 는 모듈의 최상위 레벨, 제어 흐름 구문 바깥에 기술되어야 한다.
  • 실행 시 동적으로 생성할 수 없고 상수 문자열만 허용된다.
not-allowed.ts 허용되지 않음 
if (condition) {
  import a from "a";
} else {
  import b from "b";
}

불필요한 제약처럼 보이지만, 이 제약 덕분에 CJS에서는 불가능했던 여러 시나리오가 열린다. 트리 셰이킹 같은 코드 최적화를 위한 종속성 트리의 정적 분석이 가능해지는 것이다.

함께 알아두기 보강

동적 import() 는 CJS 파일 안에서도 쓸 수 있다. CJS 에서 ESM 을 부르는 오래된 표준 우회로가 바로 이것이었다. 지금은 아래 "최신 반영"에서 보듯 조건부로 require() 도 가능해졌다.

모듈 적재 이해하기

인터프리터의 목표는 모든 모듈의 종속성 그래프를 만드는 것이다. 진입점에서 시작해 필요한 모든 코드가 탐색/평가될 때까지 import 를 재귀적인 DFS 로 따라간다.

  1. 1단계 — 모든 점들 찾기 (파싱)

    모든 import 구문을 찾고, 재귀적으로 각 파일로부터 모듈의 내용을 적재한다.

  2. 2단계 — 각 점들을 연결해서 길 만들기 (인스턴스화)

    export 된 모든 개체에 대한 참조를 메모리에 유지한다. import / export 문에 참조가 생성되고 이들 간의 종속성 관계를 추적한다. 여기서 어떤 코드도 실행되지 않는다.

  3. 3단계 — 올바른 순서로 길을 걷기 (평가)

    마지막으로 코드를 실행해 실제 값을 얻는다.

CJS의 경우 동적 성질로 인해 그래프가 탐색되기 전에 파일을 실행시킨다. 그래서 모든 코드가 이미 실행된 뒤에도 새로운 require 구문을 쓸 수 있다.

flowchart LR
  subgraph CJS["CJS — 실행하며 그래프를 그린다"]
    C1["파일 실행"] --> C2["require 만나면 즉시 그 파일 실행"]
    C2 --> C3["돌아와서 나머지 실행"]
  end
  subgraph ESM["ESM — 그래프를 다 그린 뒤 실행한다"]
    E1["파싱: import 만 훑어 그래프 완성"] --> E2["인스턴스화: 참조만 연결, 실행 없음"]
    E2 --> E3["평가: 후위 DFS 순서로 실행"]
  end
이 한 장의 차이가 두 시스템의 모든 차이를 만든다 — ESM 은 실행 전에 그래프가 확정되므로 트리 셰이킹과 라이브 바인딩이 가능하고, 대신 조건부 import 를 포기해야 한다. CJS 는 정반대다.
읽기 전용 라이브 바인딩
  • import 된 모듈은 export 된 값에 대해 읽기 전용으로 바인딩된다.
  • 즉 원래 모듈이 값을 바꾸면 그 변화가 그대로 보이지만, import 한 쪽에서는 바꿀 수 없다.
  • CJS 는 require 시 얕은 복사가 이루어지므로 이런 연동이 되지 않는다.

export function increment() {
  count += 1;
}

// main.js

console.log(count); // 0
increment();
console.log(count); // 1  ← 라이브 바인딩. 복사본이었다면 여전히 0
count += 1;

런타임 에러

TypeError: Assignment to constant variable.

Node v24.17.0 에서 직접 실행해 확인했다. import 바인딩은 읽기 전용이므로 임포트한 쪽에서의 재할당은 막힌다. 값을 바꾸려면 모듈이 제공한 함수(increment)를 통해야 한다.

순환 종속성 분석
  • CJS와 동일한 형태의 순환 구조를 만들 수 있다.
  • 하지만 CJS와 달리 a 와 b 가 서로에 대한 정보를 모두 온전히 가진다.

export let loaded = false;

2-4의 CJS 결과와 나란히 놓고 보면 차이가 명확하다. CJS 에서는 한쪽이 loaded: false 인 미완성 객체를 붙잡았지만, ESM 은 양쪽 모두 loaded: true 다. 참조를 먼저 연결(2단계)하고 실행(3단계)을 나중에 하기 때문이다.

1단계 — 파싱

진입점인 app.js 부터 탐색을 시작하며, 이 단계에서는 오직 import 구문만 훑는다.

  1. app.js → a.js 로 향한다

  2. a.js → b.js 로 향한다

  3. b.js 의 a.js import 는 이미 탐색했으므로 건너뛴다

    순환을 여기서 끊는다.

  4. 더 이상 import 가 없으므로 app.js 로 되돌아간다

    결과적으로 app → a → b 종속성 그래프가 완성된다.

2단계 — 인스턴스화

인터프리터가 각 모듈이 export 하는 속성을 찾아 메모리에 맵을 작성한다.

  1. b 는 aModule 이라는 이름으로 a 의 export 를 연결

  2. a 는 bModule 이라는 이름으로 b 의 export 를 연결

  3. app 은 a, b 두 모듈의 모든 export 를 연결

  4. 아직 인스턴스화는 되지 않았고 값에 대한 참조만 연결된다

    여기가 CJS 와 갈라지는 결정적 지점이다.

3단계 — 평가
  • 종속성 그래프에 그려진 모든 코드가 실행된다.
  • 순서는 후위 깊이 우선 탐색으로, 잎에서 뿌리 방향으로 올라간다.
  • 메인 비즈니스 로직을 수행하기 전에 모든 값이 초기화되는 것을 보장해 준다. b → a → app 순으로 진행되고 최종적으로 app.js 의 코드가 실행된다.
모듈의 수정
  • export default 로 내보낸 객체는 여전히 속성 재할당이 가능하다(바인딩 자체가 아니라 객체 내부이므로).
  • 명명된 export 는 재할당이 불가능하지만, module 코어 모듈이 제공하는 API 로 우회할 수 있다. import { syncBuiltinESMExports } from "module"

CJS 에서 ESM 을 부르려면 동적 import() 밖에 없다는 전제가 깨졌다. require(esm) 이 Node v20.19+, v22.12+ 에서 플래그 없이 동작하며 v24 에서 안정화되었다. 반환값은 모듈 네임스페이스 객체라서 default export 는 .default 에 담긴다. 단 대상 모듈(과 그 종속성)이 top-level await 를 쓰면 ERR_REQUIRE_ASYNC_MODULE 로 실패한다. (근거: Node.js Docs — Loading ECMAScript modules using require())

정리

  • import 는 최상위 + 상수 문자열만 → 대신 정적 분석과 트리 셰이킹을 얻는다
  • 적재는 파싱 → 인스턴스화 → 평가 3단계. 실행은 마지막에 후위 DFS 순서로
  • 라이브 바인딩: 원본이 바뀌면 보이지만, 임포트 측에서 재할당하면 TypeError
  • 순환 종속성에서 CJS 는 미완성 스냅샷을, ESM 은 완성된 참조를 준다
  • 동적 import() 로 조건부 로딩 가능. 반대로 require(esm) 도 이제 가능하다

ESM과 CJS의 차이점과 상호 운용

둘을 섞어 쓸 때 실제로 발목을 잡는 것은 문법이 아니라 사라진 전역 변수들이다.

핵심 ESM 파일에서는 __dirname, __filename, require 가 존재하지 않는다. 셋 다 재구성할 수 있고, 요즘은 재구성할 필요조차 없어졌다.

strict 모드에서의 ESM

  • ESM 은 기본적으로 모든 코드가 "use strict" 가 적용된 것처럼 작동한다.
  • 그리고 이 동작은 해제할 수 없다.

ESM에서의 참조 유실

ESM 에서는 CJS 의 몇 가지 중요한 참조가 정의되지 않는다 — __dirname, __filename, require, module, exports. 다행히 재구성할 수 있다.

dirname.mjs 
import { fileURLToPath } from "url";
import { dirname } from "path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
↑

Node 20.11 / 21.2 이후 최신 반영

이제 위의 두 줄짜리 변환 없이 import.meta.dirname 과 import.meta.filename 을 바로 쓸 수 있다. 값은 fileURLToPath 로 변환한 것과 동일한 절대 경로 문자열이다. Node v24.17.0 에서 직접 실행해 확인했다.

dirname.mjs Node 20.11+ 
console.log(import.meta.dirname);  // /Users/.../scratchpad
console.log(import.meta.filename); // /Users/.../scratchpad/meta.mjs
i

require 를 되살리려면 보강

ESM 파일에서 CJS 전용 패키지를 꼭 require 로 불러야 한다면 module 코어 모듈의 createRequire 를 쓴다.
import { createRequire } from "module"; const require = createRequire(import.meta.url);

원문 교정 원문 교정

노트에는 "하지만 export default만 해당함"이라고 적혀 있으나, 명명된 import 도 대체로 동작한다. Node 는 cjs-module-lexer 로 CJS 파일을 정적 분석해 exports.foo = ... 형태의 할당을 찾아내고, 이를 명명된 export 로 노출한다.

Node v24.17.0 에서 exports.info / exports.verbose 를 가진 .cjs 파일을 import pkg, { info, verbose } from "./legacy.cjs" 로 불러 정상 동작을 확인했다.

다만 이는 정적으로 탐지 가능할 때만 통한다. 반복문이나 조건문 안에서 동적으로 exports 를 채우는 모듈은 탐지에 실패하므로, 그때는 default import 후 구조 분해해야 한다. (근거: Node.js Docs — CommonJS Namespaces)

정적 탐지 가능
// legacy.cjs
exports.info = () => "info!";
exports.verbose = () => "verbose!";

// main.mjs
import { info, verbose } from "./legacy.cjs";
// → 동작함
탐지 실패
// legacy.cjs
for (const k of ["info", "verbose"]) {
  exports[k] = () => k;
}

// main.mjs
import pkg from "./legacy.cjs";
const { info, verbose } = pkg; // 이렇게 우회

정리

  • ESM 은 항상 strict, 최상위 this 는 undefined
  • __dirname / __filename 은 없다 → import.meta.dirname / .filename (Node 20.11+)
  • require 가 필요하면 createRequire(import.meta.url)
  • ESM → CJS 는 명명된 import 도 대체로 동작한다 (정적 탐지 가능할 때)
  • CJS → ESM 도 이제 require(esm) 로 가능하다 (top-level await 만 아니라면)
