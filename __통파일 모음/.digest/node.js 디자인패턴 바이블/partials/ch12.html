12-1

애플리케이션 확장 소개

확장은 한 방향이 아니라 세 축이다. 어느 축이 막혔는지 먼저 알아야 한다.

핵심 Node 는 단일 스레드라서 X축(복제)이 선택이 아니라 기본값이다. 다른 언어에서는 한 프로세스로 코어를 다 쓸 수 있지만, Node 는 그럴 수 없기 때문이다.

Node.js 애플리케이션 확장

Node 는 단일 스레드 특성상 여러 프로세스와 여러 시스템에 걸쳐 확장할 필요가 있다.

확장성 3차원

세 축은 독립적이며 동시에 적용할 수 있다 — 마이크로서비스로 쪼갠(Y) 각 서비스를 여러 인스턴스로 복제하고(X), 그 뒤의 DB 를 샤딩한다(Z). "확장이 안 된다"는 말은 항상 어느 축이 막혔는지를 먼저 물어야 한다.
X축 — 복제
  • 대부분의 경우 시간과 비용 측면에서 가장 저렴하고 효과적이다.
  • 동일한 앱을 N번 복제하고, 각 인스턴스가 1/N 의 부하를 처리한다.
Y축 — 서비스/기능별 분해
  • 고유한 코드베이스를 가진 앱들로 나누는 것을 의미한다.
  • 흔히 마이크로서비스 아키텍처라고 부른다(12-3).
Z축 — 데이터 파티션 분할
  • 주로 데이터베이스에서 쓰는 개념으로, 수평/수직 분할이라고 부른다.
i

축마다 비용의 종류가 다르다 보강

X축은 인프라 비용만 늘고 코드는 그대로다 — 단, 상태가 없어야 가능하다(12-2).
Y축은 코드를 나누는 순간 분산 시스템의 모든 문제가 따라온다(13장).
Z축은 셋 중 가장 복잡하며, 파티션 키를 잘못 고르면 되돌리기가 거의 불가능하다.

순서는 대체로 X → Y → Z 다. 가장 싼 축부터 밀어 보고, 막히면 다음으로 간다.

정리

  • 확장성 3차원: X(복제) / Y(기능 분해) / Z(데이터 분할)
  • Node 는 단일 스레드이므로 X축이 기본값이다 — 코어를 쓰려면 프로세스를 늘려야 한다
  • 세 축은 독립적이며 동시에 적용된다
  • 비용이 싼 순서대로: X → Y → Z
12-2

복제 및 로드밸런싱

프로세스를 늘리는 순간 모든 상태가 갈라진다. 그 사실을 먼저 받아들여야 한다.

핵심 cluster 모듈은 CPU 활용과 무중단 배포를 거의 공짜로 준다. 대신 메모리에 있던 모든 것(세션, 캐시)이 워커마다 갈라진다. 복제의 진짜 작업은 프로세스를 늘리는 것이 아니라 상태를 밖으로 빼는 것이다.

복제 및 로드밸런싱

  • 기존의 멀티스레드 웹 서버는 사용 가능한 모든 프로세서와 메모리를 써서 처리 능력을 전부 활용할 수 있다.
  • Node 는 단일 스레드 환경이라 기존 웹 서버보다 더 이른 시점에 확장이 필요하다.

클러스터 모듈

  • 여러 인스턴스에 부하를 분산하는 가장 간단한 패턴이다.
  • 마스터(primary) 프로세스가 요청을 받고 워커 프로세스에 작업을 분산한다.
  • 보통 라운드로빈 알고리즘으로 모든 워커에 균등하게 분산한다.
↑

용어와 기본값 최신 반영

Node 16.0.0 부터 cluster.isMaster 는 deprecated 이며 cluster.isPrimary 로 대체되었다. cluster.setupMaster() 도 cluster.setupPrimary() 로 바뀌었다. 아래 예제들은 노트의 isMaster 를 그대로 두었으나, 새 코드에는 isPrimary 를 쓴다.

라운드로빈(SCHED_RR)이 기본인 것도 맞지만 윈도우는 예외다. 윈도우에서는 OS 가 분배하는 SCHED_NONE 이 기본이며, NODE_CLUSTER_SCHED_POLICY 환경 변수로 바꿀 수 있다. (근거: Node.js Docs — Cluster)

간단한 웹 서버

현재는 하나의 프로세스가 모두 처리하므로 pid 가 항상 같다.

single.ts 
import { createServer } from "http";

const { pid } = process;
const server = createServer((req, res) => {
  let i = 1e7;
  while (i > 0) {
    i--;                       // 의도적인 CPU 부하
  }

  console.log(`Worker pid: ${pid}`);
  res.end(`Hello from worker ${pid}`);
});

server.listen(8080, () => {
  console.log(`Master pid: ${pid}`);
});
클러스터 모듈을 통한 확장

기존 단일 프로세스보다 처리 가능한 양이 9~10배 정도 늘어난다(노트 저자의 코어 수 기준).

cluster.ts 
import { createServer } from "http";
import { cpus } from "os";
import cluster from "cluster";

if (cluster.isMaster) {          // 새 코드에서는 cluster.isPrimary
  const availableCpus = cpus();
  console.log("Clustering with %d CPUs", availableCpus.length);

  availableCpus.forEach(() => cluster.fork());
} else {
  const { pid } = process;

  const server = createServer((req, res) => {
    let i = 1e7;
    while (i > 0) {
      i--;
    }

    res.end(`Hello from worker ${pid}`);
  });

  server.listen(8080, () => {    // 같은 포트를 여러 워커가 listen 한다
    console.log(`Worker pid: ${pid}`);
  });
}
i

같은 포트를 여러 프로세스가 listen 할 수 있는 이유 보강

실제로는 마스터만 포트를 열고, 워커의 listen() 호출은 IPC 를 통해 마스터로 전달된다. 마스터가 들어온 연결을 라운드로빈으로 워커에 넘긴다. 그래서 EADDRINUSE 가 나지 않는 것이다. 11-4의 프로세스 풀과 구조가 같고, 분배하는 것이 작업이 아니라 소켓일 뿐이다.

클러스터 모듈의 탄력성 및 가용성
  • 워커 프로세스는 서로 완전히 별개이므로, 다른 워커에 영향 없이 제거하거나 추가할 수 있다.
  • Node 는 워커 수를 자동으로 관리해 주지 않는다. 관리는 앱의 책임이다.
  • 인스턴스가 여러 개면 하나가 죽어도 요청을 처리할 백업이 항상 존재한다.
resilient.ts 
import { createServer } from "http";
import { cpus } from "os";
import cluster from "cluster";

if (cluster.isMaster) {
  const availableCpus = cpus();
  console.log("Clustering with %d CPUs", availableCpus.length);
  availableCpus.forEach(() => cluster.fork());

  cluster.on("exit", (worker, code) => {
    if (code !== 0 && !worker.exitedAfterDisconnect) {
      console.log(`Worker ${worker.id} crashed. Restarting...`);
      cluster.fork();          // 의도치 않은 종료만 재시작
    }
  });
} else {
  setTimeout(() => {
    throw new Error("OOOPS");  // 랜덤하게 죽는 워커
  }, Math.ceil(Math.random() * 3) * 1000);
  const { pid } = process;

  const server = createServer((req, res) => {
    let i = 1e7;
    while (i > 0) {
      i--;
    }

    res.end(`Hello from worker ${pid}`);
  });

  server.listen(8080, () => {
    console.log(`Worker pid: ${pid}`);
  });
}

워커가 무작위로 죽고 재시작되는 와중에도 25,000개 요청 중 1,000개만 실패했다. exitedAfterDisconnect 검사가 중요한 이유는, 아래의 의도적인 종료까지 재시작해 버리면 무중단 배포가 무한 루프가 되기 때문이다.

다운타임 제로 시작
  • 새 버전을 릴리즈할 때 다운타임이 생길 수 있다.
  • 다운타임 동안에는 새 요청을 처리할 수 없고, 제약에 따라 이를 허용할 수 없는 경우가 있다.
  • SIGUSR2 신호를 받으면 워커를 하나씩 종료하고 새 워커를 만들어 무중단 배포를 구현한다.
zero-downtime.ts 
import { createServer } from "http";
import { cpus } from "os";
import cluster from "cluster";
import { once } from "events";

const { pid } = process;

if (cluster.isMaster) {
  console.log("master", pid);

  const availableCpus = cpus();
  console.log("Clustering with %d CPUs", availableCpus.length);
  availableCpus.forEach(() => cluster.fork());

  process.on("SIGUSR2", async () => {
    const workers = Object.values(cluster.workers!);
    for (const worker of workers) {
      console.log("Stopping Worker: %d", worker?.process.pid);
      worker?.disconnect();                  // 새 연결을 받지 않는다
      await once(worker!, "exit");           // 기존 요청이 끝나기를 기다린다
      if (!worker?.exitedAfterDisconnect) {
        continue;
      }
      const newWorker = cluster.fork();
      await once(newWorker!, "listening");   // 새 워커가 준비될 때까지
    }
  });
} else {
  const server = createServer((req, res) => {
    let i = 1e7;
    while (i > 0) {
      i--;
    }

    res.end(`Hello from worker ${pid}`);
  });

  server.listen(8080, () => {
    console.log(`Worker pid: ${pid}`);
  });
}

한 번에 하나씩 교체하므로 언제나 처리 가능한 워커가 남아 있다 — await once(newWorker, "listening") 이 핵심이다. 이걸 빼고 동시에 다 죽이면 그냥 다운타임이 있는 재시작이 된다.

상태 저장 통신 다루기

  • 클러스터 모듈의 문제는 캐싱된 데이터가 각 워커에만 남는다는 점이다.
  • 이는 클러스터에만 국한된 문제가 아니라, 상태를 고려하지 않는 모든 로드밸런싱 알고리즘에 적용된다.

단일 프로세스에서 잘 돌던 코드가 조용히 깨진다

11-2에서 만든 Map 기반 캐시를 떠올려 보자. 워커가 4개면 캐시도 4개가 되어 적중률이 1/4로 떨어지고, 워커마다 다른 값을 들고 있을 수 있다. 메모리 세션도 마찬가지다 — 로그인한 사용자가 다음 요청에서 로그아웃 상태로 보인다. 코드는 그대로인데 프로세스만 늘렸을 뿐인데도 그렇다.

여러 인스턴스의 상태 공유
  • 외부 저장소인 데이터베이스나 Redis 같은 캐시 계층을 쓸 수 있다.
  • 단점은 기존 코드에서 바꿔야 하는 부분이 상당히 많다는 것이다.
  • 간단히 하려면 스티키 세션처럼 고정 로드밸런싱을 쓸 수도 있다.
고정 로드밸런싱
  • 모든 요청을 항상 고정된 인스턴스로 라우팅하는 방법이 고정(스티키) 로드밸런싱이다.
  • 로드밸런서가 새 요청을 받으면, 알고리즘이 고른 인스턴스가 아니라 정해진 인스턴스로 보낸다.
  • 보통 세션 ID 나 IP 를 기준으로 하는데, IP 는 LTE 환경이나 네트워크 로밍처럼 주소가 바뀌는 환경에서 제대로 동작하지 않는다.
  • 또한 고정된 인스턴스에 장애가 나면 답이 없으므로, 가능하면 공유 저장소에 세션 상태를 두는 편이 좋다.
기준공유 저장소 (Redis 등)스티키 세션
코드 변경많음거의 없음

부하 분산 균형고름치우칠 수 있음

역방향 프록시 확장

  • 클러스터 외에, 전통적인 기술들은 고가용성 운영 환경에서 더 많은 제어와 성능을 보장해 선호된다.
  • 동일한 앱을 실행하는 인스턴스들 앞에 로드밸런서를 두어 트래픽을 분산한다.
  • Nginx, HAProxy 등 다양한 방법이 있다.

동적 수평 확장

  • 서버 개수를 미리 모르는 상태에서, 트래픽에 따라 동적으로 조정할 수 있다.
서비스 레지스트리 사용
  • 실행 중인 서버와 그들이 제공하는 서비스를 추적하는 중앙 서비스(서비스 레지스트리)를 두는 것이 일반적인 패턴이다.

피어 투 피어 로드밸런싱

  • 중앙 집중식 로드밸런서를 제거하고 클라이언트가 서버에 직접 접근하는 방식이다.

컨테이너를 사용한 앱 확장

  • Docker 를 사용해 컨테이너 단위로 확장할 수 있다.
  • Kubernetes — 컨테이너를 관리할 수 있는 도구.
i

그럼 클러스터 모듈은 언제 쓰는가 보강

오케스트레이터(Kubernetes 등)를 쓰는 환경이라면 컨테이너 하나에 프로세스 하나가 일반적이다. 복제·재시작·무중단 배포를 오케스트레이터가 이미 하기 때문에 클러스터 모듈이 그 일을 중복한다.

반대로 단일 VM 에 직접 배포하는 환경에서는 클러스터(또는 PM2 같은 프로세스 매니저)가 코어를 다 쓰는 가장 저렴한 방법이다. 어느 쪽이든 상태를 밖으로 빼야 한다는 결론은 같다.

정리

  • cluster 로 코어 수만큼 워커를 띄운다. 마스터가 소켓을 라운드로빈으로 분배 (윈도우 제외)
  • cluster.isMaster 는 deprecated → cluster.isPrimary (Node 16+)
  • 워커 재시작 시 exitedAfterDisconnect 로 의도적 종료와 크래시를 구분한다
  • 무중단 배포는 한 번에 하나씩 교체하고, 새 워커의 listening 을 기다린다
  • 복제의 진짜 비용은 상태 분산이다 — 스티키 세션은 임시방편, 공유 저장소가 정답
12-3

복잡한 애플리케이션 분해

쪼개는 것은 쉽다. 어려운 것은 쪼갠 것들을 다시 잇는 방법이다.

핵심 마이크로서비스의 비용은 대부분 통합 방식에서 나온다. 프록시 → 오케스트레이션 → 메시지 브로커 순으로 결합도가 낮아지고, 대신 추적 난이도가 올라간다.

모놀리식 아키텍처

  • 모든 구성요소가 하나로 합쳐진 아키텍처다.
  • 단점은 구성요소 하나에 장애가 나도 전체에 영향을 미친다는 것이다.

마이크로서비스 아키텍처

  • 작은 단위로 모듈을 쪼개서 하나의 큰 애플리케이션을 이루는 아키텍처다.
  • 하나의 서비스는 단일 데이터베이스를 가지고, 그 서비스들이 상호작용한다.

    S1 -.->|"통신"| S2
    S2 -.->|"통신"| S3
  end
서비스마다 자기 DB 를 갖는다는 것이 결정적이다 — DB 를 공유하면 스키마 변경이 다시 전체를 묶어 버려 분해의 의미가 사라진다. 대신 트랜잭션이 서비스 경계를 넘지 못한다는 대가를 치른다.

마이크로서비스 아키텍처의 통합 패턴

API 프록시
  • 서비스 간 통신을 프록시하는 API 프록시 / 게이트웨이를 둔다.
  • 단일 진입점 제공, 캐싱, 확장 등에 매우 유용하다.
API 오케스트레이션
  • 서비스 집합을 통합하고 구성하는 가장 일반적인 방법이다.
  • 서로 다른 서비스의 데이터를 단일 응답으로 결합한다.
  • completeCheckout 같은 함수가 각 서비스를 호출해 최종적으로 하나의 진입점을 만든다.
메시지 브로커와의 통합
  • 오케스트레이터의 단점은 너무 많은 것을 알고 수행하는 God 객체가 된다는 점이다.
  • 높은 결합도, 낮은 응집력, 높은 복잡도를 야기한다.
  • 이를 해결하기 위해 중앙에 메시지 브로커를 두고 pub/sub 방식으로 구현할 수 있다(13-2).

화살표의 방향이 결합도를 말해 준다 — 왼쪽은 오케스트레이터가 세 서비스를 전부 알아야 하고, 배송 서비스가 추가되면 오케스트레이터를 고쳐야 한다. 오른쪽은 주문 서비스가 누가 듣는지 모르므로 구독자를 늘려도 발행자는 그대로다. 대신 "이 요청이 어디까지 갔는지" 추적하기가 훨씬 어려워진다.
i

패턴 이름은 다르지만 이미 아는 이야기다 보강

API 프록시는 8-1 프록시를 네트워크 경계로 옮긴 것이고, 메시지 브로커 방식은 3-2 관찰자 패턴을 프로세스 경계 너머로 확장한 것이다 (그래서 13-2가 pub/sub 을 "분산된 옵저버 패턴"이라 부른다). 같은 패턴이 규모만 바뀌어 반복된다는 것이 이 책 전체를 관통하는 구조다.

정리

  • 모놀리식은 한 곳의 장애가 전체로 번지고, 마이크로서비스는 격리되는 대신 인프라가 복잡해진다
  • 서비스마다 자기 DB 를 갖는 것이 원칙 — 공유하면 분해의 의미가 사라진다
  • 통합은 API 프록시 → 오케스트레이션 → 메시지 브로커 순으로 결합도가 낮아진다
  • 오케스트레이터는 God 객체가 되기 쉽다. 브로커는 결합을 끊는 대신 추적을 어렵게 한다
