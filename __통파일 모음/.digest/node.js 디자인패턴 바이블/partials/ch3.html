3-1

콜백 패턴

콜백의 규칙은 취향이 아니다. 하나라도 어기면 앱이 조용히 망가진다.

핵심 하나의 API 는 항상 동기이거나 항상 비동기여야 한다. 조건에 따라 갈리는 순간, 리스너를 등록할 틈이 있느냐 없느냐가 입력에 따라 달라지고 로그조차 남지 않는 버그가 태어난다.

콜백 패턴

  • 자바스크립트는 콜백에 이상적인 언어다.
  • 함수가 일급 객체다 — 변수에 할당하고, 인자로 전달하고, 반환할 수 있다.
  • 클로저가 있다 — 생성된 함수의 환경을 참조할 수 있어, 호출 시점과 무관하게 비동기 작업이 요청된 컨텍스트를 유지한다.

연속 전달 방식(CPS)

자바스크립트에서 콜백은 다른 함수에 인자로 전달되는 함수이며, 이 방식을 연속 전달 방식(Continuation Passing Style)이라 부른다. 항상 비동기 작업과 연관되는 것은 아니고, 단순히 결과를 호출자에게 반환하는 대신 다른 함수로 전달하는 것을 뜻한다.

동기식 연속 전달 방식

결과를 return 으로 돌려주는 일반적인 방식은 직접(direct) 스타일이라고 부른다.

sync-cps.ts 
function add(a: number, b: number) {
  return a + b;                      // 직접 스타일
}

function addCps(a: number, b: number, c: (num: number) => void) {
  c(a + b);                          // 연속 전달 방식 (동기)
}

console.log("before");
addCps(1, 2, (result) => console.log(`Result: ${result}`));
console.log("after");

/**
 * output
 *
 * before
 * Result: 3
 * after
 */
비동기 연속 전달 방식
  • setTimeout 은 비동기 작업을 실행시키기 위해 콜백의 실행이 끝날 때까지 기다리지 않는다.
  • 즉시 반환되고 제어권은 호출자에게 넘어간다.
  • 핸들러의 실행은 이벤트 루프에서 시작되기 때문에 새로운 스택을 가진다.
  • 다른 시점, 다른 위치에서 호출되더라도 클로저 덕분에 호출자의 컨텍스트가 유지된다.
async-cps.ts 
function additionAsync(a: number, b: number, cb: (num: number) => void) {
  setTimeout(() => cb(a + b), 100);
}

console.log("before");
additionAsync(1, 2, (result) => {
  console.log(`result: ${result}`);
});
console.log("after");

/**
 * output
 *
 * before
 * after           ← 순서가 뒤집혔다
 * result: 3
 */
비연속 전달 콜백

콜백 파라미터가 있다고 해서 비동기이거나 CPS 인 것은 아니다. 구현 방식에 따라 다르다.

non-cps.ts 
const result = [1, 2, 3].map((item) => item * item);
console.log(result); // [1, 4, 9]  ← 콜백이지만 동기이고 CPS 도 아니다

동기? 비동기?

일반적으로 모순과 혼돈을 만드는 방법은 무조건 피해야 한다.

예측할 수 없는 함수
  • 캐시에 파일이 저장되어 있다면 동기식으로 반환한다.
  • 처음 보는 파일이라면 비동기식으로 반환한다.
  • 조건에 따라 동기/비동기로 갈리는 함수는 매우 위험하다.
inconsistentRead.ts Zalgo 
import { readFile } from "fs";

const cache = new Map();

function inconsistentRead(filename: string, cb: (data: unknown) => unknown) {
  if (cache.has(filename)) {
    // 동기 호출
    cb(cache.get(filename));
  } else {
    // 비동기 호출
    readFile(filename, "utf8", (err, data) => {
      cache.set(filename, data);
      cb(data);
    });
  }
}
Zalgo를 풀어놓다

예측 불가능한 함수를 쓰면 앱이 쉽게 손상된다. Node.js 커뮤니티에서는 이런 행동을 "Zalgo를 풀어놓았다"고 부른다.

createFileReader.ts 두 번째 로그가 찍히지 않는다 
function createFileReader(filename: string) {
  const listeners: Array<(v: unknown) => void> = [];
  inconsistentRead(filename, (value) => {
    listeners.forEach((listener) => listener(value));
  });

  return {
    onDataReady: (listener: (v: unknown) => void) => listeners.push(listener),
  };
}

const reader1 = createFileReader("data.txt");
reader1.onDataReady((data) => {
  console.log(`First call data: ${data}`);

  // 잠시 후 같은 파일을 다시 읽으려고 시도
  const reader2 = createFileReader("data.txt");
  reader2.onDataReady((data) => {
    console.log(`Second call data: ${data}`);
  });
});

/**
 * output
 *
 * First call data: Hello, world!
 *                              ← Second call 은 영원히 찍히지 않는다
 */

리스너를 등록할 "틈"이 있느냐가 캐시 상태에 따라 달라진다 — 비동기 경로에서는 반환 후 등록할 시간이 있지만, 동기 경로에서는 생성자가 반환되기도 전에 콜백이 끝나 버린다.

이런 버그는 실제 앱에서 로그도 남지 않고 예외도 던지지 않아 탐지가 극도로 어렵다. 매우 위험한 결함이다.

해결책 1 — 동기 API 사용
  • 함수를 완전히 동기 방식으로 바꾸면 모순이 사라진다.
  • 동기식이 되면 더 이상 CPS 를 가질 이유도 없어진다.
  • 다만 대부분의 경우 동기 I/O 는 권장되지 않고, 큰 파일을 동기식으로 다루는 것은 절대 금물이다.
sync-fix.ts 모순 없음 
function consistentReadSync(filename: string) {
  if (cache.has(filename)) {
    return cache.get(filename);
  } else {
    const data = readFileSync(filename, "utf8");
    cache.set(filename, data);
    return data;
  }
}
해결책 2 — 지연 실행으로 비동시성 보장
  • 비동기 방식을 유지하면서도 고칠 수 있다.
  • 중요한 트릭은 동기 콜백 호출을 즉시 실행하는 대신 가까운 미래로 예약하는 것이다.
  • Node의 process.nextTick() 이 그 역할을 한다 — 현재 진행 중인 작업의 완료 시점 뒤로 함수 실행을 지연시킨다.
nextTick-fix.ts 항상 비동기 
function consistentRead(filename: string, cb: (data: unknown) => unknown) {
  if (cache.has(filename)) {
    process.nextTick(() => cb(cache.get(filename)));
  } else {
    readFile(filename, "utf-8", (err, data) => {
      cache.set(filename, data);
      cb(data);
    });
  }
}

용어 다듬기 원문 교정

노트는 process.nextTick() 으로 지연된 콜백을 "마이크로 태스크"라고 부르지만, Node 문서는 nextTick 큐와 마이크로태스크(Promise) 큐를 별개로 구분한다. 두 큐 모두 현재 작업 직후에 비워지지만 nextTick 큐가 항상 먼저다. "이벤트 루프의 다음 페이즈로 넘어가기 전에 처리되는 별도의 큐"라고 이해하는 편이 정확하다.

또한 setImmediate() 를 "setTimeout(fn, 0) 과 비슷하다"고 한 서술은 결과적으로는 비슷해 보이지만 메커니즘이 다르다. setImmediate 는 이벤트 루프의 check 페이즈에서, setTimeout 은 timers 페이즈에서 실행된다. 그래서 메인 모듈에서 둘을 나란히 호출하면 실행 순서가 비결정적이지만, I/O 콜백 안에서 호출하면 setImmediate 가 항상 먼저다. (근거: Node.js Docs — Event Loop, Timers, and process.nextTick())

노드의 콜백 규칙

CPS 콜백은 일련의 특정한 규칙을 따른다. 콜백 API 를 정의한다면 이를 이해하고 반드시 준수해야 한다.

콜백 함수는 맨 마지막에
  • 함수가 입력으로 콜백을 받는다면, 콜백은 마지막 인자여야 한다.
  • 위치가 마지막이면 함수 호출의 가독성이 좋아진다.
last-arg.ts 
readFile("data.txt", (err, buffer) => {});
오류는 맨 처음에
  • 첫 번째 인자로 오류를, 실제 결과나 기타 값은 두 번째 인자부터 전달한다.
  • 콜백에서는 항상 오류를 먼저 체크하는 것이 좋고, err 의 타입은 항상 Error 여야 한다.
error-first.ts 
import { readFile } from "fs";

readFile("foo.txt", "utf-8", (err, data) => {
  if (err) {
    // ...
  } else {
    process(data);
  }
});

스타일전파 방식

readJSON.ts try/catch 로 감싸 콜백으로 전달 
import { readFile } from "fs";

function readJSON(
  filename: string,
  cb: (err: Error | unknown | null, arg?: string) => void
) {
  readFile(filename, "utf8", (err, data) => {
    let parsed: any;

    if (err) {
      return cb(err);
    }

    try {
      parsed = JSON.parse(data);
    } catch (err) {
      return cb(err);
    }

    cb(null, parsed);
  });
}
catch 되지 않는 예외
  • 에러는 비동기 실행을 발생시킨 함수 쪽이 아니라, 예외가 발생한 별도의 콜스택을 타고 이벤트 루프까지 전파된다.
  • 예외가 이벤트 루프에 도달하는 순간 앱은 중단된다.
  • Node는 프로세스를 종료하기 전에 uncaughtException 이라는 특수 이벤트를 발행한다.
  • 이런 문제가 생기면 앱을 즉시 종료하고 프로세스 관리자가 재시작하게 하는 편이 좋다. 이를 fail-fast 접근법이라고 부른다.

왜 바깥 try/catch 로 못 잡는가 보강

readJSON() 을 try/catch 로 감싸도 소용없다. readFile 의 콜백은 readJSON 이 이미 반환된 뒤, 완전히 새로운 스택에서 이벤트 루프가 호출하기 때문이다. 1-2에서 본 리액터 패턴의 구조가 그대로 에러 전파 경로를 결정한다.

정리

  • CPS = 결과를 반환하는 대신 다음 함수로 전달. 비동기와 동의어가 아니다
  • 동기/비동기가 조건에 따라 갈리면 Zalgo — 리스너 등록 타이밍이 입력에 따라 달라진다
  • 해법은 두 개: 완전히 동기로 만들거나, process.nextTick() 으로 항상 비동기로 만들거나
  • 규칙: 콜백은 마지막 인자, 에러는 첫 번째 인자, 에러는 던지지 말고 콜백으로 전달
  • 콜백 안의 예외는 새 스택에서 터진다 → 바깥 try/catch 로 못 잡는다 → fail-fast

관찰자 패턴

콜백은 한 번, 이벤트는 여러 번. 그리고 EventEmitter 는 구독 해제를 잊으면 새는 그릇이다.

핵심 딱 한 번 결과가 나오면 콜백, 같은 종류의 일이 여러 번 일어나면 이벤트. 이 기준 하나면 대부분의 API 설계 선택이 끝난다.

EventEmitter 클래스

  • Node에서는 내장 EventEmitter 클래스로 관찰자 패턴을 구현한다.
  • 특정 유형의 이벤트가 발생하면 호출되는 하나 이상의 함수를 리스너로 등록할 수 있다.
emitter.ts 
import { EventEmitter } from "events";

const emitter = new EventEmitter();
필수 메서드
메서드동작
on(event, listener)주어진 이벤트에 대한 리스너 등록
once(event, listener)이벤트가 한 번 전달되고 나서 자동 제거되는 리스너 등록
off(event, listener)지정된 이벤트에 대한 리스너 제거
emit(event, ...args)이벤트를 동기적으로 발생시켜 등록 순서대로 리스너 호출
!

원문 교정 원문 교정

노트에는 리스너 제거 메서드가 remove(event, listener) 로 적혀 있는데, 실제 API 이름은 removeListener(event, listener) 이고 그 별칭이 off() 다. remove() 라는 메서드는 존재하지 않는다.

또한 노트 뒷부분의 removeEventListener 역시 DOM 의 API 이름이며 EventEmitter 에는 없다. Node v24.17.0 에서 확인하면 typeof emitter.off 와 typeof emitter.removeListener 는 "function", typeof emitter.removeEventListener 는 undefined 다. (근거: Node.js Docs — emitter.removeListener())

findRegex.ts 
import { EventEmitter } from "events";
import { readFile } from "fs";
import path from "path";

function findRegex(files: string[], regex: RegExp) {
  const emitter = new EventEmitter();
  for (const file of files) {
    readFile(file, "utf8", (err, content) => {
      if (err) {
        return emitter.emit("error", err);
      }

      emitter.emit("fileread", file);
      const match = content.match(regex);
      if (match) {
        match.forEach((line) => emitter.emit("found", file, line));
      }
    });
  }

  return emitter;
}

const files = [
  path.join(__dirname, "..", "static", "fileA.txt"),
  path.join(__dirname, "..", "static", "fileB.txt"),
];

findRegex(files, /hello \w+/g)
  .on("fileread", (file) => console.log(`${file} was found`))
  .on("found", (file, match) => console.log(`Matched ${match} in file ${file}`))
  .on("error", (err) => console.error(`Error emitted ${err.message}`));

/**
 * output
 *
 * Error emitted ENOENT: no such file or directory, open '.../static/fileB.txt'
 * .../static/fileA.txt was found
 */
i

이 예제가 동작하는 이유 보강

findRegex() 는 emitter 를 즉시 반환하고, readFile 콜백은 이벤트 루프의 다음 사이클에 실행된다. 그래서 .on(...) 체인을 붙일 시간이 생긴다. 이 순서가 뒤집히면 어떻게 되는지가 바로 아래 "동기 및 비동기 이벤트"의 주제다.

오류 전파

  • EventEmitter 는 콜백처럼 에러를 단순히 throw 할 수 없다.
  • 대신 "error" 라는 특수 이벤트를 발생시키고 Error 객체를 인자로 전달하는 규약을 따른다.
×

error 리스너가 없으면 프로세스가 죽는다

"error" 이벤트는 특별 취급된다. 리스너가 하나도 등록되어 있지 않은 상태에서 emit 되면 Node 는 그 Error 를 그대로 던져 프로세스를 종료시킨다. EventEmitter 를 반환하는 API 를 쓸 때 .on("error", ...) 는 선택이 아니다.

관찰 가능한 객체 만들기

EventEmitter 를 그대로 쓰는 경우는 드물고, 보통 다른 클래스가 이를 확장한다.

FindRegex.ts 
import { EventEmitter } from "events";
import { readFile } from "fs";
import path from "path";

class FindRegex extends EventEmitter {
  private regex: RegExp;
  private files: string[] = [];

  constructor(regex: RegExp) {
    super();
    this.regex = regex;
  }

  addFile(file: string) {
    this.files.push(file);
    return this;                 // 체이닝을 위해 this 반환
  }

  find() {
    for (const file of this.files) {
      readFile(file, "utf8", (err, content) => {
        if (err) {
          return this.emit("error", err);
        }

        this.emit("fileread", file);
        const match = content.match(this.regex);
        if (match) {
          match.forEach((line) => this.emit("found", file, line));
        }
      });
    }

    return this;
  }
}

const fileA = path.join(__dirname, "..", "static", "fileA.txt");
const fileB = path.join(__dirname, "..", "static", "fileB.txt");

new FindRegex(/hello \w+/g)
  .addFile(fileA)
  .addFile(fileB)
  .find()
  .on("fileread", (file) => console.log(`${file} was found`))
  .on("found", (file, match) => console.log(`Matched ${match} in file ${file}`))
  .on("error", (err) => console.error(`Error emitted ${err.message}`));

EventEmitter와 메모리 누수

  • 이벤트를 구독하고 나서 더 이상 필요하지 않다면 구독을 해지하는 것이 필수다.
  • 그러지 않으면 메모리 사용량이 무한히 증가하므로 명백한 소프트웨어 결함이다.
leak.ts 누수 
import EventEmitter from "events";

const thisTakesMemory = "A big string";
const listener = () => {
  console.log(thisTakesMemory);
};

const emitter = new EventEmitter();
emitter.on("event", listener);

리스너가 해제되기 전까지 thisTakesMemory 는 클로저에 붙들려 GC 대상이 되지 않는다. 수명이 긴 EventEmitter 에 리스너를 계속 등록하면 그대로 메모리 누수다.

경고와 예방 원문 교정

동일 이벤트에 리스너가 10개를 초과하면(즉 11번째부터) Node 가 MaxListenersExceededWarning 을 출력한다. 노트의 "10개 이상부터"는 경계가 한 칸 어긋난 표현이다. 기본값은 events.defaultMaxListeners 이며 Node v24.17.0 에서 10 임을 확인했다.

예방 수단은 off() / removeListener() 로 해제하거나, 인스턴스별로는 emitter.setMaxListeners(n), 전역으로는 events.defaultMaxListeners 를 조정하는 것이다. 다만 경고를 끄는 것이 누수를 고치는 것은 아니다 — 상한을 올리기 전에 왜 리스너가 쌓이는지부터 봐야 한다.

동기 및 비동기 이벤트

  • 이벤트도 콜백과 마찬가지로 이벤트를 생성하는 작업이 언제 호출되느냐에 따라 동기/비동기로 갈린다.
  • 그리고 이 둘을 절대 섞어 쓰면 안 된다.
  • 비동기라면 이벤트가 이벤트 루프의 다음 사이클까지 실행되지 않는 것이 보장되므로, 현재 스택이 이벤트 루프로 넘어가기 전까지 새 리스너를 등록할 시간이 있다.
이벤트를 동기적으로 발생시킨다면?

동기라면 모든 리스너를 작업 실행 전에 등록해야 한다. 그러지 않으면 이벤트를 전부 유실한다.

FindRegex.ts (동기 버전) 리스너 등록 틈이 없다 
  find() {
    for (const file of this.files) {
      let content: string;

      try {
        content = readFileSync(file, "utf8");
        this.emit("fileread", file);
        const match = content.match(this.regex);
        if (match) {
          match.forEach((elem) => this.emit("found", file, elem));
        }
      } catch (err) {
        this.emit("error", err);
      }
    }

    return this;
  }

readFile 을 readFileSync 로 바꾸면 find() 가 반환되기 전에 모든 이벤트가 이미 끝나 있다. 아래처럼 .on("error", ...) 를 find() 뒤에 붙이면 리스너가 등록될 틈이 없다.

main.ts 
const findRegexInstance = new FindRegex(/hello \w+/g);
findRegexInstance
  .addFile(fileA)
  .addFile(fileB)
  .find()                        // ← 여기서 이벤트가 전부 끝난다
  .on("fileread", (file) => console.log(`${file} was found`))
  .on("found", (file, match) => console.log(`Matched ${match} in file ${file}`))
  .on("error", (err) => console.error(`Error emitted ${err.message}`));

EventEmitter vs Callback

상황선택
딱 한 번 호출되고, 결과가 비동기적으로 반환됨콜백
반복적이고, 발생한 사건에 연결되어야 함이벤트
여러 종류의 결과를 구분해서 알려야 함이벤트

거의 동일한 기능을 나타내더라도 가독성, 의미, 구현 또는 코드의 양에서 갈린다.

compare.ts 
import { EventEmitter } from "events";

function helloEvents() {
  const eventEmitter = new EventEmitter();
  setTimeout(() => eventEmitter.emit("complete", "event hello world"), 100);
  return eventEmitter;
}

function helloCallback(
  cb: (err: Error | null | unknown, data: string) => void
) {
  setTimeout(() => cb(null, "callback hello world"), 100);
}

helloEvents().on("complete", (message) => console.log(message));
helloCallback((err, message) => console.log(message));
i

둘을 섞는 것도 정답일 때가 있다 보강

fs.createReadStream 처럼 "결과는 여러 번, 완료는 한 번"인 API 는 이벤트로 진행 상황을 알리고 콜백/Promise 로 최종 완료를 알린다. 6-2 스트림이 정확히 이 구조이며, EventEmitter 를 상속받은 대표적인 사례다.

정리

  • on / once / off(= removeListener) / emit 이 기본 4종
  • 에러는 throw 하지 않고 "error" 이벤트로. 리스너가 없으면 프로세스가 죽는다
  • 리스너 해제를 잊으면 클로저가 붙든 메모리가 그대로 누수된다. 11개째부터 경고
  • 이벤트를 동기적으로 발생시키면 리스너 등록 틈이 사라진다 → Zalgo 와 같은 함정
  • 한 번 = 콜백, 여러 번 = 이벤트. 진행 + 완료가 섞이면 둘 다 쓴다

연습문제 — FindRegex와 Ticker

직접 짜 보면 "리스너 등록 타이밍"이라는 개념이 손에 남는다.

1. 단순 이벤트

입력 파일 리스트를 인자로 넘기고, find 프로세스를 시작할 때 이벤트를 방출하도록 비동기 FindRegex 클래스를 수정한다.

exercise-1.ts 
import { EventEmitter } from "events";
import { readFile } from "fs";
import path from "path";

class FindRegex extends EventEmitter {
  private regex: RegExp;

  constructor(regex: RegExp) {
    super();
    this.regex = regex;
  }

  find(files: string[]) {
    for (const file of files) {
      readFile(file, "utf8", (err, content) => {
        this.emit("find_start", files);

        if (err) {
          return this.emit("error", err);
        }

        this.emit("fileread", file);
        const match = content.match(this.regex);
        if (match) {
          match.forEach((line) => this.emit("found", file, line));
        }
      });
    }

    return this;
  }
}

const fileA = path.join(__dirname, "..", "static", "fileA.txt");

const findRegexInstance = new FindRegex(/hello \w+/g);
findRegexInstance
  .find([fileA])
  .on("find_start", (files) =>
    console.log(`Searching in ${files.length} files`)
  )
  .on("fileread", (file) => console.log(`${file} was found`))
  .on("found", (file, match) => console.log(`Matched ${match} in file ${file}`))
  .on("error", (err) => console.error(`Error emitted ${err.message}`));
!

이 구현의 문제 보강

find_start 를 readFile 콜백 안에서 emit 하기 때문에, 파일 개수만큼 중복 발행된다. "find 프로세스를 시작할 때"라는 요구사항대로라면 루프 바깥에서 한 번만 emit 해야 한다. 다만 그러면 이번에는 find() 반환 전에 emit 되어 리스너가 못 받는다 — 3-1에서 본 대로 process.nextTick() 으로 한 틱 미뤄야 한다.

exercise-1-fixed.ts 한 번만, 그러나 한 틱 뒤에 
  find(files: string[]) {
    process.nextTick(() => this.emit("find_start", files));

    for (const file of files) {
      readFile(file, "utf8", (err, content) => {
        // ... 나머지는 동일
      });
    }

    return this;
  }

2. Ticker

  • number 와 콜백을 인자로 받는 함수를 작성한다.
  • 호출 후 number 밀리초가 지나기 전까지 매 50밀리초마다 tick 이벤트를 내보내는 EventEmitter 를 반환한다.
  • number 밀리초가 지났을 때 tick 이 일어난 횟수를 받는 콜백을 호출한다.
exercise-2.ts 
import EventEmitter from "events";

let count = 0;

const tick = (emitter: EventEmitter) => {
  count++;
  emitter.emit("tick");
};

const ticker = (ms: number, cb: (count: number) => void) => {
  const eventEmitter = new EventEmitter();
  const interval = setInterval(() => tick(eventEmitter), 50);

  setTimeout(() => {
    clearInterval(interval);
    cb(count);
  }, ms);

  return eventEmitter;
};

const emitter = ticker(500, (count) => {
  console.log(count);
}).on("tick", () => {});
i

count 를 모듈 전역에 둔 부작용 보강

ticker() 를 두 번 호출하면 두 인스턴스가 같은 count 를 공유해 값이 섞인다. ticker 함수 안에 let count = 0 을 두면 클로저마다 독립된 카운터가 된다 — 7-1 팩토리에서 다루는 "클로저로 상태 캡슐화"의 가장 작은 사례다.

3. 간단한 수정

함수 호출 즉시 tick 이벤트를 생성하도록 바꾼다.

exercise-3.ts 
const ticker = (ms: number, cb: (count: number) => void) => {
  const eventEmitter = new EventEmitter();
  tick(eventEmitter);                          // ← 즉시 한 번
  const interval = setInterval(() => tick(eventEmitter), 50);

  setTimeout(() => {

    cb(count);
  }, ms);

  return eventEmitter;

첫 tick 은 아무도 듣지 못한다

tick(eventEmitter) 를 반환 전에 동기적으로 호출하므로, 호출자가 .on("tick", ...) 을 붙이기 전에 이미 emit 이 끝난다. 3-2의 "동기 이벤트" 함정이 그대로 재현된 것이다. process.nextTick(() => tick(eventEmitter)) 로 한 틱 미루면 해결된다.

4. 에러 다루기

tick 발생 시 timestamp 가 5로 나누어떨어지면 에러를 생성하도록 수정하고, 콜백과 EventEmitter 를 활용해 에러를 전파한다.

exercise-4.ts 
import EventEmitter from "events";

let count = 0;

const tick = (emitter: EventEmitter, ms: number) => {
  if (ms % 5 === 0) {
    throw new Error("ms must be a multiple of 5");
  }

  count++;
  emitter.emit("tick");
};

const ticker = (ms: number, cb: (count: number) => void) => {
  const eventEmitter = new EventEmitter();

  try {
    tick(eventEmitter, ms);
    const interval = setInterval(() => tick(eventEmitter, ms), 50);
    setTimeout(() => {
      clearInterval(interval);
      cb(count);
    }, ms);
  } catch (err) {
    eventEmitter.emit("error", err);
  }

  return eventEmitter;
};

const emitter = ticker(500, (count) => {
  console.log(count);
})
  .on("tick", () => {})
  .on("error", (err) => {
    console.error(err);
  });
×

이 코드는 두 군데에서 터진다

(1) 첫 tick 이 던진 에러를 catch 해서 즉시 emit("error") 하는데, 아직 .on("error") 리스너가 없다 → Node 가 그대로 다시 던진다.

(2) setInterval 안에서 던진 에러는 이 try 블록이 잡지 못한다. 타이머 콜백은 3-1에서 본 대로 완전히 새로운 스택에서 실행되기 때문이다 → uncaughtException 으로 직행한다.

둘 다 process.nextTick(() => emitter.emit("error", err)) 로 emit 을 미루고, 인터벌 콜백 내부에도 자체 try/catch 를 두어야 해결된다.

정리

  • 이벤트를 emit 하기 전에 호출자가 리스너를 붙일 틈이 있는지 항상 확인한다
  • 생성 함수 안에서 동기적으로 emit 하면 그 이벤트는 아무도 듣지 못한다 → process.nextTick
  • 타이머/IO 콜백 안의 throw 는 바깥 try/catch 가 잡지 못한다
  • 모듈 전역 상태는 인스턴스가 둘 이상일 때 반드시 샌다 → 클로저 안으로 넣는다
