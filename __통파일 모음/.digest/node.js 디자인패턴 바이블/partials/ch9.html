9-1

전략 패턴

if 분기를 객체로 뽑아내면, 새 경우를 추가할 때 기존 코드를 열지 않아도 된다.

핵심 컨텍스트는 언제 호출할지만 알고, 전략은 무엇을 할지만 안다. 이 분리 덕분에 새 형식을 지원하는 데 Config 클래스를 한 줄도 고칠 필요가 없다.

전략 패턴

  • 컨텍스트라는 객체를 활성화시키고, 변하는 부분을 전략이라는 별도의 상호 교환 가능한 객체로 추출해 로직 변경을 지원한다.
  • 컴포넌트의 동작에 따라 복잡한 if / else if 분기가 필요한 경우 매우 유용하다.

여러 형식을 지원하는 환경설정 객체

하나의 대표 클래스를 두고, 내부 전략만 바꿔 가며 처리한다.

config.ts 
import { promises as fs } from "fs";
import ini from "ini";

interface FormatStrategy {
  deserialize: (data: any) => any;
  serialize: (data: any) => any;
}

class Config {
  data: any;
  private formatStrategy: FormatStrategy;

  constructor(formatStrategy: FormatStrategy) {
    this.data = {};
    this.formatStrategy = formatStrategy;
  }

  async load(filePath: string) {
    const file = await fs.readFile(filePath, "utf-8");
    this.data = this.formatStrategy.deserialize(file);
  }

  async save(filePath: string) {
    const file = this.formatStrategy.serialize(this.data);
    await fs.writeFile(filePath, file, "utf-8");
  }
}

const iniStrategy = {
  deserialize: (data: any) => ini.parse(data),
  serialize: (data: any) => ini.stringify(data),
};

const jsonStrategy = {
  deserialize: (data: any) => JSON.parse(data),
  serialize: (data: any) => JSON.stringify(data),
};

const main = async () => {
  const jsonConfig = new Config(jsonStrategy);
  await jsonConfig.load("static/config.json");
  await jsonConfig.save("static/config.json");
  console.log(jsonConfig.data);

  const iniConfig = new Config(iniStrategy);
  await iniConfig.load("static/config.ini");
  await iniConfig.save("static/config.ini");
  console.log(iniConfig.data);
};

main();

  S -.-> I["iniStrategy"]
  S -.-> Y["yamlStrategy (추가해도 Config 는 그대로)"]
YAML 을 지원하려면 전략 객체 하나만 추가하면 된다 — Config 안에 if (format === "yaml") 을 넣지 않아도 된다는 것이 전략 패턴이 사는 유일한 이유다.
i

자바스크립트에서는 객체 하나면 충분하다 보강

GoF 원문에서는 전략마다 클래스를 정의하지만, 여기서는 { serialize, deserialize } 형태의 평범한 객체 리터럴이면 된다. 7-1의 noopProfiler 와 같은 덕 타이핑 덕분이다. 전략이 함수 하나뿐이라면 아예 함수 그 자체를 전략으로 넘겨도 된다.

정리

  • 변하는 부분을 교체 가능한 객체(전략)로 뽑고, 컨텍스트는 호출 시점만 관리한다
  • 새 경우를 추가할 때 기존 클래스를 수정하지 않아도 된다
  • 자바스크립트에서는 클래스 없이 객체 리터럴 또는 함수만으로 전략을 표현할 수 있다
  • 전략은 런타임에 교체 가능하다는 점이 9-3 템플릿과의 결정적 차이
9-2

상태 패턴

전략을 사람이 고르면 전략 패턴, 상태가 고르면 상태 패턴이다.

핵심 상태 패턴은 전략 패턴의 특수한 경우다. 전략을 누가 선택하느냐 — 외부의 사용자냐, 컨텍스트 자신의 상태냐 — 만 다르다.
  • 컨텍스트의 상태에 따라 전략이 변경되는 특별한 전략 패턴이다.
  • 상태 패턴을 사용하면 서로 다른 컨텍스트 상태에서 서로 다른 전략이 선택된다. 이는 곧 컨텍스트 객체가 상태에 따라 다른 동작을 채택한다는 뜻이다.

이 책에서 상태 패턴이 실제로 쓰이는 곳 보강

원본 노트는 여기서 정의만 다루고 예제 없이 끝난다. 하지만 11-1 비동기적으로 초기화되는 컴포넌트의 사전 초기화 큐가 정확히 이 패턴이다 — 연결 전에는 query() 가 큐에 넣고, 연결 후에는 즉시 실행한다. 같은 메서드, 다른 동작, 상태에 의한 선택. 그쪽 아이템을 상태 패턴의 구현 예로 읽으면 좋다.

정리

  • 상태 패턴 = 전략을 컨텍스트의 상태가 선택하는 전략 패턴
  • 실행 중에 전략이 계속 바뀌고, 각 상태는 다음 상태를 알고 있다
  • 호출부에서 if (상태) 분기가 사라지는 것이 얻는 것
  • 구현 예는 11-1의 사전 초기화 큐
9-3

템플릿 패턴

전략은 런타임에 갈아 끼우고, 템플릿은 클래스를 정의하는 순간 확정된다.

핵심 같은 문제(변하는 부분 분리)에 대한 두 가지 답이다. 전략은 컴포지션, 템플릿은 상속. 그래서 결정 시점이 런타임과 정의 시점으로 갈린다.
  • 전략 패턴과 공통점이 많다.
  • 컴포넌트의 스켈레톤을 구현하는 추상 클래스를 정의한다.
  • 하위 클래스는 템플릿 함수라 불리는 누락된 부분을 구현해 빈 자리를 채운다.
  • 전략은 런타임에 동적으로 변경할 수 있지만, 템플릿은 구체 클래스가 정의되는 그 순간 전체 동작이 결정된다.

  A --> J["JsonConfig — _serialize / _deserialize 구현"]
  A --> I["IniConfig — _serialize / _deserialize 구현"]
골격은 부모가, 구멍은 자식이 채운다 — 9-1의 전략 버전과 최종 결과는 같지만, 여기서는 new JsonConfig() 하는 순간 형식이 확정되어 이후 바꿀 수 없다.

이 책 안에서 이미 만난 템플릿 보강

6-2 스트림의 _read / _write / _transform 이 전형적인 템플릿 함수다. Readable 이 흐름 제어·버퍼·배압이라는 골격을 완성해 두고, "데이터를 어디서 가져올지"라는 구멍만 _read 로 남겨 둔 것이다. 밑줄로 시작하는 이름 자체가 "이건 네가 채우는 자리"라는 신호다.

정리

  • 템플릿 = 추상 클래스가 골격을, 서브클래스가 빈 함수를 채우는 상속 기반 패턴
  • 전략(컴포지션)은 런타임 교체 가능, 템플릿(상속)은 정의 시점 확정
  • Node 스트림의 _read / _write / _transform 이 대표적인 실제 사례
9-4

반복자

자바스크립트에서는 클래스가 아니라 프로토콜로 구현된다.

핵심 next() 를 가지면 반복자, [Symbol.iterator]() 를 가지면 반복 가능자. 두 프로토콜을 만족하는 순간 for...of, 스프레드, 구조 분해가 공짜로 따라온다.

반복자

  • 반복자 패턴은 순회 결과를 처리하는 방식과 순회 알고리즘의 구현을 분리할 수 있게 한다.
  • 순서대로 생성되거나 조회된 요소들을 반복하는 인터페이스를 정의한다.

반복자 프로토콜

  • 자바스크립트에서 반복자 패턴은 상속 같은 구조가 아니라 프로토콜로 구현된다.
  • 반복의 현재 위치를 어떻게든 추적해야 하므로, 많은 경우 반복자는 상태 저장 객체다.
alphabet-iterator.ts 
const A_CHAR_CODE = 65;
const Z_CHAR_CODE = 90;

function createAlphabetIterator() {
  let currCode = A_CHAR_CODE;    // 클로저에 상태를 담는다

  return {
    next() {
      const currChar = String.fromCharCode(currCode);
      if (currCode > Z_CHAR_CODE) {
        return { done: true };
      }

      currCode++;
      return { done: false, value: currChar };
    },
  };
}

const iterator = createAlphabetIterator();

let iterationResult = iterator.next();
while (!iterationResult.done) {
  console.log(iterationResult.value);
  iterationResult = iterator.next();
}
!

이 반복자로는 for...of 를 못 쓴다

next() 만 있고 [Symbol.iterator]() 가 없기 때문이다. 반복자이지만 반복 가능자는 아니다. 그래서 위 예제가 while 루프로 직접 돌리고 있는 것이다. 아래의 반복 가능자 프로토콜이 필요한 이유가 여기 있다.

반복 가능자(iterable) 프로토콜

  • 객체가 반복자를 반환하는 표준화된 방법을 정의한다.
  • 자바스크립트에서는 내장 심볼인 Symbol.iterator 를 사용해 구현한다.
iterable.ts for...of 가 동작한다 
const alphabet = {
  [Symbol.iterator]() {
    return createAlphabetIterator();
  },
};

for (const letter of alphabet) {
  console.log(letter);
}

console.log([...alphabet]);   // 스프레드도 동작
const [first, second] = alphabet;   // 구조 분해도 동작
둘은 다른 프로토콜이다 — 배열이나 제너레이터 객체처럼 양쪽을 모두 만족하는 객체도 많다(자기 자신을 반환하는 [Symbol.iterator] 를 가진다). 6-2의 Readable 스트림이 for await 로 소비되는 것도 비동기판 같은 구조다.

제너레이터

  • ES2015 는 반복자와 밀접한 구문 구조를 도입했다.
  • 제너레이터 함수가 반환하는 제너레이터 객체는 반복자이면서 동시에 반복 가능자다.
generator.ts 
function* fruitGenerator() {
  yield "a";
  yield "b";
  return "c";
}

const generator = fruitGenerator();

console.log(generator.next()); // { value: 'a', done: false }
console.log(generator.next()); // { value: 'b', done: false }
console.log(generator.next()); // { value: 'c', done: true }
!

return 값은 for...of 에서 빠진다

세 번째 next() 는 { value: 'c', done: true } 를 돌려주지만, for (const x of fruitGenerator()) 는 "a" 와 "b" 만 순회한다. done: true 인 결과의 value 는 순회 대상이 아니라 반환값으로 취급되기 때문이다. [...fruitGenerator()] 도 ['a', 'b'] 다. 내보내고 싶은 값은 return 이 아니라 yield 해야 한다.

반복자 제어
  • next() 는 선택적으로 인자를 받을 수 있다.
  • 그 인자는 제너레이터 안에서 yield 표현식의 반환값으로 전달된다.
two-way.ts 
function* twoWay() {
  const received = yield "질문";     // next(x) 의 x 가 여기로 들어온다
  console.log(`받은 값: ${received}`);
}

const g = twoWay();
console.log(g.next().value);  // "질문"
g.next("대답");                // 받은 값: 대답

제너레이터가 단순한 값 생성기가 아니라 양방향 통신 채널이라는 점이 여기서 드러난다. async/await 가 등장하기 전, 이 성질을 이용해 비동기 흐름을 동기처럼 쓰는 기법(co 라이브러리)이 널리 쓰였다.

정리

  • 반복자 = next() 로 { done, value } 를 돌려주는 상태 저장 객체
  • 반복 가능자 = [Symbol.iterator]() 로 반복자를 돌려주는 객체. 둘은 별개의 프로토콜
  • 반복 가능자여야 for...of / 스프레드 / 구조 분해가 동작한다
  • 제너레이터 객체는 둘 다 만족하며, next(x) 로 값을 되돌려 보낼 수도 있다
  • return 한 값은 순회 대상에서 제외된다 — 내보내려면 yield
9-5

미들웨어

Express가 유행시킨 이름이지만, 실체는 인터셉터 필터와 책임 사슬이다.

핵심 미들웨어는 비동기 순차 실행 흐름(4-2)에 데이터를 넘겨 가며 각 단계가 처리 여부를 결정하는 구조다. 스트림의 pipe() 와 발상이 같고, 다루는 것이 청크가 아니라 요청일 뿐이다.

Express의 미들웨어

  • Express 의 미들웨어는 파이프라인으로 구성되어, 들어오는 HTTP 요청과 응답을 처리하는 함수들의 집합이다.
  • 이 로직은 비즈니스 로직처럼 엄격하지 않고 필수 기능도 아니다. 그저 액세서리에 가깝다.

패턴으로써 미들웨어

  • 실제로는 인터셉터 필터 패턴 및 책임 사슬 패턴으로 볼 수 있다.
  • 더 일반적인 용어로는 스트림을 연상시키는 파이프라인 처리로 보인다.
  • 이 패턴의 필수 컴포넌트는 미들웨어 관리자다.
    • use() 를 통해 미들웨어를 등록한다.
    • 처리할 새 데이터가 수신되면 등록된 미들웨어들이 비동기 순차 실행 흐름으로 호출된다.
  • 파이프라인 간 데이터 공유가 가능하다.
    • 추가 속성이나 함수를 붙여 입력 데이터를 증강한다.
    • 또는 불변성을 지키며 처리하고 항상 복사본을 반환한다.
flowchart LR
  REQ["요청"] --> M1["logger"]
  M1 -->|"next()"| M2["auth"]
  M2 -->|"next()"| M3["bodyParser"]
  M3 -->|"next()"| H["핸들러"]
  M2 -.->|"권한 없음 → next() 안 부름"| STOP["401 응답, 사슬 중단"]
next() 를 부르지 않으면 사슬이 거기서 끝난다 — 이것이 책임 사슬의 핵심이다. 각 단계는 처리하고 넘길지, 처리하고 끝낼지를 스스로 결정한다. 6-3에서 done() 호출 시점이 흐름을 결정했던 것과 같은 구조다.
i

증강 vs 불변 — 실무에서의 선택 보강

Express 는 증강 쪽이다. req.user = ... 처럼 요청 객체에 속성을 붙인다. 쓰기 쉽지만, 어느 미들웨어가 무엇을 붙였는지 타입으로 알 수 없고 이름 충돌 위험도 있다.

Koa 는 ctx.state 라는 별도 네임스페이스를 두어 이를 완화했고, Fastify 는 decorateRequest 로 미리 선언하게 한다. 직접 미들웨어 관리자를 만든다면, 붙일 자리를 명시적으로 하나 정해 두는 것이 나중을 편하게 한다.

미완성 노트

원본 노트는 여기까지이고, 책이 다루는 ZeroMQ 용 미들웨어 관리자 구현 예제는 적혀 있지 않다. 내용을 지어내지 않고, 위 개념 정리와 도해까지만 둔다.

정리

  • 미들웨어 = 인터셉터 필터 + 책임 사슬. 스트림 파이프라인과 발상이 같다
  • 미들웨어 관리자가 use() 로 등록받고 비동기 순차 실행으로 호출한다
  • next() 를 부르지 않으면 사슬이 중단된다 — 각 단계가 흐름을 통제한다
  • 데이터 전달 방식은 증강(Express) 또는 불변 복사본. 증강이라면 붙일 자리를 정해 두자
9-6

명령

"무엇을 할 것인가"를 객체로 만들면, 미루고 취소하고 보내고 되돌릴 수 있게 된다.

핵심 함수를 즉시 호출하면 그걸로 끝이지만, 호출 의도를 객체로 만들어 두면 실행 시점과 실행 주체를 나중에 정할 수 있다. 큐잉·재시도·되돌리기가 전부 여기서 열린다.

명령

  • 실행에 필요한 모든 정보를 캡슐화하며, 이렇게 만든 객체를 명령이라고 부른다.
  • 함수나 기능을 직접 호출하는 대신, 호출을 수행하려는 의도를 나타내는 객체를 만든다.
  • 구체화된 작업을 실제로 실행하는 것은 다른 컴포넌트가 담당한다.

작업 패턴

자바스크립트에서 호출을 나타내는 객체를 만드는 가장 쉬운 방법은 함수 주위에 클로저를 만드는 것이다.

createTask.ts 
function createTask(target: any, ...args: any[]) {
  // 방법 1 — bind 로 인자를 미리 묶는다
  const task = target.bind(null, ...args);
  return task;
}

function createTask2(target: any, ...args: any[]) {
  // 방법 2 — 클로저로 감싼다
  return () => {
    target(...args);
  };
}
!

노트의 코드는 두 방법이 한 함수에 섞여 있다 원문 교정

원본은 const task = target.bind(...) 로 만든 값을 쓰지 않고 버린 뒤 곧바로 클로저를 반환한다. 주석 #1, #2 로 미루어 두 가지 대안을 나란히 적어 둔 것으로 보여 위처럼 분리했다.

둘의 실질적 차이: bind 는 반환값을 그대로 전달하지만, 클로저 버전은 return 이 없어 반환값을 버린다. 결과를 받아야 한다면 return target(...args) 로 고쳐야 한다.

flowchart LR
  C["클라이언트 — 무엇을 할지 정한다"] --> CMD["명령 객체 — 대상 + 인자를 담는다"]
  CMD --> I["인보커 — 언제 실행할지 정한다"]
  I --> T["타깃 — 실제로 수행한다"]
  I -.-> Q["큐 / 재시도 / 취소 / 직렬화"]
호출을 객체로 만들면 그 사이에 무엇이든 끼워 넣을 수 있다 — 큐에 쌓거나(4-2 TaskQueue), 원격으로 보내거나(13-1 명령 메시지), 나중에 되돌리는 것이 전부 이 구조 위에서 가능해진다.

이 책에서 이미 지나온 명령들 보강

  • 13-1 명령 메시지 — 명령을 직렬화해 네트워크 너머로 보낸 것

패턴을 배우기 전에 이미 세 번 써 온 셈이다. 명령 패턴이 특별히 새로운 기법이라기보다 이미 하고 있던 일에 이름을 붙인 것에 가깝다는 뜻이기도 하다.

정리

  • 명령 = 호출의 의도(대상 + 인자)를 담은 객체. 실행은 다른 컴포넌트가 한다
  • 자바스크립트에서는 bind 나 클로저만으로 최소 형태를 만들 수 있다
  • 클로저로 감쌀 때 반환값을 버리지 않도록 return 을 빠뜨리지 않는다
  • 실행 시점을 분리했기에 큐잉 / 재시도 / 취소 / 원격 전송 / 되돌리기가 가능해진다
