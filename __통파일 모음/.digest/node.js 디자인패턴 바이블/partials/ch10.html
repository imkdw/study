10-1

브라우저와 코드 공유

서버는 파일을 그냥 실행하지만, 브라우저는 누군가 미리 묶어 줘야 한다.

핵심 번들러가 하는 일은 2-6에서 본 ESM 의 파싱 → 인스턴스화 단계를 빌드 타임에 미리 수행하는 것이다. 그래서 트리 셰이킹이 가능하고, 그래서 import 가 정적이어야 했다.

브라우저와 코드 공유

Node 에는 DOM 이나 수명이 긴 View 가 없고, 브라우저에는 파일 시스템 같은 OS 레벨 기능이 없다 (1-3의 벤 다이어그램).

크로스 플랫폼 컨텍스트의 자바스크립트 모듈

  • 브라우저에서 많은 파일을 개별로 내려받고 구문 분석하는 것은 성능이 매우 나쁘다.
  • 일반적인 해결 방법은 브라우저용 번들을 빌드하는 것이다.
  • 또한 코드 축소(minify)로 주석, 미사용 코드 등을 제거해 크기를 최소화할 수 있다.
번들러
  • 브라우저는 빌드와 런타임 두 단계가 필요하지만, 서버는 바로 실행할 수 있다.
  • 번들러에는 Webpack, Rollup 등 다양한 종류가 있다.
모듈 번들러의 작동 원리
  • 번들러는 비즈니스 로직을 바꾸지 않고, 브라우저에서 실행되도록 최적화된 파일만 생성한다.
  • 또한 Babel 같은 트랜스파일러를 통해 구버전 브라우저에서도 동작하도록 변환해 준다.
  • 번들러의 작업은 종속성 해결과 패킹 두 단계로 나뉜다.
종속성 해결
  • 모듈 시스템과 동일하게 진입점부터 시작해 종속성 그래프(비순환 유향 그래프)를 그린다.
  • 트리 셰이킹으로 미사용 import 등을 제거해 번들 크기를 줄인다.
패킹
  • 종속성 해결 단계의 최종 산출물인 모듈 맵을 가져와, 기존 비즈니스 로직을 포함한 단일 자바스크립트 실행 번들로 변환한다.
flowchart LR
  E["진입점 index.js"] --> D["종속성 해결 (그래프 작성 + 트리 셰이킹)"]
  D --> M["모듈 맵 (id → 모듈 함수)"]
  M --> P["패킹 (런타임 + 모듈 맵을 한 파일로)"]
  P --> B["bundle.js"]
번들은 "모듈 맵 + 아주 작은 require 구현"이다 — 2-4에서 손으로 짠 require1 과 cache 가 번들 런타임 안에 거의 그대로 들어간다. 발상이 새로운 것이 아니라 실행 위치만 바뀐 것이다.

2026년의 번들러 지형 보강

Webpack / Rollup 은 여전히 유효하지만, 개발 서버는 대체로 네이티브 ESM 을 그대로 브라우저에 던지고 번들하지 않는 방식(Vite 등)으로 옮겨갔다. 브라우저가 <script type="module"> 을 지원하므로 개발 중에는 묶을 이유가 없어졌기 때문이다. 프로덕션 빌드에서는 여전히 번들한다 — 요청 수와 트리 셰이킹 때문이다. 즉 위 두 단계 설명은 지금도 그대로 유효하고, 적용 시점만 개발/프로덕션으로 갈렸다.

정리

  • 브라우저는 빌드 단계가 필요하다 — 요청 수와 구문 분석 비용 때문
  • 번들러 = 종속성 해결(그래프 + 트리 셰이킹) → 패킹(모듈 맵 + 런타임을 한 파일로)
  • 트리 셰이킹이 가능한 이유는 ESM 의 import 가 정적이기 때문 (2-6)
  • 번들 런타임은 결국 작은 require 구현이다 (2-4)
10-2

크로스 플랫폼 개발의 기초

플랫폼 차이를 런타임에 흡수할지, 빌드 타임에 잘라낼지가 갈림길이다.

핵심 런타임 분기는 양쪽 코드를 모두 번들에 넣는다. 빌드 타임 분기는 한쪽을 아예 지운다. 번들 크기와 보안(서버 코드가 클라이언트로 새는 것)이 걸린 문제라 취향의 문제가 아니다.

런타임 코드 분기

  • 플랫폼마다 같은 코드를 쓰다 보면 코드 분기와 모듈 스와핑 문제가 생긴다.
  • 이럴 때는 런타임에 호스트 플랫폼을 인식해 if...else 로 분기하는 로직이 필요하다.
runtime-branch.ts 조건을 바로잡은 형태 
function sayHello(name: string) {
  if (typeof window !== "undefined" && window.document) {
    // 클라이언트 사이드 코드
    return;
  }

  // Node.js 코드
}
!

원문 교정 원문 교정

노트의 조건은 typeof window === "undefined" && window.document 인데, 이는 논리적으로 성립할 수 없다. window 가 정의되어 있지 않다는 것이 참이면 바로 다음의 window.document 접근에서 ReferenceError: window is not defined 가 난다.

브라우저를 감지하려는 의도이므로 !== 여야 한다. typeof 를 쓴 이유도 선언되지 않은 식별자에 안전하게 접근하기 위해서인데, 비교 방향이 뒤집히면서 그 안전장치가 무력화됐다.

런타임 코드 분기의 문제점
  • 사용되지 않는 불필요한 코드가 번들에 들어가 크기가 증가한다.
  • 호환성을 위한 코드가 비즈니스 로직과 섞여 가독성이 떨어진다.
  • 다행히 동적 임포트로 불러오는 모듈은 초기 번들에 포함되지 않는다.

번들 크기보다 심각한 문제

런타임 분기는 서버 전용 코드를 클라이언트 번들에 그대로 넣는다. 그 안에 DB 접속 문자열이나 API 시크릿이 있었다면 브라우저에서 읽을 수 있다. "죽은 코드니까 실행되지 않는다"는 것과 "보이지 않는다"는 것은 전혀 다른 이야기다.

빌드 시 코드 분기
  • Webpack 에서는 DefinePlugin, terser-webpack-plugin 등을 활용한다.
  • 미사용 코드를 압축·제거하고 코드 축소, 최적화를 적용할 수 있다.
flowchart TB
  S["if (typeof window !== 'undefined')"] --> D["DefinePlugin 이 상수로 치환"]
  D --> C["if (false) { ... }"]
  C --> T["Terser 가 죽은 코드로 판단해 삭제"]
  T --> R["번들에서 완전히 사라짐"]
조건을 상수로 만들어야 죽은 코드 제거가 작동한다 — 번들러가 false 임을 확정할 수 있어야 블록을 지운다. 런타임 값에 의존하는 조건은 지울 수 없으므로 코드가 그대로 남는다.
모듈 스와핑
  • 대부분의 경우 클라이언트 번들에 포함되어야 할 코드와 아닌 코드를 이미 알고 있다.
  • 사전에 정의해 두면 모듈 단위로 통째 교체할 수 있다.
!

표기 정정 원문 교정

노트는 모듈 스와핑도 Webpack.DefindPlugin(오타)으로 가능하다고 적었지만, DefinePlugin 은 값을 치환하는 플러그인이라 모듈 교체와는 역할이 다르다. 모듈 단위 교체는 resolve.alias(Webpack), NormalModuleReplacementPlugin, 또는 package.json 의 browser 필드 / exports 조건부 진입점으로 한다.

다만 DefinePlugin 으로 조건을 상수화하고 죽은 코드를 제거한다는 앞 절의 서술은 정확하다. 두 기법이 인접해 있어 섞인 것으로 보인다.

크로스 플랫폼 개발을 위한 디자인 패턴
패턴교체 단위노트의 설명
전략 / 템플릿알고리즘의 일부 단계 알고리즘의 공통 단계를 정의하고 일부만 교체한다. 플랫폼 무관한 부분을 공유하고, 다른 전략으로 플랫폼별 부분만 바꾼다
어댑터전체 컴포넌트 전체를 교체해야 할 때 가장 유용하다. 서버에서 쓰던 SQLite 를 브라우저용으로 대체하는 느낌
프록시같은 인터페이스의 내부 구현 fs 를 써야 할 때 프록시를 두고, 내부를 웹소켓이나 Ajax 로 서버에 위임한다

세 패턴이 교체 단위의 크기 순으로 늘어서 있다는 점이 이 표의 요점이다. 한 단계만 다르면 전략, 통째로 다르면 어댑터, 인터페이스는 같은데 구현만 원격이면 프록시다.

정리

  • 런타임 분기는 쉽지만 양쪽 코드가 모두 번들에 남는다 — 크기 문제이자 보안 문제
  • 빌드 타임 분기는 조건을 상수로 치환한 뒤 죽은 코드를 제거해 한쪽을 아예 지운다
  • 모듈 통째 교체는 resolve.alias / browser 필드 / 조건부 exports 로 한다
  • 패턴 선택은 교체 단위의 크기로 정한다 — 단계(전략) < 구현(프록시) < 컴포넌트(어댑터)
