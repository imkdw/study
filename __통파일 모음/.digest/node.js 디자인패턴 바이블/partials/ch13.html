13-1

메시징 시스템의 기초

메시징 설계는 세 개의 선택으로 거의 다 결정된다.

핵심 (1) 단방향인가 요청/응답인가, (2) 큐인가 스트림인가, (3) P2P 인가 브로커인가. 이 세 축의 조합이 곧 아키텍처다. 나머지는 프로토콜 선택일 뿐이다.

메시징과 통합 패턴

  • 확장성이 시스템의 배포에 관한 것이라면, 통합은 시스템들을 연결하는 것이다.
  • 분산 앱을 통합하는 방법에는 두 가지가 있다.
    • 공유 스토리지를 중앙의 중재자이자 정보 관리자로 사용
    • 메시지를 사용해 시스템 노드들에게 데이터, 이벤트, 명령을 전파
  • 분산 아키텍처에서 메시징 시스템은 네트워크를 통한 정보 교환을 용이하게 하는 솔루션을 가리킨다.

단방향 vs 요청/응답 패턴

구분단방향요청/응답

예웹소켓으로 브라우저에 메시지 보내기웹 서비스 호출, DB 쿼리
난이도단순여러 노드가 끼면 복잡해진다

메시지 유형

명령 메시지 수신자에서 작업의 실행을 트리거할 때. RPC 같은 시스템에서 사용 작업 이름 + 인자 목록
이벤트 메시지 무언가 발생했음을 다른 컴포넌트에 알릴 때. 분산 앱에서 매우 중요한 메커니즘 일어난 일과 그 맥락

명령과 이벤트의 차이가 결합도를 만든다 보강

명령은 "결제해라"이고 이벤트는 "주문이 생성되었다"이다. 명령은 수신자가 무엇을 해야 하는지 발신자가 안다는 뜻이므로 결합이 남고, 이벤트는 일어난 사실만 알릴 뿐이라 누가 어떻게 반응하든 발신자와 무관하다. 12-3에서 오케스트레이션과 브로커 방식이 갈리는 지점이 정확히 이 차이다.

명령 메시지는 9-6 명령 패턴을 직렬화해 네트워크 너머로 보낸 것이기도 하다.

비동기 메시징, 큐 및 스트림

구분동기식 통신비동기식 통신
비유전화 통화SMS
연결두 피어가 동시에 같은 채널에 연결되어 있어야 한다수신자가 연결되어 있지 않아도 보낼 수 있다
수신 시점실시간즉시, 일정 시간 후, 또는 아예 못 받을 수도
리소스더 많이 사용더 적게 사용하며 병렬 처리에 유리

비동기식은 메시지를 저장해 두었다가 가능한 한 빨리, 또는 나중에 전달할 수 있다. 메시지 대기열이 생산자와 소비자 사이에서 이를 가능하게 한다.

큐 vs 스트림

큐는 "누가 처리했나", 스트림은 "어디까지 읽었나"를 관리한다 — 그래서 스트림은 소비자를 나중에 추가해 과거 메시지를 전부 다시 읽게 할 수 있고, 큐는 그럴 수 없다.
구분큐스트림
소비 후메시지를 제거한다제거되지 않는다
전달보통 한 소비자에게 한 번에 하나소비자가 가져간다(pull), 처리할 수 있는 만큼
본질메시지 브로커데이터 저장소에 가깝다
재시작처리 중이던 메시지는 재전달이전에 처리한 지점부터 이어서
적합한 경우작업 분배, 각 메시지가 독립적일괄 처리, 과거 메시지 간 상관관계가 필요한 순차 데이터

피어 투 피어 또는 중개자 기반의 메시징

구분피어 투 피어중개자(브로커) 기반
전달 책임모든 노드가 수신자에게 직접 전달할 책임을 진다중앙의 메시지 브로커가 전달한다

브로커의 단일 장애 지점은 대개 해결되어 있다 보강

실무의 브로커(RabbitMQ, Kafka 등)는 클러스터와 복제를 지원하므로 "브로커 = SPOF" 는 개념적 정리이지 운영상의 결론은 아니다. 진짜 트레이드오프는 운영해야 할 인프라가 하나 더 생긴다는 것과, 그 대가로 모든 노드가 서로를 몰라도 된다는 것이다.

정리

  • 메시징 설계의 세 축: 방향(단방향/요청·응답) · 저장(큐/스트림) · 위상(P2P/브로커)
  • 메시지 유형 3종: 명령(무엇을 해라) / 이벤트(무엇이 일어났다) / 문서(데이터)
  • 명령은 결합을 남기고 이벤트는 결합을 끊는다
  • 큐는 소비 시 삭제, 스트림은 남기고 소비자마다 오프셋을 관리한다
  • P2P 는 지연이 짧고 SPOF 가 없지만, 브로커는 운영이 단순하다
13-2

발행/구독 패턴

프로세스 경계를 넘어간 관찰자 패턴.

핵심 pub/sub 의 가치는 발행자가 구독자를 모른다는 것 하나다. 구독자를 추가해도 발행자 코드는 그대로다 — 3-2의 EventEmitter 와 같은 이야기를 네트워크에서 반복하는 것이다.

발행/구독 패턴

  • pub/sub 또는 분산된 옵저버 패턴으로 잘 알려진 단방향 메시징 패턴이다.
  • 수신자는 메시지 수신에 대한 관찰을 등록한다.
  • 게시자는 모든 관련 구독자에게 배포되는 메시지를 생성한다.
  • 메시지 브로커를 사용하면 양쪽이 느슨하게 결합되어 분산 시스템의 노드를 통합하기에 이상적이다.
flowchart LR
  P["발행자"] -->|"publish('topic', msg)"| B["브로커 / 토픽"]
  B -->|"deliver"| S1["구독자 A"]
  B -->|"deliver"| S2["구독자 B"]
  B -.->|"나중에 추가해도 발행자는 그대로"| S3["구독자 C"]
발행자는 화살표의 끝을 모른다 — 3-2의 emitter.emit("found", ...) 가 리스너가 몇 개든 신경 쓰지 않았던 것과 정확히 같다. 달라진 것은 경계가 프로세스에서 네트워크로 넓어졌다는 점뿐이다.

큐를 통한 안정적인 메시지 전달

  • 메시징 시스템에서 가장 중요한 추상화는 메시지 큐다.
  • 큐 덕분에 발신자와 수신자가 동시에 활성 상태일 필요가 없어진다.
  • 시스템은 구독자의 연결이 끊겨 있는 동안 메시지를 쌓아 두어야 한다.
i

EventEmitter 와 결정적으로 다른 점 보강

3-2에서 봤듯 EventEmitter 는 emit 하는 순간 듣고 있지 않으면 놓친다. 큐가 있는 pub/sub 은 구독자가 죽어 있어도 메시지를 보관했다가 돌아오면 전달한다. "분산된 옵저버"라는 이름이 붙었지만, 내구성이라는 새 차원이 추가된 셈이다.

AMQP
  • 메시지 큐는 미션 크리티컬한 앱을 포함해, 메시지가 손실되면 안 되는 상황에서 사용된다.
  • AMQP 는 많은 메시지 대기열 시스템이 지원하는 개방형 표준 프로토콜이다.

스트림을 통한 안정적인 메시징

  • 순서가 지정되고 추가 전용인 영구적 데이터 구조다.
  • 메시지는 항상 스트림의 끝에 추가되고, 큐와 달리 소비될 때 자동으로 삭제되지 않는다.
  • 메시지 브로커보다는 데이터 저장소에 더 가깝다.
  • 소비자가 레코드를 가져오며, 자신이 처리할 수 있는 만큼만 가져온다.
  • 도중에 소비자가 중지됐다가 다시 실행되면 이전에 처리하고 남은 지점부터 처리를 시작한다.
스트림 vs 메시지 대기열
  • 스트림: 소비자가 메시지를 일괄 처리해야 하거나, 과거 메시지와의 상관관계를 찾아야 하는 순차적인 데이터를 처리하는 경우에 적합하다.
!

미완성 노트

원본 노트는 "스트림" 항목만 적혀 있고 큐 쪽 서술이 비어 있다. 내용을 지어내지 않고, 13-1에서 정리한 두 방식의 대비를 참고하도록 남긴다. 요약하면 각 메시지가 독립적인 작업이고 한 번만 처리되면 되는 경우가 큐 쪽이다.

i

6장의 스트림과는 다른 것이다 보강

같은 "스트림"이라는 단어지만 6장의 Node 스트림과는 층위가 다르다. 6장은 한 프로세스 안에서 데이터를 청크 단위로 흘리는 API 이고, 여기서는 브로커에 영구 저장되어 여러 소비자가 각자의 오프셋으로 읽는 로그다(Kafka 등). 공통점은 "전체를 한 번에 들지 않고 순서대로 흘려보낸다"는 발상뿐이다.

정리

  • pub/sub = 분산된 옵저버 패턴. 발행자가 구독자를 모르는 것이 전부이자 핵심
  • 큐가 붙으면 발신자와 수신자가 동시에 살아 있지 않아도 된다 — 내구성
  • AMQP 는 메시지 손실이 허용되지 않는 상황을 위한 개방형 표준
  • 스트림은 소비해도 지워지지 않고, 소비자가 오프셋을 들고 재개할 수 있다
  • 일괄 처리와 과거 메시지 상관관계가 필요하면 스트림, 독립적 작업이면 큐
13-3

작업 배포 패턴

소비자가 가져가게 만들면 확장이 저절로 따라온다.

핵심 HTTP 는 서버가 받는 구조라 부하 분산을 앞단이 책임져야 하지만, 작업 배포는 소비자가 가져가는 구조라 처리 속도가 곧 분배 비율이 된다.
  • 여러 컴퓨터에 작업을 분산시킬 수 있는 메시징 패턴이다.
  • 개별 작업 청크 또는 분할 정복 접근 방식을 사용한다.
  • HTTP 와의 차이는 소비자가 더 적극적인 역할을 한다는 것이다.
  • 단방향 비동기 통신을 사용해 더 나은 병렬 처리와 확장을 얻는다.
flowchart LR
  P["생산자"] -->|"작업 투입"| Q["작업 큐"]
  Q -->|"pull"| W1["워커 1 (빠름 → 많이 가져감)"]
  Q -->|"pull"| W2["워커 2 (느림 → 적게 가져감)"]
  Q -->|"pull"| W3["워커 3"]
  W1 --> R["결과 수집"]
  W2 --> R
  W3 --> R
부하 분산이 자동으로 일어난다 — 누구에게 얼마나 보낼지 정하는 주체가 없다. 워커가 여유가 생겨야 가져가므로 처리 속도가 그대로 분배 비율이 된다. 워커를 추가하는 것만으로 처리량이 늘어난다.

미완성 노트

원본 파일에는 위 다섯 줄까지만 적혀 있고 구현 예제가 없다. 내용을 지어내지 않고, 이 책 안에서 이미 만난 같은 구조만 아래에 연결해 둔다.

i

이미 세 번 만난 구조 보강

  • 4-2 TaskQueue — 한 프로세스 안, 동시성 제한 슬롯
  • 11-4 프로세스 풀 — 한 머신 안, OS 프로세스
  • 13-3 작업 배포 — 여러 머신, 메시지 큐

세 경우 모두 생산자가 큐에 넣고, 여유 있는 소비자가 가져간다는 구조가 같다. 경계가 함수 → 프로세스 → 네트워크로 넓어졌을 뿐이다. 정식 이름은 경쟁 소비자(competing consumers) 패턴이다.

정리

  • 원본 노트 미완성 — 개념 서술만 있고 구현 예제 없음
  • 작업 배포 = 생산자가 큐에 넣고 소비자가 가져가는 pull 구조
  • 분배 결정 주체가 없어 처리 속도가 곧 부하 분산이 된다
  • 4-2 TaskQueue / 11-4 프로세스 풀과 같은 구조가 네트워크로 확장된 것
13-4

요청/응답 패턴

단방향 채널 위에서 응답을 되받으려면, 상관관계를 직접 만들어야 한다.

  • 단방향 통신이 병렬성과 효율성 측면에서 큰 이점이 있지만, 때로는 다른 방법도 필요하다.
!

미완성 노트

원본 파일에는 위 한 줄만 적혀 있다. 내용을 지어내지 않고, 이 책 안에서 이미 다룬 같은 문제와 같은 해법만 아래에 연결해 둔다.

이 패턴이 푸는 문제

단방향 채널에서는 응답이 언제, 어떤 순서로 돌아올지 알 수 없다. 요청 A와 B를 연달아 보냈는데 B의 응답이 먼저 온다면, 그 응답이 누구의 것인지 알아낼 방법이 필요하다.

상관 식별자(correlation id)를 요청에 붙이고 응답에 되돌려받는다 — 6-4 멀티플렉싱에서 채널 ID 를 패킷 앞에 붙였던 것과 같은 발상이다. 공유 채널 위에서 논리적 흐름을 구분하려면, 결국 봉투에 이름을 써야 한다.
i

이 책 안의 같은 해법들 보강

  • 6-4 — 멀티플렉싱: [채널ID][길이][데이터] 로 하나의 소켓 위에서 두 흐름을 구분
  • 11-2 — 요청 일괄 처리: Map 에 id → Promise 를 담아 두었다가 응답과 짝짓기
  • 11-1 — 사전 초기화 큐: pending Promise 를 보관했다가 나중에 resolve

세 경우 모두 보낸 것과 돌아온 것을 잇는 자료구조를 발신자 쪽에 두었다. 요청/응답 패턴에서 추가로 필요한 것은 반환 주소(return address) — 응답을 어느 큐로 보낼지 요청에 함께 실어 보내는 것 — 정도다.
