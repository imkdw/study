7-1

레디스에서 데이터를 영구 저장하기

스냅숏을 찍을 것인가, 일지를 쓸 것인가. 백업 방식의 선택은 곧 얼마까지 잃어도 되는가에 대한 대답이다.

핵심 RDB 는 어느 시점의 사진이고 AOF 는 모든 변경의 일지다. 사진은 가볍고 빠르지만 찍은 순간 이후를 잃고, 일지는 무겁지만 마지막 순간까지 복원한다.
  • 레디스는 모든 데이터를 메모리에서 관리한다
  • 재부팅하면 모든 데이터가 사라진다
  • 캐시가 아닌 영구 저장소로 쓰려면 RDB, AOF 두 가지 백업 방법을 사용할 수 있다
    • 데이터 복구는 재부팅 시점에만 가능하며, 실행 중에는 불가능하다

AOF (Append Only File)

  • 처리한 모든 쓰기 작업을 차례대로 기록한다
  • 복원할 때는 파일을 다시 읽어 가며 데이터 세트를 재구성한다
  • 파일은 레디스 자체 프로토콜인 RESP 형태로 저장된다
  • 원하는 시점으로 복구가 가능하다

RDB (Redis Database)

  • 일정 시점에 메모리에 있는 전체 데이터를 저장한다. 스냅숏 방식이라고도 한다
  • 원하는 시점으로의 복구는 불가능하다. 저장된 시점으로만 돌아갈 수 있다
구분RDBAOF
저장 형태바이너리 스냅숏RESP 형식의 쓰기 커맨드
파일 크기작다크다 (재구성 필요)
재시작 로딩 속도빠르다느리다
손실 가능 범위마지막 저장 이후 전부최대 1초 (everysec)
시점 복구불가가능

둘 중 하나가 아니다 보강

RDB 와 AOF 는 동시에 켤 수 있고, 대개 그렇게 쓴다. 둘 다 켜져 있으면 재시작 시 더 완전한 AOF 를 우선 읽어 복원한다. RDB 는 그 자체로 백업 파일을 다른 서버에 옮기기 좋고 복제의 전체 동기화에도 쓰이므로, "AOF 를 켰으니 RDB 는 끈다"는 선택은 대개 손해다.

정리

  • 메모리 저장소이므로 재시작하면 데이터는 사라진다. 복구는 재부팅 시점에만 일어난다.
  • RDB 는 작고 빠르지만 마지막 스냅숏 이후를 잃는다. AOF 는 크고 느리지만 거의 잃지 않는다.
  • 실무에서는 둘 다 켜고, 재시작 시에는 AOF 가 우선한다.
7-2

RDB 방식의 데이터 백업

가장 간단한 백업. 대신 "언제 찍었느냐"가 곧 "언제까지 살아남았느냐"가 된다.

핵심 SAVE 는 서버를 멈추고 찍고, BGSAVE 는 자식 프로세스를 fork 해서 찍는다. 운영에서 쓰는 것은 후자뿐이다.
  • 레디스에서 데이터를 백업하는 가장 간단한 방법
  • 장애 시 손실 가능성을 최소화해야 하는 서비스에는 권장하지 않는다

특정 조건에 자동으로 RDB 생성

redis.conf 파일에 정의할 수 있다.

redis.conf
save <기간(초)> <변경된 키 개수>
dbfilename <파일명>
dir <RDB 파일이 저장될 경로>
save
  • save 900 1 : 900초(15분) 동안 1개 이상의 키가 변경된 경우 저장
  • save "" : RDB 생성 비활성화
  • CONFIG SET save "" 후 CONFIG REWRITE : 실행 중인 상태에서 RDB 생성 비활성화

save 는 여러 줄을 겹쳐 쓸 수 있고, 조건 중 하나라도 만족하면 저장이 일어난다. 변경이 잦을수록 자주, 뜸할수록 드물게 찍히도록 계단식으로 설정하는 것이 기본 구성이다.

수동으로 RDB 생성

  • SAVE, BGSAVE 로 수동 생성할 수 있다
  • LASTSAVE 로 최근 RDB 생성 시각을 확인할 수 있다
SAVE
  • 동기 방식으로 파일을 생성한다
    • 파일이 생성되는 동안 다른 커맨드를 실행할 수 없다
  • 일반적인 운영 환경에서는 사용하지 않는 것을 권장한다
redis-cli 운영 금지
127.0.0.1:6379> save
OK
BGSAVE
  • fork 로 자식 프로세스를 만들고, 그 프로세스가 RDB 를 생성한다
  • 이미 백그라운드 저장이 진행 중이면 에러가 나므로 BGSAVE SCHEDULE 로 예약하는 편이 안전하다
redis-cli 권장
127.0.0.1:6379> bgsave
Background saving started

복제를 사용하는 경우 자동으로 RDB 생성

  • REPLICAOF 로 복제를 요청하면 마스터가 RDB 를 만들어 복제본에 전달한다
  • 네트워크 장애 등으로 재동기화가 필요할 때도 복제본으로 RDB 를 전달한다
  • 처음 연결이든 이미 연결된 상태든 언제든 RDB 가 생성될 수 있다
!

RDB 를 껐다고 fork 가 사라지지 않는다

save "" 로 자동 저장을 꺼도, 복제본이 붙는 순간 전체 동기화를 위해 fork 가 일어난다. 뒤의 7-4 에서 다루는 copy-on-write 메모리 급증은 백업을 끈 인스턴스에서도 발생할 수 있다는 뜻이다. (7.0 부터는 기본값이 디스크리스 복제라 RDB 파일 자체는 만들지 않지만 fork 는 그대로다.)

정리

  • save <초> <변경 키 수> 조건을 여러 줄 겹쳐 두면 변경 빈도에 따라 저장 주기가 달라진다.
  • 운영에서는 SAVE 를 쓰지 않는다. BGSAVE 를, 중복이 걱정되면 BGSAVE SCHEDULE 을 쓴다.
  • 복제 연결 때도 RDB 생성(과 fork)이 일어난다. 백업 설정과 무관하게 메모리 여유가 필요하다.
7-3

AOF 방식의 데이터 백업

모든 쓰기를 적어 두는 대신, 그 파일이 무한히 커지지 않게 하는 일이 운영의 절반이다.

핵심 AOF 의 안정성은 appendfsync 하나로 결정된다. 기본값 everysec 은 최대 1초치 손실과 거의 no 수준의 성능을 맞바꾼 지점이다.
  • 파일명은 기본적으로 appendonly.aof 로 저장된다
  • 메모리상 데이터가 변화하는 작업만 기록된다
    • FLUSHALL 로 모든 데이터를 날려도 (그 커맨드 앞까지는) 복구할 수 있다
  • 모든 데이터가 실제 입력한 커맨드 그대로 저장되지는 않는다
    • BRPOP 같은 경우 AOF 에는 RPOP 으로 기록된다

블로킹 커맨드가 비블로킹 형태로 바뀌어 기록되는 이유는, 복원할 때는 기다릴 대상이 없기 때문이다. 같은 이유로 SPOP, EXPIRE 처럼 실행할 때마다 결과가 달라지는 커맨드도 결정적인 형태(SREM, PEXPIREAT)로 변환되어 기록된다.

redis.conf
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"

AOF 파일 재구성하기

  • AOF 를 안정적으로 쓰려면 점점 커지는 파일을 주기적으로 압축(재구성)해야 한다
    • 조건부 또는 수동으로 재구성할 수 있다
  • 디스크에 있는 기존 AOF 를 재사용하는 것이 아니라, 메모리에 있는 현재 데이터로 새 파일을 만든다

그래서 INCR counter 를 백만 번 실행했더라도 재구성 후에는 SET counter 1000000 한 줄로 줄어든다.

버전 7 이전의 재구성 과정
  1. fork 로 자식 프로세스 생성

    메모리의 데이터를 새 임시 파일로 쓰기 시작한다.

  2. 그동안의 변경은 두 곳에 기록

    기존 AOF 파일과 인메모리 버퍼에 동시에 저장된다.

  3. 버퍼 내용을 임시 파일 끝에 이어 붙임

    재구성이 끝나면 버퍼에 쌓인 변경을 임시 파일 마지막에 추가한다.

  4. 임시 파일로 기존 AOF 를 덮어씀

    이 과정에서 큰 파일 쓰기가 한 번 더 일어난다.

버전 7 이후의 재구성 과정
  1. fork 로 자식 프로세스 생성

    메모리의 데이터를 새 임시 파일(base)로 쓴다.

  2. 그동안의 변경은 신규 AOF 에 기록

    이전처럼 두 곳에 중복 기록하지 않는다.

  3. 임시 manifest 파일 생성 후 갱신

    어떤 base 와 incr 파일이 현재 세트인지 manifest 가 가리킨다.

  4. manifest 를 덮어쓰고 이전 파일 삭제

    순차적인 I/O 만 발생해 디스크 접근이 매우 효율적이다.

Redis 7.0 의 multi-part AOF 최신 반영

7.0 부터 AOF 는 파일 하나가 아니라 appenddirname(기본 appendonlydir) 디렉터리 안의 base 파일 + incr 파일 + manifest 파일 세트로 관리된다. 그래서 백업 스크립트가 appendonly.aof 파일 하나만 복사하도록 짜여 있다면 7.0 업그레이드 후 반드시 고쳐야 한다.

자동 AOF 재구성

  • 현재 파일 크기와 마지막으로 재구성했을 때의 크기를 비교해 처리한다
  • 파일이 작을 때 재구성하는 것은 비효율적이니, 일정 크기 이상일 때만 하도록 지정하는 것을 권장한다
redis.conf
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

위 기본값은 "직전 재구성 시점보다 100% 커졌고(즉 두 배), 그러면서 64MB 이상일 때" 재구성한다는 뜻이다. 두 조건을 모두 만족해야 한다.

수동 AOF 재구성

  • BGREWRITEAOF 로 원하는 시점에 수동으로 재구성할 수 있다
  • 자동 재구성과 동일하게 동작한다

노트의 BGREWRITEOF 는 BGREWRITEAOF 의 오타다 (A 가 빠졌다).

AOF 타임스탬프

  • 버전 7 이상부터 AOF 에 타임스탬프를 남길 수 있다
  • aof-timestamp-enabled 옵션을 켜서 사용한다 (기본값 no)
  • 타임스탬프가 있으면 redis-check-aof 로 특정 시점까지만 잘라 복원할 수 있다

AOF 파일 복원

  • redis-check-aof 는 AOF 파일이 손상됐을 때도 사용할 수 있다
  • --fix 옵션은 원본 파일을 직접 고치므로, 가능하면 사본을 만들어 두고 작업하는 것을 권장한다

AOF 파일의 안정성

OS 가 파일을 저장하는 방법
  1. 레디스가 커널에 WRITE 를 호출

    애플리케이션 입장에서는 여기서 "썼다"고 판단한다.

  2. 커널이 OS 버퍼(page cache)에 담는다

    아직 디스크에는 없다. 이 상태에서 전원이 나가면 사라진다.

  3. OS 가 여유가 있거나 지연 한계에 도달하면 디스크에 쓴다

    리눅스의 기본 지연 한계는 약 30초다. FSYNC 는 이 버퍼 내용을 디스크에 강제로 내리는 시스템 콜이다.

원문 교정 원문 교정

노트에 APPENDASYNC 로 적힌 설정의 실제 이름은 appendfsync 다. 값은 no / always / everysec 세 가지이며 기본값은 everysec 이다. (근거: redis.conf)

appendfsync호출하는 시스템 콜최대 손실성능
noWRITE 만OS 에 맡김 (최대 30초)가장 빠름
alwaysWRITE + FSYNC (매 쓰기)사실상 없음가장 느림
everysec (기본/권장)WRITE + 1초마다 FSYNC최대 1초no 와 거의 동일
  • appendfsync no
    • AOF 를 쓸 때 WRITE 시스템 콜만 호출한다
    • 커널 영역까지 잘 넘어갔는지만 확인하므로 성능이 가장 좋다
  • appendfsync always
    • 쓸 때마다 WRITE + FSYNC 를 호출한다
    • 매번 디스크에 정확히 저장되기를 기다리므로 성능이 가장 낮다
  • appendfsync everysec
    • WRITE 를 호출하고, FSYNC 는 1초에 한 번 호출한다
    • 성능은 no 와 거의 비슷하면서 손실 범위는 1초로 묶인다

정리

  • AOF 는 쓰기 커맨드를 RESP 로 기록하되, 비결정적인 커맨드는 결정적인 형태로 바꿔 저장한다.
  • 재구성은 디스크의 옛 파일이 아니라 메모리의 현재 상태로 새로 쓴다. 기본 조건은 "직전의 2배 그리고 64MB 이상".
  • 7.0 부터 AOF 는 base + incr + manifest 의 디렉터리 구조다. 백업 스크립트를 함께 손봐야 한다.
  • 설정 이름은 appendfsync. 기본값 everysec 이 손실 1초와 성능을 맞바꾼 실용적인 지점이다.
7-4

백업 사용 시 주의할 점

백업이 장애의 원인이 되는 순간 — fork 와 copy-on-write 가 메모리를 두 배로 부풀릴 때.

핵심 fork 직후 메모리는 공유되지만, 부모가 데이터를 고칠 때마다 그 페이지가 복사된다. 쓰기가 많을수록 백업 중 메모리가 부푼다.
  • RDB, AOF 를 사용하는 경우 인스턴스의 maxmemory 는 실제 서버 메모리보다 여유를 두고 설정하는 것이 좋다

BGSAVE 커맨드

  • fork 로 프로세스를 하나 더 만든다
  • 부모 프로세스는 그동안에도 다른 요청을 계속 받아야 한다
  • 레디스는 copy-on-write 방식이라 변경이 일어난 부분만 메모리에 하나 더 만든다
    • 최악의 경우 실제로 메모리를 2배 이상 쓸 수도 있다
  • OS 메모리가 가득 차 out of memory 가 발생하면 그대로 장애로 이어진다
백업 중 늘어나는 메모리는 데이터 크기가 아니라 "그동안 바뀐 양"에 비례한다 — 읽기만 많은 인스턴스는 거의 늘지 않지만, 쓰기가 몰리는 시간대에 백업이 겹치면 최악의 경우 두 배까지 뛴다. 백업 시각을 트래픽이 한가한 때로 옮겨야 하는 이유다.
i

현장에서 하는 조치 보강

가장 흔한 대응은 백업을 복제본에서 수행하는 것이다. 마스터에서는 자동 저장을 끄고, 트래픽을 받지 않는 복제본에 BGSAVE 를 걸면 마스터의 fork 부담이 사라진다. 그리고 vm.overcommit_memory = 1 을 설정해 두라는 레디스의 시작 경고 로그는 바로 이 fork 실패를 막기 위한 것이다.

정리

  • BGSAVE/BGREWRITEAOF/복제 전체 동기화는 모두 fork 를 부른다.
  • copy-on-write 로 인해 늘어나는 메모리는 백업 도중의 쓰기 양에 비례한다. 최악의 경우 2배 이상.
  • maxmemory 는 물리 메모리보다 충분히 낮게 잡고, 가능하면 백업은 복제본에서 돌린다.
