12-1

클라이언트 핸들링

클라이언트 하나가 버퍼 하나다. 커넥션 수는 그대로 서버의 메모리 그래프에 나타난다.

핵심 레디스의 메모리는 데이터만 먹지 않는다. 클라이언트마다 출력 버퍼와 쿼리 버퍼가 붙고, 이것이 통제되지 않으면 데이터를 하나도 안 넣고도 메모리가 찬다.

클라이언트 핸들링

  • 기본적으로 소켓과 TCP 를 사용하고, 원하면 포트와 유닉스 소켓 경로를 바꿀 수 있다
  • 멀티플렉싱 방식을 사용해 하나의 통신 채널로 여러 데이터 스트림을 전송할 수 있다
  • 논블로킹 I/O 로 다수의 클라이언트를 지원한다
  • TCP_NODELAY 옵션으로 작은 데이터도 버퍼링하지 않고 즉시 보내 빠른 통신을 보장한다
  • 최대 클라이언트 수는 기본 10000 이며, 초과하면 에러와 함께 새 연결을 거절한다

클라이언트 버퍼 제한

  • 클라이언트에 돌려줄 데이터를 임시로 담기 위해 클라이언트마다 출력 버퍼를 만든다
    • 연결된 클라이언트가 1000개면 출력 버퍼도 1000개다
  • 클라이언트가 데이터를 제때 읽어 가지 못하고 요청만 계속하면 버퍼가 계속 커져 메모리 사용량이 올라간다
    • 이를 대비해 버퍼가 일정 크기를 넘으면 커넥션을 끊는다
  • 출력 버퍼 외에 쿼리 버퍼도 있다
    • 요청이 들어오면 버퍼에 담아 두었다가 처리한다
    • 기본값은 1GB 로, 쿼리 버퍼가 무한히 커지는 것을 막기 위한 값이다
    • client-query-buffer-limit 으로 조정한다
클라이언트 종류하드 제한소프트 제한소프트 유지 시간
normal (일반)0 (무제한)00
pubsub32MB8MB60초
replica (복제본)256MB64MB60초

하드 제한은 넘는 순간 연결을 끊고, 소프트 제한은 그 크기를 지정 시간 동안 계속 유지할 때 끊는다. 일반 클라이언트가 무제한인 이유는 요청-응답 패턴에서는 버퍼가 자연히 비워지기 때문이다. 반대로 pub/sub 과 복제본은 서버가 일방적으로 밀어 넣는 구조라 제한이 필요하다.

Pub/Sub 제한
  • 하드 제한 : 32MB
  • 소프트 제한 : 60초 동안 8MB
복제본 제한
  • 하드 제한 : 256MB
  • 소프트 제한 : 60초 동안 64MB
  • 마스터로부터 대용량 데이터를 받아야 한다면 더 큰 출력 버퍼가 필요하다

복제가 무한 루프에 빠지는 전형적인 시나리오

전체 동기화 중에 복제본용 출력 버퍼가 한계를 넘으면 마스터가 연결을 끊는다. 복제본은 다시 붙어 전체 동기화를 시작하고, 또 넘고, 또 끊긴다. 데이터가 큰 인스턴스에서 client-output-buffer-limit replica 를 넉넉히 잡아야 하는 이유다.

제한 변경하기
  • CONFIG SET 으로 변경할 수 있다

클라이언트 이빅션(eviction)

  • 7 이전 버전에서는 클라이언트별 client-output-buffer-limit 으로만 개별 통제가 가능했다
  • 7 이후 버전에서는 maxmemory-clients 로 모든 클라이언트가 쓰는 메모리의 총합을 관리한다
    • 임계치에 도달하면 메모리를 가장 많이 쓰는 클라이언트부터 커넥션을 끊는다
!

원문 보완 원문 교정

노트에는 "7 이전에는 maxmemory-policy 로 관리"라고 되어 있으나, maxmemory-policy 는 데이터 키의 이빅션 정책이지 클라이언트 메모리와는 관계가 없다. 7 이전에는 클라이언트 하나하나에 대한 client-output-buffer-limit 만 있었고 총합을 제한할 방법이 없었다. 7.0 의 maxmemory-clients 가 그 총합 제한을 추가한 것이다. 기본값은 0(비활성)이다. (근거: redis.conf)

maxmemory-clients 설정
  • redis.conf 또는 CONFIG SET 으로 설정한다
  • 복제본에 연결된 마스터/복제본 커넥션은 이 설정의 영향을 받지 않는다
  • 특정 클라이언트만 이빅션 대상에서 빼려면 그 커넥션에서 CLIENT NO-EVICT ON 을 실행한다
  • 대용량 트래픽 환경에서는 5~10% 사이 값을 권장한다
redis.conf
# 클라이언트가 쓸 수 있는 메모리 총합을 1GB로 제한
maxmemory-clients 1G

# maxmemory 의 5% 까지 허용
maxmemory-clients 5%

# 기능 미사용 (기본값)
maxmemory-clients 0

Timeout, TCP Keepalive

Timeout
  • 설정한 초 동안 아무 요청이 없는 클라이언트의 커넥션을 끊는다
  • CONFIG SET timeout <초> 로 설정한다 (기본값 0, 즉 끊지 않음)
TCP Keepalive
  • 주기적으로 TCP ACK 를 보내고 응답이 없으면 연결을 정리한다
  • 클라이언트가 정상적으로 응답할 수 있는 상태인지를 먼저 확인하고 끊는 방식이다
  • 기본적으로 300초(5분) 마다 신호를 보낸다
i

둘 중에는 keepalive 쪽 보강

timeout 은 유휴 커넥션을 무조건 끊으므로, 커넥션 풀이 조용히 잡고 있던 커넥션까지 잘라 애플리케이션에서 간헐적인 에러를 만든다. 반면 tcp-keepalive 는 실제로 죽은 상대만 정리한다. 특별한 이유가 없다면 timeout 0 을 두고 keepalive 에 맡기는 편이 안전하다.

정리

  • 클라이언트마다 출력 버퍼와 쿼리 버퍼가 붙는다. 커넥션 수 자체가 메모리 사용량이다.
  • 출력 버퍼 기본 제한은 pubsub 32MB/8MB/60s, replica 256MB/64MB/60s. 큰 인스턴스는 replica 값을 키워야 복제가 안정된다.
  • 7.0 의 maxmemory-clients 는 클라이언트 메모리 총합을 제한한다. 기본값은 비활성(0).
  • 유휴 커넥션 정리는 timeout 보다 tcp-keepalive(기본 300초)에 맡기는 편이 안전하다.
12-2

파이프라이닝

레디스가 느린 게 아니라 왕복이 잦은 것이었다는 걸 확인하는 기능.

핵심 커맨드 100개를 따로 보내면 네트워크 왕복도 100번이다. 파이프라이닝은 그것을 왕복 1번으로 줄인다. 서버 성능이 아니라 왕복 횟수를 줄이는 최적화다.
  • 레디스가 아무리 빨라도 네트워크 지연이 크면 처리량이 떨어진다
  • 파이프라이닝으로 여러 쿼리를 한 번에 보내면 성능이 크게 향상된다
  • 연속된 여러 커맨드를 한 번에 보낼 수 있는 기능이다
    • 커맨드마다 네트워크를 왕복하지 않고 일괄 처리하므로 응답 시간을 줄이고 처리량을 높인다
줄어드는 것은 서버의 처리 시간이 아니라 대기 시간이다 — 커맨드가 100개면 왕복도 100번이고, 왕복당 1ms 라면 그것만으로 100ms 다. 서버가 실제로 일한 시간은 그중 극히 일부다.

주의점

  • 한 번에 너무 많이 묶으면 네트워크 대역폭 한계와 쿼리 버퍼 제한 때문에 에러가 날 수 있다
  • 여러 커맨드를 파이프라이닝할 때는 일정한 개수로 나누어 배치 처리하는 편이 좋다

서버 쪽에서도 응답이 모두 쌓일 때까지 출력 버퍼를 붙들고 있으므로, 파이프라인이 지나치게 길면 12-1 의 출력 버퍼 제한에 걸린다. 보통 수백에서 수천 개 단위로 끊는다.

원자성

  • 파이프라이닝은 원자성을 보장하지 않는다
  • 트랜잭션처럼 동작하지 않으므로, 오류가 난 커맨드 외의 나머지는 모두 정상 실행된다
!

파이프라이닝과 MULTI/EXEC 는 다른 것을 해결한다

파이프라이닝은 왕복 횟수를 줄이고, MULTI/EXEC 는 중간에 다른 클라이언트가 끼어들지 못하게 한다. 파이프라인으로 보낸 커맨드들 사이에는 다른 클라이언트의 커맨드가 얼마든지 실행될 수 있다. 둘 다 필요하다면 MULTI/EXEC 자체를 파이프라인에 담아 보내면 된다.

정리

  • 파이프라이닝은 네트워크 왕복 횟수를 줄이는 최적화다. 지연이 클수록 효과가 크다.
  • 너무 크게 묶으면 쿼리 버퍼와 출력 버퍼에 걸린다. 수백~수천 단위로 배치를 나눈다.
  • 원자성은 없다. 격리가 필요하면 MULTI/EXEC 를 함께 쓴다.
12-3

클라이언트 사이드 캐싱

캐시 앞에 또 캐시를 둔다. 문제는 그 캐시가 언제 틀렸는지 아는 방법이다.

핵심 클라이언트 캐시의 어려움은 저장이 아니라 무효화다. 레디스는 서버가 무효화 메시지를 보내 주는 방식(트래킹)으로 이 문제를 푼다.
  • RDB 성능도 최적화하고 캐시까지 도입했는데 만족스럽지 않을 때 고려할 수 있다
  • 클라이언트 쪽에서 데이터를 로컬에 캐싱하고 그 데이터를 활용하는 방법이다
  • 데이터셋의 아이템이 자주 변경되지 않을 때 유용하다
  • 변경된 데이터를 어떻게 처리할지 고려해야 하며, 레디스는 이를 트래킹이라 부른다
  • 자주 요청되지만 드물게 변경되는 키를 잘 고르는 것이 중요하다

캐싱 모드

기본 모드
  • 레디스가 클라이언트가 접근한 키를 기억해 두었다가, 그 키가 수정되면 무효화 메시지를 보낸다
  • 서버에 메모리 비용이 들지만, 클라이언트가 실제로 들고 있는 키에 대해서만 정확히 무효화를 보낼 수 있다
브로드캐스팅 모드
  • 접근한 키를 모두 기억하지 않고 특정 prefix 만 기억한다
  • 서버 메모리 사용량이 적지만, 클라이언트는 자신이 어떤 키를 들고 있는지 스스로 알아야 한다
  • 그 prefix 에 속한 키가 하나라도 바뀌면 관심 없는 변경까지 모두 수신하게 되고, 그만큼 CPU 를 더 쓴다
구분기본 모드브로드캐스팅 모드
서버가 기억하는 것클라이언트별 접근 키 목록등록된 prefix 목록
서버 메모리많이 든다거의 안 든다
무효화 정확도정확하다불필요한 알림 포함

RESP3 가 전제다 보강

무효화 메시지를 같은 커넥션으로 받으려면 Redis 6 의 RESP3 프로토콜이 필요하다(HELLO 3 후 CLIENT TRACKING ON). RESP2 클라이언트라면 무효화 알림을 받을 별도의 pub/sub 커넥션을 만들고 REDIRECT 옵션으로 그 커넥션 ID 를 지정해야 한다. 즉 이 기능은 클라이언트 라이브러리의 지원 여부를 먼저 확인해야 쓸 수 있다.

정리

  • 클라이언트 사이드 캐싱은 자주 읽고 드물게 바뀌는 키에서만 이득이다.
  • 기본 모드는 서버가 키를 기억해 정확히 무효화하고, 브로드캐스팅 모드는 prefix 만 기억해 메모리를 아끼는 대신 과도한 알림을 감수한다.
  • RESP3(또는 RESP2 + REDIRECT) 지원이 필요하므로 클라이언트 라이브러리 확인이 먼저다.
