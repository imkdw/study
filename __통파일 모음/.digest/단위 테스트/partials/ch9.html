9-1

목의 가치를 극대화하기

목은 시스템 끝단에 붙일수록 더 많은 코드를 지켜준다.

핵심 비관리 의존성과 통신하는 마지막 타입을 목으로 처리한다. 그래야 통합 테스트가 거치는 클래스 수가 늘어나 회귀 방지가 극대화된다.

시스템 끝에서 상호 작용 검증하기

목을 쓸 때는 시스템 끝에서 비관리 의존성과의 상호작용을 검증해야 한다. 회귀 방지는 테스트 중에 실행되는 코드 양의 함수이므로, 목을 바깥으로 밀수록 그 사이에 있는 클래스가 전부 테스트 범위 안으로 들어온다.

8-6 의 DomainLogger 와 Logger 를 예로 들면, 둘 중 바깥쪽인 Logger 를 목으로 처리해야 DomainLogger 의 변환 로직까지 함께 검증된다.

✓

두 가지 책임을 분리한다

외부 라이브러리의 복잡성을 숨기는 일과 모든 앱 메세지를 한 곳에 모으는 일은 서로 다른 책임이므로 분리되어 있는 게 좋다. 목은 그중 바깥쪽, 즉 라이브러리에 가장 가까운 타입에 붙인다.

목을 스파이로 대체하기

스파이와 목은 목적이 같고 생성하는 방식만 다르다.

구분생성 방식
목외부 라이브러리의 도움으로 생성한다
스파이직접 작성한다. 그래서 "직접 작성한 목" 이라고도 부른다
bus-spy.ts 스파이 + 플루언트 인터페이스 
interface IBus {
  send(message: string): void;
}

class BusSpy implements IBus {
  private sentMessages: string[] = [];

  send(message: string): void {
    this.sentMessages.push(message);
  }

  shouldSendNumberOfMessages(count: number): BusSpy {
    expect(this.sentMessages).toHaveLength(count);
    return this; // 메소드 체이닝
  }

  withEmailChangedMessage(userId: number, newEmail: string): BusSpy {
    const expected = `Type: USER EMAIL CHANGED; Id: ${userId}; NewEmail: ${newEmail}`;
    expect(this.sentMessages).toContain(expected);
    return this;
  }
}
user-controller.integration.spec.ts 
it("changing_email_from_corporate_to_non_corporate", () => {
  const busSpy = new BusSpy();
  const messageBus = new MessageBus(busSpy); // 시스템 끝단을 스파이로
  const loggerMock: jest.Mocked<IDomainLogger> = {
    userTypeHasChanged: jest.fn(),
  };
  const sut = new UserController(messageBus, loggerMock);

  // ...

  busSpy
    .shouldSendNumberOfMessages(1)
    .withEmailChangedMessage(userId, newEmail);
});
플루언트 인터페이스

메소드 체이닝을 기반으로 코드가 쉬운 영어 문장처럼 보이게 하는 설계 기법이다. 위 예제에서 BusSpy 는 검증 구문을 플루언트 인터페이스로 제공해 상호작용 검증을 간결하고 표현력 있게 만든다.

i

스파이가 목보다 나은 지점 보강

스파이는 테스트가 직접 소유하는 코드다. 메세지 포맷 같은 검증 로직을 한곳에 모아두면, 포맷이 바뀌었을 때 고칠 자리가 하나뿐이다. 목 라이브러리로 같은 일을 하면 그 문자열 조립이 테스트마다 흩어진다.

정리

  • 목은 비관리 의존성과 통신하는 마지막 타입에 붙인다.
  • 바깥으로 밀수록 실행되는 코드가 늘어 회귀 방지가 커진다.
  • 스파이는 직접 작성한 목이며, 검증 로직을 한곳에 모을 수 있다.
  • 플루언트 인터페이스로 검증 구절을 문장처럼 읽히게 만든다.
9-2

목 처리에 대한 모범 사례

목은 통합 테스트만을 위한 것이다.

핵심 도메인 모델은 단위 테스트, 컨트롤러는 통합 테스트. 목은 비관리 의존성을 다루는 컨트롤러에만 붙으므로, 결국 통합 테스트에만 등장한다.

목은 통합 테스트만을 위한 것

도메인 모델은 단위 테스트에 속하고, 컨트롤러는 통합 테스트에 속한다. 목은 비관리 의존성에만 해당하며, 그런 의존성을 처리하는 코드는 컨트롤러뿐이다. 따라서 통합 테스트에서 컨트롤러를 테스트할 때만 목을 적용한다.

테스트당 목이 하나일 필요는 없음

"단위" 는 코드 단위가 아니라 동작 단위이며, 동작 단위를 구현하는 데 필요한 코드의 양과는 상관이 없다. 마찬가지로 동작 단위를 검증하는 데 필요한 목의 수도 상관이 없다. 목의 수는 오직 그 연산에 참여하는 비관리 의존성의 수에만 의존한다.

호출 횟수 검증하기

비관리 의존성과의 통신에서는 두 가지를 모두 확인해야 한다.

  • 예상하는 호출이 있는가
  • 예상치 못한 호출이 없는가

앱은 외부 시스템이 예상하는 메세지를 생략해서도 안 되고, 예상치 못한 메세지를 만들어서도 안 되기 때문이다.

integration.spec.ts 
// 기대한 인자로 호출됐는가
expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledWith(
  userId,
  newEmail
);

// 그리고 그 외의 호출은 없었는가
expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledTimes(1);

보유 타입만 목으로 처리하기

서드파티 라이브러리 위에는 항상 어댑터를 작성하고, 기본 타입 대신 그 어댑터를 목으로 처리하라는 지침이다. 이유는 세 가지다.

  1. 서드파티 코드의 작동 방식을 정확히 알지 못한다
  2. 라이브러리가 인터페이스를 제공하더라도 확인이 필요하다

    목으로 처리한 동작이 실제 외부 라이브러리의 동작과 일치하는지 검증해야 한다.

  3. 기술 세부 사항이 앱에 필요하지 않다

    어댑터가 그것을 추상화하고, 앱 관점에서 라이브러리와의 관계를 정의해야 한다.

✓

어댑터는 손상 방지 계층이다

실제로 어댑터는 우리 코드와 외부 환경 사이의 손상 방지 계층(anti-corruption layer) 으로 작동한다. 외부 라이브러리의 모델이 우리 도메인 모델을 오염시키는 것을 막는다.

정리

  • 목은 통합 테스트에서 컨트롤러를 테스트할 때만 쓴다.
  • 목의 수는 연산에 참여하는 비관리 의존성 수로만 결정된다.
  • 기대한 호출과 예상치 못한 호출 둘 다 검증한다.
  • 서드파티 타입이 아니라 그 위의 어댑터를 목으로 처리한다.
