1-1

단위 테스트 현황

질문은 "테스트를 써야 하나" 에서 "좋은 테스트란 뭔가" 로 옮겨왔다.

핵심 테스트를 작성하는 것 자체는 이미 논쟁거리가 아니다. 남은 문제는 노력 대비 최대의 이익을 내는 방식으로 쓰는 법이다.

단위 테스트는 이미 업계 표준에 가깝게 자리 잡았다. 프로젝트에 따라 제품 코드와 테스트 코드의 비율이 1:1 에서 1:10 까지 다양하게 나타나고, 그 비율 자체는 좋고 나쁨을 말해주지 않는다.

문제는 그 다음이다. 테스트가 있는데도 개발자들이 원하는 결과를 얻지 못하는 경우가 많다. 배포가 여전히 무섭고, 리팩터링은 여전히 망설여진다. 그래서 지금 던져야 할 질문은 이렇게 바뀐다.

✓

질문의 이동

"단위 테스트를 작성해야 되는가?" → "좋은 단위 테스트를 작성하는 건 어떤 의미인가?"

정리

  • 테스트 코드의 양이나 비율은 품질을 말해주지 않는다.
  • 단순한 테스트 작성이 아니라 노력 대비 이익을 기준으로 삼는다.
  • 이 책 전체가 "무엇이 좋은 테스트인가" 에 대한 판단 기준을 세우는 과정이다.
1-2

단위 테스트 목표

목표는 좋은 설계가 아니라 소프트웨어 프로젝트의 지속 가능한 성장이다.

핵심 단위 테스트의 목표는 소프트웨어 프로젝트의 지속 가능한 성장이다. 좋은 설계는 그 과정에서 따라오는 사이드 이펙트일 뿐이다.

코드베이스에 대해 단위 테스트를 작성하다 보면 일반적으로 더 나은 설계로 이어진다. 테스트하기 어려운 코드는 대개 결합도가 높은 코드이기 때문이다. 다만 이것을 단위 테스트의 주된 목표로 두면 방향을 잃는다. 좋은 설계는 좋은 사이드 이펙트일 뿐이다.

진짜 목표는 성장 곡선에 있다. 초기에는 테스트 작성으로 시간이 더 걸리지만, 시간이 갈수록 효율이 역전된다.

테스트 없는 프로젝트는 어느 시점부터 침체 국면에 빠진다 — 초기에는 테스트가 더 느리지만, 진척도가 쌓일수록 두 곡선은 교차하고 다시는 만나지 않는다.

결국 테스트는 안전망 역할을 하며, 대부분의 회귀(regression) 에 대한 보험을 제공하는 도구다. 코드베이스를 지속적으로 검증하는 테스트 없이는 소프트웨어 개발이 쉽게 확장되지 않는다.

좋은 테스트와 좋지 않은 테스트를 가르는 요인

여기서 중요한 반전이 있다. 테스트가 프로젝트 성장에 도움이 되는 건 맞지만, 단순히 작성한다고 도움이 되는 건 아니다. 모든 테스트를 작성할 필요도 없다.

테스트를 하나 더 쓸 때마다 아래 비용이 함께 늘어난다는 걸 계산에 넣어야 한다.

  • 기반 코드를 리팩터링할 때 테스트도 함께 리팩터링해야 한다
  • 각 코드 변경마다 테스트를 실행해야 한다
  • 테스트가 잘못된 경고를 발생시키면 그것도 처리해야 한다
  • 기반 코드가 어떻게 동작하는지 이해하려 할 때 테스트를 읽는 시간이 든다

가치와 유지비를 함께 저울에 올렸을 때 유지비가 이기는 테스트가 코드베이스에 쌓이면, 그래프는 아래처럼 된다.

잘못된 테스트를 포함한 프로젝트는 테스트가 아예 없는 것보다 조금 나은 정도에 그친다 — 노란 곡선은 초반엔 파란 곡선 아래에 있지만 끝내 위로 올라선다.
!

지속 가능한 성장의 조건

테스트를 늘리는 것이 아니라 고품질 테스트에만 집중해야 한다. 가치가 유지비를 넘지 못하는 테스트는 코드베이스에 있는 것이 없느니만 못하다.

정리

  • 단위 테스트의 목표는 지속 가능한 프로젝트 성장이다. 좋은 설계는 부산물이다.
  • 테스트는 회귀에 대한 보험이며, 없으면 개발이 확장되지 않는다.
  • 모든 테스트를 쓸 필요는 없다. 항상 가치와 유지비를 함께 계산한다.
  • 잘못된 테스트가 쌓인 프로젝트는 테스트 없는 프로젝트와 크게 다르지 않다.
1-3

테스트 스위트 품질 측정을 위한 커버리지 지표

커버리지는 좋은 부정 지표이지만 나쁜 긍정 지표다.

핵심 커버리지 10% 는 확실히 나쁜 신호다. 하지만 커버리지 100% 라고 해서 좋은 테스트 스위트라는 뜻은 전혀 아니다.

커버리지 지표는 테스트 스위트가 소스 코드를 얼마나 실행하는지 백분율로 나타낸다. 중요한 피드백을 주기는 하지만, 이것만으로 테스트 품질을 효과적으로 측정할 수는 없다.

코드 커버리지 지표에 대한 이해

코드 커버리지(테스트 커버리지)는 실행 코드 라인 수 / 전체 라인 수 다. 라인 수만 세기 때문에, 동작을 하나도 바꾸지 않고 코드를 줄이는 것만으로 지표가 올라간다.

1-2.spec.ts 
import { isStringLong } from "../1-2.js";

describe("isStringLong", () => {
  it("문자열의 길이가 5보다 크다면 true 반환", () => {
    expect(isStringLong("123456")).toBe(true);
  });
});

동일한 이 테스트 하나를 두고, 제품 코드만 바꿔보자.

1-2.ts 커버리지 80% 
export const isStringLong = (str: string): boolean => {
  if (str.length > 5) {
    return true;
  }

  return false;
};

테스트는 그대로인데 지표만 올랐다

두 버전 모두 "123456" 하나만 검증한다. 검증 범위는 조금도 넓어지지 않았는데 커버리지는 80% 에서 100% 가 됐다. 코드가 작을수록 커버리지 지표가 좋아진다는 뜻이다.

분기 커버리지 지표에 대한 이해

분기 커버리지는 코드 커버리지의 이 단점을 극복하므로 더 정확한 결과를 준다. 원시 코드 라인 수 대신 if, switch 같은 제어 구조에 중점을 둔다.

계산식은 통과 분기 수 / 전체 분기 수 다. 코드베이스의 모든 가능한 분기를 합산하고, 그중 테스트가 얼마나 실행하는지 확인한다.

1-2.ts 
export const isStringLong = (str: string): boolean => {
  // 이 한 줄이 다루는 분기는 두 개다
  //   str.length >  5  -> true
  //   str.length <= 5  -> false
  // 테스트가 true 케이스만 검증하므로 분기 커버리지는 50%
  return str.length > 5;
};

라인 커버리지가 100% 인 바로 그 코드의 분기 커버리지가 50% 다. 같은 테스트를 두고도 두 지표가 이렇게 갈린다.

커버리지 지표에 관한 문제점

분기 커버리지조차도 품질의 근거가 될 수 없다. 두 가지 이유가 있다.

가능한 모든 결과를 검증한다고 보장할 수 없다

커버리지는 코드가 실행됐는지만 볼 뿐, 그 결과를 검증했는지는 보지 않는다. 테스트에서 결과가 여러 개라면 그 모두를 검증해야 지표가 유의미해진다.

1-2.ts 
export const isStringLong = (str: string): boolean => {
  const result = str.length > 5;
  wasLastStringLong = result; // 검증되지 않는 두 번째 결과
  return result;
};

두 케이스를 모두 통과시켜 라인 / 분기 모두 100% 를 찍어도, wasLastStringLong 이 올바른지는 아무도 확인하지 않았다.

외부 라이브러리 코드 경로를 고려할 수 없다
parse.ts 
export const parse = (str: string): number => {
  return parseInt(str, 10);
};

describe("parse", () => {
  it("`1234`를 숫자로 변환하면 1234다", () => {
    expect(parse("1234")).toBe(1234);
  });
});

parseInt 내부에는 공백 처리, 부호 처리, 파싱 실패 시 NaN 반환 같은 다양한 경로가 있다. 커버리지는 100% 로 나오지만 그 경로들은 하나도 테스트되지 않았다.

함께 알아두기 보강

이 한계 때문에 커버리지 대신 뮤테이션 테스팅(mutation testing) 을 쓰기도 한다. 제품 코드를 일부러 조금씩 바꿔놓고(> 를 >= 로 등) 테스트가 실패하는지 보는 방식이라, "실행됐는가" 가 아니라 "검증됐는가" 를 직접 측정한다. JS/TS 진영에서는 Stryker Mutator 가 대표적이다.

커버리지 목표치를 강제하면 벌어지는 일

숫자를 목표로 삼는 순간 개발자는 가치 있는 테스트가 아니라 숫자를 채우는 테스트를 쓰기 시작한다. 커버리지는 관찰하되, 통과 기준으로 삼지 않는다.

커버리지 지표는 좋은 부정 지표이지만 나쁜 긍정 지표다. 60% 처럼 낮은 숫자는 문제의 징후로 읽을 만하지만, 높은 숫자는 아무것도 보증하지 않는다.

정리

  • 코드 커버리지 = 실행 라인 / 전체 라인. 코드를 줄이는 것만으로도 올라간다.
  • 분기 커버리지 = 통과 분기 / 전체 분기. 더 정확하지만 여전히 충분하지 않다.
  • 커버리지는 검증 여부와 외부 라이브러리 경로를 볼 수 없다.
  • 낮은 커버리지는 나쁜 신호, 높은 커버리지는 좋은 신호가 아니다. 목표치로 삼지 않는다.
1-4

무엇이 성공적인 테스트를 만드는가

개발 주기에 통합되고, 가장 중요한 부분만 겨냥하고, 최소 유지비로 최대 가치를 낸다.

핵심 코드베이스의 모든 부분에 똑같이 주목할 필요는 없다. 비즈니스 로직이 있는 도메인 모델이 시간 투자 대비 최고의 수익을 낸다.

개발 주기에 통합되어 있음

자동화된 테스트를 유지하는 방법은 끊임없이 실행하는 것뿐이다. 코드 변경마다 돌아가지 않는 테스트는 곧 아무도 안 보는 테스트가 된다. 모든 테스트는 개발 주기에 통합되어야 한다.

코드베이스에서 가장 중요한 부분만을 대상으로 한다

대부분의 앱에서 가장 중요한 부분은 비즈니스 로직이 존재하는 도메인 모델이다. 인프라 코드나 외부 시스템 연동, 프레임워크 설정은 같은 노력을 들여도 같은 가치를 돌려주지 않는다.

최소 유지비로 최대 가치를 끌어냄

가치 있는 테스트 식별하기

가치가 높은 테스트와 낮은 테스트를 구별하려면 기준 틀이 필요하다. 그 틀이 4장의 네 가지 요소다. 그리고 이 식별 작업은 테스트만 봐서는 안 되고 코드베이스 자체에 노력을 기울여야 가능하다.

가치 있는 테스트 작성하기

식별만으로는 부족하다. 테스트하기 좋은 코드로 제품 코드를 바꾸는 일까지가 세트다. 의미 없는 부분이 아니라 비즈니스 로직처럼 가치 있는 부분에 테스트를 만든다.

정리

  • 테스트는 개발 주기에 통합되어 계속 실행되어야 의미가 있다.
  • 도메인 모델 / 비즈니스 로직이 투자 대비 수익이 가장 높다.
  • 가치 있는 테스트를 식별하는 기준 틀과, 그렇게 쓸 수 있도록 코드를 바꾸는 작업이 함께 간다.
