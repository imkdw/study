4-1

좋은 단위 테스트의 4대 요소

회귀 방지, 리팩터링 내성, 빠른 피드백, 유지 보수성.

핵심 거짓 양성을 줄이는 방법은 하나뿐이다. 테스트를 구현 세부 사항에서 떼어내는 것. 최종 사용자에게 의미 있는 결과만 확인한다.

어떤 자동화된 테스트든 아래 네 가지 특성으로 분석할 수 있다.

요소묻는 것
회귀 방지이 테스트가 버그를 잡아낼 수 있는가
리팩터링 내성동작이 그대로일 때 이 테스트가 조용히 있어 주는가
빠른 피드백얼마나 빨리 알려주는가
유지 보수성이해하고 실행하기 얼마나 어려운가

회귀 방지

회귀는 소프트웨어 버그로, 코드를 수정한 후 기능이 의도한 대로 작동하지 않는 경우다. 개발자의 삶에서 불행한 사실 하나는 코드가 자산이 아니라 책임이라는 점이다. 코드베이스가 커질수록 잠재적인 버그에 더 많이 노출된다.

회귀 방지 지표를 극대화하려면 테스트가 가능한 한 많은 코드를 실행하는 것을 목표로 해야 한다. 다만 그 코드가 비즈니스적으로 중요한 로직일 때만 유효하다. 단순한 코드를 테스트하는 것은 가치가 거의 없다.

리팩터링 내성

거짓 양성(false positive) 은 허위 경보다. 실제로는 기능이 의도한 대로 작동하는데 테스트가 실패하는 상황을 말한다. 일반적으로 코드를 리팩터링할 때, 즉 구현을 수정하지만 식별할 수 있는 동작은 유지할 때 발생한다.

단위 테스트의 목표는 프로젝트 성장을 지속 가능하게 하는 것이고, 그 메커니즘은 회귀 없이 주기적으로 리팩터링하고 새 기능을 추가할 수 있는 것이다. 리팩터링 내성이 그 메커니즘의 전제 조건이다.

테스트가 있을 때거짓 양성이 잦을 때
기존 기능이 고장 나면 배포 전에 조기 경고를 받는다타당한 이유 없이 실패하는 경험이 쌓인다
변경이 회귀로 이어지지 않는다는 확신을 얻는다실패에 익숙해져 타당한 실패도 무시하기 시작한다
확신이 있으니 리팩터링을 계속하게 된다신뢰가 무너지고, 회귀를 피하려 코드 변경을 최소화한다

거짓 양성의 원인

거짓 양성의 수는 테스트 구성 방식과 직접적인 관련이 있다. 테스트가 SUT 의 구현 세부 사항과 많이 결합될수록 허위 경보가 늘어난다.

✓

거짓 양성을 줄이는 유일한 방법

구현 세부 사항에서 테스트를 분리하는 것뿐이다. 테스트는 최종 사용자의 관점에서 SUT 를 검증해야 하고, 최종 사용자에게 의미 있는 결과만 확인해야 한다.

예제 — 하위 렌더러 구성을 검증하는 테스트
message-renderer.ts 
class Message {
  constructor(
    public header: string,
    public body: string,
    public footer: string
  ) {}
}

interface IRenderer {
  render(message: Message): string;
}

/** MessageRenderer 는 여러 개의 하위 렌더링 클래스를 가지고 있다 */
class MessageRenderer implements IRenderer {
  readonly subRenderers: IRenderer[];

  constructor() {
    this.subRenderers = [
      new HeaderRenderer(),
      new BodyRenderer(),
      new FooterRenderer(),
    ];
  }

  render(message: Message): string {
    return this.subRenderers
      .map((renderer) => renderer.render(message))
      .join("");
  }
}
message-renderer.spec.ts 구현에 결합됨 
it("messageRenderer_uses_correct_sub_renderers", () => {
  const sut = new MessageRenderer();

  const renderers = sut.subRenderers;

  expect(renderers).toHaveLength(3);
  expect(renderers[0]).toBeInstanceOf(HeaderRenderer);
  expect(renderers[1]).toBeInstanceOf(BodyRenderer);
  expect(renderers[2]).toBeInstanceOf(FooterRenderer);
});

최종 결과만 보는 테스트 — 내부 단계를 어떻게 바꾸든 클라이언트가 받는 결과가 같으면 테스트는 조용하다. 이것이 리팩터링 내성이다.

정리

  • 네 요소는 회귀 방지 / 리팩터링 내성 / 빠른 피드백 / 유지 보수성이다.
  • 회귀 방지를 높이려면 비즈니스적으로 중요한 코드를 많이 실행해야 한다.
  • 거짓 양성은 테스트가 구현 세부 사항과 결합된 만큼 늘어난다.
  • 해법은 하나다. 최종 사용자 관점의 결과만 검증한다.
4-2

첫 번째 특성과 두 번째 특성 간 본질적인 관계

회귀 방지는 신호를 키우고, 리팩터링 내성은 소음을 줄인다.

핵심 테스트 정확도 = 신호(발견된 버그 수) / 소음(허위 경보 수). 분자를 키우는 것이 회귀 방지, 분모를 줄이는 것이 리팩터링 내성이다.

회귀 방지와 리팩터링 내성 간의 관계

테스트 결과와 실제 기능 상태를 교차하면 네 가지 경우가 나온다. 의학의 진단 검사와 같은 구조다.

기능이 올바르게 작동기능이 고장남
테스트 통과올바른 추론 (참 음성)2종 오류 (거짓 음성)
테스트 실패1종 오류 (거짓 양성)올바른 추론 (참 양성)

회귀 방지가 없으면 거짓 음성(버그가 있는데 통과)이 늘어나고, 리팩터링 내성이 없으면 거짓 양성(멀쩡한데 실패)이 늘어난다.

테스트 정확도 극대화

!

원문 교정 원문 교정

노트에는 "테스트 정확도 = 소음 / 신호" 로 적혀 있는데 분자와 분모가 뒤집혔다. 정확도가 높다는 것은 신호가 크고 소음이 작다는 뜻이므로 정확도 = 신호 / 소음 이 맞다.

테스트의 정확도를 향상시키는 방법은 두 가지다.

  1. 신호를 증가시킨다

    회귀를 더 잘 찾아내는 테스트로 개선한다. 곧 회귀 방지를 높이는 일이다.

  2. 소음을 줄인다

    허위 경보를 발생시키지 않는 테스트로 개선한다. 곧 리팩터링 내성을 높이는 일이다.

거짓 양성과 거짓 음성의 중요성 — 역학 관계

둘의 무게는 프로젝트 시점에 따라 다르다.

  • 단기적으로 거짓 양성은 거짓 음성만큼 나쁘지 않다. 프로젝트 시작 시점에 잘못된 경고를 받는 것은, 경고를 아예 못 받아서 버그가 운영 환경에 들어가는 위험에 비하면 별일이 아니다.
  • 초기에는 리팩터링이 그렇게 중요하지 않다. 코드가 아직 작기 때문이다.
  • 시간이 지나면 리팩터링이 점점 중요해지고, 동시에 테스트의 리팩터링 내성도 함께 중요해진다.

따라서 중대형 프로젝트에서는 거짓 음성과 거짓 양성에 똑같이 주의를 기울여야 한다.

정리

  • 정확도 = 신호 / 소음. 회귀 방지가 분자를, 리팩터링 내성이 분모를 담당한다.
  • 거짓 음성 = 2종 오류(버그를 놓침), 거짓 양성 = 1종 오류(허위 경보).
  • 프로젝트 초기에는 거짓 음성이, 코드베이스가 커질수록 거짓 양성이 더 치명적이다.
4-3

세 번째, 네 번째 요소 빠른 피드백과 유지 보수성

테스트 코드는 제품 코드와 같은 등급의 시민이다.

핵심 빠른 테스트는 피드백 루프를 줄여 버그 수정 비용을 거의 0 으로 만든다. 그리고 그 테스트를 유지하는 비용은 코드 라인 수와 외부 의존성 수에 비례한다.

빠른 피드백

테스트가 빠를수록 더 많이, 더 자주 실행할 수 있다. 결함이 생기자마자 경고를 주므로 피드백 루프가 짧아지고, 버그를 수정하는 비용이 거의 0 에 수렴한다. 반대로 느린 테스트는 피드백을 늦추고 버그를 뒤늦게 드러낸다.

유지 보수성

유지 보수성은 두 가지로 나뉜다.

  • 이해하기 얼마나 어려운가 — 테스트 크기의 함수다. 코드 라인이 적을수록 읽기 쉽다.
  • 실행하기 얼마나 어려운가 — 프로세스 외부 의존성의 함수다. 디비, 네트워크 같은 의존성을 상시 운영하는 데 시간이 든다.
✓

테스트 코드는 일급 시민이다

테스트 코드의 품질은 제품 코드만큼 중요하다. 테스트를 작성할 때 절차를 생략하면 안 된다. 이름 짓기, 중복 제거, 추상화 모두 제품 코드와 같은 기준을 적용한다.

정리

  • 빠른 테스트 = 짧은 피드백 루프 = 낮은 수정 비용.
  • 유지 보수성 = 테스트 크기 + 외부 의존성 운영 부담.
  • 테스트 코드를 일급 시민으로 취급한다.
4-4

이상적인 테스트를 찾아서

네 요소는 덧셈이 아니라 곱셈이다. 하나가 0 이면 전체가 0 이다.

핵심 리팩터링 내성과 유지 보수성은 챙기고, 회귀 방지와 빠른 피드백 사이에서 선택한다. 이것이 현실에서 가능한 최선의 전략이다.

테스트의 가치는 회귀 방지 × 리팩터링 내성 × 빠른 피드백 × 유지 보수성 으로 측정한다. 곱셈이므로 넷 중 하나라도 0 이면 테스트의 가치는 0 이다.

테스트 코드를 포함한 모든 코드는 책임이다. 최소 임계치를 높게 설정하고, 그 임계치를 충족하는 테스트만 남기는 것이 좋다.

이상적인 테스트를 만들 수 있는가

네 범주 모두에서 최대 점수를 받는 테스트는 현실적으로 불가능하다. 앞 세 요소는 서로 상호 배타적이라 2개를 얻으면 나머지 1개를 희생해야 한다. 그러니 목표는 최대화가 아니라, 어느 것도 크게 줄지 않는 지점을 찾는 것이다.

극단적인 사례 1 — E2E 테스트

  • 모든 코드를 테스트하므로 회귀 방지를 훌륭하게 해낸다.
  • 사용자 입장에서 기능이 어떻게 동작하는지만 보므로 구현 세부 사항이 최대한 제거된다. 리팩터링 내성도 우수하다.
  • 하지만 느리다. 모든 테스트를 E2E 로 만든 시스템에서 빠른 피드백을 받는 것은 불가능하다.

극단적인 사례 2 — 간단한 테스트

E2E 와 정반대로 빠르게 실행되어 빠른 피드백을 주고, 거짓 양성 가능성도 낮아 리팩터링 내성이 우수하다. 하지만 기반 코드에 실수할 여지가 없을 만큼 간단해서 회귀를 나타내지 않는다.

user.spec.ts 동어 반복 테스트 
class User {
  constructor(private name: string) {}

  getName(): string {
    return this.name;
  }
}

it("User", () => {
  const name = "name";

  const sut = new User("name");

  expect(sut.getName()).toBe(name);
});

이런 테스트는 이름만 바꾼 동어 반복 테스트(tautology test) 를 낳는다. 항상 통과하거나 검증이 무의미하다.

극단적인 사례 3 — 깨지기 쉬운 테스트

실행이 빠르고 회귀를 잡을 가능성도 높지만 거짓 양성이 많은 테스트를 쓰기는 아주 쉽다. 이를 깨지기 쉬운 테스트(brittle test) 라고 부른다. 리팩터링을 견디지 못하고, 기능이 고장 났는지와 무관하게 빨간불이 된다.

user-repository.spec.ts 깨지기 쉬운 테스트 
class UserRepository {
  private lastExecutedSqlStatement: string;

  getById(id: number) {
    // ...
  }

  getLastExecutedSqlStatement() {
    return this.lastExecutedSqlStatement;
  }
}

it("getById_executes_correct_SQL_code", () => {
  const sut = new UserRepository();

  const user = sut.getById(5);

  expect(sut.getLastExecutedSqlStatement()).toBe(
    "SELECT * FROM dbo.[User] WHERE UserID = 5"
  );
});

같은 결과를 내는 다른 SQL 들

아래 쿼리는 전부 같은 결과를 돌려주지만, 위 테스트는 전부 실패시킨다.

  • SELECT * FROM dbo.[User] WHERE UserID = 5
  • SELECT * FROM dbo.User WHERE UserID = 5
  • SELECT UserId, Name, Email FROM dbo.User WHERE UserID = 5

테스트가 SUT 의 구현 세부 사항에 결합되어 더 이상의 리팩터링을 막고 있다. 빠르고 회귀 방지도 훌륭하지만 리팩터링 내성이 거의 없다.

결론

세 요소 중 둘만 고를 수 있다 — 세 교집합에는 각각 이름 붙은 실패 사례가 앉아 있고, 한가운데는 비어 있다.

네 번째 특성인 유지 보수성은 앞의 세 요소와 상호 배타적이지 않다. 다만 E2E 테스트는 외부 프로세스 의존성을 계속 운영해야 하므로 유지비 측면에서 별도로 더 비싸다.

✓

현실에서의 전략

E2E 만 쓰거나 테스트가 상당히 빠르지 않은 한, 리팩터링 내성을 최대한 챙긴다. 리팩터링 내성과 유지 보수성을 지키면서 회귀 방지와 빠른 피드백 중 하나를 고르는 것이 최선이다.

정리

  • 테스트 가치 = 네 요소의 곱. 하나가 0 이면 전체가 0 이다.
  • E2E 는 피드백을, 간단한 테스트는 회귀 방지를, 깨지기 쉬운 테스트는 리팩터링 내성을 잃는다.
  • 리팩터링 내성은 타협 대상이 아니다. 회귀 방지와 빠른 피드백 사이에서만 저울질한다.
4-5

대중적인 테스트 자동화 개념

테스트 피라미드와 블랙박스/화이트박스를 4대 요소로 다시 읽는다.

핵심 피라미드의 어느 계층도 리팩터링 내성만은 포기하지 않는다. 계층 간에 저울질하는 것은 회귀 방지와 빠른 피드백뿐이다.

테스트 피라미드 분해

테스트 스위트에서 테스트 유형 간 일정한 비율을 나타내는 개념이다.

가로는 개수, 세로는 실제 유저를 모방하는 정도 — 위로 갈수록 회귀 방지에 유리하고, 아래로 갈수록 실행 속도가 강조된다.

항상 지켜지는 리팩터링 내성

어느 계층도 리팩터링 내성을 포기하지 않는다. 모든 테스트는 거짓 양성을 최소화하는 것을 목표로 하며, 제품 코드로 직접 작업할 때도 마찬가지다. 테스트 개수는 E2E < 통합 < 단위 순으로 많아야 한다.

E2E 는 가장 중요한 기능에 적용하거나, 단위 / 통합과 동일한 수준으로 보호해야 할 때만 쓴다.

앱의 성격피라미드 형태
단순 CRUD 만 있는 앱통합과 단위 테스트 개수가 거의 같아진다. 알고리즘이나 비즈니스 복잡도가 없으면 단위 테스트는 간단한 테스트 수준으로 빠르게 내려간다
외부 의존성(디비) 하나만 두는 API유저 인터페이스가 없어 유지비가 크지 않으므로 E2E 를 더 많이 두는 편이 적합할 수 있다

블랙박스 / 화이트박스 테스트 선택하기

블랙박스 테스트

시스템 내부 구조를 몰라도 기능을 검증할 수 있는 방법이다. 앱이 어떻게 해야 하는지가 아니라 무엇을 해야 하는지를 중심으로 구축된다.

화이트박스 테스트

앱의 내부 작업을 검증한다. 요구 사항이나 명세가 아니라 소스 코드에서 테스트가 파생된다. 소스 코드 분석을 통해 외부 명세만으로는 놓칠 오류를 발견할 수 있지만, 특정 구현과 결합되어 테스트가 깨지기 쉽다.

종류회귀 방지리팩터링 내성
화이트박스좋음나쁨
블랙박스나쁨좋음

모든 테스트가 리팩터링 내성을 가져야 하므로, 기본값은 블랙박스다. 시스템을 블랙박스로 바라보고 동작을 검증한다.

i

화이트박스가 쓸모 있는 자리 보강

화이트박스 방식이 유용한 것은 테스트를 쓸 때가 아니라 분석할 때다. 커버리지 리포트로 어느 분기가 안 걸렸는지 확인하고, 그 분기를 블랙박스 테스트로 덮는 식으로 쓴다.

정리

  • 피라미드는 개수(가로) × 사용자 모방 정도(세로)의 관계다.
  • 어느 계층도 리팩터링 내성은 포기하지 않는다.
  • CRUD 앱이나 UI 없는 API 는 피라미드가 납작해질 수 있다.
  • 테스트 작성의 기본값은 블랙박스. 화이트박스는 커버리지 분석에만 쓴다.
