6-1

단위 테스트의 세 가지 스타일

출력을 보느냐, 상태를 보느냐, 통신을 보느냐.

핵심 같은 동작을 검증해도 무엇을 근거로 삼느냐에 따라 세 스타일이 갈리고, 이 선택이 네 가지 요소 점수를 좌우한다.

출력 기반 테스트 정의

SUT 에 입력을 넣고 생성되는 출력을 검증한다. 전역 상태나 내부 상태를 변경하지 않는 코드에만 적용할 수 있으므로 반환값만 검증하면 된다. 함수형 스타일이라고도 부른다.

price-engine.spec.ts 출력 기반 
class PriceEngine {
  calculateDiscount(products: Product[]) {
    const discount = products.length * 0.01;
    return Math.min(discount, 0.02);
  }
}

it("discount_of_two_products", () => {
  const product1 = new Product("Hand Wash");
  const product2 = new Product("Shampoo");
  const sut = new PriceEngine();

  const discount = sut.calculateDiscount([product1, product2]);

  expect(discount).toBe(0.02);
});

상태 기반 스타일 정의

작업이 완료된 후 시스템의 상태를 확인한다. 여기서 상태는 SUT 자신의 상태일 수도, 협력자의 상태일 수도, 디비나 파일 시스템 같은 프로세스 외부 의존성의 상태일 수도 있다.

order.spec.ts 상태 기반 
class Order {
  products: Product[] = [];

  addProduct(product: Product) {
    this.products.push(product); // 상태를 변경한다
  }
}

it("adding_a_product_to_an_order", () => {
  const product = new Product("Hand Wash");
  const sut = new Order();

  sut.addProduct(product);

  expect(sut.products).toHaveLength(1);
  expect(sut.products[0]).toBe(product);
});

통신 기반 스타일 정의

목을 사용해 SUT 와 협력자 간의 통신을 검증한다.

controller.spec.ts 통신 기반 
it("sending_a_greetings_email", () => {
  const emailGatewayMock: jest.Mocked<IEmailGateway> = {
    sendGreetingsEmail: jest.fn(),
  };
  const sut = new Controller(emailGatewayMock);
  const email = "imkdw@gmail.com";

  sut.greetUser(email);

  expect(emailGatewayMock.sendGreetingsEmail).toHaveBeenCalledWith(email);
});

정리

  • 출력 기반 = 반환값만 검증. 함수형 스타일.
  • 상태 기반 = 작업 후 SUT / 협력자 / 외부 의존성의 상태를 검증.
  • 통신 기반 = 목으로 SUT 와 협력자 간 통신을 검증.
6-2

단위 테스트 스타일 비교

네 가지 요소로 세 스타일을 저울에 올리면 순위가 분명하다.

핵심 가능하면 항상 출력 기반 테스트를 선호한다. 다만 그건 함수형으로 작성된 코드에서만 가능하므로, 결국 제품 코드를 바꿔야 한다.

회귀 방지와 피드백 속도 지표로 비교

회귀 방지 지표를 결정하는 것은 세 가지 수치다.

  • 테스트 중 실행되는 코드의 양
  • 코드 복잡도
  • 도메인 유의성

이 셋은 스타일과 큰 상관이 없다. 어떤 스타일로든 코드를 많이 또는 적게 실행하도록 테스트를 쓸 수 있다. 다만 통신 기반 스타일에는 예외가 있다. 남용하면 아주 작은 코드 조각만 검증하고 나머지는 전부 목으로 채우는 피상적인 테스트가 나오기 쉽다.

피드백 속도 역시 스타일과 상관관계가 거의 없다. 목이 런타임에 약간의 지연을 만들긴 하지만, 테스트가 수만 개가 아니라면 체감되지 않는다.

리팩터링 내성 지표로 스타일 비교

  • 출력 기반 — 테스트가 대상 메소드에만 결합되므로 거짓 양성 방지가 가장 우수하다.
  • 상태 기반 — 대상 메소드 외에 클래스 상태와도 함께 동작하므로 거짓 양성이 되기 쉽다.
  • 통신 기반 — 허위 경보에 가장 취약하다. 테스트 대역으로 상호작용을 확인하는 테스트는 대부분 깨지기 쉽다.

유지 보수성 지표로 스타일 비교하기

유지 보수성은 스타일과 밀접하게 얽혀 있고, 완화할 방법도 많지 않다. 유지비는 두 가지 특성으로 정의한다.

  • 테스트를 이해하기 얼마나 어려운가 — 테스트 크기의 함수
  • 테스트를 실행하기 얼마나 어려운가 — 직접 관련된 프로세스 외부 의존성의 함수
출력 기반 테스트의 유지 보수성

세 스타일 중 가장 유지 보수하기 쉽다. 거의 항상 짧고 간결하며, 전역이나 내부 상태를 변경할 일이 없다.

상태 기반 테스트의 유지 보수성

일반적으로 출력 기반보다 어렵다. 상태 검증은 출력보다 더 많은 공간을 차지하기 때문이다.

article.spec.ts 검증부가 네 줄 
it("adding_a_comment_to_an_article", () => {
  const sut = new Article();
  const text = "Comment Text";
  const author = "John Doe";
  const now = new Date("2024-11-24");

  sut.addComment(text, author, now);

  // 글(Article)의 상태를 검증한다
  expect(sut.comments).toHaveLength(1);
  expect(sut.comments[0].text).toBe(text);
  expect(sut.comments[0].author).toBe(author);
  expect(sut.comments[0].date).toBe(now);
});

댓글이 하나뿐인 단순한 테스트인데도 검증이 네 줄이다. 상태 기반 테스트는 확인할 데이터가 늘수록 크기가 대폭 커진다.

완화 1 — 상태를 검증하는 헬퍼 메소드
article.spec.ts 
it("adding_a_comment_to_an_article", () => {
  const sut = new Article();
  const text = "Comment Text";
  const author = "John Doe";
  const now = new Date("2024-11-24");

  sut.addComment(text, author, now);

  // 헬퍼 메소드를 통한 상태 검증
  expect(sut).shouldContainNumberOfComments(1).withComment(text, author, now);
});

여러 줄을 한 줄로 줄일 수 있지만, 이런 헬퍼를 작성하고 유지하는 데 상당한 노력이 든다.

완화 2 — 동등 멤버 정의를 통한 상태 검사
article.spec.ts 
it("adding_a_comment_to_an_article", () => {
  const sut = new Article();
  const comment = new Comment(
    "Comment Text",
    "John Doe",
    new Date("2024-11-24")
  );

  sut.addComment(comment.text, comment.author, comment.date);

  expect(sut.comments).toEqual([comment]);

이 기법의 조건

강력하지만 클래스가 값에 해당하고 값 객체로 변환할 수 있을 때만 효과적이다. 그렇지 않은 클래스에 억지로 동등성을 넣으면 오히려 코드 오염으로 이어진다. 어떤 방법을 쓰든 상태 기반 테스트는 출력 기반보다 공간을 더 차지한다.

통신 기반 테스트의 유지 보수성

테스트 대역 설정과 상호작용 검증을 모두 작성해야 하므로 공간을 많이 차지한다. 목이 사슬 형태(목이 다른 목을 반환하는 식)로 있으면 테스트는 더 커지고 유지가 힘들어진다.

스타일 비교하기 — 결론

구분출력 기반상태 기반통신 기반
리팩터링 내성을 지키기 위한 노력낮음중간중간
유지비낮음중간높음

가능하면 항상 출력 기반 테스트를 선호하는 게 좋다. 하지만 쉽지 않다. 출력 기반은 함수형으로 작성된 코드에만 적용할 수 있고, 대부분의 객체지향 코드는 그렇지 않기 때문이다.

✓

그래서 다음 아이템이 필요하다

코드를 순수 함수로 만들면 상태 기반이나 통신 기반 대신 출력 기반 테스트를 쓸 수 있게 된다. 테스트 스타일을 바꾸는 일은 결국 제품 코드를 바꾸는 일이다.

정리

  • 회귀 방지와 피드백 속도는 스타일과 상관이 적다. 단, 통신 기반은 피상적 테스트로 흐르기 쉽다.
  • 리팩터링 내성 / 유지 보수성 모두 출력 > 상태 > 통신 순이다.
  • 상태 기반의 크기는 헬퍼나 동등 멤버로 줄일 수 있지만 한계가 있다.
  • 출력 기반을 쓰려면 코드를 순수 함수로 만들어야 한다.
6-3

함수형 아키텍쳐에 대한 이해

결정을 내리는 코드와, 그 결정에 따라 작용하는 코드를 분리한다.

핵심 수학적 함수는 숨은 입출력이 없는 함수다. 모든 입출력이 시그니처에 드러나 있어야 하고, 출력 기반 테스트를 적용할 수 있는 것은 수학적 함수뿐이다.

함수형 프로그래밍이란

수학적 함수를 사용하는 프로그래밍이다. 수학적 함수란 숨은 입출력이 없는 함수로, 모든 입출력이 메소드명 / 인수 / 반환 타입으로 구성된 시그니처에 명시되어 있어야 한다.

discount.ts 수학적 함수 
/**
 * 이름   : calculateDiscount
 * 입력   : Product[]
 * 출력   : number
 * 시그니처: calculateDiscount(products: Product[]): number
 */
const calculateDiscount = (products: Product[]): number => {
  const discount = products.length * 0.01;
  return Math.min(discount, 0.02);
};

숨은 입출력 유형

메소드가 수학적 함수인지 판별하는 가장 좋은 방법은, 프로그램 동작을 바꾸지 않고 그 호출을 반환값으로 대체할 수 있는지 확인하는 것이다. 이렇게 호출을 값으로 바꾸는 성질을 참조 투명성(referential transparency) 이라 부른다.

유형내용
사이드 이펙트시그니처에 없는 출력. 상태를 변경하거나 디스크의 파일을 업데이트하는 등
예외시그니처에 설정된 계약을 우회하는 경로를 만든다. 호출 스택 어디에서도 발생할 수 있으므로 시그니처가 전달하지 않는 출력이 추가된다
내외부 상태 참조new Date() 처럼 현재 시각을 가져오거나, 디비에 질의하거나, 비공개 가변 필드를 참조하는 것. 모두 시그니처에 없는 입력이다

사이드 이펙트 예시

사이드 이펙트는 숨은 출력의 가장 흔한 유형이다. 아래 코드는 댓글을 반환하지만, 동시에 상태를 변경한다.

article.ts 숨은 출력 
class Article {
  comments: Comment[] = [];

  addComment(text: string): Comment {
    const comment = new Comment(text);
    this.comments.push(comment); // 사이드 이펙트 — 시그니처에 없는 출력
    return comment;
  }
}

함수형 아키텍쳐란

비즈니스 로직을 처리하는 코드와 사이드 이펙트를 일으키는 코드를 분리하는 것이다. 사이드 이펙트를 비즈니스 연산의 끝으로 몰아서 비즈니스 로직과 떼어놓는다.

구분역할다른 이름
결정을 내리는 코드사이드 이펙트가 필요 없으므로 수학적 함수로 작성한다함수형 코어, 불변 코어
결정에 따라 작용하는 코드수학적 함수가 내린 결정을 디비 변경이나 메세지 발행처럼 가시적인 것으로 바꾼다가변 셸
목표는 출력 기반 테스트로 함수형 코어를 두루 다루고, 가변 셸은 훨씬 적은 수의 통합 테스트에 맡기는 것이다 — 셸은 결정을 내리지 않고 실어 나르기만 한다.
함수형 코어와 가변 셸의 협력
  1. 가변 셸이 모든 입력을 수집한다
  2. 함수형 코어가 결정을 생성한다
  3. 셸이 그 결정을 사이드 이펙트로 변환한다

    가변 셸이 아무런 결정도 내리지 않아야 계층이 잘 분리된 것이다.

함수형과 육각형 비교

함수형 아키텍쳐육각형 아키텍쳐
기반 아이디어관심사 분리
의존성 흐름단방향
사이드 이펙트모두 가변 셸로 밀어낸다도메인 계층 안에 갇혀 있는 한 문제없다

즉 함수형 아키텍쳐는 육각형 아키텍쳐의 더 엄격한 버전이다.

정리

  • 수학적 함수 = 숨은 입출력이 없는 함수. 참조 투명성으로 판별한다.
  • 숨은 입출력의 세 유형: 사이드 이펙트, 예외, 내외부 상태 참조.
  • 함수형 아키텍쳐 = 결정을 내리는 함수형 코어 + 결정을 실행하는 가변 셸.
  • 육각형과 아이디어는 같고, 사이드 이펙트 처리에서 더 엄격하다.

함수형 아키텍쳐와 출력 기반 테스트로의 전환

감사 시스템을 세 번 고쳐 쓰면서 네 요소 점수가 어떻게 움직이는지 본다.

핵심 목으로 파일 시스템을 떼어내면 빠른 피드백까지는 얻는다. 함수형 아키텍쳐로 가야 유지 보수성까지 얻는다.

감사 시스템 — 초기 버전

AuditManager 가 파일 시스템과 밀접하게 얽혀 있어 테스트하기 어렵다. 테스트 전에 파일을 올바른 위치에 배치해야 하고, 끝나면 읽어서 내용을 확인한 뒤 삭제해야 한다. 게다가 파일 시스템을 다루는 이상 이것은 단위 테스트가 아니라 통합 테스트다.

audit-manager.ts 초기 버전 
import fs from "fs/promises";
import path from "path";

class AuditManager {
  constructor(
    private readonly maxEntriesPerFile: number,
    private readonly directoryName: string
  ) {}

  async addRecord(visitorName: string, timeOfVisit: Date): Promise<void> {
    const filePaths = await fs.readdir(this.directoryName);
    const sorted = this.sortByIndex(filePaths);

    const newRecord = `${visitorName};${timeOfVisit.toISOString()}`;

    if (sorted.length === 0) {
      const newFile = path.join(this.directoryName, "audit_1.txt");
      await fs.writeFile(newFile, newRecord);
      return;
    }

    const lastEntry = sorted[sorted.length - 1];
    const currentFileIndex = lastEntry.index;
    const currentFilePath = lastEntry.path;

    const content = await fs.readFile(
      path.join(this.directoryName, currentFilePath),
      "utf8"
    );
    const lines = content.split("\r\n");

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      await fs.writeFile(
        path.join(this.directoryName, currentFilePath),
        lines.join("\r\n")
      );
    } else {
      const newName = `audit_${currentFileIndex + 1}.txt`;
      await fs.writeFile(path.join(this.directoryName, newName), newRecord);
    }
  }

  private sortByIndex(files: string[]) {
    return files
      .map((p) => ({ index: this.getIndex(p), path: p }))
      .sort((a, b) => a.index - b.index);
  }

  private getIndex(filePath: string): number {
    // 파일명 예시: audit_1.txt
    const fileName = path.parse(filePath).name;
    return parseInt(fileName.split("_")[1]);
  }
}

테스트를 파일 시스템에서 분리하기 위한 목 사용하기

파일의 모든 연산을 별도의 클래스로 도출하고 생성자로 주입한다. 이제 AuditManager 가 파일 시스템에서 분리되므로 공유 의존성이 사라지고 테스트를 서로 독립적으로 실행할 수 있다.

audit-manager.ts 목 사용 버전 
interface IFileSystem {
  getFiles(directory: string): Promise<string[]>;
  writeAllText(filePath: string, content: string): Promise<void>;
  readAllLines(filePath: string): Promise<string[]>;
}

class AuditManager {
  constructor(
    private readonly maxEntriesPerFile: number,
    private readonly directoryName: string,
    private readonly fileSystem: IFileSystem
  ) {}

  async addRecord(visitorName: string, timeOfVisit: Date): Promise<void> {
    const filePaths = await this.fileSystem.getFiles(this.directoryName);
    const sorted = this.sortByIndex(filePaths);

    const newRecord = `${visitorName};${timeOfVisit.toISOString()}`;

    if (sorted.length === 0) {
      const newFile = path.join(this.directoryName, "audit_1.txt");
      await this.fileSystem.writeAllText(newFile, newRecord);
      return;
    }

    const lastEntry = sorted[sorted.length - 1];
    const lines = await this.fileSystem.readAllLines(
      path.join(this.directoryName, lastEntry.path)
    );

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      await this.fileSystem.writeAllText(
        path.join(this.directoryName, lastEntry.path),
        lines.join("\r\n")
      );
    } else {
      const newName = `audit_${lastEntry.index + 1}.txt`;
      await this.fileSystem.writeAllText(
        path.join(this.directoryName, newName),
        newRecord
      );
    }
  }
}

테스트 속도는 훨씬 빨라졌지만 복잡한 설정이 붙었다. 유지비 측면에서 이상적이지 않고, 평이한 입출력에 의존하는 테스트만큼 읽기 쉽지도 않다.

함수형 아키텍쳐로 리팩터링하기

함수형 아키텍쳐에서는 사이드 이펙트를 클래스 외부로 완전히 이동할 수 있다. AuditManager 는 파일에 무엇을 할지 결정만 책임지고, 새 클래스 Persister 가 그 결정에 따라 파일 시스템을 업데이트한다.

AuditManager — 함수형 코어
audit-manager.ts 함수형 코어 
class AuditManager {
  constructor(private readonly maxEntriesPerFile: number) {}

  // 경로가 아니라 FileContent 배열을 받고, 사이드 이펙트 대신 "명령"을 반환한다
  addRecord(
    files: FileContent[],
    visitorName: string,
    timeOfVisit: Date
  ): FileUpdate {
    const sorted = this.sortByIndex(files);
    const newRecord = `${visitorName};${timeOfVisit.toISOString().slice(0, 19)}`;

    if (sorted.length === 0) {
      return { fileName: "audit_1.txt", newContent: newRecord };
    }

    const lastEntry = sorted[sorted.length - 1];
    const currentFile = lastEntry.file;
    const lines = [...currentFile.lines];

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      return {
        fileName: currentFile.fileName,
        newContent: lines.join("\r\n"),
      };
    }

    return {
      fileName: `audit_${lastEntry.index + 1}.txt`,
      newContent: newRecord,
    };
  }

  private sortByIndex(files: FileContent[]) {
    return files
      .map((file) => ({ index: this.getIndex(file.fileName), file }))
      .sort((a, b) => a.index - b.index);
  }

  private getIndex(fileName: string): number {
    return parseInt(fileName.replace(".txt", "").split("_")[1]);
  }
}
Persister — 가변 셸
persister.ts 가변 셸 
class Persister {
  async readDirectory(directoryName: string): Promise<FileContent[]> {
    const files = await fs.readdir(directoryName);
    return Promise.all(
      files.map(async (file) => {
        const content = await fs.readFile(
          path.join(directoryName, file),
          "utf8"
        );
        return {
          fileName: file,
          lines: content.split("\r\n").filter((line) => line.length > 0),
        };
      })
    );
  }

  async applyUpdate(directoryName: string, update: FileUpdate): Promise<void> {
    const filePath = path.join(directoryName, update.fileName);
    await fs.writeFile(filePath, update.newContent);
  }
}

모든 복잡도는 AuditManager 에 남고, Persister 는 받은 업데이트 명령을 작업 폴더에 수행하기만 한다. 비즈니스 로직과 사이드 이펙트가 분리됐다.

ApplicationService — 둘을 붙이는 진입점
application-service.ts 
class ApplicationService {
  private readonly auditManager: AuditManager;
  private readonly persister: Persister;

  constructor(
    private readonly directoryName: string,
    maxEntriesPerFile: number
  ) {
    this.auditManager = new AuditManager(maxEntriesPerFile);
    this.persister = new Persister();
  }

  async addRecord(visitorName: string, timeOfVisit: Date): Promise<void> {
    const files = await this.persister.readDirectory(this.directoryName);
    const update = this.auditManager.addRecord(files, visitorName, timeOfVisit);
    await this.persister.applyUpdate(this.directoryName, update);
  }
}

정리

  • 초기 버전은 파일 시스템과 얽혀 있어 피드백과 유지 보수성 둘 다 잃는다.
  • 목 도입으로 피드백은 회복하지만 복잡한 설정이 유지비로 남는다.
  • 함수형 아키텍쳐는 결정(FileUpdate 반환)과 실행(Persister)을 분리한다.
  • 결과적으로 목 없이 평이한 입출력만으로 테스트할 수 있게 된다.
6-5

함수형 아키텍쳐 단점 이해하기

두루 적용되는 해결책은 없다. 순수성의 비용이 크면 순수성을 포기한다.

핵심 목표는 모든 테스트를 출력 기반으로 바꾸는 것이 아니라 가능한 한 많은 테스트를 전환하는 것이다.

함수형 아키텍쳐 적용 가능성

감사 시스템은 결정을 내리기 전에 입력을 모두 미리 수집할 수 있어서 함수형 아키텍쳐가 잘 맞았다. 하지만 실행 흐름이 늘 그렇게 단순하지는 않다. 의사 결정 도중의 중간 결과에 따라 프로세스 외부 의존성에 추가로 질의해야 하는 경우가 있다.

sequenceDiagram
  participant AS as 앱 서비스
  participant AM as AuditManager
  participant FS as 파일 시스템 / DB
  AS->>FS: Read Directory
  FS-->>AS: 파일 목록
  AS->>AM: 레코드 추가
  AM->>FS: 접근 레벨 획득
  FS-->>AM: 접근 레벨
  AM-->>AS: FileUpdate
  AS->>FS: Apply Update
의사 결정 중간에 외부 의존성을 다시 부르는 순간 숨은 입력이 생긴다 — AuditManager 는 더 이상 수학적 함수가 아니게 된다.
두 가지 해결 방법
  1. 앱 서비스 전면에서 미리 모두 수집한다

    폴더 내용과 함께 방문자 접근 레벨까지 앞에서 읽어둔다. 대신 접근 레벨이 필요하지 않은 경우에도 매번 디비에 질의하게 되어 성능이 저하된다.

  2. AuditManager 에 isAccessLevelCheckRequired 를 추가한다

    디비를 호출할지 말지를 코어가 먼저 알려주고, 앱 서비스가 그때만 조회한다. 성능은 지키지만 디비 호출 여부의 결정이 앱 서비스로 넘어가면서 분리가 다소 완화된다.

!

지켜야 할 선

함수형 코어의 클래스는 협력자로 작동해서는 안 되고, 작업의 결과인 값으로 작동해야 한다. 이 선만 지키면 두 방법 모두 선택지가 된다.

성능 단점

함수형 아키텍쳐를 두고 가장 흔히 벌어지는 논쟁이다. 문제가 되는 것은 테스트의 성능이 아니라 앱의 성능이다. 필요 없을지도 모르는 데이터까지 미리 읽어오기 때문이다.

결국 함수형과 전통적인 아키텍쳐 사이의 선택은 성능과 코드 유지 보수성 간의 절충이다. 성능 영향이 눈에 띄지 않는 시스템에서는 함수형 아키텍쳐로 유지 보수성을 얻는 편이 낫다. 두루 적용되는 해결책은 없다.

코드베이스 크기 증가

함수형 코어와 가변 셸을 명확히 분리해야 하므로 초기에 보일러플레이트가 늘어난다. 궁극적으로는 복잡도가 낮아지고 유지 보수성이 향상되지만, 그 전에 코드량을 먼저 지불해야 한다.

✓

현실적인 목표

함수형 방식의 순수성에 많은 비용이 든다면 순수성을 따르지 않는다. 대부분의 프로젝트는 모든 도메인 모델을 불변으로 둘 수 없으므로 출력 기반 테스트에만 의존할 수 없다. 모든 테스트를 전환하는 것이 아니라, 가능한 한 많은 테스트를 전환하는 것이 목표다.

정리

  • 의사 결정 중간에 외부 조회가 필요하면 숨은 입력이 생겨 수학적 함수가 깨진다.
  • 미리 다 읽거나(성능 손해), 조회 필요 여부를 코어가 알려주거나(분리 완화) 중 선택한다.
  • 함수형 vs 전통적 아키텍쳐 = 성능 vs 유지 보수성의 절충이다.
  • 보일러플레이트는 먼저 늘고 복잡도는 나중에 준다. 순수성의 비용이 크면 포기한다.
