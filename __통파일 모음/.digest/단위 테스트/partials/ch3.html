3-1

단위 테스트를 구성하는 방법

준비 / 실행 / 검증. 구절의 크기가 곧 설계의 신호다.

핵심 실행 구절이 두 줄을 넘으면 SUT 의 공개 API 에 문제가 있다. 테스트 구조는 제품 코드 설계를 되비추는 거울이다.

AAA 패턴 사용

각 테스트를 준비(Arrange) / 실행(Act) / 검증(Assert) 세 부분으로 나눈다. 테스트 스위트 내 모든 테스트가 단순하고 균일한 구조를 갖게 되며, 이 일관성이 패턴의 가장 큰 장점이다.

TDD 를 할 때는 기능이 어떻게 동작할지 아직 모르므로 기대하는 동작(검증)으로 먼저 윤곽을 잡고 개발한다. 반대로 테스트 전에 제품 코드를 작성했다면 무엇을 예상하는지 이미 알고 있으므로 준비 구절부터 시작하는 편이 좋다.

구절하는 일
준비테스트 대상 시스템(SUT)과 해당 의존성을 원하는 상태로 만든다
실행SUT 의 메소드를 호출하고, 준비된 의존성을 전달하며, 출력 값을 캡처한다
검증실행 결과를 검증한다. 반환값, 협력자의 상태, 협력자에 호출한 메소드 등으로 검증할 수 있다
3-1.ts 
export default class Calculator {
  sum(first: number, second: number) {
    return first + second;
  }
}
3-1.spec.ts 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  // 준비
  const first = 10;
  const second = 20;
  const calculator = new Calculator();

  // 실행
  const result = calculator.sum(first, second);

  // 검증
  expect(result).toBe(30);
});
Given-When-Then 패턴

AAA 와 사실상 같은 패턴이다. Given 이 준비, When 이 실행, Then 이 검증에 대응한다. 두 패턴에 기능적 차이는 없고, 비개발자가 읽기에는 Given-When-Then 이 더 읽기 쉽다는 점만 다르다.

여러 개의 준비, 실행, 검증 구절 피하기

준비 → 실행 → 검증 → 더 실행 → 다시 검증 같은 테스트를 만날 수 있다. 이런 테스트는 더 이상 단위 테스트가 아니라 통합 테스트다.

실행이 하나라면 테스트가 단위 테스트 범주에 있게끔 보장되고, 간단하고 빠르며 이해하기 쉽다. 일련의 실행과 검증이 포함된 테스트를 보면 리팩터링해서 각 동작을 고유의 테스트로 도출한다.

테스트 내 if 피하기

단위 테스트든 통합 테스트든, 테스트는 분기가 없는 간단한 일련의 단계여야 한다. if 문은 테스트가 한 번에 너무 많은 것을 검증한다는 표시다. 분기가 있어서 얻는 이점은 없고 추가 유지비만 불어난다.

각 구절은 얼마나 커야 하는가

준비 구절이 가장 큰 경우

일반적으로 준비 구절이 세 구절 중 가장 크다. 너무 크다면 같은 테스트 클래스 내의 비공개 메소드나 별도의 팩토리 클래스로 도출하는 게 좋다. 코드 재사용에 도움이 되는 패턴으로 오브젝트 마더(Object Mother) 와 테스트 데이터 빌더(Test Data Builder) 가 있다.

실행 구절이 한 줄 이상인 경우를 경계하라

실행 구절은 보통 코드 한 줄이다. 두 줄 이상이라면 SUT 의 공개 API 에 문제가 있다는 신호다. 클라이언트가 두 단계를 순서대로 올바르게 호출해야만 객체가 일관된 상태를 유지한다면, 그 순서를 어기는 순간 모순이 생긴다.

!

불변 위반과 캡슐화

이런 모순을 불변 위반(invariant violation) 이라 하고, 잠재적 모순으로부터 코드를 보호하는 행위를 캡슐화라고 한다. 해결책은 캡슐화를 항상 지키는 것, 즉 불변 위반을 초래할 수 있는 잠재적 행동 자체를 API 에서 제거하는 것이다.

검증 구절에는 검증문이 얼마나 있어야 할까

단위 테스트의 단위는 동작의 단위이지 코드의 단위가 아니다. 단일 동작 단위는 여러 결과를 낼 수 있고, 하나의 테스트로 그 모든 결과를 평가하는 게 좋다.

그렇다고 검증이 너무 많아지는 것은 경계해야 한다. 객체의 모든 속성을 하나하나 검증하는 대신, 클래스 내에 적절한 동등 멤버를 정의해서 객체 단위로 비교하는 편이 낫다.

종료 단계는 어떤가

단위 테스트는 프로세스 외부에 종속적이지 않으므로 처리해야 할 사이드 이펙트를 남기지 않는다. 일반적으로 단위 테스트에는 종료 구절이 필요 없다.

테스트 대상 시스템 구별하기

SUT 는 앱에서 호출하고자 하는 동작에 대한 진입점을 제공한다. 동작은 여러 클래스에 걸칠 만큼 크거나 단일 메소드만큼 작을 수 있지만, 진입점은 하나만 존재해야 한다.

테스트에 여러 객체가 등장하면 무엇이 테스트 대상인지 헷갈린다. SUT 에 해당하는 변수의 이름을 sut 로 고정하면 이 문제가 사라진다.

3-1.spec.ts sut 로 이름 고정 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  // 준비
  const first = 10;
  const second = 20;
  const sut = new Calculator(); // 테스트 대상을 sut 으로

  // 실행
  const result = sut.sum(first, second);

  // 검증
  expect(result).toBe(30);
});
!

원문 교정 원문 교정

노트에서는 const sut = calculator.sum(...) 처럼 실행 결과에 sut 라는 이름을 붙였는데, sut 는 테스트 대상 객체 자체에 붙이는 이름이다. 결과 변수는 result 로 두고 new Calculator() 쪽을 sut 로 바꾸는 것이 원서의 의도다.

준비, 실행, 검증 주석 제거하기

주석 대신 각 단계를 빈 줄로 띄우는 방법이 흔히 쓰인다. 다만 통합 테스트에서는 준비 / 검증 구절이 여러 문단으로 나뉠 만큼 복잡해지는 경우가 있다.

기준은 이렇다. 구절 안쪽에 빈 줄을 넣지 않아도 되는 테스트라면 주석을 지우고, 그렇지 않다면 주석을 남긴다.

3-1.spec.ts 주석 없이 빈 줄로만 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  const first = 10;
  const second = 20;
  const sut = new Calculator();

  const result = sut.sum(first, second);

  expect(result).toBe(30);
});

정리

  • AAA 로 구조를 통일한다. Given-When-Then 과 기능적 차이는 없다.
  • 실행 구절이 두 줄 이상이면 공개 API 의 캡슐화 문제를 의심한다.
  • 다단계 테스트와 if 는 나눠서 없앤다.
  • 테스트 대상 변수는 sut 으로 이름을 고정한다.
  • 구절 안에 빈 줄이 필요 없으면 AAA 주석을 지운다.
3-2

XUnit 테스트 프레임워크

테스트 하나는 문제 영역에 대한 원자적인 사실 하나여야 한다.

핵심 테스트가 통과한다는 것은 그 사실 또는 시나리오가 실제로 참이라는 증거다. 제품 코드의 기능 목록을 나열하는 것이 아니다.

각 테스트는 이야기를 가져야 한다. 그 이야기는 문제 영역에 대한 개별적이고 원자적인 사실 또는 시나리오여야 하며, 테스트 통과는 그 사실이 참이라는 증거가 된다.

×

테스트가 기능 목록이 되면

제품 코드에 있는 메소드를 하나씩 따라가며 테스트를 만들면, 테스트 스위트는 명세가 아니라 코드의 복사본이 된다. 코드가 바뀌면 테스트도 똑같이 바뀌므로 아무것도 지켜주지 못한다.

앱 동작에 대한 고수준의 명세가 있어야 하고, 그 명세는 비즈니스 담당자에게도 의미가 있어야 한다. 이 기준이 다음 아이템의 명명법으로 곧장 이어진다.

정리

  • 테스트 하나 = 문제 영역의 원자적인 사실 하나.
  • 제품 코드의 기능을 나열하는 테스트는 명세가 아니라 코드의 복사본이다.
  • 테스트 스위트는 비즈니스 담당자에게도 읽히는 고수준 명세여야 한다.
3-3

테스트 간 테스트 픽스처 재사용

beforeEach 로 묶지 말고 비공개 팩토리 메소드로 뽑는다.

핵심 beforeEach 로 픽스처를 공유하면 테스트 간 결합도가 올라가고 가독성이 떨어진다. 팩토리 메소드는 둘 다 지킨다.

테스트 픽스처란

테스트 실행 대상 객체, 즉 SUT 로 전달되는 정규 의존성이자 인수다. 디비의 데이터나 하드디스크의 파일일 수도 있다. 이런 객체는 각 테스트 실행 전에 알려진 고정 상태로 유지되기 때문에 동일한 결과를 만들어낸다.

테스트 픽스처를 재사용하는 올바르지 않은 방법

두 테스트에 공통된 준비 과정이 필요하니 beforeEach 로 뽑아 재사용성을 높인 코드다.

customer.spec.ts 문제 
describe("CustomerTests", () => {
  let _store: Store;
  let _sut: Customer;

  // 각 테스트 실행 이전에 호출됨
  beforeEach(() => {
    _store = new Store();
    _store.addInventory(Product.Shampoo, 10);
    _sut = new Customer();
  });

  it("purchase_succeeds_when_enough_inventory", () => {
    const success = _sut.purchase(_store, Product.Shampoo, 5);
    expect(success).toBe(true);
    expect(_store.getInventory(Product.Shampoo)).toBe(5);
  });

  it("purchase_fails_when_not_enough_inventory", () => {
    const success = _sut.purchase(_store, Product.Shampoo, 15);
    expect(success).toBe(false);
    expect(_store.getInventory(Product.Shampoo)).toBe(10);
  });
});
!

원문 교정 원문 교정

노트에는 addInventory(Product.Shampoo, 5) 로 적혀 있지만, 그러면 두 테스트의 기대값(5 와 10)과 앞뒤가 맞지 않는다. 재고 10 으로 두어야 "5개 구매 성공 후 잔여 5", "15개 구매 실패 후 잔여 10" 이 성립한다. 아래 팩토리 메소드 예제도 같은 이유로 10 으로 맞췄다.

이 기법에는 두 가지 단점이 있다.

테스트 간의 높은 결합도는 안티 패턴이다

테스트를 수정해도 다른 테스트에 영향을 주어서는 안 된다. 이 지침을 따르려면 동일한 테스트 클래스 내에 공유 상태를 두지 말아야 한다.

customer.spec.ts 
// 첫 번째 테스트를 위해 이 한 줄만 바꿔도
_store.addInventory(Product.Shampoo, 10);

// 두 번째 테스트의 기대값까지 함께 깨진다
_store.addInventory(Product.Shampoo, 20);

테스트 가독성을 떨어뜨리는 생성자 사용

준비 과정의 일부를 위로 옮기면 테스트 본문만 봐서는 전체 그림을 볼 수 없다. 무엇이 준비됐는지 확인하려면 파일 위쪽의 beforeEach 로 눈을 옮겨야 한다.

더 나은 테스트 픽스처 재사용법

테스트 클래스에 비공개 팩토리 메소드를 두면 된다. 공통 초기화 코드를 팩토리 메소드로 추출하면 테스트 코드를 짧게 유지하면서 동시에 진행 상황에 대한 전체 맥락도 지킬 수 있다.

customer.spec.ts 개선 
describe("CustomerTests", () => {
  const createStoreWithInventory = (product: Product, quantity: number) => {
    const store = new Store();
    store.addInventory(product, quantity);
    return store;
  };

  const createCustomer = () => new Customer();

  it("purchase_succeeds_when_enough_inventory", () => {
    const store = createStoreWithInventory(Product.Shampoo, 10);
    const sut = createCustomer();

    const success = sut.purchase(store, Product.Shampoo, 5);

    expect(success).toBe(true);
    expect(store.getInventory(Product.Shampoo)).toBe(5);
  });

  it("purchase_fails_when_not_enough_inventory", () => {
    const store = createStoreWithInventory(Product.Shampoo, 10);
    const sut = createCustomer();

    const success = sut.purchase(store, Product.Shampoo, 15);

    expect(success).toBe(false);
    expect(store.getInventory(Product.Shampoo)).toBe(10);
  });
});

테스트 픽스처 재사용의 예외 사항

테스트 전부 또는 대부분에서 쓰이는 픽스처는 생성자 단계에서 인스턴스화해도 된다. 일반적으로 디비와 작동하는 통합 테스트가 여기 해당한다. 모든 테스트가 디비 연결을 필요로 하니, 한 번 초기화한 뒤 재사용하는 편이 합리적이다.

integration.spec.ts 예외 케이스 
let db: Database;

describe("SomeIntegrationTests", () => {
  beforeAll(async () => {
    db = new Database();
    await db.connect();
  });

  afterAll(async () => {
    await db.close();
  });

  beforeEach(async () => {
    await db.clear();
  });

  it("some_test", () => {
    // 실행
  });
});
i

이 예외의 조건 보강

연결 객체처럼 테스트가 그 상태를 바꾸지 않는 것만 이 예외에 해당한다. 데이터를 넣는 준비 작업까지 beforeEach 로 올리면 앞서 지적한 결합도 문제가 통합 테스트에서 똑같이 재현된다. 데이터 정리 방식은 10-3 테스트 데이터 생명주기 에서 자세히 다룬다.

정리

  • 픽스처 = 각 테스트 전에 알려진 고정 상태로 유지되는 SUT 의 인수.
  • beforeEach 공유는 테스트 간 결합도와 가독성 저하 두 문제를 낳는다.
  • 비공개 팩토리 메소드로 뽑으면 짧게 유지하면서도 맥락이 남는다.
  • 디비 연결처럼 상태를 바꾸지 않는 공용 자원만 예외로 둔다.
3-4

단위 테스트 명명법

가장 유명한 명명 규칙이 가장 도움이 되지 않는 규칙이다.

핵심 [메서드]_[시나리오]_[결과] 형식은 동작이 아니라 구현 세부 사항에 집중하게 만든다. 쉬운 영어 구문이 훨씬 효과적이다.

테스트에 표현력 있는 이름을 붙이는 일은 생각보다 중요하다. 가장 널리 알려진 [테스트 대상 메서드]_[시나리오]_[예상 결과] 형태는 사실 가장 도움이 되지 않는 방법 중 하나다. 메서드 이름이 들어가는 순간, 테스트가 동작이 아니라 구현에 매이기 때문이다.

문제
describe("Sum_twoNumbers_ReturnSum", () => {
  // ...
});
개선
describe("sum_of_two_numbers", () => {
  // ...
});

간단한 문구로 쓰면 고객이나 도메인 전문가에게도 의미 있는 방식으로 시스템 동작을 설명할 수 있다. 물론 단위 테스트는 도메인 전문가가 아니라 개발자를 위해 개발자가 작성하는 것이다. 다만 그 개발자도 도메인 언어로 읽을 때 훨씬 빨리 이해한다.

단위 테스트 명명 지침

  • 엄격한 명명 규칙을 강제하지 않고 표현의 자유를 허용한다.
  • 비개발자에게 시나리오를 설명하듯 이름을 쓴다.
  • 단어는 밑줄로 구분한다. 특히 긴 이름에서 가독성이 크게 좋아진다.
  • 단위 테스트의 "단위" 는 동작의 단위지 클래스의 단위가 아니다.

예제 — 지침에 따른 테스트 이름 변경

delivery.spec.ts 출발점 
it("IsDeliveryValid_InvalidDate_ReturnsFalse", () => {
  const sut = new DeliveryService();
  const pastDate = new Date();
  pastDate.setDate(pastDate.getDate() - 1);
  const delivery = new Delivery(pastDate);

  const isValid = sut.isDeliveryValid(delivery);

  expect(isValid).toBe(false);
});
  1. Delivery_with_invalid_date_should_be_considered_invalid

    이제 개발자가 아닌 사람에게도 납득되고, 개발자도 더 쉽게 이해한다. SUT 의 메소드 이름 isDeliveryValid 가 테스트명에서 사라졌다.

  2. Delivery_with_past_date_should_be_considered_invalid

    "invalid date" 를 도메인 언어인 "past date" 로 바꿨다. 나아지긴 했지만 여전히 장황하다. considered 는 빼도 의미가 퇴색되지 않는다.

  3. Delivery_with_past_date_should_be_invalid

    should be 는 또 다른 안티패턴이다. 하나의 테스트는 동작 단위에 대한 단순하고 원자적인 사실이므로, 사실을 서술할 때 소망이나 욕구가 들어가면 안 된다.

  4. Delivery_with_past_date_is_invalid

    사실의 진술이 됐다. 마지막으로 기초 영문법을 지킨다.

  5. Delivery_with_a_past_date_is_invalid

    관사를 붙이니 문장으로 완벽하게 읽힌다. 최종 버전은 사실을 단도직입적으로 설명한다.

이 테스트가 설명하는 것은 앱 동작의 한 관점, 즉 배송 가능 여부를 결정하는 관점이다.

정리

  • [메서드]_[시나리오]_[결과] 는 구현에 테스트를 묶는다. 쓰지 않는다.
  • 비개발자에게 설명하듯, 밑줄로 단어를 나눠 쓴다.
  • should be 를 쓰지 않는다. 테스트는 소망이 아니라 사실의 진술이다.
  • 관사까지 챙기면 이름이 그대로 명세 문장이 된다.
3-5

매개변수화된 테스트 리팩토링하기

코드의 양과 가독성은 상충한다. 부정 케이스만 묶고 긍정 케이스는 뽑아낸다.

핵심 매개변수가 늘수록 그 테스트가 나타내는 사실이 흐려진다. 절충안은 가장 중요한 케이스를 별도 테스트로 도출하는 것이다.

테스트 하나로는 동작 단위를 완전히 설명하기에 부족한 경우가 많다. 동작 단위는 여러 구성 요소를 포함하고, 각 구성 요소는 자체 테스트로 캡처해야 한다.

flowchart TB
  APP["앱"] --> B1["동작 1"]
  APP --> B2["동작 2"]
  APP --> BN["동작 N"]
  B2 --> F1["사실 1"]
  B2 --> F2["사실 2"]
  B2 --> FN["사실 N"]
  F1 --- G["매개변수화된
테스트로 그룹화 가능"]
  F2 --- G
앱은 동작으로, 동작은 사실로 쪼개진다 — 각 사실을 테스트 하나로 표현하되, 서로 비슷한 사실끼리는 매개변수화된 테스트로 묶을 수 있다.

사실을 검증하기 위해서 여러 가지 항목 전달하기

가장 빠른 배송일이 오늘로부터 이틀 후가 되도록 작동하는 배송 기능이 있다고 하자. 테스트 하나로는 부족하다. 지난 날짜뿐 아니라 오늘, 내일, 그리고 이틀 후까지 확인해야 한다.

  • delivery_for_today_is_invalid
  • delivery_for_tomorrow_is_invalid
  • the_soonest_delivery_date_is_two_days_from_now

이런 경우 테스트 코드의 양을 줄이고자 하나로 묶는 것이 매개변수화된 테스트다.

delivery.spec.ts 
describe("DeliveryServiceTests", () => {
  it.each([
    [-1, false],
    [0, false],
    [1, false],
    [2, true],
  ])("can_detect_an_invalid_delivery_date", (daysFromNow, expected) => {
    const sut = new DeliveryService();
    const deliveryDate = new Date();
    deliveryDate.setDate(deliveryDate.getDate() + daysFromNow);
    const delivery = new Delivery(deliveryDate);

    const isValid = sut.isDeliveryValid(delivery);

    expect(isValid).toBe(expected);
  });
});

원문 교정 원문 교정

노트에는 네 케이스가 모두 false 로 적혀 있는데, 가장 빠른 배송일이 이틀 후라는 규칙상 [2, true] 여야 한다. 네 케이스가 전부 false 라면 "이틀 후는 유효하다" 는 핵심 사실이 아예 검증되지 않는다.

매개변수화된 테스트의 단점

테스트 코드 양을 크게 줄일 수 있지만 비용이 따른다. 테스트 메서드가 나타내는 사실을 파악하기 어려워지고, 매개변수가 많을수록 더 어려워진다.

절충안은 이렇다. 부정적인 케이스는 매개변수화해서 묶고, 긍정적인 케이스는 별도 테스트로 도출한 뒤 가장 중요한 부분을 잘 설명하는 이름을 붙인다.

delivery.spec.ts 절충안 
describe("DeliveryServiceTests", () => {
  it.each([[-1], [0], [1]])(
    "can_detect_an_invalid_delivery_date",
    (daysFromNow) => {
      // ...
    }
  );

  it("the_soonest_delivery_date_is_two_days_from_now", () => {
    // ...
  });
});
상황선택
입력 매개변수만으로 테스트 케이스를 판단할 수 있다긍정 / 부정 케이스를 하나의 메소드로 둔다
그렇지 않다긍정적인 케이스를 별도 테스트로 도출한다

i

읽히는 케이스 이름 붙이기 보강

Jest 의 it.each 는 테스트 이름에 %s / %i / %p 같은 포맷 자리와, 객체 배열을 쓸 때의 $변수명 치환을 지원한다. it.each([{ daysFromNow: 2, expected: true }])("delivery in $daysFromNow days -> $expected", ...) 처럼 쓰면 실패했을 때 어느 케이스가 깨졌는지가 리포트에 그대로 찍힌다.

정리

  • 동작 하나는 여러 사실로 쪼개지고, 비슷한 사실끼리 묶는 것이 매개변수화된 테스트다.
  • 코드의 양과 가독성은 상충한다. 매개변수가 늘수록 사실이 흐려진다.
  • 부정 케이스는 묶고, 가장 중요한 긍정 케이스는 이름 있는 테스트로 도출한다.
  • 동작이 복잡하면 매개변수화를 포기하는 것도 선택지다.
