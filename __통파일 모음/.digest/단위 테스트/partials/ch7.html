7-1

리팩터링할 코드 식별하기

복잡도 및 도메인 유의성 × 협력자 수. 두 축이면 충분하다.

핵심 코드가 더 중요해지거나 복잡해질수록 협력자는 더 적어야 한다. 그 반대 지점에 있는 코드가 리팩터링 대상이다.

코드의 4가지 유형

모든 제품 코드는 두 개의 차원으로 분류된다.

복잡도(code complexity)

코드 내 의사 결정(분기) 지점의 수로 정의한다. 순환 복잡도는 1 + 분기점 수 로 계산한다.

도메인 유의성(domain significance)

코드가 프로젝트의 문제 도메인에 대해 얼마나 의미 있는지를 나타낸다. 도메인 계층의 코드는 최종 유저의 목표와 직접 연결되므로 도메인 유의성이 높다. 복잡하거나 도메인 유의성이 높은 코드가 단위 테스트에서 제일 이롭다.

협력자 수

여기서 협력자란 가변 의존성이거나 프로세스 외부 의존성, 또는 둘 다인 것을 뜻한다. 유지 보수성 지표가 테스트 크기에 따라 달라지므로, 협력자가 많은 코드는 테스트 비용이 많이 든다.

협력자의 유형도 중요하다. 도메인 모델이라면 프로세스 외부 협력자를 사용해서는 안 된다. 또 리팩터링 내성을 지키려면 목을 아주 신중하게 써야 하는데, 목은 앱 경계를 넘는 상호작용에만 쓸 수 있다. 따라서 프로세스 외부 의존성과의 통신은 모두 도메인 계층 바깥의 클래스에 위임하는 것이 좋다.

4가지 코드 유형

지나치게 복잡한 코드는 도메인 모델과 컨트롤러로 쪼개야 한다 — 왼쪽 위는 테스트하고, 오른쪽 아래는 통합 테스트로 얇게 덮고, 왼쪽 아래는 그냥 둔다.

지나치게 복잡한 코드를 피하고 도메인 모델과 알고리즘만 테스트하는 것이, 가치 있고 유지 보수하기 쉬운 테스트 스위트로 가는 길이다. 오른쪽 위에 있는 코드는 도메인 모델 및 알고리즘과 컨트롤러로 나눠서 리팩터링한다.

험블 객체 패턴으로 복잡한 코드 분할

지나치게 복잡한 코드를 쪼개는 도구가 험블 객체(Humble Object) 패턴이다.

테스트하기 어려운 의존성의 예로는 비동기 또는 멀티스레드 실행, 유저 인터페이스, 프로세스 외부 의존성과의 통신 등이 있다. 로직이 이런 의존성과 한 덩어리로 붙어 있으면 로직만 따로 테스트할 방법이 없다.

  H["험블 객체
얇은 래퍼"] --> DEP["테스트하기 어려운 의존성"]
  H --> LOGIC["로직"]

테스트 가능한 부분을 먼저 추출하고, 남은 껍데기를 험블 래퍼로 만든다 — 래퍼는 어려운 의존성과 추출된 구성 요소를 붙이기만 할 뿐 자체 로직이 거의 없어서 테스트할 필요가 없다.

정리

  • 두 축은 복잡도 및 도메인 유의성과 협력자 수다.
  • 도메인 모델 및 알고리즘 = 테스트 최고 가치. 간단한 코드 = 테스트 불필요.
  • 지나치게 복잡한 코드를 도메인 모델과 컨트롤러로 쪼갠다.
  • 험블 객체는 로직을 뽑아낸 뒤 남는 로직 없는 얇은 래퍼다.
7-2

가치 있는 단위 테스트를 위한 리팩터링하기

CRM 하나를 네 단계에 걸쳐 사분면 위에서 이동시킨다.

핵심 앱 서비스의 역할은 오케스트레이션뿐이다. 복잡도나 도메인 유의성이 있는 로직은 하나도 남아 있으면 안 된다.

고객 관리 시스템 소개

CRM 이고, 모든 사용자가 디비에 저장된다. 현재 지원하는 유스케이스는 유저 이메일 변경 하나뿐이다.

user.ts 지나치게 복잡한 코드 
enum UserType {
  CUSTOMER,
  EMPLOYEE,
}

class User {
  userId: number;
  email: string;
  type: UserType;

  changeEmail(userId: number, newEmail: string) {
    // 디비에서 사용자 검색
    const data = Database.getUserById(userId);
    this.userId = userId;
    this.email = data[1];
    this.type = data[2];

    if (this.email === newEmail) {
      return;
    }

    // 조직의 도메인명과 사원 수 검색
    const companyData = Database.getCompany();
    const companyDomainName = companyData[0];
    const numberOfEmployees = companyData[1];

    // 새 이메일의 도메인 이름에 따라 사용자 유형을 설정
    const emailDomain = newEmail.split("@")[1];
    const isEmailCorporate = emailDomain === companyDomainName;
    const newType = isEmailCorporate ? UserType.EMPLOYEE : UserType.CUSTOMER;

    // 필요한 경우 조직원 수를 업데이트
    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      Database.saveCompany(numberOfEmployees + delta);
    }

    this.email = newEmail;
    this.type = newType;

    Database.saveUser(this);
    MessageBus.sendEmailChangedMessage(userId, newEmail);
  }
}
  • 암시적 의존성 — Database, MessageBus
  • 명시적 의존성 — userId, newEmail
!

Active Record 패턴

도메인 클래스가 스스로 디비를 검색하고 다시 저장하는 패턴을 Active Record 라고 한다. 초기에는 편하지만 확장이 어렵다. 비즈니스 로직과 프로세스 외부 의존성과의 통신 사이에 분리가 없기 때문이다.

1단계 — 암시적 의존성을 명시적으로 만들기

테스트 용이성을 개선하는 일반적인 첫 수는 암시적 의존성을 명시적으로 바꾸는 것이다. Database 와 MessageBus 를 인터페이스로 뽑아 User 의 생성자에 주입하고, 테스트에서는 목으로 처리한다.

하지만 이것으로는 부족하다. 도메인 모델이 여전히 프로세스 외부 의존성과 직접 통신하기 때문이다.

2단계 — 앱 서비스 계층 도입

도메인 모델이 외부 시스템과 직접 통신하는 문제를 극복하려면 그 책임을 다른 클래스, 즉 험블 컨트롤러로 옮겨야 한다.

user-controller.ts 아직 문제가 남았다 
class UserController {
  private readonly database: Database = new Database();
  private readonly messageBus: MessageBus = new MessageBus();

  changeEmail(userId: number, newEmail: string) {
    const data = this.database.getUserById(userId);
    const email = data[1];
    const type = data[2];
    const user = new User(userId, email, type);

    const companyData = this.database.getCompany();
    const companyDomainName = companyData[0];
    const numberOfEmployees = companyData[1];

    const newNumberOfEmployees = user.changeEmail(
      newEmail,
      companyDomainName,
      numberOfEmployees
    );

    this.database.saveCompany(newNumberOfEmployees);
    this.database.saveUser(user);
    this.messageBus.sendEmailChangedMessage(userId, newEmail);
  }
}
남아 있는 문제점
  1. 외부 의존성을 주입받지 않고 직접 인스턴스화한다

    이 클래스를 위해 작성할 통합 테스트에서 문제가 된다.

  2. 디비에서 받은 원시 데이터를 User 인스턴스로 재구성한다

    이는 복잡한 로직이며 앱 서비스에 속하면 안 된다. 앱 서비스의 역할은 오케스트레이션뿐이다.

  3. 회사 데이터를 다루는 책임이 잘못 놓여 있다

    회사 직원 수는 특정 사용자와 아무 관련이 없다.

  4. 새 이메일이 기존과 다른지 확인하지 않는다

    같은 이메일이어도 무조건 저장하고 메세지를 발행한다.

user.ts 협력자가 사라진 User 
class User {
  userId: number;
  email: string;
  type: UserType;

  changeEmail(
    newEmail: string,
    companyDomainName: string,
    numberOfEmployees: number
  ) {
    if (this.email === newEmail) {
      return numberOfEmployees;
    }

    const emailDomain = newEmail.split("@")[1];
    const isEmailCorporate = emailDomain === companyDomainName;
    const newType = isEmailCorporate ? UserType.EMPLOYEE : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      numberOfEmployees = numberOfEmployees + delta;
    }

    this.email = newEmail;
    this.type = newType;

    return numberOfEmployees;
  }
}

이제 User 는 프로세스 외부 의존성과 통신할 필요가 없다. 프로세스 내부에도 외부에도 협력자가 하나도 없다.

2단계 이후 — 아직 경계에 걸쳐 있다 — User 는 도메인 모델 쪽으로 왔지만, UserController 는 여전히 "지나치게 복잡한 코드" 와 "컨트롤러" 사이에 걸쳐 있다.

3단계 — 앱 서비스 복잡도 낮추기

컨트롤러에 남아 있는 "원시 데이터 → 인스턴스 재구성" 로직을 뽑아내야 컨트롤러 사분면에 확실히 자리 잡는다. 보통은 ORM 이 이 일을 해주고, 불가능하다면 팩토리를 만들면 된다.

user-factory.ts 
export const createUser = (data: unknown[]) => {
  const id = data[0] as number;
  const email = data[1] as string;
  const type = data[2] as UserType;

  return new User(id, email, type);
};

4단계 — 새로운 Company 클래스

User.changeEmail 이 업데이트된 직원 수를 반환한다는 점이 이상하다. 이는 책임을 잘못 뒀다는 신호이자, 추상화가 빠져 있다는 신호다. 회사 관련 로직과 데이터를 함께 묶는 도메인 클래스 Company 를 만들어야 한다.

company.ts 빠져 있던 추상화 
class Company {
  constructor(
    public domainName: string,
    public numberOfEmployees: number
  ) {}

  changeNumberOfEmployees(delta: number) {
    if (this.numberOfEmployees + delta < 0) {
      throw new Error("Invalid number of employees");
    }

    this.numberOfEmployees += delta;
  }

  isEmailCorporate(email: string) {
    const emailDomain = email.split("@")[1];
    return emailDomain === this.domainName;
  }
}
user-controller.ts 리팩터링 후 
class UserController {
  constructor(
    private readonly database: Database,
    private readonly messageBus: MessageBus
  ) {}

  changeEmail(userId: number, newEmail: string) {
    const userData = this.database.getUserById(userId);
    const user = createUser(userData);

    const companyData = this.database.getCompany();
    const company = createCompany(companyData);

    user.changeEmail(newEmail, company);

    this.database.saveCompany(company);
    this.database.saveUser(user);
    this.messageBus.sendEmailChangedMessage(userId, newEmail);
  }
}
user.ts 리팩터링 후 
class User {
  constructor(
    public userId: number,
    public email: string,
    public type: UserType
  ) {}

  changeEmail(newEmail: string, company: Company) {
    if (this.email === newEmail) {
      return;
    }

    const newType = company.isEmailCorporate(newEmail)
      ? UserType.EMPLOYEE
      : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      company.changeNumberOfEmployees(delta); // 책임을 Company 에 위임
    }

    this.email = newEmail;
    this.type = newType;
  }
}

이제 User 는 회사 데이터를 직접 다루지 않고 Company 인스턴스에 책임을 위임한다. 협력자가 하나 생긴 만큼 테스트가 조금 어려워졌지만, 아주 조금이다. Company 는 프로세스 외부 의존성이 아닌 도메인 협력자이기 때문이다.

4단계 이후 — 모두 제자리를 찾았다 — 도메인 클래스와 팩토리는 왼쪽 위로, UserController 는 컨트롤러 사분면 안쪽으로 완전히 들어왔다.

정리

  • Active Record 는 비즈니스 로직과 외부 통신을 분리하지 않아 확장되지 않는다.
  • 1단계 암시적 → 명시적 의존성, 2단계 앱 서비스(험블 컨트롤러) 도입.
  • 3단계 팩토리로 재구성 로직 추출, 4단계 빠진 추상화(Company) 도입.
  • "이상한 반환값" 은 대개 책임이 잘못 놓였거나 추상화가 빠졌다는 신호다.
7-3

최적의 단위 테스트 커버리지 분석

네 사분면 중 왼쪽 위만 단위 테스트로 촘촘히 덮는다.

핵심 도메인 유의성이 있는 전제 조건은 테스트한다. 도메인 유의성이 없는 전제 조건은 테스트하지 않는다.

도메인 계층과 유틸리티 코드 테스트

사분면의 좌측 상단을 대상으로 하는 테스트가 비용 편익 측면에서 최상의 결과를 준다. 복잡도나 도메인 유의성이 높아 회귀 방지가 뛰어나고, 협력자가 거의 없어 유지비가 가장 낮다.

user.spec.ts 
it("change_email_from_non_corporate_to_corporate", () => {
  const company = new Company("mycorp.com", 1);
  const sut = new User(1, "user@gmail.com", UserType.CUSTOMER);

  sut.changeEmail("new@mycorp.com", company);

  expect(company.numberOfEmployees).toBe(2);
  expect(sut.email).toBe("new@mycorp.com");
  expect(sut.type).toBe(UserType.EMPLOYEE);
});
커버리지를 만족하기 위한 추가 테스트
  • change_email_from_corporate_to_non_corporate
  • change_email_without_changing_user_type
  • change_email_to_the_same_one

이 테스트들의 코드는 훨씬 짧을 것이고, 매개변수화된 테스트로 여러 케이스를 묶을 수도 있다.

company.spec.ts 
it.each([
  ["mycorp.com", "email@mycorp.com", true],
  ["mycorp.com", "email@gmail.com", false],
])(
  "differentiates_a_corporate_email_from_non_corporate",
  (domain, email, expectedResult) => {
    const sut = new Company(domain, 0);

    const isEmailCorporate = sut.isEmailCorporate(email);

    expect(isEmailCorporate).toBe(expectedResult);
  }
);

나머지 세 사분면에 대한 코드 테스트

팩토리 클래스 같은 코드는 너무 간단해서 굳이 테스트를 만들 필요가 없다. 만들어봐야 회귀 방지가 떨어지는 테스트만 늘어난다.

전제 조건을 테스트해야 되는가

일반적인 지침은 도메인 유의성이 있는 모든 전제 조건을 테스트하라는 것이다. Company 에서 직원 수가 음수가 되면 안 된다는 요구 사항이 여기 해당한다. 반대로 도메인 유의성이 없는 방어적 검사는 테스트할 필요가 없다.

company.spec.ts 도메인 유의성이 있는 전제 조건 
it("number_of_employees_cannot_become_negative", () => {
  const sut = new Company("mycorp.com", 0);

  expect(() => sut.changeNumberOfEmployees(-1)).toThrow(
    "Invalid number of employees"
  );
});

정리

  • 사분면 좌측 상단이 비용 편익 최고 지점이다.
  • 팩토리 같은 간단한 코드는 테스트하지 않는다.
  • 도메인 유의성이 있는 전제 조건만 테스트한다.
7-4

컨트롤러에서 조건부 로직 처리

테스트 유의성 / 컨트롤러 단순성 / 성능. 셋 중 둘만 가질 수 있다.

핵심 성능은 협상 불가, 도메인 모델에 외부 의존성 주입도 불가. 그러니 컨트롤러의 복잡도만 완화하는 쪽으로 간다.

비즈니스와 오케스트레이션 분리

비즈니스 연산은 아래 순서일 때 가장 깔끔하다.

  1. 저장소에서 데이터 검색
  2. 비즈니스 로직 실행
  3. 데이터를 다시 저장소에 저장

여기서 개발자는 세 가지 특성의 균형을 맞춰야 한다.

CanExecute / Execute 패턴

컨트롤러 복잡도를 완화하는 첫 번째 방법이자, 비즈니스 로직이 도메인 모델에서 컨트롤러로 유출되는 것을 방지하는 방법이다.

예를 들어 "이메일은 사용자가 확인(confirm)하기 전까지만 변경할 수 있다" 는 규칙이 추가됐다고 하자.

예제 1 — User 에 새로운 속성 추가

user.ts 
class User {
  // 기존 속성...
  isEmailConfirmed: boolean;

  changeEmail(newEmail: string, company: Company): string | null {
    if (this.isEmailConfirmed) {
      return "이메일이 이미 확인되었습니다.";
    }
    // ...
    return null;
  }
}
user-controller.ts 의사 결정을 도메인에 남김 
class UserController {
  changeEmail(userId: number, newEmail: string) {
    const userData = this.database.getUserById(userId);
    const user = createUser(userData);

    const companyData = this.database.getCompany();
    const company = createCompany(companyData);

    // 의사 결정은 도메인 모델이 한다
    const error = user.changeEmail(newEmail, company);
    if (error !== null) {
      return error;
    }

    this.database.saveCompany(company);
    this.database.saveUser(user);
    this.messageBus.sendEmailChangedMessage(userId, newEmail);

    return "OK";
  }
}

원문 교정 원문 교정

노트에는 if (!error) { return error; } 로 적혀 있는데, 이러면 에러가 없을 때 조기 반환하게 되어 정상 흐름이 통째로 건너뛰어진다. 조건은 if (error !== null) 이어야 한다.

단점은 성능이다. user.changeEmail() 을 호출하려면 확인 여부와 무관하게 항상 Company 를 디비에서 가져와야 한다.

예제 2 — 컨트롤러에서 isEmailConfirmed 확인

user-controller.ts 캡슐화 저하 
class UserController {
  changeEmail(userId: number, newEmail: string) {
    const userData = this.database.getUserById(userId);
    const user = createUser(userData);

    // 의사 결정 로직이 컨트롤러로 이동했다

노트에는 changeEmail 안에서 if (!this.changeEmail()) 를 호출하는데, 자기 자신을 다시 부르는 무한 재귀가 된다. 호출해야 하는 것은 this.canChangeEmail() 이다.

이제 도메인 계층이 모든 결정을 통합한다. 컨트롤러는 canChangeEmail() 을 먼저 물어보기만 하면 되고, 의사 결정 지점은 사라진다.

도메인 이벤트를 사용해 도메인 모델 변경 사항 추적

도메인 모델을 현재 상태로 만든 단계를 되짚기 어려울 때가 많다. 하지만 앱에서 정확히 무슨 일이 일어났는지 외부 시스템에 알려야 하므로 그 단계를 아는 것이 중요할 수 있다.

이럴 때는 도메인 모델에서 중요한 변경 사항을 추적하고, 비즈니스 연산이 끝난 뒤 그것을 프로세스 외부 의존성 호출로 변환하면 된다. 도메인 이벤트가 그 도구다.

기존 로직의 문제는 이메일이 기존과 동일해도 디비에 다시 저장하고 이벤트를 발행한다는 점이었다.

user.ts 도메인 이벤트 도입 
/**
 * 도메인 이벤트는 항상 "이미 발생한 일" 을 나타낸다.
 * 그러므로 항상 과거 시제로 명명한다.
 */
class EmailChangedEvent {
  constructor(
    public readonly userId: number,
    public readonly newEmail: string
  ) {}
}

class User {
  userId: number;
  email: string;
  type: UserType;
  emailChangedEvents: EmailChangedEvent[] = [];
  private isEmailConfirmed: boolean;

  private canChangeEmail() {
    return !this.isEmailConfirmed;
  }

  changeEmail(newEmail: string, company: Company) {
    if (!this.canChangeEmail()) {
      throw new Error("이메일이 이미 확인되었습니다.");
    }

    if (this.email === newEmail) {
      return;
    }

    const newType = company.isEmailCorporate(newEmail)
      ? UserType.EMPLOYEE
      : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      company.changeNumberOfEmployees(delta);
    }

    this.email = newEmail;
    this.type = newType;
    this.emailChangedEvents.push(new EmailChangedEvent(this.userId, newEmail));
  }
}
user-controller.ts 이벤트를 메세지로 변환 
class UserController {
  changeEmail(userId: number, newEmail: string) {
    const userData = this.database.getUserById(userId);
    const user = createUser(userData);

    if (!user.canChangeEmail()) {
      return "ERROR_EMAIL_CONFIRMED";
    }

    const companyData = this.database.getCompany();
    const company = createCompany(companyData);

    user.changeEmail(newEmail, company);

    this.database.saveCompany(company);
    this.database.saveUser(user);
    for (const event of user.emailChangedEvents) {
      this.messageBus.sendEmailChangedMessage(event.userId, event.newEmail);
    }

    return "OK";
  }
}

디비 저장은 왜 그대로 두는가

디비의 최종 상태만 올바르면 호출 횟수는 크게 중요하지 않다. ORM 을 쓰면 변경점이 없을 때 실제 쿼리가 나가지도 않는다. 반면 메세지 버스는 비관리 의존성이라 발행 여부 자체가 외부에서 보이는 동작이므로, 이벤트로 정확히 통제해야 한다. 필요하다면 별도의 이벤트 디스패처를 두어도 된다.

테스트 리팩터링
user.spec.ts 목 없이 이벤트를 검증 
it("changing_email_from_corporate_to_non_corporate", () => {
  const company = new Company("mycorp.com", 1);
  const sut = new User(1, "user@mycorp.com", UserType.EMPLOYEE, false);

  sut.changeEmail("new@gmail.com", company);

  expect(company.numberOfEmployees).toBe(0);
  expect(sut.email).toBe("new@gmail.com");
  expect(sut.type).toBe(UserType.CUSTOMER);
  expect(sut.emailChangedEvents).toEqual([
    new EmailChangedEvent(1, "new@gmail.com"),
  ]);
});

도메인 이벤트는 컨트롤러에서 의사 결정 책임을 제거하고 그 책임을 도메인 모델로 되돌린다. 덕분에 외부 시스템과의 통신도 단위 테스트에서 간결하게 검증할 수 있다.

정리

  • 테스트 유의성 / 컨트롤러 단순성 / 성능 중 둘만 가질 수 있다.
  • 성능과 도메인 모델의 순수성을 지키고, 컨트롤러 복잡도만 완화한다.
  • CanExecute / Execute 로 의사 결정을 도메인에 남긴다.
  • 도메인 이벤트는 "무슨 일이 있었는가" 를 값으로 만들어 컨트롤러가 실어 나르게 한다.
