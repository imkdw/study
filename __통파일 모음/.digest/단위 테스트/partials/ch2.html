2-1

단위 테스트의 정의

작게, 빠르게, 격리해서. 마지막 단어 하나에서 두 분파가 갈린다.

핵심 "격리" 를 SUT 를 협력자에게서 떼는 것으로 읽으면 런던파, 단위 테스트끼리 떼는 것으로 읽으면 고전파다.

정의

단위 테스트는 아래 세 가지를 만족하는 자동화된 테스트다.

  1. 작은 코드 조각을 검증한다

    흔히 "단위" 라고 부르는 그것.

  2. 빠르게 수행한다

    테스트 스위트 전체의 실행 시간이 충분히 짧으면 충분히 빠른 것이다.

  3. 격리된 방식으로 처리한다

    바로 여기서 고전파와 런던파가 갈린다.

첫 번째와 두 번째는 대체로 이견이 없다. 세 번째 속성만이 논쟁거리다.

고전파 예제

준비 / 실행 / 검증 세 구절로 나뉜다.

  • 준비 — 의존성과 테스트 대상 시스템을 모두 준비한다. 아래 예제에서는 고객(Customer)이 SUT, 상점(Store)이 협력자다.
  • 실행 — 검증하고자 하는 동작을 수행한다.
  • 검증 — 그 동작이 예상 결과로 이어지는지 확인한다.
2-1.spec.ts 고전파 
const Product = {
  Shampoo: "Shampoo",
  Book: "Book",
};

it("purchase_succeeds_when_enough_inventory", () => {
  // 준비
  const store = new Store();
  store.addInventory(Product.Shampoo, 10);
  const customer = new Customer();

  // 실행
  const success = customer.purchase(store, Product.Shampoo, 5);

  // 검증
  expect(success).toBe(true);
  expect(store.getInventory(Product.Shampoo)).toBe(5);
});

it("purchase_fails_when_not_enough_inventory", () => {
  // 준비
  const store = new Store();
  store.addInventory(Product.Shampoo, 10);
  const customer = new Customer();

  // 실행
  const success = customer.purchase(store, Product.Shampoo, 15);

  // 검증
  expect(success).toBe(false);
  expect(store.getInventory(Product.Shampoo)).toBe(10);
});

여기서 Customer 가 올바르게 작동해도 Store 가 올바르지 않으면 검증에 실패한다. 두 클래스는 서로 격리돼 있지 않다.

런던파 예제

실제 Store 인스턴스를 만들지 않고 jest.fn() 으로 대체한다. 대체한 목의 메소드 반환값을 직접 지정하고, toHaveBeenCalledWith 로 호출 여부와 전달된 인자까지 검증할 수 있다.

2-1.spec.ts 런던파 
it("purchase_succeeds_when_enough_inventory", () => {
  // 준비
  const storeMock = {
    hasEnoughInventory: jest.fn().mockReturnValue(true),
    removeInventory: jest.fn(),
  };
  const customer = new Customer();

  // 실행
  const success = customer.purchase(storeMock, Product.Shampoo, 5);

  // 검증
  expect(success).toBe(true);
  expect(storeMock.hasEnoughInventory).toHaveBeenCalledWith(Product.Shampoo, 5);
});

it("purchase_fails_when_not_enough_inventory", () => {
  // 준비
  const storeMock = {
    hasEnoughInventory: jest.fn().mockReturnValue(false),
    removeInventory: jest.fn(),
  };
  const customer = new Customer();

  // 실행
  const success = customer.purchase(storeMock, Product.Shampoo, 15);

  // 검증
  expect(success).toBe(false);
  expect(storeMock.removeInventory).toHaveBeenCalledTimes(0);
});

격리 문제에 대한 런던파의 접근

런던파에서 격리란 테스트 대상 시스템을 협력자에게서 떼어내는 것이다. 하나의 클래스가 다른 클래스에 의존하면, 그 모든 의존성을 테스트 대역(test double) 으로 대체한다.

flowchart LR
  SUT["테스트 대상 시스템"] --> D1["의존성 1"]
  SUT --> D2["의존성 2"]
  D1 -.->|"교체"| M1["테스트 대역 1"]
  D2 -.->|"교체"| M2["테스트 대역 2"]
  SUT2["테스트 대상 시스템"] --> M1
  SUT2 --> M2
모든 협력자를 대역으로 바꾸면 해당 시스템 검증에만 집중할 수 있다 — 클래스마다 자기 테스트를 갖게 되고, 그 테스트는 오직 자기 클래스의 결함에만 반응한다.

의존성을 가진 코드베이스를 테스트 대역 없이 테스트하는 건 힘들다. 방법이 없진 않지만 결국 의존성 그래프를 직접 전부 만들어줘야 하는데, 이는 매우 고된 작업이다.

격리 문제에 대한 고전파의 접근

런던 스타일은 대역으로 코드 조각을 분리해 격리 요구 사항에 다가간다. 모든 클래스를 격리해야 한다면 테스트 대상 코드 조각은 당연히 단일 클래스나 그 클래스의 메소드여야 한다.

고전파는 다르다. 여러 클래스를 동시에 테스트해도 되고, 테스트 대역은 테스트 간 공유 상태를 일으키는 의존성에만 쓴다.

flowchart LR
  T["단위 테스트"] --> SUT["테스트 대상 시스템"]
  SUT -->|"공유 의존성 / 교체"| DB[("DB")]
  SUT -->|"공유 의존성 / 교체"| FS["파일 시스템"]
  SUT -->|"비공개 의존성 / 유지"| C["다른 클래스"]
고전파가 대역으로 바꾸는 것은 공유 의존성뿐이다 — 다른 클래스는 실제 인스턴스를 그대로 쓴다. 격리해야 하는 대상은 협력자가 아니라 단위 테스트끼리다.

공유 / 비공개 / 프로세스 외부 의존성

공유 의존성(Shared Dependency)

테스트 간에 공유되어 서로의 결과에 영향을 미칠 수 있는 수단을 제공하는 의존성이다. 전형적인 예가 정적 가변 필드(static mutable field) 다. 이 필드의 변경 사항은 동일한 프로세스에서 실행되는 모든 단위 테스트에서 보인다. 데이터베이스도 대표적인 공유 의존성이다.

비공개 의존성(Private Dependency)

공유하지 않는 의존성이다.

프로세스 외부 의존성(Out-of-Process Dependency)

앱 실행 시 프로세스 외부에서 실행되는 의존성으로, 아직 메모리에 없는 데이터에 대한 프록시다. 디비는 프로세스 외부이면서 공유 의존성이다. 다만 테스트마다 도커 컨테이너로 디비를 띄운다면 프로세스 외부이지만 공유 의존성은 아니다. 그런 환경에서는 한 테스트의 데이터 변경이 다른 테스트 결과에 영향을 주지 않기 때문이다.

i

공유는 "테스트 대상 사이" 가 아니라 "테스트 사이" 다

공유 의존성은 테스트 대상 클래스들끼리 공유하는 것이 아니라 단위 테스트끼리 공유하는 것이다. 싱글턴 의존성이라도 각 테스트에서 새 인스턴스를 만들 수 있기만 하면 공유되지 않는다.

공유 / 휘발성 의존성

휘발성 의존성(volatile dependency)은 아래 중 하나에 해당한다.

  • 개발자 머신에 기본으로 설치돼 있지 않아, 런타임 환경의 설정과 구성을 별도로 요구한다. 디비와 API 서비스가 대표적이다.
  • 비결정적 동작(nondeterministic behavior) 을 포함한다. 난수를 생성하거나 현재 날짜를 반환하는 클래스처럼, 호출마다 다른 결과를 주는 것들이다.

공유 의존성을 가진 테스트는 단위 테스트 영역에서 통합 테스트 영역으로 넘어간다. 반대로 말하면, 단위 테스트는 클래스 하나에 국한될 필요가 없다. 공유 의존성이 없는 한 여러 클래스를 묶어서 단위 테스트할 수 있다.

정리

  • 단위 테스트 = 작은 코드 조각 + 빠른 수행 + 격리. 세 번째에서 분파가 갈린다.
  • 런던파는 SUT 를 협력자로부터, 고전파는 단위 테스트끼리 격리한다.
  • 공유 의존성은 테스트끼리 서로 영향을 주는 통로다. 정적 가변 필드, 디비가 대표적이다.
  • 공유 의존성이 없다면 여러 클래스를 묶어도 여전히 단위 테스트다.
2-2

단위 테스트의 런던파와 고전파

무엇을 교체할 것인가에 대한 두 답. 협력자 전부인가, 공유 의존성만인가.

핵심 런던파는 불변 의존성을 제외한 모든 것을, 고전파는 공유 의존성만 대역으로 바꾼다.

두 분파는 세 가지 주제에서 의견이 갈린다.

분류격리 주체단위의 크기테스트 대역 사용 대상
런던파단위단일 클래스불변 의존성 외 모든 의존성
고전파단위 테스트단일 클래스 또는 클래스 세트공유 의존성

고전파와 런던파가 의존성을 다루는 방법

절대 변하지 않는 객체, 즉 불변 객체는 교체하지 않아도 된다. ENUM 처럼 값이 고정된 것들이 그렇다. 불변 객체의 주요 특징은 각각의 정체성이 없고 내용에 의해서만 식별된다는 점이다.

비공개 의존성은 변경 가능할 수도 있고 불변일 수도 있다. 디비 의존성은 공유 의존성이며, 그 내부 상태는 모든 자동화된 테스트가 함께 본다.

flowchart TB
  D["의존성"] --> S["공유 의존성
고전파에서 교체"]
  D --> P["비공개 의존성"]
  P --> M["변경 가능 의존성"]
  P --> V["값 객체
교체 대상 아님"]
  S --> COL["협력자
런던파에서 교체"]
  M --> COL
협력자 = 공유 의존성 + 변경 가능 의존성 — 고전파는 왼쪽 가지만 교체하고, 런던파는 값 객체를 뺀 나머지 전부를 교체한다.
!

원문 교정 원문 교정

노트에는 "Store 인스턴스는 변경 가능한 비공개 의존성이고, Product 인스턴스는 변경 가능한 비공개 의존성" 이라고 적혀 있지만, Product 는 불변 값 객체다. ENUM 처럼 정체성이 없고 내용으로만 식별되므로 교체 대상이 아니다.

협력자 vs 의존성

협력자(collaborator) 는 공유하거나 변경이 가능한 의존성이다.

  • 디비는 공유 의존성이므로 디비 접근 권한을 제공하는 클래스는 협력자다.
  • 앞 예제의 Store 도 시간에 따라 상태가 변할 수 있으므로 협력자다.
  • Product 와 숫자 5 는 의존성이지만 협력자가 아니다. 값 또는 값 객체로 분류된다.

프로세스 외부 의존성이 공유 의존성이 되려면, 그것이 단위 테스트끼리 서로 통신할 수 있는 수단을 제공해야 한다.

예시 — 읽기 전용 API 는 공유 의존성이 아니다

조직이 판매하는 모든 제품 카탈로그를 반환하는 API 가 있다고 하자. 이 API 가 카탈로그를 변경하는 기능을 노출하지 않는 한 공유 의존성이 아니다. 휘발성이고 앱 경계를 벗어나는 것은 사실이지만, 테스트가 반환 데이터에 영향을 미칠 수 없으므로 공유가 아니다.

두 축은 서로 독립이다 — 싱글턴은 공유이지만 프로세스 내부, 읽기 전용 API 는 프로세스 외부이지만 공유가 아니다. 디비만 교집합에 놓인다.

다만 대부분의 경우 테스트 속도를 위해 이런 외부 API 도 대역으로 교체한다. 충분히 빠르고 연결이 안정적이라면 실제로 써도 괜찮다.

정리

  • 런던파는 값 객체를 뺀 모든 의존성을, 고전파는 공유 의존성만 교체한다.
  • 협력자 = 공유 의존성 ∪ 변경 가능 의존성. 값 객체는 협력자가 아니다.
  • 프로세스 외부라고 다 공유는 아니다. 테스트끼리 통신할 수단을 제공해야 공유다.
2-3

고전파와 런던파의 비교

런던파의 세 가지 이점은 모두 그럴듯하지만, 각각 반론이 있다.

핵심 테스트는 코드의 단위가 아니라 동작의 단위를 검증해야 한다. 이 한 문장이 런던파의 세 이점을 모두 되받는다.

목을 사용하는 런던파 테스트는 고전파 테스트보다 불안정한 경향이 있다. 그럼에도 런던파가 내세우는 이점은 분명하다.

런던파 접근 방식의 이점

  • 테스트가 세밀해서 한 번에 한 클래스만 확인한다. 즉 입자성이 좋다.
  • 의존성 그래프가 커져도 테스트가 쉽다. 모든 협력자가 대역으로 대체되므로 그래프를 걱정할 필요가 없다.
  • 테스트 대상 클래스 외에 의심할 여지가 없어서 어떤 기능이 실패했는지 확실히 파악할 수 있다.

한 번에 한 클래스만 테스트하기

OOP 개발자는 클래스를 코드베이스의 기초에 있는 원자 빌딩 블록으로 본다. 그래서 자연스럽게 클래스를 테스트에서 검증할 원자 단위로 취급하는데, 여기에 오해의 소지가 있다.

✓

단위는 클래스가 아니라 동작이다

테스트는 코드의 단위를 검증해서는 안 되고 동작의 단위, 즉 문제 영역에서 의미가 있는 것을 검증해야 한다. 테스트는 해결하려는 문제에 대한 이야기를 들려줘야 하며, 그 이야기는 일반 사람들에게도 응집도 있고 의미 있어야 한다.

상호 연결된 클래스의 큰 그래프를 단위 테스트하기

런던파처럼 협력자를 목으로 대체하면 복잡한 의존성 그래프를 가진 동작도 쉽게 테스트할 수 있다. 하지만 순서가 뒤집혔다. 협력자를 모킹하기 전에 그런 의존성 그래프를 갖지 않는 데 먼저 집중해야 한다. 일반적으로 그래프가 커진 것은 코드 설계 문제의 결과다.

버그 위치 정확히 찾아내기

런던파에서는 시스템에 버그가 생기면 그 버그를 포함한 SUT 의 테스트만 실패한다. 반대로 고전파에서는 오작동하는 클래스를 참조하는 클라이언트의 테스트까지 함께 실패하며, 하나의 버그가 전체 시스템에 걸쳐 테스트 실패의 파급 효과를 일으킨다.

다만 이는 생각만큼 큰 문제가 아니다. CI 과정에서 테스트를 정기적으로 실행하면 마지막으로 성공한 커밋과의 차이로 버그 위치를 금방 좁힐 수 있고, 오히려 실패한 테스트 전체가 그 버그의 영향 범위를 보여준다는 점에서 가치가 있다.

고전파와 런던파의 다른 점

나머지 차이는 TDD 를 통한 시스템 설계 방식과 과도한 명세에 있다.

런던 스타일 — 하향식 TDD

시스템에 대한 기대치를 설정하는 상위 레벨 테스트부터 시작한다. 모든 클래스를 구현할 때까지 클래스 그래프를 아래로 다져 나간다. SUT 의 모든 협력자를 차단하므로 그 협력자의 구현을 나중으로 미룰 수 있다.

고전 스타일 — 상향식 TDD

테스트에서 의존성에 대한 실제 객체를 다뤄야 하므로 같은 지침을 두지 않는다. 도메인 모델에서 시작해 최종 사용자가 소프트웨어를 사용할 수 있을 때까지 그 위에 계층을 더한다.

정리

  • 런던파의 세밀한 입자성은 동작이 아니라 코드를 단위로 삼는 오해에서 온다.
  • 큰 의존성 그래프는 모킹으로 덮을 게 아니라 설계로 줄여야 한다.
  • 고전파의 파급 실패는 CI 를 정기 실행하면 해결되고, 오히려 영향 범위를 보여준다.
  • 런던파는 하향식 TDD, 고전파는 상향식 TDD 로 이어진다.
2-4

두 분파의 통합 테스트

단위 테스트의 세 조건 중 하나라도 못 맞추면 그것은 통합 테스트다.

핵심 통합 테스트는 단위 테스트의 특성을 만족하지 못하는 모든 테스트다. E2E 는 그중 의존성을 가장 많이 포함하는 부분집합이다.

런던파는 실제 협력자 객체를 사용하는 모든 테스트를 통합 테스트로 간주한다. 그러면 고전파의 테스트 상당수가 런던파 기준으로는 통합 테스트가 된다.

통합 테스트의 일부인 E2E 테스트

통합 테스트는 공유 / 프로세스 외부 의존성뿐 아니라 조직 내 다른 팀이 개발한 코드까지 통합해서 검증한다. 그 안에 E2E(end-to-end) 테스트 개념이 포함되며, E2E 는 일반적으로 더 많은 의존성을 포함한다.

세 테스트는 동심원 관계다 — 단위 테스트는 프로세스 안쪽만, 통합 테스트는 앱이 통제하는 디비까지, E2E 는 결제 게이트웨이 같은 외부 앱까지 포함한다.

E2E 는 모든 외부 앱을 포함해 시스템을 최종 사용자의 관점에서 검증한다. 일반적으로 디비나 파일 시스템은 실제로 포함하지만, 결제 게이트웨이처럼 외부에 의존하는 것은 대역으로 대체한다.

!

E2E 는 언제 돌리나

유지 보수 측면에서 가장 비싸다. 모든 단위 테스트와 통합 테스트를 통과한 뒤 빌드 프로세스 후반에 실행하는 것이 좋다.

정리

  • 단위 테스트의 세 조건을 하나라도 못 맞추면 통합 테스트다.
  • E2E 는 통합 테스트의 부분집합이며 의존성을 가장 많이 포함한다.
  • E2E 에서도 결제 같은 외부 시스템은 보통 대역으로 대체한다.
  • 가장 비싸므로 빌드 후반에 배치한다.
