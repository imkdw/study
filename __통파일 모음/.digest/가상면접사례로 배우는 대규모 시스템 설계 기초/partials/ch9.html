9-1

웹 크롤러의 쓰임새

시드 URL에서 출발해 링크를 따라 웹을 넓혀 나가는 프로그램.

핵심 크롤러는 결국 거대한 그래프 순회다. 노드는 페이지, 간선은 링크이며, 이 관점이 뒤의 모든 설계 결정을 설명한다.
  • 검색 엔진에서 널리 쓰는 기술로, 웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 것이 주 목적이다.
  • 콘텐츠는 웹페이지부터 PDF, 이미지, 비디오까지 다양하다.
  • 단순히 웹페이지 몇 개에서 시작해 그 안에 있는 링크를 따라 콘텐츠를 수집해 나간다.
flowchart LR
  S["시드 URL"] --> P1["페이지 A"]
  P1 --> P2["페이지 B"]
  P1 --> P3["페이지 C"]
  P2 --> P4["페이지 D"]
  P3 --> P4
  P4 -.->|"이미 방문"| P1
웹은 트리가 아니라 그래프다 — 점선처럼 되돌아오는 간선이 있기 때문에 "이미 방문한 URL" 판별이 필수 컴포넌트가 된다.

크롤링의 쓰임새

검색 엔진 인덱싱 (Search Engine Indexing)
  • 웹 페이지를 모아 검색 엔진을 위한 로컬 인덱스를 만든다.
  • Googlebot이 구글 검색 엔진이 쓰는 웹 크롤러다.
웹 아카이빙 (Web Archiving)
  • 나중에 쓸 목적으로 장기 보관하기 위해 웹에서 정보를 모으는 행위다.
  • 대표적으로 미국 국회도서관의 웹 아카이브가 있다.
웹 마이닝 (Web Mining)
  • 인터넷에서 유용한 지식을 도출해 낸다.
  • 금융 기업들은 크롤러로 주주총회 자료, 연차보고서 등을 모아 기업의 핵심 사업 방향을 알아내기도 한다.
웹 모니터링 (Web Monitoring)
  • 인터넷에서 저작권이나 상표권이 침해되는 사례를 모니터링한다.
  • 디지마크(Digimarc)사는 웹 크롤러로 해적판 저작물을 찾아 보고해 준다.

크롤러의 규모

  • 데이터 규모에 따라 난이도가 크게 달라진다.
  • 간단한 것은 한 시간이면 끝나지만, 큰 것은 전문 개발팀이 필요하기도 하다.

정리

  • 크롤링은 시드 URL에서 시작하는 그래프 순회다.
  • 쓰임새는 검색 인덱싱 / 아카이빙 / 마이닝 / 모니터링.
  • 웹이 그래프라는 사실에서 중복 방문 판별이라는 요구사항이 나온다.
9-2

크롤러의 규모와 개략적 설계안

컴포넌트 아홉 개가 하나의 순환 고리를 이룬다.

핵심 크롤러 아키텍처의 특징은 끝이 없는 루프라는 점이다. URL 추출기가 뽑은 URL이 다시 미수집 URL 저장소로 돌아가면서 고리가 닫힌다.

크롤러의 규모

  • 매달 10억 개의 웹 페이지를 다운로드한다.
  • QPS = 10억 ÷ 30일 ÷ 24시간 ÷ 3600초 ≈ 초당 400개의 페이지
  • 최대 QPS = 2 × QPS = 800개
  • 웹 페이지 평균 크기를 500KB로 가정
  • 10억 페이지 × 500KB = 500TB/월, 5년이면 30PB의 공간이 필요하다

개략적 설계안

flowchart TB
  SEED["시작 URL 집합"] --> FRONTIER[["미수집 URL 저장소"]]
  FRONTIER --> DL["HTML 다운로더"]
  DNS["도메인 이름 변환기"] --> DL
  DL --> PARSER["콘텐츠 파서"]
  PARSER --> DUP{"이미 본 콘텐츠인가?"}
  DUP -->|"중복"| DROP["폐기"]
  DUP -->|"신규"| STORE[("콘텐츠 저장소")]
  STORE --> EXT["URL 추출기"]
  EXT --> FILTER["URL 필터"]
  FILTER --> SEEN{"이미 방문한 URL인가?"}
  SEEN -->|"방문함"| DROP
  SEEN -->|"신규"| USTORE[("URL 저장소")]
  USTORE --> FRONTIER
이 고리가 닫히는 지점이 크롤러의 심장 — URL 저장소에서 미수집 URL 저장소로 되돌아가는 화살표가 크롤링을 무한히 이어 가게 한다.
시작 URL 집합
  • 크롤링을 시작하는 출발점이다.
  • 어떤 대학 사이트에서 찾아 나갈 수 있는 모든 페이지를 크롤링하려면 그 대학의 도메인을 시드로 쓰는 것이 가장 직관적이다.
  • 가능하면 크롤러가 탐색을 많이 할 수 있는 도메인을 고르는 것이 좋다.
  • 일반적으로 전체 URL 공간을 작은 부분집합으로 나누는 전략을 쓴다 — 쇼핑, 스포츠, 건강 등.
HTML 다운로더
  • 웹 페이지를 다운로드하는 컴포넌트다.
  • 다운로드할 페이지의 URL은 미수집 URL 저장소가 제공한다.
도메인 이름 변환기
  • URL을 IP 주소로 변환하는 컴포넌트다.
콘텐츠 파서
  • 다운로드한 웹 페이지의 파싱과 검증을 담당한다.
  • 크롤링 서버 내부에 두면 자원만 낭비하므로 외부 컴포넌트로 분리한다.
중복 콘텐츠 여부
  • 중복 콘텐츠 감별용 자료구조를 도입해 중복을 줄이고 처리 시간을 아낀다.
  • 일반적인 문자열 비교는 데이터가 많을수록 느려지는데, 해시값을 비교하면 훨씬 빠르다.
URL 추출기
  • HTML 페이지를 파싱해 그 안의 URL을 골라내는 역할을 맡는다.
page.html
<body>
  <a href="http://www.naver.com">Naver</a>
  <a href="http://www.daum.net">Daum</a>
</body>
추출 결과 → 해시값
// 링크 목록
["http://www.naver.com", "http://www.daum.net"]

// 링크 목록의 해시값 — 비교는 이 값으로 한다
["0x1f0a0d", "0x1f0a0e"]
URL 필터
  • 특정 콘텐츠 타입이나 파일 확장자를 갖는 URL, 접속 시 오류가 나는 URL, 접근 제외 목록에 포함된 URL을 크롤링 대상에서 제외한다.
이미 방문한 URL인가
  • 이미 방문한 URL을 제외해 서버 부하를 줄이고 시스템이 무한 루프에 빠지는 것을 막는다.
  • 자료구조로는 블룸 필터나 해시 테이블이 많이 쓰인다.
URL 저장소
  • 이미 방문한 URL을 보관하는 장소다.
i

여기서도 블룸 필터 보강

수십억 개의 URL을 해시 테이블로 들고 있으려면 메모리가 감당이 안 된다. 블룸 필터는 훨씬 적은 메모리로 "확실히 안 봤음 / 아마 봤음"을 답한다. 거짓 양성이 생기면 안 본 페이지를 건너뛰는 손해가 있을 뿐 중복 방문이라는 사고는 나지 않으므로, 이 용도에 안전하게 맞는다. 6장 카산드라 읽기 경로에서와 같은 성질을 활용하는 것이다.

정리

  • 월 10억 페이지 = 초당 400개, 5년 30PB.
  • 아홉 개 컴포넌트가 URL 저장소를 통해 순환 고리를 이룬다.
  • 중복 판별은 해시값 비교, 방문 여부 판별은 블룸 필터가 표준.
9-3

상세 설계

예의 / 우선순위 / 신선도. 미수집 URL 저장소가 이 셋을 전부 떠맡는다.

핵심 미수집 URL 저장소는 단순한 큐가 아니다. "누구에게 / 어떤 순서로 / 얼마나 자주" 요청할지를 결정하는 정책 엔진이다.

DFS vs BFS

  • 웹의 구조는 유향 그래프와 같다. 페이지가 노드, 링크가 간선이다.
  • DFS는 좋은 선택이 아닐 가능성이 높다. 그래프가 크면 어느 정도로 깊이 들어갈지 가늠하기 어렵다.
  • 보통 BFS로 탐색하며, 이는 큐를 쓰는 알고리즘이다. 우선순위 없이 모든 페이지를 공평하게 대우한다.
  • 하지만 정답은 없으며, 페이지 순위 / 트래픽 양 / 업데이트 빈도 등 여러 척도로 우선순위를 구별할 필요가 있다.

예의 없는(impolite) 크롤러

  • 한 페이지에 나오는 링크의 상당수는 같은 서버로 되돌아간다.
  • 이 상태로 병렬 처리를 하면 크롤링 대상 서버가 엄청난 트래픽을 받게 된다.
  • 이를 예의 없는 크롤러라고 부른다.
flowchart LR
  T1["작업 스레드 1"] --> H["wikipedia.org"]
  T2["작업 스레드 2"] --> H
  T3["작업 스레드 3"] --> H
  T4["작업 스레드 4"] --> H
  T5["작업 스레드 5"] --> H
  H --> DOWN["대상 서버 마비"]
순진한 병렬화는 DoS와 구분되지 않는다 — 페이지 안의 링크가 대부분 같은 호스트를 가리키므로, 스레드를 늘릴수록 한 서버만 두들기게 된다.

미수집 URL 저장소

  • 다운로드할 URL을 저장하는 저장소다.
  • 잘 구현하면 예의(politeness)를 갖춘 크롤러, 그리고 URL 사이의 우선순위와 신선도(freshness)를 구별하는 크롤러를 만들 수 있다.

예의 (politeness)

  • 수집 대상 URL에 짧은 시간 안에 너무 많은 요청을 보내는 것을 막아야 한다.
  • 이는 무례한(impolite) 행위이며, 방어 장치가 없는 사이트는 마비될 수도 있다.
  • 지켜야 할 원칙은 동일 웹사이트에는 한 번에 한 페이지만 요청하기다.
  • 웹사이트의 호스트명과 다운로드를 수행하는 작업 스레드 사이의 관계를 유지하면 된다.

예의를 갖춘 크롤러 설계

flowchart TB
  IN["URL 유입"] --> QR["큐 라우터"]
  MT[("매핑 테이블
호스트 → 큐")] <--> QR
  QR --> B1[["큐 b1 (호스트 A 전용)"]]
  QR --> B2[["큐 b2 (호스트 B 전용)"]]
  QR --> BN[["큐 bn (호스트 N 전용)"]]
  B1 --> QS["큐 선택기"]
  B2 --> QS
  BN --> QS
  QS -->|"큐 하나당 스레드 하나"| W1["작업 스레드 1"]
  QS --> W2["작업 스레드 2"]
  QS --> WN["작업 스레드 n"]
호스트 하나에 큐 하나, 큐 하나에 스레드 하나 — 이 1:1:1 사슬이 "같은 사이트에 동시에 하나만"이라는 원칙을 구조적으로 보장한다.
큐 라우터 (Queue Router)
  • 같은 호스트에 속한 URL이 항상 같은 큐로 가도록 보장한다.
매핑 테이블 (Mapping Table)
  • 호스트 이름과 큐 사이의 관계를 보관하는 테이블이다.
FIFO 큐 (b1 ~ bn)
  • 같은 호스트에 속한 URL은 언제나 같은 큐에 보관된다.
큐 선택기 (Queue Selector)
  • 큐들을 순회하면서 URL을 꺼내, 그 큐에 지정된 작업 스레드에 전달한다.
작업 스레드 (Worker Thread)
  • 전달된 URL을 다운로드한다.
  • 전달된 URL은 순차적으로 처리되며, 작업 사이에 일정한 지연 시간을 둘 수 있다.

우선순위 정하기

  • 유용성에 따라 URL의 우선순위를 나눌 때는 페이지랭크, 트래픽 양, 갱신 빈도 등 다양한 척도를 쓸 수 있다.
  • 순위결정장치(prioritizer)가 URL의 우선순위를 정하는 컴포넌트다.
flowchart TB
  IN["URL 유입"] --> PR["순위결정장치 (prioritizer)
페이지랭크 / 트래픽 / 갱신빈도"]
  PR -->|"높은 우선순위"| F1[["큐 f1"]]
  PR --> F2[["큐 f2"]]
  PR -->|"낮은 우선순위"| FN[["큐 fn"]]
  F1 --> QS["큐 선택기
순위 높은 큐에서 더 자주 꺼냄"]
  F2 --> QS
  FN --> QS
  QS --> BACK["예의 큐 계층 (b1 ~ bn) 으로 전달"]
전면 큐가 순서를 정하고 후면 큐로 넘긴다 — 여기서 나온 URL이 앞 그림의 큐 라우터로 들어가 호스트별로 다시 나뉜다. 두 계층이 직렬로 겹쳐지는 구조다.
순위 결정 장치
  • URL을 입력받아 우선순위를 계산한다.
큐 (f1 ~ fn)
  • 우선순위별로 큐가 하나씩 할당된다.
  • 우선순위가 높으면 선택될 확률도 올라간다.
큐 선택기
  • 임의의 큐에서 처리할 URL을 꺼내는 역할을 담당한다.
  • 순위가 높은 큐에서 더 자주 꺼내도록 프로그래밍되어 있다.
i

두 계층이 위아래로 겹쳐진다 보강

우선순위 큐(전면 큐, f1~fn)와 예의 큐(후면 큐, b1~bn)는 서로를 대체하는 것이 아니라 직렬로 연결된다. 위쪽에서 "무엇을 먼저 볼까"를 정하고, 아래쪽에서 "누구를 배려하며 볼까"를 정한다. 관심사가 다르므로 계층이 나뉜 것이다.

신선도 (freshness)

  • 이미 다운로드한 URL이라도 웹의 특성상 계속 변경되므로 재수집할 필요가 있다.
  • 모든 URL을 재수집하는 것은 많은 시간과 자원이 드는 일이다.
  • 웹 페이지 변경 이력을 활용하거나, 우선순위를 통해 중요한 페이지를 더 자주 수집하는 방법이 있다.

미수집 URL 저장소를 위한 지속성 저장장치

  • 검색 엔진용 크롤러가 다뤄야 하는 URL의 수는 수억, 수십억 개에 이른다.
  • 전부 메모리에 두자니 용량이 부족하고, 디스크에 두자니 병목이 생긴다.
  • 좋은 방법은 메모리에 버퍼를 두고 주기적으로 디스크에 기록하는 절충이다.

HTML 다운로더

  • HTTP 프로토콜로 웹 페이지를 내려받는다.
로봇 제외 프로토콜 (Robots Exclusion Protocol)
  • robots.txt는 웹사이트가 크롤러와 소통하는 표준적 방법이다.
  • 이 파일에 크롤러가 수집해도 되는 페이지가 나열되므로, 항상 이 파일을 먼저 확인해야 한다.
robots.txt
User-agent: *
Disallow: /creatorhub/*
Disallow: /rss/people/*/reviews
...
i

robots.txt도 캐싱한다 보강

페이지를 받을 때마다 robots.txt를 다시 내려받으면 그 자체가 무례한 행위가 된다. 실무에서는 호스트별로 파싱 결과를 캐시하고 주기적으로 갱신한다.

HTML 다운로더의 성능 최적화

분산 크롤링
  • 성능을 위해 크롤링 작업을 여러 서버에 분산한다.
  • 각 서버는 여러 스레드로 다운로드를 처리한다.
도메인 이름 변환 결과 캐시
  • DNS 요청은 동기 방식으로 작동해, 응답을 받을 때까지 다음 작업을 진행할 수 없다.
  • 일반적으로 DNS 요청 처리에는 10ms ~ 200ms가 소요된다.
  • 조회 결과를 캐시하고 배치로 주기적으로 갱신하면 성능을 크게 높일 수 있다.
지역성
  • 크롤링 서버를 지역별로 분산 배치한다.
  • 크롤링 서버와 대상 URL의 서버가 가까울수록 다운로드 시간이 줄어든다.
  • 지역성 최적화는 크롤 서버뿐 아니라 캐시, 큐 등 대부분의 컴포넌트에 적용할 수 있다.
짧은 타임아웃
  • 어떤 웹 서버는 응답이 매우 느리거나 아예 응답하지 않는다.
  • 최대 대기 시간을 미리 정해 두고, 그 시간이 지나면 다음 대상으로 넘어간다.

안정성

안정 해시 (consistent hashing)
  • 다운로더 서버들에 부하를 분산할 때 적용할 수 있다.
  • 다운로더 서버를 쉽게 추가/삭제할 수 있게 된다. (5장 참조)
크롤링 상태 및 수집 데이터의 저장
  • 장애가 나도 쉽게 복구할 수 있도록 결과를 디스크에 기록하는 것이 좋다.
  • 저장된 데이터를 로딩하면 중단된 크롤링을 쉽게 재시작할 수 있다.
예외 처리
  • 에러는 불가피할 뿐 아니라 흔하게 벌어진다.
  • 예외가 발생해도 전체 시스템이 중단되지 않고 우아하게 이어 갈 수 있어야 한다.
데이터 검증
  • 시스템 오류를 방지하기 위한 중요한 수단이다.

확장성

  • 설계 시에는 새로운 형태의 콘텐츠를 쉽게 지원할 수 있게 신경 써야 한다.
  • PNG 다운로더, 웹 모니터 같은 모듈을 플러그인처럼 끼워 넣을 수 있는 구조로 만든다.
flowchart LR
  DL["HTML 다운로더"] --> PARSER["콘텐츠 파서"]
  PARSER --> PLUG{"플러그인 지점"}
  PLUG --> P1["PNG 다운로더"]
  PLUG --> P2["웹 모니터"]
  PLUG --> P3["신규 콘텐츠 모듈"]
확장 지점을 미리 하나 뚫어 둔다 — 새 콘텐츠 타입이 생겨도 파이프라인 전체를 다시 손대지 않아도 된다.

문제 있는 콘텐츠 감지 및 회피

중복 콘텐츠
  • 웹의 30% 가량은 중복된 콘텐츠다.
  • 해시나 체크섬으로 쉽게 탐지할 수 있다.
거미 덫 (Spider Trap)
  • 크롤러를 무한 루프에 빠뜨리도록 설계한 웹 페이지다. 예: example.com/foo/bar/foo/bar/foo/bar…
  • 덫이 설치된 사이트인지 알아내는 것은 어렵지 않다. 기이할 정도로 많은 페이지를 가진 것이 일반적이기 때문이다.
  • 다만 이를 자동 탐지하는 알고리즘을 만드는 것은 매우 까다롭다.
  • 수작업으로 처리한다면, 덫을 확인한 뒤 해당 사이트를 크롤 대상에서 제외하거나 URL 필터 목록에 넣는다.
데이터 노이즈
  • 전혀 가치 없는 콘텐츠도 존재한다.
  • 광고, 스크립트 코드, 스팸 URL 같은 것이 여기 해당한다.
  • 가능하면 이런 콘텐츠는 제외하는 것이 좋다.
!

URL 길이 제한이 가장 싼 방어책 보강

거미 덫을 완벽히 탐지하는 알고리즘은 어렵지만, URL 길이나 경로 깊이에 상한을 두는 것만으로도 대부분의 덫에서 빠져나올 수 있다. 정교한 판별보다 단순한 상한이 실무에서 먼저 쓰이는 이유다.

정리

  • 탐색은 BFS가 기본이되, 우선순위 척도를 얹는다.
  • 예의 = 호스트 하나당 큐 하나당 스레드 하나 + 요청 사이 지연.
  • 우선순위 큐(전면)와 예의 큐(후면)는 직렬로 겹쳐진다.
  • 성능은 분산 / DNS 캐시 / 지역성 / 짧은 타임아웃으로, 안정성은 안정 해시 / 상태 저장 / 예외 처리로.
  • 거미 덫은 경로 깊이/길이 상한으로 실용적으로 막는다.
