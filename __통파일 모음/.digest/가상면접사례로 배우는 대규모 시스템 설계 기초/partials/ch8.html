8-1

요구사항과 개략적 규모

기능은 두 줄로 끝난다. 어려움은 3,650억 개라는 숫자에서 온다.

핵심 URL 단축기는 기능이 단순한 대신 읽기가 쓰기의 10배이고 데이터가 계속 쌓이기만 하는 시스템이다. 이 두 성질이 설계를 결정한다.

기능

  • URL 단축 — 긴 URL을 짧게 줄여 준다.
  • URL 리디렉션 — 짧아진 URL을 원래 URL로 리디렉션한다.
  • 높은 가용성, 규모 확장성, 장애 감내가 요구된다.

규모 추정

  • 쓰기 — 매일 1억 개의 단축 URL 생성
  • 초당 쓰기 연산 = 1억 ÷ 24 ÷ 3600 ≈ 1,160
  • 읽기 연산 — 읽기:쓰기를 10:1로 가정하면 ≈ 11,600
  • 데이터 크기 — 10년 운영 시 1억 × 365 × 10 = 3,650억 개의 레코드
  • 축약 전 URL의 평균 길이는 100바이트
  • 저장 용량 = 3,650억 × 100바이트 = 36.5TB
i

읽기 10배가 뜻하는 것 보강

읽기가 압도적이므로 리디렉션 경로를 캐시로 덮는 것이 가장 큰 효과를 낸다. 1장의 주-부 다중화와 캐시 계층이 그대로 쓰이는 대목이다. 반대로 쓰기 경로(단축)는 초당 1,160회에 불과해 단일 DB로도 여유가 있다.

정리

  • 기능은 단축과 리디렉션 둘뿐.
  • 쓰기 1,160 QPS, 읽기 11,600 QPS, 10년 저장 36.5TB.
  • 읽기 편중이 심하므로 캐시가 핵심 최적화 지점이다.
8-2

API 설계와 301 vs 302

두 개의 엔드포인트, 그리고 상태 코드 하나가 만드는 사업적 차이.

핵심 301이냐 302냐는 성능 문제가 아니라 "클릭 데이터를 볼 것인가 말 것인가"의 문제다.

단축된 URL 생성

POST /api/v1/data/shorten
// Request Body
{ "url": "https://www.google.com" }

// Response Body
{ "shortened_url": "http://localhost:8080/abcde" }

단축된 URL 리디렉션

GET /abcde
HTTP/1.1 302 Found
Location: https://www.google.com

HTTP 301 vs HTTP 302

HTTP 301 Permanent Redirect
  • HTTP 요청 처리의 책임이 영구적으로 Location URL로 이전되었다는 응답이다.
  • 브라우저가 이 응답을 캐시하므로 이후에는 단축 URL 서버로 요청을 보내지 않는다.
  • 단순히 URL을 줄이는 것이 목적이라면 이쪽이 권장된다.
HTTP 302 Found
  • 요청이 일시적으로 Location URL로 처리되어야 한다는 응답이다.
  • 단축 URL로 접근할 때마다 반드시 단축 URL 서버를 거친다는 뜻이다.
  • 사용자 데이터 분석이 필요할 때 권장된다.

  participant T as 단축 URL 서버

  Note over B,T: 301 — 첫 요청만 서버를 거친다

301은 서버 부하를 줄이고, 302는 클릭 수를 지킨다 — 마케팅 링크라면 302, 단순 편의용이라면 301이다.

정리

  • API는 POST /shorten과 GET /{hash} 두 개면 충분하다.
  • 301 = 브라우저가 캐시 → 서버 부하 감소, 분석 불가.
  • 302 = 매번 서버 경유 → 분석 가능, 부하 증가.
8-3

단축 방법 설계

해시하고 자르느냐, 진법을 바꾸느냐. 두 길의 대가가 정반대다.

핵심 두 방식의 차이는 결국 충돌을 감수하고 길이를 고정할 것인가, ID 생성기를 도입하고 길이를 양보할 것인가다.
  • 중요한 것은 긴 URL을 고유한 해시값으로 대응시킬 해시 함수를 찾는 것이다.
  • 서로 다른 긴 URL은 서로 다른 해시값을 가져야 한다.
  • 계산된 해시값으로부터 원래의 긴 URL을 복원할 수 있어야 한다.

데이터 모델

  • 해시 테이블은 초기 전략으로는 괜찮지만 실제 시스템에 쓰기에는 곤란하다.
  • 메모리는 유한하고 비싸다.
  • 대안은 관계형 DB에 저장하는 것이다.

해시 함수

아래에서는 해시 함수가 계산해 내는 단축 URL 값을 hashValue라 부른다.

해시값 길이
  • hashValue는 [0-9, a-z, A-Z]로 구성되어 총 10 + 26 + 26 = 62개의 문자를 쓴다.
  • 길이를 정하려면 62n ≥ 3,650억을 만족하는 n을 구해야 한다.
  • n = 7이면 약 3.5조로 충분하므로 hashValue의 길이는 7로 정한다.
  • 해시값을 만드는 방법은 해시 후 충돌 해소와 base-62 변환 두 가지가 있다.
n62n3,650억 커버?
5약 9.16억✗
6약 568억✗
7약 3.52조✓
해시 후 충돌 해소
  • 일반적으로 알려진 CRC32, MD5 등을 쓴다.
  • 하지만 대부분의 방법은 지정한 hashValue 길이보다 큰 값을 반환한다.
  • 앞 7자만 잘라 쓸 수는 있으나 중복 위험이 생긴다.
  • 충돌이 있으면 다시 계산해야 하므로, 경우에 따라 DB 접근이 많아질 수 있다.

충돌마다 DB 조회가 한 번 더 붙는다 — 데이터가 쌓일수록 충돌 확률이 올라가므로, 이 루프의 기대 횟수도 함께 올라간다. 블룸 필터로 존재 여부를 먼저 걸러 완화할 수 있다.
base-62 변환
  • 진법 변환은 URL 단축키 구성에 흔히 쓰이는 방법이다.
  • 수의 표현 방식이 다른 두 시스템이 같은 수를 공유할 때 유용하다.
  • 62진법을 쓰는 이유는 hashValue에 쓸 수 있는 문자 개수가 62개이기 때문이다.
base-62 변환 예시
  • 62개 문자를 쓰므로 16진수처럼 숫자와 문자를 매핑한다 — 0 → 0, 10 → a, 35 → z, 61 → Z
  • ID 11157 를 62진법으로 바꾸면 2TX가 되고, 최종 URL은 https://tinyurl.com/2TX가 된다.
base62.ts
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

function toBase62(id: number): string {
  if (id === 0) return ALPHABET[0];
  let out = "";
  while (id > 0) {
    out = ALPHABET[id % 62] + out; // 나머지를 앞에 붙인다
    id = Math.floor(id / 62);
  }
  return out;
}

toBase62(11157); // "2TX"

!

추론 가능성은 실제 보안 문제다 보강

base-62는 ID를 그대로 인코딩하므로 2TX 다음이 2TY임을 쉽게 안다. 공격자가 순회하며 남의 단축 URL을 전부 수집할 수 있다는 뜻이다. 실무에서는 ID를 그대로 쓰지 않고 가역적인 난독화(예: Feistel 치환)를 거친 뒤 base-62로 인코딩하거나, 7장의 스노플레이크처럼 예측이 어려운 ID를 쓴다.

단축키 상세 프로세스

  1. 긴 URL을 입력받는다
  2. DB에 이미 있는지 확인한다

    있으면 기존 단축 URL을 그대로 돌려준다.

  3. 없으면 유일 ID를 발급받는다

    7장의 ID 생성기가 여기서 쓰인다.

  4. ID를 base-62로 변환한다
  5. ID / 단축 URL / 원본 URL을 저장하고 반환한다

추가 고려사항

  • 처리율 제한 장치(4장)로 IP 기반 남용을 막는다.
  • 데이터 분석 솔루션으로 클릭 데이터를 사업 가치로 연결한다.
  • 가용성 / 데이터 일관성 / 안정성 — 1장의 다중화와 샤딩이 그대로 적용된다.

정리

  • 627 ≈ 3.5조 > 3,650억 이므로 해시 길이는 7자.
  • 해시 후 충돌 해소 = 길이 고정 + 충돌 처리 비용.
  • base-62 = 충돌 없음 + ID 생성기 필요 + 추론 가능.
  • 리디렉션 경로는 캐시로 덮는 것이 최우선 최적화다.
