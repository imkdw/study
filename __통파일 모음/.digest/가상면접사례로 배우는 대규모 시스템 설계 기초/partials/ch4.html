4-1

처리율 제한 장치란

임계치를 넘은 요청을 잘라내는 장치. 방어이자 비용 통제 수단이다.

핵심 처리율 제한은 보안 장치처럼 보이지만, 실제로는 비용과 안정성을 동시에 지키는 운영 장치다.
  • 네트워크 시스템에서 클라이언트가 보내는 트래픽의 처리율을 제어하기 위한 장치다.
  • 정의된 임계치를 넘어가는 순간, 추가로 도달한 모든 요청은 처리가 중단된다.

예시

  • 사용자는 초당 2회 이상 새 글을 올릴 수 없다.
  • 같은 IP 주소는 하루에 10개 이상의 계정을 생성할 수 없다.
  • 같은 기기에서는 주당 5회 이상 리워드 요청이 불가능하다.

처리율 제한 장치의 장점

  • DoS(Denial of Service) 공격에 의한 자원 고갈을 방지할 수 있다.
  • 제3자 서비스 호출 비용을 줄이고, 모든 요청을 처리하기 위해 스케일 아웃된 서버 대수를 줄여 비용을 절감한다.
  • 봇에서 오는 트래픽이나 잘못된 이용 패턴이 유발한 트래픽을 막을 수 있다.

정리

  • 임계치를 넘은 요청을 버리는 것이 처리율 제한이다.
  • DoS 방어 / 비용 절감 / 봇 차단의 세 가지 효용이 있다.
4-2

문제 이해 및 설계 범위 확정

"정확히 제한하되, 가볍고, 분산 환경에서 동작하고, 자기가 죽어도 남을 죽이지 않을 것."

핵심 마지막 요구사항 — 제한 장치의 장애가 다른 서비스에 영향을 끼치면 안 된다 — 이 조건이 뒤의 모든 설계 결정을 좌우한다.
  • API를 위한 처리율 제한 장치를 설계한다.
  • 설정된 처리율을 초과하는 요청은 정확하게 제한해야 한다.
  • 가능한 한 적은 메모리를 사용해야 하고, 여러 서버나 프로세스에서 동일하게 동작해야 한다.
  • 요청이 블록되면 사용자에게 그 사실을 정확하게 전달해야 한다.
  • 제한 장치 자체의 장애가 다른 서비스에 영향을 끼쳐서는 안 된다.

정리

  • 정확성 / 저메모리 / 분산 지원 / 명확한 사용자 통지 / 장애 격리.
  • 다섯 요구사항 중 정확성과 저메모리는 서로 충돌하며, 알고리즘 선택이 그 저울이다.
4-3

처리율 제한 장치를 어디에 둘 것인가

클라이언트는 못 믿는다. 그래서 서버 쪽 미들웨어 아니면 API 게이트웨이다.

핵심 클라이언트 측 제한은 UX 개선용일 수는 있어도 방어용일 수는 없다. 클라이언트 코드는 언제든 변조된다.

클라이언트에 두기

  • 일반적으로 처리율 제한을 안정적으로 걸 수 있는 장소가 못 된다.
  • 클라이언트 요청은 너무 쉽게 변조된다.

서버에 두기

  • 클라이언트와 서버 중간에 처리율 제한 장치를 구성한다.
  • 미들웨어처럼 동작하며, 보통 API 게이트웨이라 부르는 곳에 구현된다.
  • 처리율에 걸리면 HTTP 429 Too Many Requests를 반환한다.
flowchart LR
  C["클라이언트"] -->|"요청"| M["처리율 제한 미들웨어
(API Gateway)"]
  M -->|"허용"| S["API 서버"]
  M -->|"초과 → 429"| C
제한 장치는 API 서버 앞에 선다 — 버려질 요청이 애플리케이션 코드에 도달하지 않는다는 것이 이 배치의 핵심이다.

고려 사항

  • 현재 사용 중인 프로그래밍 언어가 서버 측 구현을 지원하기에 충분한지 확인한다.
  • 사업에 필요한 올바른 알고리즘을 고른다.
  • 이미 MSA 구조에서 API 게이트웨이를 쓰고 있다면 거기에 포함시켜야 할 수도 있다.
  • 직접 만들면 오래 걸린다. 인력이 부족하다면 상용 서비스를 쓰는 편이 낫다.

정리

  • 클라이언트 측 제한은 방어 수단이 아니다.
  • 서버 측 미들웨어 또는 API 게이트웨이가 표준 위치다.
  • 초과 시 응답은 429 Too Many Requests.
4-4

처리율 제한 알고리즘

다섯 가지 알고리즘, 그리고 메모리와 정확도 사이의 저울.

핵심 다섯 알고리즘의 차이는 결국 "버스트를 허용하는가"와 "경계 부근에서 정확한가" 두 축으로 정리된다.

토큰 버킷

  • 처리율 제한에 폭넓게 이용된다.
  • 아마존과 스트라이프가 API 요청 통제에 사용 중인 방법이다.
동작 원리
  1. 버킷은 지정된 용량을 갖는 컨테이너다

    지정된 주기마다 새 토큰이 추가되고, 용량을 넘는 토큰은 버려진다.

  2. 요청 하나가 토큰 하나를 쓴다

    토큰이 충분하면 처리하고, 없으면 요청을 버린다.

flowchart LR
  R["토큰 공급기
주기마다 n개"] -->|"보충"| B["버킷 (용량 4)"]
  B -->|"넘치면 버림"| X["폐기"]
  Q["요청"] --> C{"토큰 있나?"}
  B --> C
  C -->|"있음 → 토큰 1 소모"| OK["처리"]
  C -->|"없음"| DROP["요청 폐기"]
버킷에 토큰이 쌓여 있으면 순간 폭주도 받아낸다 — 이 "미리 쌓아 두는" 성질이 버스트 허용의 정체다.
세부 사항
  • 인자는 버킷 크기(담을 수 있는 최대 토큰 수)와 토큰 공급률(주기마다 추가되는 토큰 수) 두 개다.
  • 버킷을 몇 개 둘지 —
    • API마다 버킷을 두는 방식. 사용자 기준으로 제한 기능이 3개면 사용자당 버킷 3개가 필요하다.
    • IP 기반이면 IP 주소마다 버킷이 필요하다.
    • 시스템 전체 처리율이 10,000개라면 크기 10,000짜리 버킷 하나를 전체가 공유한다.
장점 / 단점
  • 장점 — 구현이 쉽고 메모리 효율적이다. 짧은 시간에 집중되는 트래픽도 처리할 수 있다.
  • 단점 — 버킷 크기와 공급률 두 인자를 적절히 튜닝하기가 까다롭다.

누출 버킷 알고리즘

  • 토큰 버킷과 비슷하지만 요청 처리율이 고정이라는 점이 다르다.
  • 보통 FIFO 큐로 구현한다.
동작 원리
  • 요청이 도착하면 큐가 가득 찼는지 확인하고, 빈자리가 있으면 큐에 넣는다.
  • 큐가 가득 차 있으면 요청을 버린다.
  • 지정된 시간마다 큐에서 요청을 꺼내 처리한다.
  • Shopify가 이 알고리즘을 사용하고 있다.
flowchart LR
  Q1["요청 유입"] --> C{"큐가 찼나?"}
  C -->|"여유 있음"| FIFO[["FIFO 큐 (고정 크기)"]]
  C -->|"가득 참"| DROP["요청 폐기"]
  FIFO -->|"고정 처리율로 유출"| S["서버"]
출력이 항상 일정하다 — 뒷단 서버가 감당할 수 있는 속도를 보장하는 대신, 큐에 오래 앉아 있던 요청이 최신 요청보다 먼저 나간다.
세부 사항
  • 버킷 크기 — 큐에 담을 수 있는 총 작업 수.
  • 처리율 — 지정된 시간당 몇 개의 항목을 처리할지.
장점 / 단점
  • 장점 — 큐 크기가 제한되어 메모리 사용량이 효율적이다. 고정된 처리율이라 안정적인 출력이 필요한 경우 적합하다.
  • 단점 — 단시간에 트래픽이 몰리면 큐에 오래된 요청이 쌓이고 최신 요청은 버려진다. 두 인자 튜닝도 까다롭다.

고정 윈도 카운터 알고리즘

  • 타임라인을 고정된 윈도로 나누고, 윈도마다 카운터를 붙인다.
  • 요청이 접수되면 카운터가 1씩 증가한다.
  • 카운터가 임계치에 도달하면 새 윈도가 열릴 때까지 모든 요청이 버려진다.
고정 윈도의 구조적 결함 — 윈도 경계를 걸치는 1초를 잘라 보면 허용치의 두 배가 통과한다. 카운터는 잘못이 없고, 윈도를 자르는 방식이 문제다.
장점 / 단점
  • 장점 — 메모리 효율이 좋고 이해하기 쉽다. 윈도가 닫히는 시점에 카운터를 초기화하는 방식은 특정 트래픽 패턴 처리에 적합하다.
  • 단점 — 윈도 경계 부근에 트래픽이 몰리면 기대했던 것보다 더 많은 요청이 처리된다.

이동 윈도 로깅 알고리즘

  • 요청의 타임스탬프를 추적해 Redis의 sorted set 같은 곳에 보관한다.
  • 새 요청이 오면 만료된 타임스탬프를 제거한다.
  • 로그 크기가 허용치보다 작거나 같으면 요청을 전달하고, 아니면 거부한다.
예시 (허용치: 1분에 2개)
시각로그 상태크기결과
1:00:01비어 있음 → [1:00:01]1✓ 허용
1:00:30[1:00:01, 1:00:30]2✓ 허용
1:00:50[1:00:01, 1:00:30, 1:00:50]3✗ 거부 (타임스탬프는 남김)
1:01:40만료분 제거 후 [1:00:50, 1:01:40]2✓ 허용
!

거부된 요청도 로그에 남는다 원문 교정

노트의 마지막 줄은 1:01:40 시점에 "1:00:01, 1:00:30을 지우고 나면 2개"라고 적고 있는데, 이때 남는 것은 1:00:50과 1:01:40이다. 1:00:50 요청은 거부됐지만 타임스탬프는 로그에 그대로 남기 때문이다. 이 성질이 곧 아래 단점의 원인이다.

장점 / 단점
  • 장점 — 메커니즘이 아주 정교하다. 어느 순간의 윈도를 보더라도 허용 요청 수가 한도를 넘지 않는다.
  • 단점 — 거부된 요청의 타임스탬프까지 저장하므로 많은 메모리를 쓴다.

이동 윈도 카운터 알고리즘

  • 고정 윈도 카운터와 이동 윈도 로깅을 결합한 형태다.
  • 직전 윈도의 카운터를 겹치는 비율만큼 가중해서 더한다. 로그를 전부 저장하지 않으면서도 경계 문제를 완화한다.
i

다섯 알고리즘 한눈에 보강

알고리즘버스트 허용메모리경계 정확도
토큰 버킷✓적음양호

정리

  • 토큰 버킷 — 버스트를 허용하며 가장 널리 쓰인다.
  • 누출 버킷 — 출력이 고정. 뒷단 보호가 목적일 때.
  • 고정 윈도 — 가장 싸지만 경계에서 2배가 새어 나간다.
  • 이동 윈도 로깅 — 완벽하지만 메모리를 많이 먹는다.
  • 이동 윈도 카운터 — 둘의 절충안.
4-5

개략적인 아키텍처

카운터를 어디에 둘 것인가. 답은 디스크가 아니라 메모리다.

핵심 Redis를 고르는 이유는 단순히 빨라서가 아니라, INCR와 EXPIRE가 처리율 제한이 필요한 연산 그 자체이기 때문이다.
  • 기본 아이디어는 아주 단순하다. IP 기반이든 API 주소별이든, 카운터 값이 한도를 넘으면 추가 요청을 거부한다.

카운터를 어디에 저장할까

  • DB는 디스크 기반이라 느리므로 쓰지 않는다.
  • 일반적으로 Redis에 저장한다. 빠른 속도와 데이터 만료 시간을 지원하기 때문이다.
flowchart LR
  C["클라이언트"] --> M["처리율 제한 미들웨어"]
  M -->|"INCR key"| R[("Redis 카운터")]
  R -->|"현재 값"| M
  M -->|"한도 이하 → 통과"| S["API 서버"]
  M -->|"한도 초과 → 429"| C
카운터 조회와 증가가 한 번의 왕복으로 끝난다 — INCR는 값을 올리면서 결과를 돌려주므로 읽기와 쓰기를 나눌 필요가 없다.
i

Redis 명령 두 개면 충분하다 보강

redis-cli
INCR   rate:user123:1700000000   # 카운터 +1, 증가된 값을 그대로 반환
EXPIRE rate:user123:1700000000 1 # 윈도 끝나면 자동 소멸 → 청소 코드 불필요

키에 윈도 시각을 붙여 두면 윈도가 바뀔 때 새 키가 생기고, 옛 키는 TTL로 알아서 사라진다. 별도의 정리 작업이 필요 없다.

정리

  • 카운터는 디스크 기반 DB가 아니라 인메모리 저장소에 둔다.
  • Redis의 INCR + EXPIRE 조합이 사실상의 표준 구현이다.
4-6

상세 설계

규칙 파일, 응답 헤더, 그리고 분산 환경의 두 가지 함정.

핵심 미들웨어를 여러 대로 늘리는 순간 경쟁 조건과 동기화라는 새 문제가 생긴다. 이 둘을 어떻게 푸는지가 이 절의 알맹이다.

처리율 제한 규칙

  • 설정 파일은 보통 디스크에 저장된다.
ratelimit.yaml
domain: messaging
descriptors:
  - key: message_type
    value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 1000

처리율 한도 트래픽의 처리

  • 요청이 한도에 걸리면 HTTP 429를 반환한다.
  • 경우에 따라서는 제한에 걸린 요청을 나중에 처리하도록 큐에 보관하기도 한다.
처리율 제한 장치가 사용하는 HTTP 헤더
  • 클라이언트는 HTTP 헤더로 현재 요청이 제한에 걸렸는지 확인할 수 있다.
  • X-RateLimit-Remaining — 윈도 안에 남은 처리 가능 요청 수
  • X-RateLimit-Limit — 윈도당 전송할 수 있는 요청 수
  • Retry-After — 다음 요청까지 기다려야 하는 시간(초)

원문 교정 원문 교정

노트에 적힌 X-Ratelimit-Renaming은 X-RateLimit-Remaining의 오기다. 또한 X-Ratelimit-Retry-After라는 헤더는 존재하지 않으며, 재시도 대기 시간을 알리는 표준 헤더는 접두사 없는 Retry-After(RFC 9110)다. X-RateLimit-*계열은 표준이 아니라 널리 퍼진 관행이다. (근거: IETF draft-ietf-httpapi-ratelimit-headers)

↑

표준화가 진행 중이다 최신 반영

IETF httpapi 워킹그룹이 RateLimit과 RateLimit-Policy 두 필드로 정리한 Internet-Draft를 진행 중이다(아직 RFC는 아니다). 초기 드래프트에 있던 RateLimit-Limit / -Remaining / -Reset 세 이름이 사실상의 관행으로 굳어져 널리 쓰이고 있으니, 지금 새로 설계한다면 이 세 이름을 쓰되 향후 병합될 수 있음을 염두에 두면 된다.

상세 설계

  1. 규칙을 캐싱한다

    처리율 제한 규칙은 디스크에 보관하고, 작업 프로세스가 수시로 파일을 읽어 캐시에 올린다.

  2. 요청이 미들웨어에 도달한다

    클라이언트 요청은 API 서버보다 먼저 미들웨어에 닿는다.

  3. 두 곳에서 데이터를 읽는다

    미들웨어는 제한 규칙을 로컬 캐시에서 가져오고, 카운터 등 나머지 정보는 Redis에서 가져온다.

flowchart TB
  D[("규칙 파일 (디스크)")] -->|"주기적 로드"| WK["작업 프로세스"]
  WK --> RC["규칙 캐시 (로컬)"]
  C["클라이언트"] --> M["처리율 제한 미들웨어"]
  RC --> M
  M <-->|"카운터 조회 / 증가"| R[("Redis")]
  M -->|"통과"| API["API 서버"]
  M -->|"초과"| Q[["(선택) 지연 처리 큐"]]
규칙은 로컬 캐시, 카운터는 Redis — 규칙은 거의 안 바뀌므로 로컬에 두고, 카운터는 매 요청 바뀌므로 공유 저장소에 둔다.

분산 환경에서의 미들웨어

  • 여러 서버와 병렬 스레드를 지원하도록 확장하면 또 다른 문제가 생긴다.
  • 경쟁 조건과 동기화 문제를 풀어야 한다.
경쟁 조건 (Race Condition)
  • 여러 곳에서 동시에 Redis 카운터를 올리는 상황을 생각해 보자.
  • 값이 3일 때 두 요청이 각각 1을 더하면 5가 되어야 하는데 4가 될 수 있다.
  • 가장 널리 알려진 해결책은 락을 쓰는 것이며, 실무에서는 Lua 스크립트나 sorted set을 토대로 구현한다.
sequenceDiagram
  participant A as 미들웨어 A
  participant R as Redis
  participant B as 미들웨어 B
  A->>R: GET counter
  R-->>A: 3
  B->>R: GET counter
  R-->>B: 3
  A->>R: SET counter 4
  B->>R: SET counter 4
  Note over R: 두 번 증가했지만 값은 4 — 하나가 사라졌다
읽고-더하고-쓰기를 나누면 갱신이 유실된다 — Redis의 INCR는 이 세 단계를 원자적으로 처리하므로 이 문제 자체가 생기지 않는다. 여러 키를 함께 다뤄야 할 때 Lua 스크립트가 필요해진다.
동기화 이슈
  • 수백만 사용자를 다루는 서비스는 미들웨어 한 대로 부족할 수 있다.
  • 여러 대를 배치했을 때 스티키 세션을 쓰면 같은 미들웨어로 가는 것은 보장되지만, 확장성 면에서 권장되지 않는다.
  • 미들웨어끼리도 공유 저장소(Redis 등)를 통해 상태를 나누는 편이 낫다.
성능 최적화
  • 미들웨어도 사용자에게 가장 가까운 엣지에 배치하면 지연이 줄어든다.
모니터링
  • 설치 후 의도대로 동작하고 있는지 모니터링이 필요하다.
  • 알고리즘이 효율적인지, 규칙이 잘 적용되고 있는지 확인해야 한다.
  • 제한 규칙이 너무 빡빡하면 정상 요청까지 대량으로 버려진다.

정리

  • 규칙은 디스크 → 로컬 캐시, 카운터는 Redis.
  • 응답 헤더는 X-RateLimit-Limit / X-RateLimit-Remaining / Retry-After.
  • 분산 환경의 두 함정은 경쟁 조건(원자 연산 / Lua로 해결)과 동기화(공유 저장소로 해결).
  • 규칙이 과하면 정상 트래픽이 잘려 나가므로 모니터링이 필수다.
