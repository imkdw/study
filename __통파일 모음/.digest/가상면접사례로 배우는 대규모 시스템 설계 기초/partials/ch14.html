14-1

요구사항과 개략적 규모

하루 150TB의 저장소와 하루 15만 달러의 CDN 비용.

핵심 유튜브 설계의 지배적 제약은 성능이 아니라 비용이다. CDN 요금이 하루 15만 달러라는 계산이 뒤의 모든 최적화를 정당화한다.

필요한 기능

  • 빠른 비디오 업로드
  • 원활한 비디오 재생
  • 재생 품질 선택 기능
  • 낮은 인프라 비용
  • 높은 가용성과 규모 확장성, 안정성
  • 지원 클라이언트 — 모바일 앱, 웹 브라우저, 스마트 TV

개략적 규모

  • DAU — 5,000,000
  • 사용자 한 명이 평균 하루 5개의 비디오를 시청
  • 10%의 사용자가 하루에 1개의 비디오를 업로드
  • 비디오 평균 크기는 300MB
  • 하루 저장 용량 = 500만 × 10% × 300MB = 150TB
  • CDN 비용 —
    • AWS CloudFront 기준, 모든 트래픽이 미국에서 발생한다면 1GB당 $0.02
    • 매일 500만 × 5비디오 × 0.3GB × $0.02 = $150,000
×

연간 5,475만 달러

하루 15만 달러는 연 5천만 달러가 넘는 비용이다. 14-3의 "인기 없는 비디오는 미리 인코딩하지 않는다", "지역 편중 비디오는 옮기지 않는다", "ISP와 계약해 CDN을 직접 구축한다" 같은 제안들이 왜 나오는지가 이 숫자 하나로 설명된다.

정리

  • 하루 저장 증가 150TB, 하루 CDN 비용 15만 달러.
  • 기능 요구사항 안에 "낮은 인프라 비용"이 명시적으로 들어 있다.
  • 이 장의 최적화는 대부분 비용 최적화다.
14-2

개략적 설계

비디오는 BLOB에, 배포는 CDN에. 나머지는 트랜스코딩 파이프라인이다.

핵심 업로드 요청은 파일 업로드와 메타데이터 갱신 두 갈래로 병렬 진행된다. 큰 파일 전송을 기다리며 메타데이터까지 멈출 이유가 없기 때문이다.

저장 공간과 CDN

직접 바닥부터 모든 걸 만드는 것은 매우 비싼 시간적/물적 비용이 든다. 이미 만들어진 것을 적절하게 쓰자.

  • 비디오를 저장하기 위해 BLOB 스토리지를 쓴다.
  • 빠른 다운로드를 위해 CDN을 쓴다.
  • 넷플릭스는 AWS CloudFront를, 페이스북은 Akamai를 쓰는 등 회사마다 다양하다.
flowchart TB
  D["단말기들
Web / App / TV"] -->|"비디오 스트리밍 요청"| CDN["CDN"]
  D -->|"그 외 나머지 요청"| API["API 서버"]
비디오 트래픽은 우리 서버에 오지 않는다 — 스트리밍은 전부 CDN이 받고, API 서버는 메타데이터 / 검색 / 추천 같은 가벼운 요청만 처리한다.

업로드가 끝나도 재생 준비는 끝나지 않는다 — 트랜스코딩이 완료되고 완료 핸들러가 메타데이터를 갱신해야 비로소 재생 가능 상태가 된다. 완료 큐가 이 비동기 구간을 이어 준다.
트랜스코딩 서버 (transcoding server)
  • 트랜스코딩은 비디오 인코딩이라고도 부르며, 비디오의 포맷을 변환하는 절차다.
  • 단말이나 대역폭 요구사항에 맞는 최적의 비디오 스트림을 제공하기 위해 필요하다.
트랜스코딩 비디오 저장소 (transcoded storage)
  • 트랜스코딩이 완료된 비디오를 저장하는 BLOB 스토리지다.
CDN
  • 트랜스코딩이 완료된 비디오를 캐시한다.
  • 사용자가 재생을 누르면 스트리밍은 CDN을 통해 이루어진다.
트랜스코딩 완료 큐 (completion queue)
  • 비디오 트랜스코딩 완료 이벤트를 보관할 메시지 큐다.
트랜스코딩 완료 핸들러 (completion handler)
  • 완료 큐에서 이벤트를 꺼내 처리한다.
  • 메타데이터 캐시와 메타데이터 DB를 갱신하는 작업 서버들이다.

프로세스 A : 비디오 업로드

  1. 비디오를 원본 저장소에 업로드한다
  2. 트랜스코딩 서버가 원본을 가져와 변환한다
  3. 결과물을 트랜스코딩 비디오 저장소에 올린다
  4. 완료 이벤트를 큐에 넣고, 핸들러가 메타데이터를 갱신한다
  5. CDN에 배포하고 사용자에게 알린다

프로세스 B : 메타데이터 갱신

  • 원본 저장소에 파일이 업로드되는 동안, 단말은 병렬로 비디오 메타데이터 갱신 요청을 보낸다.
  • 메타데이터에는 이름, 크기, 포맷 등의 정보가 포함된다.
flowchart TB
  U["유저 단말기"] -->|"메타데이터 갱신 요청"| LB["로드밸런서"]
  LB --> API["API 서버"]
  API --> MC[("메타데이터 캐시")]
  API --> MDB[("메타데이터 DB")]
파일 전송과 무관한 가벼운 경로 — 300MB 전송이 끝나기를 기다리지 않고 제목/설명 같은 정보를 먼저 저장할 수 있다.

비디오 스트리밍 절차

  • 유튜브에서 비디오를 재생하면 다운로드가 끝난 뒤 재생되는 것이 아니라 즉시 영상이 시작된다.
  • 스트리밍은 지속적으로 비디오 스트림을 전송받아 영상을 재생하는 것을 뜻한다.
스트리밍 프로토콜
  • 비디오 스트리밍을 위해 데이터를 전송할 때 쓰이는 표준화된 통신 방법이다.
  • MPEG-DASH, HLS, MSS, HDS 등 다양한 프로토콜이 있다.
i

프로토콜이 곧 화질 전환의 메커니즘 보강

MPEG-DASH와 HLS는 비디오를 몇 초짜리 조각들로 잘라 두고, 화질별 조각 목록을 담은 매니페스트를 준다. 플레이어가 네트워크 상태를 보며 조각 단위로 화질을 바꿔 요청하기 때문에 재생 중에도 화질이 자연스럽게 바뀐다. "재생 품질 선택 기능"이 별도 기능이 아니라 프로토콜 위에서 자동으로 얻어지는 이유다.

정리

  • 비디오는 BLOB 스토리지, 배포는 CDN, 메타데이터는 DB + 캐시.
  • 업로드는 파일 전송과 메타데이터 갱신 두 갈래로 병렬 진행된다.
  • 트랜스코딩 완료 큐가 비동기 구간을 이어 준다.
  • 스트리밍 프로토콜(HLS/DASH)이 조각 단위 적응형 화질 전환을 제공한다.
14-3

상세 설계

DAG로 파이프라인을 추상화하고, GOP로 쪼개 병렬화하고, 롱테일로 비용을 깎는다.

핵심 이 절의 최적화는 전부 "쪼개서 병렬로"라는 한 가지 아이디어의 변주다. GOP로 쪼개 업로드하고, 작업으로 쪼개 스케줄링하고, 단계로 쪼개 메시지 큐로 잇는다.

비디오 트랜스코딩

  • 비트레이트는 비디오를 구성하는 비트가 얼마나 빨리 처리되어야 하는지를 나타낸다.
  • 비트레이트가 높을수록 화질이 좋다.
  • 높은 비트레이트의 비디오를 재생하려면 고성능 컴퓨팅 파워와 좋은 회선이 있어야 한다.
비디오 트랜스코딩이 중요한 이유
  • 원본 비디오(raw video)는 저장 공간을 많이 쓴다. 초당 60FPS로 녹화된 HD 비디오는 수백 GB를 차지할 수도 있다.
  • 상당수의 단말과 브라우저는 특정 종류의 포맷만 지원한다. 여러 단말과 브라우저를 지원하려면 여러 포맷으로 인코딩해야 한다.
  • 끊김 없는 재생을 위해 네트워크 대역폭에 따라 고화질/저화질을 모두 제공할 수 있어야 한다.
인코딩 포맷
  • 다양한 포맷이 있지만 크게 두 부분으로 나뉜다.
  • 컨테이너 —
    • 비디오 파일, 오디오, 메타데이터를 담는 바구니다.
    • .avi, .mov, .mp4 같은 확장자로 구분한다.
  • 코덱 —
    • 화질은 보존하고 파일 크기를 줄일 목적으로 고안된 압축/해제 프로토콜이다.
    • 가장 많이 쓰이는 코덱은 H.264, VP9, HEVC다.

유향 비순환 그래프(DAG) 모델

  • 모든 비디오는 사용자 취향에 따라 다양한 커스텀이 들어간다.
  • 서로 다른 유형의 비디오 프로세싱 파이프라인을 지원하면서 병렬 처리 효율을 높이려면 적절한 수준의 추상화가 필요하다.
  • 예를 들어 클라이언트가 직접 실행할 작업을 손수 정의할 수 있게 하는 방식이 있다.

단계가 나뉘면 스케줄링 단위가 생긴다 — DAG 스케줄러가 이 단계들을 작업 큐에 밀어 넣는다.

비디오 트랜스코딩 아키텍처

전처리기 (preprocessor)
  • 비디오 분할(video splitting) —
    • 비디오 스트림을 GOP(Group of Pictures) 단위로 쪼갠다.
    • GOP 하나는 독립적으로 재생 가능하며 보통 몇 초 정도다.
    • 구버전 단말이나 브라우저는 GOP 단위 분할을 지원하지 않아 전처리기가 대신 담당한다.
  • DAG 생성 — 클라이언트가 작성한 설정 파일에 따라 DAG를 만든다.
  • 데이터 캐시 —
    • 전처리기는 분할된 비디오의 캐시 역할도 한다.
    • GOP와 메타데이터를 임시 저장소에 보관하고, 인코딩 실패 시 보관된 데이터로 재개한다.
dag-config.json
{
  "name": "transcode",
  "type": "Transcode",
  "input": {
    "input": "context.input"
  }
}
DAG 스케줄러
  • DAG 그래프를 몇 개의 단계로 분할해 각각을 자원 관리자의 작업 큐에 집어넣는다.
자원 관리자
  • 자원 배분을 효과적으로 수행하는 역할을 담당한다.
  • 작업 큐(task queue) — 실행될 작업이 들어 있는 우선순위 큐
  • 작업 서버 큐(worker queue) — 작업 서버의 가용 상태 정보가 보관된 큐
  • 실행 큐(running queue) — 현재 실행 중인 작업 및 작업 서버 정보가 보관된 큐
  • 작업 스케줄러 — 최적의 서버와 작업을 골라 그 서버가 작업을 수행하도록 지시한다
flowchart LR
  TQ[["작업 큐"]] -->|"가장 높은 우선순위 작업"| SCH["작업 스케줄러"]
  WQ[["작업 서버 큐"]] -->|"최적 작업 서버"| SCH
  SCH -->|"실행 큐에 작업/서버 정보 추가"| RQ[["실행 큐"]]
  SCH -->|"작업 실행"| WS["작업 서버"]
스케줄러는 두 큐에서 하나씩 꺼내 짝지어 준다 — 무엇을 할지(작업 큐)와 누가 할지(작업 서버 큐)를 분리해 둔 덕에 각각을 독립적으로 확장할 수 있다.
임시 저장소
  • 저장할 데이터 유형, 크기, 이용 빈도에 따라 구현을 골라야 한다.
  • 메타데이터는 작업 서버가 빈번하게 참조하고 크기도 작은 것이 보통이다 → 메모리 캐시.
  • 오디오나 동영상을 저장하려면 BLOB 스토리지가 낫다.
  • 임시 저장소의 데이터는 비디오 프로세싱이 끝나면 삭제한다.

시스템 최적화

속도 최적화 : 비디오 병렬 업로드
  • 비디오 전부를 한 번의 업로드로 올리는 것은 비효율적이다.
  • 비디오를 GOP 단위로 분할해 병렬로 업로드하면 효율적이다 —
    • 중간에 실패해도 업로드한 지점부터 이어서 작업할 수 있다.
    • 병렬로 처리되므로 업로드 속도가 올라간다.

  V["Video"] -->|"GOP 단위로 분할"| ORIG[("원본 저장소")]
  ORIG --> G1["GOP 1"]
  ORIG --> G2["GOP 2"]
  ORIG --> G3["GOP 3"]
  G1 -->|"병렬 처리"| U["유저 단말기"]
  G2 --> U
  G3 --> U
실패의 단위가 파일 전체에서 조각 하나로 줄어든다 — 300MB를 99% 올리고 끊겼을 때 처음부터 다시 하지 않아도 된다.
속도 최적화 : 업로드 센터를 위치 기반으로 지정
  • 업로드 센터를 여러 곳에 배치한다.
  • 미국 거주자는 미국 업로드 센터로, 중국 거주자는 아시아로 보낸다.
  • 이를 위해 CDN을 업로드 센터로 활용할 수 있다.
속도 최적화 : 모든 절차를 병렬화
  • 낮은 지연을 달성하기는 어렵다.
  • 또 다른 방법은 느슨하게 결합된 시스템을 만들어 병렬성을 높이는 것이다.
  • 기존에는 선행 작업이 끝나야 다음 작업이 진행되었지만, 메시지 큐를 도입해 느슨하게 결합하면 이벤트 각각을 병렬로 처리할 수 있다.
flowchart LR
  subgraph BEFORE["기존 — 직렬"]
    O1[("원본 저장소")] -->|"분할된 원본 다운"| D1["다운로드 모듈"]

    E1 -->|"인코딩된 비디오"| UP1["업로드 모듈"]

  end
기존 구조에서는 앞 단계가 끝나야 뒤 단계가 시작한다 — 다운로드 중에는 인코딩 모듈이 놀고 있다.

모듈 사이마다 큐를 끼운다 — 각 모듈은 자기 큐만 보면 되므로 서로의 속도를 기다리지 않고, 모듈별로 따로 증설할 수 있다. 1-8 메시지 큐의 효용이 그대로 적용된 사례다.
안정성 최적화 : pre-signed URL
  • 허가받은 사용자만 동영상을 업로드할 수 있도록 제한한다.
  • 대표적으로 AWS S3의 pre-signed URL이 있다.
sequenceDiagram
  participant U as 유저 단말기
  participant A as API 서버
  participant S as 원본 저장소
  U->>A: 1. POST /upload
  A-->>U: 2. pre-signed URL 반환
  U->>S: 3. 그 URL 로 직접 비디오 업로드
비디오는 우리 서버를 거치지 않는다 — API 서버는 권한만 발급하고, 300MB 전송은 클라이언트와 저장소가 직접 처리한다. 서버 대역폭을 아끼는 동시에 권한도 통제하는 구조다.
안정성 최적화 : 비디오 보호
  • 디지털 저작권 관리(DRM) — 가장 널리 쓰이는 방식. 애플의 FairPlay, 구글의 Widevine, MS의 PlayReady가 있다.
  • AES 암호화 —
    • 비디오를 암호화하고 접근 권한을 설정하는 방식이다.
    • 암호화된 비디오는 재생 시에만 복호화된다.
    • 허락된 사용자만 시청할 수 있다.
  • 워터마크 —
    • 비디오 위에 소유자 정보를 포함하는 이미지 오버레이를 올린다.
    • 회사 로고나 이름 등을 이 용도로 쓸 수 있다.

비용 최적화

  • CDN은 이 서비스의 핵심이자 가장 많은 요금을 지불하는 서비스다.
  • 연구 결과에 따르면 유튜브 비디오 스트리밍은 롱테일 분포를 따른다 — 인기 있는 것은 자주 재생되지만 나머지는 거의 보는 사람이 없다.
  • 인기 없는 비디오는 미리 인코딩할 필요가 없을 수도 있고, 짧은 비디오라면 필요할 때 인코딩해 재생시켜 줄 수도 있다.
  • 어떤 비디오는 특정 지역에서만 인기가 높아 다른 지역으로 옮길 필요가 없을 수도 있다.
  • ISP와 계약을 맺어 CDN을 직접 구축할 수도 있다. 기존 통신비보다는 절감되겠지만, CDN을 직접 구축하는 것은 매우 힘든 일이다.
비용은 꼬리에서 샌다 — 거의 재생되지 않는 영상까지 미리 인코딩해 CDN에 얹으면 저장/전송 비용만 나가고 회수되지 않는다.

오류 처리

  • 대형 시스템에서 오류는 불가피하다.
  • 가능하면 장애를 잘 감내하는 서비스를 만들어 우아하게 처리하고 빠르게 회복해야 한다.
회복 가능 오류 (recoverable error)
  • 특정 비디오 세그먼트를 트랜스코딩하다 실패하는 등의 오류는 회복할 수 있다.
  • 일반적으로는 몇 번 재시도하면 해결된다.
  • N번 이상 재시도해도 실패한다면 적절한 오류 코드를 반환해야 한다.
회복 불가능 오류 (non-recoverable error)
  • 비디오 포맷이 잘못되었거나 회복 불가능한 오류가 발견되면, 시스템은 그 비디오에 대한 작업을 중단하고 적절한 오류 코드를 반환해야 한다.

정리

  • 트랜스코딩은 저장 공간 / 단말 호환성 / 적응형 화질 세 가지를 위해 필요하다.
  • DAG로 파이프라인을 추상화하고, 스케줄러가 단계를 작업 큐에 넣는다.
  • GOP 단위 분할이 병렬 업로드와 재개 가능한 업로드를 동시에 준다.
  • 모듈 사이에 큐를 끼워 전 과정을 병렬화한다.
  • pre-signed URL로 서버를 거치지 않고 권한만 통제한다.
  • 롱테일 분포를 이용해 인기 없는 비디오의 인코딩/캐싱 비용을 줄인다.
