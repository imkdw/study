13-1

요구사항과 규모 추정

100ms. 이 한 숫자가 데이터베이스 질의를 설계에서 몰아낸다.

핵심 자동완성이 특이한 이유는 글자를 칠 때마다 요청이 나간다는 점이다. "dinner"를 치면 요청이 6번이다. 그래서 QPS가 검색량의 몇 배로 뛴다.

요구사항

빠른 응답 속도
  • 사용자가 검색어를 입력하면 자동완성도 빠르게 표시되어야 한다.
  • 페이스북 문서를 보면 100ms 이내에 표시되어야 한다고 되어 있다.
연관성
  • 출력되는 검색어는 사용자가 입력한 단어와 연관된 것이어야 한다.
정렬
  • 계산 결과는 인기도 등의 순위 모델에 의해 정렬되어야 한다.
규모 확장성
  • 많은 트래픽을 감당할 수 있도록 확장 가능해야 한다.
고가용성
  • 일부에 장애가 나거나 느려지거나 네트워크 문제가 생겨도 시스템은 계속 동작해야 한다.

규모 추정

  • DAU는 1,000만 명으로 가정한다.
  • 사용자 한 명이 매일 10건의 검색을 한다고 가정한다.
  • 검색 시 평균 20바이트의 데이터를 입력한다 —
    • ASCII를 가정하고 1문자 = 1바이트로 계산한다.
    • 질의문은 평균 4개의 단어, 각 단어는 평균 5글자로 이루어진다.
    • 질의당 평균 4 × 5 = 20바이트
  • 글자를 입력할 때마다 클라이언트가 API를 호출한다. dinner를 입력하면 총 6번의 API 호출이 발생한다.
  • QPS = 1,000만 명 × 10회/일 × 20자 ÷ 24시간 ÷ 3600초 ≈ 24,000건
  • 최대 QPS = 24,000 × 2 = 48,000
  • 질의 중 20% 정도가 신규 검색어라고 가정하면 하루 신규 데이터는 약 0.4GB — 1,000만 × 10 × 20 × 20% = 0.4GB
!

한글이라면 이 계산이 3배가 된다 보강

2-2에서 짚었듯 이 추정의 전제는 ASCII다. 한글 서비스라면 UTF-8에서 한 글자가 3바이트이므로 저장소 추정치는 0.4GB가 아니라 약 1.2GB가 된다. 또한 한글은 초성/중성/종성 조합 과정에서 입력 이벤트가 더 잦게 발생해 QPS도 더 올라갈 수 있다.

정리

  • 요구사항 다섯: 100ms 응답 / 연관성 / 인기도 정렬 / 확장성 / 고가용성.
  • 글자마다 요청이 나가므로 QPS가 검색 건수의 20배로 뛴다(24,000 → 최대 48,000).
  • ASCII 기준 신규 데이터 0.4GB/일. 한글이면 3배로 잡아야 한다.
13-2

개략적인 설계안

데이터를 모으는 쪽과 답을 주는 쪽. 두 서비스로 나눈다.

핵심 이 절의 순진한 설계가 실패하는 지점을 정확히 이해해야 한다. LIKE 'prefix%' + ORDER BY가 초당 48,000번 실행되는 것을 어떤 DB도 견디지 못한다.

데이터 수집 서비스

  • 사용자가 입력한 질의를 실시간으로 수집하는 시스템이다.
  • twitch, twitter, twiter, twillo를 차례로 입력하면 빈도 테이블이 아래처럼 변해 간다.
수집 서비스가 하는 일은 카운팅뿐 — 이 단순한 테이블이 13-3에서 트라이로 재구성되면서 성능 문제가 풀린다.

이 쿼리가 왜 안 되는가

LIKE 'prefix%'는 인덱스를 탈 수 있지만, 그 뒤의 ORDER BY frequency DESC는 매칭된 행 전부를 정렬해야 한다. 접두어가 짧을수록(예: t) 매칭 행이 수백만 개가 되고, 그것을 초당 48,000번 정렬하는 것은 불가능하다. 다음 절의 트라이는 이 정렬을 미리 해 두는 방식으로 문제를 없앤다.

정리

  • 수집 서비스는 질의 빈도를 세고, 질의 서비스는 그 위에서 상위 k개를 뽑는다.
  • RDBMS의 LIKE + ORDER BY는 접두어가 짧을 때 정렬 비용이 폭발한다.
  • 해법은 정렬을 요청 시점이 아니라 미리 해 두는 것이다.
13-3

상세 설계

트라이를 세우고, 각 노드에 답을 미리 넣고, 갱신은 배치로 미룬다.

핵심 이 장의 두 가지 최적화를 한 문장으로 하면 — 탐색을 O(1)로 만들고, 갱신을 실시간에서 배치로 옮긴다.

트라이 자료구조

  • 트라이는 문자열을 간결하게 저장할 수 있는 자료구조다.
  • 트리 형태를 띠며 루트 노드는 빈 문자열을 나타낸다.
  • 각 노드는 글자를 한 개씩 저장하며, (영문 기준) 26개의 자식 노드를 가질 수 있다.
  • 앞 절의 데이터베이스 설계가 가진 단점을 극복할 수 있다.

공통 접두어를 한 번만 저장한다 — tr은 tree/true/try 세 단어가 공유하므로 노드 하나면 충분하다. 이 공유가 트라이의 공간 효율성의 근거다.
구현 방식
  • p — 접두어(prefix)의 길이
  • n — 트라이 안에 있는 노드의 개수
  • c — 주어진 노드의 자식 개수
  • 가장 많이 사용된 접두어를 찾는 로직 —
    1. 접두어를 표현하는 노드를 찾는다

      시간복잡도 O(p)

    2. 그 노드부터 시작하는 하위 트리를 탐색해 모든 유효 노드를 찾는다

      유효한 검색 문자열을 구성하는 노드가 유효 노드다. 시간복잡도 O(c)

    3. 유효 노드를 정렬해 가장 인기 있는 검색어 k개를 찾는다

      시간복잡도 O(c log c)

구현 예시
  • be를 입력하고 관련 검색어 2개를 찾는 경우 —
    • be로 시작하는 노드를 탐색한다.
    • 그 노드부터 시작하는 하위 트리를 탐색해 모든 유효 노드를 찾는다.
    • 유효 노드를 정렬해 2개만 골라낸다. 결과는 [best: 35, bet: 29].

트라이 최적화

트라이는 트리 형태라서, 최악의 경우 k개의 결과를 얻기 위해 전체 트라이를 다 뒤져야 할 수도 있다.

접두어 최대 길이 제한
  • 일반적으로 아주 긴 검색어를 입력하는 일은 거의 없다.
  • 따라서 검색어 길이를 작은 정숫값(예: 50)으로 제한해도 안전하다.
  • 최대 길이를 제한하면 접두어 노드를 찾는 단계의 시간복잡도가 O(p) → O(1)로 줄어든다.
노드에 인기 검색어 캐싱
  • 각 노드에 k개의 인기 검색어를 미리 저장해 두면 전체 트라이를 탐색하는 일을 없앨 수 있다.
  • 단점은 캐싱을 위한 추가 저장 공간이 필요하다는 것이다.
  • 빠른 응답 속도를 위해서라면 저장 공간을 희생할 가치가 있다.
  • 이렇게 최적화하면 시간복잡도가 O(n) → O(1)로 줄어든다.

top-k = best:35 / bet:29 / bee:20"]

  BU --> BUY["buy : 14"]
  BE --> BEE["bee : 20

  BE --> BET["bet : 29"]

모든 노드가 자기 아래의 정답을 미리 들고 있다 — 이제 be를 치면 노드를 찾아 저장된 리스트를 그대로 반환하면 끝이다. 하위 트리 탐색도 정렬도 필요 없다.

하위 트리 탐색O(c)O(1)노드에 top-k 캐싱

개선된 설계 방안

  • 기존 구성은 사용자가 실시간으로 검색어를 입력할 때마다 트라이를 갱신한다.
  • 매일 수천만 건의 질의가 발생하는데 매번 갱신하면 서비스가 상당히 느려진다.
  • 일단 트라이가 만들어지면 인기 검색어는 그다지 자주 바뀌지 않으므로, 트라이를 자주 갱신할 필요가 없다.

  AGG --> DATA["취합된 데이터"]

갱신 주기를 실시간에서 주 단위로 늦춘다 — 인기 검색어 순위는 며칠 사이에 크게 바뀌지 않으므로, 이 지연을 감수하면 쓰기 부하가 사실상 0이 된다.

  • 인덱스를 걸지 않고, 새 데이터가 추가되기만 하며 수정은 발생하지 않는다.

작업 서버
  • 주기적으로 비동기 작업을 담당하는 서버다.
  • 트라이 자료구조를 만들고 트라이 데이터베이스에 저장하는 역할을 한다.
트라이 캐시
  • 분산 캐시 시스템으로, 트라이 데이터를 메모리에 유지해 읽기 성능을 높인다.
  • 위 설계에서는 매주 트라이 DB의 스냅샷을 떠서 캐싱한다.
트라이 데이터베이스
  • 문서 저장소(document store) — 대표적으로 MongoDB. 주기적으로 트라이를 직렬화해 저장할 수 있다.
  • 키-값 저장소 — 트라이에 보관된 모든 접두어를 해시 테이블의 키로, 각 노드에 보관된 데이터를 값으로 변환한다.

트리를 평평하게 펴면 키-값이 된다

노드마다 top-k를 캐싱해 두면 트리 구조 자체가 더 이상 필요 없어진다. 접두어를 키로 하는 평평한 해시 테이블 하나면 충분하고, 조회는 그야말로 O(1)이 된다. 자료구조를 만들어 놓고 결국 버리는 이 흐름이 이 장의 백미다.

추가 최적화 방안
  • AJAX 요청 — 새로고침 없이 자동완성 결과를 가져와 UX를 개선한다.
  • 브라우저 캐싱 — 자동완성 결과를 브라우저에 캐싱하면 사용자는 더 빠르게 결과를 받고 서버 부하도 줄어든다. 구글은 max-age=3600, private 설정으로 최적화한다.
  • 데이터 샘플링 — 대규모 시스템에서 모든 것을 로깅하면 저장 공간이 매우 많이 필요하다. N개의 요청당 1개만 로깅하도록 최적화한다.

트라이 연산

트라이 생성
  • 작업 서버가 담당한다.
  • 데이터 분석 서비스의 로그나 데이터베이스에서 취합된 데이터를 이용한다.
트라이 갱신
  • 매주 한 번씩 갱신하는 방법은 새 트라이를 만들어 기존 트라이를 통째로 대체한다.
  • 트라이의 각 노드를 개별적으로 갱신하는 방법은 성능이 좋지 않다 —
    • 트라이가 작으면 고려해 볼 만하지만 대규모 트라이에는 적합하지 않다.
    • 하위 노드를 변경하면 그 노드를 캐싱하고 있던 모든 상위 노드의 데이터도 함께 바꿔야 하기 때문이다.
검색어 삭제
  • 혐오적, 성적, 스팸 등 위험한 질의어는 자동완성 결과에서 제거해야 한다.
  • 트라이 캐시 앞에 필터 계층을 두어 특정 질의어가 반환되지 않게 한다.
  • 이미 DB에 저장된 데이터는 다음 업데이트 때 비동기적으로 삭제되게 하면 된다.

필터를 캐시 앞에 두는 이유

DB에서 지우는 데는 최대 일주일이 걸린다(갱신 주기). 그동안 유해 검색어가 노출되면 안 되므로, 응답 경로 맨 앞에 필터를 세워 즉시 차단하고 DB 정리는 느긋하게 진행한다. 즉시성이 필요한 것과 그렇지 않은 것을 분리하는 전형적인 패턴이다.

저장소 규모 확장

시작 글자를 기준으로 샤딩
  • 영어만 저장한다면 첫 글자를 기준으로 샤딩하는 방법을 생각할 수 있다.
  • a~m은 1번 서버, 나머지는 2번 서버에 두는 식이며, 동일하게 26/N으로 나눌 수 있다.
  • 이 방법으로는 알파벳 개수인 최대 26개까지만 샤딩을 늘릴 수 있다.
계층적으로 샤딩
  • 26개 이상의 샤드가 필요하면 계층적으로 나눈다.
  • aa~am, an~az처럼 두 글자 단위로 쪼개면 한 번 더 계층적인 샤딩이 가능해진다.
!

첫 글자 샤딩은 불균형하다 보강

영어에서 a, s, c로 시작하는 단어는 x, z로 시작하는 단어보다 훨씬 많다. 단순히 26등분하면 일부 샤드만 과부하가 걸린다. 실무에서는 과거 질의 분포를 분석해 각 샤드가 비슷한 트래픽을 받도록 경계를 정하는 샤드 관리자를 따로 둔다.

정리

  • 트라이는 공통 접두어를 공유해 저장 공간을 아낀다.
  • 접두어 길이 상한 + 노드별 top-k 캐싱으로 조회를 O(1)로 만든다.
  • top-k를 캐싱하고 나면 트리 구조가 필요 없어져 키-값 저장소로 평평해진다.
  • 갱신은 실시간이 아니라 주 단위 배치로 미룬다.
  • 유해어는 캐시 앞 필터로 즉시 차단하고 DB 정리는 나중에.
  • 샤딩은 첫 글자 → 계층적으로 확장하되, 분포 불균형을 고려해야 한다.
