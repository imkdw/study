10-1

설계 범위와 플랫폼별 알림 구조

푸시 / SMS / 이메일. 채널은 셋이지만 구조는 하나로 수렴한다.

핵심 세 채널 모두 알림 제공자 → 제3자 서비스 → 단말이라는 동일한 삼단 구조를 갖는다. 그래서 뒤에서 하나의 파이프로 묶을 수 있다.

설계 범위

  • 알림 종류 — 푸시 알림, SMS 메시지, 이메일
  • 연성 실시간(soft real-time)으로 가정한다. 가능한 한 빨리 전달하되, 부하가 있을 때 약간의 지연은 허용한다.
  • 지원 플랫폼 — iOS, Android, 랩톱/데스크톱
  • 알림은 클라이언트에서 만들 수도, 서버에서 스케줄링으로 만들 수도 있다.
  • 알림 수신 여부는 사용자가 제어할 수 있어야 한다.
  • 하루 발송량 — 모바일 푸시 1,000만 건, SMS 100만 건, 이메일 500만 건 이하

iOS 푸시 알림

  P["알림 제공자
(우리 서버)"] -->|"단말 토큰 + 페이로드"| A["APNs

우리는 애플에게 부탁만 한다 — 실제 단말 전달은 APNs가 책임진다. 우리 쪽 설계 대상은 첫 번째 화살표까지다.
알림 제공자 (Provider)
  • 알림 요청을 만들어 애플 푸시 알림 서비스로 보내는 주체다.
  • 필요한 데이터 —
    • 단말 토큰(device token) — 알림 요청을 보내는 데 필요한 고유 식별자
    • 페이로드(payload) — 알림 내용을 담은 JSON 객체
apns-payload.json
{
  "aps": {
    "alert": {
      "title": "내 알림",
      "body": "알림 내용"
    },
    "badge": 5
  }
}
APNs (Apple Push Notification service)
  • 애플이 제공하는 원격 서비스다.
  • 푸시 알림을 iOS 기기로 보내는 역할을 담당한다.
iOS 기기
  • 알림을 받는 주체다.
↑

APNs 레거시 바이너리 프로토콜은 종료되었다 최신 반영

과거 APNs는 포트 2195/2197을 쓰는 바이너리 프로토콜을 지원했으나, 애플은 2021년 3월 31일부로 레거시 바이너리 엔드포인트를 폐쇄했다. 현재는 api.push.apple.com:443을 쓰는 HTTP/2 기반 프로바이더 API만 동작하며, JSON Web Token 기반 인증과 알림 단위 피드백을 제공한다. 지금 알림 제공자를 새로 구현한다면 HTTP/2 + JWT가 유일한 선택지다. (근거: Apple Developer News — Updated APNs provider API deadline)

안드로이드 푸시 알림

  • iOS와 큰 차이는 없다.
  • APNs 대신 FCM(Firebase Cloud Messaging)을 쓴다.
↑

FCM 레거시 API도 종료되었다 최신 반영

FCM의 레거시 HTTP/XMPP API는 2023년 6월 20일 지원 중단이 예고되었고 2024년 중 셧다운되었다. 현재는 /v1/projects/{project-id}/messages:send 형태의 HTTP v1 API를 써야 하며, 고정 서버 키 대신 OAuth2 단기 액세스 토큰으로 인증한다. 페이로드 구조도 플랫폼 공통 키와 플랫폼별 키(android, apns)로 나뉘도록 바뀌었다. (근거: Migrate from legacy FCM APIs to HTTP v1)

SMS 메시지

  • 일반적으로 Twilio, Nexmo 같은 제3 사업자의 서비스를 많이 쓴다.
  • 대부분 상용 서비스라 요금이 부과된다.

이메일

  • 회사가 자체 이메일 서버를 갖출 역량은 대체로 있다.
  • 하지만 많은 회사가 상용 이메일 서비스를 쓴다.
  • Sendgrid, Mailchimp 등이 유명하며 전송 성공률이 높고 데이터 분석 서비스도 제공한다.

1:N 이라는 점이 중요하다 보강

한 사용자가 여러 단말을 가질 수 있으므로 user : device는 1:N이다. 알림 하나를 보낼 때 그 사용자의 모든 단말 토큰으로 팬아웃해야 한다는 뜻이고, 이는 12장 채팅 시스템의 "여러 단말 간 메시지 동기화"와 같은 문제다.

정리

  • iOS는 APNs, Android는 FCM, SMS는 Twilio류, 이메일은 Sendgrid류.
  • 네 채널 모두 제공자 → 제3자 서비스 → 단말 구조라 어댑터로 추상화된다.
  • APNs 바이너리 프로토콜과 FCM 레거시 API는 모두 종료되어 각각 HTTP/2, HTTP v1을 써야 한다.
  • user : device 는 1:N 이며 알림 발송은 단말 단위 팬아웃이다.
10-2

알림 전송 및 수신 절차

1차 설계는 SPOF와 병목을 만든다. 그걸 깨는 도구가 메시지 큐다.

핵심 채널별로 큐를 나누는 것이 이 절의 결론이다. 이메일이 밀려도 푸시는 나가야 하기 때문이다.

1차 설계안

flowchart LR
  S1["서비스 1"] --> N["알림 시스템 (단일 서버)"]
  S2["서비스 2"] --> N
  SN["서비스 N"] --> N
  N --> A["APNs"]
  N --> F["FCM"]
  N --> T["SMS"]
  N --> E["이메일"]
가운데 상자 하나에 모든 것이 걸려 있다 — 이 상자가 죽으면 알림이 전부 멈추고, 이 상자가 밀리면 모든 채널이 함께 밀린다.
1 ~ N개의 서비스
  • 각 마이크로서비스, 크론잡, 분산 시스템 컴포넌트 등 다양하다.
  • 메시지를 발생시키는 주체이며 과금 서비스, 배송 알림 등이 여기 해당한다.
알림 시스템
  • 알림 전송/수신의 핵심이다. 위 구성도에서는 서버 한 대만 쓴다고 가정한다.
  • 서비스들에게 알림 발송용 API를 공개해야 하고, 제3자 서비스에 전달할 알림 페이로드를 만들어야 한다.
제3자 서비스
  • 사용자에게 알림을 실제로 전달하는 역할을 한다.
  • 통합할 때 유의할 것은 확장성이다. 서비스를 쉽게 제거하거나 추가할 수 있어야 한다.
  • 또한 국가별로 사용 가능한 서비스에 제약이 있다. 중국에서는 FCM이 아니라 JPush, PushY 같은 것을 쓴다.
SPOF (Single Point of Failure)
  • 중앙의 알림 서비스에 장애가 나면 모든 서비스의 장애로 이어진다.
  • DB나 캐시 등 중요 컴포넌트의 규모를 개별적으로 늘릴 방법이 없다.
성능 병목
  • 알림을 처리하고 보내는 것은 자원을 많이 쓰는 작업일 수 있다.
  • 모든 것을 한 서버로 처리하면 트래픽이 몰리는 시간에 과부하가 걸린다.

2차 설계안 (개선 버전)

  • DB와 캐시를 주 서버에서 분리하고, 알림 서버에 로드밸런싱과 오토스케일링을 적용한다.
  • 메시지 큐로 시스템 컴포넌트 사이의 강한 결합을 끊는다.
알림 서버가 제공하는 기능
  • 알림 전송 API — 사내 서비스나 인증된 API만 이용할 수 있다.
  • 알림 검증 — 이메일이나 전화번호 등에 대한 기본적인 검증을 수행한다.
  • DB 또는 캐시 질의 — 알림에 포함될 데이터를 가져온다.
  • 알림 전송 — 알림 데이터를 각 역할별 메시지 큐에 전달한다. 큐가 여러 개이므로 병렬 처리가 가능하다.
flowchart TB
  SVC["1 ~ N 개의 서비스"] --> LB["로드밸런서"]
  LB --> NS1["알림 서버 1"]
  LB --> NS2["알림 서버 N"]
  CACHE[("캐시")] --- NS1
  DB[("DB")] --- NS1
  NS1 --> QA[["iOS 푸시 큐"]]
  NS1 --> QB[["Android 푸시 큐"]]
  NS1 --> QC[["SMS 큐"]]
  NS1 --> QD[["이메일 큐"]]
  QA --> WA["작업 서버"] --> APNS["APNs"]
  QB --> WB["작업 서버"] --> FCM["FCM"]
  QC --> WC["작업 서버"] --> SMS["SMS 서비스"]
  QD --> WD["작업 서버"] --> MAIL["이메일 서비스"]
채널마다 큐가 따로다 — 이메일 제공자가 느려져도 그 큐만 쌓일 뿐, 푸시 알림은 정상 속도로 나간다. 장애 격리가 이 분리의 목적이다.

정리

  • 1차 설계의 문제는 SPOF와 성능 병목 두 가지.
  • DB/캐시 분리 + 로드밸런싱 + 오토스케일링으로 서버 계층을 풀고,
  • 채널별 메시지 큐로 컴포넌트 간 결합과 장애 전파를 끊는다.
10-3

상세 설계

잃지 않되 중복도 줄이기, 그리고 사용자를 지치게 하지 않기.

핵심 "절대 잃지 않는다"와 "절대 중복되지 않는다"는 동시에 달성할 수 없다. 알림 시스템은 손실 방지를 택하고 중복은 감지로 줄이는 쪽을 고른다.

안정성

데이터 손실 방지
  • 요구사항 중 하나는 어떤 상황에서도 알림이 소멸되면 안 된다는 것이다.
  • 알림 데이터를 데이터베이스에 먼저 기록하고, 재시도 메커니즘을 구현해야 한다.
알림 중복 전송 방지
  • 같은 알림이 여러 번 발송되는 것을 완전히 방지하는 것은 불가능하다.
  • 대부분은 한 번만 전송되지만, 분산 시스템의 특성상 가끔 중복이 발생한다.
  • 빈도를 줄이려면 중복 메시지 감지 메커니즘을 도입한다.
  • 보낼 알림이 도착하면 이벤트 ID를 검사해 이전에 본 적이 있는지 확인한다.
i

왜 "완전 방지"가 불가능한가 보강

알림을 보낸 직후 응답을 받기 전에 작업 서버가 죽으면, 시스템은 그 알림이 나갔는지 알 수 없다. 다시 보내면 중복이고, 안 보내면 손실이다. 둘 중 하나를 반드시 고르게 되는 구조다. 26장 결제 시스템은 정확히 이 지점에서 반대 선택(중복 방지 우선)을 하며, 그래서 멱등 키가 필수가 된다.

추가 고려사항

알림 템플릿
  • 하루에도 수백만 건을 처리하는데 매번 형식을 새로 만들 필요는 없다.
  • 인자나 스타일, 링크만 조정하면 사전에 지정한 형식을 재사용할 수 있다.
  • 형식이 일관되게 유지되고, 오류 가능성과 작성 시간이 줄어든다.
template
[item_name]이 다시 입고되었습니다. [end_time]까지 세일합니다!
전송률 제한
  • 사용자에게 적절한 양의 알림을 보내는 것이 중요하다.
  • 너무 많이 보내면 사용자가 알림을 아예 비활성화해 버릴 수 있다.
재시도 방법
  • 제3자 서비스가 발송에 실패하면 실패한 알림을 다시 큐에 넣는다.
  • 같은 문제가 N번 이상 발생하면 개발자에게 통보하는 시스템을 갖추면 좋다.
푸시 알림과 보안
  • 푸시 알림은 appKey, appSecret으로 보안을 유지한다.
  • 인증되거나 승인된 클라이언트만 이 API로 알림을 발송할 수 있다.
큐 모니터링
  • 중요한 메트릭 중 하나는 큐에 쌓인 알림의 개수다.
  • 이 수가 너무 크면 작업 서버들이 이벤트를 빠르게 처리하지 못하고 있다는 뜻이다.
  • 이럴 때는 작업 서버를 증설해 처리 속도를 높인다.
큐 길이는 소비 속도와 생산 속도의 차이를 그대로 보여 준다 — 그래프가 우상향하기 시작하는 순간이 증설 신호다.
이벤트 추적
  • 알림 확인율, 클릭률 등 실제 앱 사용으로 이어지는 비율은 사용자를 이해하는 데 중요하다.
  • 데이터 분석 서비스는 보통 이벤트 추적 기능도 함께 제공한다.
이벤트의미이 지표가 나쁘면
발송(sent)제3자 서비스로 넘김우리 시스템 문제
전달(delivered)단말까지 도착토큰 만료 / 제3자 문제
열람(opened)사용자가 확인내용이 매력적이지 않음
해제(opt-out)알림 끄기전송률 제한이 필요함

10장의 종착점 — 알림 서버는 검증과 전송률 제한만, 실제 발송의 지저분한 일(중복 감지 / 재시도)은 전부 작업 서버가 맡는다.

정리

  • 손실 방지는 DB 기록 + 재시도로, 중복은 이벤트 ID 감지로 줄인다(완전 제거는 불가).
  • 템플릿으로 일관성과 작성 비용을, 전송률 제한으로 사용자 이탈을 관리한다.
  • 큐 적체량이 가장 중요한 운영 메트릭이다.
  • 발송/전달/열람/해제 네 이벤트를 추적하면 문제 지점을 특정할 수 있다.
