11-1

문제 이해와 설계 방안

기능은 둘. 피드를 올리는 것과 친구들의 피드를 보는 것.

핵심 "친구 최대 5,000명"과 "DAU 1,000만"이라는 두 숫자가 이 장 전체의 난이도를 정한다. 친구가 5,000명이면 포스팅 한 번이 5,000번의 쓰기가 될 수 있기 때문이다.

문제 이해

  • 지원 플랫폼 — 웹/앱 모두
  • 중요한 기능 —
    • 뉴스 피드 페이지에 새로운 게시글 업로드
    • 친구들이 올리는 스토리 확인
  • 스토리 표시 순서 — 단순한 시간 흐름 역순
  • 사용자의 최대 친구 수 — 5,000명
  • 트래픽 규모 — 매일 1,000만 명 방문 (10 million DAU)
  • 피드에 이미지나 비디오 업로드 가능

뉴스 피드 API

피드 발행
POST /v1/me/feed
Authorization: Bearer <token>

# Body: 포스팅 내용 (content, media 등)
피드 조회
GET /v1/me/feed
Authorization: Bearer <token>

발행 요청 하나가 세 갈래로 퍼진다 — 저장 / 팬아웃 / 알림. 이 중 팬아웃이 가장 비싸고, 그래서 11-2 전체가 팬아웃 이야기다.

정리

  • API는 발행(POST)과 조회(GET) 둘뿐.
  • 정렬은 단순 시간 역순, 친구 상한 5,000명, DAU 1,000만.
  • 발행 시 팬아웃이 가장 비싼 작업이다.
11-2

상세 설계

쓰기 시점 팬아웃과 읽기 시점 팬아웃. 정답은 둘 다다.

핵심 두 팬아웃 전략은 비용을 쓰기 쪽에 지불할 것인가, 읽기 쪽에 지불할 것인가의 선택이다. 실무의 답은 사용자 유형에 따라 둘을 섞는 것이다.

피드 발행 흐름 상세 설계

웹 서버
  • 인증이나 처리율 제한 기능도 함께 수행한다.
  • 인증 — Authorization 토큰으로 올바른 사용자인지 검증한다.
  • 처리율 제한 — 스팸과 중복 콘텐츠를 막기 위해 사용자가 올릴 수 있는 포스팅 수를 제한한다.
포스팅 전송(fanout) 서비스
  • fanout — 특정 사용자가 새 피드를 올리면, 그 사용자와 친구 관계인 모든 사용자에게 전달하는 과정이다.
  • 쓰기 시점 팬아웃(fanout-on-write)과 읽기 시점 팬아웃(fanout-on-read) 두 방식이 있다.

쓰기 시점 팬아웃

  • 새 포스팅을 기록하는 시점에 뉴스 피드를 갱신한다. 포스팅이 완료되면 바로 친구들의 캐시에 그 포스팅을 기록한다.
  • 뉴스 피드가 실시간으로 갱신되고, 친구 목록에 있는 사용자에게 즉시 전송된다.
  • 기록되는 순간 이미 피드가 갱신되어 있으므로 읽는 데 필요한 시간이 짧다.
  • 친구가 많은 사용자의 경우 친구 목록을 가져와 그 전원의 피드를 갱신하는 데 많은 시간이 걸린다. 이것이 핫키(hotkey) 문제다.
  • 서비스를 자주 쓰지 않는 사용자의 피드까지 갱신해야 하므로 컴퓨팅 자원이 낭비된다.

읽기 시점 팬아웃

  • 피드를 읽어야 하는 시점에 뉴스 피드를 갱신한다. 요청 기반 모델이며, 사용자가 홈이나 타임라인을 로딩하는 순간 새 포스트를 가져온다.
  • 비활성 사용자나 거의 로그인하지 않는 사용자에게 유리하다. 로그인 전까지는 어떤 자원도 쓰지 않는다.
  • 데이터를 친구 각각에게 푸시할 필요가 없으므로 핫키 문제도 생기지 않는다.
  • 대신 뉴스 피드를 읽는 데 많은 시간이 소요될 수 있다.

실무의 답은 하이브리드

일반 사용자에게는 쓰기 시점 팬아웃을 써서 읽기를 빠르게 하고, 팔로워가 수백만인 유명인의 포스팅은 읽기 시점에 가져오도록 예외 처리한다. 이렇게 하면 핫키 문제는 유명인 계정에만 국한되고, 대다수 사용자는 빠른 읽기를 누린다.

flowchart TB
  POST["새 포스팅"] --> FO["포스팅 전송 서비스"]
  FO -->|"친구 ID 목록 조회"| GDB[("그래프 DB")]
  FO -->|"친구 관계 추출"| UC["유저 정보 캐시"] --> UDB[("유저 정보 DB")]
  FO -->|"친구 목록 + 신규 포스트"| MQ[["메시지 큐"]]
  MQ --> WK["포스팅 전송 작업 서버"]
  WK --> NFC[("뉴스 피드 캐시
postID + userID 만 저장")]
뉴스 피드 캐시에는 ID만 담는다 — 포스팅 본문을 사람 수만큼 복사하면 메모리가 감당이 안 되므로, postID와 userID 쌍만 저장하고 본문은 읽을 때 붙인다.

ID를 먼저 얻고 내용을 나중에 붙인다 — 캐시 세 개(피드 / 유저 / 포스팅)를 나눠 둔 덕분에, 포스팅 내용이 수정돼도 피드 캐시를 건드릴 필요가 없다.

1장 / 5장 / 7장이 여기서 다시 만난다 보강

핫키 문제는 1-10 샤딩의 유명인사 문제와 같은 뿌리이고, 시간 역순 정렬은 7장 스노플레이크 ID가 있으면 별도 정렬 없이 해결된다. 그리고 팬아웃 작업을 큐로 넘기는 것은 1-8 메시지 큐 그 자체다. 뉴스 피드는 새 부품이 거의 없이 기존 부품만으로 조립되는 대표적인 설계다.

정리

  • 쓰기 시점 팬아웃 = 읽기가 빠르지만 핫키와 자원 낭비.
  • 읽기 시점 팬아웃 = 핫키가 없지만 읽기가 느림.
  • 실무는 일반 사용자에게 쓰기 팬아웃, 유명인에게 읽기 팬아웃을 섞는다.
  • 피드 캐시에는 ID만 담고 본문은 읽을 때 결합한다.
