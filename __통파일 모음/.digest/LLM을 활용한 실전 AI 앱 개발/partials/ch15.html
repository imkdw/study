15-1

에이전트란

감각으로 보고, 두뇌로 판단하고, 도구로 행동한다.

핵심 LLM 은 텍스트만 생성할 수 있다. 그래서 에이전트가 바깥 세상에 영향을 미치려면 반드시 도구가 필요하다 — 이 제약이 에이전트 설계의 출발점이다.

에이전트란

  • 알아서 생각하고 행동하는 시스템을 에이전트라고 부른다.
  • 에이전트는 LLM 과 RAG 를 하나의 구성요소로 사용한다. 지금까지 배운 것들이 부품이 되는 셈이다.
  • 철학에서는 더 넓은 범위로 행동을 할 수 있는 능력이 있는 개체를 뜻한다.

에이전트의 구성요소

감각 → 두뇌 → 행동의 순환 — 한 바퀴로 끝날 수도 있고, 복잡한 문제라면 여러 번 돈다.
  1. 감각으로 인식한다

    감각을 통해 외부 환경과 사용자의 요청을 인식한다.

  2. 두뇌로 판단한다

    두뇌로 가지고 있는 지식이나 지금까지의 기억을 확인하고, 계획을 세우거나 추론을 통해 다음에 어떤 행동을 할지 의사결정한다.

  3. 도구로 행동한다

    문제를 해결하기 위해 취할 수 있는 적절한 도구를 선택해 행동한다.

이 과정은 한 번에 수행될 수도 있고, 복잡한 경우 여러 번 반복될 수도 있다.

에이전트의 두뇌

  • 에이전트의 핵심은 인식하고 판단하는 두뇌다.
  • 어떤 행동을 취할지 결정할 때, 지금까지 수행했던 사용자와의 대화나 행동을 저장한 기억을 확인한다.
  • 목표 달성을 위해 작업을 세분화하는 계획 세우기 단계를 거치고, 바로 다음에 어떤 행동이 필요한지 결정해 행동 단계로 넘어간다.
  • LLM 은 이 과정에 필요한 모든 능력을 갖추고 있다 — 이해, 추론, 계획, 그리고 그것을 텍스트로 표현하는 능력.

에이전트의 감각

  • LLM 은 기본적으로 텍스트만 이해할 수 있었지만, 멀티 모달 LLM(14장)을 통해 사진/영상 등 다양한 정보를 다룰 수 있게 됐다.
  • 활용할 수 있는 데이터 유형이 많아질수록 훨씬 풍부한 정보를 처리하고 다양한 상황에 대응할 수 있다.
  • 비디오/오디오 멀티 모달인 Video-LLaVA 는 동영상을 분석할 때 오디오와 비디오 정보를 각각의 인코더에 전달하고, 그 결과를 LLM 으로 분석한다.

에이전트의 행동

LLM 은 텍스트만 생성할 수 있다. 따라서 외부에 영향을 미치는 행동을 하려면 LLM 이 사용할 수 있는 도구를 제공해야 한다.

도구 예시에이전트가 얻는 능력
검색 API학습 시점 이후의 최신 정보 획득
DALL-E / Stable Diffusion이미지 생성
코드 실행 환경계산/데이터 처리/파일 생성 (15-4 의 실습)
벡터 DB 검색 (RAG)사내 문서 등 비공개 지식 활용
i

"도구를 쓴다"의 실제 의미 보강

LLM 이 도구를 직접 실행하는 것이 아니다. LLM 이 하는 일은 "이 함수를 이 인자로 호출해 달라"는 구조화된 텍스트를 생성하는 것뿐이고, 실제 실행은 바깥의 프로그램이 한다. 그래서 15-3 에서 에이전트의 대표적 실패 원인으로 "요청한 출력 형식으로 응답하지 않은 경우" 가 꼽힌다 — 형식이 깨지면 바깥 프로그램이 파싱하지 못해 아무 행동도 일어나지 않는다.

정리

  • 에이전트 = 알아서 생각하고 행동하는 시스템. LLM 과 RAG 를 부품으로 쓴다.
  • 구성요소는 감각 / 두뇌 / 행동이며, 필요하면 여러 번 순환한다.
  • 두뇌는 기억 확인 → 계획 → 다음 행동 결정을 담당하고, LLM 이 이 능력을 제공한다.
  • 멀티 모달 LLM 이 감각의 폭을 넓혔다.
  • LLM 은 텍스트만 만든다 → 도구가 있어야 바깥에 영향을 준다.
15-2

에이전트 시스템의 형태

혼자 다 하거나, 사람과 주고받거나, 여럿이 나눠 맡거나.

핵심 구체적인 프로필을 부여하는 것만으로 관련 작업의 전문성이 올라간다. 멀티 에이전트가 단일 에이전트보다 나은 결과를 내는 가장 단순한 이유다.

단일 에이전트

  • AutoGPT 는 입력받은 프롬프트만으로 모든 결정을 내린다.
  • 프롬프트에는 목표 / 제약사항 / 활용 가능한 도구 등이 들어가고, 그 내용을 바탕으로 다음에 수행할 도구를 선택한다.
  • 장점: 모든 과정을 스스로 처리해 편리하고, 범용적인 프롬프트로 동작하므로 다양한 작업에 쓸 수 있다.
  • 단점: 그만큼 작업 도중 길을 잃을 가능성도 크다. 내부에서 쓰는 LLM 의 성능에 크게 좌우된다.
  • 아직까지는 목표가 명확하고 작업의 크기가 작은 경우에만 선택적으로 활용하는 것이 좋다.

사용자와 에이전트의 상호작용

  • 대표적인 예시가 ChatGPT 다.
  • 요청과 응답 사이에서 사용자가 피드백을 주고, 이 과정을 반복해 점차 목표에 도달하는 코드를 만들어 간다.
  • 다만 이 방식은 사용자의 개입이 여전히 많이 필요하다. 에이전트를 쓰면 직접 도구를 사용하므로 ChatGPT 보다 개입이 덜 필요하다.
  • 반대로 전문 도메인에서는 LLM 의 전문성이 사람보다 떨어질 수 있어 사용자 개입이 오히려 중요한 경우도 있다.

멀티 에이전트

  • 단일 에이전트와 달리 각 에이전트마다 서로 다른 프로필을 주고 작업을 수행한다.
  • LLM 에 구체적인 프로필을 부여하는 것만으로도 관련 작업의 전문성이 높아져 결과 품질이 올라간다.
  • 에이전트 간 협력을 통해 작업의 품질이 더 향상될 수 있다.

15-4 코드에서 이 둘을 구분하는 방법 보강

다음 절의 AutoGen 실습에서 autogen.GroupChat(...) 의 speaker_selection_method 인자가 정확히 이 선택이다. "round_robin" 은 정해진 순서로 돌아가며 발언하는 수평형에 가깝고, "auto" 는 GroupChatManager 가 다음 발언자를 LLM 으로 고르는 위계형이다.

정리

  • 단일 에이전트(AutoGPT): 범용적이고 편하지만 길을 잃기 쉽다. 작고 명확한 작업에 쓴다.
  • 사용자 상호작용(ChatGPT): 통제하기 쉽지만 개입이 많이 필요하다. 전문 도메인에서는 오히려 장점.
  • 멀티 에이전트: 서로 다른 프로필을 부여해 전문성과 품질을 높인다.
  • 대화 형태는 수평형(다 함께) / 위계형(매니저가 선택)으로 나뉜다.
15-3

에이전트 평가하기

사람이 채점하거나, 사람과 구분되는지 보거나, 벤치마크로 재거나.

핵심 에이전트가 실패하는 대표적인 이유는 추론 실패와 출력 형식 위반이다. 후자는 능력의 문제가 아닌데도 작업 전체를 무산시킨다.

왜 평가인가

모든 AI 제품 개발에서 성능 평가는 가장 핵심적인 부분 중 하나다. 크게 두 갈래로 나뉜다.

  • 결과를 사람이 직접 평가하는 방식 — 두 에이전트의 결과에 사람이 각각 점수를 매기는 것이 일반적인 사람 평가 방식이다.
  • 사람의 결과와 비교해 구분할 수 있는지 확인하는 방식.
튜링 테스트

에이전트와 사람의 결과물을 구분할 수 있는지 확인하는 평가 방식을 튜링 테스트라 한다. 에이전트의 결과물을 사람의 것이라고 판단하거나 구분할 수 없다면, 사람과 동등한 지능적 행동이 가능하다고 말할 수 있다.

벤치마크 데이터셋을 활용한 객관적 평가

에이전트를 평가하는 네 가지 기준
기준무엇을 보는가
유용성작업을 자동으로 수행할 때의 작업 성공률 같은 기준
사회성언어를 얼마나 숙련되게 쓰는지, 협력/협상이 뛰어난지, 부여된 역할에 얼마나 부합하게 행동하는지
가치관거짓말을 지어내지 않고 신뢰할 수 있는 정확한 정보를 전달하는지, 차별적 편향이 있는지
진화 능력상황에 맞춰 스스로 발전할 수 있는지 — 지속적 학습, 스스로 목표를 설정하고 달성하는 능력

이 중에서는 아직까지 목표한 작업을 얼마나 성공적으로 수행하는지를 평가하는 유용성을 중심으로 연구가 활발히 진행되고 있다.

노트에는 유요성 으로 적혀 있는데 유용성(有用性)의 오타다. 이 정리본에서는 바로잡았다.

AgentBench
  • 칭화대에서 만든 LLM 에이전트 평가 데이터셋이다.
  • 하나의 작업으로 평가하는 것이 아니라 8개의 작업으로 평가하기 때문에, 일반화 성능을 확인할 수 있다는 장점이 있다.
  • 평가 결과, 오픈소스 LLM 의 일반화 능력이 상용 LLM 에 미치지 못한다는 결과가 나왔다.

높은 점수와 낮은 점수의 차이

에이전트가 실패하는 대표적인 경우는 두 가지다.

  • 대화가 여러 턴에 걸쳐 진행되면서 추론과 의사결정 능력이 떨어지는 경우
  • 요청한 출력 형식으로 응답하지 않은 경우

LLM 에이전트는 텍스트 입출력으로 작업을 진행하므로, 출력이 원하는 형식으로 나오지 않으면 그 자체로 실패가 된다.

i

두 번째 실패는 공학으로 줄일 수 있다 보강

추론 실패는 모델 능력의 문제지만, 출력 형식 위반은 대체로 해결 가능한 문제다. 6-2 에서 GPT-4 평가에 response_format: {"type": "json_object"} 를 강제한 것이 그 예다. 요즘은 구조화된 출력(structured output)이나 함수 호출(function calling)로 스키마 자체를 모델에 강제할 수 있어, 이 유형의 실패는 크게 줄었다. 벤치마크 점수의 상당 부분이 모델의 지능이 아니라 출력 파싱 성공률이었다는 뜻이기도 하다.

정리

  • 평가는 사람이 채점하거나 사람과 구분되는지(튜링 테스트) 보는 방식으로 나뉜다.
  • 객관적 기준 네 가지: 유용성 / 사회성 / 가치관 / 진화 능력. 현재는 유용성 중심.
  • AgentBench: 8개 작업으로 일반화 성능을 잰다. 오픈소스가 상용에 아직 못 미친다.
  • 실패 원인 두 가지: 멀티 턴에서의 추론 저하, 출력 형식 위반.
15-4

에이전트 구현

AutoGen — 에러를 읽고, 패키지를 깔고, 다시 시도한다.

핵심 이 절의 실습이 보여주는 것은 에이전트가 실패에서 회복하는 장면이다. 코드가 에러를 내면 에러 메시지를 읽고 원인을 파악해 스스로 고친다 — 사람의 개입 없이.

LLM 컨피그 설정

AutoGen 은 사용할 모델 목록을 JSON 파일로 관리하고, filter_dict 로 필요한 모델만 골라 쓴다. 에이전트마다 다른 모델을 배정하기 위한 구조다.

OAI_CONFIG_LIST.json 
[
  { "model": "gpt-4-turbo-preview", "api_key": "" },
  { "model": "gpt-4o",              "api_key": "" },
  { "model": "dall-e-3",            "api_key": "" }
]

에이전트 실행 — 코드를 짜고 실행하는 에이전트

basic_agent.py 
import json, os
import autogen
from autogen import AssistantAgent, UserProxyAgent

openai_api_key = ""
os.environ["OPENAI_API_KEY"] = openai_api_key

with open('OAI_CONFIG_LIST.json', 'w') as f:
    config_list = [
        {"model": "gpt-4-turbo-preview", "api_key": openai_api_key},
        {"model": "gpt-4o",              "api_key": openai_api_key},
        {"model": "dall-e-3",            "api_key": openai_api_key},
    ]
    json.dump(config_list, f)

config_list = autogen.config_list_from_json(
    "OAI_CONFIG_LIST.json",
    file_location=".",
    filter_dict={"model": ["gpt-4-turbo-preview"]},
)

llm_config = {"config_list": config_list, "temperature": 0}

assistant = AssistantAgent("assistant", llm_config=llm_config)

# UserProxyAgent 를 통해 명령이나 피드백을 전달한다
user_proxy = UserProxyAgent(
    "user_proxy",
    # 응답이 TERMINATE 로 끝나면 대화를 종료한다
    is_termination_msg=lambda x: x.get("content", "")
        and x.get("content", "").rstrip().endswith("TERMINATE"),

    # NEVER 로 두면 사람의 추가 피드백 없이 알아서 처리한다
    human_input_mode="NEVER",

    # 생성된 코드를 이 디렉터리에서 실제로 실행한다
    code_execution_config={"work_dir": "coding", "use_docker": False},
)

response = user_proxy.initiate_chat(assistant, message="""

텍스트로 이미지 생성하기 — DALLEAgent

AutoGen 에 없는 에이전트는 ConversableAgent 를 상속해 직접 만든다. 핵심은 register_reply 로 "메시지를 받았을 때 어떻게 응답할지" 를 갈아끼우는 부분이다.

dalle_agent.py 
import os
import autogen
import matplotlib.pyplot as plt
from openai import OpenAI
from autogen import Agent, ConversableAgent, UserProxyAgent
from autogen.agentchat.contrib.img_utils import _to_pil, get_image_data

config_list_4o = autogen.config_list_from_json(
    "OAI_CONFIG_LIST.json", filter_dict={"model": ["gpt-4o"]},
)
config_list_dalle = autogen.config_list_from_json(
    "OAI_CONFIG_LIST.json", filter_dict={"model": ["dall-e-3"]},
)

def dalle_call(client, prompt, model="dall-e-3", size="1024x1024",
               quality="standard", n=1) -> str:
    response = client.images.generate(
        model=model, prompt=prompt, size=size, quality=quality, n=n)
    image_url = response.data[0].url
    return get_image_data(image_url)

class DALLEAgent(ConversableAgent):
    def __init__(self, name, llm_config: dict, **kwargs):
        super().__init__(name, llm_config=llm_config, **kwargs)

        try:
            config_list = llm_config["config_list"]
            api_key = config_list[0]["api_key"]
        except Exception as e:
            print("Unable to fetch API Key, because", e)
            api_key = os.getenv("OPENAI_API_KEY")

        self.client = OpenAI(api_key=api_key)

        # 이 에이전트가 메시지를 받으면 generate_dalle_reply 로 응답하게 한다
        self.register_reply([Agent, None], DALLEAgent.generate_dalle_reply)

    def generate_dalle_reply(self, messages, sender, config):
        client = self.client if config is None else config
        if client is None:
            return False, None
        if messages is None:
            messages = self._oai_messages[sender]

        prompt = messages[-1]["content"]
        img_data = dalle_call(client=self.client, prompt=prompt)
        plt.imshow(_to_pil(img_data))
        plt.axis("off")
        plt.show()
        return True, 'result.jpg'

# 이미지 생성 에이전트를 인스턴스화

AutoGen 은 두 갈래로 갈라졌다 최신 반영

이 절의 코드는 AutoGen v0.2 API 다. 이후 프로젝트가 분화했다.

  • Microsoft AutoGen v0.4+ — 비동기/이벤트 주도 액터 모델로 전면 재작성됐다. autogen-agentchat / autogen-core / autogen-ext 로 패키지가 나뉘며, v0.2 코드와 호환되지 않는다.
  • AG2 — 커뮤니티 포크가 pyautogen / autogen PyPI 패키지명을 이어받았다. v0.2 계열 API 와 RetrieveUserProxyAgent 같은 contrib 에이전트를 계속 유지한다.

따라서 pip install autogen 으로 설치되는 것이 어느 쪽인지 확인해야 하며, 위 코드를 그대로 돌리려면 AG2 계열이 맞다. 근거: AutoGen v0.2 → v0.4 마이그레이션 가이드

정리

  • AssistantAgent(코드 작성) + UserProxyAgent(코드 실행) 조합이 AutoGen 의 기본 단위다.
  • 실습의 핵심 장면은 에러 메시지를 읽고 스스로 패키지를 설치해 회복하는 부분이다.
  • 모르는 주제에 대해 에이전트는 없는 제품이라고 단정하고 지어낸다 — RAG 를 붙이면 정확해진다.
  • speaker_selection_method 가 수평형(round_robin) 과 위계형(auto) 을 가른다.
  • ConversableAgent 를 상속하고 register_reply 를 등록하면 커스텀 에이전트를 만들 수 있다.
  • 설명 에이전트 + 화가 에이전트 = 14장의 멀티 모달 구조를 텍스트로 이어붙인 형태.
