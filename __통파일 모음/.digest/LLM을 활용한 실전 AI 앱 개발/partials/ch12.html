12-1

벡터 데이터베이스란

키가 문자열이 아니라 벡터인 데이터베이스.

핵심 벡터 DB 는 벡터 사이의 거리 계산에 특화된 데이터베이스다. "같은 값 찾기"가 아니라 "가까운 값 찾기"가 기본 연산이라는 점이 RDBMS 와의 결정적 차이다.

벡터 데이터베이스의 정의

  • 벡터 임베딩을 키로 사용하는 데이터베이스를 말한다.
  • 텍스트/이미지/음성 같은 비정형 데이터는 물론, 서비스를 사용하는 사용자도 임베딩 모델을 통해 벡터로 표현할 수 있다.
  • 데이터를 벡터로 바꿔 저장해 두면, 거리 계산으로 유사하거나 관련 깊은 데이터를 검색할 수 있다.

딥러닝과 벡터 데이터베이스

머신러닝과 딥러닝의 차이는 사람이 직접 데이터의 특징을 정의하는지 여부다. 머신러닝은 특징을 사람이 설계해야 하지만, 딥러닝은 그 과정조차 학습한다. 데이터만 충분하면 모델이 알아서 특징을 뽑는데, 이를 표현 학습(representation learning)이라 한다.

벡터 DB 가 지금 시점에 필요해진 이유가 여기 있다 — 딥러닝이 좋은 표현(임베딩)을 만들어주기 시작했기 때문에, 그 표현을 담고 검색할 저장소가 필요해진 것이다.

벡터 DB 를 활용하는 3단계
  1. 저장

    저장할 데이터를 임베딩 모델에 통과시켜 벡터로 변환하고 벡터 DB 에 넣는다.

  2. 검색

    검색할 데이터도 같은 임베딩 모델로 벡터로 바꾸고 DB 에서 찾는다. 거리 계산에는 유클리드 거리 / 코사인 유사도 / 점곱(내적) 을 가장 많이 쓴다.

  3. 결과 반환

    검색 쿼리 임베딩과 거리가 가까운 벡터들을 찾아 반환한다.

활용처
  • 핀터레스트처럼 이미지 검색 등 비정형 데이터의 유사성 기반 검색을 제공하는 서비스
  • 사용자가 구매한 상품과 유사한 상품을 추천하는 추천 시스템

정리

  • 벡터 DB = 벡터 임베딩을 키로 쓰는, 거리 계산에 특화된 DB.
  • 딥러닝의 표현 학습이 좋은 임베딩을 만들어주면서 벡터 DB 의 필요성이 생겼다.
  • 저장 → 검색 → 반환의 3단계. 거리는 유클리드 / 코사인 / 점곱.
  • 라이브러리 / 전용 DB / 기능 추가형 세 갈래이며, 부가 기능과 운영 부담으로 고른다.

벡터 디비 작동 원리

KNN 의 한계 → ANN → NSW → 계층 구조 → HNSW.

핵심 정확도를 조금 포기하고 속도를 크게 얻는다는 것이 ANN 의 전부다. HNSW 는 여기에 "적당히 랜덤한 연결"과 "계층 구조"라는 두 아이디어를 더한 결과물이다.

KNN 검색과 그 한계

가장 기본적인 방법은 KNN 검색이다 — 저장된 모든 임베딩 벡터를 조회해 가장 유사한 K 개를 반환한다.

  • 장점: 직관적이고, 모든 데이터를 조사하므로 정확하다.
  • 단점: 데이터가 많아질수록 연산량이 데이터 수에 비례해 늘어나 속도가 느려지고 확장성이 떨어진다.
벡터 검색의 두 단계와 네 가지 지표

인덱스(RDBMS 의 테이블에 해당)에 벡터를 저장하는 과정을 색인한다고 표현한다.

KNN 은 선형으로 느려진다

SIFT1M 은 128차원 벡터 100만 개의 데이터셋이다. 참고로 BERT 는 768차원, text-embedding-ada-002 는 1536차원을 쓴다. 차원이 커질수록 검색 속도는 더 느려진다.

knn_scaling.py 
import time
import faiss
from faiss.contrib.datasets import DatasetSIFT1M
import psutil

# 현재 프로세스의 메모리 사용량을 MB 단위로 반환
def get_memory_usage_mb():
    process = psutil.Process()
    return process.memory_info().rss / (1024 * 1024)

ds = DatasetSIFT1M()

xq = ds.get_queries()      # 검색에 사용할 쿼리 벡터
xb = ds.get_database()     # 저장할 벡터 데이터
gt = ds.get_groundtruth()  # 실제 정답 (재현율 계산용)

k = 1
d = xq.shape[1]
nq = 1000                  # 검색 수행 횟수를 1,000회로 제한
xq = xq[:nq]

for i in range(1, 10, 2):
    start_memory = get_memory_usage_mb()
    start_indexing = time.time()

    # 임베딩 벡터 색인 — IndexFlatL2 는 전수 비교(KNN)
    index = faiss.IndexFlatL2(d)
    index.add(xb[:(i + 1) * 100000])

    end_indexing = time.time()
    end_memory = get_memory_usage_mb()

    t0 = time.time()
    D, I = index.search(xq, k)   # 검색 수행
    t1 = time.time()

    print(f"데이터 {(i + 1) * 100000}개:")
    print(f"색인: {(end_indexing - start_indexing) * 1000:.3f} ms "
          f"({end_memory - start_memory:.3f} MB) "
          f"검색: {(t1 - t0) * 1000 / nq:.3f} ms")

메모리 수치가 들쭉날쭉한 이유 보강

표의 메모리 증가량이 데이터 수와 비례하지 않는다(600,000 건이 400,000 건보다 작다). psutil 의 RSS 는 OS 가 이 프로세스에 실제로 매핑한 물리 메모리 총량이라, 앞 반복에서 해제된 인덱스의 메모리가 재사용되면 증가량이 작게 잡힌다. 증가분 측정 방식 자체의 노이즈이므로, 절대적인 값보다 경향으로 읽어야 한다. 이 점은 12-3 의 실험 결과를 해석할 때 다시 중요해진다.

ANN 검색이란

  • 대용량 데이터셋에서 주어진 쿼리와 가장 유사한 항목을 효율적으로 찾는 기술이다.
  • 약간의 정확도를 희생하는 대신 훨씬 빠른 검색 속도를 제공한다.
  • 실제 응용에서는 데이터셋이 크고 고차원인 경우가 많아 ANN 을 이해하고 응용할 줄 알아야 한다.
  • 대표적으로 IVF 와 HNSW 가 쓰인다.
IVF (Inverted File Index)
  • 검색 공간을 제한하기 위해 데이터셋 벡터들을 클러스터로 그룹화하는 근사 최근접 이웃 알고리즘이다.
  • 인덱싱 시점: 데이터를 가져와 중심점(클러스터)을 형성한다.
  • 쿼리 시점: 가장 가까운 클러스터를 먼저 찾고, 그 클러스터 안에서 가장 가까운 포인트를 찾는다.
  • 전체 대신 몇 개의 클러스터만 검색하는 것이 IVF 의 전략이다. 일부 이웃을 놓칠 수 있다는 비용을 감수하고 검색 시간을 크게 줄인다.
HNSW (Hierarchical Navigable Small World)
  • 효율적인 ANN 검색을 위한 그래프 기반 인덱싱 구조다.
  • 상위에는 연결이 적고 하위에는 연결이 밀집된 다층 그래프를 구축한다.
  • 상위 계층은 연결이 적어 한 번에 먼 거리를 이동할 수 있으므로 빠르게 탐색한다.
  • 검색은 최상위 → 하위 순으로 내려가며, 하위로 갈수록 연결이 많아 더 꼼꼼히 탐색한다.
  • 속도가 빠르면서 검색 성능도 뛰어나 가장 많이 활용되는 알고리즘이다.

탐색 가능한 작은 세계(NSW)

HNSW 는 그래프 기반이고, 그래프는 노드와 간선 두 요소로 이뤄진다. 서로 연결된 노드끼리만 탐색이 가능하므로 노드 사이에 간선이 얼마나 있는지에 따라 성능이 달라진다.

NSW 란 규칙적으로 연결된 그래프와 랜덤 그래프 사이의, 적당히 랜덤하게 연결된 그래프를 뜻한다.

그래프 유형탐색 정확도탐색 속도문제
규칙적으로 연결된 그래프정확느림촘촘히 연결돼 있어 많은 단계를 거쳐야 한다
랜덤 그래프불안정경우에 따라 빠름연결되지 않은 노드가 있으면 탐색 자체가 불가능하고, 되려 더 오래 걸리기도 한다
적당히 랜덤한 그래프 (NSW)정확빠름규칙적 연결로 정확성을, 랜덤 연결로 속도를 얻는다

NSW 는 규칙적인 연결에서 일부만 랜덤하게 바꾼 형태다. 규칙적 연결 덕분에 정확한 탐색이 가능하면서, 랜덤한 성질 덕분에 먼 거리를 건너뛰는 지름길이 생긴다.

작은 세계에서 랜덤 연결 만들기

구현상으로는 벡터의 순서를 랜덤으로 섞어서 저장하는 방식을 쓴다. 다만 여기에 문제가 하나 있다.

지역 최솟값 문제

랜덤하게 저장하다 보니, 진입점에서 출발했을 때 찾으려는 벡터와 가장 가까운 점이 아닌 엉뚱한 노드에서 탐색을 멈추는 경우가 생긴다. 이웃 중에 자기보다 가까운 노드가 없으면 거기서 멈춰버리는데, 전역적으로는 더 가까운 노드가 다른 곳에 있는 상황이다. 이를 지역 최솟값(local minimum) 문제라 한다. 이 문제를 해결하려고 추가된 것이 계층 구조다.

계층 구조

  • 계층 구조는 자료구조 연결 리스트 방식으로 구성된다.
  • 데이터가 크기순으로 정렬되어 있어야 연결 리스트의 탐색 속도를 높일 수 있다.
  • 레벨 0 에는 모든 데이터를 두고, 레벨 1 / 2 로 갈수록 데이터를 듬성듬성 배치한다.
  • HNSW 는 이 계층 구조를 NSW 에 접목해, 여러 계층에 그래프를 배치하는 방식으로 벡터를 저장한다.
  • 확률을 이용해 높은 층으로 갈수록 데이터가 적어지는 구조를 만든다. 높은 층의 벡터는 NSW 의 랜덤 연결이 탐색 단계를 줄인 것과 같은 방식으로 탐색 단계를 줄여준다.
위층은 지도, 아래층은 골목이다 — 상위 계층에서 대략적인 위치를 잡고 내려오므로 지역 최솟값에 갇힐 확률이 크게 줄어든다.

정리

  • KNN: 전수 비교라 정확하지만 검색 시간이 데이터 수에 선형 비례한다.
  • ANN: 정확도를 조금 포기하고 속도를 얻는 기술의 총칭. IVF(클러스터링) / HNSW(그래프).
  • NSW: 규칙적 그래프(정확/느림)와 랜덤 그래프(불안정) 사이의 절충.
  • NSW 만으로는 지역 최솟값 문제가 남는다 → 계층 구조로 해결.
  • HNSW = NSW + 계층. 상위 계층은 듬성듬성해 멀리 점프하고, 레벨 0 에는 모든 데이터가 있다.
  • 색인은 메모리/시간, 검색은 시간/재현율 — 이 네 지표가 서로 맞물린다.

HNSW 인덱스의 핵심 파라미터 이해하기

m / ef_construction / ef_search — 셋이 네 지표를 흔든다.

핵심 m 은 메모리를, ef_construction 은 색인 시간을, ef_search 는 검색 시간을 대가로 재현율을 산다. 어느 자원을 내줄 수 있는지가 튜닝의 출발점이다.
파라미터의미주로 영향받는 지표
m하나의 벡터에 연결하는 간선의 수메모리 / 색인 시간 / 재현율
ef_construction색인 과정에서 가장 가까운 M 개를 고르기 위해 저장하는 후보 수색인 시간 / 그래프 품질
ef_search검색 과정에서 가장 가까운 K 개를 고를 때 저장하는 후보 수검색 시간 / 재현율

파라미터 m 이해하기

  • HNSW 에서 추가하는 임베딩 벡터에 연결하는 간선의 수다.
  • 연결이 많을수록 그래프가 촘촘해져 검색 품질(재현율)이 좋아진다.
  • 대신 더 많은 연결을 만들고 저장해야 하므로 메모리 사용량이 커지고 색인 시간이 길어진다.
!

원문 교정 원문 교정

노트는 m 을 "하나의 벡터에 연결하는 최소 연결 수" 라고 적었지만, HNSW 원논문(Malkov & Yashunin)에서 M 은 노드를 삽입할 때 만드는 연결의 수이자 각 계층에서 유지하는 연결 수의 상한이다. 최소가 아니라 목표치이자 상한에 가깝다. 또 한 가지 — 상위 계층은 M 개까지 유지하지만 레벨 0 은 2M 까지 유지한다(Mmax0 = 2M). 아래 표에서 M 을 두 배로 늘릴 때 메모리가 정확히 두 배로 늘지 않는 것도 이 비대칭 때문이다.

param_m.py 
import numpy as np
import time
import faiss
from faiss.contrib.datasets import DatasetSIFT1M
import psutil

def get_memory_usage_mb():
    return psutil.Process().memory_info().rss / (1024 * 1024)

ds = DatasetSIFT1M()
xq = ds.get_queries()
xb = ds.get_database()
gt = ds.get_groundtruth()

k = 1
d = xq.shape[1]
nq = 1000
xq = xq[:nq]

for m in [8, 16, 32, 64]:
    # 간선의 수를 늘려가며 색인
    index = faiss.IndexHNSWFlat(d, m)
    time.sleep(3)
    start_memory = get_memory_usage_mb()
    start_index = time.time()
    index.add(xb)
    end_memory = get_memory_usage_mb()
    end_index = time.time()
    print(f"M: {m} - 색인 시간: {end_index - start_index} s, "
          f"메모리 사용량: {end_memory - start_memory} MB")

    t0 = time.time()
    D, I = index.search(xq, k)
    t1 = time.time()

    # 재현율 계산 — 정답과 일치한 비율
    recall_at_1 = np.equal(I, gt[:nq, :1]).sum() / float(nq)
    print(f"{(t1 - t0) * 1000.0 / nq:.3f} ms per query, R@1 {recall_at_1:.3f}")

1614.66 s440.72 MB0.009 ms0.777
3226.44 s689.97 MB0.011 ms0.904
6433.05 s984.58 MB0.015 ms0.937

간선이 늘어날수록 색인 시간과 검색 시간이 증가하지만 재현율도 함께 올라간다(0.678 → 0.937). 보통 5~48 범위를 쓰며, 메모리가 허용하는 선에서 값을 키워 검색 품질을 높이는 것이 유리하다.

!

메모리 열은 그대로 믿으면 안 된다

노트는 "간선 수가 늘어날수록 메모리 사용량이 증가한다"고 정리했지만, 표에서는 M=8(734MB)이 M=16(440MB)보다 크다. 실제로 M 이 커지면 메모리는 늘어나는 게 맞다. 어긋난 이유는 12-2 에서 짚은 RSS 증가분 측정의 노이즈 때문이다 — 앞 반복의 인덱스가 해제되고 남은 메모리를 다음 반복이 재사용하면 증가분이 작게 잡힌다. M=8 → 64 로 갈 때 전체 경향이 우상향이라는 점만 취하면 된다.

파라미터 ef_construction 이해하기

  • 인덱스에 새 벡터를 추가할 때도 검색과 마찬가지로 그 벡터와 가장 가까운 벡터들을 탐색한다.
  • ef_construction 은 이때 저장하는 후보의 수를 결정한다.
  • 값이 클수록 더 많은 후보를 탐색하므로 실제로 가장 가까운 벡터를 고를 가능성이 높아진다 = 그래프 품질이 좋아진다.
  • 단, 색인 시간은 증가하지만 메모리 사용량과 검색 시간은 크게 영향받지 않는다.

이 실험에서 얻을 실무 결론 보강

efConstruction 은 수익 체감이 매우 빠른 파라미터다. 이 데이터셋에서는 40 에서 320 으로 8배 올려 색인 시간을 4배 쓰고 재현율은 0.01 얻었다. 재현율을 올리고 싶다면 efConstruction 보다 m 이나 ef_search 를 먼저 건드리는 편이 낫다(m: 0.678→0.937, ef_search: 0.902→0.995). 다만 색인은 한 번, 검색은 수백만 번이므로 색인 시간은 상대적으로 지불하기 쉬운 비용이라는 점도 함께 고려한다.

파라미터 ef_search 이해하기

  • 후보군이 커지면 더 많은 벡터를 탐색하므로 재현율이 높아진다.
  • 대신 검색 시간이 길어진다.

✓

세 파라미터 중 가장 다루기 쉬운 것

ef_search 는 색인을 다시 하지 않고 런타임에 바꿀 수 있는 유일한 파라미터다. m 과 ef_construction 은 그래프 구조 자체에 박히므로 바꾸려면 전체 재색인이 필요하다. 그래서 실무 튜닝 순서는 보통 이렇다 — 먼저 메모리 예산 안에서 m 을 정해 색인하고, 그 다음 재현율 목표와 지연 예산에 맞춰 ef_search 를 조절한다.

정리

  • m: 간선 수. ↑ 하면 재현율 ↑, 메모리/색인 시간 ↑. 통상 5~48. 레벨 0 은 2M.
  • ef_construction: 색인 시 후보 수. ↑ 하면 색인 시간이 크게 ↑ 하는데 재현율 개선은 미미했다.
  • ef_search: 검색 시 후보 수. 0.902 → 0.995 로 재현율을 가장 크게 끌어올린 파라미터.
  • ef_search 만 재색인 없이 런타임에 조정 가능하다.
  • 그래프 생성에 랜덤성이 있어 결과가 늘 단조롭게 나오지는 않는다.
12-4

파인콘으로 벡터 검색 구현하기

인덱스 만들고, 임베딩 넣고, 검색한다 — 관리형 벡터 DB 의 3단계.

핵심 파인콘에서 인덱스 생성 시 차원 수를 고정한다. 이 값은 사용할 임베딩 모델의 출력 차원과 반드시 일치해야 하며, 나중에 바꿀 수 없다.

파인콘 연동과 인덱스 생성

create_index.py 
from pinecone import Pinecone, ServerlessSpec

pinecone_api_key = ''
pc = Pinecone(api_key=pinecone_api_key)

# 인덱스(테이블) 이름: llm-book
# 스펙: 서버리스 / AWS / us-east-1 / 768차원
index_name = "llm-book"

if not pc.has_index(index_name):
    pc.create_index(
        name=index_name,
        spec=ServerlessSpec(cloud="aws", region="us-east-1"),
        dimension=768,
    )

index = pc.Index(index_name)

dimension=768 은 임의의 값이 아니다. 아래에서 쓸 snunlp/KR-SBERT-V40K-klueNLI-augSTS 가 klue/roberta-base 기반이라 출력이 768차원이기 때문이다(3-3 의 config.json 에서 hidden_size: 768 로 확인할 수 있다). 모델을 바꾸면 인덱스를 다시 만들어야 한다.

임베딩 생성

embed.py 
from sentence_transformers import SentenceTransformer
from datasets import load_dataset

sentence_model = SentenceTransformer('snunlp/KR-SBERT-V40K-klueNLI-augSTS')
klue_dp_train = load_dataset('klue', 'dp', split='train[:100]')

embeddings = sentence_model.encode(klue_dp_train['sentence'])

데이터 형식 변환 및 인덱스에 저장

파인콘은 {id, values, metadata} 형식을 요구한다. values 는 파이썬 리스트여야 하므로 넘파이 배열을 tolist() 로 변환한다. metadata 에 원본 텍스트를 넣어두면 검색 결과에서 바로 꺼내 쓸 수 있다.

upsert.py 
# 넘파이 배열 → 파이썬 리스트
embeddings = embeddings.tolist()

# 파인콘에 추가할 데이터 형식으로 변환
insert_data = []
for idx, (embedding, text) in enumerate(zip(embeddings, klue_dp_train['sentence'])):
    insert_data.append({
        "id": str(idx),                 # 문자열이어야 한다
        "values": embedding,            # 임베딩 벡터
        "metadata": {'text': text},     # 함께 저장할 부가 정보
    })

# 인덱스에 저장 (namespace 로 논리적 구획을 나눈다)
upsert_response = index.upsert(vectors=insert_data, namespace='llm-book-sub')

인덱스 검색 수행

include_values 는 대개 False 가 낫다 보강

include_values=True 면 결과마다 768개의 실수가 통째로 따라온다. top_k=10 이면 7,680개 — 네트워크와 파싱 비용이 만만치 않은데 대부분의 애플리케이션은 이 값을 쓰지 않는다. 필요한 것은 metadata 의 원문과 score 뿐이므로, 실제 서비스에서는 include_values=False 로 두는 편이 좋다.

수정 및 삭제

update_delete.py 
new_text = '변경할 새로운 텍스트'
new_embedding = sentence_model.encode(new_text).tolist()

# 수정 — 벡터와 메타데이터를 함께 갱신해야 일관성이 유지된다
update_response = index.update(
    id='기존_문서_id',
    values=new_embedding,
    set_metadata={'text': new_text},
    namespace='llm-book-sub',
)

# 삭제
delete_response = index.delete(ids=['기존_문서_id'], namespace='llm-book-sub')

수정할 때 벡터만 바꾸고 메타데이터를 그대로 두거나 그 반대로 하면 데이터가 어긋난다. 검색은 벡터로 하고 결과는 메타데이터로 보여주기 때문에, 둘이 다른 내용을 가리키면 엉뚱한 결과가 나온다.

라마인덱스에서 벡터 DB 바꾸기

라마인덱스는 기본 벡터 DB(인메모리)를 쓰지만, 다양한 벡터 DB 와 쉽게 통합할 수 있는 기능을 제공한다. StorageContext 만 갈아끼우면 된다.

llamaindex_pinecone.py 
import os
from pinecone import Pinecone, ServerlessSpec
from llama_index.vector_stores.pinecone import PineconeVectorStore
from llama_index.core import StorageContext, Document, VectorStoreIndex
from datasets import load_dataset

pinecone_api_key = ''
pc = Pinecone(api_key=pinecone_api_key)
index_name = "llm-book"

if not pc.has_index(index_name):
    pc.create_index(
        name=index_name,
        spec=ServerlessSpec(cloud="aws", region="us-east-1"),
        dimension=768,
    )

pinecone_index = pc.Index(index_name)

# documents 생성
os.environ["OPENAI_API_KEY"] = ""
dataset = load_dataset('klue', 'mrc', split='train')
text_list = dataset[:100]['context']
documents = [Document(text=t) for t in text_list]

# 벡터 DB 를 파인콘으로 교체
vector_store = PineconeVectorStore(pinecone_index=pinecone_index)
storage_context = StorageContext.from_defaults(vector_store=vector_store)
index = VectorStoreIndex.from_documents(documents, storage_context=storage_context)
!

차원 불일치에 주의

위 코드의 인덱스는 768차원으로 만들어져 있는데, 라마인덱스가 OPENAI_API_KEY 만 보고 기본 임베딩 모델(text-embedding-ada-002, 1536차원)을 쓰면 차원이 맞지 않아 업서트가 실패한다. 파인콘 인덱스를 1536 으로 만들거나, Settings.embed_model 에 768차원 모델을 명시해야 한다(10-3 참고).

정리

  • 인덱스 생성 시 차원 수를 정하며, 임베딩 모델의 출력 차원과 반드시 일치해야 한다.
  • 저장 형식은 {id, values, metadata}. id 는 문자열, values 는 리스트.
  • namespace 로 하나의 인덱스를 논리적으로 구획한다.
  • 수정 시 벡터와 메타데이터를 함께 갱신해야 어긋나지 않는다.
  • 라마인덱스는 StorageContext 교체만으로 벡터 DB 를 바꿀 수 있다.

파인콘을 활용한 멀티 모달 검색 구현하기

텍스트로 색인한 DB 를 이미지로 검색한다 — CLIP 이 있어서 가능한 일.

핵심 CLIP 의 텍스트 인코더로 색인하고 이미지 인코더로 검색한다. 두 인코더의 출력이 같은 벡터 공간에 있기 때문에, 인코더가 달라도 거리 비교가 성립한다.

import requests, base64, os
from io import BytesIO
from datasets import load_dataset

os.environ["OPENAI_API_KEY"] = ""

def make_base64(image):
    buffered = BytesIO()
    image.save(buffered, format="JPEG")
    return base64.b64encode(buffered.getvalue()).decode("utf-8")

def generate_description_from_image_gpt4(prompt, image64):
    headers = {
        "Content-Type": "application/json",
        "Authorization": f"Bearer {os.getenv('OPENAI_API_KEY')}",
    }
    payload = {
        "model": "gpt-4o",
        "messages": [{
            "role": "user",
            "content": [
                {"type": "text", "text": prompt},
                {"type": "image_url",
                 "image_url": {"url": f"data:image/jpeg;base64,{image64}"}},
            ],
        }],
        "max_tokens": 300,
    }
    response_oai = requests.post(
        "https://api.openai.com/v1/chat/completions", headers=headers, json=payload
    )
    return response_oai.json()["choices"][0]["message"]["content"]

원문 교정 원문 교정

노트에는 이 줄에 # 무료 차원인 512차원 사용 이라는 주석이 달려 있는데, 파인콘 무료 플랜에 512차원이라는 제한은 없다. 512 를 쓴 진짜 이유는 이 실습이 쓰는 openai/clip-vit-base-patch32 의 프로젝션 출력 차원이 512 이기 때문이다. 12-4 에서 768 을 쓴 것과 같은 원리다 — 인덱스 차원은 늘 임베딩 모델이 결정한다. 다른 CLIP 변형을 쓰면(예: ViT-L/14 는 768) 이 값도 따라 바뀐다.

프롬프트 텍스트 → 임베딩 → 파인콘 저장
index_prompts.py 
import torch
from tqdm.auto import trange
from transformers import AutoTokenizer, CLIPTextModelWithProjection

device = "cuda" if torch.cuda.is_available() else "cpu"

# CLIP 의 텍스트 쪽 인코더
text_model = CLIPTextModelWithProjection.from_pretrained("openai/clip-vit-base-patch32")
tokenizer  = AutoTokenizer.from_pretrained("openai/clip-vit-base-patch32")

tokens = tokenizer(dataset['prompt'], padding=True, return_tensors="pt", truncation=True)
batch_size = 16
text_embs = []

for start_idx in trange(0, len(dataset), batch_size):
    with torch.no_grad():
        outputs = text_model(
            input_ids=tokens['input_ids'][start_idx:start_idx + batch_size],
            attention_mask=tokens['attention_mask'][start_idx:start_idx + batch_size],
        )
        text_embs.append(outputs.text_embeds)

text_embs = torch.cat(text_embs, dim=0)

'''
tensor([[-0.1001, -0.0165,  0.1752,  ..., -0.1827, -0.1109, -0.7854],
        [ 0.4135,  0.1837, -0.0263,  ..., -0.0776, -0.2004, -0.3663],
        ...,
        [ 0.1094, -0.1349, -0.5255,  ..., -0.1460,  0.4290,  0.1840]])
'''
print(text_embs)

# 파인콘에 저장
input_data = []
for id_int, emb, prompt in zip(range(0, len(dataset)), text_embs.tolist(), dataset['prompt']):
    input_data.append({
        "id": str(id_int),
        "values": emb,
        "metadata": {"prompt": prompt},
    })

index.upsert(vectors=input_data)   # {'upserted_count': 1000}

torch.no_grad() 로 그레이디언트 계산을 끄고, 배치 단위로 나눠 처리한다. 추론만 할 때 필수적인 두 가지 습관이다.

generate_compare.py 
import requests
from PIL import Image
import matplotlib.pyplot as plt
from openai import OpenAI

client = OpenAI()

def generate_image_dalle3(prompt):
    response_oai = client.images.generate(
        model="dall-e-3",
        prompt=str(prompt),
        size="1024x1024",
        quality="standard",
        n=1,
    )
    return response_oai.data[0].url

# 생성된 이미지 URL 을 로컬에 저장
def get_generated_image(image_url, sequence):
    generated_image = requests.get(image_url).content
    image_filename = f"gen_img_{sequence}.png"
    with open(image_filename, "wb") as image_file:
        image_file.write(generated_image)
    return Image.open(image_filename)

# (b) GPT-4o 가 만든 설명으로 생성
gpt_described_image_url = generate_image_dalle3(described_result)
gpt4o_prompt_image = get_generated_image(gpt_described_image_url, sequence="1")

# (c) 원본 프롬프트로 생성
original_prompt_image_url = generate_image_dalle3(original_prompt)
original_prompt_image = get_generated_image(original_prompt_image_url, sequence="2")

# (d) 이미지 임베딩으로 검색한 유사 프롬프트로 생성
searched_prompt_image_url = generate_image_dalle3(dataset[searched_idx]['prompt'])

(b) GPT-4o 가 이미지를 보고 쓴 설명 풀밭에 엎드린 사자. 갈기가 통째로 공작 깃털로 바뀌어 청록색이 지배적이고, 얼굴에도 푸른 무늬가 번져 있다 사자 + 공작 갈기는 맞지만 색/자세가 크게 다름
(c) 원본 프롬프트 그대로 고양이/토끼 하이브리드. 긴 귀와 꽃 장식 머리띠, 뒤로 뻗은 공작 깃털 꼬리, 몸통은 고양이 프롬프트의 요소를 가장 충실히 반영
(d) 이미지 검색으로 찾은 유사 프롬프트 (#918) (c)와 거의 같은 계열의 솜털 고양이형 생명체. 꼬리가 더 크게 말려 있고 전체 색조가 갈색/세피아로 차분하다 (c)와 같은 부류 — 검색이 유효했음

반면 (b)는 사자로 돌아갔다. GPT-4o 는 (a)를 보고 "공작 갈기를 가진 사자"라고 정확히 묘사했지만, 원본 프롬프트에 있던 cat rabbit hybrid 라는 생성 의도는 알 수 없었다. 이미지를 설명하는 것과 그 이미지를 만든 프롬프트를 복원하는 것은 다른 일이다.

정리

  • CLIP 의 텍스트 인코더로 색인하고 이미지 인코더로 검색하는 것이 멀티 모달 검색의 핵심 구조다.
  • 인덱스 차원(512)은 무료 플랜 제한이 아니라 CLIP ViT-B/32 의 출력 차원이다.
  • CLIP 유사도는 절대값이 작고 상위권이 촘촘하다 — 순위로 읽어야 한다.
  • 검색으로 찾은 남의 프롬프트가 원본 프롬프트와 비슷한 그림을 만들어냈다.
  • 이미지 설명과 이미지 생성 프롬프트 복원은 다른 문제다.
