10-1

텍스트 임베딩 이해하기

의미를 숫자로 바꾸는 방법의 역사 — 원핫에서 워드투벡까지.

핵심 임베딩은 데이터의 의미를 압축한 숫자 배열이다. 의미가 숫자가 되는 순간, "비슷한가?"라는 질문이 거리 계산으로 바뀐다.

텍스트 임베딩이란

여러 문장의 텍스트를 임베딩 벡터로 변환하는 방식을 텍스트 임베딩 또는 문장 임베딩이라 부른다. 데이터의 의미를 숫자로 표현할 수 있다면 서로 유사한지, 관련이 있는지 같은 중요한 정보를 활용할 수 있다.

embedding.py 
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

smodel = SentenceTransformer('snunlp/KR-SBERT-V40K-klueNLI-augSTS')
dense_embeddings = smodel.encode(['학교', '공부', '운동'])

'''
          학교        공부        운동
학교  [0.9999999  0.5950744  0.32537562]
공부  [0.5950744  1.         0.5459569 ]
운동  [0.32537562 0.5459569  0.9999998 ]
'''
print(cosine_similarity(dense_embeddings))
쌍코사인 유사도해석
학교 ↔ 공부0.595"배움"이라는 공통 의미가 잡혔다
공부 ↔ 운동0.546둘 다 "하는 활동"이라는 점에서 중간
학교 ↔ 운동0.325가장 멀다
!

원문 교정 원문 교정

노트는 "공부, 운동은 0.325 만큼 유사함" 이라고 적었지만, 출력 행렬에서 0.325 는 학교 ↔ 운동 값이다(1행 3열 / 3행 1열). 공부 ↔ 운동 은 0.546(2행 3열)이다. 행렬을 읽을 때 i행 j열 = i번째와 j번째 문장의 유사도 이며, 대각선이 1.0 인 대칭 행렬이라는 점을 기억하면 헷갈리지 않는다.

원핫 인코딩

범주형 데이터 사이에 의도하지 않은 관계가 담기는 것을 방지한다는 장점이 있다. 하지만 충분히 관련 있는 단어 사이의 관계조차 표현할 수 없다는 치명적 단점이 있다.

onehot.py 모든 쌍이 0 
import numpy as np
from sklearn.metrics.pairwise import cosine_similarity

word_dict = {
    "school":  np.array([[1, 0, 0]]),
    "study":   np.array([[0, 1, 0]]),
    "workout": np.array([[0, 0, 1]]),
}

# [[0.]]
cosine_school_study = cosine_similarity(word_dict["school"], word_dict["study"])

# [[0.]]
cosine_workout_study = cosine_similarity(word_dict["workout"], word_dict["study"])

"학교"와 "공부" 사이에는 무언가 배운다는 공통점이 있지만, 원핫 인코딩에서는 그 의미를 전혀 살릴 수 없다. 서로 다른 축에 놓인 벡터라 모든 쌍의 유사도가 기계적으로 0 이 된다.

원핫은 모든 단어를 등거리에 놓고, 밀집 임베딩은 의미에 따라 거리를 다르게 준다 — 이것이 임베딩이 필요한 이유 전부다.

백오브워즈

비슷한 단어가 많이 나오면 비슷한 문서라는 가정으로 문서를 숫자로 바꾼다. 단어의 순서와 관계없이 등장한 단어와 그 횟수만 집계한다.

  • 아이디어가 직관적이고 구현이 간단한데도 잘 작동해, 문서의 의미를 표현하는 방법으로 오랫동안 쓰였다.
  • 하지만 많이 나온 단어가 문서의 의미를 대표하지 않는 경우가 있다. 한국어 기사에는 은/는/이/가/을/를 가 항상 가장 많이 나온다.

TF-IDF

어느 문서에나 나오는 단어 문제를 보완하기 위해, 많은 문서에 등장하는 단어의 중요도를 낮추는 수식을 쓴다.

기호의미
TF(w)특정 단어 w 가 이 문서에 등장한 횟수
DF(w)특정 단어 w 가 등장한 문서의 수
N전체 문서 수
TF-IDF(w)TF(w) × log(N / DF(w))

log(N / DF(w)) 는 특정 단어가 여러 문서에 등장할수록 작아진다. N 개 문서 전부에 존재하면 log(1) = 0 이 되어 그 단어의 점수는 완전히 사라진다 — 조사가 걸러지는 원리다.

이 방식은 백오브워즈의 문제를 해결했고, BM25 같은 변형은 현재까지도 가장 보편적인 연관도 점수 계산 방식으로 쓰인다. BM25 는 10-4 에서 다시 다룬다.

워드투벡

단어가 함께 등장하는 빈도 정보를 활용해 단어의 의미를 압축하는 단어 임베딩 방법이다. 학습 방식은 두 가지다.

방식입력 → 출력
CBOW주변 단어들 → 가운데 단어를 예측
스킵그램(Skip-gram)가운데 단어 → 주변 단어들을 예측
i

워드투벡의 한계, 그리고 다음 절 보강

워드투벡은 단어 하나에 벡터 하나를 고정 할당한다. 그래서 "배를 타다 / 배가 아프다 / 배를 먹다"의 "배"가 전부 같은 벡터가 된다(문맥 독립). BERT 이후의 모델은 문장 전체를 보고 같은 단어라도 문맥에 따라 다른 벡터를 만든다. 다음 절에서 다루는 문장 임베딩이 필요한 배경이다.

정리

  • 임베딩 = 의미를 압축한 숫자 배열. 유사도 판단이 거리 계산이 된다.
  • 원핫: 관계를 전혀 표현 못 함 → 모든 쌍의 유사도가 0.
  • 백오브워즈: 등장 횟수만 셈 → 조사/불용어가 지배.
  • TF-IDF: TF × log(N/DF) 로 흔한 단어의 가중치를 깎음. BM25 의 조상.
  • 워드투벡: 함께 등장하는 빈도로 의미를 학습(CBOW / 스킵그램). 단, 문맥 독립.
10-2

문장 임베딩 방식

교차 인코더는 정확하고, 바이 인코더는 확장된다.

핵심 바이 인코더는 각 문장을 독립적으로 임베딩하므로 미리 계산해 저장할 수 있다. 검색 시에는 쿼리 하나만 인코딩하면 되니 문서가 백만 개여도 BERT 연산은 1회다.

왜 문장 임베딩인가

워드투벡은 단어를 임베딩 벡터로 바꿔 단어 사이의 관계를 판단할 길을 열었다. 하지만 실제로 텍스트를 다룰 때는 단어가 아니라 문장이나 문단 같은 더 큰 단위를 쓴다. 여러 단어가 합쳐진 문장을 임베딩 벡터로 바꾸는 방법이 필요하다.

트랜스포머 인코더 구조를 활용한 BERT 모델은 입력 문장을 임베딩으로 변환하는 데 뛰어난 성능을 보였다. 그 위에서 문장 사이의 관계를 계산하는 방법이 두 가지로 갈린다.

교차 인코더

  • 하나의 BERT 모델에 검색 쿼리 문장과 검색 대상 문장을 함께 넣고 유사도 점수를 계산한다.
  • 두 텍스트 사이의 관계를 전부 계산하므로 정확도가 높다.
  • 하지만 다른 문장과의 유사도를 알려면 동일한 연산을 처음부터 다시 해야 한다.
  • 1,000개 문장 중 A 와 가장 유사한 것을 찾으려면 1,000번 전부 계산해야 한다.
  • BERT 의 어텐션 연산은 계산량이 많은 무거운 연산이라 가급적 적게 수행하는 게 좋다.
  • 결국 확장성이 떨어진다.

바이 인코더

  • 각 문장이 동일한 모델을 각각 통과해 문장별 임베딩으로 변환된다.
  • 변환된 임베딩끼리 코사인 유사도 같은 가벼운 계산으로 최종 점수를 낸다.
  • 각 문장의 임베딩이 독립적이므로, 비교 대상이 바뀌어도 추가 BERT 연산이 필요 없다.
  • 새로운 문장 B 와 가까운 문장을 검색할 때 B 에 대해서만 BERT 연산을 하면 되므로 계산량이 줄고 확장성이 높다.

바이 인코더 모델 구조

Sentence-Transformers 의 바이 인코더는 트랜스포머 층 + 풀링 층을 이어 붙인 구조다. 풀링 층이 토큰별 출력 여러 개를 문장 하나의 벡터로 압축한다.

bi_encoder.py 
from sentence_transformers import SentenceTransformer, models

# BERT 모델 (트랜스포머 층)
word_embedding_model = models.Transformer('klue/roberta-base')

# 풀링 층 — 입력 차원만 알려주면 된다
pooling_model = models.Pooling(word_embedding_model.get_word_embedding_dimension())

# 두 모듈 결합
model = SentenceTransformer(modules=[word_embedding_model, pooling_model])

'''
SentenceTransformer(
    (0): Transformer({'max_seq_length': 512, 'do_lower_case': False})
         with Transformer model: RobertaModel,
    (1): Pooling({
        'word_embedding_dimension': 768,
        'pooling_mode_cls_token': False,
        'pooling_mode_mean_tokens': True,      ← 기본값은 평균 모드
        'pooling_mode_max_tokens': False,
        'pooling_mode_mean_sqrt_len_tokens': False,
        'pooling_mode_weightedmean_tokens': False,
        'pooling_mode_lasttoken': False,
        'include_prompt': True
    })
)
'''
print(model)
풀링 모드동작비고
pooling_mode_cls_token
클래스 모드		첫 번째 토큰 [CLS] 의 출력 임베딩을 문장 임베딩으로 사용BERT 의 원래 설계 의도
pooling_mode_mean_tokens
평균 모드		문장 내 모든 토큰의 임베딩을 평균일반적으로 가장 많이 쓴다
pooling_mode_max_tokens
최대 모드		문장 길이 방향으로 각 차원의 최댓값을 취함특정 신호가 강한 경우

Sentence-Transformers 로 임베딩 생성

텍스트 임베딩
text_emb.py 
from sentence_transformers import SentenceTransformer, util

model = SentenceTransformer('snunlp/KR-SBERT-V40K-klueNLI-augSTS')

embeddings = model.encode(['잠이 안옵니다', '졸음이 옵니다', '기차가 옵니다'])
cos_scores = util.cos_sim(embeddings, embeddings)

'''
tensor([[1.0000, 0.6039, 0.1658],
        [0.6039, 1.0000, 0.2730],
        [0.1658, 0.2730, 1.0000]])

- '잠' 과 '졸음' 은 0.60 으로 유사하다
- '잠' 과 '기차' 는 0.17 로 유사하지 않다
  → "옵니다" 라는 같은 단어를 공유하는데도 낮게 나온다
'''
print(cos_scores)

이 예제가 재미있는 이유는 세 문장이 모두 "옵니다"로 끝난다는 데 있다. 키워드 기반이라면 셋 다 비슷하다고 판정했을 텐데, 문장 임베딩은 "잠"과 "졸음"이 가깝고 "기차"는 멀다는 것을 안다.

이미지 임베딩 — CLIP

CLIP 모델을 쓰면 이미지와 텍스트를 같은 벡터 공간에 놓을 수 있다. 이미지 벡터와 텍스트 벡터를 직접 비교하는 게 가능해진다.

image_emb.py 
from PIL import Image
from sentence_transformers import SentenceTransformer, util

model = SentenceTransformer('clip-ViT-B-32')

img_embs  = model.encode([Image.open('dog.jpg'), Image.open('cat.jpg')])
text_embs = model.encode(['A dog on grass', 'Brown cat on yellow background'])

'''
                  "A dog..."  "Brown cat..."
강아지 이미지  [[  0.2965,      0.1280],
고양이 이미지   [  0.1924,      0.2422]]

- 강아지 이미지: 강아지 텍스트 0.29 > 고양이 텍스트 0.13
- 고양이 이미지: 고양이 텍스트 0.24 > 강아지 텍스트 0.19
  → 각 행에서 올바른 짝이 가장 높다
'''
print(util.cos_sim(img_embs, text_embs))
i

CLIP 의 절대값은 낮게 나온다 보강

위 점수가 0.2~0.3 대로 작아 보이지만 정상이다. CLIP 은 이미지와 텍스트라는 서로 다른 모달리티를 맞춘 모델이라 절대 유사도의 스케일이 작다. 중요한 건 같은 행 안에서 어느 쪽이 더 큰가이지 값 자체가 아니다. 이 성질은 12-5 의 멀티 모달 검색에서 다시 확인할 수 있다(0.37 vs 0.37 로 상위권이 촘촘하다). CLIP 자체는 14-2 에서 자세히 다룬다.

구분상업용오픈소스
성능대량 데이터로 학습돼 뛰어남모델/도메인에 따라 편차
비용LLM 텍스트 생성보다 훨씬 저렴자체 인프라 비용
미세 조정임베딩 모델은 지원하지 않음내 데이터에 맞춰 가능

일부 텍스트 생성 모델은 파인튜닝을 지원하지만, 임베딩 모델에 대한 파인튜닝은 지원하지 않는다. 내 데이터에 맞춘 임베딩 모델을 만들고 싶다면 오픈소스로 가야 한다 — 11장이 그 이야기다.

정리

  • 교차 인코더: 두 문장을 함께 넣어 정확하지만, 비교 대상마다 재계산 → 확장성 없음.
  • 바이 인코더: 문장별 독립 임베딩 → 사전 계산 가능, 검색 시 쿼리만 인코딩.
  • 바이 인코더 = 트랜스포머 층 + 풀링 층. 풀링 모드는 CLS / 평균 / 최대이며 평균이 기본.
  • CLIP 을 쓰면 이미지와 텍스트가 같은 공간에 놓여 서로 비교된다.
  • 상업용 임베딩 모델은 성능이 좋지만 미세 조정이 안 된다.
10-3

의미 검색 구현하기

키워드가 하나도 겹치지 않아도 찾는다 — 그리고 가끔 엉뚱한 걸 찾는다.

핵심 의미 검색은 키워드가 겹치지 않아도 찾는 대신, 고유명사가 정확히 겹쳐야 하는 질문에는 약하다. 이 두 성질이 다음 절의 하이브리드 검색을 부른다.

의미 검색이란

단순 키워드 매칭이 아니라, 밀집 임베딩을 이용해 문장이나 문서의 의미를 고려한 검색을 수행하는 것이다. 구현은 간단하다 — 검색 쿼리를 문장 임베딩으로 바꿔 인덱스에서 찾으면 된다.

성공 사례
semantic_search.py 키워드 없이 찾아냄 
from datasets import load_dataset
from sentence_transformers import SentenceTransformer
import faiss

# 1,000건만 선택
klue_mrc_dataset = load_dataset('klue', 'mrc', split='train') \
    .train_test_split(train_size=1000, shuffle=False)['train']
sentence_model = SentenceTransformer('snunlp/KR-SBERT-V40K-klueNLI-augSTS')

# 문장 임베딩으로 변환
embeddings = sentence_model.encode(klue_mrc_dataset['context'])

# 인덱스 생성 — RDBMS 의 테이블처럼 벡터를 담아두는 공간
index = faiss.IndexFlatL2(embeddings.shape[1])
index.add(embeddings)

# 검색 쿼리를 문장 임베딩으로 변환
query = '이번 연도에는 언제 비가 많이 올까?'
query_embedding = sentence_model.encode([query])

# 인덱스에서 검색 (3 = 가져올 개수)
distances, indices = index.search(query_embedding, 3)

'''
(정답) 올여름 장마가 17일 제주도에서 시작됐다. 서울 등 중부지방은 예년보다 사나흘 정도 늦은
(오답) 연구 결과에 따르면, 오리너구리의 눈은 대부분의 포유류보다는 어류인 칠성장어나 먹장어, 그
(오답) 연구 결과에 따르면, 오리너구리의 눈은 대부분의 포유류보다는 어류인 칠성장어나 먹장어, 그
'''
for inx in indices[0]:
    print(klue_mrc_dataset['context'][inx][:50])

왜 실패했나

쿼리에는 "로버트 헨리 딕" 이라는 결정적인 고유명사가 들어 있다. 그런데 임베딩은 이 이름 대신 "장군 / 1940년대 / 연구소" 같은 전반적인 분위기를 잡아버렸다. 밀집 임베딩은 의미를 압축하는 과정에서 희귀한 고유명사의 신호를 흐린다. 반대로 키워드 검색이라면 "로버트 헨리 딕"이 들어간 문서를 즉시 1위로 올렸을 것이다.

두 검색은 강점이 정확히 어긋나 있다 — 그래서 합치는 것이 자연스러운 다음 수순이다.

10-4

검색 방식을 조합해 성능 높이기

점수를 더하지 말고 순위를 더한다 — 상호 순위 조합.

핵심 BM25 점수와 임베딩 유사도는 분포가 다르므로 그냥 더하면 한쪽이 지배한다. 그래서 점수 대신 순위를 합친다.

왜 조합하는가

키워드 검색은 동일한 키워드가 많이 포함될수록 유사도를 높게 평가한다. 의미 검색과는 장단점이 정확히 반대다. 각자의 단점을 서로 메우기 위해 두 방식을 합치는 것이 하이브리드 검색이다.

키워드 검색 방식 — BM25

  • TF-IDF 와 유사한 통계 기반 스코어링에 문서 길이 가중치를 추가한 알고리즘이다.
  • 간단하고 계산량이 적으면서도 성능이 뛰어나, 대표적인 검색 엔진인 Elasticsearch 의 기본 알고리즘으로 쓰인다.
  • 기본 로직은 TF-IDF 와 같다 — 많은 문서에 등장하는 토큰은 중요도를 낮게, 특정 문서에 많이 등장하는 토큰은 높게 본다.
  • 차이는 두 가지다: 단어 빈도 항의 포화 효과와 문서 길이의 영향을 고려한다.
i

포화 효과와 길이 정규화가 하는 일 보강

포화 효과: TF-IDF 에서 단어가 100번 나오면 점수도 100배다. 하지만 "장마"가 10번 나온 기사와 100번 나온 기사가 10배 더 관련 있지는 않다. BM25 는 TF 가 커질수록 증가폭이 완만해져 어느 지점에서 사실상 상한에 수렴한다.
길이 정규화: 긴 문서는 단순히 길다는 이유로 모든 단어의 빈도가 높다. BM25 는 문서 길이를 평균 길이로 나눠 보정해, 짧고 정확한 문서가 길고 산만한 문서에 밀리지 않게 한다.

상호 순위 조합 이해하기

하이브리드 검색을 하려면 통계 기반 점수와 임베딩 유사도 점수를 하나로 합쳐야 한다. 문제는 두 점수의 분포가 다르다는 것이다. 그냥 더하면 둘 중 하나의 영향이 훨씬 크게 반영된다.

점수범위성질
BM250 ~ 상한 없음문서/쿼리에 따라 스케일이 크게 요동친다
코사인 유사도−1 ~ 1 (보통 0 ~ 1)범위가 고정돼 있고 변동이 작다

이 문제를 해결하기 위해 상호 순위 조합(RRF, Reciprocal Rank Fusion)은 점수 자체가 아니라 각 검색에서의 순위를 활용해 최종 점수를 산출한다.

flowchart LR
  Q["쿼리"] --> BM["BM25 검색"]
  Q --> SE["의미 검색"]
  BM --> R1["순위 목록 A
1위 / 2위 / 3위 ..."]
  SE --> R2["순위 목록 B
1위 / 2위 / 3위 ..."]
  R1 --> RRF["상호 순위 조합
순위의 역수를 합산"]
  R2 --> RRF
  RRF --> F["최종 순위"]
RRF 는 점수를 버리고 순위만 쓴다 — 스케일 정규화라는 까다로운 문제를 아예 우회하는 방식이다.
i

RRF 의 실제 계산 보강

문서 d 의 최종 점수는 각 검색기에서의 순위 r 에 대해 Σ 1 / (k + r) 로 계산한다(k 는 보통 60). 순위의 역수이므로 상위권의 차이는 크게, 하위권의 차이는 작게 반영된다 — 1위와 2위의 기여 차이가 50위와 51위의 차이보다 훨씬 크다. 두 검색 모두에서 상위권인 문서가 자연스럽게 위로 올라오는 구조다.

!

노트 상태 안내

원문 노트의 10-5 「하이브리드 검색 구현하기」 는 제목만 있고 본문이 "패스"로 비어 있어 이 정리본에서는 아이템으로 만들지 않았다. BM25 구현과 RRF 결합 코드가 그 자리에 들어갈 내용이다.

정리

  • 키워드 검색과 의미 검색은 장단점이 반대라서 합치는 게 이득이다.
  • BM25 = TF-IDF + 포화 효과 + 문서 길이 정규화. Elasticsearch 의 기본값.
  • 두 점수는 분포가 달라 단순 합산이 안 된다.
  • RRF 는 점수 대신 순위의 역수를 합산해 이 문제를 우회한다.
