ITEM 8-1

헬스체크를 지원하는 도커 이미지 만들기

도커는 기본적으로 프로세스가 살아 있는지만 본다. 앱이 일을 하는지는 이미지가 직접 알려 줘야 한다.

핵심 HEALTHCHECK 는 앱의 실제 상태를 도커에게 알려 주는 계약이다. 도커는 그 결과를 상태로 기록만 하고, 그것을 보고 무엇을 할지는 오케스트레이터가 결정한다.

도커가 확인하는 앱의 상태

  • 도커는 컨테이너 내부 앱의 프로세스 실행 상태를 감지한다.
  • 프로세스가 종료되면 도커 컨테이너도 같이 종료된다.

프로세스만 확인하는 방법의 문제점

프로세스가 여전히 실행 중이어도 실제 앱이 API 요청을 처리할 수 없다면 죽은 것과 다름없다.

terminal 
$ docker run -d -p 8080:80 diamol/ch08-numbers-api
17cbf30ff3bdd1de5f128786e0bf4bb1bf10152f95fdee8d8eb429c9dffe82af

$ curl http://localhost:8080/rng
82
$ curl http://localhost:8080/rng
20
$ curl http://localhost:8080/rng
66

# 4번째부터는 HTTP 500 을 반환 → 앱이 비정상 동작
$ curl http://localhost:8080/rng
{"type":"...rfc7231#section-6.6.1","title":"An error occured while processing your request.","status":500,"traceId":"|63e19d6d-433b13eab37d0c35."}

# 그런데 컨테이너는 여전히 정상 작동 중으로 보인다
$ docker ps
CONTAINER ID   IMAGE                     COMMAND                   CREATED          STATUS          PORTS                    NAMES
17cbf30ff3bd   diamol/ch08-numbers-api   "dotnet /app/Numbers…"    25 seconds ago   Up 24 seconds   0.0.0.0:8080->80/tcp     fervent_black
×

이것이 문제의 전부다

STATUS 는 Up 24 seconds 인데 모든 요청이 500 을 뱉는다. 로드밸런서도, 오케스트레이터도, 모니터링도 이 컨테이너를 정상으로 판단해 계속 트래픽을 보낸다. 프로세스 생존 여부만으로는 앱의 상태를 알 수 없다.

HEALTHCHECK 인스트럭션

  • 도커는 앱이 실제로 정상인지 확인하는 로직을 이미지에 넣을 수 있는 기능을 제공한다.
  • --fail 옵션을 붙이면 curl 이 받은 HTTP 상태를 종료 코드로 도커에 전달한다.
  • 헬스체크 주기는 기본 30초 간격이며, 3번 이상 실패하면 비정상으로 간주한다.
Dockerfile.v2 
# multi-stage build commands...

FROM diamol/dotnet-aspnet

ENTRYPOINT ["dotnet", "/app/Numbers.Api.dll"]
HEALTHCHECK CMD curl --fail http://localhost/health

WORKDIR /app
COPY --from=builder /out/ .
!

원문 보강 — 종료 코드 2 는 예약값이다 원문 교정

노트에는 "0 은 정상, 이외는 모두 비정상"으로 적혀 있지만, 공식 Dockerfile 레퍼런스는 세 가지를 구분한다.

종료 코드의미
0success — 컨테이너가 정상이며 사용 가능
1unhealthy — 컨테이너가 정상 동작하지 않음
2reserved — 예약값이므로 사용하지 말 것

커스텀 체크 스크립트를 만들 때 exit 2 를 쓰지 않도록 주의한다. 실패는 반드시 exit 1 로 표현한다.

i

HEALTHCHECK 옵션 기본값 (공식 문서 기준) 보강

옵션기본값의미
--interval30s체크 간격
--timeout30s이 시간을 넘기면 실패로 간주하고 SIGKILL
--retries3연속 실패 횟수. 이만큼 실패해야 unhealthy
--start-period0s기동 유예 시간. 이 동안의 실패는 retries 에 세지 않는다
--start-interval5sstart-period 동안의 체크 간격. Docker Engine 25.0 이상 필요

상태는 처음에 starting 이고, 한 번이라도 통과하면 healthy, 연속으로 retries 만큼 실패하면 unhealthy 가 된다.

Log 에 출력이 남는 이유 보강

헬스체크 명령이 stdout / stderr 로 쓴 텍스트는 도커가 상태에 함께 저장한다(선두 4096바이트). 그래서 위처럼 curl: (22) ... 원문이 그대로 보인다. 커스텀 체크를 만들 때 실패 이유를 한 줄 출력해 두면 장애 시 docker inspect 만으로 원인을 알 수 있다. 상태가 바뀌는 순간에는 health_status 이벤트도 발생하므로 docker events 로 감시할 수 있다.

헬스체크가 실패해도 변화가 없는 이유

  • 헬스체크에 실패했다면 무언가 조치를 해서 앱을 다시 띄워야 할 것 같은데 변화가 없다.
  • 도커가 이런 컨테이너를 감지해 재시작할 수는 있지만, 재시작하는 동안 앱은 중단된다.
  • 컨테이너 교체 작업이 상황을 더 악화시키지 않으리라는(스토리지 초기화 등) 보장이 없어 그대로 둔다.
  • 도커 스웜이나 쿠버네티스로 클러스터링을 한다면, 이 헬스체크를 근거로 고가용성을 보장할 수 있다.
✓

역할 분담이 명확하다

이미지는 상태를 알리고, 플랫폼은 그 상태를 보고 조치한다. 단일 도커 엔진에는 "여분의 컨테이너를 먼저 띄운 뒤 옛것을 내린다"는 개념이 없으므로 섣불리 재시작하지 않는 것이 안전한 선택이다. 스웜이나 쿠버네티스에는 그 개념이 있으므로 같은 헬스체크가 실제 자동 복구로 이어진다.

정리

  • 프로세스 생존만으로는 앱 상태를 알 수 없다. Up 인데 전부 500 일 수 있다.
  • HEALTHCHECK 로 앱이 직접 상태를 알린다. 0 = 정상, 1 = 비정상, 2 는 예약값.
  • 기본값은 30초 간격 / 30초 타임아웃 / 3회 연속 실패. 기동이 느리면 --start-period 를 준다.
  • 단일 엔진은 상태를 기록만 한다. 조치는 오케스트레이터의 몫이다.
ITEM 8-2

디펜던시 체크가 적용된 컨테이너 실행하기

의존 대상이 준비되지 않았다면 아예 시작하지 않고 죽는 편이 낫다.

핵심 디펜던시 체크에는 전용 인스트럭션이 없다. 실행 명령 앞에 체크 로직을 붙이고 && 로 이어 붙이는 방식으로 구현한다. 실패하면 컨테이너가 그대로 종료된다.

분산 앱에서 발생할 수 있는 문제

  • 예를 들어 API 서버와 웹 서버를 띄운다고 하자.
  • 아직 API 서버가 준비되지 않았거나 에러가 난 상태에서 웹 서버를 시작하면 문제가 생긴다.
  • 이상이 생긴 컨테이너를 교체할 때는 처음 앱을 실행할 때처럼 컨테이너 간 의존 관계를 고려하지 않기 때문이다.

문제 상황

  • 기존에 있던 API 서버를 삭제하고 진행한다.
  • 웹에 접속은 되지만 숫자를 요청하면 에러가 발생한다.
terminal 
# 싹 다 삭제
$ docker rm -f $(docker ps -aq);
a598b37fbf04

# 웹 서버만 실행 (API 서버는 없는 상태)
$ docker run -d -p 8082:80 diamol/ch08-numbers-web
da49926d76a9fbfdfd9ffa0502aa82f2fa64e6403d6eb931e1cd0e04b4a6336e

# 정상적으로 웹 서버가 구동되는 모습
$ docker ps
CONTAINER ID   IMAGE                     COMMAND                   CREATED          STATUS          PORTS                  NAMES
da49926d76a9   diamol/ch08-numbers-web   "dotnet /app/Numbers…"    33 seconds ago   Up 32 seconds   0.0.0.0:8082->80/tcp   lucid_gates
웹 서버는 멀쩡히 떠 있고 컨테이너 상태도 Up 이다 — 의존 대상이 없다는 사실은 사용자가 버튼을 누른 뒤에야 드러난다.

의존 관계 만족 여부 추가하기

별도의 인스트럭션이 있는 게 아니라, 앱 실행 명령에 체크 로직을 덧붙이는 방법으로 구현한다.

Dockerfile.v2 
FROM diamol/dotnet-aspnet

ENV RngApi:Url=http://numbers-api/rng

# curl 요청이 성공해야만 dotnet 커맨드가 실행된다
CMD curl --fail http://numbers-api/rng && \
    dotnet Numbers.Web.dll

WORKDIR /app
COPY --from=builder /out/ .

✓

"빨리 실패하기(fail fast)"가 목적이다

컨테이너가 Exited 로 끝나는 건 실패가 아니라 의도한 동작이다. 반쯤 동작하는 컨테이너가 트래픽을 받아 사용자에게 에러를 보여 주는 것보다, 아예 뜨지 않아 플랫폼이 재시도하게 만드는 편이 낫다. 8-4 의 restart: on-failure 와 짝을 이룰 때 비로소 "될 때까지 재시도"가 완성된다.

결론

  • 헬스체크와 의존 체크를 갖췄다면 이제 컨테이너 플랫폼 환경에 적합한 앱이라고 할 수 있다.
  • 외부 도구를 쓸 수도 있지만, 단순한 방법으로도 목적을 달성할 수 있으니 굳이 외부 도구에 의존할 필요는 없다.

정리

  • 의존 대상이 준비되지 않은 채로 뜬 앱은 Up 이지만 쓸모가 없다.
  • 디펜던시 체크는 CMD 체크 && 앱실행 형태로 구현한다. 전용 인스트럭션은 없다.
  • 실패 시 컨테이너가 종료되는 것이 정상이다. 재시도는 플랫폼이 맡는다.
ITEM 8-3

앱 체크를 위한 커스텀 유틸리티 만들기

체크하려고 curl 을 넣는 순간, 공격자에게 다운로드 도구를 쥐여 준 셈이 된다.

핵심 체크 유틸리티를 앱과 같은 언어로 만들면 추가 소프트웨어 없이 체크가 가능하고, 앱의 설정을 그대로 재사용할 수 있으며, 플랫폼이 바뀌어도 그대로 동작한다.

유틸리티를 만드는 이유

  • 모순 같지만, 앞 절에서는 curl 정도로 충분하다고 했다.
  • 하지만 실무에서는 테스트를 위해 curl 을 쓰지 않는다. 보안 정책상 포함이 불가능한 경우가 많다.
  • 도커 이미지에는 앱을 구동하기 위한 최소한의 내용만 들어가야 한다.
  • 이런 이유로 앱과 같은 언어로 만든 별도의 유틸리티를 쓰는 편이 낫다.

커스텀 유틸리티의 장점

  • 앱과 같은 코드 / 도구라서 별도의 추가 소프트웨어를 포함하지 않아도 된다.
  • 셸 스크립트로 표현하기 까다로운 로직을 작성할 수 있다.
  • 앱과 같은 설정을 사용해 누락되는 부분을 최소화할 수 있다.
  • 앱과 같은 환경에서 실제 컨테이너 실행 전에 모든 사항을 검증할 수 있다.
flowchart LR
  B1["builder (FROM sdk, 앱 빌드)"] -->|"COPY --from"| APP["최종 이미지 (FROM runtime)"]
  B2["check-builder (FROM sdk, 유틸 빌드)"] -->|"COPY --from"| APP
  APP -.->|"HEALTHCHECK 시 실행"| U["Utilities.HttpCheck.dll"]
  APP -.->|"컨테이너 진입점"| A["Numbers.Api.dll"]
앱과 체크 유틸리티를 각자의 스테이지에서 빌드해 최종 이미지에 함께 담는다 — SDK 는 두 빌더 스테이지에만 있고, 최종 이미지에는 런타임과 두 개의 dll 만 남는다. curl 을 넣을 필요가 없어진다.

커스텀 유틸리티를 적용한 컨테이너 시작

--health-interval 플래그로 헬스체크 주기를 5초로 줄였다.

!

오탈자 교정 원문 교정

원문에는 --health-inverval 로 적혀 있다. 올바른 플래그는 --health-interval 이다.

ENTRYPOINT ["dotnet", "Numbers.Api.dll"]
HEALTHCHECK CMD ["dotnet", "Utilities.HttpCheck.dll", "-u", "http://localhost/health"]

WORKDIR /app
COPY --from=http-check-builder /out/ .
COPY --from=builder /out/ .

웹 서버 실행 시 의존 관계 체크하기

curl 로그와 비교해 보자 보강

8-2 의 curl 은 진행률 표시줄까지 찍고 curl: (6) 이라는 curl 의 종료 코드를 남겼다. 커스텀 유틸리티는 HTTPCheck: error. Url ..., exception ... 한 줄로 어떤 URL 이 왜 실패했는지를 바로 알려 준다. 로그 품질도 자체 유틸리티의 이점이다.

커스텀 유틸리티의 장점 (다시)

  • 컨테이너 플랫폼마다 헬스체크와 디펜던시 체크를 정의하고 실행하는 방법이 모두 다르다.
  • 커스텀 유틸리티를 쓰면 플랫폼과 관계없이 어떤 환경에서도 그대로 동작시킬 수 있다.

정리

  • 체크를 위해 curl 을 넣으면 공격자에게도 다운로드 도구를 주는 셈이다.
  • 앱과 같은 언어로 만든 체크 유틸리티를 별도 빌드 스테이지에서 만들어 최종 이미지에 함께 담는다.
  • URL 대신 설정 키를 넘겨 앱과 체크가 같은 설정을 보게 한다.
  • --health-interval 로 실행 시점에 주기를 조절할 수 있다.
ITEM 8-4

도커 컴포즈에 헬스 체크와 디펜던시 체크 정의하기

기동 순서를 보장하는 대신, 순서가 틀려도 결국 맞춰지게 만든다.

핵심 depends_on 을 빼고 헬스체크 + restart: on-failure 조합으로 가면, 기동 순서를 보장하지 않아도 재시도를 거쳐 결국 정상 상태에 도달한다.

도커 컴포즈의 헬스체크 옵션

컴포즈 설정에서는 헬스체크 관련 옵션을 더 세세하게 지정할 수 있다.

옵션의미
interval헬스체크 실시 간격
timeout언제까지 응답을 받지 못하면 실패로 처리할지
retries상태를 이상으로 간주할 때까지 필요한 연속 실패 횟수
start_period컨테이너 실행 후 몇 초 뒤에 헬스체크를 처음 시작할지. 부트스트랩이 오래 걸리는 앱은 조절이 필요하다

원문 교정 — 오탈자 원문 교정

원문의 retires 는 retries 의 오타다.

docker-compose.yml 
services:
  numbers-api:

디펜던시 체크와 재시작 정책

  • restart: on-failure 로 컨테이너 시작 실패 시 재시작하게 한다.
  • 미리 정의해 둔 유틸리티로 헬스체크와 의존 관계 체크를 함께 수행한다.
docker-compose.yml 
services:
  numbers-web:
    image: diamol/ch08-numbers-web:v3
    restart: on-failure
    environment:
      - RngApi__Url=http://numbers-api/rng
    ports:
      - "8088:80"
    healthcheck:
      test: ["CMD", "dotnet", "Utilities.HttpCheck.dll", "-t", "150"]
      interval: 5s
      timeout: 1s
      retries: 2
      start_period: 10s
    networks:
      - app-net

이 스크립트에 대한 의문점

  • 이전 스크립트에서는 depends_on 으로 의존 관계를 설정했다.
  • 여기서 쓰지 않은 이유는, 도커 컴포즈가 의존 관계 체크를 할 수 있는 범위가 단일 서버로 제한되기 때문이다.
  • 실제 운영 환경에서는 무슨 일이 벌어질지 예측하기 어렵기 때문에 이 속성을 제거했다.
  • 이 스크립트는 실행 순서를 보장하지 않지만, 헬스체크와 restart 옵션을 통해 결국 컨테이너가 정상 상태에 도달한다.

  C["Created (디펜던시 체크 수행)"] -->|"API 아직 준비 안 됨"| E["Exited (체크 실패)"]
  E -->|"restart: on-failure 로 재시작"| C
  C -->|"API 준비 완료"| U["Up / healthy"]
순서를 보장하는 대신 될 때까지 다시 시도한다 — 웹이 API 보다 먼저 떠도 디펜던시 체크에 걸려 종료되고, restart: on-failure 가 다시 띄운다. API 가 준비되는 순간 그 재시도가 성공한다.
↑

지금은 depends_on 으로도 준비 완료를 기다릴 수 있다 최신 반영

노트가 depends_on 을 뺀 것은 "시작만 확인하고 준비는 확인하지 못한다"는 한계 때문이었다. 현재 컴포즈 스펙은 긴 문법으로 조건을 지정할 수 있어서 헬스체크 통과까지 대기가 가능하다.

compose.yaml 현재 가능 
  numbers-web:
    depends_on:
      numbers-api:
        condition: service_healthy    # 헬스체크 통과까지 대기
        restart: true                 # 의존 서비스가 갱신되면 이 서비스도 재시작

다만 이것은 단일 호스트 안에서만 유효하다는 원문의 지적은 여전히 옳다. 클러스터로 나가면 컴포즈가 기동 순서를 통제할 수 없으므로, 앱 자체가 의존 대상의 부재를 견디도록 만드는 것이 근본 해법이라는 결론은 그대로다.

i

restart 정책 네 가지 보강

값동작
no기본값. 재시작하지 않는다
on-failure0 이 아닌 종료 코드로 끝났을 때만 재시작
always어떤 이유로 종료돼도 재시작. 도커 재시작 시에도 다시 뜬다
unless-stoppedalways 와 같지만, 사람이 명시적으로 멈춘 것은 다시 띄우지 않는다

디펜던시 체크에는 on-failure 가 맞다. 체크 실패는 0 이 아닌 코드로 끝나므로 재시도되고, 정상 종료는 재시작되지 않기 때문이다.

정리

  • 컴포즈의 healthcheck 로 interval/timeout/retries/start_period 를 세밀히 지정한다.
  • 기동 순서를 보장하는 대신 헬스체크 + restart: on-failure 로 수렴시킨다.
  • 현재는 depends_on + condition: service_healthy 로 준비 완료 대기가 가능하다. 단, 단일 호스트 한정.
ITEM 8-5

헬스체크와 디펜던시 체크로 복원력 있는 앱을 만들 수 있는 이유

순서를 맞추려 애쓰는 대신, 순서가 틀려도 스스로 회복하는 앱을 만든다.

핵심 일시적인 에러를 플랫폼이 알아서 해결하게 만드는 것이 자기 수복이다. 앱은 상태를 정직하게 알리고, 플랫폼은 그 신호를 보고 컨테이너를 갈아 끼운다.

헬스체크와 디펜던시 체크가 활약하는 부분

  • 이 두 기능을 쓰면 굳이 플랫폼이 실행 순서를 보장할 필요가 없다.
  • 대규모 시스템이라도 최대한 빠르게 뜨고, 반복적인 체크를 통해 빠르게 정상 상태로 올리면 된다.
  • 클러스터링된 여러 컨테이너 중 하나에서 에러가 발생하면 다른 컨테이너를 빠르게 띄울 수 있다.

자기 수복 능력

일시적인 에러를 플랫폼에서 해결해 주는 것을 말한다.

앱 시작 시 라이프사이클
시작 실패는 최종 상태가 아니라 경유 상태다 — 의존 대상이 준비될 때까지 Exited → 재시작을 반복하다가 결국 healthy 로 수렴한다.
앱 가동 중 라이프사이클
된 다음 기존 컨테이너를 종료하는 순서가 중요하다
새 컨테이너가 healthy 가 된 뒤에 옛 컨테이너를 내린다 — 순서가 반대면 그 사이에 서비스가 비게 된다. 이 순서를 지켜 주는 것이 오케스트레이터의 역할이다.
!

자기 수복이 고칠 수 있는 것과 없는 것 보강

컨테이너 교체로 해결되는 것은 일시적인(transient) 문제뿐이다. 메모리 누수, 커넥션 고갈, 데드락처럼 재시작하면 초기화되는 상태가 여기 해당한다.

반대로 영속적인 문제는 재시작이 오히려 상황을 악화시킨다. DB 가 내려갔거나 설정이 잘못됐다면, 컨테이너는 뜨고 죽기를 무한 반복하면서 의존 대상에 재접속 폭풍을 일으킨다. 그래서 자기 수복은 모니터링과 함께 운영해야 한다. 재시작 횟수 자체를 지표로 잡아 두면 "고쳐지고 있는 것"과 "무한 반복 중인 것"을 구분할 수 있다. 이것이 9장 의 주제다.

정리

  • 기동 순서를 보장하는 대신, 순서가 틀려도 재시도로 수렴하게 만든다.
  • 가동 중 문제는 새 컨테이너를 먼저 healthy 로 만든 뒤 옛것을 내리는 순서로 교체한다.
  • 자기 수복이 고치는 건 일시적 문제뿐이다. 영속적 문제는 무한 재시작으로 이어지므로 모니터링이 필요하다.
