ITEM 11-1

도커를 이용한 CI 절차

CI 서버가 아무것도 설치하지 않아도 되게 만드는 것. 그것이 도커가 CI 에 가져오는 변화다.

핵심 빌드도 테스트도 컨테이너 안에서 돌면, CI 서버가 바뀌어도 결과가 같다. 자동화된 테스트를 이미지 빌드 단계에 넣으면 테스트 실패가 곧 빌드 실패가 된다.

CI 에서 어려운 점

  • 모든 CI 파이프라인은 프로젝트마다 다르다.
  • 도커는 이러한 CI 절차의 일관성을 유지해 준다.
  • 자동화된 테스트 또한 이미지 빌드 단계에 포함되므로, 빌드가 실패하면 CI 도 중단된다.

도커와 함께하는 CI 플로우

세 단계가 모두 컨테이너 안이라는 것이 요점이다 — 코드 로딩만 CI 서버가 하고, 나머지는 전부 도커가 맡는다. 그래서 로컬에서든 CI 에서든 같은 명령으로 같은 결과가 나온다.
i

테스트를 빌드 단계에 넣는다는 것 보강

4-5 의 멀티 스테이지 빌드에서 테스트 스테이지를 하나 두면, 테스트 실패가 곧 docker build 실패가 된다. 별도의 테스트 실행 명령을 파이프라인에 따로 적을 필요가 없고, 테스트를 통과하지 못한 이미지는 애초에 만들어지지 않는다.

Dockerfile 
FROM sdk AS builder
COPY . .
RUN build

FROM builder AS test
RUN test          # 실패하면 여기서 빌드가 멈춘다

FROM runtime
COPY --from=builder /out/ .
✓

배포 단계가 "푸시"인 이유

마지막 단계가 다시 빌드하는 게 아니라 이미 만들어진 이미지를 푸시하는 것임에 주목하자. 10-5 에서 본 "한 번 빌드하고 그 산출물을 승격시킨다"가 파이프라인 위에서 그대로 구현된 모습이다.

정리

  • CI 서버에는 도커만 있으면 된다. 빌드 / 테스트 / 배포가 모두 컨테이너 안에서 돈다.
  • 테스트를 빌드 스테이지에 넣으면 테스트 실패가 곧 빌드 실패가 된다.
  • 배포 단계는 다시 빌드하지 않고 이미 만든 이미지를 푸시한다.
ITEM 11-2

도커를 이용한 빌드 인프라 구축

형상관리 / 레지스트리 / 자동화 서버 세 가지를 컨테이너로 띄우면 사내 파이프라인이 완성된다.

핵심 요즘은 매니지드 서비스가 좋아서 직접 구축할 이유가 줄었다. 그럼에도 폐쇄망처럼 외부로 코드를 내보낼 수 없는 환경에서는 이 구성이 여전히 유효하다.

언제 사용할까

  • 요즈음에는 신뢰성 있는 무료 매니지드 서비스가 많아서 굳이 직접 구축할 필요는 없다.
  • 하지만 폐쇄망 등 외부 네트워크로 공개하기 꺼려지는 경우에 유용하다.
역할이 실습에서 쓰는 도구흔한 매니지드 대안
형상관리GogsGitHub / GitLab
이미지 배포오픈소스 도커 레지스트리Docker Hub / ECR / GHCR
자동화 서버젠킨스GitHub Actions / GitLab CI

$ docker-compose -f docker-compose.yml -f docker-compose-linux.yml up -d

$ echo '\n127.0.0.1 registry.local' | sudo tee -a /etc/hosts

원문 교정 — 명령문 오타 원문 교정

원문에는 echo &'\n127.0.0.1 registry.local' 로 & 가 섞여 있다. 그래서 출력에 [1] + 53715 done echo 라는 잡 제어 메시지가 함께 찍혔다. 올바른 명령은 echo '\n127.0.0.1 registry.local' | sudo tee -a /etc/hosts 이며, 위 코드 블록에는 고쳐서 실었다.

i

/etc/hosts 를 왜 건드리나 보강

레지스트리 컨테이너의 이름이 registry.local 이라서, 이미지 이름도 registry.local:5000/... 형태가 된다. 그런데 호스트 PC 는 그 이름을 모른다. 컨테이너끼리는 도커 DNS 로 서로를 찾지만(7-3), 호스트에서 docker push 를 하려면 호스트도 그 이름을 풀 수 있어야 한다. /etc/hosts 한 줄이 그 역할을 한다.

i

젠킨스 컨테이너가 도커를 쓰려면 보강

컨테이너 안의 젠킨스가 docker build 를 실행하려면 도커 API 에 닿아야 한다. 가장 흔한 방법은 호스트의 도커 소켓을 바인드 마운트하는 것이다 (-v /var/run/docker.sock:/var/run/docker.sock).

다만 이것은 사실상 호스트 root 권한을 컨테이너에 넘기는 것과 같다. 소켓에 접근할 수 있으면 특권 컨테이너를 띄우거나 호스트 파일 시스템을 마운트할 수 있기 때문이다. 신뢰할 수 없는 코드를 빌드하는 CI 에서는 특히 위험하므로, 가능하면 원격 빌더나 소켓이 필요 없는 빌드 도구를 검토한다.

정리

  • 형상관리 / 레지스트리 / 자동화 서버 세 가지를 컨테이너로 띄우면 자체 CI 인프라가 된다.
  • 매니지드 서비스가 있으면 그쪽이 낫다. 자체 구축은 폐쇄망 같은 제약이 있을 때의 선택지다.
  • 사내 레지스트리 이름은 호스트에서도 풀려야 하므로 DNS 나 /etc/hosts 설정이 필요하다.
  • CI 컨테이너에 도커 소켓을 마운트하는 것은 편하지만 보안 위험이 크다.
ITEM 11-3

도커 컴포즈를 이용한 빌드 설정

레지스트리 주소를 변수로 빼고, 빌드 번호를 이미지에 새겨 넣는다.

핵심 ARG 는 빌드 시점에만 살아 있고 최종 이미지에 남지 않는다. 반대로 LABEL 은 이미지에 영구히 새겨진다. 이 둘을 짝지어 빌드 정보를 기록한다.

도커 컴포즈 환경 변수 기본값 설정

:- 문법으로 기본값을 지정한다.

docker-compose.yml 
services:
  numbers-api:
    image: ${REGISTRY:-docker.io}/diamol/...
i

:- 와 - 는 다르다 보강

문법동작
${VAR:-기본값}VAR 가 없거나 빈 문자열이면 기본값
${VAR-기본값}VAR 가 정의되지 않았을 때만 기본값 (빈 문자열은 그대로 씀)
${VAR:?메시지}없거나 비었으면 에러로 중단

필수 값에는 :? 를 쓰면 좋다. 값이 빠진 채로 엉뚱한 이미지를 만드는 대신 컴포즈가 그 자리에서 멈춘다.

새로운 인스트럭션

LABEL
  • Dockerfile 에 정의되는 키-값 쌍을 빌드되는 이미지에 적용해 준다.
Dockerfile 
LABEL version=3.0
ARG
  • 이미지를 빌드하는 시점에만 유효한 빌드 전용 변수다.
  • 실제 빌드된 이미지로 실행한 컨테이너에는 적용되지 않는다.
  • 보통 이미지 레이블에 들어갈 값을 제공하기 위해 쓴다.
Dockerfile 
ARG BUILD_NUMBER=0

둘을 함께 쓰기

CI 서버의 빌드 번호를 ARG 로 받아 LABEL 에 새기는 것이 전형적인 조합이다.

Dockerfile 
ARG BUILD_NUMBER=0
LABEL build_number=${BUILD_NUMBER}
terminal 
$ docker build --build-arg BUILD_NUMBER=421 -t myapp:2.1.421 .

# 이미지에 새겨진 레이블 확인
$ docker image inspect myapp:2.1.421 --format '{{.Config.Labels}}'
map[build_number:421]

ARG 로 비밀값을 넘기지 말 것 보강

ARG 값은 최종 이미지의 환경 변수로 남지는 않지만, docker history 에 그대로 보인다. 공식 문서도 자격 증명이나 API 토큰을 빌드 인자로 넘기지 말라고 명시적으로 경고한다. 빌드 중 비밀값이 필요하면 RUN --mount=type=secret 을 쓴다. 이 방식은 값이 레이어에 남지 않는다.

정리

  • ${VAR:-기본값} 으로 레지스트리 주소 같은 값을 환경에 따라 바꾼다. 필수 값에는 :?.
  • ARG 는 빌드 시점 전용, LABEL 은 이미지에 영구 기록.
  • CI 빌드 번호를 ARG 로 받아 LABEL 에 새기면 이미지 추적이 쉬워진다.
  • ARG 는 docker history 에 노출된다. 비밀값에는 쓰지 않는다.
