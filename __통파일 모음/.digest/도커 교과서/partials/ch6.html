ITEM 6-1

컨테이너 속 데이터가 사라지는 이유

읽기 전용 이미지 레이어 위에 컨테이너마다 얇은 기록 가능 레이어가 하나씩 얹힌다. 그 레이어의 수명이 컨테이너의 수명이다.

핵심 컨테이너의 파일 시스템은 공유되는 읽기 전용 레이어 + 컨테이너 전용 기록 가능 레이어다. 데이터가 사라지는 이유는 쓴 내용이 전부 후자에만 남고, 그 레이어가 컨테이너와 함께 삭제되기 때문이다.

컨테이너의 파일 시스템

  • 컨테이너의 디스크는 이미지 레이어를 순서대로 연결해 만든 가상 파일 시스템이다.
  • 모든 컨테이너는 독립된 파일 시스템을 갖는다.
  • 같은 이미지에서 실행된 컨테이너는 처음엔 같은 내용이지만, 한쪽의 파일을 수정해도 다른 쪽에는 영향이 없다.
컨테이너의 파일시스템이 독립적임을 확인해 보기

같은 이미지로 시작한 컨테이너지만 내부 내용물이 서로 다르다. 각 컨테이너가 독립적인 저장 공간을 가진다는 증명이다.

terminal 
$ docker run --name rn1 diamol/ch06-random-number
$ docker run --name rn2 diamol/ch06-random-number

$ docker cp rn1:/random/number.txt number1.txt
Successfully copied 2.05kB to /Users/imkdw/number1.txt
$ docker cp rn2:/random/number.txt number2.txt
Successfully copied 2.05kB to /Users/imkdw/number2.txt

$ cat number1.txt
10341

$ cat number2.txt
8719

컨테이너 파일시스템 구성

기본적으로 이미지 레이어와 컨테이너의 기록 가능 레이어로 나뉜다.

구분공유 여부쓰기수명
이미지 레이어 모든 컨테이너가 공유 ✗ 읽기 전용 이미지를 지울 때까지
기록 가능 레이어 컨테이너마다 하나씩 ✓ 수정 가능 컨테이너와 동일 — 지우면 함께 삭제
같은 이미지, 다른 난수 — 각자 자기 기록 가능 레이어에 썼기 때문이다. 아래 두 레이어는 물리적으로 한 벌만 존재하고 둘이 함께 본다.

이미지 레이어 수정하기

  • 읽기 전용이라 수정이 안 되는 게 맞지만, 기록 중 복사(copy-on-write) 방식으로 수정이 가능하다.
  • 컨테이너나 앱에서는 이 과정이 드러나지 않지만, 도커가 스토리지를 아끼는 매우 좋은 방법이다.
  • 컨테이너 속 파일을 수정하면 해당 컨테이너에만 영향을 미친다.
    • 이미지를 공유하는 다른 컨테이너나 이미지는 영향을 받지 않는다.
    • 수정된 파일은 그 컨테이너의 기록 가능 레이어에만 존재하기 때문이다.
i

기록 중 복사가 실제로 하는 일 보강

읽기 전용 레이어의 파일을 수정하면 도커는 그 파일을 기록 가능 레이어로 통째로 복사한 뒤 거기서 수정한다. 그래서 큰 파일을 한 바이트만 고쳐도 파일 전체가 복사되고, 그 순간 디스크와 시간을 쓴다. 데이터베이스처럼 큰 파일을 계속 쓰는 워크로드를 기록 가능 레이어 위에 두면 안 되는 성능상의 이유가 여기 있다. 그런 데이터는 볼륨이나 바인드 마운트로 뺀다.

예제
  • 최초 컨테이너 실행 시에는 https://... 문구가 출력된다.
  • 이후 "asdf" 문구가 담긴 파일을 f1 컨테이너에 복사했다.
  • f1 컨테이너를 다시 실행하니 복사한 내용이 출력된다.
terminal 
$ docker run --name f1 diamol/ch06-file-display
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ echo "asdf" > url.txt

$ docker container cp url.txt f1:/input.txt
Successfully copied 2.05kB to f1:/input.txt

$ docker container start --attach f1
asdf

컨테이너 스토리지 라이프사이클 확인하기

  • 최초 구동 이후 f3 컨테이너의 파일을 복사하니 컨테이너와 동일한 내용이 보인다.
  • 이후 f3 컨테이너를 삭제하니 No such container: f3 에러가 발생한다.
  • 컨테이너의 파일 시스템이 컨테이너와 동일한 라이프사이클을 지닌 것을 확인할 수 있다.
terminal 
$ docker run --name f3 diamol/ch06-file-display
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ docker container cp f3:/input.txt .
Successfully copied 2.05kB to /Users/imkdw/.

$ cat input.txt
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ docker rm -f f3
f3

$ docker container cp f3:/input.txt .
Error response from daemon: No such container: f3

컨테이너의 영속성?

  • 도커로 DB 를 운영하다가 컨테이너를 교체한다고 해 보자. 교체되면 지워지고 다시 뜨는 것이므로 내부 내용이 전부 삭제된다.
  • 이런 상황을 감안해 도커는 도커 볼륨(Docker Volume) 과 마운트(Mount) 를 제공한다.
  • 이 둘은 컨테이너와 다른 라이프사이클을 가지므로, 지속돼야 할 데이터를 담을 수 있다.

정리

  • 컨테이너 파일 시스템 = 공유되는 읽기 전용 이미지 레이어 + 컨테이너 전용 기록 가능 레이어.
  • 쓰기는 전부 기록 가능 레이어에 남고, 그 레이어는 컨테이너와 함께 사라진다.
  • 이미지 레이어 수정은 기록 중 복사로 처리된다. 큰 파일에는 비용이 크다.
  • 살아남아야 할 데이터는 볼륨이나 마운트로 컨테이너 밖에 둔다.
ITEM 6-2

도커 볼륨을 사용하는 컨테이너 실행하기

볼륨은 컨테이너를 위한 USB 다. 뽑아서 다른 컨테이너에 꽂을 수 있다.

핵심 볼륨은 이미지 / 컨테이너와 동급인 도커 리소스다. 그래서 docker volume ls 로 조회되고, 컨테이너를 지워도 남으며, 다른 컨테이너에 그대로 다시 붙일 수 있다.

도커 볼륨

  • 도커 볼륨은 도커에서 스토리지를 다루는 단위다.
  • 마치 컨테이너를 위한 USB 라고 이해하면 쉽다.

수동으로 직접 생성해서 컨테이너에 연결하기

  • docker volume create <volume_name> 으로 볼륨을 만들 수 있다.
  • -v 플래그로 컨테이너 시작 시 볼륨을 마운트할 수 있다.
  • 아래는 v1 컨테이너에서 데이터를 추가하면 v2 에도 반영되는(디스크 공유) 모습이다.
terminal 
# 도커 볼륨 생성
$ docker volume create todo-list
todo-list

# v1 컨테이너 시작
$ docker run -d -p 8011:80 -v todo-list:/data --name todo-v1 diamol/ch06-todo-list
7d0dcc71e0a98fe8a315a98d9d30a9504ad2e1c777c47add41c5c7a9810b91b1

# v2 컨테이너 시작 (같은 볼륨을 붙인다)
$ docker run -d -p 8012:80 -v todo-list:/data --name todo-v2 diamol/ch06-todo-list:v2
66b19a7f8118ee52addfa0bb570e883faec599c3505272b277f5a67696b70878
서로 다른 이미지 버전, 서로 다른 포트, 같은 데이터 — 볼륨을 공유하므로 v1 에서 넣은 항목이 v2 목록에 그대로 보인다. 컨테이너 교체형 업데이트가 가능한 이유가 이것이다.

Dockerfile 에서 VOLUME 인스트럭션 사용하기

VOLUME 인스트럭션은 VOLUME <target-directory> 형식으로 쓴다.

Dockerfile 
# 일부 내용

# set in the base image - `/data` for Linux, `C:\data` for Windows
VOLUME $SQLITE_DATA_DIRECTORY

# ...
terminal 
# 명시적인 -v 연결은 없지만 Dockerfile 의 VOLUME 때문에 볼륨이 붙는다
$ docker run -d --name todo1 -p 8010:80 diamol/ch06-todo-list
cbb8096739d34b4cc51a5dcc48b2c3c38b0c64a2721c260c9316d8785843e4c1

# mounts 항목에서 볼륨 관련 정보를 확인할 수 있다
$ docker inspect --format '{{.Mounts}}' todo1
[{volume 5baf8fce2819f63c731417e0be889db779460f88316ffc44d099c2ce9150f8f3 /var/lib/docker/volumes/5baf8fce.../_data /data local  true }]

# 볼륨은 도커에서 이미지나 컨테이너와 동급인 요소다
$ docker volume ls
DRIVER    VOLUME NAME
local     5baf8fce2819f63c731417e0be889db779460f88316ffc44d099c2ce9150f8f3
!

이름 없는 볼륨이 조용히 쌓인다 보강

VOLUME 인스트럭션만 있고 -v 로 이름을 주지 않으면, 위 출력처럼 해시 이름의 익명 볼륨이 컨테이너를 실행할 때마다 새로 생긴다. 컨테이너를 지워도 이 볼륨은 남으므로 실습을 반복하면 디스크가 계속 차오른다. docker volume ls 로 확인하고, 붙어 있지 않은 볼륨은 docker volume prune 으로 정리한다. 실제 데이터가 들어 있는 볼륨도 같이 지워지므로 반드시 목록을 먼저 확인할 것. 컨테이너를 지울 때 익명 볼륨까지 함께 지우려면 docker rm -v 를 쓴다.

정리

  • docker volume create + -v 볼륨명:컨테이너경로 가 기본형이다.
  • 같은 볼륨을 여러 컨테이너에 붙이면 데이터를 공유한다. 컨테이너 교체 업데이트의 기반이다.
  • Dockerfile 의 VOLUME 은 이름 없는 볼륨을 자동으로 만든다. 방치하면 디스크가 찬다.
ITEM 6-3

파일시스템 마운트를 사용하는 컨테이너 실행하기

볼륨이 도커가 관리하는 저장소라면, 바인드 마운트는 호스트의 특정 폴더를 그대로 꽂는 것이다.

핵심 바인드 마운트는 호스트 파일 시스템의 폴더를 컨테이너 폴더로 만든다. 호스트에서 접근 가능한 것이면 SSD 든 SAN 이든 컨테이너에서 그대로 쓸 수 있다.

볼륨의 장점

  • 컨테이너와 스토리지의 라이프사이클을 분리하면서, 도커를 쓰던 방식 그대로 스토리지를 제어할 수 있다.

바인드 마운트(Bind Mount)

  • 호스트의 스토리지를 컨테이너에 좀 더 직접적으로 연결하는 수단이다.
  • 즉 호스트 컴퓨터 파일 시스템의 폴더를 컨테이너 파일 시스템의 폴더로 만든다.
  • SSD, 디스크 어레이, SAN 등 호스트에서 접근 가능한 파일 시스템이면 무엇이든 컨테이너에서 쓸 수 있다.

--mount 플래그

컨테이너에서 읽기 전용으로 쓰게 하려면 --mount 옵션에 readonly 를 함께 지정할 수 있다.

terminal 
$ source="$(pwd)/databases" && target='/data'

$ mkdir ./databases

$ docker run --mount type=bind,source=$source,target=$target -d -p 8013:80 diamol/ch06-todo-list
6e071e5e8cdf9b1bb641ed5dc586144264fb3f1d6e0cb7c8396d47a81fcd5c40

$ ll ./databases
total 24
-rw-r--r--@ 1 imkdw  staff    12K 10 27 11:09 todo-list.db
i

볼륨과 바인드 마운트, 언제 무엇을 보강

볼륨바인드 마운트
저장 위치도커가 관리하는 영역호스트의 지정한 경로
호스트 경로 의존✓ 없음 (이식성 높음)✗ 경로가 머신마다 달라짐
호스트에서 직접 편집✗ 불편✓ 바로 가능
주 용도운영 데이터 (DB 등)개발 중 소스 공유, 설정 파일 주입

읽기 전용으로 붙이려면 --mount type=bind,source=...,target=...,readonly 로 쓴다. 설정 파일을 주입할 때는 이 옵션을 붙이는 게 안전하다.

정리

  • 바인드 마운트는 호스트 폴더를 컨테이너 폴더로 그대로 노출한다.
  • --mount type=bind,source=<호스트>,target=<컨테이너> 형식, readonly 를 붙일 수 있다.
  • 운영 데이터는 볼륨, 개발 중 소스 공유와 설정 주입은 바인드 마운트가 기본 선택이다.
ITEM 6-4

파일 시스템 마운트의 한계점

마운트는 합치는 게 아니라 덮는다. 그리고 그 규칙마저 OS 마다 다르다.

핵심 디렉터리를 마운트하면 원본이 기존 내용을 완전히 대체한다. 이미지 안에 있던 파일은 사라진 게 아니라 가려진 것이며, 마운트를 떼면 다시 나타난다.

기존 이미지의 파일 시스템 사용 불가

  • 이미 존재하는 대상 폴더에 마운트하면, 마운트의 원본 폴더가 기존 폴더를 완전히 대체한다.
  • 즉 이미지에 포함돼 있던 원래 파일은 사용할 수 없다.
terminal 
$ source="$(pwd)/new" && target='/init';

# 기존 이미지에 포함되어 있던 파일들
$ docker run diamol/ch06-bind-mount
abc.txt
def.txt

# 마운트된 디스크에 존재하는 파일들 — 이미지 쪽 파일은 보이지 않는다
$ docker run --mount type=bind,source=$source,target=$target diamol/ch06-bind-mount
1.txt
2.txt
×

실무에서 가장 자주 밟는 지뢰

개발 중 소스 폴더를 -v $(pwd):/app 로 붙이는 순간, 이미지 빌드 때 설치해 둔 /app/node_modules 가 호스트 폴더에 가려서 사라진다. 컨테이너 안에서 Cannot find module 이 뜨는 전형적인 원인이다. 해결은 그 하위 경로에 익명 볼륨을 겹쳐 덮어쓰기를 막는 것이다.

해결 
$ docker run -v $(pwd):/app -v /app/node_modules myapp
#                            └ 이 경로만 호스트가 아닌 볼륨으로 덮어 되살린다

OS 별 파일 시스템의 차이점 문제

호스트 컴퓨터의 파일 하나를 컨테이너에 이미 존재하는 디렉터리로 마운트할 때, OS 마다 결과가 다르다.

호스트 OS결과
유닉스 계열디렉터리의 파일이 합쳐져 이미지 + 호스트 마운트 파일이 모두 보인다
윈도우Invalid Mount Config 에러가 발생한다
!

단일 파일 마운트의 또 다른 함정 보강

리눅스에서 단일 파일을 마운트하면 inode 단위로 묶인다. 그래서 호스트에서 그 파일을 에디터로 저장할 때(대부분 임시 파일을 만들고 rename 하는 방식) 마운트가 끊겨, 컨테이너 안에서는 변경이 반영되지 않는다. 설정 파일을 실시간으로 갈아 끼워야 한다면 파일 하나가 아니라 그 파일이 든 디렉터리를 마운트하는 편이 안전하다.

정리

  • 디렉터리 마운트는 이미지의 기존 내용을 가린다. 합쳐지지 않는다.
  • node_modules 가 사라지는 문제는 하위 경로에 익명 볼륨을 겹쳐 해결한다.
  • 단일 파일 마운트는 OS 마다 동작이 다르고 에디터 저장에 끊긴다. 디렉터리 단위로 마운트하자.
ITEM 6-5

컨테이너 파일시스템이 만들어지는 방법

여러 출처를 하나의 가상 디스크로 합치는 것이 유니언 파일 시스템. 저장할 곳을 고르는 다섯 가지 선택지.

핵심 한 컨테이너에서 기록 가능 레이어는 정확히 하나이고, 나머지는 여러 개일 수 있다. 데이터를 어디에 둘지는 "이 데이터가 컨테이너보다 오래 살아야 하는가"로 갈린다.

유니언 파일 시스템(Union File System)

  • 모든 컨테이너는 도커가 여러 출처에서 모아 만든 단일 가상 디스크로 구성된 파일 시스템을 갖는다. 이것을 유니언 파일 시스템이라고 부른다.
  • 유니언 파일 시스템은 OS 마다 다르게 구현돼 있지만, 사용자가 신경 쓸 필요는 없다. 도커가 알아서 처리한다.
  • 파일 시스템 중 기록 가능 레이어는 하나만 가질 수 있고, 나머지는 여러 개가 가능하다.

컨테이너 스토리지 구성 시 고려사항

위로 갈수록 수명이 짧고, 아래로 갈수록 공유 범위가 넓다 — 기록 가능 레이어는 컨테이너와 함께 사라지고, 이미지 레이어는 모든 컨테이너가 함께 쓴다. 그 사이의 세 층이 "컨테이너보다 오래 살아야 하는 데이터"를 담는 자리다.
기록 가능 레이어
  • 캐싱 등 단기 저장에 적합하다.
  • 각 컨테이너마다 독립적이다.
  • 생명주기가 컨테이너와 동일해서 컨테이너가 삭제되면 같이 삭제된다.
로컬 바인드 마운트
  • 호스트 PC 와 컨테이너 간 데이터를 공유하기 위해 쓴다.
  • 예를 들어 개발 중인 코드를 컨테이너와 공유하면 다시 빌드하지 않고 바로 실행할 수 있다.
분산 바인드 마운트
  • 네트워크 스토리지와 컨테이너 간 데이터 공유를 위해 쓴다.
  • 가용성이 높지만 로컬 파일 시스템에 비해 지원하지 않는 기능이 있을 수 있다.
볼륨 마운트
  • 앱의 데이터를 볼륨에 영구히 저장할 수 있다(영속성).
  • 컨테이너를 교체하는 방식으로 앱을 업데이트해도 이전 버전 컨테이너의 데이터를 그대로 유지할 수 있다.
이미지 레이어
  • 컨테이너의 초기 파일 시스템을 구성한다.
  • 읽기 전용이며 여러 컨테이너가 공유한다.
i

고르는 기준 한 줄 보강

"컨테이너를 지웠을 때 같이 사라져도 되는가?" 하나만 물으면 된다. 사라져도 되면 기록 가능 레이어(임시 파일, 캐시), 남아야 하면 볼륨(운영 데이터), 호스트에서 직접 편집해야 하면 바인드 마운트(개발 소스, 설정 파일)다.

정리

  • 컨테이너 파일 시스템은 여러 출처를 겹쳐 만든 단일 가상 디스크(유니언 파일 시스템)다.
  • 기록 가능 레이어는 하나뿐이고, 나머지 층은 여러 개일 수 있다.
  • 수명 기준으로 고른다 — 임시는 기록 가능 레이어, 영속은 볼륨, 편집 필요는 바인드 마운트.
