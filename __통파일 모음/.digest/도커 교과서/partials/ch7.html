ITEM 7-1

도커 컴포즈 파일의 구조

컴포즈 파일은 "이 앱이 다 떠 있을 때 어떤 모습이어야 하는가"를 적은 문서다.

핵심 컴포즈 파일은 절차가 아니라 원하는 상태(desired state) 를 기술한다. docker run 에 붙이던 플래그들이 전부 YAML 의 필드로 옮겨 온 것이라고 보면 된다.

Docker Compose 란

  • 앱의 원하는 상태, 즉 모든 컴포넌트가 실행 중일 때 어떤 상태여야 하는지를 기술하는 파일이다.
  • docker run 에서 지정해야 하는 모든 옵션을 모아 놓은 단순한 형식의 파일이다.
docker-compose.yml 노트 원본 (구형 문법) 
version: "3.7"

services:
  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - "8020:80"
    networks:
      - app-net

networks:
  app-net:
    external:
      name: nat

주요 블록

version
  • 도커 컴포즈 파일 형식의 버전을 나타낸다.
  • 노트에는 "24.10.27 기준 deprecated 될 예정" 이라고 기록되어 있다.
services
  • 앱을 구성하는 모든 컴포넌트를 열거하는 부분이다.
  • 실제 컨테이너가 아닌 서비스 개념을 단위로 삼는다.
  • 하나의 서비스를 같은 이미지로 여러 개의 컨테이너에서 실행할 수 있다.
networks
  • 서비스 컨테이너가 연결될 도커 네트워크를 열거하는 부분이다.
↑

위 두 문법은 현재 버전에서 경고가 뜬다 최신 반영

노트의 예측대로 version 은 정리됐고, external 아래에 name 을 중첩하는 형태도 함께 바뀌었다. 로컬(Compose v5.1.2)에서 위 파일을 그대로 config 에 넣어 확인한 결과다.

verify 
$ docker compose -f docker-compose.yml config

warning: the attribute `version` is obsolete, it will be ignored, please remove it to avoid potential confusion
warning: networks.app-net: external.name is deprecated. Please set name and external: true

공식 문서도 version 을 "informative 할 뿐이며 쓰면 obsolete 경고가 뜬다"고 명시한다. 컴포즈는 이 값을 무시하고 항상 최신 스키마로 검증한다. 아래가 지금의 권장 형태다.

compose.yaml 현재 권장 
services:
  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - "8020:80"
    networks:
      - app-net

networks:
  app-net:
    external: true
    name: nat

도커 컴포즈를 통한 컨테이너 실행

  • external 필드는 이미 존재하는 네트워크가 있으니 새로 만들지 말라는 뜻이다. 윈도우는 도커 설치 시 nat 네트워크가 자동 생성되어 그것을 쓴다.
  • docker-compose up 으로 서비스를 구동할 수 있다. docker-compose.yml 파일을 찾아 그 내용대로 컨테이너가 뜬다.

docker-compose 대신 docker compose 최신 반영

노트 전반에 나오는 하이픈 있는 docker-compose 는 파이썬으로 만들어진 Compose V1 이고, 2023년 7월 이후 지원이 종료되어 새 Docker Desktop 에는 포함되지 않는다. 지금은 도커 CLI 플러그인인 Compose V2, 즉 공백으로 쓰는 docker compose 가 표준이다. 하위 명령과 옵션은 대부분 그대로라, 이 정리본의 실습 명령은 하이픈만 공백으로 바꾸면 그대로 동작한다. 파일명도 docker-compose.yml 과 compose.yaml 을 모두 인식하며, 새 프로젝트는 compose.yaml 이 권장 이름이다.

정리

  • 컴포즈 파일은 절차가 아니라 원하는 상태를 적는다. docker run 플래그가 YAML 필드가 된 것.
  • 단위는 컨테이너가 아니라 서비스다. 서비스 하나가 컨테이너 여러 개일 수 있다.
  • version 은 이제 obsolete, external.name 은 deprecated. external: true + name: 으로 쓴다.
  • 명령은 docker compose(공백)가 표준이다.

도커 컴포즈를 사용해서 여러 컨테이너로 구성된 앱 실행하기

핵심 컴포즈는 파일에 적힌 상태를 실현할 뿐이다. CLI 로 손댄 변경(스케일 아웃 등)은 파일에 없으므로, 다음 up 에서 파일 기준으로 되돌아간다.

원문 교정 — depends_on 은 "실행됨"까지만 보장한다 원문 교정

노트에는 "depends_on 을 통해 iotd, accesslog 가 모두 실행되고 나서 진행된다"고 적혀 있는데, 여기서 말하는 "실행"은 컨테이너가 시작된 상태일 뿐 앱이 요청을 받을 준비가 된 상태가 아니다. 스프링 부트가 부팅되는 몇 초 동안 image-gallery 는 이미 떠서 요청을 보낼 수 있다. 이 간극이 바로 8장의 디펜던시 체크가 필요한 이유다.

현재 컴포즈에서는 긴 문법으로 조건을 붙여 헬스체크 통과까지 기다리게 할 수 있다. 공식 문서가 지원하는 조건은 service_started, service_healthy, service_completed_successfully 세 가지다.

compose.yaml 개선 
  image-gallery:
    depends_on:
      iotd:
        condition: service_healthy      # 헬스체크를 통과할 때까지 대기
      accesslog:
        condition: service_started      # 기본값 — 시작만 확인

주의점

  • 도커 컴포즈로 앱을 관리한다면 내부적으로는 도커 API 에 명령을 보내는 방식이다.
  • 컴포즈 파일을 수정하거나 도커 CLI 로 직접 앱을 손대면, 앱이 컴포즈 파일에 기술된 구조와 어긋날 수 있다.
  • 예를 들어 앞서 스케일 아웃했던 서비스가, 컴포즈를 재시작하면 다시 1개로 줄어든다.
  • 도커 컴포즈로 리소스를 관리해야 앱이 파일과 일치한 상태로 유지된다.

되돌아가는 게 버그가 아니라 설계다

컴포즈는 매번 "파일에 적힌 상태"로 수렴시킨다. CLI 로 임시로 3개를 띄운 것은 파일에 없는 상태이므로 다음 up 에서 정리된다. 스케일 값을 유지하고 싶다면 파일의 deploy.replicas 에 적어 두거나 매번 --scale 을 함께 넘겨야 한다. 원하는 상태는 항상 파일에 적혀 있어야 한다는 원칙이 여기서도 그대로 적용된다.

정리

  • up 한 번으로 여러 서비스가 뜨고, --scale 로 골라서 늘릴 수 있다.
  • depends_on 은 기동 순서만 보장한다. 준비 완료를 기다리려면 condition: service_healthy 를 쓴다.
  • stop 은 정지, down 은 삭제, down -v 는 볼륨까지 삭제.
  • CLI 로 만든 상태는 파일에 없으므로 다음 up 에서 되돌아간다.
ITEM 7-3

도커 컨테이너 간 통신

컨테이너 IP 는 바뀐다. 그래서 IP 가 아니라 이름으로 부른다.

핵심 도커에는 DNS 서버가 내장되어 있어 서비스 이름을 IP 로 풀어 준다. 스케일 아웃한 서비스는 여러 개의 IP 가 돌아오므로, 앱 쪽에서 그것으로 로드밸런싱을 할 수 있다.

DNS 디스커버리

  • 모든 컨테이너는 고유의 IP 주소를 갖는다.
  • 컨테이너가 교체되면 IP 도 바뀌는데, 그래도 문제가 없도록 도커는 DNS 디스커버리 기능을 제공한다.
  • 도커에는 DNS 서비스가 내장돼 있으며, 컨테이너 이름을 도메인 삼아 조회하면 IP 주소를 찾아 준다.

i

이 로드밸런싱의 한계 보강

도커 DNS 는 응답 순서를 매번 섞어 반환하지만, 이것만으로는 부하가 고르게 나뉜다는 보장이 없다. 많은 HTTP 클라이언트가 첫 번째 IP 만 쓰거나 DNS 결과를 캐싱하기 때문이다. JVM 은 기본 DNS 캐시 정책이 특히 길어서, 컨테이너가 교체돼 IP 가 바뀌어도 옛 IP 로 계속 붙는 사고가 잘 생긴다. 실제 분산이 필요하면 프록시를 두거나 스웜/쿠버네티스의 가상 IP 방식을 쓴다.

정리

  • 컨테이너 IP 는 교체될 때마다 바뀌므로 서비스 이름으로 부른다.
  • 도커 내장 DNS 가 이름을 IP 로 풀어 주고, 스케일 아웃된 서비스는 IP 목록을 돌려준다.
  • 고르는 것은 앱이다. 클라이언트의 DNS 캐싱 때문에 실제 분산은 보장되지 않는다.
ITEM 7-4

도커 컴포즈로 앱 설정값 지정하기

SQLite 로 돌던 앱을 코드 수정 없이 Postgres 로 갈아 끼운다. 바뀐 것은 설정뿐이다.

핵심 패키징된 앱과 설정값을 분리할 수 있다는 것이 도커의 핵심 장점 중 하나다. 개발 환경에서 검증을 마친 바로 그 이미지를 운영에서도 그대로 쓸 수 있게 된다.

도커 컴포즈로 설정값 지정

  • 환경 변수는 주로 클러스터 환경에서 쿠버네티스나 도커 스웜 같은 컨테이너 플랫폼을 통해 제공된다.
  • 다만 단일 PC 에서 구동하는 경우는 파일로 제공해도 무방하다.
  • 패키징된 앱과 설정값을 분리할 수 있다는 게 도커의 핵심 장점 중 하나다. 개발 환경에서 계속 테스트하고 검증한 이미지를 그대로 프로덕션에서도 쓸 수 있다.
docker-compose.yml 
services:
  todo-db:
    image: diamol/postgres:11.5
    ports:
      - "5433:5432"
    networks:
      - app-net

  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - "8030:80"
    environment:
      - Database:Provider=Postgres
    depends_on:
      - todo-db
    networks:
      - app-net
    secrets:
      - source: postgres-connection
        target: /app/config/secrets.json

networks:
  app-net:

secrets:
  postgres-connection:
    file: ./config/secrets.json

{
  "ConnectionStrings": {
    "ToDoDb": "Server=todo-db;Database=todo;User Id=postgres;Password=postgres;"
  }

SQLite 대신 Postgres

실제로 추가한 데이터가 도커로 실행한 Postgres 에 저장된다.

앱 이미지는 그대로, 저장소만 바뀌었다 — 코드를 고치지 않고 environment 와 비밀값 파일만 바꿔 SQLite 에서 Postgres 로 전환했다.
!

여기의 비밀값은 진짜 비밀이 아니다 보강

컴포즈의 secrets 는 파일 내용을 컨테이너 안의 지정 경로에 얹어 줄 뿐, 암호화하지 않는다. 원본은 여전히 ./config/secrets.json 평문 파일이다. 실제 암호화 저장은 스웜의 docker secret 이나 쿠버네티스 Secret, 외부 볼트가 담당한다. 그래도 environment 로 넘기는 것보다는 낫다. 환경 변수는 docker inspect 와 프로세스 목록에 그대로 노출되지만, 파일로 얹은 값은 그렇지 않기 때문이다.

정리

  • 같은 이미지에 설정만 갈아 끼워 저장소를 바꿨다. 앱과 설정의 분리가 실제로 작동하는 모습이다.
  • 커넥션 스트링의 호스트명 자리에 서비스 이름을 그대로 쓴다. DNS 가 풀어 준다.
  • 민감한 값은 environment 보다 secrets(파일 주입)가 낫다. 다만 암호화는 아니다.
ITEM 7-5

도커 컴포즈도 만능은 아니다

컴포즈는 상태를 만들어 주지만 지켜 주지는 않는다. 그 차이가 프로덕션의 경계다.

핵심 컴포즈에는 앱이 정의된 상태를 계속 유지하게 하는 기능이 없다. 컨테이너가 죽으면 죽은 채로 남는다. 이것이 컴포즈와 오케스트레이터를 가르는 결정적 차이다.

도커 컴포즈의 역할

  • 도커 컴포즈는 쿠버네티스나 도커 스웜 같은 완전한 컨테이너 플랫폼이 아니다.
  • 앱이 지속적으로 정의된 상태를 유지하도록 하는 기능이 없다.
  • 다만 컨테이너 클러스터를 운영할 계획이 없는 소규모 앱이라면 도커 컴포즈로도 충분하다.

앱 운영의 어떤 과정에서 써야 할까

단계컴포즈의 역할적합도
Dev / E2E TestE2E 테스트를 위한 서비스 구성이 필요할 때 앱을 실행✓
CI 파이프라인빌드 및 자동화된 테스트에 컴포즈로 앱을 실행✓
Test / QA단일 서버에서 앱을 실행해 테스트. 테스트 환경을 최소한으로 유지✓
프로덕션도커 스웜이나 쿠버네티스를 쓰는 게 옳다. 다만 앱 정의에는 컴포즈 파일 포맷을 여전히 쓴다✗
i

그래도 프로덕션에서 굴려야 한다면 보강

컴포즈에도 restart 정책이 있어서 컨테이너가 종료됐을 때 다시 띄우는 것까지는 된다 (restart: always / unless-stopped). 여기에 8-4 의 헬스체크를 더하면 단일 서버 수준의 자동 복구는 흉내 낼 수 있다.

하지만 이것은 한 대 안에서만 유효하다. 그 서버 자체가 죽으면 앱도 함께 죽고, 다른 노드로 옮겨 붙일 방법이 없다. 여러 대에 걸쳐 상태를 지켜 주는 것이 12장 의 오케스트레이터가 하는 일이다.

정리

  • 컴포즈는 상태를 만들지만 유지하지는 않는다. 죽은 컨테이너를 되살리는 건 오케스트레이터의 몫이다.
  • 개발 / CI / QA 에는 컴포즈로 충분하고, 프로덕션은 스웜이나 쿠버네티스로 간다.
  • 플랫폼이 바뀌어도 앱 정의 포맷은 컴포즈 파일 형식을 계속 쓴다.
