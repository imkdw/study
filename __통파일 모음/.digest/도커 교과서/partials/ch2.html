ITEM 2-1

컨테이너로 헬로월드 실행하기

이미지가 로컬에 없으면 받아 오고, 받아 온 뒤 실행한다. docker container run 한 줄이 그 두 단계를 다 한다.

핵심 첫 실행에서 Unable to find image ... locally 가 뜬 뒤 여러 줄의 Pull complete 가 이어지는 것이 이미지가 여러 개의 레이어로 나뉘어 있다는 첫 번째 증거다.

diamol/ch02-hello-diamol 이미지를 내려받고 컨테이너로 실행하는 과정이다. docker container run 은 컨테이너로 앱을 실행하라는 도커 명령이다.

$ docker container run diamol/ch02-hello-diamol

출력에서 눈여겨볼 것은 컨테이너가 자기 자신에 대해 말하는 세 가지다.

함께 알아두기 보강

docker container run 은 사실 두 명령의 합성이다. 이미지가 없으면 docker image pull, 그다음 컨테이너를 만드는 docker container create, 마지막으로 docker container start. 뒤에 나올 docker container start --attach 로 같은 컨테이너를 다시 살릴 수 있는 것도 이 때문이다.

정리

  • docker container run <이미지> 는 "없으면 받아서, 컨테이너 만들고, 실행한다"를 한 번에 한다.
  • 이미지는 Pull complete 줄 수만큼의 레이어로 쪼개져 내려온다.
  • 컨테이너는 자기만의 호스트명과 IP 를 갖지만, 커널은 호스트 것을 그대로 쓴다.
ITEM 2-3

컨테이너를 원격 컴퓨터처럼 사용하기

컨테이너에 들어가서 셸을 쓰고, 밖에서 프로세스 / 로그 / 상세 정보를 들여다보는 네 가지 명령.

핵심 컨테이너 조회 명령은 전부 ID 앞글자만 입력해도 패턴 매칭으로 동작한다. docker top 84 처럼 두 글자면 충분하다.

--interactive 플래그

  • --interactive 플래그를 쓰면 컨테이너에 접속한 상태로 실행할 수 있다.
  • 도커가 구동 중인 환경에 따라 프롬프트가 다르지만, 컨테이너 내부에서는 동일한 명령어를 쓸 수 있다.
  • 아래 예시에서는 hostname, date 로 호스트명과 날짜를 확인한다.
terminal 
$ docker run --interactive --tty diamol/base

Unable to find image 'diamol/base:latest' locally
latest: Pulling from diamol/base
941f399634ec: Already exists
716aca3e500c: Pull complete
Digest: sha256:787fe221a14f46b55e224ea0436aca77d345c3ded400aaf6cd40125e247f35c7
Status: Downloaded newer image for diamol/base:latest
/ # hostname
840925fb1055
/ # date
Sat Oct 26 04:04:15 UTC 2024
/ #
i

함께 알아두기 보강

941f399634ec: Already exists 를 놓치지 말자. 앞의 ch02-hello-diamol 과 diamol/base 가 같은 기반 레이어를 공유하고 있어서 다시 내려받지 않은 것이다. 이미지 레이어가 왜 읽기 전용이어야 하는지는 3-4 에서 이어진다.

docker container ls

  • 현재 실행 중인 모든 컨테이너의 정보를 확인할 수 있다.
  • 컨테이너의 바탕이 된 이미지, 컨테이너 ID 등이 출력된다. 컨테이너 ID 는 실행할 때마다 무작위로 생성된다.
  • --all 플래그를 붙이면 실행 상태와 상관없이 모든 컨테이너 목록을 볼 수 있다.
terminal 
$ docker container ls

CONTAINER ID   IMAGE         COMMAND     CREATED              STATUS              PORTS     NAMES
840925fb1055   diamol/base   "/bin/sh"   About a minute ago   Up About a minute             reverent_bhaskara

docker top <container_id>

  • 특정 컨테이너에서 실행 중인 프로세스 목록을 보여준다.
  • 패턴 매칭 방식이라 컨테이너 ID 의 앞글자만 입력해도 된다. 여러 개가 매칭되면 매칭된 모든 컨테이너의 프로세스를 출력한다.
terminal 
$ docker top 84

PID                 USER                TIME                COMMAND
7979                root                0:00                /bin/sh
i

함께 알아두기 보강

여기 찍힌 PID 7979 는 호스트에서 본 번호다. 컨테이너 안에서 ps 를 치면 같은 프로세스가 PID 1 로 보인다. 같은 프로세스를 PID 네임스페이스 안팎에서 각각 다른 번호로 보는 것이고, 이것이 "컨테이너는 격리된 프로세스일 뿐"이라는 말의 실체다.

docker logs <container_id>

  • 대상 컨테이너에서 수집된 모든 로그를 출력한다.
  • 실제 앱이 구동되는 컨테이너에서는 앱이 출력하는 로그만 보인다.
terminal 
$ docker logs 84

/ # hostname
840925fb1055
/ # date
Sat Oct 26 04:04:15 UTC 2024
i

함께 알아두기 보강

도커가 수집하는 것은 PID 1 프로세스의 표준 출력/표준 에러뿐이다. 앱이 로그를 파일에 쓰도록 설정돼 있으면 docker logs 에는 아무것도 안 나온다. 컨테이너용 앱에서 로그를 stdout 으로 내보내는 게 관례가 된 이유가 여기 있다.

docker inspect <container_id>

  • 대상 컨테이너의 상세한 정보를 보여준다.
  • JSON 포맷으로 출력되며 상태, 네트워크 설정 등 앱에 일어난 문제를 추적하기 위해 일상적으로 쓴다.
terminal 
$ docker inspect 84

[
    {
        "Id": "840925fb1055450623273c76ddecb6e6b6b8f4be9015c5060ea636beb051a395",
        "Created": "2024-10-26T04:04:04.909715959Z",
        "Path": "/bin/sh",
        "Args": [],
        "State": {
            "Status": "running",
            "Running": true,
            "Paused": false
        }
        // more...
    }
]
!

원문 교정 원문 교정

노트에는 docker inspect 로 "CPU 사용량, 네트워크 상태"를 본다고 적혀 있지만, inspect 가 보여주는 것은 설정과 상태 스냅숏(경로, 마운트, 네트워크 설정, 헬스 상태 등)이지 실시간 리소스 사용량이 아니다. 실시간 CPU / 메모리 사용량은 docker stats 가 담당한다.

정리

  • --interactive --tty (줄여서 -it) 로 컨테이너 안에서 셸을 쓴다.
  • ls 는 목록, top 은 프로세스, logs 는 stdout, inspect 는 설정 스냅숏.
  • 컨테이너 ID 는 앞글자만 써도 되고, --all 없이는 종료된 컨테이너가 안 보인다.
ITEM 2-4

컨테이너를 사용해서 웹 사이트 호스팅하기

컨테이너 IP 로는 못 들어간다. 호스트 포트를 열어 도커가 트래픽을 넘겨줘야 들어갈 수 있다.

핵심 --publish 8088:80 은 "호스트의 8088 로 들어온 트래픽을 컨테이너의 80 으로 넘겨라"는 뜻이다. 공개하지 않은 컨테이너는 외부에서 IP 로 직접 찔러도 열리지 않는다.

모든 도커 컨테이너 확인하기

docker container ls --all 로 확인할 수 있다. 여기서 알아야 할 점이 두 가지 있다.

  1. 컨테이너 내부의 앱이 실행 중이어야 컨테이너도 실행이 유지된다

    종료된 컨테이너는 더 이상 CPU 나 메모리 자원을 사용하지 않는다.

  2. 컨테이너가 종료돼도 사라지지 않는다

    나중에 다시 실행하거나 로그를 확인하는 등의 작업이 가능하다. 다만 계속 남아 있어서 저장 공간을 차지한다.

컨테이너에서 간단한 웹 사이트 호스팅하기

  • --detach — 컨테이너를 백그라운드에서 실행하며 컨테이너 ID 를 출력하는 플래그
  • --publish — 컨테이너의 포트를 호스트 컴퓨터에 공개하는 플래그
terminal 
$ docker run --detach --publish 8088:80 diamol/ch02-hello-diamol-web

latest: Pulling from diamol/ch02-hello-diamol-web

컨테이너 포트를 호스트 컴퓨터에 공개하는 원리

  • 도커를 설치하면 호스트 컴퓨터의 네트워크 계층에 도커가 끼어든다.
  • 호스트를 드나드는 네트워크 트래픽을 도커가 가로채서, 필요한 것만 컨테이너에 전달한다.
  • 기본적으로 컨테이너는 외부에 노출되지 않으므로 외부에서 컨테이너 IP 로 직접 접근할 수 없다.
컨테이너 IP 는 호스트 안에서만 유효한 주소다 — 외부에서 닿을 수 있는 유일한 통로는 --publish 로 연 호스트 포트뿐이고, 그 앞에서 도커가 트래픽을 받아 컨테이너로 넘긴다.

docker stats <container_id>

  • 컨테이너의 리소스 사용 현황을 확인하는 명령이다.
  • 실시간으로 CPU, 메모리, 네트워크, 디스크 사용량을 볼 수 있다.
  • 출력 결과는 리눅스와 윈도우에서 조금 다르다.
terminal 
$ docker stats 06

CONTAINER ID   NAME           CPU %     MEM USAGE / LIMIT    MEM %     NET I/O           BLOCK I/O        PIDS
066b8d99bf04   kind_khorana   0.00%     3.23MiB / 5.189GiB   0.06%     4.04kB / 2.64kB   5.69MB / 4.1kB   109

실습 환경에서만 쓸 것

이 명령은 이 머신의 모든 컨테이너를 지운다. 실습용 컨테이너만 골라내려면 --filter 를 쓰는 편이 안전하다. 예를 들어 종료된 것만 지우려면 docker container prune, 특정 이름 패턴만 지우려면 docker rm -f $(docker ps -aq --filter "name=todo") 처럼 쓴다.

정리

  • 컨테이너는 종료돼도 남아 있다. 자원은 안 쓰지만 디스크는 차지한다.
  • --publish 호스트:컨테이너 로 연 포트만 외부에서 닿는다. 컨테이너 IP 직접 접근은 안 된다.
  • 실시간 사용량은 docker stats, 설정 스냅숏은 docker inspect 로 역할이 갈린다.
ITEM 2-5

도커가 컨테이너를 실행하는 원리

CLI 는 아무 일도 하지 않는다. REST API 를 호출할 뿐이고, 실제 작업은 엔진이 한다.

핵심 docker 명령은 API 클라이언트일 뿐이다. CLI 와 엔진이 API 로 분리돼 있기 때문에 Portainer 같은 다른 클라이언트도, 원격 호스트 제어도 같은 방식으로 가능해진다. 
flowchart TB
  CLI["docker CLI"] -->|"HTTP REST 호출"| API["Docker API"]
  OTHER["다른 클라이언트 (Portainer 등)"] -->|"같은 API"| API
  API --> ENG["Docker Engine (상시 데몬)"]
  ENG -->|"컨테이너 / 가상 네트워크 생성"| OS["호스트 OS"]
  ENG <-->|"없으면 내려받고 있으면 재사용"| CACHE["로컬 이미지 캐시"]
CLI → API → 엔진 순서로 흐른다 — CLI 를 통째로 다른 도구로 갈아 끼워도 아래 두 층은 그대로다. 엔진 설정을 바꾸면 이 API 를 네트워크 너머에서 호출하도록 열 수도 있다.

도커 엔진

  • 도커의 관리 기능을 담당하는 컴포넌트다.
  • 로컬 이미지 캐싱을 담당한다. 새 이미지가 필요하면 내려받고, 기존에 있으면 그대로 쓴다.
  • 호스트 OS 와 함께 컨테이너와 가상 네트워크 등 도커 리소스를 만드는 일도 담당한다.
  • 항시 동작하는 백그라운드 프로세스다.

도커 API

  • 표준 HTTP 기반 REST API 다.
  • 도커 엔진은 이 API 를 통해 맡은 기능을 수행한다.
  • 엔진 설정을 바꾸면 네트워크를 경유해 외부 컴퓨터에서 호출할 수 있는지를 제어할 수 있다.
!

주의 보강

도커 API 를 TCP 로 열 때는 인증 없이 열지 않는다. 도커 데몬은 사실상 호스트의 root 권한과 동등하므로, 인증 없는 2375 포트는 호스트를 통째로 넘겨주는 것과 같다. 원격 접근이 필요하면 TLS 로 상호 인증(2376)하거나 SSH 컨텍스트 (docker context create --docker "host=ssh://...")를 쓴다.

도커 CLI

  • 도커 API 의 클라이언트다.
  • 명령을 실행할 때 실제로 도커 API 를 호출하는 주체가 도커 CLI 다.

오픈소스인 도커 API

  • 도커는 모든 API 명세가 공개돼 있다.
  • 도커 CLI 외에도 다른 클라이언트(Portainer 등)를 쓸 수 있다.

정리

  • 구조는 CLI → API → 엔진 → OS 네 층이다. CLI 는 얇은 클라이언트일 뿐이다.
  • 엔진이 이미지 캐시를 관리한다. Already exists 가 뜨는 이유가 이것이다.
  • API 가 공개돼 있어 다른 UI 나 원격 제어가 붙을 수 있다. 반대로 함부로 열면 위험하다.
ITEM 2-6

연습문제 — 컨테이너 파일 시스템 다루기

실행 중인 컨테이너에 파일을 밀어 넣어 화면을 바꿔 본다. 그 변경이 어디에 저장되는지가 6장의 주제가 된다.

핵심 docker container cp 로 호스트의 파일을 실행 중인 컨테이너로 복사할 수 있다. 이 변경은 그 컨테이너에만 남고, 이미지에도 다른 컨테이너에도 영향을 주지 않는다.

문제 — 웹 사이트 컨테이너를 실행하고 index.html 파일을 교체해서 웹 페이지 내용을 수정하라. index.html 은 /usr/local/apache2/htdocs 에 위치한다.

기존 웹 사이트

이미지에 포함된 원래 index.html — 이 파일을 갈아 끼우는 게 이번 문제다.

풀이

1. 웹 사이트 컨테이너를 백그라운드로 실행
terminal 
$ docker run -d -p 8080:80 diamol/ch02-hello-diamol-web

b04b0fbe9e7eeb151111f80c4c1f5d8f1547878d036ce9f02cdc440342e9bd20
2. 새로운 index.html 파일을 해당 경로에 복사하기

docker exec 로 기존 파일을 먼저 확인할 수 있다.

terminal 
$ docker exec b04 ls /usr/local/apache2/htdocs
index.html

이후 로컬에서 index.html 을 만들고 위 경로에 복사한다.

terminal 
$ docker container cp index.html b04:/usr/local/apache2/htdocs/index.html
Successfully copied 2.05kB to b04:/usr/local/apache2/htdocs/index.html

파일 변경 후 웹 사이트

이미지는 그대로인데 화면만 바뀌었다 — 바뀐 파일은 이 컨테이너의 기록 가능 레이어에만 존재한다. 컨테이너를 지우면 원래 화면으로 돌아온다.
i

함께 알아두기 보강

같은 이미지로 컨테이너를 하나 더 띄워 보면 원래 화면이 그대로 나온다. 이 변경이 이미지가 아니라 컨테이너에 붙는다는 것을 눈으로 확인하는 가장 빠른 방법이다. 왜 그런지는 6-1 의 기록 가능 레이어와 기록 중 복사(copy-on-write)에서 이어진다.

정리

  • docker exec <id> <명령> 으로 실행 중인 컨테이너 안에서 명령을 돌릴 수 있다.
  • docker container cp 는 호스트 ↔ 컨테이너 양방향으로 파일을 복사한다.
  • 실행 중인 컨테이너의 파일 변경은 그 컨테이너에만 남는다. 이미지는 변하지 않는다.
