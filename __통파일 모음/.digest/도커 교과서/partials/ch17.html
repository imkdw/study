ITEM 17-1

도커 이미지를 최적화하는 방법

한 번 레이어에 들어간 파일은 지워도 사라지지 않는다. 애초에 넣지 않는 것만이 답이다.

핵심 RUN rm -rf 는 파일을 안 보이게 만들 뿐 이미지 크기를 줄이지 않는다. 레이어는 쌓이기만 하고 아래 레이어의 내용을 되돌릴 수 없기 때문이다.

도커 이미지의 특성

  • 한 번 내려받은 이미지는 명시적으로 삭제하지 않으면 계속 남아 있다.
  • docker system df 로 도커 자원이 점유하는 사용량을 확인할 수 있다.
  • 가능하면 docker system prune 으로 미사용 자원을 주기적으로 지워 주는 게 좋다.
!

prune 은 범위를 알고 쓰자 보강

명령지우는 것
docker system prune정지된 컨테이너, 미사용 네트워크, dangling 이미지, 빌드 캐시
docker system prune -a위 + 컨테이너가 쓰지 않는 모든 이미지
docker system prune --volumes위 + 미사용 볼륨 (데이터 손실)

-a 는 잠시 안 쓰는 이미지까지 전부 날려 다음 빌드가 크게 느려진다. --volumes 는 DB 데이터를 지울 수 있다. 상세 내역은 docker system df -v 로 먼저 확인하는 습관을 들이자.

도커 이미지 개선하기 — 꼭 필요한 파일만 이미지에 포함하기

  • 이미지 크기는 내부에서 실행한 명령이 아니라, 인스트럭션이 만들어 낸 레이어에 영향을 받는다.
  • 아래 v2 예제에서 rm -rf docs 로 폴더를 삭제했지만, 앞선 COPY 레이어에는 그대로 남아 있다.
  • 이미지는 여러 레이어를 겹쳐 하나로 보이게 만든 것이다. 즉 한 번 복사된 것은 뺄 수 없다.
  • 결국 각 레이어마다 최적화가 필요하다.
Dockerfile 
# v1) 모든 디렉토리 구조를 이미지에 복사함
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY . .

# v2) 불필요한 파일을 별도로 삭제 — 화면에서만 사라지고 크기는 그대로
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY . .
RUN rm -rf docs

# v3) 꼭 필요한 파일만 복제하기 — 이것만이 실제로 작아진다
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY ./app ./app
삭제는 위 레이어에 "가림막"을 하나 더 얹는 일이다 — 아래 레이어의 파일은 그대로 남아 전송량과 디스크를 그대로 잡아먹는다. 게다가 그 파일은 여전히 이미지 안에 있으므로 추출도 가능하다. 비밀 파일을 이렇게 지우면 안 되는 이유다.

.dockerignore

  • .gitignore 와 유사한 파일로, 제외하고 싶은 목록을 적으면 된다.
.dockerignore 
.git
node_modules
docs
*.md
.env
**/*.test.js
i

.dockerignore 는 두 가지를 동시에 해결한다 보강

첫째, 빌드 컨텍스트 전송량이 줄어 빌드가 빨라진다. 둘째, COPY . . 를 써도 제외된 파일은 애초에 복사되지 않는다. RUN rm 으로 지우는 것과 달리 레이어에 흔적도 남지 않는다는 점이 결정적이다.

한 가지 함정 — .dockerignore 에 node_modules 를 넣어 두면 캐시 최적화(3-5)와도 잘 맞는다. 호스트의 node_modules 가 컨텍스트에 안 들어가므로 COPY . . 가 그것 때문에 캐시를 깨뜨리는 일이 없어진다.

정리

  • 레이어는 쌓이기만 한다. RUN rm 은 가림막만 얹을 뿐 크기를 줄이지 않는다.
  • 애초에 필요한 것만 COPY 하고, 나머지는 .dockerignore 로 막는다.
  • 지운 파일도 이미지에서 추출 가능하다. 비밀 파일을 이 방식으로 처리하면 안 된다.
  • docker system df 로 확인하고 prune 은 범위를 알고 쓴다.
ITEM 17-2

좋은 기반 이미지 고르기

이미지 크기 문제는 디스크 문제가 아니라 공격 표면 문제다.

핵심 이미지에 들어 있는 모든 실행 파일은 침입자도 쓸 수 있는 도구다. 앱 실행에 필요 없는 것이 하나도 없어야 한다는 원칙은 보안에서 나온다.

이미지의 취약점

  • 크기가 큰 이미지는 OS 입장에서는 편하겠지만, 그만큼 내부에 많은 것이 포함된다.
  • 예를 들어 curl 이 들어 있다면 컨테이너에 침입한 공격자가 악성 프로그램을 내려받을 수 있다.
  • 또한 빌드가 가능한 SDK 등이 포함돼 있다면 컨테이너 자체가 망가질 수도 있다.
기반 이미지대략적 크기포함된 것성격
ubuntu / debian~75MB+완전한 배포판, 패키지 관리자, 셸, curl 등디버깅 편함 / 공격 표면 큼
*-slim~30MB+배포판에서 문서와 부가 도구를 뺀 것절충안
alpine~8MBmusl libc 기반 최소 배포판, 셸 있음작지만 glibc 호환 이슈 가능
distroless~2MB+런타임만. 셸도 패키지 관리자도 없음가장 안전 / exec 로 못 들어감
scratch0아무것도 없음정적 링크된 바이너리 전용
i

작을수록 좋지만 공짜는 아니다 보강

distroless 나 scratch 이미지는 셸이 없어서 docker exec -it ... sh 가 안 된다. 장애 상황에서 컨테이너 안을 들여다보는 통상적인 방법이 막힌다는 뜻이다. 그래서 이런 이미지를 쓸 때는 8-3 처럼 앱과 같은 언어로 만든 체크 유틸리티가 더욱 중요해진다. 셸 스크립트를 쓸 수 없으니 선택의 여지도 없다.

alpine 은 glibc 대신 musl libc 를 쓰기 때문에, 네이티브 모듈을 쓰는 Node.js / Python 앱에서 미묘한 호환성 문제나 성능 차이가 나타나는 경우가 있다. 무조건 alpine 이 정답은 아니다.

골든 이미지

  • 앞서 설명한 골든 이미지는 인증을 받고 공유되는 이미지라서 이러한 문제를 피할 수 있는 방법 중 하나다.

이미지 검증 도구

  • 앤코어(Anchore) 같은 오픈소스 도커 이미지 분석 도구로 CI/CD 파이프라인에서 이미지를 검증할 수 있다.
↑

지금은 선택지가 더 많다 최신 반영

노트가 언급한 Anchore 외에도, 그사이 이미지 스캐닝이 훨씬 흔한 일이 됐다.

  • Docker Scout — 도커의 자체 서비스. 이미지에서 SBOM 을 만들어 취약점 DB 와 대조한다. Docker Hub, Docker CLI, Scout 대시보드에서 쓸 수 있다.
  • Trivy — 오픈소스. 컨테이너 이미지뿐 아니라 파일 시스템, IaC 설정까지 스캔한다. CI 에 붙이기 쉽다.
  • Grype — Anchore 계열의 오픈소스 스캐너.

핵심은 도구 선택이 아니라 스캔을 파이프라인에 자동으로 넣는 것이다. 11-1 의 CI 흐름에서 빌드와 푸시 사이에 스캔 단계를 두고, 심각도 기준을 넘으면 푸시를 막는 방식이 표준적이다.

정리

  • 이미지에 든 도구는 침입자의 도구이기도 하다. 앱에 필요 없는 것은 넣지 않는다.
  • slim / alpine / distroless / scratch 순으로 작아지지만 디버깅은 어려워진다.
  • alpine 은 musl libc 라 네이티브 모듈에서 호환성 문제가 날 수 있다.
  • 이미지 스캔을 CI 파이프라인에 자동으로 넣는다. Scout / Trivy / Grype 등.
ITEM 17-3

이미지 레이어 수와 이미지 크기는 최소한으로

패키지를 설치하고 캐시를 지우는 일은 같은 RUN 안에서 끝내야 한다.

핵심 RUN 을 && 로 이어 붙이는 이유는 문법 취향이 아니다. 설치와 정리가 같은 레이어에서 일어나야 캐시 파일이 이미지에 남지 않기 때문이다.

이미지 레이어 수 최소화하기

  • 이미지를 만들 때 기본은 보안성을 갖춘 기반 이미지를 쓰는 것이다.
  • 추가로 꼭 필요한 것만 포함하는 이미지를 만들어야 한다.

예제 1. 패키지 설치

  • 차이점은 인스트럭션의 개수와, RUN 커맨드 뒤에 apt 캐시를 삭제하는 구문이 추가된 것이다.
  • 인스트럭션을 줄이면 여러 장점이 있다.
    • OS 별로 다르지만 최대 레이어 개수 제한이 존재한다.
    • 레이어 수가 적으면 컨테이너 파일 시스템의 내용을 추적하기도 쉽다.
v1 — 이미지 90MB 
FROM debian:stretch-slim

RUN apt-get update
RUN apt-get install -y curl=7.52.1-5+deb9u16
RUN apt-get install -y socat=1.7.3.1-2+deb9u1
v2 — 이미지 70MB 
FROM debian:stretch-slim

RUN apt-get update \
 && apt-get install -y --no-install-recommends \
    curl=7.52.1-5+deb9u16 \
    socat=1.7.3.1-2+deb9u1 \
 && rm -rf /var/lib/apt/lists/*
i

v2 가 20MB 를 아낀 두 가지 이유 보강

  • --no-install-recommends — apt 는 기본적으로 "추천 패키지"까지 함께 설치한다. 이 플래그로 진짜 의존성만 설치한다.
  • rm -rf /var/lib/apt/lists/* 를 같은 RUN 안에 둔 것 — apt-get update 가 받아 온 패키지 목록 캐시를 지운다. 17-1 에서 봤듯 별도의 RUN 으로 지우면 소용이 없다. 같은 레이어 안에서 만들었다 지워야 그 레이어의 최종 결과에 캐시가 없다.

참고로 apt-get update 와 install 을 나누면 캐시 관점에서도 위험하다. update 레이어가 캐시에 걸린 채 install 만 다시 실행되면, 오래된 패키지 목록으로 설치를 시도해 실패하거나 낡은 버전이 깔린다.

!

"최대 레이어 개수"의 실제 수치 보강

지금 표준 스토리지 드라이버인 overlay2 는 최대 128개의 lower 레이어를 지원한다. 이를 넘기면 max depth exceeded 로 빌드가 실패한다.

실제로는 128 보다 적은 수에서 터지는 경우가 흔한데, 커널의 마운트 옵션 문자열이 4KB 로 제한되어 있어 data-root 경로가 길수록 쓸 수 있는 레이어가 줄기 때문이다. 보고 사례에서는 120~126 층 부근에서 실패했다. 어쨌든 정상적인 Dockerfile 이 128 층에 닿는 일은 드물다. 레이어를 줄이는 진짜 이유는 개수 제한이 아니라 크기와 추적 가능성이다.

예제 2. 머신러닝 데이터 압축 해제

단순히 삭제만 한다고 해서 이미지 레이어의 크기가 줄지 않는다.

v1 — 이미지 2.5GB 
FROM diamol/base

ARG DATASET_URL=https://archive.ics.uci.edu/ml/\
machine-learning-databases/url/url_svmlight.tar.gz

WORKDIR /dataset

RUN wget -O dataset.tar.gz ${DATASET_URL} && \
    tar xvzf dataset.tar.gz

WORKDIR /dataset/url_svmlight
RUN cp Day1.svm Day1.bak && \
    rm -f *.svm && \
    mv Day1.bak Day1.svm
v2 — 이미지 25MB 
FROM diamol/base

ARG DATASET_URL=https://archive.ics.uci.edu/ml/\
machine-learning-databases/url/url_svmlight.tar.gz

WORKDIR /dataset

RUN wget -O dataset.tar.gz ${DATASET_URL} && \
    tar -xf dataset.tar.gz url_svmlight/Day1.svm && \
    rm -f dataset.tar.gz
✓

2.5GB → 25MB, 100배 차이

v1 은 전체를 풀어놓은 뒤 지웠기 때문에, 아래 레이어에 압축 파일과 풀린 전체 데이터가 모두 남아 있다. v2 는 tar 에 파일 이름을 지정해 필요한 하나만 꺼냈다. 원칙은 언제나 같다 — 지우지 말고 애초에 만들지 않는다.

정리

  • 설치와 정리는 반드시 같은 RUN 안에서 끝낸다. 나누면 정리 효과가 없다.
  • apt-get 은 --no-install-recommends + rm -rf /var/lib/apt/lists/* 가 기본형이다.
  • overlay2 의 레이어 한계는 128 이지만, 줄이는 진짜 이유는 크기와 추적 가능성이다.
  • 큰 아카이브는 통째로 풀고 지우는 대신 필요한 파일만 꺼낸다.
ITEM 17-4

멀티 스테이지 빌드를 한 단계 업그레이드하기

--target 으로 중간 스테이지까지만 빌드하면, 어느 단계에서 크기가 폭발하는지 눈으로 확인할 수 있다.

핵심 --target 은 디버깅 도구다. 스테이지별 이미지를 각각 만들어 크기를 재 보면, 어느 단계가 무엇을 남기고 있는지가 그대로 드러난다.

--target 인자

이 인자로 특정 스테이지에서 빌드를 중단할 수 있다.

terminal 
# 이미지 끝까지 빌드
$ docker image build -t diamol/ch17-ml-dataset:v3 -f Dockerfile.v3 .

# download 스테이지까지만 빌드
$ docker build -t diamol/ch17-ml-dataset:v3-download -f Dockerfile.v3 --target download .

# expand 스테이지까지만 빌드
$ docker build -t diamol/ch17-ml-dataset:v3-expand -f Dockerfile.v3 --target expand .

# 각 단계마다 이미지의 크기가 다르다
$ docker image ls | grep diamol/ch17-ml-dataset
diamol/ch17-ml-dataset   v3            26080e7d3ce4   13 minutes ago   25.3MB
diamol/ch17-ml-dataset   v3-expand     adb8e54075dd   13 minutes ago   2.46GB
diamol/ch17-ml-dataset   v3-download   35e3d8920e1e   14 minutes ago   252MB
2.46GB 짜리 스테이지를 거쳐 25.3MB 이미지가 나온다 — COPY --from 으로 명시한 파일만 넘어오기 때문이다. --target 이 없으면 이 중간 크기는 보이지 않는다.

주의점

  • RUN 으로 내려받거나 설치한 소프트웨어 등 불필요한 데이터가 캐싱되지 않도록 주의해야 한다.
  • 앞 단계에서 캐싱된 데이터는 해당 Dockerfile 안에서 그 인스트럭션을 수정할 때까지 캐시에 유지된다.
  • 이미지에 패키지를 추가할 때는 정확한 버전을 명시해서 설치하거나 업데이트하는 게 좋다.
!

버전 고정이 중요한 이유 보강

RUN apt-get install -y curl 처럼 버전 없이 쓰면, 이 레이어가 캐시에 걸려 있는 동안은 몇 달 전 버전이 계속 쓰이다가 어느 날 캐시가 깨지는 순간 갑자기 최신 버전으로 바뀐다. 빌드가 언제 깨질지 예측할 수 없다는 뜻이다.

그래서 17-3 의 예제처럼 curl=7.52.1-5+deb9u16 로 버전을 못 박는다. 업그레이드는 사람이 의도적으로 그 줄을 고칠 때만 일어나야 한다. FROM 의 기반 이미지도 마찬가지로 latest 대신 구체적인 태그를 쓴다.

i

--target 의 또 다른 쓰임 보강

CI 에서 테스트 스테이지까지만 빌드하는 데도 쓴다. docker build --target test . 로 테스트만 돌리고, 통과하면 --target 없이 최종 이미지를 만드는 식이다. 개발용으로 디버깅 도구가 포함된 스테이지를 따로 두고 --target dev 로 뽑아 쓰는 패턴도 흔하다.

정리

  • --target 으로 중간 스테이지까지만 빌드해 어느 단계가 무거운지 확인한다.
  • 중간 스테이지가 커도 최종 이미지에는 COPY --from 으로 넘긴 것만 남는다.
  • 패키지와 기반 이미지의 버전은 못 박는다. 캐시가 깨지는 순간 조용히 바뀌는 것을 막는다.
  • --target 은 CI 의 테스트 전용 빌드, 개발용 이미지 분리에도 쓰인다.
