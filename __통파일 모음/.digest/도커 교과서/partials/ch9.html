ITEM 9-1

컨테이너화된 앱에서 사용되는 모니터링 기술 스택

감시 대상이 계속 떴다 사라지는 환경에서는, 서버를 지켜보는 방식이 통하지 않는다.

핵심 프로메테우스는 앱의 언어와 무관하게 /metrics 라는 하나의 규약으로 측정값을 모은다. 그 덕에 자바든 고든 닷넷이든 같은 방식으로 감시할 수 있다.

일반 환경에서의 모니터링

  • 단일 서버에서 앱이 동작하는 경우, 모니터링이라고 하면 디스크 공간 / RAM / CPU 같은 것들이다.
  • 보통 대시보드가 있고 임계치를 넘어가면 알람이 발생하는 구조다.

컨테이너 환경에서의 모니터링

  • 정적인 컨테이너나 고정된 IP 없이도 실행 중인 앱을 확인할 수 있는 모니터링 방식이 필요하다.

프로메테우스(Prometheus)

  • CNCF 에서 개발을 담당하고 있으며 널리 쓰인다.
  • 마찬가지로 컨테이너에서 동작하기 때문에 분산 앱에 어렵지 않게 모니터링을 붙일 수 있다.
  • 앱의 프로그래밍 언어와 무관하게 모든 앱을 표준적인 형태로 모니터링할 수 있어 일관성을 보장한다.
  • 도커 엔진의 측정값도 뽑아낼 수 있다.
i

프로메테우스의 위상 보강

프로메테우스는 2016년 5월 CNCF 에 쿠버네티스 다음 두 번째로 합류했고, 2018년 8월 9일 Graduated(졸업) 등급이 됐다. 사실상 컨테이너 환경 메트릭의 표준이다. 수집 모델은 풀(pull) 이며, 짧게 살다 죽는 배치 작업만 예외적으로 Pushgateway 라는 중계 서버를 통해 푸시한다. 

flowchart LR
  P["Prometheus"] -->|"주기적으로 GET /metrics"| D["Docker Engine (:9323/metrics)"]
  P -->|"GET /metrics"| S1["앱 컨테이너 1"]
  P -->|"GET /metrics"| S2["앱 컨테이너 2"]
  D -.->|"인프라 관점 측정값"| P
  S1 -.->|"런타임 + 커스텀 측정값"| P
프로메테우스가 찾아가서 긁어 온다 — 앱이 프로메테우스를 알 필요가 없다. 각자 /metrics 를 열어 두기만 하면 되고, 대상 목록은 프로메테우스 설정이 관리한다.

도커 엔진 메트릭 수집 설정

orbstack 기준으로 ~/.orbstack/config/docker.json 을 수정하고 orb restart docker 를 실행한다.

~/.orbstack/config/docker.json 
{
  "metrics-addr": "0.0.0.0:9323"
}
!

0.0.0.0 은 실습용이다 보강

0.0.0.0:9323 은 모든 네트워크 인터페이스에 메트릭 엔드포인트를 여는 것이다. 컨테이너 안에서 호스트를 찔러야 하는 실습에서는 편하지만, 이 포트는 인증이 없다. 실제 서버에서는 내부 인터페이스에만 바인딩하거나 방화벽으로 막아야 한다. 도커 데몬의 메트릭 자체가 호스트 구성 정보를 상당히 드러낸다.

이 텍스트 형식이 전부다 보강

프로메테우스 노출 형식은 사람이 읽을 수 있는 평문이다. 한 줄이 메트릭이름{라벨="값"} 숫자 구조이고, # HELP 는 설명, # TYPE 은 종류다. 종류는 네 가지 — 계속 증가만 하는 counter, 오르내리는 gauge, 분포를 버킷으로 담는 histogram, 분위수를 담는 summary. 위 출력에서 _bucket{...,le="0.005"} 이 히스토그램의 "0.005초 이하" 버킷이다.

job 과 instance 라벨은 프로메테우스가 붙인 것이다 보강

action="changes" 는 도커 엔진이 원래 붙인 라벨이지만, job="docker" 와 instance="DOCKER_HOST:9323" 은 프로메테우스가 수집하면서 자동으로 덧붙인 라벨이다. job 은 설정 파일의 job_name 에서, instance 는 수집 대상 주소에서 온다. 스케일 아웃한 서비스의 인스턴스를 구분할 수 있는 것도 이 라벨 덕분이다 (9-3).

정리

  • 컨테이너 환경에서는 대상이 계속 바뀌므로, 대상 목록을 스스로 관리하는 수집기가 필요하다.
  • 프로메테우스는 CNCF 졸업 프로젝트이며 /metrics 를 주기적으로 긁어 오는 풀 방식이다.
  • 도커 엔진도 metrics-addr 을 열면 같은 형식으로 측정값을 낸다.
  • 수집 시 job / instance 라벨이 자동으로 붙어 인스턴스를 구분할 수 있다.
ITEM 9-2

앱의 측정값 출력하기

엔진 메트릭은 켜기만 하면 되지만, 앱 메트릭은 앱이 직접 내보내야 한다.

핵심 클라이언트 라이브러리를 붙이면 런타임 수준의 측정값은 공짜로 따라온다. 진짜 가치는 그 위에 얹는 연산 중심 / 비즈니스 중심 지표에 있다.

앱의 측정값

  • 앱의 유용한 정보를 측정값으로 구성하려면 API 엔드포인트로 출력해야 해서, 도커 엔진 측정값보다는 좀 더 복잡하다.
  • 각 프로그래밍 언어별로 공식 또는 비공식 라이브러리가 존재한다.
  • 보통 수집되는 정보는 런타임 수준의 측정값이다. 예를 들면
    • Go — 활성 상태인 고루틴의 개수
    • Java — JVM 의 메모리 사용량

수집하는 정보들

런타임 지표는 라이브러리가 주고, 연산 지표는 코드 몇 줄로 얻고, 비즈니스 지표는 도메인을 알아야 정의할 수 있다. 장애 대응에는 위쪽이 쓰이지만, "장애인지 아닌지"를 판단하는 것은 아래쪽이다. 메모리가 정상이어도 주문 수가 0 이면 그건 장애다.

정리

  • 앱 메트릭은 클라이언트 라이브러리를 붙이고 /metrics 엔드포인트를 여는 것으로 시작한다.
  • 런타임 지표는 자동으로 따라온다. 연산 / 비즈니스 지표는 직접 정의해야 한다.
  • 메트릭 종류는 counter / gauge / histogram / summary 네 가지다.
ITEM 9-3

측정값 수집을 맡을 프로메테우스 컨테이너 실행하기

고정된 컨테이너는 static_configs, 늘었다 줄었다 하는 것은 dns_sd_configs.

핵심 스케일 아웃하는 서비스를 감시하려면 주소를 적어 두는 대신 DNS 로 찾게 해야 한다. dns_sd_configs 가 7-3 의 DNS 디스커버리를 그대로 활용한다.

프로메테우스의 데이터 수집

  • 프로메테우스는 대상 시스템에서 데이터를 받아 오는 폴링 방식으로 동작한다.
  • 이 과정을 스크래핑(scraping) 이라고 부른다.

프로메테우스 설정

  • scrape_interval — 스크래핑 주기를 기본값인 10초로 지정
  • static_configs — 정적 설정으로 단일 컨테이너를 지정
  • dns_sd_configs — 도커의 DNS 디스커버리 기능으로 여러 개의 컨테이너를 지정
prometheus.yml 
global:
  scrape_interval: 10s

scrape_configs:
  - job_name: "image-gallery"
    metrics_path: /metrics
    static_configs:
      - targets: ["image-gallery"]

  - job_name: "iotd-api"
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["iotd"]

  - job_name: "access-log"
    metrics_path: /metrics
    scrape_interval: 3s
    dns_sd_configs:
      - names:
          - accesslog
        type: A
        port: 80

  - job_name: "docker"
    metrics_path: /metrics
    static_configs:
      - targets: ["DOCKER_HOST:9323"]
대상 수가 고정이면 정적 설정, 변하면 DNS 디스커버리 — accesslog 만 dns_sd_configs 인 이유는 이것만 --scale 로 늘리기 때문이다.

4 / 3 / 4 라는 숫자가 말해 주는 것 보강

11번의 요청이 세 인스턴스에 4/3/4 로 나뉘었다. 정확히 균등하지는 않은데, 이것이 바로 7-3 에서 짚은 DNS 기반 로드밸런싱의 성격이다. 인스턴스별 라벨이 분리돼 있기 때문에 이런 편차를 눈으로 확인할 수 있다는 것이 모니터링의 값어치다. 라벨이 없었다면 합계 11만 보였을 것이다.

그래프 추가하기

  • 아래에 쓰인 sum() 함수는 프로메테우스에서 쓰는 PromQL 이라는 언어다.
  • 사실 이런 UI 를 대시보드라고 하긴 어렵다. 메트릭 데이터를 기반으로 UI 를 만드는 Grafana 가 따로 있다.
without(hostname, instance) 로 세 시계열을 하나로 합쳤다 — counter 라서 계단식으로 증가만 하고, 요청이 몰린 구간에서 가파르게 올라간다.
i

counter 는 보통 그대로 보지 않는다 보강

counter 는 계속 누적되므로 그래프가 늘 우상향한다. 실무에서 알고 싶은 것은 보통 "지금 초당 몇 건인가" 이고, 그럴 때는 rate() 를 씌운다. sum(rate(access_log_total[1m])) without(hostname, instance) 처럼 쓰면 분당 증가율을 초당 건수로 환산해 준다. counter 는 컨테이너가 재시작하면 0 으로 돌아가는데, rate() 는 그 리셋을 자동으로 보정해 준다는 이점도 있다.

정리

  • 프로메테우스는 scrape_interval 마다 대상의 /metrics 를 긁는다(스크래핑).
  • 고정 대상은 static_configs, 개수가 변하는 대상은 dns_sd_configs.
  • 인스턴스별 라벨이 분리되어 있어 부하 편차까지 보인다.
  • PromQL 의 sum() ... without() 으로 라벨을 접어 합칠 수 있다. counter 에는 rate() 를 씌운다.
ITEM 9-4

측정값 시각화를 위한 그라파나 컨테이너 실행하기

프로메테우스가 데이터를 갖고, 그라파나가 그것을 화면으로 만든다.

핵심 대시보드에서 어려운 것은 PromQL 이 아니라 무엇을 보여 줄지 고르는 일이다. 쿼리는 복잡할 필요가 없고, 화면에 올릴 지표를 잘 고르는 것이 전부다.

그라파나가 포함된 컨테이너 실행

terminal 
# IP 설정 (macOS)
$ export HOST_IP=$(ipconfig getifaddr en0)

$ echo $HOST_IP
172.30.1.6

# grafana 가 포함된 컨테이너 실행
$ docker-compose -f docker-compose-with-grafana.yml up -d --scale accesslog=3

# 부하 발생시키기
$ for i in {1..20}; do curl http://localhost:8010 > /dev/null; done

Grafana 접속

  • docker-compose 에 기재된 주소인 http://localhost:3000 으로 접속한다.
  • 이후 data source 설정과 대시보드 JSON import 를 진행한다.
서비스별로 행을 나눠 묶은 것이 이 대시보드의 핵심 구조다 — Image Gallery / IOTD API / Access Log 세 행이 각각 그 서비스의 상태를 한 줄로 보여 준다. 장애가 나면 어느 행이 붉어지는지로 원인 구간을 좁힐 수 있다.

대시보드 팁

  • 정보는 모두 PromQL 로 만들어지는데, 이때 복잡한 쿼리가 중요한 게 아니다.
  • 어떤 측정값을 보여 줄지 잘 골라서 시각화하는 것이 중요하다.

대시보드를 코드로 관리하기 보강

UI 에서 손으로 만든 대시보드는 컨테이너를 지우면 사라진다. 위 실습이 JSON import 로 대시보드를 넣는 이유가 이것이다. 그라파나는 데이터 소스와 대시보드를 파일로 미리 넣어 두는 프로비저닝 기능을 지원하므로, 이미지에 함께 구워 두면 docker run 한 번으로 대시보드까지 완성된 상태로 뜬다. 투명성도 코드로 관리되어야 재현 가능해진다.

정리

  • 프로메테우스가 저장소, 그라파나가 화면. 데이터 소스로 연결한다.
  • 서비스 단위로 행을 나눠 배치하면 장애 구간을 빠르게 좁힐 수 있다.
  • 대시보드는 JSON 으로 관리해 이미지에 함께 넣으면 재현 가능해진다.
ITEM 9-5

투명성의 수준

개념 검증과 실제 제품을 가르는 것 중 하나가 "지금 무슨 일이 일어나는지 볼 수 있는가"다.

핵심 수십 개의 패널보다 중요한 것은 앱 전체를 한 화면에 조망하는 대시보드 하나다. 가장 중요한 지표만 모아 한 화면에 담을 수 있어야 한다.

투명성(Observability)

  • 간단한 개념 검증 수준의 앱에서 실제 제품으로 나아가려면 투명성이 필요하다.
  • 실제 운영 환경에서는 대시보드가 꼭 필요한데, 그중에서도 앱의 전체 상황을 조망하는 대시보드가 중요하다.
  • 측정값 중 앱에 가장 중요한 데이터를 모아 하나의 화면으로 구성할 수 있어야 한다.

투명성 아키텍처 한눈에 보기

세 층이 각자 한 가지 일만 한다 — 앱과 엔진은 /metrics 로 내보내고, 프로메테우스는 모아서 저장하고, 그라파나는 보여 준다. 각 층이 독립적이라 어느 하나를 바꿔도 나머지는 그대로 둘 수 있다.
i

메트릭만으로는 부족하다 보강

여기서 다룬 것은 관측 가능성의 세 기둥 중 메트릭 하나다. 메트릭은 "무언가 이상하다"를 빠르게 알려 주지만 "왜"를 말해 주지 못한다. 나머지 두 기둥은 로그(무슨 일이 있었는지)와 트레이스(요청이 어느 구간에서 느려졌는지)다. 메트릭으로 이상을 감지하고, 트레이스로 구간을 좁히고, 로그로 원인을 확인하는 흐름이 표준이다.

정리

  • 투명성은 제품 수준으로 가기 위한 필수 조건이다.
  • 앱 전체를 조망하는 대시보드 하나가 패널 수십 개보다 중요하다.
  • 내보내기 / 수집 / 시각화 세 층이 독립적이라 각각 교체할 수 있다.
  • 메트릭은 이상 감지용이다. 원인 규명에는 로그와 트레이스가 함께 필요하다.
