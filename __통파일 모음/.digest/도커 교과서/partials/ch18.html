ITEM 18-1

다단 앱 설정

설정은 한 겹이 아니다. 이미지의 기본값 위에 환경별 파일이 얹히고, 그 위에 환경 변수가 얹힌다.

핵심 설정 모델은 데이터의 성격을 반영해야 한다. 버전에 묶인 값, 환경에 묶인 값, 실행 시점에만 바꾸고 싶은 값은 서로 다른 층에 두어야 한다.

다단 앱 설정

설정 모델에는 설정에 담긴 데이터의 구조가 반영되어야 한다.

분류성격어디에 두는가
버전에 따라 달라지는 설정 모든 환경에서 동일하지만 버전별로 달라짐 이미지 안 (기본 설정 파일)
환경에 따라 달라지는 설정 개발 / 운영 등 환경별로 달라짐 마운트하는 오버라이드 파일
기능 설정 버전별 앱의 동작을 제어하기 위함 환경 변수 (실행 시점에 주입)
병합된다 — 위 층이 없으면 아래 값이 그대로 쓰인다 어느 층이 없어도 앱은 뜬다. 이것이 다단 설정의 목적이다
바닥이 항상 채워져 있기 때문에 아무것도 주입하지 않아도 앱이 뜬다 — 개발자는 docker run 만 하면 되고, 환경이 필요로 하는 만큼만 위층을 얹는다.

예제 1. 로컬 설정 파일 오버라이드

미리 정의된 경로에서 오버라이드 설정 파일을 읽어 들이도록 해 두면, 어떤 경로든 컨테이너 파일 시스템에 설정 파일을 주입하기만 하면 그 설정을 쓸 수 있다.

terminal 
# 기본 설정 사용
$ docker run -d -p 8080:80 diamol/ch18-access-log
3ea38fcbf319abcfd609116747bbc221112b1f62f7973e63256d943b509f5c90

# 로컬에 존재하는 설정 파일 마운트
$ docker run -d -p 8081:80 -v "$(pwd)/config/dev:/app/configoverride" diamol/ch18-access-log
62ccb944842a3f0d4673e13fca1b3cd7f0c702fc20f0e4341484671f93782d95

# 기본 설정 확인
$ curl http://localhost:8080/config
{"release":"19.12","environment":"UNKNOWN","metricsEnabled":true}

# 마운트된 설정 확인 — environment 만 바뀌었다
$ curl http://localhost:8081/config
{"release":"19.12","environment":"DEV","metricsEnabled":true}
i

주목할 것은 바뀌지 않은 값이다 보강

오버라이드 파일이 environment 만 DEV 로 바꿨는데, release 와 metricsEnabled 는 그대로다. 덮어쓰기가 아니라 병합이라는 증거다.

여기서 6-4 의 함정을 피한 방식도 눈여겨볼 만하다. 기본 설정 파일이 있는 폴더에 직접 마운트하면 기본 설정이 통째로 가려졌을 것이다. 그래서 /app/configoverride 라는 별도의 빈 폴더를 마운트 지점으로 두고, 앱이 두 폴더를 모두 읽어 병합한다.

!

오탈자 교정 원문 교정

원문의 diamol?ch18-access-log 는 diamol/ch18-access-log 의 오타다. 위 코드 블록에는 고쳐서 실었다.

예제 2. 환경 변수로부터 값 읽어 오기

  • 기본 파일 + 볼륨 파일 + 주입한 환경 변수를 병합해서 최종 설정이 만들어진다.
  • 이 구성은 개발자의 워크플로를 부드럽게 유지할 수 있는 좋은 사례다.
  • 단점은 값이 JSON 으로 들어가야 한다는 점이다.
terminal 
# 환경변수 직접 주입
$ docker run -d -p 8082:80 -v "$(pwd)/config/dev:/app/configoverride" \
    -e NODE_CONFIG='{"metrics": {"enabled": "true"}}' diamol/ch18-access-log
869b0523b12809008d706a92592f675be273047ff2a147e081f260904ca09ad6

# 주입된 환경변수가 적용된 모습
$ curl http://localhost:8082/config
{"release":"19.12","environment":"UNKNOWN","metricsEnabled":true}
i

JSON 을 환경 변수에 넣는 것의 대가 보강

원문이 지적한 "값이 JSON 으로 들어가야 한다"는 단점은 생각보다 크다. 셸에서 따옴표 이스케이프가 까다롭고, 오타가 나면 조용히 무시되거나 파싱 에러로 앱이 죽는다. CI 스크립트나 컴포즈 파일을 거치면서 이스케이프가 한 번 더 꼬이는 일도 흔하다.

그래서 실무에서는 설정 라이브러리가 지원한다면 중첩 구조를 평평한 키로 표현하는 방식을 선호한다. .NET 의 Database__Provider(더블 언더스코어 = 계층 구분)나 Spring 의 SPRING_DATASOURCE_URL 같은 규칙이 그것이다. 8-3 의 RngApi__Url 도 같은 관례다.

정리

  • 설정은 이미지 기본값 / 환경별 파일 / 환경 변수 세 층으로 나눈다.
  • 위 층이 아래를 덮어쓰되 병합된다. 아무것도 주입하지 않아도 앱이 뜬다.
  • 기본 설정 폴더를 직접 마운트하면 가려진다. 별도의 오버라이드 폴더를 둔다.
  • 환경 변수에 JSON 을 넣는 방식은 이스케이프가 취약하다. 평평한 키 규칙이 안전하다.
ITEM 18-2

환경별 설정 패키징하기

환경별 설정을 이미지 안에 미리 담아 두고, 환경 변수 하나로 어느 것을 쓸지 고른다.

핵심 설정 파일을 이미지에 함께 굽고 환경 변수로 선택하는 방식이다. 주입할 파일이 없어 배포가 단순해지는 대신, 민감한 값은 절대 이 방식으로 담으면 안 된다.

환경별 설정 패키징하기

terminal 
# 기본 설정 실행
$ docker run -d -p 8083:80 diamol/ch18-todo-list
e8dcce707cf0ff3640f781fd9e37584606b122985105bd14eb881ae1484d995b

# DOTNET_ENVIRONMENT 추가 — 이미지 안의 Test 설정이 선택된다
$ docker run -d -p 8084:80 -e DOTNET_ENVIRONMENT=Test diamol/ch18-todo-list
80322b949244722beda23b84dd8187b10c15bb64eb0ef38d36c85ff180d04383
주입할 파일이 없다 — 볼륨도 비밀값도 없이 환경 변수 하나로 환경이 결정된다. 배포가 단순해지는 대신, 그 파일들은 이미지를 가진 누구나 읽을 수 있다.
×

이 방식에 비밀번호를 넣으면 안 되는 이유

이미지에 구운 설정 파일은 그 이미지를 받을 수 있는 누구나 읽을 수 있다. 17-1 에서 봤듯 레이어에서 파일을 꺼내는 것은 어렵지 않고, 나중에 RUN rm 으로 지워도 아래 레이어에 그대로 남는다.

그래서 이미지에 담아도 되는 것은 환경별로 다르지만 비밀은 아닌 값에 한한다 — 로그 수준, 기능 플래그, 캐시 크기, 타임아웃 같은 것들이다. 커넥션 스트링과 API 키는 10-3 의 비밀값으로 런타임에 주입한다.

i

이 방식이 좋은 이유 보강

단점만 있는 것은 아니다. 오히려 비밀이 아닌 설정에 대해서는 이 방식이 더 낫다. 환경별 설정이 이미지와 함께 버전 관리되므로, "운영 서버의 설정 파일이 언제 누구에 의해 바뀌었는지 아무도 모르는" 상황이 생기지 않는다. 설정 변경도 코드 리뷰와 파이프라인을 거친다.

결국 18-1 의 다단 구조와 같은 결론이다. 이미지에는 안전한 기본값을, 런타임에는 비밀만.

정리

  • 환경별 설정 파일을 모두 이미지에 담고 환경 변수로 선택한다. 주입할 파일이 없어 배포가 단순하다.
  • 설정이 이미지와 함께 버전 관리되어 변경 이력이 남는다.
  • 이미지에 담은 파일은 누구나 읽을 수 있다. 비밀번호와 키는 절대 넣지 않는다.
  • 비밀이 아닌 값은 이미지에, 비밀은 런타임 주입으로 — 이것이 전체 설정 전략의 결론이다.
