ITEM 10-1

도커 컴포즈로 여러 개의 앱 배포하기

같은 파일을 두 번 올려도 컨테이너는 하나다. 프로젝트 이름이 다르면 이야기가 달라진다.

핵심 컴포즈는 프로젝트 라는 이름표로 "이 리소스가 어느 앱의 것인지"를 판단한다. 프로젝트 이름이 같으면 기존 것을 재사용하고, 다르면 완전히 별개의 앱으로 취급한다.

동일한 프로젝트 2개 띄우기

이미 실행 중인 프로젝트를 또 실행하면, 이미 떠 있다고 판단해 추가 컨테이너를 만들지 않는다.

terminal 
$ docker-compose -f ./todo-list/docker-compose.yml up -d
[+] Running 2/2
 ✔ Network todo-list_app-net       Created                                      0.0s
 ✔ Container todo-list-todo-web-1  Started                                      0.3s

$ docker-compose -f ./todo-list/docker-compose.yml up -d
[+] Running 1/0
 ✔ Container todo-list-todo-web-1  Running                                      0.0s

$ docker-compose -f ./todo-list/docker-compose.yml up -d
[+] Running 1/0
 ✔ Container todo-list-todo-web-1  Running                                      0.0s

프로젝트(project) 개념

  • 도커 컴포즈는 도커 리소스가 어떤 앱의 일부인지 판단하기 위해 프로젝트라는 개념을 사용한다.
  • 아래 예시는 todo1, todo2 두 프로젝트를 지정해 동일한 컴포즈 파일로 앱을 두 벌 구동한다.
  • 단점은 포트 정보를 일일이 찾아야 한다는 점이다.
terminal 
$ docker-compose -f ./todo-list/docker-compose.yml -p todo1 up -d
[+] Running 1/1
 ✔ Container todo1-todo-web-1  Started                                          0.2s

$ docker-compose -f ./todo-list/docker-compose.yml -p todo2 up -d
[+] Running 1/1
 ✔ Container todo2-todo-web-1  Started                                          0.2s

$ docker ps
CONTAINER ID   IMAGE                   COMMAND                 CREATED         STATUS         PORTS                       NAMES
a9e87ecca98c   diamol/ch06-todo-list   "dotnet ToDoList.dll"   2 seconds ago   Up 1 second    0.0.0.0:32784->80/tcp       todo2-todo-web-1
0e60f031537b   diamol/ch06-todo-list   "dotnet ToDoList.dll"   5 seconds ago   Up 4 seconds   0.0.0.0:32783->80/tcp       todo1-todo-web-1
i

포트가 32783, 32784 로 나온 이유 보강

컴포즈 파일에 ports: - 80 처럼 컨테이너 포트만 적으면 도커가 사용 가능한 호스트 포트를 자동으로 골라 준다. 같은 앱을 두 벌 띄우면서 포트 충돌이 안 나는 이유가 이것이다. 대신 매번 docker ps 로 확인해야 하는데, docker compose -p todo1 port todo-web 80 으로 해당 서비스의 포트만 콕 집어 볼 수 있다.

리소스 명명 규칙

todo-list_todo-web_1 을 기준으로 살펴본다.

조각정체비고
todo-list 프로젝트 이름 기본값은 컴포즈 파일이 들어 있던 폴더명
todo-web 컴포즈 파일에 정의된 서비스 이름 다른 컨테이너와 통신하기 위한 DNS 도메인 이름으로도 쓰인다
1 컨테이너 번호 스케일링으로 컨테이너 수를 늘리면 함께 증가
!

프로젝트 이름을 폴더명에 맡기지 말 것 보강

기본 프로젝트 이름이 폴더명이라는 것은 곧, 같은 저장소를 다른 이름의 폴더에 clone 하면 다른 앱으로 인식된다는 뜻이다. CI 서버의 작업 디렉터리 이름이 매번 달라지면 기존 컨테이너를 재사용하지 못하고 계속 새 프로젝트가 쌓인다. 프로젝트 이름은 -p 플래그, 환경 변수 COMPOSE_PROJECT_NAME, 또는 컴포즈 파일 최상위의 name: 필드로 명시해 고정하는 편이 안전하다.

compose.yaml 권장 
name: todo-list       # 폴더명과 무관하게 프로젝트 이름을 고정

services:
  todo-web:
    image: diamol/ch06-todo-list

정리

  • 컴포즈는 프로젝트 이름으로 리소스 소유권을 판단한다. 같은 이름이면 재사용, 다르면 별개의 앱.
  • -p 로 프로젝트를 나누면 같은 파일로 여러 벌을 한 서버에 띄울 수 있다.
  • 리소스 이름은 프로젝트-서비스-번호 형식이고, 서비스 이름은 DNS 이름이기도 하다.
  • 기본 프로젝트 이름이 폴더명이므로, 중요한 환경에서는 name: 으로 고정한다.
ITEM 10-2

도커 컴포즈의 오버라이드 파일

환경마다 파일을 통째로 복사하면 90%가 중복된다. 달라지는 부분만 얹는다.

핵심 -f 로 나열한 파일은 순서대로 병합된다. 뒤에 온 파일이 앞을 덮으므로 순서가 곧 우선순위이며, 순서를 잘못 주면 엉뚱한 결과가 나온다.

한 개의 앱을 여러 개의 설정으로 켜야 할 때

  • 대부분은 컴포즈 파일을 환경마다 하나씩 두는 방법을 쓴다.
  • 이 방법은 컴포즈 파일 내용이 90% 이상 중복된다.
  • 더 나은 방법은 나중에 지정된 파일이 이전 파일의 내용을 덮어쓰기(override) 하는 방식이다.
베이스 한 장 + 환경별 차이만 담은 얇은 파일 — 공통 서비스 정의는 한 곳에만 있으므로 고칠 곳도 한 군데다.

덮어쓰기 구성하기

  • 오버라이드 파일에는 해당 환경에서 변경할 항목만 적으면 된다.
  • config 부명령으로 병합 결과가 유효한지 검증할 수 있다. 검증과 결과 출력만 하고 실제로 실행하지는 않는다.
  • 덮어쓰기할 순서대로 -f 플래그로 파일을 나열해야 한다. 순서가 잘못되면 이상한 결과가 나올 수 있다.
docker-compose.yml 
services:
  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - 80
    environment:
      - Database:Provider=Sqlite
    networks:
      - app-net

networks:
  app-net:
docker-compose-v2.yml 
services:
  todo-web:
    image: diamol/ch06-todo-list:v2

docker-compose config

두 컴포즈 스크립트가 병합되어 출력된다.

terminal 
$ docker-compose -f docker-compose.yml -f docker-compose-v2.yml config

name: todo-list
services:
  todo-web:
    environment:
      Database:Provider: Sqlite       # 베이스에서 온 값
    image: diamol/ch06-todo-list:v2   # 오버라이드가 이겼다
    networks:
      app-net: null
    ports:
      - mode: ingress
        target: 80
        protocol: tcp
networks:
  app-net:
    name: todo-list_app-net
!

스칼라는 덮어쓰지만 리스트는 합쳐진다 보강

병합 규칙이 항목 종류마다 다르다는 점이 함정이다. image 같은 단일 값은 뒤의 파일이 덮어쓰지만, ports / volumes 같은 리스트는 합쳐진다. 운영 파일에서 포트를 지우려고 ports 를 다시 쓰면 지워지는 게 아니라 포트가 두 개가 되어 버린다.

그래서 원칙은 베이스에는 모든 환경의 공통분모만 넣는 것이다. 일부 환경에서만 필요한 포트나 볼륨은 베이스가 아니라 그 환경 파일에 적는다. 병합 결과가 의심스러우면 실행 전에 반드시 config 로 확인한다.

실전 예제

  • docker-compose.yml — 베이스 파일
  • docker-compose-dev.yml — 개발용. 헬스 / 디펜던시 체크 비활성화
  • docker-compose-test.yml — CI 환경용. API 포트 미공개
  • docker-compose-uat.yml — 인수 테스트용. 모든 테스트를 꼼꼼히 수행

이렇게 구동된 모든 서비스는 독립적이다. 운영 환경을 제외한 다른 환경에서 도커 컴포즈는 매우 효율적이다.

  • test-numbers-api-1 의 PORTS 가 80/tcp 뿐이다 — CI 용 파일이 API 포트를 공개하지 않았다.

  • -f 나열 순서가 우선순위다. 단일 값은 덮어쓰고 리스트는 합쳐진다.
  • 실행 전 config 로 병합 결과를 확인하는 습관을 들인다.
  • down 할 때도 같은 -p / -f 조합을 줘야 한다.
ITEM 10-3

환경 변수와 비밀값을 이용해 설정 주입하기

설정을 넣는 통로가 네 개다. 무엇을 어디에 넣을지가 이 절의 전부다.

핵심 environment / env_file / secrets / .env 는 각각 다른 문제를 푼다. 가독성 / 공유 / 민감도 / 기본값 중 무엇이 필요한지로 고른다.

도커 컴포즈의 환경 변수 및 설정 파일

대부분의 앱은 환경 변수나 설정 파일에서 설정을 불러오는데, 도커 컴포즈도 이를 잘 지원한다.

비밀값

  • 도커 컴포즈 / 스웜, 쿠버네티스 모두 지원하는 기능으로 설정값을 주입하기에 매우 유용하다.
  • 원본 위치와 대상 위치를 모두 지정할 수 있다.
    • 원본 위치 — 런타임이 비밀값을 읽어 오는 곳
    • 대상 위치 — 컨테이너 안에서 비밀값이 위치할 경로
루트 컴포즈 파일
  • 아래는 todo-db-connection 으로부터 설정을 읽어 오게 되어 있다.
  • 이 값을 읽으려면 그 이름으로 정의된 값이 컴포즈 파일에 있어야 한다.
  • 비밀값의 내용은 컨테이너 속 경로인 /app/config/secrets.json 으로 전달된다.
  • 아래 스크립트에는 비밀값 정의가 없으므로 단독으로 쓰면 유효하지 않다.
docker-compose.yml (베이스) 
services:
  todo-web:
    image: diamol/ch06-todo-list
    secrets:
      - source: todo-db-connection
        target: /app/config/secrets.json
개발용 컴포즈 파일의 환경 변수 설정
항목하는 일특징
environment 컨테이너 내부에서만 쓰이는 환경 변수를 추가 설정값을 전달받는 가장 간단한 방법
env_file 텍스트 파일 경로를 값으로 받고, 그 파일에 정의된 환경 변수를 컨테이너에 적용 등호로 구분해 한 줄에 하나씩 표기. 여러 컴포넌트가 공유 가능
secrets 실제 값이나 파일 경로를 전달 services, networks 처럼 최상위 프로퍼티
docker-compose-dev.yml 
services:
  todo-web:
    ports:
      - 8089:80
    environment:
      - Database:Provider=Sqlite
    env_file:
      - ./config/logging.debug.env

secrets:
  todo-db-connection:
    file: ./config/empty.json

호스트 PC 의 환경 변수 전달하기

  • 컴포즈 파일을 수정하지 않아도 설정값을 바꿀 수 있어 이식성이 좋아진다.
  • 아래 예시에서 호스트 PC 의 환경 변수 TODO_WEB_PORT 가 9000 이라면 9000:80 이 된다.
docker-compose-prod.yml 
services:
  todo-web:
    ports:
      - "${TODO_WEB_PORT}:80"
    environment:
      - Database:Provider=Postgres
    env_file:
      - ./config/logging.information.env
    networks:
      - app-net

secrets:
  todo-db-connection:
    file: ./config/secrets.json

.env 사용하기

  • .env 를 쓰면 따로 지정하지 않아도 값이 자동으로 채워진다.
!

원문 교정 — 환경별 env 파일도 가능하다 원문 교정

노트에는 ".env 파일만 인식하기 때문에 환경별로 만드는 건 불가능하다"고 적혀 있으나, 컴포즈는 --env-file 플래그로 다른 파일을 지정할 수 있다. 공식 문서가 명시하는 보간(interpolation) 우선순위는 다음과 같다.

  1. 셸 환경 변수

    가장 우선한다.

  2. --env-file 로 지정한 파일

    지정하면 프로젝트 디렉터리의 .env 를 대체한다.

  3. 프로젝트 디렉터리의 .env

    --env-file 이 없을 때만 쓰인다.

terminal 환경별 분리 
$ docker compose --env-file ./config/dev.env  -p dev  up -d
$ docker compose --env-file ./config/prod.env -p prod up -d

다만 "기본 이름은 .env 하나뿐"이라는 원문의 관찰은 정확하다. 플래그 없이 자동으로 읽히는 파일은 여전히 .env 하나다.

정리 — 어떤 방법을 언제 쓸까

environment
  • 프로퍼티로 환경 변수를 지정하는 가장 간단하고 가독성 좋은 방법이다.
  • 평문으로 작성되기 때문에 민감한 정보에는 쓰지 않는 것이 좋다.
비밀값에 설정값 지정
  • 유출될 여지도 적고 런타임에도 적용 가능해서 유연성이 매우 뛰어나다.
  • 비밀값의 실제 값은 로컬 파일 시스템이나 관련 플랫폼에 저장할 수 있다.
  • 값이 어디 있건 앱이 실행될 때 컨테이너 내부의 특정 파일로 전달된다.
설정값을 파일에 저장하고 env_file 에 경로를 지정하는 방법
  • 여러 서비스가 공유하는 설정이 많은 경우 유용하다.
  • 컴포즈가 로컬 파일을 읽어 각 설정값을 지정하므로, 원격에서 실행 중인 도커 엔진을 다룰 때도 로컬 PC 의 설정값을 적용할 수 있다.
.env 파일
  • 환경을 막론하고 기본 설정을 지정할 때 유용하다.
i

한 번에 보는 선택 기준 보강

방법적용 대상민감 정보주 용도
environment컨테이너 환경 변수✗ 부적합짧고 명확한 설정
env_file컨테이너 환경 변수✗ 부적합여러 서비스가 공유하는 설정 묶음
secrets컨테이너 안의 파일✓ 상대적으로 안전커넥션 스트링, 키
.env컴포즈 파일 자체의 ${VAR}✗ 부적합포트 / 태그 등 기본값

.env 와 env_file 은 이름이 비슷하지만 층이 다르다. .env 는 컴포즈 파일을 읽는 시점에 ${VAR} 를 치환하고, env_file 은 컨테이너 안 프로세스의 환경 변수를 채운다. environment 로 넘긴 값은 docker inspect 에 그대로 노출되므로 비밀번호는 반드시 secrets 쪽으로 보낸다.

정리

  • 설정 주입 통로는 environment / env_file / secrets / .env 네 가지다.
  • .env 는 컴포즈 파일의 ${VAR} 치환용, env_file 은 컨테이너 환경 변수용으로 층이 다르다.
  • 민감한 값은 secrets 로 파일 주입한다. 환경 변수는 inspect 에 노출된다.
  • --env-file 로 환경별 env 파일을 쓸 수 있다. 자동으로 읽히는 이름만 .env 하나다.
ITEM 10-4

확장 필드로 중복 제거하기

노트에서는 "잘 안 쓰므로 패스"로 넘어간 절. 무엇을 넘겼는지만 짧게 남겨 둔다.

i

원문 노트에서는 "잘 안 쓰므로 패스"로 넘어간 절이다

나중에 필요해질 때 되돌아올 수 있도록 골자만 남긴다.

무엇을 푸는 기능인가

10-2 의 오버라이드는 파일 사이의 중복을 없앤다. 확장 필드는 한 파일 안, 서비스 사이의 중복을 없앤다. 서비스가 여러 개인데 로깅 설정이나 네트워크 지정이 똑같이 반복될 때 쓴다.

기본 골자

x- 로 시작하는 최상위 키는 컴포즈가 무시한다. 여기에 공통 조각을 정의해 두고, YAML 의 앵커(&)와 별칭(*), 병합 키(<<)로 각 서비스에 끌어다 쓴다.

중복 
services:
  api:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
  web:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
확장 필드 
x-logging: &default-logging
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"

services:
  api:
    logging: *default-logging
  web:
    logging: *default-logging
!

파일 하나 안에서만 유효하다 보강

앵커와 별칭은 YAML 파서 수준의 기능이라 같은 파일 안에서만 해석된다. 베이스 파일에 정의한 앵커를 오버라이드 파일에서 참조할 수는 없다. 그래서 "파일 사이 중복은 오버라이드, 파일 안 중복은 확장 필드"로 역할이 갈린다. 노트가 이 절을 건너뛴 것도 무리는 아니다. 서비스가 서너 개 수준이면 중복을 그냥 두는 편이 오히려 읽기 쉽다.

정리

  • x- 로 시작하는 최상위 키는 컴포즈가 무시하므로 공통 조각을 담아 둘 수 있다.
  • YAML 앵커 / 별칭으로 서비스마다 끌어다 쓴다.
  • 같은 파일 안에서만 동작한다. 파일 사이 중복은 오버라이드로 푼다.
  • 서비스가 적으면 굳이 쓸 필요 없다.
ITEM 10-5

도커를 이용한 설정 워크플로 이해하기

여기까지 배운 것을 한 문장으로 묶으면 — 이미지는 그대로 두고 설정만 바꿔 가며 승격시킨다.

핵심 모든 환경에서 동일한 이미지를 사용한다. 이것이 이 장 전체의 결론이며, "테스트 환경에서 통과한 그 이미지"가 그대로 운영에 가는 유일한 방법이다.

앱 구성 요소의 조합

  • 모든 환경에서 전체 스택을 실행할 필요는 없다.
  • 오버라이드 파일을 써서 공통 서비스는 그대로 두고, 환경마다 필요한 서비스를 달리하는 설정을 깔끔하게 작성할 수 있다.

컨테이너 설정

  • 각 환경의 상황과 요구 사항에 맞춰 설정을 바꿀 필요가 있다.
  • 오버라이드와 네트워크를 통해 단일 서버에 격리된 여러 앱을 실행할 수 있다.

앱 설정

  • 환경별로 컨테이너 내부 동작이 달라야 하는 경우가 있다.
  • 로그 수준, 캐시 크기 등을 상황에 맞게 컨테이너에 주입할 수 있다.

중요한 점

  • 모든 환경에서 동일한 이미지를 사용하게 된다.
  • 최종적으로 여러 단계를 거쳐 프로덕션에 배포할 수 있게 된다.
flowchart LR
  IMG["이미지 1개 (myapp:2.1.106)"] -->|"+ dev 오버라이드"| DEV["dev"]
  IMG -->|"+ test 오버라이드"| TEST["test"]
  IMG -->|"+ uat 오버라이드"| UAT["uat"]
  IMG -->|"+ prod 오버라이드 / 비밀값"| PROD["production"]
  DEV -.->|"통과"| TEST
  TEST -.->|"통과"| UAT
  UAT -.->|"통과"| PROD
화살표가 전부 같은 이미지에서 나온다 — 환경마다 다시 빌드하지 않는다. 바뀌는 것은 오버라이드 파일과 주입되는 설정뿐이고, 단계를 통과할 때마다 같은 산출물이 승격된다.
✓

환경마다 다시 빌드하면 무엇이 깨지는가

운영 배포 직전에 docker build 를 다시 돌리면, 그것은 테스트를 통과한 이미지가 아니다. 기반 이미지의 latest 가 그사이 바뀌었을 수도, 패키지 저장소의 버전이 올라갔을 수도 있다. 테스트가 검증한 대상과 운영에 나가는 대상이 달라지는 순간, 그 테스트는 아무것도 보증하지 못한다.

그래서 파이프라인은 한 번 빌드하고, 태그를 붙이고, 그 태그를 각 환경으로 옮긴다. 이 원칙이 5-4 의 태그 전략과 11장 의 CI 절차를 하나로 묶는다.

정리

  • 환경 차이는 이미지가 아니라 오버라이드 파일과 주입 설정으로 표현한다.
  • 모든 환경이 같은 이미지를 쓴다. 이것이 테스트가 의미를 갖는 조건이다.
  • 단계를 통과할 때마다 같은 산출물이 다음 환경으로 승격된다.
