ITEM 12-1

컨테이너 오케스트레이션 도구

여러 대의 호스트를 한 대처럼 다루게 해 주는 것. 그리고 원하는 상태를 계속 지켜 주는 것.

핵심 오케스트레이터는 컴포즈가 못 하던 일을 한다 — 선언한 상태를 계속 유지하고, 그 유지를 여러 대의 호스트에 걸쳐 수행한다.

컨테이너 오케스트레이션 도구

  • 기본적으로 클러스터로 구성되는 여러 대의 호스트 컴퓨터를 의미한다.
  • 안정적인 서비스 운영을 위해서는 고가용성이 필요한데, 이때 오케스트레이션 도구가 필요해진다.
  • 작업 분배, 관리, 로드밸런싱 등을 담당한다.
어느 서버에 뜰지는 개발자가 정하지 않는다 — YAML 로 "무엇이 몇 개 떠 있어야 하는가"만 선언하면, 오케스트레이터가 배치와 유지를 맡는다. 도커 API 를 그대로 쓰는 것도 여전하다.
i

기능내용컴포즈

8장 에서 "도커 엔진은 unhealthy 를 기록만 한다"고 했던 것을 실제 조치로 바꿔 주는 층이 바로 여기다.

정리

  • 오케스트레이터는 여러 대의 호스트를 하나의 클러스터로 묶어 준다.
  • YAML 로 원하는 상태를 선언하면 배치와 유지는 플랫폼이 맡는다.
  • 스케줄링 / 자동 복구 / 롤링 업데이트가 컴포즈와의 결정적 차이다.
ITEM 12-2

도커 스웜으로 클러스터 만들기

설치할 것이 없다. 도커 엔진에 이미 들어 있고, 명령 하나로 켠다.

핵심 스웜의 가장 큰 장점은 진입 비용이 거의 없다는 것이다. docker swarm init 한 줄이면 그 순간부터 그 머신이 매니저 노드가 된다.

도커 스웜으로 클러스터 만들기

  • 도커 엔진에 내장돼 있어 별도의 설치가 필요 없다.
  • docker swarm init 으로 스웜 모드로 전환한다.
  • 출력의 docker swarm join ... 부분은 다른 PC 를 이 스웜에 참여시킬 때 입력하는 명령이다.
  • 스웜에 추가된 컴퓨터를 노드라고 부르며, 스웜과 같은 네트워크에 있어야 추가할 수 있다.
  • 쿠버네티스에 비해 클러스터를 구성하고 관리하는 작업이 단순하다.
terminal 
$ docker swarm init

Swarm initialized: current node (jdzrsgh27yrhzppkwwsnhxjiq) is now a manager.

To add a worker to this swarm, run the following command:

    docker swarm join --token SWMTKN-1-4zcbdnqxxr34ockht1oret9pvusn6c409y7n89u5iu2k70fkgh-3bq1p0m44t276olpkieb93t7p 198.19.248.65:2377

To add a manager to this swarm, run 'docker swarm join-token manager' and follow the instructions.

관련 명령어들

terminal 
# 스웜에 참여 중인 노드 목록 확인
$ docker node ls

ID                            HOSTNAME   STATUS    AVAILABILITY   MANAGER STATUS   ENGINE VERSION
jdzrsgh27yrhzppkwwsnhxjiq *   orbstack   Ready     Active         Leader           27.3.1
i

매니저와 워커, 그리고 Leader 보강

노드에는 두 역할이 있다. 매니저는 클러스터 상태를 관리하고 스케줄링을 결정하며, 워커는 배정받은 컨테이너를 실행하기만 한다. 매니저는 Raft 합의 알고리즘으로 상태를 복제하는데, 그중 실제로 결정을 내리는 하나가 위 출력의 Leader 다.

합의 알고리즘 특성상 매니저는 홀수 개여야 하고, (N-1)/2 대까지 장애를 견딘다. 매니저 3대면 1대, 5대면 2대까지 죽어도 클러스터가 유지된다. 매니저가 과반을 잃으면 실행 중인 컨테이너는 계속 돌지만 새로운 스케줄링 결정을 내리지 못한다.

!

join 토큰은 자격 증명이다 보강

SWMTKN-... 토큰을 가진 사람은 누구나 클러스터에 노드를 붙일 수 있다. 문서나 채팅에 그대로 붙여 넣지 말고, 유출됐다면 docker swarm join-token --rotate worker 로 재발급한다. 스웜은 2377(관리), 7946(노드 간 통신), 4789(오버레이 네트워크) 포트를 쓰므로 이들 역시 신뢰하는 네트워크에서만 열어야 한다.

정리

  • docker swarm init 한 줄로 스웜 모드가 켜지고 그 노드가 매니저가 된다.
  • 노드는 매니저와 워커로 나뉘고, 매니저는 홀수 개로 두어 과반을 유지한다.
  • join 토큰은 자격 증명이므로 유출되면 즉시 재발급한다.
ITEM 12-3

도커 스웜 서비스로 앱 실행하기

컨테이너를 지워도 다시 살아난다. 이것이 "원하는 상태를 유지한다"의 실제 모습이다.

핵심 스웜에서는 컨테이너를 직접 다루지 않는다. 서비스를 선언하면 스웜이 레플리카 수를 맞추고, 하나가 사라지면 즉시 새로 만든다.

도커 스웜 서비스로 앱 실행하기

  • 서비스를 배포하면 스웜이 컨테이너를 알아서 실행한다. 직접 실행할 필요가 없다.
  • 서비스는 도커 스웜의 일급 객체로, 도커 엔진이 스웜 모드이거나 매니저에 연결된 상태여야 한다.
terminal 
# 서비스 실행
$ docker service create --name timecheck --replicas 1 diamol/ch12-timecheck:1.0
vbrmfwap9empswux9licqj8jz
overall progress: 1 out of 1 tasks
1/1: running   [==================================================>]
verify: Service vbrmfwap9empswux9licqj8jz converged

# 서비스 확인
$ docker service ls
ID             NAME        MODE         REPLICAS   IMAGE                       PORTS
vbrmfwap9emp   timecheck   replicated   1/1        diamol/ch12-timecheck:1.0

레플리카(Replica) 란

  • 도커 스웜에서 서비스를 구성하는 컨테이너를 레플리카라고 부른다. 도커 기준으로는 평범한 컨테이너다.
  • 동일하게 docker container 명령으로 제어할 수 있지만, 스웜이 제어하므로 직접 다룰 일은 많지 않다.
명령어들
terminal 
# 특정 서비스의 레플리카(컨테이너) 목록 확인
$ docker service ps timecheck
ID             NAME          IMAGE                       NODE       DESIRED STATE   CURRENT STATE
qlazk5o5r0y8   timecheck.1   diamol/ch12-timecheck:1.0   orbstack   Running         Running 15 minutes ago

# 현재 컴퓨터에서 실행 중인 컨테이너 확인
$ docker container ls
CONTAINER ID   IMAGE                       COMMAND                  CREATED          STATUS          NAMES
f880fd1e8b5d   diamol/ch12-timecheck:1.0   "dotnet TimeCheck.dll"   15 minutes ago   Up 15 minutes   timecheck.1.qlazk5o5r0y8f82qtoanaxv9d

# 가장 최근에 실행된 컨테이너 1개 삭제
$ docker container rm -f $(docker container ls --last 1 -q)
f880fd1e8b5d

# 하나를 종료했는데 도커 스웜이 새로운 컨테이너를 띄웠다
$ docker service ps timecheck
ID             NAME              IMAGE                       NODE       DESIRED STATE   CURRENT STATE                    ERROR
u5d8gatt116j   timecheck.1       diamol/ch12-timecheck:1.0   orbstack   Running         Running less than a second ago
qlazk5o5r0y8    \_ timecheck.1   diamol/ch12-timecheck:1.0   orbstack   Shutdown        Failed 6 seconds ago             "task: non-zero exit (137)"
✓

이 출력이 이 장의 핵심 장면이다

컨테이너를 강제로 지웠는데 1초도 안 되어 새 레플리카가 떠 있다. timecheck.1 이라는 이름은 그대로이고 그 아래 \_ 로 옛 시도가 이력으로 남는다. 컴포즈였다면 지워진 채로 끝났을 것이다(7-5). exit 137 은 SIGKILL 로 종료됐다는 뜻이다(128 + 9).

docker service 명령어

스웜 모드에서 앱을 관리하기 위한 명령으로, 전반적인 정보를 확인할 수 있다.

terminal 
# 최근 10초간의 로그를 출력
$ docker service logs --since 10s timecheck
timecheck.1.u5d8gatt116j@orbstack    | App version: 1.0; time check: 01:10.43
timecheck.1.u5d8gatt116j@orbstack    | App version: 1.0; time check: 01:10.48

# 서비스 정보 중 이미지 정보를 출력
$ docker service inspect timecheck -f '{{.Spec.TaskTemplate.ContainerSpec.Image}}'
diamol/ch12-timecheck:1.0@sha256:9d3010a572344c988da8e28444ed345c63662a5c211886e670a8ef3c84689b4e
i

태그 뒤에 다이제스트가 붙어 있다 보강

:1.0 뒤에 @sha256:... 이 붙은 것에 주목하자. 스웜은 서비스를 만들 때 태그를 다이제스트로 고정해 저장한다. 누군가 레지스트리에서 1.0 태그를 다른 이미지로 덮어써도, 스웜이 레플리카를 다시 만들 때는 처음 그 이미지를 쓴다. 5-4 에서 말한 "태그는 옮겨 붙지만 다이제스트는 변하지 않는다"가 플랫폼 차원에서 강제되는 것이다.

클러스터 데이터베이스

  • 클러스터에서 운영하는 대부분의 정보는 내부 데이터베이스에 저장된다.
  • 상당히 많은 정보가 저장되며, 이들은 암호화되어 매니저 노드마다 복제본이 저장된다.
  • 또한 컴포즈에서는 앱 정의가 컴포즈 파일에만 있었지만, 스웜 모드에서는 앱 정의가 클러스터에 저장된다.

서비스 정의 변경하기

  • 클러스터에 배포된 앱은 docker service 명령으로 변경한다.
  • 서비스 정의를 변경하면 스웜이 레플리카를 하나씩 새것으로 교체하며 변경 사항을 적용한다.

롤링 업데이트 방식

  • 앱을 중단시키지 않고 컨테이너를 교체하기 위해 롤링 업데이트 방식을 쓴다.
  • 점진적으로 컨테이너를 교체하는 방식이다.
  • 한 번에 몇 개씩 업데이트할지 등 세밀한 설정이 가능하다.
  • 단점은 N 개가 뜨고 N 개가 사라지는 방식이라 사용자가 구/신 버전을 동시에 경험할 수 있다는 점이다. 이는 UX 를 위한 직접 핸들링이 필요하다.
!

구/신 버전 공존이 만드는 진짜 문제 보강

화면이 달라 보이는 정도는 사소한 편이다. 실제로 위험한 것은 DB 스키마 변경이다. 롤링 업데이트 중에는 신버전이 기대하는 스키마와 구버전이 기대하는 스키마가 동시에 살아 있어야 한다.

그래서 스키마 변경은 보통 두 단계로 나눈다. 먼저 구버전도 신버전도 동작하는 하위 호환 변경(컬럼 추가 등)만 배포하고, 모든 레플리카가 교체된 뒤 다음 릴리스에서 정리 작업(옛 컬럼 삭제)을 한다. "컬럼 이름 바꾸기"를 한 번에 하면 롤링 업데이트 도중 반드시 깨진다.

롤백

  • 스웜의 데이터베이스에 이전 버전의 서비스 정의가 남아 있어 명령어 한 줄로 롤백할 수 있다.
  • 보통 새 버전 컨테이너에 문제가 생겼을 때 바로 되돌리기 위해 쓴다.
terminal 
# 이전 버전으로 롤백
$ docker service update --rollback timecheck

$ docker service ps timecheck

n2swyj106cw7    \_ timecheck.1   diamol/ch12-timecheck:2.0   orbstack   Shutdown        Shutdown 11 seconds ago
u5d8gatt116j    \_ timecheck.1   diamol/ch12-timecheck:1.0   orbstack   Shutdown        Shutdown 10 minutes ago
qlazk5o5r0y8    \_ timecheck.1   diamol/ch12-timecheck:1.0   orbstack   Shutdown        Failed 31 minutes ago     "task: non-zero exit (137)"

# 로그도 1.0 으로 돌아왔다
$ docker service logs --since 25s timecheck

timecheck.1.kp25blzps69a@orbstack    | App version: 1.0; time check: 01:25.49
timecheck.1.n2swyj106cw7@orbstack    | App version: 2.0; time check: 01:25.38

롤백은 한 단계뿐이다 보강

스웜이 보관하는 것은 직전 서비스 정의 하나다. --rollback 을 두 번 실행하면 더 옛날로 가는 게 아니라 방금 되돌린 것을 다시 되돌린다. 두 단계 이상 되돌리려면 --image 로 원하는 태그를 명시해 업데이트해야 한다.

또한 --update-failure-action rollback 을 걸어 두면 업데이트 중 헬스체크 실패가 감지될 때 자동으로 롤백한다. 8장 의 헬스체크가 여기서 무중단 배포의 안전장치로 쓰인다.

정리

  • 스웜에서는 컨테이너가 아니라 서비스를 선언한다. 레플리카가 사라지면 즉시 새로 만든다.
  • 앱 정의가 컴포즈 파일이 아니라 클러스터 DB 에 저장되고 매니저마다 암호화 복제된다.
  • 서비스 이미지 태그는 다이제스트로 고정되어 저장된다.
  • 업데이트는 롤링 방식이라 구/신 버전이 잠시 공존한다. 스키마 변경은 두 단계로 나눈다.
  • 롤백은 직전 정의 한 단계까지만 가능하다.
ITEM 12-4

클러스터 환경에서 네트워크 트래픽 관리하기

컴포즈에서는 IP 목록이 돌아왔지만, 스웜에서는 가상 IP 하나가 돌아온다.

핵심 스웜은 서비스에 가상 IP(VIP) 하나를 주고 그 뒤에서 트래픽을 나눈다. 앱이 로드밸런싱을 신경 쓸 필요가 없어지고, DNS 캐싱 문제도 사라진다.

스웜 모드에서의 네트워크

  • 기본적으로 스웜 모드의 네트워크는 표준 TCP/IP 방식을 쓴다.
  • 서로 다른 노드에서 실행 중인 컨테이너 간 통신도 되지만 앱에서 신경 쓸 필요가 없다.
  • 스웜 모드에서는 오버레이 네트워크(overlay network) 라는 새로운 형태의 도커 네트워크를 쓸 수 있다.

오버레이 네트워크(overlay network)

  • 클러스터에 속한 모든 노드를 연결하는 가상 네트워크다.
  • 서비스 이름을 도메인 삼아 다른 서비스와 통신할 수 있다. 기존에는 어디로 통신할지가 컨슈머의 몫이었지만, 스웜의 오버레이 네트워크는 가상 IP 주소 하나를 반환해 준다.
  • 다만 서로 다른 네트워크끼리는 통신할 수 없다.
terminal 
# 오버레이 네트워크 iotd-net 생성
$ docker network create --driver overlay iotd-net
lwy5bisjofbv65b1sle6r87ji

# 웹서버를 3개의 레플리카로 실행
$ docker service create -d --replicas 3 --network iotd-net --name iotd diamol/ch09-image-of-the-day
avljyx7xkzox9nric2beosn5j

# 로그서버를 2개의 레플리카로 실행
$ docker service create -d --replicas 2 --network iotd-net --name accesslog diamol/ch09-access-log
jxp52k8fw9zsz5q0jrild7fsz

# 서비스가 구동되는 모습
$ docker service ls

VIP 방식이 DNS 캐싱 문제를 근본적으로 없앤다 — 7-3 에서 클라이언트가 IP 를 캐싱해 옛 컨테이너로 붙던 문제가, 주소가 하나뿐이면 생기지 않는다.

인그레스 네트워크(Ingress Network)

  • 특정 노드가 통신 불가 상태일 경우 같은 네트워크 내의 다른 노드로 트래픽을 전달한다.
  • 한 노드에서 컨테이너가 여러 개 실행 중이면 도커 엔진이 컨테이너에 요청을 고르게 분배한다.
  • 서비스의 포트를 공개하는 경우 인그레스 네트워크가 기본적으로 적용된다.
i

라우팅 메시(routing mesh) 보강

인그레스가 만들어 내는 효과를 라우팅 메시라고 부른다. 핵심은 클러스터의 어느 노드로 요청을 보내든 서비스에 닿는다는 것이다. 그 노드에 해당 레플리카가 하나도 없어도, 노드가 알아서 레플리카가 있는 노드로 넘겨준다.

덕분에 앞단 로드밸런서 설정이 단순해진다. "어느 노드에 무엇이 떠 있는지"를 추적할 필요 없이 모든 노드를 백엔드로 등록해 두면 된다.

!

오탈자 교정 원문 교정

원문의 "새로운 형태의 노커 네트워크"는 "도커 네트워크"의 오타다. 본문에는 고쳐서 실었다.

정리

  • 오버레이 네트워크는 클러스터의 모든 노드를 잇는 가상 네트워크다.
  • 서비스 조회 시 IP 목록이 아니라 가상 IP 하나가 돌아오고, 분산은 스웜이 맡는다.
  • 인그레스 네트워크 덕분에 어느 노드로 요청해도 서비스에 닿는다(라우팅 메시).
ITEM 12-5

도커 스웜, 쿠버네티스 중 뭘 쓸까

기술 우열이 아니라 운영 환경의 문제다. 매니지드 서비스가 있는가 없는가.

핵심 판단 기준은 단순하다. 클라우드면 쿠버네티스(매니지드가 있으니), 온프레미스면 스웜(직접 운영해야 하니). 복잡도를 누가 감당하느냐의 문제다.

도커 스웜

  • 온프레미스 환경일 경우 권장된다.
  • 클라우드 매니지드 서비스가 없기 때문에 모든 인프라 구성을 직접 해야 한다.
  • 초기에 도입했다가 쿠버네티스가 필요해질 때 넘어가는 방법도 있다.

쿠버네티스

  • 클라우드 환경일 경우 권장된다.
  • AWS, GCP 등 대부분의 클라우드에서 매니지드 서비스를 제공한다.
  • 도커 스웜에 비해 러닝 커브가 높다.

스웜은 아직 살아 있다 최신 반영

도커의 엔터프라이즈 사업이 Mirantis 로 넘어간 뒤 "스웜은 끝났다"는 인식이 퍼졌지만, Mirantis 는 최소 2030년까지 스웜을 지원하겠다고 공식적으로 밝혔고 CSI 스토리지 지원, Seccomp / AppArmor 프로파일 API 같은 기능 추가와 정기 보안 업데이트가 계속되고 있다.

따라서 "스웜을 고르면 곧 죽는 기술에 올라타는 것"은 아니다. 다만 생태계의 무게 중심이 쿠버네티스에 있다는 사실은 그때보다 더 확고해졌다. 채용 시장, 문서, 서드파티 도구, 클라우드 통합 모두 쿠버네티스 쪽이 압도적이다. 원문의 결론 — 온프레미스면 스웜, 클라우드면 쿠버네티스 — 는 여전히 실용적인 판단 기준으로 유효하다.

i

어느 쪽을 고르든 잃지 않는 것 보강

지금까지 만들어 온 것 — Dockerfile, 멀티 스테이지 빌드, 헬스체크, 디펜던시 체크, /metrics 엔드포인트, 설정 주입 — 은 플랫폼에 종속되지 않는다. 스웜에서 쿠버네티스로 옮길 때 바뀌는 것은 배포 정의 파일(docker-compose.yml → 매니페스트)이지 이미지가 아니다. 8-3 에서 커스텀 체크 유틸리티를 만든 이유도 정확히 이것이었다.

정리

  • 클라우드면 쿠버네티스, 온프레미스면 스웜이 실용적인 기준이다.
  • 스웜은 진입 비용이 낮고 지원도 2030년까지 이어진다. 다만 생태계는 쿠버네티스가 압도적이다.
  • 이미지와 체크 로직은 플랫폼에 종속되지 않는다. 옮겨 갈 때 바뀌는 것은 배포 정의뿐이다.
