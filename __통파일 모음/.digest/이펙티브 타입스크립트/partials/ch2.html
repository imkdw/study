ITEM 6

편집기를 사용하여 타입 시스템 탐색하기

타입스크립트를 설치하면 컴파일러와 함께 언어 서비스가 딸려 온다. 타입 시스템을 배우는 가장 빠른 길은 편집기에 물어보는 것이다.

핵심 타입을 어떻게 추론하는지 직접 보면서 감을 잡아야 한다. 마우스를 올리는 습관 하나가 이 책의 절반이다.

1. 변수의 타입 추론

let num = 0;
let num: number
초기값 0 으로부터 number 가 추론된다. : number 를 적을 필요가 없다.

2. 함수 반환값의 타입 추론

function add(a: number, b: number) {
  return a + b;
}
function add(a: number, b: number): number
숫자 + 숫자는 숫자. 반환 타입을 적지 않아도 number 로 추론된다. 왜 굳이 적지 않는 게 나은지는 아이템 19에서 다룬다.

3. 조건문 분기 안에서의 타입 좁히기

function logMessage(message: string | null) {
  if (message) {
    console.log(message);
  }
}
(parameter) message: string
매개변수는 string | null 인데, if 블록 안에서는 string 으로 좁혀져 있다. 이 동작이 아이템 22의 주제다.

4. 객체 안쪽의 추론 결과 한 번에 보기

const foo = {
  x: [1, 2, 3],
  bar: {
    name: "Fred",
  },
};
const foo: { x: number[]; bar: { name: string; }; }
중첩된 객체도 통째로 추론된다. x 가 number[] 로 넓혀진 것에 주목할 것 — 아이템 21.

5. 메서드 체이닝 중간의 타입

function restOfPath(path: string) {
  return path.split("/").slice(1).join("/");
}
(method) Array<string>.slice(start?: number, end?: number): string[]
배열의 일부를 얕게 복사해 새 배열로 반환한다. 음수를 넘기면 끝에서부터 센다. 예를 들어 -2 는 마지막 두 개를 뜻한다.
split("/") 가 string[] 를 돌려주므로 slice 는 Array<string> 의 메서드로 해석된다. 짧은 체인에서는 사소하지만, 긴 체인에서 어디부터 타입이 어긋났는지 찾을 때 결정적이다.

6. 오류 메시지를 읽고 코드를 고치기

dom.ts 두 군데에서 같은 오류 
function getElement(elOrId: string | HTMLElement | null): HTMLElement {
  if (typeof elOrId === "object") {
    return elOrId;
    //     ~~~~~~~ 'HTMLElement | null' 형식은 'HTMLElement' 형식에 할당할 수 없습니다.
  } else if (elOrId === null) {
    return document.body;
  } else {
    return document.getElementById(elOrId);
    //     ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ 'HTMLElement | null' 형식은 ...
  }
}
×

왜 두 번 다 null 이 남았나

첫 번째는 typeof null === "object" 라는 자바스크립트의 유명한 특성 때문이다. object 분기에 null 이 그대로 들어온다. 두 번째는 getElementById 자체가 HTMLElement | null 을 반환하기 때문이다.

dom.ts null 을 먼저 걷어낸다 
function getElement(elOrId: string | HTMLElement | null): HTMLElement {
  if (!elOrId) {
    return document.body;
  }

  if (typeof elOrId === "object") {
    return elOrId; // HTMLElement
  }

  const el = document.getElementById(elOrId);
  if (!el) {
    throw new Error(`Element with id ${elOrId} not found`);
  }
  return el;
}

ITEM 7

타입이 값들의 집합이라고 생각하기

이 챕터에서 가장 중요한 관점 전환. 타입을 "할당 가능한 값들의 집합"으로 보면 나머지가 전부 따라온다.

핵심 "A 는 B 에 할당 가능하다", "A 는 B 를 상속한다", "A 는 B 의 서브타입이다" — 셋 다 "A 는 B 의 부분집합이다" 라는 한 문장의 다른 표현이다.
  • 런타임에 모든 변수는 자바스크립트 세상의 값으로부터 정해지는 고유한 값을 갖는다.
  • 코드가 실행되기 전, 타입 체커가 오류를 검사하는 시점에는 타입을 갖는다.
  • 타입은 할당 가능한 값들의 집합이다. 이 집합을 타입의 범위라고 부르기도 한다.
  • 42, 37.5 는 number 에 속하지만 "Canada" 는 속할 수 없다.
  • null 과 undefined 가 number 에 속하는지는 strictNullChecks 설정에 따라 달라진다.

집합 크기 순으로 본 타입들

타입스크립트 용어집합 용어예
never공집합 ∅아무 값도 할당할 수 없다
리터럴 타입 (유닛 타입)원소가 1개인 집합type A = "A"
유니온 A | B합집합 ∪"A" | "B"
인터섹션 A & B교집합 ∩Person & LifeSpan
A extends BA ⊆ B부분집합
unknown전체집합모든 값이 속한다

가장 작은 집합 — never

sets.ts 
const a: never = 12;
//    ~ 'number' 형식은 'never' 형식에 할당할 수 없습니다.

never 는 아무 값도 포함하지 않는 공집합이다. 그래서 어떤 값도 할당할 수 없다.

그다음으로 작은 집합 — 유닛 타입(리터럴 타입)

sets.ts 
type A = "A";
type B = "B";
type Twelve = 12;

// 여러 개를 묶으려면 유니온
type AB = A | B;          // "A" | "B"
type AB12 = A | B | Twelve; // "A" | "B" | 12

여기서 타입스크립트 오류 메시지의 "할당 가능한" 이라는 표현이 집합의 언어로 번역된다. "~의 원소" 또는 "~의 부분집합"이라는 뜻이다.

sets.ts 
const a: AB = "A";  // 정상. "A" 는 { "A", "B" } 의 원소
const c: AB = "C";
//    ~ '"C"' 형식은 'AB' 형식에 할당할 수 없습니다.

const ab: AB = Math.random() < 0.5 ? "A" : "B";
const ab12: AB12 = ab;  // 정상. { "A","B" } ⊆ { "A","B",12 }

declare let twelve: AB12;
const back: AB = twelve;
//    ~~~~ 'AB12' 형식은 'AB' 형식에 할당할 수 없습니다.
//         '12' 형식은 'AB' 형식에 할당할 수 없습니다.
할당 가능성은 방향이 있다 — 작은 집합의 값은 큰 집합에 넣을 수 있지만, 그 반대는 안 된다. 12 가 AB 에 들어갈 자리가 없기 때문이다.

인터섹션(&) — 값의 집합에 적용되는 연산

sets.ts 
interface Person {
  name: string;
}
interface LifeSpan {
  birth: Date;
  death?: Date;
}
type PersonSpan = Person & LifeSpan;

const ps: PersonSpan = {
  name: "John",
  birth: new Date("1999-09-21"),
  death: new Date("2000-09-21"),
}; // 정상
!

직관과 다른 지점

Person 과 LifeSpan 은 공통 속성이 하나도 없다. 그래서 & 의 결과가 never 가 될 것 같지만 그렇지 않다. & 는 속성이 아니라 값의 집합에 적용되기 때문이다.

"Person 인 값들의 집합"과 "LifeSpan 인 값들의 집합"의 교집합에는, 두 조건을 동시에 만족하는 값이 들어간다. 구조적 타이핑에서 타입은 열려 있으므로(아이템 4) 그런 값은 얼마든지 만들 수 있다. 결과적으로 인터섹션 타입의 값은 각 타입의 속성을 모두 가진다.

keyof 를 끼우면 방향이 뒤집힌다

sets.ts 
type K = keyof (Person | LifeSpan); // never

어떤 값이 Person 이거나 LifeSpan 이라고만 알고 있다면, 확실히 있다고 말할 수 있는 속성은 하나도 없다. 그래서 never 다. 이 관계는 두 줄로 정리된다.

외워 둘 만한 항등식 
keyof (A & B) = (keyof A) | (keyof B)
keyof (A | B) = (keyof A) & (keyof B)

extends — 부분집합을 선언하는 방법

sets.ts 
interface Vector1D { x: number; }
interface Vector2D extends Vector1D { y: number; }
interface Vector3D extends Vector2D { z: number; }
상속 방향과 집합 크기는 반대다 — Vector3D 는 "더 많은 것"을 가졌지만, 그 조건을 만족하는 값의 개수는 더 적다.

제네릭 한정자로 쓰이는 extends

sets.ts 
function getKey<K extends string>(val: any, key: K) {
  // ...
}

getKey({}, "x");                                  // "x" 는 string 의 부분집합
getKey({ x: 1 }, Math.random() < 0.5 ? "x" : "y"); // "x" | "y" 도 마찬가지
getKey({}, document.title);                       // string 자기 자신도 포함
getKey({}, 12);
//         ~~ 'number' 형식의 인수는 'string' 형식의 매개 변수에 할당될 수 없습니다.

여기서 K extends string 을 "K 는 string 을 상속한다"로 읽으면 어색하다. "K 는 string 의 부분집합이다" 로 읽으면 위 네 줄이 전부 자연스럽게 설명된다. 리터럴도, 리터럴의 유니온도, string 자기 자신도 string 의 부분집합이다.

sets.ts 
interface Point { x: number; y: number; }
type PointKeys = keyof Point; // "x" | "y"

function sortBy<K extends keyof T, T>(vals: T[], key: K): T[] {
  // ...
}

const pts: Point[] = [{ x: 1, y: 2 }, { x: 3, y: 4 }];

sortBy(pts, "x");                              // 정상
sortBy(pts, "y");                              // 정상
sortBy(pts, Math.random() < 0.5 ? "x" : "y");  // 정상
sortBy(pts, "z");
//          ~~~ '"z"' 형식의 인수는 'keyof Point' 형식의 매개 변수에 할당될 수 없습니다.

상속 관계가 아닌 타입들 — 집합 관점이 필요한 이유

sets.ts 
type T = (string | number) & (string | Date); // string

상속 트리로는 설명할 수 없지만 집합으로는 자명하다. 두 합집합의 교집합에 남는 건 string 뿐이다. 배열과 튜플의 관계도 마찬가지다.

sets.ts 
const list = [1, 2];                     // number[]
const tuple: [number, number] = list;
//    ~~~~~ 'number[]' 형식은 '[number, number]' 형식에 할당할 수 없습니다.
//          대상에 2개 요소가 필요하지만, 소스에 더 적게 있을 수 있습니다.

const tuple2: [number, number] = [1, 2];
const list2: number[] = tuple2;          // 정상
i

방향을 다시 확인해 보자

[number, number] 는 "길이가 정확히 2 인 숫자 배열"의 집합, number[] 는 "길이가 얼마든 상관없는 숫자 배열"의 집합이다. 전자가 후자의 부분집합이므로 tuple → list 는 되고 list → tuple 은 안 된다.

정리

  • 타입을 값의 집합으로 생각하면 할당 가능성이 곧 부분집합 관계가 된다.
  • & 는 교집합, | 는 합집합을 계산한다. 단 속성이 아니라 값에 적용된다.
  • "A 는 B 에 할당 가능하다" = "A 는 B 를 상속한다" = "A 는 B 의 서브타입이다" = "A 는 B 의 부분집합이다".
  • 배열과 튜플, 유니온의 인터섹션처럼 상속으로 설명되지 않는 관계도 집합으로는 명확하다.
ITEM 8

타입 공간과 값 공간의 심벌 구분하기

타입스크립트의 심벌은 타입 공간과 값 공간 중 한 곳에 존재한다. 이름이 같아도 서로 다른 것일 수 있다.

핵심 지금 읽고 있는 이름이 어느 공간의 것인지 항상 구분해야 한다. 헷갈리는 오류 메시지의 상당수가 여기서 나온다.

같은 이름, 다른 존재

cylinder.ts 문제가 생기는 구조 
interface Cylinder {          // 타입 공간
  radius: number;
  height: number;
}

const Cylinder = (radius: number, height: number) => ({ radius, height }); // 값 공간

function calculateVolume(shape: unknown) {
  if (shape instanceof Cylinder) {
    return shape.radius * shape.height * Math.PI;
    //           ~~~~~~ '{}' 형식에 'radius' 속성이 없습니다.
  }
}

instanceof 는 런타임 연산이므로 값 공간의 Cylinder, 즉 화살표 함수를 참조한다. 타입 좁히기가 의도대로 되지 않는다.

!

원문 교정 원문 교정

원문 노트에는 인터페이스 속성이 raidus 로, 화살표 함수 반환 객체가 ({ radius, history }) 로 적혀 있었다. 각각 radius 와 ({ radius, height }) 의 오타로 보여 바로잡았다.

공간을 확인하는 실전 팁 보강

TypeScript Playground 에 코드를 붙여 넣고 컴파일된 자바스크립트를 본다. 사라진 것은 타입, 남은 것은 값이다. 이보다 확실한 판별법은 없다.

class 와 enum — 양쪽에 동시에 존재한다

cylinder.ts 클래스로 바꾸면 동작한다 
class Cylinder {
  radius = 1;
  height = 1;
}

function calculateVolume(shape: unknown) {
  if (shape instanceof Cylinder) {  // 값으로 참조 (생성자 함수)
    return shape.radius * shape.height * Math.PI;
    //     shape: Cylinder — 타입으로도 참조되어 좁혀졌다
  }
}

클래스가 타입으로 쓰일 때는 인스턴스의 형태(속성과 메서드)를, 값으로 쓰일 때는 생성자를 가리킨다.

typeof — 공간에 따라 완전히 다른 연산자

공간하는 일결과
타입값을 읽어 타입스크립트 타입을 돌려준다정밀한 타입
값자바스크립트 런타임 typeof 연산자"object", "function" 등 8개 문자열 중 하나
typeof.ts 
interface Person { first: string; last: string; }
const p: Person = { first: "Kim", last: "Dongwoo" };

type T1 = typeof p;   // Person
const v1 = typeof p;  // "object"

declare function email(p: Person, subject: string, body: string): Response;

type T2 = typeof email;
// (p: Person, subject: string, body: string) => Response
const v2 = typeof email; // "function"

typeof 를 클래스에 쓰면

typeof.ts 
class Cylinder {
  radius = 1;
  height = 1;
}

const v = typeof Cylinder; // "function" — JS 에서 class 는 함수다
type T = typeof Cylinder;  // typeof Cylinder — 인스턴스가 아니라 생성자 타입!

타입 T 는 Cylinder 인스턴스가 아니라 생성자 함수의 타입이다. 인스턴스 타입이 필요하면 한 번 더 꺼내야 한다.

typeof.ts 
declare let fn: T;
const c = new fn();              // Cylinder

type C = InstanceType<typeof Cylinder>; // Cylinder

indexed.ts 
interface Person { first: string; last: string; }

타입 단언보다는 타입 선언을 사용하기

둘 다 타입을 붙이는 방법이지만, 하나는 검사를 하고 하나는 검사를 건너뛴다.

핵심 const x: T = ... 는 검사이고, const x = ... as T 는 선언이다. 기본값은 언제나 전자다.
타입 선언 검사한다 
interface Person { first: string; last: string; }

const dongwoo: Person = { first: "Kim" };
//    ~~~~~~~ 'last' 속성이 '{ first: string; }'
//            형식에 없지만 'Person' 형식에서 필수입니다.
타입 단언 검사하지 않는다 
interface Person { first: string; last: string; }

const dongwoo = { first: "Kim" } as Person;
// 오류 없음. 런타임에 last 는 undefined.

단언은 "타입스크립트가 추론한 타입이 있어도 내 말이 맞으니 그렇게 간주하라"는 뜻이다. 잉여 속성 체크(아이템 11)도 함께 꺼진다.

화살표 함수에서 흔한 실수

// 1. 원하는 건 Person[] 인데
const people1 = ["alice", "bob", "jan"].map((name) => ({ name }));
//    { name: string }[]

// 2. 단언으로 때우면 타입은 맞지만 검사가 사라진다
const people2 = ["alice", "bob", "jan"].map((name) => ({} as Person));
//    Person[] — name 이 하나도 없는데 오류가 나지 않는다

// 3. 반환 타입을 선언하는 게 정답
const people3 = ["alice", "bob", "jan"].map((name): Person => ({ name }));
//    Person[] — 속성이 빠지면 바로 잡힌다
!

2번이 왜 위험한가

({} as Person) 은 빈 객체를 Person 이라고 우겨 넘긴 것이다. 컴파일은 통과하고 people2 의 타입도 Person[] 이지만, 런타임 배열에는 {} 세 개가 들어 있다. 원문 노트가 "단언을 쓰면 오류가 발생한다"고 적은 부분은 정확히는 오류가 발생하지 않는 것이 문제다. 원문 교정

세 번째 형태는 화살표 함수의 반환 타입 선언이다. (name): Person => 에서 : Person 이 매개변수가 아니라 반환값에 붙는다는 점을 잘 봐야 한다.

그래도 단언이 필요한 경우

타입스크립트가 알 수 없는 정보를 개발자가 알고 있을 때다. DOM 조작이 대표적이다.

ITEM 10

객체 래퍼 타입 피하기

string 은 쓰고 String 은 쓰지 않는다. 대문자로 시작하는 래퍼 타입은 거의 언제나 실수다.

핵심 타입 자리에는 항상 소문자 기본형을 쓴다. String, Number, Boolean, Symbol, BigInt 는 타입으로 쓰지 않는다.

기본형에 메서드가 있는 것처럼 보이는 이유

wrapper.ts 
const str = "string";      // typeof str === "string"
console.log(str.charAt(1)); // "t"

기본형에는 메서드가 없다. 자바스크립트가 필요한 순간에 String 객체로 임시 래핑하고, 메서드 호출이 끝나면 버릴 뿐이다. 몽키 패치를 하면 이 과정을 눈으로 볼 수 있다.

monkey.js 
const originalCharAt = String.prototype.charAt;

String.prototype.charAt = function (pos) {
  console.log(this, typeof this, pos);
  return originalCharAt.call(this, pos);
};

console.log("primitive".charAt(1)); // "r"
!

출력이 두 가지로 갈린다 원문 교정

실행 환경console.log(this, typeof this, pos)

엄격 모드 (ESM, "use strict")primitive 'string' 1

원문 노트는 두 번째(엄격 모드) 결과를 기록했다. 둘 다 맞지만, "래핑된다"는 사실이 눈에 보이는 쪽은 첫 번째다. 엄격 모드에서는 this 가 박싱되지 않고 기본형 그대로 전달된다.

ITEM 11

잉여 속성 체크의 한계 인지하기

구조적 타이핑이라면 통과해야 할 코드가 막힌다. 이건 버그가 아니라 별개의 검사가 하나 더 돌기 때문이다.

핵심 잉여 속성 체크는 객체 리터럴을 타입이 명시된 자리에 직접 대입할 때만 작동한다. 할당 가능성 검사와는 다른 절차다.

같아 보이는데 결과가 다르다

직접 대입 오류 
interface Room {
  numDoors: number;
  ceilingHeightFt: number;

  numDoors: 1,
  ceilingHeightFt: 10,
  elephant: "present",

이건 또 다른 검사다

모든 속성이 선택적인 타입을 약한 타입(weak type) 이라고 하고, 여기에는 공통 속성 체크가 따로 돈다. "값과 선언 타입에 공통 속성이 최소 하나는 있어야 한다"는 규칙이다. 잉여 속성 체크와 달리 변수를 거쳐도 작동한다는 점이 다르다.

정리

  • 객체 리터럴을 타입이 명시된 변수에 대입하거나 함수에 인수로 전달할 때 잉여 속성 체크가 수행된다.
  • 오타를 잡는 데 효과적이지만 적용 범위가 매우 제한적이다. 임시 변수를 거치거나 단언을 쓰면 꺼진다.
  • 이 한계를 알고 있어야 "왜 여기서는 오류가 나고 저기서는 안 나지?" 라는 혼란을 피할 수 있다.
  • 선택적 속성만 있는 약한 타입에는 공통 속성 체크라는 별도 규칙이 적용된다.
ITEM 12

함수 표현식에 타입 적용하기

함수의 매개변수부터 반환값까지 전체를 하나의 타입으로 선언할 수 있다. 이게 함수 표현식을 쓰는 가장 큰 이유다.

핵심 함수 문장 대신 함수 표현식을 쓰면 시그니처를 타입으로 뽑아내 재사용할 수 있다.
forms.ts 
function rollDice1(sides: number): number { /* ... */ }        // 문장(statement)
const rollDice2 = function (sides: number): number { /* ... */ }; // 표현식(expression)
const rollDice3 = (sides: number): number => { /* ... */ };      // 표현식

반복 제거

함수 문장 시그니처가 네 번 반복 
function add(a: number, b: number) { return a + b; }
function sub(a: number, b: number) { return a - b; }
function mul(a: number, b: number) { return a * b; }
function div(a: number, b: number) { return a / b; }
함수 표현식 한 번만 선언 
type BinaryFn = (a: number, b: number) => number;

const add: BinaryFn = (a, b) => a + b;
const sub: BinaryFn = (a, b) => a - b;
const mul: BinaryFn = (a, b) => a * b;
const div: BinaryFn = (a, b) => a / b;

매개변수 a, b 에 타입을 적지 않았는데도 number 로 추론된다. 문맥에서 타입이 흘러들어오기 때문이다(아이템 26).

실전 — fetch 감싸기

quote.ts 숨은 버그 
async function getQuote() {
  const response = await fetch("https://api.something.com/quote");
  const json = await response.json();
  return json;
}
×

404 가 오면

fetch 는 HTTP 오류 상태에서도 reject 하지 않는다. 서버가 "404 Not Found" 같은 HTML 이나 텍스트를 돌려주면 response.json() 이 파싱에 실패하고, 호출한 쪽은 404 와 아무 상관 없는 파싱 오류 메시지를 받는다. 진짜 원인이 가려진다.

checked-fetch.ts 1차 개선 
async function checkedFetch(input: RequestInfo, init?: RequestInit) {
  const response = await fetch(input, init);
  if (!response.ok) {
    throw new Error("Request failed: " + response.status);
  }
  return response;
}

여기서 typeof fetch 를 쓰면 매개변수 타입을 다시 적을 필요조차 없어진다.

checked-fetch.ts 2차 개선 
const checkedFetch: typeof fetch = async (input, init) => {
  const response = await fetch(input, init);
  if (!response.ok) {
    throw new Error("Request failed: " + response.status);
  }
  return response;
};
  • 함수 문장을 함수 표현식으로 바꿨다.
  • 함수 전체에 typeof fetch 를 적용해 input, init 이 자동으로 추론되게 했다.
  • 덤으로 반환 타입까지 보장된다. 실수로 throw 대신 return 을 쓰면 바로 잡힌다.
checked-fetch.ts throw 를 return 으로 잘못 쓴 경우 
const checkedFetch: typeof fetch = async (input, init) => {
//    ~~~~~~~~~~~~
// '(input: RequestInfo | URL, init?: RequestInit) => Promise<Response | Error>' 형식은
// '(input: RequestInfo | URL, init?: RequestInit) => Promise<Response>' 형식에
// 할당할 수 없습니다.
  const response = await fetch(input, init);
  if (!response.ok) {
    return new Error("Request failed: " + response.status); // throw 여야 한다
  }
  return response;
};
i

라이브러리를 감쌀 때 습관 보강

다른 함수의 시그니처를 그대로 따라야 한다면 typeof 원본함수 를 붙이는 것이 가장 안전하다. 원본 라이브러리가 시그니처를 바꾸면 내 래퍼에서 즉시 오류가 난다. 매개변수를 손으로 베껴 적었다면 조용히 어긋난 채로 남았을 것이다.

정리

  • 매개변수나 반환값에 타입을 각각 명시하기보다 함수 표현식 전체에 타입 구문을 적용하는 것이 낫다.
  • 같은 시그니처를 반복해서 쓴다면 함수 타입을 분리해 내거나 이미 있는 타입을 찾는다.
  • 라이브러리 함수를 감쌀 때는 typeof fn 을 쓴다.
ITEM 13

타입과 인터페이스의 차이점 알기

둘은 대부분의 경우 서로 바꿔 쓸 수 있다. 그러니 중요한 건 바꿔 쓸 수 없는 몇 가지다.

핵심 복잡한 타입이면 type. 간단한 객체 타입이면 팀 컨벤션을 따른다. 다만 선언 병합이 필요한지 아닌지는 반드시 의식하고 고른다.
type 
type TState = {
  name: string;
  capital: string;
};
interface 
interface IState {
  name: string;
  capital: string;
}
i

접두사 I 는 관례가 아니다

여기서는 두 방식을 구분하려고 T/I 를 붙였지만, 실제 코드에서 IState 같은 헝가리안 표기는 권장되지 않는다. 타입스크립트 공식 코딩 가이드라인에서도 인터페이스 이름에 I 를 붙이지 말라고 명시한다.

한눈에 보는 비교표

함수 타입✓✓단순 함수는 type 이 읽기 편하다
제네릭✓✓
서로 확장✓✓& 와 extends

공통점 — 대부분은 똑같다

차이점 1 — 유니온 인터페이스는 없다

// 유니온에 속성을 덧붙이려면 type 과 & 가 필요하다
type Input = { /* ... */ };

i

병합이 꼭 필요한 곳

타입스크립트는 표준 라이브러리를 이 방식으로 조립한다. lib.es5.d.ts 에 interface Array<T> 가 있고, tsconfig.json 의 lib 에 es2015 를 넣으면 lib.es2015.core.d.ts 의 interface Array<T> { find(...) } 가 병합되어 메서드가 늘어난다. 서드파티 라이브러리의 타입을 확장하는 모듈 보강(아이템 43)도 같은 원리다.

반대로 말하면, 내 프로젝트의 도메인 타입이 여기저기서 병합되고 있다면 설계가 잘못된 것이다. 그런 경우라면 type 을 써서 중복 선언 자체를 막는 편이 낫다.

그래서 뭘 쓰나

  1. 복잡한 타입이면 type

    유니온, 튜플, 매핑된 타입, 조건부 타입은 선택의 여지가 없다.

  2. 공개 API 나 라이브러리 타입이면 interface 를 고려

    사용자가 모듈 보강으로 확장할 수 있어야 한다면 인터페이스여야 한다.

  3. 그 외 간단한 객체 타입은 팀 컨벤션

    일관성이 어느 쪽을 고르느냐보다 중요하다.

정리

  • type 과 interface 는 대부분 상호 교환 가능하다. 차이점을 알고 일관되게 쓴다.
  • 유니온, 튜플, 매핑된 타입, 조건부 타입은 type 으로만 표현된다.
  • 선언 병합은 interface 만 지원한다. 표준 라이브러리와 모듈 보강이 이 기능 위에 서 있다.
  • 병합이 일어나면 안 되는 타입이라면 type 을 쓰는 것 자체가 방어책이 된다.
ITEM 14

타입 연산과 제네릭 사용으로 반복 줄이기

코드에는 DRY 를 적용하면서 타입에는 적용하지 않는 경우가 많다. 도구를 모르기 때문이다.

핵심 타입에도 이름을 붙이고, 확장하고, 계산해서 반복을 없앤다. 값에서 하던 리팩터링을 타입에서도 똑같이 한다.

1. 타입에 이름 붙이기

전 중복 
function distance(
  a: { x: number; y: number },
  b: { x: number; y: number }
) {
  return Math.sqrt(
    (a.x - b.x) ** 2 + (a.y - b.y) ** 2
  );
}
후 이름을 붙였다 
interface Point2D {
  x: number;
  y: number;
}

function distance(a: Point2D, b: Point2D) {
  return Math.sqrt(
    (a.x - b.x) ** 2 + (a.y - b.y) ** 2
  );
}

함수 시그니처 전체가 반복될 때도 마찬가지다(아이템 12).

http.ts

const get: HTTPFunction = (url, options) => { /* ... */ };

Pick 은 그냥 매핑된 타입이다

4. 유니온에서 뽑아내기

type ActionType2 = Action["type"];   // "save" | "load"  ← 유니온 인덱싱

type ActionType3 = Pick<Action, "type">;
// { type: "save" | "load" } — 객체가 나온다. 원하던 게 아니다!
!

Pick 과 인덱싱의 차이

Action["type"] 은 속성의 타입을 꺼내고, Pick<Action, "type"> 은 그 속성만 남긴 객체 타입을 만든다. 이름이 비슷해 헷갈리기 쉬운 지점이다.

방향에 주의

값에서 타입을 뽑는 방향으로만 쓴다. 반대로 타입을 먼저 정의하고 값이 그 타입을 따르게 하는 편이 나은 경우가 더 많다. 값에서 타입을 뽑으면 값을 잘못 고쳤을 때 타입이 조용히 따라 바뀌어 오류가 드러나지 않는다.

7. 함수 반환값에서 타입 만들기 — ReturnType

function parseCSV(input: string): { [columnName: string]: string }[] {
  const lines = input.split("\n");
  const [header, ...rows] = lines;
  const headerColumns = header.split(",");

  return rows.map((rowStr) => {
    const row: { [columnName: string]: string } = {};
    rowStr.split(",").forEach((cell, index) => {
      row[headerColumns[index]] = cell;
    });
    return row;
  });
}

변경 관련된 오류 방지를 위해 readonly 사용하기

함수가 매개변수를 바꾸지 않는다는 사실을 타입으로 선언하면, 그 약속을 컴파일러가 지켜 준다.

핵심 변경하지 않는 매개변수에는 readonly 를 붙인다. 오류를 잡고, 의도를 문서화하고, 호출하는 쪽의 부담을 줄인다.

function printTriangles(n: number) {

}

// 기대: 0 1 3 6 10
// 실제: 0 1 2 3 4

깊은 readonly 가 필요하다면 보강

표준 라이브러리에는 없다. ts-essentials 의 DeepReadonly 같은 것을 쓰거나 직접 재귀 타입을 만든다. 다만 깊은 readonly 는 오류 메시지가 급격히 길어지므로, 대부분은 얕은 것으로 충분하다는 판단이 먼저다.

타입과 코드가 같이 바뀌도록 묶어 두는 기법. 속성을 추가했을 때 컴파일러가 "여기도 고쳐라"라고 알려 준다.

핵심 { [K in keyof T]: ... } 로 만든 상수 객체는, T 가 바뀌면 반드시 함께 고쳐야만 컴파일된다.

방법 1 — 보수적, 실패에 닫힌(fail close) 접근

    if (oldProps[k] !== newProps[k]) {

  return false;
}

  • 인터페이스에 새 속성을 추가할 때 선택을 강제하고 싶다면 이 패턴을 쓴다.
