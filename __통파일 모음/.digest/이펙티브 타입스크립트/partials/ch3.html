ITEM 19

추론 가능한 타입을 사용해 장황한 코드 방지하기

타입스크립트를 처음 쓰면 모든 곳에 타입을 적게 된다. 좋은 타입스크립트 코드는 타입 구문이 적은 코드다.

핵심 타입 추론이 되는 자리에 타입을 적으면 가독성만 떨어지고 얻는 게 없다. 대신 추론되지 않는 자리에는 반드시 적는다.

적지 않아도 되는 곳

infer.ts 
let a: number = 1;  // ✗ 군더더기
const a2 = 1;       // ✓ 1 로 추론

const person: { name: string; age: number } = { name: "John", age: 32 }; // ✗
const person2 = { name: "John", age: 32 };                               // ✓

함수 내부의 지역 변수도 마찬가지다. 비구조화 할당을 쓰면 모든 지역 변수의 타입이 한 번에 추론된다.

장황함 타입 세 번 반복 
function logProduct(product: Product) {
  const id: number = product.id;
  const name: string = product.name;
  const price: number = product.price;
  console.log(id, name, price);
}
비구조화 할당 추론에 맡긴다 
function logProduct(product: Product) {
  const { id, name, price } = product;
  console.log(id, name, price);
}
!

타입을 적으면 오히려 틀린다

위 왼쪽 코드에서 Product.id 가 number 에서 string 으로 바뀌었다고 하자. 오른쪽은 아무 수정 없이 그대로 동작하지만, 왼쪽은 세 줄을 고쳐야 한다. 명시적 타입은 고쳐야 할 자리를 늘린다.

반드시 적어야 하는 곳

자리적는가이유
함수 매개변수거의 항상추론할 근거가 없다 (기본값이 있으면 예외)
객체 리터럴가급적잉여 속성 체크가 켜진다 (아이템 11)
함수 반환값경우에 따라아래 참고
지역 변수거의 안 함추론이 정확하다

반환 타입을 적는 게 나은 세 가지 경우

  1. 호출하는 쪽에 이름을 보여 주고 싶을 때
    vector.ts 
    // 추론 결과: { x: number; y: number }
function add(a: Vector2D, b: Vector2D) {
  return { x: a.x + b.x, y: a.y + b.y };
}

// 명시하면 호출자가 Vector2D 라는 개념을 그대로 본다
function add2(a: Vector2D, b: Vector2D): Vector2D {
  return { x: a.x + b.x, y: a.y + b.y };
}
  2. 구현 오류가 반환 타입 오류로 드러나게 하고 싶을 때

    반환 타입을 적어 두면 오류가 함수 안에서 잡힌다. 적지 않으면 오류가 호출하는 쪽까지 흘러가서 원인을 찾기 어려워진다.

  3. 명명된 타입을 쓰고 싶을 때

    공개 API 라면 반환 타입에 이름이 있어야 문서로서 읽힌다(아이템 47).

i

린터로 강제하기 보강

typescript-eslint 의 @typescript-eslint/no-inferrable-types 규칙은 const a: number = 1 같은 군더더기를 자동으로 잡아 준다. 반대로 공개 API 의 반환 타입을 강제하고 싶다면 explicit-module-boundary-types 를 켠다. 두 규칙은 이 아이템의 앞뒤를 각각 담당한다.

정리

  • 타입스크립트가 타입을 추론할 수 있다면 적지 않는다.
  • 이상적인 코드는 함수/메서드 시그니처에는 타입이 있고, 본문의 지역 변수에는 없는 형태다.
  • 추론된 타입이 틀리거나 호출자에게 혼란을 줄 때만 명시한다.
ITEM 20

다른 타입에는 다른 변수 사용하기

자바스크립트에서는 변수 하나를 여러 목적으로 재사용할 수 있다. 타입스크립트에서는 그러지 않는 편이 낫다.

핵심 변수의 값은 바뀔 수 있지만 타입은 바뀌지 않는다. 타입이 달라진다면 그건 다른 변수여야 한다.
JavaScript 문제없음 
let id = "12-34-56";
fetchProduct(id);

id = 123456;           // 마음대로
fetchProductBySerial(id);
TypeScript 막힌다 
let id = "12-34-56";  // string
fetchProduct(id);

id = 123456;
// ~~ 'number' 형식은 'string' 형식에
//    할당할 수 없습니다.

유니온으로 억지로 맞출 수는 있지만

union.ts 쓸 때마다 좁혀야 한다 
let id: string | number = "12-34-56";
fetchProduct(id);

id = 123456;
fetchProductBySerial(id);
// 동작은 하지만, 이제 id 를 쓸 때마다 어느 쪽인지 확인해야 한다
separate.ts 그냥 변수를 나눈다 
const id = "12-34-56";
fetchProduct(id);

const serial = 123456;
fetchProductBySerial(serial);
i

변수를 나누면 딸려 오는 것들

  • 서로 관련 없는 두 개념에 다른 이름이 생긴다 — 코드가 자기 자신을 설명한다
  • let 대신 const 를 쓸 수 있다 — 타입 추론이 더 좁고 정확해진다(아이템 21)
  • 타입이 단순해져서 타입 선언을 생략할 수 있다
!

가려진 변수(shadowing)와 구분할 것

다른 스코프에서 같은 이름을 다시 쓰는 건 타입스크립트 입장에서는 완전히 다른 변수라 문제가 없다. 하지만 읽는 사람은 헷갈린다. no-shadow 규칙을 켜 두는 편이 낫다.

정리

  • 변수의 값은 바뀔 수 있어도 타입은 일반적으로 바뀌지 않는다.
  • 혼란을 막기 위해 타입이 다른 값을 다룰 때는 변수를 재사용하지 않는다.
ITEM 21

타입 넓히기

하나의 값으로부터 "이 변수에 들어올 수 있는 값들"을 유추하는 과정. 이걸 모르면 추론 결과가 자꾸 어긋난다.

핵심 타입스크립트는 단일 값을 보고 가능한 값들의 집합을 유추한다. 이걸 넓히기(widening) 라고 한다.

let 과 const 의 차이가 여기서 나온다

widening.ts 
interface Vector3D { x: number; y: number; z: number; }

function getComponent(vector: Vector3D, axis: keyof Vector3D) {
  return vector[axis];
}

const v: Vector3D = { x: 1, y: 2, z: 3 };

let axis1 = "x";    // string   ← 나중에 다른 문자열이 올 수 있으니까
const axis2 = "x";  // "x"      ← 재할당이 불가능하니까

getComponent(v, axis1);
//              ~~~~~ 'string' 형식의 인수는 'keyof Vector3D' 형식의
//                    매개 변수에 할당될 수 없습니다.
getComponent(v, axis2); // 정상
재할당 가능성이 집합 크기를 정한다 — let 은 나중에 다른 문자열이 올 수 있으므로 넓게, const 는 그럴 수 없으므로 좁게 추론된다.

const 라도 내부는 넓혀진다

widening.ts 
const mixed = [1, "x"];  // (string | number)[]

const obj = { x: 1, y: "1" };
// { x: number; y: string }  ← "1" 이 아니라 string

const 로 선언해도 배열 요소와 객체 속성은 나중에 바꿀 수 있으므로 넓게 추론된다. obj.x = 2 는 유효한 코드다.

넓히기의 강도를 조절하는 세 가지 방법

1. 명시적 타입 구문
control.ts 
const v: { x: 1 | 3 | 5 } = { x: 1 };
// { x: 1 | 3 | 5 }
2. 문맥 제공

함수 매개변수처럼 타입이 이미 정해진 자리에 값을 넣으면 그 타입이 흘러들어온다(아이템 26).

3. const 단언 — as const
as-const.ts 
const v1 = { x: 1, y: 2 };
// { x: number; y: number }

const v2 = { x: 1 as const, y: 2 };
// { x: 1; y: number }        ← 부분적으로 고정

const v3 = { x: 1, y: 2 } as const;
// { readonly x: 1; readonly y: 2 }  ← 전부 고정 + readonly

const a1 = [1, 2, 3];            // number[]
const a2 = [1, 2, 3] as const;   // readonly [1, 2, 3]
!

const 와 as const 는 다른 것이다

const 는 값 공간에서 변수 재할당을 막는 선언이고, as const 는 타입 공간에서 추론을 리터럴로 고정하는 단언이다(아이템 8). 전자는 얕고 후자는 깊다.

↑

satisfies 연산자 TS 4.9+

"타입은 검사받되 추론은 좁게 유지하고 싶다"는 요구가 오랫동안 있었다. TypeScript 4.9 의 satisfies 가 그 답이다.

satisfies.ts 
type Palette = Record<string, string | [number, number, number]>;

// 타입 선언 — 검사는 되지만 추론이 넓어진다
const p1: Palette = { red: [255, 0, 0], green: "#00ff00" };
p1.red.at(0);       // string | [number,number,number] 라 .at 을 못 쓴다

// satisfies — 검사도 하고 추론도 좁게 유지한다
const p2 = { red: [255, 0, 0], green: "#00ff00" } satisfies Palette;
p2.red.at(0);       // number[] 로 좁혀져 있다
p2.blue;
// ~~~~ 'blue' 속성이 존재하지 않습니다 — 오타도 잡힌다

설정 객체, 상수 맵, 라우트 테이블처럼 "형태는 검증하되 값은 정확히 알고 싶은" 경우에 as const satisfies T 조합이 특히 유용하다.

정리

  • 타입스크립트가 넓히기를 통해 상수의 타입을 추론하는 과정을 이해해야 한다.
  • const, 타입 구문, 문맥, as const 로 넓히기 과정을 제어할 수 있다.
  • 검사는 받되 좁은 추론을 유지하고 싶다면 satisfies 를 쓴다.
ITEM 22

타입 좁히기

넓히기의 반대. 넓은 타입에서 더 좁은 타입으로 범위를 줄이는 과정이다.

핵심 타입스크립트는 제어 흐름을 따라가며 타입을 좁힌다. 어떤 코드가 좁히기를 유발하는지 알아 두면 단언을 쓸 일이 크게 줄어든다.

1. null 체크

narrow.ts 
const el = document.getElementById("el"); // HTMLElement | null
if (el) {
  el; // HTMLElement
} else {
  el; // null
}

// 예외를 던져 남은 코드를 좁히는 방식도 같은 원리다
const el2 = document.getElementById("el2");
if (!el2) throw new Error("#el2 not found");
el2; // HTMLElement

2. instanceof

narrow.ts 
function contains(text: string, search: string | RegExp) {
  if (search instanceof RegExp) {
    search; // RegExp
    return !!search.exec(text);
  }
  search;   // string
  return text.includes(search);
}

3. in 연산자로 속성 확인

narrow.ts 
interface A { a: number; }
interface B { b: number; }

function pickAB(ab: A | B) {
  if ("a" in ab) {
    return ab.a; // A
  }
  return ab.b;   // B
}

4. 내장 함수

narrow.ts 
function contains(text: string, terms: string | string[]) {
  const termList = Array.isArray(terms) ? terms : [terms]; // string[]
  return termList.some((term) => text.includes(term));
}

Array.isArray 는 arg is any[] 라는 타입 서술(type predicate)을 갖고 있어서 좁히기가 작동한다.

5. 명시적 태그 — 태그된 유니온

narrow.ts 가장 견고한 방법 
interface UploadEvent {
  type: "upload";
  filename: string;
  contents: string;
}
interface DownloadEvent {
  type: "download";
  filename: string;
}
type AppEvent = UploadEvent | DownloadEvent;

function handleEvent(event: AppEvent) {
  switch (event.type) {
    case "upload":
      event; // UploadEvent — contents 접근 가능
      break;
    case "download":
      event; // DownloadEvent
      break;
  }
}

6. 사용자 정의 타입 가드

guard.ts 
function isInputElement(el: HTMLElement): el is HTMLInputElement {
  return "value" in el;
}

function getElementContent(el: HTMLElement) {
  if (isInputElement(el)) {
    el;                // HTMLInputElement
    return el.value;
  }
  el;                  // HTMLElement
  return el.textContent;
}

반환 타입 el is HTMLInputElement 가 핵심이다. boolean 으로 두면 좁히기가 일어나지 않는다.

실전 — undefined 걸러 내기

filter.ts 
const jackson5 = ["Jackie", "Tito", "Jermaine", "Marlon", "Michael"];

const members1 = ["Jackie", "Janet"].map((who) =>
  jackson5.find((n) => n === who)
);
// (string | undefined)[]

const members2 = ["Jackie", "Janet"]
  .map((who) => jackson5.find((n) => n === who))
  .filter((who) => who !== undefined);
// (string | undefined)[]  ← TS 5.4 이전에는 좁혀지지 않았다

function isDefined<T>(x: T | undefined): x is T {
  return x !== undefined;
}

const members3 = ["Jackie", "Janet"]
  .map((who) => jackson5.find((n) => n === who))
  .filter(isDefined);
// string[]  ✓
↑

이제는 타입 가드 없이도 된다 TS 5.5+

TypeScript 5.5 부터 타입 서술을 자동으로 추론한다. 함수가 매개변수를 좁히는 불리언 표현식을 그대로 반환하면, 컴파일러가 x is T 를 알아서 붙여 준다.

ts5.5.ts 
const members = ["Jackie", "Janet"]
  .map((who) => jackson5.find((n) => n === who))
  .filter((who) => who !== undefined);
// TS 5.5+ : string[]

다만 인라인 화살표 함수처럼 조건이 맞아야 작동하므로, 복잡한 판별이 필요하면 x is T 를 명시하는 편이 여전히 확실하다.

좁히기가 실패하는 대표적인 두 가지

pitfall.ts typeof null === "object" 
const el = document.getElementById("el"); // HTMLElement | null
if (typeof el === "object") {
  el; // HTMLElement | null  ← 좁혀지지 않았다
}
pitfall.ts falsy 값들이 남는다 
function foo(x?: number | string | null) {
  if (!x) {
    x; // string | number | null | undefined
    //   "" 와 0 도 falsy 이므로 여전히 남아 있다
  }
}
i

헷갈릴 때는 편집기에 물어본다

좁혀졌다고 생각하는 자리에 마우스를 올려 실제 타입을 확인하는 게 가장 빠르다(아이템 6). 안 좁혀졌다면 단언을 붙이기 전에 왜 안 좁혀졌는지 먼저 본다. 거의 언제나 진짜 이유가 있다.

정리

  • 분기문 외에도 instanceof, in, Array.isArray, 태그된 유니온, 타입 가드로 타입을 좁힐 수 있다.
  • 사용자 정의 타입 가드는 반환 타입을 x is T 형태로 쓴다.
  • typeof null === "object" 와 falsy 값 때문에 좁히기가 실패하는 경우를 조심한다.
ITEM 23

한꺼번에 객체 생성하기

변수의 타입은 초기화 시점에 결정된다. 그러니 객체는 한 번에 만드는 게 유리하다.

핵심 속성을 하나씩 추가하지 말고 전개 연산자로 한 번에 만든다.
build.ts 나눠서 만들면 막힌다 
const obj = {};   // {}
obj.x = 1;
//  ~ '{}' 형식에 'x' 속성이 없습니다.
obj.y = 2;
//  ~ '{}' 형식에 'y' 속성이 없습니다.

객체 전개 연산자

build.ts 타입이 자동으로 합쳐진다 
const pt = { x: 3, y: 4 };
const id = { name: "John" };

const obj = { ...pt, ...id };
// { x: number; y: number; name: string }
obj.name; // 정상

조건부로 속성 추가하기

conditional.ts 
declare let hasMiddle: boolean;

const president = {
  first: "John",
  last: "Doe",
  ...(hasMiddle ? { middle: "C" } : {}),
};
// { middle?: string; first: string; last: string }

middle 이 선택적 속성으로 추론되는 것이 핵심이다. 조건이 거짓이면 {} 를 펼치므로 속성이 없을 수도 있음을 타입스크립트가 안다.

conditional.ts 
declare let hasDates: boolean;
const nameTitle = { name: "Khufu", title: "Pharaoh" };

const pharaoh = {
  ...nameTitle,
  ...(hasDates ? { start: -2589, end: -2566 } : {}),
};
// { start?: number; end?: number; name: string; title: string }
!

두 속성은 함께 있거나 함께 없다

위 추론 결과는 start 만 있고 end 는 없는 상태도 허용한다. 실제로는 그럴 수 없는데도 그렇다. 이런 "동시에 존재해야 하는 속성"을 타입으로 정확히 표현하는 방법은 아이템 28에서 다룬다.

헬퍼 함수로 정리하기

helper.ts 
function addOptional<T extends object, U extends object>(
  a: T,
  b: U | null
): T & Partial<U> {
  return { ...a, ...b };
}

const pharaoh = addOptional(
  nameTitle,
  hasDates ? { start: -2589, end: -2566 } : null
);
// { name: string; title: string } & Partial<{ start: number; end: number }>
i

배열도 마찬가지 보강

같은 원리가 배열에도 적용된다. const list = [] 는 never[] 로 시작해 push 가 막히거나, noImplicitAny 아래에서 진화하는 any 가 된다(아이템 41). 루프 안에서 조건부로 담을 때는 filter·flatMap 으로 한 번에 만드는 편이 타입도 코드도 깔끔하다(아이템 27).

정리

  • 속성을 하나씩 추가하기보다 한꺼번에 객체로 만든다. 타입 추론에 유리하다.
  • 안전한 타입으로 속성을 추가하려면 객체 전개를 쓴다.
  • 조건부 속성은 ...(cond ? {k: v} : {}) 패턴으로 선택적 속성으로 만든다.
ITEM 24

일관성 있는 별칭 사용하기

별칭을 만드는 순간 타입스크립트의 제어 흐름 분석이 끊긴다. 이 아이템은 그 지점에 대한 이야기다.

핵심 별칭을 만들었으면 일관되게 그것만 쓴다. 더 나은 방법은 비구조화 할당이다.
i

이 아이템은 원문 노트가 짧아 예제를 보강했습니다 보강

원문에는 "별칭을 남발하면 흐름 파악에 방해가 된다", "구조 분해 할당을 권장한다" 두 줄만 기록되어 있었습니다. 왜 그런지 보여 주는 표준 예제를 채웠습니다.

polygon.ts 
interface Coordinate { x: number; y: number; }

  y: [number, number];

  holes: Coordinate[][];

  if (polygon.bbox) {                // 원본을 검사했다
    if (pt.x < box.x[0] || pt.x > box.x[1] ||
        //   ~~~           ~~~
        // 'box'은(는) 'undefined'일 수 있습니다.

타입스크립트가 옳다

polygon.ts 별칭을 일관되게 쓴다 
function isPointInPolygon(polygon: Polygon, pt: Coordinate) {
  const box = polygon.bbox;
  if (box) {                          // 별칭을 검사한다
    if (pt.x < box.x[0] || pt.x > box.x[1] ||
        pt.y < box.y[0] || pt.y > box.y[1]) {
      return false;
    }
  }
  // ...

더 나은 방법은 비구조화 할당이다. 이름이 하나로 통일되어 애초에 둘을 헷갈릴 수 없다.

function isPointInPolygon(polygon: Polygon, pt: Coordinate) {

      return false;
    }
  }
  // ...
}

타입 체커가 낙관적인 지점

타입스크립트는 fn(polygon) 이 polygon.bbox 를 지웠을 가능성을 무시한다. 매번 무효화하면 실사용이 불가능할 만큼 까다로워지기 때문에 내린 절충이다. 그래서 지역 변수(비구조화 결과)를 쓰는 편이 안전하다. 지역 변수라면 타입 체커가 확실히 추적할 수 있다.

정리

  • 별칭은 타입스크립트가 타입을 좁히는 것을 방해한다. 만들었다면 일관되게 사용한다.
  • 가능하면 비구조화 할당으로 별칭 대신 이름을 통일한다.
  • 함수 호출이 객체 속성의 타입 정제를 무효화할 수 있다는 점을 기억한다. 속성보다 지역 변수를 믿는다.
ITEM 25

비동기 코드에는 콜백 대신 async 함수 사용하기

콜백보다 프로미스, 프로미스보다 async/await. 타입 추론까지 생각하면 선택지는 하나다.

핵심 async 함수는 반드시 프로미스를 반환한다. 이 강제성이 "때로는 동기, 때로는 비동기"라는 최악의 설계를 원천 차단한다.

콜백 지옥

callback.js 실행 순서가 위에서 아래가 아니다 
fetchURL(url1, function (res1) {
  fetchURL(url2, function (res2) {
    fetchURL(url3, function (res3) {
      // ...
    });
  });
});
async.ts 순차 실행 
async function fetchPages() {
  const res1 = await fetch(url1);
  const res2 = await fetch(url2);
  const res3 = await fetch(url3);
  // ...
}

병렬로 돌려야 할 때 — Promise.all

parallel.ts 타입까지 정확히 풀린다 
async function fetchPages() {
  const [res1, res2, res3] = await Promise.all([
    fetch(url1),
    fetch(url2),
    fetch(url3),
  ]);
  // res1, res2, res3 모두 Response 로 추론된다
}

Promise.all 과 비구조화 할당의 조합에서 세 변수의 타입이 한 번에 정확히 추론되는 것이 인상적이다. 콜백으로 같은 일을 하면 타입 추론이 거의 불가능하다.

메서드동작쓰는 곳
Promise.all전부 성공하면 결과 배열, 하나라도 실패하면 reject전부 필요할 때
Promise.race가장 먼저 결정된 것 하나타임아웃 구현
Promise.allSettled전부 기다리고 성공/실패를 모두 보고일부 실패를 허용할 때
Promise.any가장 먼저 성공한 것 하나여러 후보 중 하나면 될 때

타임아웃 — race 의 대표적 쓰임

timeout.ts 
function timeout(millis: number): Promise<never> {
  return new Promise((resolve, reject) => {
    setTimeout(() => reject("timeout"), millis);
  });
}

async function fetchWithTimeout(url: string, millis: number) {
  return Promise.race([fetch(url), timeout(millis)]);
}
i

반환 타입이 왜 Response 인가

timeout 의 반환 타입이 Promise<never> 이기 때문이다. Response | never 의 유니온은 Response 로 정리된다 — 공집합과의 합집합은 원래 집합 그대로다(아이템 7). 타입 구문을 하나도 추가하지 않고도 정확한 타입이 나온다.

가장 중요한 이유 — 일관성

inconsistent.ts 때로는 동기, 때로는 비동기 
const cache: { [url: string]: string } = {};

function fetchWithCache(url: string, callback: (text: string) => void) {
  if (url in cache) {
    callback(cache[url]);   // 동기적으로 즉시 호출
    return;
  }
  fetch(url)
    .then((r) => r.text())
    .then((text) => {
      cache[url] = text;
      callback(text);       // 비동기적으로 나중에 호출
    });
}
×

이런 함수는 쓰기가 극도로 어렵다

캐시가 있을 때와 없을 때 콜백이 호출되는 시점이 다르다. 호출하는 쪽에서는 상태 갱신 순서가 상황에 따라 뒤집히므로, 재현하기 어려운 버그가 생긴다. async 로 바꾸면 이 문제 자체가 사라진다 — 캐시 히트든 아니든 항상 프로미스다.

consistent.ts 언제나 비동기 
const cache: { [url: string]: string } = {};

async function fetchWithCache(url: string) {
  if (url in cache) {
    return cache[url];   // 값을 반환해도 Promise<string> 이 된다
  }
  const response = await fetch(url);
  const text = await response.text();
  cache[url] = text;
  return text;
}
i

중복 요청까지 막고 싶다면 보강

위 코드는 같은 URL 에 대한 동시 요청이 여러 번 나갈 수 있다. 캐시에 값 대신 프로미스를 저장하면 해결된다.

dedupe.ts 
const cache: { [url: string]: Promise<string> } = {};

function fetchWithCache(url: string): Promise<string> {
  if (!(url in cache)) {
    cache[url] = fetch(url).then((r) => r.text());
  }
  return cache[url];
}

정리

  • 콜백보다 프로미스가 코드 작성과 타입 추론 모두에 유리하다.
  • 가능하면 프로미스를 직접 만들기보다 async/await 를 쓴다. 간결하고 오류 처리가 자연스럽다.
  • 어떤 함수가 프로미스를 반환한다면 async 로 선언한다.
  • async 함수는 항상 프로미스를 반환하므로, 동기와 비동기가 섞이는 최악의 설계를 막아 준다.
ITEM 26

타입 추론에 문맥이 어떻게 사용되는지 이해하기

타입스크립트는 값만 보지 않고 그 값이 놓인 자리도 본다. 값을 상수로 분리하는 순간 그 자리가 사라진다.

핵심 값을 변수로 뽑아내면 문맥이 소실되어 추론이 넓어진다. 해결책은 as const, 타입 선언, 또는 시그니처 완화 셋 중 하나다.

문제의 형태 — 인라인일 때는 되는데 분리하면 안 된다

language.ts 
type Language = "JavaScript" | "TypeScript" | "Python";
function setLanguage(lang: Language) { /* ... */ }

setLanguage("JavaScript"); // 정상 — 문맥에서 Language 로 추론

let language = "JavaScript"; // string 으로 넓혀졌다
setLanguage(language);
//          ~~~~~~~~ 'string' 형식의 인수는 'Language' 형식의
//                   매개 변수에 할당될 수 없습니다.
language.ts 두 가지 해법 
// 1. const 로 선언해 리터럴 타입 유지
const language1 = "JavaScript";
setLanguage(language1);

// 2. 타입을 명시해 문맥을 되살린다
let language2: Language = "JavaScript";
setLanguage(language2);

튜플에서 생기는 문제

tuple.ts 
function panTo(where: [number, number]) { /* ... */ }

panTo([10, 20]); // 정상

const loc = [10, 20]; // number[]  ← 길이 정보가 사라졌다
panTo(loc);
//    ~~~ 'number[]' 형식의 인수는 '[number, number]' 형식의
//        매개 변수에 할당될 수 없습니다.

const loc2 = [10, 20] as const; // readonly [10, 20]
panTo(loc2);
//    ~~~~ 'readonly [10, 20]' 형식의 인수는 '[number, number]' 형식의
//         매개 변수에 할당될 수 없습니다.
//         'readonly' 형식은 변경 가능한 형식에 할당할 수 없습니다.
!

as const 만으로는 부족하다

as const 가 길이는 고정했지만 이번엔 readonly 가 걸린다. panTo 는 매개변수를 바꿀 수 있는 타입을 요구하기 때문이다. 진짜 해법은 함수 시그니처를 고치는 것이다 — 아이템 17의 결론과 정확히 같다.

tuple.ts 시그니처를 고친다 
function panTo(where: readonly [number, number]) { /* ... */ }

const loc = [10, 20] as const;
panTo(loc);      // 정상
panTo([10, 20]); // 여전히 정상
×

as const 의 오류는 엉뚱한 곳에서 난다

const loc = [10] as const 처럼 값 자체가 틀린 경우, 오류는 선언한 자리가 아니라 panTo(loc) 호출부에서 난다. 값과 오류 위치가 떨어져 있어 원인을 찾기 어렵다. 특히 중첩된 객체에서 심해진다.

객체에서 생기는 문제

object.ts 
interface GovernedLanguage {
  language: Language;
  org: string;
}
function complain(language: GovernedLanguage) { /* ... */ }

complain({ language: "TypeScript", org: "Microsoft" }); // 정상

const ts = { language: "TypeScript", org: "Microsoft" };
// { language: string; org: string }  ← language 가 넓혀졌다
complain(ts);
//       ~~ '{ language: string; org: string; }' 형식의 인수는
//          'GovernedLanguage' 형식의 매개 변수에 할당될 수 없습니다.

// 해법 1 — as const
const ts2 = { language: "TypeScript", org: "Microsoft" } as const;

// 해법 2 — 타입 선언 (오류가 선언한 자리에서 난다)
const ts3: GovernedLanguage = { language: "TypeScript", org: "Microsoft" };

콜백에서 생기는 문제

callback.ts 
function callWithRandomNumbers(fn: (n1: number, n2: number) => void) {
  fn(Math.random(), Math.random());
}

// 인라인이면 문맥에서 타입이 흘러들어온다

  n2; // number
});

// 분리하면 문맥이 사라진다

//                ~~  ~~ 'n1', 'n2' 매개 변수에 암시적으로 'any' 형식이 있습니다.

// 해법 1 — 매개변수에 타입을 적는다

원문 교정 원문 교정

원문 노트의 마지막 줄이 callWithRandomNumbers(callback) 으로 되어 있는데, 타입을 명시한 callback2 를 넘겨야 의도가 맞다.

정리

  • 타입 추론에서 문맥이 어떻게 쓰이는지 주의해서 살펴야 한다.
  • 변수를 뽑아내서 별도로 선언했을 때 오류가 발생한다면, 문맥 소실이 원인일 가능성이 높다.
  • 변수에 타입 선언을 추가하거나 as const 를 쓴다. 가능하다면 함수 시그니처를 완화하는 것이 가장 깔끔하다.
ITEM 27

함수형 기법과 라이브러리로 타입 흐름 유지하기

자바스크립트에서 서드파티 라이브러리는 취향의 문제였다. 타입스크립트에서는 손익 계산이 달라진다.

핵심 직접 루프를 돌리면 타입 구문을 계속 붙여야 한다. 라이브러리 함수를 쓰면 타입이 알아서 흘러간다.

CSV 파싱 — 세 단계로 줄여 보기

1단계 — 직접 루프 row 의 타입이 {} 라 막힌다 
const rows = rawRows.slice(1).map((rowStr) => {
  const row = {};
  rowStr.split(",").forEach((val, i) => {
    row[headers[i]] = val;
    // ~~~~~~~~~~~~ '{}' 형식에 인덱스 시그니처가 없으므로
    //              요소에 암시적으로 'any' 형식이 있습니다.
  });
  return row;
});
2단계 — reduce 짧아졌지만 타입 구문이 붙었다 
const rows = rawRows
  .slice(1)
  .map((rowStr) =>
    rowStr.split(",").reduce(
      (row, val, i) => ((row[headers[i]] = val), row),
      {} as { [k: string]: string }   // ← 단언이 필요해졌다
    )
  );
3단계 — lodash zipObject 타입 구문 0개 
import { zipObject } from "lodash";

const rows = rawRows
  .slice(1)
  .map((rowStr) => zipObject(headers, rowStr.split(",")));
// { [key: string]: string }[] 로 정확히 추론된다
!

원문 교정 원문 교정

원문 1단계 코드의 row[headers[j]] 에서 j 는 선언되지 않은 변수였다. forEach 의 인덱스 매개변수 index(위에서는 i)를 써야 한다.

팀별 최고 연봉 선수 찾기

명령형 타입 선언 두 개 + 중간 변수 두 개 
interface BasketballPlayer {
  name: string;
  team: string;
  salary: number;
}
declare const allPlayers: BasketballPlayer[];

interface TeamToPlayers {
  [team: string]: BasketballPlayer[];
}

const teamToPlayers: TeamToPlayers = {};
for (const player of allPlayers) {
  const { team } = player;
  teamToPlayers[team] = teamToPlayers[team] || [];
  teamToPlayers[team].push(player);
}

for (const players of Object.values(teamToPlayers)) {
  players.sort((a, b) => b.salary - a.salary);
}

const bestPaid = Object.values(teamToPlayers).map((players) => players[0]);
bestPaid.sort((a, b) => b.salary - a.salary);
lodash 체인 타입 구문 0개 
import _ from "lodash";

const bestPaid = _(allPlayers)
  .groupBy((player) => player.team)
  .mapValues((players) => _.maxBy(players, (p) => p.salary)!)
  .values()
  .sortBy((p) => -p.salary)
  .value();
// BasketballPlayer[]

원문 교정 원문 교정

원문의 .map((players, team) => players.sortBy("salary").first()) 는 실행되지 않는다. players 는 일반 배열이라 sortBy 메서드가 없다. 위 코드는 mapValues + _.maxBy 로 같은 결과를 내는 형태로 고친 것이다.

i

여기서 ! 하나가 필요한 이유

_.maxBy 는 빈 배열을 받으면 undefined 를 반환할 수 있어서 반환 타입이 Player | undefined 다. groupBy 의 결과에는 빈 배열이 있을 수 없지만 타입 시스템은 그걸 모른다. 이럴 때가 아이템 9 가 말하는 "개발자가 더 잘 아는 상황"이다.

이제는 표준 문법으로도 상당 부분 최신 반영

책이 나온 뒤 자바스크립트 표준에 편입된 것들이 있다. Object.groupBy(ES2024)와 Array.prototype.flatMap(ES2019)이 대표적이다. 라이브러리 없이도 타입 흐름을 유지할 수 있는 범위가 넓어졌다.

modern.ts 
// ES2024 — lib 을 "es2024" 이상으로 설정해야 한다
const byTeam = Object.groupBy(allPlayers, (p) => p.team);
// Partial<Record<string, BasketballPlayer[]>>

// flatMap 은 map + filter 를 한 번에 처리한다
const names = allPlayers.flatMap((p) => (p.salary > 1e7 ? [p.name] : []));
// string[]

정리

  • 타입 흐름을 개선하고, 가독성을 높이고, 명시적 타입 구문을 줄이기 위해 내장 함수형 기법과 lodash 같은 라이브러리를 쓴다.
  • 직접 루프를 구현하면 타입 안전성을 잃기 쉽다. 라이브러리 함수는 이미 정확한 타입 선언을 갖고 있다.
  • 같은 코드라도 자바스크립트에서보다 타입스크립트에서 라이브러리를 쓸 이유가 하나 더 있다.
