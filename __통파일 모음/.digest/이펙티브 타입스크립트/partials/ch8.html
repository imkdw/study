ITEM 58

모던 자바스크립트로 작성하기

타입스크립트 마이그레이션의 첫 단계는 타입이 아니다. 구버전 자바스크립트를 최신 자바스크립트로 옮기는 것이다.

핵심 이 작업은 타입스크립트 없이도 가치가 있고, 끝내고 나면 타입 추론이 훨씬 잘 붙는다. 타입스크립트 컴파일러를 트랜스파일러로만 써서 시작할 수도 있다.

1. ECMAScript 모듈 사용하기

CommonJS 과거 
// b.js
const name = "b";
module.exports = { name };

// a.js
const b = require("./b");
console.log(b.name);
ES Modules 현재 
// b.ts
export const name = "b";

// a.ts
import { name } from "./b";
console.log(name);

모듈 단위로 전환할 수 있으므로 마이그레이션의 자연스러운 경계가 된다(아이템 61).

2. 프로토타입 대신 클래스

프로토타입 과거 
function Person(first, last) {
  this.first = first;
  this.last = last;
}

Person.prototype.getName = function () {
  return this.first + " " + this.last;
};

const p = new Person("im", "kdw");
클래스 현재 
class Person {
  first: string;
  last: string;

  constructor(first: string, last: string) {
    this.first = first;
    this.last = last;
  }

  getName() {
    return `${this.first} ${this.last}`;
  }
}
i

편집기가 대신 해 준다

VS Code 에서 function 생성자에 커서를 두고 빠른 수정(Cmd/Ctrl + .) → "ES2015 클래스로 변환"을 쓰면 자동으로 바꿔 준다. 손으로 옮기다 실수하는 것보다 안전하다.

3. var 대신 let / const

  • var 는 함수 스코프이고 호이스팅되어 실행 순서를 예측하기 어렵게 만든다.
  • let/const 는 블록 스코프를 지키므로 기대대로 동작한다.
  • 함수도 마찬가지다. 선언식보다 화살표 함수 표현식이 호이스팅 문제를 피한다.
!

바꾸다 오류가 났다면 그게 소득이다

var 를 let/const 로 바꿨더니 오류가 난다면, 기존 코드에 스코프 문제가 숨어 있었다는 뜻이다. 고칠 기회다.

4. for(;;) 대신 for-of 와 배열 메서드

loop.ts 
const arr = [1, 2, 3];

// C 스타일 — 인덱스 변수를 잘못 쓸 여지가 있다
for (let i = 0; i < arr.length; i++) {
  console.log(arr[i]);
}

// for-of — 가장 간결하다
for (const item of arr) {
  console.log(item);
}

// 인덱스가 필요하면 forEach
arr.forEach((item, index) => {
  console.log(index, item);
});

for-in 은 배열에 쓰지 않는다(아이템 16). 객체를 순회해야 한다면 Object.entries 와 for-of 를 쓴다(아이템 54).

5. 함수 표현식보다 화살표 함수

arrow.ts 
class Foo {
  method() {
    [1, 2].forEach(function (i) {
      console.log(this); // undefined (strict) / globalThis (sloppy)
    });

    [1, 2].forEach((i) => {
      console.log(this); // Foo — 바깥 스코프의 this
    });
  }
}
!

원문 교정 원문 교정

원문 노트에 "함수 선언식의 this 는 window 같은 global 객체를 가리킨다"고 적혀 있는데, 이는 느슨한 모드에서만 그렇다. 엄격 모드(ES 모듈은 항상 엄격 모드다)에서는 undefined 다. 타입스크립트가 컴파일한 코드는 대부분 엄격 모드이므로, 실제로는 undefined 를 만나게 된다.

noImplicitThis(strict 에 포함)를 켜면 이런 this 를 컴파일러가 미리 잡아 준다(아이템 49).

6. 단축 표기법과 구조 분해

shorthand.ts 
const x = 1, y = 2, z = 3;

const pt1 = { x: x, y: y, z: z }; // 장황
const pt2 = { x, y, z };          // 단축 속성

// 화살표 함수에서 객체 반환 — 괄호로 감싼다
const arr1 = ["A", "B"].map((char, index) => {
  return { char, index };
});
const arr2 = ["A", "B"].map((char, index) => ({ char, index }));

// 메서드 단축 표기
const obj = {
  onClick(e: MouseEvent) { /* ... */ },  // onClick: function(e) {...} 과 같다
};
destructuring.ts 
const obj = { props: { a: 1, b: 2 } };

// 중첩 구조 분해
const { props: { a, b } } = obj;

// 기본값
const { c = "default" } = obj.props as { c?: string };

// 배열 구조 분해
const point = [1, 2, 3];
const [px, py, pz] = point;

// 매개변수 기본값
const sum = (a = 0, b = 0) => a + b;

매개변수 기본값을 쓰면 타입이 자동으로 추론된다는 부수 효과도 있다. (a = 0) 은 a: number 로 추론되므로 타입 구문을 적지 않아도 된다(아이템 19).

7. 저수준 프로미스/콜백 대신 async/await

async.ts 
function getJSON1(url: string) {
  return fetch(url).then((response) => response.json());
}

async function getJSON2(url: string) {
  const response = await fetch(url);
  return response.json();
}

코드가 간결해지고, 비동기 코드에 타입 정보가 전달되어 추론이 잘 붙는다(아이템 25).

8. 연관 배열에는 객체 대신 Map

count.ts 프로토타입 오염 
function countWords(text: string) {
  const counts: { [word: string]: number } = {};
  for (const word of text.split(/\s+/)) {
    counts[word] = (counts[word] || 0) + 1;
  }
  return counts;
}

console.log(countWords("Objects have a constructor property"));
// {
//   Objects: 1, have: 1, a: 1,
//   constructor: "function Object() { [native code] }1",  ← ?!
//   property: 1
// }
×

무슨 일이 일어났나

counts["constructor"] 는 undefined 가 아니라 Object.prototype.constructor 함수다. || 가 그걸 통과시키고, 함수 + 1 이 문자열 연결이 되어 저 괴상한 값이 나왔다. toString, valueOf, __proto__ 도 같은 문제를 일으킨다.

count.ts Map 은 프로토타입이 없다 
function countWords(text: string) {
  const counts = new Map<string, number>();
  for (const word of text.split(/\s+/)) {
    counts.set(word, 1 + (counts.get(word) ?? 0));
  }
  return counts;
}

console.log(countWords("Objects have a constructor property"));
// Map(5) { "Objects" => 1, "have" => 1, "a" => 1,
//          "constructor" => 1, "property" => 1 }
i

Map 을 쓰는 다른 이유들 보강

  • 키가 문자열이 아니어도 된다 — 객체, 숫자, 심벌 모두 가능
  • 삽입 순서가 보장된다 (객체는 숫자 같은 키가 앞으로 정렬된다)
  • size 로 개수를 바로 알 수 있다
  • 잦은 추가·삭제에서 성능이 낫다

객체를 꼭 써야 한다면 Object.create(null) 로 프로토타입 없는 객체를 만들거나, 조회에 Object.hasOwn(obj, key)(ES2022)를 쓴다.

9. "use strict" 를 직접 넣지 않기

타입스크립트에서 수행되는 안전성 검사는 "use strict" 보다 훨씬 엄격하다. 필요하다면 alwaysStrict(strict 에 포함)를 켜면 컴파일러가 출력 파일에 알아서 넣어 준다. 소스 코드에 직접 쓰지 않는다.

정리

  • 타입스크립트 개발 환경은 모던 자바스크립트도 실행할 수 있으므로, 모던 문법을 적극 사용한다.
  • 코드 품질이 올라가고 타입스크립트의 추론도 더 잘 동작한다.
  • 마이그레이션의 시작으로 모던 자바스크립트로 바꾸는 것부터 하면 부담이 적다.
  • 타입스크립트에 새로 추가된 기능(아이템 53)은 배우지 않아도 되지만, 자바스크립트 표준 기능은 알아 두는 것이 좋다.
ITEM 59

타입스크립트 도입 전에 @ts-check와 JSDoc으로 시험해보기

파일 이름을 바꾸기 전에, 자바스크립트인 채로 타입 체커를 돌려 본다.

핵심 // @ts-check 한 줄이면 .js 파일에서 타입 체크가 돌아간다. 어떤 문제가 기다리고 있는지 미리 볼 수 있다.
!

기대치를 낮춰야 한다

@ts-check 는 noImplicitAny 를 끈 것보다도 훨씬 느슨하게 검사한다. 여기서 오류가 없다고 해서 타입스크립트로 옮겼을 때 오류가 없는 것은 아니다. 수면 위로 드러나는 것만 본다고 생각해야 한다.

1. 선언되지 않은 전역 변수

app.js 
// @ts-check
console.log(user.name);
//          ~~~~ 'user' 이름을 찾을 수 없습니다.

다른 스크립트가 만들어 놓은 전역 변수라면 정상 동작하는 코드다. 타입 선언 파일을 하나 만들어 알려 준다. 이 파일이 프로젝트 타입 선언의 초석이 된다.

types.d.ts 
interface UserData {
  firstName: string;
  lastName: string;
}
declare let user: UserData;

2. 서드파티 라이브러리

@types/* 를 설치하면 대부분 해결된다(아이템 45). 이 단계에서 어떤 라이브러리에 타입이 없는지 미리 파악해 두면 이후 계획이 정확해진다.

3. DOM 문제

app.js 브라우저에서는 잘 돌아가는 코드 
// @ts-check
const ageEl = document.getElementById("age");
ageEl.value = "12";
//    ~~~~~ 'HTMLElement' 형식에 'value' 속성이 없습니다.

아이템 55에서 본 그 문제다. JSDoc 으로 타입 단언을 할 수 있다.

app.js 괄호가 필수다 
// @ts-check
const ageEl = /** @type {HTMLInputElement} */ (document.getElementById("age"));
ageEl.value = "12"; // 정상
!

원문 교정 원문 교정

원문 노트에는 대상 표현식을 괄호로 감싸지 않은 형태로 적혀 있었다. JSDoc 타입 단언은 /** @type {T} */ (expr) 처럼 괄호가 반드시 필요하다. 없으면 주석이 무시되어 단언이 적용되지 않는다.

4. 이미 있던 JSDoc 이 부정확한 경우

legacy.js 
// @ts-check
/**
 * @param {number} price
 * @returns {string}
 */
function formatPrice(price) {
  return price; // 'number' 형식은 'string' 형식에 할당할 수 없습니다.
}

이미 JSDoc 주석을 쓰고 있었다면 @ts-check 를 붙이는 순간 오류가 쏟아진다. 대부분은 주석이 오래되어 실제 코드와 어긋난 경우다. 당황하지 말고 하나씩 정리한다.

i

파일 단위 vs 프로젝트 단위 보강

방법범위쓸 때
// @ts-check그 파일 하나한 파일씩 시험해 볼 때
"checkJs": trueallowJs 대상 전체전체 규모를 파악할 때
// @ts-nocheck그 파일만 제외checkJs 중 특정 파일을 미룰 때

한 파일씩 @ts-check 를 붙여 나가다가, 대부분이 통과하면 checkJs 로 승격시키는 순서가 자연스럽다.

!

종착지가 아니다

이 방법은 점진적 마이그레이션에는 유용하지만 오래 머무를 곳은 아니다. JSDoc 은 장황하고, 타입스크립트의 표현력을 다 쓸 수 없다. 궁극적인 목표는 .js + JSDoc 이 아니라 모든 코드가 .ts 가 되는 것이다.

정리

  • 파일 확장자를 바꾸기 전에 @ts-check 와 JSDoc 을 사용해 미리 시험해 볼 수 있다.
  • 이 단계에서 초기 오류를 발견하는 데 큰 도움이 된다. 하지만 너무 공들이지 않는다.
  • 궁극적인 목표는 .ts 로의 전환이다.
ITEM 60

allowJs로 타입스크립트와 자바스크립트 같이 사용하기

대규모 프로젝트를 하루아침에 옮길 수는 없다. 둘이 공존할 수 있게 만드는 것이 먼저다.

i

이 아이템은 원문 노트가 짧아 내용을 보강했습니다 보강

원문에는 "allowJs 로 같이 동작하게 만들 수 있다"는 세 줄만 기록되어 있었습니다.

핵심 allowJs: true 는 타입스크립트 파일과 자바스크립트 파일이 서로를 임포트할 수 있게 만든다. 마이그레이션의 전제 조건이다.
tsconfig.json 
{
  "compilerOptions": {
    "allowJs": true,
    "outDir": "./dist",
    "target": "es2020",
    "module": "esnext"
  },
  "include": ["src/**/*"]
}

이제 tsc 가 .js 파일도 입력으로 받아 .ts 파일과 함께 처리한다. 이 시점에서 파일 하나를 .ts 로 바꿔도 나머지가 그대로 동작한다.

flowchart LR
  A["100% JS"] --> B["allowJs 켜기
빌드·테스트 체인 통과 확인"]
  B --> C["모듈 단위 전환
.js → .ts 하나씩"]
  C --> D["noImplicitAny
strict"]
  C -.->|"반복"| C
두 번째 칸이 이 아이템이다 — 코드를 한 줄도 고치지 않고, 도구 체인만 타입스크립트를 통과하도록 만드는 단계다.

도구 체인이 진짜 관문이다

도구할 일
번들러Vite·webpack·esbuild 등이 .ts 를 처리하도록 설정한다. 대부분 플러그인 하나면 된다
테스트 러너Jest 라면 ts-jest 또는 @swc/jest. Vitest 는 기본 지원한다
린터typescript-eslint 를 추가하고 .js/.ts 양쪽 규칙을 정리한다
CItsc --noEmit 를 별도 스텝으로 추가한다
경로 별칭paths 설정을 번들러·테스트 러너와 동기화한다
✓

이 단계의 성공 기준

빈 .ts 파일 하나를 추가해도 빌드와 테스트가 그대로 통과하는 것. 여기까지 오면 나머지는 반복 작업이다. 반대로 이 단계를 건너뛰고 파일을 바꾸기 시작하면, 타입 오류와 빌드 오류가 뒤섞여 원인을 구분할 수 없게 된다.

!

함께 켤 것과 켜지 말 것

  • 켜지 않는다 — checkJs. 이 단계에서 .js 파일까지 검사하면 오류가 폭발한다. 아이템 59처럼 파일 단위로 시험할 때만 쓴다.
  • 끈다 — noImplicitAny. 마지막 단계에서 켠다(아이템 62).
  • 켠다 — sourceMap. 섞여 있는 동안 디버깅이 훨씬 편해진다(아이템 57).

정리

  • 점진적 마이그레이션을 위해 allowJs 로 타입스크립트와 자바스크립트를 공존시킨다.
  • 대규모 마이그레이션을 시작하기 전에 빌드 체인과 테스트 체인에 타입스크립트를 적용하는 것이 먼저다.
  • 이 단계에서는 코드를 고치지 않는다. 도구만 준비한다.
ITEM 61

의존성 관계에 따라 모듈 단위로 전환하기

아무 파일이나 골라 바꾸면 안 된다. 의존성 그래프의 아래쪽부터 올라간다.

핵심 다른 모듈에 의존하지 않는 리프(leaf) 모듈부터 시작해서, 마지막에 최상단을 전환한다. 테스트 코드가 제일 마지막이다. 
flowchart BT
  U["utils.ts
1순위 — 아무것도 의존하지 않는다"] --> M["models.ts
2순위"]
  M --> S["services.ts
3순위"]
  S --> C["components.ts
4순위"]
  C --> T["tests
마지막"]
아래에서 위로 — 리프를 먼저 바꾸면 그 위를 바꿀 때 이미 타입 정보가 준비되어 있다. 반대로 하면 아직 any 인 것들에 의존한 채 작업하게 된다.

준비 — 전환 대상이 아닌 두 가지

  1. 서드파티 라이브러리 타입 확보

가장 중요한 규칙 — 리팩터링하지 않는다

마이그레이션 중에는 오직 타입 정보만 추가한다. 지금의 목표는 코드 개선이 아니다. 타입을 붙이다 보면 잘못된 설계가 잔뜩 보이지만 메모만 남기고 지나간다. 둘을 섞으면 문제가 생겼을 때 타입 때문인지 리팩터링 때문인지 구분할 수 없다.

전환 중에 자주 만나는 오류

1. 선언되지 않은 클래스 멤버
before.js 
class Greeting {

    this.name = name;

after.ts 
class Greeting {
  name: string;
  greeting: string;

  constructor(name: string) {
    this.name = name;
    this.greeting = "Hello";
  }
  greet() {
    return `${this.greeting} ${this.name}`;
  }
}

편집기의 빠른 수정 → "누락된 모든 멤버 선언" 이 한 번에 해결해 준다. 손으로 적지 않는다.

테스트 코드는 마지막에

✓

왜 마지막인가

테스트 코드는 의존성 그래프의 최상단이다. 아무도 테스트를 임포트하지 않는다. 그래서 마지막에 전환하는 것이 자연스럽고, 무엇보다 전환 작업 내내 테스트가 계속 돌아간다. 모듈 하나를 바꿀 때마다 회귀를 즉시 확인할 수 있다는 뜻이다.

정리

  • 마이그레이션의 첫 단계는 서드파티 모듈과 외부 API 의 타입 정보를 추가하는 것이다.
  • 의존성 관계도의 아래에서 위로 올라가며 마이그레이션한다. 첫 번째 모듈은 보통 유틸리티다.
  • 의존성 관계도를 시각화하여 진행 상황을 파악한다.
  • 이상한 설계를 발견해도 리팩터링하지 않는다. 지금 할 일은 타입 정보 추가다.
  • 테스트 코드는 가장 마지막에 전환한다.
ITEM 62

마이그레이션의 완성을 위해 noImplicitAny 설정하기

모든 파일이 .ts 가 되었다고 끝난 것이 아니다. 진짜 마지막 관문이 남아 있다.

핵심 noImplicitAny 를 켜기 전까지는 타입이 있는 척하는 코드가 남아 있다. 이걸 켜야 마이그레이션이 끝난다.
chart.ts noImplicitAny 없이는 통과한다 
class Chart {
  indices: number[];

  getRanges() {
    for (const r of this.indices) {
      const low = r[0];  // any
      const high = r[1]; // any
      // ...
    }
  }
}

indices 는 number[] 이므로 r 은 number 인데, 거기에 [0] 으로 인덱싱하고 있다. noImplicitAny 없이는 조용히 any 가 되어 넘어간다.

chart.ts 켜면 드러난다 
// noImplicitAny: true
const low = r[0];
//          ~~~~ 'Number' 형식에 인덱스 시그니처가 없으므로
//               요소에 암시적으로 'any' 형식이 있습니다.
✓

이런 오류가 진짜 버그다

indices 의 타입이 애초에 [number, number][] 였어야 했다. 마이그레이션 중에 잘못 붙인 타입이 여기서 드러난다. noImplicitAny 가 없었다면 영원히 몰랐을 것이다.

점진적으로 켜는 방법

  1. 로컬에서 먼저 켜 본다

    설정을 바꾸고 tsc --noEmit 을 돌려 오류 개수를 센다. 이 숫자가 남은 작업량이자 진척도 지표다.

    terminal 
    npx tsc --noEmit --noImplicitAny | grep -c "error TS"
  2. 오류를 줄여 나간다

    커밋할 때마다 숫자가 줄어드는 것을 확인한다. 0 이 되기 전까지는 설정 파일에 반영하지 않는다. 팀원들이 계속 빌드할 수 있어야 한다.

  3. 0 이 되면 설정에 반영한다

    이제 되돌아갈 수 없다. 새 코드는 처음부터 타입을 갖게 된다.

  4. strict 로 올린다

    strictNullChecks 를 포함한 나머지 옵션을 같은 방식으로 하나씩 켠다. 가장 어려운 것은 대개 strictNullChecks 다.

함께 쓰면 좋은 것 보강

  • type-coverage(아이템 44) — noImplicitAny 가 잡지 못하는 명시적 any 까지 추적한다. --at-least 임계값을 걸어 후퇴를 막는다.
  • @typescript-eslint/no-explicit-any — 새로 들어오는 any 를 리뷰 단계에서 차단한다.
  • 디렉터리 단위 tsconfig — 이미 정리된 폴더만 strict 로 올리고 나머지는 뒤따르게 하는 방법도 있다.

여기까지 오면

1장부터 8장까지의 모든 조언이 실제로 작동하는 환경이 갖춰진 것이다. 타입 체커를 믿을 수 있게 되고(아이템 5), 타입 설계에 투자한 것이 돌아오기 시작한다(아이템 28).

정리

  • noImplicitAny 설정을 활성화하여 마이그레이션의 마지막 단계를 진행한다.
  • 이 설정이 없으면 타입 선언과 관련된 실제 오류가 드러나지 않는다.
  • 최종적으로 strict: true 를 목표로 한다. 오류 개수를 진척도로 삼아 점진적으로 올린다.
