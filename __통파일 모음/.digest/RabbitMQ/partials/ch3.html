ITEM 10

컨슈머 ack: 자동과 수동

ack는 "받았다"가 아니라 "다 처리했다"는 뜻이다.

핵심 noAck: true는 전송한 순간 처리 완료로 간주한다. 컨슈머가 그 직후 죽으면 메시지는 그냥 사라진다.

두 가지 모드

자동 ack (noAck: true)수동 ack (기본)
확정 시점브로커가 소켓에 쓴 직후내가 ch.ack()를 부를 때
유실컨슈머 크래시 시 유실미확인 메시지는 requeue
흐름 제어prefetch가 안 먹는다prefetch로 제어
쓸 자리유실해도 되는 메트릭/로그 스트림그 외 전부

공식 문서는 자동 ack를 두고 "안전하지 않으며 모든 워크로드에 적합하지 않다"고 못박는다. 실무 기본값은 수동 ack다.

delivery tag

브로커는 배달마다 채널 범위의 단조 증가 정수를 붙인다. ack는 반드시 배달받은 그 채널에서 해야 하고, 다른 채널에서 하면 프로토콜 예외로 연결이 끊긴다. amqplib에서는 메시지 객체를 그대로 넘기므로 (ch.ack(msg)) 태그를 직접 만질 일은 드물다.

consumer.ts
await ch.consume('order.payment', async (msg) => {
  if (!msg) return;                 // 컨슈머가 취소되면 null이 온다
  try {
    await handle(JSON.parse(msg.content.toString()));
    ch.ack(msg);                    // 여기까지 와야 큐에서 지워진다
  } catch (err) {
    ch.nack(msg, false, false);     // 재큐 없이 DLX로
  }
}, { noAck: false });
i

배치 ack

ch.ack(msg, true)는 이 태그까지의 모든 미확인 배달을 한 번에 확정한다 (multiple 플래그). 처리량이 아주 높은 컨슈머에서 네트워크 왕복을 줄이는 데 쓴다. 단, 중간에 실패한 게 하나라도 있으면 그것까지 같이 ack되므로 순서대로 성공하는 파이프라인에만 쓴다.

!

ack를 안 하고 오래 버티면 최신 반영

미확인 배달에는 기본 30분의 타임아웃(consumer_timeout)이 있다. 3.x 시절에는 이걸 넘기면 채널이 PRECONDITION_FAILED로 강제로 닫히면서 그 채널의 모든 배달이 requeue됐다. 4.3부터는 이 보호가 quorum queue에 대해 큐 레벨에서 처리되고, 채널을 끊는 대신 프로토콜에 맞는 방식으로 메시지만 회수한다. 그래도 30분 넘게 걸리는 작업이라면 메시지를 즉시 ack하고 진행 상태는 애플리케이션 DB에서 관리하는 쪽이 맞다.

정리

  • 수동 ack가 기본. noAck: true는 유실해도 되는 데이터에만.
  • ack는 배달받은 채널에서만 유효하다.
  • 커넥션/채널이 끊기면 미확인 배달은 자동으로 requeue된다.
  • 기본 미확인 타임아웃 30분. 그보다 긴 작업은 설계를 바꾼다.
ITEM 11

nack, reject, 그리고 requeue의 함정

requeue: true는 대부분의 경우 무한 루프의 다른 이름이다.

핵심 실패했을 때 nack(msg, false, true)로 되돌리면, 같은 메시지가 즉시 다시 배달되어 같은 이유로 또 실패한다. 백오프가 없기 때문이다.
메서드여러 건 처리비고
ch.reject(msg, requeue)✗AMQP 표준
ch.nack(msg, allUpTo, requeue)✓RabbitMQ 확장. 실무에서는 이것만 써도 된다

requeue 플래그가 결정하는 것

flowchart LR
  F["처리 실패"] --> D{"requeue 값?"}
  D -->|"true"| Q["큐로 즉시 복귀"]
  Q --> R["같은 컨슈머가 곧바로 재수신"]
  R --> F
  D -->|"false"| X{"DLX가 설정돼 있나?"}
  X -->|"예"| DLQ["Dead Letter Exchange 로"]
  X -->|"아니오"| DROP["메시지 폐기"]
requeue: true의 위험 — 결정론적으로 실패하는 메시지(스키마 오류, 없는 참조)는 CPU를 태우는 무한 루프가 된다.

실패의 두 종류를 구분한다

error-policy.ts권장
try {
  await handle(payload);
  ch.ack(msg);
} catch (err) {
  if (err instanceof TransientError) {
    // 일시적 장애(DB 커넥션, 외부 API 5xx): 재시도할 가치가 있다.
    // 단, 즉시 requeue 대신 재시도 큐로 보낸다 (ITEM 22, 24)
    ch.nack(msg, false, false);
  } else {
    // 영구 실패(스키마 위반, 존재하지 않는 리소스): 재시도해도 결과가 같다.
    ch.nack(msg, false, false);   // 바로 DLQ로
  }
}

두 갈래 모두 requeue: false인 게 포인트다. 재시도가 필요하면 즉시 되돌리는 게 아니라 지연을 걸어 되돌린다. 그 방법이 ITEM 22와 24다.

!

requeue: true가 맞는 드문 경우

컨슈머 자신의 상태 문제로 지금 이 인스턴스는 처리할 수 없지만 다른 인스턴스는 할 수 있을 때 (예: 로컬 캐시 미준비, 셧다운 진행 중) 정도다. 이때도 요청이 몰리면 핫루프가 되므로 짧은 대기를 넣거나 컨슈머를 취소하는 편이 낫다.

정리

  • 실무에서는 nack 하나로 통일해도 된다.
  • requeue: false가 기본 전략. 재시도는 지연을 끼워서 한다.
  • requeue: false + DLX 미설정 = 조용한 메시지 폐기다. DLX는 사실상 필수.
ITEM 12

prefetch: 동시성의 진짜 손잡이

BullMQ의 concurrency에 가장 가까운 것.

핵심 prefetch는 한 컨슈머가 동시에 붙들 수 있는 미확인 메시지 수다. 이 값을 안 정하면 브로커는 큐에 있는 걸 전부 밀어 넣는다.

basic.qos(amqplib의 ch.prefetch(n))를 호출하지 않으면 기본값은 무제한이다. 컨슈머 하나가 10만 건을 통째로 받아 메모리에 쌓고, 다른 인스턴스는 놀게 된다. 수동 ack 모드에서만 의미가 있다. 

flowchart LR
  Q["Queue: 미처리 10000건"] -->|"prefetch=1"| C1["컨슈머 A: 1건 처리 중"]
  Q -->|"prefetch=1"| C2["컨슈머 B: 1건 처리 중"]
  Q -.->|"prefetch 미설정"| C3["컨슈머 C: 10000건 전부 선점"]
prefetch는 부하 분산 손잡이이기도 하다 — 값이 클수록 한 인스턴스가 많이 선점한다.
작업 성격권장 prefetch이유
건당 수 초 이상 걸리는 무거운 작업1 ~ 5공평한 분배가 처리량보다 중요
건당 수 ms 수준의 가벼운 작업100 ~ 300왕복 지연을 감추는 구간
매우 짧고 지연이 큰 네트워크더 크게단, 수확 체감이 빠르게 온다

공식 가이드도 100~300 구간을 처리량과 자원 소비의 균형점으로 제시하고, 그 이상은 수확 체감이라고 설명한다. prefetch(1)은 가장 안전하지만 지연이 큰 환경에서 처리량이 크게 떨어진다.

BullMQ concurrency와의 차이

BullMQ
new Worker('email', handler, {
  concurrency: 10,
});
// 한 워커가 최대 10개 잡을
// 동시에 실행한다.
RabbitMQ
await ch.prefetch(10);
await ch.consume(q, handler);
// 미확인 10건까지 받아둘 뿐,
// 동시 실행 여부는 내 핸들러가 정한다.

amqplib의 consume 콜백은 순차 실행을 보장하지 않는다. 콜백이 async이면 앞 건이 끝나기 전에 다음 건이 들어올 수 있다. 즉 실제 동시성은 prefetch 값이고, 이걸 넘는 동시 실행은 일어나지 않는다. 반대로 순차 처리를 원하면 prefetch를 1로 두거나 핸들러 안에서 직접 큐잉해야 한다.

i

global 플래그 보강

ch.prefetch(n, true)는 채널 전체에 걸쳐 n건으로 제한하고, 기본값(false)은 컨슈머별로 n건이다. 참고로 quorum queue는 global QoS를 지원하지 않는다. 컨슈머별 prefetch만 쓸 수 있으니, 채널 하나에 컨슈머를 여러 개 붙일 계획이면 이 점을 기억해 둔다.

정리

  • prefetch를 설정하지 않으면 무제한이다. 반드시 명시한다.
  • 무거운 작업은 1~5, 가벼운 작업은 100~300이 출발점.
  • prefetch가 사실상 컨슈머의 동시성 상한이다. 순차 보장은 prefetch=1.
  • quorum queue에서는 global QoS를 못 쓴다.
ITEM 13

퍼블리셔 컨펌

publish()가 true를 돌려줬다는 건 아무것도 보장하지 않는다.

핵심 기본 채널의 publish()는 로컬 버퍼에 썼다는 뜻일 뿐이다. 브로커가 실제로 받았는지 알려면 confirm 모드를 켜야 한다.

BullMQ에서는 await queue.add()가 Redis 응답까지 기다리기 때문에 이 고민이 없었다. AMQP의 발행은 원래 단방향(fire-and-forget)이다. 브로커가 죽어 있거나 디스크가 꽉 찼어도 클라이언트는 모른다. 그래서 RabbitMQ는 confirm.select라는 확장을 제공한다. 

sequenceDiagram
  participant P as Publisher
  participant B as Broker
  participant Q as Queue
  P->>B: confirm.select (채널을 컨펌 모드로)
  P->>B: basic.publish seq=1
  B->>Q: 라우팅 후 저장
  Q-->>B: 디스크 기록 완료
  B-->>P: basic.ack seq=1
  P->>B: basic.publish seq=2
  B-->>P: basic.nack seq=2 (내부 오류)
컨펌은 비동기다 — 발행마다 순번이 붙고, ack/nack가 순서와 무관하게 돌아온다.

ack가 오는 시점

상황ack 시점
라우팅될 큐가 없음라우팅 실패를 확인한 직후 (그래도 ack다)
persistent 메시지 → durable classic queue디스크에 기록된 뒤
quorum queue과반 복제본이 리더에게 확인한 뒤
×

라우팅 실패도 ack다

갈 큐가 하나도 없어서 메시지가 버려져도 브로커는 ack를 보낸다. "브로커가 책임지고 받았다"와 "누군가 처리할 것이다"는 다른 얘기다. 라우팅 실패를 알고 싶으면 mandatory가 필요하다 (ITEM 14).

amqplib에서 쓰기

confirm.ts
const ch = await conn.createConfirmChannel();

// 방식 1: 건별 콜백 (권장) — 옵션 객체와 콜백이 필수 인자다
ch.publish('order.events', 'order.paid', buf, { persistent: true }, (err) => {
  if (err) markForRetry(buf);   // nack 또는 채널 종료
  else markPublished(buf);
});

// 방식 2: 배치 후 한 번에 대기
for (const e of events) ch.publish('order.events', e.key, e.buf, { persistent: true });
await ch.waitForConfirms();     // 하나라도 nack면 reject
!

건별로 await하지 말 것

publish 하나마다 컨펌을 await하면 왕복 지연이 그대로 처리량 상한이 된다. persistent 메시지의 컨펌은 디스크 배치 기록 때문에 수백 ms까지 걸릴 수 있다고 공식 문서가 명시한다. 파이프라이닝(여러 건 발행 후 일괄 확인)이나 비동기 콜백으로 처리한다. 또한 컨펌은 발행 순서대로 오지 않을 수 있으므로 순서에 의존하는 코드를 쓰면 안 된다.

정리

  • 유실이 곤란한 발행에는 createConfirmChannel()을 쓴다.
  • ack = 브로커가 책임진다는 뜻. 처리된다는 뜻이 아니고, 라우팅 성공을 뜻하지도 않는다.
  • 건별 await는 금물. 콜백이나 waitForConfirms() 배치를 쓴다.
  • 컨펌 순서는 보장되지 않는다.
ITEM 14

라우팅 실패는 에러가 아니다

오타 하나로 메시지가 조용히 사라지는 게 RabbitMQ의 기본 동작이다.

핵심 exchange가 갈 큐를 못 찾으면 메시지는 말없이 버려진다. 이걸 막는 장치가 mandatory와 alternate-exchange다.

BullMQ에는 없는 실패 유형이다. 큐 이름을 잘못 쓰면 BullMQ는 그 이름의 큐를 그냥 만들어버리지만, RabbitMQ에서 routing key를 잘못 쓰면 아무 일도 일어나지 않는다. 로그도 없다. 신규 서비스 붙일 때 가장 많이 밟는 지뢰다.

1) mandatory + basic.return

mandatory.ts
// 반송된 메시지를 받는 핸들러를 먼저 등록한다
ch.on('return', (msg) => {
  logger.error({
    exchange: msg.fields.exchange,
    routingKey: msg.fields.routingKey,
    replyText: msg.fields.replyText,   // NO_ROUTE
  }, '라우팅 실패');
});

ch.publish('order.events', 'order.paidd', buf, {
  persistent: true,
  mandatory: true,      // 갈 큐가 없으면 되돌려 달라
});

컨펌 모드와 같이 쓰면 basic.return이 basic.ack보다 먼저 온다. 즉 "반송 이벤트가 안 왔고 ack가 왔다"면 최소한 어느 큐엔가 들어갔다는 뜻이 된다.

2) alternate exchange

exchange를 선언할 때 alternateExchange를 주면, 라우팅에 실패한 메시지를 그 exchange로 넘긴다. 여기에 unrouted 큐를 하나 걸어 두면 잃어버린 메시지가 눈에 보이는 곳에 쌓인다.

alt-exchange.ts권장
await ch.assertExchange('unrouted', 'fanout', { durable: true });
await ch.assertQueue('unrouted.bucket', { durable: true, arguments: { 'x-queue-type': 'quorum' } });
await ch.bindQueue('unrouted.bucket', 'unrouted', '');

await ch.assertExchange('order.events', 'topic', {
  durable: true,
  alternateExchange: 'unrouted',
});
✓

둘 다 쓰는 게 정답

mandatory는 발행자가 즉시 알아차리게 하고, alternate exchange는 메시지를 잃지 않게 한다. 역할이 다르니 같이 건다. unrouted.bucket의 길이에 알람을 걸어두면 새 서비스의 바인딩 누락을 배포 당일에 잡을 수 있다.

정리

  • 라우팅 실패는 예외가 아니라 정상 흐름이다. 기본은 조용한 폐기.
  • mandatory: true + channel.on('return')으로 즉시 감지.
  • exchange에 alternateExchange를 걸어 미라우팅 메시지를 모은다.
ITEM 15

at-least-once와 멱등성

중복은 버그가 아니라 사양이다.

핵심 RabbitMQ의 보장은 at-least-once다. exactly-once는 브로커가 주는 게 아니라 컨슈머가 만드는 성질이다.

중복이 생기는 자리

  1. 컨슈머가 처리는 끝냈는데 ack 직전에 죽는다

    브로커는 미확인으로 보고 다른 컨슈머에게 다시 준다. 같은 일이 두 번 실행된다.

  2. 네트워크가 끊겨 ack가 브로커에 도달하지 못한다

    결과는 위와 같다.

  3. 발행자가 컨펌을 못 받고 재발행한다

    브로커는 이미 받았을 수 있다. 같은 메시지가 두 벌 생긴다.

redelivered 플래그(msg.fields.redelivered)가 true면 재배달이지만, 이걸 중복 판정 기준으로 쓰면 안 된다. 첫 배달에도 중복일 수 있고(3번 케이스), 재배달이어도 앞 시도가 아무것도 안 했을 수 있다.

컨슈머를 멱등하게 만드는 세 가지 방법

방법구현적합한 곳
자연 멱등UPDATE ... SET status='paid'처럼 몇 번 해도 같은 결과가 되게 쓴다가능하면 항상 1순위
처리 기록 테이블messageId에 유니크 제약을 건 테이블에 먼저 insert. 중복이면 스킵부작용이 있는 처리

"exactly once"라는 표현에 속지 않기

BullMQ 문서도 exactly-once 시맨틱을 말하지만 엣지 케이스에서는 at-least-once임을 함께 밝힌다. 분산 시스템에서 진짜 exactly-once 전달은 불가능하고, 실제로 가능한 건 언제나 at-least-once 전달 + 멱등한 처리다. 이건 브로커를 바꿔도 달라지지 않는 성질이다.

정리

  • 중복은 반드시 온다. 컨슈머를 멱등하게 짜는 것 외에 답이 없다.
  • redelivered 플래그는 힌트일 뿐 중복 판정 근거가 아니다.
  • messageId + 유니크 제약 + 트랜잭션이 가장 무난한 구현이다.
