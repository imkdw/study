ITEM 20

DLX: 실패한 메시지의 종착지

BullMQ의 failed 셋에 해당하지만, 이건 진짜 큐다.

핵심 dead letter exchange는 특별한 종류의 exchange가 아니다. 그냥 평범한 exchange인데, 큐가 "여기로 버려라"고 지목했을 뿐이다.

메시지가 dead-letter되는 네 가지 경우

  1. 컨슈머가 requeue 없이 거절

    basic.reject 또는 basic.nack에 requeue=false. 가장 흔한 경로.

  2. 메시지 TTL 만료

    메시지별 expiration 또는 큐의 x-message-ttl이 지났을 때.

  3. 큐 길이 초과

    x-max-length/x-max-length-bytes를 넘겨 밀려난 메시지.

  4. 재배달 한도 초과

    quorum queue의 x-delivery-limit을 넘었을 때.

!

큐 자체가 만료되면 dead-letter되지 않는다

x-expires로 큐가 통째로 사라지는 경우, 안에 있던 메시지는 DLX로 가지 않고 그냥 없어진다. 헷갈리기 쉬운 예외다.

구성

dlx.ts
// 1) DLX 와 DLQ 를 먼저 만든다
await ch.assertExchange('order.dlx', 'topic', { durable: true });
await ch.assertQueue('order.payment.dlq', {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});
await ch.bindQueue('order.payment.dlq', 'order.dlx', 'order.payment');

// 2) 업무 큐가 그 DLX 를 지목한다
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-dead-letter-exchange': 'order.dlx',
    'x-dead-letter-routing-key': 'order.payment',  // 생략하면 원래 routing key 유지
  },
});
flowchart LR
  X{{"order.events"}} --> WQ["order.payment (업무 큐)"]
  WQ --> C["컨슈머"]
  C -->|"nack requeue=false"| DLX{{"order.dlx"}}
  DLX --> DLQ["order.payment.dlq"]
  DLQ --> OPS["사람이 조사하거나 재투입"]
DLQ는 종점이자 대기실이다 — 원인을 고친 뒤 다시 업무 큐로 흘려보낼 수 있어야 한다.

x-death 헤더 읽기

dead-letter된 메시지에는 x-death 헤더가 붙는다. 어느 큐에서, 왜, 몇 번, 언제 버려졌는지가 배열로 쌓이고 최신 항목이 앞에 온다.

x-death.json
{
  "x-death": [
    {
      "count": 3,
      "reason": "rejected",
      "queue": "order.payment",
      "exchange": "order.events",
      "routing-keys": ["order.payment.requested"],
      "time": "2026-08-22T04:11:07Z"
    }
  ]
}

reason은 rejected / expired / maxlen / delivery_limit 중 하나다. DLQ 컨슈머는 이 값만 봐도 "코드 버그로 거절된 건지, 그냥 늦어서 만료된 건지"를 구분할 수 있다.

i

DLX로 가는 길에도 유실이 있다 보강

기본 dead lettering은 퍼블리셔 컨펌 없이 재발행한다(at-most-once). 클러스터 상황에 따라 DLQ에 도착하지 못할 수 있다. quorum queue라면 policy로 dead-letter-strategy: at-least-once를 걸어 내부 컨펌을 켤 수 있는데, overflow: reject-publish가 함께 필요하다. 결제/정산처럼 실패 기록조차 잃으면 안 되는 큐에는 이 조합을 쓴다.

정리

  • DLX는 평범한 exchange다. 큐가 x-dead-letter-exchange로 지목할 뿐.
  • 거절/TTL만료/길이초과/재배달한도 네 가지가 dead-letter를 유발한다. 큐 만료는 아니다.
  • x-death의 reason과 count가 사후 분석의 핵심 자료다.
  • 중요한 큐라면 dead-letter-strategy: at-least-once를 검토한다.
ITEM 21

delivery-limit와 poison message

BullMQ의 attempts에 가장 가까운 브로커 기능.

핵심 quorum queue는 재배달 횟수를 브로커가 직접 센다. 기본 한도는 20이고, 넘으면 dead-letter된다.

poison message는 처리할 때마다 반드시 실패하는 메시지다. 스키마가 깨졌거나, 참조하는 리소스가 사라졌거나, 컨슈머 코드에 버그가 있는 경우다. 방치하면 이 한 건이 컨슈머 CPU를 영원히 태운다.

delivery-limit.ts
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-delivery-limit': 5,                        // 5회 초과하면 포기
    'x-dead-letter-exchange': 'order.dlx',        // 포기한 메시지는 여기로
  },
});

컨슈머는 현재 시도 횟수를 헤더로 볼 수 있다.

4.3: 명시적 return은 횟수에 안 센다 최신 반영

4.3부터 한도 판정 기준이 acquired-count가 아니라 delivery-count로 바뀌었다. 컨슈머가 "지금은 내가 못 하니 다른 데 줘"라고 명시적으로 되돌리는 경우는 무제한으로 허용되고, 실제 실패로 인한 재배달만 한도에 반영된다. 셧다운 중 메시지를 되돌리는 패턴을 쓸 때 이 차이가 크다.

!

classic queue에는 이 기능이 없다

classic queue를 쓴다면 재시도 횟수를 직접 세야 한다. 보통 x-death의 count를 읽거나, 커스텀 헤더에 시도 횟수를 담아 재발행하는 식으로 구현한다. quorum queue를 기본으로 두라는 권고에는 이 이유도 있다.

정리

  • quorum queue의 x-delivery-limit이 무한 재시도를 막는 안전장치다. 기본 20.
  • 한도를 넘으면 DLX로 간다. DLX가 없으면 그냥 버려진다.
  • 한도는 큐 단위다. 메시지별 재시도 횟수 차등은 애플리케이션에서 구현한다.
ITEM 22

지연 재시도: 4.3의 백오프

드디어 브로커가 백오프를 해준다. 단, 선형이다.

핵심 RabbitMQ 4.3부터 quorum queue는 재시도에 지연을 넣을 수 있다. 실패한 메시지를 큐 내부에 잠시 치워 뒀다가 시간이 지나면 다시 배달 가능 상태로 만든다.
delayed-retry.ts
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-delayed-retry-type': 'failed',   // disabled | all | returned | failed
    'x-delayed-retry-min': 5000,        // 최소 지연 5초
    'x-delayed-retry-max': 60000,       // 최대 지연 60초
    'x-delivery-limit': 8,
    'x-dead-letter-exchange': 'order.dlx',
  },
});

지연 계산식

✓

선형 백오프

지연 = min(min_delay × delivery_count, max_delay)
min 5초 / max 60초라면 5초 → 10초 → 15초 → ... → 60초에서 고정된다. BullMQ의 지수 백오프 (2^n × delay)와 달리 선형이라는 점만 주의하면 된다.

x-delayed-retry-type어떤 경우에 지연을 거는가
disabled기본값. 지연 없음
returned컨슈머가 명시적으로 되돌린 경우
failed실패로 되돌아온 경우 (컨슈머 크래시, 타임아웃 등)
all되돌아온 모든 경우
 
flowchart LR
  Q["order.payment 큐"] --> C["컨슈머"]
  C -->|"실패"| S["큐 내부 대기 영역"]
  S -->|"min x count 만큼 지연"| Q
  Q -->|"delivery-limit 초과"| DLX{{"order.dlx"}}
큐 밖으로 안 나간다 — 별도 재시도 큐를 만들 필요 없이 원래 큐 안에서 지연이 처리된다.
!

4.2 이하라면 못 쓴다

이 기능은 4.3에서 추가됐고 quorum queue 전용이다. 이직할 회사의 브로커 버전을 먼저 확인하자. 4.2 이하이거나 classic queue를 쓴다면 ITEM 23~24의 TTL+DLX 방식으로 직접 만들어야 한다.

정리

  • 4.3 + quorum queue에서는 백오프 재시도가 큐 인자 세 개로 끝난다.
  • 지연은 선형이다. min × 시도횟수, 상한은 max.
  • 재시도 큐를 따로 만들 필요가 없어서 토폴로지가 훨씬 단순해진다.
  • 4.2 이하라면 이 기능이 없다. 버전 확인이 먼저다.
ITEM 23

지연 메시지: TTL+DLX와 플러그인의 종말

BullMQ의 delay: 60000에 해당하는 기능은 RabbitMQ에 없다.

핵심 "10분 뒤에 이 메시지를 처리해라"는 네이티브 기능이 아니다. TTL이 만료되면 DLX로 흘러가는 성질을 이용해 흉내 낸다.
×

delayed message exchange 플러그인은 끝났다 주의

검색하면 반드시 나오는 rabbitmq_delayed_message_exchange(x-delayed-message exchange 타입 + x-delay 헤더)는 2026년 4월 16일 저장소가 아카이브됐다. Mnesia에 의존했는데 Mnesia가 4.3에서 완전히 제거되면서 4.3 이상 오픈소스 버전에서는 로드되지 않는다. 원래도 "지연 메시지를 단일 노드 테이블에 저장하므로 그 노드가 죽으면 전부 유실"되고 대량 사용에 부적합하다는 경고가 붙어 있던 물건이다. 새 코드에서 이 경로를 택하지 않는다.

정석: TTL + DLX 지연 큐

flowchart LR
  P["Publisher"] -->|"발행"| DQ["delay.5s 큐: 컨슈머 없음, TTL 5초, DLX 지정"]
  DQ -->|"5초 뒤 TTL 만료"| DLX{{"work.exchange"}}
  DLX --> WQ["order.payment 업무 큐"]
  WQ --> C["컨슈머"]
컨슈머 없는 큐를 타이머로 쓴다 — 아무도 안 꺼내가면 TTL이 만료되고, 만료된 메시지는 DLX로 나간다.
delay-queue.ts
// 지연 전용 큐: 컨슈머를 절대 붙이지 않는다
await ch.assertQueue('delay.30s', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-message-ttl': 30000,                    // 30초 뒤 만료
    'x-dead-letter-exchange': 'work.exchange', // 만료되면 업무 exchange 로
    'x-dead-letter-routing-key': 'order.payment',
  },
});

// 30초 뒤에 처리하고 싶으면 이 큐로 보낸다
ch.sendToQueue('delay.30s', buf, { persistent: true });
!

메시지별 TTL을 섞으면 머리에서 막힌다

큐는 FIFO다. 메시지마다 expiration을 다르게 줘서 한 큐에 넣으면, 맨 앞 메시지의 TTL이 끝나야 그 뒤가 검사된다. 60초짜리가 앞에 있으면 뒤의 5초짜리는 60초를 기다린다. 그래서 지연 큐는 delay.5s, delay.30s, delay.5m처럼 지연 단계별로 큐를 따로 만들고 큐 인자 x-message-ttl로 고정하는 게 정석이다.

i

긴 지연은 브로커에 맡기지 않는다 보강

"3일 뒤 리마인드", "한 달 뒤 구독 갱신" 같은 건 메시지 브로커의 일이 아니다. DB 테이블에 실행 시각을 저장하고 스케줄러가 그 시각에 메시지를 발행하는 구조가 맞다. 브로커의 지연 패턴은 초~시간 단위 재시도까지가 적정선이다.

정리

  • 지연 발행은 네이티브 기능이 아니다. TTL 만료 → DLX 흐름으로 만든다.
  • 지연 플러그인은 아카이브됐고 4.3에서 못 쓴다. 새로 쓰지 않는다.
  • 지연 큐는 단계별로 분리한다. 한 큐에 여러 TTL을 섞으면 head-of-line 블로킹이 생긴다.
  • 일 단위 이상 지연은 DB + 스케줄러로 뺀다.
ITEM 24

재시도 아키텍처를 직접 설계하기

BullMQ 옵션 두 줄이 여기서는 그림 한 장이 된다.

핵심 4.3 + quorum queue면 큐 인자만으로 끝난다. 그게 안 되는 환경이면 업무 큐 / 재시도 큐 / DLQ 3단 구조를 직접 만든다.

패턴 A — 4.3 quorum queue (권장)

가장 단순
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-delayed-retry-type': 'all',
    'x-delayed-retry-min': 2000,
    'x-delayed-retry-max': 120000,
    'x-delivery-limit': 6,
    'x-dead-letter-exchange': 'order.dlx',

패턴 B — TTL+DLX 3단 구조

flowchart LR
  IN{{"work.exchange"}} --> W["order.payment 업무 큐"]
  W --> C["컨슈머"]
  C -->|"실패: retry.exchange 로 재발행"| RX{{"retry.exchange"}}
  RX --> R1["retry.10s TTL 10초"]
  RX --> R2["retry.60s TTL 60초"]
  RX --> R3["retry.300s TTL 300초"]
  R1 --> IN
  R2 --> IN
  R3 --> IN

  DLX --> DLQ["order.payment.dlq"]
계단식 재시도 — 시도 횟수에 따라 다른 TTL의 재시도 큐로 보내면 지수 백오프를 흉내 낼 수 있다.
retry-router.ts
const LEVELS = [10, 60, 300];   // 초 단위 재시도 단계

function onFailure(ch, msg) {
  const attempt = Number(msg.properties.headers?.attempt ?? 0);
  if (attempt >= LEVELS.length) {
    ch.nack(msg, false, false);            // DLX 로 보낸다
    return;
  }
  ch.publish('retry.exchange', `retry.${LEVELS[attempt]}s`, msg.content, {
    ...msg.properties,
    headers: { ...msg.properties.headers, attempt: attempt + 1 },
    persistent: true,
  });
  ch.ack(msg);                             // 원본은 확정 처리
}
!

"재발행 후 ack"의 위험

위 코드는 재발행이 성공한 뒤 원본을 ack한다. 하지만 재발행과 ack 사이에 프로세스가 죽으면 원본이 requeue되어 메시지가 두 벌이 된다. 그래서 발행에는 컨펌 채널을 쓰고, 컨슈머는 어차피 멱등해야 한다(ITEM 15). 이 복잡도가 싫으면 그게 바로 패턴 A를 쓸 이유다.

DLQ 이후를 반드시 설계한다

  • 알람. DLQ 메시지 수에 임계값을 걸어 둔다. 아무도 안 보는 DLQ는 그냥 쓰레기통이다.
  • 재투입 경로. 원인을 고친 뒤 DLQ → 업무 큐로 되돌리는 스크립트나 관리 화면을 미리 만든다. shovel 플러그인으로 큐 사이 이동을 걸 수도 있다.
  • 보존. DLQ에 x-max-length를 걸어 무한정 쌓이지 않게 한다.

정리

  • 4.3 + quorum이면 재시도는 큐 인자만으로 끝난다. 이걸 1순위로 검토한다.
  • 안 되면 재시도 큐를 지연 단계별로 만들고 헤더로 시도 횟수를 관리한다.
  • 재발행 방식은 중복 위험이 있다. 컨펌 + 멱등 컨슈머가 전제다.
  • DLQ에 알람과 재투입 경로가 없으면 DLQ를 만든 의미가 없다.
