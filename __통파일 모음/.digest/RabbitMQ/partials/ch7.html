ITEM 30

관리 UI와 봐야 할 지표

Ready와 Unacked 두 숫자만 봐도 절반은 진단된다.

핵심 Ready는 아무도 안 가져간 메시지, Unacked는 누군가 붙들고 있는 메시지다. 둘 중 어느 쪽이 쌓이느냐로 원인이 갈린다.
증상해석조치
Ready가 계속 증가컨슈머 처리 능력 부족, 또는 컨슈머가 아예 없음컨슈머 인스턴스 증설, prefetch 상향, 큐에 Consumers 수 확인
Unacked가 증가만 하고 안 줄어듦ack 누락 또는 핸들러가 멈춤(무한 대기)ack 경로 점검, 외부 호출 타임아웃 설정
Unacked ≈ prefetch × 컨슈머 수에서 고정정상. 포화 상태로 돌고 있음처리량이 부족하면 컨슈머 증설
Publish rate만 있고 Deliver rate가 0바인딩이 없거나 컨슈머 미등록바인딩 확인, unrouted 큐 확인
DLQ 길이 증가지속적 처리 실패x-death의 reason으로 원인 분류

관리 UI 켜기

terminal
rabbitmq-plugins enable rabbitmq_management
# 브라우저에서 http://localhost:15672
# 도커의 management 태그 이미지에는 이미 켜져 있다

UI에서 실제로 보는 화면

  • Queues 탭 — 큐별 Ready / Unacked / Total, Consumers 수, 큐 타입. 정렬해서 이상한 큐를 먼저 찾는다.
  • 큐 상세의 Get messages — 메시지를 실제로 꺼내 본다. Ack Mode를 Nack message requeue true로 두지 않으면 메시지가 사라지니 주의한다.
  • Connections / Channels — connection_name을 채워 두면 어느 서비스가 붙었는지 바로 보인다. Channel 수가 계속 늘면 채널 누수다.
  • Exchanges 탭의 바인딩 — 새 서비스 배포 후 바인딩이 실제로 걸렸는지 확인하는 곳.
i

알람으로 걸어 둘 것 보강

Prometheus 플러그인(rabbitmq_prometheus)을 켜면 지표를 그대로 긁어갈 수 있다. 최소한 이 네 개는 알람을 건다. 큐별 Ready 수(임계 초과), DLQ 길이(0보다 큼), unrouted 큐 길이(0보다 큼), 컨슈머 수 0(있어야 할 큐에 컨슈머가 없음). 마지막 것이 배포 사고를 가장 빨리 잡아준다.

정리

  • Ready가 쌓이면 처리 능력 문제, Unacked가 쌓이면 컨슈머 코드 문제다.
  • Get messages는 기본 설정으로 누르면 메시지를 소비해 버린다.
  • DLQ 길이, unrouted 길이, 컨슈머 수 0에 알람을 건다.
ITEM 31

알람과 flow control

브로커는 죽는 대신 발행자를 멈춰 세운다.

핵심 메모리나 디스크가 임계에 닿으면 RabbitMQ는 발행하는 커넥션을 블록한다. 앱에서는 publish가 조용히 멈춘 것처럼 보인다.
설정기본값권장
vm_memory_high_watermark.relative0.6 (RAM의 60%)0.4 ~ 0.7 범위. 0.7 이상은 모니터링이 확실할 때만
disk_free_limit.absolute50MB운영에는 절대 부족. 4GB 이상으로 올린다
파일 디스크립터OS 기본최소 50K, 필요하면 500K까지
 
flowchart LR
  P["Publisher"] -->|"publish"| B["브로커"]
  B --> M{"메모리 60% 초과?"}
  M -->|"아니오"| Q["큐에 저장"]
  M -->|"예"| BL["connection.blocked 전송 후 발행 차단"]
  BL --> C["컨슈머가 큐를 비우면"]
  C --> UB["connection.unblocked 후 재개"]
백프레셔는 기능이다 — 브로커가 OOM으로 죽는 대신 발행 쪽을 눌러 시스템을 살린다.

앱에서 감지하기

blocked.ts
conn.on('blocked', (reason) => {
  logger.error({ reason }, '브로커가 발행을 차단했다');
  metrics.gauge('amqp.blocked', 1);
});
conn.on('unblocked', () => {
  logger.info('발행 차단 해제');
  metrics.gauge('amqp.blocked', 0);
});

이 이벤트를 안 잡으면 "발행이 멈췄는데 에러는 없는" 상황을 디버깅하느라 오래 헤맨다. 반드시 로깅과 알람을 건다.

!

발행/소비 커넥션 분리가 여기서 효과를 낸다

블록은 커넥션 단위다. 발행과 소비가 같은 커넥션을 공유하면 블록된 순간 컨슈머까지 멈춰 큐를 비울 주체가 사라진다. ITEM 5에서 커넥션을 나누라고 한 이유가 이것이다.

i

근본 원인은 대개 큐 길이 보강

메모리 알람이 뜨는 진짜 이유는 대부분 컨슈머가 멈춰 큐가 무한정 자란 것이다. 브로커 메모리를 늘리는 건 시간을 버는 것뿐이다. 업무 큐에는 x-max-length와 x-overflow를 걸어 상한을 두고, 넘치면 DLQ로 흘리거나 발행을 거부하게 설계한다.

정리

  • 메모리 60%, 디스크 여유 부족 시 발행 커넥션이 블록된다. 에러가 아니라 대기다.
  • disk_free_limit 기본값 50MB는 운영에 쓰면 안 된다.
  • 'blocked'/'unblocked' 이벤트를 반드시 로깅한다.
  • 큐 길이 상한을 걸어 알람 자체가 안 뜨게 하는 게 근본 대책이다.
ITEM 32

로컬 환경과 자주 밟는 지뢰

처음 한 달 동안 만날 문제는 대체로 이 목록 안에 있다.

docker compose

docker-compose.yml
services:
  rabbitmq:
    image: rabbitmq:4-management
    ports:
      - "5672:5672"      # AMQP
      - "15672:15672"    # 관리 UI
    environment:
      RABBITMQ_DEFAULT_USER: app
      RABBITMQ_DEFAULT_PASS: app
      RABBITMQ_DEFAULT_VHOST: /dev
    volumes:
      - rabbitmq-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 10s
      retries: 5
volumes:
  rabbitmq-data:
!

vhost는 URL에 인코딩해서 넣는다

vhost /dev에 붙으려면 접속 URL이 amqp://app:app@localhost:5672/%2Fdev가 된다. 슬래시를 %2F로 인코딩하지 않으면 기본 vhost /에 붙어서 "큐를 만들었는데 UI에 안 보이는" 상황이 된다. 처음 이틀 안에 반드시 한 번 겪는다.

✓

입사 첫 주에 물어볼 것

브로커 버전(4.3 여부에 따라 재시도 설계가 달라진다), 큐 타입(classic인지 quorum인지), 클라이언트 라이브러리(amqplib인지 래퍼인지), 토폴로지 선언 주체(앱인지 definitions인지 policy인지), DLQ 운영 방식(누가 보고 어떻게 재투입하는지). 이 다섯 개면 기존 코드를 읽을 좌표가 잡힌다.

정리

  • 로컬은 rabbitmq:4-management 이미지 하나면 충분하다.
  • vhost는 URL에 %2F로 인코딩한다.
  • 대부분의 초기 문제는 바인딩 누락, prefetch 미설정, ack 누락, 에러 핸들러 누락 넷 중 하나다.
