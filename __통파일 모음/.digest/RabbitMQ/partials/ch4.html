ITEM 16

Classic, Quorum, Stream

큐 타입은 선언할 때 정하고, 나중에 못 바꾼다.

핵심 RabbitMQ 4.x의 실질적 기본값은 quorum queue다. classic은 복제 기능이 제거되어 단일 노드용으로 남았고, stream은 큐라기보다 로그다.

queue-types.ts
// 타입을 안 주면 classic 이 된다. 업무 큐라면 항상 명시한다.
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});

await ch.assertQueue('audit.events', {
  durable: true,
  arguments: { 'x-queue-type': 'stream', 'x-max-age': '7D' },
});
!

타입은 사후 변경 불가

x-queue-type은 선언 시에만 정해진다. classic → quorum 전환은 새 큐를 만들고 트래픽을 옮기는 마이그레이션이다. shovel 플러그인으로 기존 메시지를 옮기거나, 새 큐를 같은 exchange에 바인딩해 놓고 옛 큐가 비면 지우는 식으로 한다. 그래서 처음 만들 때 제대로 정하는 게 중요하다.

정리

  • 업무 큐의 기본값은 quorum. 고민되면 quorum.
  • classic은 이제 임시/짧은 수명 큐용이다. 복제가 없다.
  • stream은 다른 물건이다. 큐 대체재가 아니라 로그다.
  • 타입은 선언 시 고정. 바꾸려면 마이그레이션.
ITEM 17

Quorum queue를 기본으로 두기

Raft 합의로 복제된다. 안전한 대신 규칙이 몇 개 붙는다.

핵심 quorum queue는 과반이 살아 있어야 동작한다. 노드 3개 중 2개가 살아야 하고, 모든 메시지가 디스크에 기록된다. 
flowchart LR
  P["Publisher"] --> L["Leader 복제본 (노드 1)"]
  L --> F1["Follower (노드 2)"]
  L --> F2["Follower (노드 3)"]
  F1 -.->|"기록 확인"| L
  F2 -.->|"기록 확인"| L
  L -->|"과반 확인 후 confirm"| P
과반 합의 — 퍼블리셔 컨펌은 과반 복제본이 받아들인 뒤에 나간다. 그래서 confirm이 곧 내구성 보증이 된다.

인자기본값뜻

x-delivery-limit20재배달 한도. 초과 시 dead-letter (-1이면 무제한)

classic에 있던 게 없는 것들

  • 비내구성 큐 불가. 항상 durable이다.
  • exclusive 큐 불가. RPC 응답 큐 같은 건 classic으로 만든다.
  • 서버 생성 이름 불가. 큐 이름을 내가 지어야 한다.
  • global QoS 불가. 컨슈머별 prefetch만 쓴다.
  • x-max-priority 불필요. 0~31 우선순위가 항상 켜져 있다.
↑

4.3에서 좋아진 점 최신 반영

4.3은 quorum queue에 32단계 엄격 우선순위(관리 UI에서 우선순위별 메시지 수까지 보인다), 지연 재시도, 무제한 return(acquired-count와 delivery-count를 분리 추적해, 컨슈머가 명시적으로 되돌린 횟수는 재배달 한도에 안 세는 것), 그리고 32 KiB 이하 메시지의 메모리 오버헤드 50% 감소를 넣었다. 3.x 시절 "quorum은 느리고 무겁다"는 평이 지금도 맞다고 보긴 어렵다.

i

단일 노드 개발 환경에서도 보강

노드가 하나뿐인 로컬 도커에서도 quorum queue는 잘 돈다(복제본 1개짜리 Raft 그룹). 운영과 같은 타입으로 개발하는 편이 낫다. classic으로 개발하다 운영에서 quorum으로 바꾸면 exclusive/global QoS 같은 제약에 배포 당일 걸린다.

정리

  • 과반 노드가 살아 있어야 쓰기가 된다. 홀수 개(보통 3개)로 구성한다.
  • 항상 durable, exclusive 불가, global QoS 불가, 우선순위 항상 활성.
  • x-delivery-limit 기본값 20이 무한 재시도를 자동으로 막아 준다.
ITEM 18

Stream: 지우지 않는 큐

Kafka를 써봤다면 익숙한 모델. 소비해도 메시지가 남는다.

핵심 stream은 추가 전용 로그다. 소비는 읽기일 뿐이고, 메시지는 보존 정책에 따라 지워진다. 
flowchart TB
  subgraph QQ["큐: 파괴적 소비"]
    Q1["m1 m2 m3"] --> CA["컨슈머 A가 m1 처리 후 ack"]
    CA --> Q2["남은 것: m2 m3"]
  end
  subgraph ST["스트림: 비파괴적 읽기"]
    S["m1 m2 m3 m4 ..."]
    S --> RA["리더 A: offset 2 에서 읽는 중"]
    S --> RB["리더 B: offset 0 부터 다시 읽는 중"]
  end
소비의 의미가 다르다 — 스트림에서 컨슈머는 자기 오프셋만 들고 있고, 데이터는 공유된다.

선언과 읽기

stream.ts
await ch.assertQueue('events.stream', {
  durable: true,
  arguments: {
    'x-queue-type': 'stream',
    'x-max-age': '7D',                       // 7일 보존
    'x-max-length-bytes': 20_000_000_000,    // 또는 크기 기준
  },
});

// AMQP 0-9-1 로 읽을 때는 prefetch 가 필수다.
await ch.prefetch(100);
await ch.consume('events.stream', handler, {
  noAck: false,
  arguments: { 'x-stream-offset': 'first' },  // first | last | next | 숫자 | 타임스탬프
});

언제 쓰나

이럴 때선택
같은 이벤트를 여러 팀이 각자 처리, 나중에 팀이 늘 수도 있음Stream
버그 고친 뒤 지난 24시간을 다시 처리하고 싶음Stream
초당 수십만 건의 적재성 이벤트Stream

작업 분배(하나의 일을 하나의 워커가)Quorum queue
!

stream에 없는 것

메시지 TTL, 우선순위, dead lettering이 전부 없다. 개별 메시지를 실패 처리한다는 개념 자체가 없기 때문이다. 실패하면 오프셋을 안 올리고 다시 읽거나, 실패분을 별도 큐로 넘기는 걸 내가 짜야 한다. 전용 stream 프로토콜(포트 5552, 전용 클라이언트)을 쓰면 성능이 훨씬 좋지만 amqplib으로는 AMQP 0-9-1 경유로만 접근할 수 있다.

정리

  • stream은 소비해도 안 지워지는 로그다. 오프셋으로 위치를 잡고 재생할 수 있다.
  • 대량 팬아웃/재처리/감사 로그에 강하다.
  • TTL, 우선순위, DLX가 없으니 작업 큐 용도로는 쓰지 않는다.
ITEM 19

4.x에서 사라진 것들

검색해서 나오는 자료의 절반은 이미 유효하지 않다.

핵심 3.x 기준 블로그 글을 그대로 따라 하면 존재하지 않는 기능을 설정하게 된다. 특히 미러링, Mnesia, 지연 메시지 플러그인.
사라진 것언제지금은
클래식 큐 미러링 (ha-mode, ha-params policy)4.0quorum queue로 대체
Mnesia 메타데이터 저장소4.3에서 완전 제거Khepri가 유일한 저장소
네트워크 분단 처리 전략 (pause_minority, autoheal 등)4.3Raft가 처리. 설정 항목 자체가 없어짐
rabbitmq_delayed_message_exchange 플러그인2026-04 아카이브4.3+에서 로드되지 않는다 (ITEM 23)
transient non-exclusive 클래식 큐4.3부터 기본 비활성durable로 선언. 굳이 쓰려면 deprecated_features.permit.transient_nonexcl_queues = true
×

이런 자료를 만나면 일단 의심한다

ha-mode: all이라는 policy 설정이 나오면 3.x 자료다. x-delayed-message exchange 타입으로 지연을 구현하라는 글도 마찬가지다. 두 가지 모두 4.3에서는 아예 동작하지 않는다. RabbitMQ 자료를 읽을 때는 작성 시점과 대상 버전을 먼저 확인하는 습관이 필요하다.

Khepri가 뭔지 한 줄로

큐/exchange/바인딩/사용자 같은 메타데이터를 저장하는 내부 데이터베이스다. 옛 Mnesia는 네트워크 분단에 취약해 사람이 개입해야 하는 경우가 있었지만, Khepri는 Raft 기반이라 클러스터가 스스로 일관성을 지킨다. 애플리케이션 개발자가 직접 만질 일은 없지만, 클러스터 운영 절차가 바뀌었다는 사실은 알아야 한다.

정리

  • 미러링은 없다. 복제가 필요하면 quorum queue.
  • Mnesia와 분단 처리 전략은 4.3에서 제거. Khepri가 유일한 메타데이터 저장소.
  • 지연 메시지 플러그인은 아카이브됐고 4.3에서 못 쓴다.
  • 검색 결과를 볼 때 버전을 먼저 확인한다.
