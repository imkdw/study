ITEM 1

잡 큐와 메시지 브로커

BullMQ는 Redis 위에 얹은 라이브러리고, RabbitMQ는 그 자체로 서버다.

핵심 BullMQ는 작업의 생애를 저장하고, RabbitMQ는 메시지를 전달만 한다. 이 한 문장에서 나머지 차이가 전부 파생된다.

BullMQ: 서버가 없는 큐

BullMQ에는 설치할 브로커가 없다. Redis에 리스트/해시/정렬셋/스트림을 깔고, 그 위에서 Lua 스크립트로 원자적 상태 전이를 구현한 클라이언트 라이브러리다. new Queue()도 new Worker()도 전부 내 Node.js 프로세스 안의 객체이고, 둘은 Redis라는 공유 메모리를 통해서만 만난다.

그래서 BullMQ의 1급 개념은 메시지가 아니라 잡(job)이다. 잡에는 상태(waiting → active → completed / failed)가 있고, 시도 횟수가 있고, 반환값이 있고, 진행률이 있다. 이 모든 게 Redis에 남기 때문에 나중에 조회할 수 있다.

RabbitMQ: 프로토콜을 말하는 서버

RabbitMQ는 Erlang/OTP로 짜인 별도 프로세스다. 5672 포트에서 AMQP 0-9-1이라는 바이너리 프로토콜을 말하고, 어떤 언어의 클라이언트든 그 프로토콜만 지키면 붙을 수 있다. Node.js, Java, Go, Python이 같은 큐를 공유하는 게 기본 전제다.

RabbitMQ에게 메시지는 바이트 덩어리 + 헤더일 뿐이다. 브로커는 그 안에 무슨 일이 적혀 있는지 모르고, 알 필요도 없다. 컨슈머가 ack하는 순간 메시지는 큐에서 사라진다. 잡 결과도, 진행률도, 완료 이력도 개념 자체가 없다.

가장 흔한 착각

"큐니까 BullMQ에서 쓰던 기능이 다 있겠지"는 틀렸다. 진행률(job.updateProgress), 결과 조회(job.returnvalue), 완료 잡 목록, 잡 ID로 상태 조회 같은 것은 RabbitMQ에 대응물이 없다. 그런 게 필요하면 애플리케이션 DB에 직접 테이블을 만들어야 한다.

정리

  • BullMQ = Redis 위의 잡 상태 머신. RabbitMQ = 독립 프로세스인 메시지 라우터.
  • BullMQ는 잡의 이력이 남고, RabbitMQ는 ack 즉시 메시지가 사라진다.
  • RabbitMQ는 언어 중립 프로토콜이라 서비스 간 통신에 강하고, 대신 잡 관리 기능은 하나도 없다.
ITEM 2

BullMQ의 Queue와 RabbitMQ의 Queue는 다른 것이다

RabbitMQ에서 발행자는 큐 이름을 모른다. 그게 전부다.

핵심 RabbitMQ에는 발행자와 큐 사이에 Exchange라는 한 겹이 더 있다. 이 한 겹이 두 시스템의 설계 차이를 통째로 만든다.

BullMQ: 큐 이름이 곧 목적지

bullmq.ts
const queue = new Queue('email');

// 'email' 큐에 넣는다. 이 잡을 누가 가져갈지는 큐 이름이 이미 결정했다.
await queue.add('welcome', { userId: 42 });

발행자가 'email'이라는 이름을 알고 있어야 한다. 이 잡을 알림 서비스도 같이 받아야 한다면? queue.add를 한 번 더 호출하거나, 별도의 pub/sub을 하나 더 놓아야 한다. 발행자가 소비자 목록을 안다.

RabbitMQ: 발행자는 exchange에만 던진다

publisher.ts
// exchange 이름과 routing key만 안다. 큐 이름은 모른다.
channel.publish('user.events', 'user.created', Buffer.from(JSON.stringify({ userId: 42 })));
consumer.ts
// 소비자 쪽이 "나는 이런 메시지를 받겠다"고 선언한다.
await channel.assertQueue('email.welcome', { durable: true });
await channel.bindQueue('email.welcome', 'user.events', 'user.created');

나중에 알림 서비스가 같은 이벤트를 받고 싶어지면, 발행자 코드를 한 줄도 건드리지 않고 자기 큐를 만들어 바인딩만 추가하면 된다. 발행자는 구독자가 몇 개인지 영원히 모른다. 

flowchart LR
  P["Publisher"] -->|"routing key: user.created"| X{{"Exchange: user.events"}}
  X -->|"binding: user.created"| Q1["Queue: email.welcome"]
  X -->|"binding: user.*"| Q2["Queue: analytics.all"]
  X -->|"binding: user.created"| Q3["Queue: crm.sync"]

한 번 발행, 여러 큐 — 큐를 하나 더 붙이는 일이 바인딩 한 줄이다. 이게 BullMQ에는 없는 축이다.
i

처음에 헷갈리는 sendToQueue 보강

amqplib의 channel.sendToQueue('email', buf)는 BullMQ의 queue.add처럼 보인다. 하지만 실제로는 이름 없는 기본 exchange("")에 routing key를 큐 이름으로 넣어 발행하는 축약형이다. 모든 큐는 자기 이름과 같은 routing key로 기본 exchange에 자동 바인딩되어 있기 때문에 그렇게 동작한다. 편하지만, 이걸로만 쓰면 RabbitMQ를 비싼 BullMQ로 쓰는 셈이다.

정리

  • BullMQ: 발행자가 큐(목적지)를 지정한다. RabbitMQ: 발행자가 exchange + routing key(의도)를 지정한다.
  • 큐와 바인딩은 소비자 쪽 관심사다. 구독자 추가가 발행자 배포와 무관해진다.
  • sendToQueue는 기본 exchange를 쓰는 축약형이다. 편의 문법이지 다른 모델이 아니다.
ITEM 3

책임의 경계선 다시 긋기

BullMQ가 대신 해주던 일 중 상당수는 이제 내 설계다.

핵심 RabbitMQ가 보장하는 것은 사실상 "큐에 넣은 메시지를 컨슈머에게 최소 한 번 전달한다" 하나다. 그 위의 모든 것은 토폴로지 설계와 애플리케이션 코드다.

4.3에서 브로커 쪽으로 넘어온 것들 최신 반영

예전에는 "재시도 제한도 백오프도 전부 애플리케이션 몫"이라고 설명했지만, 지금은 그렇지 않다. quorum queue는 x-delivery-limit(기본 20)로 재배달 횟수를 세고, 4.3부터는 x-delayed-retry-type 계열 인자로 선형 백오프 재시도까지 브로커가 처리한다. BullMQ의 attempts/backoff에 상당히 가까워진 지점이다. 자세한 건 ITEM 21~22에서 다룬다.

✓

사고방식의 전환

BullMQ에서는 옵션 객체로 표현하던 것을, RabbitMQ에서는 큐와 exchange를 몇 개 어떻게 놓을지로 표현한다. "재시도 3번 후 실패 처리"가 코드 한 줄이 아니라 work 큐 + retry 큐 + dlq 큐 세 개의 그림이 된다. 대신 그 그림은 관리 UI에서 눈으로 보이고, 언어에 상관없이 공유된다.

정리

  • RabbitMQ의 보장은 "라우팅 + 최소 한 번 전달"까지다.
  • 스케줄, 레이트 리밋, 결과, 진행률, 잡 의존성은 없다. 필요하면 직접 만든다.
  • 대신 팬아웃, 라우팅, DLX, 발행 확인은 브로커가 훨씬 제대로 해준다.
  • 옵션으로 풀던 문제를 이제 토폴로지로 푼다.
ITEM 4

그래서 언제 무엇을 쓰나

둘은 경쟁 관계가 아니다. 실무에서는 같이 쓰는 경우가 오히려 흔하다.

BullMQ가 계속 나은 자리

  • 한 서비스 안에서 끝나는 백그라운드 작업. 썸네일 생성, PDF 렌더, 리포트 집계.
  • 작업의 결과나 진행률을 사용자에게 보여줘야 하는 경우.
  • 크론/반복 작업, 레이트 리밋이 핵심인 경우. (외부 API 초당 10회 제한 같은)
  • 부모-자식 작업 그래프(Flow)가 필요한 경우.
  • 이미 Redis가 있고, 인프라를 하나라도 덜 늘리고 싶은 경우.

RabbitMQ가 필요해지는 자리

  • 서비스 경계를 넘는 통신. 특히 Node 아닌 언어의 서비스가 섞여 있을 때.
  • 한 사건을 여러 소비자가 각자 처리해야 할 때(이벤트 팬아웃).
  • 메시지 종류에 따라 다른 처리 경로로 갈라야 할 때(라우팅).
  • 결제/정산처럼 유실이 곧 사고인 도메인. 퍼블리셔 컨펌 + quorum queue + DLX 조합이 필요할 때.
  • 느린 컨슈머를 브로커 차원의 백프레셔로 눌러야 할 때.
flowchart TB
  A["처리해야 할 일이 생겼다"] --> B{"다른 서비스도 알아야 하나?"}
  B -->|"아니오"| C{"결과/진행률/크론이 필요한가?"}
  C -->|"예"| D["BullMQ"]
  C -->|"아니오"| E["둘 다 가능. 팀 표준을 따른다"]
  B -->|"예"| F{"소비자가 여럿이거나 언어가 다른가?"}
  F -->|"예"| G["RabbitMQ"]
  F -->|"아니오"| H{"유실이 치명적인가?"}
  H -->|"예"| G
  H -->|"아니오"| E
고민의 순서 — "서비스 경계를 넘는가"가 첫 질문이다. 성능이 아니라 경계가 기준이다.

현실의 조합 보강

흔한 구성은 이렇다. 서비스 간 이벤트는 RabbitMQ로 흘리고, 각 서비스가 그 이벤트를 받아 자기 안에서 처리할 무거운 작업은 BullMQ 잡으로 다시 만든다. 브로커는 배달만 하고, 재시도/진행률/결과 같은 잡 관리는 서비스 내부에서 하는 셈이다. 이직한 회사에서 RabbitMQ를 쓴다고 해서 BullMQ 지식이 버려지는 게 아니라, 층이 하나 위로 올라간다고 보면 된다.

정리

  • 기준은 성능이 아니라 경계다. 서비스/언어 경계를 넘으면 RabbitMQ.
  • 잡 관리 기능(결과, 진행률, 크론, 레이트 리밋)이 핵심이면 BullMQ.
  • 둘을 계층으로 나눠 같이 쓰는 구성이 실무에서 가장 흔하다.
