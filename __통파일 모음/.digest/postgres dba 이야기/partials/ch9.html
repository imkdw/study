9-1

MVCC 모델과 PG MVCC 특징

이전 버전을 테이블 안에 쌓는 선택이 블로팅과 Vacuum과 Wraparound를 한꺼번에 낳았다.

핵심 “데드 튜플을 테이블 내부에 둔다”와 “XID가 32비트다” 두 가지 설계 결정이 이 챕터 전체의 원인이다. Vacuum은 그 결정의 청구서다.

MVCC의 이해

  • DB는 다수의 사용자가 동시에 데이터를 읽고 쓰는 환경에서 동작한다.
  • 읽기와 쓰기가 서로 블로킹하면 동시성이 매우 떨어지므로, 이를 해결하기 위해 MVCC 기법을 적용한다.
  • MVCC는 쿼리가 수행된 시점에 맞는 데이터 버전을 읽을 수 있게 해준다.
  • 이 “수행 시점”은 트랜잭션 ID로 식별하며, 트랜잭션 ID는 매 트랜잭션마다 1씩 증가한다.
  • 결국 쿼리는 시작 시점의 트랜잭션 ID와 같거나 더 작은 버전을 읽게 된다.

PostgreSQL의 MVCC 특징

  • MVCC를 구현하려면 이전 버전의 데이터를 일정 시간 보관해야 한다.
  • PostgreSQL은 테이블 내부에 이전 버전 데이터를 함께 저장하는 방식으로 동작한다.
  • 현재 레코드를 라이브 튜플, 이전 데이터를 데드 튜플이라고 부른다.

오라클과 갈리는 지점 보강

오라클은 이전 버전을 별도 공간(UNDO)에 보관한다. 그래서 테이블은 깨끗하게 유지되지만 UNDO가 부족하면 ORA-01555 snapshot too old가 난다. PostgreSQL은 반대로 테이블 안에 쌓으므로 그런 에러는 거의 없는 대신 테이블이 부풀고, 그것을 청소할 Vacuum이 반드시 필요해진다. 어느 쪽이 나은 설계가 아니라 비용을 어디에 둘 것인가의 선택이다.

특징 1. 데드 튜플을 테이블 내부에 저장한다
  • 데드 튜플을 테이블 내부에 보관하기 위해 수정 연산이 DELETE + INSERT 방식으로 동작한다.
  • 데드 튜플이 누적될수록 테이블 크기가 커지는데, 이 현상을 블로팅(Bloating)이라고 부른다.
  • 블로팅을 줄이려면 데드 튜플을 지속적으로 삭제해야 하는데, 이 작업이 바로 Vacuum이다.
  • 수동으로도, Autovacuum 프로세스로 자동으로도 수행할 수 있다.
  • 정상적으로만 수행되면 문제가 없어 보이지만, 슬로우 쿼리 같은 외부 요인이 Vacuum을 방해할 수 있다.
특징 2. 레코드별로 트랜잭션 ID를 관리한다
  • 쿼리 시점의 정합성에 맞는 레코드를 읽으려면 레코드별 트랜잭션 ID 관리가 필요하다.
  • PostgreSQL은 이를 위해 두 개의 시스템 컬럼을 쓴다.
    • XMIN — 해당 레코드를 생성한 시점의 트랜잭션 ID
    • XMAX — 해당 레코드가 삭제되거나 변경된 시점의 트랜잭션 ID
  • 레코드가 변경되면 새로운 라이브 튜플이 만들어지고, 데드 튜플의 XMAX와 새 라이브 튜플의 XMIN이 같은 값으로 설정된다.
    • XMAX가 0이면 그 튜플은 라이브 튜플이다.
  • 레코드마다 두 개의 시스템 컬럼을 갖는 것은 비효율적이므로, 오버헤드를 줄이기 위해 4바이트 정수형으로 저장한다. 즉 32비트 트랜잭션 ID로 관리한다.
UPDATE 한 번에 튜플이 하나 늘어난다 — 원본은 지워지지 않고 XMAX만 채워진 채 같은 블록에 남는다. 이것이 블로팅의 최소 단위다.
4바이트 트랜잭션 ID의 문제점
  • 32비트로 표현 가능한 값은 약 43억 개인데, TPS가 1000이면 50일이면 모두 고갈된다.
  • 43억 개를 모두 쓰면 다시 처음부터 순환해 번호를 부여해야 한다.
  • 이 현상을 Wraparound라고 부른다.
Wraparound를 방지하는 방법
  • PostgreSQL은 이 현상이 발생하기 전에 Vacuum 작업을 수행한다.
  • 이를 Anti-Wraparound Vacuum이라 부르며, 일반적인 데드 튜플 정리 목적의 Vacuum보다 훨씬 복잡하다.
  • 64비트로 바꾸거나 특정 값 조합으로도 해결할 수 있지만, PostgreSQL은 공간 오버헤드 문제 때문에 도입하지 않고 있다.
  • 현재 레코드당 약 20바이트 남짓을 메타데이터 관리에 쓰는데, 64비트를 도입하면 30바이트에 달하는 오버헤드가 발생한다.

32비트 XID 문제 해결을 위한 두 가지 기법

  • 43억 개의 XID를 모두 소진하고 다시 3부터 시작하면 43억 + 3번째 ID를 가지게 된다.
  • 그래서 이 값을 모든 XID보다 큰 수로 인식할 수 있게 만드는 방법이 필요하다.
    • 한 바퀴를 돌기 전에 오래된 레코드를 Frozen 상태로 만든다.
    • 43억의 50%인 21.5억만큼은 항상 읽을 수 있는 상태로 간주한다.
Frozen이란
  • 데이터를 “얼려서” XID와 무관하게 항상 읽을 수 있는 상태로 만드는 것이다.
  • Frozen 상태가 되면 해당 레코드의 XMIN이 2로 설정된다. 일반 XID는 3부터 시작하므로 항상 과거가 된다.
XID이름쓰임
1Bootstrap XIDinitdb 수행 시 사용
2Frozen XIDAnti-wraparound Vacuum이 부여. 항상 “가장 오래된” 값
3 이상일반 XID일반 트랜잭션에서 사용
  • 다만 Frozen 작업에는 시간이 걸리므로, PostgreSQL은 일정 범위 내의 레코드는 Frozen이 아니어도 항상 읽을 수 있도록 설계되어 있다.
  • 즉 현재 XID를 기준으로 21.5억 이전까지의 레코드는 항상 읽을 수 있는 것으로 간주한다.
signed int를 사용하는 이유
  • 예를 들어 3 - 43억은 음수가 나와야 할 계산이다.
  • 하지만 signed int에서 오버플로가 발생해 양수로 해석된다.
  • 그러면 PostgreSQL은 해당 레코드를 과거의 것으로 인식하고 정상적으로 읽을 수 있다.
  • 반대로 21.5억 이후의 XID에 대해서는 모두 Frozen 상태가 되어야만 읽을 수 있다.
  • 현재 XID가 3인데 10이 Frozen되지 않았다면 3 - 10은 signed int로도 여전히 음수다.
  • Frozen 처리가 일정 속도로 따라가지 못하면 PostgreSQL은 에러를 내며 트랜잭션 처리를 중단시킨다.

이 에러를 보면 이미 늦은 것이다

서버 로그
ERROR: database is not accepting commands to avoid wraparound data...
HINT: Stop the postmaster and use a standalone backend to VACUUM that database

이 상태가 되면 DB가 쓰기를 전면 거부한다. 단일 사용자 모드로 내려 Vacuum을 돌려야 하므로 사실상 전면 장애다. 그래서 XID 나이는 사후 대응이 아니라 상시 모니터링 대상이다.

DB별 XID 나이 감시
select datname, age(datfrozenxid),
       round(100 * age(datfrozenxid) / 2100000000.0, 1) as pct_to_limit
from   pg_database
order  by age(datfrozenxid) desc;

정리

  • PostgreSQL의 MVCC는 이전 버전을 테이블 안에 남긴다. 그래서 UPDATE는 DELETE + INSERT이고 블로팅이 생긴다.
  • 가시성 판단은 레코드의 XMIN/XMAX와 현재 XID의 비교로 이뤄진다.
  • XID가 32비트라 43억에서 순환한다. 앞뒤를 구분하기 위해 절반인 21.5억을 “과거”의 경계로 쓴다.
  • 경계를 넘기 전에 오래된 레코드를 XMIN = 2(Frozen)로 만드는 것이 Anti-Wraparound Vacuum이다.
  • 따라잡지 못하면 DB가 쓰기를 거부한다. age(datfrozenxid)는 상시 감시 지표다.
9-2

Vacuum 기본

VACUUM과 VACUUM FULL은 이름만 닮았지 다른 명령이다. WAL 발생량 72바이트와 15MB가 그 차이다.

핵심 일반 Vacuum은 공간을 재사용 가능하게 만들고, VACUUM FULL은 테이블을 새로 쓴다. 그래서 후자는 Access Exclusive 락을 잡고 테이블 크기만큼 WAL을 만든다.

Vacuum 수행 방법과 옵션

  • VACUUM 명령으로 수행하며 테이블이나 DB 단위로 가능하다.
  • 일반적으로 테이블 단위로 수행하며, 스키마나 인덱스 단위 작업은 제공하지 않는다.
테스트 환경 구성 
-- 테이블 페이지 상태 관찰을 위한 익스텐션
postgres=# create extension pageinspect;

-- 테이블 생성 & 인덱스 추가 & 데이터 삽입
postgres=# create table vt1 (c1 integer, c2 integer);
postgres=# create index vt1_n1 on vt1 (c1);
postgres=# insert into vt1 select i, i from generate_series(1, 2) i;

FULL 옵션

  • 일반적인 Vacuum과 달리 테이블을 재구성하는 작업이다.
  • 이 옵션은 Vacuum의 하위 옵션이라기보다 별도의 명령어로 이해하는 편이 바람직하다.
  • pg_relation_filepath()로 VACUUM FULL 이후 테이블과 인덱스가 재생성되는 것을 볼 수 있다.
파일이 통째로 바뀐다 
-- 수행 전
postgres=# select pg_relation_filepath('vt1');    -- base/5/16464
postgres=# select pg_relation_filepath('vt1_n1'); -- base/5/16467

-- VACUUM FULL 수행
postgres=# vacuum full vt1;

-- 수행 후
postgres=# select pg_relation_filepath('vt1');    -- base/5/16513
postgres=# select pg_relation_filepath('vt1_n1'); -- base/5/16516

파일 번호가 바뀌었다는 것은 새 파일을 만들어 데이터를 옮겨 담았다는 뜻이다. 그래서 작업 중 원본 크기만큼의 여유 디스크가 추가로 필요하고, 끝날 때까지 Access Exclusive 락이 유지된다.

FREEZE

  • 레코드에 대한 Frozen 작업을 매우 공격적으로 수행하는 옵션이다.
  • 기본적으로 VACUUM은 설정된 파라미터에 따라 일부 레코드만 Frozen 처리한다.
  • FREEZE를 쓰면 테이블 내 모든 레코드를 대상으로 Frozen 처리한다.
  • 참고로 VACUUM FULL은 내부적으로 FREEZE가 자동으로 동작한다.

SKIP_LOCKED

  • Vacuum은 Share Update Exclusive 모드의 테이블 락이 필요하며, 이는 Share 모드 이상과 호환되지 않는다.
  • 락 충돌 상황에서 대기하지 않고 Vacuum 작업을 건너뛰는 옵션이다.
  • 여러 테이블에 대해 Vacuum을 순차 처리할 때 특히 유용하다.
  • 진행 가능한 테이블만 우선 처리하고, 스킵한 테이블은 별도로 다시 처리하는 유연한 운영이 가능해진다.
-- 세션#1) 트랜잭션 시작 후 인덱스 생성 (Share 모드 락)
postgres=# begin;
postgres=*# create index vt1_n2 on vt1(c2);

-- 세션#2) 바큠 수행 + 락 대기로 인해서 명령어 중단요청
postgres=# vacuum (verbose) vt1;

-- 세션#2) SKIP_LOCKED 옵션을 사용해서 바큠 수행
postgres=# vacuum (verbose, skip_locked) vt1;
WARNING:  skipping vacuum of "vt1" --- lock not available

INDEX_CLEANUP

  • Vacuum은 기본적으로 테이블과 그 테이블의 모든 인덱스에 대해 수행된다.
  • 이 옵션은 인덱스에 대한 Vacuum 수행 여부를 결정하며 기본값은 AUTO다.
  • AUTO는 데드 튜플 개수를 기준으로 인덱스 Vacuum 수행 여부를 PostgreSQL이 판단한다.
  • OFF면 인덱스에 대한 Vacuum을 수행하지 않는다.
  • 인덱스 Vacuum은 테이블 Vacuum보다 훨씬 오래 걸리는 작업이므로, 대용량 테이블의 데드 튜플 정리와 Frozen 작업만 빠르게 끝내고 싶을 때 인덱스 Vacuum 생략을 고려할 수 있다.

파라미터를 테이블 단위로 설정하기
  • INDEX_CLEANUP은 테이블 단위로 설정 가능한 스토리지 파라미터이기도 하다.
  • 설정값은 수동/자동 Vacuum 모두에 적용된다.
  • Autovacuum이 인덱스 Vacuum을 장시간 수행한다면 꺼두었다가 나중에 수동으로 처리할 수도 있다.
-- index_cleanup 비활성화
postgres=# alter table vt1 set (vacuum_index_cleanup=off);

-- pg_class 카탈로그 테이블에서 설정된 값 확인
postgres=# select reloptions from pg_class where relname='vt1';
         reloptions
----------------------------
 {vacuum_index_cleanup=off}

TRUNCATE

  • 테이블 맨 뒤부터 일정 크기 이상의 공간이 모두 비었을 때, 그 공간을 OS에 반납할지 결정하는 옵션이다.
  • 기본값은 ON이며 빈 공간을 OS에 자동으로 반환한다.
    • 정리된 페이지 수가 1000개 이상이거나 테이블 전체 크기의 6.25% 이상이면 반납한다.
  • 반납하면 테이블의 물리적 파일 크기가 줄어 디스크 사용량 절감 효과가 있다.
  • 다만 INDEX_CLEANUP이 꺼져 있으면 TRUNCATE도 동작하지 않으므로 확인이 필요하다.
  • VACUUM FULL과 마찬가지로 Access Exclusive 락을 요청하지만, 일정 시간 재시도한 뒤 해당 단계를 스킵한다.
  • 이런 동작 덕분에 백엔드 프로세스와의 락 경합 이슈는 크게 발생하지 않는다.

PARALLEL

  • 인덱스에 대한 Vacuum 작업을 병렬로 수행하도록 설정하는 옵션이다.
  • 수동 Vacuum에만 적용되고 Autovacuum에는 적용되지 않는다.
  • 일반적으로 Vacuum 단계 중 가장 오래 걸리는 것이 인덱스 정리 작업이다.
  • 테이블에 인덱스가 2개 이상이고 각 인덱스가 일정 크기 이상이면, 백엔드 프로세스와 병렬 프로세스가 함께 인덱스 Vacuum을 수행한다.
  • 인덱스가 많은 대용량 테이블의 Vacuum 성능 개선에 매우 유용하다.

왜 6이 아니라 5인가 보강

병렬 Vacuum은 인덱스 하나당 워커 하나를 배정하고, 그중 하나는 작업을 지시한 백엔드 프로세스 본인이 처리한다. 인덱스가 6개이므로 추가로 필요한 워커는 5개이고, parallel 6이라고 적어도 5개만 뜬다. 인덱스 수가 곧 병렬도의 상한이라는 뜻이다. 인덱스가 1개인 테이블에서는 parallel이 아무 효과가 없다.

체크포인트 직후에 WAL이 폭증하는 이유 보강

체크포인트 이후 처음 수정되는 페이지는 변경분이 아니라 페이지 전체(8KB)가 WAL에 기록된다. 이것이 FPW(Full Page Write)이고, 부분 쓰기로 페이지가 찢어지는 사고를 막기 위한 장치다. 그래서 같은 FREEZE가 2750kB에서 16MB로 뛴다. 실무에서 “체크포인트 직후에만 WAL 생성량이 튄다”는 관찰의 정체가 이것이며, checkpoint_timeout을 늘려 체크포인트 빈도를 낮추면 전체 WAL 양이 줄어드는 이유이기도 하다. 7-5의 pg_stat_wal에서 Full Page Write 횟수를 봐야 한다고 한 것이 이 지표다.

vacuumlo를 이용한 Orphan LOB 정리

  • PostgreSQL은 BYTEA, TEXT, OID 세 가지 타입의 LOB(Large Object)를 지원한다.
  • OID 타입은 LOB를 pg_largeobject 시스템 테이블에 저장하는데, 여기서 Orphan LOB 문제가 발생할 수 있다.
Orphan LOB 문제
  • OID 타입을 쓰면 Vacuum을 수행해도 pg_largeobject에 남은 LOB 데이터가 정리되지 않는다.
  • 원본 데이터가 삭제된 뒤에도 남아 있는 LOB를 Orphan LOB라고 부른다.

  • 한번 커진 pg_largeobject 테이블 크기는 자동으로 줄어들지 않는다.
  • 이 테이블을 쓴다면 모니터링하면서 주기적으로 VACUUM FULL을 수행해야 한다.
  • OID 기반 LOB를 잘못 쓰면 저장공간이 낭비되므로, 올바른 삭제 처리 로직 구성이 필요하다.

AGE

  • AGE는 말 그대로 나이를 의미하며 일상적인 나이 개념과 유사하다.
  • 테이블이 생성된 시점이 생일이고, 트랜잭션이 발생할 때마다 1살씩 먹는다고 생각하면 된다.
  • 중요한 점은 해당 테이블에 트랜잭션이 직접 발생하지 않더라도 전체 시스템의 트랜잭션이 증가하면 테이블의 나이도 증가한다는 것이다.
PG에서 AGE를 관리하는 이유
  • Frozen 처리를 위해서는 현재 XID와 비교할 기준값이 필요한데, 그 값이 relfrozenxid다.
  • 현재 XID와의 차이(age())가 바로 나이다.
  • 그래서 Frozen 작업을 수행하면 AGE는 다시 작아진다.
테이블 하나를 더 만들었을 뿐인데 at1이 늙는다

postgres=# select relname, relfrozenxid, age(relfrozenxid) from pg_class where relname in ('at1', 'at2');

모든 행의 나이가 동시에 1씩 오른다. 나이는 절대 시간이 아니라 시스템 전체의 트랜잭션 진행량이기 때문이다. 조용한 테이블도 바쁜 시스템에서는 빠르게 늙는다.

Visibility Map

  • PostgreSQL의 MVCC 특성 때문에 필요한 오브젝트다.
  • 각 테이블 블록당 2비트로 구성되며, 각 비트는 그 블록 내 레코드의 가시성과 Frozen 상태를 나타낸다.
비트1이 되는 조건효과
ALL_VISIBLE 모든 레코드가 모든 트랜잭션에게 가시적일 때. 하나라도 아니면 0. Vacuum 직후에는 모든 블록이 1이 되고, 하나라도 변경되면 다시 0이 된다 이 비트가 1인 블록만 Index Only Scan이 가능하다
ALL_FROZEN 블록 내 모든 레코드가 Frozen 상태일 때 0이면 향후 Frozen 작업 대상으로 간주된다. 1이면 Vacuum이 그 블록을 건너뛴다
VACUUM FULL 직후에 VACUUM이 또 필요한 이유
  • VACUUM FULL 내부에는 FREEZE가 포함되므로 t_infomask의 9, 10번째 비트가 모두 1로 설정된다.
  • 하지만 VACUUM FULL 이후에는 VM 파일이 자동으로 만들어지지 않아 VM이 주는 이점을 쓸 수 없다.
  • 그래서 VACUUM FULL 이후에는 VACUUM 또는 VACUUM (FREEZE)를 한 번 더 수행해 VM을 생성해야 한다.
!

이걸 빠뜨리면 Index Only Scan이 죽는다

블로팅을 잡으려고 정기 점검에 VACUUM FULL을 돌린 뒤, 다음 날부터 특정 쿼리가 느려졌다면 이 이유일 가능성이 높다. VM이 없으면 ALL_VISIBLE을 판정할 수 없어 Index Only Scan이 매번 힙을 확인하게 되고, 실행계획의 Heap Fetches가 0에서 갑자기 치솟는다. VACUUM FULL 뒤에는 VACUUM ANALYZE까지 한 세트로 묶어두는 편이 안전하다.

정리

  • VACUUM은 공간을 재사용 가능하게 만들고(72바이트), VACUUM FULL은 테이블을 새로 쓴다(15MB + Access Exclusive).
  • 일반 Vacuum은 테이블 끝만 잘라낼 수 있고 인덱스는 줄이지 못한다. 인덱스는 REINDEX가 필요하다.
  • 체크포인트 직후 첫 수정은 FPW로 페이지 전체가 WAL에 실린다. WAL 폭증의 흔한 원인이다.
  • 병렬 Vacuum의 상한은 인덱스 개수다. 워커 하나는 백엔드 본인이 맡는다.
  • AGE는 시스템 전체 트랜잭션 진행량이다. 조용한 테이블도 함께 늙는다.
  • VACUUM FULL은 VM을 남기지 않는다. 뒤에 VACUUM ANALYZE를 반드시 붙인다.
9-3

Vacuum 및 Autovacuum 관련 주요 파라미터

Autovacuum 튜닝은 언제 시작할지(임계값)와 얼마나 세게 할지(코스트) 두 축뿐이다.

핵심 시작 조건은 전부 threshold + scale_factor × reltuples 한 공식이다. 대용량 테이블에서는 scale_factor가 지배하므로 테이블 단위로 낮춰줘야 한다.

Autovacuum 프로세스의 역할

  • 통계 정보 갱신, 데드 튜플 정리, 입력 레코드 Vacuum, XID Frozen 작업을 자동으로 수행한다.
  • XID Frozen은 MVCC 일관성 유지를 위한 필수 작업이라 관련 파라미터가 off여도 작동한다.
  • 백그라운드에서 자동 수행되는 작업이므로 파라미터 조정으로 업무 시간대 부하를 최소화해야 한다.
입력 레코드에 대한 Autovacuum
  • 13부터 추가된 기능이다. 이전까지는 데드 튜플이 있는 블록에 대해서만 작업이 수행됐다.
  • 13부터는 데드 튜플 없이 레코드 추가만 발생한 블록에 대해서도 자동으로 작업이 수행된다.
i

왜 INSERT만 하는 테이블에도 Vacuum이 필요한가 보강

로그 테이블처럼 INSERT만 쌓이는 테이블에는 데드 튜플이 없다. 그런데도 13에서 이 기능이 추가된 이유는 두 가지다. 첫째, Frozen 처리가 밀리면 결국 Anti-Wraparound Vacuum이 한꺼번에 몰아친다. 둘째, VM의 ALL_VISIBLE 비트가 서지 않아 Index Only Scan이 동작하지 않는다. 즉 지울 게 없어도 Vacuum은 필요하다.

autovacuum_naptime
  • 런처 프로세스가 postgres 프로세스에게 워커를 요청하는 주기를 설정한다.
  • 기본값은 60초다.
  • 런처는 이 주기마다 1개의 워커 프로세스를 요청한다.
  • Autovacuum 대상이 많아 60초 이내에 처리되지 않으면, 최초 워커 생성 60초 후에 새 프로세스가 추가로 생성된다.
!

CIC 옵션과는 무관하다 원문 교정

노트에는 “기본값은 60초며 CIC 옵션으로 변경이 가능함”이라고 적혀 있는데, CIC(CREATE INDEX CONCURRENTLY)는 인덱스 생성 옵션이라 이 파라미터와 아무 관계가 없다. 공식 문서 기준 autovacuum_naptime은 postgresql.conf 또는 서버 커맨드라인에서만 설정할 수 있고, 변경 후에는 pg_ctl reload(또는 select pg_reload_conf())로 반영한다. 재시작은 필요 없다. 참고로 같은 그룹에서 autovacuum_max_workers와 autovacuum_freeze_max_age는 재시작이 필요하다.

autovacuum_max_workers
  • 최대 생성 가능한 워커 프로세스 수를 설정한다.
  • 기본값은 3이며 시스템 리소스에 따라 조정할 수 있다.

Autovacuum 작업 부하 조절용 파라미터

  • Autovacuum은 대상 레코드가 많을수록 작업량이 커지고 시스템 부하도 커진다.
  • 수동 Vacuum처럼 실행 시점을 조정할 수 없어 피크 타임에도 실행될 수 있다.
  • 그래서 가능한 한 적은 부하로 백그라운드에서 실행되도록 설계되어 있고, 파라미터 조정으로 최적화할 수 있다.
autovacuum_vacuum_cost_delay
  • 기본값 2ms. Autovacuum이 일정 작업량을 처리한 후 얼마나 대기할지 결정한다.
  • 길수록 시스템 부하는 줄지만 작업이 오래 걸리고, 짧을수록 자원 사용률이 올라가고 빨리 끝난다.
  • 리소스 여유가 있는 시스템에서는 줄이고, 없으면 늘린다.
  • 수동 Vacuum은 이 값이 0이므로 쉬지 않고 연속으로 작업한다.
autovacuum_vacuum_cost_limit
  • 기본값 -1이며 작업 단위를 설정하는 데 쓴다.
  • -1이면 vacuum_cost_limit을 사용하고, 이 파라미터의 기본값은 200이다.
  • Autovacuum은 cost_limit만큼 작업하고 cost_delay만큼 대기하는 방식으로 동작한다.

  autovacuum_vacuum_threshold    = 50000
);

  • 하지만 모든 레코드를 Frozen 처리해 테이블 나이를 0으로 만들지는 않는다.
  • vacuum_freeze_min_age 값 이상인 레코드만 Frozen 처리한다.
예시: 테이블 AGE가 2억인 경우
  1. AGE가 vacuum_freeze_min_age(5천만) 미만인 레코드는 대상에서 제외
  2. Frozen 처리 이후 테이블의 나이는 vacuum_freeze_min_age 수준으로 리셋
  3. 이후 트랜잭션이 1.5억 개 더 발생
  4. 다시 2억에 도달하면 Frozen 작업 수행
Frozen 작업 성능 최적화: VM을 활용한 스킵
  • 9.6부터 VM(Visibility Map)을 활용해 이미 Frozen 처리된 블록을 건너뛸 수 있게 됐다.
  • 반복적인 Frozen 작업으로 인한 시스템 부하 문제를 효과적으로 해소할 수 있게 되었다.

FK가 많은 시스템은 이쪽을 먼저 본다 보강

8-1에서 확인했듯 FK는 마스터 레코드에 멀티 트랜잭션을 대량 생산한다. 그런 시스템에서는 일반 XID 나이보다 mxid_age가 먼저 차오르는 일이 흔하다. 감시 쿼리에 두 나이를 나란히 넣어두는 편이 좋다.

select relname,
       age(relfrozenxid)    as xid_age,
       mxid_age(relminmxid) as mxid_age
from   pg_class
where  relkind in ('r','m','t')
order  by greatest(age(relfrozenxid), mxid_age(relminmxid)) desc
limit  10;

정리

  • Autovacuum 튜닝은 시작 조건(threshold/scale_factor)과 진행 속도(cost_limit/cost_delay) 두 축이다.
  • 시작 조건은 전부 threshold + scale_factor × reltuples. 대용량 테이블은 테이블 단위로 낮춘다.
  • cost_limit 200은 버퍼 히트 200블록 / 디스크 100블록 / 더티 10블록에 해당한다.
  • autovacuum_naptime은 reload로 반영되고, max_workers와 freeze_max_age는 재시작이 필요하다.
  • XID 나이와 멀티 트랜잭션 나이는 별개다. FK가 많으면 후자가 먼저 찬다.
9-4

Slow Query 수행과 Vacuum

커트라인은 테이블마다가 아니라 DB 전체에 하나다. 그래서 슬로우 쿼리 하나가 모든 테이블의 Vacuum을 멈춘다.

핵심 Vacuum은 가장 오래된 쿼리의 XID보다 과거의 데드 튜플만 지울 수 있다. 그 커트라인이 DB 전역이라는 점이 이 항목의 모든 것이다.

Slow Query 수행과 Vacuum

  • 슬로우 쿼리가 있으면 Vacuum이 데드 튜플을 정상적으로 정리하지 못하는 현상이 있다.
  • 대부분의 시스템에서는 큰 문제가 되지 않는다. 블록 I/O 관점에서 실제로 읽어야 할 블록 수가 크게 늘지는 않기 때문이다.
  • 하지만 동일 레코드에 대해 반복적으로 변경이 수행되면 문제가 된다. 데드 튜플 정리가 지연되면서 저장공간이 낭비되고 성능 저하로 이어진다.

데드 튜플 삭제 기준(Cutoff) 정책

  • DBMS는 다수의 유저가 동시에 조회하고 변경하는 시스템이다.
  • 언제나 수많은 쿼리가 동시에 실행되고, 이 과정에서 데드 튜플이 지속적으로 발생한다.
  • 데드 튜플은 MVCC 읽기 일관성 보장을 위해 반드시 필요한 정보다.
  • Vacuum이 실행될 때마다 모든 데드 튜플을 제거한다면, 과거 시점의 데이터를 참조 중인 쿼리에서 Snapshot Too Old 에러가 발생할 것이다.
PostgreSQL의 Cutoff 정책
  • 이 문제를 해결하기 위해 데드 튜플을 안전하게 삭제할 수 있는 기준점을 설정한다.
  • 이 기준점은 현재 수행 중인 쿼리 중 가장 오래전에 시작된 쿼리의 XID다.
  • 즉 Vacuum은 가장 오래된 쿼리의 시작 시점보다 더 과거에 생성된 데드 튜플만 삭제할 수 있다.
  • 이 값은 pg_stat_activity.backend_xmin에서 확인할 수 있다.
중요한 특징
  • Cutoff 기준점은 테이블 단위가 아니라 DB 전체에서 단 하나만 설정된다.
  • 특정 테이블을 조회하는 슬로우 쿼리가 수행 중이면 이 기준이 DB 전체에 공통으로 적용된다.
  • 그래서 슬로우 쿼리 하나가 나머지 모든 테이블의 Vacuum에 영향을 미친다.
커트라인이 하나라서 무관한 테이블까지 함께 묶인다 — t_log를 읽는 긴 쿼리가 orders의 데드 튜플까지 붙잡아둔다. 이것이 슬로우 쿼리 모니터링이 Vacuum 운영의 일부인 이유다.

예방책은 감시만이 아니다 보강

감시가 1차 방어라면, 2차 방어는 긴 트랜잭션이 애초에 오래 살지 못하게 막는 것이다. idle_in_transaction_session_timeout(열어놓고 노는 트랜잭션 강제 종료)과 statement_timeout(쿼리 자체의 상한)을 걸어두면 커트라인이 무한정 뒤처지는 상황을 구조적으로 막을 수 있다. 그리고 이 항목의 클릭 카운터 같은 케이스는 9-6의 fillfactor 조정으로 HOT 갱신을 유도하는 것이 근본 처방에 가깝다.

정리

  • Vacuum의 삭제 커트라인은 DB 전역에 하나이고, 가장 오래된 backend_xmin이 그 값이다.
  • 그래서 무관한 테이블을 읽는 슬로우 쿼리가 다른 모든 테이블의 Vacuum을 막는다.
  • 평소에는 싱글 페이지 클린업이 막아주지만, 커트라인이 밀리면 그것마저 무력해진다(2블록 → 244블록).
  • 조기 경보는 pg_current_xact_id() - min(backend_xmin) 한 줄이다.
  • 예방은 idle_in_transaction_session_timeout / statement_timeout, 근본 처방은 fillfactor + HOT.

원문 상태 보강

이 노트(9-5. 복제 충돌과 Hot Standby Feekback.md)는 본문이 # 패스 한 줄뿐이다. 원문에 없는 서술을 지어내지 않는다는 원칙에 따라, 아래는 제목이 가리키는 개념만 공식 문서에서 확인해 최소한으로 채운 보강이다. 이 항목 전체가 원문이 아니라는 점을 밝혀둔다.

핵심 hot_standby_feedback = on은 리플리카의 쿼리를 살리는 대신, 마스터의 블로팅을 리플리카가 결정하게 만든다. 9-4의 커트라인 문제가 서버를 건너뛰어 전파되는 구조다.

왜 충돌이 생기는가

마스터에서 Vacuum이 데드 튜플을 정리하면 그 사실이 WAL로 리플리카에 전달된다. 그런데 리플리카에서는 그 데드 튜플을 아직 보고 있는 쿼리가 돌고 있을 수 있다. 마스터는 리플리카에서 무엇이 도는지 모르기 때문에 9-4의 커트라인 계산에 리플리카의 쿼리가 반영되지 않는다. 이 상태로 정리 WAL이 적용되면 실행 중이던 쿼리가 읽어야 할 버전이 사라진다.

두 가지 선택지

파라미터기본값동작대가
max_standby_streaming_delay 30초 충돌하는 WAL을 적용하기 전에 이만큼 기다렸다가, 그래도 쿼리가 안 끝나면 쿼리를 취소한다. -1이면 무한정 기다린다 쿼리가 취소되거나(짧게 잡으면), 복제 적용이 지연된다(길게 잡으면)
hot_standby_feedback off 리플리카가 자기가 지금 무엇을 보고 있는지를 마스터에 알린다. 마스터는 그 정보를 커트라인 계산에 넣어 애초에 정리하지 않는다 리플리카의 긴 쿼리가 마스터의 블로팅을 유발한다

공식 문서는 hot_standby_feedback을 두고 “can be used to eliminate query cancels caused by cleanup records, but can cause database bloat on the primary for some workloads”라고 서술한다. 즉 쿼리 취소와 마스터 블로팅 중 무엇을 감수할지의 선택이다. 피드백은 wal_receiver_status_interval보다 자주 전송되지 않으며, 캐스케이드 복제에서는 상위로 계속 전달되어 결국 마스터까지 도달한다.

!

on으로 켤 때 함께 봐야 할 것

켜는 순간 리플리카에서 도는 장기 쿼리와 idle in transaction 세션이 마스터의 Vacuum을 막게 된다. 9-4의 문제가 서버 경계를 넘어 확대되는 셈이다. 그래서 켠다면 리플리카 쪽에도 statement_timeout과 idle_in_transaction_session_timeout을 반드시 함께 걸어야 하고, 마스터의 age()와 데드 튜플 추이를 감시해야 한다. 리플리카가 순수 조회 전용이고 쿼리가 짧다면 기본값 off + max_standby_streaming_delay 조정만으로 충분한 경우가 많다.

충돌 이력 확인

실제로 얼마나 취소됐는지는 리플리카에서 pg_stat_database_conflicts로 확인한다. 취소 사유가 스냅샷, 락, 테이블스페이스, 버퍼 핀, 데드락으로 나뉘어 집계되므로, 어떤 조정이 필요한지 판단할 수 있다.

리플리카에서 실행 
select datname, confl_tablespace, confl_lock, confl_snapshot,
       confl_bufferpin, confl_deadlock
from   pg_stat_database_conflicts
where  datname is not null;

애플리케이션에서는 아래 에러로 나타난다. 이 메시지를 보면 위의 두 파라미터를 검토할 때다.

리플리카 로그 
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.

정리

  • 원문은 이 항목을 건너뛰었다. 위 내용은 공식 문서로 확인한 최소한의 보강이다.
  • 복제 충돌은 마스터의 정리 WAL과 리플리카의 실행 중 쿼리가 부딪히는 상황이다.
  • max_standby_streaming_delay(기본 30초)는 쿼리 취소 vs 복제 지연의 선택이다.
  • hot_standby_feedback(기본 off)은 쿼리 취소 vs 마스터 블로팅의 선택이다.
  • 켠다면 리플리카에도 타임아웃을 걸고, 마스터의 데드 튜플과 age()를 함께 감시한다.
9-6

Heap Only Tuples 및 fillfactor

인덱스 컬럼이 안 바뀌었다면 인덱스를 건드리지 않는다. 단, 같은 블록에 자리가 있을 때만.

핵심 HOT은 “블록 안에 여유가 있는가”로 성립 여부가 갈린다. fillfactor 기본값 100은 그 여유를 0으로 만드는 설정이다.

HOT(Heap-Only Tuples)

  • PostgreSQL의 MVCC 모델에서 발생할 수 있는 성능 저하를 완화하기 위한 중요한 튜닝 기법이다.
  • HOT은 MVCC 및 Vacuum과 밀접하게 연결되어 있다.

HOT 탄생 배경과 기본 컨셉

  • PostgreSQL의 MVCC는 데드 튜플로 구현되므로 UPDATE가 기본적으로 INSERT + DELETE로 동작한다.
  • 이 방식은 MVCC 구현에는 유리하지만 테이블과 인덱스의 크기가 커진다는 부작용이 있다.
  • 특히 인덱스 컬럼 값이 변하지 않았어도 레코드가 새로 추가되면서 인덱스 엔트리도 생긴다.
  • 인덱스가 많을수록 심해지며 성능 저하와 디스크 공간 낭비로 이어진다.
  • 이 문제를 해결하기 위해 도입된 것이 HOT이다.

HOT 기본 컨셉
  • 핵심 아이디어는 인덱스 컬럼이 변경되지 않았다면 인덱스를 갱신하지 않는다는 것이다.
  • 인덱스가 없는 컬럼에 대해 UPDATE를 수행하면 인덱스에는 아무 변화 없이 테이블 내 레코드만 변경된다.
  • 이를 지원하기 위해 PostgreSQL은 테이블 블록 내부에 HOT 체인을 만든다.
  • 인덱스는 기존의 테이블 위치를 그대로 가리키고, 쿼리 실행 시 그 위치에서 HOT 체인을 따라가 최종 라이브 튜플을 찾는다.

HOT: 인덱스는 그대로, 체인만 이어진다 — 인덱스 엔트리는 여전히 (0,1)을 가리키고, 읽는 쪽이 블록 안에서 체인을 따라가 최신 버전을 찾는다.
HOT 제약 사항
  • 가장 중요한 조건은 변경된 레코드가 기존 레코드와 동일한 테이블 블록에 위치해야 한다는 점이다.
  • 이 조건을 만족하지 못하면 HOT은 적용되지 않고 DELETE + INSERT로 동작한다.
  • 여러 블록에 걸친 체인도 기술적으로는 가능하지만, 조회 시 여러 블록을 탐색해야 하므로 동일 블록 내로 제한한다.
  • 업데이트가 잦은 테이블이라면 HOT이 동작할 수 있도록 fillfactor를 조정해 블록 내 여유 공간을 확보해두는 것이 중요하다.

HOT 동작 원리

CTID
  • 인덱스와 테이블 사이의 연결고리를 뜻한다.
  • 블록 번호와 슬롯 번호 형태로 구성되며, 인덱스에는 이 CTID와 키 값이 저장된다.

패턴 1: INSERT 직후 UPDATE

  • 레코드 입력 직후 업데이트가 연속으로 발생하고 블록에 여유 공간이 있으면 HOT이 동작한다.
  • 인덱스는 최초 레코드 위치를 그대로 유지하고, 테이블 내부에서 HOT 체인을 따라 최신 레코드를 찾는다.
테스트 데이터 추가 
postgres=# create table ht1 (c1 integer, amt integer);
postgres=# alter table ht1 add constraint ht1_pk primary key (c1);
postgres=# insert into ht1 values(1, 1);
CTID 확인 
-- 삽입한 레코드의 CTID는 블록 0번 + 슬롯 1번으로 구성됨
postgres=# select ctid, c1, amt from ht1 where c1 = 1;
 ctid  | c1 | amt
-------+----+-----
 (0,1) |  1 |   1

-- 인덱스에 저장된 내용 확인
postgres=# select ctid, data from bt_page_items('ht1_pk', 1);
 ctid  |          data
-------+-------------------------
 (0,1) | 01 00 00 00 00 00 00 00

-- 힙 페이지 확인
postgres=# select t_ctid, lp, lp_off, t_xmin, t_xmax, t_data from heap_page_items(get_raw_page('ht1', 0));
 t_ctid | lp | lp_off | t_xmin  | t_xmax |       t_data
--------+----+--------+---------+--------+--------------------
 (0,1)  |  1 |   8160 | 4960979 |      0 | \x0100000001000000
업데이트 후 HOT 동작 확인 인덱스는 그대로 
-- 업데이트 수행
postgres=# update ht1 set amt = amt + 1 where c1 = 1;

-- CTID가 (0,2)로 변경되었음
postgres=# select ctid, c1, amt from ht1 where c1 = 1;
 ctid  | c1 | amt
-------+----+-----
 (0,2) |  1 |   2
(1 row)

-- 인덱스는 여전히 (0,1)을 가리키는 중
postgres=# select ctid, data from bt_page_items('ht1_pk', 1);
 ctid  |          data
-------+-------------------------
 (0,1) | 01 00 00 00 00 00 00 00
(1 row)

-- 1번 슬롯의 t_ctid가 (0,2)를 가리키며 체인이 이어졌다
postgres=# select t_ctid, lp, lp_off, t_xmin, t_xmax, t_data from heap_page_items(get_raw_page('ht1', 0));
 t_ctid | lp | lp_off | t_xmin  | t_xmax  |       t_data
--------+----+--------+---------+---------+--------------------
 (0,2)  |  1 |   8160 | 4960979 | 4960980 | \x0100000001000000
 (0,2)  |  2 |   8128 | 4960980 |       0 | \x0100000002000000
(2 rows)

1번 슬롯의 t_ctid가 자기 자신이 아닌 (0,2)를 가리킨다. 이것이 HOT 체인의 실체다. 인덱스는 (0,1)을 가리킨 채 갱신되지 않았고, 조회하는 쪽이 블록 안에서 (0,1) → (0,2)를 따라간다.

패턴 2: 블록이 꽉 찬 뒤의 UPDATE

  • PostgreSQL은 이 스키마 기준으로 하나의 블록에 약 220건 정도의 레코드를 저장할 수 있다.
  • 아래 예제는 300건을 넣어 블록이 넘치도록 만든 것이다.
HOT 실패 
-- 테이블 초기화
postgres=# truncate ht1;

-- 데이터 300건 추가, 0번째 블록의 저장공간을 모두 사용함
postgres=# insert into ht1 select i, i from generate_series(1, 300) i;

-- 첫번째 레코드 업데이트 수행
postgres=# update ht1 set amt = amt + 1 where c1 = 1;

-- UPDATE 이후 새로 생성된 레코드는 1번째 블록에 저장된 모습
postgres=# select ctid, c1, amt from ht1 where c1 = 1;
  ctid  | c1 | amt
--------+----+-----
 (1,75) |  1 |   2

-- 인덱스 상태 확인
-- 기존 (0,1)은 dead 상태이고, (1,75)를 가리키는 엔트리가 새로 추가되었다
postgres=# select ctid, data, dead from bt_page_items('ht1_pk', 1);
  ctid   |          data           | dead
---------+-------------------------+------
 (0,1)   | 01 00 00 00 00 00 00 00 | t
 (1,75)  | 01 00 00 00 00 00 00 00 | f

블록 0에 여유가 없어 새 버전이 블록 1로 갔고, 그 순간 HOT은 성립하지 않는다. 인덱스에 엔트리가 하나 추가됐고 기존 엔트리는 dead = t로 남았다. 같은 UPDATE인데 블록 여유 유무만으로 결과가 갈린 것이 이 두 실험의 요점이다.

fillfactor와 HOT 업데이트 최적화

  • 테이블이나 인덱스 블록에 데이터를 어느 정도까지 채울지 지정하는 옵션이다.
  • 기본값은 테이블 100%, 인덱스 90%다.
  • 기본값을 쓰면 테이블 블록에 향후 업데이트를 위한 여유 공간이 전혀 없는 상태가 된다.
  • 저장 효율은 높아지지만 이후 업데이트가 HOT으로 처리되지 않는 문제가 생긴다.
  • 테이블의 업데이트 유형과 빈도에 따라 적절한 값을 설정하는 것이 중요하다.
운영 환경에서의 설정 기준
  • 프로젝트 초기에는 테이블별 업데이트 패턴이나 빈도를 정확히 알 수 없다.
  • 이런 경우 가능성이 있는 테이블에 대해 90% ~ 95% 정도로 설정하는 것이 일반적이다.
  • 운영 단계에서는 pg_stat_all_tables로 테이블별 업데이트 패턴을 확인할 수 있다.
테이블별 업데이트 패턴 확인
  • n_tup_upd — 업데이트된 레코드 수
  • n_tup_hot_upd — HOT 방식으로 업데이트된 레코드 수
  • n_tup_newpage_upd — non-HOT 방식으로 업데이트된 레코드 수
postgres=# select relname, n_tup_upd, n_tup_hot_upd, n_tup_newpage_upd
from pg_stat_all_tables where relname='ht1';
 relname | n_tup_upd | n_tup_hot_upd | n_tup_newpage_upd
---------+-----------+---------------+-------------------
 ht1     |         2 |             1 |                 1
(1 row)

앞의 두 실험 결과가 그대로 찍혔다. 총 2번의 업데이트 중 1번은 HOT, 1번은 새 페이지로 갔다. 이 비율이 곧 fillfactor를 조정할지 판단하는 지표다. n_tup_newpage_upd가 크면 여유 공간이 부족하다는 뜻이다.

fillfactor 설정 
-- fillfactor 90%로 설정
postgres=# alter table ht1 set (fillfactor=90);

-- fillfactor 설정 확인
postgres=# select relname, reloptions from pg_class where relname='ht1';
 relname |   reloptions
---------+-----------------
 ht1     | {fillfactor=90}
기존 블록에 적용하려면 VACUUM FULL
  • fillfactor를 바꿔도 기존에 있던 블록에는 적용되지 않는다.
  • 새로운 블록에 반영하려면 VACUUM FULL이 필요하다.
!

VACUUM FULL 뒤에는 VACUUM ANALYZE를 잊지 않는다

9-2에서 확인했듯 VACUUM FULL은 VM을 남기지 않는다. fillfactor 적용을 위해 돌렸다가 Index Only Scan을 잃는 일이 없도록, 한 세트로 묶어 실행한다. 온라인으로 처리해야 한다면 pg_repack 같은 확장이 대안이 된다.

fillfactor 설정에 따른 장단점
  • 테이블에 생성된 인덱스가 많을수록 HOT 방식의 업데이트는 큰 이점을 준다.
  • 인덱스가 10개이고 대부분의 업데이트가 인덱스와 무관한 필드에서 발생한다고 가정하면 다음과 같다.
방식UPDATE 1회당 기록결과

HOT테이블 1건만. 인덱스는 그대로WAL과 디스크 I/O 감소, 응답 속도 개선

HOT 방식은 WAL의 양과 디스크 I/O를 줄일 뿐 아니라 쿼리 응답 속도 개선에도 효과적이다. 9-4의 클릭 카운터처럼 인덱스와 무관한 컬럼을 반복해서 갱신하는 테이블이 fillfactor 조정의 1순위 후보다.

정리

  • HOT은 인덱스 컬럼이 안 바뀌었고 같은 블록에 자리가 있을 때만 성립한다. 두 조건 다 필요하다.
  • 성립하면 인덱스 엔트리가 늘지 않고 블록 안 t_ctid 체인으로만 이어진다.
  • fillfactor 기본 100은 여유 공간을 0으로 만든다. 갱신이 잦은 테이블은 90~95로 낮춘다.
  • 판단 지표는 n_tup_hot_upd vs n_tup_newpage_upd 비율이다.
  • fillfactor 변경은 기존 블록에 소급되지 않는다. VACUUM FULL(+ ANALYZE) 또는 pg_repack이 필요하다.
