7-2

데이터베이스 모니터링

누적값은 정보가 아니다. 델타와 초당 값으로 바꾸는 순간부터 지표가 된다.

핵심 pg_stat_database의 모든 카운터는 인스턴스 기동 이후의 누적값이다. 두 시점을 빼서 주기당 증가량으로 바꿔야 비로소 의미가 생긴다.

데이터베이스 모니터링

  • PostgreSQL은 Top-Down 방식의 모니터링을 적용하기 어렵다. 세션 레벨에서 제공되는 성능 데이터가 충분하지 않기 때문이다.
  • 아직 세션 단위의 성능 지표는 제공하지 않지만, DB 전체의 일량 확인은 가능하므로 여러 정보를 얻을 수 있다.

pg_stat_database 뷰를 활용한 성능 모니터링

  • DB 레벨의 성능 정보를 제공하는 뷰다.
  • 모니터링 관점에서는 누적값보다 모니터링 주기 내 증가량(델타값)과 이를 초 단위로 환산한 초당 처리량이 더 의미 있다.
  • 자체 모니터링 시스템을 구축할 때는 이 델타값과 초당 값을 쓰는 편이 좋다.
컬럼의미이 값이 튀면
numbackends현재 이 DB에 접속 중인 백엔드 프로세스 수커넥션 풀 설정이나 누수를 본다
xact_commit커밋 횟수커밋은 트랜잭션 보장을 위한 필수 요소지만, 지나치게 빈번한 커밋은 성능에 악영향을 준다
blks_read디스크에서 읽은 블록 수인덱스가 없는 테이블을 풀 스캔할 때 급격히 증가한다
blks_hit공유 버퍼에서 읽은 블록 수비정상적으로 높다면 비효율적인 쿼리가 돌고 있을 가능성이 높다
active_time쿼리 수행 시간DB가 실제로 일한 시간의 총량
stats_resetpg_stat_reset()으로 초기화된 시간누적값의 기준점. 이 값이 언제인지 모르면 위 숫자들은 해석할 수 없다
i

“공유 버퍼 히트가 높으면 좋은 것 아닌가” 보강

비율로 보면 그렇지만, 절대량으로 보면 다르다. blks_hit이 크다는 것은 그만큼 많은 블록을 “만졌다”는 뜻이고, 메모리 읽기도 CPU를 쓴다. 인덱스 없이 캐시된 테이블을 반복 풀스캔하는 쿼리는 디스크 I/O 없이도 CPU를 태운다. 이 관점은 7-4의 shared_blks_hit 상위 쿼리부터 튜닝하라는 조언과 7-5의 client backend / normal 비중 해석으로 그대로 이어진다.

i

델타 계산을 SQL 한 줄로 보강

모니터링 도구가 없다면 stats_reset 이후 경과 시간으로 나눠 평균 초당 값을 구할 수 있다. 정확한 주기별 델타는 아니지만 기준선을 잡는 데는 충분하다.

select datname,
       xact_commit,
       round(xact_commit / extract(epoch from now() - stats_reset)) as commit_per_sec,
       round(blks_read  / extract(epoch from now() - stats_reset)) as read_blk_per_sec
from   pg_stat_database
where  datname is not null and stats_reset is not null;

정리

  • PostgreSQL은 세션 단위 성능 지표가 약해 Top-Down 분석이 어렵다. DB 전체 일량부터 잡는다.
  • pg_stat_database는 누적 카운터다. 델타와 초당 값으로 바꿔서 본다.
  • blks_read는 디스크, blks_hit은 메모리. 둘 다 절대량이 크면 문제 신호다.
  • stats_reset을 확인하지 않으면 나머지 숫자는 해석할 수 없다.
7-3

세션 모니터링

pg_stat_activity 없이는 모니터링을 할 수 없다고 해도 과언이 아니다.

핵심 이 뷰 하나에 누가(usename/client_addr) 무엇을(query) 언제부터(xact_start/query_start) 왜 못 하고 있는지(wait_event)가 전부 들어 있다.

세션 모니터링

  • DB 성능 모니터링에서 가장 핵심적인 요소가 세션 모니터링이다.
  • 접속 중인 세션, 쿼리 수행 정보 등 다양한 내용을 확인할 수 있다.
  • pg_stat_activity 뷰로 세션 단위 모니터링을 수행한다.

pg_stat_activity 뷰를 이용한 세션 모니터링

  • 세션 레벨의 성능 정보를 제공하는 대표적인 뷰다.
  • 성능 모니터링 관점에서 이 뷰 없이는 모니터링이 불가능하다고 할 만큼 필수적이다.
컬럼쓰임
datname데이터베이스 이름. 대부분의 stat 정보는 인스턴스 단위로 수집되어 어느 DB에서 조회해도 값이 같으므로, 이 컬럼으로 DB를 식별한다
pid백엔드 프로세스의 OS PID. OS 레벨에서 세션을 추적할 때 유용하다
usename접속한 유저 이름. 유저별 접속 통계를 낼 때 쓴다
application_name앱 이름. JDBC 기반 접속 여부를 식별하는 데 유용하다
client_addr클라이언트 IP. WAS 서버별 접속 통계를 볼 때 쓴다
xact_start트랜잭션 시작 시간. 트랜잭션 응답 시간을 파악하는 매우 중요한 지표
query_start쿼리 시작 시간. 쿼리 응답 시간을 측정하는 핵심 컬럼
wait_event_type대기 이벤트 유형. 병목 발생 위치를 대략적으로 파악한다
wait_event구체적인 대기 이벤트
state세션 상태. active, idle, idle in transaction 등
backend_xmin쿼리 수행 시점의 XMIN 값
query_id쿼리 ID. compute_query_id를 on으로 설정해야 값이 채워진다
query현재 수행 중인 SQL 문장. 실시간 모니터링에 반드시 필요하다
!

이 뷰에서 가장 먼저 찾아야 할 두 가지

첫째는 state = 'idle in transaction'이면서 xact_start가 오래된 세션이다. 이 세션 하나가 CIC를 무한정 대기시키고, 데이터베이스 전체의 Vacuum을 막는다. 둘째는 backend_xmin이 가장 작은 세션이다. 이 값이 곧 Vacuum이 넘어설 수 없는 경계선이다.

오래된 트랜잭션 찾기
select pid, usename, state,
       now() - xact_start  as xact_age,
       now() - query_start as query_age,
       backend_xmin, left(query, 60) as query
from   pg_stat_activity
where  state <> 'idle' and xact_start is not null
order  by xact_start;
extract(epoch from ...)

타임스탬프 형식을 초 단위로 변환하는 함수다. 위와 같은 경과 시간 계산에서 반복적으로 쓰인다.

pg_blocking_pids 함수

현재 세션을 블로킹하고 있는 세션의 PID를 알려준다.

i

블로킹 관계를 한 번에 펼치기 보강

2-2에서 본 blocked_pid / blocking_query 형태의 출력은 이 함수로 만든다. pg_locks를 직접 조인하는 것보다 훨씬 간단하다.

select a.pid           as blocked_pid,
       a.wait_event_type || ':' || a.wait_event as waiting_on,
       left(a.query, 50) as blocked_query,
       b.pid           as blocking_pid,
       b.state         as blocking_state,
       left(b.query, 50) as blocking_query
from   pg_stat_activity a
join   lateral unnest(pg_blocking_pids(a.pid)) as bp(pid) on true
join   pg_stat_activity b on b.pid = bp.pid
where  cardinality(pg_blocking_pids(a.pid)) > 0;

정리

  • pg_stat_activity 하나로 접속 주체 / 수행 쿼리 / 경과 시간 / 대기 원인을 모두 본다.
  • state와 xact_start로 idle in transaction 장기 세션을 잡는 것이 첫 번째 일이다.
  • backend_xmin은 Vacuum의 삭제 경계선과 직결된다.
  • 블로킹 관계는 pg_blocking_pids()로 펼치는 것이 가장 간단하다.
7-4

SQL 모니터링

느린 쿼리 한 개보다 빠른 쿼리 백만 개가 시스템을 더 자주 무너뜨린다.

핵심 log_min_duration_statement는 한 번이 느린 쿼리를, pg_stat_statements는 합쳐서 느린 쿼리를 잡는다. 둘은 겹치지 않는다.

SQL 모니터링

  • DB 성능을 개선하는 활동은 OS 레벨, 인스턴스 레벨 등 매우 다양하다.
  • 하지만 가장 직접적인 효과를 주는 것은 SQL 튜닝이다.
  • 1회 수행 시 응답 시간이 느린 쿼리, 반복 수행으로 시스템 자원을 과도하게 쓰는 쿼리 등이 대상이다.

1회 수행 시 응답시간이 느린 쿼리 모니터링

  • log_min_duration_statement 값보다 오래 실행된 쿼리는 자동으로 로그 파일에 기록된다.
  • 1000으로 설정하면 1초 이상 수행된 쿼리가 기록된다.
  • 바인드 방식으로 실행된 쿼리는 바인드 변수에 입력된 실제 값도 함께 기록된다.
  • 주의할 점은 정상적으로 처리된 쿼리만 로그에 남는다는 것이다.
슬로우 쿼리 확인 방법

MySQL처럼 별도의 슬로우 쿼리 파일을 제공하지 않으므로, 일반 로그 파일에서 duration 키워드로 검색해야 한다.

-- 1초 이상 걸린 쿼리를 로그 파일에 기록
postgres=# SET log_min_duration_statement = 1000;

-- 5초 동안 대기
postgres=# SELECT pg_sleep(5);
terminal 
root@dff5953eda06:/var/lib/postgresql/data/log# cat postgresql-2025-11-07_143835.log
# ...
2025-11-07 14:39:03.759 UTC [41] STATEMENT:  select sleep(5);
2025-11-07 14:39:11.640 UTC [41] LOG:  duration: 5006.742 ms  statement: select pg_sleep(5);
!

“정상 처리된 쿼리만 남는다”가 뜻하는 것

log_min_duration_statement는 쿼리가 끝났을 때 소요 시간을 판단해 기록한다. 그래서 취소되거나 타임아웃으로 죽은 쿼리, 지금 이 순간 몇 시간째 돌고 있는 쿼리는 이 로그에 없다. 지금 도는 것은 7-3의 pg_stat_activity로, 끝난 것은 이 로그로 본다.

런타임 실행계획 확인: auto_explain 활용

  • explain (analyze, buffers)로 쿼리 실행 시의 실행 계획과 일량을 직접 분석할 수 있다.
  • 그런데 쿼리를 다시 실행하면 매우 빠르게 끝나는 경우가 있다. 이럴 때는 로그에 기록된 시점의 실행 계획과 현재의 실행 계획을 비교해서, 응답 시간 차이가 실행 계획 변경 때문인지 디스크 I/O 때문인지 파악해야 한다.
  • auto_explain 확장을 쓰면 일정 시간 이상 수행된 쿼리의 실제 실행계획이 로그에 자동으로 기록된다.
auto_explain 설정

배치 환경에서는 60초, 온라인 환경에서는 10초 정도로 설정하고 점차 조정하면 된다.

postgresql.conf 
shared_preload_libraries = 'pg_stat_statements, auto_explain'
auto_explain.log_min_duration = 1s # 테스트를 위해서 1초로 설정
auto_explain.log_analyze = on
auto_explain.log_buffers = on
!

log_analyze = on은 공짜가 아니다

auto_explain.log_analyze를 켜면 모든 쿼리에 실행 계측이 붙는다(로그에 남는 것만이 아니다). 짧은 쿼리가 초당 수천 번 도는 OLTP에서는 이 오버헤드가 무시하기 어렵다. auto_explain.log_timing = off로 노드별 타이밍만 꺼도 부담이 크게 줄어든다. 운영에 넣기 전에 pg_test_timing으로 이 서버의 타이밍 비용을 먼저 재보는 것이 좋다.

테스트하기

반복 수행으로 과부하를 주는 쿼리 모니터링

  • 보통 튜닝은 슬로우 쿼리부터 시작한다.
  • 하지만 응답 속도는 빠르지만 매우 자주 수행되는 쿼리가 오히려 더 큰 부하를 유발하는 경우가 많다.
  • 예를 들어 0.1초 걸리는 풀 스캔 쿼리는 인덱스를 만들면 0.0001초 이내로 개선할 수 있다.
  • 실제로 디스크 I/O 사용률 개선에는 개별 슬로우 쿼리보다 빈번하게 수행되는 쿼리의 최적화가 더 효과적인 경우가 많다.
pg_stat_statements 설정하기
postgresql.conf 
pg_stat_statements.max = 10000
pg_stat_statements.track = all
track_activity_query_size = 64kb
쿼리 기본 정보 컬럼
  • userid — 쿼리를 실행한 유저
  • dbid — 쿼리가 실행된 DB ID
  • queryid — 정규화된 쿼리의 해시값
  • query — 정규화된 SQL 문장. 입력값은 변수로 치환된다
-- 기존 정보 초기화
postgres=# select pg_stat_statements_reset();

-- 쿼리 실행
postgres=# select pg_sleep(1) from generate_series(1, 1) i;

-- 쿼리 실행
postgres=# select pg_sleep(2) from generate_series(2, 2) i;

-- 쿼리 실행 후 정보 조회
postgres=# select userid, dbid, queryid, query from pg_stat_statements order by stats_since limit 3;
 userid | dbid |       queryid       |                       query
--------+------+---------------------+----------------------------------------------------
     10 |    5 | 5226144649890563814 | select pg_stat_statements_reset()
     10 |    5 | 9077879155684233118 | select pg_sleep($1) from generate_series($2, $3) i
     10 |    5 | 4463986769292944571 | select * from pg_stat_statements

두 번 실행한 서로 다른 pg_sleep 쿼리가 하나의 queryid로 합쳐진 것이 정규화다. 상수가 $1, $2, $3으로 치환되어 “같은 모양의 쿼리”를 하나로 집계할 수 있게 된다.

파싱 수행 정보 컬럼
  • pg_stat_statements.track_planning을 켜면 파싱 관련 정보를 확인할 수 있다.
  • 일반적으로 OLTP 서비스는 비활성화 상태로 운영해도 큰 문제가 없다.
  • 다만 SQL이 길고 복잡한 경우에는 파싱 정보를 수집해 분석하는 것도 좋다.
응답 시간 정보 컬럼

total_exec_time으로 DB 내 전체 실행 시간 비중이 높은 Top 쿼리를 쉽게 식별할 수 있다.

postgres=# select dbid, queryid, query, total_exec_time from pg_stat_statements order by total_exec_time desc limit 1;

------+---------------------+----------------------------------------------------+-----------------
    5 | 9077879155684233118 | select pg_sleep($1) from generate_series($2, $3) i |     3010.985278
i

total_exec_time과 mean_exec_time을 같이 본다 보강

total_exec_time = calls × mean_exec_time이다. 같은 total이라도 calls가 크고 mean이 작은 쿼리는 인덱스 추가로 극적으로 개선되고, calls가 작고 mean이 큰 쿼리는 실행계획을 뜯어봐야 한다. 이 항목 첫머리의 “0.1초 × 백만 번” 이야기가 정확히 전자다. 두 컬럼을 나란히 놓고 정렬해야 어느 쪽인지 갈린다.

I/O 정보 컬럼

쿼리 수행 시 발생하는 I/O 통계를 제공한다. 공유 버퍼 관련, Temporary 테이블 관련, 로컬 메모리 부족으로 인한 Temp 파일 I/O를 확인할 수 있다.

접두사대상튀었을 때의 해석
shared_blks_hit공유 버퍼 읽기메모리 읽기도 CPU를 쓴다. CPU 사용률을 낮추려면 이 값이 높은 쿼리부터 튜닝하는 것이 효과적이다
shared_blks_read디스크 읽기인덱스가 없거나 비효율적인 인덱스를 쓰는 경우가 많다. 인덱스 추가나 쿼리 튜닝으로 개선한다
local_Temporary 테이블local은 Temp 테이블에 대한 I/O를 의미한다는 점에 유의한다
temp_work_mem 부족으로 생긴 Temp 파일work_mem이 작아 정렬/해시 도중 메모리가 부족할 때 발생한다
!

local_과 temp_는 이름이 헷갈리게 지어졌다

직관과 반대라서 실무에서 자주 뒤집혀 읽힌다. local_은 Temp 테이블(로컬 버퍼, temp_buffers가 담당), temp_는 정렬/해시가 흘러넘쳐 만든 임시 파일(work_mem이 담당)이다. 처방도 완전히 다르다. 앞은 temp_buffers, 뒤는 work_mem이다.

정리

  • 느린 쿼리는 log_min_duration_statement, 자주 도는 쿼리는 pg_stat_statements로 잡는다.
  • 로그는 끝난 쿼리만 남긴다. 지금 도는 것은 pg_stat_activity에 있다.
  • auto_explain은 실제 실행계획을 남겨주지만 log_analyze의 계측 비용을 감수해야 한다.
  • total_exec_time은 calls와 mean_exec_time으로 분해해서 봐야 처방이 갈린다.
  • local_ = Temp 테이블(temp_buffers), temp_ = 정렬 임시 파일(work_mem).
7-5

I/O 모니터링

대용량 스캔이 공유 버퍼를 쓸어버리지 못하게 막는 장치가 링 버퍼다. pg_stat_io는 그 장치가 언제 작동했는지를 보여준다.

핵심 pg_stat_io의 context(normal / bulkread / bulkwrite / vacuum)는 곧 버퍼 액세스 전략이다. 어느 칸의 숫자가 큰지가 그대로 진단이 된다.

I/O 모니터링

  • I/O 모니터링은 성능 개선이나 성능 저하 시점 분석을 위한 필수 작업이다.
  • PostgreSQL 16부터 pg_stat_io 뷰를 제공해 시스템 레벨에서 I/O 성능을 모니터링할 수 있게 되었다.

버퍼 액세스 전략과 링 버퍼

버퍼 액세스 전략
  • I/O 유형에 따라 서로 다른 방식으로 버퍼에 접근하는 방법을 말한다.
  • 전략을 나누는 이유는 대용량 테이블을 읽거나 쓸 때 공유 버퍼 영역을 보호하기 위해서다.
  • 공유 버퍼가 10GB인 환경에서 10GB짜리 테이블을 풀스캔하면 버퍼가 바로 바닥난다.
버퍼 액세스 전략 유형
전략사용 시점링 버퍼크기
BAS_NORMAL일반적인 버퍼 I/O사용 안 함—
BAS_BULKREAD대용량 테이블 읽기사용256 KB (32 블록)
BAS_BULKWRITE대용량 파일의 COPY, CTAS사용16 MB (2048 블록)
BAS_VACUUMVACUUM 작업사용2 MB (256 블록)
대용량 테이블 판단 기준
  • 테이블의 블록 수가 전체 공유 버퍼 크기의 1/4을 초과하면 대용량 테이블로 인식하고 BULKREAD 전략을 적용한다.
  • 반대로 1/4 이내의 테이블은 Seq Scan을 수행해도 전체를 공유 버퍼에 적재할 수 있다.
링 버퍼란
  • 원형으로 동작하는 버퍼 배열이다.
  • 일정 크기의 버퍼 영역을 순환하며 사용해서, 대용량 스캔이 전체 공유 버퍼를 밀어내는 현상을 방지한다.
  • 링 버퍼는 테이블 단위로 하나씩 할당되는 것이 아니라 스캔이 시작될 때마다 하나씩 할당된다.
↑

VACUUM 링 버퍼는 이제 조절할 수 있다 최신 반영

PostgreSQL 16부터 vacuum_buffer_usage_limit 파라미터가 생겼다. 기본값은 위 표와 같은 2MB이고, 128kB~16GB 범위에서 조절할 수 있으며 0으로 두면 링 버퍼 없이 공유 버퍼를 마음껏 쓴다(단 shared_buffers의 1/8을 넘으면 조용히 잘린다). 개별 명령에서는 VACUUM (BUFFER_USAGE_LIMIT '256MB') tbl;처럼 덮어쓸 수 있다. 서비스가 멈춘 정기 점검 시간에 대용량 테이블 Vacuum을 빨리 끝내야 한다면 이 값을 크게 잡는 것이 가장 직접적인 수단이다.

pg_stat_io 뷰를 이용한 시스템 레벨 I/O 분석

  • 이 뷰로 시스템 레벨의 I/O 성능을 체계적으로 모니터링하고 병목 지점을 분석할 수 있다.
  • 프로세스를 여러 유형으로 분류한 뒤, 유형별로 오브젝트 유형과 버퍼 액세스 전략에 따른 성능 지표를 제공한다.
뷰의 구조
  • 오브젝트 유형은 relation과 temp relation 두 가지다.
    • relation — 테이블 및 인덱스
    • temp relation — Temporary 테이블 및 인덱스
  • context는 버퍼 액세스 전략과 동일한 normal, bulkread, bulkwrite, vacuum 네 가지다.
  • _time으로 끝나는 컬럼은 track_io_timing이 on이어야 채워진다.
  • 모든 시간 단위는 1/1000초(밀리초) 기준이다.
시간 정보 활성화 시 고려사항
  • I/O 성능을 정확히 분석하려면 I/O 처리 시간 정보가 반드시 필요하다.
  • 시스템 상황에 따라 처리 시간이 달라진다면, 실행계획 변경보다 시스템 레벨에서 발생한 다른 영향을 의심해야 한다.
  • 처리 시간 정보는 병목 분석에 매우 유용한 단서이며 track_io_timing이 on이어야 한다.
  • 다만 오버헤드를 유발할 수 있으므로 pg_test_timing 유틸리티로 사전에 테스트가 필요하다.

패턴별 해석

backend_type × context 조합을 읽는 법이다. 이 표가 pg_stat_io 활용의 전부라고 해도 좋다.

어느 칸이 높은가원인조치
client backend × normal 버퍼 캐시의 25%보다 작은 테이블에 대한 반복 Seq Scan. 블록 전체를 공유 버퍼에 올릴 수 있으므로 링 버퍼를 쓰지 않는다 동일 테이블 반복 Seq Scan이 확인되면 적절한 인덱스를 생성한다
client backend × bulkread 버퍼 캐시의 25%보다 큰 대용량 테이블에 대한 반복 Seq Scan. 자동으로 bulkread 전략과 링 버퍼가 적용된다 불필요한 Seq Scan인지 판단하고 인덱스 생성이나 쿼리 튜닝을 한다
client backend × bulkwrite 대용량 파일의 COPY 및 CTAS 작업 DB 이행/적재 과정의 정상 작업이므로 별도 조치는 불필요하다. 다만 작업 스케줄이 서비스 시간과 겹치지 않는지만 확인한다
client backend × temp relation temp_buffers로 설정된 로컬 메모리 공간이 부족하다 필요 이상의 데이터를 Temp 테이블로 처리하는지 점검하고, 실제로 필요하다면 temp_buffers를 늘린다
background worker × bulkread 일정 크기 이상의 테이블에 병렬 프로세스가 Seq Scan을 수행했다 PostgreSQL이 테이블 크기에 따라 자동으로 병렬 쿼리를 실행하면서 background worker가 동작한 것이다
autovacuum worker × vacuum Vacuum 대상 테이블이 많거나 동시 수행 프로세스가 많다 중요 시간대에 서비스 응답 시간에 영향을 준다고 판단되면 일시적으로 관련 파라미터를 끄고 프로세스를 정리한다

pg_stat_all_tables, pg_statio_all_tables를 이용한 테이블 I/O 분석

  • pg_stat_all_tables — 액세스 패턴별 수행 횟수, 명령어별 수행 건수 등 다양한 정보를 제공한다.
  • pg_statio_all_tables — 테이블 및 인덱스에 대한 I/O 블록 수를 제공한다.
  • Seq Scan으로 빈번하게 접근하는 테이블을 추출할 때는, 수행 횟수뿐 아니라 레코드 수 등 여러 지표를 같이 봐야 영향도를 제대로 판단할 수 있다.
i

횟수만 보면 작은 코드 테이블에 속는다 보강

seq_scan이 아무리 커도 10행짜리 코드 테이블이면 문제가 아니다. 봐야 할 것은 seq_tup_read / seq_scan, 즉 한 번 스캔할 때 몇 행을 읽는가다. 이 값이 크면서 seq_scan도 큰 테이블이 진짜 인덱스가 필요한 테이블이다.

select relname, seq_scan, seq_tup_read,
       seq_tup_read / nullif(seq_scan, 0) as tup_per_scan,
       idx_scan
from   pg_stat_all_tables
where  seq_scan > 0
order  by seq_tup_read desc
limit  10;

pg_stat_wal 뷰를 이용한 WAL I/O 모니터링

  • 성능 모니터링에서 WAL I/O 모니터링은 매우 중요하다.
  • WAL 파일은 보통 별도 볼륨으로 구성하므로 OS 모니터링으로도 현황을 볼 수 있다.
  • 하지만 성능 분석을 위해서는 초당 발생하는 WAL 크기와 Full Page Write 발생 횟수 정보가 필요하다.
  • _time으로 끝나는 컬럼은 track_wal_io_timing이 on이어야 한다.

정리

  • 버퍼 액세스 전략은 대용량 스캔으로부터 공유 버퍼를 지키는 장치다. NORMAL을 뺀 셋이 링 버퍼를 쓴다.
  • 대용량 기준선은 공유 버퍼의 1/4. 이 선을 넘으면 자동으로 bulkread로 넘어간다.

  • 테이블 Seq Scan 판단은 횟수가 아니라 seq_tup_read / seq_scan으로.

복제 모니터링

지연은 시간과 용량 두 축으로 봐야 한다. 그리고 어느 단계에서 밀렸는지까지.

핵심 sent → write → flush → replay 네 개의 LSN이 곧 복제의 파이프라인이다. 인접한 두 LSN의 간격이 어느 구간에서 막혔는지를 말해준다.

복제 모니터링

  • 복제는 일반적으로 비동기 방식을 사용한다.
  • 대량의 트랜잭션이 발생하면 복제 지연이 생긴다.
  • 지연이 발생하면 복제 지연된 WAL 용량과 복제 지연 시간을 함께 분석해야 한다.
  • 각 단계별 지연 정도도 확인이 필요하며 pg_stat_replication 뷰로 확인한다.

pg_stat_replication을 이용한 복제 지연 분석

  • 복제 지연 시간은 _lag로 끝나는 3개 컬럼으로 확인한다.
  • 각 단계별 LSN 값의 차이로 복제 지연 용량도 확인할 수 있다.
  • 차이 계산은 pg_wal_lsn_diff() 함수를 쓴다.

어느 화살표가 벌어졌는지가 원인을 가리킨다 — current↔sent는 네트워크/발송, write↔flush는 리플리카 디스크 쓰기, flush↔replay는 복구 적용 지연이다. 마지막 구간이 벌어졌다면 리플리카에서 도는 긴 쿼리와의 충돌을 의심한다.

시간과 용량을 한 화면에 보강

select application_name, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn))   as sent_gap,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn,  flush_lsn))             as flush_gap,
       pg_size_pretty(pg_wal_lsn_diff(flush_lsn, replay_lsn))            as replay_gap,
       write_lag, flush_lag, replay_lag
from   pg_stat_replication;

_lag 컬럼(시간)만 보면 트래픽이 없을 때 0으로 보여 안심하게 되고, LSN 차이(용량)만 보면 얼마나 오래 밀렸는지 알 수 없다. 두 축을 같이 봐야 한다. 그리고 pg_stat_replication은 마스터에서만 조회할 수 있다는 점도 기억해둔다. 리플리카 쪽 시선이 필요하면 pg_stat_wal_receiver를 본다.

정리

  • 지연은 _lag(시간)와 LSN 차이(용량) 두 축으로 함께 본다.
  • sent / write / flush / replay 중 어느 구간이 벌어졌는지가 원인을 좁혀준다.
  • replay만 밀린다면 리플리카에서 도는 긴 쿼리와의 충돌을 먼저 의심한다.
  • 이 뷰는 마스터 전용이다. 리플리카에서는 pg_stat_wal_receiver를 쓴다.
7-7

작업 진행 상황 모니터링

“이거 언제 끝나요”에 답할 수 있게 해주는 뷰들. phase 컬럼 하나가 절반이다.

핵심 진행률은 blks_done / blks_total이지만, 정말 봐야 할 것은 phase다. 어느 단계에서 멈춰 있는가가 남은 시간을 결정한다.

작업 진행 상황 모니터링

  • PostgreSQL은 progress 뷰들로 인덱스 생성, Vacuum 등의 진행 상황을 실시간 모니터링할 수 있게 해준다.
  • 대용량 작업의 완료 시점을 예측하거나 작업이 정상적으로 수행되는지 확인하는 데 유용하다.

인덱스 진행 상황 모니터링

  • pg_stat_progress_create_index 뷰로 인덱스 생성 작업의 현재 상태를 실시간 확인한다.
  • phase 컬럼으로 단계별 진행률을 볼 수 있다.
    • scanning table
    • sorting live tuples
    • loading tuples in tree

blocks_done이 멈춰 있고 lockers_total/lockers_done/current_locker_pid에 값이 있다면, 인덱스 생성이 느린 것이 아니라 기다리는 중이다. current_locker_pid가 가리키는 세션이 2-2에서 말한 “대상 테이블과 무관한 장기 트랜잭션”의 정체다. 그 PID를 7-3의 pg_stat_activity에 넣어 확인한다.

Vacuum 진행 상황 모니터링

  • 수동 및 Autovacuum 작업의 진행 상황은 pg_stat_progress_vacuum 뷰로 실시간 확인한다.
  • 대용량 테이블의 Vacuum은 인덱스 정리 단계에서 특히 오래 걸린다.
  • 진행률뿐 아니라 maintenance_work_mem 값이 적절한지도 판단할 수 있다.
  • 실무에서 매우 유용한 모니터링 도구다.

index_vacuum_count가 maintenance_work_mem을 말해준다 보강

Vacuum은 죽은 튜플의 위치를 메모리에 모았다가 가득 차면 인덱스를 한 바퀴 돌고 비운 뒤 다시 모은다. 그래서 index_vacuum_count가 1보다 크다는 것은 메모리가 부족해 인덱스를 여러 번 훑었다는 뜻이고, 이것이 대용량 테이블 Vacuum이 느려지는 대표적인 이유다. maintenance_work_mem(기본 64MB)을 키우면 이 횟수가 줄어든다. PostgreSQL 17부터는 Vacuum의 메모리가 1GB로 묶여 있던 제약도 사라져 큰 값을 주는 것이 실제로 의미가 있어졌다. max_dead_tuple_bytes와 dead_tuple_bytes를 나란히 보면 지금 얼마나 찼는지 알 수 있다.

  • 그래서 제한된 시간 내에 완료 가능한지 판단하기 위해 현재 수행 단계와 전체 진행률을 모니터링하는 것이 중요하다.

  • pg_stat_progress_copy 뷰로 확인한다.
  • \copy와 COPY 사이에 큰 차이는 없다.
  • 다만 bytes_total(처리 대상 파일의 전체 크기)은 COPY에서만 확인할 수 있다.

bytes_total이 COPY에서만 채워지는 이유는 6-1에서 본 차이 그대로다. COPY는 서버가 서버의 파일을 열기 때문에 크기를 알 수 있지만, \copy는 클라이언트가 스트림으로 흘려보내므로 서버가 전체 크기를 알 방법이 없다. 참고로 tuples_skipped는 6-1의 on_error ignore로 건너뛴 레코드 수를 보여준다.

정리

  • 인덱스 / Vacuum / Vacuum Full(cluster) / COPY 각각에 progress 뷰가 있다.
  • 진행률보다 phase가 먼저다. 어느 단계에 있는지가 남은 시간을 결정한다.
  • CIC가 안 끝나면 current_locker_pid를 본다. 느린 게 아니라 기다리는 중일 수 있다.
  • index_vacuum_count > 1은 maintenance_work_mem 부족 신호다.
