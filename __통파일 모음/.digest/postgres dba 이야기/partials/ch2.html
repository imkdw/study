인덱스

운영 중인 테이블에 인덱스를 거는 유일한 방법은 CONCURRENTLY다. 그 대가는 느린 속도와 INVALID 인덱스다.

핵심 CIC는 락 경합을 피하는 대신 테이블을 두 번 스캔하고, 실패하면 쓸모없는 INVALID 인덱스를 남긴다. 생성 후 상태 확인은 선택이 아니라 절차다.

PG의 인덱스

PostgreSQL은 B*Tree 인덱스 외에도 여러 종류의 인덱스를 제공한다. BRIN, GIN, GiST 등이 대표적이다.

인덱스 생성

기본 문법 
create (unique) index <index_name> on <schema_name>.<table_name> (column_name);

B*Tree 인덱스는 세 가지 방식으로 만들 수 있다.

방식목적주의
create index 기본적인 인덱스 생성 —
... include(column) 커버링 인덱스로 테이블 랜덤 액세스 제거 include 절의 컬럼은 인덱스에 저장되지만 검색 조건으로는 쓰이지 않는다
... where (condition) 조건에 맞는 레코드만 담는 partial index 데이터 분포 차이가 큰 컬럼이나 복잡한 조건이 붙는 쿼리에 효과적

CIC(Create Index Concurrently) 옵션

운영 중인 데이터베이스에서 쿼리 성능 개선을 위해 인덱스를 추가하는 일은 흔하다. 그런데 일반적인 CREATE INDEX는 다른 트랜잭션과 락이 충돌해 대기가 발생한다. 대부분의 DBMS가 트랜잭션 수행과 무관하게 인덱스를 만드는 “온라인” 기능을 제공하는데, PostgreSQL에서는 CONCURRENTLY 옵션이 그 역할을 한다.

단점 1. 일반 방식보다 느리다
  • CIC를 쓰면 테이블을 두 번 스캔한다.
  • 스캔 중 진행 중인 트랜잭션이 있으면 그 트랜잭션이 끝날 때까지 작업을 멈췄다가 재개한다.
  • 그래서 트랜잭션이 빈번한 테이블에서는 일반 방식보다 인덱스 생성이 확연히 느려진다.
  • 다만 락 경합을 회피한다는 이점에 비하면 상대적으로 사소한 단점이다.
테이블을 두 번 스캔하는 이유
  1. 1차 스캔 — 정렬해서 트리에 넣는다

    테이블 레코드를 읽어 정렬하고 인덱스 트리 구조에 입력한다. 여기까지는 CIC 없이 만들어도 동일하다.

  2. 그 사이 다른 트랜잭션이 계속 돈다

    CIC는 인덱스 생성 도중에도 DML을 허용하므로, 1차 스캔에 반영되지 않은 레코드가 생긴다.

  3. 2차 스캔 — 누락분을 따라잡는다

    1차 스캔 이후 발생해 반영되지 않은 레코드를 인덱스에 반영한다.

단점 2. INVALID 상태의 인덱스가 남을 수 있다
  • CIC로 시작하면 인덱스 메타 정보가 시스템 카탈로그에 먼저 등록되는데, 이때 상태는 INVALID다.
  • 생성이 끝나면 VALID로 바뀐다.
  • 중간에 작업이 취소되거나, 유니크 인덱스를 만들 때 중복 값 때문에 오류가 나면 INVALID로 남는다.
  • INVALID 인덱스는 쿼리에 쓰이지 못하면서 디스크만 차지하고, DML 작업도 반영되지 않는다.
  • 그래서 CIC로 인덱스를 만들었다면 생성 후 상태 확인이 반드시 필요하다.

INVALID 인덱스를 찾는 쿼리 보강

CIC 작업 뒤에 돌려볼 정형 쿼리 하나는 만들어두는 편이 낫다. pg_index.indisvalid가 false인 인덱스는 DROP INDEX (CONCURRENTLY)로 지우고 다시 만드는 것 외에 방법이 없다.

select i.indexrelid::regclass as index_name,
       i.indrelid::regclass  as table_name,
       pg_size_pretty(pg_relation_size(i.indexrelid)) as size
from   pg_index i
where  not i.indisvalid;
단점 3. 인덱스 생성이 지연될 수 있다
  • CIC는 테이블 스캔이 두 번 발생하는데, 2차 스캔 이전에 시작된 쿼리가 아직 수행 중이면 인덱스 생성을 완료하지 못하고 그 쿼리의 종료를 기다린다.
  • 그 쿼리가 인덱스 대상 테이블을 건드리지 않더라도 CIC 세션은 락을 대기한다는 점이 중요하다.
  • CIC를 쓸 때는 세션과 인덱스 진행 상황을 함께 모니터링할 필요가 있다.
  • 한 테이블에 대한 CIC 작업은 동시에 하나만 가능하다.
장시간 실행되는 쿼리로 인한 락 대기 재현 
-- 다른 세션에서 사전에 블로킹 쿼리 실행
postgres=# select pg_sleep(100000000); -- 계속 실행 중..

-- 인덱스 생성
postgres=# create index concurrently t1_n1 on svc.t1(c1); -- 계속 진행 중

-- 락 대기 정보 확인

blocking_pid   | 6014

CIC의 진짜 적은 idle in transaction

여기서 확인한 대기는 Lock:virtualxid로 관찰된다. 실무에서 CIC가 몇 시간씩 끝나지 않는 원인 대부분은 대상 테이블과 무관한, 열어놓고 커밋하지 않은 세션이다. 8-2 대기이벤트의 virtualxid 항목과 함께 보면 된다.

인덱스 리빌드

  • VACUUM FULL을 수행하면 인덱스 블로팅 문제도 함께 해결된다.
  • 그러나 VACUUM FULL은 온라인 기능을 지원하지 않아 주기적으로 돌릴 수 없다면 인덱스 리빌드가 필요하다.
  • 리빌드는 조건부 수행이 가능하고, CONCURRENTLY 옵션으로 온라인 처리도 가능하다.
리빌드 시 CIC의 동작 차이
  • 내부적으로 작업용 인덱스인 _ccnew 인덱스가 만들어진다.
  • 기존 인덱스는 그대로 두고 별도의 작업용 인덱스에 리빌드한 뒤, 완료되면 교체하는 방식이다.
  • 리빌드 도중 비정상 종료되면 이 _ccnew 인덱스가 INVALID 상태로 남는다.

인덱스 이름 변경

-- 인덱스 이름 변경
postgres=# alter index svc.t1_n1 rename to t1_idx1;

postgres=# \d svc.t1;

    "t1_idx1" btree (c1)
인덱스 구성 컬럼 변경 후 중복 인덱스 삭제 시 주의사항
  • 운영 환경에서 인덱스를 삭제할 때는 반드시 CONCURRENTLY 옵션을 사용한다.
  • 기존 인덱스를 참조 중인 쿼리가 수행되고 있으면 삭제를 요청한 세션이 락을 대기하기 때문이다.
  • CIC로 지운 다음 남은 인덱스의 이름을 바꾸는 순서가 좋다.
이 순서로 
-- 인덱스 구성 컬럼이 `c1`과 `c2`인 모습
-- 이 때 c1 컬럼의 경우 (c1, c2) 인덱스에 포함되므로 삭제 대상이 됨
postgres=# \d svc.t1;

postgres=# alter index svc.t1_n1_new rename to t1_n1;
postgres=# \d svc.t1;

    "t1_n1" btree (c1, c2)

정리

  • 운영 중 인덱스 생성/삭제/리빌드는 전부 CONCURRENTLY가 기본이다. 대가는 두 번의 테이블 스캔이다.
  • CIC 실패는 조용히 INVALID 인덱스를 남긴다. 쿼리에 쓰이지도 않으면서 디스크와 DML 비용만 먹는다.
  • CIC 세션은 대상 테이블과 무관한 장기 트랜잭션에도 막힌다. 작업 전에 오래된 세션을 정리한다.
  • include는 커버링용이라 검색 조건에 쓰이지 않고, where는 partial index를 만든다.

파티션

선언적 문법은 10부터지만, 안은 여전히 상속받은 별개의 테이블들이다. 이 사실이 인덱스 동작 전부를 설명한다.

핵심 부모 테이블은 껍데기고 데이터는 자식 테이블에 있다. 그래서 부모에는 CIC를 걸 수 없고, ONLY + 자식별 CIC + ATTACH라는 우회로가 필요하다.

파티션

  • 대용량 테이블을 효율적으로 관리하기 위한 필수 기능이다.
  • 9.6까지는 구현 방식이 매우 복잡했으나 10부터 크게 편해졌다.

PG 파티션의 특징

  • 10부터 선언적 파티션 생성 문법을 지원하지만, 내부적으로는 기존 방식을 그대로 쓴다.
  • 기존 방식은 부모 테이블을 만든 뒤 그 구조를 상속해 자식 테이블을 만드는 구조다.
  • 물리적인 관점에서 부모 테이블과 자식 테이블은 서로 별개의 테이블이다.

선언적 문법이라도 실체는 상속이다 — 부모는 파티션 키와 메타 정보만 들고 있고, 실제 블록은 자식 테이블 파일에 있다.

PG 파티션 유형

  • RANGE, LIST, HASH 세 가지를 지원하고, 이들을 조합한 서브 파티션도 가능하다.
  • 다만 실제로 서브 파티션을 적용하는 경우는 매우 드물다.

RANGE 파티션

  • 이력 테이블 관리에 큰 장점을 준다.
  • 단일 테이블에 모든 이력을 쌓으면 관리 이슈가 생긴다.
  • 오래된 데이터를 DELETE로 지우면 대량의 WAL이 발생해 부하가 커진다.
  • 테이블 단위 백업이나 Vacuum 수행에도 많은 시간이 든다.
  • RANGE 파티션을 적용하면 파티션 단위 작업이 가능해져 관리 효율이 크게 오른다.
부모 테이블 생성 
postgres@localhost:postgres> create table svc.t1_r (
 c1 integer not null,
 log_date varchar(8) not null,
 dummy varchar(10)
)
partition by range(log_date);


postgres@localhost:postgres> \d svc.t1_r;
+----------+-----------------------+-----------+
| Column   | Type                  | Modifiers |
|----------+-----------------------+-----------|
| c1       | integer               |  not null |
| log_date | character varying(8)  |  not null |
| dummy    | character varying(10) |           |
+----------+-----------------------+-----------+
Partition key: RANGE (log_date)

부모 테이블 생성 시 파티션 유형을 정의하며, \d로 파티션 테이블임을 확인할 수 있다. 최초에는 자식 테이블이 없어 파티션 개수가 0개다.

자식 테이블 생성
  • RANGE 파티션의 자식은 FROM(시작), TO(다음 파티션 시작값)으로 범위를 지정한다.
  • TO에 지정한 값은 해당 파티션에 포함되지 않는다. 경계는 항상 [FROM, TO)다.
  • 이미 운영 중인 테이블을 파티셔닝한다면 FROM(MINVALUE)로 오래된 데이터를 하나의 파티션에 묶을 수 있다.
-- 제일 작은 값부터 20210101까지 파티션 생성
postgres@localhost:postgres> create table svc.t1_r_p2020 partition of svc.t1_r for values from(MINVALUE) to ('20210101');

-- 20210101부터 20220101까지 파티션 생성
postgres@localhost:postgres> create table svc.t1_r_p2021 partition of svc.t1_r for values from('20210101') to ('20220101');

-- 20220101부터 20230101까지 파티션 생성
postgres@localhost:postgres> create table svc.t1_r_p2022 partition of svc.t1_r for values from('20220101') to ('20230101');

-- 파티션 정보 확인
postgres@localhost:postgres> \d+ svc.t1_r;
Partition key: RANGE (log_date)
Partitions: svc.t1_r_p2020 FOR VALUES FROM (MINVALUE) TO ('20210101')
            svc.t1_r_p2021 FOR VALUES FROM ('20210101') TO ('20220101')
            svc.t1_r_p2022 FOR VALUES FROM ('20220101') TO ('20230101')

LIST 파티션

  • 코드 값을 기준으로 테이블을 분할하는 방식이다.
  • 국가별, 지점별처럼 대분류 항목으로 나눌 때 유용하다.
  • IN 절로 각 자식 테이블에 들어갈 코드 값을 명시한다.
  • 새 코드 값이 반영되지 않아 오류가 나는 일이 있으니 DEFAULT 파티션을 함께 만들어두는 편이 좋다.
파티션 생성 예제 
-- A, B 코드 값을 가지는 데이터는 t1_l_p1 파티션에 저장
postgres@localhost:postgres> create table svc.t1_l_p1 partition of svc.t1_l for values in ('A', 'B');

-- C 코드 값을 가지는 데이터는 t1_l_p2 파티션에 저장
postgres@localhost:postgres> create table svc.t1_l_p2 partition of svc.t1_l for values in ('C');

-- 나머지 코드 값을 가지는 데이터는 t1_l_pd 파티션에 저장
postgres@localhost:postgres> create table svc.t1_l_pd partition of svc.t1_l default;
등록되지 않은 값은 DEFAULT 파티션으로 간다 
-- D 코드 값을 가지는 데이터는 t1_l_pd 파티션에 저장
postgres@localhost:postgres> insert into svc.t1_l values(1, 'D', 'dummy');

-- DEFAULT 파티션에 저장된 데이터 확인
postgres@localhost:postgres> select * from svc.t1_l_pd;
+----+---------+-------+
| c1 | divcode | dummy |
|----+---------+-------|
| 1  | D       | dummy |
+----+---------+-------+
DEFAULT 파티션에 들어간 값으로 새 자식 테이블을 만들 때의 오류
실패 
postgres@localhost:postgres> create table svc.t1_l_p3 partition of svc.t1_l for values in ('D');
updated partition constraint for default partition "t1_l_pd" would be violated by some row

DEFAULT 파티션에 이미 'D' 값이 들어 있어, 새 파티션을 붙이면 DEFAULT 파티션의 제약 조건이 깨지기 때문이다. 오라클은 파티션을 쪼개는 스플릿 기능을 제공하지만 PostgreSQL은 지원하지 않으므로, 다음 순서로 직접 처리한다.

  1. DEFAULT 파티션에서 스플릿 대상 데이터 추출
  2. DEFAULT 파티션에서 스플릿 대상 데이터 삭제
  3. 신규 자식 테이블 생성
  4. 추출한 데이터를 신규 자식 테이블에 입력
!

18에서도 여전히 스플릿은 없다 최신 반영

ALTER TABLE ... SPLIT PARTITION / MERGE PARTITIONS는 여러 차례 제안됐지만 PostgreSQL 17과 18 릴리스 노트 어디에도 들어가지 않았다. 위의 수작업 절차는 최신 버전에서도 그대로 유효하다.

HASH 파티션

  • 동시에 대량의 입력이 발생하면 핫 블록 때문에 병목이 생길 수 있다.
  • 이 병목을 줄이려면 입력 위치를 분산시키는 것이 효과적이고, 그때 쓰는 방법이 해시 파티션이다.
Hot Block
  • 동시에 많은 트랜잭션이 동일한 데이터 블록에 접근하려 할 때 발생하는 경합 현상이다.
  • 여러 세션이 같은 블록의 데이터를 동시에 생성/수정/삭제할 때 나타난다.
  • 해당 블록의 락을 얻으려고 대기하면서 병목이 발생한다.
mod 연산으로 자식 테이블에 분산 저장하기

해시 키는 hash(seqno) % modulus = remainder 방식으로 동작한다. 아래 예제는 나머지가 0, 1, 2, 3인 데이터를 각각의 파티션에 저장하도록 구성한 것이다.

-- 해시 파티션 생성
postgres@localhost:postgres> create table svc.t1_h (
 c1 integer not null,
 seqno integer not null,
 dummy varchar(10))
 partition by hash(seqno);

-- modulus 4, remainder 0: hash(seqno) % 4 = 0인 데이터
postgres@localhost:postgres> create table svc.t1_h_p1 partition of svc.t1_h for values with (modulus 4, remainder 0);

-- modulus 4, remainder 1: hash(seqno) % 4 = 1인 데이터
postgres@localhost:postgres> create table svc.t1_h_p2 partition of svc.t1_h for values with (modulus 4, remainder 1);

-- modulus 4, remainder 2: hash(seqno) % 4 = 2인 데이터
postgres@localhost:postgres> create table svc.t1_h_p3 partition of svc.t1_h for values with (modulus 4, remainder 2);

-- modulus 4, remainder 3: hash(seqno) % 4 = 3인 데이터
postgres@localhost:postgres> create table svc.t1_h_p4 partition of svc.t1_h for values with (modulus 4, remainder 3);

파티션 인덱스

파티션 인덱스를 만들 때는 반드시 파티션 컬럼을 포함해야 한다. 포함하지 않으면 에러가 발생한다.

!

정확히는 “유니크 인덱스에 한해서”다 원문 교정

파티션 컬럼을 반드시 포함해야 하는 것은 PRIMARY KEY / UNIQUE 인덱스다. 파티션 테이블의 유니크 제약은 각 자식 테이블 안에서만 보장되므로, 파티션 키가 인덱스에 포함되어야 전체 유일성이 성립하기 때문이다. 일반 (non-unique) 인덱스는 파티션 컬럼 없이도 만들 수 있다. 아래 예제의 t1_r_pk가 (c1, log_date)인 이유가 이것이고, t1_r_n1은 (log_date) 단독으로도 생성된다.

자동 인덱스 생성 방식
  • 11부터 지원한다. 부모 테이블에 인덱스를 만들면 자식 테이블에도 동일한 인덱스가 자동으로 생성된다.
  • 이전 버전에서는 자식 테이블을 추가할 때마다 인덱스를 수동으로 만들어야 했던 불편을 개선한 것이다.
파티션 인덱스 생성 
postgres@localhost:postgres> alter table svc.t1_r add constraint t1_r_pk primary key (c1, log_date);
postgres@localhost:postgres> create index t1_r_n1 on svc.t1_r(log_date);
부모에 만들면 자식에도 생긴다

    "t1_r_n1" btree (log_date)

수동 인덱스 생성 방식
  • 자식 테이블마다 개별적으로 인덱스를 만드는 방식이다.
  • 자동 생성 기능이 추가된 뒤로는 잘 쓰지 않지만, 특정 상황에서는 여전히 유용하다.
  • 특정 파티션에만 선별적으로 인덱스가 필요한 경우가 그렇다. 자동으로 생성된 인덱스는 자식 테이블 단위로 제거할 수 없기 때문이다.
특정 자식에만 인덱스 두기

postgres@localhost:postgres> drop index svc.t1_r_n1;

-- 자식 테이블에 인덱스 추가
postgres@localhost:postgres> create index t1_r_p2022_n1 on svc.t1_r_p2022 (log_date);

            svc.t1_r_p2021 FOR VALUES FROM ('20210101') TO ('20220101')

postgres@localhost:postgres> \d svc.t1_r_p2022;

    "t1_r_p2022_n1" btree (log_date) -- 이거

인덱스 ONLY 옵션

  • 파티션 테이블에 ONLY 옵션으로 인덱스를 만들면 부모 테이블에만 INVALID 상태의 인덱스가 생성된다.
  • 자식 테이블에는 인덱스가 생기지 않으며, 이 때문에 ONLY로 만든 인덱스는 그대로는 사용할 수 없다.
-- ONLY 옵션을 적용해서 인덱스 생성
postgres@localhost:postgres> create index t1_r_n1 on only svc.t1_r(log_date);

-- 인덱스가 INVALID 상태로 생성된 모습
postgres@localhost:postgres> \d svc.t1_r;
Indexes:
    "t1_r_pk" PRIMARY KEY, btree (c1, log_date)
    "t1_r_n1" btree (log_date) INVALID
Partition key: RANGE (log_date)
Number of partitions 3: (Use \d+ to list them.)

-- 자식 테이블에는 인덱스가 만들어지지 않았음
postgres@localhost:postgres> \d svc.t1_r_p2022;
Indexes:
    "t1_r_p2022_pkey" PRIMARY KEY, btree (c1, log_date)
Partition of: svc.t1_r FOR VALUES FROM ('20220101') TO ('20230101')
그런데 왜 이런 옵션이 필요한가

운영 중인 파티션 테이블에 인덱스를 추가해야 하는 상황을 생각해보자. PostgreSQL은 부모(파티션) 테이블에 대한 CREATE INDEX CONCURRENTLY를 지원하지 않는다. 그래서 ONLY 옵션이 우회로가 된다.

  1. ONLY 옵션으로 부모 테이블에 인덱스 생성

    INVALID 상태의 “껍데기” 인덱스가 만들어진다. 이 시점에는 아직 아무 락도 오래 잡지 않는다.

  2. 자식 테이블 각각에 CIC로 인덱스 생성

    자식은 일반 테이블이므로 CONCURRENTLY가 통한다. 서비스 영향 없이 하나씩 만든다.

  3. 자식 인덱스를 부모 인덱스에 ATTACH

    모든 자식이 붙는 순간 부모 인덱스의 INVALID 표시가 사라진다.

자식 테이블에 각각 온라인으로 인덱스 생성 
postgres@localhost:postgres> create index concurrently t1_r_p2020_n1 on svc.t1_r_p2020(log_date);
postgres@localhost:postgres> create index concurrently t1_r_p2021_n1 on svc.t1_r_p2021(log_date);
postgres@localhost:postgres> create index concurrently t1_r_p2022_n1 on svc.t1_r_p2022(log_date);
ATTACH 하면 INVALID가 사라진다 완성 
-- ATTACH 진행
postgres@localhost:postgres> alter index svc.t1_r_n1 attach partition svc.t1_r_p2020_n1;
postgres@localhost:postgres> alter index svc.t1_r_n1 attach partition svc.t1_r_p2021_n1;
postgres@localhost:postgres> alter index svc.t1_r_n1 attach partition svc.t1_r_p2022_n1;

-- 모든 자식 테이블의 인덱스가 ATTACH된 이후에 부모 테이블의 인덱스 상태가 VALID로 변경된 모습
postgres@localhost:postgres> \d+ svc.t1_r;
Indexes:
    "t1_r_pk" PRIMARY KEY, btree (c1, log_date)
    "t1_r_n1" btree (log_date) -- INVALID 사라짐
Partition key: RANGE (log_date)
Partitions: svc.t1_r_p2020 FOR VALUES FROM (MINVALUE) TO ('20210101')
            svc.t1_r_p2021 FOR VALUES FROM ('20210101') TO ('20220101')
            svc.t1_r_p2022 FOR VALUES FROM ('20220101') TO ('20230101')

파티션 관리 명령어

자식 테이블 추가

create table ... partition of 구문으로 추가한다.

자식 테이블 제거

일반 테이블과 동일하게 DROP TABLE을 사용한다.

-- 테이블 제거
postgres@localhost:postgres> drop table svc.t1_r_p2020;

-- 자식 테이블이 없어진 모습
postgres@localhost:postgres> \d+ svc.t1_r;
Indexes:
    "t1_r_pk" PRIMARY KEY, btree (c1, log_date)
    "t1_r_n1" btree (log_date)
Partition key: RANGE (log_date)
Partitions: svc.t1_r_p2021 FOR VALUES FROM ('20210101') TO ('20220101')
            svc.t1_r_p2022 FOR VALUES FROM ('20220101') TO ('20230101')
자식 테이블 분리(DETACH)
  • 제거하는 대신 부모와 분리해 보관할 수 있다.
  • DETACH 명령으로 분리하며, CONCURRENTLY도 지원하므로 온라인 작업이 가능하다.
파티션 구성 상태 확인 
postgres@localhost:postgres> select pg_partition_tree('svc.t1_r');
+------------------------------------------+
| pg_partition_tree                        |
| ---------------------------------------- |
| ('svc.t1_r', None, 'f', '0')             |
| ('svc.t1_r_p2021', 'svc.t1_r', 't', '1') |
| ('svc.t1_r_p2022', 'svc.t1_r', 't', '1') |
+------------------------------------------+
자식 테이블 분리하기 
-- 테이블 분리하기
postgres@localhost:postgres> alter table svc.t1_r detach partition svc.t1_r_p2021 concurrently;

-- 테이블이 분리된 모습
postgres@localhost:postgres> select pg_partition_tree('svc.t1_r');
+------------------------------------------+
| pg_partition_tree                        |
| ---------------------------------------- |
| ('svc.t1_r', None, 'f', '0')             |
| ('svc.t1_r_p2022', 'svc.t1_r', 't', '1') |
+------------------------------------------+
파티션 ATTACH
  • 일반 테이블을 자식 테이블로 빠르게 전환할 수 있고, 이때 두 가지 검사가 자동으로 수행된다.
  • 자동 인덱스 생성 — 자식 테이블에 이미 같은 인덱스가 있으면 이 단계는 생략된다.
  • 체크 제약 조건 검사 — 자식 테이블이 파티션 범위를 충족하는지 확인하는 과정으로, 이미 체크 제약이 있으면 건너뛴다.
  • 따라서 ATTACH를 빠르게 끝내려면 인덱스와 제약조건을 미리 만들어두면 된다.
테스트용 데이터 생성 
-- 테이블 생성
postgres@localhost:postgres> create table svc.t_log (
 c1 integer not null,
 log_date varchar(8) not null,
 dummy varchar(10));

-- PK 제약조건 추가
postgres@localhost:postgres> alter table svc.t_log add constraint t_log_pk primary key (c1, log_date);

-- 인덱스 생성
postgres@localhost:postgres> create index t1_log_n1 on svc.t_log(log_date);

-- 데이터 생성
postgres@localhost:postgres> insert into svc.t_log select c1, c2, 'dummy' from (select row_number() over () as c1, to_char(c2, 'YYYYMMDD')
  c2 from (select c2, generate_series(1, 1000) as per_day from generate_series('2020-01-01'::DATE, '2025-03-23'::DATE, '1 day') as c2) as
 t) as t;

-- RANGE 파티션 테이블 생성
postgres@localhost:postgres> create table svc.t_log_r (
 c1 integer not null,
 log_date varchar(8) not null,
 dummy varchar(10))
 partition by range(log_date);
빠른 작업을 위한 사전 작업 이걸 해두면 ATTACH가 즉시 끝난다 
-- 원본 테이블과 동일한 제약조건 생성
postgres@localhost:postgres> alter table svc.t_log_r add constraint t_log_r_pk primary key (c1, log_date);

-- 원본 테이블과 동일한 인덱스 생성
postgres@localhost:postgres> create index t_log_r_n1 on svc.t_log_r(log_date);

-- 파티션을 위한 제약조건 생성
postgres@localhost:postgres> alter table svc.t_log add constraint t_log_chk1 check (log_date < '20260101');
파티션 ATTACH 
-- 파티션 ATTACH
postgres@localhost:postgres> alter table svc.t_log_r attach partition svc.t_log for values from (MINVALUE) to ('20260101');

-- 파티션 ATTACH 후 모습
postgres@localhost:postgres> \d svc.t_log_r;

    "t_log_r_n1" btree (log_date)

정리

  • 선언적 문법 뒤에는 상속이 있다. 부모는 껍데기, 자식이 실제 테이블이다.
  • RANGE의 경계는 [FROM, TO)다. TO 값은 다음 파티션에 들어간다.
  • LIST에는 DEFAULT 파티션을 항상 같이 만든다. 대신 나중에 쪼갤 때 수작업이 필요하다.
  • 부모 테이블에 CIC는 불가능하다. ONLY → 자식별 CIC → ATTACH가 온라인으로 파티션 인덱스를 추가하는 유일한 길이다.
  • ATTACH 전에 인덱스와 CHECK 제약을 미리 만들어두면 검증 단계를 건너뛰어 즉시 끝난다.
