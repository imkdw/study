5-1

물리 복제

WAL을 그대로 흘려보낸다. 커밋을 기다리지 않기 때문에 지연이 짧고, 대신 클러스터 통째로만 복제된다.

핵심 물리 복제는 읽기 부하 분산 수단이지 가용성 확보 수단이 아니다. 마스터의 가용성은 별도의 이중화가 담당한다.

물리 복제

  • PostgreSQL은 물리 복제와 논리 복제 기능을 제공한다.
  • 주요 업무 환경은 대부분 물리 복제로 읽기 작업을 분산한다.
  • 주된 목적은 읽기 부하 분산이며, DR에서도 활용할 수 있다.
  • 다만 물리 복제만으로는 마스터 서버의 가용성을 확보할 수 없다. 디스크 이중화나 소프트웨어 이중화 솔루션이 별도로 필요하다.

물리 복제 구성하기

리플리카 서버 준비
  • 마스터 서버와 동일한 스펙의 서버를 준비한다.
  • 마스터-리플리카 간 방화벽을 열고 동일한 버전의 PostgreSQL을 설치한다.
복제 전용 유저 생성
  • 슈퍼유저(postgres)로도 복제가 가능하지만, 복제 전용 유저를 따로 만드는 것이 권장사항이다.
  • 복제 전용 유저에게는 REPLICATION 권한을 부여한다.
-- 복제 전용 유저 생성
postgres@localhost:postgres> create user dbarep with password 'reppass' replication;

-- 복제 전용 유저 권한 확인
postgres@localhost:postgres> \du dbarep

| rolname | rolsuper | rolinherit | rolcreaterole | rolcreatedb | rolcanlogin | rolreplication |
|---------+----------+------------+---------------+-------------+-------------+----------------|
| dbarep  | False    | True       | False         | False       | True        | True           |
+---------+----------+------------+---------------+-------------+-------------+----------------+
마스터 서버의 pg_hba.conf 설정
  • 물리 복제는 DB 클러스터 전체를 복제한다. 그래서 DATABASE 항목에는 특정 DB가 아닌 replication을 적는다.
  • USER에는 위에서 만든 복제용 유저를, ADDRESS에는 리플리카 서버의 IP를 적는다.
pg_hba.conf 
# TYPE  DATABASE        USER            ADDRESS                 METHOD
host    replication     dbarep          192.168.117.3/32        trust
!

운영 환경에서 trust는 그대로 쓰지 않는다

trust는 비밀번호를 아예 검사하지 않는다. 해당 IP에서 오는 연결은 무조건 통과시킨다는 뜻이다. 실습에서는 편하지만 운영에서는 scram-sha-256으로 두는 것이 맞다.

pg_basebackup을 이용한 복제
  • 리플리카 서버에 postgres 유저로 접속해 pg_basebackup으로 디스크 복제를 수행한다.
  • 수행 전에 DB 클러스터, WAL, 테이블스페이스용 디스크 볼륨의 소유자를 postgres로 바꾼다.

이 명령줄에서 눈여겨볼 세 개의 옵션 보강

  • -c fast — 즉시 체크포인트를 요청한다. 없으면 다음 정기 체크포인트까지 기다린다.
  • -X stream — 백업이 도는 동안 생성되는 WAL을 별도 연결로 함께 받아둔다. 백업 중 WAL이 지워져 복구가 불가능해지는 상황을 막는다.
  • -R — standby.signal과 primary_conninfo를 자동으로 써준다. 아래 postgresql.auto.conf에 접속 문자열이 들어 있는 이유다.
인스턴스 시작

데이터 백업이 끝나면 리플리카 인스턴스를 기동한다. 이후 pg_is_in_recovery()로 리플리카로 동작 중인지 확인할 수 있다.

물리 복제 아키텍처

WAL 파일(트랜잭션 변경사항을 담고 있는)의 내용을 스트리밍 방식으로 리플리카 서버에 전송하는 복제 방식이다.

WAL은 세 단계를 거쳐 리플리카의 메모리에 도달한다 — 전송(walsender→walreceiver) / 기록(WAL 파일) / 적용(startup recovering). synchronous_commit 레벨은 이 세 지점 중 어디까지 기다릴지를 고르는 것이다.
프로세스위치역할
walsender마스터WAL 데이터를 walreceiver에게 전송한다. walreceiver가 마스터에 접속할 때 postgres 데몬 프로세스가 생성하며, 리플리카 서버당 1개씩 할당된다.
walreceiver리플리카전송받은 WAL 데이터를 리플리카 서버의 WAL 파일에 기록한다.
startup recovering리플리카리플리카의 WAL 파일을 읽어 변경 내용을 공유 버퍼에 적용한다.
PG 물리 복제의 우수성
  • PostgreSQL의 물리 복제는 복제 지연 시간이 매우 짧다는 점에서 우수하다.
  • 트랜잭션 로그를 송/수신하는 프로세스가 별도로 존재하고, 커밋 이전에도 변경된 데이터를 리플리카로 전송한다.
  • MySQL은 커밋된 데이터만 전송하지만 PostgreSQL은 커밋 전에도 보내므로 복제 지연이 최소화된다.
  • 물론 아무리 좋은 아키텍처라도 디스크 I/O와 네트워크가 나쁘면 지연이 생긴다.
  • WAL이 저장되는 디스크는 성능이 좋은 SSD를 쓰고, 마스터-리플리카 간 네트워크 대역폭도 충분히 확보해야 한다.

동기화 모드 유형

비동기 모드(기본값)
  • 트랜잭션 성능 저하는 없으나 복제 지연이 발생할 수 있다.
  • 마스터에서 변경된 내용이 리플리카에 반영될 때까지 기다리지 않는다.
  • 즉 마스터에 변경 사항이 반영되면 즉시 트랜잭션을 완료하므로, 복제 환경에서도 트랜잭션 성능 저하가 없다.
  • 하지만 복제 지연으로 리플리카의 데이터는 일정 시간 뒤처질 수 있다.
  • 실시간 조회가 필요한 업무는 반드시 마스터에서 수행해야 한다.
동기 모드
  • 가용성 향상을 목적으로 소프트웨어 이중화를 적용할 때 고려하는 구성이다.
  • 트랜잭션 성능은 저하되지만 failover 상황에서 트랜잭션이 유실되지 않는다.
  • 다만 리플리카가 다운되면 마스터의 트랜잭션이 대기(hang) 상태에 빠지므로 최소 2대의 리플리카가 필요하다.
  • 마스터에 장애가 나면 리플리카가 마스터로 승격하는 구조다.
  • 즉 트랜잭션 유실을 방지하려면 반드시 동기 모드로 구성해야 한다.

동기 모드 복제 구성 절차

  • 마스터 — 리플리카#1 은 Sync(동기) 모드로 동작한다.
  • 마스터 — 리플리카#2 는 Async(비동기) 모드로 동작하며, 이때 Virtual IP를 사용한다.
  • VIP를 쓰면 마스터 장애로 리플리카#1이 승격하더라도 자동으로 새 마스터에 연결된다.
  • 복제도 자동으로 재개되며 설정 변경이 필요 없다.
마스터의 pg_hba.conf 
# TYPE  DATABASE        USER            ADDRESS                 METHOD

# 리플리카#1
host    replication     dbarep          192.168.147.3/32        trust

# 리플리카#2
host    replication     dbarep          192.168.147.2/32        trust
리플리카 서버의 application_name 등록
  • 리플리카를 동기 모드로 두려면 마스터의 synchronous_standby_names에 리플리카 이름을 등록해야 한다.
  • primary_conninfo의 application_name이나 cluster_name 파라미터로 이름을 정한다.
  • postgresql.auto.conf에 primary_conninfo로 설정하면 인스턴스 재시작이 필요 없으므로, 이 방법으로 설정하고 변경 사항만 reload하면 된다.
리플리카: postgresql.auto.conf 
# postgresql.auto.conf 파일을 수정해서 인스턴스 재시작 없이 적용하기

리플리카 2대 구성이라면 정족수 문법을 쓴다 보강

synchronous_standby_names는 단순 이름 나열 외에 FIRST num_sync (...)(우선순위 방식)와 ANY num_sync (...)(정족수 방식)를 지원한다. 리플리카 2대 중 아무 1대만 응답하면 커밋을 진행하고 싶다면 ANY 1 (replica1, replica2)로 두면 된다. 특정 1대를 고정으로 지정해두면 그 1대가 죽는 순간 마스터가 멈춘다. 노트가 “최소 2대가 필요하다”고 말한 지점이 바로 여기다.

동기화 레벨

  • DB가 I/O 성능을 위해 공유 버퍼를 쓰듯, OS 레벨에서도 OS 캐시를 쓴다.
  • WAL 버퍼의 내용을 파일에 기록할 때도 디스크에 직접 쓰는 것이 아니라 OS 캐시를 거친다.
  • OS 캐시에 기록할 때는 write(), 실제 디스크에 내릴 때는 fsync() 시스템 콜이 사용된다.
  • 동기 모드로 설정한 경우 synchronous_commit 파라미터로 레벨을 지정한다.
레벨어디까지 기다리는가트랜잭션 유실
off마스터의 OS 캐시가능
local마스터의 디스크가능(리플리카 기준)
remote_write리플리카의 OS 캐시가능
on 기본값리플리카의 디스크없음
remote_apply리플리카의 공유 버퍼에 적용까지없음
레벨 설정 팁
  • off, local, remote_write는 리플리카의 디스크에 WAL이 기록되는 것을 보장하지 않으므로 트랜잭션 유실 가능성이 있다.
  • 유실을 방지하려면 기본값인 on 이상으로 설정해야 한다.
  • 리플리카에서도 마스터와 동일한 실시간 조회가 필요하다면 remote_apply로 설정해야 한다.
  • 레벨이 높을수록 리플리카의 응답을 기다리는 시간이 길어지고 복제 지연 시간도 증가한다.
  • 단순히 트랜잭션 유실 방지가 목적이라면 기본값 on만으로 충분하다.

Cascade 복제 구성 절차

  • 마스터가 아닌 리플리카를 통해 또 다른 리플리카로 복제하는 방식이다.
  • 마스터 → 리플리카#1 → 리플리카#2 같은 구성이다.
  • 새 리플리카를 추가할 때 마스터에 부하가 없다는 장점이 있다.
  • 대신 홉이 늘어나므로 복제 지연 시간이 더 길어질 수 있다.
  • DR처럼 어느 정도의 지연을 감수할 수 있는 환경이라면 고려해볼 만하다.

정리

  • 물리 복제는 커밋 이전의 WAL도 흘려보내기 때문에 지연이 짧다. 대신 클러스터 전체가 대상이다.
  • 구성은 REPLICATION 유저 → pg_hba.conf에 replication 등록 → pg_basebackup -R -X stream 순서다.
  • 동기 모드는 유실을 막지만, 지정한 리플리카가 죽으면 마스터가 멈춘다. ANY n (...) 정족수 구성으로 회피한다.
  • synchronous_commit은 “전송/기록/적용” 중 어디까지 기다릴지의 선택이다. 유실 방지는 on, 실시간 조회는 remote_apply.
5-2

논리 복제

WAL을 읽어 DML로 되돌려 보낸다. 그래서 테이블 단위로 고를 수 있고, 버전이 달라도 통한다.

핵심 같은 WAL을 쓰지만 물리 복제는 블록을 그대로, 논리 복제는 SQL로 다시 만들어 보낸다. 이 한 줄의 차이가 유연성과 복잡성을 동시에 만든다.

논리 복제

  • WAL 파일을 사용한다는 점은 물리 복제와 같다.
  • 하지만 논리 복제는 WAL 내부 내용을 분석해 DML 쿼리를 생성해서 전달한다.
  • 이 과정을 Logical Decoding이라 부르며, 이 구조 덕분에 서로 다른 버전 사이에서도 잘 동작한다.
!

용어는 “디코딩”이다 원문 교정

노트에는 Logical Encoding으로 적혀 있으나, 공식 용어는 Logical Decoding이다. 이미 WAL로 인코딩되어 있는 내용을 풀어서 논리적인 변경 집합으로 되돌리는 작업이므로 방향상으로도 디코딩이 맞다. 관련 파라미터(wal_level = logical)와 함수(pg_logical_slot_get_changes) 이름도 이 용어를 따른다.

논리 복제 구성

초기 데이터 구성
postgres=# create schema svc;
postgres=# create table svc.t1 (c1 integer, c2 integer, constraint t1_pk primary key(c1));
postgres=# create table svc.t2 (c1 integer, c2 integer, constraint t2_pk primary key(c1));
postgres=# insert into svc.t1 select i, i from generate_series(1, 10) i;
postgres=# insert into svc.t2 select i, i from generate_series(1, 10) i;
발행자 서버 파라미터 설정 변경
  • 논리 복제 환경을 구성할 때 가장 먼저 할 일은 파라미터 설정이다.
  • wal_level, max_wal_senders 등의 변경이 필요하다.
  • wal_level — WAL 안에 논리 디코딩 정보를 포함해야 하므로 logical로 설정한다.
ALTER SYSTEM SET wal_level = 'logical';
발행자(Publication) 생성
  • 슈퍼유저 권한을 가진 postgres 유저로 진행한다.
  • DB 내 전체 테이블, 특정 스키마 내 테이블 등 다양한 범위로 지정할 수 있다.
-- 생성
postgres=# create publication pub_svc_tb1 for table svc.t1, svc.t2;

-- 발행자 목록 조회
postgres=# select pubname from pg_publication;

-- 발행자 테이블 목록 조회
postgres=# select * from pg_publication_tables;
   pubname   | schemaname | tablename | attnames | rowfilter
-------------+------------+-----------+----------+-----------
 pub_svc_tb1 | svc        | t1        | {c1,c2}  |

논리 복제 아키텍처와 동작 순서

  • 발행자와 구독자를 만들 때 다양한 옵션을 줄 수 있는데, 이 옵션을 정확히 이해해야 제대로 활용할 수 있다.
  • 논리 복제는 물리 복제보다 아키텍처가 복잡하고 slot, worker 같은 새로운 개념이 들어온다.
sequenceDiagram
    participant S as 구독자 서버
    participant AW as apply worker / tablesync worker
    participant L as logical replication launcher
    participant WS as walsender (2종)
    participant P as 발행자 테이블 / WAL

    S->>AW: 1. 구독 생성 → 구독 수만큼 apply worker 기동
    AW->>L: 2. 논리 복제 요청
    L->>WS: 2. walsender 2종 기동 (초기복제용 / 변경전달용)
    P->>WS: 3. 초기 데이터는 COPY, 이후는 WAL 논리 디코딩
    WS->>AW: 3. 진행 상황을 논리 복제 슬롯에 기록하며 전송
    AW->>S: 4. apply worker가 DB에 반영
초기 복제와 변경 전달은 서로 다른 프로세스 쌍이 담당한다 — tablesync worker ↔ 초기 복제용 walsender, apply worker ↔ 변경 전달용 walsender.
1단계
  • 구독자가 생성되면 그 개수만큼 apply worker 프로세스가 기동된다.
  • copy_data 옵션은 구독 시작 시 발행자 테이블의 복제 여부를 결정한다.
    • 기본값은 true로, 처음 구독자가 생성되면 발행자 테이블의 모든 데이터를 초기에 복제한다.
  • 초기 데이터 복제를 담당하는 프로세스를 tablesync worker라고 부른다.
    • 복제 대상 테이블 수와 관계없이 기본 2개까지 기동되며, 복제가 끝나면 자동으로 종료된다.
  • 구독 서버의 max_sync_workers_per_subscription 값을 조정하면 초기 데이터 복제를 더 빠르게 할 수 있다.
i

“최대 2개”는 상한이 아니라 기본값이다 보강

max_sync_workers_per_subscription의 기본값이 2다. 값을 올리면 그만큼 병렬로 초기 복제가 진행된다. 다만 테이블 하나당 sync worker는 하나이고, 이 워커들은 max_logical_replication_workers(기본 4)라는 공통 풀에서 꺼내 쓴다. 그래서 sync worker만 올리고 풀을 그대로 두면 apply worker가 굶는다. 두 값을 함께 올려야 한다.

2단계
  • 논리 복제 요청을 받은 발행자 서버의 logical replication launcher 프로세스는 두 유형의 walsender를 기동한다.
  • 하나는 지속적인 데이터 변경 사항을 전달하기 위한 walsender다.
  • 다른 하나는 초기 데이터를 복제하기 위한 walsender다.
  • 이들은 구독자 서버의 apply worker 및 tablesync worker와 각각 통신한다.
3단계
  • 초기 데이터 복제를 담당하는 walsender는 발행자 테이블을 읽어 COPY 방식으로 전달한다.
    • 이 과정에서 진행 상황을 논리 복제 슬롯에 기록한다.
  • 일반적인 walsender는 WAL 파일을 읽어 논리 디코딩을 수행하고 변경 내용을 구독 서버에 전달한다.
    • 동일하게 진행 상황을 논리 복제 슬롯에 기록한다.
  • pg_replication_slots, pg_stat_replication, pg_stat_activity에서 확인할 수 있다.

pg_replication_slots — 현재 생성된 복제 슬롯과 슬롯 타입을 볼 수 있다. 구독자 1개당 1개의 슬롯이 생기고, 초기 데이터 복제용 임시 슬롯은 복제가 끝나면 자동으로 삭제된다.

  • tablesync worker는 COPY 명령을 수신해 해당 데이터를 DB에 적재한다.

publish 옵션

  • 기본은 INSERT, UPDATE, DELETE, TRUNCATE다.

  • 따라서 구독 서버에도 동일한 자식 테이블이 있어야 한다. 구독 서버가 일반 테이블이라면 이 옵션을 true로 바꾼다.

적용 방법

발행자와 동일하게 생성 시에는 WITH 절, 이후에는 SET을 사용한다.

streaming 옵션
  • 논리 복제의 기본 동작은 트랜잭션이 완료된 뒤 변경 데이터를 논리 디코딩해 구독 서버로 전달하는 구조다.
  • 즉 발행자 대상 테이블에 대량의 트랜잭션이 발생하면 복제 지연이 길어질 수 있다. 이를 개선하려고 나온 것이 스트리밍 옵션이다.
값디코딩 시점구독 서버에서의 처리
off 기본값트랜잭션 커밋 후 한 번에완성된 트랜잭션을 그대로 적용
on트랜잭션 진행 중임시 파일에 쌓아두고, 발행자에서 커밋된 뒤 apply

!

발행자의 커밋이 구독자를 기다리지는 않는다 원문 교정

노트에는 “streaming=on/parallel이면 디코딩 결과를 구독 서버로 전달한 뒤에야 트랜잭션이 완료되므로 트랜잭션 성능이 저하된다”고 적혀 있다. 그러나 공식 문서는 on/parallel에서도 변경분이 “applied only after the transaction is committed on the publisher”라고 서술한다. 즉 커밋이 먼저고 적용이 나중이며, walsender의 디코딩은 백엔드의 커밋 경로와 분리되어 있다. 발행자의 커밋을 실제로 지연시키는 것은 streaming이 아니라 구독자 쪽 synchronous_commit과 synchronous_standby_names 설정이다(바로 아래 항목).

스트리밍이 발행자에 부담을 주는 것은 사실이지만 그 이유는 다르다. 트랜잭션이 도는 동안 디코딩과 전송이 함께 일어나므로 CPU와 네트워크를 더 쓴다. 그래서 “복제 지연은 줄지만 발행자 부하는 는다”는 트레이드오프는 유효하고, 운영 환경에서 off로 두는 관행도 그대로 합리적이다.

on과 parallel의 차이
  • on은 트랜잭션 진행 중 디코딩한 결과를 구독 서버의 임시 파일에 저장한다. 이후 트랜잭션이 끝나면 apply 프로세스가 그 파일을 읽어 반영한다.
  • parallel은 임시 파일 대신 병렬 apply 워커가 곧바로 적용한다.
  • 그래서 on보다 parallel이 복제 성능은 더 우수하다.
↑

parallel은 PostgreSQL 16부터 최신 반영

streaming = parallel과 이를 뒷받침하는 max_parallel_apply_workers_per_subscription(기본값 2)은 16에서 추가됐다. 이 워커들 역시 max_logical_replication_workers 풀을 공유한다. 참고로 parallel 모드에서 워커에 에러가 나면 원격 트랜잭션의 finish LSN이 서버 로그에 남지 않을 수 있는데, 이는 아래 “에러 발생 지점 스킵”에서 LSN을 지정해야 하는 상황과 정면으로 부딪힌다.

synchronous_commit
  • 운영 환경이라면 활성화하지 않는 것이 권장된다.
  • 동기 커밋을 쓰면 대량 트랜잭션 때문에 락 대기가 장기간 걸릴 수 있다.
  • 또한 구독 서버에 장애가 나면 모든 트랜잭션이 행 상태에 빠지는 심각한 문제가 발생한다.
구독자 관련 주요 작업
  • 주로 중단, 재개, 에러 발생 지점 스킵을 수행하게 된다.
  • 중단은 매우 간단하지만, 중단 시점에 복제 지연이 있다면 지연 중인 레코드는 복제되지 않는다.
  • 에러 발생 지점 스킵은 대표적으로 양쪽에 동일한 키 값을 가진 데이터가 존재하는 경우에 필요하다.
  • 이런 오류가 나면 apply worker가 반복적으로 종료/재시작되면서 복제 지연이 발생한다.
  • LSN 값을 입력해 해당 위치를 건너뛰면 바로 해결된다.

양방향 논리 복제

  • PostgreSQL은 현재까지 멀티 마스터 기능을 지원하지 않는다.
  • 오라클 RAC 같은 디스크 공유 방식의 멀티 마스터 구조를 PostgreSQL 아키텍처에 적용하는 것은 매우 어렵다.
양방향 복제 동작 원리
  • 구독 서버에서 발생한 변경도 다시 발행 서버로 전송되는 구조다.
  • 즉 양쪽 서버가 모두 발행자이자 구독자가 된다.
  • 가장 중요한 것은 무한 루프 복제의 위험을 제거하는 것이다.
  • 각 변경 사항이 실제 트랜잭션에 의한 것인지, 복제로 전달된 것인지 구분하면 된다. 이 역할을 origin 옵션이 한다.
1번째 DB에서 발행자 생성 
postgres=# create publication pub_svc_tbl1 for table svc.t1;
2번째 DB에서 발행자 생성 
postgres=# create publication pub_svc_tbl2 for table svc.t1;
1번째 DB에서 구독자 생성 
create subscription sub_svc_tbl2 connection 'host=192.168.147.3 port=5432 dbname=postgres user=postgres password=postgres' publication pub_svc_tbl2 with (origin='none');
2번째 DB에서 구독자 생성 
create subscription sub_svc_tbl2 connection 'host=192.168.147.4 port=5432 dbname=postgres user=lglrep password=reppass' publication pub_svc_tbl2 with (origin='none');
i

origin='none'이 무한 루프를 끊는 방법 보강

origin의 기본값은 any로, 출처를 가리지 않고 모든 변경을 받는다. 양방향 구성에서 이 값을 그대로 두면 A→B로 간 변경이 B→A로 되돌아오고 다시 A→B로 가는 순환이 생긴다. none으로 두면 “origin이 없는”, 즉 복제로 들어온 것이 아닌 변경만 보내달라고 발행자에게 요청하므로 순환이 끊긴다. PostgreSQL 16부터 사용 가능하다.

다만 origin='none'은 루프만 막을 뿐 충돌을 해결해주지는 않는다. 양쪽에서 같은 PK를 동시에 쓰면 여전히 apply worker가 멈춘다. 양방향을 쓴다면 키 공간을 서버별로 나눠두는 설계가 함께 필요하다.

정리

  • 논리 복제는 WAL을 논리 디코딩해 DML로 되돌려 보낸다. 테이블 선택과 버전 간 복제가 가능한 이유다.
  • 구성은 wal_level=logical → publication → 구독 서버에 동일 구조 생성 → subscription 순서다.
  • 워커는 apply worker(변경)와 tablesync worker(초기 복제) 두 종류이며, 모두 max_logical_replication_workers 풀을 공유한다.
  • streaming은 복제 지연 ↓ / 발행자 부하 ↑의 트레이드오프다. 발행자 커밋을 막는 것은 streaming이 아니라 synchronous_commit이다.
  • 양방향은 origin='none'으로 루프만 끊을 수 있다. 충돌은 여전히 설계로 피해야 한다.
5-3

논리/물리 복제를 활용한 전일자 배치 환경 구성

여러 서버에서 필요한 테이블만 모으고, 그 위에 물리 복제를 얹어 매일 자정의 스냅샷을 만든다.

핵심 논리 복제로 필요한 테이블만 모으고, 물리 복제로 시점을 고정한다. 두 복제의 성질을 각각 다르게 쓰는 구성이다.

상황

  • 매일 00시 30분 기준으로 전일 데이터를 활용해 배치 작업을 수행한다고 가정한다.
  • 가장 간단한 방법은 OS가 제공하는 디스크 스냅샷 기능을 쓰는 것이다.
  • 하지만 필요한 테이블이 일부뿐이고 복잡한 JOIN 쿼리가 필요하다면 적절하지 않다.

방법

  • 이런 상황에서는 논리 복제와 물리 복제를 혼합한 구성을 고려할 수 있다.
  • 각 서버에서 필요한 테이블만 선별해 하나의 통합 논리 복제 서버로 복제한다.
  • 이 통합 서버에 물리 복제로 리플리카를 붙인다.
  • 이 리플리카가 실제로 배치 작업을 수행할 대상 서버가 된다.
flowchart LR
  A["서비스 DB #1"] -->|"논리 복제
(필요한 테이블만)"| H["통합 논리 복제 서버"]
  B["서비스 DB #2"] -->|"논리 복제"| H
  C["서비스 DB #3"] -->|"논리 복제"| H
  H -->|"물리 복제"| R["리플리카
= 배치 수행 서버"]
논리 복제는 모으는 데, 물리 복제는 멈추는 데 쓴다 — 00시 30분에 논리 복제를 끊으면 통합 서버의 시점이 고정되고, 그 리플리카를 승격시켜 배치 전용 DB로 삼는다.

상세 절차

  1. 00시 30분, 복제 지연 여부를 확인하고 논리 복제를 중단한다

    한쪽 서버에서 alter subscription <subscription_name> disable을 수행한다. 중단하면 논리 복제와 관련된 모든 프로세스가 멈춘다.

  2. 리플리카를 마스터로 승격시킨다

    이제 통합 복제 서버에는 특정 시점 기준의 데이터가 놓여 있다. pg_ctl promote로 리플리카를 마스터로 승격시킨다.

  3. 중단했던 subscription을 다시 활성화한다

    alter subscription <subscription_name> enable. 통합 서버는 다시 원본을 따라잡기 시작한다.

  4. 배치가 끝나면 리플리카를 재구성한다

    승격된 서버에서 배치 작업이 완료되면 pg_basebackup으로 리플리카를 다시 만든다.

!

1단계의 “복제 지연 여부 확인”이 이 구성의 급소다

지연이 있는 상태에서 disable하면 지연 중이던 변경분은 그대로 누락된 채 시점이 고정된다(5-2의 “중단 시 지연 레코드는 복제되지 않는다”와 같은 이야기다). 자동화한다면 pg_replication_slots의 confirmed_flush_lsn이 현재 LSN을 따라잡았는지 확인하는 단계를 스크립트에 반드시 넣어야 한다. 확인 방법은 5-4 복제 슬롯에 있다.

정리

  • 여러 소스에서 필요한 테이블만 모으는 데는 논리 복제, 시점을 고정하는 데는 물리 복제를 쓴다.
  • 절차는 subscription disable → pg_ctl promote → subscription enable → 배치 후 pg_basebackup 재구성이다.
  • 중단 직전의 복제 지연 확인을 빠뜨리면 데이터가 조용히 누락된다.
5-4

복제 슬롯

WAL을 지켜주는 안전장치가, 방치되면 디스크를 채워 인스턴스를 죽이는 장치가 된다.

핵심 슬롯은 “아직 안 보낸 WAL을 지우지 마”라는 약속이다. 그래서 죽은 슬롯 하나가 WAL 볼륨을 무한정 채운다. 슬롯 모니터링은 선택이 아니다.

복제 슬롯

  • 복제 진행 상태를 기록하기 위해 사용하는 구조체다.
  • 물리/논리 모두 사용할 수 있지만 논리 복제에서는 반드시 필요하다.
  • 복제를 재구성하는 작업은 시간이 많이 들기 때문에, 복제 대상 WAL 파일을 유지하는 것이 매우 중요하다.
  • 슬롯을 쓰면 복제 대상 WAL이 삭제되는 것을 막을 수 있어 안정성 확보에 매우 중요한 도구다.
복제 슬롯이 필요한 이유
  • 슬롯 내부에 진행 완료 위치를 기록하고, 아직 전송되지 않은 WAL이 삭제되지 않도록 보존한다.
  • 논리 복제를 재개할 때 복제 시작 위치를 정확히 알 수 있다.
!

슬롯은 메모리 구조체가 아니다 원문 교정

노트에는 슬롯을 “메모리 구조체로 이해하면 된다”고 적혀 있으나, 복제 슬롯은 $PGDATA/pg_replslot/<slot_name>/ 아래에 디스크로 영속화된다. 이것이 핵심이다. 슬롯이 메모리에만 있었다면 인스턴스를 재시작하는 순간 사라지고 WAL도 풀려났을 것이다. 재시작을 넘어 살아남기 때문에 “아무도 쓰지 않는 슬롯이 WAL을 영원히 붙잡는” 아래의 장애가 성립한다.

미사용 슬롯의 문제점

  • 슬롯을 쓰면 WAL 파일이 WAL 디스크 볼륨에 보존된다는 장점이 있다.
  • 하지만 WAL 볼륨이 가득 차서 인스턴스가 비정상 종료되는 문제가 발생할 수 있다.
  • 복제 안정성을 위한 슬롯이 오히려 서비스 가용성을 떨어뜨릴 수 있으므로 지속적인 모니터링이 매우 중요하다.
슬롯 상태 확인
  • 정상이라면 active가 t이고, active_pid에 연결된 walsender의 PID가 들어 있다.
  • 현재 LSN과 confirmed_flush_lsn의 차이로 복제 지연 상태를 확인할 수 있다. 복제가 끝나면 이 값은 0이 된다.
슬롯 상태 + 지연량 한 번에 보기 
postgres=# select slot_name, active, active_pid, confirmed_flush_lsn, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) as flush_lag_sz
from pg_replication_slots;
                slot_name                | active | active_pid | confirmed_flush_lsn | flush_lag_sz
-----------------------------------------+--------+------------+---------------------+--------------
 sub_svc_tb1                             | t      |       2234 | 0/187D088           | 0 bytes
 pg_16407_sync_16389_7568446880728596519 | f      |            | 0/187C858           | 2096 bytes
 sub_from_db1                            | t      |       2235 | 0/187D088           | 0 bytes

가운데 줄의 pg_16407_sync_...가 초기 복제용 임시 슬롯이다. active = f이면서 active_pid가 비어 있다면 아무도 이 슬롯의 WAL을 가져가지 않는다는 뜻이고, 그 상태로 flush_lag_sz가 계속 커진다면 이미 장애가 진행 중인 것이다.

WAL 볼륨 공간 부족으로 인스턴스가 비정상 종료됐을 때의 조치

  1. 서비스 정상화가 우선이다

    인스턴스 복구에 필요한 WAL만 남기고 나머지는 삭제한다.

  2. 필요한 WAL은 “마지막 체크포인트 이후”의 것이다

    pg_controldata로 마지막 체크포인트의 REDO WAL 파일을 확인한다.

  3. 그 파일만 남기고 삭제한 뒤, 미사용 슬롯을 제거한다

    select pg_drop_replication_slot('<slot_name>').

WAL 파일을 rm으로 지우는 것은 최후의 수단이다

필요한 WAL을 하나라도 잘못 지우면 인스턴스가 기동조차 하지 못한다. 여유가 조금이라도 있다면 pg_archivecleanup을 쓰거나, 먼저 pg_drop_replication_slot()으로 원인 슬롯을 제거해 체크포인트가 스스로 WAL을 재활용하게 만드는 편이 안전하다. 손으로 지우기 전에 지우려는 파일이 pg_controldata가 알려준 REDO 파일보다 앞선 것인지 반드시 확인한다.

max_slot_wal_keep_size 파라미터를 이용한 장애 방지

  • 복제 슬롯이 유지할 WAL 파일의 최대 크기를 제한하는 파라미터다.
  • 내부적으로 wal_keep_size와 비교해 더 큰 쪽이 실질적인 WAL 보존 크기가 된다.
  • 이 값들을 WAL 볼륨 크기보다 작게 설정하면 슬롯으로 인한 장애를 사전에 방지할 수 있다.
  • 일반적으로 WAL 디스크 볼륨의 80% 정도로 설정하는 것이 적절하다.
i

이 파라미터는 슬롯을 “버린다” 보강

기본값은 -1(무제한)이다. 값을 설정하면 슬롯의 restart_lsn이 현재 LSN보다 그 크기 이상 뒤처졌을 때 해당 슬롯을 쓰는 스탠바이가 복제를 이어갈 수 없게 된다. 즉 이 파라미터는 장애를 없애는 것이 아니라 “인스턴스 다운”이라는 장애를 “복제 하나 끊김”이라는 장애로 바꾸는 스위치다. 어느 쪽이 덜 아픈지 정해두고 설정해야 하고, 끊긴 복제는 pg_basebackup부터 다시 해야 한다. pg_replication_slots.wal_status가 lost가 되면 그 상황이다.

정리

  • 슬롯은 디스크에 영속화된다. 재시작해도 살아남고, 그래서 방치된 슬롯이 WAL을 무한정 붙든다.
  • 모니터링 지표는 active/active_pid와 pg_current_wal_lsn() - confirmed_flush_lsn이다.
  • 사고가 났다면 원인 슬롯 제거가 먼저다. WAL 수동 삭제는 pg_controldata로 확인한 뒤 최후에.
  • max_slot_wal_keep_size는 인스턴스 다운을 복제 끊김으로 바꾼다. 트레이드오프를 알고 설정한다.
5-5

LSN과 WAL 파일명

24자리 16진수는 타임라인 + 파일 ID + 세그먼트 ID다. 읽는 법을 알면 복제 로그가 문장으로 보인다.

핵심 LSN 14/263F7E88은 “WAL File ID 0x14의 오프셋 0x263F7E88”이고, 그 자리의 파일명은 000000010000001400000026이다. 상위 바이트가 세그먼트 번호로 올라간다.

LSN(Log Sequence Number)

  • WAL 파일 내의 트랜잭션 위치를 식별하는 데 쓴다.
  • WAL File ID / WAL Segment ID + Offset 형식을 따른다. 예: 14/263F7E88

WAL 파일명

총 24자리의 16진수로 구성되며 8자리씩 나뉜다.

파일명의 뒤 16자리가 곧 LSN의 앞부분이다 — LSN 14/263F7E88에서 14는 File ID, 오프셋의 상위 바이트 26이 세그먼트 번호가 된다.
Timeline
  • initdb로 DB 클러스터를 만들 때 1로 시작한다.
  • 이후 복구 작업이나 리플리카의 마스터 승격(promote) 시 1씩 증가한다.
WAL Segment ID
  • 0 ~ 255 사이의 값을 가지며, 세그먼트 단위는 총 256개다.
  • 4GB를 WAL 크기로 나눈 값으로 계산된다.
  • 예를 들어 WAL 크기가 16MB라면 4GB / 16MB = 256이므로 세그먼트 단위가 256이 된다.
WAL File ID

WAL Segment ID가 256을 넘어갈 때마다 1씩 증가한다.

PG 함수로 계산해보기
postgres=# select pg_walfile_name('14/263F7E88');
     pg_walfile_name
--------------------------
 000000010000001400000026
(1 row)
i

타임라인이 갈라지면 .history 파일이 생긴다 보강

promote가 일어나면 pg_wal에 00000002.history 같은 파일이 만들어지고, 여기에 “몇 번 타임라인의 어느 LSN에서 갈라져 나왔는지”가 기록된다. PITR로 특정 시점 복구를 할 때 어느 타임라인을 따라갈지 결정하는 근거가 이 파일이다. 승격 이후 리플리카를 다시 붙일 때 “timeline이 맞지 않는다”는 에러를 보게 되는 지점이기도 하다.

정리

  • WAL 파일명 24자리 = Timeline(8) + WAL File ID(8) + Segment ID(8).
  • 세그먼트는 0~255. 16MB × 256 = 4GB마다 File ID가 하나 올라간다.
  • LSN → 파일명 변환은 pg_walfile_name(), 두 LSN의 거리는 pg_wal_lsn_diff()가 계산해준다.
  • promote는 타임라인을 하나 올리고 .history 파일을 남긴다.
