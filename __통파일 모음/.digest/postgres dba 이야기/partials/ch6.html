6-1

논리 백업과 복구

pg_dump는 복구 도구가 아니라 보관과 이행 도구다. 그 전제를 잡고 옵션을 고른다.

핵심 논리 백업은 백업 시점으로만 돌아간다. 장애 시점까지 되돌리는 완전 복구는 아카이브 WAL을 쓰는 물리 백업만 할 수 있다.

논리 백업과 복구

  • 논리 백업은 물리 백업과 달리 완전한 복구 기능을 제공하지 않는다.
  • 물리 백업은 아카이브 파일을 써서 장애 시점까지 복구하지만 논리 백업은 그렇지 않다.
  • 논리 백업은 백업 시점의 데이터를 복원하는 용도이며, 복구보다는 데이터 보관 및 이행 목적으로 활용된다.

pg_dumpall을 이용한 백업

  • DB 클러스터 내 모든 DB와 관련 정보를 한꺼번에 백업한다.
  • DB가 여럿일 때 편하지만 압축과 병렬 백업을 지원하지 않는다는 단점이 있다.
  • 보통 논리 복제 구성 시 클러스터 내 모든 형상 정보와 Role 정보를 백업하는 데 쓴다.
DB 생성 스크립트 백업
  • 오브젝트 생성 스크립트만 백업할 때는 -s 옵션을 쓴다. 데이터는 빠지고 스크립트만 남는다.
  • 롤 정보만 따로 백업하려면 -r 옵션을 쓴다.
terminal 
# 백업하기
postgres@dff5953eda06:~$ pg_dumpall -s -f database_cluter.sql

plain 복원은 에러가 나도 멈추지 않는다 보강

위 출력의 ERROR: role "postgres" already exists를 지나쳐 계속 진행된 것을 보라. psql은 기본적으로 에러를 만나도 다음 문장을 실행한다. 복원 도중 어디까지 성공했는지 알 수 없게 되므로, 진짜 복원이라면 psql -v ON_ERROR_STOP=1 --single-transaction로 전부 성공 아니면 전부 롤백을 강제하는 편이 안전하다.

pg_dump를 이용한 백업

  • 개발 환경 DB 백업이나 DB/스키마 단위 이행 업무에 자주 쓴다.
  • 사용 범위가 넓고 빈도도 높아 다양한 실무 상황에 맞는 옵션을 제공한다.
  • 압축과 병렬 처리도 지원하므로 대용량 백업에도 유용하다.
Format 옵션

-F 옵션으로 파일 포맷을 지정하며 기본값은 p(plain)이다. p, c(custom), d(directory), t(tar) 네 가지를 지원한다.

포맷압축부분 복구병렬(-j)쓰임
p plain전체 파일 단위만✗✗스크립트 백업 / psql로 복원
c custom✓✓✗단일 파일. 관리가 편하다
d directory✓✓✓여러 파일로 분할. 백업 속도가 빠르다
t tar✗✓✗압축이 안 돼 활용도가 낮다

p(plain) — 부분 복구를 지원하지 않아 복구 목적의 백업에는 거의 쓰지 않는다. 대신 DB나 스키마 단위의 오브젝트 생성 스크립트를 백업하는 용도로 활용한다. svcdb의 svc 스키마에 포함된 모든 오브젝트의 생성 스크립트를 백업한다면 이렇게 쓴다.

pg_dump -Fp -d svcdb -n svc -s -f svc_schema.sql

c(custom) / d(directory) — 압축과 부분 복구를 모두 지원해 개발 DB 데이터 백업에 자주 쓴다. c는 하나의 파일로, d는 여러 파일로 분할 저장된다. 백업 속도가 중요하면 d, 관리 편의가 중요하면 c가 일반적인 선택이다.

t(tar) — TAR 파일로 묶어 저장하지만 압축을 지원하지 않아 활용도가 낮다.

!

plain도 압축은 된다 원문 교정

노트에는 plain이 “압축과 부분 복구를 지원하지 않는다”고 되어 있으나, 공식 문서는 “For plain text output, setting a nonzero compression level causes the entire output file to be compressed”라고 서술한다. 즉 파일 전체를 통째로 압축하는 것은 가능하고(기본값이 무압축일 뿐), 다만 테이블 단위로 골라 꺼내는 부분 복구가 불가능한 것이 plain의 진짜 한계다. 압축이 아예 안 되는 포맷은 tar다.

압축 옵션
  • -Z 옵션으로 압축 방식을 지정한다.
  • gzip — 레벨이 높아질수록 파일 크기는 줄지만 압축 시간이 오래 걸린다.
  • lz4 — 16 버전부터 사용할 수 있다.
  • 어떤 조합이 좋은지는 시스템 환경과 데이터 특성에 따라 달라지므로 직접 테스트해서 찾아야 한다.
↑

zstd도 있다 최신 반영

PostgreSQL 16부터 -Z가 받는 값은 gzip, lz4, zstd, none 네 가지다. 노트에는 zstd가 빠져 있는데, 압축률과 속도의 균형이 가장 좋아 대용량 덤프에서 실질적인 기본 선택지가 되는 경우가 많다. -Z zstd:long으로 long 모드를 켜면 메모리를 더 쓰는 대신 압축률이 더 올라간다. 형식은 -Z <method>:<level>이다.

병렬 처리 옵션
  • -j 옵션을 사용하며, d(directory) 포맷일 때만 가능하다. 여러 프로세스가 동시에 데이터를 쓸 수 있는 유일한 포맷이기 때문이다.
  • 병렬로 데이터를 백업하는 워커 프로세스 개수를 지정하는데, 적정값은 CPU 코어나 디스크 I/O에 따라 달라진다.
  • 이것도 직접 테스트해서 적절한 값을 찾는 편이 좋다.

psql과 pg_restore를 이용한 복원

스키마 형상을 타 DB에 적용하기

개발 단계에서는 테이블 구조가 수시로 바뀌고, 현 시점의 스키마를 다른 DB에 반영할 일이 생긴다. 여러 방법이 있지만 아래가 효율이 좋다.

  1. 개발 DB에서 스키마 형상 백업
    pg_dump -Fp -n svc -s -f svc_schema.sql
  2. 이행 대상 DB에서 기존 스키마 제거
    psql -d svcdb_mig
  3. 백업한 스키마를 psql로 적용
    psql -d svcdb_mig -f svc_schema.sql
스키마 형상 및 데이터를 함께 적용하기
  • 절차는 거의 동일하지만 데이터가 포함되므로 -Fc 또는 -Fd로 백업하는 편이 유리하다.
  • -Fc로 백업한 파일은 바이너리 포맷이므로 복원 시 pg_restore를 써야 한다.
  • 백업 파일이 크거나 오브젝트 수가 많으면 -j 병렬 처리로 속도를 높일 수 있다.
terminal 
# 스키마 형상 및 데이터를 함께 백업
pg_dump -Fc -Z1 -n svc -f svc_schema_data.custom

# 대상 DB의 기존 스키마 삭제
psql -d svc

# custom 포맷은 pg_restore 로 복원
pg_restore -d svcdb_mig -v svc_schema_data.custom

# 오브젝트가 많다면 병렬로
pg_restore -d svcdb_mig -v -j <worker> svc_schema_data.custom
i

-j는 백업과 복원에서 조건이 다르다 보강

백업(pg_dump -j)은 directory 포맷에서만 되지만, 복원(pg_restore -j)은 custom과 directory 양쪽에서 동작한다. 그래서 -Fc로 한 덩어리로 백업해두고 복원만 병렬로 돌리는 조합이 실무에서 꽤 유용하다.

pg_restore를 이용한 복구

특정 테이블 복구
  • 일 단위로 DB 전체를 custom 포맷으로 백업한다고 가정한다.
    • pg_dump -Fc -Z1 -f svcdb_full_20251104.custom
  • t1 테이블만 복구해야 한다면 이렇게 한다.
    • pg_restore -d svcdb -v -n svc -t t1 svcdb_full_20251104.custom
  • 데이터가 잘못된 경우는 전부 지우고 복구하면 되는데, pg_restore는 기본적으로 테이블 생성 → 데이터 입력 순서로 동작하므로 테이블이 이미 있으면 에러가 난다. 이때 -a(데이터만) 옵션을 활용한다.
×

테이블 단위 복구에서 -c는 위험하다

pg_restore -c는 기존 테이블을 DROP하고 다시 만드는 방식으로 동작한다. 그런데 기존에 설정된 제약조건, 인덱스, PK는 복구되지 않는다. 테이블 단위 복구 작업에서 -c 사용은 신중해야 한다. 데이터만 되돌리는 것이 목적이라면 -a가 맞다.

COPY

  • COPY 명령으로 테이블 단위 데이터 추출 및 적재가 가능하다.
  • 이 명령어의 가장 큰 장점은 유연한 데이터 추출이다.
COPY와 \copy의 차이
  • psql로 접속한 상태에서 \copy 또는 COPY로 실행한다.
  • 일반적으로는 유저가 접근할 수 있는 경로의 파일을 읽고 쓸 수 있고 별도 권한 설정이 불필요한 \copy를 쓴다.
i

둘의 차이는 “누구의 파일 시스템인가”다 보강

COPY는 서버가 서버의 파일을 읽고 쓴다. 그래서 슈퍼유저나 pg_read_server_files 같은 롤이 필요하다. \copy는 psql 클라이언트가 로컬 파일을 읽어 프로토콜로 흘려보내므로 별도 권한이 필요 없다. 원격에서 붙어 작업한다면 사실상 \copy가 유일한 선택지다. 이 차이가 7-7에서 bytes_total이 COPY에서만 보이는 이유이기도 하다.

데이터 추출 및 적재
  • 구분자는 한 글자만 지정할 수 있다.
  • 덤프 파일의 컬럼 구성을 쉽게 확인하려면 header 옵션을 함께 쓰는 편이 좋다.
  • 구분자는 헥사 코드로도 지정할 수 있다. 탭 문자는 E'\x09'처럼 표기한다.
구분자가 값 안에 들어 있어도 안전하다 
-- 테이블 생성
postgres=# create table svc.t1 ( c1 integer, c2 varchar(10), c3 varchar(10), c4 integer );

-- 데이터 생성, 값 안에 구분자 | 가 들어 있다
postgres=# insert into svc.t1 values (1, 'A|B', 'C|D', 1);
postgres=# select * from svc.t1;
 c1 | c2  | c3  | c4
----+-----+-----+----
  1 | A|B | C|D |  1

-- \copy를 통해서 t1.csv로 추출한다. 이 때 구분자는 | 이다
postgres=# \copy svc.t1 to 't1.csv' with (format csv, delimiter '|', header);

-- 백업이 된 모습 (값이 큰따옴표로 감싸졌다)
postgres=# \! cat t1.csv;
c1|c2|c3|c4
1|"A|B"|"C|D"|1

-- csv -> table 복원을 위해 동일한 구조를 가진 테이블 생성
postgres=# create table svc.t1_bak ( c1 integer, c2 varchar(10), c3 varchar(10), c4 integer );

-- t1.csv -> svc.t1_bak 테이블로 복원
postgres=# \copy svc.t1_bak from 't1.csv' with (format csv, delimiter '|', header);

-- 복원된 모습
postgres=# select * from svc.t1_bak;
 c1 | c2  | c3  | c4
----+-----+-----+----
  1 | A|B | C|D |  1
쿼리 결과 추출 기능
  • 테이블 전체가 아닌 특정 쿼리 결과를 추출하는 기능도 제공한다.
  • 정제된 데이터를 외부로 내보낼 때 유용하지만, COPY는 반드시 한 줄로 입력해야 한다는 제약이 있다.
  • 쿼리문이 길다면 View를 만들고 그 뷰로 추출하는 편이 효율적이다.
-- 2건의 데이터가 존재함
postgres=# select * from svc.t1;
 c1 | c2  | c3  | c4
----+-----+-----+----
  1 | A|B | C|D |  1
  2 | A|B | C|D |  2

-- 쿼리 결과를 csv로 추출
postgres=# \copy (select * from svc.t1 where c1 = 1) to './query_result.csv' with (format csv, delimiter '|', header);

-- 추출된 모습
postgres=# \! cat query_result.csv
c1|c2|c3|c4
1|"A|B"|"C|D"|1
에러 처리 기능
  • PostgreSQL 17부터 COPY에 에러 처리 기능이 추가되어 덤프 파일 안에서 에러를 유발하는 레코드를 식별하고 무시할 수 있다.
  • on_error ignore — 오류가 발생한 레코드는 생략한다.
  • log_verbosity — 오류 발생 라인을 로그로 출력한다.
17+ 
postgres=# \copy svc.t1 from './asis_t1.csv' with (on_error ignore, log_verbosity verbose, format csv, delimiter '|', header);

정리

  • 논리 백업은 백업 시점까지만 되돌린다. 완전 복구는 물리 백업의 영역이다.
  • 포맷 선택은 속도면 -Fd, 관리면 -Fc, 스크립트면 -Fp. tar는 압축이 안 돼 잘 쓰지 않는다.
  • pg_dump -j는 directory 전용이지만 pg_restore -j는 custom에서도 동작한다.
  • 테이블 단위 복구에서 -c는 인덱스와 제약을 날린다. 데이터만 되돌릴 땐 -a.
  • COPY는 서버 파일, \copy는 클라이언트 파일. 17부터 on_error ignore로 불량 레코드를 넘길 수 있다.
6-2

물리 백업과 복구

완전 복구의 조건은 “백업 + 그 이후 모든 WAL”이다. 백업 전략은 이 한 줄에서 파생된다.

핵심 17부터 pg_basebackup이 블록 단위 증분 백업을 지원한다. 파일 단위 증분만 가능했던 pgBackRest와의 우열이 이 지점에서 갈린다.

물리 백업과 복구

  • 물리 백업은 DB 클러스터를 구성하는 파일 단위의 백업이다.
  • DB 가동 중에 수행하는 온라인 백업과, 종료하고 수행하는 오프라인 백업으로 구분된다.
  • 가장 큰 장점은 장애 시점까지의 완벽한 복구를 지원한다는 점이다.
  • 유저 실수로 데이터가 삭제되어도 손실 직전 시점까지 복구할 수 있는 시점 복구(PITR) 기능도 함께 제공한다.
명령어
  • pg_basebackup 또는 pg_backup_start(), pg_backup_stop() 함수로 수행할 수 있다.
  • 가장 강력한 백업/복구 기능을 제공하는 도구는 pgBackRest다.

백업 및 복구 개요

  • 복구의 목표는 트랜잭션 유실이 없는 완벽한 복구를 실현하는 데 있다.
  • 이를 위해서는 단순히 백업을 수행하는 것뿐 아니라 백업 주기, 보관 기간 등 백업 전반의 전략을 사전에 마련하는 것이 중요하다.
일반적인 백업 유형
유형백업 대상복구에 필요한 세트
전체 백업클러스터 내 모든 파일마지막 전체 백업 + 이후 WAL
증분 백업마지막 증분 백업 이후 변경분마지막 전체 백업 + 모든 증분 백업 + 이후 WAL
차등 백업마지막 전체 백업 이후 변경분마지막 전체 백업 + 마지막 차등 백업 + 이후 WAL
완벽한 복구를 위한 백업 데이터 세트
  • 완벽한 복구를 위해서는 장애 시점까지 생성된 모든 WAL 파일이 필요하다.
  • 증분 백업을 수행한 경우, 마지막 전체 백업 + 모든 증분 백업 + 마지막 증분 이후의 WAL이 필요하다.
  • 차등 백업을 수행한 경우, 마지막 전체 백업 + 마지막 차등 백업 + 그 시점 이후의 WAL이 필요하다.
  • 증분은 백업 속도가 빠르지만, 전체 백업 주기가 길수록 복구 대상이 많아져 복구 시간이 늘어날 수 있다.
  • 차등은 전체 백업 이후의 변경분만 담으므로, 일반적으로 복구 속도 측면에서는 차등이 유리하다.
백업 주기
  • 복구 시간 관점에서는 전체 백업을 매일 수행하는 것이 가장 이상적이다.
  • 매일 전체 백업이 가능한 환경이라면 전체 백업만으로 운영하는 것이 가장 효율적이다.
  • 어렵다면 전체 백업은 주 1회, 차등/증분 백업을 매일 수행하는 방식이 일반적이다.
백업 파일 보관 기간
  • 백업 파일을 장기간 보관할 필요는 없지만, 여러 상황을 고려해 기간을 길게 잡는 경우가 많다.
  • 만약 1주일 전 상태로 되돌려야 한다면 그 시점의 백업 파일이 반드시 있어야 한다.
  • 이런 이유로 일반적으로 1주 ~ 1달 범위에서 보관 기간을 설정한다.

백업 툴 선정

  • 버전 16까지는 pgBackRest를 쓰는 것이 모든 면에서 유리하다.
  • 하지만 17부터는 pg_basebackup이 증분 백업을 지원하므로 상황에 맞게 고르면 된다.
  • pgBackRest도 증분 백업을 제공하지만 이는 변경된 파일 단위의 증분이다.
    • 1GB 파일에서 1바이트만 바뀌어도 1GB를 다시 백업해야 한다.
  • pg_basebackup의 증분 백업은 변경된 블록 단위로 동작하므로 백업 시간과 용량을 모두 줄일 수 있다.
  • 증분 백업 방식을 제외한 모든 항목은 pgBackRest가 우수하다.
  • 델타 복구가 특히 중요하다. PostgreSQL은 데이터 파일 중 하나라도 손실되면 전체를 복구해야 하는데, 델타 복구를 쓰면 손상된 파일만 복원하고 진행할 수 있다.

17 증분 백업은 summarize_wal이 켜져 있어야 한다 최신 반영

PostgreSQL 17 릴리스 노트의 “Add support for incremental file system backup”이 이 기능이다. 다만 그냥 --incremental만 붙인다고 되는 것은 아니고, 서버에서 summarize_wal = on으로 WAL 서머라이저를 켜둬야 어떤 블록이 바뀌었는지 추적할 수 있다. 그리고 복원할 때는 pg_basebackup이 아니라 pg_combinebackup으로 전체 백업과 증분들을 하나로 합쳐야 한다는 점이 기존 흐름과 다르다.

!

도구 이름 원문 교정

노트에 한 차례 pgRestBack으로 적힌 부분이 있는데 pgBackRest가 맞다. 검색할 때 헷갈리기 쉬운 이름이다.

원문 범위

노트는 여기서 “이후 실제 복구 과정은 생략”으로 끝난다. 이 문서도 확인되지 않은 내용을 채워 넣지 않고 원문의 범위를 그대로 따른다.

정리

  • 완전 복구 = 백업 세트 + 그 이후 모든 WAL. 하나라도 빠지면 그 지점까지밖에 못 간다.
  • 복구 속도는 차등이, 백업 속도는 증분이 유리하다. 가능하면 매일 전체 백업이 가장 낫다.
  • 16까지는 pgBackRest, 17부터는 블록 단위 증분이 필요하면 pg_basebackup도 후보가 된다.
  • 17 증분 백업은 summarize_wal = on + 복원 시 pg_combinebackup이 짝이다.
