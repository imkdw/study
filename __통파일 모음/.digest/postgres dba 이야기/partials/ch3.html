3-1

인스턴스

공유 메모리 두 덩어리와 fork()로 갈라지는 프로세스 세 종류. PostgreSQL 인스턴스는 이게 전부다.

핵심 공유 버퍼는 디스크 I/O를 줄이고, WAL 버퍼는 안정성 비용을 줄인다. 성능과 안전성이라는 두 요구가 각각 하나씩의 메모리 영역을 만들어냈다.

공유 메모리

  • DBMS의 핵심 요소는 안정성과 성능이다. 트랜잭션의 안정성을 보장하면서 최대한의 성능을 내야 한다.
  • PostgreSQL은 성능을 위해 공유 메모리를 활용하는데, 그중 가장 중요한 것이 공유 버퍼와 WAL 버퍼다.
공유 버퍼
  • Disk I/O를 최소화해 성능을 올리는 것이 목적이다.
  • 큰 크기여도 빠르게 접근할 수 있어야 하고, 다수의 사용자가 동시에 접근해도 경합이 최소화되어야 한다.
  • 자주 쓰이는 블록은 가능한 한 오래 공유 버퍼에 남아 있어야 한다.
WAL 버퍼
  • 트랜잭션 처리의 신뢰성 보장은 필수다. 즉 커밋된 트랜잭션은 반드시 DB에 반영되어야 한다.
  • PostgreSQL은 이를 위해 WAL(Write-Ahead Logging) 방식을 쓴다.
  • 트랜잭션 내용을 데이터 파일에 기록하기 전에 WAL 파일에 먼저 기록하는 방식이다.
  • 매번 WAL에 직접 기록하면 디스크 I/O 때문에 성능 문제가 생긴다.
  • 그래서 공유 메모리 안에 WAL 버퍼를 두고 트랜잭션 정보를 임시로 담았다가, 일정 조건을 만족하면 WAL 파일에 기록한다.
i

이 두 버퍼가 곧 두 개의 병목이다 보강

공유 버퍼 접근에서 생기는 경합은 BufferMapping, WAL 버퍼 접근에서 생기는 경합은 WALInsert, WAL 파일 기록에서 생기는 경합은 WALWrite/WALSync 대기이벤트로 관찰된다. 구조를 알면 대기이벤트 이름이 그대로 읽힌다. 8-2 대기이벤트에서 하나씩 다룬다.

프로세스

postgres 프로세스
  • 인스턴스 기동 시 가장 먼저 시작되는 프로세스다.
  • 인스턴스 복구 작업, 공유 메모리 초기화 등을 수행한다.
  • 이후 다른 프로세스들이 여기서 갈라져 나온다.

접속 하나에 프로세스 하나 — 백그라운드 프로세스는 기동 시점에 한 번 fork되고, 백엔드 프로세스는 클라이언트가 접속할 때마다 fork된다.
백그라운드 프로세스

PostgreSQL은 백그라운드 프로세스로 시스템을 유지/관리한다. logger, checkpointer, walwriter 등 여러 종류가 있다.

백엔드 프로세스
  • 클라이언트의 요청을 받아 쿼리를 수행하고 결과를 반환한다.
  • 쿼리 수행을 위해 백엔드 프로세스 메모리 내부에 할당되는 공간을 로컬 메모리라고 부른다.
  • 로컬 메모리는 work_mem, temp_buffers 등의 파라미터로 튜닝한다.
i

로컬 메모리는 세션당이 아니라 “연산당”이다 보강

work_mem은 세션 하나가 아니라 정렬/해시 연산 하나에 허용되는 크기다. 하나의 쿼리에 정렬과 해시 조인이 여러 개 들어 있으면 그만큼 배로 잡힌다. 여기서 부족해지면 임시 파일이 생기고, 그것이 7-4 SQL 모니터링의 temp_ 계열 컬럼과 3-2의 TEMP 테이블스페이스 용량 문제로 이어진다.

DB 클러스터 주요 디렉터리 및 파일

postgresql.conf
  • 인스턴스 환경 설정용 파일이다.
  • 파일 내부에 동일한 파라미터가 여러 번 있다면 아래쪽에 위치한 것이 우선이다.
postgresql.conf 
#------------------------------------------------------------------------------
# ERROR HANDLING
#------------------------------------------------------------------------------

#exit_on_error = off                    # terminate session on any error?
#restart_after_crash = on               # reinitialize after backend crash?
#data_sync_retry = off                  # retry or panic on failure to fsync
                                        # data?
                                        # (change requires restart)
#recovery_init_sync_method = fsync      # fsync, syncfs (Linux 5.8+)


#------------------------------------------------------------------------------
# CONFIG FILE INCLUDES
#------------------------------------------------------------------------------

# These options allow settings to be loaded from files other than the
# default postgresql.conf.  Note that these are directives, not variable
# assignments, so they can usefully be given more than once.

include_dir = 'conf.d'                  # include files ending in '.conf' from
                                        # a directory, e.g., 'conf.d'
#include_if_exists = '...'              # include file only if it exists
#include = '...'                        # include file


#------------------------------------------------------------------------------
# CUSTOMIZED OPTIONS
#------------------------------------------------------------------------------

# Add settings for extensions here
postgresql.auto.conf
  • 같은 환경 설정용 파일이지만, ALTER SYSTEM SET으로 파라미터를 바꾸면 여기에 기록된다.
  • ALTER SYSTEM SET ... TO DEFAULT로 항목을 삭제할 수 있다.
  • 파라미터의 최종 적용값을 알려면 두 파일을 다 봐야 하므로, 이 파일을 통한 변경은 최소화하는 편이 좋다.
!

우선순위가 반대다 원문 교정

노트에는 “동일한 파라미터가 postgresql.conf에도 존재한다면 해당 파일(postgresql.conf)의 설정이 우선”이라고 적혀 있지만, 실제로는 반대다. postgresql.auto.conf는 서버가 postgresql.conf를 모두 읽은 뒤에 마지막으로 읽으므로, 같은 파라미터가 양쪽에 있으면 postgresql.auto.conf의 값이 이긴다. ALTER SYSTEM이 “설정을 덮어쓰는” 명령으로 동작하는 이유가 이것이고, 동시에 이 파일을 남용하면 안 되는 이유이기도 하다. 최종 적용값은 파일을 뒤지지 말고 pg_settings로 확인하는 것이 확실하다.

-- 어떤 파일의 몇 번째 줄에서 온 값인지까지 알려준다
select name, setting, source, sourcefile, sourceline
from   pg_settings
where  name = 'work_mem';

정리

  • 공유 메모리의 두 축은 성능을 위한 공유 버퍼와 안정성 비용을 낮추는 WAL 버퍼다.
  • 프로세스는 postgres(최초) → 백그라운드(기동 시 fork) → 백엔드(접속마다 fork) 구조다.
  • 설정 파일은 같은 파일 안에서는 아래가, 파일 간에는 postgresql.auto.conf가 이긴다.
  • 최종 적용값 확인은 pg_settings의 source/sourcefile로 한다.
3-2

테이블스페이스

PostgreSQL의 테이블스페이스는 그냥 디렉터리다. 오라클처럼 무언가를 관리하는 단위가 아니다.

핵심 테이블스페이스 단위로 할 수 있는 작업이 거의 없다. 사용자 테이블스페이스를 만들면 얻는 것 없이 복잡도만 늘어난다.

테이블스페이스

  • PostgreSQL에서 테이블스페이스는 하나의 디스크 볼륨(혹은 디렉터리)이다.
  • 테이블스페이스 단위로 수행할 수 있는 작업이 거의 없어서, 사용자 테이블스페이스를 만들면 오히려 복잡해진다.
  • initdb를 수행하면 기본적으로 두 개(pg_default, pg_global)가 생성된다.
테이블스페이스 목록 조회 
postgres@localhost:postgres> \db
+------------+----------+----------+
| Name       | Owner    | Location |
|------------+----------+----------|
| pg_default | postgres |          |
| pg_global  | postgres |          |
+------------+----------+----------+

pg_default 테이블스페이스

  • $PGDATA/base 폴더에 생성된다. 테이블이나 인덱스를 만들 때 따로 지정하지 않으면 여기 만들어진다.
  • 이 폴더에는 데이터베이스 OID별로 서브 디렉터리가 생긴다.
  • 1: template1, 4: template0, 5: postgres 데이터베이스 폴더다.
    • svcdb라는 새 데이터베이스를 만들면 새로운 OID가 할당되고 그 폴더가 만들어진다.
  • PostgreSQL의 테이블은 파일 단위이며, 저장 경로는 pg_relation_filepath() 함수로 확인한다.

pg_global 테이블스페이스

  • $PGDATA/global 폴더에 데이터가 저장되며, 데이터베이스 클러스터 전체에 걸친 공통 데이터를 담는다.
  • DB 목록, 사용자 및 규칙 정보는 어떤 데이터베이스에서 조회해도 동일한 결과가 나오는데, 모두 pg_global에 있기 때문이다.

TEMP 테이블스페이스

  • 정렬이나 해시 작업 중 로컬 메모리가 부족하면 임시 파일을 사용한다.
  • 작업이 끝나면 자동으로 삭제되지만 $PGDATA 내부에 임시 파일이 생기므로, 용량 계획 시 이 공간도 고려해야 한다.
  • 일반적으로 임시 파일용 TEMP 테이블스페이스를 따로 만들지는 않지만, 예외적으로 구성하는 경우가 있다.
i

임시 파일은 어디에 얼마나 쌓이는가 보강

위 ls 결과에 보이는 pgsql_tmp 디렉터리가 그 자리다. log_temp_files = 0으로 두면 임시 파일이 생길 때마다 크기가 로그에 남고, pg_stat_database의 temp_files/temp_bytes로 누적량을 볼 수 있다. 대형 정렬이 몰리는 시간대에 디스크가 갑자기 차오른다면 여기부터 확인한다.

정리

  • 테이블스페이스는 디렉터리일 뿐이다. 사용자 테이블스페이스는 대체로 만들지 않는 편이 낫다.
  • pg_default는 $PGDATA/base/<DB OID>/<relfilenode>, pg_global은 클러스터 공통 카탈로그다.
  • 파일 경로가 궁금하면 pg_relation_filepath()가 정답을 준다.
  • 임시 파일도 $PGDATA를 먹는다. 용량 산정에서 빠뜨리기 쉬운 항목이다.
3-3

테이블

Heap / Unlogged / Temp 세 종류, 그리고 하나의 레코드가 블록을 넘칠 때를 위한 TOAST.

핵심 Unlogged와 Temp는 WAL을 만들지 않는다. 그래서 빠르지만, 같은 이유로 복제되지 않고 크래시에서 살아남지 못한다.

테이블

PostgreSQL은 세 가지 유형의 테이블을 제공한다. 테이블(Heap), Unlogged, Temp다.

테이블(Heap 테이블)

  • 일반적으로 업무 데이터를 저장하기 위해 만드는 테이블이다.
  • 물리적으로는 세 가지 유형의 파일로 구성된다.
파일파일명역할생기는 시점
데이터<OID>실제 레코드테이블 생성 즉시
FSM<OID>_fsm여유 공간 관리테이블이 일정 크기 이상 커진 뒤
VM<OID>_vm블록의 Visibility / Freezing 정보첫 번째 Vacuum 수행 시
물리적으로 저장되는 파일 확인하기 
-- 테이블 만들기
postgres@localhost:postgres> create table svc.t1_heap (c1 integer);

-- svc.t1_heap 테이블 저장 경로 조회
postgres@localhost:postgres> select pg_relation_filepath('svc.t1_heap')
+----------------------+
| pg_relation_filepath |
| -------------------- |
| base/5/16529         |
+----------------------+
최초 상태

맨 처음에는 단순 테이블 파일 하나만 생긴다.

terminal 
root@68212c6c65f5:/var/lib/postgresql/data/base/5# ls -al | grep 16529
-rw------- 1 postgres postgres         0 Nov  2 08:14 16529
테이블 크기가 커지면 FSM 파일이 생성된다
  • PostgreSQL의 기본값으로 1블록 = 8KB이므로, 아래 실습에서는 테이블이 16KB(2블록)가 되는 시점에 FSM이 관찰됐다.
  • 블록 크기는 컴파일 타임에만 바꿀 수 있고, 클러스터가 생성된 이후에는 변경이 불가능하다.
terminal 
root@68212c6c65f5:/var/lib/postgresql/data/base/5# ls -al | grep 16529
-rw------- 1 postgres postgres     16384 Nov  2 08:16 16529
-rw------- 1 postgres postgres     24576 Nov  2 08:16 16529_fsm
첫 번째 Vacuum이 수행되면 VM 파일이 생성된다
terminal 
root@68212c6c65f5:/var/lib/postgresql/data/base/5# ls -al | grep 16529
-rw------- 1 postgres postgres     16384 Nov  2 08:16 16529
-rw------- 1 postgres postgres     24576 Nov  2 08:16 16529_fsm
-rw------- 1 postgres postgres      8192 Nov  2 08:16 16529_vm
i

VM은 나중에 세 번 더 등장한다 보강

여기서 만들어진 _vm 파일이 9-2의 ALL_VISIBLE/ALL_FROZEN 비트, 9-3의 Frozen 스킵 최적화, 그리고 Index Only Scan의 성립 조건까지 전부 떠받친다. VACUUM FULL이 VM을 다시 만들어주지 않는다는 함정도 같은 파일 이야기다.

Unlogged 테이블

  • WAL이 발생하지 않는다. 배치/이행 작업의 중간 결과를 임시 저장하는 용도로 쓸 수 있다.
  • WAL을 만들지 않으므로 물리 복제 환경에서 조회할 수 없고, 논리 복제도 불가능하다.
  • 세션 간 데이터 공유가 되고 재시작 후에도 데이터가 유지되지만, 비정상 종료 시에는 모두 삭제된다.
  • 임시 데이터 저장처럼 매우 제한적인 범위에서만 쓰는 편이 좋다.
-- Unlogged 테이블 생성
postgres@localhost:postgres> create unlogged table u1 (c1 integer);


-- Unlogged 테이블 목록 조회
postgres@localhost:postgres> select relname from pg_class where relpersistence='u';
+---------+
| relname |
| ------- |
| u1      |
+---------+

Temp 테이블

  • 세션이나 트랜잭션이 종료되면 자동으로 삭제된다.
  • Unlogged처럼 WAL이 발생하지 않아 임시 데이터 저장에 적절하다.
  • 생성 시 pg_temp_{N} 형식의 스키마에 만들어지며, N은 임의의 숫자다.
  • 기존 테이블명과 중복된 이름으로 만들 수 있는데, SELECT 시 Temp 테이블이 먼저 조회된다.
  • CREATE 권한이 없는 유저도 만들 수 있다. Temp 테이블 생성 권한이 기본적으로 PUBLIC에 부여되어 있기 때문이다.
    • 권한을 회수하고 싶다면 PUBLIC으로부터 회수하면 된다.

이름이 겹치면 조용히 다른 테이블을 읽는다

Temp 테이블이 pg_temp_N 스키마에 만들어지고 search_path에서 그 스키마가 앞에 놓이기 때문에, 실수로 운영 테이블과 같은 이름의 Temp 테이블을 만들면 에러 없이 엉뚱한 데이터를 읽는다. 배치 스크립트에서 특히 위험하다.

TOAST(The Oversized-Attribute Storage Technique)

  • PostgreSQL은 레코드 하나를 여러 블록에 걸쳐 저장하는 기능을 지원하지 않는다.
  • 길이가 긴 레코드는 TOAST 기법으로 저장한다.
  • 레코드 하나의 길이가 약 2KB를 초과하면 컬럼 단위로 압축을 시도한다.
  • 압축 이후에도 2KB를 넘으면, 길이가 긴 컬럼부터 테이블 외부 스토리지로 옮긴다.
스토리지 유형

TOAST는 컬럼 타입별로 지정된 스토리지 유형에 따라 동작 방식이 달라진다. 원문에서는 Extended, Plain, Main 세 가지를 언급했다.

i

스토리지 유형은 넷이다 보강

유형압축외부 저장비고
PLAIN✗✗고정 길이 타입(integer 등)의 기본값
EXTENDED✓✓가변 길이 타입의 기본값. 압축 먼저, 그래도 크면 외부로
EXTERNAL✗✓압축을 포기하는 대신 부분 조회(substring)가 빨라진다
MAIN✓최후에만가능한 한 테이블 안에 붙들어둔다

ALTER TABLE ... ALTER COLUMN ... SET STORAGE로 컬럼별로 바꿀 수 있다.

압축 여부 확인법
  • AAAA...는 크기가 1004바이트이며 압축되지 않았다.
  • BBBB...는 크기가 44바이트이며 pglz로 압축되었다.
-- 테이블 생성 & 데이터 삽입
postgres@localhost:postgres> create table t1(c1 varchar(3000));
postgres@localhost:postgres> insert into t1 values (lpad('A', 1000, 'A'));
postgres@localhost:postgres> insert into t1 values (lpad('B', 3000, 'B'));

-- 압축 여부 확인
postgres@localhost:postgres> select c1, pg_column_compression(c1), pg_column_size(c1) from t1;
+------------+-----------------------+----------------+
| c1         | pg_column_compression | pg_column_size |
|------------+-----------------------+----------------|
| AAAA...    | <null>                | 1004           |
| BBBBB...   | pglz                  | 44             |
+------------+-----------------------+----------------+
SELECT 2

같은 3000바이트라도 'B'가 반복되는 값은 44바이트까지 줄어든다. 반대로 1000바이트짜리 'A' 값은 2KB 임계값에 미치지 않아 압축 시도 자체가 없었다.

TOAST 테이블 확인 방법
  • TOAST 대상 컬럼의 실제 데이터는 pg_toast 스키마 안의 TOAST 테이블에 저장된다.
  • 테이블 이름은 pg_toast_<원본 OID> 형식이다.
  • 직접 조회할 일은 드물지만 디스크 사용량 분석에서는 확인이 필요할 수 있다.
postgres@localhost:postgres> select a.relname, b.relname, b.relnamespace::regnamespace
 from pg_class a, pg_class b
 where a.relname='t1'
 and a.reltoastrelid=b.oid;
+---------+----------------+--------------+
| relname | relname        | relnamespace |
|---------+----------------+--------------|
| t1      | pg_toast_16545 | pg_toast     |
+---------+----------------+--------------+
i

테이블이 “작아 보이는데” 디스크는 꽉 찰 때 보강

pg_relation_size()는 TOAST 테이블을 포함하지 않는다. 실제 점유량을 보려면 pg_total_relation_size()를 써야 한다. 대용량 텍스트/JSONB 컬럼이 있는 테이블에서 두 값이 크게 벌어지면, 용량의 대부분이 pg_toast 쪽에 있다는 뜻이다.

정리

  • Heap 테이블은 데이터 파일 + _fsm + _vm 세 파일로 구성된다. VM은 첫 Vacuum 이후에 생긴다.
  • Unlogged/Temp는 WAL을 만들지 않아 빠르지만, 복제 불가 + 크래시 시 소실이라는 대가가 붙는다.
  • Temp 테이블은 search_path에서 우선이라 이름 충돌 시 조용히 오동작할 수 있다.
  • 2KB를 넘는 레코드는 압축 → 외부 저장 순으로 TOAST 처리된다. 용량 분석은 pg_total_relation_size()로.
