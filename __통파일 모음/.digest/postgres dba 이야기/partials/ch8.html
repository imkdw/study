8-1

트랜잭션과 락

모든 명령은 실행 전에 자기에게 필요한 락 모드를 잡는다. 동시성은 그 모드들의 호환표에서 결정된다.

핵심 락 모드가 여러 개인 이유는 동시성을 최대한 열어두면서 무결성을 지키기 위해서다. 어떤 두 명령이 함께 돌 수 있는지는 오직 호환표가 결정한다.

Low-Level Lock

PostgreSQL은 개별 레코드 단위로 락을 제어하는 Low-Level Lock을 제공한다. 이 락은 Exclusive Mode와 Share Mode 두 가지로 나뉜다.

Exclusive Mode
  • 레코드를 변경하는 명령어가 획득하며, 동일 레코드에 대한 동시 접근을 차단한다.
  • INSERT, DELETE, UPDATE, SELECT FOR UPDATE가 대표적이다.
  • 이 명령어들은 동일 레코드에 대해 동시에 수행될 수 없다.
Share Mode
  • 레코드의 변경을 방지할 목적으로 쓰는 SELECT FOR SHARE가 이 모드로 락을 획득한다.
  • 여러 세션이 동시에 동일 레코드에 대한 락을 설정할 수 있다.

Table-Level Lock

  • 테이블에 대한 명령을 수행할 때 필요하며 다양한 모드를 제공한다.
  • 모드가 여러 개인 이유는 한 테이블에 여러 명령이 동시에 수행될 수 있도록 동시성을 최대한 보장하면서도 데이터 무결성을 유지하기 위해서다.
  • 각 모드 간의 호환성 여부에 따라 명령어들의 동시 수행 가능 여부가 결정된다.
모드이 모드를 잡는 명령충돌하는 대표 모드
Access Share SELECT Access Exclusive와만 충돌한다. 조회 중에 DROP을 걸면 락 대기가 발생한다
Row Share SELECT FOR UPDATE, SELECT FOR SHARE 대부분의 모드와 호환된다. 예를 들어 이 명령들이 도는 중에도 인덱스 생성이 가능하다
Row Exclusive INSERT, DELETE, UPDATE Share 이상과 충돌한다. DML 중에 인덱스 생성을 시도하면 인덱스 생성 쪽이 대기한다
Share Update Exclusive CREATE INDEX CONCURRENTLY, VACUUM, ANALYZE Row Exclusive와 경합이 없어 실무에서 자주 활용된다. 자기 자신과는 충돌한다
Share CREATE INDEX (CONCURRENTLY 없이) Row Exclusive와 호환되지 않는다. 인덱스 생성 중 DML을 수행한 세션이 대기한다. Share끼리는 호환되므로 여러 인덱스를 동시에 만들 수 있다
Access Exclusive TRUNCATE, DROP, VACUUM FULL, 대부분의 ALTER TABLE 가장 강력한 모드. SELECT가 잡는 Access Share와도 충돌한다

빠진 두 개의 모드 보강

PostgreSQL의 테이블 락 모드는 총 8개다. 위 6개 외에 SHARE ROW EXCLUSIVE(예: CREATE TRIGGER, 일부 ALTER TABLE)와 EXCLUSIVE(예: REFRESH MATERIALIZED VIEW CONCURRENTLY)가 있다. 강도 순서는 아래와 같고, 오른쪽으로 갈수록 충돌 범위가 넓어진다.

ACCESS SHARE ROW SHARE ROW EXCLUSIVE SHARE UPDATE EXCLUSIVE SHARE SHARE ROW EXCLUSIVE EXCLUSIVE ACCESS EXCLUSIVE

실무에서 외울 가치가 있는 것은 두 줄이다. Access Exclusive는 SELECT조차 막는다. 그리고 Share Update Exclusive는 DML과 공존한다 — 이것이 VACUUM과 CIC가 서비스 중에 돌 수 있는 이유이고, 동시에 VACUUM과 CIC가 서로를 막는 이유이기도 하다.

데드락

  • 두 개 이상의 세션이 서로가 보유한 락을 필요로 하면서 상대방의 해제를 기다리는 상태다.
  • 각 세션이 상대의 종료를 기다리므로 교착 상태에 빠진다.
  • 데드락을 감지한 세션이 트랜잭션을 강제로 롤백하고 종료해야 문제가 해소된다.
  • 데드락은 잘못된 앱 트랜잭션 처리 로직 때문에 발생하므로, 방지하려면 일관된 트랜잭션 처리 순서와 락 최소화 설계가 중요하다.

두 세션 간 데드락
  • PostgreSQL은 일정 시간(deadlock_timeout) 동안 락을 대기한 뒤 데드락 체인을 감지한다.
  • 감지되면 해당 트랜잭션을 자동으로 종료시켜 교착 상태를 해소한다.

세 세션 간 데드락
  • 세 개의 세션이 순환적으로 락을 대기하는 구조에서도 데드락이 발생한다.
  • 동일하게 감지한 세션이 자신의 트랜잭션을 롤백하고 자동 종료된다.
  • 단 데드락 상황이 아닌 락 대기 세션은 여전히 대기한다.

데드락은 대기 그래프에 사이클이 생긴 상태다 — 두 세션이든 세 세션이든 원리는 같다. PostgreSQL은 deadlock_timeout만큼 기다린 뒤 이 그래프를 검사하고, 고리를 발견하면 한 세션을 희생시킨다.

Multi Transaction

  • 하나의 레코드에 동시에 여러 개의 트랜잭션이 걸리는 것을 의미한다.
  • INSERT, UPDATE 등은 로우 레벨 락을 Exclusive 모드로 획득하므로 동일 레코드에 대한 멀티 트랜잭션이 불가능하다.
  • SELECT FOR SHARE는 Share 모드로 획득하므로 여러 트랜잭션이 하나의 레코드에 대해 멀티 트랜잭션을 만들 수 있다.
  • PostgreSQL은 멀티 트랜잭션 정보를 $PGDATA/pg_multixact 하위의 members, offsets 서브 디렉터리에 저장한다.
  • 디스크에 저장하면 I/O 증가와 성능 저하가 발생할 수 있으므로, PostgreSQL은 이 정보를 Shared Memory에 적재해 관리하는 방식(SLRU)을 함께 쓴다.
FK와 멀티 트랜잭션
  • FK를 사용한다면 내부적으로 다수의 멀티 트랜잭션이 발생할 수 있다는 점을 반드시 인지해야 한다.
  • SELECT FOR KEY SHARE 모드는 PK의 변경을 방지하는 용도로 쓴다.
  • 마스터-디테일 관계에서 디테일에 트랜잭션이 발생하면, 마스터의 PK가 변경되지 않도록 KEY SHARE 락을 설정한다.
  • 디테일 테이블에 다수의 트랜잭션이 몰리면 마스터 테이블의 한 레코드에 멀티 트랜잭션 상황이 발생한다.
  • FK 제약이 많다면 pg_stat_slru 뷰로 관련 부하를 모니터링할 필요가 있다.
마스터 & 디테일 테이블 생성

postgres@localhost:postgres> alter table t_master add constraint t_master_pk primary key (master_id);
postgres@localhost:postgres> insert into t_master values(1, 'master_1');

-- 디테일 테이블 생성
postgres@localhost:postgres> create table t_detail (

 master_id integer not null,

postgres@localhost:postgres> alter table t_detail add constraint t_detail_pk primary key (detail_id);
postgres@localhost:postgres> alter table t_detail add constraint t_detail_fk foreign key (master_id) references t_master (master_id) on delete cascade;
postgres@localhost:postgres> create sequence t_detail_sq;

멀티 트랜잭션에도 나이가 있다 보강

MultiXact ID도 XID처럼 유한하고 wraparound가 있다. 그래서 autovacuum_multixact_freeze_max_age(기본 4억)라는 별도의 기준이 존재하고, 테이블의 멀티 트랜잭션 나이는 mxid_age(relminmxid)로 잰다. FK가 많은 시스템에서는 일반 XID보다 멀티 트랜잭션 쪽 나이가 먼저 차오르는 경우가 있으므로 양쪽을 다 봐야 한다. 9-3에서 다시 다룬다.

pg_locks 뷰

  • 현재 DB에서 활성화된 락 정보를 제공하는 시스템 뷰다.
  • PostgreSQL의 모든 명령어는 필요한 락 모드를 획득한 후 실행된다.
  • DB 전반의 락 현황 모니터링에 매우 유용하다.
조회 예시

세션 1 — DELETE 수행으로 두 개의 락을 얻는다.

  • Row Exclusive 모드의 테이블 락 (locktype = relation)
  • Exclusive 모드의 로우 레벨 락 (locktype = transactionid)

세션 2 — SELECT 수행으로 Access Share 모드의 테이블 락을 획득한다. SELECT는 로우 레벨 락을 획득하지 않는다.

조회하는 자신도 목록에 있다 보강

마지막 두 줄의 pg_locks에 대한 AccessShareLock(pid 3997)은 지금 이 조회 자체가 잡은 락이다. pg_locks를 볼 때 늘 섞여 들어오므로, 실제 분석에서는 where pid <> pg_backend_pid()나 where not granted로 걸러내는 편이 낫다. 대기 중인 락만 보고 싶다면 granted = false가 가장 빠른 필터다.

동일 레코드 락 경합 모니터링 시의 주의점

로우 레벨 락 대기가 발생하면 PostgreSQL은 대기 순서에 따라 서로 다른 종류의 락을 요청한다.

  • 첫 번째 대기 세션은 transactionid 락을 Share 모드로 요청하며 대기한다.
  • 이후 대기 세션들은 tuple 락을 Exclusive 모드로 요청하며 대기한다.
-- 세션#1) 트랜잭션 시작 후 c1 = 1 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2 = c2 + 1 where c1 = 1;

-- 세션#2) 트랜잭션 시작 후 동일 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2 = c2 + 1 where c1 = 1;

-- 현재 락 상태, Share 모드로 요청하면서 대기중
   locktype    | relation | virtualxid | transactionid | virtualtransaction | pid  |       mode       | granted
---------------+----------+------------+---------------+--------------------+------+------------------+---------
 transactionid |          |            |       4854633 | 53/5               | 3967 | ShareLock        | f

-- 세션#3) 트랜잭션 시작 후 동일 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2 = c2 + 1 where c1 = 1;

-- 현재 락 상태, 세 번째 세션은 tuple 락을 Exclusive 모드로 요청하면서 대기중임
   locktype    | relation | virtualxid | transactionid | virtualtransaction | pid  |     mode      | granted
---------------+----------+------------+---------------+--------------------+------+---------------+---------
 transactionid |          |            |       4854633 | 53/5               | 3967 | ShareLock     | f
 tuple         | ltest    |            |               | 54/5               | 3997 | ExclusiveLock | f

그래서 대기 세션 수를 transactionid로 세면 안 된다

같은 레코드를 두고 100개 세션이 밀려 있어도 Lock:transactionid는 딱 하나고 나머지 99개는 Lock:tuple이다. 경합 규모를 볼 때 두 대기이벤트를 함께 집계해야 하는 이유다. 8-2의 transactionid/tuple 항목이 짝을 이루는 것도 같은 구조 때문이다.

Virtual XID

  • 세션별 트랜잭션을 관리하기 위해 쓰는 내부 구조다. <ProcNumber>/<LocalTransactionId> 형식으로 표시된다.
  • ProcNumber — 백엔드 프로세스 시작 시 내부적으로 할당되는 값. 공유 메모리 내부에서 프로세스를 관리하는 배열의 인덱스다.
  • LocalTransactionId — 해당 세션 내에서 트랜잭션이 발생할 때마다 1씩 증가한다.
  • 이 락 경합은 CIC 옵션으로 인덱스를 생성하거나 삭제할 때 흔히 관찰된다.
-- 세션#1) 트랜잭션 시작 후 조회
postgres=# begin;
postgres=*# select * from ltest where c1 = 1;
 c1 | c2
----+----
  1 |  1
(1 row)

-- 세션#2) 트랜잭션 시작 후 c1 = 2 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2 = c2 + 1 where c1 = 2;

-- 세션#3) 인덱스 생성
postgres=# create index concurrently ltest_n1 on ltest(c1);

-- 현재 락 상태
virtualxid		54/7		54/7	3997	ExclusiveLock	true -- 세션#2
virtualxid		53/7		54/7	3997	ShareLock	false -- 세션#3 대기

CIC가 다른 세션의 virtual XID에 Share 락을 요청하며 대기하는 모습이다. 이것이 2-2에서 “대상 테이블을 건드리지 않는 쿼리에도 CIC가 막힌다”고 했던 현상의 실체다. CIC는 “내가 스캔을 시작하기 전부터 열려 있던 모든 트랜잭션”이 끝나기를 기다리기 때문이다.

fastpath

  • fastpath는 락을 빠르게 획득하기 위한 경량화된 방법이다.
  • PostgreSQL은 인스턴스 생성 시점에 각 프로세스마다 일정 개수의 슬롯을 공유 메모리에 할당한다.
  • 이 슬롯으로 relation 유형의 락을 관리한다.
  • 슬롯 개수는 17 버전 기준 16개이며 조절할 수 없다.
slowpath
  • 슬롯을 넘어서는 17번째 락부터는 다른 방법으로 처리하는데, 이를 slowpath라고 부른다(공식 용어는 아니다).
  • 모든 세션이 공유하는 전역 락 테이블로 락을 관리하는 방식이다.
  • 이 구조체에는 다수의 프로세스가 동시에 접근하므로 락 관리 구조 자체에 경합이 발생할 수 있다.
  • 그래서 fastpath보다 성능이 떨어진다.
↑

18에서 이 16개 제한이 사라졌다 최신 반영

고정 크기였던 fast-path 락 슬롯이 PostgreSQL 18부터 max_locks_per_transaction(기본 64)에 비례해 확장되도록 바뀌었다. 파티션 테이블처럼 하나의 쿼리가 수십 개의 relation 락을 잡는 워크로드에서 LWLock:LockManager 대기가 잦았던 원인이 바로 이 16개 제한이었고, 18에서는 같은 워크로드가 대부분 fastpath 안에서 처리된다. 아래 테스트를 18에서 다시 돌리면 결과가 달라진다.

fastpath 동작 방식
  • PostgreSQL은 트랜잭션 수행 시 테이블뿐 아니라 그 테이블에 생성된 모든 인덱스에 대해서도 relation 락을 획득한다.
  • 트랜잭션 내에서 액세스하는 테이블이 많거나 인덱스가 많은 테이블에 접근하면 슬롯 초과로 slowpath로 전환될 가능성이 높아진다.
  • 전환되면 락 테이블 접근으로 인한 경합이 발생할 수 있다.
  • 다수의 테이블을 액세스하는 트랜잭션이 동시에 수행되는 경우 slowpath 전환으로 인한 성능 저하 가능성을 염두에 둬야 한다.
테스트 1: 테이블 액세스 시 인덱스에도 relation 락을 잡는가
  • 테이블에 접근하면 실행 계획과 무관하게 그 테이블의 모든 인덱스에 대해 relation 락을 획득한다.
  • 아래 트랜잭션이 액세스한 relation은 3개이므로 모두 fastpath로 락을 획득한다.
-- 인덱스 생성
postgres=# create index ltest_n1 on ltest(c1);
postgres=# create index ltest_n2 on ltest(c2);

-- 테이블 조회
-- 인덱스를 사용하지 않고 테이블 전체를 스캔하는 방식으로 수행됨
postgres=# explain select * from ltest where c1 = 1;
                     QUERY PLAN
-----------------------------------------------------
 Seq Scan on ltest  (cost=0.00..1.04 rows=1 width=8)
   Filter: (c1 = 1)

-- 실제 테이블을 조회하기
postgres=*# select * from ltest where c1 = 1;
 c1 | c2
----+----
  1 |  1

-- 현재 락 상태
postgres=# select
        locktype,
        relation::regclass,
        pid,
        mode,
        fastpath
from pg_locks
order by pid, locktype;
  locktype  | relation | pid  |      mode       | fastpath
------------+----------+------+-----------------+----------
 relation   | ltest_n2 | 3950 | AccessShareLock | t
 relation   | ltest_n1 | 3950 | AccessShareLock | t
 relation   | ltest    | 3950 | AccessShareLock | t

Seq Scan이라 인덱스를 쓰지도 않았는데 ltest_n1, ltest_n2에 락이 잡혔다는 점이 핵심이다. 인덱스를 늘릴 때 조회 비용만 계산하면 이 비용이 빠진다.

테스트 2: 슬롯 초과 시 slowpath로 전환되는가
17번째부터 전환 
-- 기존 ltest랑 동일한 구조로 테이블 복제하기
postgres=# CREATE TABLE ltest1 (LIKE ltest INCLUDING INDEXES);
postgres=# CREATE TABLE ltest2 (LIKE ltest INCLUDING INDEXES);
postgres=# CREATE TABLE ltest3 (LIKE ltest INCLUDING INDEXES);
postgres=# CREATE TABLE ltest4 (LIKE ltest INCLUDING INDEXES);
postgres=# CREATE TABLE ltest5 (LIKE ltest INCLUDING INDEXES);
postgres=# CREATE TABLE ltest6 (LIKE ltest INCLUDING INDEXES);

-- 슬롯 사용하기
-- 테이블 5개 * 락 3개(테이블 1개, 인덱스 2개) -> 15개
postgres=*# select * from ltest1 a, ltest2 b, ltest3 c, ltest4 d, ltest5 e where a.c1 = b.c1 and a.c1 = c.c1 and a.c1 = d.c1 and a.c1 = e.c1;
 c1 | c2 | c1 | c2 | c1 | c2 | c1 | c2 | c1 | c2
----+----+----+----+----+----+----+----+----+----

-- 슬롯 추가로 사용하기
postgres=*# select * from ltest6 where c1 = 1;
 c1 | c2
----+----

-- slowpath 전환 확인하기
postgres=# select
        locktype,
        relation::regclass,
        pid,
        mode,
        fastpath
from pg_locks
order by pid, locktype;
  locktype  |   relation    | pid  |      mode       | fastpath
------------+---------------+------+-----------------+----------
 relation   | ltest6_c1_idx | 3950 | AccessShareLock | f -- 부터 slowpath로 전환됨
 relation   | ltest5_c2_idx | 3950 | AccessShareLock | t
 relation   | ltest5_c1_idx | 3950 | AccessShareLock | t
 relation   | ltest4_c2_idx | 3950 | AccessShareLock | t
 relation   | ltest4_c1_idx | 3950 | AccessShareLock | t

테이블 5개 × relation 3개(테이블 1 + 인덱스 2) = 15개로 슬롯을 채운 뒤, 6번째 테이블을 건드리자 16개를 넘어서면서 fastpath = f가 등장했다. 테이블 6개짜리 조인이면 이미 한계에 닿는다는 것이 이 실험의 요점이다.

정리

  • 테이블 락 모드는 8개이고, 동시 수행 가능 여부는 전적으로 호환표가 결정한다. Access Exclusive는 SELECT도 막는다.
  • 데드락은 대기 그래프의 사이클이다. deadlock_timeout 후 감지되고 한 세션이 희생된다.
  • FK는 마스터 레코드에 KEY SHARE를 걸어 멀티 트랜잭션을 대량 생산한다. pg_stat_slru로 감시한다.
  • 같은 레코드 경합에서 첫 대기자는 transactionid, 나머지는 tuple이다. 규모는 둘을 합쳐 세야 한다.
  • 인덱스는 쓰지 않아도 락을 먹는다. 17까지는 relation 16개가 fastpath 한계, 18부터는 max_locks_per_transaction에 비례한다.

대기이벤트

PostgreSQL은 지금 무엇을 기다리는지는 알려주지만 얼마나 기다렸는지는 알려주지 않는다.

핵심 대기 시간이 없으므로 정공법은 pg_stat_activity를 짧은 주기로 샘플링해 빈도를 쌓는 것이다. 이 한계를 알고 지표를 설계해야 한다.

대기 이벤트

  • 트랜잭션 성능 분석의 핵심은 어디에서 지연이 발생했는지, 얼마나 지연됐는지 측정하는 것이다.
  • PostgreSQL은 9.6부터 대기 이벤트 정보를 제공하기 시작했고 현재 약 200개가 존재한다.

대기 이벤트 유형

  • pg_wait_events 뷰로 시스템에 정의된 모든 대기이벤트의 목록과 유형을 확인할 수 있다.
  • 17 버전 기준 9가지 유형이 존재한다.

대기이벤트 모니터링 방법

  • pg_stat_activity의 wait_event_type, wait_event 컬럼으로 모니터링한다.
  • 값이 있으면 현재 세션이 대기 중이라는 뜻이고, NULL이면 작업을 수행 중인 상태로 해석한다.
  • 버전이 올라가며 제공되는 대기이벤트 수는 계속 늘고 있지만, 이를 모니터링하고 분석할 수단은 여전히 pg_stat_activity뿐이다.
  • PostgreSQL은 대기이벤트의 발생 여부만 알 수 있고, 세부 정보나 대기 시간은 파악할 수 없다는 한계가 있다.

그래서 샘플링한다 보강

오라클의 ASH처럼 대기 시간을 누적해주는 장치가 없으므로, 현실적인 대안은 pg_stat_activity를 1초 내외 주기로 찍어 별도 테이블에 쌓는 것이다. 어떤 대기이벤트가 몇 번 관측됐는가가 대기 시간의 근사치가 된다. pg_stat_statements가 어떤 쿼리가 오래 걸렸는지 알려준다면, 이 샘플링은 왜 오래 걸렸는지를 채워준다. 이 방식을 패키지로 구현한 것이 pg_wait_sampling이나 pgsentinel 같은 확장이다.

DataFileRead 대기 이벤트

  • 디스크 I/O가 발생할 때 관찰된다.
  • 백엔드 프로세스가 쿼리 수행 중 읽어야 할 블록이 공유 버퍼에 없으면 디스크에서 읽어 버퍼에 올리는데, 이 과정에서 발생한다.
  • 자주 발생한다면 인덱스 부재나 결합 인덱스의 비효율성으로 인한 디스크 I/O 증가가 원인일 가능성이 높다.
발생하는 주요 원인
  • 인덱스 부재로 인한 테이블 스캔
  • 비효율적으로 과도한 인덱스 스캔
  • 너무 작은 공유 버퍼

WALInsert 대기 이벤트

  • 백엔드 프로세스는 트랜잭션 수행 시 생성된 변경 정보를 WAL 버퍼에 복사하기 위해, WAL 버퍼 내부에 공간을 할당하고 그 공간에 데이터를 복사한다.
  • WAL 버퍼에 접근하려면 LWLock을 획득해야 하는데, 얻지 못하면 WALInsert 대기이벤트를 대기한다.
  • 이 작업에 쓰는 LWLock은 총 8개로 고정되어 있다. 즉 최대 8개의 백엔드 프로세스가 동시에 WAL 버퍼에 복사할 수 있는 구조다.
  • 대부분 매우 빠르게 처리되어 관찰되지 않는데, 자주 보인다면 WAL 버퍼로의 메모리 복사가 느리거나 전체 트랜잭션 처리량에 비해 WAL 버퍼 공간이 작다는 신호일 수 있다.

WALWrite & WALSync 대기이벤트

이 둘은 항상 함께 관찰되며, 백엔드 프로세스가 WAL 버퍼에 기록된 트랜잭션 정보를 WAL 파일에 기록할 때 발생한다.

WALWrite
  1. 프로세스 메모리 내에 트랜잭션 정보를 기록
  2. WAL 버퍼에 공간을 할당하고 트랜잭션 정보를 복사

    여기서 못 얻으면 WALInsert를 대기한다.

  3. WAL 버퍼의 정보를 WAL 파일에 기록

    이 단계에서 WALWrite용 LWLock 획득이 필요한데, 얻지 못한 프로세스가 WALWrite 대기이벤트를 대기한다.

이 LWLock은 단 1개만 존재한다. 여러 세션이 동시에 커밋하려는 상황에서 단 하나의 세션만 WAL 파일에 쓸 수 있고 나머지는 전부 대기한다.

WALSync
  • WAL 파일의 내용을 디스크에 flush할 때 발생한다.
  • 성능을 위해 WAL 정보를 디스크에 직접 쓰지 않고 OS 버퍼 캐시에 먼저 저장한 뒤 fsync()로 최종 반영한다.
  • fsync() 역시 WALWrite LWLock이 필요하므로, 모니터링 시 WALSync를 대기하는 세션은 항상 1개다.
병목 지점
  • WALWrite, WALSync는 디스크 I/O 성능의 영향을 직접적으로 받는 병목 지점이다.
  • 이 둘을 최소화하려면 WAL 파일이 저장되는 디스크의 쓰기 성능을 개선하는 것이 가장 효과적이다.
  • WAL은 순차적으로 기록되므로 WAL 전용 디스크는 순차 쓰기 성능이 매우 중요하다.
오라클과 PG의 커밋 처리 방식 차이
누가 로그 파일에 쓰는가결과
Oracle LGWR 백그라운드 프로세스만 동시 커밋이 많은 환경에서 다수의 세션이 log file sync를 대기하는 병목이 자주 발생한다
PostgreSQL walwriter 외에 백엔드 프로세스가 직접 일부 병목은 분산되지만 WALWrite/WALSync는 여전히 발생한다. 이 경우 디스크 쓰기 성능이 시스템 전반의 트랜잭션 처리 속도에 직접 영향을 준다

BufferMapping 대기이벤트

  • 공유 버퍼에 접근할 때 BufferMapping LWLock을 획득하지 못하면 이 이벤트를 대기한다.
  • 공유 버퍼는 다음 요소로 구성된다.
    • 해시 테이블
    • 해시 테이블에 연결된 해시 엘리먼트 및 키
    • 버퍼 상태를 관리하는 버퍼 디스크립터
    • 실제 블록을 저장하는 버퍼 풀
  • PostgreSQL은 필요한 블록을 공유 버퍼에서 빠르게 찾을 수 있도록 설계되어 있다.
  • 블록을 읽을 때는 해시 함수를 적용하고 결과에 따라 체인을 탐색하는데, 여기서 BufferMapping Lock을 공유 모드로 획득한다.
    • 공유 모드끼리는 호환되므로 여러 세션이 동시에 해시 체인을 탐색할 수 있다.
  • 공유 버퍼에 원하는 블록이 없으면 디스크에서 읽어 적재해야 한다.
    • 이 과정에서는 해시 체인을 수정해야 하므로 BufferMapping Lock을 배타 모드로 획득한다.
    • 다른 세션이 이미 그 락을 갖고 있다면 BufferMapping 대기이벤트를 대기한다.
  • BufferMapping LWLock은 9.6부터 128개로 늘어 현재까지 유지되고 있다.
    • 다만 하드웨어가 좋아지며 공유 버퍼를 수백 GB로 잡는 경우가 생기면서 한계가 있다는 지적도 있다.

이 이벤트는 디스크 I/O가 있을 때만 보인다

BufferMapping 대기는 배타 모드가 필요한 상황, 즉 디스크에서 블록을 새로 올릴 때만 발생한다. 그래서 단순히 메모리에서만 왔다 갔다 하는 비효율적인 쿼리가 아무리 많아도 이 대기이벤트는 나타나지 않는다. 디스크 I/O가 거의 없는 환경에서는 이 대기이벤트만으로 비효율적인 메모리 I/O 쿼리를 식별할 수 없다. 그쪽은 7-4의 shared_blks_hit으로 찾아야 한다.

transactionid 대기이벤트

  • 다른 세션의 트랜잭션이 아직 끝나지 않은 상태에서, 그 세션이 변경 중인 레코드에 접근하려 할 때 발생한다.
  • 동일 레코드에 대한 락 경합을 의미하므로 앱 로직 점검이 필요하다.
-- 세션#1) 트랜잭션 시작 후 c1 = 1, 2 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 in (1,2);

-- 세션#2) 트랜잭션 시작 후 c1 = 1 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 = 1;

-- 현재 대기 상태
postgres=# SELECT pid, state, wait_event_type || ':' || wait_event AS wait_info, query
FROM pg_stat_activity
WHERE pid = 3967;
 pid  | state  |     wait_info      |               query
------+--------+--------------------+------------------------------------
 3967 | active | Lock:transactionid | update ltest set c2=c2 where c1=1;

tuple 대기이벤트

  • transactionid 락을 대기하던 세션이 아직 끝나지 않은 상태에서, 또 다른 세션이 동일한 레코드를 변경하려 할 때 발생한다.
  • 마찬가지로 동일 레코드에 대한 락 경합이므로 앱 로직 점검이 필요하다.
-- 세션#1) 트랜잭션 시작 후 c1 = 1, 2 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 in (1,2);

-- 세션#2) 트랜잭션 시작 후 c1 = 1 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 = 1;

-- 세션#3) c1 = 1 레코드 수정
postgres=# update ltest set c2 = c2 where c1 = 1;

-- 현재 대기 상태
postgres=# SELECT pid, state, wait_event_type || ':' || wait_event AS wait_info, query
FROM pg_stat_activity
where pid = 4584;
 pid  | state  | wait_info  |                 query
------+--------+------------+----------------------------------------
 4584 | active | Lock:tuple | update ltest set c2 = c2 where c1 = 1;

virtualxid 대기이벤트

  • CIC 옵션을 사용하는 작업 수행 시 락을 대기할 때 발생한다.
  • CIC 작업에서는 idle in transaction 상태의 비정상 세션이 원인인 경우가 많으며, 불필요한 세션을 정리하면 해결된다.
-- 세션#1) 트랜잭션 시작 후 c1 = 1, 2 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 in (1,2);

-- 세션#2) 트랜잭션 시작 후 c1 = 1 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 = 1;

-- 세션#3) CIC 옵션으로 인덱스 생성
postgres=# create index concurrently ltest_n4 on ltest(c1, c2);

-- 대기 상태
postgres=# SELECT pid, state, wait_event_type || ':' || wait_event AS wait_info, query
FROM pg_stat_activity
where pid = 4584;
 pid  | state  |    wait_info    |                        query
------+--------+-----------------+------------------------------------------------------
 4584 | active | Lock:virtualxid | create index concurrently ltest_n4 on ltest(c1, c2);

relation 대기이벤트

  • 락 호환성이 없는 작업을 수행하려 할 때 발생한다.
  • DDL이나 VACUUM FULL 같은 작업이 원인이므로 적절한 시간대에 작업하는 것이 좋다.
-- 세션#1) 트랜잭션 시작 후 c1 = 1, 2 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 in (1,2);

-- 세션#2) 트랜잭션 시작 후 c1 = 1 레코드 수정
postgres=# begin;
postgres=*# update ltest set c2=c2 where c1 = 1;

-- 세션#3) 풀 바큠 수행
postgres=# vacuum full ltest;

-- 대기 상태
postgres=# SELECT pid, state, wait_event_type || ':' || wait_event AS wait_info, query
FROM pg_stat_activity
where pid = 4584;
 pid  | state  |   wait_info   |       query
------+--------+---------------+--------------------
 4584 | active | Lock:relation | vacuum full ltest;
i

Lock: 계열 4종은 한 장의 지도로 읽힌다 보강

대기이벤트무엇을 기다리는가처방
Lock:transactionid같은 레코드를 잡은 첫 번째 대기앱 트랜잭션 로직 / 커밋 지연 점검
Lock:tuple같은 레코드를 잡은 두 번째 이후 대기동일. 경합 규모는 이쪽으로 센다
Lock:virtualxid다른 세션의 트랜잭션이 끝나기를 (주로 CIC)idle in transaction 세션 정리
Lock:relation테이블 락 모드 충돌 (DDL, VACUUM FULL)작업 시간대 조정, lock_timeout 설정

DDL을 서비스 시간에 걸어야 한다면 세션에 SET lock_timeout = '3s'를 먼저 걸어두는 습관이 유용하다. Access Exclusive를 기다리는 DDL 뒤로 SELECT까지 줄줄이 밀리는 사태를 3초 만에 끊어준다.

정리

  • PostgreSQL은 대기 여부만 알려주고 대기 시간은 주지 않는다. 샘플링으로 빈도를 쌓아 근사한다.
  • WAL 경로에는 세 개의 관문이 있다. 버퍼 복사(WALInsert, LWLock 8개) → 파일 쓰기(WALWrite, LWLock 1개) → flush(WALSync).
  • WAL 디스크는 순차 쓰기 성능이 전부다. 여기가 곧 트랜잭션 처리량의 천장이다.
  • BufferMapping은 디스크 I/O가 있을 때만 보인다. 메모리 낭비 쿼리는 이걸로 못 찾는다.
  • Lock: 계열 4종(transactionid / tuple / virtualxid / relation)은 원인과 처방이 각각 다르다.
