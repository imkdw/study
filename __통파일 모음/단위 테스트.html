CH 1

단위 테스트의 목표

단위 테스트의 목표는 좋은 설계도, 높은 커버리지도 아니다. 소프트웨어 프로젝트의 지속 가능한 성장이다. 이 한 문장이 나머지 열 개 챕터의 판단 기준이 된다.

1-1

단위 테스트 현황

질문은 "테스트를 써야 하나" 에서 "좋은 테스트란 뭔가" 로 옮겨왔다.

핵심 테스트를 작성하는 것 자체는 이미 논쟁거리가 아니다. 남은 문제는 노력 대비 최대의 이익을 내는 방식으로 쓰는 법이다.

단위 테스트는 이미 업계 표준에 가깝게 자리 잡았다. 프로젝트에 따라 제품 코드와 테스트 코드의 비율이 1:1 에서 1:10 까지 다양하게 나타나고, 그 비율 자체는 좋고 나쁨을 말해주지 않는다.

문제는 그 다음이다. 테스트가 있는데도 개발자들이 원하는 결과를 얻지 못하는 경우가 많다. 배포가 여전히 무섭고, 리팩터링은 여전히 망설여진다. 그래서 지금 던져야 할 질문은 이렇게 바뀐다.

✓

질문의 이동

"단위 테스트를 작성해야 되는가?" → "좋은 단위 테스트를 작성하는 건 어떤 의미인가?"

정리

  • 테스트 코드의 양이나 비율은 품질을 말해주지 않는다.
  • 단순한 테스트 작성이 아니라 노력 대비 이익을 기준으로 삼는다.
  • 이 책 전체가 "무엇이 좋은 테스트인가" 에 대한 판단 기준을 세우는 과정이다.
1-2

단위 테스트 목표

목표는 좋은 설계가 아니라 소프트웨어 프로젝트의 지속 가능한 성장이다.

핵심 단위 테스트의 목표는 소프트웨어 프로젝트의 지속 가능한 성장이다. 좋은 설계는 그 과정에서 따라오는 사이드 이펙트일 뿐이다.

코드베이스에 대해 단위 테스트를 작성하다 보면 일반적으로 더 나은 설계로 이어진다. 테스트하기 어려운 코드는 대개 결합도가 높은 코드이기 때문이다. 다만 이것을 단위 테스트의 주된 목표로 두면 방향을 잃는다. 좋은 설계는 좋은 사이드 이펙트일 뿐이다.

진짜 목표는 성장 곡선에 있다. 초기에는 테스트 작성으로 시간이 더 걸리지만, 시간이 갈수록 효율이 역전된다.

테스트 없는 프로젝트는 어느 시점부터 침체 국면에 빠진다 — 초기에는 테스트가 더 느리지만, 진척도가 쌓일수록 두 곡선은 교차하고 다시는 만나지 않는다.

결국 테스트는 안전망 역할을 하며, 대부분의 회귀(regression) 에 대한 보험을 제공하는 도구다. 코드베이스를 지속적으로 검증하는 테스트 없이는 소프트웨어 개발이 쉽게 확장되지 않는다.

좋은 테스트와 좋지 않은 테스트를 가르는 요인

여기서 중요한 반전이 있다. 테스트가 프로젝트 성장에 도움이 되는 건 맞지만, 단순히 작성한다고 도움이 되는 건 아니다. 모든 테스트를 작성할 필요도 없다.

테스트를 하나 더 쓸 때마다 아래 비용이 함께 늘어난다는 걸 계산에 넣어야 한다.

  • 기반 코드를 리팩터링할 때 테스트도 함께 리팩터링해야 한다
  • 각 코드 변경마다 테스트를 실행해야 한다
  • 테스트가 잘못된 경고를 발생시키면 그것도 처리해야 한다
  • 기반 코드가 어떻게 동작하는지 이해하려 할 때 테스트를 읽는 시간이 든다

가치와 유지비를 함께 저울에 올렸을 때 유지비가 이기는 테스트가 코드베이스에 쌓이면, 그래프는 아래처럼 된다.

잘못된 테스트를 포함한 프로젝트는 테스트가 아예 없는 것보다 조금 나은 정도에 그친다 — 노란 곡선은 초반엔 파란 곡선 아래에 있지만 끝내 위로 올라선다.
!

지속 가능한 성장의 조건

테스트를 늘리는 것이 아니라 고품질 테스트에만 집중해야 한다. 가치가 유지비를 넘지 못하는 테스트는 코드베이스에 있는 것이 없느니만 못하다.

정리

  • 단위 테스트의 목표는 지속 가능한 프로젝트 성장이다. 좋은 설계는 부산물이다.
  • 테스트는 회귀에 대한 보험이며, 없으면 개발이 확장되지 않는다.
  • 모든 테스트를 쓸 필요는 없다. 항상 가치와 유지비를 함께 계산한다.
  • 잘못된 테스트가 쌓인 프로젝트는 테스트 없는 프로젝트와 크게 다르지 않다.
1-3

테스트 스위트 품질 측정을 위한 커버리지 지표

커버리지는 좋은 부정 지표이지만 나쁜 긍정 지표다.

핵심 커버리지 10% 는 확실히 나쁜 신호다. 하지만 커버리지 100% 라고 해서 좋은 테스트 스위트라는 뜻은 전혀 아니다.

커버리지 지표는 테스트 스위트가 소스 코드를 얼마나 실행하는지 백분율로 나타낸다. 중요한 피드백을 주기는 하지만, 이것만으로 테스트 품질을 효과적으로 측정할 수는 없다.

코드 커버리지 지표에 대한 이해

코드 커버리지(테스트 커버리지)는 실행 코드 라인 수 / 전체 라인 수 다. 라인 수만 세기 때문에, 동작을 하나도 바꾸지 않고 코드를 줄이는 것만으로 지표가 올라간다.

1-2.spec.ts 
import { isStringLong } from "../1-2.js";

describe("isStringLong", () => {
  it("문자열의 길이가 5보다 크다면 true 반환", () => {
    expect(isStringLong("123456")).toBe(true);
  });
});

동일한 이 테스트 하나를 두고, 제품 코드만 바꿔보자.

export const isStringLong = (str: string): boolean => {
  if (str.length > 5) {
    return true;

  return false;

두 버전 모두 "123456" 하나만 검증한다. 검증 범위는 조금도 넓어지지 않았는데 커버리지는 80% 에서 100% 가 됐다. 코드가 작을수록 커버리지 지표가 좋아진다는 뜻이다.

분기 커버리지 지표에 대한 이해

분기 커버리지는 코드 커버리지의 이 단점을 극복하므로 더 정확한 결과를 준다. 원시 코드 라인 수 대신 if, switch 같은 제어 구조에 중점을 둔다.

계산식은 통과 분기 수 / 전체 분기 수 다. 코드베이스의 모든 가능한 분기를 합산하고, 그중 테스트가 얼마나 실행하는지 확인한다.

1-2.ts 
export const isStringLong = (str: string): boolean => {
  // 이 한 줄이 다루는 분기는 두 개다
  //   str.length >  5  -> true
  //   str.length <= 5  -> false
  // 테스트가 true 케이스만 검증하므로 분기 커버리지는 50%
  return str.length > 5;
};

라인 커버리지가 100% 인 바로 그 코드의 분기 커버리지가 50% 다. 같은 테스트를 두고도 두 지표가 이렇게 갈린다.

커버리지 지표에 관한 문제점

분기 커버리지조차도 품질의 근거가 될 수 없다. 두 가지 이유가 있다.

가능한 모든 결과를 검증한다고 보장할 수 없다

커버리지는 코드가 실행됐는지만 볼 뿐, 그 결과를 검증했는지는 보지 않는다. 테스트에서 결과가 여러 개라면 그 모두를 검증해야 지표가 유의미해진다.

1-2.ts 
export const isStringLong = (str: string): boolean => {
  const result = str.length > 5;
  wasLastStringLong = result; // 검증되지 않는 두 번째 결과
  return result;
};

두 케이스를 모두 통과시켜 라인 / 분기 모두 100% 를 찍어도, wasLastStringLong 이 올바른지는 아무도 확인하지 않았다.

외부 라이브러리 코드 경로를 고려할 수 없다
parse.ts 
export const parse = (str: string): number => {
  return parseInt(str, 10);
};

describe("parse", () => {
  it("`1234`를 숫자로 변환하면 1234다", () => {
    expect(parse("1234")).toBe(1234);
  });
});

parseInt 내부에는 공백 처리, 부호 처리, 파싱 실패 시 NaN 반환 같은 다양한 경로가 있다. 커버리지는 100% 로 나오지만 그 경로들은 하나도 테스트되지 않았다.

이 한계 때문에 커버리지 대신 뮤테이션 테스팅(mutation testing) 을 쓰기도 한다. 제품 코드를 일부러 조금씩 바꿔놓고(> 를 >= 로 등) 테스트가 실패하는지 보는 방식이라, "실행됐는가" 가 아니라 "검증됐는가" 를 직접 측정한다. JS/TS 진영에서는 Stryker Mutator 가 대표적이다.

커버리지 목표치를 강제하면 벌어지는 일

숫자를 목표로 삼는 순간 개발자는 가치 있는 테스트가 아니라 숫자를 채우는 테스트를 쓰기 시작한다. 커버리지는 관찰하되, 통과 기준으로 삼지 않는다.

커버리지 지표는 좋은 부정 지표이지만 나쁜 긍정 지표다. 60% 처럼 낮은 숫자는 문제의 징후로 읽을 만하지만, 높은 숫자는 아무것도 보증하지 않는다.

정리

  • 코드 커버리지 = 실행 라인 / 전체 라인. 코드를 줄이는 것만으로도 올라간다.
  • 분기 커버리지 = 통과 분기 / 전체 분기. 더 정확하지만 여전히 충분하지 않다.
  • 커버리지는 검증 여부와 외부 라이브러리 경로를 볼 수 없다.
  • 낮은 커버리지는 나쁜 신호, 높은 커버리지는 좋은 신호가 아니다. 목표치로 삼지 않는다.

무엇이 성공적인 테스트를 만드는가

개발 주기에 통합되고, 가장 중요한 부분만 겨냥하고, 최소 유지비로 최대 가치를 낸다.

핵심 코드베이스의 모든 부분에 똑같이 주목할 필요는 없다. 비즈니스 로직이 있는 도메인 모델이 시간 투자 대비 최고의 수익을 낸다.

개발 주기에 통합되어 있음

자동화된 테스트를 유지하는 방법은 끊임없이 실행하는 것뿐이다. 코드 변경마다 돌아가지 않는 테스트는 곧 아무도 안 보는 테스트가 된다. 모든 테스트는 개발 주기에 통합되어야 한다.

코드베이스에서 가장 중요한 부분만을 대상으로 한다

대부분의 앱에서 가장 중요한 부분은 비즈니스 로직이 존재하는 도메인 모델이다. 인프라 코드나 외부 시스템 연동, 프레임워크 설정은 같은 노력을 들여도 같은 가치를 돌려주지 않는다.

가치 있는 테스트 작성하기

식별만으로는 부족하다. 테스트하기 좋은 코드로 제품 코드를 바꾸는 일까지가 세트다. 의미 없는 부분이 아니라 비즈니스 로직처럼 가치 있는 부분에 테스트를 만든다.

정리

  • 테스트는 개발 주기에 통합되어 계속 실행되어야 의미가 있다.
  • 도메인 모델 / 비즈니스 로직이 투자 대비 수익이 가장 높다.
  • 가치 있는 테스트를 식별하는 기준 틀과, 그렇게 쓸 수 있도록 코드를 바꾸는 작업이 함께 간다.
CH 2

단위 테스트란 무엇인가

"작은 코드 조각을, 빠르게, 격리해서" 라는 정의에서 마지막 단어 하나 때문에 런던파와 고전파가 갈린다. 무엇을 무엇으로부터 격리할 것인가.

2-1

단위 테스트의 정의

작게, 빠르게, 격리해서. 마지막 단어 하나에서 두 분파가 갈린다.

핵심 "격리" 를 SUT 를 협력자에게서 떼는 것으로 읽으면 런던파, 단위 테스트끼리 떼는 것으로 읽으면 고전파다.

정의

단위 테스트는 아래 세 가지를 만족하는 자동화된 테스트다.

  1. 작은 코드 조각을 검증한다

    흔히 "단위" 라고 부르는 그것.

  2. 빠르게 수행한다

    테스트 스위트 전체의 실행 시간이 충분히 짧으면 충분히 빠른 것이다.

  3. 격리된 방식으로 처리한다

    바로 여기서 고전파와 런던파가 갈린다.

첫 번째와 두 번째는 대체로 이견이 없다. 세 번째 속성만이 논쟁거리다.

고전파 예제

준비 / 실행 / 검증 세 구절로 나뉜다.

  • 준비 — 의존성과 테스트 대상 시스템을 모두 준비한다. 아래 예제에서는 고객(Customer)이 SUT, 상점(Store)이 협력자다.
  • 실행 — 검증하고자 하는 동작을 수행한다.
  • 검증 — 그 동작이 예상 결과로 이어지는지 확인한다.
2-1.spec.ts 고전파 
const Product = {
  Shampoo: "Shampoo",
  Book: "Book",
};

it("purchase_succeeds_when_enough_inventory", () => {
  // 준비
  const store = new Store();
  store.addInventory(Product.Shampoo, 10);
  const customer = new Customer();

  // 실행
  const success = customer.purchase(store, Product.Shampoo, 5);

  // 검증
  expect(success).toBe(true);
  expect(store.getInventory(Product.Shampoo)).toBe(5);
});

it("purchase_fails_when_not_enough_inventory", () => {
  // 준비
  const store = new Store();
  store.addInventory(Product.Shampoo, 10);
  const customer = new Customer();

  // 실행
  const success = customer.purchase(store, Product.Shampoo, 15);

  // 검증
  expect(success).toBe(false);
  expect(store.getInventory(Product.Shampoo)).toBe(10);
});

여기서 Customer 가 올바르게 작동해도 Store 가 올바르지 않으면 검증에 실패한다. 두 클래스는 서로 격리돼 있지 않다.

런던파 예제

실제 Store 인스턴스를 만들지 않고 jest.fn() 으로 대체한다. 대체한 목의 메소드 반환값을 직접 지정하고, toHaveBeenCalledWith 로 호출 여부와 전달된 인자까지 검증할 수 있다.

2-1.spec.ts 런던파 
it("purchase_succeeds_when_enough_inventory", () => {
  // 준비
  const storeMock = {
    hasEnoughInventory: jest.fn().mockReturnValue(true),
    removeInventory: jest.fn(),
  };
  const customer = new Customer();

  // 실행
  const success = customer.purchase(storeMock, Product.Shampoo, 5);

  // 검증
  expect(success).toBe(true);
  expect(storeMock.hasEnoughInventory).toHaveBeenCalledWith(Product.Shampoo, 5);
});

it("purchase_fails_when_not_enough_inventory", () => {
  // 준비
  const storeMock = {
    hasEnoughInventory: jest.fn().mockReturnValue(false),
    removeInventory: jest.fn(),
  };
  const customer = new Customer();

  // 실행
  const success = customer.purchase(storeMock, Product.Shampoo, 15);

  // 검증
  expect(success).toBe(false);
  expect(storeMock.removeInventory).toHaveBeenCalledTimes(0);
});

격리 문제에 대한 런던파의 접근

런던파에서 격리란 테스트 대상 시스템을 협력자에게서 떼어내는 것이다. 하나의 클래스가 다른 클래스에 의존하면, 그 모든 의존성을 테스트 대역(test double) 으로 대체한다.

flowchart LR
  SUT["테스트 대상 시스템"] --> D1["의존성 1"]
  SUT --> D2["의존성 2"]
  D1 -.->|"교체"| M1["테스트 대역 1"]
  D2 -.->|"교체"| M2["테스트 대역 2"]
  SUT2["테스트 대상 시스템"] --> M1
  SUT2 --> M2
모든 협력자를 대역으로 바꾸면 해당 시스템 검증에만 집중할 수 있다 — 클래스마다 자기 테스트를 갖게 되고, 그 테스트는 오직 자기 클래스의 결함에만 반응한다.

의존성을 가진 코드베이스를 테스트 대역 없이 테스트하는 건 힘들다. 방법이 없진 않지만 결국 의존성 그래프를 직접 전부 만들어줘야 하는데, 이는 매우 고된 작업이다.

격리 문제에 대한 고전파의 접근

런던 스타일은 대역으로 코드 조각을 분리해 격리 요구 사항에 다가간다. 모든 클래스를 격리해야 한다면 테스트 대상 코드 조각은 당연히 단일 클래스나 그 클래스의 메소드여야 한다.

고전파는 다르다. 여러 클래스를 동시에 테스트해도 되고, 테스트 대역은 테스트 간 공유 상태를 일으키는 의존성에만 쓴다.

flowchart LR
  T["단위 테스트"] --> SUT["테스트 대상 시스템"]
  SUT -->|"공유 의존성 / 교체"| DB[("DB")]
  SUT -->|"공유 의존성 / 교체"| FS["파일 시스템"]
  SUT -->|"비공개 의존성 / 유지"| C["다른 클래스"]
고전파가 대역으로 바꾸는 것은 공유 의존성뿐이다 — 다른 클래스는 실제 인스턴스를 그대로 쓴다. 격리해야 하는 대상은 협력자가 아니라 단위 테스트끼리다.

공유 / 비공개 / 프로세스 외부 의존성

공유 의존성(Shared Dependency)

테스트 간에 공유되어 서로의 결과에 영향을 미칠 수 있는 수단을 제공하는 의존성이다. 전형적인 예가 정적 가변 필드(static mutable field) 다. 이 필드의 변경 사항은 동일한 프로세스에서 실행되는 모든 단위 테스트에서 보인다. 데이터베이스도 대표적인 공유 의존성이다.

비공개 의존성(Private Dependency)

공유하지 않는 의존성이다.

프로세스 외부 의존성(Out-of-Process Dependency)

앱 실행 시 프로세스 외부에서 실행되는 의존성으로, 아직 메모리에 없는 데이터에 대한 프록시다. 디비는 프로세스 외부이면서 공유 의존성이다. 다만 테스트마다 도커 컨테이너로 디비를 띄운다면 프로세스 외부이지만 공유 의존성은 아니다. 그런 환경에서는 한 테스트의 데이터 변경이 다른 테스트 결과에 영향을 주지 않기 때문이다.

i

공유는 "테스트 대상 사이" 가 아니라 "테스트 사이" 다

공유 의존성은 테스트 대상 클래스들끼리 공유하는 것이 아니라 단위 테스트끼리 공유하는 것이다. 싱글턴 의존성이라도 각 테스트에서 새 인스턴스를 만들 수 있기만 하면 공유되지 않는다.

공유 / 휘발성 의존성

휘발성 의존성(volatile dependency)은 아래 중 하나에 해당한다.

  • 개발자 머신에 기본으로 설치돼 있지 않아, 런타임 환경의 설정과 구성을 별도로 요구한다. 디비와 API 서비스가 대표적이다.
  • 비결정적 동작(nondeterministic behavior) 을 포함한다. 난수를 생성하거나 현재 날짜를 반환하는 클래스처럼, 호출마다 다른 결과를 주는 것들이다.

공유 의존성을 가진 테스트는 단위 테스트 영역에서 통합 테스트 영역으로 넘어간다. 반대로 말하면, 단위 테스트는 클래스 하나에 국한될 필요가 없다. 공유 의존성이 없는 한 여러 클래스를 묶어서 단위 테스트할 수 있다.

정리

  • 단위 테스트 = 작은 코드 조각 + 빠른 수행 + 격리. 세 번째에서 분파가 갈린다.
  • 런던파는 SUT 를 협력자로부터, 고전파는 단위 테스트끼리 격리한다.
  • 공유 의존성은 테스트끼리 서로 영향을 주는 통로다. 정적 가변 필드, 디비가 대표적이다.
  • 공유 의존성이 없다면 여러 클래스를 묶어도 여전히 단위 테스트다.
2-2

단위 테스트의 런던파와 고전파

무엇을 교체할 것인가에 대한 두 답. 협력자 전부인가, 공유 의존성만인가.

핵심 런던파는 불변 의존성을 제외한 모든 것을, 고전파는 공유 의존성만 대역으로 바꾼다.

두 분파는 세 가지 주제에서 의견이 갈린다.

분류격리 주체단위의 크기테스트 대역 사용 대상
런던파단위단일 클래스불변 의존성 외 모든 의존성
고전파단위 테스트단일 클래스 또는 클래스 세트공유 의존성

고전파와 런던파가 의존성을 다루는 방법

절대 변하지 않는 객체, 즉 불변 객체는 교체하지 않아도 된다. ENUM 처럼 값이 고정된 것들이 그렇다. 불변 객체의 주요 특징은 각각의 정체성이 없고 내용에 의해서만 식별된다는 점이다.

비공개 의존성은 변경 가능할 수도 있고 불변일 수도 있다. 디비 의존성은 공유 의존성이며, 그 내부 상태는 모든 자동화된 테스트가 함께 본다.

고전파에서 교체"]
  D --> P["비공개 의존성"]
  P --> M["변경 가능 의존성"]
  P --> V["값 객체
교체 대상 아님"]

런던파에서 교체"]

원문 교정 원문 교정

노트에는 "Store 인스턴스는 변경 가능한 비공개 의존성이고, Product 인스턴스는 변경 가능한 비공개 의존성" 이라고 적혀 있지만, Product 는 불변 값 객체다. ENUM 처럼 정체성이 없고 내용으로만 식별되므로 교체 대상이 아니다.

협력자 vs 의존성

협력자(collaborator) 는 공유하거나 변경이 가능한 의존성이다.

  • 디비는 공유 의존성이므로 디비 접근 권한을 제공하는 클래스는 협력자다.
  • 앞 예제의 Store 도 시간에 따라 상태가 변할 수 있으므로 협력자다.
  • Product 와 숫자 5 는 의존성이지만 협력자가 아니다. 값 또는 값 객체로 분류된다.

프로세스 외부 의존성이 공유 의존성이 되려면, 그것이 단위 테스트끼리 서로 통신할 수 있는 수단을 제공해야 한다.

예시 — 읽기 전용 API 는 공유 의존성이 아니다

조직이 판매하는 모든 제품 카탈로그를 반환하는 API 가 있다고 하자. 이 API 가 카탈로그를 변경하는 기능을 노출하지 않는 한 공유 의존성이 아니다. 휘발성이고 앱 경계를 벗어나는 것은 사실이지만, 테스트가 반환 데이터에 영향을 미칠 수 없으므로 공유가 아니다.

두 축은 서로 독립이다 — 싱글턴은 공유이지만 프로세스 내부, 읽기 전용 API 는 프로세스 외부이지만 공유가 아니다. 디비만 교집합에 놓인다.

다만 대부분의 경우 테스트 속도를 위해 이런 외부 API 도 대역으로 교체한다. 충분히 빠르고 연결이 안정적이라면 실제로 써도 괜찮다.

정리

  • 런던파는 값 객체를 뺀 모든 의존성을, 고전파는 공유 의존성만 교체한다.
  • 협력자 = 공유 의존성 ∪ 변경 가능 의존성. 값 객체는 협력자가 아니다.
  • 프로세스 외부라고 다 공유는 아니다. 테스트끼리 통신할 수단을 제공해야 공유다.
2-3

고전파와 런던파의 비교

런던파의 세 가지 이점은 모두 그럴듯하지만, 각각 반론이 있다.

핵심 테스트는 코드의 단위가 아니라 동작의 단위를 검증해야 한다. 이 한 문장이 런던파의 세 이점을 모두 되받는다.

목을 사용하는 런던파 테스트는 고전파 테스트보다 불안정한 경향이 있다. 그럼에도 런던파가 내세우는 이점은 분명하다.

런던파 접근 방식의 이점

  • 테스트가 세밀해서 한 번에 한 클래스만 확인한다. 즉 입자성이 좋다.
  • 의존성 그래프가 커져도 테스트가 쉽다. 모든 협력자가 대역으로 대체되므로 그래프를 걱정할 필요가 없다.
  • 테스트 대상 클래스 외에 의심할 여지가 없어서 어떤 기능이 실패했는지 확실히 파악할 수 있다.

한 번에 한 클래스만 테스트하기

OOP 개발자는 클래스를 코드베이스의 기초에 있는 원자 빌딩 블록으로 본다. 그래서 자연스럽게 클래스를 테스트에서 검증할 원자 단위로 취급하는데, 여기에 오해의 소지가 있다.

✓

단위는 클래스가 아니라 동작이다

테스트는 코드의 단위를 검증해서는 안 되고 동작의 단위, 즉 문제 영역에서 의미가 있는 것을 검증해야 한다. 테스트는 해결하려는 문제에 대한 이야기를 들려줘야 하며, 그 이야기는 일반 사람들에게도 응집도 있고 의미 있어야 한다.

상호 연결된 클래스의 큰 그래프를 단위 테스트하기

런던파처럼 협력자를 목으로 대체하면 복잡한 의존성 그래프를 가진 동작도 쉽게 테스트할 수 있다. 하지만 순서가 뒤집혔다. 협력자를 모킹하기 전에 그런 의존성 그래프를 갖지 않는 데 먼저 집중해야 한다. 일반적으로 그래프가 커진 것은 코드 설계 문제의 결과다.

버그 위치 정확히 찾아내기

런던파에서는 시스템에 버그가 생기면 그 버그를 포함한 SUT 의 테스트만 실패한다. 반대로 고전파에서는 오작동하는 클래스를 참조하는 클라이언트의 테스트까지 함께 실패하며, 하나의 버그가 전체 시스템에 걸쳐 테스트 실패의 파급 효과를 일으킨다.

다만 이는 생각만큼 큰 문제가 아니다. CI 과정에서 테스트를 정기적으로 실행하면 마지막으로 성공한 커밋과의 차이로 버그 위치를 금방 좁힐 수 있고, 오히려 실패한 테스트 전체가 그 버그의 영향 범위를 보여준다는 점에서 가치가 있다.

고전파와 런던파의 다른 점

나머지 차이는 TDD 를 통한 시스템 설계 방식과 과도한 명세에 있다.

런던 스타일 — 하향식 TDD

시스템에 대한 기대치를 설정하는 상위 레벨 테스트부터 시작한다. 모든 클래스를 구현할 때까지 클래스 그래프를 아래로 다져 나간다. SUT 의 모든 협력자를 차단하므로 그 협력자의 구현을 나중으로 미룰 수 있다.

고전 스타일 — 상향식 TDD

테스트에서 의존성에 대한 실제 객체를 다뤄야 하므로 같은 지침을 두지 않는다. 도메인 모델에서 시작해 최종 사용자가 소프트웨어를 사용할 수 있을 때까지 그 위에 계층을 더한다.

정리

  • 런던파의 세밀한 입자성은 동작이 아니라 코드를 단위로 삼는 오해에서 온다.
  • 큰 의존성 그래프는 모킹으로 덮을 게 아니라 설계로 줄여야 한다.
  • 고전파의 파급 실패는 CI 를 정기 실행하면 해결되고, 오히려 영향 범위를 보여준다.
  • 런던파는 하향식 TDD, 고전파는 상향식 TDD 로 이어진다.
2-4

두 분파의 통합 테스트

단위 테스트의 세 조건 중 하나라도 못 맞추면 그것은 통합 테스트다.

핵심 통합 테스트는 단위 테스트의 특성을 만족하지 못하는 모든 테스트다. E2E 는 그중 의존성을 가장 많이 포함하는 부분집합이다.

런던파는 실제 협력자 객체를 사용하는 모든 테스트를 통합 테스트로 간주한다. 그러면 고전파의 테스트 상당수가 런던파 기준으로는 통합 테스트가 된다.

통합 테스트의 일부인 E2E 테스트

통합 테스트는 공유 / 프로세스 외부 의존성뿐 아니라 조직 내 다른 팀이 개발한 코드까지 통합해서 검증한다. 그 안에 E2E(end-to-end) 테스트 개념이 포함되며, E2E 는 일반적으로 더 많은 의존성을 포함한다.

세 테스트는 동심원 관계다 — 단위 테스트는 프로세스 안쪽만, 통합 테스트는 앱이 통제하는 디비까지, E2E 는 결제 게이트웨이 같은 외부 앱까지 포함한다.

E2E 는 모든 외부 앱을 포함해 시스템을 최종 사용자의 관점에서 검증한다. 일반적으로 디비나 파일 시스템은 실제로 포함하지만, 결제 게이트웨이처럼 외부에 의존하는 것은 대역으로 대체한다.

!

E2E 는 언제 돌리나

유지 보수 측면에서 가장 비싸다. 모든 단위 테스트와 통합 테스트를 통과한 뒤 빌드 프로세스 후반에 실행하는 것이 좋다.

정리

  • 단위 테스트의 세 조건을 하나라도 못 맞추면 통합 테스트다.
  • E2E 는 통합 테스트의 부분집합이며 의존성을 가장 많이 포함한다.
  • E2E 에서도 결제 같은 외부 시스템은 보통 대역으로 대체한다.
  • 가장 비싸므로 빌드 후반에 배치한다.
CH 3

단위 테스트 구조

AAA 로 뼈대를 세우고, 픽스처 재사용과 이름 짓기로 살을 붙인다. 테스트 하나는 문제 영역에 대한 원자적인 사실 하나여야 한다.

3-1

단위 테스트를 구성하는 방법

준비 / 실행 / 검증. 구절의 크기가 곧 설계의 신호다.

핵심 실행 구절이 두 줄을 넘으면 SUT 의 공개 API 에 문제가 있다. 테스트 구조는 제품 코드 설계를 되비추는 거울이다.

AAA 패턴 사용

각 테스트를 준비(Arrange) / 실행(Act) / 검증(Assert) 세 부분으로 나눈다. 테스트 스위트 내 모든 테스트가 단순하고 균일한 구조를 갖게 되며, 이 일관성이 패턴의 가장 큰 장점이다.

TDD 를 할 때는 기능이 어떻게 동작할지 아직 모르므로 기대하는 동작(검증)으로 먼저 윤곽을 잡고 개발한다. 반대로 테스트 전에 제품 코드를 작성했다면 무엇을 예상하는지 이미 알고 있으므로 준비 구절부터 시작하는 편이 좋다.

구절하는 일
준비테스트 대상 시스템(SUT)과 해당 의존성을 원하는 상태로 만든다
실행SUT 의 메소드를 호출하고, 준비된 의존성을 전달하며, 출력 값을 캡처한다
검증실행 결과를 검증한다. 반환값, 협력자의 상태, 협력자에 호출한 메소드 등으로 검증할 수 있다
3-1.ts 
export default class Calculator {
  sum(first: number, second: number) {
    return first + second;
  }
}
3-1.spec.ts 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  // 준비
  const first = 10;
  const second = 20;
  const calculator = new Calculator();

  // 실행
  const result = calculator.sum(first, second);

  // 검증
  expect(result).toBe(30);
});
Given-When-Then 패턴

AAA 와 사실상 같은 패턴이다. Given 이 준비, When 이 실행, Then 이 검증에 대응한다. 두 패턴에 기능적 차이는 없고, 비개발자가 읽기에는 Given-When-Then 이 더 읽기 쉽다는 점만 다르다.

여러 개의 준비, 실행, 검증 구절 피하기

준비 → 실행 → 검증 → 더 실행 → 다시 검증 같은 테스트를 만날 수 있다. 이런 테스트는 더 이상 단위 테스트가 아니라 통합 테스트다.

실행이 하나라면 테스트가 단위 테스트 범주에 있게끔 보장되고, 간단하고 빠르며 이해하기 쉽다. 일련의 실행과 검증이 포함된 테스트를 보면 리팩터링해서 각 동작을 고유의 테스트로 도출한다.

테스트 내 if 피하기

단위 테스트든 통합 테스트든, 테스트는 분기가 없는 간단한 일련의 단계여야 한다. if 문은 테스트가 한 번에 너무 많은 것을 검증한다는 표시다. 분기가 있어서 얻는 이점은 없고 추가 유지비만 불어난다.

각 구절은 얼마나 커야 하는가

준비 구절이 가장 큰 경우

일반적으로 준비 구절이 세 구절 중 가장 크다. 너무 크다면 같은 테스트 클래스 내의 비공개 메소드나 별도의 팩토리 클래스로 도출하는 게 좋다. 코드 재사용에 도움이 되는 패턴으로 오브젝트 마더(Object Mother) 와 테스트 데이터 빌더(Test Data Builder) 가 있다.

실행 구절이 한 줄 이상인 경우를 경계하라

실행 구절은 보통 코드 한 줄이다. 두 줄 이상이라면 SUT 의 공개 API 에 문제가 있다는 신호다. 클라이언트가 두 단계를 순서대로 올바르게 호출해야만 객체가 일관된 상태를 유지한다면, 그 순서를 어기는 순간 모순이 생긴다.

!

불변 위반과 캡슐화

이런 모순을 불변 위반(invariant violation) 이라 하고, 잠재적 모순으로부터 코드를 보호하는 행위를 캡슐화라고 한다. 해결책은 캡슐화를 항상 지키는 것, 즉 불변 위반을 초래할 수 있는 잠재적 행동 자체를 API 에서 제거하는 것이다.

검증 구절에는 검증문이 얼마나 있어야 할까

단위 테스트의 단위는 동작의 단위이지 코드의 단위가 아니다. 단일 동작 단위는 여러 결과를 낼 수 있고, 하나의 테스트로 그 모든 결과를 평가하는 게 좋다.

그렇다고 검증이 너무 많아지는 것은 경계해야 한다. 객체의 모든 속성을 하나하나 검증하는 대신, 클래스 내에 적절한 동등 멤버를 정의해서 객체 단위로 비교하는 편이 낫다.

종료 단계는 어떤가

단위 테스트는 프로세스 외부에 종속적이지 않으므로 처리해야 할 사이드 이펙트를 남기지 않는다. 일반적으로 단위 테스트에는 종료 구절이 필요 없다.

테스트 대상 시스템 구별하기

SUT 는 앱에서 호출하고자 하는 동작에 대한 진입점을 제공한다. 동작은 여러 클래스에 걸칠 만큼 크거나 단일 메소드만큼 작을 수 있지만, 진입점은 하나만 존재해야 한다.

테스트에 여러 객체가 등장하면 무엇이 테스트 대상인지 헷갈린다. SUT 에 해당하는 변수의 이름을 sut 로 고정하면 이 문제가 사라진다.

3-1.spec.ts sut 로 이름 고정 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  // 준비
  const first = 10;
  const second = 20;
  const sut = new Calculator(); // 테스트 대상을 sut 으로

  // 실행
  const result = sut.sum(first, second);

  // 검증
  expect(result).toBe(30);
});
!

원문 교정 원문 교정

노트에서는 const sut = calculator.sum(...) 처럼 실행 결과에 sut 라는 이름을 붙였는데, sut 는 테스트 대상 객체 자체에 붙이는 이름이다. 결과 변수는 result 로 두고 new Calculator() 쪽을 sut 로 바꾸는 것이 원서의 의도다.

준비, 실행, 검증 주석 제거하기

주석 대신 각 단계를 빈 줄로 띄우는 방법이 흔히 쓰인다. 다만 통합 테스트에서는 준비 / 검증 구절이 여러 문단으로 나뉠 만큼 복잡해지는 경우가 있다.

기준은 이렇다. 구절 안쪽에 빈 줄을 넣지 않아도 되는 테스트라면 주석을 지우고, 그렇지 않다면 주석을 남긴다.

3-1.spec.ts 주석 없이 빈 줄로만 
import Calculator from "../3-1";

it("sum_of_two_numbers", () => {
  const first = 10;
  const second = 20;
  const sut = new Calculator();

  const result = sut.sum(first, second);

  expect(result).toBe(30);
});

정리

  • AAA 로 구조를 통일한다. Given-When-Then 과 기능적 차이는 없다.
  • 실행 구절이 두 줄 이상이면 공개 API 의 캡슐화 문제를 의심한다.
  • 다단계 테스트와 if 는 나눠서 없앤다.
  • 테스트 대상 변수는 sut 으로 이름을 고정한다.
  • 구절 안에 빈 줄이 필요 없으면 AAA 주석을 지운다.
3-2

XUnit 테스트 프레임워크

테스트 하나는 문제 영역에 대한 원자적인 사실 하나여야 한다.

핵심 테스트가 통과한다는 것은 그 사실 또는 시나리오가 실제로 참이라는 증거다. 제품 코드의 기능 목록을 나열하는 것이 아니다.

각 테스트는 이야기를 가져야 한다. 그 이야기는 문제 영역에 대한 개별적이고 원자적인 사실 또는 시나리오여야 하며, 테스트 통과는 그 사실이 참이라는 증거가 된다.

테스트가 기능 목록이 되면

제품 코드에 있는 메소드를 하나씩 따라가며 테스트를 만들면, 테스트 스위트는 명세가 아니라 코드의 복사본이 된다. 코드가 바뀌면 테스트도 똑같이 바뀌므로 아무것도 지켜주지 못한다.

앱 동작에 대한 고수준의 명세가 있어야 하고, 그 명세는 비즈니스 담당자에게도 의미가 있어야 한다. 이 기준이 다음 아이템의 명명법으로 곧장 이어진다.

정리

  • 테스트 하나 = 문제 영역의 원자적인 사실 하나.
  • 제품 코드의 기능을 나열하는 테스트는 명세가 아니라 코드의 복사본이다.
  • 테스트 스위트는 비즈니스 담당자에게도 읽히는 고수준 명세여야 한다.
3-3

테스트 간 테스트 픽스처 재사용

beforeEach 로 묶지 말고 비공개 팩토리 메소드로 뽑는다.

핵심 beforeEach 로 픽스처를 공유하면 테스트 간 결합도가 올라가고 가독성이 떨어진다. 팩토리 메소드는 둘 다 지킨다.

테스트 픽스처란

테스트 실행 대상 객체, 즉 SUT 로 전달되는 정규 의존성이자 인수다. 디비의 데이터나 하드디스크의 파일일 수도 있다. 이런 객체는 각 테스트 실행 전에 알려진 고정 상태로 유지되기 때문에 동일한 결과를 만들어낸다.

테스트 픽스처를 재사용하는 올바르지 않은 방법

두 테스트에 공통된 준비 과정이 필요하니 beforeEach 로 뽑아 재사용성을 높인 코드다.

customer.spec.ts 문제 
describe("CustomerTests", () => {
  let _store: Store;
  let _sut: Customer;

  // 각 테스트 실행 이전에 호출됨
  beforeEach(() => {
    _store = new Store();
    _store.addInventory(Product.Shampoo, 10);
    _sut = new Customer();
  });

  it("purchase_succeeds_when_enough_inventory", () => {
    const success = _sut.purchase(_store, Product.Shampoo, 5);
    expect(success).toBe(true);
    expect(_store.getInventory(Product.Shampoo)).toBe(5);
  });

  it("purchase_fails_when_not_enough_inventory", () => {
    const success = _sut.purchase(_store, Product.Shampoo, 15);
    expect(success).toBe(false);
    expect(_store.getInventory(Product.Shampoo)).toBe(10);
  });
});

원문 교정 원문 교정

노트에는 addInventory(Product.Shampoo, 5) 로 적혀 있지만, 그러면 두 테스트의 기대값(5 와 10)과 앞뒤가 맞지 않는다. 재고 10 으로 두어야 "5개 구매 성공 후 잔여 5", "15개 구매 실패 후 잔여 10" 이 성립한다. 아래 팩토리 메소드 예제도 같은 이유로 10 으로 맞췄다.

이 기법에는 두 가지 단점이 있다.

테스트 간의 높은 결합도는 안티 패턴이다

테스트를 수정해도 다른 테스트에 영향을 주어서는 안 된다. 이 지침을 따르려면 동일한 테스트 클래스 내에 공유 상태를 두지 말아야 한다.

customer.spec.ts 
// 첫 번째 테스트를 위해 이 한 줄만 바꿔도
_store.addInventory(Product.Shampoo, 10);

// 두 번째 테스트의 기대값까지 함께 깨진다
_store.addInventory(Product.Shampoo, 20);

테스트 가독성을 떨어뜨리는 생성자 사용

준비 과정의 일부를 위로 옮기면 테스트 본문만 봐서는 전체 그림을 볼 수 없다. 무엇이 준비됐는지 확인하려면 파일 위쪽의 beforeEach 로 눈을 옮겨야 한다.

더 나은 테스트 픽스처 재사용법

테스트 클래스에 비공개 팩토리 메소드를 두면 된다. 공통 초기화 코드를 팩토리 메소드로 추출하면 테스트 코드를 짧게 유지하면서 동시에 진행 상황에 대한 전체 맥락도 지킬 수 있다.

customer.spec.ts 개선 
describe("CustomerTests", () => {
  const createStoreWithInventory = (product: Product, quantity: number) => {
    const store = new Store();
    store.addInventory(product, quantity);
    return store;
  };

  const createCustomer = () => new Customer();

  it("purchase_succeeds_when_enough_inventory", () => {
    const store = createStoreWithInventory(Product.Shampoo, 10);
    const sut = createCustomer();

    const success = sut.purchase(store, Product.Shampoo, 5);

    expect(success).toBe(true);
    expect(store.getInventory(Product.Shampoo)).toBe(5);
  });

  it("purchase_fails_when_not_enough_inventory", () => {
    const store = createStoreWithInventory(Product.Shampoo, 10);
    const sut = createCustomer();

    const success = sut.purchase(store, Product.Shampoo, 15);

    expect(success).toBe(false);
    expect(store.getInventory(Product.Shampoo)).toBe(10);
  });
});

테스트 픽스처 재사용의 예외 사항

테스트 전부 또는 대부분에서 쓰이는 픽스처는 생성자 단계에서 인스턴스화해도 된다. 일반적으로 디비와 작동하는 통합 테스트가 여기 해당한다. 모든 테스트가 디비 연결을 필요로 하니, 한 번 초기화한 뒤 재사용하는 편이 합리적이다.

    // 실행
  });

이 예외의 조건 보강

연결 객체처럼 테스트가 그 상태를 바꾸지 않는 것만 이 예외에 해당한다. 데이터를 넣는 준비 작업까지 beforeEach 로 올리면 앞서 지적한 결합도 문제가 통합 테스트에서 똑같이 재현된다. 데이터 정리 방식은 10-3 테스트 데이터 생명주기 에서 자세히 다룬다.

정리

  • 픽스처 = 각 테스트 전에 알려진 고정 상태로 유지되는 SUT 의 인수.
  • beforeEach 공유는 테스트 간 결합도와 가독성 저하 두 문제를 낳는다.
  • 비공개 팩토리 메소드로 뽑으면 짧게 유지하면서도 맥락이 남는다.
  • 디비 연결처럼 상태를 바꾸지 않는 공용 자원만 예외로 둔다.
3-4

단위 테스트 명명법

가장 유명한 명명 규칙이 가장 도움이 되지 않는 규칙이다.

핵심 [메서드]_[시나리오]_[결과] 형식은 동작이 아니라 구현 세부 사항에 집중하게 만든다. 쉬운 영어 구문이 훨씬 효과적이다.

테스트에 표현력 있는 이름을 붙이는 일은 생각보다 중요하다. 가장 널리 알려진 [테스트 대상 메서드]_[시나리오]_[예상 결과] 형태는 사실 가장 도움이 되지 않는 방법 중 하나다. 메서드 이름이 들어가는 순간, 테스트가 동작이 아니라 구현에 매이기 때문이다.

문제
describe("Sum_twoNumbers_ReturnSum", () => {
  // ...
});
개선
describe("sum_of_two_numbers", () => {
  // ...
});

간단한 문구로 쓰면 고객이나 도메인 전문가에게도 의미 있는 방식으로 시스템 동작을 설명할 수 있다. 물론 단위 테스트는 도메인 전문가가 아니라 개발자를 위해 개발자가 작성하는 것이다. 다만 그 개발자도 도메인 언어로 읽을 때 훨씬 빨리 이해한다.

단위 테스트 명명 지침

  • 엄격한 명명 규칙을 강제하지 않고 표현의 자유를 허용한다.
  • 비개발자에게 시나리오를 설명하듯 이름을 쓴다.
  • 단어는 밑줄로 구분한다. 특히 긴 이름에서 가독성이 크게 좋아진다.
  • 단위 테스트의 "단위" 는 동작의 단위지 클래스의 단위가 아니다.

예제 — 지침에 따른 테스트 이름 변경

delivery.spec.ts 출발점 
it("IsDeliveryValid_InvalidDate_ReturnsFalse", () => {
  const sut = new DeliveryService();
  const pastDate = new Date();
  pastDate.setDate(pastDate.getDate() - 1);
  const delivery = new Delivery(pastDate);

  const isValid = sut.isDeliveryValid(delivery);

  expect(isValid).toBe(false);
});
  1. Delivery_with_invalid_date_should_be_considered_invalid

    이제 개발자가 아닌 사람에게도 납득되고, 개발자도 더 쉽게 이해한다. SUT 의 메소드 이름 isDeliveryValid 가 테스트명에서 사라졌다.

  2. Delivery_with_past_date_should_be_considered_invalid

    "invalid date" 를 도메인 언어인 "past date" 로 바꿨다. 나아지긴 했지만 여전히 장황하다. considered 는 빼도 의미가 퇴색되지 않는다.

  3. Delivery_with_past_date_should_be_invalid

    should be 는 또 다른 안티패턴이다. 하나의 테스트는 동작 단위에 대한 단순하고 원자적인 사실이므로, 사실을 서술할 때 소망이나 욕구가 들어가면 안 된다.

  4. Delivery_with_past_date_is_invalid

    사실의 진술이 됐다. 마지막으로 기초 영문법을 지킨다.

  5. Delivery_with_a_past_date_is_invalid

    관사를 붙이니 문장으로 완벽하게 읽힌다. 최종 버전은 사실을 단도직입적으로 설명한다.

이 테스트가 설명하는 것은 앱 동작의 한 관점, 즉 배송 가능 여부를 결정하는 관점이다.

정리

  • [메서드]_[시나리오]_[결과] 는 구현에 테스트를 묶는다. 쓰지 않는다.
  • 비개발자에게 설명하듯, 밑줄로 단어를 나눠 쓴다.
  • should be 를 쓰지 않는다. 테스트는 소망이 아니라 사실의 진술이다.
  • 관사까지 챙기면 이름이 그대로 명세 문장이 된다.

매개변수화된 테스트 리팩토링하기

코드의 양과 가독성은 상충한다. 부정 케이스만 묶고 긍정 케이스는 뽑아낸다.

핵심 매개변수가 늘수록 그 테스트가 나타내는 사실이 흐려진다. 절충안은 가장 중요한 케이스를 별도 테스트로 도출하는 것이다.

테스트 하나로는 동작 단위를 완전히 설명하기에 부족한 경우가 많다. 동작 단위는 여러 구성 요소를 포함하고, 각 구성 요소는 자체 테스트로 캡처해야 한다.

사실을 검증하기 위해서 여러 가지 항목 전달하기

가장 빠른 배송일이 오늘로부터 이틀 후가 되도록 작동하는 배송 기능이 있다고 하자. 테스트 하나로는 부족하다. 지난 날짜뿐 아니라 오늘, 내일, 그리고 이틀 후까지 확인해야 한다.

  • delivery_for_today_is_invalid
  • delivery_for_tomorrow_is_invalid
  • the_soonest_delivery_date_is_two_days_from_now

이런 경우 테스트 코드의 양을 줄이고자 하나로 묶는 것이 매개변수화된 테스트다.

Jest 의 it.each 는 테스트 이름에 %s / %i / %p 같은 포맷 자리와, 객체 배열을 쓸 때의 $변수명 치환을 지원한다. it.each([{ daysFromNow: 2, expected: true }])("delivery in $daysFromNow days -> $expected", ...) 처럼 쓰면 실패했을 때 어느 케이스가 깨졌는지가 리포트에 그대로 찍힌다.

정리

  • 동작 하나는 여러 사실로 쪼개지고, 비슷한 사실끼리 묶는 것이 매개변수화된 테스트다.
  • 코드의 양과 가독성은 상충한다. 매개변수가 늘수록 사실이 흐려진다.
  • 부정 케이스는 묶고, 가장 중요한 긍정 케이스는 이름 있는 테스트로 도출한다.
  • 동작이 복잡하면 매개변수화를 포기하는 것도 선택지다.

4-1

좋은 단위 테스트의 4대 요소

회귀 방지, 리팩터링 내성, 빠른 피드백, 유지 보수성.

핵심 거짓 양성을 줄이는 방법은 하나뿐이다. 테스트를 구현 세부 사항에서 떼어내는 것. 최종 사용자에게 의미 있는 결과만 확인한다.

회귀 방지

회귀는 소프트웨어 버그로, 코드를 수정한 후 기능이 의도한 대로 작동하지 않는 경우다. 개발자의 삶에서 불행한 사실 하나는 코드가 자산이 아니라 책임이라는 점이다. 코드베이스가 커질수록 잠재적인 버그에 더 많이 노출된다.

회귀 방지 지표를 극대화하려면 테스트가 가능한 한 많은 코드를 실행하는 것을 목표로 해야 한다. 다만 그 코드가 비즈니스적으로 중요한 로직일 때만 유효하다. 단순한 코드를 테스트하는 것은 가치가 거의 없다.

리팩터링 내성

거짓 양성(false positive) 은 허위 경보다. 실제로는 기능이 의도한 대로 작동하는데 테스트가 실패하는 상황을 말한다. 일반적으로 코드를 리팩터링할 때, 즉 구현을 수정하지만 식별할 수 있는 동작은 유지할 때 발생한다.

단위 테스트의 목표는 프로젝트 성장을 지속 가능하게 하는 것이고, 그 메커니즘은 회귀 없이 주기적으로 리팩터링하고 새 기능을 추가할 수 있는 것이다. 리팩터링 내성이 그 메커니즘의 전제 조건이다.

테스트가 있을 때거짓 양성이 잦을 때
기존 기능이 고장 나면 배포 전에 조기 경고를 받는다타당한 이유 없이 실패하는 경험이 쌓인다
변경이 회귀로 이어지지 않는다는 확신을 얻는다실패에 익숙해져 타당한 실패도 무시하기 시작한다
확신이 있으니 리팩터링을 계속하게 된다신뢰가 무너지고, 회귀를 피하려 코드 변경을 최소화한다

거짓 양성의 원인

거짓 양성의 수는 테스트 구성 방식과 직접적인 관련이 있다. 테스트가 SUT 의 구현 세부 사항과 많이 결합될수록 허위 경보가 늘어난다.

message-renderer.ts 
class Message {
  constructor(
    public header: string,
    public body: string,
    public footer: string
  ) {}
}

interface IRenderer {
  render(message: Message): string;
}

/** MessageRenderer 는 여러 개의 하위 렌더링 클래스를 가지고 있다 */
class MessageRenderer implements IRenderer {
  readonly subRenderers: IRenderer[];

  constructor() {
    this.subRenderers = [
      new HeaderRenderer(),
      new BodyRenderer(),
      new FooterRenderer(),
    ];
  }

  render(message: Message): string {
    return this.subRenderers
      .map((renderer) => renderer.render(message))
      .join("");
  }
}

첫 번째 특성과 두 번째 특성 간 본질적인 관계

회귀 방지는 신호를 키우고, 리팩터링 내성은 소음을 줄인다.

핵심 테스트 정확도 = 신호(발견된 버그 수) / 소음(허위 경보 수). 분자를 키우는 것이 회귀 방지, 분모를 줄이는 것이 리팩터링 내성이다.

회귀 방지와 리팩터링 내성 간의 관계

테스트 결과와 실제 기능 상태를 교차하면 네 가지 경우가 나온다. 의학의 진단 검사와 같은 구조다.

기능이 올바르게 작동기능이 고장남
테스트 통과올바른 추론 (참 음성)2종 오류 (거짓 음성)
테스트 실패1종 오류 (거짓 양성)올바른 추론 (참 양성)

회귀 방지가 없으면 거짓 음성(버그가 있는데 통과)이 늘어나고, 리팩터링 내성이 없으면 거짓 양성(멀쩡한데 실패)이 늘어난다.

테스트 정확도 극대화

!

원문 교정 원문 교정

노트에는 "테스트 정확도 = 소음 / 신호" 로 적혀 있는데 분자와 분모가 뒤집혔다. 정확도가 높다는 것은 신호가 크고 소음이 작다는 뜻이므로 정확도 = 신호 / 소음 이 맞다.

테스트의 정확도를 향상시키는 방법은 두 가지다.

  1. 신호를 증가시킨다

    회귀를 더 잘 찾아내는 테스트로 개선한다. 곧 회귀 방지를 높이는 일이다.

  2. 소음을 줄인다

    허위 경보를 발생시키지 않는 테스트로 개선한다. 곧 리팩터링 내성을 높이는 일이다.

거짓 양성과 거짓 음성의 중요성 — 역학 관계

둘의 무게는 프로젝트 시점에 따라 다르다.

  • 단기적으로 거짓 양성은 거짓 음성만큼 나쁘지 않다. 프로젝트 시작 시점에 잘못된 경고를 받는 것은, 경고를 아예 못 받아서 버그가 운영 환경에 들어가는 위험에 비하면 별일이 아니다.
  • 초기에는 리팩터링이 그렇게 중요하지 않다. 코드가 아직 작기 때문이다.
  • 시간이 지나면 리팩터링이 점점 중요해지고, 동시에 테스트의 리팩터링 내성도 함께 중요해진다.

따라서 중대형 프로젝트에서는 거짓 음성과 거짓 양성에 똑같이 주의를 기울여야 한다.

정리

  • 정확도 = 신호 / 소음. 회귀 방지가 분자를, 리팩터링 내성이 분모를 담당한다.
  • 거짓 음성 = 2종 오류(버그를 놓침), 거짓 양성 = 1종 오류(허위 경보).
  • 프로젝트 초기에는 거짓 음성이, 코드베이스가 커질수록 거짓 양성이 더 치명적이다.
4-3

세 번째, 네 번째 요소 빠른 피드백과 유지 보수성

테스트 코드는 제품 코드와 같은 등급의 시민이다.

핵심 빠른 테스트는 피드백 루프를 줄여 버그 수정 비용을 거의 0 으로 만든다. 그리고 그 테스트를 유지하는 비용은 코드 라인 수와 외부 의존성 수에 비례한다.

빠른 피드백

테스트가 빠를수록 더 많이, 더 자주 실행할 수 있다. 결함이 생기자마자 경고를 주므로 피드백 루프가 짧아지고, 버그를 수정하는 비용이 거의 0 에 수렴한다. 반대로 느린 테스트는 피드백을 늦추고 버그를 뒤늦게 드러낸다.

유지 보수성

유지 보수성은 두 가지로 나뉜다.

  • 이해하기 얼마나 어려운가 — 테스트 크기의 함수다. 코드 라인이 적을수록 읽기 쉽다.
  • 실행하기 얼마나 어려운가 — 프로세스 외부 의존성의 함수다. 디비, 네트워크 같은 의존성을 상시 운영하는 데 시간이 든다.
✓

테스트 코드는 일급 시민이다

테스트 코드의 품질은 제품 코드만큼 중요하다. 테스트를 작성할 때 절차를 생략하면 안 된다. 이름 짓기, 중복 제거, 추상화 모두 제품 코드와 같은 기준을 적용한다.

정리

  • 빠른 테스트 = 짧은 피드백 루프 = 낮은 수정 비용.
  • 유지 보수성 = 테스트 크기 + 외부 의존성 운영 부담.
  • 테스트 코드를 일급 시민으로 취급한다.
4-4

이상적인 테스트를 찾아서

네 요소는 덧셈이 아니라 곱셈이다. 하나가 0 이면 전체가 0 이다.

핵심 리팩터링 내성과 유지 보수성은 챙기고, 회귀 방지와 빠른 피드백 사이에서 선택한다. 이것이 현실에서 가능한 최선의 전략이다.

테스트의 가치는 회귀 방지 × 리팩터링 내성 × 빠른 피드백 × 유지 보수성 으로 측정한다. 곱셈이므로 넷 중 하나라도 0 이면 테스트의 가치는 0 이다.

테스트 코드를 포함한 모든 코드는 책임이다. 최소 임계치를 높게 설정하고, 그 임계치를 충족하는 테스트만 남기는 것이 좋다.

이상적인 테스트를 만들 수 있는가

네 범주 모두에서 최대 점수를 받는 테스트는 현실적으로 불가능하다. 앞 세 요소는 서로 상호 배타적이라 2개를 얻으면 나머지 1개를 희생해야 한다. 그러니 목표는 최대화가 아니라, 어느 것도 크게 줄지 않는 지점을 찾는 것이다.

극단적인 사례 1 — E2E 테스트

  • 모든 코드를 테스트하므로 회귀 방지를 훌륭하게 해낸다.
  • 사용자 입장에서 기능이 어떻게 동작하는지만 보므로 구현 세부 사항이 최대한 제거된다. 리팩터링 내성도 우수하다.
  • 하지만 느리다. 모든 테스트를 E2E 로 만든 시스템에서 빠른 피드백을 받는 것은 불가능하다.

극단적인 사례 2 — 간단한 테스트

E2E 와 정반대로 빠르게 실행되어 빠른 피드백을 주고, 거짓 양성 가능성도 낮아 리팩터링 내성이 우수하다. 하지만 기반 코드에 실수할 여지가 없을 만큼 간단해서 회귀를 나타내지 않는다.

  expect(sut.getName()).toBe(name);
});

이런 테스트는 이름만 바꾼 동어 반복 테스트(tautology test) 를 낳는다. 항상 통과하거나 검증이 무의미하다.

극단적인 사례 3 — 깨지기 쉬운 테스트

실행이 빠르고 회귀를 잡을 가능성도 높지만 거짓 양성이 많은 테스트를 쓰기는 아주 쉽다. 이를 깨지기 쉬운 테스트(brittle test) 라고 부른다. 리팩터링을 견디지 못하고, 기능이 고장 났는지와 무관하게 빨간불이 된다.

결론

세 요소 중 둘만 고를 수 있다 — 세 교집합에는 각각 이름 붙은 실패 사례가 앉아 있고, 한가운데는 비어 있다.

네 번째 특성인 유지 보수성은 앞의 세 요소와 상호 배타적이지 않다. 다만 E2E 테스트는 외부 프로세스 의존성을 계속 운영해야 하므로 유지비 측면에서 별도로 더 비싸다.

현실에서의 전략

E2E 만 쓰거나 테스트가 상당히 빠르지 않은 한, 리팩터링 내성을 최대한 챙긴다. 리팩터링 내성과 유지 보수성을 지키면서 회귀 방지와 빠른 피드백 중 하나를 고르는 것이 최선이다.

정리

  • 테스트 가치 = 네 요소의 곱. 하나가 0 이면 전체가 0 이다.
  • E2E 는 피드백을, 간단한 테스트는 회귀 방지를, 깨지기 쉬운 테스트는 리팩터링 내성을 잃는다.
  • 리팩터링 내성은 타협 대상이 아니다. 회귀 방지와 빠른 피드백 사이에서만 저울질한다.
4-5

대중적인 테스트 자동화 개념

테스트 피라미드와 블랙박스/화이트박스를 4대 요소로 다시 읽는다.

핵심 피라미드의 어느 계층도 리팩터링 내성만은 포기하지 않는다. 계층 간에 저울질하는 것은 회귀 방지와 빠른 피드백뿐이다.

테스트 피라미드 분해

테스트 스위트에서 테스트 유형 간 일정한 비율을 나타내는 개념이다.

가로는 개수, 세로는 실제 유저를 모방하는 정도 — 위로 갈수록 회귀 방지에 유리하고, 아래로 갈수록 실행 속도가 강조된다.

항상 지켜지는 리팩터링 내성

어느 계층도 리팩터링 내성을 포기하지 않는다. 모든 테스트는 거짓 양성을 최소화하는 것을 목표로 하며, 제품 코드로 직접 작업할 때도 마찬가지다. 테스트 개수는 E2E < 통합 < 단위 순으로 많아야 한다.

E2E 는 가장 중요한 기능에 적용하거나, 단위 / 통합과 동일한 수준으로 보호해야 할 때만 쓴다.

블랙박스 테스트

시스템 내부 구조를 몰라도 기능을 검증할 수 있는 방법이다. 앱이 어떻게 해야 하는지가 아니라 무엇을 해야 하는지를 중심으로 구축된다.

화이트박스 테스트

앱의 내부 작업을 검증한다. 요구 사항이나 명세가 아니라 소스 코드에서 테스트가 파생된다. 소스 코드 분석을 통해 외부 명세만으로는 놓칠 오류를 발견할 수 있지만, 특정 구현과 결합되어 테스트가 깨지기 쉽다.

화이트박스 방식이 유용한 것은 테스트를 쓸 때가 아니라 분석할 때다. 커버리지 리포트로 어느 분기가 안 걸렸는지 확인하고, 그 분기를 블랙박스 테스트로 덮는 식으로 쓴다.

정리

  • 피라미드는 개수(가로) × 사용자 모방 정도(세로)의 관계다.
  • 어느 계층도 리팩터링 내성은 포기하지 않는다.
  • CRUD 앱이나 UI 없는 API 는 피라미드가 납작해질 수 있다.
  • 테스트 작성의 기본값은 블랙박스. 화이트박스는 커버리지 분석에만 쓴다.
CH 5

목과 테스트 취약성

목은 도구가 아니라 선택이다. 시스템 간 통신에 쓰면 테스트를 지켜주고, 시스템 내부 통신에 쓰면 테스트를 부순다.

5-1

목과 스텁 구분

목은 나가는 상호작용을 모방하고 검사한다. 스텁은 들어오는 상호작용을 모방만 한다.

핵심 스텁으로 상호작용을 검증하지 않는다. 최종 결과가 아닌 것을 검증하는 이 관행을 과잉 명세라고 부른다.

같은 의존성이라도 통신의 방향이 역할을 결정한다 — 상태를 바꾸러 나가는 호출은 목으로 검사하고, 데이터를 받아오는 호출은 스텁으로 모방만 한다.
  • 더미는 null 이나 아무 문자열처럼 단순하고 하드코딩된 값이다.
  • 페이크는 보통 아직 존재하지 않는 의존성을 대체하고자 구현한다.
  • 목은 일반적으로 전용 프레임워크의 도움을 받아 생성하고, 스파이는 직접 작성한다.

도구로서의 목과 테스트 대역으로서의 목

"목" 이라는 단어가 두 가지를 가리키기 때문에 혼동이 생긴다. 목 라이브러리의 클래스도 목이라 부르는데, 그 클래스는 실제 목을 만드는 데 도움을 줄 뿐 그 자체가 목은 아니다.

목과 스텁 함께 쓰기

목과 스텁을 같이 쓰는 객체는 보통 그냥 "목" 이라고 부른다. 목이라는 사실이 스텁이라는 사실보다 더 중요하기 때문이다. 스텁으로 준비된 응답을 반환하고, 목으로 행위를 검증한다. 서로 다른 메소드이므로 "스텁과 상호작용을 검증하지 말라" 는 원칙을 깨지 않는다.

목과 스텁의 구분은 명령 조회 분리(CQS, Command Query Separation) 원칙과 맞닿아 있다. 모든 메소드는 명령이거나 조회여야 하고, 둘을 혼용해서는 안 된다.

  • 목 = 나가는 상호작용을 모방 + 검사. 스텁 = 들어오는 상호작용을 모방만.
  • 도구(jest.fn())가 아니라 통신의 방향이 종류를 정한다.
  • 스텁으로 상호작용을 검증하면 과잉 명세다.
  • CQS 로 보면 명령이 목, 조회가 스텁에 대응한다.
5-2

식별할 수 있는 동작과 구현 세부 사항

클래스에서 호출해야 하는 연산의 수가 1보다 크면 구현 세부 사항이 새고 있다.

핵심 코드는 식별할 수 있는 동작이거나 구현 세부 사항이지, 둘 다는 될 수 없다. 좋은 API 설계와 좋은 단위 테스트는 같은 목표를 공유한다.

식별할 수 있는 동작은 공개 API 와 다르다

모든 제품 코드는 서로 겹치지 않는 두 개의 차원으로 분류된다.

  • 공개 API 인가, 비공개 API 인가
  • 식별할 수 있는 동작인가, 구현 세부 사항인가

코드가 식별할 수 있는 동작이려면 아래 둘 중 하나를 만족해야 한다.

  • 클라이언트가 목표를 달성하는 데 도움이 되는 연산을 노출한다. 연산은 계산을 수행하거나 사이드 이펙트를 내거나 둘 다 하는 메소드다.
  • 클라이언트가 목표를 달성하는 데 도움이 되는 상태를 노출한다.

이상적으로 시스템의 공개 API 는 식별할 수 있는 동작과 일치하고, 모든 구현 세부 사항은 캡슐화되어야 한다.

구현 세부 사항 유출 — 연산의 예

user.ts 유출 
class User {
  name: string;

  normalizeName(name: string) {
    const result = name.trim();

    if (result.length > 50) {
      return result.slice(0, 50);
    }

    return result;
  }
}

class UserController {
  renameUser(userId: number, newName: string) {
    const user = getUserFromDatabase(userId);

    // 클라이언트가 두 개의 연산을 순서대로 호출해야만 한다
    const normalizedName = user.normalizeName(newName);
    user.name = normalizedName;

    saveUserToDatabase(user);
  }
}

정규화 없이 user.name 에 값을 넣을 수도 있으므로, 클라이언트가 규칙을 어기는 순간 불변성이 깨진다. 해결책은 normalizeName 을 감추고 세터 안에서 내부적으로 호출하는 것이다.

잘 설계된 API

user.ts 캡슐화 
class User {
  private _name: string;

  constructor(name: string) {
    this._name = this.normalizeName(name);
  }

  getName() {
    return this._name;
  }

  setName(name: string) {
    this._name = this.normalizeName(name);
  }

  private normalizeName(name: string) {
    const result = (name ?? "").trim();
    if (result.length > 50) {
      return result.slice(0, 50);
    }

    return result;

잘 설계된 API 와 캡슐화

캡슐화는 불변성 위반이라고도 하는 모순을 방지하는 조치다. 불변성은 항상 참이어야 하는 조건이며, 구현 세부 사항을 노출하면 불변성 위반이 따라온다.

장기적으로 코드베이스 유지 보수에서 캡슐화가 중요한 이유는 복잡도 때문이다. 캡슐화는 궁극적으로 단위 테스트와 동일한 목표를 달성한다. 소프트웨어 프로젝트의 지속적인 성장이다.

구현 세부 사항 유출 — 상태의 예

message-renderer.ts 상태 유출 
class MessageRenderer implements IRenderer {
  readonly subRenderers: IRenderer[]; // 클라이언트에게 필요한가?

  constructor() {
    this.subRenderers = [
      new HeaderRenderer(),
      new BodyRenderer(),
      new FooterRenderer(),
    ];
  }

  render(message: Message): string {
    return this.subRenderers
      .map((renderer) => renderer.render(message))
      .join("");
  }
}

subRenderers 가 클라이언트에게 필요한가? 답은 아니오다. 클라이언트에게 필요한 것은 render 하나뿐이므로, 나머지는 감춰야 한다. 4-1 에서 본 깨지기 쉬운 테스트는 정확히 이 유출된 상태를 붙잡고 있었다.

좋은 API 설계 = 좋은 단위 테스트

API 를 잘 설계하면 단위 테스트도 자동으로 좋아진다. 연산과 상태를 최소한으로 노출하고, 목표 달성에 직접 도움이 되는 코드만 공개한다. 나머지는 전부 구현 세부 사항이므로 비공개 API 뒤에 숨긴다.

정리

  • 코드는 식별할 수 있는 동작이거나 구현 세부 사항이다. 둘 다일 수 없다.
  • 목표 하나에 필요한 연산이 둘 이상이면 유출을 의심한다.
  • 캡슐화는 불변성 위반을 막는 조치이며, 단위 테스트와 목표가 같다.
  • 공개해야 할 것은 동작뿐. 나머지는 비공개 뒤로 숨긴다.
5-3

목과 테스트 취약성 간의 관계

시스템 간 통신에 쓰는 목은 안전하고, 시스템 내부 통신에 쓰는 목은 위험하다.

핵심 시스템 내부 통신은 구현 세부 사항이고, 시스템 간 통신은 그렇지 않다. 목은 후자에만 쓴다.

육각형 아키텍쳐 정의

전형적인 앱은 도메인과 앱 서비스 두 계층으로 구성된다. 도메인 계층 위에 앱 서비스 계층이 있으며, 외부 환경과의 통신을 조정한다.

도메인은 육각형의 한가운데에 갇혀 있다 — 외부 앱은 앱 서비스 계층의 공통 인터페이스로만 연결되며, 아무도 도메인 계층에 직접 접근하지 못한다.
도메인 계층과 앱 서비스 계층 간 관심사 분리

도메인 계층은 비즈니스 로직에 대해서만 책임진다. 앱 서비스에는 어떠한 비즈니스 로직도 존재하면 안 된다.

앱 내부 통신

앱 서비스 계층에서 도메인 계층으로 흐르는 단방향 의존성을 규정한다. 앱 계층은 도메인을 알지만 그 반대는 안 된다. 도메인 계층은 외부 환경에서 완전히 격리되어야 한다.

앱 간의 통신

외부 앱은 앱 서비스 계층의 공통 인터페이스를 통해서만 연결된다. 아무도 도메인 계층에 직접 접근할 수 없다.

프랙탈(Fractal) 특성

API 를 잘 설계하면 테스트도 프랙탈 구조를 갖기 시작한다. 달성하는 목표는 같지만 서로 다른 수준에서 동작을 검증한다.

시스템 내부 통신과 시스템 간 통신

시스템 간 통신앱이 다른 앱과 하는 통신식별할 수 있는 동작여기에만 쓴다

시스템 내부 통신과 시스템 간 통신의 예

customer-controller.ts 
class CustomerController {
  purchase(customerId: number, productId: number, quantity: number) {
    // 시스템 간 통신 — 데이터베이스와의 통신
    const customer = this.customerRepository.getById(customerId);
    const product = this.productRepository.getById(productId);

    // 시스템 내부 통신 — Customer, Store 클래스 간 통신
    const isSuccess = customer.purchase(this.mainStore, product, quantity);

    // 시스템 간 통신 — 이메일 발송을 위한 SMTP 서버와의 통신
    if (isSuccess) {
      this.emailGateway.sendReceipt(customer.email, product.name, quantity);
    }

    return isSuccess;
  }
}

5-4

단위 테스트 고전파 런던파 재고

모든 프로세스 외부 의존성을 목으로 해야 하는 것은 아니다.

핵심 완전히 통제권을 가진 프로세스 외부 의존성에 목을 쓰면 깨지기 쉬운 테스트가 된다. 그 디비와 앱은 하나의 시스템으로 취급한다.

런던파의 문제

  • 불변 의존성을 제외한 모든 의존성에 목 사용을 권장한다.
  • 시스템 내 통신과 시스템 간 통신을 구분하지 않는다.
  • 목을 무분별하게 쓰면 구현 세부 사항에 결합되어 리팩터링 내성이 사라진다.
  • 리팩터링 내성이 저하되면 테스트의 가치는 0 이 된다.

고전파의 문제

고전파는 테스트 간 공유하는 의존성(디비, 메세지 버스 등)만 교체하자고 하므로 이 문제에서 훨씬 유리하다. 하지만 고전파 역시 시스템 간 통신을 다루는 데는 이상적이지 않다. 런던파만큼은 아니어도 목 사용을 지나치게 장려하는 편이다.

모든 프로세스 외부 의존성을 목으로 해야 하는 건 아니다

고전파가 공유 의존성을 피하라고 하는 이유는 테스트 격리 때문이다. 테스트가 실행 컨텍스트에서 서로 방해하면 병렬 처리가 불가능해진다. 테스트를 병렬로, 순차적으로, 또는 임의의 순서로 실행할 수 있는 것을 테스트 격리라고 부른다.

어떨 때 실제 인스턴스를 써도 되는가
  • 프로세스 외부 의존성이 앱을 통해서만 접근 가능하다면, 그 의존성과의 통신은 시스템에서 식별할 수 있는 동작이 아니다.
  • 실제로 외부에서 관찰할 수 없는 프로세스 외부 의존성은 앱의 일부로 작용한다.
  • 앱 전용 디비가 대표적이다. 어떤 외부 시스템도 그 디비에 직접 접근하지 못한다.

목을 사용한 동작 검증

중요한 것은 클라이언트의 목표까지 거슬러 올라갈 수 있는 동작이다. 목은 앱의 경계를 넘나드는 상호작용을 검증할 때, 그리고 그 상호작용의 사이드 이펙트가 외부 환경에서 보일 때만 동작과 관련이 있다.

이 기준이 8-2 관리 의존성 / 비관리 의존성 으로 이어진다.

정리

  • 런던파는 목을 남용해 리팩터링 내성을 잃는다.
  • 고전파도 시스템 간 통신 처리는 이상적이지 않다.
  • 앱이 완전히 통제하는 프로세스 외부 의존성은 앱의 일부다. 목으로 바꾸지 않는다.
  • 목의 기준은 "앱 경계를 넘고, 외부에서 사이드 이펙트가 보이는가" 다.

6-1

단위 테스트의 세 가지 스타일

출력을 보느냐, 상태를 보느냐, 통신을 보느냐.

핵심 같은 동작을 검증해도 무엇을 근거로 삼느냐에 따라 세 스타일이 갈리고, 이 선택이 네 가지 요소 점수를 좌우한다.

출력 기반 테스트 정의

SUT 에 입력을 넣고 생성되는 출력을 검증한다. 전역 상태나 내부 상태를 변경하지 않는 코드에만 적용할 수 있으므로 반환값만 검증하면 된다. 함수형 스타일이라고도 부른다.

price-engine.spec.ts 출력 기반 
class PriceEngine {
  calculateDiscount(products: Product[]) {
    const discount = products.length * 0.01;
    return Math.min(discount, 0.02);
  }
}

it("discount_of_two_products", () => {

  const product2 = new Product("Shampoo");

작업이 완료된 후 시스템의 상태를 확인한다. 여기서 상태는 SUT 자신의 상태일 수도, 협력자의 상태일 수도, 디비나 파일 시스템 같은 프로세스 외부 의존성의 상태일 수도 있다.

6-2

단위 테스트 스타일 비교

네 가지 요소로 세 스타일을 저울에 올리면 순위가 분명하다.

핵심 가능하면 항상 출력 기반 테스트를 선호한다. 다만 그건 함수형으로 작성된 코드에서만 가능하므로, 결국 제품 코드를 바꿔야 한다.

회귀 방지와 피드백 속도 지표로 비교

회귀 방지 지표를 결정하는 것은 세 가지 수치다.

  • 테스트 중 실행되는 코드의 양
  • 코드 복잡도
  • 도메인 유의성

이 셋은 스타일과 큰 상관이 없다. 어떤 스타일로든 코드를 많이 또는 적게 실행하도록 테스트를 쓸 수 있다. 다만 통신 기반 스타일에는 예외가 있다. 남용하면 아주 작은 코드 조각만 검증하고 나머지는 전부 목으로 채우는 피상적인 테스트가 나오기 쉽다.

피드백 속도 역시 스타일과 상관관계가 거의 없다. 목이 런타임에 약간의 지연을 만들긴 하지만, 테스트가 수만 개가 아니라면 체감되지 않는다.

리팩터링 내성 지표로 스타일 비교

  • 출력 기반 — 테스트가 대상 메소드에만 결합되므로 거짓 양성 방지가 가장 우수하다.
  • 상태 기반 — 대상 메소드 외에 클래스 상태와도 함께 동작하므로 거짓 양성이 되기 쉽다.
  • 통신 기반 — 허위 경보에 가장 취약하다. 테스트 대역으로 상호작용을 확인하는 테스트는 대부분 깨지기 쉽다.

유지 보수성 지표로 스타일 비교하기

유지 보수성은 스타일과 밀접하게 얽혀 있고, 완화할 방법도 많지 않다. 유지비는 두 가지 특성으로 정의한다.

  • 테스트를 이해하기 얼마나 어려운가 — 테스트 크기의 함수
  • 테스트를 실행하기 얼마나 어려운가 — 직접 관련된 프로세스 외부 의존성의 함수
출력 기반 테스트의 유지 보수성

세 스타일 중 가장 유지 보수하기 쉽다. 거의 항상 짧고 간결하며, 전역이나 내부 상태를 변경할 일이 없다.

상태 기반 테스트의 유지 보수성

일반적으로 출력 기반보다 어렵다. 상태 검증은 출력보다 더 많은 공간을 차지하기 때문이다.

  • 출력 기반을 쓰려면 코드를 순수 함수로 만들어야 한다.

함수형 아키텍쳐에 대한 이해

결정을 내리는 코드와, 그 결정에 따라 작용하는 코드를 분리한다.

핵심 수학적 함수는 숨은 입출력이 없는 함수다. 모든 입출력이 시그니처에 드러나 있어야 하고, 출력 기반 테스트를 적용할 수 있는 것은 수학적 함수뿐이다.

함수형 프로그래밍이란

수학적 함수를 사용하는 프로그래밍이다. 수학적 함수란 숨은 입출력이 없는 함수로, 모든 입출력이 메소드명 / 인수 / 반환 타입으로 구성된 시그니처에 명시되어 있어야 한다.

discount.ts 수학적 함수 
/**
 * 이름   : calculateDiscount
 * 입력   : Product[]
 * 출력   : number
 * 시그니처: calculateDiscount(products: Product[]): number
 */
const calculateDiscount = (products: Product[]): number => {
  const discount = products.length * 0.01;
  return Math.min(discount, 0.02);
};

숨은 입출력 유형

메소드가 수학적 함수인지 판별하는 가장 좋은 방법은, 프로그램 동작을 바꾸지 않고 그 호출을 반환값으로 대체할 수 있는지 확인하는 것이다. 이렇게 호출을 값으로 바꾸는 성질을 참조 투명성(referential transparency) 이라 부른다.

유형내용
사이드 이펙트시그니처에 없는 출력. 상태를 변경하거나 디스크의 파일을 업데이트하는 등
예외시그니처에 설정된 계약을 우회하는 경로를 만든다. 호출 스택 어디에서도 발생할 수 있으므로 시그니처가 전달하지 않는 출력이 추가된다
내외부 상태 참조new Date() 처럼 현재 시각을 가져오거나, 디비에 질의하거나, 비공개 가변 필드를 참조하는 것. 모두 시그니처에 없는 입력이다

사이드 이펙트 예시

사이드 이펙트는 숨은 출력의 가장 흔한 유형이다. 아래 코드는 댓글을 반환하지만, 동시에 상태를 변경한다.

article.ts 숨은 출력 
class Article {
  comments: Comment[] = [];

  addComment(text: string): Comment {
    const comment = new Comment(text);
    this.comments.push(comment); // 사이드 이펙트 — 시그니처에 없는 출력
    return comment;
  }
}

함수형 아키텍쳐란

비즈니스 로직을 처리하는 코드와 사이드 이펙트를 일으키는 코드를 분리하는 것이다. 사이드 이펙트를 비즈니스 연산의 끝으로 몰아서 비즈니스 로직과 떼어놓는다.

구분역할다른 이름
결정을 내리는 코드사이드 이펙트가 필요 없으므로 수학적 함수로 작성한다함수형 코어, 불변 코어
결정에 따라 작용하는 코드수학적 함수가 내린 결정을 디비 변경이나 메세지 발행처럼 가시적인 것으로 바꾼다가변 셸
목표는 출력 기반 테스트로 함수형 코어를 두루 다루고, 가변 셸은 훨씬 적은 수의 통합 테스트에 맡기는 것이다 — 셸은 결정을 내리지 않고 실어 나르기만 한다.
함수형 코어와 가변 셸의 협력
  1. 가변 셸이 모든 입력을 수집한다
  2. 함수형 코어가 결정을 생성한다
  3. 셸이 그 결정을 사이드 이펙트로 변환한다

    가변 셸이 아무런 결정도 내리지 않아야 계층이 잘 분리된 것이다.

감사 시스템 — 초기 버전

AuditManager 가 파일 시스템과 밀접하게 얽혀 있어 테스트하기 어렵다. 테스트 전에 파일을 올바른 위치에 배치해야 하고, 끝나면 읽어서 내용을 확인한 뒤 삭제해야 한다. 게다가 파일 시스템을 다루는 이상 이것은 단위 테스트가 아니라 통합 테스트다.

audit-manager.ts 초기 버전 
import fs from "fs/promises";
import path from "path";

class AuditManager {
  constructor(
    private readonly maxEntriesPerFile: number,
    private readonly directoryName: string
  ) {}

  async addRecord(visitorName: string, timeOfVisit: Date): Promise<void> {
    const filePaths = await fs.readdir(this.directoryName);
    const sorted = this.sortByIndex(filePaths);

    const newRecord = `${visitorName};${timeOfVisit.toISOString()}`;

    if (sorted.length === 0) {
      const newFile = path.join(this.directoryName, "audit_1.txt");
      await fs.writeFile(newFile, newRecord);
      return;
    }

    const lastEntry = sorted[sorted.length - 1];
    const currentFileIndex = lastEntry.index;
    const currentFilePath = lastEntry.path;

    const content = await fs.readFile(
      path.join(this.directoryName, currentFilePath),
      "utf8"
    );
    const lines = content.split("\r\n");

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      await fs.writeFile(
        path.join(this.directoryName, currentFilePath),
        lines.join("\r\n")
      );
    } else {
      const newName = `audit_${currentFileIndex + 1}.txt`;
      await fs.writeFile(path.join(this.directoryName, newName), newRecord);
    }
  }

  private sortByIndex(files: string[]) {
    return files
      .map((p) => ({ index: this.getIndex(p), path: p }))
      .sort((a, b) => a.index - b.index);
  }

  private getIndex(filePath: string): number {
    // 파일명 예시: audit_1.txt
    const fileName = path.parse(filePath).name;
    return parseInt(fileName.split("_")[1]);
  }
}

interface IFileSystem {
  getFiles(directory: string): Promise<string[]>;
  writeAllText(filePath: string, content: string): Promise<void>;
  readAllLines(filePath: string): Promise<string[]>;
}

class AuditManager {
  constructor(
    private readonly maxEntriesPerFile: number,
    private readonly directoryName: string,
    private readonly fileSystem: IFileSystem
  ) {}

  async addRecord(visitorName: string, timeOfVisit: Date): Promise<void> {
    const filePaths = await this.fileSystem.getFiles(this.directoryName);
    const sorted = this.sortByIndex(filePaths);

    const newRecord = `${visitorName};${timeOfVisit.toISOString()}`;

    if (sorted.length === 0) {
      const newFile = path.join(this.directoryName, "audit_1.txt");
      await this.fileSystem.writeAllText(newFile, newRecord);
      return;
    }

    const lastEntry = sorted[sorted.length - 1];
    const lines = await this.fileSystem.readAllLines(
      path.join(this.directoryName, lastEntry.path)
    );

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      await this.fileSystem.writeAllText(
        path.join(this.directoryName, lastEntry.path),
        lines.join("\r\n")
      );
    } else {
      const newName = `audit_${lastEntry.index + 1}.txt`;
      await this.fileSystem.writeAllText(
        path.join(this.directoryName, newName),
        newRecord
      );
    }
  }
}

함수형 아키텍쳐에서는 사이드 이펙트를 클래스 외부로 완전히 이동할 수 있다. AuditManager 는 파일에 무엇을 할지 결정만 책임지고, 새 클래스 Persister 가 그 결정에 따라 파일 시스템을 업데이트한다.

AuditManager — 함수형 코어
audit-manager.ts 함수형 코어 
class AuditManager {
  constructor(private readonly maxEntriesPerFile: number) {}

  // 경로가 아니라 FileContent 배열을 받고, 사이드 이펙트 대신 "명령"을 반환한다
  addRecord(
    files: FileContent[],
    visitorName: string,
    timeOfVisit: Date
  ): FileUpdate {
    const sorted = this.sortByIndex(files);
    const newRecord = `${visitorName};${timeOfVisit.toISOString().slice(0, 19)}`;

    if (sorted.length === 0) {
      return { fileName: "audit_1.txt", newContent: newRecord };
    }

    const lastEntry = sorted[sorted.length - 1];
    const currentFile = lastEntry.file;
    const lines = [...currentFile.lines];

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord);
      return {
        fileName: currentFile.fileName,
        newContent: lines.join("\r\n"),
      };
    }

    return {
      fileName: `audit_${lastEntry.index + 1}.txt`,
      newContent: newRecord,
    };
  }

  private sortByIndex(files: FileContent[]) {
    return files
      .map((file) => ({ index: this.getIndex(file.fileName), file }))
      .sort((a, b) => a.index - b.index);
  }

  private getIndex(fileName: string): number {
    return parseInt(fileName.replace(".txt", "").split("_")[1]);
  }
}

class Persister {
  async readDirectory(directoryName: string): Promise<FileContent[]> {
    const files = await fs.readdir(directoryName);
    return Promise.all(
      files.map(async (file) => {
        const content = await fs.readFile(
          path.join(directoryName, file),
          "utf8"
        );
        return {
          fileName: file,
          lines: content.split("\r\n").filter((line) => line.length > 0),
        };
      })
    );
  }

  async applyUpdate(directoryName: string, update: FileUpdate): Promise<void> {
    const filePath = path.join(directoryName, update.fileName);
    await fs.writeFile(filePath, update.newContent);
  }
}

6-5

함수형 아키텍쳐 단점 이해하기

두루 적용되는 해결책은 없다. 순수성의 비용이 크면 순수성을 포기한다.

핵심 목표는 모든 테스트를 출력 기반으로 바꾸는 것이 아니라 가능한 한 많은 테스트를 전환하는 것이다.

함수형 아키텍쳐 적용 가능성

감사 시스템은 결정을 내리기 전에 입력을 모두 미리 수집할 수 있어서 함수형 아키텍쳐가 잘 맞았다. 하지만 실행 흐름이 늘 그렇게 단순하지는 않다. 의사 결정 도중의 중간 결과에 따라 프로세스 외부 의존성에 추가로 질의해야 하는 경우가 있다.

두 가지 해결 방법
  1. 앱 서비스 전면에서 미리 모두 수집한다

    폴더 내용과 함께 방문자 접근 레벨까지 앞에서 읽어둔다. 대신 접근 레벨이 필요하지 않은 경우에도 매번 디비에 질의하게 되어 성능이 저하된다.

  2. AuditManager 에 isAccessLevelCheckRequired 를 추가한다

    디비를 호출할지 말지를 코어가 먼저 알려주고, 앱 서비스가 그때만 조회한다. 성능은 지키지만 디비 호출 여부의 결정이 앱 서비스로 넘어가면서 분리가 다소 완화된다.

!

지켜야 할 선

함수형 코어의 클래스는 협력자로 작동해서는 안 되고, 작업의 결과인 값으로 작동해야 한다. 이 선만 지키면 두 방법 모두 선택지가 된다.

성능 단점

함수형 아키텍쳐를 두고 가장 흔히 벌어지는 논쟁이다. 문제가 되는 것은 테스트의 성능이 아니라 앱의 성능이다. 필요 없을지도 모르는 데이터까지 미리 읽어오기 때문이다.

결국 함수형과 전통적인 아키텍쳐 사이의 선택은 성능과 코드 유지 보수성 간의 절충이다. 성능 영향이 눈에 띄지 않는 시스템에서는 함수형 아키텍쳐로 유지 보수성을 얻는 편이 낫다. 두루 적용되는 해결책은 없다.

코드베이스 크기 증가

함수형 코어와 가변 셸을 명확히 분리해야 하므로 초기에 보일러플레이트가 늘어난다. 궁극적으로는 복잡도가 낮아지고 유지 보수성이 향상되지만, 그 전에 코드량을 먼저 지불해야 한다.

✓

현실적인 목표

함수형 방식의 순수성에 많은 비용이 든다면 순수성을 따르지 않는다. 대부분의 프로젝트는 모든 도메인 모델을 불변으로 둘 수 없으므로 출력 기반 테스트에만 의존할 수 없다. 모든 테스트를 전환하는 것이 아니라, 가능한 한 많은 테스트를 전환하는 것이 목표다.

정리

  • 의사 결정 중간에 외부 조회가 필요하면 숨은 입력이 생겨 수학적 함수가 깨진다.
  • 미리 다 읽거나(성능 손해), 조회 필요 여부를 코어가 알려주거나(분리 완화) 중 선택한다.
  • 함수형 vs 전통적 아키텍쳐 = 성능 vs 유지 보수성의 절충이다.
  • 보일러플레이트는 먼저 늘고 복잡도는 나중에 준다. 순수성의 비용이 크면 포기한다.
CH 7

가치 있는 단위 테스트를 위한 리팩터링

테스트가 안 써지는 건 대개 테스트 탓이 아니다. 코드의 네 유형 사분면에서 지금 어디에 서 있는지 확인하고, 험블 객체로 쪼갠다.

7-1

리팩터링할 코드 식별하기

복잡도 및 도메인 유의성 × 협력자 수. 두 축이면 충분하다.

핵심 코드가 더 중요해지거나 복잡해질수록 협력자는 더 적어야 한다. 그 반대 지점에 있는 코드가 리팩터링 대상이다.

코드의 4가지 유형

모든 제품 코드는 두 개의 차원으로 분류된다.

복잡도(code complexity)

코드 내 의사 결정(분기) 지점의 수로 정의한다. 순환 복잡도는 1 + 분기점 수 로 계산한다.

도메인 유의성(domain significance)

코드가 프로젝트의 문제 도메인에 대해 얼마나 의미 있는지를 나타낸다. 도메인 계층의 코드는 최종 유저의 목표와 직접 연결되므로 도메인 유의성이 높다. 복잡하거나 도메인 유의성이 높은 코드가 단위 테스트에서 제일 이롭다.

협력자 수

여기서 협력자란 가변 의존성이거나 프로세스 외부 의존성, 또는 둘 다인 것을 뜻한다. 유지 보수성 지표가 테스트 크기에 따라 달라지므로, 협력자가 많은 코드는 테스트 비용이 많이 든다.

협력자의 유형도 중요하다. 도메인 모델이라면 프로세스 외부 협력자를 사용해서는 안 된다. 또 리팩터링 내성을 지키려면 목을 아주 신중하게 써야 하는데, 목은 앱 경계를 넘는 상호작용에만 쓸 수 있다. 따라서 프로세스 외부 의존성과의 통신은 모두 도메인 계층 바깥의 클래스에 위임하는 것이 좋다.

4가지 코드 유형

지나치게 복잡한 코드는 도메인 모델과 컨트롤러로 쪼개야 한다 — 왼쪽 위는 테스트하고, 오른쪽 아래는 통합 테스트로 얇게 덮고, 왼쪽 아래는 그냥 둔다.

지나치게 복잡한 코드를 피하고 도메인 모델과 알고리즘만 테스트하는 것이, 가치 있고 유지 보수하기 쉬운 테스트 스위트로 가는 길이다. 오른쪽 위에 있는 코드는 도메인 모델 및 알고리즘과 컨트롤러로 나눠서 리팩터링한다.

험블 객체 패턴으로 복잡한 코드 분할

지나치게 복잡한 코드를 쪼개는 도구가 험블 객체(Humble Object) 패턴이다.

테스트하기 어려운 의존성의 예로는 비동기 또는 멀티스레드 실행, 유저 인터페이스, 프로세스 외부 의존성과의 통신 등이 있다. 로직이 이런 의존성과 한 덩어리로 붙어 있으면 로직만 따로 테스트할 방법이 없다.

테스트 가능한 부분을 먼저 추출하고, 남은 껍데기를 험블 래퍼로 만든다 — 래퍼는 어려운 의존성과 추출된 구성 요소를 붙이기만 할 뿐 자체 로직이 거의 없어서 테스트할 필요가 없다.

정리

  • 두 축은 복잡도 및 도메인 유의성과 협력자 수다.
  • 도메인 모델 및 알고리즘 = 테스트 최고 가치. 간단한 코드 = 테스트 불필요.
  • 지나치게 복잡한 코드를 도메인 모델과 컨트롤러로 쪼갠다.
  • 험블 객체는 로직을 뽑아낸 뒤 남는 로직 없는 얇은 래퍼다.
7-2

가치 있는 단위 테스트를 위한 리팩터링하기

CRM 하나를 네 단계에 걸쳐 사분면 위에서 이동시킨다.

핵심 앱 서비스의 역할은 오케스트레이션뿐이다. 복잡도나 도메인 유의성이 있는 로직은 하나도 남아 있으면 안 된다.

고객 관리 시스템 소개

CRM 이고, 모든 사용자가 디비에 저장된다. 현재 지원하는 유스케이스는 유저 이메일 변경 하나뿐이다.

user.ts 지나치게 복잡한 코드 
enum UserType {
  CUSTOMER,
  EMPLOYEE,
}

class User {
  userId: number;
  email: string;
  type: UserType;

  changeEmail(userId: number, newEmail: string) {
    // 디비에서 사용자 검색
    const data = Database.getUserById(userId);
    this.userId = userId;
    this.email = data[1];
    this.type = data[2];

    if (this.email === newEmail) {
      return;
    }

    // 조직의 도메인명과 사원 수 검색
    const companyData = Database.getCompany();
    const companyDomainName = companyData[0];
    const numberOfEmployees = companyData[1];

    // 새 이메일의 도메인 이름에 따라 사용자 유형을 설정
    const emailDomain = newEmail.split("@")[1];
    const isEmailCorporate = emailDomain === companyDomainName;
    const newType = isEmailCorporate ? UserType.EMPLOYEE : UserType.CUSTOMER;

    // 필요한 경우 조직원 수를 업데이트
    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      Database.saveCompany(numberOfEmployees + delta);
    }

    this.email = newEmail;
    this.type = newType;

    Database.saveUser(this);
    MessageBus.sendEmailChangedMessage(userId, newEmail);
  }
}
  • 암시적 의존성 — Database, MessageBus
  • 명시적 의존성 — userId, newEmail
!

Active Record 패턴

도메인 클래스가 스스로 디비를 검색하고 다시 저장하는 패턴을 Active Record 라고 한다. 초기에는 편하지만 확장이 어렵다. 비즈니스 로직과 프로세스 외부 의존성과의 통신 사이에 분리가 없기 때문이다.

1단계 — 암시적 의존성을 명시적으로 만들기

테스트 용이성을 개선하는 일반적인 첫 수는 암시적 의존성을 명시적으로 바꾸는 것이다. Database 와 MessageBus 를 인터페이스로 뽑아 User 의 생성자에 주입하고, 테스트에서는 목으로 처리한다.

하지만 이것으로는 부족하다. 도메인 모델이 여전히 프로세스 외부 의존성과 직접 통신하기 때문이다.

2단계 — 앱 서비스 계층 도입

도메인 모델이 외부 시스템과 직접 통신하는 문제를 극복하려면 그 책임을 다른 클래스, 즉 험블 컨트롤러로 옮겨야 한다.

user-controller.ts 아직 문제가 남았다 
class UserController {
  private readonly database: Database = new Database();
  private readonly messageBus: MessageBus = new MessageBus();

  changeEmail(userId: number, newEmail: string) {
    const data = this.database.getUserById(userId);
    const email = data[1];
    const type = data[2];
    const user = new User(userId, email, type);

    const companyData = this.database.getCompany();
    const companyDomainName = companyData[0];
    const numberOfEmployees = companyData[1];

    const newNumberOfEmployees = user.changeEmail(
      newEmail,
      companyDomainName,
      numberOfEmployees
    );

    this.database.saveCompany(newNumberOfEmployees);
    this.database.saveUser(user);
    this.messageBus.sendEmailChangedMessage(userId, newEmail);
  }
}
남아 있는 문제점
  1. 외부 의존성을 주입받지 않고 직접 인스턴스화한다

    이 클래스를 위해 작성할 통합 테스트에서 문제가 된다.

  2. 디비에서 받은 원시 데이터를 User 인스턴스로 재구성한다

    이는 복잡한 로직이며 앱 서비스에 속하면 안 된다. 앱 서비스의 역할은 오케스트레이션뿐이다.

  3. 회사 데이터를 다루는 책임이 잘못 놓여 있다

    회사 직원 수는 특정 사용자와 아무 관련이 없다.

  4. 새 이메일이 기존과 다른지 확인하지 않는다

    같은 이메일이어도 무조건 저장하고 메세지를 발행한다.

user.ts 협력자가 사라진 User

  userId: number;
  email: string;
  type: UserType;

  changeEmail(
    newEmail: string,
    companyDomainName: string,
    numberOfEmployees: number

2단계 이후 — 아직 경계에 걸쳐 있다 — User 는 도메인 모델 쪽으로 왔지만, UserController 는 여전히 "지나치게 복잡한 코드" 와 "컨트롤러" 사이에 걸쳐 있다.

최적의 단위 테스트 커버리지 분석

네 사분면 중 왼쪽 위만 단위 테스트로 촘촘히 덮는다.

  • 팩토리 같은 간단한 코드는 테스트하지 않는다.
  • 도메인 유의성이 있는 전제 조건만 테스트한다.
7-4

컨트롤러에서 조건부 로직 처리

테스트 유의성 / 컨트롤러 단순성 / 성능. 셋 중 둘만 가질 수 있다.

핵심 성능은 협상 불가, 도메인 모델에 외부 의존성 주입도 불가. 그러니 컨트롤러의 복잡도만 완화하는 쪽으로 간다.

비즈니스와 오케스트레이션 분리

비즈니스 연산은 아래 순서일 때 가장 깔끔하다.

  1. 저장소에서 데이터 검색
  2. 비즈니스 로직 실행
  3. 데이터를 다시 저장소에 저장

여기서 개발자는 세 가지 특성의 균형을 맞춰야 한다.

컨트롤러 단순성의사 결정(분기) 지점이 있는지

  • 대부분의 소프트웨어에서 성능은 협상 대상이 아니다. 무조건 챙긴다.
  • 도메인 모델에 외부 의존성을 주입하면 테스트가 힘들어진다. 이것도 피해야 한다.
  • 남은 것은 컨트롤러가 복잡해지는 것인데, 이것만은 완화할 방법이 있다.

CanExecute / Execute 패턴

컨트롤러 복잡도를 완화하는 첫 번째 방법이자, 비즈니스 로직이 도메인 모델에서 컨트롤러로 유출되는 것을 방지하는 방법이다.

예를 들어 "이메일은 사용자가 확인(confirm)하기 전까지만 변경할 수 있다" 는 규칙이 추가됐다고 하자.

원문 교정 원문 교정

노트에는 if (!error) { return error; } 로 적혀 있는데, 이러면 에러가 없을 때 조기 반환하게 되어 정상 흐름이 통째로 건너뛰어진다. 조건은 if (error !== null) 이어야 한다.

단점은 성능이다. user.changeEmail() 을 호출하려면 확인 여부와 무관하게 항상 Company 를 디비에서 가져와야 한다.

도메인 이벤트를 사용해 도메인 모델 변경 사항 추적

도메인 모델을 현재 상태로 만든 단계를 되짚기 어려울 때가 많다. 하지만 앱에서 정확히 무슨 일이 일어났는지 외부 시스템에 알려야 하므로 그 단계를 아는 것이 중요할 수 있다.

이럴 때는 도메인 모델에서 중요한 변경 사항을 추적하고, 비즈니스 연산이 끝난 뒤 그것을 프로세스 외부 의존성 호출로 변환하면 된다. 도메인 이벤트가 그 도구다.

기존 로직의 문제는 이메일이 기존과 동일해도 디비에 다시 저장하고 이벤트를 발행한다는 점이었다.

user.ts 도메인 이벤트 도입 
/**
 * 도메인 이벤트는 항상 "이미 발생한 일" 을 나타낸다.
 * 그러므로 항상 과거 시제로 명명한다.
 */
class EmailChangedEvent {
  constructor(
    public readonly userId: number,
    public readonly newEmail: string
  ) {}
}

class User {
  userId: number;
  email: string;
  type: UserType;
  emailChangedEvents: EmailChangedEvent[] = [];
  private isEmailConfirmed: boolean;

  private canChangeEmail() {
    return !this.isEmailConfirmed;
  }

  changeEmail(newEmail: string, company: Company) {
    if (!this.canChangeEmail()) {
      throw new Error("이메일이 이미 확인되었습니다.");
    }

    if (this.email === newEmail) {
      return;
    }

    const newType = company.isEmailCorporate(newEmail)
      ? UserType.EMPLOYEE
      : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      company.changeNumberOfEmployees(delta);
    }

    this.email = newEmail;
    this.type = newType;
    this.emailChangedEvents.push(new EmailChangedEvent(this.userId, newEmail));
  }
}

정리

  • 테스트 유의성 / 컨트롤러 단순성 / 성능 중 둘만 가질 수 있다.
  • 성능과 도메인 모델의 순수성을 지키고, 컨트롤러 복잡도만 완화한다.
  • CanExecute / Execute 로 의사 결정을 도메인에 남긴다.
  • 도메인 이벤트는 "무슨 일이 있었는가" 를 값으로 만들어 컨트롤러가 실어 나르게 한다.
CH 8

통합 테스트를 하는 이유

단위 테스트는 비즈니스 시나리오를, 통합 테스트는 가장 긴 주요 흐름을 맡는다. 관리 의존성은 실제로 쓰고, 비관리 의존성만 목으로 바꾼다.

8-1

통합 테스트는 무엇인가

단위 테스트가 도메인 모델을 맡으면, 통합 테스트는 컨트롤러를 맡는다.

핵심 단위 테스트로는 가능한 한 많은 비즈니스 시나리오와 예외를, 통합 테스트로는 가장 긴 주요 흐름과 단위 테스트가 다루지 못하는 예외 상황을 확인한다.

통합 테스트를 하는 이유

단위 테스트에만 전적으로 의존하면 시스템이 전체적으로 잘 작동하는지 확신하기 어렵다. 각 부분이 디비나 메세지 버스 같은 외부 시스템과 어떻게 통합되는지 확인이 필요하다.

통합 테스트는 단위 테스트와 달리 프로세스 외부 의존성과 도메인 모델을 연결하는 코드를 확인한다. 컨트롤러 사분면에서 의존성을 모두 목으로 대체하면 단위 테스트로 만들 수도 있지만, 모든 의존성을 대체하는 것은 불가능하다.

모든 테스트는 두 사분면에만 초점을 둔다 — 간단한 코드는 테스트할 필요가 없고, 지나치게 복잡한 코드는 애초에 리팩터링으로 없애야 한다.

다시 보는 테스트 피라미드

단위와 통합 테스트의 비율을 유지하는 것이 중요하다. 통합 테스트는 더 많은 코드를 거치므로 회귀 방지가 단위보다 우수하고, 결합도도 낮으므로 리팩터링 내성도 높다. 대신 느리고 유지비가 비싸다.

통합 테스트와 빠른 실패

통합 테스트에서 프로세스 외부 의존성과의 상호작용을 모두 확인하려면 가장 긴 주요 흐름을 선택하는 것이 좋다. 모든 흐름을 한 번에 지나가는 시나리오가 없다면, 전부 커버하는 데 필요한 만큼만 통합 테스트를 추가한다.

빠른 실패 원칙

예기치 않은 오류가 발생하자마자 현재 연산을 중단하는 것을 말한다. 일반적으로 예외를 던져 연산을 끊는다. 이는 통합 테스트를 늘리는 대신 선택할 수 있는 대안이기도 하다.

  • 피드백 루프 단축 — 버그를 빨리 발견할수록 쉽게 해결된다. 운영 환경까지 넘어간 버그는 개발 중 발견된 버그보다 수정 비용이 훨씬 크다.
  • 지속성 상태 보호 — 버그는 앱의 상태를 손상시킨다. 손상된 상태가 디비에 들어가면 고치기가 훨씬 어려워진다.

정리

  • 통합 테스트는 프로세스 외부 의존성과 도메인 모델을 연결하는 코드를 검증한다.
  • 모든 테스트는 도메인 모델 사분면과 컨트롤러 사분면에만 초점을 둔다.
  • 통합 테스트는 가장 긴 주요 흐름을 고른다.
  • 빠른 실패 원칙은 피드백 루프를 줄이고 디비의 상태 오염을 막는다.
8-2

어떤 프로세스 외부 의존성을 직접 테스트할까

관리 의존성은 실제 인스턴스로, 비관리 의존성은 목으로.

핵심 구분 기준은 하나다. 그 의존성과의 상호작용이 외부에서 보이는가. 보이면 비관리(계약), 안 보이면 관리(구현 세부 사항)다.
구분정의예테스트에서
관리 의존성 앱을 통해서만 접근 가능하고, 상호작용이 외부 환경에서 보이지 않는다 앱 전용 디비 실제 인스턴스 사용
비관리 의존성 상호작용을 외부에서 볼 수 있고, 다른 앱에 보이는 사이드 이펙트를 낸다 SMTP 서버, 메세지 버스 목으로 대체
같은 "프로세스 외부" 라도 성격이 정반대다 — 관리 의존성과의 통신은 언제든 바꿀 수 있는 구현 세부 사항이지만, 비관리 의존성과의 통신은 외부와 맺은 계약이다.

관리 의존성의 실제 인스턴스를 쓰면 외부 클라이언트 관점에서 최종 상태를 확인할 수 있다. 또 컬럼 이름 변경이나 테이블 분리 같은 디비 리팩터링에도 테스트가 함께 따라와 준다.

!

애초에 이 상황을 만들지 않는 것이 낫다

시스템 간 통합을 디비로 구현하면 시스템이 서로 결합되고 이후 개발이 복잡해진다. 가능하면 API 나 메세지 버스를 쓰는 것이 좋다. 이미 그렇게 되어 있다면, 다른 앱에서 보이는 테이블만 비관리 의존성으로 취급하고 꼭 필요한 경우가 아니면 그 테이블과 상호작용하는 방식을 바꾸지 않는다.

×

디비를 모킹한 통합 테스트는 의미가 없다

디비를 테스트할 수 없다면 통합 테스트를 아예 하지 말고 도메인 모델 단위 테스트에만 집중하는 편이 낫다. 디비를 모킹하면 결국 컨트롤러의 메소드를 호출해 보는 정도밖에 되지 않는다.

i

실제 디비를 띄우는 현실적인 방법 보강

"실제 디비를 못 쓴다" 는 제약은 요즘 상당 부분 해소됐다. Testcontainers 를 쓰면 테스트 실행 시점에 PostgreSQL / MySQL / MongoDB 같은 컨테이너를 일회용으로 띄우고 끝나면 정리한다. 개발자마다 별도 인스턴스를 두라는 10-1 의 요구도 이 방식으로 자연스럽게 충족된다. 다만 컨테이너 기동 시간이 붙으므로 10-3 의 지적대로 스위트 전체 실행 시간과 저울질해야 한다.

정리

  • 관리 의존성 = 앱을 통해서만 접근. 실제 인스턴스를 쓴다.
  • 비관리 의존성 = 상호작용이 외부에서 보임. 목으로 대체한다.
  • 공유 디비는 테이블 단위로 두 성격을 나눠 다룬다.
  • 실제 디비를 못 쓰면 통합 테스트를 포기하고 단위 테스트에 집중한다.
8-3

통합 테스트 예제

가장 긴 주요 흐름 하나를 골라 디비는 실제로, 메세지 버스는 목으로.

핵심 통합 테스트와 E2E 의 차이는 하나뿐이다. 비관리 의존성을 목으로 대체하는가.

테스트 대상 코드

user-controller.ts 
class UserController {
  constructor(
    private readonly database: Database,
    private readonly messageBus: IMessageBus
  ) {}

  changeEmail(userId: number, newEmail: string) {
    const userData = this.database.getUserById(userId);
    const user = UserFactory.create(userData);

    const error = user.canChangeEmail();
    if (error !== null) {
      return error;
    }

    const companyData = this.database.getCompany();
    const company = CompanyFactory.create(companyData);

    user.changeEmail(newEmail, company);

    this.database.saveCompany(company);
    this.database.saveUser(user);
    user.emailChangedEvents.forEach((event) => {
      this.messageBus.sendEmailChangedMessage(event.userId, event.newEmail);
    });

    return "ok";
  }
}

테스트할 시나리오

일반적인 지침은 가장 긴 주요 흐름과, 단위 테스트로는 수행할 수 없는 모든 예외 상황을 다루는 것이다. 여기서 가장 긴 흐름은 기업 이메일에서 일반 이메일로 변경하는 경우다.

  • 디비에서 유저와 회사가 모두 업데이트된다. 사용자는 유형과 이메일을, 회사는 직원 수를 바꾼다.
  • 메세지 버스로 메세지를 보낸다.

디비와 메세지 버스 분류하기

  • 디비 — 다른 앱이 접근할 수 없으므로 관리 의존성이다. 실제 인스턴스를 쓴다.
  • 메세지 버스 — 다른 시스템과 통신하는 수단이므로 비관리 의존성이다. 목으로 대체한다.

E2E 테스트는 어떤가

통합 테스트에서 비관리 의존성을 목으로 대체한다는 점만 빼면 둘은 거의 같다. E2E 는 어떤 프로세스 외부 의존성도 목으로 대체하지 않는다.

테스트 작성

user-controller.integration.spec.ts 
it("changing_email_from_corporate_to_non_corporate", () => {
  // 준비
  const db = new Database();
  const user = createUser("user@mycorp.com", UserType.EMPLOYEE, db);
  createCompany("mycorp.com", 1, db);

  const messageBusMock: jest.Mocked<IMessageBus> = {
    sendEmailChangedMessage: jest.fn(),
  };
  const sut = new UserController(db, messageBusMock);

  // 실행
  const result = sut.changeEmail(user.userId, "new@gmail.com");

  // 검증
  expect(result).toBe("ok");

  // 유저 상태 검증 — 디비에서 다시 읽어온다
  const userFromDb = UserFactory.create(db.getUserById(user.userId));
  expect(userFromDb.email).toBe("new@gmail.com");
  expect(userFromDb.type).toBe(UserType.CUSTOMER);

  // 회사 상태 검증
  const companyFromDb = CompanyFactory.create(db.getCompany());
  expect(companyFromDb.numberOfEmployees).toBe(0);

  // 목 상호작용 검증
  expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledWith(
    user.userId,
    "new@gmail.com"
  );
  expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledTimes(1);
});

✓

검증할 때 디비에서 다시 읽는 이유

준비 구절에서 만든 객체를 그대로 검증하면 메모리 상태만 확인하는 셈이다. 디비에서 새로 읽어와야 저장이 실제로 이뤄졌는지, 즉 외부 클라이언트가 볼 최종 상태가 맞는지 확인할 수 있다.

정리

  • 가장 긴 주요 흐름 하나로 모든 프로세스 외부 의존성을 지나간다.
  • 디비 = 관리 = 실제 인스턴스, 메세지 버스 = 비관리 = 목.
  • E2E 와의 차이는 비관리 의존성 대체 여부뿐이다.
  • 검증은 반드시 디비에서 다시 읽어 최종 상태를 확인한다.
8-4

의존성 추상화를 위한 인터페이스 사용

단일 구현을 위한 인터페이스는 추상화가 아니다.

핵심 인터페이스를 도입할 유일하게 타당한 이유는 비관리 의존성을 목으로 대체하기 위해서다. 그 외에는 YAGNI 위반이다.

인터페이스와 느슨한 결합

대부분의 개발자는 외부 의존성마다 인터페이스를 만든다. 흔히 드는 이유는 의존성을 추상화해 느슨한 결합을 달성하고, 기존 코드를 바꾸지 않고 기능을 추가해 OCP 를 지킨다는 것이다.

×

단일 구현을 위한 인터페이스는 추상화가 아니다

진정한 추상화는 발견하는 것이지 발명하는 것이 아니다. 구현이 하나뿐인 인터페이스는 이미 존재하는 클래스의 시그니처를 한 번 더 적어놓은 것에 지나지 않는다.

YAGNI 원칙 위배

YAGNI(You Aren't Gonna Need It)는 현재 필요하지 않은 기능에 시간을 들이지 말라는 원칙이다. 지금 비즈니스 담당자에게 필요하지 않은 것에 시간을 쓰면 그건 낭비다. 처음부터 실제 필요에 따라 기능을 구현하는 편이 유리하다.

프로세스 외부 의존성에 인터페이스를 쓰는 이유

인터페이스가 없으면 테스트 대역을 만들 수 없고, 따라서 SUT 와 프로세스 외부 의존성 간 상호작용을 확인할 수 없다. 이것이 인터페이스를 도입할 유일하게 타당한 이유다. 그렇다면 결론은 하나다. 비관리 의존성에만 인터페이스를 쓴다.

user-controller.ts 관리 의존성은 구체 타입 그대로 
class UserController {
  constructor(
    private readonly database: Database, // 관리 의존성 — 인터페이스 불필요
    private readonly messageBus: IMessageBus // 비관리 의존성 — 목으로 대체
  ) {}
}

프로세스 내부 의존성을 위한 인터페이스 사용

구현이 하나뿐인 도메인 클래스에 인터페이스를 도입하는 이유는 결국 목으로 처리하기 위해서다. 하지만 5-3 에서 봤듯 도메인 클래스 간 상호작용은 시스템 내부 통신, 즉 구현 세부 사항이므로 검증해서는 안 된다. 확인하는 순간 깨지기 쉬운 테스트가 되고 리팩터링 내성이 사라진다.

정리

  • 단일 구현 인터페이스는 추상화가 아니며 YAGNI 위반이다.
  • 인터페이스의 유일한 정당한 이유는 비관리 의존성 대체다.
  • 관리 의존성은 구체 타입 그대로 주입한다.
  • 도메인 클래스에 인터페이스를 씌우면 내부 통신을 검증하게 되어 테스트가 깨진다.
8-5

통합 테스트 모범 사례

경계를 긋고, 계층을 줄이고, 순환을 끊고, 실행 구절을 하나로.

핵심 통합 테스트를 개선하는 네 가지 지침 중 셋은 제품 코드를 고치는 일이다. 테스트가 어려운 건 대개 테스트 탓이 아니다.

도메인 모델 경계 명시하기

도메인 모델을 코드베이스에서 명시적이고 잘 알려진 위치에 둔다. 경계를 지정하면 그 부분을 더 잘 보여주고 설명할 수 있다. 모든 도메인 로직이 하나의 뚜렷한 우산 아래에 있고 여기저기 흩어져 있지 않다면, 세부 배치는 크게 중요하지 않다.

계층 수 줄이기

추상 계층이 너무 많으면 코드베이스를 탐색하기 어렵고, 간단한 연산조차 숨은 로직을 이해하기 힘들어진다. 지나친 추상화는 단위 테스트에도 통합 테스트에도 도움이 되지 않는다.

✓

대부분의 백엔드 앱은 세 계층이면 충분하다

서비스 / 인프라 / 도메인. 가능한 한 간접 계층을 적게 쓴다.

i

통합 테스트에서의 예외 보강

등록 → 로그인처럼 순서 자체가 비싸고 필연적인 흐름은 통합 테스트에서 예외적으로 묶기도 한다. 다만 이는 어쩔 수 없는 절충이지 권장 사항이 아니다. 묶을 때는 그 이유를 테스트 이름이나 주석에 남긴다.

정리

  • 도메인 모델을 명시적이고 잘 알려진 위치에 모은다.
  • 백엔드는 서비스 / 인프라 / 도메인 세 계층으로 충분하다.
  • 콜백 대신 값을 반환해 순환 의존성을 끊는다.
  • 실행 구절은 하나. 통합 테스트에서만 예외적으로 묶는다.
8-6

로깅 기능을 테스트하는 방법

지원 로깅은 비즈니스 요구 사항이므로 테스트하고, 진단 로깅은 구현 세부 사항이므로 테스트하지 않는다.

핵심 기준은 하나다. 그 로그를 개발자 말고 다른 사람이 보는가. 본다면 테스트하고, 개발자만 본다면 언제든 지울 수 있는 구현 세부 사항이다.

로깅을 테스트해야 하는가

로깅은 코드베이스 어디에서나 필요할 수 있는 횡단 기능이며, 텍스트 파일이나 디비 같은 프로세스 외부 의존성에 사이드 이펙트를 낸다.

종류대상성격테스트
지원 로깅지원 담당자, 시스템 관리자비즈니스 요구 사항한다
진단 로깅개발자언제든 수정 가능한 구현 세부 사항하지 않는다

로깅을 어떻게 테스트해야 하는가

로깅에는 프로세스 외부 의존성이 있으므로, 그런 기능에 적용하던 규칙이 그대로 적용된다. 즉 앱과 로그 저장소 간 상호작용을 확인하려면 목을 쓴다.

ILogger 위에 래퍼 도입하기

지원 로깅은 비즈니스 요구 사항이므로 코드베이스에 그렇게 반영하는 것이 좋다. 내부적으로는 ILogger 를 쓰되, 비즈니스에 필요한 지원 로그를 명시적으로 나열하는 DomainLogger 를 만든다.

user.ts 
class User {
  private userId: string;
  private email: string;
  private type: UserType;

  private logger: ILogger;
  private domainLogger: IDomainLogger;

  changeEmail(newEmail: string, company: Company) {
    this.logger.info(`changeEmail: ${this.userId}`); // 진단 로그

    if (this.email === newEmail) {
      return;
    }

    const newType = company.isEmailCorporate(newEmail)
      ? UserType.EMPLOYEE
      : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      company.changeNumberOfEmployees(delta);

      // 지원 로그 — 도메인 언어로 표현된다
      this.domainLogger.userTypeHasChanged(this.userId, this.type, newType);
    }

    this.email = newEmail;
    this.type = newType;

    this.logger.info(`changeEmail: done: ${this.userId}`); // 진단 로그
  }
}
domain-logger.ts 
interface IDomainLogger {
  userTypeHasChanged(
    userId: string,
    oldType: UserType,
    newType: UserType
  ): void;
}

class DomainLogger implements IDomainLogger {
  constructor(private readonly logger: ILogger) {}

  userTypeHasChanged(userId: string, oldType: UserType, newType: UserType) {
    this.logger.info(`userTypeHasChanged: ${userId}: ${oldType} -> ${newType}`);
  }
}

DomainLogger 는 ILogger 위에서 동작하며 도메인 언어로 로그 항목을 선언한다. 덕분에 지원 로깅이 무엇인지 이해하고 유지하기 쉬워진다.

구조화된 로깅

구조화된 로깅(structured logging) 은 로그 데이터의 캡처와 렌더링을 분리하는 기술이다. 로그 저장소에 구조가 존재하며, 캡처한 데이터를 JSON, CSV 등으로 렌더링하도록 로깅 라이브러리에서 설정할 수 있다.

지원 로깅과 진단 로깅을 위한 테스트

위 코드에는 아직 문제가 있다. 도메인 안에 로거가 들어 있어서 비즈니스 로직과 프로세스 외부 의존성과의 통신을 분리해야 한다는 원칙을 위배한다. 해결책은 7-4 와 같다. 사용자 유형 변경을 추적하는 도메인 이벤트를 도입하는 것이다.

class User {
  private userId: string;
  private email: string;
  private type: UserType;

  private logger: ILogger;
  readonly domainEvents: DomainEvent[] = [];

  changeEmail(newEmail: string, company: Company) {
    this.logger.info(`changeEmail: ${this.userId}`);

    if (this.email === newEmail) {
      return;
    }

    const newType = company.isEmailCorporate(newEmail)
      ? UserType.EMPLOYEE
      : UserType.CUSTOMER;

    if (this.type !== newType) {
      const delta = newType === UserType.EMPLOYEE ? 1 : -1;
      company.changeNumberOfEmployees(delta);

      // 지원 로그를 도메인 이벤트로 대체
      this.addDomainEvent(
        new UserTypeChangedEvent(this.userId, this.type, newType)
      );
    }

    this.email = newEmail;
    this.type = newType;

    this.logger.info(`changeEmail: done: ${this.userId}`);
  }

  private addDomainEvent(event: DomainEvent) {
    this.domainEvents.push(event);
  }
}

CH 9

목 처리에 대한 모범 사례

목을 쓸 자리는 딱 하나다. 통합 테스트에서, 시스템 끝단의 비관리 의존성. 그 원칙에서 나오는 다섯 가지 실전 지침.

9-1

목의 가치를 극대화하기

목은 시스템 끝단에 붙일수록 더 많은 코드를 지켜준다.

핵심 비관리 의존성과 통신하는 마지막 타입을 목으로 처리한다. 그래야 통합 테스트가 거치는 클래스 수가 늘어나 회귀 방지가 극대화된다.

시스템 끝에서 상호 작용 검증하기

목을 쓸 때는 시스템 끝에서 비관리 의존성과의 상호작용을 검증해야 한다. 회귀 방지는 테스트 중에 실행되는 코드 양의 함수이므로, 목을 바깥으로 밀수록 그 사이에 있는 클래스가 전부 테스트 범위 안으로 들어온다.

8-6 의 DomainLogger 와 Logger 를 예로 들면, 둘 중 바깥쪽인 Logger 를 목으로 처리해야 DomainLogger 의 변환 로직까지 함께 검증된다.

✓

두 가지 책임을 분리한다

외부 라이브러리의 복잡성을 숨기는 일과 모든 앱 메세지를 한 곳에 모으는 일은 서로 다른 책임이므로 분리되어 있는 게 좋다. 목은 그중 바깥쪽, 즉 라이브러리에 가장 가까운 타입에 붙인다.

목을 스파이로 대체하기

스파이와 목은 목적이 같고 생성하는 방식만 다르다.

구분생성 방식
목외부 라이브러리의 도움으로 생성한다

스파이가 목보다 나은 지점 보강

스파이는 테스트가 직접 소유하는 코드다. 메세지 포맷 같은 검증 로직을 한곳에 모아두면, 포맷이 바뀌었을 때 고칠 자리가 하나뿐이다. 목 라이브러리로 같은 일을 하면 그 문자열 조립이 테스트마다 흩어진다.

정리

  • 목은 비관리 의존성과 통신하는 마지막 타입에 붙인다.
  • 바깥으로 밀수록 실행되는 코드가 늘어 회귀 방지가 커진다.
  • 스파이는 직접 작성한 목이며, 검증 로직을 한곳에 모을 수 있다.
  • 플루언트 인터페이스로 검증 구절을 문장처럼 읽히게 만든다.
9-2

목 처리에 대한 모범 사례

목은 통합 테스트만을 위한 것이다.

핵심 도메인 모델은 단위 테스트, 컨트롤러는 통합 테스트. 목은 비관리 의존성을 다루는 컨트롤러에만 붙으므로, 결국 통합 테스트에만 등장한다.

목은 통합 테스트만을 위한 것

도메인 모델은 단위 테스트에 속하고, 컨트롤러는 통합 테스트에 속한다. 목은 비관리 의존성에만 해당하며, 그런 의존성을 처리하는 코드는 컨트롤러뿐이다. 따라서 통합 테스트에서 컨트롤러를 테스트할 때만 목을 적용한다.

테스트당 목이 하나일 필요는 없음

"단위" 는 코드 단위가 아니라 동작 단위이며, 동작 단위를 구현하는 데 필요한 코드의 양과는 상관이 없다. 마찬가지로 동작 단위를 검증하는 데 필요한 목의 수도 상관이 없다. 목의 수는 오직 그 연산에 참여하는 비관리 의존성의 수에만 의존한다.

호출 횟수 검증하기

비관리 의존성과의 통신에서는 두 가지를 모두 확인해야 한다.

  • 예상하는 호출이 있는가
  • 예상치 못한 호출이 없는가

앱은 외부 시스템이 예상하는 메세지를 생략해서도 안 되고, 예상치 못한 메세지를 만들어서도 안 되기 때문이다.

integration.spec.ts 
// 기대한 인자로 호출됐는가
expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledWith(
  userId,
  newEmail
);

// 그리고 그 외의 호출은 없었는가
expect(messageBusMock.sendEmailChangedMessage).toHaveBeenCalledTimes(1);

보유 타입만 목으로 처리하기

서드파티 라이브러리 위에는 항상 어댑터를 작성하고, 기본 타입 대신 그 어댑터를 목으로 처리하라는 지침이다. 이유는 세 가지다.

  1. 서드파티 코드의 작동 방식을 정확히 알지 못한다
  2. 라이브러리가 인터페이스를 제공하더라도 확인이 필요하다

    목으로 처리한 동작이 실제 외부 라이브러리의 동작과 일치하는지 검증해야 한다.

  3. 기술 세부 사항이 앱에 필요하지 않다

    어댑터가 그것을 추상화하고, 앱 관점에서 라이브러리와의 관계를 정의해야 한다.

✓

어댑터는 손상 방지 계층이다

실제로 어댑터는 우리 코드와 외부 환경 사이의 손상 방지 계층(anti-corruption layer) 으로 작동한다. 외부 라이브러리의 모델이 우리 도메인 모델을 오염시키는 것을 막는다.

정리

  • 목은 통합 테스트에서 컨트롤러를 테스트할 때만 쓴다.
  • 목의 수는 연산에 참여하는 비관리 의존성 수로만 결정된다.
  • 기대한 호출과 예상치 못한 호출 둘 다 검증한다.
  • 서드파티 타입이 아니라 그 위의 어댑터를 목으로 처리한다.
CH 10

데이터베이스 테스트

실제 디비로 통합 테스트를 돌리려면 그 전에 갖춰야 할 것들이 있다. 스키마의 형상 관리, 마이그레이션, 그리고 테스트 시작 시점의 데이터 정리.

10-1

데이터베이스 테스트를 위한 전제 조건

스키마를 코드처럼 다루고, 개발자마다 인스턴스를 주고, 마이그레이션으로 배포한다.

핵심 운영 릴리스 이후에는 마이그레이션 기반 배포가 정답이다. 상태 기반 방식은 데이터 모션 문제를 다룰 수 없기 때문이다.

디비를 형상 관리 시스템에 유지

첫 단계는 디비 스키마를 일반 코드로 취급하는 것이다. 그러면 스키마를 과거의 특정 시점으로 되돌릴 수 있어 운영 환경의 버그를 재현하는 데 유용하다.

!

원천 정보는 하나여야 한다

형상 관리의 스키마와 실제 운영 디비를 둘 다 손으로 관리하면 복수의 원천 정보가 생겨 부담이 가중된다. 형상 관리로 스키마를 관리하기로 했다면 외부에서 디비 구조를 직접 수정해서는 안 된다.

참조 데이터도 디비 스키마다

참조 데이터는 앱이 제대로 작동하도록 미리 채워야 하는 데이터다. 앱의 필수 사항이므로 다른 디비 자료들과 함께 SQL INSERT 형태로 관리해야 한다.

구분앱에서 수정관리 위치
일반 데이터가능디비 (런타임에 생성됨)
참조 데이터불가능형상 관리 (마이그레이션 스크립트)

모든 개발자를 위한 별도의 디비 인스턴스

개발자마다 별도의 디비 인스턴스를 쓰는 것이 좋다. 하나를 공유하면 두 가지 문제가 생긴다.

  • 서로 다른 개발자가 실행한 테스트가 서로 간섭한다.
  • 하위 호환성이 없는 변경 하나가 다른 개발자의 작업을 막는다.

상태 기반 디비 배포와 마이그레이션 기반 디비 배포

상태 기반

개발 사이클 내내 유지 보수하는 모델 디비가 따로 있다. 배포 시점에 비교 도구가 운영 디비를 모델 디비와 대조해 스크립트를 자동 생성하고 최신 상태로 맞춘다. 이때 비교 도구는 운영 디비의 상태와 상관없이 불필요한 테이블을 삭제하고 컬럼명을 바꾸는 등 동기화에 필요한 모든 작업을 수행한다.

마이그레이션 기반

디비를 어떤 버전에서 다른 버전으로 전환하는 명시적인 마이그레이션을 작성한다. 자동화 도구로 동기화할 수 없고 업그레이드 스크립트를 직접 써야 한다. 형상 관리에 저장하는 산출물이 디비 상태가 아니라 마이그레이션 코드(보통 SQL)라는 점이 핵심이다.

방식디비 상태마이그레이션 메커니즘
상태 기반 방식명시적암묵적
마이그레이션 기반 방식암묵적명시적
왜 마이그레이션 기반을 선호하는가

데이터 모션(data motion) 문제 때문이다. 데이터 모션은 새 스키마를 준수하도록 기존 데이터의 형태를 변경하는 과정을 말한다.

  • 참조 데이터도 스키마의 일부다. 마이그레이션으로만 제어한다.
  • 개발자마다 별도의 디비 인스턴스를 준다.
  • 운영 릴리스 이후에는 마이그레이션 기반 배포. 데이터 모션 때문이다.
10-2

디비 트랜잭션 관리

레포지토리는 데이터를 다루고, 트랜잭션은 커밋과 롤백을 다룬다.

핵심 통합 테스트에서는 준비 / 실행 / 검증 구절마다 별도의 트랜잭션을 쓴다. 운영 환경의 동작을 그대로 재현하기 위해서다.

제품 코드에서 트랜잭션 관리

읽기 전용 연산에는 여러 트랜잭션을 열어도 괜찮다. 하지만 변경 연산이 포함되면 모순을 피하기 위해 그 연산의 모든 업데이트가 원자적이어야 한다.

디비 트랜잭션에서 디비 연결 분리하기

업데이트할 데이터를 정하는 일과, 그 업데이트를 유지할지 롤백할지 정하는 일은 서로 다른 책임이다. 이를 두 클래스로 나눈다.

작업 단위로 트랜잭션 업그레이드 하기

작업 단위(Unit of Work) 는 디비를 변경하기 위해 해야 할 모든 업데이트를 파악하고, 이를 하나의 단위로 실행한다. 트랜잭션과 달리 작업 단위는 비즈니스 연산이 끝나는 시점에 모든 업데이트를 한꺼번에 실행한다. 대부분의 ORM 프레임워크가 이 패턴을 구현하고 있다.

통합 테스트에서 디비 트랜잭션 관리하기

!

테스트 구절 간에 트랜잭션을 재사용하지 않는다

운영 환경에서는 각 비즈니스 연산마다 전용 인스턴스가 있고, 컨트롤러 호출 직전에 생성되어 직후에 폐기된다. 통합 테스트도 그래야 하므로 준비 / 실행 / 검증마다 별도의 트랜잭션이나 작업 단위를 쓴다.

구절 간에 하나를 재사용하면, 실행 구절이 만든 변경 사항이 아직 커밋되지 않은 채 검증 구절에서 메모리 캐시로 읽히는 일이 생긴다. 그러면 저장이 실제로 이뤄졌는지 확인할 수 없다.

정리

  • 변경 연산의 모든 업데이트는 원자적이어야 한다.
  • 데이터 접근은 Repository, 커밋/롤백은 Transaction 이 책임진다.
  • 작업 단위는 연산 종료 시점에 업데이트를 몰아서 실행한다. ORM 이 대개 구현한다.
  • 통합 테스트는 구절마다 별도의 트랜잭션을 쓴다.
10-3

테스트 데이터 생명주기

순차 실행하고, 테스트 시작 시점에 정리한다.

핵심 데이터 정리는 테스트 시작 시점에 한다. 빠르고, 일관성이 있으며, 실수로 건너뛸 수도 없다.

공유 디비를 쓰면 통합 테스트를 서로 분리할 수 없다. 통합 테스트를 순차적으로 실행해야 하고, 실행 간에 남은 데이터를 제거해야 한다. 원칙은 하나다. 테스트는 디비 상태에 의존해서는 안 되고, 스스로 디비를 원하는 조건으로 만들어야 한다.

병렬 테스트 실행과 순차적 테스트 실행

통합 테스트를 병렬로 실행하려면 상당한 노력이 필요하다. 성능 향상에 시간을 허비하기보다 순차 실행이 더 실용적이다.

대부분의 테스트 프레임워크는 별도의 테스트 모음을 정의하고 일부에 대해 병렬 처리를 비활성화할 수 있다. 두 개의 테스트군을 만들고 통합 테스트군만 병렬 처리를 끈다.

각 테스트 전 디비 백업 복원 가장 느리다. 컨테이너를 쓰더라도 인스턴스를 지우고 새로 만드는 데 보통 몇 초가 걸려 전체 실행 시간이 빠르게 늘어난다

디비 정리 스크립트 작성

삭제 스크립트는 일반 데이터를 모두 제거하되 참조 데이터는 건드리지 않아야 한다. 나머지 디비 스키마와 참조 데이터는 오직 마이그레이션으로만 제어한다.

clear-database.ts 
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

export const clearDatabase = async () => {
  await prisma.$executeRaw`SET FOREIGN_KEY_CHECKS = 0;`;

  const tables = Object.keys(prisma).filter(
    (key) =>
      typeof prisma[key] === "object" &&
      prisma[key] !== null &&
      "deleteMany" in prisma[key]
  );

  await Promise.all(tables.map((table) => prisma[table].deleteMany()));

  await prisma.$executeRaw`SET FOREIGN_KEY_CHECKS = 1;`;
};

describe("UserController", () => {
  beforeEach(async () => {
    await clearDatabase(); // 시작 시점에 정리
  });
});

정리

  • 정리는 테스트 시작 시점에 한다. 나머지 세 방법은 각각 결함이 있다.
  • 정리 스크립트는 일반 데이터만 지우고 참조 데이터는 남긴다.
  • 인메모리 디비는 운영 디비와 동작이 달라 쓰지 않는다.

디비 테스트에 대한 일반적인 질문

쓰기는 철저히, 읽기는 임계치를 높게, 레포지토리는 직접 테스트하지 않는다.

핵심 쓰기 테스트는 철저하게, 읽기 테스트는 임계치를 높게. 위험의 크기가 다르기 때문이다.

읽기 테스트를 해야 할까

쓰기 테스트의 중요성

쓰기 테스트는 매우 철저하게 해야 한다. 위험이 크기 때문이다. 쓰기 작업이 손상되면 데이터가 망가지고, 그 영향이 디비뿐 아니라 외부 앱까지 미친다. 쓰기를 다루는 테스트는 그런 실수에 대한 보호책이므로 아주 가치 있다.

읽기 테스트는
  • 읽기 작업에는 보통 해로운 문제가 없으므로 테스트 임계치가 쓰기보다 높아야 한다.
  • 가장 복잡하거나 중요한 읽기 작업만 테스트하고 나머지는 무시하는 편이 좋다.
  • 읽기에는 추상화 계층이 거의 없어서 단위 테스트가 아무 소용이 없다. 테스트한다면 실제 디비와 결합한 통합 테스트로 한다.

레포지토리를 테스트해야 될까

레포지토리는 디비 위에 유용한 추상화를 제공한다. 도메인 객체를 디비에 어떻게 매핑하는지 테스트하는 것이 유익해 보이고, 실제로 실수할 여지도 상당하다. 하지만 결론은 하지 않는다 이다. 유지비가 높고 회귀 방지가 떨어져 테스트 스위트에 손실이 생기기 때문이다.

측면레포지토리 테스트
높은 유지비 복잡도는 거의 없는데 프로세스 외부 의존성인 디비와 통신한다. 부담은 일반 통합 테스트와 비슷하다
낮은 회귀 방지 레포지토리는 복잡하지 않고, 그 회귀 방지 효과가 일반 통합 테스트가 주는 이점과 겹친다
✓

결론

레포지토리는 직접 테스트하지 말고, 포괄적인 통합 테스트 스위트의 일부로 취급한다. 통합 테스트가 컨트롤러를 지나갈 때 레포지토리도 함께 실행되므로 이미 덮여 있다.

정리

  • 쓰기 테스트는 철저하게. 데이터 손상은 외부 앱까지 영향을 미친다.
  • 읽기 테스트는 임계치를 높게. 가장 복잡하거나 중요한 것만 한다.
  • 읽기는 단위 테스트로 이득이 없다. 통합 테스트로 한다.
  • 레포지토리는 직접 테스트하지 않고 통합 테스트에 묻어간다.
CH 11

단위 테스트 안티패턴

마지막은 함정 모음이다. 비공개 메소드 테스트, 상태 노출, 도메인 지식 유출, 코드 오염, 구체 클래스 목 처리, 그리고 시간.

11-1

비공개 메소드 단위 테스트

비공개 메소드가 테스트하고 싶어질 만큼 복잡하다면, 그건 클래스가 하나 빠졌다는 뜻이다.

핵심 비공개 메소드를 테스트하는 것 자체가 나쁜 게 아니라, 비공개 메소드가 구현 세부 사항의 프록시이기 때문에 나쁘다.

비공개 메소드 테스트와 테스트 취약성

단위 테스트를 하려고 비공개 메소드를 노출하는 것은 식별할 수 있는 동작만 테스트한다는 원칙을 위반한다. 노출하는 순간 테스트가 구현 세부 사항과 결합되고 리팩터링 내성이 떨어진다.

비공개 메소드는 직접 테스트하는 대신, 그것을 포함하는 식별할 수 있는 동작을 통해 간접적으로 테스트한다.

비공개 메소드와 불필요한 커버리지

때로는 비공개 메소드가 너무 복잡해서, 식별할 수 있는 동작만으로는 충분한 커버리지를 얻을 수 없는 경우가 있다. 식별할 수 있는 동작에 이미 합리적인 커버리지가 있다고 가정하면, 아래 둘 중 하나가 원인이다.

죽은 코드

테스트에서 벗어난 코드가 어디에서도 사용되지 않는다면, 리팩터링 후에 남은 관계없는 코드일 수 있다. 이런 죽은 코드는 삭제한다.

추상화가 누락됨

비공개 메소드가 너무 복잡하다면 별도의 클래스로 도출해야 한다는 신호다. 추상화가 빠져 있다는 징후다.

11-2

비공개 상태 노출

테스트는 제품 코드와 정확히 같은 방식으로 SUT 과 상호작용해야 한다.

핵심 테스트에는 특별한 권한이 없다. 클라이언트가 볼 수 없는 것은 테스트도 봐서는 안 된다.

단위 테스트 목적으로만 비공개 상태를 노출하는 것은 안티패턴이다. 이 지침은 비공개 메소드 지침과 같다. 비공개로 지켜야 하는 상태를 노출하지 말고, 식별할 수 있는 동작만 테스트한다.

예제

customer.ts 
enum CustomerStatus {
  Regular,
  Preferred,
}

class Customer {
  private status: CustomerStatus = CustomerStatus.Regular;

  promote() {
    this.status = CustomerStatus.Preferred; // 사이드 이펙트는 비공개 필드
  }

  getDiscount() {
    return this.status === CustomerStatus.Preferred ? 0.05 : 0;
  }
}

promote() 의 사이드 이펙트는 status 의 변경인데, 비공개 필드라 직접 확인할 수 없다. 여기서 테스트를 위해 이 필드를 공개하는 순간 안티패턴이 된다.

유출된 테스트가 놓치는 것

제품 코드의 + 를 * 로 바꾸면, 왼쪽 테스트도 expected 를 똑같이 바꿔야 통과한다. 다시 말해 제품 코드와 테스트가 같이 틀려도 초록불이 뜬다. 회귀 방지가 0 이다.

직관적으로 보이지 않을 수 있지만, 테스트를 작성할 때는 특정 구현을 암시하지 않고 예상 결과를 하드코딩하는 것이 좋다.

정리

  • 테스트에서 제품 코드의 알고리즘을 다시 계산하지 않는다.
  • 기대 결과는 하드코딩하고, 케이스가 여럿이면 매개변수화한다.
  • 유출된 테스트는 제품 코드와 함께 틀려도 통과한다.
11-4

코드 오염

테스트만을 위한 코드를 제품 코드에 남기지 않는다.

핵심 코드 오염의 진짜 비용은 한 줄의 if 가 아니라, 테스트 코드와 제품 코드가 섞여 유지비가 늘어나는 것이다.

코드 오염은 테스트를 위해 필요한 코드를 제품 코드에 추가하는 것을 말한다.

logger.ts 불린 스위치가 있는 로거 
class Logger {
  constructor(private readonly isTestEnv: boolean) {}

  log(text: string) {
    if (this.isTestEnv) {
      return; // 테스트를 위한 분기가 제품 코드에 남았다
    }

    // text logging...
  }
}

it("some_test", () => {
  const logger = new Logger(true); // 테스트 환경 표시
  const controller = new Controller();
  controller.someMethod(logger);
});

이 분기는 제품 코드가 자기가 테스트 중인지 알아야 한다는 뜻이고, 그런 지식이 코드베이스 곳곳에 퍼지기 시작한다. 해결책은 테스트 코드를 제품 코드에서 완전히 분리하는 것이다.

logger.ts 별도 구현으로 분리 
interface ILogger {
  log(text: string): void;
}

class Logger implements ILogger {
  log(text: string) {
    // text logging...
  }
}

// 테스트 코드에만 존재한다
class FakeLogger implements ILogger {
  log(text: string): void {
    // do nothing
  }
}

it("some_test", () => {
  const logger = new FakeLogger();
  const controller = new Controller();
  controller.someMethod(logger);
});

정리

  • 코드 오염 = 테스트를 위한 코드가 제품 코드에 들어가는 것.
  • 제품 코드가 "테스트 중인지" 를 알면 안 된다.
  • 인터페이스를 두고 페이크 구현은 테스트 코드 쪽에 둔다.
11-5

구체 클래스를 목으로 처리하기

클래스 일부만 목으로 덮고 싶어지는 순간, 그 클래스는 두 가지 일을 하고 있다.

핵심 부분 목이 필요하다는 것은 단일 책임 원칙 위반의 신호다. 목으로 덮지 말고 클래스를 쪼갠다.

구체 클래스를 목으로 처리하면 본래 클래스의 일부 기능을 보존할 수 있어 때때로 유용해 보인다. 하지만 이 대안에는 중대한 단점이 있다.

예제 — 통계 계산 클래스

statistics-calculator.ts 두 가지 책임 
class StatisticsCalculator {
  calculate(customerId: number): { totalWeight: number; totalCost: number } {
    const records = this.getDeliveries(customerId);
    const totalWeight = records.reduce((acc, cur) => acc + cur.weight, 0);
    const totalCost = records.reduce((acc, cur) => acc + cur.cost, 0);
    return { totalWeight, totalCost };
  }

  getDeliveries(customerId: number): DeliveryRecord[] {
    // 프로세스 외부 의존성을 호출해 배달 목록을 조회한다
  }
}
customer-controller.ts 
class CustomerController {
  constructor(private readonly calculator: StatisticsCalculator) {}

  getStatistics(customerId: number): string {
    const { totalCost, totalWeight } = this.calculator.calculate(customerId);

    return `
      총 비용 : ${totalCost}
      총 무게 : ${totalWeight}
    `;
  }
}

이 컨트롤러를 테스트할 때 딜레마가 생긴다.

  • StatisticsCalculator 가 비관리 프로세스 외부 의존성을 쓰므로 실제 인스턴스를 넣을 수 없다.
  • 동시에 StatisticsCalculator 는 중요한 계산 로직을 담고 있어 통째로 교체하고 싶지도 않다.

흔히 택하는 해법 — 부분 목

customer-controller.spec.ts 단일 책임 위반의 증거

  const sut = new CustomerController(calculator);

  const result = sut.getStatistics(1);

노트의 예제는 TestStatisticsCalculator 를 정의해놓고 정작 new CustomerController(stub) 에 정의되지 않은 stub 을 넘긴다. 위처럼 jest.spyOn 으로 인스턴스의 메소드 하나만 덮어쓰는 편이 부분 목의 의도를 더 정확히 보여준다.

클래스의 일부만 대체하고 나머지는 그대로 쓸 수 있어 편해 보이지만, 일부 기능을 지키려고 클래스를 목으로 처리하는 것은 단일 책임 원칙 위반의 증거다.

책임에 따른 클래스 분리하기

StatisticsCalculator 는 비관리 의존성과 통신하는 책임과 통계를 계산하는 책임이라는, 서로 관련 없는 두 가지가 결합돼 있다. 이를 분리한다.

delivery-gateway.ts 책임 분리 
interface IDeliveryGateway {
  getDeliveries(customerId: number): DeliveryRecord[];
}

class DeliveryGateway implements IDeliveryGateway {
  getDeliveries(customerId: number): DeliveryRecord[] {
    // 프로세스 외부 의존성 호출
    return [];
  }
}

class StatisticsCalculator {
  calculate(records: DeliveryRecord[]) {
    const totalWeight = records.reduce((acc, cur) => acc + cur.weight, 0);
    const totalCost = records.reduce((acc, cur) => acc + cur.cost, 0);
    return { totalWeight, totalCost };
  }
}
customer-controller.spec.ts 험블 객체 패턴 
class CustomerController {
  constructor(
    private readonly calculator: StatisticsCalculator,
    private readonly gateway: IDeliveryGateway
  ) {}

  getStatistics(customerId: number): string {
    const records = this.gateway.getDeliveries(customerId);
    const { totalCost, totalWeight } = this.calculator.calculate(records);

    return `
      총 비용 : ${totalCost}
      총 무게 : ${totalWeight}
    `;
  }
}

it("customer_with_no_delivery", () => {
  const stub: jest.Mocked<IDeliveryGateway> = {
    getDeliveries: jest.fn().mockReturnValue([]),
  };
  const calculator = new StatisticsCalculator();
  const sut = new CustomerController(calculator, stub);

  const result = sut.getStatistics(1);

  expect(result).toBe(`
      총 비용 : 0
      총 무게 : 0
    `);
});

이 리팩터링은 험블 객체 패턴의 또 다른 사례다. 이제 비관리 의존성과의 통신은 DeliveryGateway 가, 통계 계산은 StatisticsCalculator 가 담당한다. 각자 자기 방식으로 테스트할 수 있게 됐다.

정리

  • 구체 클래스의 일부만 목으로 덮고 싶다면 그 클래스가 두 가지 일을 하고 있는 것이다.
  • 부분 목은 단일 책임 원칙 위반의 증상이지 해결책이 아니다.
  • 외부 통신 책임과 계산 책임을 분리하면 부분 목이 필요 없어진다.
11-6

시간 처리하기

시간은 서비스로 주입하지 말고 값으로 주입한다.

핵심 앰비언트 컨텍스트로서의 시간은 안티패턴이다. 명시적 의존성으로 주입하되, 서비스보다는 값이 낫다.

많은 앱이 현재 날짜와 시간에 접근해야 한다. 하지만 시간에 따라 달라지는 기능을 테스트하면 거짓 양성이 발생할 수 있다. 어제 통과한 테스트가 오늘 실패하는 식이다.

앰비언트 컨텍스트로서의 시간

date-time-server.ts 안티패턴 
class DateTimeServer {
  private static func: () => Date;

  static init(func: () => Date) {
    this.func = func;
  }

  static get now(): Date {
    return this.func();
  }
}

// 운영 환경
DateTimeServer.init(() => new Date());

// 테스트 환경
DateTimeServer.init(() => new Date("2020-01-01"));
×

로거 때와 같은 안티패턴이다

의존성이 숨어 있고, 변경하기 어려우며, 테스트가 더 어려워진다. 게다가 정적 필드는 테스트 간 공유 의존성을 만들어 그 테스트들을 통합 테스트 영역으로 밀어낸다. 앞선 테스트가 설정한 시간이 다음 테스트에 새어 나가기 때문이다.

명시적 의존성으로서의 시간

앰비언트 컨텍스트보다는 서비스 또는 일반 값으로 시간 의존성을 명시적으로 주입하는 편이 낫다. 그리고 둘 중에서는 값 쪽이 더 좋다.

서비스로 주입
interface IDateTimeServer {
  now(): Date;
}

class DateTimeServer implements IDateTimeServer {
  now(): Date {
    return new Date();
  }
}

class InquiryController {
  constructor(
    private readonly dateTimeServer: IDateTimeServer
  ) {}

  approveInquiry(id: number) {
    const inquiry = getById(id);
    inquiry.approve(this.dateTimeServer.now());
    saveInquiry(inquiry);
  }
}
값으로 주입
class Inquiry {
  // 도메인 모델은 값만 받는다
  approve(now: Date) {
    // ...
  }
}

class InquiryController {
  constructor(
    private readonly dateTimeServer: IDateTimeServer
  ) {}

  approveInquiry(id: number) {
    const inquiry = getById(id);
    // 컨트롤러가 값으로 바꿔 넘긴다
    inquiry.approve(this.dateTimeServer.now());
    saveInquiry(inquiry);
  }
}
✓

왜 값이 더 나은가

도메인 모델에 시간을 값으로 넘기면 협력자가 하나 줄어든다. 7-1 의 사분면에서 도메인 모델은 협력자가 적을수록 좋고, 시간이 값이 되는 순간 그 메소드는 수학적 함수가 된다. 시간을 읽는 일은 셸(컨트롤러)의 책임이다.

가짜 타이머라는 또 다른 선택지 최신 반영

주입이 불가능한 레거시 코드에는 테스트 프레임워크의 가짜 타이머를 쓸 수 있다. Jest 는 jest.useFakeTimers() 로 타이머를 가짜로 바꾸고, 모던 가짜 타이머에서만 동작하는 jest.setSystemTime(new Date("2020-01-01")) 로 시스템 시각을 고정할 수 있다. 다만 이는 어디까지나 차선책이다. 코드를 고칠 수 있다면 시간을 값으로 주입하는 쪽이 언제나 낫다.

inquiry.spec.ts 값 주입 방식의 테스트 
it("approved_inquiry_records_the_approval_time", () => {
  const sut = new Inquiry();
  const now = new Date("2020-01-01T00:00:00Z");

  sut.approve(now);

  expect(sut.approvedAt).toEqual(now);
});

정리

  • 시간을 앰비언트 컨텍스트(정적 필드)로 두면 공유 의존성이 생겨 테스트가 오염된다.
  • 명시적으로 주입하되, 도메인 모델에는 값으로 넘긴다.
  • 시간을 읽는 책임은 컨트롤러(가변 셸)에 둔다.
  • 고칠 수 없는 코드에는 jest.setSystemTime 같은 가짜 타이머가 차선책이다.
