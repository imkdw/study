레디스 기본 개념

레디스를 키-값 저장소라고만 부르면 절반만 맞다. 값의 자리에 리스트/해시/셋/정렬된 셋/비트맵/스트림이 들어간다. 이 챕터는 그 값의 종류와, 종류에 상관없이 키를 다루는 커맨드를 다룬다.

3-1

레디스 자료구조

레디스의 값(value)은 문자열만이 아니다. 어떤 자료구조를 고르느냐가 곧 그 기능의 시간복잡도가 된다.

핵심 레디스는 키-값 저장소가 아니라 자료구조 서버다. 값의 자리에 list, hash, set, sorted set, bitmap, stream이 들어가고 각각 전용 커맨드를 가진다.

string

  • 레디스에서 데이터를 저장할 수 있는 가장 간단한 자료구조
  • 최대 512MB의 문자열 데이터를 저장할 수 있다
  • binary-safe 하기 때문에 이미지 바이트값, HTTP 응답값 등도 그대로 넣을 수 있다
redis-cli
127.0.0.1:6379> set hello world
OK
127.0.0.1:6379> get hello
"world"
NX 옵션

NX 옵션을 사용하면 지정한 키가 없을 때만 새로운 키를 저장한다.

(nil)
127.0.0.1:6379> get hello
"world"

함께 알아두기 보강

SET 은 옵션을 붙여 여러 커맨드를 대체한다. EX/PX 로 만료시간을 같은 원자적 연산 안에서 지정할 수 있고(SET k v EX 60 NX), KEEPTTL 은 값만 바꾸고 기존 TTL 을 유지하며, GET 옵션(6.2+)은 덮어쓰기 직전의 값을 돌려준다. 그래서 SETNX/SETEX/GETSET 은 모두 deprecated 로 표시되어 있다.

숫자 저장
  • 숫자도 저장할 수 있고 INCR/INCRBY, DECR/DECRBY 로 원자적으로 조작할 수 있다
  • 원자적이라는 것은 여러 클라이언트가 동시에 호출해도 경쟁 상태가 생기지 않는다는 뜻이다
redis-cli
127.0.0.1:6379> set counter 100
OK
127.0.0.1:6379> INCR counter
(integer) 101
127.0.0.1:6379> INCRBY counter 100
(integer) 201
127.0.0.1:6379> DECR counter
(integer) 200
127.0.0.1:6379> DECRBY counter 20
(integer) 180
여러 개 한 번에 제어하기

MSET, MGET 으로 한 번에 여러 개의 키를 조작할 수 있다.

redis-cli
127.0.0.1:6379> MSET a 10 b 20 c 30
OK
127.0.0.1:6379> MGET a b c
1) "10"
2) "20"
3) "30"

list

  • 순서를 가지는 문자열의 모음으로 최대 약 42억 개(232-1)의 아이템을 담을 수 있다
  • 인덱스로 접근할 수 있고, 서비스에서는 보통 스택이나 큐로 쓴다
list 는 양쪽 끝이 모두 입구이자 출구다 — 왼쪽(L)과 오른쪽(R) 커맨드를 어떻게 조합하느냐에 따라 스택이 되기도, 큐가 되기도 한다. 음수 인덱스는 오른쪽 끝을 -1 로 두고 왼쪽으로 커진다.
LPUSH, RPUSH
  • LPUSH : list 의 왼쪽에 데이터를 추가
  • RPUSH : list 의 오른쪽에 데이터를 추가
redis-cli
127.0.0.1:6379> LPUSH myList E
(integer) 1
127.0.0.1:6379> RPUSH myList B
(integer) 2
127.0.0.1:6379> LPUSH myList A C
(integer) 4
127.0.0.1:6379> RPUSH myList D O
(integer) 6
127.0.0.1:6379> LRANGE myList 0 -1
1) "C"
2) "A"
3) "E"
4) "B"
5) "D"
6) "O"
127.0.0.1:6379> LRANGE myList 0 2
1) "C"
2) "A"
3) "E"

LPUSH myList A C 한 줄에 두 개를 넣으면 A 를 먼저, C 를 나중에 왼쪽으로 밀어 넣는다. 그래서 결과가 A C 가 아니라 C A 순서가 된다.

LPOP

왼쪽에서 데이터를 삭제하고 해당 데이터를 반환한다.

redis-cli
127.0.0.1:6379> LRANGE myList 0 -1
1) "B"
2) "D"
3) "O"
127.0.0.1:6379> LPOP myList
"B"
127.0.0.1:6379> LRANGE myList 0 -1
1) "D"
2) "O"
LTRIM
  • 지정한 범위를 제외한 모든 아이템을 삭제한다
  • LPOP 과 달리 삭제한 데이터를 반환하지 않는다
redis-cli
127.0.0.1:6379> LRANGE myList 0 -1
1) "Z"
2) "O"
3) "Y"
4) "W"
5) "B"
6) "A"
7) "D"
8) "O"
127.0.0.1:6379> LTRIM myList 0 2
OK
127.0.0.1:6379> LRANGE myList 0 -1
1) "Z"
2) "O"
3) "Y"

최대 1000개의 로그만 유지한다고 가정하면, 넣을 때마다 잘라 주면 된다.

redis-cli
127.0.0.1:6379> LPUSH log data
(integer) 1
127.0.0.1:6379> LTRIM log 0 999
OK
LINSERT
  • 원하는 데이터의 앞이나 뒤에 데이터를 추가할 수 있다
  • BEFORE 는 앞에, AFTER 는 뒤에 추가할 때 사용한다

2) "C"
3) "E"
4) "B"
5) "A"

127.0.0.1:6379> lrange mylist 0 -1

원하는 인덱스의 데이터를 확인한다.

redis-cli

list 의 인덱스 접근은 공짜가 아니다

LINDEX 와 LSET 은 O(N) 이다. 양 끝에서 멀수록 느려진다. 인덱스로 자주 찍어야 하는 데이터라면 list 대신 sorted set 을 쓰는 편이 낫다.

hash

  • 필드-값 쌍을 가진 아이템의 집합
  • 하나의 hash 안에서 아이템은 필드-값 쌍으로 저장된다
  • HSET 저장 / HGET 조회 / HMGET 여러 개 조회 / HGETALL 전체 조회
redis-cli
127.0.0.1:6379> hset product:123 name "happy hacking"
(integer) 1
127.0.0.1:6379> hset product:123 typeid 35
(integer) 1
127.0.0.1:6379> hget product:123 typeid
"35"
127.0.0.1:6379> hmget product:123 name typeid
1) "happy hacking"
2) "35"
127.0.0.1:6379> hgetall product:123
1) "name"
2) "happy hacking"
3) "typeid"
4) "35"
!

HGETALL 은 O(N) 이다

필드가 수만 개인 hash 에 HGETALL 을 걸면 싱글 스레드가 그동안 묶인다. 필요한 필드만 HMGET 으로 뽑거나, 커서를 쓰는 HSCAN 으로 나눠 읽는 편이 안전하다.

set

  • 정렬되지 않은 문자열의 모음
  • 아이템이 중복해서 저장되지 않는다
  • 객체 간 관계를 계산하거나 유일한 원소를 구해야 하는 경우에 쓴다
커맨드
  • SADD : set 에 아이템 추가
  • SREM : 원하는 아이템 삭제
  • SPOP : 랜덤으로 아이템 하나를 꺼내 반환
  • SUNION 합집합 / SINTER 교집합 / SDIFF 차집합
redis-cli
127.0.0.1:6379> SADD myset A
(integer) 1
127.0.0.1:6379> sadd myset a a a b b b c c c
(integer) 3
127.0.0.1:6379> smembers myset
1) "A"
2) "a"
3) "b"
4) "c"
127.0.0.1:6379> SREM myset b
(integer) 1
127.0.0.1:6379> SPOP myset
"a"

sadd myset a a a b b b c c c 가 9개를 넣었는데 반환값이 3인 것은, 실제로 새로 추가된 개수만 돌려주기 때문이다. 대문자 A 와 소문자 a 가 따로 남는 것에서 보듯 값은 대소문자를 구분한다.

redis-cli
127.0.0.1:6379> sadd set:111 A B C D E
(integer) 5
127.0.0.1:6379> sadd set:222 D E F G H
(integer) 5
127.0.0.1:6379> SINTER set:111 set:222
1) "D"
2) "E"
127.0.0.1:6379> SUNION set:111 set:222
1) "A"
2) "B"
3) "C"
4) "D"
5) "E"
6) "F"
7) "G"
8) "H"
127.0.0.1:6379> SDIFF set:111 set:222
1) "A"
2) "B"
3) "C"
집합 연산이 서버 안에서 끝난다 — 두 집합을 애플리케이션으로 끌어와 비교하는 대신 커맨드 한 줄로 교집합/차집합을 얻는다. 다만 원소 수에 비례하는 O(N) 연산이라 큰 집합끼리는 조심해야 한다.

sorted set

  • 스코어 값에 따라 정렬되는 고유한 문자열의 집합
  • 같은 스코어를 가진 아이템은 사전순으로 정렬된다
  • 인덱스로 접근할 일이 많다면 list 보다 sorted set 이 낫다
    • list : O(N)
    • sorted set : O(log N)
ZADD
  • sorted set 에 아이템을 추가하고, 한 번에 여러 개도 가능하다
  • 이미 데이터가 있다면 스코어만 업데이트되고, 스코어가 바뀌었다면 재정렬된다
  • 스코어는 배정밀도 부동소수점 숫자를 문자열로 표현한 값이어야 한다
  • 옵션
    • XX : 아이템이 이미 있을 때만 스코어를 업데이트
    • NX : 아이템이 없을 때만 신규 삽입하고, 기존 아이템의 스코어는 건드리지 않음
    • LT : 새 스코어가 기존보다 작을 때만 업데이트. 기존 데이터가 없으면 삽입
    • GT : 새 스코어가 기존보다 클 때만 업데이트. 기존 데이터가 없으면 삽입
redis-cli
127.0.0.1:6379> zadd score:1 100 user:b
(integer) 1
127.0.0.1:6379> zadd score:1 150 user:a 150 user:c 200 user:f
(integer) 3
인덱스로 데이터 조회

ZRANGE 로 조회하고 WITHSCORES 옵션으로 스코어까지 함께 볼 수 있다.

redis-cli
127.0.0.1:6379> zrange score:1 1 3 withscores
1) "user:a"
2) "150"
3) "user:c"
4) "150"
5) "user:f"
6) "200"
127.0.0.1:6379> zrange score:1 1 3
1) "user:a"
2) "user:c"
3) "user:f"

같은 스코어 150 을 가진 user:a 와 user:c 가 사전순으로 놓인 것을 확인할 수 있다.

스코어로 데이터 조회

ZRANGE 에 BYSCORE 옵션을 붙이면 인덱스가 아니라 스코어 범위로 조회한다.

원하는 것커맨드
스코어 100 이상 150 이하zrange score:1 100 150 byscore withscores
100 을 제외한 150 이하zrange score:1 (100 150 byscore withscores
100 이상, 150 은 제외zrange score:1 100 (150 byscore withscores
200 이상 전부zrange score:1 200 +inf byscore withscores

여는 괄호 ( 가 경계값 제외를 뜻하고, +inf/-inf 로 한쪽을 열어 둘 수 있다.

사전 순으로 데이터 조회
  • BYLEX 옵션으로 사전식 순서에 따라 특정 아이템을 조회할 수 있다
  • b 부터 f 로 시작하는 아이템 조회 : zrange sortedset (b (f bylex
  • 문자열은 ASCII 바이트 값 순으로 저장되므로 한글도 같은 방식으로 조회된다

BYLEX 는 전제 조건이 있다

사전순 조회는 모든 아이템의 스코어가 같을 때만 의미 있는 결과를 준다. 스코어가 제각각이면 정렬 기준이 스코어 우선이라 사전순 범위가 어긋난다.

비트맵

  • string 자료구조에 비트 연산을 수행할 수 있도록 확장한 형태
  • 장점은 저장 공간을 획기적으로 줄일 수 있다는 것
  • SETBIT 비트 저장 / GETBIT 비트 조회 / BITFIELD 여러 비트 저장 / BITCOUNT 켜진 비트 수 계산

127.0.0.1:6379> setbit mybit 2 1
(integer) 0
127.0.0.1:6379> getbit mybit 2
(integer) 1
127.0.0.1:6379> bitfiend mybit2 set u1 6 1 set u1 10 1
(error) ERR unknown command 'bitfiend'
127.0.0.1:6379> bitfield mybit2 set u1 6 1 set u1 10 1
1) (integer) 0
2) (integer) 0
127.0.0.1:6379> bitcount mybit2
(integer) 2

HyperLogLog

  • 집합의 원소 개수인 카디널리티를 추정하는 자료구조
  • 중복되지 않는 고유한 값을 집계할 때 유용하다
  • set 에 비해 메모리를 크게 아낄 수 있고, 표준 오차는 0.81% 로 매우 정확하다
  • PFADD 추가 / PFCOUNT 개수 계산

(integer) 1
127.0.0.1:6379> pfadd members 500
(integer) 1

(integer) 1
127.0.0.1:6379> pfcount members
(integer) 3
i

함께 알아두기 보강

HyperLogLog 는 키 하나가 최대 12KB 로 고정이고 최대 264 개 원소까지 추정한다. 대신 넣은 값을 되돌려 받을 수 없다 — "이 유저가 방문했나?"는 답할 수 없고 "몇 명이 방문했나?"만 답한다. 여러 개를 합칠 때는 PFMERGE 를 쓴다. (근거: Redis Docs — HyperLogLog)

Geospatial

  • 경도, 위도 데이터 쌍의 집합으로 지리 데이터를 간편하게 저장하는 방법
  • 내부적으로는 sorted set 을 사용하고, 키는 중복해서 저장되지 않는다
  • GEOADD 추가 / GEOPOS 조회 / GEODIST 거리 계산
redis-cli
127.0.0.1:6379> geoadd travel 14.1232142141 50.12312312 prague
(integer) 1
127.0.0.1:6379> geopos travel prague
1) 1) "14.12321180105209351"
   2) "50.12312365203619891"
127.0.0.1:6379> geoadd travel 126.12312321 37.12312 seoul
(integer) 1
127.0.0.1:6379> geodist travel seoul prague KM
"8257.0826"

입력한 좌표와 GEOPOS 로 돌려받은 좌표가 소수점 아래에서 미세하게 다르다. 내부적으로 좌표를 52비트 geohash 정수로 바꿔 sorted set 의 스코어에 넣기 때문이며, 오차는 1m 미만이다.

stream

  • 메시지 브로커로 사용할 수 있게 해 주는 자료구조
  • 데이터를 계속 추가하는 방식이라 이벤트나 로그성 데이터 저장에 쓸 수 있다

자세한 내용은 6-4. 스트림 에서 다룬다.

정리

  • string 은 512MB 까지의 binary-safe 값. SET 에 NX/XX/EX 를 붙이면 조건부 저장과 만료를 원자적으로 처리한다.
  • list 는 양쪽 끝이 O(1), 가운데는 O(N). 인덱스 접근이 잦으면 sorted set 으로 바꾼다.
  • set 은 중복 제거와 집합 연산, sorted set 은 정렬된 상태로의 저장이 존재 이유다.
  • 비트맵과 HyperLogLog 는 "정확한 값" 대신 "작은 메모리"를 택한 자료구조다. HLL 은 12KB 고정, 오차 0.81%.
  • Geospatial 은 별도 자료구조가 아니라 sorted set 에 좌표를 인코딩한 것이다.
3-2

레디스에서 키를 관리하는 방법

자료구조가 무엇이든 상관없이 통하는 커맨드들. 그리고 운영 중에 쓰면 서비스가 멈추는 커맨드들.

핵심 레디스에서 빈 컬렉션은 존재하지 않는다. 첫 아이템을 넣으면 키가 생기고 마지막 아이템을 빼면 키가 사라진다. 없는 키에 대한 조회는 에러가 아니라 "비어 있음"으로 답한다.

키의 자동 생성과 삭제

하나의 키가 여러 개의 아이템을 가지는 자료구조(stream, set, sorted set, hash, list)는 명시적으로 키를 생성하거나 삭제하지 않아도 알아서 생기고 사라진다.

키가 없을 때 아이템을 넣으면 빈 자료구조가 먼저 생성된다
redis-cli
127.0.0.1:6379> del list1
(integer) 0
127.0.0.1:6379> lpush list1 1 2 3
(integer) 3

단, 그 키에 이미 다른 자료구조가 들어 있으면 에러가 난다.

redis-cli 타입 충돌
127.0.0.1:6379> set hello world
OK
127.0.0.1:6379> lpush hello 1 2 3
(error) WRONGTYPE Operation against a key holding the wrong kind of value
127.0.0.1:6379> type hello
string
×

WRONGTYPE

WRONGTYPE Operation against a key holding the wrong kind of value
운영에서 이 에러가 뜨면 대개 키 네이밍 규칙이 겹친 것이다. user:1 을 어디선가는 string 으로, 어디선가는 hash 로 쓰고 있는 상황을 의심해 보자.

모든 아이템을 삭제하면 키도 자동으로 삭제된다
redis-cli
127.0.0.1:6379> lpush mylist 1 2
(integer) 2
127.0.0.1:6379> lpop mylist
"2"
127.0.0.1:6379> lpop mylist
"1"
127.0.0.1:6379> type mylist
none
키가 없어도 에러 대신 "비어 있는 것처럼" 동작한다
redis-cli
127.0.0.1:6379> del myl
(integer) 0
127.0.0.1:6379> llen myl
(integer) 0
127.0.0.1:6379> lpop myl
(nil)

키와 관련된 커맨드

자료구조에 상관없이 모두 사용할 수 있는 커맨드들이다.

EXISTS

키가 존재하는지 확인한다.

redis-cli
127.0.0.1:6379> set hello world
OK
127.0.0.1:6379> exists hello
(integer) 1
127.0.0.1:6379> exists world
(integer) 0
KEYS
  • 레디스에 저장된 모든 키를 조회한다
  • 글롭(glob) 패턴 스타일로 동작한다
  • 대량의 키를 조회하면 싱글 스레드 특성상 그동안 다른 커맨드를 처리할 수 없다. 운영 환경에서는 쓰지 않는다
SCAN
  • KEYS 대신 키를 조회할 때 사용한다
  • 커서 기반이라 여러 번 나눠 호출하므로 안전하다
  • COUNT, MATCH 등의 옵션을 쓸 수 있다
  • SSCAN, HSCAN, ZSCAN 은 각각 set, hash, sorted set 내부를 훑는 커맨드다
i

SCAN 의 보증 범위 보강

COUNT 는 "한 번에 이만큼 돌려줘"가 아니라 내부적으로 훑을 양의 힌트다. 그래서 매 호출의 결과 개수는 들쭉날쭉하고 0개가 나올 수도 있다 — 커서가 0으로 돌아올 때까지 반복해야 한다. 또한 스캔 도중 계속 존재한 키는 반드시 한 번 이상 반환되지만, 같은 키가 여러 번 나올 수 있다. 애플리케이션에서 중복을 걸러야 한다.

SORT
  • list, set, sorted set 에만 사용할 수 있다
  • 키 내부의 아이템을 정렬해서 반환한다
  • ASC/DESC 로 오름차순/내림차순, ALPHA 로 사전순 정렬
redis-cli
127.0.0.1:6379> lpush mylist a
(integer) 1
127.0.0.1:6379> lpush mylist b
(integer) 2
127.0.0.1:6379> lpush mylist c
(integer) 3
127.0.0.1:6379> lpush mylist hello
(integer) 4
127.0.0.1:6379> sort mylist
(error) ERR One or more scores can't be converted into double
127.0.0.1:6379> sort mylist alpha
1) "a"
2) "b"
3) "c"
4) "hello"

SORT 는 기본적으로 아이템을 숫자로 해석한다. 문자열을 정렬하려면 ALPHA 를 붙여야 한다. 참고로 SORT 는 ACL 의 @dangerous 카테고리에 들어 있을 만큼 무거운 커맨드다.

RENAME / RENAMENX
  • RENAME : 대상 이름이 이미 있어도 덮어쓰며 이름을 바꾼다
  • RENAMENX : 대상 이름이 없을 때만 이름을 바꾼다
redis-cli
127.0.0.1:6379> set a apple
OK
127.0.0.1:6379> set b banana
OK
127.0.0.1:6379> rename a aa
OK
127.0.0.1:6379> get aa
"apple"
127.0.0.1:6379> set a apple
OK
127.0.0.1:6379> renamenx a b
(integer) 0
127.0.0.1:6379> get b
"banana"

renamenx a b 가 0 을 돌려준 것은 b 가 이미 있어서 아무것도 하지 않았다는 뜻이다. 그래서 b 의 값은 banana 그대로다.

COPY
  • A 키를 B 로 복사한다
  • B 가 이미 있는 경우 REPLACE 옵션을 쓰면 기존 값을 지우고 복사한다
redis-cli
127.0.0.1:6379> set b nanana
OK
127.0.0.1:6379> copy b bb
(integer) 1
127.0.0.1:6379> get b
"nanana"
127.0.0.1:6379> get bb
"nanana"
OBJECT
  • 키에 대한 상세 정보를 반환한다
  • ENCODING, IDLETIME 등의 서브커맨드로 추가 정보를 확인할 수 있다
redis-cli
127.0.0.1:6379> set hello world
OK
127.0.0.1:6379> OBJECT ENCODING hello
"embstr"
127.0.0.1:6379> OBJECT IDLETIME HELLO
(nil)

마지막 줄이 (nil) 인 이유는 키 이름이 대소문자를 구분하기 때문이다. 저장한 키는 hello 인데 HELLO 를 물어봤으니 없는 키다. embstr 은 44바이트 이하의 짧은 문자열에 쓰이는 인코딩으로, 같은 string 이라도 길이에 따라 int/embstr/raw 로 내부 표현이 달라진다.

FLUSHALL
  • 레디스에 저장된 모든 키를 삭제한다
  • 기본은 동기(SYNC) 방식이라 모든 키가 지워질 때까지 다른 요청을 처리할 수 없다
  • ASYNC 옵션을 쓰면 백그라운드로 실행되며, 실행 당시 존재했던 키만 삭제한다
  • lazyfree-lazy-user-flush 옵션이 켜져 있으면 ASYNC 를 붙이지 않아도 비동기로 동작한다
!

원문 교정 원문 교정

노트에는 옵션 이름이 layfree-lazy-user-flush 로 적혀 있으나 실제 이름은 lazyfree-lazy-user-flush 이며 기본값은 no 다. (근거: redis.conf)

DEL

존재하는 키를 삭제한다.

redis-cli
127.0.0.1:6379> set a b
OK
127.0.0.1:6379> del a
(integer) 1
UNLINK
  • DEL 과 비슷하게 데이터를 삭제하는 커맨드
  • 우선 키와 매핑된 데이터를 끊어내기만 하고, 실제 메모리 반환은 백그라운드 스레드가 처리한다
  • 아이템이 아주 많은 키에 DEL 을 쓰면 그동안 서버가 멈추므로 UNLINK 를 권장한다
  • lazyfree-lazy-user-del 이 yes 면 DEL 도 UNLINK 처럼 동작한다 (기본값 no)
EXPIRE
  • 키의 만료시간을 지정한다
  • 옵션 (7.0 이상)
    • NX : 해당 키에 만료시간이 없을 때만 수행
    • XX : 해당 키에 만료시간이 있을 때만 수행
    • GT : 현재 만료시간보다 새로 입력한 값이 클 때만 수행
    • LT : 현재 만료시간보다 새로 입력한 값이 작을 때만 수행
EXPIREAT

특정 유닉스 타임스탬프에 만료되도록 지정한다.

redis-cli
127.0.0.1:6379> expireat hello 1251231241
(integer) 1

이 타임스탬프는 2009년이다. 과거 시각을 넣으면 만료를 기다리지 않고 즉시 삭제된다. 아래에서 expiretime hello 가 -2 를 돌려주는 것이 그 결과다.

EXPIRETIME
  • 키가 삭제될 유닉스 타임스탬프를 초 단위로 반환한다
  • 키는 있지만 만료시간이 없으면 -1
  • 키가 없으면 -2
redis-cli
127.0.0.1:6379> expiretime hello
(integer) -2
TTL
  • 키가 몇 초 뒤에 만료되는지 반환한다
  • 키는 있지만 만료시간이 없으면 -1, 키가 없으면 -2

정리

  • 컬렉션 계열 키는 첫 아이템에서 생기고 마지막 아이템에서 사라진다. "빈 list" 는 존재하지 않는다.
  • 없는 키에 대한 읽기는 에러가 아니라 0 또는 nil 이다. 타입이 어긋날 때만 WRONGTYPE 이 난다.
  • KEYS, SORT, 동기 FLUSHALL, 큰 키에 대한 DEL 은 전부 서버를 멈춘다. 각각 SCAN, 애플리케이션 정렬, ASYNC, UNLINK 로 바꾼다.
  • TTL 관련 반환값 -1(만료 없음)과 -2(키 없음)를 구분해서 다뤄야 한다.
CH 4

레디스 자료구조 활용 사례

RDB(관계형 DB)로 짜면 테이블 세 개와 정렬 쿼리가 필요한 기능이, 레디스에서는 커맨드 한두 줄로 끝나는 경우가 있다. 리더보드/검색 기록/태그/랜덤/카운팅/위치 기반 — 여섯 가지 사례로 자료구조 선택이 곧 설계라는 것을 확인한다.

4-1

sorted set을 활용한 실시간 리더보드

정렬은 읽을 때 하는 일이라는 상식을 뒤집는다. sorted set 은 쓸 때 이미 정렬해서 넣는다.

핵심 리더보드의 비용은 정렬에 있다. sorted set 은 데이터가 들어가는 순간 제자리를 찾아 들어가므로 조회 시 정렬 비용이 0 이다.
  • 리더보드는 사용자의 스코어를 기반으로 다른 사용자와 비교해 순위를 정하는 형태다
  • 사용자 기준이라 계산해야 할 데이터가 유저 수에 따라 가파르게 늘어난다
  • sorted set 을 쓰면 데이터가 저장될 때부터 정렬되어 들어간다
    • 유저의 스코어를 가중치로 저장하면 읽어올 때마다 정렬할 필요가 없다

ZADD 로 데이터 저장

스코어를 기준으로 오름차순 정렬된 데이터가 저장된다.

redis-cli
127.0.0.1:6379> zadd score:240911 28 player:286
(integer) 1
127.0.0.1:6379> zadd score:240911 400 player:234
(integer) 1
127.0.0.1:6379> zadd score:240911 45 player:101
(integer) 1
127.0.0.1:6379> zadd score:240911 357 player:24
(integer) 1
127.0.0.1:6379> zadd score:240911 199 player:143
(integer) 1

 6) "199"
 7) "player:24"
 8) "357"

10) "400"

redis-cli

1) "player:234"
2) "400"
3) "player:24"

  • 레디스는 ZUNIONSTORE 한 줄로 끝난다

클러스터에서는 키가 같은 슬롯에 있어야 한다

ZUNIONSTORE 처럼 여러 키를 한 번에 다루는 커맨드는 클러스터 모드에서 대상 키들이 같은 해시 슬롯에 있어야 실행된다. 일별 키를 합칠 계획이라면 처음부터 score:{2409}11 처럼 해시태그를 넣어 두자. (10-2 해시태그 참고)

정리

  • sorted set 은 저장 시점에 정렬을 끝내므로 리더보드 조회가 O(log N + M) 이다.
  • 점수 덮어쓰기는 ZADD, 누적은 ZINCRBY. ZADD 의 반환 0 은 실패가 아니라 "새로 추가된 멤버 없음"이다.
  • 기간별 집계는 ZUNIONSTORE 로 서버에서 처리한다. WEIGHTS 로 가중치도 줄 수 있다.
  • 새 코드에서는 ZREVRANGE 대신 ZRANGE ... REV 를 쓴다.
4-2

sorted set을 활용한 최근 검색 기록

스코어 자리에 점수 대신 시각을 넣으면, 같은 자료구조가 최신순 목록이 된다.

핵심 검색 기록에 필요한 세 가지 — 중복 제거, 최신순 정렬, 개수 제한 — 을 sorted set 하나가 전부 처리한다.
  • RDB 에서는 이런 작업이 필요하다
    • 기존에 있던 키워드인지 확인하고 새로 추가하거나 날짜를 갱신
    • 주기적으로 오래된 데이터를 삭제하고, 조회할 때마다 정렬
  • 레디스에서는
    • 저장될 때부터 중복을 허용하지 않는다
    • 검색한 날짜를 스코어로 저장하면 알아서 정렬된다

스코어에 무엇을 넣을 것인가 보강

여기서는 20240911112233 같은 사람이 읽는 형식을 스코어로 썼다. sorted set 의 스코어는 배정밀도 부동소수점이라 정수를 정확히 표현할 수 있는 한계가 253 (약 9007조) 이므로 초 단위까지의 이 형식은 안전하다. 다만 밀리초까지 붙인 17자리(20240911112233123)는 그 한계를 넘어 값이 뭉개진다. 밀리초가 필요하면 유닉스 타임스탬프(밀리초)를 쓰는 편이 안전하다.

set을 활용한 태그 기능

게시글에서 태그로, 태그에서 게시글로. 양방향 인덱스를 set 두 벌로 만든다.

핵심 RDB 의 조인 테이블이 하던 일을, 방향이 다른 두 벌의 set 이 대신한다. 조회하려는 방향마다 인덱스를 하나씩 만드는 셈이다.
!

원문 교정 원문 교정

원문 노트의 제목과 소제목은 "sorted set" 으로 되어 있지만, 실제 실습 커맨드는 전부 SADD/SMEMBERS/SINTER 즉 set 이다. 태그는 순서가 필요 없고 중복 제거와 교집합만 필요하므로 set 이 맞는 선택이다. 이 문서에서는 set 기준으로 정리했다.

  • RDB 에서의 구현: 게시글, 태그, 게시글-태그 조인 — 총 3개의 테이블이 필요하다
  • 레디스에서의 구현: 태그 중복 체크를 따로 하지 않아도 된다 (set 이 알아서 막는다)

RDB 라면 조인 테이블을 두 번 걸고 GROUP BY ... HAVING COUNT(*) = 2 를 써야 하는 질의가 커맨드 한 줄이 된다.

정리

  • 태그는 set 두 벌(게시글→태그, 태그→게시글)로 구현한다. 조인이 없는 대신 인덱스를 방향별로 직접 만든다.
  • 중복 태그 방지는 set 이 공짜로 해 준다. 별도 체크 로직이 필요 없다.
  • "태그 A 이면서 B" 는 SINTER 한 줄. 다만 삭제 시 두 방향을 함께 정리해야 데이터가 어긋나지 않는다.

랜덤 데이터 추출

ORDER BY RAND() 가 전체 정렬을 부르는 동안, 레디스는 자료구조에서 하나를 그냥 집는다.

핵심 RDB 의 랜덤 추출은 전체를 훑고 정렬한 뒤 하나를 고르는 일이지만, 레디스의 랜덤 커맨드는 자료구조 내부에서 바로 하나를 집는다.
  • RDB 에서는 보통 ORDER BY RAND() 로 구현한다
    • 정렬/필터링/개수 제한 등 여러 과정이 필요해서 데이터가 많으면 부하가 커진다
  • 레디스에서는 RANDOMKEY 로 랜덤 값을 O(1) 에 얻을 수 있다

노트에 set 용 커맨드가 DRANTMEMBER 로 적혀 있으나 실제 이름은 SRANDMEMBER 다. 참고로 SRANDMEMBER 는 값을 남겨 둔 채 읽고, SPOP 은 꺼내면서 삭제한다. 추첨처럼 중복 당첨을 막아야 하면 SPOP, 단순 샘플링이면 SRANDMEMBER 다.

COUNT 의 부호가 중복 허용 여부를 정한다

COUNT 에 양수를 쓰면 중복 없이, 음수를 쓰면 중복을 허용해서 가져온다.

redis-cli
127.0.0.1:6379> hrandfield person 2
1) "name"
2) "name:kimch"
127.0.0.1:6379> hrandfield person -2
1) "name:dongwoo"
2) "name:dongwoo"

양수일 때는 요소 수보다 큰 값을 요청해도 있는 만큼만 돌아오지만, 음수일 때는 요청한 개수만큼 반드시 채워서 돌아온다.

!

RANDOMKEY 는 O(1) 이지만 무료는 아니다

만료된 키가 많이 쌓여 있으면 RANDOMKEY 가 유효한 키를 찾을 때까지 내부적으로 여러 번 재시도한다. 또한 이 커맨드는 전체 키스페이스를 대상으로 하므로 "이벤트 응모자 중 한 명"처럼 특정 집합에서 뽑아야 한다면 SRANDMEMBER 쪽이 의도에 맞는다.

정리

  • 랜덤 추출은 자료구조별 전용 커맨드를 쓴다 — SRANDMEMBER/HRANDFIELD/ZRANDMEMBER.
  • COUNT 양수는 중복 없이, 음수는 중복을 허용해 개수를 반드시 채운다.
  • 당첨자 추첨처럼 다시 뽑히면 안 되는 경우는 SPOP, 그냥 보기만 할 때는 SRANDMEMBER.

레디스에서 다양한 카운팅 방법

정확한 수가 필요한가, 대략의 수가 필요한가. 그 답에 따라 set 과 비트맵과 HyperLogLog 로 갈린다.

핵심 카운팅은 정확도와 메모리의 거래다. 유저 목록까지 필요하면 set, 존재 여부만 필요하면 비트맵, 개수만 필요하면 HyperLogLog.
방법1000만 유저 기준 메모리정확도개별 조회
set수백 MB정확가능
bitmap약 1.2MB정확가능 (정수 ID 필요)
HyperLogLog12KB 고정오차 0.81%불가

좋아요 처리하기

  • RDB 에서 초당 몇만 건의 카운트를 감당하기에는 부하가 심하다
  • set 에 좋아요를 누른 유저를 넣고 SCARD 로 개수를 세면 간단히 구현된다
redis-cli
127.0.0.1:6379> sadd comment-like:123 1 2 3 4 5
(integer) 5
127.0.0.1:6379> scard comment-like:123
(integer) 5
!

원문 교정 원문 교정

노트에는 "sorted set 을 사용해서"라고 적혀 있지만 실습 커맨드는 SADD/SCARD 즉 set 이다. 좋아요는 순위가 필요 없고 "같은 사람이 두 번 누르지 못하게" 하는 것이 목적이므로 set 이 맞다. SCARD 는 개수를 세지 않고 저장된 값을 읽으므로 O(1) 이다.

읽지 않은 메시지 수 카운팅하기

  • 레디스에 쌓아 두었다가 필요한 시점에 한 번에 꺼내 DB 를 갱신하는 방식으로 구현한다
  • RDB 의 부하를 최소화하고 성능을 끌어올릴 수 있다
  • 예시 — 유저 아이디 123, 채널 아이디 4234 인 채널에 새 메시지 1건이 도착한 상황
redis-cli
127.0.0.1:6379> hset user:234 channel:4234 1
(integer) 1
127.0.0.1:6379> hincrby user:234 channel:4234 1
(integer) 2
127.0.0.1:6379> hgetall user:234
1) "channel:4234"
2) "2"

유저 하나에 hash 하나를 두고 채널을 필드로 삼으면, 유저의 모든 채널 뱃지를 HGETALL 한 번에 가져올 수 있다. HINCRBY 는 원자적이라 동시에 여러 메시지가 들어와도 카운트가 어긋나지 않는다.

DAU 구하기

  • DAU 는 하루 동안 서비스에 방문한 사용자 수를 뜻한다
  • set 으로도 되지만 1000만 명이 방문했을 때 모든 유저 아이디를 저장하는 건 비효율적이다
    • 가능하면 하나의 키당 2~300만 개 수준으로 값을 나누는 것이 좋다
  • 비트맵을 쓰면 메모리를 아끼면서 실시간 DAU 구현이 가능하다
  • 유저 한 명이 비트 하나이므로 1000만 명이 약 1.2MB 로 표현된다
!

원문 교정 원문 교정

노트의 "1000만 명의 사용자는 1개의 비트로 표현이 가능"은 1000만 명을 1비트에 담는다는 뜻으로 읽힌다. 정확히는 사용자 한 명이 1비트를 차지하며, 1000만 비트 = 1250000바이트 = 약 1.2MB 다.

비트 연산이 곧 집합 연산이다 — 날짜별 비트맵을 BITOP AND 로 겹치면 "3일 연속 접속자", BITOP OR 로 겹치면 "3일 중 한 번이라도 접속한 사람"이 된다. BITCOUNT 는 켜진 비트를 세어 인원수를 돌려준다.
redis-cli
# 유저 아이디가 14인 유저의 방문 시
127.0.0.1:6379> setbit dau:240912 14 1
(integer) 0

# 특정 일자 DAU 확인
127.0.0.1:6379> bitcount dau:240912
(integer) 1

# 3일 동안 연속 접속한 유저의 정보를 dau:latest로 저장
127.0.0.1:6379> bitop and dau:latest dau:240910 dau:240911 dau:240912
(integer) 2
127.0.0.1:6379> bitcount dau:latest
(integer) 1

# 비트맵 원본 가져오기
127.0.0.1:6379> get dau:latest
"\x00\x02"

비트맵 내부 값을 직접 다루고 싶다면 GET 으로 통째로 꺼내 파이썬 등에서 파싱하면 된다. BITOP 의 반환값 2 는 인원수가 아니라 결과 문자열의 바이트 길이다.

HyperLogLog 를 이용한 애플리케이션 미터링

  • 클라우드 환경은 사용한 만큼 지불하는 정책을 가진다
  • 과금 비용을 계산하기 위해 초당 수천 건 이상의 작업이 발생할 수 있다
  • 이때 쓰는 미터링 솔루션은 높은 처리량과 낮은 대기시간을 가져야 한다
  • set 과 쓰임은 비슷하지만 용량이 최대 12KB 로 고정이라 효율적이다
redis-cli
# 49483 로그 저장
127.0.0.1:6379> pfadd 240912:user:123 49483
(integer) 1

# 32714 로그 저장
127.0.0.1:6379> pfadd 240912:user:123 32714
(integer) 1

# 49483 을 다시 저장 (이미 반영된 값이라 0)
127.0.0.1:6379> pfadd 240912:user:123 49483
(integer) 0

# 중복되지 않은 데이터의 개수 확인
127.0.0.1:6379> pfcount 240912:user:123
(integer) 2

정리

  • 좋아요/읽지 않은 수처럼 누가까지 필요한 카운팅은 set 과 hash 로. SCARD 와 HINCRBY 는 원자적이고 O(1) 이다.
  • DAU 는 비트맵. 유저 한 명이 1비트이며 1000만 명이 약 1.2MB. BITOP 으로 날짜 간 교집합/합집합을 만든다.
  • 개수만 알면 되는 대규모 유니크 카운트는 HyperLogLog. 12KB 고정, 오차 0.81%, 대신 개별 조회는 불가능하다.

Geospatial Index를 이용한 위치 기반 앱

좌표를 저장하는 DB 는 많다. 좌표로 연산까지 해 주는 인메모리 저장소가 드물 뿐이다.

핵심 RDB 는 좌표를 보관하고 거리 계산은 애플리케이션이 한다. 레디스는 보관과 계산을 같은 자리에서 처리해 왕복을 없앤다.

위치 데이터

  • 위치 데이터는 아주 다양한 곳에 쓰인다
    • 현재 위치를 파악하고 목적지까지 안내하기
    • 위치를 기반으로 맞춤 광고 제공하기
  • 위치 데이터의 요구사항
    • 현재 위치 파악
    • 이동에 따른 실시간 위치 업데이트
    • 위치를 기준으로 근처 장소 검색
  • 보통 경도와 위도 쌍으로 표현한다
  • 단순 읽기/쓰기라 간단해 보이지만 유저 수에 비례해 부하가 늘어난다

레디스의 위치 데이터

  • geo 자료구조를 통해 공간 정보 데이터를 처리할 수 있다
  • RDB 를 쓰는 경우 저장은 되지만 실제 연산 로직은 외부에서 처리해야 한다
  • 레디스는 저장은 물론 실시간 위치 연산까지 제공해 빠른 응답 속도를 보장한다
  • geo set 과 pub/sub 를 결합하면 근처 사용자에게 실시간 알림을 보내는 식의 서비스도 만들 수 있다

geo set

  • 위치 공간 관리에 특화된 자료구조로, 각 데이터는 경도/위도 쌍으로 저장된다
  • 이미 존재하는 멤버에 GEOADD 를 다시 하면 좌표가 업데이트된다

Redis 6.2 이후 최신 반영

주변 검색에 오래 쓰이던 GEORADIUS/GEORADIUSBYMEMBER 는 6.2 부터 deprecated 이고, 노트에서 쓴 GEOSEARCH 가 그 자리를 대신한다. GEOSEARCH 는 원형(BYRADIUS)뿐 아니라 사각형(BYBOX) 검색을 지원하고, 기준점을 좌표(FROMLONLAT) 또는 기존 멤버(FROMMEMBER)로 지정할 수 있다. 결과를 다른 키에 저장하려면 GEOSEARCHSTORE 를 쓴다.

!

geo 는 결국 sorted set 이다

내부적으로 좌표는 52비트 geohash 정수로 인코딩되어 sorted set 의 스코어에 들어간다. 그래서 멤버를 지울 때는 별도 커맨드가 아니라 ZREM 을 쓰고, 개수는 ZCARD 로 센다. 반대로 말하면 키 하나가 통째로 한 노드에 올라간다는 뜻이라, 전국 단위 데이터를 키 하나에 몰면 그 노드만 뜨거워진다.

정리

  • geo set 은 좌표 저장과 거리/반경 연산을 서버에서 함께 처리해 왕복을 줄인다.
  • 인자는 경도 → 위도 → 멤버 순. 같은 멤버에 다시 GEOADD 하면 좌표가 갱신된다.
  • 주변 검색은 GEOSEARCH 를 쓴다. GEORADIUS 계열은 6.2 부터 deprecated 다.
  • 내부가 sorted set 이므로 삭제는 ZREM, 개수는 ZCARD. 키 분산 설계도 sorted set 과 똑같이 고민해야 한다.
CH 5

레디스를 캐시로 사용하기

캐시는 원본의 복사본이다. 복사본에는 두 가지 숙제가 따라붙는다. 언제 지울 것인가(만료와 이빅션), 원본이 바뀌면 어떻게 할 것인가(일관성). 세션 스토어는 그 반대편에 있다 — 원본이 레디스에만 있는 경우다.

5-1

레디스와 캐시

캐시를 넣는 일은 쉽다. 어려운 것은 언제 지우고, 어긋나면 어떻게 할지 정하는 일이다.

핵심 캐시는 원본의 복사본이다. 그래서 캐시 설계는 전부 두 질문으로 환원된다 — 언제 비울 것인가(TTL/이빅션), 원본이 바뀌면 어떻게 할 것인가(쓰기 전략).

캐시

  • 데이터의 원본보다 빠르고 효율적으로 접근할 수 있는 임시 데이터 저장소
  • 원본을 가져오는 것보다 빠르므로 작업 대기시간을 줄일 수 있다

캐시로서의 레디스

  • 사용이 매우 간단하다
  • 데이터를 검색하고 반환하는 속도가 매우 빠르다
  • 평균 읽기/쓰기 지연은 1ms 수준이고, 초당 수백만 건의 작업이 가능하다
  • 센티널 또는 클러스터를 통해 가용성도 확보할 수 있다

캐싱 전략

레디스를 캐시로 쓸 때 어디에 배치하느냐가 성능에 큰 영향을 미친다.

읽기 전략 — look aside
  • 데이터를 읽어갈 때 주로 사용하며 가장 일반적인 방법이다 (cache-aside 라고도 부른다)
  • 읽을 때 캐시에 있는지 먼저 확인하고, 있으면 그 데이터를 반환한다
  • 캐시에 없으면 원본 DB 에서 읽어 오고, 그 값을 레디스에 저장한다
  • 장점은 레디스에 문제가 생겨도 원본 DB 가 살아 있으면 데이터를 가져올 수 있다는 것
    • 다만 모든 요청이 DB 로 향하면 그쪽에 부하가 몰릴 수 있다
flowchart TB
  A["애플리케이션 요청"] --> B{"캐시에 있는가"}
  B -->|"HIT"| C["캐시 값 반환"]
  B -->|"MISS"| D["원본 DB 조회"]
  D --> E["레디스에 저장 + TTL"]
  E --> F["값 반환"]
look aside 는 캐시를 애플리케이션이 관리한다 — 레디스는 조회 경로에 끼어들지 않고 옆에 서 있을 뿐이다. 그래서 레디스가 죽어도 서비스는 (느려질 뿐) 계속 돌아간다.
캐시 워밍
  • 최초 애플리케이션 로딩 시 레디스에는 데이터가 없어서 모든 요청이 DB 로 향한다
  • 이때 부트스트래핑 단계에서 DB 데이터를 레디스에 미리 올려 두는 것을 캐시 워밍이라 한다
쓰기 전략과 캐시의 일관성
  • 캐시는 DB 에 저장된 데이터를 복사해 온 값이다
  • 업데이트 시 원본 DB 만 바뀌면 캐시와 불일치가 발생한다
write through
  • DB 데이터를 업데이트할 때마다 레디스도 함께 업데이트하는 전략
  • 항상 최신 데이터를 유지하지만 매번 두 곳을 써야 한다
i

함께 알아두기 보강

실무에서 가장 많이 쓰이는 쓰기 전략은 사실 write invalidate 다 — DB 를 갱신한 뒤 캐시를 갱신하지 않고 삭제하고, 다음 읽기에서 자연스럽게 채워지게 둔다. 두 저장소에 같은 값을 쓰는 write through 는 갱신 순서가 엇갈리면 오래된 값이 캐시에 남을 수 있지만, 삭제는 순서가 엇갈려도 최악의 결과가 "캐시 미스 한 번"이라 안전하다.

만료시간

레디스의 TTL 은 데이터를 얼마나 오래 저장할지에 대한 시간이며 초 단위로 표현한다.

만료된 데이터의 삭제 방식
  • passive 방식
    • 특정 키에 접근했을 때 그 데이터가 만료됐다면 그때 삭제한다
    • 하지만 사용자가 다시는 접근하지 않을 수도 있어 이 방법만으로는 충분하지 않다
  • active 방식
    • TTL 이 설정된 키 중 20개를 랜덤으로 뽑아, 만료된 키는 메모리에서 삭제한다
    • 25% 이상의 키가 삭제됐다면 다시 20개의 키를 랜덤하게 뽑아 확인한다
    • 25% 미만이면 그 주기를 끝내고 다음 주기를 기다린다
    • 위 과정을 1초에 10번씩 수행한다
  • 공통적으로, 최악의 경우 전체 사용량의 25% 정도는 이미 만료됐지만 아직 지워지지 않은 키일 수 있다
!

그래서 "TTL 이 지났으니 메모리도 줄었을 것"이 아니다

만료 시각이 지나도 삭제는 나중에 일어난다. 메모리 그래프가 TTL 만료 시점에 곧바로 떨어지지 않는 것은 정상이며, 반대로 대량의 키가 동시에 만료되도록 설계하면 그 순간 active 사이클이 길어져 지연이 튄다. 만료 시각을 조금씩 흩뿌리는 편이 안전하다.

  • 최대 메모리 사용량과, 가득 찼을 때 어떤 기준으로 내부 데이터를 지울지 정할 수 있다

  • 가득 찬 경우 가장 오래 사용되지 않은 데이터부터 삭제하는 정책
  • volatile-lru
    • 만료시간이 설정된 키만 삭제 대상으로 삼는다
    • 만료되면 안 되는 데이터(TTL 미적용)가 섞여 있을 때 적합하다
    • 단점은 모든 키에 만료시간이 없다면 noeviction 과 똑같이 동작한다는 것
  • allkeys-lru
    • 캐시로 쓸 때 잘 모르겠다면 이 방식을 권장한다
    • 모든 키를 LRU 로 삭제하므로 적어도 메모리 부족 장애는 막을 수 있다
LFU eviction
  • 가득 찼을 때 가장 자주 사용되지 않은 데이터부터 삭제하는 정책
  • 키 접근 패턴에 따라 우선순위가 유동적으로 바뀐다
  • volatile-lfu : 만료시간이 설정된 키만 대상. 마찬가지로 대상이 없으면 저장 실패로 이어질 수 있다
  • allkeys-lfu : 모든 키에 LFU 를 적용
random eviction
  • 저장된 키를 랜덤으로 골라 삭제하는 방식
  • 어떤 키를 지울지 계산하지 않아도 되어 부하가 덜하다
  • 대신 곧 쓰일 데이터를 지울 수도 있으니 주의해야 한다
  • volatile-random : 만료시간이 설정된 키만 대상
  • allkeys-random : 모든 키를 대상
  • volatile-ttl : 만료시간이 가장 가까운 키부터 삭제
!

volatile-* 정책의 함정

volatile- 로 시작하는 정책은 TTL 이 걸린 키가 하나도 없으면 지울 대상이 없어 noeviction 과 같아진다. 즉 메모리가 차는 순간 쓰기가 전부 실패한다. TTL 을 붙이는 규칙이 코드 전반에 확실히 자리 잡았을 때만 선택해야 한다.

캐시 스탬피드 현상

  • 모든 키에 TTL 을 설정하는 것을 권장하지만, 일부 환경에서는 스탬피드가 발생할 수 있다
  • N개의 애플리케이션이 같은 데이터를 보는 상황을 가정하면
    • 특정 키가 만료되는 순간 N개의 요청이 동시에 DB 로 무거운 읽기를 날린다
    • 그리고 레디스에는 같은 값이 N번 갱신된다
  • 이 현상은 DB 에 부하를 주고 서비스 장애로도 이어질 수 있다
적절한 만료시간 설정
  • 가장 간단한 방법은 만료시간을 너무 짧게 잡지 않는 것
  • 앱에서 반복적으로 여러 번 써야 하는 데이터라면 만료시간을 길게 두는 편이 좋다
선 계산

실제로 키가 만료되기 전에 미리 갱신해 두는 방법이다.

PER 알고리즘

캐시가 만료되기 전에 언제 DB 에서 데이터를 다시 읽어야 하는지 계산하는 알고리즘이다.

PER (probabilistic early recomputation)
currentTime - (timeToCompute * beta * log(rand())) > expiry

각 항의 의미는 이렇다. timeToCompute 는 값을 다시 만드는 데 걸린 시간이라 비싼 값일수록 일찍 갱신되고, log(rand()) 는 항상 음수인 난수라 클라이언트마다 갱신 시점이 제각기 흩어진다. beta 는 그 정도를 조절하는 계수(기본 1)다. 결과적으로 만료 직전에 딱 한 클라이언트만 먼저 갱신에 나서게 된다.

정리

  • look aside 는 캐시를 앱이 관리하는 방식이라 레디스가 죽어도 서비스가 이어진다. 대신 캐시 워밍이 필요하다.
  • 만료는 접근 시(passive)와 초당 10회의 샘플링(active) 두 갈래로 일어난다. 그래서 만료 시각과 메모리 반환 시점은 다르다.
  • 캐시 용도라면 allkeys-lru 가 무난한 기본값이다. volatile-* 는 TTL 이 없으면 noeviction 과 같아진다.
  • 스탬피드는 TTL 을 넉넉히, 흩뿌려서, 필요하면 PER 로 미리 갱신해 막는다.
5-2

세션 스토어로서 레디스

캐시는 지워져도 되지만 세션은 지워지면 사용자가 로그아웃된다. 같은 레디스라도 운영 기준이 달라진다.

핵심 캐시는 DB 의 부분집합이라 잃어도 복구되지만, 세션은 레디스에만 있는 원본이다. 백업/복제 정책부터 다르게 가져가야 한다.

세션이란

  • 서비스를 사용하는 클라이언트의 상태 정보
    • 현재 로그인된 클라이언트, 어떤 활동을 하는지 등을 저장한다
    • 예: 장바구니 정보, 최근 본 아이템

세션 스토어가 왜 필요할까

  • 최근에는 부하 분산을 위해 여러 대의 인스턴스를 구동하는 아키텍처가 많이 쓰인다
  • 단일 서버가 세션을 들고 있으면 여러 서버에서 동일한 세션을 다룰 수 없다
  • DB 로 세션을 관리할 수도 있지만 처리 속도가 느리고 부하가 높다
  • 레디스의 hash 자료구조는 세션 데이터를 저장하기에 좋다

    • 유저가 로그아웃할 때 데이터를 DB 에 저장할지 등은 정책에 따라 다르다
    • 데이터가 손실될 수도 있으니 더 신중한 운영이 필요하다

캐시용으로 allkeys-lru 를 걸어 둔 인스턴스에 세션을 함께 넣으면, 메모리가 찼을 때 세션이 이빅션 대상이 되어 사용자가 이유 없이 로그아웃된다. 인스턴스를 분리하거나, 최소한 논리 DB 를 나누고 정책을 다르게 가져가야 한다.

정리

  • 여러 인스턴스가 상태를 공유해야 하므로 세션은 외부 저장소로 빼야 하고, hash 가 그 그릇으로 알맞다.
  • HSET 은 다중 필드를 받으므로 HMSET 은 쓸 필요가 없다(4.0 이후 deprecated).
  • 세션은 레디스가 원본이다. 이빅션 정책/백업/복제를 캐시와 다르게 설계하고, 가능하면 인스턴스를 분리한다.
CH 6

레디스를 메시지 브로커로 사용하기

메시징 큐는 한 번 읽으면 사라지는 통로, 이벤트 스트림은 읽어도 남는 저장소다. 레디스는 pub/sub, list, stream 세 장의 카드를 쥐고 있고 셋의 보증 수준이 전부 다르다.

6-1

레디스를 메시지 브로커로 사용하기

읽으면 사라지는 큐, 읽어도 남는 스트림. 이 차이 하나가 자료구조 선택을 결정한다.

핵심 메시징 큐는 1:1 로 일을 시키는 통로이고, 이벤트 스트림은 N:M 으로 사실을 알리는 저장소다. 레디스는 list, pub/sub, stream 으로 그 스펙트럼을 모두 커버한다.

메시지 브로커

  • 최근 아키텍처는 여러 모듈이 느슨하게 연결된 구조를 선호한다
  • 모듈 간 느슨하지만 탄탄한 상호작용을 위해 메시지 브로커가 필요하다
  • 모듈 간 상호작용은 동기보다 비동기 방식을 권장한다
  • 메시지 브로커는 메시징 큐와 이벤트 스트림 두 가지로 나눌 수 있다

메시징 큐

  • 데이터를 생성하는 쪽을 생산자, 수신하는 쪽을 소비자라 부른다
  • 생산자는 소비자의 큐로 메시지를 직접 푸시한다
  • 소비자가 메시지를 읽으면 해당 데이터는 삭제된다
  • 두 소비자에게 같은 메시지를 전달해야 하면 메시지를 두 개 푸시해야 한다
  • 이미 데이터가 있는 상태에서 새 소비자가 추가되면 기존 데이터를 읽을 수 없다
  • 보통 1:1 상황에서 한 서비스가 다른 서비스에게 동작을 지시할 때 유용하다

이벤트 스트림

  • 데이터를 생성하는 쪽을 발행자, 조회하는 쪽을 구독자라 부른다
  • 발행자는 특정 저장소에 데이터를 하나만 푸시하면 된다
  • 구독자들은 동일한 메시지를 각자 읽어 가므로 메시지를 복제해 저장하지 않아도 된다
  • 구독자가 읽은 메시지는 큐와 달리 바로 삭제되지 않고 일정 시간 뒤에 정리된다
  • 저장소에 데이터가 남으므로 히스토리 조회가 가능하다
  • 보통 다대다(N:M) 상황에서 유리하다

같은 메시지를 여럿에게개수만큼 푸시 필요한 번 푸시로 충분
나중에 합류한 소비자과거 메시지 못 읽음처음부터 읽기 가능

레디스를 메시지 브로커로 사용하기

  • 자체적으로 제공하는 pub/sub 패턴으로 구현할 수 있다
  • 한번 전송된 데이터는 바로 삭제되고, 잘 전달됐는지 등의 정보는 보장하지 않는다
  • fire-and-forget 처럼 일회성으로 간단한 알림 서비스에 유용하다
레디스에서 메시징 큐
  • list 자료구조가 메시징 큐로 쓰기에 알맞다
  • 데이터 푸시/팝이 가능하고, 매번 데이터가 있는지 확인하지 않아도 되는 블로킹 기능을 쓸 수 있다
레디스에서 이벤트 스트림
  • stream 자료구조가 이벤트 스트림에 알맞다
  • Kafka 에서 영감을 받은 구조로, 오직 데이터 추가만 지원한다
i

셋 중 무엇을 고를 것인가 보강

보증 수준으로 갈린다. pub/sub 은 구독 중인 클라이언트에만 전달되고 기록이 남지 않는다(at most once). list 는 메시지가 남지만 소비자가 꺼낸 뒤 죽으면 그 메시지는 사라진다. stream 만이 소비자 그룹, ACK, 보류 리스트를 갖춰 재처리를 지원한다(at least once). 잃어도 되는 알림은 pub/sub, 반드시 처리돼야 하는 일은 stream 이다.

정리

  • 큐는 소비되면 사라지고 1:1 작업 지시에, 스트림은 남고 N:M 전파에 쓴다.
  • 레디스는 pub/sub(휘발), list(블로킹 큐), stream(그룹+ACK) 세 가지를 제공하며 보증 수준이 각각 다르다.
  • 메시지가 유실돼도 되는지 여부가 선택의 첫 번째 기준이다.
6-2

레디스의 pub/sub

가볍다는 것은 곧 아무것도 보장하지 않는다는 뜻이다. 그 대가로 지연이 거의 없다.

핵심 레디스 pub/sub 은 메시지를 저장하지 않는다. 발행 순간 구독 중이 아니었던 클라이언트는 그 메시지를 영원히 볼 수 없다.
  • 레디스는 자체적으로 아주 간단한 pub/sub 패턴을 제공한다
    • 매우 가벼워서 최소한의 메시지 전달 기능만 제공한다
  • 발행자는 특정 채널에 메시지를 보내고, 구독자는 리스닝하다가 메시지를 읽는다
  • 한번 전달된 데이터는 저장되지 않으니 정합성이 중요한 데이터에는 권장하지 않는다
    • 앱에서 메시지 송수신과 관련한 추가 로직이 필요할 수 있다

메시지 보내기

  • PUBLISH 로 메시지를 보낸다
  • 반환값은 메시지를 받은 구독자의 수다
redis-cli
127.0.0.1:6379> publish hello world
(integer) 1

이 반환값이 0 이면 아무도 받지 못했다는 뜻이며, 레디스는 그 메시지를 버린다. 발행 결과를 확인하고 싶다면 이 숫자를 봐야 한다.

메시지 구독하기

  • SUBSCRIBE 로 채널을 구독한다
  • 구독 중인 커넥션에서는 pub/sub 과 관련되지 않은 다른 커맨드를 쓸 수 없다
redis-cli
127.0.0.1:6379> subscribe hello
1) "subscribe"
2) "hello"
3) (integer) 1
1) "message"
2) "hello"
3) "world"
Reading messages... (press Ctrl-C to quit or any key to type command)

그래서 애플리케이션에서는 구독 전용 커넥션을 따로 잡아야 한다. 일반 커맨드용 커넥션과 같은 것을 쓰면 구독하는 순간 그 커넥션으로는 GET 하나 날릴 수 없다.

PSUBSCRIBE 로는 글롭 패턴을 이용해 여러 채널을 동시에 구독할 수 있다.

redis-cli
127.0.0.1:6379> PSUBSCRIBE mail-*
1) "psubscribe"
2) "mail-*"
3) (integer) 1
1) "pmessage"
2) "mail-*"
3) "mail-all"
4) "all mail"

패턴 구독의 응답은 message 가 아니라 pmessage 이고, 매칭된 패턴과 실제 채널명이 함께 온다. 그래서 응답 요소가 하나 더 많다.

클러스터 구조에서 pub/sub

  • 클러스터는 대규모 서비스에서 데이터를 분산해 저장하고 처리하기 위해 도입됐다
  • 메시지를 발행하면 클러스터에 속한 모든 노드에서 메시지를 수신할 수 있다
  • 하지만 모든 노드에 같은 메시지가 복제되는 것은 클러스터의 목표와 어긋난다
  • 불필요한 리소스 사용과 네트워크 부하가 발생한다

sharded pub/sub

  • 클러스터 환경의 비효율을 해결하기 위해 Redis 7.0 에서 도입됐다
  • 각 채널이 슬롯에 매핑되는 구조이며, 해당 슬롯을 담당하는 노드에만 메시지가 전파된다
  • SPUBLISH 로 메시지를 보낸다
    • 모든 노드에 퍼지지 않고, 슬롯을 담당하는 노드와 그 복제본에만 전달된다
  • SSUBSCRIBE 로 메시지를 구독한다
flowchart LR
  subgraph SG1["일반 PUBLISH"]
    P1["PUBLISH ch"] --> N1["노드 A"]
    N1 -.->|"전파"| N2["노드 B"]
    N1 -.->|"전파"| N3["노드 C"]
  end
  subgraph SG2["SPUBLISH (7.0)"]
    P2["SPUBLISH ch"] --> M1["슬롯 담당 노드"]
    M1 --> R1["그 노드의 복제본"]
  end
sharded pub/sub 은 메시지의 이동 범위를 슬롯으로 좁힌다 — 일반 PUBLISH 는 노드 수에 비례해 클러스터 버스 트래픽이 늘지만, SPUBLISH 는 채널이 속한 슬롯의 노드와 복제본까지만 간다.

정리

  • pub/sub 은 저장하지 않는다. PUBLISH 의 반환값(수신 구독자 수)이 유일한 전달 단서다.
  • 구독 중인 커넥션은 다른 커맨드를 못 쓰므로 전용 커넥션이 필요하다.
  • 클러스터에서 일반 pub/sub 은 전 노드로 퍼진다. 7.0 의 SPUBLISH/SSUBSCRIBE 로 범위를 슬롯 단위로 좁힐 수 있다.
6-3

레디스의 list를 메시징 큐로 사용하기

폴링을 없애는 커맨드 BLPOP, 그리고 트위터가 타임라인을 담아 둔 자료구조.

핵심 큐를 계속 들여다보는 폴링은 앱과 레디스 양쪽의 자원을 태운다. 블로킹 커맨드는 데이터가 도착하는 순간 클라이언트를 깨워 그 낭비를 없앤다.

LIST 의 EX 기능

  • SNS 에는 유저별 타임라인이 존재한다
    • 타임라인에는 팔로우한 계정의 게시글, 관련 있는 게시글 등이 표시된다
    • 트위터의 경우 각 유저의 타임라인 데이터를 레디스의 list 로 관리했다

RPUSHX 커맨드

  • RPUSH 와 달리 RPUSHX 는 키가 이미 존재할 때만 데이터를 추가한다
  • 자주 접속하지 않는 유저의 데이터는 굳이 만들어 두지 않을 때 유용하다
redis-cli
# 기존에 타임라인이 있는 유저에게는 데이터가 추가됨
127.0.0.1:6379> rpush timeline:user:a timeline:1
(integer) 1
127.0.0.1:6379> rpushx timeline:user:a timeline:2
(integer) 2
127.0.0.1:6379> lrange timeline:user:a 0 -1
1) "timeline:1"
2) "timeline:2"

# 타임라인이 없는 유저에게는 아무 일도 일어나지 않음
127.0.0.1:6379> rpushx timeline:user:b timeline:1
(integer) 0
127.0.0.1:6379> lrange timeline:user:b 0 -1
(empty array)

수천만 명의 팔로워에게 게시글을 밀어 넣을 때, 최근 접속한 유저(=타임라인 키가 살아 있는 유저)에게만 쓰기가 일어나게 하는 장치다. 휴면 유저의 타임라인은 다음 접속 때 DB 에서 다시 만들면 된다.

list 의 블로킹 기능

이벤트 루프
  • 이벤트 루프는 새로운 이벤트가 있는지 확인하고, 없으면 대기했다가 다시 반복한다
  • 이런 작업을 폴링이라 하며, 진행 중인 동안 앱과 큐의 리소스가 불필요하게 소모된다
  • 폴링 간격 사이에 새 이벤트가 들어와도 그만큼 지연이 생겨 즉시 처리되지 않는다
list 블로킹
  • 레디스 list 의 블로킹 기능으로 이벤트 루프의 단점을 보완할 수 있다
  • BLPOP, BRPOP 커맨드를 쓴다
  • 값이 있으면 바로 반환하고, 없으면 지정한 시간 동안 기다렸다가 값을 반환한다
    • 시간이 만료되면 nil 을 반환한다
  • 일반 RPOP 과 달리 반환값이 두 개인데, 키 이름과 값을 함께 준다
    • 여러 개의 큐를 동시에 기다릴 수 있도록 하기 위해서다
redis-cli
127.0.0.1:6379> brpop q:a 5
(nil)
(5.10s)
127.0.0.1:6379> brpop q:a 5
1) "q:a"
2) "1"
(1.46s)

첫 호출은 5초를 다 기다린 뒤 nil, 두 번째는 1.46초 만에 다른 클라이언트가 넣은 값을 받아 즉시 깨어났다. BRPOP q:a q:b 0 처럼 여러 키를 나열하면 왼쪽 키부터 먼저 확인하며, 타임아웃 0 은 무한 대기다.

!

원문 보완 원문 교정

노트 13-2 에는 "트랜잭션 내부에서는 BRPOP, BLPOP 을 쓸 수 없다"고 되어 있는데, 정확히는 쓸 수는 있으나 블로킹하지 않는다. MULTI/EXEC 안에서 리스트가 비어 있으면 기다리지 않고 즉시 nil 을 반환한다 — 타임아웃이 지난 것과 같은 동작이다. 블록을 원자적으로 실행하는 동안 서버 전체가 멈춰야 하므로 기다릴 방법이 없기 때문이다. (근거: Redis Docs — BLPOP)

list 를 사용한 원형 큐
  • 특정 아이템을 계속 반복해서 순회해야 하거나, 여러 클라이언트가 병렬로 같은 아이템 집합에 접근해야 할 때 원형 큐를 쓸 수 있다
  • RPOPLPUSH 로 원형 큐를 만든다
redis-cli
127.0.0.1:6379> lpush clist a
(integer) 1
127.0.0.1:6379> lpush clist b
(integer) 2
127.0.0.1:6379> lpush clist c
(integer) 3
127.0.0.1:6379> lrange clist 0 -1
1) "c"
2) "b"
3) "a"
127.0.0.1:6379> rpoplpush clist clist
"a"
127.0.0.1:6379> lrange clist 0 -1
1) "a"
2) "c"
3) "b"

출발지와 목적지를 같은 키로 주면 맨 뒤 원소가 맨 앞으로 이동한다. 여러 워커가 동시에 호출해도 각자 다른 원소를 받으므로, 목록 전체를 클라이언트로 끌어오지 않고 나눠 처리할 수 있다.

Redis 6.2 이후 최신 반영

RPOPLPUSH 와 BRPOPLPUSH 는 6.2.0 부터 deprecated 다. 대체 커맨드는 LMOVE / BLMOVE 로, 양쪽 끝을 인자로 직접 지정한다 — LMOVE clist clist RIGHT LEFT 가 위 예제와 같은 동작이다. 방향을 바꿔 LEFT RIGHT 로도 돌릴 수 있어 더 유연하다. (근거: Redis Docs — RPOPLPUSH)

i

신뢰할 수 있는 큐 패턴 보강

BLPOP 으로 꺼낸 직후 워커가 죽으면 그 메시지는 사라진다. 그래서 공식 문서는 BLMOVE 로 작업 큐에서 처리 중 큐로 옮기며 꺼내고, 처리가 끝나면 LREM 으로 처리 중 큐에서 지우는 패턴을 권한다. 처리 중 큐에 오래 남은 항목을 감시하는 별도 프로세스를 두면 유실 없는 큐가 된다.

정리

  • RPUSHX 는 키가 있을 때만 쓴다. 휴면 유저의 타임라인을 만들지 않는 데 쓰인다.
  • BLPOP/BRPOP 은 폴링을 없앤다. 반환값이 (키, 값) 두 개인 이유는 여러 큐를 동시에 기다릴 수 있기 때문이다.
  • 트랜잭션 안에서는 블로킹 커맨드가 기다리지 않고 즉시 nil 을 돌려준다.
  • 원형 큐/신뢰할 수 있는 큐는 이제 LMOVE/BLMOVE 로 만든다. RPOPLPUSH 는 6.2 부터 deprecated.
6-4

스트림

추가만 되는 로그, 소비자 그룹, ACK 와 보류 리스트. 레디스가 카프카의 문법을 빌려 온 자리.

핵심 stream 은 메시지를 지우지 않고 누가 어디까지 읽었는지를 대신 기록한다. 그래서 장애 후 재처리가 가능하다.

레디스의 스트림

  • Redis 5.0 에서 추가된 자료구조
  • 대용량/대규모 메시징 데이터 처리가 가능하도록 설계됐다
  • 계속해서 데이터를 추가만 할 수 있는 구조다
  • 사용처
    • 대량의 데이터를 효율적으로 처리하는 플랫폼
    • 생성된 데이터를 소비자들이 처리할 수 있게 지원하는 저장소 및 큐잉 시스템
  • Kafka 와 유사하며 일부 기능은 더 낫게 설계됐다

스트림

  • 연속적인 데이터의 흐름, 일정한 데이터 조각의 연속을 의미한다
  • 예를 들면 대용량 데이터를 한 번에 다 읽는 대신 여러 조각으로 쪼개어 로딩하는 것

데이터의 저장

레디스 스트림에서 각 메시지는 시간과 관련된 고유한 ID 를 가진다.

메시지 ID 형식
<millisecondsTime>-<sequenceNumber>

앞부분이 밀리초 단위 시각이라 ID 만으로 시간순이 보장되고, 같은 밀리초에 여러 건이 들어오면 뒤의 시퀀스 번호가 올라간다.

XADD
  • 새 이름의 스트림에 데이터를 저장하면 자료구조가 바로 생성된다
  • 기존 스트림에 추가하면 데이터만 붙는다
  • hash 와 유사하게 필드-값 쌍으로 저장되므로 메시지마다 유동적인 구조를 가질 수 있다
  • 기본 ID 대신 직접 지정하고 싶다면 * 자리에 ID 를 넣는다
    • 최솟값은 0-1 이며 이후 ID 는 더 큰 값이어야 한다
redis-cli
127.0.0.1:6379> xadd email * subject "first" body "hello?"
"1726208369577-0"
127.0.0.1:6379> xadd email * subject "second" body "world"
"1726208392652-0"
127.0.0.1:6379> xadd noob 0-1 "hello" "world"
"0-1"
127.0.0.1:6379> xadd noob 0-2 "hello" "world"
"0-2"
i

스트림도 잘라 줘야 한다 보강

추가만 되는 구조라 그냥 두면 메모리를 끝없이 먹는다. XADD stream MAXLEN ~ 10000 * ... 처럼 길이 상한을 함께 지정하는 것이 정석이다. 물결표(~)를 붙이면 "대략 그 정도"로 잘라 내며, 내부 노드 경계에서만 정리하므로 훨씬 빠르다. 시간 기준으로 자르려면 MINID 를 쓴다.

데이터 조회

실시간 리스닝
  • XREAD 로 스트림에 저장되는 데이터를 실시간으로 읽어 올 수 있다
  • xread block 0 streams email 0
    • block 0 : 더 가져올 데이터가 없어도 연결을 끊지 말고 계속 리스닝
    • block 1000 : 최대 1초(1000ms) 리스닝
    • streams email 0 : ID 가 0 보다 큰 값을 읽어 오라는 뜻, 즉 처음부터 전부
    • streams email $ : 커맨드를 실행한 이후 추가된 값만 읽어 오라는 뜻
redis-cli
127.0.0.1:6379> xread block 0 streams email 0
1) 1) "email"
   2) 1) 1) "1726208369577-0"
         2) 1) "subject"
            2) "first"
            3) "body"
            4) "hello?"
      2) 1) "1726208392652-0"

소비자, 소비자 그룹

  • 동일한 데이터를 여러 소비자에게 전달하는 것을 fan-out 이라 한다
  • XREAD 를 쓰면 여러 소비자가 하나의 스트림을 각자 구독할 수 있다
  • 레디스는 데이터가 저장되는 순간 ID 를 부여하므로 순서가 보장된다
  • 소비자 그룹은 그룹 내 다른 소비자가 읽지 않은 메시지만 읽어 간다
  • 그룹 내부에서 각 소비자는 고유한 이름을 가져야 한다
flowchart LR
  S["stream: email"] --> G1["그룹 EmailService"]
  S --> G2["그룹 Analytics"]
  G1 --> C1["소비자 worker-1"]
  G1 --> C2["소비자 worker-2"]
  G2 --> C3["소비자 log-1"]
그룹 사이에는 fan-out, 그룹 안에서는 분배 — 같은 메시지를 EmailService 와 Analytics 가 각각 한 번씩 받고, 그룹 안의 worker-1 과 worker-2 는 서로 다른 메시지를 나눠 가진다. 그룹마다 last_delivered_id 를 따로 들고 있기 때문이다.
redis-cli
# 새 소비자 그룹 생성. 생성 이후에 발생한 메시지만 읽도록 지정
127.0.0.1:6379> xgroup create email EmailServiceGroup $
OK
127.0.0.1:6379> xreadgroup group EmailServiceGroup emailService1 count 1 streams email >
(nil)
커맨드의 의미
  • COUNT 1 : email 스트림에서 메시지 1개만 읽어 오기, 없으면 nil
  • streams email > : 다른 소비자에게 전달되지 않은 메시지를 읽어 오기

여기서 > 대신 0 을 주면 의미가 완전히 달라진다 — 이 소비자가 받았지만 아직 ACK 하지 않은 메시지를 다시 읽는다. 워커를 재시작한 뒤 처리하다 만 메시지를 이어받을 때 쓰는 형태다.

부하 분산

  • 스트림과 소비자 그룹은 별개로 동작한다
  • 여러 소비자 그룹이 존재할 수 있고, 다른 그룹이 이미 수신한 메시지도 각자 읽을 수 있다
  • 따라서 특정 메시지가 필요한 여러 서비스로 분산할 수 있다

ACK 와 보류 리스트

  • 장애로 시스템이 종료되면 어디까지 처리했는지, 처리했는지 여부를 알아야 한다
  • 레디스는 읽어 간 메시지 목록을 관리하며, 이 값으로 같은 메시지를 중복 전달하지 않는다
    • 마지막으로 읽어 간 ID 는 last_delivered_id 로 저장/갱신된다
  • 소비자마다 보류 리스트(PEL) 를 가지며, 처리가 완료되면 ACK 로 해당 항목이 지워진다

2) (nil)
3) (nil)

원문 교정 원문 교정

노트에는 네 번째 항목이 1번과 같은 "보류 중인 개수"로 적혀 있으나, 실제로는 소비자별 보류 개수 목록이다. 어느 워커에 일이 밀려 있는지 확인하는 자리이므로 1번과 역할이 다르다.

redis-cli

127.0.0.1:6379> xack email EmailServiceGroup 1726212055826-0
(integer) 0

반환값 0 은 보류 리스트에 그 ID 가 없었다는 뜻이다. 이미 ACK 했거나 애초에 이 그룹이 읽어 간 적 없는 메시지를 지우려 한 경우다.

보증 전략

at most once
  • 메시지를 최대 한 번 보내는 것을 의미한다
  • 소비자는 실제로 처리하기 전에 ACK 를 보낸다
    • 속도는 빠르지만 장애 복구 시 처리하지 못한 데이터가 유실될 수 있다
  • 일부 메시지가 손실돼도 빠른 응답이 필요한 경우에 쓴다
at least once
  • 소비자는 받은 메시지를 실제로 처리한 뒤에 ACK 를 보낸다
  • 처리 도중 장애가 나 재처리하면 중복 처리가 발생할 수 있다
  • 멱등한 서비스면 괜찮지만, 그렇지 않으면 문제가 된다
exactly once
  • 모든 메시지가 정확히 한 번씩 처리되는 것을 보장한다는 의미
  • 레디스 내부에서 set 등을 활용해 이미 처리된 메시지인지 관리하는 추가 작업이 필요하다
!

exactly once 는 브로커가 주는 기능이 아니다

레디스 스트림이 자체적으로 보장하는 것은 at least once 까지다. exactly once 처럼 보이게 만드는 것은 소비자 쪽의 멱등 처리 — 처리한 메시지 ID 를 set 에 남기고 이미 있으면 건너뛰는 식 — 이며, 이때 "처리"와 "ID 기록"이 같은 트랜잭션 안에 있어야 한다.

메시지 재할당

  • 특정 소비자가 장애 이후 복구되지 않으면 다른 소비자가 그 일을 대신 처리해야 한다
  • XCLAIM 으로 메시지 소유권을 다른 소비자에게 넘길 수 있다
  • 사용 시 최소 대기시간 설정이 필요하다
    • 그 시간을 넘긴 메시지만 소유권을 바꿀 수 있게 해서, 같은 메시지가 여러 소비자에게 중복 할당되는 것을 막는다

메시지 자동 재할당

  • XCLAIM 은 XPENDING 으로 먼저 보류 메시지를 확인해야 해서 번거롭다
  • XAUTOCLAIM(6.2 이상) 으로 보류 메시지를 훑으며 자동으로 재할당할 수 있다

메시지 수동 재할당

  • 스트림 내부의 메시지는 각각 전달 카운터를 가지고 있다
  • XREADGROUP, XCLAIM 으로 소비자에게 할당/재할당될 때마다 1씩 증가한다
  • 메시지에 문제가 있어 처리되지 못하면 이 카운터가 끝없이 올라간다
  • 카운터가 특정 값에 도달하면 그 메시지를 다른 특수한 스트림으로 보내 나중에 수동으로 처리하게 하는 편이 현명하다
  • 이를 dead letter 라고 부른다

CH 7

레디스 데이터 백업 방법

메모리에 사는 데이터는 프로세스가 죽으면 같이 죽는다. 레디스가 내미는 답은 두 개다 — 특정 순간을 통째로 찍는 RDB, 쓰기 명령을 차례로 적어 두는 AOF. 둘은 배타적이지 않고, 보통 같이 쓴다.

7-1

레디스에서 데이터를 영구 저장하기

스냅숏을 찍을 것인가, 일지를 쓸 것인가. 백업 방식의 선택은 곧 얼마까지 잃어도 되는가에 대한 대답이다.

핵심 RDB 는 어느 시점의 사진이고 AOF 는 모든 변경의 일지다. 사진은 가볍고 빠르지만 찍은 순간 이후를 잃고, 일지는 무겁지만 마지막 순간까지 복원한다.
  • 레디스는 모든 데이터를 메모리에서 관리한다
  • 재부팅하면 모든 데이터가 사라진다
  • 캐시가 아닌 영구 저장소로 쓰려면 RDB, AOF 두 가지 백업 방법을 사용할 수 있다
    • 데이터 복구는 재부팅 시점에만 가능하며, 실행 중에는 불가능하다

AOF (Append Only File)

  • 처리한 모든 쓰기 작업을 차례대로 기록한다
  • 복원할 때는 파일을 다시 읽어 가며 데이터 세트를 재구성한다
  • 파일은 레디스 자체 프로토콜인 RESP 형태로 저장된다
  • 원하는 시점으로 복구가 가능하다

RDB (Redis Database)

  • 일정 시점에 메모리에 있는 전체 데이터를 저장한다. 스냅숏 방식이라고도 한다
  • 원하는 시점으로의 복구는 불가능하다. 저장된 시점으로만 돌아갈 수 있다

둘 중 하나가 아니다 보강

RDB 와 AOF 는 동시에 켤 수 있고, 대개 그렇게 쓴다. 둘 다 켜져 있으면 재시작 시 더 완전한 AOF 를 우선 읽어 복원한다. RDB 는 그 자체로 백업 파일을 다른 서버에 옮기기 좋고 복제의 전체 동기화에도 쓰이므로, "AOF 를 켰으니 RDB 는 끈다"는 선택은 대개 손해다.

정리

  • 메모리 저장소이므로 재시작하면 데이터는 사라진다. 복구는 재부팅 시점에만 일어난다.
  • RDB 는 작고 빠르지만 마지막 스냅숏 이후를 잃는다. AOF 는 크고 느리지만 거의 잃지 않는다.
  • 실무에서는 둘 다 켜고, 재시작 시에는 AOF 가 우선한다.
7-2

RDB 방식의 데이터 백업

가장 간단한 백업. 대신 "언제 찍었느냐"가 곧 "언제까지 살아남았느냐"가 된다.

핵심 SAVE 는 서버를 멈추고 찍고, BGSAVE 는 자식 프로세스를 fork 해서 찍는다. 운영에서 쓰는 것은 후자뿐이다.
  • 레디스에서 데이터를 백업하는 가장 간단한 방법
  • 장애 시 손실 가능성을 최소화해야 하는 서비스에는 권장하지 않는다

특정 조건에 자동으로 RDB 생성

redis.conf 파일에 정의할 수 있다.

redis.conf
save <기간(초)> <변경된 키 개수>
dbfilename <파일명>
dir <RDB 파일이 저장될 경로>
save
  • save 900 1 : 900초(15분) 동안 1개 이상의 키가 변경된 경우 저장
  • save "" : RDB 생성 비활성화
  • CONFIG SET save "" 후 CONFIG REWRITE : 실행 중인 상태에서 RDB 생성 비활성화

save 는 여러 줄을 겹쳐 쓸 수 있고, 조건 중 하나라도 만족하면 저장이 일어난다. 변경이 잦을수록 자주, 뜸할수록 드물게 찍히도록 계단식으로 설정하는 것이 기본 구성이다.

수동으로 RDB 생성

  • SAVE, BGSAVE 로 수동 생성할 수 있다
  • LASTSAVE 로 최근 RDB 생성 시각을 확인할 수 있다
SAVE
  • 동기 방식으로 파일을 생성한다
    • 파일이 생성되는 동안 다른 커맨드를 실행할 수 없다
  • 일반적인 운영 환경에서는 사용하지 않는 것을 권장한다
redis-cli 운영 금지
127.0.0.1:6379> save
OK
BGSAVE
  • fork 로 자식 프로세스를 만들고, 그 프로세스가 RDB 를 생성한다
  • 이미 백그라운드 저장이 진행 중이면 에러가 나므로 BGSAVE SCHEDULE 로 예약하는 편이 안전하다
redis-cli 권장
127.0.0.1:6379> bgsave
Background saving started

복제를 사용하는 경우 자동으로 RDB 생성

  • REPLICAOF 로 복제를 요청하면 마스터가 RDB 를 만들어 복제본에 전달한다
  • 네트워크 장애 등으로 재동기화가 필요할 때도 복제본으로 RDB 를 전달한다
  • 처음 연결이든 이미 연결된 상태든 언제든 RDB 가 생성될 수 있다
!

RDB 를 껐다고 fork 가 사라지지 않는다

save "" 로 자동 저장을 꺼도, 복제본이 붙는 순간 전체 동기화를 위해 fork 가 일어난다. 뒤의 7-4 에서 다루는 copy-on-write 메모리 급증은 백업을 끈 인스턴스에서도 발생할 수 있다는 뜻이다. (7.0 부터는 기본값이 디스크리스 복제라 RDB 파일 자체는 만들지 않지만 fork 는 그대로다.)

정리

  • save <초> <변경 키 수> 조건을 여러 줄 겹쳐 두면 변경 빈도에 따라 저장 주기가 달라진다.
  • 운영에서는 SAVE 를 쓰지 않는다. BGSAVE 를, 중복이 걱정되면 BGSAVE SCHEDULE 을 쓴다.
  • 복제 연결 때도 RDB 생성(과 fork)이 일어난다. 백업 설정과 무관하게 메모리 여유가 필요하다.
7-3

AOF 방식의 데이터 백업

모든 쓰기를 적어 두는 대신, 그 파일이 무한히 커지지 않게 하는 일이 운영의 절반이다.

핵심 AOF 의 안정성은 appendfsync 하나로 결정된다. 기본값 everysec 은 최대 1초치 손실과 거의 no 수준의 성능을 맞바꾼 지점이다.
  • 파일명은 기본적으로 appendonly.aof 로 저장된다
  • 메모리상 데이터가 변화하는 작업만 기록된다
    • FLUSHALL 로 모든 데이터를 날려도 (그 커맨드 앞까지는) 복구할 수 있다
  • 모든 데이터가 실제 입력한 커맨드 그대로 저장되지는 않는다
    • BRPOP 같은 경우 AOF 에는 RPOP 으로 기록된다

블로킹 커맨드가 비블로킹 형태로 바뀌어 기록되는 이유는, 복원할 때는 기다릴 대상이 없기 때문이다. 같은 이유로 SPOP, EXPIRE 처럼 실행할 때마다 결과가 달라지는 커맨드도 결정적인 형태(SREM, PEXPIREAT)로 변환되어 기록된다.

redis.conf
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"

AOF 파일 재구성하기

  • AOF 를 안정적으로 쓰려면 점점 커지는 파일을 주기적으로 압축(재구성)해야 한다
    • 조건부 또는 수동으로 재구성할 수 있다
  • 디스크에 있는 기존 AOF 를 재사용하는 것이 아니라, 메모리에 있는 현재 데이터로 새 파일을 만든다

그래서 INCR counter 를 백만 번 실행했더라도 재구성 후에는 SET counter 1000000 한 줄로 줄어든다.

버전 7 이전의 재구성 과정
  1. fork 로 자식 프로세스 생성

    메모리의 데이터를 새 임시 파일로 쓰기 시작한다.

  2. 그동안의 변경은 두 곳에 기록

    기존 AOF 파일과 인메모리 버퍼에 동시에 저장된다.

  3. 버퍼 내용을 임시 파일 끝에 이어 붙임

    재구성이 끝나면 버퍼에 쌓인 변경을 임시 파일 마지막에 추가한다.

  4. 임시 파일로 기존 AOF 를 덮어씀

    이 과정에서 큰 파일 쓰기가 한 번 더 일어난다.

버전 7 이후의 재구성 과정
  1. fork 로 자식 프로세스 생성

    메모리의 데이터를 새 임시 파일(base)로 쓴다.

  2. 그동안의 변경은 신규 AOF 에 기록

    이전처럼 두 곳에 중복 기록하지 않는다.

  3. 임시 manifest 파일 생성 후 갱신

    어떤 base 와 incr 파일이 현재 세트인지 manifest 가 가리킨다.

  4. manifest 를 덮어쓰고 이전 파일 삭제

    순차적인 I/O 만 발생해 디스크 접근이 매우 효율적이다.

Redis 7.0 의 multi-part AOF 최신 반영

7.0 부터 AOF 는 파일 하나가 아니라 appenddirname(기본 appendonlydir) 디렉터리 안의 base 파일 + incr 파일 + manifest 파일 세트로 관리된다. 그래서 백업 스크립트가 appendonly.aof 파일 하나만 복사하도록 짜여 있다면 7.0 업그레이드 후 반드시 고쳐야 한다.

자동 AOF 재구성

  • 현재 파일 크기와 마지막으로 재구성했을 때의 크기를 비교해 처리한다
  • 파일이 작을 때 재구성하는 것은 비효율적이니, 일정 크기 이상일 때만 하도록 지정하는 것을 권장한다
redis.conf
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

위 기본값은 "직전 재구성 시점보다 100% 커졌고(즉 두 배), 그러면서 64MB 이상일 때" 재구성한다는 뜻이다. 두 조건을 모두 만족해야 한다.

수동 AOF 재구성

  • BGREWRITEAOF 로 원하는 시점에 수동으로 재구성할 수 있다
  • 자동 재구성과 동일하게 동작한다

AOF 파일의 안정성

OS 가 파일을 저장하는 방법
  1. 레디스가 커널에 WRITE 를 호출

    애플리케이션 입장에서는 여기서 "썼다"고 판단한다.

  2. 커널이 OS 버퍼(page cache)에 담는다

    아직 디스크에는 없다. 이 상태에서 전원이 나가면 사라진다.

  3. OS 가 여유가 있거나 지연 한계에 도달하면 디스크에 쓴다

    리눅스의 기본 지연 한계는 약 30초다. FSYNC 는 이 버퍼 내용을 디스크에 강제로 내리는 시스템 콜이다.

원문 교정 원문 교정

노트에 APPENDASYNC 로 적힌 설정의 실제 이름은 appendfsync 다. 값은 no / always / everysec 세 가지이며 기본값은 everysec 이다. (근거: redis.conf)

appendfsync호출하는 시스템 콜최대 손실성능
noWRITE 만OS 에 맡김 (최대 30초)가장 빠름
alwaysWRITE + FSYNC (매 쓰기)사실상 없음가장 느림
everysec (기본/권장)WRITE + 1초마다 FSYNC최대 1초no 와 거의 동일
  • appendfsync no
    • AOF 를 쓸 때 WRITE 시스템 콜만 호출한다
    • 커널 영역까지 잘 넘어갔는지만 확인하므로 성능이 가장 좋다
  • appendfsync always
    • 쓸 때마다 WRITE + FSYNC 를 호출한다
    • 매번 디스크에 정확히 저장되기를 기다리므로 성능이 가장 낮다
  • appendfsync everysec
    • WRITE 를 호출하고, FSYNC 는 1초에 한 번 호출한다
    • 성능은 no 와 거의 비슷하면서 손실 범위는 1초로 묶인다

정리

  • AOF 는 쓰기 커맨드를 RESP 로 기록하되, 비결정적인 커맨드는 결정적인 형태로 바꿔 저장한다.
  • 재구성은 디스크의 옛 파일이 아니라 메모리의 현재 상태로 새로 쓴다. 기본 조건은 "직전의 2배 그리고 64MB 이상".
  • 7.0 부터 AOF 는 base + incr + manifest 의 디렉터리 구조다. 백업 스크립트를 함께 손봐야 한다.
  • 설정 이름은 appendfsync. 기본값 everysec 이 손실 1초와 성능을 맞바꾼 실용적인 지점이다.
7-4

백업 사용 시 주의할 점

백업이 장애의 원인이 되는 순간 — fork 와 copy-on-write 가 메모리를 두 배로 부풀릴 때.

핵심 fork 직후 메모리는 공유되지만, 부모가 데이터를 고칠 때마다 그 페이지가 복사된다. 쓰기가 많을수록 백업 중 메모리가 부푼다.
  • RDB, AOF 를 사용하는 경우 인스턴스의 maxmemory 는 실제 서버 메모리보다 여유를 두고 설정하는 것이 좋다

BGSAVE 커맨드

  • fork 로 프로세스를 하나 더 만든다
  • 부모 프로세스는 그동안에도 다른 요청을 계속 받아야 한다
  • 레디스는 copy-on-write 방식이라 변경이 일어난 부분만 메모리에 하나 더 만든다
    • 최악의 경우 실제로 메모리를 2배 이상 쓸 수도 있다
  • OS 메모리가 가득 차 out of memory 가 발생하면 그대로 장애로 이어진다
백업 중 늘어나는 메모리는 데이터 크기가 아니라 "그동안 바뀐 양"에 비례한다 — 읽기만 많은 인스턴스는 거의 늘지 않지만, 쓰기가 몰리는 시간대에 백업이 겹치면 최악의 경우 두 배까지 뛴다. 백업 시각을 트래픽이 한가한 때로 옮겨야 하는 이유다.
i

현장에서 하는 조치 보강

가장 흔한 대응은 백업을 복제본에서 수행하는 것이다. 마스터에서는 자동 저장을 끄고, 트래픽을 받지 않는 복제본에 BGSAVE 를 걸면 마스터의 fork 부담이 사라진다. 그리고 vm.overcommit_memory = 1 을 설정해 두라는 레디스의 시작 경고 로그는 바로 이 fork 실패를 막기 위한 것이다.

정리

  • BGSAVE/BGREWRITEAOF/복제 전체 동기화는 모두 fork 를 부른다.
  • copy-on-write 로 인해 늘어나는 메모리는 백업 도중의 쓰기 양에 비례한다. 최악의 경우 2배 이상.
  • maxmemory 는 물리 메모리보다 충분히 낮게 잡고, 가능하면 백업은 복제본에서 돌린다.
CH 8

복제

복제는 고가용성의 재료지 고가용성 그 자체가 아니다. 데이터를 복제본에 흘려보내는 것까지가 복제의 일이고, 마스터가 죽었을 때 누가 대신할지 정하는 일은 다음 챕터(센티널/클러스터)의 몫이다.

8-1

복제

한 벌 더 만들어 두는 일. 그것만으로 장애가 해결되지는 않지만, 해결의 전제 조건은 된다.

핵심 복제는 마스터 하나에 복제본 여럿인 단방향 구조다. 쓰기는 마스터로 모이고 읽기는 흩어질 수 있으며, 승격은 사람이나 센티널/클러스터가 결정한다.
  • 마스터 노드의 데이터를 복제본 노드로 실시간 복사한다
  • 마스터에 장애가 나도 복제본에서 데이터를 확인할 수 있다
  • 복제본은 트래픽 분산에도 쓸 수 있다. 마스터와 복제본 양쪽이 모두 트래픽을 받을 수 있다
  • 데이터를 공유하므로 복제본 노드에서 백업을 수행할 수도 있다
  • 보통 마스터가 쓰기를, 복제본이 읽기를 담당한다

복제 구조 구성하기

  • REPLICAOF 커맨드로 간단히 복제 구조를 만들 수 있다
  • 마스터는 한 개만 존재하며, 복제본 아래에 다시 복제본을 둘 수도 있다(연쇄 복제)
redis-cli
REPLICAOF <master-ip> <master-port>

복제를 끊고 독립 마스터로 되돌릴 때는 REPLICAOF NO ONE 을 쓴다. 이때 이미 받은 데이터는 그대로 유지된다.

패스워드 설정

  • ACL 이 아닌 기본 비밀번호를 쓰는 경우 masterauth 옵션에 비밀번호를 넣어야 한다
  • 마스터는 requirepass 로 비밀번호를 설정하고, 복제본은 masterauth 로 설정한다
  • CONFIG SET 으로 실행 중에도 비밀번호를 설정할 수 있다
!

모든 노드에 두 옵션을 다 넣어 둔다

복제본은 언제든 마스터로 승격될 수 있고, 그러면 지금의 마스터가 복제본이 된다. 그러므로 requirepass 와 masterauth 를 모든 노드에 같은 값으로 설정해 두어야 페일오버 이후에도 복제가 이어진다. (9-3 패스워드 인증 참고)

정리

  • REPLICAOF host port 한 줄로 복제가 시작되고, REPLICAOF NO ONE 으로 끊는다.
  • 복제본은 읽기 분산과 백업 전용 노드로 활용할 수 있다.
  • 인증은 모든 노드에 requirepass + masterauth 를 동일하게 설정한다. 역할은 언제든 뒤바뀐다.
8-2

복제 메커니즘

전체 동기화는 비싸다. 그래서 레디스는 끊긴 자리부터 이어 붙이는 부분 재동기화에 공을 들인다.

핵심 복제본이 붙을 때는 RDB 를 통째로 받는다(전체 동기화). 잠깐 끊겼다 붙을 때는 백로그 버퍼에서 빠진 offset 만 받아 온다(부분 재동기화).

복제 메커니즘 — 디스크를 사용하는 방식

  1. 복제본이 REPLICAOF 로 복제를 시도한다
  2. 마스터가 fork 로 자식 프로세스를 만들고 RDB 스냅숏을 생성한다
  3. 그동안의 변경은 복제 버퍼에 쌓인다

    RESP 형태로 마스터 노드의 복제 버퍼에 저장된다.

  4. RDB 생성이 끝나면 복제본으로 전송되고, 복제본이 그것을 로딩한다
  5. 그동안 버퍼에 쌓인 변경을 복제본에 전달해 수행시킨다
최대 복제 작업의 수
  • 복제(전체 동기화)를 위한 RDB 생성은 한 번에 하나만 진행되고, 나머지 요청은 대기한다
  • repl-diskless-sync-delay 옵션
    • 디스크리스 복제를 시작하기 전에 설정한 초만큼 기다렸다가 전송을 시작한다는 뜻이다 (기본값 5초)
    • 네트워크 문제로 재동기화를 요청할 때는 여러 복제본이 한꺼번에 몰려드는 것이 일반적이라, 잠시 기다렸다가 하나의 스트림으로 함께 보내면 마스터의 부담이 줄어든다
!

원문 교정 원문 교정

repl-diskless-sync-delay 는 "활성화/비활성화"하는 스위치가 아니라 대기 시간(초) 값이며 기본값은 5 다. 또한 이 옵션은 디스크를 쓰는 방식이 아니라 디스크리스 복제에만 적용된다. 0 으로 두면 기다리지 않고 즉시 전송을 시작한다. (근거: redis.conf)

복제 메커니즘 — 디스크를 사용하지 않는 방식 (디스크리스)

  1. 복제본이 REPLICAOF 로 복제를 시도한다
  2. 마스터가 복제본과 소켓으로 직접 연결한다

    RDB 를 파일로 남기지 않고, 만들어지는 대로 복제본의 소켓으로 흘려보낸다.

  3. 그동안의 변경은 마스터의 복제 버퍼에 쌓인다
  4. 복제본은 소켓에서 읽은 RDB 를 디스크에 저장하거나 곧바로 메모리에 로딩한다
  5. 이후는 디스크 방식과 동일하다

디스크 I/O 보다 네트워크가 빠른 환경에서 유리한 방식이다.

Redis 7.0 이후 기본값이 바뀌었다 최신 반영

repl-diskless-sync 의 기본값이 7.0 부터 yes 다. 즉 별도 설정을 하지 않았다면 지금 돌아가는 레디스는 이미 디스크리스 복제를 쓰고 있다. 복제본 쪽에도 repl-diskless-load 옵션이 있어 받은 데이터를 디스크를 거치지 않고 바로 메모리에 올릴 수 있다. (근거: redis.conf)

비동기 방식으로 동작하는 복제 연결

  • 정상적으로 연결된 상태에서 마스터에서 복제본으로의 데이터 전달은 비동기로 동작한다
  • 마스터 장애로 데이터가 복제본에 전달되지 못하면 그만큼 유실이 발생한다
    • 전달 속도가 매우 빠르므로 이런 현상이 빈번하지는 않다
!

비동기라는 말의 무게

마스터는 복제본의 응답을 기다리지 않고 클라이언트에게 OK 를 준다. 즉 성공 응답을 받은 쓰기도 페일오버에서 사라질 수 있다. 손실 폭을 제한하고 싶다면 min-replicas-to-write / min-replicas-max-lag 로 "복제본 N개가 M초 이내로 따라오고 있지 않으면 쓰기를 거부"하도록 설정할 수 있다. 완전한 동기 복제는 아니지만 유실 창을 좁혀 준다.

복제 아이디

  • 복제 기능을 쓰지 않는 인스턴스를 포함해 모든 인스턴스가 복제 ID 를 가진다
  • INFO REPLICATION 으로 복제 관련 상태를 확인할 수 있다

부분 재동기화

  • 네트워크가 불안정해 연결이 끊길 때마다 RDB 를 새로 받으면 성능이 크게 나빠진다
  • 이를 방지하기 위해 부분 재동기화를 제공한다
  • 마스터는 커넥션 유실에 대비해 백로그 버퍼에 복제본으로 보낼 데이터를 남겨 둔다
  • 복제본은 PSYNC 로 자신의 replication id 와 offset 을 마스터에 전달한다
    • 모든 데이터를 다시 받는 대신 차이 나는 offset 부터의 데이터만 백로그 버퍼에서 받아 온다
  • 백로그 버퍼에 필요한 구간이 없거나 replication id 가 다르면 전체 재동기화를 수행한다
  • 백로그 크기는 기본 1MB 이며 repl-backlog-size 로 조정한다

부분 재동기화는 두 관문을 모두 통과해야 한다 — 복제 ID 가 같고, 끊긴 동안의 데이터가 아직 백로그에 남아 있어야 한다. 끊김이 길어질수록 백로그를 넘겨 버리므로, 불안정한 환경일수록 repl-backlog-size 를 키운다.

Secondary 복제 ID

  • 기존 마스터 A 가 다운되어 복제본 B 가 마스터로 승격되는 상황을 가정한다
  • B, C 모두 A 를 바라보던 구조에서, 세컨더리 복제 ID 덕분에 C 는 B 를 새 마스터로 삼는다
  • 승격된 B 는 새 복제 ID 를 만들면서 이전 ID 를 세컨더리로 기억한다. 그래서 C 가 예전 ID 로 PSYNC 를 걸어도 알아본다
  • 덕분에 C 는 B 에 대해 전체 재동기화 없이 부분 재동기화로 이어 붙일 수 있다
  • 결국 세컨더리 복제 ID 가 존재하는 이유는 페일오버 이후 승격되는 복제본 때문이다

읽기 전용 모드로 동작하는 복제본 노드

  • 기본적으로 복제본은 읽기 전용으로 동작하며 SET 을 쓸 수 없다
  • replica-read-only 옵션으로 끌 수 있지만, 복제본에 쓴 데이터는 마스터로 전달되지 않고 재동기화 때 사라지므로 권장하지 않는다

유효하지 않은 복제본 데이터

  • 유효하지 않은 데이터란 마스터와 복제본의 데이터가 정확히 일치하지 않는 상태를 뜻한다
  • 이 상태에서는 기본적으로 에러를 반환하며, replica-serve-stale-data 옵션으로 오래된 데이터라도 응답하게 바꿀 수 있다

백업을 사용하지 않는 경우에서의 복제

  • 복제를 사용한다면 마스터와 복제본 모두 백업 기능을 켜 두는 것이 좋다
  • 백업을 쓰지 않으려면 재부팅 후 레디스가 자동으로 시작되지 않도록 설정할 것을 권장한다
  • 마스터가 빈 상태로 재시작하면, 복제본은 그 빈 데이터를 그대로 복제해 와 데이터가 전부 사라진다
×

백업 없는 복제 구성에서 가장 흔한 사고

마스터가 죽었다가 혼자 살아 돌아오면 데이터가 없는 채로 복제를 재개하고, 복제본들이 그 빈 상태를 따라가면서 전체 데이터가 사라진다. 그래서 백업을 끌 거라면 자동 재시작도 함께 꺼야 한다.

정리

  • 전체 동기화는 fork + RDB, 부분 재동기화는 백로그 버퍼에서 offset 차이만 보낸다.
  • 7.0 부터 디스크리스 복제(repl-diskless-sync yes)가 기본이며, repl-diskless-sync-delay(기본 5초)는 여러 복제본을 모아 한 번에 보내기 위한 대기 시간이다.
  • 복제는 비동기다. 성공 응답을 받은 쓰기도 유실될 수 있으며 min-replicas-* 로 창을 좁힌다.
  • 세컨더리 복제 ID 덕분에 페일오버 이후에도 전체 재동기화를 피할 수 있다.
  • 백업을 끄면 자동 재시작도 꺼야 한다. 빈 마스터가 복제본을 지워 버릴 수 있다.
CH 9

센티널

복제만 있으면 마스터가 죽었을 때 사람이 새벽에 일어나야 한다. 센티널은 그 야근을 대신하는 별도 프로세스다. 감시하고, 합의하고, 승격시키고, 클라이언트에게 새 주소를 알려 준다.

9-1

센티널이란

복제가 준비해 둔 예비 선수를, 심판 없이 경기장에 넣을 수는 없다. 센티널이 그 심판이다.

핵심 센티널은 데이터를 담지 않는다. 감시하고 합의하고 승격시키는 일만 한다. 그래서 최소 3대의 홀수로 구성해 다수결이 성립하게 만든다.

복제를 통한 레디스의 고가용성 확보

  • 복제만 쓰면 마스터가 죽었을 때 수동으로 트래픽을 복제본으로 옮겨야 한다
  • 장애 발생 시 직접 대처하지 않으면 그대로 장시간 서비스 장애로 이어진다

센티널이란?

  • 데이터를 저장하는 레디스 인스턴스와는 다른, 별도의 역할을 하는 프로그램
  • 자동 페일오버 기능으로 다운타임을 최소화할 수 있다

센티널 기능

  • 모니터링 : 마스터와 복제본 인스턴스의 상태를 실시간으로 확인한다
  • 자동 페일오버 : 마스터 이상을 감지하면 정상적인 복제본을 마스터로 승격시킨다
  • 인스턴스 구성 정보 제공 : 클라이언트에게 현재 마스터의 정보를 알려 준다
    • 페일오버가 일어나면 바뀐 마스터 정보도 함께 넘겨주므로 애플리케이션이 접속 정보를 직접 바꾸지 않아도 된다
i

클라이언트가 센티널을 알아야 한다 보강

센티널 구성에서 애플리케이션은 레디스 주소가 아니라 센티널 주소 목록과 마스터 이름을 들고 접속한다. 클라이언트 라이브러리가 SENTINEL get-master-addr-by-name 으로 현재 마스터를 물어보고, 페일오버 알림을 pub/sub 로 받아 커넥션을 다시 맺는다. 센티널을 세워 두고 애플리케이션이 마스터 IP 를 직접 물고 있으면 자동 페일오버는 아무 의미가 없다.

분산 시스템으로 동작하는 센티널

  • 센티널은 SPOF 를 방지하기 위해 최소 3대 이상일 때 정상 동작하도록 설계됐다
  • 오탐을 줄이기 위해 쿼럼(Quorum) 개념을 사용한다
    • 마스터가 비정상이라는 데 동의해야 하는 센티널의 수
    • 이를 만족하면 페일오버를 진행한다
    • 센티널이 3개면 쿼럼은 보통 2로 잡는다. 2개 이상이 동의하면 페일오버가 시작된다
    • 과반수 선출 개념을 쓰므로 3, 5 처럼 홀수로 구성하는 것이 좋다
!

쿼럼과 과반수는 다른 숫자다

쿼럼은 "장애라고 판정하는 데 필요한 동의 수"이고, 실제로 페일오버를 실행할 리더를 뽑을 때는 언제나 전체 센티널의 과반수가 필요하다. 센티널 5대에 쿼럼을 2로 낮춰도, 리더 선출에는 여전히 3표가 필요하다. 쿼럼을 낮추는 것은 감지를 예민하게 만들 뿐 안전장치를 없애지는 않는다.

센티널 인스턴스 배치 방법

  • 기본적으로 물리적으로 서로 영향을 받지 않는 서버에서 실행하는 것이 좋다
  • 마스터 장애를 제대로 감지하기 위해 서로 다른 가용 영역에 배치하는 것이 일반적이다
  • 레디스 인스턴스가 2대뿐이어도 충분한 상황이라면, 나머지 1대의 서버에는 센티널만이라도 배치하는 것이 좋다
    • 클라이언트 요청을 받지 않으니 최소 사양으로도 충분하다

정리

  • 센티널은 데이터를 담지 않는 감시 프로세스이며, 모니터링/자동 페일오버/구성 정보 제공을 담당한다.
  • 최소 3대, 홀수로, 서로 다른 장애 도메인에 배치한다.
  • 쿼럼은 장애 판정 기준이고, 리더 선출에는 항상 전체의 과반수가 필요하다.
  • 애플리케이션은 마스터 IP 가 아니라 센티널 목록을 바라봐야 페일오버 효과가 있다.

센티널 인스턴스 실행하기

설정 두 줄로 뜨지만, 확인해야 할 값은 세 개다 — 다른 센티널 수, 마스터 상태 플래그, 연결된 복제본 수.

핵심 센티널을 띄운 뒤에는 SENTINEL MASTER 와 SENTINEL CKQUORUM 으로 정말 페일오버가 가능한 상태인지 반드시 확인해야 한다.

NOQUORUM

쓸 수 있는 센티널이 1대뿐인데 쿼럼이 2 라서 페일오버가 영영 일어나지 않는 상태다. 센티널을 세운 뒤 이 커맨드가 OK 를 돌려주는지 반드시 확인해야 한다. 구성만 해 두고 확인하지 않으면, 정작 마스터가 죽는 날 아무 일도 일어나지 않는다.

커맨드를 이용한 페일오버 (수동)

SENTINEL FAILOVER <master-name>

이 커맨드는 다른 센티널의 동의를 구하지 않고 즉시 페일오버를 실행한다. 계획된 점검이나 테스트에 쓰라는 뜻이다.

마스터를 다운시켜서 페일오버 (자동)
  • 센티널은 마스터에 주기적으로 핑을 보내 헬스체크를 한다
  • sentinel.conf 에 지정한 down-after-milliseconds 동안 응답이 없으면 페일오버를 진행한다
  • 기본값은 30000ms, 즉 30초다
terminal
redis-cli -h <master-ip> -p <master-port> shutdown

정리

  • 센티널 기본 포트는 26379 이며, 설정의 핵심은 sentinel monitor 이름 IP 포트 쿼럼 한 줄이다.
  • 구성 후 SENTINEL MASTER 의 num-other-sentinels/num-slaves/flags 와 SENTINEL CKQUORUM 을 반드시 확인한다.
  • 수동 페일오버(SENTINEL FAILOVER)는 합의 없이 즉시 실행되므로 점검용이다.
9-3

센티널 운영하기

감지에서 승격까지, 센티널 안에서 벌어지는 다섯 단계. 그리고 그 합의가 깨질 때 생기는 스플릿 브레인.

핵심 페일오버는 sdown → odown → 에포크 증가 → 리더 선출 → 복제본 승격 순으로 진행된다. 각 단계마다 다수의 동의를 요구하는 것이 오탐을 막는 장치다.

패스워드 인증

  • 마스터와 복제본에 requirepass, masterauth 를 지정했다면 센티널 설정 파일에도 비밀번호를 넣어야 한다
  • 언제든 하위 복제본이 마스터가 될 수 있으므로 모든 노드가 같은 비밀번호를 써야 한다
sentinel.conf
sentinel auth-pass <master-name> <password>

복제본 우선순위

  • 각 인스턴스는 replica-priority 파라미터를 가진다
  • 센티널은 이 값이 낮을수록 먼저 마스터로 승격시킨다
  • 0 인 경우 절대 마스터로 승격되지 않는다
!

원문 교정 원문 교정

노트에는 "0~100 사이의 값을 가진다"고 되어 있으나, replica-priority 는 범위 제한이 없는 정수이며 기본값이 100 이다. 100 보다 큰 값도 쓸 수 있다. 특별한 선호가 없다면 모든 인스턴스를 기본값 그대로 두면 되고, 우선순위를 쓰기로 했다면 마스터를 포함한 모든 노드에 설정해야 한다(마스터도 언젠가 복제본이 되기 때문). (근거: Redis Docs — Sentinel)

운영 중 센티널 정보 변경

  • 센티널 실행 도중에도 모니터링할 마스터를 추가/제거/변경할 수 있다
  • 마스터를 모니터링하는 센티널이 여러 대라면 각 센티널에 모두 설정해야 한다
  • 이 설정은 다른 센티널로 전파되지 않는다
새로운 마스터를 모니터링하도록 변경
sentinel
SENTINEL MONITOR <master-name> <ip> <port> <quorum>
더 이상 특정 마스터를 모니터링하지 않도록 변경
sentinel
SENTINEL REMOVE <master-name>
특정 마스터의 파라미터 변경
sentinel
SENTINEL SET <master-name> down-after-milliseconds <milliseconds>

센티널 초기화

  • 센티널은 비정상인 노드라고 해서 마음대로 모니터링을 멈추지 않는다
  • SENTINEL RESET 으로 해당 마스터에 대해 알고 있던 상태를 초기화한다
sentinel
SENTINEL RESET <master-name>

센티널 노드의 추가/제거

  • 같은 마스터를 모니터링하도록 설정한 인스턴스를 실행하면, 자동 검색 메커니즘에 의해 기존 센티널들의 known-list 에 추가된다
  • 여러 대를 추가할 때는 약 10초 정도 간격을 두고 실행하는 것이 안전하다
  • SENTINEL MASTER <master-name> 으로 잘 추가됐는지 확인하면 좋다
  • 오랫동안 응답이 없어도 known-list 에서 자동으로 지워지지 않으므로 직접 제거해야 한다

센티널의 자동 페일오버 과정

  • 센티널은 최소 3개 이상의 인스턴스가 함께 동작하는 분산 시스템이다
  • 여러 노드가 함께 감시하므로 오탐을 줄일 수 있다

혼자만의 판단(sdown)은 아무것도 바꾸지 못한다 — 다른 센티널에게 물어 쿼럼을 채워야 odown 이 되고, 거기서 다시 과반수의 표를 얻어야 리더가 되어 승격을 실행할 수 있다.
마스터의 장애 상황 감지
  • 핑에 대한 유효한 응답은 +PONG, -LOADING, -MASTERDOWN 세 가지이며 그 외 응답은 유효하지 않다고 판단한다

-LOADING 은 재시작 후 데이터를 읽는 중, -MASTERDOWN 은 복제본이 마스터를 잃은 상태를 뜻한다. 둘 다 프로세스는 살아 있다는 증거이므로 다운으로 치지 않는다.

sdown(subjectively down), odown(objectively down) 상태로 전환
  • 상태 전환 프로세스
    • 센티널이 마스터의 응답이 늦어지면 일단 sdown 으로 플래깅한다
    • 이후 다른 센티널들에게 장애 사실을 전파한다
      • SENTINEL is-master-down-by-addr <ip> <port> <epoch> <runid>
    • 전파를 받은 센티널들은 자신도 장애로 보는지 응답한다
    • 쿼럼 이상의 센티널이 장애를 인지했다면 odown 으로 플래깅한다
  • 센티널은 마스터에 대해서만 odown 상태를 가진다
  • 복제본에 장애가 나면 sdown 으로만 플래깅하고, 그 노드는 마스터로 승격되지 않는다
에포크 증가
  • 센티널은 에포크로 각 마스터에서 발생한 페일오버의 버전을 관리한다
  • 동일한 에포크 값을 사용함으로써 페일오버가 진행되는 동안 모든 센티널이 같은 작업을 시도한다는 것을 보장할 수 있다
센티널 리더 선출
  • 에포크를 증가시킨 센티널이 다른 센티널들에게 리더를 정하기 위한 투표 메시지를 보낸다
  • 다른 센티널은 자신의 에포크와 비교해 더 작으면 값을 올리고 투표하겠다는 응답을 보낸다
  • 에포크가 동일하면 이미 리더로 선출한 센티널의 ID 를 응답한다
복제본 선정 후 마스터로 승격
  • 과반수 이상이 동의하면, 리더 센티널은 마스터로 승격 가능한 복제본을 선정한다. 우선순위는
    1. replica-priority 가 낮은 복제본
    2. 마스터로부터 더 많은 데이터를 수신한(복제 offset 이 큰) 복제본
    3. 그래도 같으면 runID 가 사전순으로 작은 복제본 — 의미는 없고 결정을 결정론적으로 만들기 위한 규칙이다
  • 선정된 복제본에는 SLAVEOF NO ONE 을 보내 기존 마스터와의 연결을 끊는다
복제 연결 변경
  • 새 마스터가 정해지면 각 인스턴스에 REPLICAOF 를 보내 새 마스터를 바라보게 한다
장애 조치 완료
  • 페일오버가 끝나면 센티널은 새 마스터를 모니터링하기 시작한다

스플릿 브레인 현상

  • 네트워크 파티션 문제로 분산 환경이 둘로 끊긴다
  • 끊긴 두 부분이 동기화되지 않은 채 각자를 정상 서비스라고 인식하는 현상이다
  • 결과적으로 마스터가 두 개 생긴다
!

스플릿 브레인을 줄이는 설정

파티션 반대편의 옛 마스터는 자신이 여전히 마스터인 줄 알고 쓰기를 받는다. 그 쓰기는 나중에 통합될 때 버려진다. 8-2 에서 본 min-replicas-to-write / min-replicas-max-lag 를 설정해 두면, 복제본과 끊긴 마스터는 스스로 쓰기를 거부하므로 버려질 데이터를 애초에 받지 않는다.

정리

  • 페일오버 단계 — sdown(혼자 판단) → odown(쿼럼 합의) → 에포크 증가 → 리더 선출(과반수) → 복제본 승격 → 구성 전파.
  • 승격 후보는 replica-priority → 복제 offset → runID 순으로 정해진다. priority 0 은 영구 제외.
  • replica-priority 는 기본값 100 인 정수이며 0~100 범위 제한은 없다.
  • 센티널 설정 변경은 전파되지 않으므로 모든 센티널에 각각 적용해야 한다.
  • 스플릿 브레인의 데이터 유실은 min-replicas-* 설정으로 줄인다.
CH 10

확장성

레디스는 커맨드를 싱글 스레드로 처리한다. 그래서 CPU를 아무리 키워도 한계가 온다. 답은 옆으로 늘리는 것 — 클러스터다. 16384개의 해시 슬롯을 여러 마스터가 나눠 가지는 구조를 이 챕터에서 끝까지 따라간다.

10-1

레디스 클러스터와 확장성

싱글 스레드라는 설계가 만든 천장. 위로 못 올리면 옆으로 늘려야 한다.

핵심 레디스는 커맨드를 싱글 스레드로 처리하므로 CPU 코어를 늘려도 처리량이 비례해 늘지 않는다. 그래서 확장의 정답은 대개 스케일 아웃, 즉 클러스터다.

스케일 업 vs 스케일 아웃

스케일 업
  • 서버 하드웨어 사양을 올리는 방법. CPU/RAM 등을 높여 처리량을 올린다
  • 서버 자체의 능력을 올리므로 수직 확장이라 부른다
  • 간단하지만 비용 문제와 사양의 한계가 있다
스케일 아웃
  • 장비를 추가해 시스템을 확장하는 방법
  • 기존 서버의 업그레이드에는 한계가 있다
  • 비슷한 서버를 여러 대 배치해 용량과 처리량을 높인다
  • 대수가 늘어나므로 수평 확장이라 부른다
  • 분산 처리에 대한 로직이 추가로 필요하다

레디스에서의 확장성

  • 운영 중에 이빅션(eviction)이 자주 발생하면 스케일 업을 고려할 수 있다
  • 이빅션은 maxmemory 가 꽉 찬 상태에서 데이터를 더 넣으려 할 때 발생한다
  • 다만 레디스는 커맨드를 싱글 스레드로 처리하므로 CPU 가 좋아도 전부 활용하지 못한다
i

"싱글 스레드"의 정확한 범위 보강

싱글 스레드인 것은 커맨드를 실행하는 부분이다. 레디스는 이미 여러 스레드를 쓴다 — UNLINK 의 지연 해제, BGSAVE 의 fork 프로세스, 그리고 6.0 부터는 io-threads 로 네트워크 소켓 읽기/쓰기를 여러 스레드에 나눌 수 있다. 다만 명령 실행 자체는 여전히 하나의 스레드가 순서대로 처리하므로, O(N) 커맨드 하나가 전체를 멈추는 성질은 그대로다.

레디스 클러스터의 기능

클러스터 모드로 사용하면 애플리케이션 아키텍처를 바꾸지 않고도 레디스를 확장할 수 있다.

데이터 샤딩
  • 여러 서버 간에 데이터를 분할하는 것을 샤딩이라 한다
  • 클러스터 기능을 쓰면 마스터를 최대 1000개 규모까지 확장할 수 있다
  • 샤딩과 관련된 모든 처리는 레디스 내부에서 이뤄지고 별도의 아키텍처가 필요하지 않다
  • 데이터는 키를 기준으로 샤딩되고, 하나의 키는 항상 하나의 마스터에 매핑된다
  • 클라이언트가 다른 노드에 접근하면 자동으로 리디렉션해 준다
  • 노드 구성이 바뀌지 않는 한 키-노드 매핑이 클라이언트에 캐싱되어 성능이 개선된다
고가용성
  • 최소 3대의 마스터와 그 복제본을 갖도록 구성하는 것이 일반적이며, 각 노드는 서로를 모니터링한다
  • 장애 발생 시 외부 개입 없이 자동으로 페일오버가 진행되므로 가용성이 올라간다
  • 마스터에 연결된 복제본 수를 파악해 잉여 복제본을 필요한 노드로 옮기는 마이그레이션도 수행한다
!

센티널과 클러스터의 결정적 차이

센티널은 감시를 외부 프로세스가 하지만, 클러스터는 레디스 노드끼리 서로 감시하고 투표한다. 그래서 클러스터에는 별도의 센티널 인스턴스가 필요 없다. 대신 투표권을 가진 것은 마스터뿐이므로 마스터가 최소 3대여야 과반수가 성립한다.

클러스터 버스
  • 클러스터 내부 노드는 클러스터 버스라는 독립적인 통신 채널을 사용한다
  • 모든 노드는 다른 노드의 연결을 받기 위해 추가 TCP 포트를 연다
  • 따로 지정하지 않으면 기본 포트에 +10000 한 값이 된다. 6379 라면 16379
  • full-mesh 토폴로지라 모든 노드가 N-1 개의 다른 노드와 TCP 연결을 맺는다
  • 한 노드로 헬스체크를 시도하고 응답이 이상하면 다른 노드로 시도하는 방식이다

방화벽에서 가장 자주 빠뜨리는 포트

클러스터가 붙지 않는 문제의 대부분은 16379 포트가 막혀 있어서다. 6379 만 열어 두면 클라이언트는 붙지만 노드끼리 서로를 발견하지 못한다. 두 포트를 모두 열어야 한다.

정리

  • 커맨드 실행이 싱글 스레드이므로 스케일 업에는 천장이 있다. 확장은 대개 클러스터로 한다.
  • 클러스터는 샤딩과 고가용성을 함께 제공하며, 별도의 감시 프로세스 없이 노드끼리 감시한다.
  • 노드 간 통신에는 포트 + 10000 의 클러스터 버스 포트가 필요하다.
10-2

레디스 클러스터 동작 방법

키를 노드에 직접 붙이지 않고 16384개의 슬롯을 한 겹 끼워 넣은 이유.

핵심 키는 노드가 아니라 슬롯에 속하고, 슬롯이 노드에 배정된다. 이 한 겹 덕분에 노드 추가/삭제가 "슬롯을 옮기는 일"로 단순해진다.

해시 슬롯을 이용한 데이터 샤딩

  • 클러스터에서 모든 데이터는 해시 슬롯에 담긴다
  • 총 16384개의 해시 슬롯이 있고, 마스터가 3개라면 하나당 약 16384/3 개씩 나눠 가진다
    • 0 ~ 5460, 5461 ~ 10922, 10923 ~ 16383
  • 입력되는 모든 키는 하나의 해시 슬롯에 저장된다
    • 키를 CRC16 으로 계산한 값을 16384 로 나눈 나머지가 슬롯 번호가 된다
  • 해시 슬롯은 마스터 사이에서 자유롭게 이동할 수 있고, 이 성질 덕분에 마스터 추가/삭제가 매우 단순하다
키와 노드 사이에 슬롯이라는 고정 좌표가 있다 — 키에서 슬롯까지는 순수한 계산이라 언제 어디서 해도 같은 답이 나오고, 슬롯에서 노드까지만 구성에 따라 바뀐다. 노드를 추가한다는 것은 곧 슬롯 구간을 넘겨받는다는 뜻이다.

해시태그

  • 클러스터에서는 여러 키를 한 번에 다루는 다중 키 커맨드를 그냥 쓸 수 없다
    • MGET user1:name user2:name 같은 커맨드
  • 해시태그를 쓰면 가능해진다
    • 키에 중괄호를 넣으면 전체가 아니라 중괄호 사이의 값으로만 해시한다
    • user:{123}:profile, user:{123}:settings
    • 두 키는 중괄호 안이 같은 123 이므로 같은 해시 슬롯에 저장되는 것이 보장된다
  • 다중 키 커맨드를 쓰려면 해시태그가 필요하지만, 하나의 슬롯에 데이터가 몰릴 수 있으니 키 분배 모니터링이 필요할 수 있다

자동 재구성

  • 센티널과 마찬가지로 복제와 페일오버를 통해 고가용성을 확보한다
  • 센티널은 별도의 인스턴스가 있지만, 클러스터는 레디스끼리 감시한다는 차이가 있다
자동 페일오버
  • 프로세스
    • 마스터 A 에 장애가 나면 복제본 AA 가 다른 마스터 노드들에게 페일오버 승인 투표를 요청한다
    • 다른 마스터들은 A 가 비정상이라고 보면 투표할 수 있고, 과반수가 동의하면 AA 가 마스터로 승격된다
    • AA 마저 장애가 나면 데이터 정합성을 위해 클러스터 전체 상태가 fail 로 바뀐다
  • 가용성이 중요하다면 아무 마스터에나 복제본을 하나 더 붙여 두고 자동 복제본 마이그레이션이 작동하게 하는 것을 권장한다
자동 복제본 마이그레이션
  • A/AA, B/BB, C/CC/CCC 구성을 가정한다
  • A 가 다운되어 AA 가 승격되면, 복제본이 없어진 AA 를 위해 CCC 가 AA 의 복제본으로 옮겨 온다. 이를 자동 복제본 마이그레이션이라 한다
  • 설정으로 제어할 수 있다
    • cluster-allow-replica-migration : 자동 마이그레이션 수행 여부 (기본값 yes)
    • cluster-migration-barrier : 복제본을 넘겨줄 때 원래 마스터에 최소 몇 개를 남겨야 하는지 (기본값 1)
      • 2 로 지정하면 위 상황에서 CCC 는 옮겨 가지 않는다. C 에 복제본이 2개 남아야 하기 때문이다

정리

  • 키 → CRC16 mod 16384 → 슬롯 → 노드. 중간의 슬롯 계층이 노드 증감을 단순한 슬롯 이동으로 만든다.
  • 다중 키 커맨드는 같은 슬롯에서만 가능하다. 해시태그 {...} 로 슬롯을 묶되 쏠림을 감시해야 한다.
  • 페일오버는 마스터들의 과반수 투표로 승인된다. 복제본 없는 마스터가 생기면 잉여 복제본이 자동으로 옮겨 간다.
10-3

레디스 클러스터 실행하기

마스터 3 + 복제본 3. 그리고 -c 플래그 하나가 만드는 차이.

핵심 클러스터에서는 아무 노드에나 요청해도 되는 게 아니다. 슬롯을 담당하지 않는 노드는 MOVED 로 다른 노드를 가리킬 뿐이며, 그 리디렉션을 따라가는 것은 클라이언트의 몫이다.
  • 일반적으로 마스터 3개, 각각의 복제본 3개, 총 6개로 구성한다

클러스터 초기화

클러스터 활성화

redis.conf 에서 클러스터 사용 여부를 지정한다.

redis.conf
cluster-enabled yes
클러스터 생성

각 레디스의 IP/PORT 를 나열하고 마스터당 복제본 개수를 지정한다.

terminal
redis-cli --cluster create [host:port ...] --cluster-replicas 1

클러스터 상태 확인하기

terminal
redis-cli cluster nodes

redis-cli 를 이용한 클러스터 접근과 리디렉션

  • 클러스터 모드에서는 키를 저장할 수 있는 노드가 정해져 있어 해당 노드로 요청해야 한다
  • 이 불편함 때문에 Jedis, Redisson 등 대부분의 클라이언트가 클러스터 모드 기능을 제공한다
일반 접속
$ redis-cli
> set user:1 true
(error) MOVED 10778 192.168.0.10:6379
-c 옵션
$ redis-cli -c
> set user:1 true
-> Redirect to Slot [12923] @ 192.168.0.22:6379
OK

-c 는 서버가 리디렉션을 대신해 준다는 뜻이 아니다. redis-cli 가 MOVED 응답을 읽고 스스로 다시 접속하는 것이다. 애플리케이션에서 클러스터 지원 클라이언트를 써야 하는 이유가 같다.

페일오버 테스트

커맨드를 이용한 페일오버 (수동)
  • 복제본 노드에서 CLUSTER FAILOVER 를 실행해 페일오버를 일으킬 수 있다
  • 수동 페일오버 동안 기존 마스터에 연결된 클라이언트는 잠시 블로킹된다

대신 이 방식은 데이터 유실이 없다. 복제본이 마스터를 따라잡을 때까지 기다렸다가 역할을 교환하기 때문이다. 계획된 점검이나 버전 업그레이드에 쓰는 방법이다.

마스터를 중지시켜서 페일오버 (자동)
  • 직접 마스터를 다운시켜 페일오버가 잘 일어나는지 확인할 수 있다
  • 복제본은 redis.conf 의 cluster-node-timeout 동안 마스터의 응답이 없으면 비정상으로 판단한다 (기본값 15000ms)
terminal
redis-cli -h <master-ip> -p <master-port> shutdown

정리

  • cluster-enabled yes 후 redis-cli --cluster create ... --cluster-replicas 1 로 6노드 구성을 만든다.
  • MOVED 를 따라가는 것은 클라이언트다. redis-cli -c 나 클러스터 지원 라이브러리가 필요하다.
  • 계획된 전환은 CLUSTER FAILOVER(무손실), 장애 감지 기준은 cluster-node-timeout(기본 15초).
10-4

레디스 클러스터 운영하기

노드를 넣고 빼는 일은 결국 슬롯을 넘기고 받는 일이다.

핵심 마스터는 슬롯이 비어 있을 때만 뺄 수 있다. 그래서 노드 제거의 실체는 리샤딩이고, 리샤딩이 끝난 뒤에야 제거 커맨드가 통한다.

클러스터 리샤딩

  • 마스터가 가진 해시 슬롯 중 일부를 다른 마스터로 옮기는 작업이다
  • redis-cli 로 리샤딩과 결과 확인이 가능하다
terminal
redis-cli --cluster reshard <ip> <port>

redis-cli --cluster check <ip> <port>

클러스터 리샤딩 — 간단 버전

  • 리샤딩이 잦거나 자동화하고 싶을 때, 대화형 입력 없이 바로 슬롯을 옮길 수 있다
  • 단점은 즉시 실행되므로 중간에 취소하거나 확인하기 어렵다는 것
terminal
redis-cli --cluster reshard <ip> <port> --cluster-from <node-id>

클러스터 확장 — 신규 노드 추가

  • 확장을 위한 마스터 추가 또는 가용성을 위한 복제본 추가가 여기 해당한다
  • 두 경우 모두 추가하려는 레디스에는 아무 데이터도 없어야 한다. 비어 있지 않으면 에러가 난다
마스터로 추가하기
terminal
redis-cli --cluster add-node <신규 노드 ip:port> <기존 노드 ip:port>

마스터로 추가하면 슬롯이 0개인 마스터가 된다. 실제로 데이터를 받으려면 이어서 리샤딩으로 슬롯을 넘겨줘야 한다.

복제본으로 추가하기
terminal
redis-cli --cluster add-node <신규 노드 ip:port> <기존 노드 ip:port> --cluster-slave <기존 마스터 ID>

노드 제거하기

  • 첫 번째 인자에는 기존 클러스터에 속한 아무 노드의 정보를 넣는다
  • 마스터는 데이터가 없을 때만 제거할 수 있다
    • 즉 리샤딩으로 모든 해시 슬롯을 다른 마스터로 옮겨야 한다
    • 또는 수동 페일오버로 역할을 복제본으로 바꾼 뒤 제거할 수도 있다
terminal
redis-cli --cluster del-node <기존 노드 ip:port> <삭제할 노드 ID>
CLUSTER FORGET
  • 노드를 제거하면 다른 노드들에게도 그 노드가 사라졌다고 알려야 한다
  • 커맨드를 전파하고 나면 60초 동안은 그 노드 정보로 다시 연결을 시도하지 않는다
  • 클러스터의 노드들은 가십 프로토콜로 새 노드를 탐지하고 자동으로 연결하기 때문에, 이 유예가 없으면 방금 지운 노드를 곧바로 다시 알게 된다
CLUSTER RESET
  • 제거될 노드에서 수행하는 커맨드로 두 가지 옵션이 있으며 기본값은 SOFT 다
  • del-node 도중에도 자동으로 실행되지만, 특정 노드를 다른 역할로 재사용하려 할 때도 쓸 수 있다
SOFT
  • 복제본이었다면 마스터로 전환되고 모든 데이터가 삭제된다
  • 마스터인데 저장된 키가 있으면 리셋이 중단된다
  • 해시 슬롯을 가지고 있었다면 모두 해제되고, 진행 중이던 페일오버 상태도 초기화된다
  • 클러스터 내 다른 노드에 대한 정보도 초기화되어 기존 클러스터 구성원을 더 이상 알지 못한다
HARD
  • SOFT 의 과정을 모두 수행하고 다음이 추가된다
  • currentEpoch, configEpoch, lastVoteEpoch 가 0 으로 초기화된다
  • 해당 노드의 ID 가 새로운 임의 ID 로 바뀐다

레디스 클러스터로의 데이터 마이그레이션

  • 싱글 또는 센티널로 운영 중인 레디스를 클러스터로 옮길 때 redis-cli 로 처리할 수 있다
  • 기존 앱에서 다중 키 커맨드를 쓰지 않았다면 커넥션 변경 외에 문제가 없고, 썼다면 해시태그를 쓰도록 앱을 수정해야 한다
  • 마이그레이션을 시작할 때는 기존 서비스의 커넥션을 모두 정리하고 하는 편이 안전하다
terminal
redis-cli --cluster import <클러스터에 합류할 노드 ip:port> --cluster-from <데이터를 가져올 노드 ip:port> --cluster-copy

복제본을 통한 읽기 성능 향상

  • 클러스터는 기본적으로 슬롯을 담당하는 마스터에서만 데이터를 읽는다
  • 복제본에서 읽고 싶다면 READONLY 를 보내 그 커넥션이 복제본에서 직접 읽도록 만든다
redis-cli
127.0.0.1:6379> readonly
OK

READONLY 는 커넥션 단위 설정이라 연결이 끊기면 사라진다. 되돌리려면 READWRITE 를 보낸다. 복제는 비동기이므로 이 경로로 읽으면 아주 최신 데이터는 아닐 수 있다.

정리

  • 노드 추가는 add-node, 제거는 del-node. 추가되는 노드는 반드시 비어 있어야 한다.
  • 마스터를 빼려면 먼저 리샤딩으로 슬롯을 모두 넘겨야 한다. 새로 넣은 마스터도 리샤딩 전에는 슬롯이 0개다.
  • CLUSTER FORGET 의 60초 유예는 가십으로 다시 발견되는 것을 막기 위한 장치다.
  • 복제본 읽기는 커넥션마다 READONLY 를 보내야 하고, 그 대가로 약간 오래된 데이터를 감수한다.

레디스 클러스터 동작 방법 (2)

하트비트와 가십, MOVED 와 ASK, PFAIL 과 FAIL. 클러스터 내부의 언어들.

핵심 MOVED 는 "앞으로 계속 저기로 가라", ASK 는 "이번만 저기로 가라"다. 이 한 글자 차이가 슬롯 이동 중에도 서비스가 멈추지 않게 한다.

  • 일반적으로 클러스터가 주고받는 유형의 패킷에 가십 섹션이 덧붙은 형태다

해시 슬롯 구성이 전파되는 방법

클러스터의 중요한 기능 중 하나는 커맨드에 사용된 키의 해시 슬롯이 어디에 있는지 정확히 파악하고 알려 주는 것이다.

  • 하트비트 패킷 : PING/PONG 을 주고받을 때 자신이 담당하는 해시 슬롯 정보를 패킷에 실어 보낸다
  • 업데이트 메시지
    • 하트비트 패킷에는 발신 노드의 구성 Epoch 가 들어 있다
    • 패킷을 보낸 노드의 Epoch 가 낡았다면, 받은 노드가 최신 구성 정보를 담은 업데이트 메시지를 보내 해시 슬롯 구성을 갱신하게 한다

노드 핸드셰이크

  • 한 노드가 클러스터에 합류하려면 CLUSTER MEET 를 보낸다
  • 그 노드를 모르던 노드들은 새로운 연결을 맺는다
  • 클러스터는 full-mesh 구조이므로 CLUSTER MEET 에는 방향성이 없고, 굳이 응답을 되돌려 보낼 필요도 없다

클러스터 라이브 재구성

  • 클러스터가 동작하는 중에도 마스터를 추가하거나 삭제할 수 있다
  • 내부적으로는 CLUSTER SETSLOT 8 MIGRATING B 같은 커맨드가 오간다
  • 인스턴스 간에 키를 옮기는 MIGRATE 는 원자적으로 동작하므로 경쟁 상태가 생기지 않는다
  • 이동이 완료되면 OK 신호를 보내고 원본 데이터는 삭제된다

리디렉션

레디스 클러스터가 반환하는 리디렉션은 두 종류다.

MOVED
  • "요청한 해시 슬롯은 저 노드에 있으니, 앞으로 이 키에 대한 요청은 저 노드로 보내라"는 뜻이다
  • 노드는 키가 어떤 해시 슬롯에 속하는지 계산하고 그 슬롯의 담당 마스터를 찾는다
  • 자신이 담당이면 바로 응답하고, 다른 노드가 담당이면 MOVED 를 반환한다
  • 클라이언트는 이 응답을 받으면 자신의 슬롯 맵을 갱신한다
ASK
  • "지금 요청한 것은 저 노드에 있다. 하지만 다음 요청은 일단 나에게 보내라"는 뜻이다
  • 해시 슬롯이 이동하는 도중에만 발생한다
  • 클라이언트는 지정된 노드로 쿼리를 재전송하되, 이후 같은 키에 대한 요청은 원래 노드로 다시 보내고 슬롯 맵은 갱신하지 않는다

슬롯 이동 중에는 키가 두 노드에 걸쳐 있다 — 이미 옮겨 간 키는 ASK, 아직 남은 키는 그 자리에서 응답된다. 이동이 끝나고 구성이 확정되면 그때부터 MOVED 로 바뀌어 클라이언트의 슬롯 맵이 갱신된다.

장애 감지와 페일오버

클러스터 내부에서 어떤 노드가 다른 노드에 접근할 수 없다고 감지하면 상태를 바꾼다.

PFAIL (Possible Failure) 플래그
  • 일부 노드에서 접근이 불가능하지만 아직 확실하지 않은 상태다
  • NODE_TIMEOUT 이상 도달하지 못하면 PFAIL 로 플래깅한다
    • 이때 마스터인지 복제본인지는 상관없다
  • 따라서 노드 간 왕복 시간보다 NODE_TIMEOUT 값이 충분히 커야 한다
  • PING 이후 NODE_TIMEOUT 의 절반이 지나도 PONG 이 없으면 다시 PING 을 보내는 방식으로 안정성을 높인다
FAIL 플래그
  • 실제로 페일오버를 진행하려면 FAIL 플래그여야 한다
  • PFAIL 로 플래깅된 뒤, 하트비트 패킷을 통해 다른 노드들도 그 노드를 PFAIL 또는 FAIL 로 보고 있다는 정보가 모이면 FAIL 로 승격시킨다

복제본 선출

  • 다음 조건에서 복제본이 직접 페일오버를 시도한다
    • 마스터가 FAIL 상태
    • 그 마스터가 1개 이상의 해시 슬롯을 담당하고 있음
    • 마스터와의 복제가 끊긴 지 너무 오래되지 않았음
  • 복제본은 마스터가 되기 위해 자신의 Epoch 를 1 증가시키고 마스터들에게 투표를 요청한다
내부에서 발생하는 과정
  • 복제본이 클러스터 내 모든 마스터에게 FAILOVER_AUTH_REQUEST 패킷으로 투표를 요청한다
  • 마스터는 FAILOVER_AUTH_ACK 패킷으로 동의를 알린다
  • 마스터들은 동시에 여러 복제본이 승격되는 것을 막기 위해 NODE_TIMEOUT * 2 동안 같은 마스터에 대한 다른 투표를 하지 않는다
    • Epoch 값이 낡은 노드에서 온 응답은 무시해서 걸러 낸다
  • 가장 많은 ACK 를 받은 복제본이 승격된다
    • NODE_TIMEOUT * 2 안에 과반수 마스터의 응답이 오지 않으면 페일오버는 취소된다
    • NODE_TIMEOUT * 4 만큼 지연된 뒤 새로운 투표를 다시 시도할 수 있다
마스터가 FAIL 이 된 이후

곧바로 투표를 시작하지 않고 짧은 지연을 둔다.

복제본의 투표 시작 지연
DELAY = 500ms + 랜덤 지연(0~500ms) + SLAVE_RANK * 1000ms

세 항의 역할이 각각 다르다. 고정 500ms 는 FAIL 상태가 클러스터 전체에 퍼질 시간을 벌고, 랜덤 지연은 여러 복제본이 동시에 나서는 것을 흩뜨리며, SLAVE_RANK 는 복제 데이터가 뒤처진 복제본일수록 늦게 나서게 만든다. 결과적으로 가장 최신 데이터를 가진 복제본이 먼저 투표를 시작하게 된다.

정리

  • 노드들은 하트비트 + 가십으로 서로의 상태와 슬롯 구성을 주고받는다. 낡은 Epoch 는 업데이트 메시지로 교정된다.
  • MOVED 는 영구적 재지정(슬롯 맵 갱신), ASK 는 이동 중의 일회성 우회(맵 유지).
  • PFAIL 은 혼자만의 의심, FAIL 은 다수의 확인. FAIL 이어야 페일오버가 시작된다.
  • 승격 지연 공식의 SLAVE_RANK 항이 최신 데이터를 가진 복제본을 먼저 나서게 만든다.
CH 11

보안

레디스는 기본적으로 믿을 수 있는 네트워크 안에 있다고 가정하고 설계됐다. 그 가정이 깨지는 순간을 막는 네 겹의 방어선 — 커넥션 제어, 커맨드 제어, ACL, 그리고 전송 구간 암호화.

11-1

커넥션 제어

레디스의 첫 번째 방어선은 암호가 아니라 어떤 주소에서 들어오는가이다.

핵심 레디스는 원래 신뢰할 수 있는 네트워크 안에 있다는 전제로 설계됐다. 그래서 보안의 출발점은 인증이 아니라 bind 로 접근 가능한 주소를 좁히는 일이다.

bind

  • 레디스 서버가 어떤 IP 로의 접속을 허용할지 설정하는 방법
  • 127.0.0.1 은 루프백 주소로, 레디스가 설치된 서버에서의 자체 접근만 허용한다는 의미다
  • 외부 접근이 필요하다면 0.0.0.0 이나 * 가 아니라 특정 IP 만 지정하는 것을 권장한다

비밀번호

노드에 직접 지정하기
  • Redis 6 이후에는 ACL 사용을 권장한다
  • redis.conf 또는 CLI 에서 설정할 수 있다
redis-cli
127.0.0.1:6379> config set requirepass password
OK

requirepass 는 사실 default 유저의 비밀번호를 설정하는 것과 같다. ACL 관점에서 보면 레디스에는 언제나 default 라는 유저가 존재하고, 예전 방식의 AUTH <password> 는 그 유저로 인증하는 축약형이다.

Protected Mode

  • 레디스를 운영 목적으로 사용한다면 켜 두기를 권장한다
  • yes : 비밀번호가 설정되지 않았다면 로컬에서의 접근만 허용한다
  • no : 비밀번호 없이도 외부에서 접근할 수 있게 한다
!

protected-mode 는 안전장치이지 보안 기능이 아니다

이 옵션은 설정을 깜빡한 인스턴스가 인터넷에 그대로 노출되는 사고를 막기 위한 것이다. bind 를 좁히고 비밀번호나 ACL 을 설정하면 이 옵션과 무관하게 안전해진다. 반대로 protected-mode no 로 껐다면, 그 순간 bind 와 인증을 스스로 책임진다는 뜻이 된다.

정리

  • 보안의 1순위는 bind 로 접근 가능한 주소를 좁히는 것이다. 0.0.0.0 은 피한다.
  • requirepass 는 default 유저의 비밀번호를 설정하는 것과 같다. 6 이후로는 ACL 을 쓴다.
  • protected-mode 는 설정 누락으로 인한 노출을 막는 최후의 안전장치다.
11-2

커맨드 제어

누구나 CONFIG SET 을 부를 수 있다는 것은, 누구나 서버 설정을 바꿀 수 있다는 뜻이다.

핵심 커맨드 이름 바꾸기는 임시방편이다. 재시작 없이는 되돌릴 수 없고 센티널과도 어긋난다. 제대로 된 답은 ACL 이다.

커맨드 제어

  • 대부분의 설정은 CONFIG GET, CONFIG SET 으로 조회하고 수정할 수 있다
  • 편리하다는 장점이 있지만, 접속한 모든 클라이언트가 제어할 수 있다는 점에서 위험하다

커맨드 이름 변경

  • rename-command 로 커맨드 이름을 바꾸거나 비활성화할 수 있다
    • redis.conf 에서만 설정할 수 있고 실행 중에 동적으로 바꿀 수는 없다
redis.conf
# 커맨드 이름 변경
rename-command CONFIG CONFIG_NEW

# 커맨드 비활성화
rename-command CONFIG ""
주의사항
  • 센티널을 사용 중이라면 커맨드 이름을 맞춰 줘야 한다
    • 센티널은 sentinel.conf 에서 따로 설정한다
sentinel.conf
sentinel rename-command mymaster CONFIG my_config

센티널은 마스터에 CONFIG, REPLICAOF 같은 커맨드를 직접 보내므로, 서버 쪽에서만 이름을 바꾸면 페일오버가 조용히 실패한다. 이런 함정 때문에라도 이름 변경보다 ACL 이 낫다.

커맨드 실행 환경 제어

  • Redis 7 부터 특정 커맨드를 실행할 수 있는 환경을 제어할 수 있다
  • 실행 중에 바꾸면 위험한 커맨드는 기본적으로 변경이 차단된다
  • 사용자가 직접 차단/허용할 수 있고, 로컬 접속에 한해 허용하는 선택지도 있다
redis.conf
enable-protected-configs {no|yes|local}
enable-debug-command {no|yes|local}
enable-module-command {no|yes|local}
커맨드 설명
옵션무엇을 막는가기본값
enable-protected-configsdir, dbfilename 등 경로 관련 설정의 변경no
enable-debug-commandDEBUG 커맨드no
enable-module-commandMODULE 커맨드no

세 옵션 모두 기본값이 no, 즉 차단이다. local 을 주면 루프백 접속에서만 허용된다. dir 과 dbfilename 이 이 목록에 있는 이유는, 그 둘을 바꿀 수 있으면 RDB 를 임의 경로에 임의 이름으로 쓸 수 있어 원격 코드 실행으로 이어질 수 있기 때문이다.

정리

  • CONFIG SET 은 접속만 하면 누구나 쓸 수 있으므로 반드시 통제해야 한다.
  • rename-command 는 정적 설정이고 센티널과 어긋나기 쉽다. 가능하면 ACL 로 대신한다.
  • 7.0 의 enable-* 옵션 세 가지는 기본이 차단이며, 경로 설정 변경을 막는 것이 핵심이다.
11-3

ACL

유저를 만들고, 쓸 수 있는 커맨드와 만질 수 있는 키를 정해 준다. Redis 6 이 가져온 가장 큰 운영 변화.

핵심 ACL 규칙은 왼쪽에서 오른쪽으로 차례대로 적용된다. +@all -@dangerous 는 "전부 허용한 뒤 위험한 것만 뺀다"는 뜻이고, 순서를 바꾸면 결과가 달라진다.

ACL

  • Redis 6 에서 도입된, 유저별 권한 관리 기능이다
    • 이전 버전에는 클라이언트의 권한을 제어할 방법이 없었다
  • rename-command 로도 커맨드를 제어할 수 있지만, 일시적인 우회일 뿐 완전한 방법은 아니다

유저 생성

문법
ACL SETUSER <username> <on|off> ><password> ~<accessable key> &<pub/sub channel> +<command>
redis-cli
127.0.0.1:6379> acl setuser dongwoo on >password ~cached:* &* +@all -@dangerous
OK
토큰의미
dongwoo유저 이름
on활성화 여부
>password비밀번호 추가
~cached:*접근 가능한 키 패턴
&*접근 가능한 pub/sub 채널
+@all -@dangerous모든 커맨드 허용 후 위험 카테고리 제외

유저 조회

유저 업데이트

수정하고 싶은 부분을 ACL SETUSER 로 다시 지정한다.

redis-cli
127.0.0.1:6379> acl setuser dongwoo ~id:*
OK
127.0.0.1:6379> acl getuser dongwoo
 7) "keys"
 8) "~cached:* ~id:*"
!

SETUSER 는 덮어쓰지 않고 더한다

위에서 보듯 키 패턴이 교체되지 않고 ~cached:* ~id:* 로 누적됐다. 이미 존재하는 유저에 대한 ACL SETUSER 는 기존 규칙 위에 새 규칙을 얹을 뿐이다. 초기화하려면 resetkeys, resetchannels, resetpass 또는 전체 reset 을 명시해야 한다.

유저 삭제

redis-cli
127.0.0.1:6379> acl deluser dongwoo
(integer) 1
127.0.0.1:6379> acl list
1) "user default on nopass sanitize-payload ~* &* +@all"

유저 상태 제어

  • on/off 두 가지로 상태를 제어한다
  • 새로 만든 유저의 기본값은 off 이며, 생성 또는 수정 시 상태를 지정할 수 있다
redis-cli
127.0.0.1:6379> acl setuser user1
OK
127.0.0.1:6379> acl getuser user1
 1) "flags"
 2) 1) "off"
    2) "sanitize-payload"

127.0.0.1:6379> acl setuser user1 on
OK
127.0.0.1:6379> acl getuser user1
 1) "flags"
 2) 1) "on"
    2) "sanitize-payload"

패스워드

  • >password 로 비밀번호를 추가한다
  • 비밀번호가 없으면 그 유저로 접속할 수 없다
    • nopass : 비밀번호 없이 접근 가능. 기존 비밀번호는 모두 삭제된다
    • resetpass : 비밀번호 목록을 비우고 nopass 도 해제한다. 이후 비밀번호를 다시 주거나 nopass 로 만들기 전까지 접근이 불가능하다
redis-cli
127.0.0.1:6379> acl list
1) "user default on nopass sanitize-payload ~* &* +@all"
2) "user user1 on sanitize-payload resetchannels -@all"

127.0.0.1:6379> acl setuser user1 resetpass
OK

유저 하나가 여러 개의 비밀번호를 가질 수 있다는 점이 중요하다. 비밀번호를 교체할 때 새 비밀번호를 먼저 추가하고, 모든 클라이언트가 옮겨 간 뒤 옛 비밀번호를 <password 로 제거하면 무중단 교체가 된다.

패스워드 저장 방식

  • requirepass 를 쓰면 설정 파일에 평문으로 저장된다
  • ACL 을 쓰면 SHA-256 해시로 저장된다
  • ACL GENPASS 로 안전한 난수 비밀번호를 생성할 수 있다
!

원문 교정 원문 교정

노트의 ACL GENAPSS 는 ACL GENPASS 의 오타다. 이 커맨드는 시스템의 암호학적 난수 생성기로 256비트를 만들어 64자리 16진수 문자열로 돌려준다. (근거: Redis Docs — ACL)

커맨드 권한 제어

  • ACL 로 유저별 커맨드 사용을 제어한다
  • +@all, allcommands : 모든 커맨드 사용 가능
  • -@all, nocommands : 모든 커맨드 사용 불가
  • +@<category>, -@<category> : 카테고리 단위 권한 추가/삭제
dangerous
  • 아무나 쓰면 위험한 커맨드들이 묶여 있다
  • 이 카테고리만 막아 두어도 의도치 않은 장애를 상당 부분 예방할 수 있다
  • 구성 변경 계열 : REPLCONF, REPLICAOF ...
  • 장애 유발 계열 : SORT, FLUSHDB, FLUSHALL, KEYS ...
  • 운영 계열 : SHUTDOWN, MONITOR, DEBUG, CONFIG ...
admin
  • 일반 애플리케이션은 쓸 일이 없는 관리용 커맨드들이다
  • REPLICAOF, CONFIG, DEBUG, SAVE, MONITOR, ACL, SHUTDOWN 등이 포함된다
!

원문 교정 원문 교정

노트에는 admin 이 "dangerous 커맨드를 제외한 커맨드"라고 되어 있으나, 실제로는 서로 배타적이지 않고 크게 겹친다. CONFIG, DEBUG, SAVE, MONITOR, SHUTDOWN, REPLICAOF 는 두 카테고리 모두에 속한다. admin 은 "관리 목적", dangerous 는 "잘못 쓰면 위험" 이라는 다른 기준으로 나눈 분류다. (근거: Redis Docs — ACL 카테고리)

admin 과 dangerous 는 배타적인 분류가 아니다 — 같은 커맨드가 여러 카테고리에 속할 수 있으므로, -@dangerous 를 걸었다고 @admin 이 통째로 남아 있다고 생각하면 안 된다. 실제 권한은 ACL CAT <카테고리> 로 확인하는 것이 확실하다.
fast
  • O(1) 로 수행되는 커맨드를 모아 놓은 카테고리
  • GET, SPOP, HSET 등이 포함된다
slow
  • fast 에 속하지 않는 모든 커맨드
  • SCAN, KEYS, SORT 등이 포함된다
keyspace
  • 자료구조와 무관하게 키 자체를 다루는 커맨드들
  • SCAN, KEYS, RENAME, DEL, EXPIRE, TTL 등이 포함된다
read
  • 키에서 데이터를 읽는 커맨드들
  • GET, HGET, XRANGE 등이 포함된다
write
  • 키에 데이터를 쓰는 커맨드들
  • SET, HSET, XADD 등이 포함된다
  • 만료시간 같은 메타데이터를 바꾸는 EXPIRE, PEXPIRE 등도 여기 포함된다

키 접근 제어

  • 유저가 접근할 수 있는 키도 제어할 수 있다
  • ~*, allkeys : 모든 키 접근 가능
  • ~<pattern> : 특정 패턴의 키만 접근 가능
    • ~mail:* 이면 mail:some 에 접근 가능
  • Redis 7 부터는 읽기/쓰기를 나눠 제어할 수 있다
    • %R~<pattern> : 읽기 권한만
    • %W~<pattern> : 쓰기 권한만
!

키 패턴이 막지 못하는 커맨드가 있다

FLUSHALL, FLUSHDB, SWAPDB 처럼 키 인자를 받지 않는 커맨드는 키 패턴의 통제를 받지 않는다. ~tenant1:* +@all 유저도 FLUSHALL 로 전체 DB 를 날릴 수 있다는 뜻이다. 커맨드 자체를 -flushall -flushdb -swapdb 로 명시적으로 빼야 한다.

셀렉터

  • Redis 7 부터 더 유연한 ACL 규칙을 위해 도입됐다
  • %R~mail:* 로 지정하면 GET 외에 TTL 읽기 등도 가능하다
  • GET 만 주고 싶다면 괄호로 셀렉터를 만들어 제한할 수 있다
    • acl setuser user1 resetkeys ~log:* (+GET ~mail:*)
    • mail:* 키에 대해서는 정확히 GET 권한만 부여된다

셀렉터는 기본 권한 또는 셀렉터 중 하나라도 통과하면 허용하는 방식으로 평가된다. 그래서 "이 키에는 이 커맨드만"이라는 조합을 여러 벌 만들 수 있다. 단, 한번 추가한 셀렉터는 개별 수정이 불가능하고 clearselectors 로 전부 지우는 것만 가능하다.

PUB/SUB 채널 접근 제어

  • &* : 모든 채널 접근 가능
  • resetchannels : 모든 채널 접근 불가 (Redis 7 부터 기본값)

유저 초기화

  • reset 으로 유저를 초기화한다
  • 방금 ACL SETUSER 로 만든 직후 상태와 동일해진다 (off, 비밀번호 없음, 권한 없음)

ACL 규칙을 파일로 관리하기

  • 기본적으로는 redis.conf 에 저장된다
  • 외부 파일로 관리하고 싶다면 redis.conf 에 aclfile <path> 를 지정한다
  • 외부 파일을 쓰지 않는다면 CLI 에서 설정한 뒤 CONFIG REWRITE 로 저장한다
i

aclfile 을 쓸 때의 저장 커맨드 보강

두 방식은 동시에 쓸 수 없고 저장 커맨드도 다르다. redis.conf 방식은 CONFIG REWRITE, aclfile 방식은 ACL SAVE(저장)와 ACL LOAD(다시 읽기)를 쓴다. CONFIG REWRITE 는 ACL 파일을 저장해 주지 않으므로, aclfile 을 쓰면서 ACL SAVE 를 잊으면 재시작 때 방금 만든 유저가 사라진다.

정리

  • ACL 규칙은 왼쪽부터 순서대로 적용된다. +@all -@dangerous 가 실무의 출발점이다.
  • ACL SETUSER 는 누적이다. 바꾸려면 resetkeys/resetchannels/reset 을 명시한다.
  • @admin 과 @dangerous 는 기준이 다른 분류라 크게 겹친다. 실제 범위는 ACL CAT 으로 확인한다.
  • 키 패턴은 키 인자를 받는 커맨드만 통제한다. FLUSHALL 류는 커맨드 단위로 막아야 한다.
  • 비밀번호는 SHA-256 으로 저장되고 여러 개를 둘 수 있어 무중단 교체가 가능하다.
11-4

SSL, TLS

기본은 평문이다. 암호화를 쓰려면 빌드 단계부터 결정해야 한다.

핵심 TLS 는 클라이언트 연결만 감싸는 게 아니다. 복제/센티널/클러스터 버스 각각에 별도 옵션이 있고, 하나라도 빠지면 그 경로만 조용히 실패한다.

레디스에서 SSL/TLS 사용하기

  • 기본적으로 비활성화되어 있다
  • 사용하려면 빌드 시점부터 지정해야 한다
    • make BUILD_TLS=yes
  • 클라이언트와 레디스가 같은 CA 를 신뢰하도록 인증서를 구성해야 한다
서버 구성
redis.conf
tls-port <port>
tls-cert-file <cert-file>
tls-key-file <key-file>
tls-ca-cert-file <ca-cert-file>

tls-port 는 기존 port 와 별개다. 평문 접속을 완전히 막으려면 port 0 으로 두어 비-TLS 리스너를 꺼야 한다.

redis 접속
  • redis-cli 나 애플리케이션 클라이언트에서 접속할 때도 tls 관련 옵션을 붙여야 한다

SSL/TLS 를 이용한 HA 구성

복제 구성
  • 기존 TLS 설정에 tls-replication yes 를 추가해야 한다
  • no 인 경우 마스터-복제본 사이가 평문 프로토콜로 연결되려 하면서 오류가 발생한다
센티널 구성
  • sentinel.conf 에도 TLS 관련 설정을 추가해야 한다
클러스터 구성
  • 기본 설정 외에 tls-cluster yes 를 추가해야 한다
!

TLS 는 공짜가 아니다

암복호화 비용이 붙으므로 처리량이 떨어지고 지연이 늘어난다. 같은 VPC 안의 통신이라면 TLS 대신 네트워크 수준의 격리로 충분한 경우가 많다. 반대로 네트워크를 넘어가는 구간이라면 반드시 켜야 한다.

정리

  • TLS 는 make BUILD_TLS=yes 로 빌드한 바이너리에서만 쓸 수 있다.
  • 클라이언트용 tls-port 외에 tls-replication, tls-cluster, 센티널 설정을 각각 켜야 한다.
  • 평문 접속을 완전히 막으려면 port 0 으로 비-TLS 리스너를 끈다.
CH 12

클라이언트 관리

레디스가 느려지는 원인이 늘 레디스 안에 있는 것은 아니다. 커넥션 수, 출력 버퍼, 네트워크 왕복 횟수 — 클라이언트 쪽 사정이 서버의 메모리와 응답 시간을 좌우한다.

12-1

클라이언트 핸들링

클라이언트 하나가 버퍼 하나다. 커넥션 수는 그대로 서버의 메모리 그래프에 나타난다.

핵심 레디스의 메모리는 데이터만 먹지 않는다. 클라이언트마다 출력 버퍼와 쿼리 버퍼가 붙고, 이것이 통제되지 않으면 데이터를 하나도 안 넣고도 메모리가 찬다.

클라이언트 핸들링

  • 기본적으로 소켓과 TCP 를 사용하고, 원하면 포트와 유닉스 소켓 경로를 바꿀 수 있다
  • 멀티플렉싱 방식을 사용해 하나의 통신 채널로 여러 데이터 스트림을 전송할 수 있다
  • 논블로킹 I/O 로 다수의 클라이언트를 지원한다
  • TCP_NODELAY 옵션으로 작은 데이터도 버퍼링하지 않고 즉시 보내 빠른 통신을 보장한다
  • 최대 클라이언트 수는 기본 10000 이며, 초과하면 에러와 함께 새 연결을 거절한다

클라이언트 버퍼 제한

  • 클라이언트에 돌려줄 데이터를 임시로 담기 위해 클라이언트마다 출력 버퍼를 만든다
    • 연결된 클라이언트가 1000개면 출력 버퍼도 1000개다
  • 클라이언트가 데이터를 제때 읽어 가지 못하고 요청만 계속하면 버퍼가 계속 커져 메모리 사용량이 올라간다
    • 이를 대비해 버퍼가 일정 크기를 넘으면 커넥션을 끊는다
  • 출력 버퍼 외에 쿼리 버퍼도 있다
    • 요청이 들어오면 버퍼에 담아 두었다가 처리한다
    • 기본값은 1GB 로, 쿼리 버퍼가 무한히 커지는 것을 막기 위한 값이다
    • client-query-buffer-limit 으로 조정한다
클라이언트 종류하드 제한소프트 제한소프트 유지 시간
normal (일반)0 (무제한)00
pubsub32MB8MB60초
replica (복제본)256MB64MB60초

하드 제한은 넘는 순간 연결을 끊고, 소프트 제한은 그 크기를 지정 시간 동안 계속 유지할 때 끊는다. 일반 클라이언트가 무제한인 이유는 요청-응답 패턴에서는 버퍼가 자연히 비워지기 때문이다. 반대로 pub/sub 과 복제본은 서버가 일방적으로 밀어 넣는 구조라 제한이 필요하다.

Pub/Sub 제한
  • 하드 제한 : 32MB
  • 소프트 제한 : 60초 동안 8MB
복제본 제한
  • 하드 제한 : 256MB
  • 소프트 제한 : 60초 동안 64MB
  • 마스터로부터 대용량 데이터를 받아야 한다면 더 큰 출력 버퍼가 필요하다

복제가 무한 루프에 빠지는 전형적인 시나리오

전체 동기화 중에 복제본용 출력 버퍼가 한계를 넘으면 마스터가 연결을 끊는다. 복제본은 다시 붙어 전체 동기화를 시작하고, 또 넘고, 또 끊긴다. 데이터가 큰 인스턴스에서 client-output-buffer-limit replica 를 넉넉히 잡아야 하는 이유다.

제한 변경하기
  • CONFIG SET 으로 변경할 수 있다

클라이언트 이빅션(eviction)

  • 7 이전 버전에서는 클라이언트별 client-output-buffer-limit 으로만 개별 통제가 가능했다
  • 7 이후 버전에서는 maxmemory-clients 로 모든 클라이언트가 쓰는 메모리의 총합을 관리한다
    • 임계치에 도달하면 메모리를 가장 많이 쓰는 클라이언트부터 커넥션을 끊는다
!

원문 보완 원문 교정

노트에는 "7 이전에는 maxmemory-policy 로 관리"라고 되어 있으나, maxmemory-policy 는 데이터 키의 이빅션 정책이지 클라이언트 메모리와는 관계가 없다. 7 이전에는 클라이언트 하나하나에 대한 client-output-buffer-limit 만 있었고 총합을 제한할 방법이 없었다. 7.0 의 maxmemory-clients 가 그 총합 제한을 추가한 것이다. 기본값은 0(비활성)이다. (근거: redis.conf)

maxmemory-clients 설정
  • redis.conf 또는 CONFIG SET 으로 설정한다
  • 복제본에 연결된 마스터/복제본 커넥션은 이 설정의 영향을 받지 않는다
  • 특정 클라이언트만 이빅션 대상에서 빼려면 그 커넥션에서 CLIENT NO-EVICT ON 을 실행한다
  • 대용량 트래픽 환경에서는 5~10% 사이 값을 권장한다
redis.conf
# 클라이언트가 쓸 수 있는 메모리 총합을 1GB로 제한
maxmemory-clients 1G

# maxmemory 의 5% 까지 허용
maxmemory-clients 5%

# 기능 미사용 (기본값)
maxmemory-clients 0

Timeout, TCP Keepalive

Timeout
  • 설정한 초 동안 아무 요청이 없는 클라이언트의 커넥션을 끊는다
  • CONFIG SET timeout <초> 로 설정한다 (기본값 0, 즉 끊지 않음)
TCP Keepalive
  • 주기적으로 TCP ACK 를 보내고 응답이 없으면 연결을 정리한다
  • 클라이언트가 정상적으로 응답할 수 있는 상태인지를 먼저 확인하고 끊는 방식이다
  • 기본적으로 300초(5분) 마다 신호를 보낸다
i

둘 중에는 keepalive 쪽 보강

timeout 은 유휴 커넥션을 무조건 끊으므로, 커넥션 풀이 조용히 잡고 있던 커넥션까지 잘라 애플리케이션에서 간헐적인 에러를 만든다. 반면 tcp-keepalive 는 실제로 죽은 상대만 정리한다. 특별한 이유가 없다면 timeout 0 을 두고 keepalive 에 맡기는 편이 안전하다.

정리

  • 클라이언트마다 출력 버퍼와 쿼리 버퍼가 붙는다. 커넥션 수 자체가 메모리 사용량이다.
  • 출력 버퍼 기본 제한은 pubsub 32MB/8MB/60s, replica 256MB/64MB/60s. 큰 인스턴스는 replica 값을 키워야 복제가 안정된다.
  • 7.0 의 maxmemory-clients 는 클라이언트 메모리 총합을 제한한다. 기본값은 비활성(0).
  • 유휴 커넥션 정리는 timeout 보다 tcp-keepalive(기본 300초)에 맡기는 편이 안전하다.
12-2

파이프라이닝

레디스가 느린 게 아니라 왕복이 잦은 것이었다는 걸 확인하는 기능.

핵심 커맨드 100개를 따로 보내면 네트워크 왕복도 100번이다. 파이프라이닝은 그것을 왕복 1번으로 줄인다. 서버 성능이 아니라 왕복 횟수를 줄이는 최적화다.
  • 레디스가 아무리 빨라도 네트워크 지연이 크면 처리량이 떨어진다
  • 파이프라이닝으로 여러 쿼리를 한 번에 보내면 성능이 크게 향상된다
  • 연속된 여러 커맨드를 한 번에 보낼 수 있는 기능이다
    • 커맨드마다 네트워크를 왕복하지 않고 일괄 처리하므로 응답 시간을 줄이고 처리량을 높인다
줄어드는 것은 서버의 처리 시간이 아니라 대기 시간이다 — 커맨드가 100개면 왕복도 100번이고, 왕복당 1ms 라면 그것만으로 100ms 다. 서버가 실제로 일한 시간은 그중 극히 일부다.

주의점

  • 한 번에 너무 많이 묶으면 네트워크 대역폭 한계와 쿼리 버퍼 제한 때문에 에러가 날 수 있다
  • 여러 커맨드를 파이프라이닝할 때는 일정한 개수로 나누어 배치 처리하는 편이 좋다

서버 쪽에서도 응답이 모두 쌓일 때까지 출력 버퍼를 붙들고 있으므로, 파이프라인이 지나치게 길면 12-1 의 출력 버퍼 제한에 걸린다. 보통 수백에서 수천 개 단위로 끊는다.

원자성

  • 파이프라이닝은 원자성을 보장하지 않는다
  • 트랜잭션처럼 동작하지 않으므로, 오류가 난 커맨드 외의 나머지는 모두 정상 실행된다
!

파이프라이닝과 MULTI/EXEC 는 다른 것을 해결한다

파이프라이닝은 왕복 횟수를 줄이고, MULTI/EXEC 는 중간에 다른 클라이언트가 끼어들지 못하게 한다. 파이프라인으로 보낸 커맨드들 사이에는 다른 클라이언트의 커맨드가 얼마든지 실행될 수 있다. 둘 다 필요하다면 MULTI/EXEC 자체를 파이프라인에 담아 보내면 된다.

정리

  • 파이프라이닝은 네트워크 왕복 횟수를 줄이는 최적화다. 지연이 클수록 효과가 크다.
  • 너무 크게 묶으면 쿼리 버퍼와 출력 버퍼에 걸린다. 수백~수천 단위로 배치를 나눈다.
  • 원자성은 없다. 격리가 필요하면 MULTI/EXEC 를 함께 쓴다.
12-3

클라이언트 사이드 캐싱

캐시 앞에 또 캐시를 둔다. 문제는 그 캐시가 언제 틀렸는지 아는 방법이다.

핵심 클라이언트 캐시의 어려움은 저장이 아니라 무효화다. 레디스는 서버가 무효화 메시지를 보내 주는 방식(트래킹)으로 이 문제를 푼다.
  • RDB 성능도 최적화하고 캐시까지 도입했는데 만족스럽지 않을 때 고려할 수 있다
  • 클라이언트 쪽에서 데이터를 로컬에 캐싱하고 그 데이터를 활용하는 방법이다
  • 데이터셋의 아이템이 자주 변경되지 않을 때 유용하다
  • 변경된 데이터를 어떻게 처리할지 고려해야 하며, 레디스는 이를 트래킹이라 부른다
  • 자주 요청되지만 드물게 변경되는 키를 잘 고르는 것이 중요하다

캐싱 모드

기본 모드
  • 레디스가 클라이언트가 접근한 키를 기억해 두었다가, 그 키가 수정되면 무효화 메시지를 보낸다
  • 서버에 메모리 비용이 들지만, 클라이언트가 실제로 들고 있는 키에 대해서만 정확히 무효화를 보낼 수 있다
브로드캐스팅 모드
  • 접근한 키를 모두 기억하지 않고 특정 prefix 만 기억한다
  • 서버 메모리 사용량이 적지만, 클라이언트는 자신이 어떤 키를 들고 있는지 스스로 알아야 한다
  • 그 prefix 에 속한 키가 하나라도 바뀌면 관심 없는 변경까지 모두 수신하게 되고, 그만큼 CPU 를 더 쓴다
구분기본 모드브로드캐스팅 모드
서버가 기억하는 것클라이언트별 접근 키 목록등록된 prefix 목록
서버 메모리많이 든다거의 안 든다
무효화 정확도정확하다불필요한 알림 포함
유리한 상황캐싱 대상이 흩어져 있을 때키 이름 규칙이 뚜렷할 때
i

RESP3 가 전제다 보강

무효화 메시지를 같은 커넥션으로 받으려면 Redis 6 의 RESP3 프로토콜이 필요하다(HELLO 3 후 CLIENT TRACKING ON). RESP2 클라이언트라면 무효화 알림을 받을 별도의 pub/sub 커넥션을 만들고 REDIRECT 옵션으로 그 커넥션 ID 를 지정해야 한다. 즉 이 기능은 클라이언트 라이브러리의 지원 여부를 먼저 확인해야 쓸 수 있다.

정리

  • 클라이언트 사이드 캐싱은 자주 읽고 드물게 바뀌는 키에서만 이득이다.
  • 기본 모드는 서버가 키를 기억해 정확히 무효화하고, 브로드캐스팅 모드는 prefix 만 기억해 메모리를 아끼는 대신 과도한 알림을 감수한다.
  • RESP3(또는 RESP2 + REDIRECT) 지원이 필요하므로 클라이언트 라이브러리 확인이 먼저다.

레디스 운영하기

마지막 챕터는 실전이다. 무엇을 그래프로 띄워 두고, 어떤 설정이 장애를 부르고, 어떤 커맨드를 운영 중에 쓰면 안 되는지 — 사고를 겪기 전에 알아둘 것들.

13-1

레디스 모니터링 구축하기

EOL 이 짧은 소프트웨어를 오래 쓰는 방법 — 무중단으로 올리는 순서를 알아 두는 것.

핵심 HA 구성(센티널/클러스터)의 진짜 가치는 장애 대응만이 아니라 다운타임 없는 업그레이드다. 복제본부터 올리고, 페일오버로 역할을 바꾸고, 마지막에 옛 마스터를 올린다.

Prometheus, Grafana 를 이용한 레디스 모니터링

  • Exporter 를 사용해 메트릭을 수집할 수 있다
  • Grafana 의 Redis 플러그인을 사용하는 방법도 있다
i

Node Exporter 와 Redis Exporter 보강

둘은 수집 대상이 다르다. Node Exporter 는 호스트의 CPU/메모리/디스크를, Redis Exporter 는 INFO 커맨드로 얻는 레디스 내부 지표(used_memory, connected_clients, keyspace_hits, master_repl_offset 등)를 가져온다. 뒤의 13-2 에서 보는 지표들은 대부분 후자에서 나오므로 둘 다 필요하다.

레디스 버전 업그레이드

  • 레디스는 릴리스 주기가 빠른 편이고 EOL(End of Life)도 상당히 짧다
  • 취약점 등 보안을 고려해 주기적으로 버전을 올리는 것이 좋다
  • 센티널이나 클러스터로 HA 를 구성했다면 무중단이 가능하지만, 싱글 구성은 다운타임이 생긴다
운영 중인 레디스 업그레이드
  • 신규 버전을 새 서버에 설치하고 데이터를 복제하는 방법
    • 접속 정보를 바꿔야 하므로 다운타임이 존재한다
  • 인스턴스를 중지하고 신규 버전으로 다시 실행하는 방법
    • 단일 인스턴스라면 그 시간만큼 다운타임이 존재한다

센티널 구성의 레디스 버전 업그레이드

i

원문에 내용이 없어 공식 문서 기준으로 보강 보강

노트에는 제목만 있고 본문이 비어 있어, 공식 문서에 근거해 정리했다. 핵심은 복제본을 먼저 올리고, 페일오버로 역할을 바꾼 뒤, 옛 마스터를 올린다는 순서다.

  1. 복제본을 하나씩 업그레이드한다

    중지할 때는 SHUTDOWN 으로 안전하게 내린다. 이렇게 종료하면 복제 정보가 RDB 에 함께 저장되어, 재시작 후 전체 재동기화 없이 부분 재동기화로 따라잡을 수 있다.

  2. 복제본이 마스터를 따라잡았는지 확인한다

    INFO REPLICATION 의 offset 이 마스터와 맞는지 본 뒤 다음 노드로 넘어간다.

  3. 수동 페일오버로 마스터를 교체한다

    SENTINEL FAILOVER <master-name> 으로 이미 업그레이드된 복제본을 마스터로 승격시킨다.

  4. 복제본이 된 옛 마스터를 업그레이드한다

    이제 이 노드는 트래픽의 주 경로가 아니므로 부담 없이 재시작할 수 있다.

  5. 센티널 프로세스도 하나씩 올린다

    센티널은 여러 대이므로 한 번에 하나씩 재시작하면 감시 공백이 생기지 않는다.

!

AOF 로 재시작하면 부분 재동기화가 안 된다

공식 문서에 따르면 AOF 파일로 재시작한 복제본은 부분 재동기화를 할 수 없다. 큰 인스턴스에서 이 차이는 크다. 필요하다면 재시작 전에 잠시 RDB 방식으로 바꿔 두었다가, 올라온 뒤 AOF 를 다시 켜는 방법이 있다.

클러스터 구성의 레디스 버전 업그레이드

  1. 복제본 노드부터 하나씩 업그레이드한다

    복제본은 슬롯을 담당하지 않으므로 재시작해도 서비스에 영향이 없다.

  2. 업그레이드된 복제본에서 CLUSTER FAILOVER 를 실행한다

    수동 페일오버는 복제본이 마스터를 따라잡을 때까지 기다린 뒤 역할을 바꾸므로 데이터 유실이 없다. (10-3 참고)

  3. 복제본이 된 옛 마스터를 업그레이드한다
  4. 모든 샤드에 대해 위 과정을 반복한다

    한 번에 한 샤드씩 진행하고, 각 단계마다 redis-cli --cluster check 로 상태가 정상인지 확인한다.

정리

  • Node Exporter(호스트)와 Redis Exporter(INFO 지표)를 함께 붙여야 그림이 완성된다.
  • 무중단 업그레이드의 원칙 — 복제본 먼저, 그다음 수동 페일오버, 마지막에 옛 마스터.
  • 복제본은 SHUTDOWN 으로 내려야 재시작 후 부분 재동기화가 가능하다. AOF 로 재시작하면 그 이점이 사라진다.
  • 클러스터에서는 CLUSTER FAILOVER 가 무손실 전환을 보장하므로 샤드마다 반복하면 된다.
13-2

레디스 운영 가이드

장애를 부르는 설정, 서버를 멈추는 커맨드, 그리고 그래프에서 먼저 봐야 할 네 가지.

핵심 레디스 장애의 대부분은 싱글 스레드를 오래 붙잡는 커맨드와 메모리 한계 두 가지에서 나온다. 운영이란 이 둘을 미리 감시하는 일이다.

장애와 성능 저하를 일으키는 설정 항목

maxmemory-policy
  • 메모리가 가득 찼을 때 어떤 키를 제거할지에 대한 설정
  • 기본값 noeviction 은 더 이상 저장할 수 없다는 에러를 낸다. 캐시 용도라면 5-1 의 표를 보고 반드시 바꿔야 한다
stop-writes-on-bgsave-error
  • RDB 스냅숏 생성에 실패하면 모든 쓰기 작업을 중단시키는 설정 (기본값 yes)
  • 최신 백업이 실패했음을 강하게 알려 더 큰 장애를 막으려는 의도다
  • 다만 모니터링으로 이미 식별할 수 있다면, 쓰기를 계속 받기 위해 꺼 둘 수도 있다

이 옵션이 켜진 채 디스크가 차면

디스크가 가득 차 BGSAVE 가 실패하는 순간, 레디스는 모든 쓰기를 거부하기 시작한다. 캐시로 쓰던 인스턴스라면 갑자기 전체 서비스가 쓰기 에러를 내는 상황이 된다. 디스크 여유 공간 알람과 이 설정은 세트로 관리해야 한다.

자동 백업 옵션
  • AOF, RDB 모두 BGSAVE(fork)로 동작할 때 메모리 사용량이 2~3배로 늘 수 있다 (7-4 참고)
  • 가능하면 트래픽이 한가한 시간대에 수행되도록 설정하는 것이 좋다

레디스 운영 및 성능 최적화

오래 걸리는 커맨드 사용
  • 레디스는 싱글 스레드로 커맨드를 처리하므로 O(N) 이상의 커맨드는 지양하는 것이 좋다

대표적인 것들이 KEYS, FLUSHALL(동기), 큰 컬렉션에 대한 HGETALL/SMEMBERS/LRANGE 0 -1, 큰 키에 대한 DEL, 그리고 SORT 다. 각각 SCAN 계열, ASYNC, HSCAN 계열, UNLINK 로 바꿀 수 있다.

레디스에서 트랜잭션
  • 싱글 스레드로 동작하기 때문에 주의해서 써야 한다
    • 트랜잭션이 실행되는 동안 다른 요청은 모두 블로킹된다
    • 트랜잭션 안에서 BRPOP, BLPOP 은 블로킹하지 않는다
  • 트랜잭션을 위한 두 가지 방법을 제공한다
!

원문 보완 원문 교정

노트에는 트랜잭션 안에서 BRPOP/BLPOP 을 "쓸 수 없다"고 되어 있으나, 정확히는 쓸 수는 있으나 기다리지 않는다. 리스트가 비어 있으면 즉시 nil 을 반환하며 이는 타임아웃이 지난 것과 같은 동작이다. 자세한 내용은 6-3 참고. (근거: Redis Docs — BLPOP)

MULTI / EXEC
  • MULTI 로 트랜잭션을 열고 EXEC 로 실행한다
  • 사이에 넣은 커맨드는 실행되지 않고 QUEUED 로 쌓였다가 EXEC 시점에 한꺼번에 실행된다
redis-cli
127.0.0.1:6379> multi
OK
127.0.0.1:6379(TX)> incrby money 100
QUEUED
127.0.0.1:6379(TX)> rpush log "입금 100"
QUEUED
127.0.0.1:6379(TX)> exec
1) (integer) 200
2) (integer) 1
!

레디스의 트랜잭션에는 롤백이 없다

EXEC 도중 어떤 커맨드가 실패해도 나머지는 그대로 실행되고 되돌아가지 않는다. 레디스가 보장하는 것은 원자성 중 "중간에 끼어들지 않는다"는 격리 쪽이지 "전부 아니면 전무"가 아니다. 다만 큐잉 단계에서 문법 오류가 발견되면 EXEC 자체가 거부된다.

루아 스크립트
  • 레디스 내부에서 원자적으로 실행된다
  • 여러 커맨드를 한 번에 수행할 수 있고 중간에 다른 요청을 받지 않아 트랜잭션처럼 쓸 수 있다
  • 원자성을 가지지만 중간에 커맨드가 실패해도 다음 줄로 넘어가며 롤백은 되지 않는다

다만 MULTI/EXEC 와 달리 이전 커맨드의 결과를 보고 분기할 수 있다는 점이 결정적인 차이다. "값이 있으면 지우고 없으면 만든다" 같은 조건부 로직은 루아로만 원자적으로 구현할 수 있다.

has-get / has-del 패턴
  • 미리 EXISTS 로 확인한 뒤 데이터를 가져오거나 삭제하는 패턴을 말한다
  • 네트워크 왕복을 늘리고 불필요한 작업이 따라붙으므로 지양하는 것이 좋다

게다가 확인과 실행 사이에 다른 클라이언트가 끼어들 수 있어 정확하지도 않다. GET 은 없으면 nil 을 돌려주고 DEL 은 지운 개수를 돌려주므로, 그냥 실행하고 반환값으로 판단하면 된다.

클라이언트 출력 버퍼 사이즈
  • 클라이언트가 응답을 받을 때 일시적으로 담아 두는 공간이다
  • 속도 차이나 부하로 인한 버퍼 오버플로를 방지해 안정적인 통신을 보장한다
  • 대용량 데이터나 많은 커맨드를 쓰면 오버플로가 발생할 수 있다
  • 복제를 사용한다면 복제본용 버퍼 크기를 반드시 늘려 줘야 한다 (12-1 참고)
키스페이스 알림 기능을 사용한 키 만료 모니터링
  • 키의 변경 사항을 내부 pub/sub 채널로 발행해 구독할 수 있게 하는 기능이다
  • notify-keyspace-events 옵션으로 어떤 이벤트를 받을지 지정한다 (기본값은 빈 문자열, 즉 비활성)
!

만료 알림은 "만료 시각"이 아니라 "삭제 시점"에 온다

5-1 에서 본 대로 만료된 키는 접근되거나 active 사이클에 걸릴 때 삭제된다. expired 이벤트는 그 삭제 시점에 발행되므로 TTL 이 끝나는 순간과 시차가 있다. 정확한 타이밍이 필요한 스케줄링에 이 기능을 쓰면 안 된다. 또한 pub/sub 기반이라 구독 중이 아니면 알림은 그냥 사라진다.

특정 prefix 를 가진 키 삭제
  • 레디스가 기본으로 제공하지 않는 기능이라 애플리케이션에서 처리해야 한다
  • 루아 스크립트로 처리하면 네트워크 부하를 줄일 수 있다

이때도 KEYS pattern 이 아니라 SCAN 으로 나눠 훑고, 모아서 UNLINK 하는 형태여야 한다. 루아 안에서 KEYS 를 부르면 그 스크립트가 실행되는 동안 서버 전체가 멈춘다.

레디스 모니터링

슬로우 로그
  • 응답 시간이 길어진 커맨드를 기록하는 로그다
  • CLI 에서 SLOWLOG GET 으로 확인한다
  • slowlog-log-slower-than 옵션에 지정한 시간보다 오래 걸리면 기록한다
  • slowlog-max-len 으로 저장할 로그 개수를 지정한다 (기본값 128)
!

원문 교정 원문 교정

노트에는 slowlog-log-slower-than 의 기본값이 "10초"라고 되어 있으나, 이 값의 단위는 마이크로초이고 기본값 10000 은 10밀리초다. 1000배 차이라 그냥 넘기면 "슬로우 로그가 텅 비어 있으니 문제없다"는 잘못된 안심으로 이어진다. 참고로 음수를 주면 슬로우 로그가 비활성화된다. (근거: redis.conf)

redis-cli
127.0.0.1:6379> slowlog get
(empty array)

기록되는 시간에는 네트워크 왕복과 I/O 대기가 포함되지 않는다. 순수하게 커맨드를 실행한 시간만 재므로, 여기 걸린 항목은 예외 없이 서버 안에서 오래 걸린 진짜 문제다.

그래프 지표

CPU
  • 커맨드를 실행하는 동안은 싱글 스레드로 동작하지만, 백업이나 파일 저장 같은 백그라운드 작업은 다른 CPU 를 쓸 수 있다
메모리
  • 가장 핵심적인 지표 중 하나이며 주의 깊게 봐야 한다
  • used_memory 는 레디스가 논리적으로 사용 중인 메모리다
  • 메모리 사용률이 100% 에 도달하면 이빅션이 발생한다
    • 이때 CPU 사용량이 과도하게 올라갈 수 있으니 주의가 필요하다
  • 항상 데이터의 TTL 을 적절히 지정하는 것이 좋다
  • used_memory_rss 는 OS 가 레디스에 실제로 할당한 물리 메모리다
    • 논리 메모리보다 물리 메모리가 크게 벌어지면 단편화 문제가 있을 수 있다
    • 대표적인 원인은 키가 갑자기 몰렸다가 삭제되거나 이빅션이 많이 발생한 경우다
    • activedefrag yes 로 단편화가 잦을 때 최적화할 수 있다. 필수는 아니다
i

단편화율은 1 근처가 정상이다 보강

INFO MEMORY 의 mem_fragmentation_ratio 는 used_memory_rss / used_memory 다. 1.0~1.5 정도가 보통이고, 1.5 를 넘으면 단편화를 의심한다. 반대로 1 미만이면 OS 가 레디스 메모리를 스왑으로 내렸다는 뜻이라 훨씬 위험한 신호다. 참고로 노트에 나오는 DatabaseMemoryUsagePercentage 는 레디스 자체 지표가 아니라 AWS ElastiCache 의 CloudWatch 메트릭 이름이다.

네트워크
  • 레디스는 더 많이 처리할 수 있는데도 네트워크 대역폭 때문에 느린 것처럼 보일 수 있다
  • 복제, 클러스터 등 다양한 방법으로 최적화할 수 있다
커넥션
  • 레디스에 연결된 클라이언트 커넥션 수를 모니터링한다
  • 애플리케이션 장애로 급격히 치솟을 수 있다
  • timeout 대신 tcp-keepalive 를 쓰면 CPU 사용량이 조금 더 들 수 있으므로 커넥션 풀링이 중요하다
복제
  • 복제 지연은 복제본이 마스터의 데이터를 따라잡지 못하는 상태를 뜻한다
  • 복제 지연이 발생하면 원인을 빠르게 파악해 해결하는 것이 좋다

구체적으로는 INFO REPLICATION 의 master_repl_offset 과 각 복제본의 offset 차이를 재면 된다. 이 값이 계속 벌어지면 백로그를 넘겨 전체 재동기화가 일어나고, 그 순간 마스터에 fork 부담까지 겹친다.

정리

  • 장애를 부르는 설정 세 가지 — maxmemory-policy 기본값, stop-writes-on-bgsave-error, 트래픽 피크와 겹친 자동 백업.
  • 트랜잭션에는 롤백이 없다. 조건부 로직이 필요하면 루아, 격리만 필요하면 MULTI/EXEC.
  • slowlog-log-slower-than 의 단위는 마이크로초이며 기본값 10000 은 10ms 다.
  • 메모리는 used_memory 와 used_memory_rss 를 함께 본다. 비율 1.5 초과는 단편화, 1 미만은 스왑 신호다.
  • 복제 지연은 offset 차이로 감시한다. 방치하면 전체 재동기화로 번진다.
