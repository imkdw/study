시작하기 전에

왜 지금 컨테이너인가. 가상 머신과 무엇이 다르고, 클라우드 이주에서 IaaS/PaaS 사이의 어느 자리를 차지하는지부터 잡는다.

ITEM 1-1

컨테이너가 IT 세상을 점령한 이유

IaaS 의 이식성과 PaaS 의 운영비 절감, 둘 중 하나를 고르지 않아도 되게 만든 것이 컨테이너다.

핵심 도커는 앱을 패키징하는 방식을 표준화한다. 그 표준 하나로 클라우드 이주, 레거시 현대화, 신규 개발, CI 파이프라인이 전부 같은 도구를 쓰게 된다.

도커란

  • 도커는 컨테이너라는 경량 단위로 애플리케이션을 실행하는 플랫폼이다.
  • 최근에는 소프트웨어 산업에서 개발과 운영 양쪽 모두에 반드시 익혀야 하는 핵심 기술로 인식되고 있다.

앱을 개발하고 빌드하고 배포하는 과정은 규모가 커질수록 까다로워진다. 도커를 쓰면 이 과정이 명령어 한 줄로 압축된다.

가상 머신과 무엇이 다른가

컨테이너를 이해하는 가장 빠른 길은 가상 머신과 나란히 놓고 보는 것이다. 둘 다 "호스트명, IP, 디스크를 독립적으로 갖는 격리된 실행 환경"을 제공한다는 목적은 같다. 다른 것은 격리를 만들어 내는 층이다.

컨테이너는 게스트 OS 한 겹을 통째로 걷어낸다 — 둘 다 호스트명 / IP / 디스크를 독립적으로 갖지만, VM 은 그것을 위해 OS 를 하나 더 부팅하고 컨테이너는 호스트 커널을 공유한다. 여기서 기동 속도와 밀도 차이가 나온다.

클라우드 환경으로 이주하기

기존 온프레미스 환경에서 클라우드로의 이주는 거의 모든 조직의 최우선 관심사다. 장비실에서 전문 인력이 직접 관리하던 일을 구글 / MS / 아마존에 맡길 수 있게 됐기 때문이다. 도커 이전의 이주 경로는 두 갈래였다.

방식앱 컴포넌트가 사는 곳얻는 것잃는 것
IaaS
Infrastructure as a Service		 가상 머신 특정 클라우드에 종속되지 않음 VM 을 그대로 옮기므로 운영비가 많이 나옴
PaaS
Platform as a Service		 클라우드의 매니지드 서비스 운영비 절감 특정 클라우드에 종속되어 이식성 하락
Docker
권장		 컨테이너 IaaS 의 독립성 + PaaS 의 운영비 절감 컨테이너용 스크립트 작성 등 초기 비용이 든다

레거시 애플리케이션 현대화하기

  • 기존에 자주 쓰던 모놀리식 방식으로는 도커와 클라우드 플랫폼의 진가가 발휘되기 어렵다.
  • 도커로 이주하는 과정은 앱의 낡은 설계를 탈바꿈하는 첫걸음이다.
  • 컴포넌트를 컨테이너 단위로 쪼개서 배포하면 외부에 공개되지 않은 네트워크를 통해 통신할 수 있다.
  • 덕분에 기능별로 빠른 배포 주기를 가져가는 등 MSA 의 장점을 누릴 수 있다.

클라우드 환경에 적합한 새로운 앱 개발하기

  • 분산 앱이든 모놀리식 앱이든 도커를 쓰면 어디서든 배포하고 운영할 수 있다.
  • 여러 개의 프로그래밍 언어로 각 분야에 알맞은 API 를 구성할 수 있다.
  • 모든 컴포넌트는 공통적으로 Dockerfile 로 패키징되고 Docker Compose 형태로 전체 앱이 정의된다.
  • 다시 말해 컴포넌트별로 별도의 개발 도구를 갖추지 않아도 도커 하나로 전부 가능하다는 뜻이다.

기술 혁신 — 서버리스와 그 너머

  • 현대 IT 기술을 주도하는 요소 중 하나는 일관성이다.
  • 개발팀은 모든 프로젝트에서 같은 도구 / 프로세스 / 런타임을 쓰고 싶어 하는데, 도커를 통해 그게 가능해진다.
  • 컨테이너 도입 이후 마주할 가장 흥미로운 기술 혁신은 서버리스 함수다.
  • 서버리스도 결국 컨테이너 기술이다. 함수 코드를 작성해 서비스에 푸시하면 서비스가 코드를 빌드하고 패키징한다.
  • 단점은 아직 개방형 표준이 없어서 이식성이 떨어진다는 점이다.

함께 알아두기 보강

"서버리스에 개방형 표준이 없다"는 서술은 지금도 상당 부분 유효하지만, 그사이 컨테이너 이미지를 그대로 서버리스로 굴리는 경로가 표준화됐다. AWS Lambda 의 컨테이너 이미지 지원, Google Cloud Run, Azure Container Apps 가 모두 OCI 이미지를 입력으로 받는다. 즉 이식성의 단위가 함수 코드에서 이미지로 옮겨 오면서 종속 위험이 예전보다는 줄었다.

데브옵스(DevOps) 도입하기

  • 기민한 소프트웨어 유지보수를 위해 앱의 전체 라이프사이클을 담당하는 전담 팀을 뜻한다.
  • 이름 그대로 개발(Dev) + 운영(Ops) 을 합친 개념이다.

정리

  • 컨테이너는 게스트 OS 한 겹을 걷어내고 호스트 커널을 공유한다. VM 과 같은 격리를 훨씬 싸게 얻는 방법이다.
  • 클라우드 이주에서 IaaS 는 이식성을, PaaS 는 운영비를 챙긴다. 도커는 그 사이에서 둘 다 챙기는 선택지다.
  • 도커의 진짜 이점은 성능이 아니라 일관성이다. 개발 / CI / 운영이 전부 같은 이미지, 같은 명령어를 쓴다.
  • 모놀리식을 그대로 컨테이너에 넣는 것만으로도 현대화의 첫 단추는 꿴 셈이다.

ITEM 2-1

함께 알아두기 보강

docker container run 은 사실 두 명령의 합성이다. 이미지가 없으면 docker image pull, 그다음 컨테이너를 만드는 docker container create, 마지막으로 docker container start. 뒤에 나올 docker container start --attach 로 같은 컨테이너를 다시 살릴 수 있는 것도 이 때문이다.

정리

  • docker container run <이미지> 는 "없으면 받아서, 컨테이너 만들고, 실행한다"를 한 번에 한다.
  • 이미지는 Pull complete 줄 수만큼의 레이어로 쪼개져 내려온다.
  • 컨테이너는 자기만의 호스트명과 IP 를 갖지만, 커널은 호스트 것을 그대로 쓴다.
ITEM 2-3

컨테이너를 원격 컴퓨터처럼 사용하기

컨테이너에 들어가서 셸을 쓰고, 밖에서 프로세스 / 로그 / 상세 정보를 들여다보는 네 가지 명령.

핵심 컨테이너 조회 명령은 전부 ID 앞글자만 입력해도 패턴 매칭으로 동작한다. docker top 84 처럼 두 글자면 충분하다.

--interactive 플래그

  • --interactive 플래그를 쓰면 컨테이너에 접속한 상태로 실행할 수 있다.
  • 도커가 구동 중인 환경에 따라 프롬프트가 다르지만, 컨테이너 내부에서는 동일한 명령어를 쓸 수 있다.
  • 아래 예시에서는 hostname, date 로 호스트명과 날짜를 확인한다.
terminal 
$ docker run --interactive --tty diamol/base

716aca3e500c: Pull complete
Digest: sha256:787fe221a14f46b55e224ea0436aca77d345c3ded400aaf6cd40125e247f35c7
Status: Downloaded newer image for diamol/base:latest
/ # hostname
840925fb1055
/ # date

/ #

함께 알아두기 보강

941f399634ec: Already exists 를 놓치지 말자. 앞의 ch02-hello-diamol 과 diamol/base 가 같은 기반 레이어를 공유하고 있어서 다시 내려받지 않은 것이다. 이미지 레이어가 왜 읽기 전용이어야 하는지는 3-4 에서 이어진다.

docker container ls

  • 현재 실행 중인 모든 컨테이너의 정보를 확인할 수 있다.
  • 컨테이너의 바탕이 된 이미지, 컨테이너 ID 등이 출력된다. 컨테이너 ID 는 실행할 때마다 무작위로 생성된다.
  • --all 플래그를 붙이면 실행 상태와 상관없이 모든 컨테이너 목록을 볼 수 있다.
terminal 
$ docker container ls

CONTAINER ID   IMAGE         COMMAND     CREATED              STATUS              PORTS     NAMES
840925fb1055   diamol/base   "/bin/sh"   About a minute ago   Up About a minute             reverent_bhaskara

docker top <container_id>

  • 특정 컨테이너에서 실행 중인 프로세스 목록을 보여준다.
  • 패턴 매칭 방식이라 컨테이너 ID 의 앞글자만 입력해도 된다. 여러 개가 매칭되면 매칭된 모든 컨테이너의 프로세스를 출력한다.
terminal 
$ docker top 84

PID                 USER                TIME                COMMAND
7979                root                0:00                /bin/sh
i

함께 알아두기 보강

여기 찍힌 PID 7979 는 호스트에서 본 번호다. 컨테이너 안에서 ps 를 치면 같은 프로세스가 PID 1 로 보인다. 같은 프로세스를 PID 네임스페이스 안팎에서 각각 다른 번호로 보는 것이고, 이것이 "컨테이너는 격리된 프로세스일 뿐"이라는 말의 실체다.

docker logs <container_id>

  • 대상 컨테이너에서 수집된 모든 로그를 출력한다.
  • 실제 앱이 구동되는 컨테이너에서는 앱이 출력하는 로그만 보인다.
terminal 
$ docker logs 84

/ # hostname
840925fb1055
/ # date
Sat Oct 26 04:04:15 UTC 2024

함께 알아두기 보강

도커가 수집하는 것은 PID 1 프로세스의 표준 출력/표준 에러뿐이다. 앱이 로그를 파일에 쓰도록 설정돼 있으면 docker logs 에는 아무것도 안 나온다. 컨테이너용 앱에서 로그를 stdout 으로 내보내는 게 관례가 된 이유가 여기 있다.

docker inspect <container_id>

  • 대상 컨테이너의 상세한 정보를 보여준다.
  • JSON 포맷으로 출력되며 상태, 네트워크 설정 등 앱에 일어난 문제를 추적하기 위해 일상적으로 쓴다.

원문 교정 원문 교정

노트에는 docker inspect 로 "CPU 사용량, 네트워크 상태"를 본다고 적혀 있지만, inspect 가 보여주는 것은 설정과 상태 스냅숏(경로, 마운트, 네트워크 설정, 헬스 상태 등)이지 실시간 리소스 사용량이 아니다. 실시간 CPU / 메모리 사용량은 docker stats 가 담당한다.

정리

  • --interactive --tty (줄여서 -it) 로 컨테이너 안에서 셸을 쓴다.
  • ls 는 목록, top 은 프로세스, logs 는 stdout, inspect 는 설정 스냅숏.
  • 컨테이너 ID 는 앞글자만 써도 되고, --all 없이는 종료된 컨테이너가 안 보인다.
ITEM 2-4

컨테이너를 사용해서 웹 사이트 호스팅하기

컨테이너 IP 로는 못 들어간다. 호스트 포트를 열어 도커가 트래픽을 넘겨줘야 들어갈 수 있다.

핵심 --publish 8088:80 은 "호스트의 8088 로 들어온 트래픽을 컨테이너의 80 으로 넘겨라"는 뜻이다. 공개하지 않은 컨테이너는 외부에서 IP 로 직접 찔러도 열리지 않는다.

모든 도커 컨테이너 확인하기

docker container ls --all 로 확인할 수 있다. 여기서 알아야 할 점이 두 가지 있다.

  1. 컨테이너 내부의 앱이 실행 중이어야 컨테이너도 실행이 유지된다

    종료된 컨테이너는 더 이상 CPU 나 메모리 자원을 사용하지 않는다.

  2. 컨테이너가 종료돼도 사라지지 않는다

    나중에 다시 실행하거나 로그를 확인하는 등의 작업이 가능하다. 다만 계속 남아 있어서 저장 공간을 차지한다.

컨테이너에서 간단한 웹 사이트 호스팅하기

  • --detach — 컨테이너를 백그라운드에서 실행하며 컨테이너 ID 를 출력하는 플래그
  • --publish — 컨테이너의 포트를 호스트 컴퓨터에 공개하는 플래그

$ docker run --detach --publish 8088:80 diamol/ch02-hello-diamol-web

컨테이너 포트를 호스트 컴퓨터에 공개하는 원리

  • 도커를 설치하면 호스트 컴퓨터의 네트워크 계층에 도커가 끼어든다.
  • 호스트를 드나드는 네트워크 트래픽을 도커가 가로채서, 필요한 것만 컨테이너에 전달한다.
  • 기본적으로 컨테이너는 외부에 노출되지 않으므로 외부에서 컨테이너 IP 로 직접 접근할 수 없다.
컨테이너 IP 는 호스트 안에서만 유효한 주소다 — 외부에서 닿을 수 있는 유일한 통로는 --publish 로 연 호스트 포트뿐이고, 그 앞에서 도커가 트래픽을 받아 컨테이너로 넘긴다.

  • 컨테이너의 리소스 사용 현황을 확인하는 명령이다.

실습 환경에서만 쓸 것

이 명령은 이 머신의 모든 컨테이너를 지운다. 실습용 컨테이너만 골라내려면 --filter 를 쓰는 편이 안전하다. 예를 들어 종료된 것만 지우려면 docker container prune, 특정 이름 패턴만 지우려면 docker rm -f $(docker ps -aq --filter "name=todo") 처럼 쓴다.

ITEM 2-5

도커가 컨테이너를 실행하는 원리

CLI 는 아무 일도 하지 않는다. REST API 를 호출할 뿐이고, 실제 작업은 엔진이 한다.

핵심 docker 명령은 API 클라이언트일 뿐이다. CLI 와 엔진이 API 로 분리돼 있기 때문에 Portainer 같은 다른 클라이언트도, 원격 호스트 제어도 같은 방식으로 가능해진다. 
flowchart TB
  CLI["docker CLI"] -->|"HTTP REST 호출"| API["Docker API"]
  OTHER["다른 클라이언트 (Portainer 등)"] -->|"같은 API"| API
  API --> ENG["Docker Engine (상시 데몬)"]
  ENG -->|"컨테이너 / 가상 네트워크 생성"| OS["호스트 OS"]
  ENG <-->|"없으면 내려받고 있으면 재사용"| CACHE["로컬 이미지 캐시"]
CLI → API → 엔진 순서로 흐른다 — CLI 를 통째로 다른 도구로 갈아 끼워도 아래 두 층은 그대로다. 엔진 설정을 바꾸면 이 API 를 네트워크 너머에서 호출하도록 열 수도 있다.

도커 엔진

  • 도커의 관리 기능을 담당하는 컴포넌트다.
  • 로컬 이미지 캐싱을 담당한다. 새 이미지가 필요하면 내려받고, 기존에 있으면 그대로 쓴다.
  • 호스트 OS 와 함께 컨테이너와 가상 네트워크 등 도커 리소스를 만드는 일도 담당한다.
  • 항시 동작하는 백그라운드 프로세스다.

도커 API

  • 표준 HTTP 기반 REST API 다.
  • 도커 엔진은 이 API 를 통해 맡은 기능을 수행한다.
  • 엔진 설정을 바꾸면 네트워크를 경유해 외부 컴퓨터에서 호출할 수 있는지를 제어할 수 있다.
!

주의 보강

도커 API 를 TCP 로 열 때는 인증 없이 열지 않는다. 도커 데몬은 사실상 호스트의 root 권한과 동등하므로, 인증 없는 2375 포트는 호스트를 통째로 넘겨주는 것과 같다. 원격 접근이 필요하면 TLS 로 상호 인증(2376)하거나 SSH 컨텍스트 (docker context create --docker "host=ssh://...")를 쓴다.

도커 CLI

  • 도커 API 의 클라이언트다.
  • 명령을 실행할 때 실제로 도커 API 를 호출하는 주체가 도커 CLI 다.

오픈소스인 도커 API

  • 도커는 모든 API 명세가 공개돼 있다.
  • 도커 CLI 외에도 다른 클라이언트(Portainer 등)를 쓸 수 있다.

정리

  • 구조는 CLI → API → 엔진 → OS 네 층이다. CLI 는 얇은 클라이언트일 뿐이다.
  • 엔진이 이미지 캐시를 관리한다. Already exists 가 뜨는 이유가 이것이다.
  • API 가 공개돼 있어 다른 UI 나 원격 제어가 붙을 수 있다. 반대로 함부로 열면 위험하다.
ITEM 2-6

연습문제 — 컨테이너 파일 시스템 다루기

실행 중인 컨테이너에 파일을 밀어 넣어 화면을 바꿔 본다. 그 변경이 어디에 저장되는지가 6장의 주제가 된다.

핵심 docker container cp 로 호스트의 파일을 실행 중인 컨테이너로 복사할 수 있다. 이 변경은 그 컨테이너에만 남고, 이미지에도 다른 컨테이너에도 영향을 주지 않는다.

문제 — 웹 사이트 컨테이너를 실행하고 index.html 파일을 교체해서 웹 페이지 내용을 수정하라. index.html 은 /usr/local/apache2/htdocs 에 위치한다.

기존 웹 사이트

이미지에 포함된 원래 index.html — 이 파일을 갈아 끼우는 게 이번 문제다.

풀이

1. 웹 사이트 컨테이너를 백그라운드로 실행
terminal 
$ docker run -d -p 8080:80 diamol/ch02-hello-diamol-web

b04b0fbe9e7eeb151111f80c4c1f5d8f1547878d036ce9f02cdc440342e9bd20
2. 새로운 index.html 파일을 해당 경로에 복사하기

docker exec 로 기존 파일을 먼저 확인할 수 있다.

terminal 
$ docker exec b04 ls /usr/local/apache2/htdocs
index.html

이후 로컬에서 index.html 을 만들고 위 경로에 복사한다.

terminal 
$ docker container cp index.html b04:/usr/local/apache2/htdocs/index.html
Successfully copied 2.05kB to b04:/usr/local/apache2/htdocs/index.html

파일 변경 후 웹 사이트

이미지는 그대로인데 화면만 바뀌었다 — 바뀐 파일은 이 컨테이너의 기록 가능 레이어에만 존재한다. 컨테이너를 지우면 원래 화면으로 돌아온다.
i

함께 알아두기 보강

같은 이미지로 컨테이너를 하나 더 띄워 보면 원래 화면이 그대로 나온다. 이 변경이 이미지가 아니라 컨테이너에 붙는다는 것을 눈으로 확인하는 가장 빠른 방법이다. 왜 그런지는 6-1 의 기록 가능 레이어와 기록 중 복사(copy-on-write)에서 이어진다.

정리

  • docker exec <id> <명령> 으로 실행 중인 컨테이너 안에서 명령을 돌릴 수 있다.
  • docker container cp 는 호스트 ↔ 컨테이너 양방향으로 파일을 복사한다.
  • 실행 중인 컨테이너의 파일 변경은 그 컨테이너에만 남는다. 이미지는 변하지 않는다.

ITEM 3-1

도커 허브에 공유된 이미지 사용하기

이미지는 논리적으로 하나지만 물리적으로는 여러 파일이다. 그리고 그 안의 환경 변수는 실행할 때 갈아 끼울 수 있다.

핵심 이미지에 박아 둔 ENV 값은 기본값일 뿐이다. --env 로 덮어쓰면 같은 이미지에서 서로 다르게 동작하는 컨테이너를 얼마든지 만들 수 있다.

도커 허브

  • 이미지를 제공하는 저장소를 레지스트리(registry) 라고 부른다.
  • 도커 허브는 무료로 제공되는 공개 레지스트리다.
  • docker pull 로 이미지를 내려받을 수 있다.

환경 변수(Environment Variable)

  • --name 을 붙이면 ID 대신 이름으로 컨테이너를 다룰 수 있다.
  • 이미지의 ENV 는 기본값, 실행 시 --env 가 그것을 덮는다. 이미지 하나로 여러 설정을 굴리는 출발점이다.
ITEM 3-2

Dockerfile 작성하기

인스트럭션을 위에서 아래로 실행한 결과가 이미지다. 다섯 개면 앱 하나를 패키징할 수 있다.

핵심 모든 이미지는 다른 이미지에서 출발한다(FROM). 나머지 인스트럭션은 그 위에 무엇을 얹고, 어디서 실행하고, 무엇을 실행할지를 적는 일이다.

Dockerfile 이란

  • 앱을 패키징하기 위한 간단한 스크립트다.
  • 일련의 인스트럭션으로 구성되며, 인스트럭션을 실행한 결과로 도커 이미지가 만들어진다.
Dockerfile 
FROM diamol/node

ENV TARGET="blog.sixeyed.com"
ENV METHOD="HEAD"
ENV INTERVAL="3000"

WORKDIR /web-ping
COPY app.js .

CMD ["node", "/web-ping/app.js"]

인스트럭션 뜯어보기

인스트럭션하는 일이 예제에서
FROM 어떤 이미지에서 출발할지 정한다. 모든 이미지는 다른 이미지에서 출발한다. Node.js 런타임이 포함된 diamol/node
ENV 환경 변수 값을 지정한다. [KEY]="[VALUE]" 형식으로 쓴다. ping 대상 / 메서드 / 간격의 기본값
WORKDIR 이미지 파일 시스템에 폴더를 만들고 작업 폴더로 지정한다. OS 와 무관하게 구분자는 슬래시(/)를 쓴다. 리눅스는 /web-ping, 윈도우는 C:\web-ping
COPY 로컬 파일/폴더를 이미지로 복사한다. [원본경로] [대상경로] 형식. app.js 를 작업 폴더로 복사
CMD 이미지로부터 컨테이너를 실행했을 때 돌릴 명령을 지정한다. Node.js 런타임으로 app.js 실행
i

함께 알아두기 보강

WORKDIR 은 단순한 cd 가 아니라 없으면 만들고 이동까지 한다. 그래서 RUN mkdir /web-ping 을 따로 쓸 필요가 없다. 또 COPY app.js . 의 . 은 현재 WORKDIR 을 가리키므로, WORKDIR 없이 쓰면 이미지 루트로 복사된다.

정리

  • FROM 으로 출발점을 정하고, 나머지 인스트럭션이 그 위에 쌓인다.
  • WORKDIR 은 폴더 생성 + 이동을 한 번에 한다. 이후 상대 경로의 기준점이 된다.
  • CMD 는 빌드 때 실행되지 않는다. 컨테이너를 실행할 때 쓰일 기본 명령을 적어 두는 것이다.
ITEM 3-3

빌드 컨텍스트를 좁혀야 하는 이유 보강

컨텍스트로 지정한 폴더는 통째로 빌더에 전송된다. 프로젝트 루트를 그대로 넘기면 node_modules, .git, 로컬 .env 까지 전송 대상이 된다. 전송이 느려지는 것도 문제지만, COPY . . 같은 줄과 만나면 그 파일들이 이미지에 그대로 실린다. .dockerignore 로 걸러 내는 습관이 필요하고, 이 이야기는 17-1 에서 본격적으로 다룬다.

정리

  • docker build --tag <이름> <컨텍스트> 가 기본형이다.
  • 컨텍스트 폴더 전체가 빌더에 전송된다. .dockerignore 로 좁히는 게 기본이다.
  • 내가 빌드한 이미지도 받아 온 이미지와 완전히 똑같이 다뤄진다.
ITEM 3-4

도커 이미지와 이미지 레이어 이해하기

핵심 레이어를 여러 이미지가 공유하기 때문에 레이어는 반드시 읽기 전용이어야 한다. 하나가 고쳐지면 그것을 공유하는 다른 모든 이미지가 함께 오염되기 때문이다.

원문 교정 — 히스토리 줄 수 ≠ 레이어 수 원문 교정

노트에는 "인스트럭션은 이미지 레이어와 1:1 관계"라고 적혀 있지만, 정확히는 인스트럭션은 docker image history 의 줄과 1:1이고, 그중 실제 파일 시스템 레이어를 만드는 것은 RUN / COPY / ADD 뿐이다. ENV / CMD / ENTRYPOINT / LABEL 은 메타데이터만 바꾸므로 위 출력에서도 전부 0B 로 찍혀 있다. 로컬(Docker Engine 29.4)에서 확인한 결과다.

verify 
# FROM / ENV×2 / WORKDIR / COPY / RUN / CMD 로 빌드한 이미지
$ docker image history layertest --format '{{.CreatedBy}}\t{{.Size}}'
CMD ["true"]                             0B
RUN /bin/sh -c echo hi > /w/hi.txt       4.1kB
COPY app.js .                            4.1kB
WORKDIR /w                               0B
ENV B=2                                  0B
ENV A=1                                  0B
...                                             # 히스토리 8줄

$ docker image inspect layertest --format '{{len .RootFS.Layers}}'
4                                               # 실제 파일 시스템 레이어는 4개

도커 이미지와 레이어

  • 도커 이미지는 도커 레이어가 모인 논리적 대상이다.
  • 이미지 레이어는 도커 엔진의 캐시에 물리적으로 저장된 파일이다.
  • 이미지 레이어는 여러 이미지와 컨테이너에서 공유된다.
  • docker image ls 로 확인한 이미지 크기는 논리적 용량이지 실제 디스크 점유량이 아니다.

도식화

같은 기반 이미지를 쓰면 무거운 레이어는 한 벌만 저장된다 — docker image ls 에 두 이미지가 각각 75MB 로 보여도 디스크에서는 server.js 레이어만 두 벌이다.

주의점

  • 이미지 레이어를 여러 이미지가 공유한다면, 공유되는 레이어는 수정이 불가능해야 한다.
  • 수정이 가능하다면 그 레이어를 공유받고 있는 다른 이미지에도 영향을 미친다.
  • 도커는 이미지 레이어를 읽기 전용으로 만들어 이 문제를 방지한다.
i

실제 디스크 사용량을 보려면 보강

docker image ls 의 SIZE 는 논리 용량이라 다 더하면 실제보다 크게 나온다. 중복을 걷어낸 실제 점유량은 docker system df 로 확인하고, 어떤 이미지가 얼마나 잡아먹는지 자세히 보려면 docker system df -v 를 쓴다. 이 명령은 17-1 에서 이미지 최적화의 출발점으로 다시 등장한다.

정리

  • 이미지 = 레이어의 논리적 묶음, 레이어 = 엔진 캐시에 있는 물리적 파일.
  • 히스토리 줄 수와 실제 레이어 수는 다르다. 파일 시스템을 바꾸는 RUN/COPY/ADD 만 레이어가 된다.
  • 레이어를 공유하므로 읽기 전용이어야 하고, 그래서 docker image ls 의 SIZE 는 합산하면 안 된다.
ITEM 3-5

이미지 레이어 캐시를 이용한 Dockerfile 스크립트 최적화

캐시는 한 번 깨지면 그 아래가 전부 무너진다. 그래서 자주 바뀌는 것을 아래로 내린다.

핵심 캐시 무효화는 연쇄적이다. 어떤 인스트럭션에서 캐시가 깨지면 그 아래는 캐시가 있어도 전부 다시 실행된다. 따라서 안 바뀌는 것을 위로, 자주 바뀌는 것을 아래로.

캐싱 원리

  • 인스트럭션의 결과가 이전에 빌드한 것과 동일하다면 캐싱된 레이어를 재사용한다.
  • 캐시에 일치하는 인스트럭션이 있는지 확인하기 위해 해시값을 쓴다.
  • 한 번 캐시가 깨져 인스트럭션이 실행되면, 그 다음 인스트럭션은 캐싱된 게 있어도 모두 실행된다.

ITEM 3-6

연습 문제 — Dockerfile 없이 이미지 빌드하기

컨테이너의 현재 상태를 그대로 굽는 docker commit. 가능하긴 하지만 권장 경로는 아니다.

핵심 docker commit 은 컨테이너의 기록 가능 레이어를 새 이미지 레이어로 굳히는 명령이다. 빠르지만 재현 가능한 빌드 기록이 남지 않는다.

문제 — Dockerfile 없이 이미지를 빌드하라. 여러 방법이 있지만 docker commit 을 활용한다.

CH 4

애플리케이션 소스코드에서 도커 이미지까지

빌드 도구를 로컬에 깔지 않고 컨테이너 안에서 컴파일한다. 멀티 스테이지 빌드가 표준화/성능/이미지 크기 세 가지를 한 번에 해결하는 방식.

ITEM 4-5

멀티 스테이지 Dockerfile 스크립트 이해하기

빌드 도구는 빌드 단계에만 있으면 된다. 최종 이미지에는 실행에 필요한 것만 남긴다.

핵심 멀티 스테이지 빌드는 표준화 / 성능 / 이미지 크기 세 가지를 한 번에 해결한다. 스테이지 사이에서 넘어가는 것은 COPY --from 으로 명시한 산출물뿐이다. 
flowchart LR
  S1["Stage 1: build-stage (FROM sdk)"] -->|"COPY --from 산출물만"| S2["Stage 2: test-stage (FROM sdk)"]
  S2 -->|"COPY --from 산출물만"| S3["Stage 3: 최종 이미지 (FROM runtime)"]
  S1 -.->|"SDK / 컴파일러 / curl 은 버려진다"| X["최종 이미지에 없음"]
각 스테이지는 독립된 이미지 빌드이고, 마지막 스테이지만 최종 이미지가 된다 — 앞 스테이지에서 쓴 SDK, 컴파일러, curl 은 COPY --from 으로 명시하지 않는 한 남지 않는다.

표준화

  • 모든 빌드 과정이 컨테이너 내부에서 이뤄진다.
  • 모든 컨테이너가 빌드 도구를 동일한 버전으로 유지한다.
  • 실무에 적용하면 신규 인원의 적응 기간이나 환경 설정으로 인한 빌드 실패를 줄일 수 있다.
i

이게 왜 중요한가 보강

빌드 도구가 Dockerfile 안에 FROM 으로 명시돼 있으면, 신규 인원의 로컬 환경에도 CI 서버에도 언어 런타임을 깔 필요가 없다. 필요한 것은 도커 하나뿐이다. 이 발상이 11장 의 "CI 서버에 아무것도 설치하지 않는 파이프라인"으로 이어진다.

성능 향상

  • 멀티 스테이지 빌드의 각 단계는 자신만의 캐시를 따로 가진다.
  • 도커는 빌드 중 각 인스트럭션에 해당하는 레이어 캐시를 찾는다.
  • Dockerfile 을 세심하게 최적화해 두면 캐시 재사용으로 90% 이상의 빌드 단계에서 시간을 아낄 수 있다.

최종 이미지의 크기 줄이기

  • 최종 산출물인 이미지에서 불필요한 도구는 모두 뺄 수 있다.
  • 예를 들어 curl 은 빌드 중 파일을 내려받기 위한 도구지만 최종 결과물에는 필요 없다.
  • 최종 산출되는 이미지를 매우 작게 유지할 수 있다.
✓

크기 줄이기는 곧 보안

이미지에 남지 않은 도구는 공격자도 쓸 수 없다. 컨테이너에 침입해도 curl 이 없으면 추가 페이로드를 내려받기 어렵고, 컴파일러가 없으면 그 자리에서 뭘 만들어 내기도 어렵다. 같은 이야기가 17-2 에서 기반 이미지 선택 기준으로 다시 나온다.

정리

  • 스테이지를 여러 개 두고, 스테이지 사이에는 COPY --from 으로 산출물만 넘긴다.
  • 빌드 도구 버전이 Dockerfile 에 고정되므로 "내 로컬에서는 됐는데"가 사라진다.
  • 스테이지마다 캐시가 따로 있어 잘 짜면 대부분의 단계가 캐시에 걸린다.
  • 최종 이미지에는 실행에 필요한 것만 남아 작고, 그만큼 공격 표면도 작다.
CH 5

도커 허브 등 레지스트리에 이미지 공유하기

이미지 이름은 그냥 이름이 아니라 레지스트리 주소다. 태그 전략과 신뢰할 수 있는 기반 이미지 고르기까지.

ITEM 5-1

레지스트리, 레포지토리, 이미지 태그

이미지 이름은 이름이 아니라 주소다. 네 부분으로 쪼개 보면 어디서 무엇을 받아 오는지가 그대로 읽힌다.

핵심 docker.io/diamol/golang:latest 는 레지스트리 / 계정 / 레포지토리 / 태그 네 조각이다. 로컬에서만 쓸 때는 아무래도 좋지만, 공유하는 순간 이 문자열이 유일한 식별자가 된다.

도커 허브

  • 도커 허브는 도커 엔진에 기본으로 설정된 레지스트리다.
  • 로컬에 없는 이미지를 실행하려고 하면 가장 먼저 찾아보는 곳이 도커 허브다.
  • 이미지 이름은 크게 네 가지 요소로 구분된다.

도커 이미지 이름 구분

생략된 부분은 사라진 게 아니라 기본값으로 채워진 것이다 — docker pull nginx 는 실제로는 docker.io/library/nginx:latest 를 받는다.
!

오탈자 교정 원문 교정

원문에는 docker.io 설명이 "기본값은 도커 gjqmek"으로 적혀 있다. 한영 전환 오타이며 "기본값은 도커 허브" 가 맞다.

이미지 이름이 중요한 이유

  • 로컬에서 단순하게 빌드할 때는 상관없지만, 레지스트리를 통해 공유한다면 잘 입력해야 한다.
  • 그 이미지 참조가 레지스트리에서 특정 이미지를 식별하는 식별자 역할을 하기 때문이다.

이미지 태그가 중요한 이유

  • 애플리케이션을 배포한다면 반드시 태그로 어떤 버전 / 변종인지 표기하자.
  • 태그가 없는 이미지를 빌드하면 이게 실제로 최신 버전인지 구분할 수 없게 된다.
i

latest 는 "최신"이라는 뜻이 아니다 보강

latest 는 태그를 생략했을 때 붙는 기본 문자열일 뿐, 최신 버전을 가리킨다는 보장이 전혀 없다. 누군가 오래된 이미지에 latest 를 붙여 푸시하면 그게 latest 가 된다. 배포 대상을 완전히 고정하려면 태그 대신 다이제스트를 쓴다 (image@sha256:...). 태그는 옮겨 붙을 수 있지만 다이제스트는 내용 해시라 변하지 않는다.

정리

  • 이미지 이름 = 레지스트리/계정/레포지토리:태그. 생략하면 docker.io 와 latest 가 채워진다.
  • 레포지토리 하나에 여러 버전의 이미지가 태그로 구분되어 담긴다.
  • latest 는 기본값일 뿐 최신 보장이 아니다. 배포에는 명시적 태그, 완전 고정에는 다이제스트를 쓴다.
ITEM 5-2

도커 허브에 직접 빌드한 이미지 푸시하기

푸시할 때 Mounted from 이 뜨는 이유 — 레지스트리도 레이어를 공유한다.

핵심 푸시는 이미지 전체를 올리는 게 아니라 레지스트리에 아직 없는 레이어만 올린다. 나머지는 Mounted from 으로 기존 레이어를 참조하고 끝난다.

원문 노트에서는 "패스"로 넘어간 절이다

나중에 필요해질 때 되돌아올 수 있도록, 이 절이 다루는 내용의 골자만 짧게 남긴다. 실제 운영 구축은 11-2 의 빌드 인프라 구축에서 다시 다뤄진다.

언제 자체 레지스트리가 필요한가

  • 폐쇄망 — 외부 인터넷으로 이미지를 내보내거나 받아 올 수 없는 환경
  • 대역폭과 속도 — 같은 이미지를 수십 대가 동시에 받아야 할 때, 사내 레지스트리가 캐시 역할을 한다
  • 규정 준수 — 이미지 안에 들어간 코드가 조직 밖으로 나가면 안 되는 경우
  • 도커 허브 요금/제한 — 비인증 풀 횟수 제한, 프라이빗 레포지토리 개수 제한을 피하고 싶을 때

기본 골자

레지스트리 자체도 컨테이너로 뜬다. 오픈소스 구현체 (registry / CNCF Distribution)를 컨테이너로 실행하고, 이미지 이름 앞에 그 호스트와 포트를 붙이면 그쪽으로 푸시된다.

terminal 
# 레지스트리를 컨테이너로 실행
$ docker run -d -p 5000:5000 --name registry registry:2

# 이미지 이름 앞에 레지스트리 호스트:포트를 붙여 태그
$ docker image tag web-ping registry.local:5000/diamol/web-ping:v1
$ docker image push registry.local:5000/diamol/web-ping:v1
!

HTTPS 가 기본이다 보강

도커 엔진은 레지스트리와 HTTPS 로만 통신하려 한다. 인증서 없이 띄운 사내 레지스트리에 푸시하면 http: server gave HTTP response to HTTPS client 로 거부당한다. 정식으로는 인증서를 붙이고, 실습이라면 데몬 설정의 insecure-registries 에 해당 호스트를 등록한 뒤 도커를 재시작한다. 이 예외는 신뢰하는 사내망에서만 쓴다.

정리

  • 폐쇄망 / 대역폭 / 규정 준수 / 도커 허브 제한 회피가 자체 레지스트리를 두는 이유다.
  • 레지스트리도 컨테이너다. 이미지 이름 앞에 호스트:포트 를 붙이면 그쪽으로 간다.
  • 기본은 HTTPS 다. 인증서를 붙이거나, 실습 한정으로 insecure-registries 를 쓴다.
ITEM 5-4

이미지 태그를 효율적으로 사용하기

semver 자릿수만큼 태그를 붙여 두면, 사용자가 "얼마나 최신을 따라갈지"를 스스로 고를 수 있다.

핵심 실제 버전을 가리키는 태그는 2.1.106 하나뿐이고, 2.1 / 2 / latest 는 움직이는 별명이다. 어느 별명을 참조하느냐가 곧 업데이트 수용 범위가 된다.

이미지 태그의 특성

  • 어떠한 문자열도 포함시킬 수 있다.
  • 같은 이미지에 여러 개의 태그를 부여할 수 있다.
  • 태그를 통해 버전을 구별하고, 사용자는 어떤 이미지를 쓸지 고를 수 있다.

버저닝 방식

  • 대부분의 소프트웨어처럼 semver 방식이 표준이다. [major].[minor].[patch] 형식이다.
자리올라가는 조건호환성
patch버그만 수정됨✓ 기존 그대로
minor기능이 추가됐지만 기존 기능은 모두 유지됨✓ 기존 그대로
major완전히 다른 기능을 가짐✗ 깨질 수 있음
terminal 
$ docker image tag temp registry.local:5000/temp/ui:latest
$ docker image tag temp registry.local:5000/temp/ui:2
$ docker image tag temp registry.local:5000/temp/ui:2.1
$ docker image tag temp registry.local:5000/temp/ui:2.1.106

버전업에 따른 태그 변화 예시

한 달에 한 번 릴리스할 때마다 버전이 바뀐다고 가정한다.

어느 태그를 참조하느냐가 곧 업데이트 정책이다 — :2.1 을 쓰면 patch 만, :2 를 쓰면 minor 까지 자동으로 따라간다. :2.1.106 을 쓰면 아무것도 바뀌지 않는다.
참조하는 태그자동으로 받는 업데이트적합한 곳
:2.1.106없음 (완전 고정)운영 배포
:2.1patch 업데이트버그 픽스는 자동으로 받고 싶을 때
:2minor + patch 업데이트호환되는 범위는 계속 따라가고 싶을 때
:latest전부 (major 포함)실습 / 로컬 실험

정리

  • 같은 이미지에 semver 자릿수만큼 태그를 겹쳐 붙여 사용자에게 선택권을 준다.
  • 전체 버전 태그 하나만 불변이고 나머지는 릴리스마다 옮겨 붙는 별명이다.
  • 운영에서는 전체 버전을, 실험에서는 별명을 쓴다. latest 는 운영에 쓰지 않는다.
ITEM 5-5

공식 이미지에서 골든 이미지로 전환하기

공식 이미지의 검증은 그대로 물려받으면서, 조직의 규칙을 한 겹 얹은 것이 골든 이미지다.

핵심 골든 이미지는 새로 만드는 게 아니라 공식 이미지를 FROM 으로 삼아 한 겹 얹는 것이다. 그래야 공식 이미지의 이점(취약점 스캔, 정기 업데이트)을 유지한 채 조직 표준을 강제할 수 있다.

도커 허브의 신뢰성

  • 누구나 이미지를 만들어 레지스트리에 푸시할 수 있다.
  • 해커의 관점에서 보면 멀웨어를 배포하기 제격인 조건이다.
  • 도커 허브는 이런 피해를 방지하기 위해 검증된 퍼블리셔와 공식 이미지 제도를 두고 있다.
검증된 퍼블리셔(Verified Publisher)
  • IBM, MS, Oracle 등 신뢰할 수 있는 큰 기업을 검증된 퍼블리셔로 지정한다.
  • 이들이 배포하는 이미지는 사전에 취약점 탐지 등 승인 절차를 거쳐 공개된다.
  • 컨테이너에서 최신 버전의 상용 소프트웨어를 써야 한다면, 검증된 퍼블리셔의 인증된 이미지를 쓰는 게 최선이다.
공식 이미지(Official Image)
  • 주로 오픈소스 소프트웨어가 배포되며, 해당 프로젝트 개발팀과 도커팀이 함께 이미지를 관리한다.
  • 마찬가지로 취약점 탐색을 거쳐 주기적으로 업데이트되고, 잘 최적화된 Dockerfile 로 구성된다.

지금의 도커 허브 신뢰 콘텐츠는 네 종류다 최신 반영

노트가 쓰인 이후 프로그램이 늘었다. 현재 도커 허브의 신뢰 콘텐츠(Trusted Content)는 다음 네 가지다.

프로그램주로 담는 것
Docker Official Images큐레이션된 오픈소스 이미지. 정기 업데이트, 모범 사례 Dockerfile
Verified Publisher도커가 검증한 상용 퍼블리셔의 이미지
Docker-Sponsored Open Source도커가 후원하는 오픈소스 프로젝트가 직접 관리하는 이미지
Docker Hardened Images도커가 관리하는 최소 이미지. CVE 를 거의 0 에 가깝게 유지하고 SBOM / 프로버넌스 서명을 포함

원문의 "Verfieid Publisher" 는 Verified Publisher 의 오타다.

골든 이미지(Golden Image)

  • 대부분은 공식 이미지로 무언가를 빌드하지만, 언젠가는 좀 더 많은 것을 통제하고 싶어지는 시기가 온다.
  • 이때 개발자는 자신이 선호하는 기반 이미지로 전환하는데, 이것을 골든 이미지라고 부른다.
  • 기반 이미지에 원하는 환경 설정값 등 필요한 설정을 추가하는 것을 뜻한다.
  • 공식 이미지의 이점을 그대로 누리면서 필요한 설정을 더할 수 있는 것이 장점이다.
flowchart TB
  HUB["node:20 (도커 허브 공식 이미지)"] -->|"FROM"| GOLD["golden/node:20 (사내 인증서 / 보안 패치 추가)"]
  GOLD -->|"FROM"| APP["project/node-app (앱 코드 추가)"]
골든 이미지는 공식 이미지를 대체하지 않고 그 위에 한 겹 얹는다 — 각 프로젝트는 골든 이미지만 FROM 으로 쓰면 사내 표준을 자동으로 물려받는다.
i

골든 이미지에 보통 무엇을 넣는가 보강

사내 CA 인증서, 사설 패키지 저장소 설정, 비 root 실행 사용자, 타임존/로케일, 공통 로깅 설정 정도가 대표적이다. 여기에 기반 이미지 버전을 조직 단위로 고정하는 효과까지 따라온다. 프로젝트마다 node:20, node:22 가 제각각 흩어지는 대신 골든 이미지 하나만 올리면 전 프로젝트가 함께 올라간다.

정리

  • 도커 허브는 아무나 푸시할 수 있으므로 신뢰 콘텐츠 프로그램으로 기반 이미지를 고른다.
  • 골든 이미지 = 공식 이미지 + 조직 표준 한 겹. 새로 만드는 게 아니라 FROM 으로 얹는다.
  • 각 프로젝트가 골든 이미지만 참조하면 기반 이미지 업그레이드가 한 곳에서 끝난다.
CH 6

도커 볼륨을 이용한 퍼시스턴트 스토리지

컨테이너가 사라지면 데이터도 사라진다. 그 이유를 유니언 파일 시스템으로 설명하고, 볼륨과 바인드 마운트로 라이프사이클을 떼어낸다.

ITEM 6-1

컨테이너 속 데이터가 사라지는 이유

읽기 전용 이미지 레이어 위에 컨테이너마다 얇은 기록 가능 레이어가 하나씩 얹힌다. 그 레이어의 수명이 컨테이너의 수명이다.

핵심 컨테이너의 파일 시스템은 공유되는 읽기 전용 레이어 + 컨테이너 전용 기록 가능 레이어다. 데이터가 사라지는 이유는 쓴 내용이 전부 후자에만 남고, 그 레이어가 컨테이너와 함께 삭제되기 때문이다.

컨테이너의 파일 시스템

  • 컨테이너의 디스크는 이미지 레이어를 순서대로 연결해 만든 가상 파일 시스템이다.
  • 모든 컨테이너는 독립된 파일 시스템을 갖는다.
  • 같은 이미지에서 실행된 컨테이너는 처음엔 같은 내용이지만, 한쪽의 파일을 수정해도 다른 쪽에는 영향이 없다.
컨테이너의 파일시스템이 독립적임을 확인해 보기

같은 이미지로 시작한 컨테이너지만 내부 내용물이 서로 다르다. 각 컨테이너가 독립적인 저장 공간을 가진다는 증명이다.

terminal 
$ docker run --name rn1 diamol/ch06-random-number
$ docker run --name rn2 diamol/ch06-random-number

$ docker cp rn1:/random/number.txt number1.txt
Successfully copied 2.05kB to /Users/imkdw/number1.txt
$ docker cp rn2:/random/number.txt number2.txt
Successfully copied 2.05kB to /Users/imkdw/number2.txt

$ cat number1.txt
10341

$ cat number2.txt
8719

컨테이너 파일시스템 구성

기본적으로 이미지 레이어와 컨테이너의 기록 가능 레이어로 나뉜다.

구분공유 여부쓰기수명
이미지 레이어 모든 컨테이너가 공유 ✗ 읽기 전용 이미지를 지울 때까지
기록 가능 레이어 컨테이너마다 하나씩 ✓ 수정 가능 컨테이너와 동일 — 지우면 함께 삭제
같은 이미지, 다른 난수 — 각자 자기 기록 가능 레이어에 썼기 때문이다. 아래 두 레이어는 물리적으로 한 벌만 존재하고 둘이 함께 본다.

이미지 레이어 수정하기

  • 읽기 전용이라 수정이 안 되는 게 맞지만, 기록 중 복사(copy-on-write) 방식으로 수정이 가능하다.
  • 컨테이너나 앱에서는 이 과정이 드러나지 않지만, 도커가 스토리지를 아끼는 매우 좋은 방법이다.
  • 컨테이너 속 파일을 수정하면 해당 컨테이너에만 영향을 미친다.
    • 이미지를 공유하는 다른 컨테이너나 이미지는 영향을 받지 않는다.
    • 수정된 파일은 그 컨테이너의 기록 가능 레이어에만 존재하기 때문이다.
i

기록 중 복사가 실제로 하는 일 보강

읽기 전용 레이어의 파일을 수정하면 도커는 그 파일을 기록 가능 레이어로 통째로 복사한 뒤 거기서 수정한다. 그래서 큰 파일을 한 바이트만 고쳐도 파일 전체가 복사되고, 그 순간 디스크와 시간을 쓴다. 데이터베이스처럼 큰 파일을 계속 쓰는 워크로드를 기록 가능 레이어 위에 두면 안 되는 성능상의 이유가 여기 있다. 그런 데이터는 볼륨이나 바인드 마운트로 뺀다.

예제
  • 최초 컨테이너 실행 시에는 https://... 문구가 출력된다.
  • 이후 "asdf" 문구가 담긴 파일을 f1 컨테이너에 복사했다.
  • f1 컨테이너를 다시 실행하니 복사한 내용이 출력된다.
terminal 
$ docker run --name f1 diamol/ch06-file-display
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ echo "asdf" > url.txt

$ docker container cp url.txt f1:/input.txt
Successfully copied 2.05kB to f1:/input.txt

$ docker container start --attach f1
asdf

컨테이너 스토리지 라이프사이클 확인하기

  • 최초 구동 이후 f3 컨테이너의 파일을 복사하니 컨테이너와 동일한 내용이 보인다.
  • 이후 f3 컨테이너를 삭제하니 No such container: f3 에러가 발생한다.
  • 컨테이너의 파일 시스템이 컨테이너와 동일한 라이프사이클을 지닌 것을 확인할 수 있다.
terminal 
$ docker run --name f3 diamol/ch06-file-display
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ docker container cp f3:/input.txt .
Successfully copied 2.05kB to /Users/imkdw/.

$ cat input.txt
https://www.manning.com/books/learn-docker-in-a-month-of-lunches

$ docker rm -f f3
f3

$ docker container cp f3:/input.txt .
Error response from daemon: No such container: f3

컨테이너의 영속성?

  • 도커로 DB 를 운영하다가 컨테이너를 교체한다고 해 보자. 교체되면 지워지고 다시 뜨는 것이므로 내부 내용이 전부 삭제된다.
  • 이런 상황을 감안해 도커는 도커 볼륨(Docker Volume) 과 마운트(Mount) 를 제공한다.
  • 이 둘은 컨테이너와 다른 라이프사이클을 가지므로, 지속돼야 할 데이터를 담을 수 있다.

정리

  • 컨테이너 파일 시스템 = 공유되는 읽기 전용 이미지 레이어 + 컨테이너 전용 기록 가능 레이어.
  • 쓰기는 전부 기록 가능 레이어에 남고, 그 레이어는 컨테이너와 함께 사라진다.
  • 이미지 레이어 수정은 기록 중 복사로 처리된다. 큰 파일에는 비용이 크다.
  • 살아남아야 할 데이터는 볼륨이나 마운트로 컨테이너 밖에 둔다.
ITEM 6-2

도커 볼륨을 사용하는 컨테이너 실행하기

볼륨은 컨테이너를 위한 USB 다. 뽑아서 다른 컨테이너에 꽂을 수 있다.

핵심 볼륨은 이미지 / 컨테이너와 동급인 도커 리소스다. 그래서 docker volume ls 로 조회되고, 컨테이너를 지워도 남으며, 다른 컨테이너에 그대로 다시 붙일 수 있다.

도커 볼륨

  • 도커 볼륨은 도커에서 스토리지를 다루는 단위다.
  • 마치 컨테이너를 위한 USB 라고 이해하면 쉽다.

수동으로 직접 생성해서 컨테이너에 연결하기

  • docker volume create <volume_name> 으로 볼륨을 만들 수 있다.
  • -v 플래그로 컨테이너 시작 시 볼륨을 마운트할 수 있다.
  • 아래는 v1 컨테이너에서 데이터를 추가하면 v2 에도 반영되는(디스크 공유) 모습이다.
terminal 
# 도커 볼륨 생성
$ docker volume create todo-list
todo-list

# v1 컨테이너 시작
$ docker run -d -p 8011:80 -v todo-list:/data --name todo-v1 diamol/ch06-todo-list
7d0dcc71e0a98fe8a315a98d9d30a9504ad2e1c777c47add41c5c7a9810b91b1

# v2 컨테이너 시작 (같은 볼륨을 붙인다)
$ docker run -d -p 8012:80 -v todo-list:/data --name todo-v2 diamol/ch06-todo-list:v2
66b19a7f8118ee52addfa0bb570e883faec599c3505272b277f5a67696b70878
서로 다른 이미지 버전, 서로 다른 포트, 같은 데이터 — 볼륨을 공유하므로 v1 에서 넣은 항목이 v2 목록에 그대로 보인다. 컨테이너 교체형 업데이트가 가능한 이유가 이것이다.

Dockerfile 에서 VOLUME 인스트럭션 사용하기

VOLUME 인스트럭션은 VOLUME <target-directory> 형식으로 쓴다.

Dockerfile 
# 일부 내용

# set in the base image - `/data` for Linux, `C:\data` for Windows
VOLUME $SQLITE_DATA_DIRECTORY

# ...
terminal 
# 명시적인 -v 연결은 없지만 Dockerfile 의 VOLUME 때문에 볼륨이 붙는다
$ docker run -d --name todo1 -p 8010:80 diamol/ch06-todo-list
cbb8096739d34b4cc51a5dcc48b2c3c38b0c64a2721c260c9316d8785843e4c1

# mounts 항목에서 볼륨 관련 정보를 확인할 수 있다
$ docker inspect --format '{{.Mounts}}' todo1
[{volume 5baf8fce2819f63c731417e0be889db779460f88316ffc44d099c2ce9150f8f3 /var/lib/docker/volumes/5baf8fce.../_data /data local  true }]

# 볼륨은 도커에서 이미지나 컨테이너와 동급인 요소다
$ docker volume ls
DRIVER    VOLUME NAME
local     5baf8fce2819f63c731417e0be889db779460f88316ffc44d099c2ce9150f8f3
!

이름 없는 볼륨이 조용히 쌓인다 보강

VOLUME 인스트럭션만 있고 -v 로 이름을 주지 않으면, 위 출력처럼 해시 이름의 익명 볼륨이 컨테이너를 실행할 때마다 새로 생긴다. 컨테이너를 지워도 이 볼륨은 남으므로 실습을 반복하면 디스크가 계속 차오른다. docker volume ls 로 확인하고, 붙어 있지 않은 볼륨은 docker volume prune 으로 정리한다. 실제 데이터가 들어 있는 볼륨도 같이 지워지므로 반드시 목록을 먼저 확인할 것. 컨테이너를 지울 때 익명 볼륨까지 함께 지우려면 docker rm -v 를 쓴다.

정리

  • docker volume create + -v 볼륨명:컨테이너경로 가 기본형이다.
  • 같은 볼륨을 여러 컨테이너에 붙이면 데이터를 공유한다. 컨테이너 교체 업데이트의 기반이다.
  • Dockerfile 의 VOLUME 은 이름 없는 볼륨을 자동으로 만든다. 방치하면 디스크가 찬다.
ITEM 6-3

파일시스템 마운트를 사용하는 컨테이너 실행하기

볼륨이 도커가 관리하는 저장소라면, 바인드 마운트는 호스트의 특정 폴더를 그대로 꽂는 것이다.

핵심 바인드 마운트는 호스트 파일 시스템의 폴더를 컨테이너 폴더로 만든다. 호스트에서 접근 가능한 것이면 SSD 든 SAN 이든 컨테이너에서 그대로 쓸 수 있다.

볼륨의 장점

  • 컨테이너와 스토리지의 라이프사이클을 분리하면서, 도커를 쓰던 방식 그대로 스토리지를 제어할 수 있다.

바인드 마운트(Bind Mount)

  • 호스트의 스토리지를 컨테이너에 좀 더 직접적으로 연결하는 수단이다.
  • 즉 호스트 컴퓨터 파일 시스템의 폴더를 컨테이너 파일 시스템의 폴더로 만든다.
  • SSD, 디스크 어레이, SAN 등 호스트에서 접근 가능한 파일 시스템이면 무엇이든 컨테이너에서 쓸 수 있다.

--mount 플래그

컨테이너에서 읽기 전용으로 쓰게 하려면 --mount 옵션에 readonly 를 함께 지정할 수 있다.

terminal 
$ source="$(pwd)/databases" && target='/data'

$ mkdir ./databases

$ docker run --mount type=bind,source=$source,target=$target -d -p 8013:80 diamol/ch06-todo-list
6e071e5e8cdf9b1bb641ed5dc586144264fb3f1d6e0cb7c8396d47a81fcd5c40

$ ll ./databases
total 24
-rw-r--r--@ 1 imkdw  staff    12K 10 27 11:09 todo-list.db
i

볼륨바인드 마운트
저장 위치도커가 관리하는 영역호스트의 지정한 경로
호스트 경로 의존✓ 없음 (이식성 높음)✗ 경로가 머신마다 달라짐

읽기 전용으로 붙이려면 --mount type=bind,source=...,target=...,readonly 로 쓴다. 설정 파일을 주입할 때는 이 옵션을 붙이는 게 안전하다.

정리

  • 바인드 마운트는 호스트 폴더를 컨테이너 폴더로 그대로 노출한다.
  • --mount type=bind,source=<호스트>,target=<컨테이너> 형식, readonly 를 붙일 수 있다.
  • 운영 데이터는 볼륨, 개발 중 소스 공유와 설정 주입은 바인드 마운트가 기본 선택이다.
ITEM 6-4

파일 시스템 마운트의 한계점

마운트는 합치는 게 아니라 덮는다. 그리고 그 규칙마저 OS 마다 다르다.

핵심 디렉터리를 마운트하면 원본이 기존 내용을 완전히 대체한다. 이미지 안에 있던 파일은 사라진 게 아니라 가려진 것이며, 마운트를 떼면 다시 나타난다.

기존 이미지의 파일 시스템 사용 불가

  • 이미 존재하는 대상 폴더에 마운트하면, 마운트의 원본 폴더가 기존 폴더를 완전히 대체한다.
  • 즉 이미지에 포함돼 있던 원래 파일은 사용할 수 없다.
terminal 
$ source="$(pwd)/new" && target='/init';

# 기존 이미지에 포함되어 있던 파일들
$ docker run diamol/ch06-bind-mount
abc.txt
def.txt

# 마운트된 디스크에 존재하는 파일들 — 이미지 쪽 파일은 보이지 않는다
$ docker run --mount type=bind,source=$source,target=$target diamol/ch06-bind-mount
1.txt
2.txt
×

실무에서 가장 자주 밟는 지뢰

개발 중 소스 폴더를 -v $(pwd):/app 로 붙이는 순간, 이미지 빌드 때 설치해 둔 /app/node_modules 가 호스트 폴더에 가려서 사라진다. 컨테이너 안에서 Cannot find module 이 뜨는 전형적인 원인이다. 해결은 그 하위 경로에 익명 볼륨을 겹쳐 덮어쓰기를 막는 것이다.

해결 
$ docker run -v $(pwd):/app -v /app/node_modules myapp
#                            └ 이 경로만 호스트가 아닌 볼륨으로 덮어 되살린다

OS 별 파일 시스템의 차이점 문제

호스트 컴퓨터의 파일 하나를 컨테이너에 이미 존재하는 디렉터리로 마운트할 때, OS 마다 결과가 다르다.

호스트 OS결과
유닉스 계열디렉터리의 파일이 합쳐져 이미지 + 호스트 마운트 파일이 모두 보인다
윈도우Invalid Mount Config 에러가 발생한다
!

단일 파일 마운트의 또 다른 함정 보강

리눅스에서 단일 파일을 마운트하면 inode 단위로 묶인다. 그래서 호스트에서 그 파일을 에디터로 저장할 때(대부분 임시 파일을 만들고 rename 하는 방식) 마운트가 끊겨, 컨테이너 안에서는 변경이 반영되지 않는다. 설정 파일을 실시간으로 갈아 끼워야 한다면 파일 하나가 아니라 그 파일이 든 디렉터리를 마운트하는 편이 안전하다.

정리

  • 디렉터리 마운트는 이미지의 기존 내용을 가린다. 합쳐지지 않는다.
  • node_modules 가 사라지는 문제는 하위 경로에 익명 볼륨을 겹쳐 해결한다.
  • 단일 파일 마운트는 OS 마다 동작이 다르고 에디터 저장에 끊긴다. 디렉터리 단위로 마운트하자.
ITEM 6-5

컨테이너 파일시스템이 만들어지는 방법

여러 출처를 하나의 가상 디스크로 합치는 것이 유니언 파일 시스템. 저장할 곳을 고르는 다섯 가지 선택지.

핵심 한 컨테이너에서 기록 가능 레이어는 정확히 하나이고, 나머지는 여러 개일 수 있다. 데이터를 어디에 둘지는 "이 데이터가 컨테이너보다 오래 살아야 하는가"로 갈린다.

유니언 파일 시스템(Union File System)

  • 모든 컨테이너는 도커가 여러 출처에서 모아 만든 단일 가상 디스크로 구성된 파일 시스템을 갖는다. 이것을 유니언 파일 시스템이라고 부른다.
  • 유니언 파일 시스템은 OS 마다 다르게 구현돼 있지만, 사용자가 신경 쓸 필요는 없다. 도커가 알아서 처리한다.
  • 파일 시스템 중 기록 가능 레이어는 하나만 가질 수 있고, 나머지는 여러 개가 가능하다.

컨테이너 스토리지 구성 시 고려사항

위로 갈수록 수명이 짧고, 아래로 갈수록 공유 범위가 넓다 — 기록 가능 레이어는 컨테이너와 함께 사라지고, 이미지 레이어는 모든 컨테이너가 함께 쓴다. 그 사이의 세 층이 "컨테이너보다 오래 살아야 하는 데이터"를 담는 자리다.
기록 가능 레이어
  • 캐싱 등 단기 저장에 적합하다.
  • 각 컨테이너마다 독립적이다.
  • 생명주기가 컨테이너와 동일해서 컨테이너가 삭제되면 같이 삭제된다.
로컬 바인드 마운트
  • 호스트 PC 와 컨테이너 간 데이터를 공유하기 위해 쓴다.
  • 예를 들어 개발 중인 코드를 컨테이너와 공유하면 다시 빌드하지 않고 바로 실행할 수 있다.
분산 바인드 마운트
  • 네트워크 스토리지와 컨테이너 간 데이터 공유를 위해 쓴다.
  • 가용성이 높지만 로컬 파일 시스템에 비해 지원하지 않는 기능이 있을 수 있다.
볼륨 마운트
  • 앱의 데이터를 볼륨에 영구히 저장할 수 있다(영속성).
  • 컨테이너를 교체하는 방식으로 앱을 업데이트해도 이전 버전 컨테이너의 데이터를 그대로 유지할 수 있다.
이미지 레이어
  • 컨테이너의 초기 파일 시스템을 구성한다.
  • 읽기 전용이며 여러 컨테이너가 공유한다.
i

고르는 기준 한 줄 보강

"컨테이너를 지웠을 때 같이 사라져도 되는가?" 하나만 물으면 된다. 사라져도 되면 기록 가능 레이어(임시 파일, 캐시), 남아야 하면 볼륨(운영 데이터), 호스트에서 직접 편집해야 하면 바인드 마운트(개발 소스, 설정 파일)다.

정리

  • 컨테이너 파일 시스템은 여러 출처를 겹쳐 만든 단일 가상 디스크(유니언 파일 시스템)다.
  • 기록 가능 레이어는 하나뿐이고, 나머지 층은 여러 개일 수 있다.
  • 수명 기준으로 고른다 — 임시는 기록 가능 레이어, 영속은 볼륨, 편집 필요는 바인드 마운트.
CH 7

도커 컴포즈로 분산 앱 실행

여러 개의 docker run 명령을 YAML 한 장으로 대체한다. 서비스/네트워크 개념과 DNS 디스커버리가 여기서 나온다.

ITEM 7-1

도커 컴포즈 파일의 구조

컴포즈 파일은 "이 앱이 다 떠 있을 때 어떤 모습이어야 하는가"를 적은 문서다.

핵심 컴포즈 파일은 절차가 아니라 원하는 상태(desired state) 를 기술한다. docker run 에 붙이던 플래그들이 전부 YAML 의 필드로 옮겨 온 것이라고 보면 된다.

Docker Compose 란

  • 앱의 원하는 상태, 즉 모든 컴포넌트가 실행 중일 때 어떤 상태여야 하는지를 기술하는 파일이다.
  • docker run 에서 지정해야 하는 모든 옵션을 모아 놓은 단순한 형식의 파일이다.
docker-compose.yml 노트 원본 (구형 문법) 
version: "3.7"

services:
  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - "8020:80"
    networks:
      - app-net

networks:
  app-net:
    external:
      name: nat

주요 블록

version
  • 도커 컴포즈 파일 형식의 버전을 나타낸다.
  • 노트에는 "24.10.27 기준 deprecated 될 예정" 이라고 기록되어 있다.
services
  • 앱을 구성하는 모든 컴포넌트를 열거하는 부분이다.
  • 실제 컨테이너가 아닌 서비스 개념을 단위로 삼는다.

docker-compose 대신 docker compose 최신 반영

노트 전반에 나오는 하이픈 있는 docker-compose 는 파이썬으로 만들어진 Compose V1 이고, 2023년 7월 이후 지원이 종료되어 새 Docker Desktop 에는 포함되지 않는다. 지금은 도커 CLI 플러그인인 Compose V2, 즉 공백으로 쓰는 docker compose 가 표준이다. 하위 명령과 옵션은 대부분 그대로라, 이 정리본의 실습 명령은 하이픈만 공백으로 바꾸면 그대로 동작한다. 파일명도 docker-compose.yml 과 compose.yaml 을 모두 인식하며, 새 프로젝트는 compose.yaml 이 권장 이름이다.

정리

  • 컴포즈 파일은 절차가 아니라 원하는 상태를 적는다. docker run 플래그가 YAML 필드가 된 것.
  • 단위는 컨테이너가 아니라 서비스다. 서비스 하나가 컨테이너 여러 개일 수 있다.
  • version 은 이제 obsolete, external.name 은 deprecated. external: true + name: 으로 쓴다.
  • 명령은 docker compose(공백)가 표준이다.

되돌아가는 게 버그가 아니라 설계다

컴포즈는 매번 "파일에 적힌 상태"로 수렴시킨다. CLI 로 임시로 3개를 띄운 것은 파일에 없는 상태이므로 다음 up 에서 정리된다. 스케일 값을 유지하고 싶다면 파일의 deploy.replicas 에 적어 두거나 매번 --scale 을 함께 넘겨야 한다. 원하는 상태는 항상 파일에 적혀 있어야 한다는 원칙이 여기서도 그대로 적용된다.

정리

  • up 한 번으로 여러 서비스가 뜨고, --scale 로 골라서 늘릴 수 있다.
  • depends_on 은 기동 순서만 보장한다. 준비 완료를 기다리려면 condition: service_healthy 를 쓴다.
  • stop 은 정지, down 은 삭제, down -v 는 볼륨까지 삭제.
  • CLI 로 만든 상태는 파일에 없으므로 다음 up 에서 되돌아간다.
ITEM 7-3

도커 컨테이너 간 통신

컨테이너 IP 는 바뀐다. 그래서 IP 가 아니라 이름으로 부른다.

핵심 도커에는 DNS 서버가 내장되어 있어 서비스 이름을 IP 로 풀어 준다. 스케일 아웃한 서비스는 여러 개의 IP 가 돌아오므로, 앱 쪽에서 그것으로 로드밸런싱을 할 수 있다.

DNS 디스커버리

  • 모든 컨테이너는 고유의 IP 주소를 갖는다.
  • 컨테이너가 교체되면 IP 도 바뀌는데, 그래도 문제가 없도록 도커는 DNS 디스커버리 기능을 제공한다.
  • 도커에는 DNS 서비스가 내장돼 있으며, 컨테이너 이름을 도메인 삼아 조회하면 IP 주소를 찾아 준다.

이 로드밸런싱의 한계 보강

도커 DNS 는 응답 순서를 매번 섞어 반환하지만, 이것만으로는 부하가 고르게 나뉜다는 보장이 없다. 많은 HTTP 클라이언트가 첫 번째 IP 만 쓰거나 DNS 결과를 캐싱하기 때문이다. JVM 은 기본 DNS 캐시 정책이 특히 길어서, 컨테이너가 교체돼 IP 가 바뀌어도 옛 IP 로 계속 붙는 사고가 잘 생긴다. 실제 분산이 필요하면 프록시를 두거나 스웜/쿠버네티스의 가상 IP 방식을 쓴다.

정리

  • 컨테이너 IP 는 교체될 때마다 바뀌므로 서비스 이름으로 부른다.
  • 도커 내장 DNS 가 이름을 IP 로 풀어 주고, 스케일 아웃된 서비스는 IP 목록을 돌려준다.
  • 고르는 것은 앱이다. 클라이언트의 DNS 캐싱 때문에 실제 분산은 보장되지 않는다.
ITEM 7-4

도커 컴포즈로 앱 설정값 지정하기

SQLite 로 돌던 앱을 코드 수정 없이 Postgres 로 갈아 끼운다. 바뀐 것은 설정뿐이다.

핵심 패키징된 앱과 설정값을 분리할 수 있다는 것이 도커의 핵심 장점 중 하나다. 개발 환경에서 검증을 마친 바로 그 이미지를 운영에서도 그대로 쓸 수 있게 된다.

도커 컴포즈로 설정값 지정

  • 환경 변수는 주로 클러스터 환경에서 쿠버네티스나 도커 스웜 같은 컨테이너 플랫폼을 통해 제공된다.
  • 다만 단일 PC 에서 구동하는 경우는 파일로 제공해도 무방하다.
  • 패키징된 앱과 설정값을 분리할 수 있다는 게 도커의 핵심 장점 중 하나다. 개발 환경에서 계속 테스트하고 검증한 이미지를 그대로 프로덕션에서도 쓸 수 있다.

      - "8030:80"
    environment:
      - Database:Provider=Postgres
    depends_on:
      - todo-db
    networks:
      - app-net
    secrets:
      - source: postgres-connection
        target: /app/config/secrets.json

networks:
  app-net:

secrets:
  postgres-connection:
    file: ./config/secrets.json

{
  "ConnectionStrings": {
    "ToDoDb": "Server=todo-db;Database=todo;User Id=postgres;Password=postgres;"
  }
}

SQLite 대신 Postgres

실제로 추가한 데이터가 도커로 실행한 Postgres 에 저장된다.

앱 이미지는 그대로, 저장소만 바뀌었다 — 코드를 고치지 않고 environment 와 비밀값 파일만 바꿔 SQLite 에서 Postgres 로 전환했다.
!

여기의 비밀값은 진짜 비밀이 아니다 보강

컴포즈의 secrets 는 파일 내용을 컨테이너 안의 지정 경로에 얹어 줄 뿐, 암호화하지 않는다. 원본은 여전히 ./config/secrets.json 평문 파일이다. 실제 암호화 저장은 스웜의 docker secret 이나 쿠버네티스 Secret, 외부 볼트가 담당한다. 그래도 environment 로 넘기는 것보다는 낫다. 환경 변수는 docker inspect 와 프로세스 목록에 그대로 노출되지만, 파일로 얹은 값은 그렇지 않기 때문이다.

정리

  • 같은 이미지에 설정만 갈아 끼워 저장소를 바꿨다. 앱과 설정의 분리가 실제로 작동하는 모습이다.
  • 커넥션 스트링의 호스트명 자리에 서비스 이름을 그대로 쓴다. DNS 가 풀어 준다.
  • 민감한 값은 environment 보다 secrets(파일 주입)가 낫다. 다만 암호화는 아니다.
ITEM 7-5

도커 컴포즈도 만능은 아니다

컴포즈는 상태를 만들어 주지만 지켜 주지는 않는다. 그 차이가 프로덕션의 경계다.

핵심 컴포즈에는 앱이 정의된 상태를 계속 유지하게 하는 기능이 없다. 컨테이너가 죽으면 죽은 채로 남는다. 이것이 컴포즈와 오케스트레이터를 가르는 결정적 차이다.

도커 컴포즈의 역할

  • 도커 컴포즈는 쿠버네티스나 도커 스웜 같은 완전한 컨테이너 플랫폼이 아니다.
  • 앱이 지속적으로 정의된 상태를 유지하도록 하는 기능이 없다.
  • 다만 컨테이너 클러스터를 운영할 계획이 없는 소규모 앱이라면 도커 컴포즈로도 충분하다.

앱 운영의 어떤 과정에서 써야 할까

단계컴포즈의 역할적합도
Dev / E2E TestE2E 테스트를 위한 서비스 구성이 필요할 때 앱을 실행✓
CI 파이프라인빌드 및 자동화된 테스트에 컴포즈로 앱을 실행✓
Test / QA단일 서버에서 앱을 실행해 테스트. 테스트 환경을 최소한으로 유지✓
프로덕션도커 스웜이나 쿠버네티스를 쓰는 게 옳다. 다만 앱 정의에는 컴포즈 파일 포맷을 여전히 쓴다✗
i

그래도 프로덕션에서 굴려야 한다면 보강

컴포즈에도 restart 정책이 있어서 컨테이너가 종료됐을 때 다시 띄우는 것까지는 된다 (restart: always / unless-stopped). 여기에 8-4 의 헬스체크를 더하면 단일 서버 수준의 자동 복구는 흉내 낼 수 있다.

하지만 이것은 한 대 안에서만 유효하다. 그 서버 자체가 죽으면 앱도 함께 죽고, 다른 노드로 옮겨 붙일 방법이 없다. 여러 대에 걸쳐 상태를 지켜 주는 것이 12장 의 오케스트레이터가 하는 일이다.

정리

  • 컴포즈는 상태를 만들지만 유지하지는 않는다. 죽은 컨테이너를 되살리는 건 오케스트레이터의 몫이다.
  • 개발 / CI / QA 에는 컴포즈로 충분하고, 프로덕션은 스웜이나 쿠버네티스로 간다.
  • 플랫폼이 바뀌어도 앱 정의 포맷은 컴포즈 파일 형식을 계속 쓴다.
CH 8

헬스체크와 디펜던시 체크로 앱의 신뢰성 확보하기

프로세스가 살아 있다고 앱이 살아 있는 건 아니다. HEALTHCHECK 로 진짜 상태를 알리고, 디펜던시 체크로 기동 순서 의존을 없앤다.

ITEM 8-1

헬스체크를 지원하는 도커 이미지 만들기

도커는 기본적으로 프로세스가 살아 있는지만 본다. 앱이 일을 하는지는 이미지가 직접 알려 줘야 한다.

핵심 HEALTHCHECK 는 앱의 실제 상태를 도커에게 알려 주는 계약이다. 도커는 그 결과를 상태로 기록만 하고, 그것을 보고 무엇을 할지는 오케스트레이터가 결정한다.

도커가 확인하는 앱의 상태

  • 도커는 컨테이너 내부 앱의 프로세스 실행 상태를 감지한다.
  • 프로세스가 종료되면 도커 컨테이너도 같이 종료된다.

프로세스만 확인하는 방법의 문제점

프로세스가 여전히 실행 중이어도 실제 앱이 API 요청을 처리할 수 없다면 죽은 것과 다름없다.

STATUS 는 Up 24 seconds 인데 모든 요청이 500 을 뱉는다. 로드밸런서도, 오케스트레이터도, 모니터링도 이 컨테이너를 정상으로 판단해 계속 트래픽을 보낸다. 프로세스 생존 여부만으로는 앱의 상태를 알 수 없다.

HEALTHCHECK 인스트럭션

  • 도커는 앱이 실제로 정상인지 확인하는 로직을 이미지에 넣을 수 있는 기능을 제공한다.
  • --fail 옵션을 붙이면 curl 이 받은 HTTP 상태를 종료 코드로 도커에 전달한다.
  • 헬스체크 주기는 기본 30초 간격이며, 3번 이상 실패하면 비정상으로 간주한다.
Dockerfile.v2 
# multi-stage build commands...

FROM diamol/dotnet-aspnet

ENTRYPOINT ["dotnet", "/app/Numbers.Api.dll"]
HEALTHCHECK CMD curl --fail http://localhost/health

WORKDIR /app
COPY --from=builder /out/ .
!

원문 보강 — 종료 코드 2 는 예약값이다 원문 교정

노트에는 "0 은 정상, 이외는 모두 비정상"으로 적혀 있지만, 공식 Dockerfile 레퍼런스는 세 가지를 구분한다.

종료 코드의미
0success — 컨테이너가 정상이며 사용 가능
1unhealthy — 컨테이너가 정상 동작하지 않음
2reserved — 예약값이므로 사용하지 말 것

커스텀 체크 스크립트를 만들 때 exit 2 를 쓰지 않도록 주의한다. 실패는 반드시 exit 1 로 표현한다.

HEALTHCHECK 옵션 기본값 (공식 문서 기준) 보강

옵션기본값의미

--timeout30s이 시간을 넘기면 실패로 간주하고 SIGKILL

헬스체크가 실패해도 변화가 없는 이유

  • 헬스체크에 실패했다면 무언가 조치를 해서 앱을 다시 띄워야 할 것 같은데 변화가 없다.
  • 도커가 이런 컨테이너를 감지해 재시작할 수는 있지만, 재시작하는 동안 앱은 중단된다.
  • 컨테이너 교체 작업이 상황을 더 악화시키지 않으리라는(스토리지 초기화 등) 보장이 없어 그대로 둔다.
  • 도커 스웜이나 쿠버네티스로 클러스터링을 한다면, 이 헬스체크를 근거로 고가용성을 보장할 수 있다.

역할 분담이 명확하다

이미지는 상태를 알리고, 플랫폼은 그 상태를 보고 조치한다. 단일 도커 엔진에는 "여분의 컨테이너를 먼저 띄운 뒤 옛것을 내린다"는 개념이 없으므로 섣불리 재시작하지 않는 것이 안전한 선택이다. 스웜이나 쿠버네티스에는 그 개념이 있으므로 같은 헬스체크가 실제 자동 복구로 이어진다.

정리

  • 프로세스 생존만으로는 앱 상태를 알 수 없다. Up 인데 전부 500 일 수 있다.
  • HEALTHCHECK 로 앱이 직접 상태를 알린다. 0 = 정상, 1 = 비정상, 2 는 예약값.
  • 기본값은 30초 간격 / 30초 타임아웃 / 3회 연속 실패. 기동이 느리면 --start-period 를 준다.
  • 단일 엔진은 상태를 기록만 한다. 조치는 오케스트레이터의 몫이다.
ITEM 8-2

디펜던시 체크가 적용된 컨테이너 실행하기

의존 대상이 준비되지 않았다면 아예 시작하지 않고 죽는 편이 낫다.

핵심 디펜던시 체크에는 전용 인스트럭션이 없다. 실행 명령 앞에 체크 로직을 붙이고 && 로 이어 붙이는 방식으로 구현한다. 실패하면 컨테이너가 그대로 종료된다.

분산 앱에서 발생할 수 있는 문제

  • 예를 들어 API 서버와 웹 서버를 띄운다고 하자.
  • 아직 API 서버가 준비되지 않았거나 에러가 난 상태에서 웹 서버를 시작하면 문제가 생긴다.
  • 이상이 생긴 컨테이너를 교체할 때는 처음 앱을 실행할 때처럼 컨테이너 간 의존 관계를 고려하지 않기 때문이다.

문제 상황

  • 기존에 있던 API 서버를 삭제하고 진행한다.
  • 웹에 접속은 되지만 숫자를 요청하면 에러가 발생한다.

  • 실패 시 컨테이너가 종료되는 것이 정상이다. 재시도는 플랫폼이 맡는다.
ITEM 8-3

앱 체크를 위한 커스텀 유틸리티 만들기

체크하려고 curl 을 넣는 순간, 공격자에게 다운로드 도구를 쥐여 준 셈이 된다.

핵심 체크 유틸리티를 앱과 같은 언어로 만들면 추가 소프트웨어 없이 체크가 가능하고, 앱의 설정을 그대로 재사용할 수 있으며, 플랫폼이 바뀌어도 그대로 동작한다.

유틸리티를 만드는 이유

  • 모순 같지만, 앞 절에서는 curl 정도로 충분하다고 했다.
  • 하지만 실무에서는 테스트를 위해 curl 을 쓰지 않는다. 보안 정책상 포함이 불가능한 경우가 많다.
  • 도커 이미지에는 앱을 구동하기 위한 최소한의 내용만 들어가야 한다.
  • 이런 이유로 앱과 같은 언어로 만든 별도의 유틸리티를 쓰는 편이 낫다.

커스텀 유틸리티의 장점

  • 앱과 같은 코드 / 도구라서 별도의 추가 소프트웨어를 포함하지 않아도 된다.
  • 셸 스크립트로 표현하기 까다로운 로직을 작성할 수 있다.
  • 앱과 같은 설정을 사용해 누락되는 부분을 최소화할 수 있다.
  • 앱과 같은 환경에서 실제 컨테이너 실행 전에 모든 사항을 검증할 수 있다.

앱과 체크 유틸리티를 각자의 스테이지에서 빌드해 최종 이미지에 함께 담는다 — SDK 는 두 빌더 스테이지에만 있고, 최종 이미지에는 런타임과 두 개의 dll 만 남는다. curl 을 넣을 필요가 없어진다.

정리

  • 체크를 위해 curl 을 넣으면 공격자에게도 다운로드 도구를 주는 셈이다.
  • 앱과 같은 언어로 만든 체크 유틸리티를 별도 빌드 스테이지에서 만들어 최종 이미지에 함께 담는다.
  • URL 대신 설정 키를 넘겨 앱과 체크가 같은 설정을 보게 한다.
  • --health-interval 로 실행 시점에 주기를 조절할 수 있다.
ITEM 8-4

도커 컴포즈에 헬스 체크와 디펜던시 체크 정의하기

기동 순서를 보장하는 대신, 순서가 틀려도 결국 맞춰지게 만든다.

핵심 depends_on 을 빼고 헬스체크 + restart: on-failure 조합으로 가면, 기동 순서를 보장하지 않아도 재시도를 거쳐 결국 정상 상태에 도달한다.

도커 컴포즈의 헬스체크 옵션

컴포즈 설정에서는 헬스체크 관련 옵션을 더 세세하게 지정할 수 있다.

옵션의미
interval헬스체크 실시 간격
timeout언제까지 응답을 받지 못하면 실패로 처리할지
retries상태를 이상으로 간주할 때까지 필요한 연속 실패 횟수
start_period컨테이너 실행 후 몇 초 뒤에 헬스체크를 처음 시작할지. 부트스트랩이 오래 걸리는 앱은 조절이 필요하다

원문 교정 — 오탈자 원문 교정

원문의 retires 는 retries 의 오타다.

docker-compose.yml

  numbers-api:
    image: diamol/ch08-numbers-api:v3
    ports:
      - "8087:80"
    healthcheck:

      retries: 2
      start_period: 5s
    networks:
      - app-net

디펜던시 체크와 재시작 정책

  • restart: on-failure 로 컨테이너 시작 실패 시 재시작하게 한다.
  • 미리 정의해 둔 유틸리티로 헬스체크와 의존 관계 체크를 함께 수행한다.
docker-compose.yml 
services:
  numbers-web:
    image: diamol/ch08-numbers-web:v3
    restart: on-failure
    environment:
      - RngApi__Url=http://numbers-api/rng
    ports:
      - "8088:80"
    healthcheck:
      test: ["CMD", "dotnet", "Utilities.HttpCheck.dll", "-t", "150"]
      interval: 5s
      timeout: 1s
      retries: 2
      start_period: 10s
    networks:
      - app-net

이 스크립트에 대한 의문점

  • 이전 스크립트에서는 depends_on 으로 의존 관계를 설정했다.
  • 여기서 쓰지 않은 이유는, 도커 컴포즈가 의존 관계 체크를 할 수 있는 범위가 단일 서버로 제한되기 때문이다.
  • 실제 운영 환경에서는 무슨 일이 벌어질지 예측하기 어렵기 때문에 이 속성을 제거했다.
  • 이 스크립트는 실행 순서를 보장하지 않지만, 헬스체크와 restart 옵션을 통해 결국 컨테이너가 정상 상태에 도달한다.

  C["Created (디펜던시 체크 수행)"] -->|"API 아직 준비 안 됨"| E["Exited (체크 실패)"]
  E -->|"restart: on-failure 로 재시작"| C
  C -->|"API 준비 완료"| U["Up / healthy"]
순서를 보장하는 대신 될 때까지 다시 시도한다 — 웹이 API 보다 먼저 떠도 디펜던시 체크에 걸려 종료되고, restart: on-failure 가 다시 띄운다. API 가 준비되는 순간 그 재시도가 성공한다.

지금은 depends_on 으로도 준비 완료를 기다릴 수 있다 최신 반영

노트가 depends_on 을 뺀 것은 "시작만 확인하고 준비는 확인하지 못한다"는 한계 때문이었다. 현재 컴포즈 스펙은 긴 문법으로 조건을 지정할 수 있어서 헬스체크 통과까지 대기가 가능하다.

compose.yaml 현재 가능 
  numbers-web:
    depends_on:
      numbers-api:
        condition: service_healthy    # 헬스체크 통과까지 대기
        restart: true                 # 의존 서비스가 갱신되면 이 서비스도 재시작

다만 이것은 단일 호스트 안에서만 유효하다는 원문의 지적은 여전히 옳다. 클러스터로 나가면 컴포즈가 기동 순서를 통제할 수 없으므로, 앱 자체가 의존 대상의 부재를 견디도록 만드는 것이 근본 해법이라는 결론은 그대로다.

i

restart 정책 네 가지 보강

값동작
no기본값. 재시작하지 않는다
on-failure0 이 아닌 종료 코드로 끝났을 때만 재시작
always어떤 이유로 종료돼도 재시작. 도커 재시작 시에도 다시 뜬다
unless-stoppedalways 와 같지만, 사람이 명시적으로 멈춘 것은 다시 띄우지 않는다

디펜던시 체크에는 on-failure 가 맞다. 체크 실패는 0 이 아닌 코드로 끝나므로 재시도되고, 정상 종료는 재시작되지 않기 때문이다.

정리

  • 컴포즈의 healthcheck 로 interval/timeout/retries/start_period 를 세밀히 지정한다.
  • 기동 순서를 보장하는 대신 헬스체크 + restart: on-failure 로 수렴시킨다.
  • 현재는 depends_on + condition: service_healthy 로 준비 완료 대기가 가능하다. 단, 단일 호스트 한정.
ITEM 8-5

헬스체크와 디펜던시 체크로 복원력 있는 앱을 만들 수 있는 이유

순서를 맞추려 애쓰는 대신, 순서가 틀려도 스스로 회복하는 앱을 만든다.

핵심 일시적인 에러를 플랫폼이 알아서 해결하게 만드는 것이 자기 수복이다. 앱은 상태를 정직하게 알리고, 플랫폼은 그 신호를 보고 컨테이너를 갈아 끼운다.

헬스체크와 디펜던시 체크가 활약하는 부분

  • 이 두 기능을 쓰면 굳이 플랫폼이 실행 순서를 보장할 필요가 없다.
  • 대규모 시스템이라도 최대한 빠르게 뜨고, 반복적인 체크를 통해 빠르게 정상 상태로 올리면 된다.
  • 클러스터링된 여러 컨테이너 중 하나에서 에러가 발생하면 다른 컨테이너를 빠르게 띄울 수 있다.

자기 수복 능력

일시적인 에러를 플랫폼에서 해결해 주는 것을 말한다.

앱 시작 시 라이프사이클
시작 실패는 최종 상태가 아니라 경유 상태다 — 의존 대상이 준비될 때까지 Exited → 재시작을 반복하다가 결국 healthy 로 수렴한다.
앱 가동 중 라이프사이클
된 다음 기존 컨테이너를 종료하는 순서가 중요하다
새 컨테이너가 healthy 가 된 뒤에 옛 컨테이너를 내린다 — 순서가 반대면 그 사이에 서비스가 비게 된다. 이 순서를 지켜 주는 것이 오케스트레이터의 역할이다.
!

자기 수복이 고칠 수 있는 것과 없는 것 보강

컨테이너 교체로 해결되는 것은 일시적인(transient) 문제뿐이다. 메모리 누수, 커넥션 고갈, 데드락처럼 재시작하면 초기화되는 상태가 여기 해당한다.

반대로 영속적인 문제는 재시작이 오히려 상황을 악화시킨다. DB 가 내려갔거나 설정이 잘못됐다면, 컨테이너는 뜨고 죽기를 무한 반복하면서 의존 대상에 재접속 폭풍을 일으킨다. 그래서 자기 수복은 모니터링과 함께 운영해야 한다. 재시작 횟수 자체를 지표로 잡아 두면 "고쳐지고 있는 것"과 "무한 반복 중인 것"을 구분할 수 있다. 이것이 9장 의 주제다.

정리

  • 기동 순서를 보장하는 대신, 순서가 틀려도 재시도로 수렴하게 만든다.
  • 가동 중 문제는 새 컨테이너를 먼저 healthy 로 만든 뒤 옛것을 내리는 순서로 교체한다.
  • 자기 수복이 고치는 건 일시적 문제뿐이다. 영속적 문제는 무한 재시작으로 이어지므로 모니터링이 필요하다.
CH 9

컨테이너 모니터링으로 투명성 있는 앱 만들기

떴다 사라지는 컨테이너를 어떻게 감시할 것인가. 프로메테우스가 /metrics 를 긁어 오고, 그라파나가 그것을 화면으로 만든다.

ITEM 9-1

컨테이너화된 앱에서 사용되는 모니터링 기술 스택

감시 대상이 계속 떴다 사라지는 환경에서는, 서버를 지켜보는 방식이 통하지 않는다.

핵심 프로메테우스는 앱의 언어와 무관하게 /metrics 라는 하나의 규약으로 측정값을 모은다. 그 덕에 자바든 고든 닷넷이든 같은 방식으로 감시할 수 있다.

일반 환경에서의 모니터링

  • 단일 서버에서 앱이 동작하는 경우, 모니터링이라고 하면 디스크 공간 / RAM / CPU 같은 것들이다.
  • 보통 대시보드가 있고 임계치를 넘어가면 알람이 발생하는 구조다.

컨테이너 환경에서의 모니터링

  • 정적인 컨테이너나 고정된 IP 없이도 실행 중인 앱을 확인할 수 있는 모니터링 방식이 필요하다.

프로메테우스(Prometheus)

  • CNCF 에서 개발을 담당하고 있으며 널리 쓰인다.
  • 마찬가지로 컨테이너에서 동작하기 때문에 분산 앱에 어렵지 않게 모니터링을 붙일 수 있다.
  • 앱의 프로그래밍 언어와 무관하게 모든 앱을 표준적인 형태로 모니터링할 수 있어 일관성을 보장한다.
  • 도커 엔진의 측정값도 뽑아낼 수 있다.
i

프로메테우스의 위상 보강

프로메테우스는 2016년 5월 CNCF 에 쿠버네티스 다음 두 번째로 합류했고, 2018년 8월 9일 Graduated(졸업) 등급이 됐다. 사실상 컨테이너 환경 메트릭의 표준이다. 수집 모델은 풀(pull) 이며, 짧게 살다 죽는 배치 작업만 예외적으로 Pushgateway 라는 중계 서버를 통해 푸시한다.

  • 프로메테우스는 CNCF 졸업 프로젝트이며 /metrics 를 주기적으로 긁어 오는 풀 방식이다.
  • 도커 엔진도 metrics-addr 을 열면 같은 형식으로 측정값을 낸다.
  • 수집 시 job / instance 라벨이 자동으로 붙어 인스턴스를 구분할 수 있다.
ITEM 9-2

앱의 측정값 출력하기

엔진 메트릭은 켜기만 하면 되지만, 앱 메트릭은 앱이 직접 내보내야 한다.

핵심 클라이언트 라이브러리를 붙이면 런타임 수준의 측정값은 공짜로 따라온다. 진짜 가치는 그 위에 얹는 연산 중심 / 비즈니스 중심 지표에 있다.

앱의 측정값

  • 앱의 유용한 정보를 측정값으로 구성하려면 API 엔드포인트로 출력해야 해서, 도커 엔진 측정값보다는 좀 더 복잡하다.
  • 각 프로그래밍 언어별로 공식 또는 비공식 라이브러리가 존재한다.
  • 보통 수집되는 정보는 런타임 수준의 측정값이다. 예를 들면
    • Go — 활성 상태인 고루틴의 개수
    • Java — JVM 의 메모리 사용량

ITEM 9-3

측정값 수집을 맡을 프로메테우스 컨테이너 실행하기

고정된 컨테이너는 static_configs, 늘었다 줄었다 하는 것은 dns_sd_configs.

핵심 스케일 아웃하는 서비스를 감시하려면 주소를 적어 두는 대신 DNS 로 찾게 해야 한다. dns_sd_configs 가 7-3 의 DNS 디스커버리를 그대로 활용한다.

프로메테우스의 데이터 수집

  • 프로메테우스는 대상 시스템에서 데이터를 받아 오는 폴링 방식으로 동작한다.
  • 이 과정을 스크래핑(scraping) 이라고 부른다.

프로메테우스 설정

  • scrape_interval — 스크래핑 주기를 기본값인 10초로 지정
  • static_configs — 정적 설정으로 단일 컨테이너를 지정
  • dns_sd_configs — 도커의 DNS 디스커버리 기능으로 여러 개의 컨테이너를 지정
prometheus.yml 
global:
  scrape_interval: 10s

scrape_configs:
  - job_name: "image-gallery"
    metrics_path: /metrics
    static_configs:
      - targets: ["image-gallery"]

  - job_name: "iotd-api"
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["iotd"]

  - job_name: "access-log"
    metrics_path: /metrics
    scrape_interval: 3s
    dns_sd_configs:
      - names:
          - accesslog
        type: A
        port: 80

  - job_name: "docker"
    metrics_path: /metrics
    static_configs:
      - targets: ["DOCKER_HOST:9323"]
대상 수가 고정이면 정적 설정, 변하면 DNS 디스커버리 — accesslog 만 dns_sd_configs 인 이유는 이것만 --scale 로 늘리기 때문이다.

counter 는 보통 그대로 보지 않는다 보강

counter 는 계속 누적되므로 그래프가 늘 우상향한다. 실무에서 알고 싶은 것은 보통 "지금 초당 몇 건인가" 이고, 그럴 때는 rate() 를 씌운다. sum(rate(access_log_total[1m])) without(hostname, instance) 처럼 쓰면 분당 증가율을 초당 건수로 환산해 준다. counter 는 컨테이너가 재시작하면 0 으로 돌아가는데, rate() 는 그 리셋을 자동으로 보정해 준다는 이점도 있다.

정리

  • 프로메테우스는 scrape_interval 마다 대상의 /metrics 를 긁는다(스크래핑).
  • 고정 대상은 static_configs, 개수가 변하는 대상은 dns_sd_configs.
  • 인스턴스별 라벨이 분리되어 있어 부하 편차까지 보인다.
  • PromQL 의 sum() ... without() 으로 라벨을 접어 합칠 수 있다. counter 에는 rate() 를 씌운다.

ITEM 9-5

투명성의 수준

개념 검증과 실제 제품을 가르는 것 중 하나가 "지금 무슨 일이 일어나는지 볼 수 있는가"다.

핵심 수십 개의 패널보다 중요한 것은 앱 전체를 한 화면에 조망하는 대시보드 하나다. 가장 중요한 지표만 모아 한 화면에 담을 수 있어야 한다.

투명성(Observability)

  • 간단한 개념 검증 수준의 앱에서 실제 제품으로 나아가려면 투명성이 필요하다.
  • 실제 운영 환경에서는 대시보드가 꼭 필요한데, 그중에서도 앱의 전체 상황을 조망하는 대시보드가 중요하다.
  • 측정값 중 앱에 가장 중요한 데이터를 모아 하나의 화면으로 구성할 수 있어야 한다.

투명성 아키텍처 한눈에 보기

세 층이 각자 한 가지 일만 한다 — 앱과 엔진은 /metrics 로 내보내고, 프로메테우스는 모아서 저장하고, 그라파나는 보여 준다. 각 층이 독립적이라 어느 하나를 바꿔도 나머지는 그대로 둘 수 있다.
i

메트릭만으로는 부족하다 보강

여기서 다룬 것은 관측 가능성의 세 기둥 중 메트릭 하나다. 메트릭은 "무언가 이상하다"를 빠르게 알려 주지만 "왜"를 말해 주지 못한다. 나머지 두 기둥은 로그(무슨 일이 있었는지)와 트레이스(요청이 어느 구간에서 느려졌는지)다. 메트릭으로 이상을 감지하고, 트레이스로 구간을 좁히고, 로그로 원인을 확인하는 흐름이 표준이다.

정리

  • 투명성은 제품 수준으로 가기 위한 필수 조건이다.
  • 앱 전체를 조망하는 대시보드 하나가 패널 수십 개보다 중요하다.
  • 내보내기 / 수집 / 시각화 세 층이 독립적이라 각각 교체할 수 있다.
  • 메트릭은 이상 감지용이다. 원인 규명에는 로그와 트레이스가 함께 필요하다.

프로젝트 이름을 폴더명에 맡기지 말 것 보강

기본 프로젝트 이름이 폴더명이라는 것은 곧, 같은 저장소를 다른 이름의 폴더에 clone 하면 다른 앱으로 인식된다는 뜻이다. CI 서버의 작업 디렉터리 이름이 매번 달라지면 기존 컨테이너를 재사용하지 못하고 계속 새 프로젝트가 쌓인다. 프로젝트 이름은 -p 플래그, 환경 변수 COMPOSE_PROJECT_NAME, 또는 컴포즈 파일 최상위의 name: 필드로 명시해 고정하는 편이 안전하다.

compose.yaml 권장 
name: todo-list       # 폴더명과 무관하게 프로젝트 이름을 고정

services:
  todo-web:
    image: diamol/ch06-todo-list

정리

  • 컴포즈는 프로젝트 이름으로 리소스 소유권을 판단한다. 같은 이름이면 재사용, 다르면 별개의 앱.
  • -p 로 프로젝트를 나누면 같은 파일로 여러 벌을 한 서버에 띄울 수 있다.
  • 리소스 이름은 프로젝트-서비스-번호 형식이고, 서비스 이름은 DNS 이름이기도 하다.
  • 기본 프로젝트 이름이 폴더명이므로, 중요한 환경에서는 name: 으로 고정한다.
ITEM 10-2

도커 컴포즈의 오버라이드 파일

환경마다 파일을 통째로 복사하면 90%가 중복된다. 달라지는 부분만 얹는다.

핵심 -f 로 나열한 파일은 순서대로 병합된다. 뒤에 온 파일이 앞을 덮으므로 순서가 곧 우선순위이며, 순서를 잘못 주면 엉뚱한 결과가 나온다.

한 개의 앱을 여러 개의 설정으로 켜야 할 때

  • 대부분은 컴포즈 파일을 환경마다 하나씩 두는 방법을 쓴다.
  • 이 방법은 컴포즈 파일 내용이 90% 이상 중복된다.
  • 더 나은 방법은 나중에 지정된 파일이 이전 파일의 내용을 덮어쓰기(override) 하는 방식이다.
베이스 한 장 + 환경별 차이만 담은 얇은 파일 — 공통 서비스 정의는 한 곳에만 있으므로 고칠 곳도 한 군데다.

덮어쓰기 구성하기

  • 오버라이드 파일에는 해당 환경에서 변경할 항목만 적으면 된다.
  • config 부명령으로 병합 결과가 유효한지 검증할 수 있다. 검증과 결과 출력만 하고 실제로 실행하지는 않는다.
  • 덮어쓰기할 순서대로 -f 플래그로 파일을 나열해야 한다. 순서가 잘못되면 이상한 결과가 나올 수 있다.
docker-compose.yml 
services:
  todo-web:
    image: diamol/ch06-todo-list
    ports:
      - 80
    environment:
      - Database:Provider=Sqlite
    networks:
      - app-net

networks:
  app-net:
docker-compose-v2.yml 
services:
  todo-web:
    image: diamol/ch06-todo-list:v2

docker-compose config

스칼라는 덮어쓰지만 리스트는 합쳐진다 보강

병합 규칙이 항목 종류마다 다르다는 점이 함정이다. image 같은 단일 값은 뒤의 파일이 덮어쓰지만, ports / volumes 같은 리스트는 합쳐진다. 운영 파일에서 포트를 지우려고 ports 를 다시 쓰면 지워지는 게 아니라 포트가 두 개가 되어 버린다.

그래서 원칙은 베이스에는 모든 환경의 공통분모만 넣는 것이다. 일부 환경에서만 필요한 포트나 볼륨은 베이스가 아니라 그 환경 파일에 적는다. 병합 결과가 의심스러우면 실행 전에 반드시 config 로 확인한다.

실전 예제

  • docker-compose.yml — 베이스 파일
  • docker-compose-dev.yml — 개발용. 헬스 / 디펜던시 체크 비활성화
  • docker-compose-test.yml — CI 환경용. API 포트 미공개
  • docker-compose-uat.yml — 인수 테스트용. 모든 테스트를 꼼꼼히 수행

원문 교정 — 환경별 env 파일도 가능하다 원문 교정

노트에는 ".env 파일만 인식하기 때문에 환경별로 만드는 건 불가능하다"고 적혀 있으나, 컴포즈는 --env-file 플래그로 다른 파일을 지정할 수 있다. 공식 문서가 명시하는 보간(interpolation) 우선순위는 다음과 같다.

  1. 셸 환경 변수

    가장 우선한다.

  2. --env-file 로 지정한 파일

    지정하면 프로젝트 디렉터리의 .env 를 대체한다.

  3. 프로젝트 디렉터리의 .env

    --env-file 이 없을 때만 쓰인다.

terminal 환경별 분리 
$ docker compose --env-file ./config/dev.env  -p dev  up -d
$ docker compose --env-file ./config/prod.env -p prod up -d

다만 "기본 이름은 .env 하나뿐"이라는 원문의 관찰은 정확하다. 플래그 없이 자동으로 읽히는 파일은 여전히 .env 하나다.

정리 — 어떤 방법을 언제 쓸까

environment
  • 프로퍼티로 환경 변수를 지정하는 가장 간단하고 가독성 좋은 방법이다.
  • 평문으로 작성되기 때문에 민감한 정보에는 쓰지 않는 것이 좋다.
비밀값에 설정값 지정
  • 유출될 여지도 적고 런타임에도 적용 가능해서 유연성이 매우 뛰어나다.
  • 비밀값의 실제 값은 로컬 파일 시스템이나 관련 플랫폼에 저장할 수 있다.
  • 값이 어디 있건 앱이 실행될 때 컨테이너 내부의 특정 파일로 전달된다.
설정값을 파일에 저장하고 env_file 에 경로를 지정하는 방법
  • 여러 서비스가 공유하는 설정이 많은 경우 유용하다.
  • 컴포즈가 로컬 파일을 읽어 각 설정값을 지정하므로, 원격에서 실행 중인 도커 엔진을 다룰 때도 로컬 PC 의 설정값을 적용할 수 있다.
.env 파일
  • 환경을 막론하고 기본 설정을 지정할 때 유용하다.
i

한 번에 보는 선택 기준 보강

방법적용 대상민감 정보주 용도
environment컨테이너 환경 변수✗ 부적합짧고 명확한 설정
env_file컨테이너 환경 변수✗ 부적합여러 서비스가 공유하는 설정 묶음
secrets컨테이너 안의 파일✓ 상대적으로 안전커넥션 스트링, 키
.env컴포즈 파일 자체의 ${VAR}✗ 부적합포트 / 태그 등 기본값

.env 와 env_file 은 이름이 비슷하지만 층이 다르다. .env 는 컴포즈 파일을 읽는 시점에 ${VAR} 를 치환하고, env_file 은 컨테이너 안 프로세스의 환경 변수를 채운다. environment 로 넘긴 값은 docker inspect 에 그대로 노출되므로 비밀번호는 반드시 secrets 쪽으로 보낸다.

정리

  • 설정 주입 통로는 environment / env_file / secrets / .env 네 가지다.
  • .env 는 컴포즈 파일의 ${VAR} 치환용, env_file 은 컨테이너 환경 변수용으로 층이 다르다.
  • 민감한 값은 secrets 로 파일 주입한다. 환경 변수는 inspect 에 노출된다.
  • --env-file 로 환경별 env 파일을 쓸 수 있다. 자동으로 읽히는 이름만 .env 하나다.

확장 필드로 중복 제거하기

노트에서는 "잘 안 쓰므로 패스"로 넘어간 절. 무엇을 넘겼는지만 짧게 남겨 둔다.

i

원문 노트에서는 "잘 안 쓰므로 패스"로 넘어간 절이다

나중에 필요해질 때 되돌아올 수 있도록 골자만 남긴다.

무엇을 푸는 기능인가

10-2 의 오버라이드는 파일 사이의 중복을 없앤다. 확장 필드는 한 파일 안, 서비스 사이의 중복을 없앤다. 서비스가 여러 개인데 로깅 설정이나 네트워크 지정이 똑같이 반복될 때 쓴다.

기본 골자

x- 로 시작하는 최상위 키는 컴포즈가 무시한다. 여기에 공통 조각을 정의해 두고, YAML 의 앵커(&)와 별칭(*), 병합 키(<<)로 각 서비스에 끌어다 쓴다.

중복 
services:
  api:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
  web:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
확장 필드 
x-logging: &default-logging
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"

services:
  api:
    logging: *default-logging
  web:
    logging: *default-logging
!

파일 하나 안에서만 유효하다 보강

앵커와 별칭은 YAML 파서 수준의 기능이라 같은 파일 안에서만 해석된다. 베이스 파일에 정의한 앵커를 오버라이드 파일에서 참조할 수는 없다. 그래서 "파일 사이 중복은 오버라이드, 파일 안 중복은 확장 필드"로 역할이 갈린다. 노트가 이 절을 건너뛴 것도 무리는 아니다. 서비스가 서너 개 수준이면 중복을 그냥 두는 편이 오히려 읽기 쉽다.

정리

  • x- 로 시작하는 최상위 키는 컴포즈가 무시하므로 공통 조각을 담아 둘 수 있다.
  • YAML 앵커 / 별칭으로 서비스마다 끌어다 쓴다.
  • 같은 파일 안에서만 동작한다. 파일 사이 중복은 오버라이드로 푼다.
  • 서비스가 적으면 굳이 쓸 필요 없다.
ITEM 10-5

도커를 이용한 설정 워크플로 이해하기

여기까지 배운 것을 한 문장으로 묶으면 — 이미지는 그대로 두고 설정만 바꿔 가며 승격시킨다.

핵심 모든 환경에서 동일한 이미지를 사용한다. 이것이 이 장 전체의 결론이며, "테스트 환경에서 통과한 그 이미지"가 그대로 운영에 가는 유일한 방법이다.

앱 구성 요소의 조합

  • 모든 환경에서 전체 스택을 실행할 필요는 없다.
  • 오버라이드 파일을 써서 공통 서비스는 그대로 두고, 환경마다 필요한 서비스를 달리하는 설정을 깔끔하게 작성할 수 있다.

컨테이너 설정

  • 각 환경의 상황과 요구 사항에 맞춰 설정을 바꿀 필요가 있다.
  • 오버라이드와 네트워크를 통해 단일 서버에 격리된 여러 앱을 실행할 수 있다.

앱 설정

  • 환경별로 컨테이너 내부 동작이 달라야 하는 경우가 있다.
  • 로그 수준, 캐시 크기 등을 상황에 맞게 컨테이너에 주입할 수 있다.

중요한 점

  • 모든 환경에서 동일한 이미지를 사용하게 된다.
  • 최종적으로 여러 단계를 거쳐 프로덕션에 배포할 수 있게 된다.
flowchart LR

화살표가 전부 같은 이미지에서 나온다 — 환경마다 다시 빌드하지 않는다. 바뀌는 것은 오버라이드 파일과 주입되는 설정뿐이고, 단계를 통과할 때마다 같은 산출물이 승격된다.
✓

환경마다 다시 빌드하면 무엇이 깨지는가

운영 배포 직전에 docker build 를 다시 돌리면, 그것은 테스트를 통과한 이미지가 아니다. 기반 이미지의 latest 가 그사이 바뀌었을 수도, 패키지 저장소의 버전이 올라갔을 수도 있다. 테스트가 검증한 대상과 운영에 나가는 대상이 달라지는 순간, 그 테스트는 아무것도 보증하지 못한다.

그래서 파이프라인은 한 번 빌드하고, 태그를 붙이고, 그 태그를 각 환경으로 옮긴다. 이 원칙이 5-4 의 태그 전략과 11장 의 CI 절차를 하나로 묶는다.

정리

  • 환경 차이는 이미지가 아니라 오버라이드 파일과 주입 설정으로 표현한다.
  • 모든 환경이 같은 이미지를 쓴다. 이것이 테스트가 의미를 갖는 조건이다.
  • 단계를 통과할 때마다 같은 산출물이 다음 환경으로 승격된다.
CH 11

도커, 컴포즈를 통한 앱 빌드 및 테스트

CI 서버에 언어 런타임을 깔지 않는다. 빌드도 테스트도 컨테이너 안에서 돌면 파이프라인이 어디서든 같은 결과를 낸다.

ITEM 11-1

도커를 이용한 CI 절차

CI 서버가 아무것도 설치하지 않아도 되게 만드는 것. 그것이 도커가 CI 에 가져오는 변화다.

핵심 빌드도 테스트도 컨테이너 안에서 돌면, CI 서버가 바뀌어도 결과가 같다. 자동화된 테스트를 이미지 빌드 단계에 넣으면 테스트 실패가 곧 빌드 실패가 된다.

CI 에서 어려운 점

  • 모든 CI 파이프라인은 프로젝트마다 다르다.
  • 도커는 이러한 CI 절차의 일관성을 유지해 준다.
  • 자동화된 테스트 또한 이미지 빌드 단계에 포함되므로, 빌드가 실패하면 CI 도 중단된다.

도커와 함께하는 CI 플로우

세 단계가 모두 컨테이너 안이라는 것이 요점이다 — 코드 로딩만 CI 서버가 하고, 나머지는 전부 도커가 맡는다. 그래서 로컬에서든 CI 에서든 같은 명령으로 같은 결과가 나온다.
i

테스트를 빌드 단계에 넣는다는 것 보강

4-5 의 멀티 스테이지 빌드에서 테스트 스테이지를 하나 두면, 테스트 실패가 곧 docker build 실패가 된다. 별도의 테스트 실행 명령을 파이프라인에 따로 적을 필요가 없고, 테스트를 통과하지 못한 이미지는 애초에 만들어지지 않는다.

Dockerfile 
FROM sdk AS builder
COPY . .
RUN build

FROM builder AS test
RUN test          # 실패하면 여기서 빌드가 멈춘다

FROM runtime
COPY --from=builder /out/ .
✓

배포 단계가 "푸시"인 이유

마지막 단계가 다시 빌드하는 게 아니라 이미 만들어진 이미지를 푸시하는 것임에 주목하자. 10-5 에서 본 "한 번 빌드하고 그 산출물을 승격시킨다"가 파이프라인 위에서 그대로 구현된 모습이다.

정리

  • CI 서버에는 도커만 있으면 된다. 빌드 / 테스트 / 배포가 모두 컨테이너 안에서 돈다.
  • 테스트를 빌드 스테이지에 넣으면 테스트 실패가 곧 빌드 실패가 된다.
  • 배포 단계는 다시 빌드하지 않고 이미 만든 이미지를 푸시한다.
ITEM 11-2

도커를 이용한 빌드 인프라 구축

형상관리 / 레지스트리 / 자동화 서버 세 가지를 컨테이너로 띄우면 사내 파이프라인이 완성된다.

핵심 요즘은 매니지드 서비스가 좋아서 직접 구축할 이유가 줄었다. 그럼에도 폐쇄망처럼 외부로 코드를 내보낼 수 없는 환경에서는 이 구성이 여전히 유효하다.

언제 사용할까

  • 요즈음에는 신뢰성 있는 무료 매니지드 서비스가 많아서 굳이 직접 구축할 필요는 없다.
  • 하지만 폐쇄망 등 외부 네트워크로 공개하기 꺼려지는 경우에 유용하다.
역할이 실습에서 쓰는 도구흔한 매니지드 대안
형상관리GogsGitHub / GitLab

자동화 서버젠킨스GitHub Actions / GitLab CI

i

/etc/hosts 를 왜 건드리나 보강

레지스트리 컨테이너의 이름이 registry.local 이라서, 이미지 이름도 registry.local:5000/... 형태가 된다. 그런데 호스트 PC 는 그 이름을 모른다. 컨테이너끼리는 도커 DNS 로 서로를 찾지만(7-3), 호스트에서 docker push 를 하려면 호스트도 그 이름을 풀 수 있어야 한다. /etc/hosts 한 줄이 그 역할을 한다.

i

젠킨스 컨테이너가 도커를 쓰려면 보강

컨테이너 안의 젠킨스가 docker build 를 실행하려면 도커 API 에 닿아야 한다. 가장 흔한 방법은 호스트의 도커 소켓을 바인드 마운트하는 것이다 (-v /var/run/docker.sock:/var/run/docker.sock).

다만 이것은 사실상 호스트 root 권한을 컨테이너에 넘기는 것과 같다. 소켓에 접근할 수 있으면 특권 컨테이너를 띄우거나 호스트 파일 시스템을 마운트할 수 있기 때문이다. 신뢰할 수 없는 코드를 빌드하는 CI 에서는 특히 위험하므로, 가능하면 원격 빌더나 소켓이 필요 없는 빌드 도구를 검토한다.

정리

  • 형상관리 / 레지스트리 / 자동화 서버 세 가지를 컨테이너로 띄우면 자체 CI 인프라가 된다.
  • 매니지드 서비스가 있으면 그쪽이 낫다. 자체 구축은 폐쇄망 같은 제약이 있을 때의 선택지다.
  • 사내 레지스트리 이름은 호스트에서도 풀려야 하므로 DNS 나 /etc/hosts 설정이 필요하다.
  • CI 컨테이너에 도커 소켓을 마운트하는 것은 편하지만 보안 위험이 크다.
ITEM 11-3

도커 컴포즈를 이용한 빌드 설정

레지스트리 주소를 변수로 빼고, 빌드 번호를 이미지에 새겨 넣는다.

핵심 ARG 는 빌드 시점에만 살아 있고 최종 이미지에 남지 않는다. 반대로 LABEL 은 이미지에 영구히 새겨진다. 이 둘을 짝지어 빌드 정보를 기록한다.

도커 컴포즈 환경 변수 기본값 설정

:- 문법으로 기본값을 지정한다.

docker-compose.yml 
services:
  numbers-api:
    image: ${REGISTRY:-docker.io}/diamol/...
i

:- 와 - 는 다르다 보강

문법동작
${VAR:-기본값}VAR 가 없거나 빈 문자열이면 기본값
${VAR-기본값}VAR 가 정의되지 않았을 때만 기본값 (빈 문자열은 그대로 씀)
${VAR:?메시지}없거나 비었으면 에러로 중단

필수 값에는 :? 를 쓰면 좋다. 값이 빠진 채로 엉뚱한 이미지를 만드는 대신 컴포즈가 그 자리에서 멈춘다.

새로운 인스트럭션

LABEL
  • Dockerfile 에 정의되는 키-값 쌍을 빌드되는 이미지에 적용해 준다.
Dockerfile 
LABEL version=3.0
ARG
  • 이미지를 빌드하는 시점에만 유효한 빌드 전용 변수다.
  • 실제 빌드된 이미지로 실행한 컨테이너에는 적용되지 않는다.
  • 보통 이미지 레이블에 들어갈 값을 제공하기 위해 쓴다.
Dockerfile 
ARG BUILD_NUMBER=0

둘을 함께 쓰기

CI 서버의 빌드 번호를 ARG 로 받아 LABEL 에 새기는 것이 전형적인 조합이다.

Dockerfile 
ARG BUILD_NUMBER=0
LABEL build_number=${BUILD_NUMBER}

ARG 로 비밀값을 넘기지 말 것 보강

ARG 값은 최종 이미지의 환경 변수로 남지는 않지만, docker history 에 그대로 보인다. 공식 문서도 자격 증명이나 API 토큰을 빌드 인자로 넘기지 말라고 명시적으로 경고한다. 빌드 중 비밀값이 필요하면 RUN --mount=type=secret 을 쓴다. 이 방식은 값이 레이어에 남지 않는다.

정리

  • ${VAR:-기본값} 으로 레지스트리 주소 같은 값을 환경에 따라 바꾼다. 필수 값에는 :?.
  • ARG 는 빌드 시점 전용, LABEL 은 이미지에 영구 기록.
  • CI 빌드 번호를 ARG 로 받아 LABEL 에 새기면 이미지 추적이 쉬워진다.
  • ARG 는 docker history 에 노출된다. 비밀값에는 쓰지 않는다.
CH 12

컨테이너 오케스트레이션 — 도커 스웜과 쿠버네티스

한 대에서 여러 대로. 클러스터가 원하는 상태를 스스로 유지하고, 서비스 정의를 바꾸면 롤링 업데이트가 돈다.

ITEM 12-1

컨테이너 오케스트레이션 도구

여러 대의 호스트를 한 대처럼 다루게 해 주는 것. 그리고 원하는 상태를 계속 지켜 주는 것.

핵심 오케스트레이터는 컴포즈가 못 하던 일을 한다 — 선언한 상태를 계속 유지하고, 그 유지를 여러 대의 호스트에 걸쳐 수행한다.

컨테이너 오케스트레이션 도구

  • 기본적으로 클러스터로 구성되는 여러 대의 호스트 컴퓨터를 의미한다.
  • 안정적인 서비스 운영을 위해서는 고가용성이 필요한데, 이때 오케스트레이션 도구가 필요해진다.
  • 작업 분배, 관리, 로드밸런싱 등을 담당한다.
어느 서버에 뜰지는 개발자가 정하지 않는다 — YAML 로 "무엇이 몇 개 떠 있어야 하는가"만 선언하면, 오케스트레이터가 배치와 유지를 맡는다. 도커 API 를 그대로 쓰는 것도 여전하다.

정리

  • 오케스트레이터는 여러 대의 호스트를 하나의 클러스터로 묶어 준다.
  • YAML 로 원하는 상태를 선언하면 배치와 유지는 플랫폼이 맡는다.
  • 스케줄링 / 자동 복구 / 롤링 업데이트가 컴포즈와의 결정적 차이다.
ITEM 12-2

도커 스웜으로 클러스터 만들기

설치할 것이 없다. 도커 엔진에 이미 들어 있고, 명령 하나로 켠다.

핵심 스웜의 가장 큰 장점은 진입 비용이 거의 없다는 것이다. docker swarm init 한 줄이면 그 순간부터 그 머신이 매니저 노드가 된다.

도커 스웜으로 클러스터 만들기

  • 도커 엔진에 내장돼 있어 별도의 설치가 필요 없다.
  • docker swarm init 으로 스웜 모드로 전환한다.
  • 출력의 docker swarm join ... 부분은 다른 PC 를 이 스웜에 참여시킬 때 입력하는 명령이다.
  • 스웜에 추가된 컴퓨터를 노드라고 부르며, 스웜과 같은 네트워크에 있어야 추가할 수 있다.
  • 쿠버네티스에 비해 클러스터를 구성하고 관리하는 작업이 단순하다.

매니저와 워커, 그리고 Leader 보강

노드에는 두 역할이 있다. 매니저는 클러스터 상태를 관리하고 스케줄링을 결정하며, 워커는 배정받은 컨테이너를 실행하기만 한다. 매니저는 Raft 합의 알고리즘으로 상태를 복제하는데, 그중 실제로 결정을 내리는 하나가 위 출력의 Leader 다.

합의 알고리즘 특성상 매니저는 홀수 개여야 하고, (N-1)/2 대까지 장애를 견딘다. 매니저 3대면 1대, 5대면 2대까지 죽어도 클러스터가 유지된다. 매니저가 과반을 잃으면 실행 중인 컨테이너는 계속 돌지만 새로운 스케줄링 결정을 내리지 못한다.

!

join 토큰은 자격 증명이다 보강

SWMTKN-... 토큰을 가진 사람은 누구나 클러스터에 노드를 붙일 수 있다. 문서나 채팅에 그대로 붙여 넣지 말고, 유출됐다면 docker swarm join-token --rotate worker 로 재발급한다. 스웜은 2377(관리), 7946(노드 간 통신), 4789(오버레이 네트워크) 포트를 쓰므로 이들 역시 신뢰하는 네트워크에서만 열어야 한다.

정리

  • docker swarm init 한 줄로 스웜 모드가 켜지고 그 노드가 매니저가 된다.
  • 노드는 매니저와 워커로 나뉘고, 매니저는 홀수 개로 두어 과반을 유지한다.
  • join 토큰은 자격 증명이므로 유출되면 즉시 재발급한다.
ITEM 12-3

도커 스웜 서비스로 앱 실행하기

컨테이너를 지워도 다시 살아난다. 이것이 "원하는 상태를 유지한다"의 실제 모습이다.

핵심 스웜에서는 컨테이너를 직접 다루지 않는다. 서비스를 선언하면 스웜이 레플리카 수를 맞추고, 하나가 사라지면 즉시 새로 만든다.

도커 스웜 서비스로 앱 실행하기

  • 서비스를 배포하면 스웜이 컨테이너를 알아서 실행한다. 직접 실행할 필요가 없다.
  • 서비스는 도커 스웜의 일급 객체로, 도커 엔진이 스웜 모드이거나 매니저에 연결된 상태여야 한다.

  • 도커 스웜에서 서비스를 구성하는 컨테이너를 레플리카라고 부른다. 도커 기준으로는 평범한 컨테이너다.
  • 동일하게 docker container 명령으로 제어할 수 있지만, 스웜이 제어하므로 직접 다룰 일은 많지 않다.

구/신 버전 공존이 만드는 진짜 문제 보강

화면이 달라 보이는 정도는 사소한 편이다. 실제로 위험한 것은 DB 스키마 변경이다. 롤링 업데이트 중에는 신버전이 기대하는 스키마와 구버전이 기대하는 스키마가 동시에 살아 있어야 한다.

그래서 스키마 변경은 보통 두 단계로 나눈다. 먼저 구버전도 신버전도 동작하는 하위 호환 변경(컬럼 추가 등)만 배포하고, 모든 레플리카가 교체된 뒤 다음 릴리스에서 정리 작업(옛 컬럼 삭제)을 한다. "컬럼 이름 바꾸기"를 한 번에 하면 롤링 업데이트 도중 반드시 깨진다.

  • 보통 새 버전 컨테이너에 문제가 생겼을 때 바로 되돌리기 위해 쓴다.

롤백은 한 단계뿐이다 보강

스웜이 보관하는 것은 직전 서비스 정의 하나다. --rollback 을 두 번 실행하면 더 옛날로 가는 게 아니라 방금 되돌린 것을 다시 되돌린다. 두 단계 이상 되돌리려면 --image 로 원하는 태그를 명시해 업데이트해야 한다.

또한 --update-failure-action rollback 을 걸어 두면 업데이트 중 헬스체크 실패가 감지될 때 자동으로 롤백한다. 8장 의 헬스체크가 여기서 무중단 배포의 안전장치로 쓰인다.

정리

  • 스웜에서는 컨테이너가 아니라 서비스를 선언한다. 레플리카가 사라지면 즉시 새로 만든다.
  • 앱 정의가 컴포즈 파일이 아니라 클러스터 DB 에 저장되고 매니저마다 암호화 복제된다.
  • 서비스 이미지 태그는 다이제스트로 고정되어 저장된다.
  • 업데이트는 롤링 방식이라 구/신 버전이 잠시 공존한다. 스키마 변경은 두 단계로 나눈다.
  • 롤백은 직전 정의 한 단계까지만 가능하다.
ITEM 12-4

클러스터 환경에서 네트워크 트래픽 관리하기

컴포즈에서는 IP 목록이 돌아왔지만, 스웜에서는 가상 IP 하나가 돌아온다.

핵심 스웜은 서비스에 가상 IP(VIP) 하나를 주고 그 뒤에서 트래픽을 나눈다. 앱이 로드밸런싱을 신경 쓸 필요가 없어지고, DNS 캐싱 문제도 사라진다.

스웜 모드에서의 네트워크

  • 기본적으로 스웜 모드의 네트워크는 표준 TCP/IP 방식을 쓴다.
  • 서로 다른 노드에서 실행 중인 컨테이너 간 통신도 되지만 앱에서 신경 쓸 필요가 없다.
  • 스웜 모드에서는 오버레이 네트워크(overlay network) 라는 새로운 형태의 도커 네트워크를 쓸 수 있다.

오버레이 네트워크(overlay network)

  • 클러스터에 속한 모든 노드를 연결하는 가상 네트워크다.
  • 서비스 이름을 도메인 삼아 다른 서비스와 통신할 수 있다. 기존에는 어디로 통신할지가 컨슈머의 몫이었지만, 스웜의 오버레이 네트워크는 가상 IP 주소 하나를 반환해 준다.
  • 다만 서로 다른 네트워크끼리는 통신할 수 없다.
terminal 
# 오버레이 네트워크 iotd-net 생성

인그레스 네트워크(Ingress Network)

  • 특정 노드가 통신 불가 상태일 경우 같은 네트워크 내의 다른 노드로 트래픽을 전달한다.
  • 한 노드에서 컨테이너가 여러 개 실행 중이면 도커 엔진이 컨테이너에 요청을 고르게 분배한다.
  • 서비스의 포트를 공개하는 경우 인그레스 네트워크가 기본적으로 적용된다.

라우팅 메시(routing mesh) 보강

인그레스가 만들어 내는 효과를 라우팅 메시라고 부른다. 핵심은 클러스터의 어느 노드로 요청을 보내든 서비스에 닿는다는 것이다. 그 노드에 해당 레플리카가 하나도 없어도, 노드가 알아서 레플리카가 있는 노드로 넘겨준다.

덕분에 앞단 로드밸런서 설정이 단순해진다. "어느 노드에 무엇이 떠 있는지"를 추적할 필요 없이 모든 노드를 백엔드로 등록해 두면 된다.

정리

  • 오버레이 네트워크는 클러스터의 모든 노드를 잇는 가상 네트워크다.
  • 서비스 조회 시 IP 목록이 아니라 가상 IP 하나가 돌아오고, 분산은 스웜이 맡는다.
  • 인그레스 네트워크 덕분에 어느 노드로 요청해도 서비스에 닿는다(라우팅 메시).
ITEM 12-5

도커 스웜, 쿠버네티스 중 뭘 쓸까

기술 우열이 아니라 운영 환경의 문제다. 매니지드 서비스가 있는가 없는가.

핵심 판단 기준은 단순하다. 클라우드면 쿠버네티스(매니지드가 있으니), 온프레미스면 스웜(직접 운영해야 하니). 복잡도를 누가 감당하느냐의 문제다.

도커 스웜

  • 온프레미스 환경일 경우 권장된다.
  • 클라우드 매니지드 서비스가 없기 때문에 모든 인프라 구성을 직접 해야 한다.
  • 초기에 도입했다가 쿠버네티스가 필요해질 때 넘어가는 방법도 있다.

쿠버네티스

  • 클라우드 환경일 경우 권장된다.
  • AWS, GCP 등 대부분의 클라우드에서 매니지드 서비스를 제공한다.
  • 도커 스웜에 비해 러닝 커브가 높다.

스웜은 아직 살아 있다 최신 반영

도커의 엔터프라이즈 사업이 Mirantis 로 넘어간 뒤 "스웜은 끝났다"는 인식이 퍼졌지만, Mirantis 는 최소 2030년까지 스웜을 지원하겠다고 공식적으로 밝혔고 CSI 스토리지 지원, Seccomp / AppArmor 프로파일 API 같은 기능 추가와 정기 보안 업데이트가 계속되고 있다.

따라서 "스웜을 고르면 곧 죽는 기술에 올라타는 것"은 아니다. 다만 생태계의 무게 중심이 쿠버네티스에 있다는 사실은 그때보다 더 확고해졌다. 채용 시장, 문서, 서드파티 도구, 클라우드 통합 모두 쿠버네티스 쪽이 압도적이다. 원문의 결론 — 온프레미스면 스웜, 클라우드면 쿠버네티스 — 는 여전히 실용적인 판단 기준으로 유효하다.

i

어느 쪽을 고르든 잃지 않는 것 보강

지금까지 만들어 온 것 — Dockerfile, 멀티 스테이지 빌드, 헬스체크, 디펜던시 체크, /metrics 엔드포인트, 설정 주입 — 은 플랫폼에 종속되지 않는다. 스웜에서 쿠버네티스로 옮길 때 바뀌는 것은 배포 정의 파일(docker-compose.yml → 매니페스트)이지 이미지가 아니다. 8-3 에서 커스텀 체크 유틸리티를 만든 이유도 정확히 이것이었다.

정리

  • 클라우드면 쿠버네티스, 온프레미스면 스웜이 실용적인 기준이다.
  • 스웜은 진입 비용이 낮고 지원도 2030년까지 이어진다. 다만 생태계는 쿠버네티스가 압도적이다.
  • 이미지와 체크 로직은 플랫폼에 종속되지 않는다. 옮겨 갈 때 바뀌는 것은 배포 정의뿐이다.
CH 17

도커 이미지 최적화하기

이미지 크기는 디스크 문제만이 아니라 보안 문제다. 한 번 레이어에 들어간 파일은 지워도 사라지지 않는다는 원리에서 출발한다.

ITEM 17-1

도커 이미지를 최적화하는 방법

한 번 레이어에 들어간 파일은 지워도 사라지지 않는다. 애초에 넣지 않는 것만이 답이다.

핵심 RUN rm -rf 는 파일을 안 보이게 만들 뿐 이미지 크기를 줄이지 않는다. 레이어는 쌓이기만 하고 아래 레이어의 내용을 되돌릴 수 없기 때문이다.

도커 이미지의 특성

  • 한 번 내려받은 이미지는 명시적으로 삭제하지 않으면 계속 남아 있다.
  • docker system df 로 도커 자원이 점유하는 사용량을 확인할 수 있다.
  • 가능하면 docker system prune 으로 미사용 자원을 주기적으로 지워 주는 게 좋다.
!

prune 은 범위를 알고 쓰자 보강

명령지우는 것
docker system prune정지된 컨테이너, 미사용 네트워크, dangling 이미지, 빌드 캐시
docker system prune -a위 + 컨테이너가 쓰지 않는 모든 이미지
docker system prune --volumes위 + 미사용 볼륨 (데이터 손실)

-a 는 잠시 안 쓰는 이미지까지 전부 날려 다음 빌드가 크게 느려진다. --volumes 는 DB 데이터를 지울 수 있다. 상세 내역은 docker system df -v 로 먼저 확인하는 습관을 들이자.

도커 이미지 개선하기 — 꼭 필요한 파일만 이미지에 포함하기

  • 이미지 크기는 내부에서 실행한 명령이 아니라, 인스트럭션이 만들어 낸 레이어에 영향을 받는다.
  • 아래 v2 예제에서 rm -rf docs 로 폴더를 삭제했지만, 앞선 COPY 레이어에는 그대로 남아 있다.
  • 이미지는 여러 레이어를 겹쳐 하나로 보이게 만든 것이다. 즉 한 번 복사된 것은 뺄 수 없다.
  • 결국 각 레이어마다 최적화가 필요하다.
Dockerfile 
# v1) 모든 디렉토리 구조를 이미지에 복사함
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY . .

# v2) 불필요한 파일을 별도로 삭제 — 화면에서만 사라지고 크기는 그대로
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY . .
RUN rm -rf docs

# v3) 꼭 필요한 파일만 복제하기 — 이것만이 실제로 작아진다
FROM diamol/base
CMD echo app- && ls app && echo docs- && ls docs
COPY ./app ./app
삭제는 위 레이어에 "가림막"을 하나 더 얹는 일이다 — 아래 레이어의 파일은 그대로 남아 전송량과 디스크를 그대로 잡아먹는다. 게다가 그 파일은 여전히 이미지 안에 있으므로 추출도 가능하다. 비밀 파일을 이렇게 지우면 안 되는 이유다.

.dockerignore

  • .gitignore 와 유사한 파일로, 제외하고 싶은 목록을 적으면 된다.
.dockerignore 
.git
node_modules
docs
*.md
.env
**/*.test.js
i

.dockerignore 는 두 가지를 동시에 해결한다 보강

첫째, 빌드 컨텍스트 전송량이 줄어 빌드가 빨라진다. 둘째, COPY . . 를 써도 제외된 파일은 애초에 복사되지 않는다. RUN rm 으로 지우는 것과 달리 레이어에 흔적도 남지 않는다는 점이 결정적이다.

한 가지 함정 — .dockerignore 에 node_modules 를 넣어 두면 캐시 최적화(3-5)와도 잘 맞는다. 호스트의 node_modules 가 컨텍스트에 안 들어가므로 COPY . . 가 그것 때문에 캐시를 깨뜨리는 일이 없어진다.

정리

  • 레이어는 쌓이기만 한다. RUN rm 은 가림막만 얹을 뿐 크기를 줄이지 않는다.
  • 애초에 필요한 것만 COPY 하고, 나머지는 .dockerignore 로 막는다.
  • 지운 파일도 이미지에서 추출 가능하다. 비밀 파일을 이 방식으로 처리하면 안 된다.
  • docker system df 로 확인하고 prune 은 범위를 알고 쓴다.
ITEM 17-2

좋은 기반 이미지 고르기

이미지 크기 문제는 디스크 문제가 아니라 공격 표면 문제다.

핵심 이미지에 들어 있는 모든 실행 파일은 침입자도 쓸 수 있는 도구다. 앱 실행에 필요 없는 것이 하나도 없어야 한다는 원칙은 보안에서 나온다.

이미지의 취약점

  • 크기가 큰 이미지는 OS 입장에서는 편하겠지만, 그만큼 내부에 많은 것이 포함된다.
  • 예를 들어 curl 이 들어 있다면 컨테이너에 침입한 공격자가 악성 프로그램을 내려받을 수 있다.
  • 또한 빌드가 가능한 SDK 등이 포함돼 있다면 컨테이너 자체가 망가질 수도 있다.

작을수록 좋지만 공짜는 아니다 보강

distroless 나 scratch 이미지는 셸이 없어서 docker exec -it ... sh 가 안 된다. 장애 상황에서 컨테이너 안을 들여다보는 통상적인 방법이 막힌다는 뜻이다. 그래서 이런 이미지를 쓸 때는 8-3 처럼 앱과 같은 언어로 만든 체크 유틸리티가 더욱 중요해진다. 셸 스크립트를 쓸 수 없으니 선택의 여지도 없다.

alpine 은 glibc 대신 musl libc 를 쓰기 때문에, 네이티브 모듈을 쓰는 Node.js / Python 앱에서 미묘한 호환성 문제나 성능 차이가 나타나는 경우가 있다. 무조건 alpine 이 정답은 아니다.

골든 이미지

  • 앞서 설명한 골든 이미지는 인증을 받고 공유되는 이미지라서 이러한 문제를 피할 수 있는 방법 중 하나다.

이미지 검증 도구

  • 앤코어(Anchore) 같은 오픈소스 도커 이미지 분석 도구로 CI/CD 파이프라인에서 이미지를 검증할 수 있다.
↑

지금은 선택지가 더 많다 최신 반영

노트가 언급한 Anchore 외에도, 그사이 이미지 스캐닝이 훨씬 흔한 일이 됐다.

  • Docker Scout — 도커의 자체 서비스. 이미지에서 SBOM 을 만들어 취약점 DB 와 대조한다. Docker Hub, Docker CLI, Scout 대시보드에서 쓸 수 있다.
  • Trivy — 오픈소스. 컨테이너 이미지뿐 아니라 파일 시스템, IaC 설정까지 스캔한다. CI 에 붙이기 쉽다.
  • Grype — Anchore 계열의 오픈소스 스캐너.

핵심은 도구 선택이 아니라 스캔을 파이프라인에 자동으로 넣는 것이다. 11-1 의 CI 흐름에서 빌드와 푸시 사이에 스캔 단계를 두고, 심각도 기준을 넘으면 푸시를 막는 방식이 표준적이다.

정리

  • 이미지에 든 도구는 침입자의 도구이기도 하다. 앱에 필요 없는 것은 넣지 않는다.
  • slim / alpine / distroless / scratch 순으로 작아지지만 디버깅은 어려워진다.
  • alpine 은 musl libc 라 네이티브 모듈에서 호환성 문제가 날 수 있다.
  • 이미지 스캔을 CI 파이프라인에 자동으로 넣는다. Scout / Trivy / Grype 등.
ITEM 17-3

이미지 레이어 수와 이미지 크기는 최소한으로

패키지를 설치하고 캐시를 지우는 일은 같은 RUN 안에서 끝내야 한다.

핵심 RUN 을 && 로 이어 붙이는 이유는 문법 취향이 아니다. 설치와 정리가 같은 레이어에서 일어나야 캐시 파일이 이미지에 남지 않기 때문이다.

이미지 레이어 수 최소화하기

  • 이미지를 만들 때 기본은 보안성을 갖춘 기반 이미지를 쓰는 것이다.
  • 추가로 꼭 필요한 것만 포함하는 이미지를 만들어야 한다.

예제 1. 패키지 설치

  • 차이점은 인스트럭션의 개수와, RUN 커맨드 뒤에 apt 캐시를 삭제하는 구문이 추가된 것이다.
  • 인스트럭션을 줄이면 여러 장점이 있다.
    • OS 별로 다르지만 최대 레이어 개수 제한이 존재한다.
    • 레이어 수가 적으면 컨테이너 파일 시스템의 내용을 추적하기도 쉽다.
v1 — 이미지 90MB 
FROM debian:stretch-slim

RUN apt-get update
RUN apt-get install -y curl=7.52.1-5+deb9u16
RUN apt-get install -y socat=1.7.3.1-2+deb9u1
v2 — 이미지 70MB 
FROM debian:stretch-slim

RUN apt-get update \
 && apt-get install -y --no-install-recommends \
    curl=7.52.1-5+deb9u16 \
    socat=1.7.3.1-2+deb9u1 \
 && rm -rf /var/lib/apt/lists/*
i

v2 가 20MB 를 아낀 두 가지 이유 보강

  • --no-install-recommends — apt 는 기본적으로 "추천 패키지"까지 함께 설치한다. 이 플래그로 진짜 의존성만 설치한다.
  • rm -rf /var/lib/apt/lists/* 를 같은 RUN 안에 둔 것 — apt-get update 가 받아 온 패키지 목록 캐시를 지운다. 17-1 에서 봤듯 별도의 RUN 으로 지우면 소용이 없다. 같은 레이어 안에서 만들었다 지워야 그 레이어의 최종 결과에 캐시가 없다.

참고로 apt-get update 와 install 을 나누면 캐시 관점에서도 위험하다. update 레이어가 캐시에 걸린 채 install 만 다시 실행되면, 오래된 패키지 목록으로 설치를 시도해 실패하거나 낡은 버전이 깔린다.

!

"최대 레이어 개수"의 실제 수치 보강

지금 표준 스토리지 드라이버인 overlay2 는 최대 128개의 lower 레이어를 지원한다. 이를 넘기면 max depth exceeded 로 빌드가 실패한다.

실제로는 128 보다 적은 수에서 터지는 경우가 흔한데, 커널의 마운트 옵션 문자열이 4KB 로 제한되어 있어 data-root 경로가 길수록 쓸 수 있는 레이어가 줄기 때문이다. 보고 사례에서는 120~126 층 부근에서 실패했다. 어쨌든 정상적인 Dockerfile 이 128 층에 닿는 일은 드물다. 레이어를 줄이는 진짜 이유는 개수 제한이 아니라 크기와 추적 가능성이다.

단순히 삭제만 한다고 해서 이미지 레이어의 크기가 줄지 않는다.

FROM diamol/base

ARG DATASET_URL=https://archive.ics.uci.edu/ml/\
machine-learning-databases/url/url_svmlight.tar.gz

WORKDIR /dataset

RUN wget -O dataset.tar.gz ${DATASET_URL} && \
    tar xvzf dataset.tar.gz

WORKDIR /dataset/url_svmlight
RUN cp Day1.svm Day1.bak && \
    rm -f *.svm && \
    mv Day1.bak Day1.svm

machine-learning-databases/url/url_svmlight.tar.gz

2.5GB → 25MB, 100배 차이

v1 은 전체를 풀어놓은 뒤 지웠기 때문에, 아래 레이어에 압축 파일과 풀린 전체 데이터가 모두 남아 있다. v2 는 tar 에 파일 이름을 지정해 필요한 하나만 꺼냈다. 원칙은 언제나 같다 — 지우지 말고 애초에 만들지 않는다.

정리

  • 설치와 정리는 반드시 같은 RUN 안에서 끝낸다. 나누면 정리 효과가 없다.
  • apt-get 은 --no-install-recommends + rm -rf /var/lib/apt/lists/* 가 기본형이다.
  • overlay2 의 레이어 한계는 128 이지만, 줄이는 진짜 이유는 크기와 추적 가능성이다.
  • 큰 아카이브는 통째로 풀고 지우는 대신 필요한 파일만 꺼낸다.
ITEM 17-4

멀티 스테이지 빌드를 한 단계 업그레이드하기

--target 으로 중간 스테이지까지만 빌드하면, 어느 단계에서 크기가 폭발하는지 눈으로 확인할 수 있다.

핵심 --target 은 디버깅 도구다. 스테이지별 이미지를 각각 만들어 크기를 재 보면, 어느 단계가 무엇을 남기고 있는지가 그대로 드러난다.

--target 인자

이 인자로 특정 스테이지에서 빌드를 중단할 수 있다.

terminal 
# 이미지 끝까지 빌드
$ docker image build -t diamol/ch17-ml-dataset:v3 -f Dockerfile.v3 .

# download 스테이지까지만 빌드
$ docker build -t diamol/ch17-ml-dataset:v3-download -f Dockerfile.v3 --target download .

# expand 스테이지까지만 빌드
$ docker build -t diamol/ch17-ml-dataset:v3-expand -f Dockerfile.v3 --target expand .

# 각 단계마다 이미지의 크기가 다르다
$ docker image ls | grep diamol/ch17-ml-dataset
diamol/ch17-ml-dataset   v3            26080e7d3ce4   13 minutes ago   25.3MB
diamol/ch17-ml-dataset   v3-expand     adb8e54075dd   13 minutes ago   2.46GB
diamol/ch17-ml-dataset   v3-download   35e3d8920e1e   14 minutes ago   252MB
2.46GB 짜리 스테이지를 거쳐 25.3MB 이미지가 나온다 — COPY --from 으로 명시한 파일만 넘어오기 때문이다. --target 이 없으면 이 중간 크기는 보이지 않는다.

주의점

  • RUN 으로 내려받거나 설치한 소프트웨어 등 불필요한 데이터가 캐싱되지 않도록 주의해야 한다.
  • 앞 단계에서 캐싱된 데이터는 해당 Dockerfile 안에서 그 인스트럭션을 수정할 때까지 캐시에 유지된다.
  • 이미지에 패키지를 추가할 때는 정확한 버전을 명시해서 설치하거나 업데이트하는 게 좋다.
!

버전 고정이 중요한 이유 보강

RUN apt-get install -y curl 처럼 버전 없이 쓰면, 이 레이어가 캐시에 걸려 있는 동안은 몇 달 전 버전이 계속 쓰이다가 어느 날 캐시가 깨지는 순간 갑자기 최신 버전으로 바뀐다. 빌드가 언제 깨질지 예측할 수 없다는 뜻이다.

그래서 17-3 의 예제처럼 curl=7.52.1-5+deb9u16 로 버전을 못 박는다. 업그레이드는 사람이 의도적으로 그 줄을 고칠 때만 일어나야 한다. FROM 의 기반 이미지도 마찬가지로 latest 대신 구체적인 태그를 쓴다.

i

--target 의 또 다른 쓰임 보강

CI 에서 테스트 스테이지까지만 빌드하는 데도 쓴다. docker build --target test . 로 테스트만 돌리고, 통과하면 --target 없이 최종 이미지를 만드는 식이다. 개발용으로 디버깅 도구가 포함된 스테이지를 따로 두고 --target dev 로 뽑아 쓰는 패턴도 흔하다.

정리

  • --target 으로 중간 스테이지까지만 빌드해 어느 단계가 무거운지 확인한다.
  • 중간 스테이지가 커도 최종 이미지에는 COPY --from 으로 넘긴 것만 남는다.
  • 패키지와 기반 이미지의 버전은 못 박는다. 캐시가 깨지는 순간 조용히 바뀌는 것을 막는다.
  • --target 은 CI 의 테스트 전용 빌드, 개발용 이미지 분리에도 쓰인다.
CH 18

컨테이너의 앱 설정관리

설정은 한 겹이 아니다. 이미지에 담긴 기본값 위에 환경별 파일이 얹히고, 그 위에 환경 변수가 얹힌다.

ITEM 18-1

다단 앱 설정

설정은 한 겹이 아니다. 이미지의 기본값 위에 환경별 파일이 얹히고, 그 위에 환경 변수가 얹힌다.

핵심 설정 모델은 데이터의 성격을 반영해야 한다. 버전에 묶인 값, 환경에 묶인 값, 실행 시점에만 바꾸고 싶은 값은 서로 다른 층에 두어야 한다.

다단 앱 설정

설정 모델에는 설정에 담긴 데이터의 구조가 반영되어야 한다.

분류성격어디에 두는가
버전에 따라 달라지는 설정 모든 환경에서 동일하지만 버전별로 달라짐 이미지 안 (기본 설정 파일)
환경에 따라 달라지는 설정 개발 / 운영 등 환경별로 달라짐 마운트하는 오버라이드 파일
기능 설정 버전별 앱의 동작을 제어하기 위함 환경 변수 (실행 시점에 주입)
병합된다 — 위 층이 없으면 아래 값이 그대로 쓰인다 어느 층이 없어도 앱은 뜬다. 이것이 다단 설정의 목적이다
바닥이 항상 채워져 있기 때문에 아무것도 주입하지 않아도 앱이 뜬다 — 개발자는 docker run 만 하면 되고, 환경이 필요로 하는 만큼만 위층을 얹는다.

예제 1. 로컬 설정 파일 오버라이드

미리 정의된 경로에서 오버라이드 설정 파일을 읽어 들이도록 해 두면, 어떤 경로든 컨테이너 파일 시스템에 설정 파일을 주입하기만 하면 그 설정을 쓸 수 있다.

terminal 
# 기본 설정 사용
$ docker run -d -p 8080:80 diamol/ch18-access-log
3ea38fcbf319abcfd609116747bbc221112b1f62f7973e63256d943b509f5c90

# 로컬에 존재하는 설정 파일 마운트
$ docker run -d -p 8081:80 -v "$(pwd)/config/dev:/app/configoverride" diamol/ch18-access-log
62ccb944842a3f0d4673e13fca1b3cd7f0c702fc20f0e4341484671f93782d95

# 기본 설정 확인
$ curl http://localhost:8080/config
{"release":"19.12","environment":"UNKNOWN","metricsEnabled":true}

# 마운트된 설정 확인 — environment 만 바뀌었다
$ curl http://localhost:8081/config
{"release":"19.12","environment":"DEV","metricsEnabled":true}
i

주목할 것은 바뀌지 않은 값이다 보강

오버라이드 파일이 environment 만 DEV 로 바꿨는데, release 와 metricsEnabled 는 그대로다. 덮어쓰기가 아니라 병합이라는 증거다.

여기서 6-4 의 함정을 피한 방식도 눈여겨볼 만하다. 기본 설정 파일이 있는 폴더에 직접 마운트하면 기본 설정이 통째로 가려졌을 것이다. 그래서 /app/configoverride 라는 별도의 빈 폴더를 마운트 지점으로 두고, 앱이 두 폴더를 모두 읽어 병합한다.

!

오탈자 교정 원문 교정

원문의 diamol?ch18-access-log 는 diamol/ch18-access-log 의 오타다. 위 코드 블록에는 고쳐서 실었다.

예제 2. 환경 변수로부터 값 읽어 오기

  • 기본 파일 + 볼륨 파일 + 주입한 환경 변수를 병합해서 최종 설정이 만들어진다.
  • 이 구성은 개발자의 워크플로를 부드럽게 유지할 수 있는 좋은 사례다.
  • 단점은 값이 JSON 으로 들어가야 한다는 점이다.
terminal 
# 환경변수 직접 주입
$ docker run -d -p 8082:80 -v "$(pwd)/config/dev:/app/configoverride" \
    -e NODE_CONFIG='{"metrics": {"enabled": "true"}}' diamol/ch18-access-log
869b0523b12809008d706a92592f675be273047ff2a147e081f260904ca09ad6

# 주입된 환경변수가 적용된 모습
$ curl http://localhost:8082/config
{"release":"19.12","environment":"UNKNOWN","metricsEnabled":true}
i

JSON 을 환경 변수에 넣는 것의 대가 보강

원문이 지적한 "값이 JSON 으로 들어가야 한다"는 단점은 생각보다 크다. 셸에서 따옴표 이스케이프가 까다롭고, 오타가 나면 조용히 무시되거나 파싱 에러로 앱이 죽는다. CI 스크립트나 컴포즈 파일을 거치면서 이스케이프가 한 번 더 꼬이는 일도 흔하다.

그래서 실무에서는 설정 라이브러리가 지원한다면 중첩 구조를 평평한 키로 표현하는 방식을 선호한다. .NET 의 Database__Provider(더블 언더스코어 = 계층 구분)나 Spring 의 SPRING_DATASOURCE_URL 같은 규칙이 그것이다. 8-3 의 RngApi__Url 도 같은 관례다.

정리

  • 설정은 이미지 기본값 / 환경별 파일 / 환경 변수 세 층으로 나눈다.
  • 위 층이 아래를 덮어쓰되 병합된다. 아무것도 주입하지 않아도 앱이 뜬다.
  • 기본 설정 폴더를 직접 마운트하면 가려진다. 별도의 오버라이드 폴더를 둔다.
  • 환경 변수에 JSON 을 넣는 방식은 이스케이프가 취약하다. 평평한 키 규칙이 안전하다.
ITEM 18-2

환경별 설정 패키징하기

환경별 설정을 이미지 안에 미리 담아 두고, 환경 변수 하나로 어느 것을 쓸지 고른다.

핵심 설정 파일을 이미지에 함께 굽고 환경 변수로 선택하는 방식이다. 주입할 파일이 없어 배포가 단순해지는 대신, 민감한 값은 절대 이 방식으로 담으면 안 된다.

환경별 설정 패키징하기

terminal 
# 기본 설정 실행
$ docker run -d -p 8083:80 diamol/ch18-todo-list
e8dcce707cf0ff3640f781fd9e37584606b122985105bd14eb881ae1484d995b

# DOTNET_ENVIRONMENT 추가 — 이미지 안의 Test 설정이 선택된다
$ docker run -d -p 8084:80 -e DOTNET_ENVIRONMENT=Test diamol/ch18-todo-list
80322b949244722beda23b84dd8187b10c15bb64eb0ef38d36c85ff180d04383
주입할 파일이 없다 — 볼륨도 비밀값도 없이 환경 변수 하나로 환경이 결정된다. 배포가 단순해지는 대신, 그 파일들은 이미지를 가진 누구나 읽을 수 있다.
×

이 방식에 비밀번호를 넣으면 안 되는 이유

이미지에 구운 설정 파일은 그 이미지를 받을 수 있는 누구나 읽을 수 있다. 17-1 에서 봤듯 레이어에서 파일을 꺼내는 것은 어렵지 않고, 나중에 RUN rm 으로 지워도 아래 레이어에 그대로 남는다.

그래서 이미지에 담아도 되는 것은 환경별로 다르지만 비밀은 아닌 값에 한한다 — 로그 수준, 기능 플래그, 캐시 크기, 타임아웃 같은 것들이다. 커넥션 스트링과 API 키는 10-3 의 비밀값으로 런타임에 주입한다.

i

이 방식이 좋은 이유 보강

단점만 있는 것은 아니다. 오히려 비밀이 아닌 설정에 대해서는 이 방식이 더 낫다. 환경별 설정이 이미지와 함께 버전 관리되므로, "운영 서버의 설정 파일이 언제 누구에 의해 바뀌었는지 아무도 모르는" 상황이 생기지 않는다. 설정 변경도 코드 리뷰와 파이프라인을 거친다.

결국 18-1 의 다단 구조와 같은 결론이다. 이미지에는 안전한 기본값을, 런타임에는 비밀만.

정리

  • 환경별 설정 파일을 모두 이미지에 담고 환경 변수로 선택한다. 주입할 파일이 없어 배포가 단순하다.
  • 설정이 이미지와 함께 버전 관리되어 변경 이력이 남는다.
  • 이미지에 담은 파일은 누구나 읽을 수 있다. 비밀번호와 키는 절대 넣지 않는다.
  • 비밀이 아닌 값은 이미지에, 비밀은 런타임 주입으로 — 이것이 전체 설정 전략의 결론이다.
