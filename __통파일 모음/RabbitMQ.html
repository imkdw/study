RabbitMQ

CH 1

잡 큐와 메시지 브로커는 다른 물건이다

BullMQ에서 RabbitMQ로 넘어갈 때 가장 먼저 갈아끼워야 하는 건 API가 아니라 머릿속 모델이다. 무엇이 라이브러리의 기능이었고 무엇이 브로커의 기능인지부터 분리한다.

ITEM 1

잡 큐와 메시지 브로커

BullMQ는 Redis 위에 얹은 라이브러리고, RabbitMQ는 그 자체로 서버다.

핵심 BullMQ는 작업의 생애를 저장하고, RabbitMQ는 메시지를 전달만 한다. 이 한 문장에서 나머지 차이가 전부 파생된다.

BullMQ: 서버가 없는 큐

BullMQ에는 설치할 브로커가 없다. Redis에 리스트/해시/정렬셋/스트림을 깔고, 그 위에서 Lua 스크립트로 원자적 상태 전이를 구현한 클라이언트 라이브러리다. new Queue()도 new Worker()도 전부 내 Node.js 프로세스 안의 객체이고, 둘은 Redis라는 공유 메모리를 통해서만 만난다.

그래서 BullMQ의 1급 개념은 메시지가 아니라 잡(job)이다. 잡에는 상태(waiting → active → completed / failed)가 있고, 시도 횟수가 있고, 반환값이 있고, 진행률이 있다. 이 모든 게 Redis에 남기 때문에 나중에 조회할 수 있다.

RabbitMQ: 프로토콜을 말하는 서버

RabbitMQ는 Erlang/OTP로 짜인 별도 프로세스다. 5672 포트에서 AMQP 0-9-1이라는 바이너리 프로토콜을 말하고, 어떤 언어의 클라이언트든 그 프로토콜만 지키면 붙을 수 있다. Node.js, Java, Go, Python이 같은 큐를 공유하는 게 기본 전제다.

RabbitMQ에게 메시지는 바이트 덩어리 + 헤더일 뿐이다. 브로커는 그 안에 무슨 일이 적혀 있는지 모르고, 알 필요도 없다. 컨슈머가 ack하는 순간 메시지는 큐에서 사라진다. 잡 결과도, 진행률도, 완료 이력도 개념 자체가 없다.

가장 흔한 착각

"큐니까 BullMQ에서 쓰던 기능이 다 있겠지"는 틀렸다. 진행률(job.updateProgress), 결과 조회(job.returnvalue), 완료 잡 목록, 잡 ID로 상태 조회 같은 것은 RabbitMQ에 대응물이 없다. 그런 게 필요하면 애플리케이션 DB에 직접 테이블을 만들어야 한다.

정리

  • BullMQ = Redis 위의 잡 상태 머신. RabbitMQ = 독립 프로세스인 메시지 라우터.
  • BullMQ는 잡의 이력이 남고, RabbitMQ는 ack 즉시 메시지가 사라진다.
  • RabbitMQ는 언어 중립 프로토콜이라 서비스 간 통신에 강하고, 대신 잡 관리 기능은 하나도 없다.
ITEM 2

BullMQ의 Queue와 RabbitMQ의 Queue는 다른 것이다

RabbitMQ에서 발행자는 큐 이름을 모른다. 그게 전부다.

핵심 RabbitMQ에는 발행자와 큐 사이에 Exchange라는 한 겹이 더 있다. 이 한 겹이 두 시스템의 설계 차이를 통째로 만든다.

BullMQ: 큐 이름이 곧 목적지

bullmq.ts
const queue = new Queue('email');

// 'email' 큐에 넣는다. 이 잡을 누가 가져갈지는 큐 이름이 이미 결정했다.
await queue.add('welcome', { userId: 42 });

발행자가 'email'이라는 이름을 알고 있어야 한다. 이 잡을 알림 서비스도 같이 받아야 한다면? queue.add를 한 번 더 호출하거나, 별도의 pub/sub을 하나 더 놓아야 한다. 발행자가 소비자 목록을 안다.

RabbitMQ: 발행자는 exchange에만 던진다

publisher.ts
// exchange 이름과 routing key만 안다. 큐 이름은 모른다.
channel.publish('user.events', 'user.created', Buffer.from(JSON.stringify({ userId: 42 })));
consumer.ts
// 소비자 쪽이 "나는 이런 메시지를 받겠다"고 선언한다.
await channel.assertQueue('email.welcome', { durable: true });
await channel.bindQueue('email.welcome', 'user.events', 'user.created');

나중에 알림 서비스가 같은 이벤트를 받고 싶어지면, 발행자 코드를 한 줄도 건드리지 않고 자기 큐를 만들어 바인딩만 추가하면 된다. 발행자는 구독자가 몇 개인지 영원히 모른다.

처음에 헷갈리는 sendToQueue 보강

amqplib의 channel.sendToQueue('email', buf)는 BullMQ의 queue.add처럼 보인다. 하지만 실제로는 이름 없는 기본 exchange("")에 routing key를 큐 이름으로 넣어 발행하는 축약형이다. 모든 큐는 자기 이름과 같은 routing key로 기본 exchange에 자동 바인딩되어 있기 때문에 그렇게 동작한다. 편하지만, 이걸로만 쓰면 RabbitMQ를 비싼 BullMQ로 쓰는 셈이다.

정리

  • BullMQ: 발행자가 큐(목적지)를 지정한다. RabbitMQ: 발행자가 exchange + routing key(의도)를 지정한다.
  • 큐와 바인딩은 소비자 쪽 관심사다. 구독자 추가가 발행자 배포와 무관해진다.
  • sendToQueue는 기본 exchange를 쓰는 축약형이다. 편의 문법이지 다른 모델이 아니다.

4.3에서 브로커 쪽으로 넘어온 것들 최신 반영

예전에는 "재시도 제한도 백오프도 전부 애플리케이션 몫"이라고 설명했지만, 지금은 그렇지 않다. quorum queue는 x-delivery-limit(기본 20)로 재배달 횟수를 세고, 4.3부터는 x-delayed-retry-type 계열 인자로 선형 백오프 재시도까지 브로커가 처리한다. BullMQ의 attempts/backoff에 상당히 가까워진 지점이다. 자세한 건 ITEM 21~22에서 다룬다.

✓

사고방식의 전환

BullMQ에서는 옵션 객체로 표현하던 것을, RabbitMQ에서는 큐와 exchange를 몇 개 어떻게 놓을지로 표현한다. "재시도 3번 후 실패 처리"가 코드 한 줄이 아니라 work 큐 + retry 큐 + dlq 큐 세 개의 그림이 된다. 대신 그 그림은 관리 UI에서 눈으로 보이고, 언어에 상관없이 공유된다.

정리

  • RabbitMQ의 보장은 "라우팅 + 최소 한 번 전달"까지다.
  • 스케줄, 레이트 리밋, 결과, 진행률, 잡 의존성은 없다. 필요하면 직접 만든다.
  • 대신 팬아웃, 라우팅, DLX, 발행 확인은 브로커가 훨씬 제대로 해준다.
  • 옵션으로 풀던 문제를 이제 토폴로지로 푼다.
ITEM 4

그래서 언제 무엇을 쓰나

둘은 경쟁 관계가 아니다. 실무에서는 같이 쓰는 경우가 오히려 흔하다.

BullMQ가 계속 나은 자리

  • 한 서비스 안에서 끝나는 백그라운드 작업. 썸네일 생성, PDF 렌더, 리포트 집계.
  • 작업의 결과나 진행률을 사용자에게 보여줘야 하는 경우.
  • 크론/반복 작업, 레이트 리밋이 핵심인 경우. (외부 API 초당 10회 제한 같은)
  • 부모-자식 작업 그래프(Flow)가 필요한 경우.
  • 이미 Redis가 있고, 인프라를 하나라도 덜 늘리고 싶은 경우.

RabbitMQ가 필요해지는 자리

  • 서비스 경계를 넘는 통신. 특히 Node 아닌 언어의 서비스가 섞여 있을 때.
  • 한 사건을 여러 소비자가 각자 처리해야 할 때(이벤트 팬아웃).
  • 메시지 종류에 따라 다른 처리 경로로 갈라야 할 때(라우팅).
  • 결제/정산처럼 유실이 곧 사고인 도메인. 퍼블리셔 컨펌 + quorum queue + DLX 조합이 필요할 때.
  • 느린 컨슈머를 브로커 차원의 백프레셔로 눌러야 할 때.

현실의 조합 보강

흔한 구성은 이렇다. 서비스 간 이벤트는 RabbitMQ로 흘리고, 각 서비스가 그 이벤트를 받아 자기 안에서 처리할 무거운 작업은 BullMQ 잡으로 다시 만든다. 브로커는 배달만 하고, 재시도/진행률/결과 같은 잡 관리는 서비스 내부에서 하는 셈이다. 이직한 회사에서 RabbitMQ를 쓴다고 해서 BullMQ 지식이 버려지는 게 아니라, 층이 하나 위로 올라간다고 보면 된다.

정리

  • 기준은 성능이 아니라 경계다. 서비스/언어 경계를 넘으면 RabbitMQ.
  • 잡 관리 기능(결과, 진행률, 크론, 레이트 리밋)이 핵심이면 BullMQ.
  • 둘을 계층으로 나눠 같이 쓰는 구성이 실무에서 가장 흔하다.
CH 2

AMQP 0-9-1 코어 모델

RabbitMQ를 안다는 건 사실상 AMQP 0-9-1의 다섯 개 명사 Connection / Channel / Exchange / Queue / Binding을 안다는 뜻이다. 여기만 정확히 잡으면 나머지는 전부 이 위의 옵션이다.

ITEM 5

Connection과 Channel

TCP 연결은 비싸고, 채널은 싸다. 대신 채널은 공유하면 안 된다.

핵심 Connection은 TCP 연결 하나, Channel은 그 위에 다중화된 가상 연결이다. 프로세스당 커넥션은 소수로, 작업 단위는 채널로 나눈다.

왜 두 겹인가

AMQP는 오래 살아 있는 TCP 연결을 전제로 만들어졌다. 연결을 맺는 일(TCP 핸드셰이크 + TLS + AMQP 핸드셰이크 + 인증)은 무겁고, 브로커 쪽에서도 커넥션마다 Erlang 프로세스와 파일 디스크립터를 잡는다. 그래서 연결은 오래 쓰고, 동시 작업은 그 안의 채널로 나눈다. 채널을 여는 건 프레임 몇 개면 끝난다.

  subgraph APP["Node.js 프로세스"]
    CH1["Channel 1: 발행"]
    CH2["Channel 2: 컨슈머 A"]

  CH1 --> CONN["Connection (TCP 하나)"]

커넥션 하나, 채널 여럿 — 채널은 프레임에 채널 번호를 실어 하나의 TCP 위에서 다중화된다.

채널을 나누는 기준

  • 컨슈머마다 채널 하나. ack의 delivery tag는 채널 단위로 매겨지고, 채널이 닫히면 그 채널의 미확인 메시지가 전부 requeue된다. 컨슈머를 섞으면 하나가 죽을 때 다른 하나도 말려든다.
  • 발행용 채널과 소비용 채널을 분리. 특히 퍼블리셔 컨펌을 쓰는 채널은 따로 두는 게 깔끔하다.
  • 동시에 여러 곳에서 같은 채널을 쓰지 않는다. amqplib의 Channel 객체는 스레드/동시성 안전을 보장하지 않는다.
!

connection churn

HTTP 요청마다 amqp.connect()를 호출하는 코드는 RabbitMQ에서 가장 유명한 안티패턴이다. 공식 프로덕션 체크리스트가 connection churn이라는 이름으로 명시적으로 경고한다. 연결은 앱 부팅 때 만들어 프로세스 수명 내내 재사용하고, 끊어지면 재연결한다.

i

발행자와 소비자의 커넥션도 분리 보강

브로커가 메모리 압박을 받으면 발행하는 커넥션을 블록한다(ITEM 31). 이때 소비 전용 커넥션이 따로 있으면 컨슈머는 계속 돌면서 큐를 비울 수 있다. 같은 커넥션을 공유하면 밀린 큐를 비워야 할 컨슈머까지 같이 멈춰 교착에 가까운 상황이 된다. 공식 문서도 발행/소비 커넥션 분리를 권장한다.

하트비트

죽은 TCP 연결은 양쪽 다 한동안 모른다. AMQP는 heartbeat 프레임으로 이를 감지한다. 기본값은 클라이언트와 서버가 협상하며 보통 60초다. 공식 문서는 네트워크 혼잡 시 오탐을 막기 위해 5초 미만으로 내리지 말라고 한다.

정리

  • 커넥션은 오래, 적게. 채널은 가볍게, 용도별로.
  • 컨슈머마다 채널을 따로 두고, 채널을 동시에 공유하지 않는다.
  • 발행 커넥션과 소비 커넥션을 분리하면 플로우 컨트롤 상황에서 컨슈머가 살아남는다.
ITEM 6

Exchange 네 종류

exchange는 메시지를 저장하지 않는다. 어디로 보낼지만 정한다.

핵심 exchange는 라우팅 함수다. 입력은 routing key와 헤더, 출력은 "이 메시지를 어느 큐들에 복사할 것인가"이다.

directrouting key 완전 일치작업 분배, 로그 레벨별 분리
fanout기준 없음. 바인딩된 모든 큐에 복사브로드캐스트, 캐시 무효화
topicrouting key 패턴 매칭도메인 이벤트 버스 (가장 많이 씀)
headers메시지 헤더 값 매칭 (x-match)routing key로 표현 못 하는 다차원 조건

  M["메시지 routing key = order.paid.kr"] --> D{{"direct"}}
  M --> F{{"fanout"}}
  M --> T{{"topic"}}
  D -->|"order.paid.kr 만"| DQ["정확히 일치하는 큐"]

같은 메시지, 다른 판단 — exchange 타입은 "누가 이 메시지를 받을 자격이 있나"를 정하는 규칙이다.

기본 exchange

이름이 빈 문자열("")인 direct exchange가 브로커에 미리 선언되어 있다. 모든 큐는 자동으로 자기 이름과 동일한 routing key로 여기에 바인딩된다. 그래서 sendToQueue('email', buf)가 큐 이름만으로 동작한다. 튜토리얼과 간단한 작업 큐에서는 이걸 쓰지만, 실서비스 토폴로지에서는 이름 있는 exchange를 명시적으로 선언하는 편이 낫다. 나중에 소비자를 늘릴 여지가 생긴다.

topology.ts
// durable: true 여야 브로커 재시작 후에도 exchange가 남는다.
await ch.assertExchange('user.events', 'topic', { durable: true });

// 라우팅 실패한 메시지를 흘려보낼 곳을 지정할 수도 있다 (ITEM 14)
await ch.assertExchange('order.events', 'topic', {
  durable: true,
  alternateExchange: 'unrouted',
});
i

exchange를 exchange에 묶을 수도 있다 보강

channel.bindExchange(dest, source, pattern)으로 exchange끼리 연결하는 exchange-to-exchange 바인딩이 있다. 팀별로 exchange를 나눠 놓고 상위 이벤트 버스에서 일부만 흘려보내는 계층 구조를 만들 때 쓴다. 처음에는 필요 없지만, 나중에 토폴로지가 커질 때 이런 게 있다는 걸 알면 큐를 무한정 늘리지 않게 된다.

정리

  • exchange는 저장하지 않는다. 라우팅만 한다. 갈 곳이 없으면 메시지는 그냥 버려진다.
  • 실무에서는 topic이 기본값에 가깝다. direct는 topic의 특수 케이스로 볼 수 있다.
  • 이름 없는 기본 exchange는 큐 이름 = routing key 규칙으로 동작하는 편의 장치다.
ITEM 7

Binding과 라우팅 키

라우팅 키는 주소가 아니라 메시지에 대한 설명이다.

핵심 binding은 "이 exchange의 이런 메시지는 이 큐로"라는 규칙이다. 규칙을 여러 개 걸 수 있고, 하나도 안 걸 수도 있다.

topic 와일드카드

topic exchange의 routing key는 점으로 구분된 단어들이다(최대 255바이트). 바인딩 패턴에서 두 개의 특수문자를 쓸 수 있다.

문자의미예시 패턴매칭
*정확히 한 단어order.*.krorder.paid.kr ✓ / order.kr ✗
#0개 이상의 단어order.#order ✓ / order.paid.kr ✓
bindings.ts
await ch.assertExchange('order.events', 'topic', { durable: true });

// 결제 완료만 처리하는 큐
await ch.bindQueue('invoice.issue', 'order.events', 'order.paid');

// 주문 도메인의 모든 이벤트를 적재하는 큐
await ch.bindQueue('audit.log', 'order.events', 'order.#');

// 한 큐에 규칙을 여러 개 걸 수 있다
await ch.bindQueue('alerting', 'order.events', 'order.failed');
await ch.bindQueue('alerting', 'order.events', 'payment.failed');
!

한 큐에 두 규칙이 동시에 맞으면?

메시지는 큐당 한 번만 들어간다. order.#와 *.paid가 같은 큐에 걸려 있고 order.paid 메시지가 오면, 큐에는 사본이 하나만 생긴다. 반대로 서로 다른 큐가 각각 매칭되면 큐 개수만큼 사본이 만들어진다. "큐 단위 중복은 없고, 큐 사이에는 복사"라고 기억하면 된다.

라우팅 키 네이밍

라우팅 키는 나중에 바꾸기가 아주 어렵다. 이미 남이 걸어둔 바인딩을 전부 찾아야 하기 때문이다. 처음부터 계층 구조로 잡아 두면 오래간다.

권장
<도메인>.<엔티티>.<사건>

order.payment.succeeded
order.payment.failed
user.profile.updated
inventory.stock.depleted

이렇게 두면 order.#(주문 도메인 전부), *.payment.*(모든 결제 사건), *.*.failed(모든 실패)처럼 나중에 필요한 축으로 자유롭게 잘라낼 수 있다.

정리

  • binding은 exchange와 큐 사이의 규칙이다. n:m으로 걸 수 있다.
  • *는 한 단어, #은 0개 이상 단어.
  • 같은 큐에 여러 규칙이 맞아도 사본은 하나. 다른 큐끼리는 각각 복사된다.
  • 라우팅 키는 도메인.엔티티.사건 계층으로 설계한다. 나중에 못 바꾼다.
ITEM 8

Queue의 속성과 arguments

큐 선언은 멱등하지만, 속성이 다르면 멱등이 아니라 에러다.

핵심 큐의 성격은 표준 속성 4개와 x- 접두사 인자들로 정해진다. 인자는 선언 시점에 고정되고, 나중에 바꾸려면 큐를 지워야 한다.

표준 속성

durable브로커 재시작 후에도 큐 정의가 남는가true
exclusive선언한 커넥션만 쓸 수 있고, 끊기면 삭제RPC 응답 큐 정도에만
autoDelete마지막 컨슈머가 떠나면 삭제임시 큐에만
argumentsx- 인자 맵큐 타입, TTL, DLX 등
!

durable은 큐만 살린다

durable: true는 큐라는 그릇이 재시작 후에도 존재한다는 뜻이지, 안에 든 메시지가 살아남는다는 뜻이 아니다. 메시지가 살아남으려면 발행할 때 persistent: true를 줘야 한다. 둘 다 있어야 유실을 막는다. (quorum queue와 stream은 항상 durable이라 이 고민이 사라진다.)

자주 쓰는 인자

queue.ts
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',              // classic | quorum | stream
    'x-dead-letter-exchange': 'order.dlx', // 실패/만료 시 보낼 exchange
    'x-delivery-limit': 5,                 // 재배달 5회 초과 시 dead-letter (quorum)
    'x-message-ttl': 3600000,              // 큐 안 메시지 수명 (ms)
    'x-max-length': 100000,                // 큐 길이 상한
    'x-overflow': 'reject-publish',        // 초과 시 발행 거부 (기본은 drop-head)
  },
});
×

PRECONDITION_FAILED - inequivalent arg

이미 있는 큐를 다른 인자로 assertQueue하면 이 에러와 함께 채널이 닫힌다. 큐 인자는 사후 변경이 불가능하다. 그래서 실무에서는 자주 바뀔 값(TTL, 길이 제한, DLX)을 인자 대신 policy로 거는 걸 권장한다. policy는 운영 중에 rabbitmqctl set_policy나 관리 UI로 바꿀 수 있다. 자세한 건 ITEM 29.

정리

  • durable은 큐를, persistent는 메시지를 살린다. 둘은 별개다.
  • 큐 인자는 선언 시 고정이다. 바꾸려면 큐를 지우고 다시 만들어야 한다.
  • 변할 여지가 있는 설정(TTL, DLX, 길이)은 인자보다 policy로 거는 게 안전하다.
ITEM 9

메시지의 구조

브로커는 payload를 안 본다. 대신 properties와 headers는 본다.

핵심 properties는 프로토콜이 정의한 고정 필드, headers는 내가 마음대로 넣는 맵이다. 브로커가 라우팅/만료에 쓰는 건 properties 쪽이다. 
flowchart TB
  MSG["AMQP 메시지"] --> P["properties: 프로토콜 정의 필드"]
  MSG --> H["headers: 자유 형식 맵"]
  MSG --> B["body: 그냥 바이트 배열"]
  P --> P1["deliveryMode / priority / expiration"]
  P --> P2["contentType / messageId / correlationId / replyTo / timestamp"]

payload는 작게 보강

메시지 본문에 이미지 바이너리나 거대한 JSON을 그대로 싣는 건 피한다. 브로커 메모리와 디스크를 그대로 먹고, 큐가 밀리는 순간 그 압박이 클러스터 전체로 번진다. 큰 데이터는 오브젝트 스토리지에 두고 메시지에는 키만 싣는 claim check 패턴이 정석이다. 참고로 4.3에서 32 KiB 이하 메시지의 메모리 오버헤드가 절반으로 줄었는데, 이 크기 대역을 기본 타깃으로 본다는 신호이기도 하다.

정리

  • body는 브로커에게 불투명한 바이트다. 의미 있는 정보는 properties/headers에 둔다.
  • persistent: true는 습관처럼 붙인다. 안 붙이면 재시작 때 사라진다.
  • messageId는 나중에 멱등 처리를 가능하게 하는 최소 투자다.
  • 큰 payload는 싣지 말고 참조만 보낸다.
CH 3

전달 보장: ack와 confirm

메시지를 잃지 않는 일은 브로커 혼자 못 한다. 발행 쪽 확인(publisher confirms)과 소비 쪽 확인(consumer acknowledgements)이 양쪽에서 맞물려야 한다. BullMQ가 Lua 스크립트 뒤에 숨겨 두었던 것이 여기서는 전부 내 코드로 나온다.

ITEM 10

컨슈머 ack: 자동과 수동

ack는 "받았다"가 아니라 "다 처리했다"는 뜻이다.

핵심 noAck: true는 전송한 순간 처리 완료로 간주한다. 컨슈머가 그 직후 죽으면 메시지는 그냥 사라진다.

두 가지 모드

자동 ack (noAck: true)수동 ack (기본)
확정 시점브로커가 소켓에 쓴 직후내가 ch.ack()를 부를 때
유실컨슈머 크래시 시 유실미확인 메시지는 requeue
흐름 제어prefetch가 안 먹는다prefetch로 제어
쓸 자리유실해도 되는 메트릭/로그 스트림그 외 전부

공식 문서는 자동 ack를 두고 "안전하지 않으며 모든 워크로드에 적합하지 않다"고 못박는다. 실무 기본값은 수동 ack다.

delivery tag

브로커는 배달마다 채널 범위의 단조 증가 정수를 붙인다. ack는 반드시 배달받은 그 채널에서 해야 하고, 다른 채널에서 하면 프로토콜 예외로 연결이 끊긴다. amqplib에서는 메시지 객체를 그대로 넘기므로 (ch.ack(msg)) 태그를 직접 만질 일은 드물다.

consumer.ts
await ch.consume('order.payment', async (msg) => {
  if (!msg) return;                 // 컨슈머가 취소되면 null이 온다
  try {
    await handle(JSON.parse(msg.content.toString()));
    ch.ack(msg);                    // 여기까지 와야 큐에서 지워진다
  } catch (err) {
    ch.nack(msg, false, false);     // 재큐 없이 DLX로
  }
}, { noAck: false });
i

배치 ack

ch.ack(msg, true)는 이 태그까지의 모든 미확인 배달을 한 번에 확정한다 (multiple 플래그). 처리량이 아주 높은 컨슈머에서 네트워크 왕복을 줄이는 데 쓴다. 단, 중간에 실패한 게 하나라도 있으면 그것까지 같이 ack되므로 순서대로 성공하는 파이프라인에만 쓴다.

!

ack를 안 하고 오래 버티면 최신 반영

미확인 배달에는 기본 30분의 타임아웃(consumer_timeout)이 있다. 3.x 시절에는 이걸 넘기면 채널이 PRECONDITION_FAILED로 강제로 닫히면서 그 채널의 모든 배달이 requeue됐다. 4.3부터는 이 보호가 quorum queue에 대해 큐 레벨에서 처리되고, 채널을 끊는 대신 프로토콜에 맞는 방식으로 메시지만 회수한다. 그래도 30분 넘게 걸리는 작업이라면 메시지를 즉시 ack하고 진행 상태는 애플리케이션 DB에서 관리하는 쪽이 맞다.

정리

  • 수동 ack가 기본. noAck: true는 유실해도 되는 데이터에만.
  • ack는 배달받은 채널에서만 유효하다.
  • 커넥션/채널이 끊기면 미확인 배달은 자동으로 requeue된다.
  • 기본 미확인 타임아웃 30분. 그보다 긴 작업은 설계를 바꾼다.
ITEM 11

nack, reject, 그리고 requeue의 함정

requeue: true는 대부분의 경우 무한 루프의 다른 이름이다.

핵심 실패했을 때 nack(msg, false, true)로 되돌리면, 같은 메시지가 즉시 다시 배달되어 같은 이유로 또 실패한다. 백오프가 없기 때문이다.
메서드여러 건 처리비고
ch.reject(msg, requeue)✗AMQP 표준
ch.nack(msg, allUpTo, requeue)✓RabbitMQ 확장. 실무에서는 이것만 써도 된다

requeue 플래그가 결정하는 것

flowchart LR

  D -->|"true"| Q["큐로 즉시 복귀"]
  Q --> R["같은 컨슈머가 곧바로 재수신"]
  R --> F
  D -->|"false"| X{"DLX가 설정돼 있나?"}
  X -->|"예"| DLQ["Dead Letter Exchange 로"]
  X -->|"아니오"| DROP["메시지 폐기"]
requeue: true의 위험 — 결정론적으로 실패하는 메시지(스키마 오류, 없는 참조)는 CPU를 태우는 무한 루프가 된다.

실패의 두 종류를 구분한다

error-policy.ts권장
try {
  await handle(payload);
  ch.ack(msg);
} catch (err) {
  if (err instanceof TransientError) {
    // 일시적 장애(DB 커넥션, 외부 API 5xx): 재시도할 가치가 있다.
    // 단, 즉시 requeue 대신 재시도 큐로 보낸다 (ITEM 22, 24)
    ch.nack(msg, false, false);
  } else {
    // 영구 실패(스키마 위반, 존재하지 않는 리소스): 재시도해도 결과가 같다.
    ch.nack(msg, false, false);   // 바로 DLQ로
  }
}

두 갈래 모두 requeue: false인 게 포인트다. 재시도가 필요하면 즉시 되돌리는 게 아니라 지연을 걸어 되돌린다. 그 방법이 ITEM 22와 24다.

!

requeue: true가 맞는 드문 경우

컨슈머 자신의 상태 문제로 지금 이 인스턴스는 처리할 수 없지만 다른 인스턴스는 할 수 있을 때 (예: 로컬 캐시 미준비, 셧다운 진행 중) 정도다. 이때도 요청이 몰리면 핫루프가 되므로 짧은 대기를 넣거나 컨슈머를 취소하는 편이 낫다.

정리

  • 실무에서는 nack 하나로 통일해도 된다.
  • requeue: false가 기본 전략. 재시도는 지연을 끼워서 한다.
  • requeue: false + DLX 미설정 = 조용한 메시지 폐기다. DLX는 사실상 필수.
ITEM 12

prefetch: 동시성의 진짜 손잡이

BullMQ의 concurrency에 가장 가까운 것.

핵심 prefetch는 한 컨슈머가 동시에 붙들 수 있는 미확인 메시지 수다. 이 값을 안 정하면 브로커는 큐에 있는 걸 전부 밀어 넣는다.

basic.qos(amqplib의 ch.prefetch(n))를 호출하지 않으면 기본값은 무제한이다. 컨슈머 하나가 10만 건을 통째로 받아 메모리에 쌓고, 다른 인스턴스는 놀게 된다. 수동 ack 모드에서만 의미가 있다. 

flowchart LR
  Q["Queue: 미처리 10000건"] -->|"prefetch=1"| C1["컨슈머 A: 1건 처리 중"]
  Q -->|"prefetch=1"| C2["컨슈머 B: 1건 처리 중"]
  Q -.->|"prefetch 미설정"| C3["컨슈머 C: 10000건 전부 선점"]
prefetch는 부하 분산 손잡이이기도 하다 — 값이 클수록 한 인스턴스가 많이 선점한다.
작업 성격권장 prefetch이유
건당 수 초 이상 걸리는 무거운 작업1 ~ 5공평한 분배가 처리량보다 중요
건당 수 ms 수준의 가벼운 작업100 ~ 300왕복 지연을 감추는 구간
매우 짧고 지연이 큰 네트워크더 크게단, 수확 체감이 빠르게 온다

공식 가이드도 100~300 구간을 처리량과 자원 소비의 균형점으로 제시하고, 그 이상은 수확 체감이라고 설명한다. prefetch(1)은 가장 안전하지만 지연이 큰 환경에서 처리량이 크게 떨어진다.

BullMQ concurrency와의 차이

BullMQ
new Worker('email', handler, {
  concurrency: 10,
});
// 한 워커가 최대 10개 잡을
// 동시에 실행한다.
RabbitMQ
await ch.prefetch(10);
await ch.consume(q, handler);
// 미확인 10건까지 받아둘 뿐,
// 동시 실행 여부는 내 핸들러가 정한다.

amqplib의 consume 콜백은 순차 실행을 보장하지 않는다. 콜백이 async이면 앞 건이 끝나기 전에 다음 건이 들어올 수 있다. 즉 실제 동시성은 prefetch 값이고, 이걸 넘는 동시 실행은 일어나지 않는다. 반대로 순차 처리를 원하면 prefetch를 1로 두거나 핸들러 안에서 직접 큐잉해야 한다.

i

global 플래그 보강

ch.prefetch(n, true)는 채널 전체에 걸쳐 n건으로 제한하고, 기본값(false)은 컨슈머별로 n건이다. 참고로 quorum queue는 global QoS를 지원하지 않는다. 컨슈머별 prefetch만 쓸 수 있으니, 채널 하나에 컨슈머를 여러 개 붙일 계획이면 이 점을 기억해 둔다.

정리

  • prefetch를 설정하지 않으면 무제한이다. 반드시 명시한다.
  • 무거운 작업은 1~5, 가벼운 작업은 100~300이 출발점.
  • prefetch가 사실상 컨슈머의 동시성 상한이다. 순차 보장은 prefetch=1.
  • quorum queue에서는 global QoS를 못 쓴다.
ITEM 13

퍼블리셔 컨펌

publish()가 true를 돌려줬다는 건 아무것도 보장하지 않는다.

핵심 기본 채널의 publish()는 로컬 버퍼에 썼다는 뜻일 뿐이다. 브로커가 실제로 받았는지 알려면 confirm 모드를 켜야 한다.

BullMQ에서는 await queue.add()가 Redis 응답까지 기다리기 때문에 이 고민이 없었다. AMQP의 발행은 원래 단방향(fire-and-forget)이다. 브로커가 죽어 있거나 디스크가 꽉 찼어도 클라이언트는 모른다. 그래서 RabbitMQ는 confirm.select라는 확장을 제공한다. 

sequenceDiagram
  participant P as Publisher
  participant B as Broker
  participant Q as Queue
  P->>B: confirm.select (채널을 컨펌 모드로)
  P->>B: basic.publish seq=1
  B->>Q: 라우팅 후 저장
  Q-->>B: 디스크 기록 완료
  B-->>P: basic.ack seq=1
  P->>B: basic.publish seq=2
  B-->>P: basic.nack seq=2 (내부 오류)
컨펌은 비동기다 — 발행마다 순번이 붙고, ack/nack가 순서와 무관하게 돌아온다.

라우팅 실패도 ack다

갈 큐가 하나도 없어서 메시지가 버려져도 브로커는 ack를 보낸다. "브로커가 책임지고 받았다"와 "누군가 처리할 것이다"는 다른 얘기다. 라우팅 실패를 알고 싶으면 mandatory가 필요하다 (ITEM 14).

amqplib에서 쓰기

confirm.ts
const ch = await conn.createConfirmChannel();

// 방식 1: 건별 콜백 (권장) — 옵션 객체와 콜백이 필수 인자다
ch.publish('order.events', 'order.paid', buf, { persistent: true }, (err) => {
  if (err) markForRetry(buf);   // nack 또는 채널 종료
  else markPublished(buf);
});

// 방식 2: 배치 후 한 번에 대기
for (const e of events) ch.publish('order.events', e.key, e.buf, { persistent: true });
await ch.waitForConfirms();     // 하나라도 nack면 reject

건별로 await하지 말 것

publish 하나마다 컨펌을 await하면 왕복 지연이 그대로 처리량 상한이 된다. persistent 메시지의 컨펌은 디스크 배치 기록 때문에 수백 ms까지 걸릴 수 있다고 공식 문서가 명시한다. 파이프라이닝(여러 건 발행 후 일괄 확인)이나 비동기 콜백으로 처리한다. 또한 컨펌은 발행 순서대로 오지 않을 수 있으므로 순서에 의존하는 코드를 쓰면 안 된다.

정리

  • 유실이 곤란한 발행에는 createConfirmChannel()을 쓴다.
  • ack = 브로커가 책임진다는 뜻. 처리된다는 뜻이 아니고, 라우팅 성공을 뜻하지도 않는다.
  • 건별 await는 금물. 콜백이나 waitForConfirms() 배치를 쓴다.
  • 컨펌 순서는 보장되지 않는다.
ITEM 14

라우팅 실패는 에러가 아니다

오타 하나로 메시지가 조용히 사라지는 게 RabbitMQ의 기본 동작이다.

핵심 exchange가 갈 큐를 못 찾으면 메시지는 말없이 버려진다. 이걸 막는 장치가 mandatory와 alternate-exchange다.

BullMQ에는 없는 실패 유형이다. 큐 이름을 잘못 쓰면 BullMQ는 그 이름의 큐를 그냥 만들어버리지만, RabbitMQ에서 routing key를 잘못 쓰면 아무 일도 일어나지 않는다. 로그도 없다. 신규 서비스 붙일 때 가장 많이 밟는 지뢰다.

1) mandatory + basic.return

mandatory.ts
// 반송된 메시지를 받는 핸들러를 먼저 등록한다
ch.on('return', (msg) => {
  logger.error({
    exchange: msg.fields.exchange,
    routingKey: msg.fields.routingKey,
    replyText: msg.fields.replyText,   // NO_ROUTE
  }, '라우팅 실패');
});

ch.publish('order.events', 'order.paidd', buf, {
  persistent: true,
  mandatory: true,      // 갈 큐가 없으면 되돌려 달라
});

컨펌 모드와 같이 쓰면 basic.return이 basic.ack보다 먼저 온다. 즉 "반송 이벤트가 안 왔고 ack가 왔다"면 최소한 어느 큐엔가 들어갔다는 뜻이 된다.

2) alternate exchange

exchange를 선언할 때 alternateExchange를 주면, 라우팅에 실패한 메시지를 그 exchange로 넘긴다. 여기에 unrouted 큐를 하나 걸어 두면 잃어버린 메시지가 눈에 보이는 곳에 쌓인다.

alt-exchange.ts권장
await ch.assertExchange('unrouted', 'fanout', { durable: true });
await ch.assertQueue('unrouted.bucket', { durable: true, arguments: { 'x-queue-type': 'quorum' } });
await ch.bindQueue('unrouted.bucket', 'unrouted', '');

await ch.assertExchange('order.events', 'topic', {
  durable: true,
  alternateExchange: 'unrouted',
});
✓

둘 다 쓰는 게 정답

mandatory는 발행자가 즉시 알아차리게 하고, alternate exchange는 메시지를 잃지 않게 한다. 역할이 다르니 같이 건다. unrouted.bucket의 길이에 알람을 걸어두면 새 서비스의 바인딩 누락을 배포 당일에 잡을 수 있다.

정리

  • 라우팅 실패는 예외가 아니라 정상 흐름이다. 기본은 조용한 폐기.
  • mandatory: true + channel.on('return')으로 즉시 감지.
  • exchange에 alternateExchange를 걸어 미라우팅 메시지를 모은다.
ITEM 15

at-least-once와 멱등성

중복은 버그가 아니라 사양이다.

핵심 RabbitMQ의 보장은 at-least-once다. exactly-once는 브로커가 주는 게 아니라 컨슈머가 만드는 성질이다.

중복이 생기는 자리

  1. 컨슈머가 처리는 끝냈는데 ack 직전에 죽는다

    브로커는 미확인으로 보고 다른 컨슈머에게 다시 준다. 같은 일이 두 번 실행된다.

  2. 네트워크가 끊겨 ack가 브로커에 도달하지 못한다

    결과는 위와 같다.

  3. 발행자가 컨펌을 못 받고 재발행한다

    브로커는 이미 받았을 수 있다. 같은 메시지가 두 벌 생긴다.

redelivered 플래그(msg.fields.redelivered)가 true면 재배달이지만, 이걸 중복 판정 기준으로 쓰면 안 된다. 첫 배달에도 중복일 수 있고(3번 케이스), 재배달이어도 앞 시도가 아무것도 안 했을 수 있다.

컨슈머를 멱등하게 만드는 세 가지 방법

방법구현적합한 곳
자연 멱등UPDATE ... SET status='paid'처럼 몇 번 해도 같은 결과가 되게 쓴다가능하면 항상 1순위
처리 기록 테이블messageId에 유니크 제약을 건 테이블에 먼저 insert. 중복이면 스킵부작용이 있는 처리
조건부 갱신버전/상태를 조건으로 건 업데이트. 영향 행이 0이면 이미 처리된 것상태 머신이 있는 도메인
idempotent-consumer.ts권장

  // messageId 에 UNIQUE 제약. 이미 있으면 여기서 걸린다.
  const inserted = await tx.insertProcessed(msg.properties.messageId);
  if (!inserted) return;              // 이미 처리한 메시지

  await tx.applyBusinessChange(payload);
});
ch.ack(msg);
!

"exactly once"라는 표현에 속지 않기

BullMQ 문서도 exactly-once 시맨틱을 말하지만 엣지 케이스에서는 at-least-once임을 함께 밝힌다. 분산 시스템에서 진짜 exactly-once 전달은 불가능하고, 실제로 가능한 건 언제나 at-least-once 전달 + 멱등한 처리다. 이건 브로커를 바꿔도 달라지지 않는 성질이다.

정리

  • 중복은 반드시 온다. 컨슈머를 멱등하게 짜는 것 외에 답이 없다.
  • redelivered 플래그는 힌트일 뿐 중복 판정 근거가 아니다.
  • messageId + 유니크 제약 + 트랜잭션이 가장 무난한 구현이다.
CH 4

CH 5

실패, 재시도, 지연

BullMQ의 attempts와 backoff가 한 줄이었다면, RabbitMQ에서는 그 한 줄이 토폴로지 설계가 된다. 대신 어떤 메시지가 왜 몇 번 실패했는지가 전부 눈에 보인다.

ITEM 20

DLX: 실패한 메시지의 종착지

BullMQ의 failed 셋에 해당하지만, 이건 진짜 큐다.

핵심 dead letter exchange는 특별한 종류의 exchange가 아니다. 그냥 평범한 exchange인데, 큐가 "여기로 버려라"고 지목했을 뿐이다.

메시지가 dead-letter되는 네 가지 경우

  1. 컨슈머가 requeue 없이 거절

    basic.reject 또는 basic.nack에 requeue=false. 가장 흔한 경로.

  2. 메시지 TTL 만료

    메시지별 expiration 또는 큐의 x-message-ttl이 지났을 때.

  3. 큐 길이 초과

    x-max-length/x-max-length-bytes를 넘겨 밀려난 메시지.

  4. 재배달 한도 초과

    quorum queue의 x-delivery-limit을 넘었을 때.

!

큐 자체가 만료되면 dead-letter되지 않는다

x-expires로 큐가 통째로 사라지는 경우, 안에 있던 메시지는 DLX로 가지 않고 그냥 없어진다. 헷갈리기 쉬운 예외다.

구성

dlx.ts
// 1) DLX 와 DLQ 를 먼저 만든다
await ch.assertExchange('order.dlx', 'topic', { durable: true });
await ch.assertQueue('order.payment.dlq', {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});
await ch.bindQueue('order.payment.dlq', 'order.dlx', 'order.payment');

// 2) 업무 큐가 그 DLX 를 지목한다
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-dead-letter-exchange': 'order.dlx',
    'x-dead-letter-routing-key': 'order.payment',  // 생략하면 원래 routing key 유지
  },
});

dead-letter된 메시지에는 x-death 헤더가 붙는다. 어느 큐에서, 왜, 몇 번, 언제 버려졌는지가 배열로 쌓이고 최신 항목이 앞에 온다.

i

DLX로 가는 길에도 유실이 있다 보강

기본 dead lettering은 퍼블리셔 컨펌 없이 재발행한다(at-most-once). 클러스터 상황에 따라 DLQ에 도착하지 못할 수 있다. quorum queue라면 policy로 dead-letter-strategy: at-least-once를 걸어 내부 컨펌을 켤 수 있는데, overflow: reject-publish가 함께 필요하다. 결제/정산처럼 실패 기록조차 잃으면 안 되는 큐에는 이 조합을 쓴다.

정리

  • DLX는 평범한 exchange다. 큐가 x-dead-letter-exchange로 지목할 뿐.
  • 거절/TTL만료/길이초과/재배달한도 네 가지가 dead-letter를 유발한다. 큐 만료는 아니다.
  • x-death의 reason과 count가 사후 분석의 핵심 자료다.
  • 중요한 큐라면 dead-letter-strategy: at-least-once를 검토한다.

4.3: 명시적 return은 횟수에 안 센다 최신 반영

4.3부터 한도 판정 기준이 acquired-count가 아니라 delivery-count로 바뀌었다. 컨슈머가 "지금은 내가 못 하니 다른 데 줘"라고 명시적으로 되돌리는 경우는 무제한으로 허용되고, 실제 실패로 인한 재배달만 한도에 반영된다. 셧다운 중 메시지를 되돌리는 패턴을 쓸 때 이 차이가 크다.

!

classic queue에는 이 기능이 없다

classic queue를 쓴다면 재시도 횟수를 직접 세야 한다. 보통 x-death의 count를 읽거나, 커스텀 헤더에 시도 횟수를 담아 재발행하는 식으로 구현한다. quorum queue를 기본으로 두라는 권고에는 이 이유도 있다.

정리

  • quorum queue의 x-delivery-limit이 무한 재시도를 막는 안전장치다. 기본 20.
  • 한도를 넘으면 DLX로 간다. DLX가 없으면 그냥 버려진다.
  • 한도는 큐 단위다. 메시지별 재시도 횟수 차등은 애플리케이션에서 구현한다.
ITEM 22

지연 재시도: 4.3의 백오프

드디어 브로커가 백오프를 해준다. 단, 선형이다.

핵심 RabbitMQ 4.3부터 quorum queue는 재시도에 지연을 넣을 수 있다. 실패한 메시지를 큐 내부에 잠시 치워 뒀다가 시간이 지나면 다시 배달 가능 상태로 만든다.
delayed-retry.ts
await ch.assertQueue('order.payment', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-delayed-retry-type': 'failed',   // disabled | all | returned | failed
    'x-delayed-retry-min': 5000,        // 최소 지연 5초
    'x-delayed-retry-max': 60000,       // 최대 지연 60초
    'x-delivery-limit': 8,
    'x-dead-letter-exchange': 'order.dlx',
  },
});

4.2 이하라면 못 쓴다

이 기능은 4.3에서 추가됐고 quorum queue 전용이다. 이직할 회사의 브로커 버전을 먼저 확인하자. 4.2 이하이거나 classic queue를 쓴다면 ITEM 23~24의 TTL+DLX 방식으로 직접 만들어야 한다.

정리

  • 4.3 + quorum queue에서는 백오프 재시도가 큐 인자 세 개로 끝난다.
  • 지연은 선형이다. min × 시도횟수, 상한은 max.
  • 재시도 큐를 따로 만들 필요가 없어서 토폴로지가 훨씬 단순해진다.
  • 4.2 이하라면 이 기능이 없다. 버전 확인이 먼저다.

지연 메시지: TTL+DLX와 플러그인의 종말

delayed message exchange 플러그인은 끝났다 주의

검색하면 반드시 나오는 rabbitmq_delayed_message_exchange(x-delayed-message exchange 타입 + x-delay 헤더)는 2026년 4월 16일 저장소가 아카이브됐다. Mnesia에 의존했는데 Mnesia가 4.3에서 완전히 제거되면서 4.3 이상 오픈소스 버전에서는 로드되지 않는다. 원래도 "지연 메시지를 단일 노드 테이블에 저장하므로 그 노드가 죽으면 전부 유실"되고 대량 사용에 부적합하다는 경고가 붙어 있던 물건이다. 새 코드에서 이 경로를 택하지 않는다.

메시지별 TTL을 섞으면 머리에서 막힌다

큐는 FIFO다. 메시지마다 expiration을 다르게 줘서 한 큐에 넣으면, 맨 앞 메시지의 TTL이 끝나야 그 뒤가 검사된다. 60초짜리가 앞에 있으면 뒤의 5초짜리는 60초를 기다린다. 그래서 지연 큐는 delay.5s, delay.30s, delay.5m처럼 지연 단계별로 큐를 따로 만들고 큐 인자 x-message-ttl로 고정하는 게 정석이다.

긴 지연은 브로커에 맡기지 않는다 보강

"3일 뒤 리마인드", "한 달 뒤 구독 갱신" 같은 건 메시지 브로커의 일이 아니다. DB 테이블에 실행 시각을 저장하고 스케줄러가 그 시각에 메시지를 발행하는 구조가 맞다. 브로커의 지연 패턴은 초~시간 단위 재시도까지가 적정선이다.

정리

  • 지연 발행은 네이티브 기능이 아니다. TTL 만료 → DLX 흐름으로 만든다.
  • 지연 플러그인은 아카이브됐고 4.3에서 못 쓴다. 새로 쓰지 않는다.
  • 지연 큐는 단계별로 분리한다. 한 큐에 여러 TTL을 섞으면 head-of-line 블로킹이 생긴다.
  • 일 단위 이상 지연은 DB + 스케줄러로 뺀다.

retry-router.ts
const LEVELS = [10, 60, 300];   // 초 단위 재시도 단계

function onFailure(ch, msg) {
  const attempt = Number(msg.properties.headers?.attempt ?? 0);
  if (attempt >= LEVELS.length) {
    ch.nack(msg, false, false);            // DLX 로 보낸다
    return;
  }
  ch.publish('retry.exchange', `retry.${LEVELS[attempt]}s`, msg.content, {
    ...msg.properties,
    headers: { ...msg.properties.headers, attempt: attempt + 1 },
    persistent: true,
  });
  ch.ack(msg);                             // 원본은 확정 처리
}

"재발행 후 ack"의 위험

위 코드는 재발행이 성공한 뒤 원본을 ack한다. 하지만 재발행과 ack 사이에 프로세스가 죽으면 원본이 requeue되어 메시지가 두 벌이 된다. 그래서 발행에는 컨펌 채널을 쓰고, 컨슈머는 어차피 멱등해야 한다(ITEM 15). 이 복잡도가 싫으면 그게 바로 패턴 A를 쓸 이유다.

DLQ 이후를 반드시 설계한다

  • 알람. DLQ 메시지 수에 임계값을 걸어 둔다. 아무도 안 보는 DLQ는 그냥 쓰레기통이다.
  • 재투입 경로. 원인을 고친 뒤 DLQ → 업무 큐로 되돌리는 스크립트나 관리 화면을 미리 만든다. shovel 플러그인으로 큐 사이 이동을 걸 수도 있다.
  • 보존. DLQ에 x-max-length를 걸어 무한정 쌓이지 않게 한다.

정리

  • 4.3 + quorum이면 재시도는 큐 인자만으로 끝난다. 이걸 1순위로 검토한다.
  • 안 되면 재시도 큐를 지연 단계별로 만들고 헤더로 시도 횟수를 관리한다.
  • 재발행 방식은 중복 위험이 있다. 컨펌 + 멱등 컨슈머가 전제다.
  • DLQ에 알람과 재투입 경로가 없으면 DLQ를 만든 의미가 없다.

amqplib에 자동 복구가 생겼다 최신 반영

오랫동안 amqplib의 대표적인 불편함은 "자동 재연결이 없다"는 것이었고, 그래서 amqp-connection-manager 같은 래퍼를 얹는 게 관행이었다. 하지만 1.1.0에서 opt-in 커넥션 복구가 들어갔고, 1.2.0부터는 타입 정의도 패키지에 번들되어 @types/amqplib이 더 이상 필요 없다. 현재 최신은 2.0.1이다. 회사 코드가 0.10.x 대라면 이 기능이 없으니, package.json의 버전부터 확인하자.

1) 복구를 켜는 방식 (amqplib 1.1.0+)

'error' 핸들러를 빼먹으면

amqplib의 Connection과 Channel은 EventEmitter다. Node.js에서 핸들러 없는 'error' 이벤트는 예외를 던져 프로세스를 종료시킨다. 브로커가 잠깐 재시작했을 뿐인데 앱 전체가 죽는 사고가 여기서 나온다. 커넥션과 모든 채널에 'error'와 'close'를 건다.

재연결 후 반드시 다시 해야 하는 것

  1. 채널을 새로 연다

    옛 채널 객체는 무효다. 참조를 들고 있으면 안 된다.

  2. prefetch를 다시 설정한다

    채널 단위 설정이므로 새 채널에는 안 걸려 있다.

  3. 토폴로지를 다시 선언한다

    assertExchange/assertQueue/bindQueue는 멱등하므로 매번 호출해도 안전하다.

  4. 컨슈머를 다시 등록한다

    consume은 채널에 붙어 있던 것이라 같이 사라진다.

!

채널 하나를 전역으로 돌려쓰지 않기

채널은 하나만 잘못돼도 통째로 닫힌다. 예를 들어 없는 exchange에 발행하거나 인자가 다른 assertQueue를 호출하면 그 채널이 죽는다. 전역 채널 하나를 공유하고 있었다면 모든 발행과 소비가 동시에 멈춘다. 용도별로 채널을 나누는 진짜 이유가 이것이다.

i

대안 라이브러리 보강

rabbitmq-client는 자동 재연결, TypeScript 지원, Consumer/Publisher/RPCClient 추상화를 기본 제공하고 의존성이 없다. 성능은 amqplib과 비슷하다. 다만 회사 코드가 amqplib이라면 라이브러리를 바꾸자고 하기 전에 위의 recovery 옵션을 켜는 쪽이 훨씬 싼 개선이다.

정리

  • amqplib 1.1.0+는 recovery 옵션으로 자동 재연결을 제공한다. 기본은 꺼져 있다.
  • setup 콜백에서 채널/prefetch/토폴로지/컨슈머를 전부 다시 세운다.
  • 'error' 핸들러 누락은 프로세스 종료로 이어진다.
  • connection_name을 채워두면 관리 UI에서 누가 붙었는지 보인다.

  const { consumerTag } = await ch.consume('order.payment', async (msg) => {
    if (msg === null) return;                  // 컨슈머가 취소됨

    const attempt = Number(msg.properties.headers?.['x-delivery-count'] ?? 0) + 1;
    try {
      const payload = JSON.parse(msg.content.toString());
      await handlePayment(payload, { messageId: msg.properties.messageId });
      ch.ack(msg);
    } catch (err) {
      logger.error({ err, attempt, messageId: msg.properties.messageId }, '처리 실패');
      ch.nack(msg, false, false);              // 재시도/DLX 는 브로커가 판단
    }
  }, { noAck: false });

  return { ch, consumerTag };
}

지점왜 이렇게 하나
msg === null 체크컨슈머가 취소되면 콜백이 null로 한 번 불린다
prefetch를 consume보다 먼저나중에 걸면 이미 밀려든 메시지에는 안 먹는다
핸들러 전체를 try로 감쌈JSON.parse 실패도 잡아야 한다. 안 잡으면 unhandled rejection
requeue: false즉시 재큐는 핫루프. 재시도 정책은 큐 설정에 맡긴다
ack/nack가 모든 경로에 정확히 한 번빠지면 메시지가 미확인으로 남아 prefetch를 잠식한다
×

가장 흔한 버그: ack 누락

if (조건) return;처럼 중간에서 빠져나가는 분기에서 ack를 안 하면, 그 메시지는 영원히 미확인 상태로 남는다. prefetch 20이면 이런 게 20건 쌓이는 순간 컨슈머가 완전히 멈춘다. 관리 UI의 Unacked 수치가 계속 오르고 안 내려간다면 거의 이 문제다.

i

중복 처리 방어는 별도로 보강

위 템플릿은 전달 보장까지만 다룬다. handlePayment 안에서 messageId 기반 멱등 처리(ITEM 15)를 반드시 함께 구현한다. RabbitMQ는 at-least-once이므로 이 방어가 없으면 네트워크가 한 번 흔들릴 때 결제가 두 번 잡힐 수 있다.

정리

  • 모든 경로에서 ack 또는 nack가 정확히 한 번 일어나야 한다.
  • prefetch는 consume 전에, 채널을 열 때마다.
  • 핸들러 전체를 try로 감싼다. 파싱 실패도 실패다.
  • Unacked가 안 줄면 ack 누락을 먼저 의심한다.
ITEM 27

퍼블리셔 템플릿

발행이 성공했다는 걸 알아야 트랜잭션을 닫을 수 있다.

publisher.ts기본형
let pubCh: amqp.ConfirmChannel | null = null;

async function getPublishChannel() {
  if (pubCh) return pubCh;
  const conn = await getConnection();
  pubCh = await conn.createConfirmChannel();
  pubCh.on('error', (err) => logger.error({ err }, 'publish channel error'));
  pubCh.on('close', () => { pubCh = null; });
  pubCh.on('return', (msg) => {
    logger.error({ routingKey: msg.fields.routingKey }, 'NO_ROUTE: 바인딩 누락 의심');
  });
  return pubCh;
}

export function publishEvent(routingKey: string, payload: unknown, messageId: string) {
  return new Promise<void>(async (resolve, reject) => {
    const ch = await getPublishChannel();
    ch.publish(
      'order.events',
      routingKey,
      Buffer.from(JSON.stringify(payload)),
      {
        persistent: true,
        mandatory: true,
        contentType: 'application/json',
        messageId,
        timestamp: Date.now(),
      },
      (err) => (err ? reject(err) : resolve()),
    );
  });
}
!

DB 커밋과 발행 사이의 틈

"DB에 저장하고 이벤트를 발행한다"는 코드는 두 개의 원자적 연산이다. 커밋 직후 프로세스가 죽으면 DB에는 남고 이벤트는 안 나간다. 반대 순서면 이벤트만 나가고 DB에는 없다. RabbitMQ에는 이걸 해결할 기능이 없다.

정석은 transactional outbox다. 같은 트랜잭션 안에서 outbox 테이블에 이벤트를 INSERT하고, 별도 워커가 그 테이블을 읽어 발행한 뒤 발행 완료 표시를 한다. 발행이 두 번 될 수는 있어도 누락되지는 않는다. 그래서 컨슈머 멱등성이 다시 전제가 된다.

×

AMQP 트랜잭션(tx.select)은 답이 아니다

AMQP에는 채널 트랜잭션이 있지만 느리고, DB 트랜잭션과 묶이지도 않는다. 실무에서는 거의 쓰지 않는다. 발행 신뢰성은 퍼블리셔 컨펌 + outbox로 푼다.

배치 발행

batch.ts
const ch = await getPublishChannel();
for (const e of events) {
  ch.publish('order.events', e.key, e.buf, { persistent: true, messageId: e.id });
}
await ch.waitForConfirms();   // 전부 확인될 때까지. 하나라도 nack 면 throw
await markAllPublished(events);

정리

  • 발행 채널은 createConfirmChannel()로, 'return' 핸들러까지 함께 건다.
  • persistent + mandatory + messageId는 기본 세트.
  • DB와 발행의 원자성은 outbox 패턴으로 푼다. AMQP 트랜잭션은 쓰지 않는다.
  • 대량 발행은 waitForConfirms() 배치로.
ITEM 28

Graceful shutdown

배포할 때마다 메시지가 재처리된다면 이 코드가 없는 것이다.

핵심 종료 순서는 컨슈머 취소 → 진행 중인 작업 완료 → 채널 닫기 → 커넥션 닫기다. 순서를 지키지 않으면 미확인 메시지가 requeue되어 중복 처리된다.
shutdown.ts
const inFlight = new Set<Promise<void>>();

async function shutdown() {
  closing = true;

  // 1) 새 메시지 수신을 멈춘다. 이미 받은 건 계속 처리된다.
  await ch.cancel(consumerTag);

  // 2) 진행 중인 처리를 기다린다 (타임아웃 포함)
  await Promise.race([
    Promise.allSettled([...inFlight]),
    new Promise((r) => setTimeout(r, 25_000)),
  ]);

  // 3) 채널 → 커넥션 순으로 닫는다
  await ch.close();
  await conn.close();
  process.exit(0);
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
flowchart LR
  S["SIGTERM 수신"] --> A["ch.cancel: 새 배달 중단"]
  A --> B["진행 중 작업 완료 대기"]
  B --> C["ch.close"]
  C --> D["conn.close"]
  D --> E["프로세스 종료"]
  S -.->|"이 단계를 건너뛰면"| X["미확인 메시지가 전부 requeue 되어 중복 처리"]
순서가 곧 정확성 — cancel 없이 커넥션을 닫으면 처리 중이던 메시지가 통째로 되돌아간다.
i

쿠버네티스라면 보강

terminationGracePeriodSeconds가 위의 대기 시간보다 커야 한다. 기본값은 30초라서 25초 대기를 두면 빠듯하다. 처리 시간이 긴 컨슈머라면 grace period를 늘리고, 그래도 부족하면 애초에 메시지를 먼저 ack하고 진행 상태를 DB로 관리하는 구조로 바꾸는 게 맞다.

정리

  • cancel → 대기 → close 순서를 지킨다.
  • 이 코드가 없으면 배포할 때마다 prefetch 개수만큼 중복 처리가 발생한다.
  • grace period와 대기 시간을 함께 맞춘다.
ITEM 29

토폴로지는 누가 선언하나

앱이 assertQueue를 부르는 게 항상 정답은 아니다.

핵심 큐 인자는 선언 시 고정이므로, 앱 코드에 박아 두면 설정을 바꿀 때마다 배포가 필요하고 그마저도 실패한다. 자주 바뀌는 값은 policy로 뺀다.
방식장점단점

policy운영 중 무중단 변경 가능policy로 설정 가능한 항목만

인자 대신 policy로 빼면 좋은 것들

policy.sh

  • 같은 항목이 인자와 policy에 둘 다 있으면 인자가 이긴다.
  • 선언은 앱, 운영 파라미터는 policy가 무난한 분담이다.

ITEM 34

BullMQ 기능별 RabbitMQ 구현법

"이거 BullMQ에선 한 줄이었는데"를 만날 때 펴 보는 장.

1. 재시도 3회 + 백오프

BullMQ

  attempts: 3,

2. 5분 뒤 실행

TTL 300초짜리 지연 큐를 만들고 DLX를 업무 exchange로 지정한 뒤 그 큐로 발행한다(ITEM 23). 지연 값이 여러 개면 값마다 큐를 따로 만든다. 일 단위 이상이면 DB + 스케줄러로 뺀다.

3. 레이트 리밋 (외부 API 초당 10회)

브로커에는 없다. 컨슈머 쪽에서 만든다. 가장 단순한 방법은 prefetch를 낮추고 처리에 인위적 간격을 두는 것이고, 정확한 제어가 필요하면 Redis 기반 토큰 버킷을 컨슈머 앞에 두거나 이 구간만 BullMQ를 유지하는 게 현실적이다.

4. 크론 / 반복 작업

RabbitMQ에 스케줄러는 없다. 쿠버네티스 CronJob, 애플리케이션 내 스케줄러, 또는 BullMQ의 repeatable job이 메시지를 발행하게 한다. 브로커는 배달만 한다.

5. 잡 결과 받아오기 (RPC)

rpc.ts
// 요청자: 응답 전용 임시 큐를 만들고 replyTo/correlationId 로 짝을 맞춘다
const { queue: replyTo } = await ch.assertQueue('', { exclusive: true });
const correlationId = randomUUID();

await ch.consume(replyTo, (msg) => {
  if (msg?.properties.correlationId === correlationId) resolve(msg.content);
}, { noAck: true });

ch.sendToQueue('rpc.calc', payload, { replyTo, correlationId });
!

RPC는 최후의 수단

메시지 브로커로 동기 요청-응답을 흉내 내면 브로커 장애가 곧 API 장애가 되고, 타임아웃과 응답 큐 정리를 전부 직접 관리해야 한다. 정말 응답이 필요하면 HTTP/gRPC를 쓰고, 브로커는 비동기 흐름에 쓰는 게 낫다.

6. 진행률 표시

대응물이 없다. 컨슈머가 애플리케이션 DB나 Redis에 진행률을 쓰고, 프런트가 그걸 폴링하거나 SSE로 받는다. 브로커를 경유시키지 않는다.

7. 부모-자식 작업 (Flow)

없다. 여러 단계를 엮어야 하면 각 단계가 다음 단계 이벤트를 발행하는 코레오그래피로 풀거나, 상태를 들고 있는 오케스트레이터(사가) 서비스를 둔다. 이 지점은 BullMQ가 확실히 편하다.

✓

마지막 조언

RabbitMQ를 BullMQ 대체재로 보면 계속 불편하다. 잡 관리 도구가 아니라 서비스 사이의 배관으로 보는 순간 설계가 자연스러워진다. 배관은 라우팅과 유실 방지에 집중하고, 잡 관리가 필요한 자리에는 여전히 BullMQ를 써도 된다. 두 개를 겹쳐 쓰는 건 타협이 아니라 각자 잘하는 일을 시키는 것이다.

정리

  • 재시도/백오프/우선순위/DLQ는 RabbitMQ 4.3에서 브로커 설정으로 해결된다.
  • 지연, 레이트 리밋, 크론, 진행률, 잡 의존성은 내가 만들거나 다른 도구로 푼다.
  • RPC는 가능하지만 권장하지 않는다.
  • 브로커는 배관, 잡 관리는 별개 층. 이 구분이 설계의 출발점이다.
