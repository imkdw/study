Evaluations 101

왜 평가가 필요한지, 그리고 평가의 구성 요소와 채점 방식을 배웁니다.

원본: 01_intro_to_evals.ipynb

레슨

LLM 애플리케이션 개발에서 모델 성능을 측정하지 못하는 것이 프로덕션 도입의 가장 큰 장벽이라는 말이 있습니다. 평가(evals) 없이 프롬프팅은 과학이 아니라 예술이 됩니다. evals는 앞에서 시간을 들이면 장기적으로 개발 시간을 절약해 줍니다.

벤치마크 vs 고객 평가

모델 벤치마크(MMLU, ARC, TruthfulQA 등)는 AI 세계의 표준 시험입니다. 모델의 일반적 능력을 비교하는 데는 좋지만, 내 특정 태스크에서 얼마나 잘하는지는 알려주지 않습니다. IQ 점수가 그 사람이 특정 직무에 맞는지 말해주지 않는 것과 같습니다.

프롬프트 평가(prompt evals / customer evals)는 내 유스케이스에서 모델+프롬프트 조합이 얼마나 잘 동작하는지 측정하는 체계적 테스트입니다.

평가의 이점

  • 반복적 프롬프트 개선: 프롬프트 v2가 v1보다 나은가?
  • 품질 보증: 최신 프롬프트 변경이 회귀를 일으켰는가?
  • 객관적 모델 비교: 최신 모델로 바꿔도 성능이 유지되는가?
  • 비용 절감: 더 싸고 빠른 모델로 바꿔도 성능이 유지되는가?

평가 루프

  1. 테스트 케이스 개발
  2. 프롬프트 초안 작성
  3. 테스트 케이스로 실행해 기준 점수(baseline) 측정
  4. 프롬프트 수정 → 재측정 → 반복

평가의 4가지 구성 요소

요소설명
Example Input모델에 주는 입력. 실제 운영 입력을 대표해야 함
Golden Answer정답/이상적 응답. 도메인 전문가의 검토가 필요할 수 있음
Model Output모델이 실제로 생성한 응답
Score성능을 나타내는 정량/정성 값
데이터셋 크기

일반적으로 최소 100개의 입력/정답 쌍을 권장합니다. 이 코스의 실습은 비용 때문에 더 작은 세트를 사용하지만, 실제 프로덕션에서는 규모를 키워야 통계적으로 의미 있는 결과가 나옵니다.

평가 데이터셋 예시 (고객 불만 분류):

const evalData = [
  { complaint: "The app crashes every time I try to upload a photo",
    goldenAnswer: ["Software Bug"] },
  { complaint: "My printer isn't recognized by my computer",
    goldenAnswer: ["Hardware Malfunction"] },
  { complaint: "I can't figure out how to change my password",
    goldenAnswer: ["User Error"] },
];

채점(grading) 방식 3가지

1. 사람 채점 (Human-based)

미묘한 판단이 필요한 태스크의 황금 표준. 전문가 리뷰(의료/법률 도메인), UX 패널 등. 정확하지만 느리고 비싸며 채점자 간 일관성 문제가 있습니다.

2. 코드 채점 (Code-based)

명확하고 객관적인 기준이 있을 때 적합. 빠르고 확장 가능하지만 주관적/미묘한 응답은 다루기 어렵습니다.

  • 정확한 문자열 일치: 출력이 정답과 정확히 동일 ("파리")
  • 키워드 존재 여부: 필수 단어 포함 확인
  • 정규식: 복잡한 패턴 매칭 (\d{3} 같은)

3. LLM 채점 (Model-based)

다른(또는 같은) LLM이 출력을 평가. 코드 채점보다 주관적 기준을 다룰 수 있고 사람 채점보다 빠르고 확장 가능. 단, 채점 프롬프트 자체가 잘 설계되어야 하고 채점 모델의 편향 가능성이 있습니다.

  • 요약 품질: 이 요약이 간결하고 정확한가?
  • 톤 평가: 브랜드 가이드라인/어조를 따르는가?
  • 커스텀 루브릭: 사과 표현이 있는가? 경쟁사를 언급하는가?
